# Units A1 and A2 — the approval card owns focus, its keys work, and it names them

**Two charter units are one plan, and the click affordance is not in it.** The v0.3 orchestration charter lists A1 and A2 separately and itself notes that A2 "belongs to spine B as much as to spine A" (`docs/plans/2026-08-11-v0-3-orchestration-charter.md:88-91`). They are one change to one widget on one code path — an approval card that takes focus when it mounts, whose advertised keys do what the card says they do, and which names every key that does something. Planning them apart would produce two plans editing the same mount path in `talaria/ui/prompts.py:1118-1173`. This document plans them together and says so. The charter's A1 originally paired the focus-owning card with "a visible click affordance… a clickable jump control rather than an advertised keystroke" (`:85-86`). That half is removed by operator decision made 2026-08-12, because it depended on unit A3 — the mis-aimed mouse — which needs a hand-driven capture and is now out of this release. The keyboard path ships; the mouse path does not. Where a click would later belong, one sentence names it.

The operator defect that drives this work is recorded in [the hands-on notes](../analysis/2026-08-10-v0-2-hands-on-notes.md), notes 8 and 9 (`:262-306`, `:592-623`): an approval card seen for the first time outside a test, on macOS, could only be answered with the mouse, the cursor was not focused inside the card, and the two keys the card advertises did nothing in the state the operator was actually in.

> its pretty cramped and needs some UX consideration. I can only select with the mouse, the cursor is not focused inside the approval card

and, tested live:

> escape does not work

The note's own diagnosis traces the cause to one line, quoted exactly:

`if focus_new and isinstance(card.action_widget, Input): card.focus_answer()` (`talaria/ui/prompts.py:1171`)

and states the chain that follows: an approval card is button-backed, so it never auto-focuses; it is reachable by keyboard only through the `F1` jump; `F1` is intercepted by macOS and never reaches the application (`hands-on notes:603-606`), and therefore on macOS an approval card is keyboard-unreachable. The card meanwhile prints `"enter select · esc decline"` (`talaria/ui/prompts.py:222`, `CHOICE_HINT: Final[str] = "enter select · esc decline"`) and, with focus sitting in the composer, neither `enter` nor `esc` reaches the card.

## The requirement the card serves

v0.2's answerability spine is R1 and R3, as re-stated in the v0.3 charter's spine A (`:81-91`): an outstanding prompt must be answerable where the operator's hands already are, and a prompt that can be declined must be declinable by a key. The card that carries that requirement is `PromptCard` (`talaria/ui/prompts.py:604-945`), and the control it offers for an approval is a row of `Button` widgets (`:822-838`), not an `Input`. The decision that settles the scheme is D9 in [the decision log](2026-08-11-v0-3-decision-log.md:162-181): "the card takes focus when it mounts and names its keys, and clickable controls layer on top where a control is a genuine target." This plan implements that decision, it does not re-open which scheme wins, and it keeps the clickable half as one sentence naming where it would later belong.

## Mechanism — verified by reading, at `main` = `d56eb09`

All `file:line` below were opened in this worktree on the branch `docs/v0-3-unit-a1-a2`, whose base is `d56eb09` — the commit that merged unit B1.

**The card and its hint.** `PromptCard` is a `Vertical` with a bordered title (`talaria/ui/prompts.py:633-667`). Its `DEFAULT_CSS` tints the whole card when a descendant holds focus (`:664-666`, `PromptCard:focus-within { background: $accent 20%; }`), which is R2's visible focus for a card — the second of two in the product (the other is `AgentRow.-interruptible:focus` in `talaria/ui/agents.py:127-128`). The hint line under a button-backed approval is the static constant `CHOICE_HINT` (`:222`), rendered at `:838` as `Static(literal_text(CHOICE_HINT), markup=False, classes="prompt--hint")`. The deny-all-only card uses `DENY_ALL_HINT: Final[str] = "enter deny all"` (`:237`), rendered at `:816`. An input-backed card (a `clarify`, `secret`, or `sudo` with no gateway-offered choices) uses `ANSWER_HINT: Final[str] = "enter send · esc decline"` (`:228`), rendered at `:849`, and its `Input` carries the placeholder `"answer · Enter sends"` (`:842`). Each hint is rendered with `markup=False` through `literal_text`, so the keys are literal text, not markup.

**The binding that the hint names.** `PromptCard.BINDINGS` (`:681-683`) binds `escape` to `decline` with `show=False`:

`Binding("escape", "decline", "decline", show=False)` (`:682`)

`show=False` because the card already names the key on its own hint line, where the operator is looking when the control is in front of them. `action_decline` (`:886-922`) checks `decline_value(self.row.kind)` (`:917`) and, for an unanswerable card, posts `DeclineRefused` instead of `Declined` (`:919-920`), which is the surface that makes a refused escape distinguishable from a dead one. `enter` is not a `Binding` on the card at all — a focused `Button` activates on `enter` through the framework's own button dispatch, and a focused `Input` submits on `enter` through `on_input_submitted` (`:936-944`). The hint therefore names one framework key (`enter`) and one card binding (`esc`), and both are reachable only when the card's own control holds focus, because Textual resolves a key against `focused.ancestors_with_self` (`prompts.py:671-677`).

**The present auto-focus, and why it never reaches an approval.** `PromptRegion.apply` (`:1118-1189`) reconciles cards by `request_id`, mounts each new `PromptCard` at an explicit position (`:1159-1161`), and, at `:1171-1172`, conditionally hands it the caret:

`if focus_new and isinstance(card.action_widget, Input): card.focus_answer()` (`:1171-1172`)

`focus_new` is the caller's answer to "is the operator in the middle of something", and the application passes `not self.composer.text.strip()` (`talaria/ui/app.py:1394` via the call site that feeds `apply`). An input-backed card keeps this auto-focus. A button-backed card — every approval, every multiple-choice clarify, and the deny-all-only card — is `Horizontal` of `Button` (`:822-838`), so `isinstance(card.action_widget, Input)` is false and the call is never made. The comment directly above states the consequence in as many words (`:1169-1170`): "every other kind is reachable exclusively through the jump."

`focus_answer` itself (`:866-884`) already handles both kinds: if `self._input is not None` it focuses the `Input`, otherwise it walks `self.query(Button)` and focuses the first one, which is the first choice in gateway order. The extension for button-backed cards was made for the `F1` jump (KTD1 at `:874-877`), but the guard at `:1171` never calls it for them on mount.

**The deliberate jump that is the only keyboard path today.** `PromptRegion.focus_first_unanswered` (`:995-1017`) jumps to the oldest outstanding card's control in mount order, scrolling it into view and calling `focus_answer`. The application exposes it as `action_jump_to_prompt` (`talaria/ui/app.py:1469-1486`), bound to `F1` with `priority=True` (`:825`, `Binding("f1", "jump_to_prompt", ... priority=True)`). The jump is deliberate (KTD1 at `prompts.py:1006-1008`) and is allowed to move the caret even mid-word, unlike mount-time auto-focus. Two tests pin that it lands and stays on the card (`tests/ui/test_focus_returns.py:191-228`, `:341-378`).

**The return path.** When a card is taken away — answered, declined, or expired — `PromptRegion.apply` notes `released = holds_caret(doomed)` (`:1147`) and, after the reconciliation, posts `CaretReleased` only if no remaining card still holds the caret (`:1187-1188`, `if released and not any(holds_caret(card) for card in self._cards.values()): self.post_message(CaretReleased())`). The module docstring states the rule in one sentence (`talaria/ui/focus.py:23-26`): "when Talaria takes a control away, the caret goes back to the composer." The application answers `on_caret_released` by focusing `self.composer.text_area` (`talaria/ui/app.py:4275-4290`). Operator focus moves — `tab` into the transcript, a click on a sub-agent row — are untouched, because no control was taken away. The invariant is pinned by `test_a_deliberate_focus_move_is_left_alone` (`tests/ui/test_focus_returns.py:154-181`).

**The incumbent whose behaviour this plan must not contradict.** Unit B1, merged at `d56eb09` as pull request 72, removed the `caret: X` status row and replaced it with a transient latched composer notice that fires when a printable key or a paste would otherwise be silently discarded because focus sits in a no-text region (`talaria/ui/app.py:4198-4474`). The three no-text regions are transcript, agents, and the prompts container outside a card (`:4204-4208`, `_NO_TEXT_REGION_IDS`). The predicate explicitly excludes a focused `PromptCard` (`:4242-4244`, `for widget in focused.ancestors_with_self: if isinstance(widget, PromptCard): return None`), so a printable key on a focused approval button is silently discarded today and stays silent under that plan (B1 KTD3, `docs/plans/2026-08-11-v0-3-unit-b1-caret-status-row.md:306-325`). The discard latch is stored in `self._discard_latch` (`:1040-1043`) and cleared whenever the caret leaves the announced region, via `on_descendant_focus` / `on_descendant_blur` (`:4267-4271`). Text reaching the composer notice bar is `height: 1`, `text-wrap: nowrap`, `text-overflow: ellipsis` (`talaria/ui/composer.py:145-160`), which is why B1's wording leads with the way back — a notice whose operative clause is past column 60 is clipped with nothing on screen to say it clipped.

**The counter-example that decides the shape, and what this plan takes from it.** The session picker (`talaria/ui/dialog.py:1-405`) and its model (`talaria/domain/selection.py:1-325`, `talaria/ui/picker.py:1-511`) are fully keyboard-operable and were driven successfully in the same hand-driven session that produced every defect in this release (`hands-on notes:308-320`). The picker is a `ModalScreen[str | None]` (`dialog.py:72`), which is why it owns focus while it is up — Textual puts a modal on top of the screen stack and only the top screen receives keys. It names its keys in a footer: `LIST_HINT = "↑↓ move · →/enter select · ←/esc back · type to filter · ctrl+q quit"` (`selection.py:40`) plus a per-stage hint and a refusal line (`dialog.py:268-270`, `REFUSED_PREFIX = "cannot select — "` at `:69`). Its key handling is a single `on_key` (`:278-366`) that owns every key including printables for the filter, and its `escape` is layered — clear the filter first, then pop a stage, then close (`:371-387`), the same ordering Hermes's own model overlay uses. What this plan takes from it is the shape that works: a control that owns focus while it is the thing being answered, and a footer that names every key that does something, with refusal distinguished from silence. What it does deliberately differently is that the approval card is not a modal. A modal would block the composer — the operator could not type a message while an approval is outstanding, which is not the contract approvals have (they block the turn, not the composer). The card lives inline in `PromptRegion` (`talaria/ui/app.py:1067-1071`, `compose` yields `#transcript`, `#agents`, `#prompts`, then `#composer`), and focus ownership is per-card, not per-screen. The picker needs `enter` to mean "select the highlighted row" while the composer needs `enter` to mean "send the message" — the collision that forced the picker to be modal (`dialog.py:11-22`). The approval card resolves the same collision without a modal because, when it holds focus, its button handles `enter` and its binding handles `esc`, and when it does not, the composer does.

## The design space — the options, and why three fail

All four options below were weighed before settling the five decisions that follow under Key technical decisions. Each failed option is stated with the evidence that rejects it.

### 1. Keep the mount-time guard as it is and rely on `F1` — rejected

This is the incumbent: `if focus_new and isinstance(card.action_widget, Input):` (`prompts.py:1171`). Approvals stay reachable only through `F1`, which on macOS is eaten before the application sees it (`hands-on notes:262-274`). The hand-driven session proved the consequence: an approval that can only be reached through `F1` is mouse-only on the only platform anyone drives. The same session proved `F8` and `F9` do arrive (`:567-582`), so the failure is specific to `F1`/`F2`, not to function keys as a class, but the defect is not that the wrong key was chosen — it is that a blocking prompt has no keyboard path that does not depend on a function key surviving the desktop. The charter reframed spine A away from "make `F1` arrive" for this reason (`charter:68-92`, D8 at `decision-log:128-161`). A plan that preserves the guard preserves the defect.

### 2. Auto-focus every new card unconditionally, stealing mid-word — rejected

Removing the `focus_new` guard and calling `focus_answer` for every new `PromptCard` regardless of kind would make every approval keyboard-reachable the instant it appears. It is also the data-loss failure the existing guard exists to prevent. B1's own risk section names it (`B1 plan:266-268`): the triggering input is discarded and that loss is accepted for a transient notice, but stealing the caret mid-word drops the keystrokes already in flight without notice, because the composer loses focus while the operator is still typing. The guard at `prompts.py:1171` already encodes the operator's mid-word protection (`focus_new=not self.composer.text.strip()` at `app.py:1394`), and the `F1` jump's docstring distinguishes the two cases explicitly — a keypress this explicit is allowed to move the caret even mid-word (`prompts.py:1006-1008`), mount-time auto-focus is not. Unconditional stealing would also break the deliberate `tab` into the transcript: an operator who tabs to scroll and then receives a late approval would be yanked back to the card.

### 3. Make the card a modal dialog like the picker — rejected

Replacing `PromptCard` with a `ModalScreen` would give the strongest focus ownership: a modal is the only focus owner, `enter` and `esc` are unambiguous, and the implementation is the same as `PickerDialog` (`dialog.py:72-405`), which is proven in hand-driven use. It fails on the contract approvals have. A modal blocks every other control — while it is up, the operator cannot type in the composer, cannot scroll the transcript with arrow keys, and cannot interact with any other card. Approvals block the agent's turn, not the operator's composer, and the gateway can queue more than one — the uncorrelated-approval rule (`prompts.py:35-43`) shows a card with more than one queued approval offering only `deny all` as the affirmative-free path. A modal per card would stack or would have to coalesce, and either hides the queue that the inline region is built to show in order (`prompts.py:1150-1155`, "Order is the one thing an approval queue must not lie about"). The picker earns its modal because its collision is `enter`-to-send versus `enter`-to-select while filtering — the whole point is to own `enter` (`dialog.py:11-22`). The approval card already owns `enter` on its button and `esc` on its binding without becoming a screen, because those keys are handled by the focused control, not by the composer.

### 4. Route printable keys on a focused card back into the composer — rejected

An attractive repair for the "typing while the card holds focus loses characters silently" concern (decision 2): if a focused approval button receives `z`, move focus to the composer and insert `z`. This would make B1's silent-discard on cards observable rather than silent. It is rejected because it misdirects keys from the answerability spine. A printable key on a focused card is, in the interface's own terms, an operator acting on the card or about to press `enter` on it — the card is visibly focused (accent tint, R2) and names its keys (`CHOICE_HINT`), so the operator has been told what to do with it, which is exactly the quality the transcript pane lacks (B1 KTD3). Moving focus off the card on a printable would turn an intended "answer this approval next" into "typed a message into the composer instead", a new failure the interface does not have today. It would also break `F1`-then-type-then-`enter` sequences the tests pin (`test_answering_via_the_f1_jumped_to_control_hands_the_caret_back`, `test_focus_returns.py:341-378`). Excluding card controls from the no-text predicate is the deliberate boundary B1 already drew (`app.py:4242-4244`); moving that boundary now would make the discard notice fire on a focused card, which B1's own design says is wrong.

### Chosen shape

The card takes focus when it mounts, but only through the existing mid-word guard and only when no card already holds focus. Its advertised keys are exactly the ones the card binds, and the card names them on a static hint line per kind, following the picker's footer convention. Keys the card does not handle are discarded silently while the card is visibly focused — the deliberate exclusion B1 drew — and focus returns to the composer through the existing `CaretReleased` path when the card is taken away.

## Key technical decisions

### KTD1 — when the card takes focus, and what happens when a second card mounts while the first is still outstanding

Extend the mount-time auto-focus to button-backed cards, keeping the existing guard. In `PromptRegion.apply` (`talaria/ui/prompts.py:1118-1173`), replace the `isinstance(card.action_widget, Input)` test at `:1171` with a test that is true for any focusable control the card offers — `Input` or the first `Button` — and keep `focus_new` as `not self.composer.text.strip()` evaluated at the call site (`talaria/ui/app.py:1394`). Auto-focus fires only when `focus_new` is true and no existing `PromptCard` already holds the caret (`talaria/ui/focus.py:49-67`, `holds_caret`). The implementation therefore checks, before focusing the newly mounted card, whether any card in `self._cards` already returns `holds_caret(card)` true; if one does, the new card is mounted but not focused, regardless of `focus_new`.

The second-card rule is the consequence: **the first card of a batch takes focus (when the guard allows), every subsequent card in the same outstanding set does not steal it.** With one approval queued, the card holds focus. With two queued, the oldest card continues to hold focus; the second card is mounted in order (`prompts.py:1156-1161`) but does not move the caret. This preserves the oldest-first ordering the queue must not lie about (`prompts.py:1152-1155`, `app.py:1464-1465` jumping to the oldest) and avoids the disruptive steal that unconditional auto-focus would cause when the operator is about to press `enter` on the first card. `F1` remains the deliberate way to reach the oldest card from the composer or from a no-text pane, and it is allowed to steal mid-word (`prompts.py:1006-1008`, `focus_first_unanswered` docstring) because the keypress is explicit. A late-arriving second card arriving while the operator is typing in the composer, with `focus_new` false, also does not steal — the composer keeps the caret, the new card is visible but unfocused, and the operator can reach it with `F1` when they choose.

Rejected: focusing the newest card on arrival (would reverse the queue the gateway resolves first, and would steal from the oldest the operator is reading), focusing every new card (would yank the caret within a queue the operator is answering), and not auto-focusing at all (preserves the defect on macOS).

### KTD2 — what the card does with keys it does not handle, including printable characters while the card holds focus

A focused card handles exactly three keys: `enter` (activates the focused `Button` or submits the `Input`), `esc` (decline via `PromptCard.action_decline` at `:886-922`), and `tab`/`shift+tab` (framework focus movement, leaving the card). Every other key, including printable characters, is not consumed by the card and bubbles to `TalariaApp.on_key` (`talaria/ui/app.py:4455-4474`). The card's contract is: **printable keys while a card holds focus are discarded silently — no B1 notice, no re-dispatch into the composer, no focus move.**

This is B1's deliberate exclusion preserved, not a new silence. `_no_text_region` (`app.py:4228-4250`) returns `None` when any `PromptCard` ancestor is in the focused chain (`:4242-4244`), so `on_key`'s discard test (`:4470-4474`, `if region is not None and region != self._discard_latch`) does not fire for a focused card control. The rationale is the one B1 KTD3 gives and this plan inherits: a focused card is visibly focused (card-level `PromptCard:focus-within` tint, `prompts.py:664-666`, and `Button`'s own reverse-video) and names its keys on its hint line (`CHOICE_HINT` / `ANSWER_HINT`), so the operator has been told what to do with it — the quality the transcript pane and the prompts container outside a card lack, where B1 does announce. The auto-focus guard in KTD1 makes this acceptable: the card only steals focus when the composer is empty, so the operator is not mid-word when the steal happens, and the first lost printable is at most the first character of a new message typed without noticing the tint — a low-cost signal that the card is the thing being answered. Re-dispatching that character into the unfocused composer would open the questions B1 KTD2 explicitly refuses (whether to move focus, whether to rescue the triggering input), and would be a behaviour change this plan has not decided. A paste posted while a card holds focus (`events.Paste`) is handled the same way: `on_paste` (`app.py:4437-4453`) also tests `_no_text_region` first and returns without a notice when the region is `None`; the pasted body is discarded, not inserted into the composer, and focus does not move.

Rejected: showing a B1-style notice on the card (would announce a state that is already visibly announced and would put typing-paused wording on an answerable control), moving focus back to the composer on any printable (would misdirect keys from the answer flow and break `F1`-then-`enter` pins), and inserting the printable into the composer while leaving focus on the card (would make two widgets appear to hold the caret at once).

### KTD3 — which keys the card advertises and what each does

The advertised keys are exactly the keys the card binds, as rendered on its hint line. No other keys are advertised, because a control that advertises a key it does not act on is the defect this unit exists to fix (hands-on notes:606-615, "The interface is printing a promise it cannot keep in the state the operator is actually in").

For an answerable button-backed card (an approval, or a multiple-choice clarify), `CHOICE_HINT` (`prompts.py:222`) reads:

`"enter select · esc decline"` (`:222`, `Final[str] = "enter select · esc decline"`)

`enter` activates the focused `Button`'s press (framework behaviour, not a card binding) and therefore selects the highlighted choice. `esc` runs `PromptCard.action_decline` (`:886-922`), which posts `Declined` carrying `request_id` and `kind` (`:922`), and the application declines the prompt via `decline_value` (`prompts.py:384-393`), which for approvals is `"deny"` (`:197`, `DENY_ALL_CHOICE = "deny"`). The application then discards the answer path through the same registry the answer path uses, so a late `esc` after expiry sends nothing (R8). For an input-backed card (a free-text `clarify`, `secret`, or `sudo`), `ANSWER_HINT` (`:228`) reads:

`"enter send · esc decline"` (`:228`, `Final[str] = "enter send · esc decline"`)

`enter` submits the `Input` through `on_input_submitted` (`:936-944`), which posts `Answered`; `esc` declines exactly as above. For the unanswerable approval queue — more than one approval outstanding, where the correlated affirmative would release the wrong entry (`prompts.py:35-43`) — the card shows only `DENY_ALL_HINT` (`:237`):

`"enter deny all"` (`:237`, `Final[str] = "enter deny all"`)

and `esc` is deliberately not named there. Denying the whole queue already is the decline for every prompt on that card (KTD8's sweep), so naming a second key would promise a control the card does not carry (`:230-237` comment at `:231-236`). Pressing `esc` on that card today does nothing that looks identical to having worked; the card now posts `DeclineRefused` (`:736-749`) and the application surfaces `REFUSED_PREFIX`-style feedback, so the distinction is visible rather than silent (the same AE11 rule B3 used for controls that cannot be dispatched).

Whether `esc` declining is defensible: it is. The action is safe in the gateway's own consumer semantics, as cited at `talaria/ui/prompts.py:174-177`: for approvals the declined value is `"deny"`, which blocks rather than authorizes, so an `esc` that arrives in error denies a command the operator was trying to refuse — it does not authorize it. The same safety holds for `clarify`/`secret`/`sudo`, where `EMPTY_ANSWER` (`:194`) declines without revealing a prior value. The destructiveness that would make `esc` the wrong key — an `esc` that *approves* — cannot happen through this path, and the card is visibly focused when `esc` is bound (`prompts.py:671-677`, ancestors-with-self), so the key is not reachable from the composer where a double-press could be destructive.

Rejected: not advertising `esc` at all (would leave the card reachable but not declinable by keyboard, which is half of R3), advertising `esc` on the deny-all-only card (would promise a second control that does not exist), and repurposing printable keys as shortcuts (would steal letters from the filter-free hint and collide with future typing).

### KTD4 — how the card names its keys, following the picker's footer, and whether the naming is static or reflects what is actually bound

Following the picker, strictly. The picker's footer is a static sentence per stage — `LIST_HINT` (`selection.py:40`) at the stage level (`Stage.hint`, `selection.py:300`, default `hint: str = LIST_HINT`) — plus a dynamic refusal line when `enter` lands on an unselectable row (`dialog.py:268-270`, `REFUSED_PREFIX`). The card does the same: a static hint per kind, reflecting exactly what is bound on that card instance, and a dynamic refusal only when the card cannot be declined that way.

Concretely: a button-backed answerable card always renders `CHOICE_HINT` (`:838`), an input-backed card always renders `ANSWER_HINT` (`:849`), and a deny-all-only card always renders `DENY_ALL_HINT` (`:816`). The text is literal, not markup, and is the line the operator is looking at when the control is in front of them (`prompts.py:678-680`). The hint is not globally static across the region — it varies by card kind because the binding varies by kind (`esc` is absent on deny-all-only) — but it is static for a given card instance, so the line always truthfully describes the keys that card will act on. The card does not try to reflect ambient bindings that are not its own (`F1`, `F5`, `tab`): those are application-level keys, and a card that named `F1` would be naming a key that moves *away* from it. The way the card "reflects what is actually bound" is therefore at the kind boundary, not per keystroke, which is the honest rendering for a card: the operator can read the card and know which two keys to reach for, without the line rewriting itself under them.

Rejected: a single global hint for all cards (would misdescribe deny-all-only), a dynamically assembled hint that hides `esc` until the card is focused (would add no information — when unfocused, neither key works because the binding is card-level — and would make the hint appear to change for no user-visible reason), and not naming keys at all in favour of tooltips or off-card help (would repeat the discoverability failure the charter's A2 names).

### KTD5 — how focus returns when the card is answered or dismissed

Unchanged from today, and deliberately so: the existing `CaretReleased` path is the correct narrower rule, and this plan does not re-implement it. When a card that holds the caret is removed — by answering (`Answered`/`DeniedAll` at `prompts.py:685-714`), by declining (`Declined` at `:715-734`), by expiry (reconciliation dropping the row in `PromptRegion.apply` at `:1143-1148`), or by the correlated queue becoming deny-all-only and the card being rebuilt (`:1132-1139` rebuilt-not-left-alone case) — `PromptRegion.apply` posts `CaretReleased` after the removal, but only if no remaining card still holds the caret (`:1187-1188`). The application answers `on_caret_released` (`app.py:4275-4290`) by focusing `self.composer.text_area`. The `holds_caret` predicate (`talaria/ui/focus.py:49-67`) checks `widget in focused.ancestors` via `focused.ancestors_with_self` (`prompts.py:54`, `focus.py:66`), so a card whose `Button` holds focus correctly counts as holding the caret.

With two approvals outstanding, answering the oldest (which holds focus) removes it; the next oldest remains mounted, but Textual's own `_reset_focus` hands focus to the enclosing `PromptRegion` (`focus.py:10-14`), not to the next card's button. The `any(holds_caret(card) for card in self._cards.values())` test is therefore false, `CaretReleased` fires, and focus goes to the composer, not to the next approval. The operator reaches the next approval with `F1`, which jumps to the oldest remaining card's control (`prompts.py:995-1017`). This is the existing behaviour, pinned by `test_answering_via_the_f1_jumped_to_control_hands_the_caret_back` (`tests/ui/test_focus_returns.py:341-378`), and this plan keeps it: auto-focusing the next card after an answer would keep the operator in an answer flow that may not be the next thing they want to do, and it would be a focus steal as surprising as the mount-time steal KTD1 refuses.

The B1 / B3 focus-latch interplay is preserved without a new handler. The discard latch (`app.py:1040-1043`, `self._discard_latch: str = ""`) is cleared in `on_descendant_focus` / `on_descendant_blur` (`:4267-4271`) whenever the caret leaves the announced no-text region. A card that held focus and is removed therefore clears any latch that was set on a prior no-text hold via the same path, because focus transitions through the region and then to the composer. The card's own removal does not itself set a discard notice; it returns focus silently, which is correct — an answer is not a discarded key. The deliberate-focus invariant (`test_a_deliberate_focus_move_is_left_alone`, `:154-181`) and the take-away pins (`:37-93`, `:96-126`, `:129-152`) remain the tests that would go red if this path regressed.

Rejected: auto-focusing the next outstanding card after an answer (would steal the caret in a queue and would be a new narrower rule this plan has not validated in hand-driven use), leaving focus on the `PromptRegion` container (would land the caret in a widget that discards every printable key and draws no caret, the same silent-loss state B1 removed the status row to repair), and adding a new focus-return binding that moves focus on `enter` rather than on removal (would couple the widget's key to the application's focus policy rather than to the domain truth that the control is gone).

## Risk this unit must clear

**A plan that removes a promise without keeping it.** Today `PromptRegion.apply` promises, in prose, that a button-backed card is reachable only through the jump (`prompts.py:1169-1170`); the interface then prints a hint promising `enter` does something, while `enter` in the composer does nothing to the card. Changing one half without the other ships a different broken promise: either the card names keys that still do not work from the composer (the present defect), or the card takes focus but names no keys (the same silence with a different cause). AE2 and AE4 below pin both halves together, the way B1 AE1/AE4 pair the caret-row's absence with the notice's presence.

**A latch that never clears, or one that fires on the card.** Two copies of the same mistake, in opposite directions. If the auto-focus rule is too broad, a printable while the card holds focus would either trigger B1's transcript-region notice (wrong region, wrong wording) or trigger nothing while losing characters silently at scale. KTD2 preserves B1's ancestor check (`app.py:4242-4244`) so the notice does not fire on a focused card, and KTD1 preserves the composer's non-empty guard so the steal does not happen mid-word. If the latch's clear-point were only "when the caret returns to the composer", the composer-free re-entry `transcript → F1 (card) → shift+tab (PromptRegion) → transcript` would keep the latch set and suppress the next notice (B1 KTD2/KTD4, `app.py:4252-4265`). The existing widened condition — clear whenever the current region differs from the latched one — already covers that path and is not changed.

**The shared composer notice bar.** The card's answer feedback (gateway-refusal lines at `app.py:2465-2492`, paste-collapse notices, B3's `JUMP_NOTHING_OUTSTANDING` at `app.py:275` and `JUMP_BLOCKED_BY_MODAL` at `:279`) and B1's discard notice all write `self.composer.show_notice` (`talaria/ui/composer.py:252-255`). The same bar is overwritten by the next writer; that is the accepted cost of every notice on a shared bar (B1 risk section, `docs/plans/2026-08-11-v0-3-unit-b1-caret-status-row.md:368-373`, B3 KTD4). The card introduces no new writer beyond the decline-path that already exists; `Declined`/`Answered` do not themselves write a notice on the discard path, so the bar is not made more contentious.

**The geometry of `PromptRegion`.** The card lives inside a `VerticalScroll` with `max-height: 70%` (`prompts.py:959-963`). Its `focus_answer` calls `self.scroll_to_widget(target, animate=False)` before focusing (`:1014-1015`), so a card whose control is below the fold is scrolled into view before it is focused. Without that, auto-focus would hand the caret to a widget the operator cannot see, which reads as the same silent defect this plan fixes, only one level up. The scroll is minimal (no-op when already visible), so an operator who has scrolled up to read a long command is not yanked back.

**Sequencing with B1.** B1 merged before this plan, so the citations above already describe a tree that contains it and there is no merge order left to negotiate. This unit touches `on_key` (`app.py:4455-4474`) beside B1's printable-key fall-through but does not move that branch, and touches `PromptRegion.apply` (`prompts.py:1118-1173`) without changing B1's `_NO_TEXT_REGION_IDS` or `_DISCARD_NOTICE_BY_REGION`. The boundary is mutual: B1's plan states it "does not implement D9's focus-owning card" and names this unit's surface, and this plan returns the courtesy by changing none of B1's four discard-notice sites.

## Acceptance evidence

Each item is a testable claim. Items marked operator-only require a person at a keyboard and are not claimed as met by anyone else.

- **AE1 — the card takes focus when it mounts, without a jump key.** With the composer empty, feed a gateway `approval.request` whose `choices` list is `["once", "deny"]` (a button-backed card). After `settle`, `app.screen.focused` is the card's first `Button` (`#choice-0`) — the same widget `focus_answer` (`prompts.py:866-884`) lands on for `F1`. No `F1` was pressed.
- **AE2 — the advertised keys do what the card says, and the card names every key that does something.** (a) With focus on the card's `Button` from AE1, pressing `enter` posts `Answered` for the request id and the card is removed; (b) with a fresh card holding focus, pressing `esc` posts `Declined` (or `DeniedAll` for the deny-all-only queue shape) and the card is removed; (c) the card's rendered hint is exactly `CHOICE_HINT` (`"enter select · esc decline"`) at `prompts.py:222` for the answerable button-backed shape, `ANSWER_HINT` (`"enter send · esc decline"`) at `:228` for the input-backed shape, and `DENY_ALL_HINT` (`"enter deny all"`) at `:237` for the deny-all-only shape. No card renders a hint naming a key that is not bound on that instance. `esc` from the composer (no card focused) does nothing to prompts — no `Declined` is posted and no card is removed.
- **AE3 — a `F1` jump still reaches the oldest card, and survives the new auto-focus.** With two approvals queued and focus in the composer, `F1` lands on the oldest card's `#choice-0`, not the second card's, regardless of whether the first card auto-focused on mount. Asserted as `app.screen.focused is oldest_card.query_one("#choice-0", Button)`.
- **AE4 — a second card does not steal focus from the first.** Mount a first approval, let it auto-focus (AE1). Without moving focus, feed a second `approval.request`. After `settle`, `app.screen.focused` is still the first card's `#choice-0`. The second card is mounted in order (`prompts.py:1156-1161`) but `holds_caret(second_card)` is false.
- **AE5 — the mid-word guard is kept.** With `app.composer.text = "hi"` (non-empty after `strip`), feed a new `approval.request`. After `settle`, `app.screen.focused is app.composer.text_area` — the composer kept the caret — and the card is still mounted and visible but unfocused. Typing another printable appends to `"hi"` rather than being discarded.
- **AE6 — keys the card does not handle are silently discarded while it is visibly focused, with no B1 notice.** With focus on the card's `Button` from AE1, press a printable `z` (or post `Paste("body")`). The composer's text is unchanged, no `press tab to return to the message box — typing is paused …` notice appears (`app.py:4213-4226`, `_DISCARD_NOTICE_BY_REGION`), `app.screen.focused` is still the same `Button`, and the card is still focus-tinted (`PromptCard:focus-within` at `prompts.py:664-666`). The silence is a requirement, not an omission, and is the B1 KTD3 exclusion (`app.py:4242-4244`) preserved.
- **AE7 — focus returns to the composer when the card is taken away, by any path.** After AE1, (a) `enter` on the button, (b) `click` on `#choice-0`, (c) `esc` via `action_decline`, and (d) a reapplied `PromptView` that drops the row (expiry) each leave `app.screen.focused is app.composer.text_area` after `settle`, via `CaretReleased` (`talaria/ui/focus.py:37-46`, `talaria/ui/prompts.py:1187-1188`, `talaria/ui/app.py:4275-4290`). Typing a printable after the return appends to the composer. If two approvals are queued and the oldest is removed by (a), focus still goes to the composer — not to the next card — and `F1` is required to reach the survivor.
- **AE8 — the deliberate-move invariant is untouched.** `test_a_deliberate_focus_move_is_left_alone` (`tests/ui/test_focus_returns.py:154-181`) survives unchanged: `tab` into the transcript keeps the caret there across renders, and no new snap-back drags it back.
- **AE9 — the replay gate runs green over the existing gate corpus, with both `content_is_complete` and `interface_shows_everything` true.** The corpus is named by digest and frame count, never by path. A card mounted during a gate run writes no transcript row, and the gate drives no focus away from the composer, so the new auto-focus has no surface under the gate — the same reason B1 KTD6 gives. The check is that a run that would have passed before this change still passes.
- **AE10 — the project check is clean:** `ruff`, `mypy`, `pytest`, `bandit`, `git diff --check`.

**Acceptance for a person, per the charter's evidence rule 2** (`docs/plans/2026-08-11-v0-3-orchestration-charter.md:182-186`): driving the application, the operator never needs `F1` to reach a newly arrived approval when the composer is empty — the card is already focused and visibly tinted, its hint names `enter` and `esc`, and pressing them does what the hint says; when the composer holds text, the card does not steal the caret and the operator keeps typing uninterrupted. ## What this unit does not do

- **It does not ship a click affordance.** The charter's A1 originally paired the focus-owning card with a clickable jump control; that half is removed by operator decision made 2026-08-12 because it depends on unit A3, the mis-aimed mouse, which needs a hand-driven capture no agent can make. Nothing in this plan adds a clickable control, a jump affordance, or any mouse-driven path, and nothing plans around the mouse offset. Where a click would later belong — a button beside the activity line that runs `focus_first_unanswered` — one sentence naming it is enough.
- **It does not re-decide any key binding.** `F1`, `F2`, `F4`, `F5`, and `tab` are untouched. The function-key row as a whole is spine A's unit A4, under D9 (`decision-log:128-181`); this plan does not re-litigate it and does not replace `F1` with a chord.
- **It does not change the focus chain.** The transcript pane stays focusable (`talaria/ui/transcript.py:638`, `VerticalScroll`) and the sub-agent rows stay clickable (`talaria/ui/agents.py:98`, `can_focus = self.interruptible`). Making the panes unfocusable so the discard hazard cannot exist is a navigation decision in spine A's mis-aimed-input family and is deliberately out of scope here.
- **It does not add focus styling to the transcript pane.** That remains unit U3's deferred follow-up (`docs/plans/2026-08-08-talaria-v0-2-answerability-and-session-story-plan.md:300-301`), and styling announces a state where the card announces a consequence.
- **It does not implement a slash-command palette, history, or any composer convention.** That is spine C (`charter:129-137`), additive and sequenced after A and B are merged.
- **It does not touch the domain core.** The focus decision is presentation state queried through `holds_caret` (`talaria/ui/focus.py:49-67`) and the prompt region's view, not domain truth, so ADR-0002's boundary (`platform-specs/04-architecture/adrs/0002-the-domain-core-is-framework-independent.md:36-51`) holds. The hint constants are presentation strings in the widget that renders them.
- **It does not change where the next queued approval receives focus after an answer.** The take-away return to the composer is kept as it is (`focus.py:23-26`, `prompts.py:1187-1188`), even when another outstanding approval remains; `F1` is the way to the survivor.
