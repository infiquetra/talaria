Talaria is an experimental, Hermes-native terminal UI. Through v0.3 it was a window onto one session of one gateway. This release makes it a fleet client: **one running Talaria dials every configured profile, tracks every session those gateways can see, and keeps one queue that answers the operator's standing question — what is waiting on me?** The scope comes out of driving v0.3 across several concurrent workstreams, where a terminal that shows one session answers the wrong question.

Twelve pull requests: eight code units, a live-gateway analysis that measured the running gateway before anything was built, a mid-turn replan that slotted the foreign-wait slice, a closing review-and-QA pass over the whole release together, and the acceptance record. Every code unit merged behind adversarial review. The deepest — the needs-you queue — took twelve review rounds plus a bounded confirmation, and its hardest finding corrected the project's own review rules: a mutation that survives the test suite proves only that no test distinguished it, never that the change was inert. The recurring defect class of this release was **code written, tested, and reached by nothing** — found at function, unit, app-assembly and cross-unit-seam scale — so the closing pass mechanically swept all 320 names exported across `talaria/` for production reachability: twelve had no production caller, one was the release's last defect, one is documented as deliberately uncalled, and ten are filed to the queue of deferred work. The unit-by-unit record is in [the fleet-turn plan](https://github.com/infiquetra/talaria/blob/v0.4.0/docs/plans/2026-08-16-talaria-v0-4-fleet-turn-plan.md).

## Read this part first

Carried forward from earlier releases, unchanged and not superseded by anything here:

- **No person has driven the interface on Linux.** The suite runs there in continuous integration; nobody has used it there.
- **A credential your shell exported before Talaria started is still visible** in the process environment for the life of the process. Use the credential file.
- **The measurements behind the framework claims were taken against a bare pseudo-terminal**, not a real terminal emulator.

New to this release, and the limit to weigh hardest:

- **Ten of the eleven acceptance expectations are verified by tests. The eleventh is not yet verified by anyone.** That expectation — a real background prompt discovered from the summary, opened in the drill-down, answered, and its confirming clear observed, by hand, against a live gateway — is reserved for an operator drive and was **not satisfied when this release was tagged**. An agent-driven rehearsal of that drive is recorded in [the acceptance results](https://github.com/infiquetra/talaria/blob/v0.4.0/docs/plans/2026-08-19-v0-4-live-acceptance-results.md), clearly labelled as not counting, together with the two prerequisites it surfaced: the *serving* gateway process must register `approval.pending` — a checkout that has the method is not enough — and the driven session's mode must raise approvals rather than execute. The rehearsal did bank seven live observations against a real gateway, each beside evidence that had previously been test-only, including the reserved summary row, the hedged empty state, the named absent seam, and frame-clock ages that freeze rather than drift.
- **On a gateway that does not register `approval.pending`, another session's approval cannot become answerable.** Talaria says so — the seam board names the absent method and the queue names the disabled feature — but the wait stays a roster row. Discovering-and-answering a foreign approval needs that method on the serving process.

## What is new to use

- **Configure more than one profile and Talaria dials them all.** `build_live_app` assembles one connection per configured profile endpoint, plus the credential file's own gateway. Each connection carries its own credential, correlator, epoch, reconnect schedule and probe state; one gateway down never stalls another's dial or frame flow. A named profile resolves its own `[profiles.<name>].token` and nothing else, written by `refresh-credential --profile <name>`. Two profiles whose endpoints parse equal share a connection only when their tokens are byte-identical; otherwise the launch refuses loudly and names both.
- **The needs-you row.** One screen row, reserved from first mount, that cannot grow. It names how many things are waiting on you across the fleet, then the oldest item's source, age and session. Empty states are honest: a fleet that could not be fully asked reads "part of the fleet could not be asked", never a bare "none".
- **`/needs`** opens the drill-down: every outstanding human-facing blocking prompt from every session the fleet can see, in one flat wait-age-ordered list — fed by events where Talaria drives and by `approval.pending` polls where it does not. An approval is answerable inline through the same function the prompt card uses; answering is a descent into named choices, never an empty choice, because the gateway reads any resolved non-deny answer — an empty one included — as approved. Enter on anything else travels to its session and lands the caret on the card's control.
- **Background sessions have rows.** An event from a session you are not looking at updates its row and leaves your transcript alone; an unknown session creates a row rather than being discarded. A session never observed says so — it is not "idle", and its age is not zero. Every derived value renders stale-since with source and age, ages freeze when frames stop, and a row is retired only when two roster sweeps of the same epoch both omit it.
- **Confirm before steal.** Moving focus to a session another live client is driving asks first, in a dedicated two-row modal — deliberately not the picker, which gives every printable key to its filter, because a stray keystroke must not answer a question about taking somebody's session.
- **Fleet recording and replay.** A multi-connection `--record` run writes a version-2 frame log with its connections in the header and a profile on every frame. Replay reproduces the registry, the queue and the focused projection deterministically, ages included, and `talaria gate` gains seven fleet checkpoints at two speeds.

## What changed that you may have been relying on

- **`/profiles` no longer drop-switches.** Selecting a profile brings its connection up and makes it the home for the next create or resume, leaving every other socket alone. Since v0.1 it had dialed the selected gateway in place of the current one.
- **A multi-connection recording is a version-2 log, and older readers refuse it.** A reader that only knows version 1 stops rather than silently merging session ids across gateways. Single-connection recordings are unchanged and byte-identical, so existing recordings and the reference corpus are untouched.
- **`refresh-credential` verifies its edit instead of trusting its scanner.** Review found four ways a line-wise TOML editor misreads structure, each able to destroy one profile's token or leave a stale one authoritative while reporting success. The writer now parses the document before and after and requires the result to equal the original with exactly one key set — otherwise it refuses and touches nothing. Two exotic shapes the old writer handled are now refused by design; a refusal that names the problem is a strictly better failure than a silent write.
