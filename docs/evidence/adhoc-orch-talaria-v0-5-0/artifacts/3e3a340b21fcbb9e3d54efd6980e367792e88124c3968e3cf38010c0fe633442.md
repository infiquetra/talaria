#### 80. (P2) Tests here routinely enumerate committed artifacts, but a shallow directory pattern shared by every enumerator hides the 133 quarantined receipts, and the one guard whose whole subject is that hidden set is the one written against a fabricated input

`scripts/acceptance/v050_receipt.py:489` · lens `architecture-maintainability` · dimension `architectural-fit-ownership-single-sources` · raised by architecture · confidence 100 · route `manual` -> `review-fixer`

**Why it matters.** This is the rewritten form of a finding whose first version overreached, and the corrected version is the sharper one. The practice of deriving a test's input from artifacts the system actually produced is not missing from this repository; it is established and widely used, in at least ten places I read directly, including the very file that validates receipts. What is missing is its reach into one specific directory, and that directory is exactly where a live defect sits. The acceptance evidence tree holds two populations: 42 active receipts at evidence/<tester>/receipts/, and 133 quarantined ones two levels deeper at evidence/<tester>/superseded/<commit>/receipts/. Every enumerator in the repository uses the same one-level pattern '*/receipts/*.json'. The record generator uses it, the receipt validator uses it, and the one test that validates real receipts against the schema uses it. I measured that this pattern matches 42 files and zero quarantined ones. So the quarantined population is invisible to every piece of code, production or test, that walks the evidence tree. Against that background the guard added this cycle to stop quarantined evidence being reused does not inspect directory location at all: it inspects the receipt's own path fields for a 'superseded' component. Quarantining moves directories without rewriting receipt contents, so the fields never say 'superseded'. I measured the guard against both real populations: it matches 0 of the 133 quarantined receipts and 0 of the 42 active ones. Its regression test constructs a receipt in a temporary directory with a fabricated path field, which is the only shape that makes it fire. The pattern this review has been chasing is therefore not that nobody here writes derived guards. It is narrower and more actionable: a shared shallow directory convention made one population unenumerable, and the guard written for that population was consequently written against something typed by hand instead. That is a mechanical cause with a mechanical fix, and it explains why a green test sits beside a live defect.

**Evidence.**

- Measured on the committed tree at the frozen revision: docs/acceptance/v0.5.0/evidence holds 42 files matching '*/receipts/*.json' and 133 matching '*/superseded/*/receipts/*.json'. Sample quarantined path: evidence/t2/superseded/d869791/receipts/item-32-talaria-t2.json.
- Measured: the glob '*/receipts/*.json' used at tests/docs/test_v050_acceptance_records.py:138 returns 42 paths, of which 0 are under a superseded directory. The same one-level pattern appears in production code at scripts/acceptance/v050_records.py:228 and scripts/acceptance/v050_receipt.py:714, so the blind spot is a shared convention rather than one test's oversight.
- Measured by importing the guard and running it over both real populations: scripts/acceptance/v050_receipt.py:489 _has_superseded_path matches 0 of 133 quarantined receipts and 0 of 42 active receipts. This independently corroborates the testing lens's finding rather than relaying it.
- scripts/acceptance/v050_receipt.py:501 is the mechanism: the check tests 'superseded' in Path(value).parts over the receipt's own path fields, which quarantining never rewrites.
- scripts/acceptance/test_v050_harness.py:1053-1066 test_verify_run_rejects_superseded_origin_in_active_receipt builds a receipt under tmp_path and sets a field to the literal 'docs/acceptance/v0.5.0/evidence/t1/superseded/old/pty-result.json'. That fabricated shape is what makes the guard fire; no committed receipt has it.

#### 81. (P3) The status configuration module grew its own control-character sanitiser, which the existing one's documentation explicitly forbids and which misses six of eight hazard classes

`talaria/status/contract.py:303` · lens `architecture-maintainability` · dimension `architectural-fit-ownership-single-sources` · raised by architecture · confidence 100 · route `manual` -> `review-fixer`

**Why it matters.** Talaria has one function that turns an untrusted string into something a terminal will draw rather than obey: defang, at talaria/ui/literal.py:175, backed by a roughly 430-codepoint translation table. Its docstring states the design rule in the imperative: it is 'deliberately one function rather than a strict version for commands and a lenient one for prose, because two rules means one of them is eventually applied to the wrong string.' This release adds a second rule. talaria/status/contract.py:303 defines _defang_status_segment over a ten-entry table plus a catch-all for bytes below 0x20. Measured on eight hazard inputs, the two rules agree on two and disagree on six: a right-to-left override, a zero-width joiner, a byte-order mark, a soft hyphen, a Unicode Tag letter and a left-to-right isolate all pass through the new rule untouched and are marked by the canonical one. Nothing is broken today, because the caller wraps the result in Python's repr(), and repr() escapes every one of the eight. That is the problem in miniature: the new function is contributing nothing to safety that repr() was not already contributing, while establishing a second, weaker authority under a name that promises the first one's guarantee. The next caller who reads the name 'defang' and uses it without repr() gets six hazard classes straight through into a rendered notice. The reason the copy exists is real and good: talaria/status/contract.py must not import talaria.ui, and tests/test_framework_boundaries.py enforces that. But the constraint forces a module move, not a second rule.

**Evidence.**

- talaria/ui/literal.py:203-206 states the rule being broken: defang 'is deliberately one function rather than a strict version for commands and a lenient one for prose, because two rules means one of them is eventually applied to the wrong string.'
- Measured at the frozen revision, eight probe strings through both functions: ESC and DEL agree; U+202E right-to-left override, U+200D zero-width joiner, U+FEFF byte-order mark, U+00AD soft hyphen, U+E0041 Tag letter A and U+2066 left-to-right isolate all return the canonical marker from talaria.ui.literal.defang and return the character unchanged from talaria.status.contract._defang_status_segment. Six of eight diverge.
- Measured: normalize_status_segments(['seg<U+202E>ment', 'connection']) at the frozen revision emits a notice whose repr shows '\u202e'. Running the same probe against a copy where _defang_status_segment is replaced by the identity gives a notice with '\u202e' as well, and for the ESC probe gives '\x1b' instead of the control picture. The raw hazard character is absent in both, so repr() is doing all of the containment and the new function is changing only how the escape is spelled.
- Measured: replacing the whole body of _defang_status_segment with 'return value' on a disposable copy and running the three suites that exercise it (tests/ui/test_status_bar.py, tests/test_config.py, tests/status) gives 1 failed, 149 passed, and the only test that dies is test_unknown_configured_segment_escape_is_rendered_not_obeyed, which feeds one typed ESC byte.
- talaria/ui/literal.py:175 defang has nine importers across talaria/; the transform itself is a single str.translate call and does not use the rich import that makes literal.py framework-coupled.
- tests/test_framework_boundaries.py:44-53 is what forbids talaria/status from importing talaria.ui, so the duplication is a consequence of a boundary this release correctly enforces, not of carelessness.

**Suggested fix.** Move the translation table and the defang function out of talaria/ui/literal.py into a framework-free home, for example a new talaria/text.py or an existing module under talaria/domain/. talaria/ui/literal.py keeps literal_text and re-exports defang so its nine current importers are unchanged; talaria/status/contract.py imports the same function and _NOTICE_CONTROL_PICTURES and _defang_status_segment are deleted. Add the new module to the framework-free sweep in tests/test_framework_boundaries.py so the move is held. If moving is judged too large for this release, the minimum is to rename _defang_status_segment to something that does not promise the defang guarantee and to say in its docstring that repr() is the containment and this function is presentation only.
