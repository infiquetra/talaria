## How this run is driven

The canonical execution spec describes seventeen units as one dependency graph: nine
implementation units (U1–U9) with an adversarial-review unit (CR1–CR8) interleaved behind each of
the first eight as a scheduling gate. The operator brief requires that **each unit land as its own
pull request, squash-merged on green required checks**, and that a `blocked` review verdict halt
every dependent unit until remediation and re-review.

Those two facts settle the execution shape: the graph runs **one segment at a time**, a segment
being one implementation unit plus its review unit. Running the whole graph in a single Workflow
launch would produce every unit's code before any pull request existed, which the per-unit pull
request rule forbids, and would let a blocked verdict arrive only after its dependents had already
spent their work.

Per segment:

1. Branch from `origin/main`.
2. Derive a segment spec from the canonical spec with `.saga/segment_spec.py` — it keeps only that
   segment's units and drops `depends_on` entries pointing at units already merged to main (the
   dependency is satisfied by the branch's merge base, not by a barrier inside the run). Unit
   prompts are otherwise byte-identical to the canonical spec.
3. Emit the segment workflow with the saga emitter, run the Phase-1.5 pre-submit protocol
   (`.saga/presubmit.py`: lease render, `reserve`, `attest` as the launch gate, settlement render,
   dispatch manifest, one spawn attempt per unit), and launch the Workflow tool.
4. Read the review unit's verdict. A non-clean verdict halts the segment: remediate, re-review.
5. Run the full check battery, commit, open the pull request, merge on green.

Nothing under `.saga/` is committed — `.gitignore:20` excludes it. It holds the machine-local
preflight brief and the derived segment artifacts.

## S1 — U1 and its review

connections and two throwaway sessions in total, each session created and closed by its own run —

**Its headline finding is a discipline result, not a protocol one.** The checkout at the Hermes

## A decision this segment surfaced, since ruled

U1 found that the gateway's live-status function derives `waiting` from the blocking-prompt
registry only. Approvals live in a different structure it never reads, so **a session blocked on an
approval reports `working`, never `waiting`** — verified at source by the driver, at every revision
examined.

That breaks a plan mechanism. KTD11 fires the pending-approval query only at rows already reporting
`waiting`, and KTD2's second feed turns `waiting` rows into queue items. For a **foreign** session —
one Talaria does not drive, where events are transport-scoped and therefore invisible — an approval
would never surface at all: the row shows `working`, indistinguishable from ordinary work. The
needs-you queue's foreign-approval path, which is close to the feature's headline use case, cannot
work as specified.

The shape of a fix is available and stays inside KTD11's intent. The rule exists because the query
warms a cold session's agent build; a row reporting `working` has a live agent by construction,
exactly as a `waiting` row does. So the trigger can widen from `waiting` to `waiting` **or**
`working` without ever touching an `idle` or `starting` row. The cost is polling pressure: every
working row would attract a query.

**Operator ruling, 2026-08-17: widen.** The trigger fires at rows reporting `waiting` or `working`.
The recorded rationale: KTD11's gate exists to avoid warming lazy agent builds; a pending approval
does not surface as `waiting` because approvals ride the approval registry rather than the
blocking-prompt registry that feeds status, and a `working` row's agent is live by construction, so
the widened trigger preserves the exact safety property — `idle`, `starting` and lazy rows stay
excluded and are never polled — while keeping R14 true for foreign approvals. The cost is bounded to
active rows at the existing coalesce and backstop cadence.

The amendment lands with U6, not here: the plan's KTD11 text and the U6 commit both carry the
rationale, and U6's unit brief carries the widened trigger so the implementing agent builds it
rather than restoring the plan's original wording. Editing the plan body is normally out of bounds
during execution; this edit is explicitly instructed, so it is in bounds there and only there.

### Round four: the scanner stops being the safety mechanism

Round four found three more, all demonstrated by executing the committed code, and one of them was a
**regression against `origin/main`** — the loose boundary matcher from round three fires on
multi-line-string content and inline-array continuation lines, which the original code had handled
correctly.

That is the round where the pattern of the whole segment became legible. Four review rounds had found
four different ways a line-wise scanner misreads TOML structure: a header with a trailing comment, an
array-of-tables or quoted-key header, a quoted key carrying a bracket, and a header-shaped line that
is really the inside of a multi-line string. Each fix taught the scanner one more shape and the next
round found the shape after it. Every one failed the same way — silently, destroying a credential or
leaving a stale one authoritative, with the command reporting success.

**So the scanner stopped being the safety mechanism.** Line-wise editing stays, because an operator's
comments, `url` key and spacing must survive a refresh. But the guarantee is now a verification gate:
parse the document before and after, and require that the result equals the original with exactly one
key set. Any misread — a false span start, a false end, string content mistaken for structure, an
insert landing inside an array — changes some other key or fails to change the target, and is refused
before anything reaches the disk, with the file left untouched. **A shape nobody has thought of yet
fails the same way**, which is the property no pattern can have. A file that did not parse on the way
in is exempt, preserving the long-standing contract that such a file is kept verbatim.

The third finding was a socket leak: `close` takes no per-profile lock, and the previously-tested
branch was a dial *failing* during teardown. When the dial **succeeds**, the attach stored an open
authenticated socket on a source whose `close` had already run — verified live, with a ping over that
socket still answered after teardown returned. The ensure now re-checks the closed flag after the
dial and retires on that branch.

### Round five: the gate holds, and a test that proved the wrong thing

Round five confirmed the verification gate against a full attack battery — every demonstrated shape
refused with the file byte-identical on disk, ordinary files still written, no token in any message,
and the deep comparison unfoolable by a value moved between tables that compare equal. **The
credential-corruption family that consumed four rounds is closed.**

One finding survived, and it was as much about the test as the code. The socket leak lives deeper
than round four fixed it: `close` can land *inside* the dial, during the credential acquire or the
attach, where teardown finds no connection to drop — and then the attach resolves with a live socket
on an already-closed source. The connection-set re-check could not help, because `close` had already
emptied the source map, so its retire popped nothing.

**And the round-four test proved the wrong thing.** It gated `LiveSource.start`, whose own
closed-guard returns before any dial runs, so it never opened a socket after close at all. It pinned
the report reason and looked like coverage. The test now gates the credential acquire, inside the
dial, and its docstring says why so the next reader does not undo it. The fix moved to the dial
itself, where all four callers share the window and only that frame holds the connection before it
is stored.

One caveat was declined with reasons rather than fixed: a credentials file containing a float `nan`
has a correct edit refused, because `nan` never equals itself. That is the fail-safe direction on a
fantastical shape, and special-casing it would put a branch in the one piece of this module whose
value is having none. The reviewer concurred.

### Two incidents worth recording

The round-two reviewer ran a destructive git command on the credential writer while mutation-testing
an **uncommitted** tree, discarding the unit's work on that file, and reconstructed it from an
earlier read. It disclosed this. The driver re-read the module's security-critical parts directly and
observed that its behaviour is independently pinned by tests the incident never touched, all of which
pass. Then, writing the warning about that hazard, the driver put the command in backticks inside a
double-quoted shell argument and executed it — harmlessly, but it corrupted the reviewer's brief,
which was regenerated from a file.

**The standing change:** from segment S3 on, each unit is committed to its branch *before* its review
is dispatched, so a mutation-testing reviewer has a commit to revert to instead of nothing. U2 was
committed before its round-four review for the same reason.
