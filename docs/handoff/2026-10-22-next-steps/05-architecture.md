# 05 — Recommended architecture

Status: `proposed` (the decisions here become architecture decision records, or ADRs, when the
operator accepts them; drafts are in [adr-drafts/](adr-drafts/))

Research reports are cited by number; for example, u11 is research/u11-language-framework.md, the
language and framework evaluation.

## The shape in one picture

```text
                 ┌──────────────────────────────────────────────────────────┐
                 │ Hermes gateway: one per machine, supervised, owns every  │
                 │ session of every profile (the "session authority")      │
                 └───────────▲───────────────────────────▲──────────────────┘
        hermes-gateway-v1    │ WebSocket, ticket minted  │ same protocol
        on $HERMES_HOME/gateway.sock                     │
                 ┌───────────┴───────────┐   ┌───────────┴───────────────────┐
                 │ talaria               │   │ talaria workflow run --detach │
                 │ terminal UI (viewer)  │◄──┤ headless runner, journal on   │
                 │ one process per       │   │ disk; the UI watches it       │
                 │ terminal pane         │   └───────────────────────────────┘
                 └───────────────────────┘
```

Everything with a lifetime longer than a terminal window lives in Hermes or on disk. The terminal UI
can be closed, killed or opened in three panes at once without losing anything.

## Principles

1. **Thin cockpit, thick backend.** Talaria contains no agent logic. The agent loop, tools, memory,
   skills, delegation, scheduling and model calls belong to Hermes. When Talaria needs something
   Hermes lacks, the fix is a Hermes contribution, not a client-side imitation.
2. **Inline first.** Finished transcript output is written once into the terminal's own scrollback.
   Only a small live region at the bottom is ever redrawn. Overlays (fleet, agents, pickers,
   settings, diff review, transcript pager) take the alternate screen temporarily and leave nothing
   behind.
3. **Generate the protocol; do not transcribe it.** Types come from the contract Hermes publishes, pinned
   to a Hermes release, regenerated by a script, and checked in continuous integration.
4. **One event loop, one way to change state.** Every source of change — the network, the keyboard,
   timers, the workflow runner — sends a message into one channel. A pure reducer updates state; a
   render is scheduled only when something visible changed. Rendering never blocks input.
5. **Schema-driven where Hermes provides a schema.** Settings screens are built from Hermes's config
   schema; the slash palette from its command catalog; the model picker from `model.options`. New
   Hermes features appear without a Talaria release where possible.
6. **Every number the operator feels is a test.** Launch time, keystroke latency while streaming,
   streaming CPU, bytes per frame and idle repaints are measured in continuous integration with
   budgets (see "Performance budgets").

## Layers

Names are given as Rust crates; the same boundaries apply in any language.

| Layer | Owns | Must not |
|---|---|---|
| `hermes-contract` | Types generated from the pinned Hermes contract, plus the hand-written canonical events the contract omits (`approval.request`, `approval.settled`, `clarify.request`, `clarify.settled`, `session.replay_gap`) | Contain behaviour |
| `hermes-client` | Finding the gateway (`identify`), minting tickets, the WebSocket, JSON-RPC request/response correlation, notifications, server-to-client requests, heartbeat (ping every 15 s, 45 s deadline), reconnect with backoff (1 s to 30 s), replay with `session.events.since` and gap handling, `client.capabilities`, the dashboard REST calls that have no RPC (config schema, `.env`) | Know about the screen |
| `talaria-core` | Domain state and the reducer: per-session transcript state machine, fleet registry, needs-you queue, settings model, workflow run model. Pure functions only | Do input/output or import the terminal library |
| `talaria-core` (dependencies) | May depend on `hermes-contract` for event payload types. It defines its own `Event` enum that wraps them (`Event::Session(SessionId, hermes_contract::events::Notification)`) plus local intents, and its own `Effect` enum. `talaria-app` executes effects; it does not re-map payloads | Import `hermes-client` |
| `talaria-app` | Application services that turn intents into protocol calls, wrap protocol events in `talaria-core`'s `Event` enum, and execute the effects the reducer returns: connection, sessions, prompts and approvals, models, settings, workflows | Render |
| `talaria-tui` | Inline history writer, live region (streaming tail, status line, composer), overlays, key handling, themes | Hold protocol or session state |
| `talaria-workflow` | The runner: embedded script engine, journal, staffing table, per-provider scheduler, budget | Depend on the terminal UI |
| `talaria-cli` | The binary and its subcommands | Contain logic beyond wiring |

Talaria's ADR-0002 rule survives unchanged: the domain core never imports the terminal framework. What
is new is the application layer between them, whose absence produced the `TalariaApp` class of about
7,100 lines.

## The screen

```text
 ...terminal scrollback: finished cells, written once...
 > fix the failing test
 ⏺ Read calc.py
 ⏺ Bash(pytest -q)  ✗ 1 failed · 0.8s
 ⏺ Edit calc.py  +1 −1
     9 −   return total / (len(values) + 1)
     9 +   return total / len(values)
 ⏺ Bash(pytest -q)  ✓ 2 passed · 0.7s
 Fixed the off-by-one in average().
──────────────────────────── live region (redrawn) ────────────────────────────
 ✻ Working · 12s · ↓1.2k tokens · esc to interrupt                  queued (1)
╭────────────────────────────────────────────────────────────────────────────╮
│ > _                                                                          │
╰────────────────────────────────────────────────────────────────────────────╯
 opus-5.5 high │ ~/proj (main) │ ctx 34% │ $0.12 │ ⚑ 2 need you │ 3 working
```

- **Cells.** A user prompt, an assistant message, a tool call (name, one-line argument summary,
  outcome, duration; expandable output in the pager), a diff, a subagent batch, a notice. A cell is
  committed to scrollback when it is final; until then it lives in the live region.
- **Streaming.** The live region shows the tail of the streaming message, re-parsing only the trailing
  Markdown block; finished blocks are committed to scrollback as soon as they close.
- **The status line** is one line, user-configurable, with the external-command contract Talaria
  already has.
- **Switching the foreground session** prints a separator and the new session's recent history into
  scrollback, the way Claude Code's resume does. Side-by-side sessions are the multiplexer's job:
  inside a terminal multiplexer such as Herdr (built for running coding agents in panes) or tmux,
  "open in new pane" runs `talaria attach <session>` in a split.

## The fleet view

```text
 NEEDS YOU (2)
  ● api-refactor       gpt-6.1-sol        approval: rm -rf build/            2m
  ● docs-sweep         minimax-m3.1-flash question: which section?           5m
 WORKING (3)
  ◐ talaria-rewrite    opus-5.5           editing crates/core/src/state.rs   12m  $1.20
  ◐ review-pr-482      workflow           phase 2/3 · 6 agents                4m  $0.40
  ◐ bench-startup      haiku-5.5          running cargo bench                 1m
 DONE (1)
  ✓ triage-issues      sonnet-5.5         "Closed 4, labelled 9"             1h
 enter open · space peek · r reply · x stop · n new · w new in worktree · / filter
```

- Rows come from `session.list` across every profile the gateway serves (a host-scope ticket),
  refreshed on `sessions.changed`, and from live events for sessions Talaria is subscribed to.
- **Peek and reply** without leaving the current session: a reply to a working session is queued
  (`prompt.submit` on a busy session queues durably); approvals can be answered from the peek panel.
- **New in worktree** creates a git worktree from freshly fetched `origin`, creates a session with that
  working directory and the chosen model, and submits the prompt. The session runs in the gateway; the
  operator keeps typing elsewhere.
- **Notifications**: a terminal bell and an OSC 9 desktop notification (a terminal escape sequence
  that asks the terminal to show a system notification) when something needs the operator; inside
  Herdr, Talaria reports its own pane state (working, blocked, idle) so Herdr's sidebar shows it.

## Configuration

- **Schema-driven settings.** `GET /api/config/schema` returns every field with its category, type,
  description and default. Talaria renders forms from it, reads values with `config.get`, writes with
  `config.set`, and labels each field "applies now" or "needs restart". New Hermes settings appear
  without a Talaria release.
- **Typed screens where Hermes has typed methods**: providers and keys (`model.options`,
  `model.save_key`, `model.disconnect`), Model Context Protocol (MCP) servers (`mcp.catalog`,
  `mcp.servers.*` including OAuth),
  skills (`skills.manage`), plugins (`plugins.manage`), toolsets (`tools.list`, `tools.configure`),
  cron (`cron.manage`), profiles (`profiles.*`), connectors (`connectors.*`).
- **Secrets** are never displayed except through a deliberate one-shot reveal, never logged, never
  recorded.
- **Conversational configuration.** `/configure add the GitHub MCP server to my work profile` starts a
  short-lived Hermes session with a configuration skill; it proposes changes; Talaria shows the
  proposed changes as a diff of config keys; the operator approves; Talaria applies them with
  `config.set` and the typed methods. This makes "extremely user friendly" reachable without
  hand-building a form for every Hermes feature.

## Protocol rules every client layer must keep

Carried from Talaria's recorded lessons (the Talaria history report,
[u03](research/u03-talaria-history.md) §3.1) and Hermes's own client (the language and framework
report, [u11](research/u11-language-framework.md) §3.4); re-verify each against the pinned Hermes.

- Send `client.capabilities {server_requests: true}` once per connection after `gateway.ready`.
- Key every approval and clarification by (`session_id`, `prompt_id`, `execution_generation`) as
  carried on the `approval.request` or `clarify.request` event; a response always echoes all three.
  Refuse a response that matches no outstanding request.
- A turn's outcome comes from `message.complete`'s status, never from an event's arrival.
- Interrupt is a latch: once interrupted, later writes for that turn are suppressed until a new
  `message.start`.
- Subagent rows are keyed by the server's `subagent_id`; a terminal state is never overwritten by a
  late start; late events never create rows.
- Merge usage field by field; never default a missing field to zero.
- Surface an unknown event type once per connection, not once per frame.
- A call whose connection dropped has an unknown outcome, never success; replies from a replaced
  connection never update liveness (use a per-connection generation counter).
- Approval responses may take up to 300 s; the client timeout must not be shorter.
- After a reconnect, replay each subscribed session from its last sequence number; if the gateway says
  a snapshot is required, call `session.resume`.

## Performance budgets

Measured with a pseudo-terminal harness at 160×48 (the approach in [u02](research/u02-talaria-performance.md)),
enforced in continuous integration on recorded fixtures.

| Budget | Value |
|---|---|
| Launch to first frame | ≤ 100 ms |
| Launch to a usable composer, gateway running | ≤ 200 ms |
| Keystroke to frame while a reply streams at 1× and 10× the recorded rate | ≤ 16 ms at the 95th percentile, ≤ 33 ms worst |
| CPU while streaming the reference recording | ≤ 5% of one core on average, ≤ 15% peak |
| Bytes written per streamed frame | proportional to changed cells; never growing with transcript length |
| Worst single frame | ≤ 50 ms |
| Idle | zero frames when nothing changes |
| Resident memory | ≤ 40 MB at start; ≤ 100 MB after a 2,000-message session |

## Security

- Tickets, tokens and keys are never printed, logged or recorded; the recorder applies redaction
  before anything reaches disk (method deny-set, URL credentials by position, route-aware HTTP bodies).
- The status-line command and any user scripts get an allow-listed environment.
- Untrusted text is rendered literally: no markup interpretation, control and bidirectional-override
  characters replaced by visible stand-ins.

## Stack

**Rust, with ratatui 0.30, crossterm 0.29 and tokio.** TypeScript on Bun with OpenTUI is the named
fallback. The call is close: the TypeScript builds needed fewer fixes, and the Rust builds are far
faster and lighter at runtime. The reasons, the costs and the conditions for switching are below.
[ADR 0010](../../../platform-specs/04-architecture/adrs/0010-rust-and-ratatui.md) records the decision.

### The bake-off

On 2026-10-22 four agents each built the same small client against the live gateway on a free model,
with a 120-minute time box. The client had to attach through the ticket path, create a session,
stream a reply, show tool calls with diffs, answer an approval, interrupt a turn, detach, record and
replay frames, and write finished output into native scrollback. Two builders ran Sonnet 5.5 at high
effort, the builder tier in the operator's staffing policy. The other two ran Haiku 5.5 at xhigh, the
policy's floor. The two Sonnet clients are kept in [reference-slices/](reference-slices/), and the
full results are in [research/u16-stack-bakeoff.md](research/u16-stack-bakeoff.md).

| | Rust, Sonnet | TypeScript, Sonnet | Rust, Haiku | TypeScript, Haiku |
|---|---|---|---|---|
| Every acceptance item worked live | yes | yes | yes | yes |
| Human help needed | none | none | none | none |
| Wall-clock minutes (self-reported) | 20 | 13 | 20 | 20 |
| Fixes needed (the builder's own count) | 11 | 3 | 5 | 6 |
| — of which terminal library or language | 6 | 0 | 1, not reproduced | 0 |
| — of which protocol surprises | 3 | 1 | 3 | 3 |
| Lines written, source and tests | 1,780 | 1,403 | 1,820 | 1,485 |
| Program start to `gateway.ready` | 12–26 ms | 271–533 ms, median about 300 | 23 ms | 271–350 ms, median 279 |
| Resident memory after a turn | 2.8–5.5 MB | 104–114 MB | 5.5 MB | 111–122 MB |
| Binary | 2.2 MB | 74.9 MB | 2.3 MB | 74.9 MB |

The builders measured start-up in slightly different ways, and the machine was heavily loaded, so
read the timings as orders of magnitude. They agree with the stack evaluation's controlled
measurement: a minimal ratatui program draws its first frame in 3.7 ms including process start, and a
minimal OpenTUI program takes 178 to 321 ms ([u11](research/u11-language-framework.md) §3.2).

### What the numbers say

1. **Moderate agents can build either.** All four clients passed every item, and none needed help.
   The Haiku builder wrote its Rust client with no compile errors at all.
2. **Rust's extra cost sits in one place: the terminal layer.** Six of the Rust Sonnet builder's
   eleven fixes were there, and so was the Rust Haiku builder's one unexplained failure. Three
   problems caused them:
   - ratatui's inline viewport asks the terminal for the cursor position, and crossterm cannot answer
     while its key reader is running;
   - ratatui's `insert_before` scrolls with an escape sequence (scroll-up, `CSI S`) that a terminal
     may not keep in its scrollback;
   - the first line was lost when the live region started on the top row.

   The TypeScript builders met none of these, because OpenTUI's split-footer mode and its
   `writeToScrollback` call handle them.
3. **The rest was the protocol, and it cost both languages the same.** Those traps are now listed in
   [03-hermes-today.md](03-hermes-today.md) §2.
4. **At runtime, Rust is in a different class.** It used about 20 times less memory, its binary was
   about 30 times smaller, and it reached the gateway in about 15 ms instead of about 300 ms.

### Why Rust

- **The performance budgets above are the operator's complaint written as numbers.** The TypeScript
  clients miss two of them before any feature exists. One is launch to a usable composer (budget
  200 ms; measured about 300 ms just to attach). The other is memory at start (budget 40 MB; measured
  about 90 MB attached and idle). Rust meets both with a wide margin.
- **The design multiplies the cost of each process.** "Open in new pane" runs one viewer per pane,
  and the fleet invites many. Ten panes would hold about 50 MB in Rust and about 1.1 GB in
  TypeScript (ten times the measured figures).
- **The extra friction is a one-time cost in one crate, and it has already been solved once.** The
  Rust reference slice contains a working answer to each terminal problem: a fixed viewport that the
  program moves itself, and the newline-scrolling insertion technique from OpenAI Codex, under the
  Apache-2.0 licence. Unit P1-06 is staffed at the top tier and is the only code allowed to write
  escape sequences, so moderate agents never meet these problems.
- **The compiler catches protocol drift.** When the types are regenerated from a new Hermes
  contract, a `match` with no catch-all arm fails to compile until someone handles each new event
  kind. TypeScript can do the same only where the code opts in with an exhaustive `switch` check;
  in Rust it is the default.
- **The evidence and the operator agree.** The stack evaluation ranked Rust first (81 against 78 out
  of 100, [u11](research/u11-language-framework.md) §5), and the operator's fourth point leaned
  towards Rust.

### What Rust costs, accepted knowingly

- **No reuse of Hermes's own TypeScript client.** That client is 8,672 lines under the MIT licence.
  Reconnect, replay, heartbeat and server-request deadlines are re-implemented in P1-02 and P1-03,
  and the `contract-drift` job keeps them in step with Hermes.
- **Fewer ready-made widgets** for the settings and fleet screens than OpenTUI offers.
- **Workflow scripts need an embedded JavaScript engine** (`rquickjs`). In TypeScript they would run
  natively.
- **Sonnet-tier agents need more fixes in terminal code:** 11 against 3 in the bake-off.

### When to switch to TypeScript and OpenTUI

Start from [reference-slices/typescript/](reference-slices/typescript/) if any of these happens:

- P1-06, the inline renderer, fails its acceptance twice at Opus 5.5 high.
- In phase 1, more than two units other than P1-06 need a workaround for the terminal library.
- Hermes publishes its TypeScript client as a supported, versioned package, and OpenTUI reaches 1.0.
  Reconsider at the start of phase 2, because reuse would then outweigh the runtime cost.

ADR 0010 decides which of these apply. Its switching conditions are the first two. The third is a reason to reconsider at the start of phase 2, not a reason to switch.

### What the bake-off did not measure

- **Keystroke latency and CPU use while a reply streams.** This was the operator's other complaint.
  The stack evaluation's micro-benchmarks put both stacks well inside budget: Rust re-renders a 16 KB
  message in 5.4 ms, and OpenTUI streams Markdown at 1.1 to 1.6 ms per frame. P1-11 measures this in
  the real client.
- **Real terminals.** Every scrollback check used the `pyte` terminal emulator. This is the most
  likely way the decision fails: the terminal layer passes in an emulator and then breaks in real
  terminals, with lines missing from scrollback or history duplicated on resize. That is why P1-06's
  definition of done includes a manual check in Herdr, tmux and one plain terminal.

### Versions the bake-off used

Rust stable 1.98, ratatui 0.30.2, crossterm 0.29, tokio 1, tokio-tungstenite 0.26 to 0.28 and
serde_json. Pin exact versions in P0-02, and name the APIs not to use in P0-04's patterns guide. Two
already belong on that list: `Viewport::Inline` resizing after start-up, and `insert_before` for
committing history.
