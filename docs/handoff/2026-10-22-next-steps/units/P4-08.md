Words used here:

- **Job**: one entry in a Hermes profile's cron store (`cron/jobs.json` under the profile's home).
  A job has a schedule, a prompt (or skills, or a script) and a delivery target.
- **Run** (or fire): one execution of a job. An agent run is an ordinary Hermes session whose
  `source` is `cron`; a script-only run writes an output document instead.
- **Socket**: the canonical gateway WebSocket Talaria is attached to (`P1-01`, `P1-02`).
- **REST**: Hermes's dashboard HTTP routes on the loopback `api_origin`, reached with `P4-01`'s
  `RestClient` and a fresh `native-http` ticket per request.

## 1. What this unit adds, in one paragraph

A full-screen **Scheduled jobs** overlay (`/cron`) for the connected Hermes profile. The list shows
every job, paused ones included, with its schedule, state, next run and last result, and refreshes
when Hermes says the cron store moved. From the list a person creates a job in a form, pauses or
resumes it, removes it, runs it now, and opens its detail card with the run history. List, create,
pause, resume and remove use the gateway method `cron.manage`; run now and run history have no
gateway method at v0.22.4 and use the dashboard REST routes, as Hermes Desktop does. It serves the
`configurer` and the `fleet-lead`, and it delivers the phase 4 operator check item "create a cron
job without leaving Talaria or opening a YAML file".

## 4. Design

### 4.1 Settled decisions (with reasons)

1. **Socket for the store, REST for runs.** `cron.manage` (H7) does list, add, pause, resume and
   remove; the roadmap names it and it needs no profile selector (H4). Run now and run history have
   no gateway method (H1, H7), so they use `POST .../trigger` and `GET .../runs` exactly as Hermes
   Desktop does (H28). The delivery-target list (`GET /api/cron/delivery-targets`) is REST too.
   Rejected: all-REST (the REST list returns raw records whose `last_error` is not redacted, H31,
   and every jobs route needs a profile selector, H29); `cron.submit` for run now (it is the
   scheduler's private producer path, H38); sending `/cron run` through `slash.exec` (refused on a
   viewer connection, H37).
2. **The REST jobs routes name the profile.** Every `/api/cron/jobs...` request carries
   `?profile=<percent-encoded connected profile name>` because Hermes refuses a `native-http`
   ticket on those paths otherwise (H29, H46). `P4-01`'s body and specification still say "no unit
   sends a profile selector"; that rule was written for `/api/config`, where an omitted selector is
   accepted. This unit is the one exception, and the value is always the ticket's own profile, which
   the ticket check verifies, so it cannot reach another profile. `/api/cron/delivery-targets` sends
   no selector. `P4-01`'s owner should add this exception to `P4-01`; until then the exception
   lives here. `RestClient::request` takes the path and query as one string, so no client change
   is needed; if `P4-01`'s client rejects or rewrites a `profile` query, stop.
3. **The list always asks for paused jobs** (`include_disabled: true`), or a paused job would look
   deleted (H8).
4. **`name` carries the job id for pause, resume and remove** (H10). Talaria always sends the
   `job_id` from the row, never the display name, so a duplicate name can never act on the wrong job.
5. **A result with `success: false` is a failure** (H11). The service turns it into
   `CallFailure::Tool`; nothing treats a `result` frame as success by itself.
6. **Run now confirms first, says which model it will use without promising one, and warns when it
   will resume a paused job** (H32, H40, H43). It costs tokens, may deliver to a messaging
   platform, and on a paused job it changes the schedule.
7. **Run now runs in the background.** The REST call waits for the whole job (H31), so it runs on a
   background task with a 24-hour deadline (Desktop's value, H33); the overlay never waits on it, and
   closing the overlay does not cancel it.
8. **Talaria reads nothing from the REST trigger reply.** `trigger_job` drops the body before it
   returns (it returns `Result<(), RestError>`), so no caller can show, log, trace or record it.
   What Talaria says about a run comes from a fresh socket list: the row's `last_run_at`,
   `last_status`, `last_error` (redacted by Hermes, H20), `last_delivery_error` and
   `last_fire_error` (not redacted by Hermes, H44, so Talaria hides credential-shaped text itself,
   decision 14).
9. **Refresh = `cron.changed` + backstop.** A list on open, after each write, on `cron.changed`
   (debounced, coalesced), and every 60 s while the overlay is open, because `cron.changed` watches
   only the launch profile (H26).
10. **`/cron` is a Talaria local command.** It shadows Hermes's own `/cron`, whose write forms are
    refused on Talaria's connection anyway (H37). `P2-03`'s rule that a local entry wins applies.
    Talaria does not parse Hermes's `/cron add <schedule> <prompt>` syntax; the form replaces it.
11. **No schedule parser in Talaria.** Hermes parses and explains (H12, H13); Talaria shows the
    examples and Hermes's error text.
12. **Every call acts on the connected profile only**; no profile picker in this unit. The REST
    selector, the overlay title and every notice use one value: the profile `CronService` was built
    with, which is `P1-12`'s `OpenConnection.profile_name` of the foreground connection.
13. **Agents never change Hermes configuration, run `hermes update` or restart the gateway.** Live
    writes need the operator's opt-in (`TALARIA_PROBE_WRITES=1`) and touch only `fixture`.
14. **Talaria hides credential-shaped text in the fields Hermes does not redact.** Before any text
    reaches the reducer, the service passes `last_error`, `last_delivery_error`,
    `last_fire_error.detail`, `paused_reason`, every tool `error`, every RPC `message` and every REST
    failure detail, and the free-text run and preview fields (run `title` and `preview`, the job's
    `prompt_preview`), through `hide_secrets` (4.12). Then the core sanitises each line (4.12). Job
    names, schedules, `deliver` values and target names are deliberately not hidden: they are labels
    the person chose, and hiding one would make its row unidentifiable.
15. **The `last_fire_error` contract defect is fixed at the contract boundary, not here.** Hermes
    writes `last_fire_error` as an object `{at, detail}` (H39) while the contract's `CronJobRow`
    declares string or null. `P0-03`'s rule is that contract errors are corrected only in
    `crates/hermes-contract/src/overrides.rs`, each with a comment citing Hermes and a test. This
    unit adds that one override as a named minimal touch (4.2). If `P0-03`'s override mechanism
    cannot change a result field's type, stop and report to `P0-03`'s owner; never edit
    `src/generated/`, never use `call_raw`, never coerce the object to a string silently.
16. **Replies are fenced by request number and by connection generation** (4.13). A list or
    history reply older than the newest applied write is ignored; anything from a replaced
    connection (a profile switch) is dropped, except a run-now outcome, which becomes a notice that
    names its original profile.

### 4.3 The list

Title: `Scheduled jobs · profile <p>`. Under it, when the last list carried `warning` (H17), one
banner line in the warning colour: the sanitised `warning` text, cut to the width by the renderer.
The banner follows the newest successful list reply (gone when one arrives without `warning`); a
failed list keeps the current banner.

Columns, left-aligned, one space apart, for a body width `W`: at `W >= 100`, name 28, schedule 22,
state 36, last run `W - 89`; at `W < 100`, no last run, schedule 18, state 24, name `W - 44`. A text
longer than its column is cut to the column width minus one, plus `…`. When the width is below 60
or the height below 12 (either one), the renderer draws T20 only. The view holds full texts; only
the renderer cuts to width.

Order: `scheduled` jobs by next run (earliest first; a job with no readable `next_run_at` after
those that have one), then `paused`, then `completed`, then `error`, then every other state,
grouped by state text (byte order of the lower-cased state). Inside every group the order is by
name (case-insensitive), then `job_id`, after the next-run key in the scheduled group.

State column (`job_state_label`, first match wins; `ahead = next_run_unix - wall_unix`):

| Condition | Text |
|---|---|
| a run started here is outstanding (4.6) | `running now (started here)` |
| `state == "paused"` | `paused` |
| `state == "completed"` | `finished` |
| `state == "error"` | `schedule error` |
| `state == "scheduled"`, `next_run_at` parses, `ahead > 60` | `next <relative>` (for example `next in 3h 12m`) |
| `state == "scheduled"`, `next_run_at` parses, `ahead <= 60` (past included) | `due now` |
| `state == "scheduled"`, no or unparseable `next_run_at` | `scheduled` |
| any other state | the state text, sanitised |

So 59 s and 60 s ahead read `due now`; 61 s ahead reads `next in 1m`.

Last-run column (`last_run_label`): empty when `last_run_at` is null or unparseable; otherwise
`<status> <relative>` where status is `ok` → `ok`, `error` → `failed`, `delivery_failed` →
`delivery failed`, anything else → the value with `_` as spaces (for example `blocked config`);
a null status with a set `last_run_at` gives `ran <relative>`. Example: `failed 2h ago`.

Relative text (`relative(from, to)`), `d = to - from` in whole seconds, every unit **floored**:
`|d| < 60` → `now`; below an hour `in <m>m`; below a day `in <h>h <m>m` (`in <h>h` when the
minutes are 0); otherwise `in <D>d <h>h` (`in <D>d` when the hours are 0). Past values use the same
units with ` ago` (`5m ago`, `2h 10m ago`). Boundary examples (test 2):

| d (s) | text | d (s) | text |
|---|---|---|---|
| 59 | `now` | -59 | `now` |
| 60 | `in 1m` | -60 | `1m ago` |
| 3599 | `in 59m` | -3599 | `59m ago` |
| 3600 | `in 1h` | -3600 | `1h ago` |
| 86399 | `in 23h 59m` | -86399 | `23h 59m ago` |
| 86400 | `in 1d` | -86400 | `1d ago` |

`parse_iso_instant` accepts `YYYY-MM-DDTHH:MM[:SS[.fraction]]` followed by `Z` or `±HH:MM`, and
returns the Unix instant plus the wall text `YYYY-MM-DD HH:MM` as written (Hermes's zone). Anything
else is `None` (the detail card then shows the raw string, sanitised). No new date-time dependency.

Filter: typing printable characters on the list filters (`y` and `n` with no open question too;
a filter change is a silent state change that emits no effect); every space-separated, lower-cased word
must be a substring of the lower-cased `"<name> <schedule> <prompt_preview> <deliver>"`.
Backspace edits the filter; Esc clears it, a second Esc closes the overlay. The selection follows
the selected `job_id` when rows change; if it is gone, the nearest row above is selected.

Empty and failure states (texts in 4.9): T2 not connected; T3 loading; T4 no jobs; T5 no match;
T6 list failed (keeps the last rows if there were any, with T6 as `ListView.status`).

### 4.4 Refresh rules and the one timer

The reducer keeps a small set of deadlines (`Instant`s): `debounce`, `backstop`, `minute`,
`history_poll`, `history_backstop`, `pending_expiry`. After every `update` it computes the earliest
deadline. If that differs from the timer it last asked for, it emits exactly one
`ScheduleTick { after: earliest - now }`; the app keeps one timer, and a new `ScheduleTick`
replaces the old one. `Tick` handles every deadline at or before `now`, then re-arms as above. The
minute deadline is computed from `wall_unix`: the next whole minute (`60 - wall_unix % 60` seconds).

- `Open` emits `List { seq }` (unless a list is in flight) and arms `minute` and `backstop`.
- `seq` is a counter in `CronState`, incremented for every `List` and every `Runs`.
- **At most one `List` in flight and at most one queued.** Any reason to list while one is in
  flight sets `queued`; when the in-flight reply arrives, a queued list is emitted.
- After any write's reply (success or failure) the reducer lists (or queues). The write's reply
  records `fence = <seq of that List>`; a `Listed` with `seq < fence` is ignored except that it
  clears "in flight" (so a list sent before a pause cannot undo the row the pause reply replaced).
- `Changed`: while closed, ignored (but see 4.6: a settling run lists even while closed). While
  open, if `debounce` is unset it is set to `now + 300 ms`; further `Changed` within the window do
  nothing. When `debounce` fires, the reducer lists (or queues) and, if a detail card is open,
  loads runs (or queues).
- `backstop`: while open, `now + 60 s` after every `Listed` reply, `Ok` or `Err` (a failed list is
  retried 60 s later); when it fires, list.
- `minute`: while open, at each whole minute; it emits nothing but makes the view change (relative
  texts), so the app draws one frame if `view()` differs.
- The detail card's history: `Runs` on opening the card; on `debounce` as above;
  `history_backstop` 60 s after each `RunsLoaded`; `history_poll` every 2 s while a run started
  here for that job has no matching row (4.6), ending at `pending_expiry` (90 s after `y`).
  At most one `Runs` in flight; a `RunsLoaded` for a job whose card has closed, or with a `seq`
  older than the newest `Runs` sent, is ignored.
- Close clears every deadline (`debounce`, `backstop`, `minute`, `history_*`, `pending_expiry`).
  The app's timer may still fire once; a `Tick` with no deadline due does nothing. A settling run
  needs no timer: its list is an effect and its reply is handled while closed (4.6).

Idle example for test 7 (open at wall `12:00:30`, list replies arrive at once, no `Changed`): over
600 s the reducer emits exactly 10 `List` effects (at 60 s, 120 s, ... after each reply), the
minute deadline fires 10 times (12:01:00, 12:02:00, ...), and every other effect is a
`ScheduleTick` whose `after` equals the time to the next deadline. Nothing else is emitted. The
opening `List` (at 0 s) is not one of the 10: they are the backstop lists at 60, 120, ... 600 s,
the one at 600 s included.

Frames: the app draws a frame only when `view()` differs from the last drawn `CronView`
(`PartialEq`). A backstop reply with unchanged rows draws nothing; a minute tick draws one frame
when a relative text changed.

### 4.5 The add form

Opened with Ctrl+N or `/cron new` (alias `/cron add` with no further words). Emits

Editing keys: Tab and Down move to the next field, Shift+Tab and Up to the previous (in Prompt, Up
and Down move between its lines; Tab still leaves it). Left, Right, Home, End, Backspace and Delete
edit the focused text field at the cursor. Enter inserts a newline in Prompt and moves to the next
field elsewhere. On Deliver, Left/Right (and Up/Down) move between choices, skipping unselectable
ones. `Paste(text)` inserts at the cursor; in single-line fields every `\r\n`, `\n` and `\r`
becomes a space; in Prompt newlines are kept. The state keeps a private cursor per text field;
`FormView.cursor` is the focused field's `(line, column)` in characters (line 0 in single-line
fields, `None` on Deliver). Home and End go to the start and end of the current line; PageUp and
PageDown move 10 lines in Prompt and do nothing elsewhere. Enter on Deliver moves to Name. Ctrl+S
(`cron_save`) saves from any field. Esc cancels: if any field differs from its default it asks T24
first. While the form is locked (Saving) Esc and every editing key do nothing; only the reply
unlocks it, so an add reply never arrives after its form closed.

Ctrl+S with field errors shows each under its field, sends nothing and leaves the focus where it
was. Otherwise it emits
`Add(AddRequest)`, shows T13 in the form status, and locks the form. On success the form closes,
the filter is cleared, the new row is selected (by `job_id` once the list reply has it), and the
notice line is T14. On a tool failure (H11) the form stays open and unlocked; the status shows
T15: `Hermes did not create the job:` then Hermes's `error` split on newlines (each line sanitised,
at most 8 Hermes lines after that header line). The bad-schedule help has six lines in total (H12). On H16 (`job_saved: true`)
the form closes and the notice line is T16; the list reloads.

### 4.6 Run now (state machine)

```text
Idle --ctrl+t--> Confirm(job) --n/esc--> Idle
Confirm --y--> Waiting(job, last_run_at_at_click, started_at = wall now) [emit Trigger]
Waiting --Triggered(Accepted)--> Settling [list, even while closed]
Settling --Listed (seq at or after the settle list)--> Idle [T17a/b/c/e from the row, T17d unchanged, T17f row gone]
Waiting --Triggered(Failed(Refused{409}))--> Idle [T18a]
Waiting --Triggered(Failed(NotFound))--> NotFoundCheck [list]
NotFoundCheck --Listed--> Idle [row gone: T18b; row present: T18f]
Settling or NotFoundCheck --Listed(Err(f)) at or after its list--> Idle [T17h with the 4.8 text for f]
Waiting --Triggered(Failed(Unknown))--> Idle [T18d, list when connected]
Waiting --Triggered(Failed(NotSent(r)))--> Idle [T18e]
Waiting --Triggered(Failed(other))--> Idle [T18c with rest_reason]
any state --Triggered for a job with no outstanding run--> unchanged [ignored]
```

- Confirm text: T19a for a job whose state is not `paused`; T19b for a paused job (it will resume).
  T19b carries the same `<how>` part, and the same T19c, as T19a.
  The `<how>` part of T19a: `It runs its script only, with no agent` when `no_agent`; `It uses its
  pinned model <model>` (plus ` on <provider>` when set) when `pinned`; otherwise `It uses this
  profile's cron model (cron.model, else the main model)` (H40). When `deliver` is not `local`, T19a
  adds T19c (H43).
- Ctrl+T while REST is unavailable: T21 on the notice line, nothing else.
- One outstanding run per job from this Talaria; Ctrl+T on a job that is `Waiting` or `Settling`
  gives T22. Runs of different jobs may be outstanding together. Writes (add, pause, resume,
  remove) remain allowed while runs are outstanding, one write at a time (4.8).
- Settling compares the fresh row's `last_run_at` with `last_run_at_at_click`: changed → T17a
  (`ok`), T17b (`error`, with `last_error`), T17c (`delivery_failed`, with `last_delivery_error`),
  T17e (any other status, for example `blocked_config` or `delivery_queued`); unchanged → T17d; row
  absent → T17f (a one-shot job removes itself after its last run, H45).
- The pending history row: while `Waiting` or `Settling` and the job's card is open, the history
  shows a first row `starting… (requested <relative>)` until a run row with
  `started_at >= started_at_click - 2` appears, or 90 s pass; meanwhile `Runs` every 2 s (H27 uses
  1 s; 2 s halves the load).
- **State lifetime.** `CronState` lives as long as the foreground connection (4.13). Close keeps
  rows, outstanding runs and an in-flight write; Open resets the screen (list or form), clears the
  filter and lists. The outstanding-run map lives in `CronState`, so a second Ctrl+T after a
  close and reopen still gives T22.
- Quitting Talaria drops the request; Hermes keeps running the job in its own thread pool (read
  from code; section 9 item 7).

### 4.7 Run history and the detail card

Enter on a row opens the detail card: name and id; schedule and repeat; deliver; state (4.3 text)
plus `paused <wall>` and `paused_reason` when present; next run (wall and relative); last run with
status; `last_error`, `last_delivery_error` and `last_fire_error` (its `detail`, with `at` as wall
text when it parses) when present (after `hide_secrets`, split and sanitised, at most 6 lines
each); prompt preview (Hermes's 100-character preview; Talaria never has the full prompt from the
socket); skills, model and provider (with `pinned`), workdir, and tags `script`, `no agent`,
`continuity` when present. Then **Recent runs**.

Run rows (`run_status`, first match wins):

| Row | `RunStatus` | Status text |
|---|---|---|
| `source == "cron"`, `scheduler_owned` | `Running` | `running` |
| `source == "cron"`, `ended_at` null, `is_active` | `Running` | `running` |
| `source == "cron"`, `ended_at` null otherwise | `Unclosed` | `did not finish` |
| `source == "cron"`, `ended_at` set | `Finished(end_reason)` | `finished`, plus ` · <end_reason>` when it is a non-empty string |
| `source == "cron_output"` | `Output(word)` | `output`, plus ` · <word>` |
| any other source | `Other(source)` | the source, sanitised |

`cron_output` rows are not proof of a script run: Hermes also makes them for ledger attempts that
left no session and no output document, failed agent fires included (H42). `word` is the title's
text before the first ` · ` (or the whole title when there is none), lower-cased, but only when that
text consists solely of upper-case ASCII letters, spaces and underscores (`COMPLETED`, `FAILED`,
`OK`, `ERROR`, `DELIVERY FAILED`); otherwise `word` is `None` (`Script-only run` gives `output`).

Each run row (`RunRowView`): start (`relative(started_at, wall)`; empty when `started_at` is null), status, duration
(`duration_text(ended_at - started_at)` when ended, else empty), tokens (`<in>/<out> tokens` as
plain integers without separators when either is non-zero, else empty), title (else preview,
else the run id; first line only). Renderer column widths: start 12, status 24, duration 9, tokens
18, title the rest.

`duration_text(s)`: below 60 → `<s>s` (`0s`, `45s`); below 3600 → `<m>m <ss>s` (`3m 05s`); else
`<h>h <mm>m` (`1h 00m`, `1h 02m`, `25h 00m`). Negative values give `0s`.

Decoding (in the service): a runs reply without a `runs` array, or a targets reply without a
`targets` array, is `RestFailure::BadBody`. A run row without a string `id` or `source`, or a target
without a string `id`, is skipped. Epochs accept JSON integers and floats; any other type is
`None`. Missing or mistyped counts are 0, booleans false, optional strings `None`; a target's
missing `name` is its `id`, a missing `home_target_set` is false, and `local` is always selectable.

The card opens with its fields focused (`CardFocus::Fields`); Tab and Shift+Tab move focus between
the fields and Recent runs, and the renderer draws the focused section's heading in the accent
style. Fields focused: Up and Down scroll one line, PageUp and PageDown 10, Home and End to the top
and bottom (`fields_scroll`); Enter does nothing. History focused: Up and Down move between runs,
PageUp and PageDown 10 runs, Home and End to the first and last. Ctrl+R on the card reloads the list
and the card's runs. Enter on a run shows the run card (id, source, started and ended as relative text
and UTC `YYYY-MM-DD HH:MM:SS UTC`, duration, model, messages, tool calls, tokens, end reason,
title, preview split and sanitised to 12 lines). `o` (`cron_open_run`) on a run whose status is
`Finished` emits `OpenSession { session_id: id }`; on any other run it shows T23.

History states: T8 loading; T9 no runs; T10 REST unavailable (with the reason); T7 failed. History
failure mapping (`rest_reason`: `RestFailure` → `<reason>` in T7, T18c and T17g):

| Failure | `<reason>` |
|---|---|
| `Forbidden(d)` | `Hermes refused the request (403 <d>)` |
| `NotFound` | `Hermes answered 404 (the job or the route is not there)` |
| `Refused { status, detail }` | `Hermes refused the request (<status> <detail>)` |
| `Server(s)` | `Hermes failed (<s>)` |
| `Unauthorized` | `Hermes refused the ticket` |
| `Unknown` | `the reply was lost` |
| `NotSent(r)` | `<r>` |
| `BadBody(t)` | `the reply did not decode` |

Delivery targets use the same failure set but always show T12 (the reason is not shown).

### 4.8 Writes and failures

- One write (add, pause, resume, remove) at a time; a second one gives T25 and sends nothing.
- Pause and resume (Ctrl+E): `paused` rows resume, all others pause. A `completed` job gives T26 and
  sends nothing. No confirmation: Ctrl+E is the deliberate action (test 27). Reply
  `{success: true, job}` replaces the row at once; notices T27a (paused) or T27b (resumed, with next

  ignored (the list after the write corrects the screen); the notice uses the reply row's name. An

- Remove (Ctrl+D): T28 confirmation; `y` emits `Remove`; reply → the row leaves, notice T29; if
  that job's detail card is open it closes and the nearest row above is selected.

### 4.12 Secrecy and hostile text

- `hide_secrets(text)` (in `crates/talaria-app/src/cron.rs`) calls `P1-04`'s
  `hermes_client::redact::scan_for_secrets(text)`; if it returns any hit, the whole text becomes
  T33; otherwise the text is returned unchanged. It never logs the text. It is applied in the
  service to every field named in decision 14.
- `split_and_sanitise(text, max_lines)` splits on `\r\n`, `\n` and `\r`, passes each line through
  `P1-06`'s `history::sanitize` (which works on one line), and keeps at most `max_lines` lines
  (the last kept line ends with `…` when lines were dropped). Every multi-line Hermes text uses it;
  single-line texts use `history::sanitize` directly.
- Allowed REST projections: delivery-target `id` and `name`, and the run-row fields of 4.7. They
  are sanitised like every Hermes string. The raw trigger reply is never read (decision 8). This
  unit's code writes no REST body and no Hermes error text to `tracing` at any level, or to a
  recording. What `P1-02`'s `Client` and `P4-01`'s `RestClient` log is their own issues' rule and
  is never changed here; test 33 captures `tracing` end to end, and if it shows a value logged
  inside either client, stop and report to its owner.

### 4.13 Connection generations

- The app owns at most one `(generation, CronState, CronService)` for the foreground connection.
  `generation` increases only when the foreground **profile** changes (`P2-07`'s different-profile
  switch; switching away and back counts twice), and then the app builds a new `CronState` and
  `CronService`. A same-profile reconnect or same-profile session switch keeps `generation` and
  `CronState`: the app builds a new `CronService` on the new `Client` with the same generation and
  feeds `Connection { up: false }`, then `Connection { up: true }`. Calls in flight on the old
  client end as `P1-02` reports them (`Unknown` → T31 or T18d) and apply, their generation being
  current.
- Every spawned task carries the `CronTag` from `CronService::tag_for(&effect)`, taken when the
  effect is spawned. When its inputs arrive: current generation → each goes to `update`. Older
  generation → all are dropped, except a `Triggered` whose tag has `run_name`: the app commits a
  `NoticeCell` `Scheduled jobs: <stale_run_notice(run_name, tag.profile, tag.profile == the current
  profile, &outcome)>`. The old `CronState` is not needed.

### 4.14 App wiring (answers for the builder)

- **Socket timeouts.** List: `Client::call_with(params, CallOptions { timeout: Some(15 s) })`;
  writes: 30 s (`P1-02`). `P1-02` knows whether the frame was written: `TimedOut` and `Unknown`
  have `outcome_unknown()` true (→ `CallFailure::Unknown`); `NotConnected`, `Encode` and
  `InvalidTimeout` sent nothing (→ `NotSent`). The service adds no timer of its own. REST deadlines
  go in `RequestOpts` (15 s for runs and targets, `trigger_opts()` for run now).
- **REST availability.** `CronService.rest` is the truth; the app builds
  `CronState::new(profile, service.rest_status())` from the same service, so the two never
  disagree. `rest` is `None` only when `P4-01` gives no client (no `api_origin`): a runtime fact,
  no build switch. A route refusing at run time shows its failure text (T7, T18c). `P4-00`'s finding
  (`docs/analysis/<date>-hermes-configuration-surface.md`) studies the configuration routes and may
  say nothing about `/api/cron/jobs/*`; then tests 43 and 45 are the evidence. If it says a
  `native-http` ticket cannot reach those routes, build with `rest: None` and say so in the pull
  request.
- **`o` routing.** In `KeyContext::Cron` the key bound to `cron_open_run` becomes
  `CronKey::Action(OpenRun)` only while `state.history_focused()`; otherwise it is sent as the key
  it is (`Char('o')` by default, so it can be typed into the filter or a form field). Every other
  `CronAction` is always an action. `update` ignores `Action(OpenRun)` when history is not focused.
- **`OpenSession { session_id }`.** The app closes the overlay (as for `CloseOverlay`) and calls
  `P2-07`'s `switch_foreground(app, RowKey { profile: service.profile().into(), session_id })`.
  `SwitchOutcome::Failed { text }` becomes a `NoticeCell` `Scheduled jobs: <text>`; `Switched`
  shows `P2-07`'s own notice. Whether Hermes resumes a `cron` session is section 9 item 10
  (`session.resume`, `tui_gateway/methods_session.py:1049`, has no `cron` check at v0.22.4; verify
  at the pinned commit before relying on it); if it refuses, the person sees that refusal text and
  no code changes.
- **Frames.** `talaria-tui`'s `CronFrameGate` keeps the last drawn `CronView`; `app.rs` calls
  `needs_draw(&view(&state, wall))` after each `update` and calls `draw_cron` only when it returns
  true. Test 40 drives the core through the gate and counts the `true`s.

## 6. Mock-server rules

The mock gateway (`P1-12`'s `crates/talaria-app/tests/support/mock_gateway.rs`) gains one
`cron.manage` handler and the ability to push a `cron.changed` event; the mock REST server
(`P4-01`'s `MockRest`) gains three routes. Both follow these rules, taken from section 2 and
nothing else:

1. `cron.manage` keeps an in-memory list of rows in the H20 shape. Unknown param keys → `4000`.
   Unknown `action` → `4016`.
2. `list` returns only enabled rows unless `include_disabled` is truthy (H8), with `count`, and
   `gateway_running: true` when non-empty.
3. `add` requires a non-empty `schedule` and `prompt` (else `{success: false, error}` with the H12
   texts); it accepts any schedule string except two: exactly `blue moon` returns the six-line H12 error,
   and exactly `every blue moon` returns the one-line H47 duration error (texts as in 5.1); it creates a row with a 12-character lower-case hex `job_id`.
   A test hook makes the next add return the H16 partial failure.
4. `pause`, `resume`, `remove` look `name` up as an id, then as a case-insensitive name; two name
   matches return the H10 `matches` failure; none returns the not-found failure.
5. Every write moves a counter; the test decides whether the mock then pushes `cron.changed` (to
   simulate a launch profile) or not (a non-launch profile).
6. The REST routes are added with `P4-01`'s `MockRest::with_route(method, path, handler)`; if a
   handler cannot delay its reply, answer 409, or close the connection after reading the request,
   stop and report to `P4-01`'s owner. The mock gateway gains, additively (never changing existing
   behaviour): a `cron.manage` handler, a way to push a global event frame, and a hook that drops
   the connection after reading the next frame of a named method. If `P1-09` or `P1-12` already
   provide an equivalent hook, reuse it.
   REST `POST .../trigger` checks `profile` equals the configured profile (else 403); unknown id →
   404; a hook can delay the reply, return 409, or drop the connection after reading the request.
   On success it sets the row's `last_run_at` to now, `last_status` to `ok` (or the hook's value),
   and, for a paused row, enables it (H32).
7. REST `GET .../runs` requires `profile` (else 403) and returns the configured rows.
8. REST `GET /api/cron/delivery-targets` must not require `profile`; it returns `local` plus the
   configured targets.
9. No handler invents a field or a code not in this document. A new need goes back to the test
   author with the Hermes line that justifies it.

## 7. Edge cases

| Case | Behaviour |
|---|---|
| A job's `name` is empty in storage | Hermes fills it from the prompt (H20); Talaria shows what it gets, or the id if still empty |
| Two jobs with the same name | Both shown; every write uses `job_id` (decision 4) |
| `next_run_at` in an unexpected format | State `scheduled`; detail shows the raw string |
| `state` is `error` | `schedule error`; detail shows `last_error`; Ctrl+E pauses (allowed) |
| `state` is `completed` (one-shot done) | `finished`; Ctrl+E gives T26; Ctrl+T confirms and sends (Hermes decides; 409 or 404 are mapped) |
| A job removed elsewhere while its card is open | Next list drops it; the card closes with T18b |
| `cron.changed` storm during a scheduler tick | Debounce and one queued list (4.4) |
| Non-launch profile (no `cron.changed`) | 60 s backstop list keeps the screen fresh |
| Gateway not running the scheduler (`warning`) | Banner line above the list |
| REST unavailable (no `api_origin`, or `P4-00` found the routes unusable) | List and writes work; history shows T10; Ctrl+T shows T21; the form offers only `local` |
| Trigger reply after the job was removed | `Accepted` then row gone → T17f; `NotFound` then row gone → T18b |
| A row whose `last_fire_error` is an object | Decoded as `FireError` (H39, decision 15); the card shows its detail |
| Profile switch while a run is outstanding | The old run's outcome becomes T17g naming the old profile; its list replies are dropped (4.13) |
| A list reply sent before a pause arrives after the pause reply | Ignored by the fence (4.4) |
| Talaria reconnects while a write is in flight | T31; list after reconnect; never resent |
| Talaria quits while a run is outstanding | The request is dropped; Hermes keeps running the job (section 9 item 7) |
| Very long prompt preview, error or title | Sanitised and cut; detail wraps to the stated line limits |
| Hostile text (escape sequences, bidirectional controls) in any Hermes string | `history::sanitize` before drawing (test 26) |
| Delivery target with `home_target_set: false` | Shown dimmed, not selectable |
| Prompt over 16,000 characters | T11d; nothing sent |
| `repeat` typed as `0`, `-1`, `3.5`, `abc` or `10000` | T11e; nothing sent |
| Run row with no `title` and no `preview` | Shows the run id |
| A run whose `ended_at` is null and not owned | `did not finish` |
