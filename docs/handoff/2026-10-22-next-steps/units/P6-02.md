## 3. Design

Talaria already has a pure fleet registry (state, queue, ordering), a fleet view (rows, peek, answer, stop), and an application layer that owns connections and reports owned sessions into the registry. The ACP adapter is another application service with that shape, plus the seam, built first in this unit, that lets an external backend live in the same registry, queue and view.

- `talaria-core` gains the pure module `fleet::acp`: decoded ACP values in, registry inputs, transcript cells and queue items out. It holds the mapping (section 5), the state rules and the transcript accumulation, and calls the core sanitiser (S6). It spawns nothing and reads no clock; time arrives on its inputs.
- `talaria-app` gains `acp`: configuration parsing, subprocess ownership, stdio framing, request correlation, timeouts, permission responders and the transcript store. One service owns all ACP agent processes; one process may hold several sessions.
- `talaria-tui` changes only through the seam: row detail text (backend tag plus agent name), the peek's ACP content source, and the ACP launch affordance.
- `talaria-cli` gains `talaria acp agents [--probe]`.

Why not a new crate: the workspace layout has no ACP crate, and the adapter is small (one transport, one mapping). A crate split can be proposed later if a second ACP consumer appears.

Session ownership rule: an ACP row exists only while its agent process lives and only inside the Talaria run that spawned it. No disk state, no reopening (REQ-6).

### 3.1 The seam stage (REQ-0): exact contents, naming and gate

The parent assigned the seam to this unit as its first stage, in the same branch and pull request as the adapter (the parent's decision 6; the parent's specification, section 5, holds the same rules). There is no separate seam pull request and no merged-seam start gate.

- Marker: every seam commit uses the conventional-commit scope `fleet-seam`, and seam commits come before any adapter commit (adapter commits use another scope).
- Gate, at the newest `fleet-seam` commit and before any adapter commit: the suites of the phase 3 fleet units (registry, fleet view, attention) pass unchanged, using the commands the parent's specification section 5 copies from their Verification sections (re-read at scheduling), plus the seam tests the planner names for S1 (row tag and `fleet list` fields), S2 (external input and responder-keyed slot), S5 (launch affordance) and S6 (one sanitiser, custody check in both crates). The test author writes those seam tests first and records their red run, like every other test. Then the reviewer posts `Seam stage reviewed: <that commit>` on the pull request.
- S3 (transcript cell type and peek source) and S4 (backend-routed answer and stop) are seam code verified only at merge, by this unit's tests (S4 by issue test 21).
- A seam fix after adapter commits started is a new `fleet-seam` commit; the gate is rerun at it and the reviewer posts a new `Seam stage reviewed:` line. The latest one counts.
- Where S2 and S5 below leave a choice, the planner makes it before the test author starts and writes the chosen shape and the seam's type names into the issue.

These are the seam's items; the adapter is written against them.

- S1 Row identity and display. `FleetRow` gains a backend discriminator (`Hermes` versus `Acp`), an optional agent display name, and usage presentation fields that can hold context occupancy (`used`, `size`) and a cost as amount plus currency text (never assumed dollars). The row-detail function (in `talaria-core::fleet_view`, the function that builds a row's detail text) renders `[acp <display name>]` for ACP rows. `talaria fleet list` text shows the same tag and its versioned JSON gains additive `backend` and `agent` fields; the fleet format document records them. Hermes rows render exactly as before.
- S2 Registry input and queue identity. The registry gains an input for an owned external session (proposed shape: an `External`-style variant carrying the namespaced key of REQ-7, the backend, title, model, activity, row state and outcome, plus needs) or an equivalent extension of the subscribed path — the planner picks one shape and records it. The queue gains a slot variant for an external permission whose identity is an opaque responder key (REQ-10), and a queue item gains an options list carrying each option's identifier, name and kind alongside the existing string choices used for Hermes. Hermes items keep their exact current behaviour.
- S3 Transcript and peek. A pure transcript cell type lives with the adapter's core module (section 4): text, thought, tool (title, body, status), plan and notice cells, all sanitised strings. The service holds one transcript per ACP session. The peek panel gains a content source that can render an ACP transcript snapshot where it today renders only a Hermes session state; Hermes peeking is unchanged. No Hermes session state is built for an ACP session and the session reducer is not touched.
- S4 Backend-routed actions. The application wiring routes the fleet view's answer and stop intents by the row's backend: Hermes rows keep the existing Hermes answer (`approval.respond`) and stop (`session.interrupt`) paths; ACP rows go to `AcpService::answer_permission` and `AcpService::cancel`. Acceptance: the mixed-backend wire test (issue test 21) with a Hermes mock proving zero Hermes requests for ACP answer and stop.
- S5 Launch affordance. Starting an ACP session is reachable from the fleet view: either the existing launch dialog gains an ACP mode (pick agent, working directory defaulting to Talaria's launch directory, first prompt) or a sibling ACP dialog owned by this unit is opened from the same "new" action. The planner picks one and records which files carry it. The Hermes launch modes are unchanged.
- S6 One sanitiser in the core. The character table today owned by the inline renderer (`sanitize` in the terminal crate's history module) moves to `talaria_core::text::sanitize` with identical outputs; the terminal crate re-exports it so its callers and tests keep passing. No second copy of the table exists anywhere (checked by the custody tests of both crates).

Every operator-facing error is a plain sentence: command not found, version mismatch naming both versions, agent refusal carried verbatim, timeout naming the agent.

## 5. Mapping: ACP traffic to fleet state

Turn state rule (corrects the earlier draft): turn state comes only from the prompt lifecycle and from transport or process failure. A failed tool call is a tool status, not a turn outcome.

| ACP traffic (snapshot names; V2, V3) | Fleet effect |
|---|---|
| `session/new` result | One row, backend `acp`, profile key `acp:<agent-id>` (REQ-7), title from the first prompt until a session information update names it, state Idle |
| Prompt sent, no result yet | State Working |
| Agent message / thought chunk | Consecutive chunks join into one text (or thought) cell until a non-text cell intervenes; append that joined cell to the adapter transcript |
| Tool call | Create one tool cell (identifier, title) |

| Plan update | Row activity becomes the current plan step (one line); also a plan cell in the transcript |
| Available commands / mode / config option updates | Stored for the peek panel; the model shown on the row comes from the model config option when reported; no state change |

### 5.1 Permission items and responders

One item per JSON-RPC permission request, never per tool call. The service keeps a `PermissionResponder` (connection generation plus the request's own identifier, the ACP session key, and the tool-call identifier as association data). The queue item's identity is the session key plus that responder identity (through the seam's S2 slot); its options carry identifier, name and kind. Answering sends exactly one reply to that responder with the selected outcome carrying the chosen option identifier; a duplicate or late answer finds no responder and reports already settled. Rejection is the operator selecting the agent's reject-kind option. Cancellation (operator stop, or Talaria closing while the channel is writable) replies to each outstanding responder of the turn exactly once with the cancelled outcome and removes its queue item; after process death responders are dropped with no reply claimed.

## 6. Wire shapes (snapshot; all verify at scheduling per V1 to V3)

Transport: JSON-RPC 2.0 over stdio, one JSON value per line at the snapshot (verify framing).

`initialize` request parameters, pinned for the three capability cases. A disabled capability is present with value `false`, never omitted; enabling one power flips only its own flag:

```json
// no powers (default, and the --probe handshake)
{"protocolVersion": 1, "clientInfo": {"name": "talaria", "version": "<binary version>"},
 "clientCapabilities": {"fs": {"readTextFile": false, "writeTextFile": false}, "terminal": false}}
// file access on for this agent: only the fs flags change
{"clientCapabilities": {"fs": {"readTextFile": true, "writeTextFile": true}, "terminal": false}}
// terminal on for this agent: only the terminal flag changes
{"clientCapabilities": {"fs": {"readTextFile": false, "writeTextFile": false}, "terminal": true}}
```

Capability field names and nesting verify at scheduling; the present-but-false rule does not. Reply: only `protocolVersion` is required (snapshot `InitializeResponse`); `agentInfo` may be absent or null (fall back to the configured display name), `agentCapabilities` and `authMethods` take schema defaults when absent.

Other requests Talaria sends:

- `authenticate`: `{"methodId": "<configured method>"}` only under REQ-3's three conditions.
- `session/new`: `{"cwd": "<chosen absolute directory>", "mcpServers": []}` giving result `{"sessionId": "..."}` (plus optional config options or modes at scheduling).
- `session/prompt`: `{"sessionId": "...", "prompt": [{"type": "text", "text": "..."}]}` giving a result whose stop reason is one of the snapshot values mapped in section 5 (field name `stopReason` at the snapshot; values include end of turn, maximum tokens, maximum turn requests, refusal, cancelled — verify).
- `session/cancel`: a notification (no reply expected) with parameters `{"sessionId": "..."}` and nothing else (snapshot `CancelNotification`; verify it is still a notification).
- Permission replies (Talaria answers the agent's request): selected is `{"outcome": {"outcome": "selected", "optionId": "<chosen option identifier>"}}`; cancelled is `{"outcome": {"outcome": "cancelled"}}`. There is no rejected outcome variant.

Requests Talaria receives: `session/update` as `{"sessionId": "...", "update": {"sessionUpdate": "<kind>", ...}}`; `session/request_permission` carrying a tool-call reference and `options` (each with identifier, name, kind); and the fs/terminal methods of REQ-9. Refusing a disabled or out-of-tree fs/terminal call is a JSON-RPC error reply `{"code": -32601, "message": "talaria: <power> is not enabled for this agent"}` (for an enabled-but-outside path the message names the refusal: `"talaria: path is outside the session working directory"`); the code and whether a `data` member is used verify at scheduling, and the planner records the verified shape here. Enabled replies at the snapshot: a text read returns the file content with its line range fields, a text write returns an empty success result, terminal creation returns a terminal identifier and its output and exit calls follow the snapshot terminal shapes — all verify at scheduling before tests 24 and 25 are written. Elicitation calls are not advertised; if one arrives anyway it is refused with the same error shape and one diagnostic.

### 6.1 Standard-error capture, diagnostics sink

Agent standard error is captured on a dedicated reader into a bounded ring holding the last 64 KiB, redacted before storage with the same redaction the frame recorder uses (credential-shaped values and URL credentials replaced, never the raw text in any log or fixture), and sunk as fleet diagnostics: the registry's diagnostic channel, at most once per distinct text, plus the tail shown by a failing probe on standard error. Spawn failure (command missing or not executable at exec time) creates no row and surfaces exactly like an agent refusal in the launch affordance. Every other "one diagnostic" site in this specification (unknown update kind, unknown tool-call id, malformed usage, refused powers per session per method, unrenderable permission) sinks to that same diagnostic channel with the same once-per-distinct-text rule, scoped as each requirement states.

### 6.2 Terminal and file powers in detail (snapshot shapes; verify fs/terminal parameter names at scheduling)

Zero-confirmation rule: when a power is enabled for an entry, its calls execute directly. Talaria never inserts its own permission request before them and never holds a reply for an operator confirmation. (The agent may itself have asked the operator through `session/request_permission` before calling; that is the agent's flow, not a Talaria gate.)

Terminal scope: only `terminal/create`, `terminal/output`, `terminal/wait_for_exit`, `terminal/release` and `terminal/kill` are answered; any other `terminal/` method is refused as not enabled. A terminal's working directory must satisfy the same confinement as files (canonicalised, inside the session directory) or the create is refused. Terminal lifetime is bounded: a single terminal call waits at most 120 seconds (then the terminal is killed and the call answers with a timeout result in the snapshot shape), captured output is capped at 64 KiB with a truncation marker cell in the transcript, and session end (REQ-6 close, process exit, or Talaria close) kills and releases every terminal of that session. Parameters and result shapes for these methods verify at scheduling before tests 24 and 25 are written.

Allow-listed environment for enabled terminal calls: exactly `PATH`, `HOME`, `TERM`, `LANG`, `LC_ALL`, `TMPDIR` are inherited (each only when present in Talaria's own environment); nothing else is passed, and the command is exec'd directly without a shell, so no shell profile runs. Proof (issue test 25): the mock's terminal runs a print-environment command; its output must name exactly that subset (as present) and must not contain the sentinel variable the test exports into Talaria's environment as `TALARIA_SHELL_PROFILE_SENTINEL`, which only a shell profile or a full-environment inheritance could leak.

File confinement for a path that does not exist yet: canonicalise the nearest existing parent directory; the parent must be inside the session tree and the final component is appended as a plain name (no separators). A symlinked parent pointing outside is therefore refused for creates exactly as for existing paths. Reads and writes of existing paths canonicalise the path itself. Both reads and writes are recorded as transcript tool cells naming the (in-tree) path.

## 7. Mock rules

The mock ACP agent is an executable, not a test module: source `crates/talaria-app/src/bin/mock_acp_agent.rs`, declared as binary `mock-acp-agent` in `crates/talaria-app/Cargo.toml`. Application tests locate it through a test-support helper that uses the `TALARIA_MOCK_ACP_BIN` environment variable when set and otherwise the Cargo-provided binary path for the `talaria-app` package. Command-line tests (in another package, where that Cargo path does not reach) use the same variable or build it once with `cargo build -p talaria-app --bin mock-acp-agent` and read it from the workspace target directory; the test setup helper does this once per test run, not per test.

- M1. Delivery: the test helper writes the step script to a temporary file and spawns the mock with environment variable `TALARIA_MOCK_ACP_SCRIPT` set to that file's path and `TALARIA_MOCK_ACP_LOG` set to the step-log path; wrong-version mode is selected with `TALARIA_MOCK_ACP_MODE=wrong_version` (used by probes, which have no script). The step log is one JSON object per line at that path: `{"seen": <full JSON-RPC message>}` for everything received, `{"sent": <full message>}` for everything sent, `{"outcome": <permission outcome>}` for each permission reply, and `{"counts": {"session/new": n, "authenticate": n}}` as the final line on exit. The mock is driven by the script (one JSON object per line), distinct from the recorded fixture (M3). Step kinds: `expect`, `reply`, `reply_error`, `emit`, `ask_permission`, `stderr` (write the M2 line to standard error), `sleep_ms`, `exit`, and `mode`. Nothing in a script invents a method or field: shapes come from section 6 (the schema) first; where the schema and the recording disagree, the schema wins, the test stops, and the planner re-records (issue stop condition 4 applies to the recording, not to the schema).
- M2. The mock writes one deliberate non-protocol line (`mock-acp-agent: diagnostic line, not protocol`) to standard error on a `stderr` step, and counts `session/new` and `authenticate` calls so the probe test can prove neither happened. In `wrong_version` mode it replies to `initialize` with an unsupported protocol version and then waits, so the test can prove Talaria refuses and kills it.
- M3. The recorded fixture `fixtures/acp/mock-agent-session.jsonl` is recorded in planning (R5) from the operator's named real agent doing one short session (one prompt, one tool call with a content-only update, one permission request, one usage update, a clean finish). Credentials, home paths and the operator's working directory are replaced by placeholders before the file is committed; profile names in any Hermes-side content remain only `default` and `fixture`. The fixture carries, after the frames, the expected final row fields, transcript cells and usage, and the replay test asserts against those. A recording whose frames the mock cannot reproduce step-for-step is still valid for the replay test, which feeds the frames through the real client rather than through the mock.

## 8. Edge cases

| # | Case | Rule |
|---|---|---|
| E1 | Two agents return the same session identifier | Keys carry `acp:<agent-id>` (REQ-7); rows never merge |
| E2 | Update for an unknown session | One diagnostic; no row is created by a late or stray update |
| E3 | Late chunk after the turn finished | Terminal state stands; transcript keeps it only if it belongs to that session's finished turn record, else dropped and counted |
| E4 | Permission open, then the process dies | Responders cleared locally, no reply claimed; queue items leave with their rows (REQ-10) |
| E5 | Operator answers after the agent settled the request | No responder remains: "already settled", nothing sent (test 20) |
| E6 | Two permission requests for one tool call | Two responders, two queue items (core test 8; the wire suite proves the same through two ask_permission steps answered independently in test 20's fixture script) |
| E7 | Agent offers no renderable permission option | The request is refused with the section 6 error and one diagnostic; never auto-approved |
| E8 | Working directory deleted before launch | Launch fails plainly naming the directory; no process lingers |
| E9 | Very long chunk stream | Transcript appends are batched; pipe reads are continuous so a full pipe never stalls the agent |
| E10 | Secret-shaped agent text | Untrusted text: sanitised, kept only in the transcript, redacted in any recording |
| E11 | Talaria exits with turns running | `close()` settles writable permissions as cancelled, then terminates the processes (REQ-11) |
| E12 | Symlink inside the working directory pointing outside | Canonicalised path is outside: refused for read and write (issue test 24) |

## 9. Configuration

### 9.1 Configuration layout and exact command output

Configuration is repeated array-of-tables entries in Talaria's config file (the hand-walked loader learns this one repeated-table family, following the `[fleet]` precedent of teaching the loader a new table; no dynamic table names are used):

```toml
[[acp.agents]]
id = "example"
display_name = "Example Agent"
command = "example-acp-adapter"
args = []
auth_method = "example-login"   # optional; names a method, never a credential
allow_fs = false                # default false (REQ-9)
allow_terminal = false          # default false (REQ-9)
```

Rules: the loader walks `[acp]` looking only for `agents`, then each entry in file order. One notice per unknown key inside an entry. Validation (each failure skips the entry with one notice naming it, except where noted): missing/empty/non-string `id`, or an `id` outside `[a-z0-9][a-z0-9-]*` (32 max): skip. Duplicate `id`: the first entry wins, later ones are skipped. Missing/empty/non-string `command`, or whitespace-only: skip. Missing or empty `display_name`: keep the entry, display name falls back to `id` (no notice beyond any unknown-key notices); duplicate display names are allowed. `args` present but not a list of strings: skip. `allow_fs`/`allow_terminal` present but not boolean: skip. `auth_method` present but not a string: skip; an empty string means no method. Unknown keys never skip the entry. When every entry is skipped the printable set is empty: `talaria acp agents` prints nothing and exits 0. There is no working-directory key: the working directory is chosen at launch (REQ-4), defaulting to Talaria's launch directory. Relative commands resolve on the path at probe and launch time. Existence for the command: a value containing a slash is checked at that path, otherwise by path search; the file must be executable. No credential value is ever a configuration key.

Exact `talaria acp agents` output (standard output, one line per printable entry in configuration order; these bytes are the contract that issue test 28 asserts):

```text
example: Example Agent - ok
oldone: Old Agent - missing: command "old-agent-acp" not found
```

With `--probe`, a successful entry's line gains the agent name and protocol version: `example: Example Agent - ok - Example Agent, protocol 1`, where the name after the second ` - ` is the agent's reported name when it sent one and the configured display name when it did not. This matches the issue's REQ-12 form `<id>: <display name> - ok - <agent name>, protocol <version>`. A failed probe prints no agent line for that entry; instead standard error gains `example: probe failed: <plain reason>` (for a version mismatch the reason names both versions) and the exit code is 1 (REQ-12). Exit 2's standard error line is the loader's own could-not-read notice, printed unchanged. No line is printed for a skipped (empty-command or duplicate) entry.
