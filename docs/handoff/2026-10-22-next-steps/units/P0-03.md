# P0-03: Vendor the pinned Hermes contract and generate typed protocol bindings (unit P0-03)

Status: `proposed`. The GitHub issue for this unit is the contract; this document is its reference specification. If they disagree, the issue wins and the disagreement is reported on the issue.

## How to use this document

Read the issue first. It says what to build, which tests to write first and what counts as done. This document holds the evidence behind it: every Hermes fact with the file and line at Hermes v0.22.4, the exact shapes the code must handle, the rules for the native-method list, tables of edge cases, notes for each test, and the reasoning behind the design. Hermes links point at the v0.22.4 tag. Links to the handoff are relative. Every fact marked "verify at the pinned commit" must be re-checked against the release you pin, because the pin may be newer than v0.22.4. If a release newer than v0.22.4 exists when the unit starts, recompute every v0.22.4 number in this document (hash, counts, marker totals, default rows) from the file you pin; tests read them from the repository and never from a literal.

Facts below were checked on 2026-10-22 against a read-only copy of Hermes at the v0.22.4 tag (commit `4d04303818b61bf3aa09278af48356315515965b`), against the GitHub API, and by running the recorded frames through a JSON Schema validator. Anything not checked is listed at the end under "Not verified".

## 1. What this unit is for

Talaria talks to Hermes in JSON-RPC (a request and reply protocol carried as JSON). Hermes publishes a machine-readable description of every method, event and server-to-client request. Hand-copying shapes from Hermes source is how the Python client fell behind. This unit pins one Hermes release, keeps a byte-exact copy of that release's description in the repository, and generates Rust types from it. Later units import these types and never write a protocol struct by hand, except the five events the description leaves out.

Draft architecture decision 0008 ([../adr-drafts/0008-protocol-types-are-generated-from-the-hermes-contract.md](../adr-drafts/0008-protocol-types-are-generated-from-the-hermes-contract.md)) records the decision. Requirement R9 in [../01-vision-and-requirements.md](../01-vision-and-requirements.md) is the requirement it serves: a scheduled job that notices contract drift before the operator does.

At v0.22.4 the sha256 is `248ce12519dcc1e830a15c5819c93e6d27ef18404d19da38c960570710f83d00`. The same hash came from the local read-only copy and from the API, so the two sources agree. The file is 1.2 MB, which is above the limit of the plain contents API response, so the `raw` media type is required.

The Hermes licence is MIT (`LICENSE` at the repository root, "Copyright (c) 2025 Nous Research"). Vendoring the contract file copies a substantial portion of a Hermes file, so the licence text is kept next to it as `crates/hermes-contract/vendor/LICENSE.hermes`.

The hash file `vendor/gateway-contract.openrpc.json.sha256` holds one line in the format `shasum -a 256` prints: 64 lowercase hex characters, two spaces, the file name, a newline. The licence file is a byte copy of `LICENSE` at the Hermes repository root at the pinned commit, fetched with the same `gh api` raw call (1,070 bytes at v0.22.4). `verify-vendor` fetches that `LICENSE` the same way and compares its bytes with `vendor/LICENSE.hermes`, printing both sha256 values on a mismatch; `test_cli.py::test_verify_vendor_checks_the_contract_and_the_licence` (fake `gh`) covers it, so a wrong licence copy cannot pass unseen.

`TAG` and `COMMIT` in `src/pinned.rs` are hand-typed `&'static str` constants; the test `pinned.rs::pinned_parses_tag_and_commit` keeps them equal to `PINNED` (read with `include_str!`), so a bump that forgets one fails.

`live_skip_reason(code_sha)` returns `None` when `code_sha` is a case-insensitive prefix of `COMMIT` with at least 7 characters (so a full 40-character sha and an abbreviated one both match), and otherwise `Some(message)`. The two exact texts: for a value that does not match (including one shorter than 7 characters), `gateway code_sha "<value>" does not match the pinned Hermes commit <COMMIT> (<TAG>); live tests are skipped`; for `None`, `the gateway reported no code_sha; live tests need Hermes <TAG> (commit <COMMIT>) and are skipped without it`. Test 21 asserts that both messages contain the tag and the commit and that the first also contains the value received. Hermes sends the full install commit: `hermes_cli/version_info.py` `get_code_identity` (line 308 onward) returns `info.commit` as `sha`, taken from the install stamp or from `git rev-parse HEAD` (line 209), and `gateway/status.py:812` puts it in `code_sha`, which `identify` includes (`gateway/control_socket.py:171` onward). It is a commit sha, never the annotated tag object's sha. Whether a release install's stamp carries the tag's commit is not verified (section 17); where it does not, the live tests skip with the message, which is the safe outcome. {{P1-01}} and {{P1-12}} define the same skip rule as a prefix match of at least 7 characters; they should call this function instead of repeating it.

Git can change bytes on checkout (line endings, a byte order mark). Hermes's own generator reads the file with `utf-8-sig` (`scripts/gen_gateway_contracts.py`, `main`), which shows byte order marks are a live concern there. Mark the vendor folder `-text` in `.gitattributes` so git never rewrites it.

## 4. Preprocessing the schemas (tools/contract-gen)

Input: `components.schemas`. Output: a JSON Schema 2020-12 document for `cargo typify`.

1. Lift `components.schemas` into `$defs`. Rewrite every `$ref` of the form `#/components/schemas/X` to `#/$defs/X`. After this step no `components` path may remain.
2. Remove every `additionalProperties` whose value is exactly `false` inside `components.schemas` (751 at v0.22.4; the 752nd marker is the inline `voice.interrupted` schema, which is handled by the event rule, not the lift). Leave `additionalProperties: true` and schema-valued `additionalProperties` alone. Reason (u11 section 3.4): typify turned `false` into `#[serde(deny_unknown_fields)]` 746 times on an older revision, so any frame with a field Hermes added later would not decode. Evidence from the recording: real `tool.start`, `tool.complete` and `message.complete` payloads carry fields their closed schemas do not list (section 9), so leaving the marker in would fail on live traffic today.
3. Drop the defaults typify rejects. u11 found three schemas, by bisecting the 548 schemas that carry defaults (at the older revision): `DisplayLease`, `MessageCompletePayload` and `ProviderUsageWindow`. All three exist at v0.22.4. What each one carries:
   - `DisplayLease.viewer_id`: `{"default": null, "title": "Viewer Id", "type": "null"}` (a null-typed field with a null default).
   - `MessageCompletePayload.text`: `{"anyOf": [{"type": "string"}, {}], "default": "", "title": "Text"}` (a string-or-anything field with a string default).
   - `ProviderUsageWindow`: the report says the field passes alone and the likely cause is inline enums titled `Scope` (nine schemas carry that title at v0.22.4); this is inferred, not confirmed. At v0.22.4 the schema has one `scope` property with `default: "account"` and an inline enum `["account","model"]`. Do not assume which property fails; let typify tell you.

   Preprocessing is a generator rule, not an override: `overrides.rs` is for protocol-level corrections such as `prompt.submit` (section 11). Keep the removals in a named table in the script (schema name, property name, keyword (`default` or `title`), reason), with one test per row (test 5 checks the keyword too). The independent test author must run this bisect before writing the `ProviderUsageWindow` row's test. The research marks the cause as inferred, and the red run comes before the generator exists, so the generator cannot be used for it. Write, outside the repository, a scratch JSON Schema document that holds the `ProviderUsageWindow` schema as it is in the contract (it has no `$ref`; verify at the pin), run `cargo typify <file>` on it and, if typify rejects it, delete one `default` at a time and rerun. If one deletion clears the rejection, that property is the table row. If no single deletion does, the cause is probably the inline enums that all carry the title `Scope` (nine schemas carry that title at v0.22.4); the row then drops the `title` keyword of the inline `scope` enum instead (the table has a `keyword` column, `default` or `title`, for this case, and its test checks the right keyword). If that does not clear it either, stop and report; the operator decides. If typify accepts the schema alone, the failure depends on the surrounding document: bisect the lifted document the same way, which adds at most one more row. The result (property and keyword, or the stop) goes in the pull request. This is research, not production code. If typify rejects another schema at the pin, add a row, comment why, add its test, and say so in the pull request. Do not widen the rule to "drop every default": dropped defaults change the generated types, and u11 found the other defaulted schemas (548 carry defaults at the older revision) generate fine.
4. Emit two documents (u11 did): one with `$defs` only, and one whose root is an `anyOf` referencing every definition, so typify generates every type rather than only the reachable ones.
5. Constrained strings. Typify turns a string with `pattern`, `minLength` or `maxLength` into a validating newtype whose `Deserialize` fails on a violating value (read from typify-impl 0.8.0, `type_entry.rs`; verify by running it). At v0.22.4 the contract has five `pattern` constraints, all inside four sent parameter types (`ConnectorAccountsParams`, `ConnectorAccountsRenameParams`, `ConnectorPolicySetParams`, `ConnectorsConnectParams`), and `minLength` or `maxLength` constraints in five schemas (`ConnectorAccountsRemoveParams`, `ConnectorAccountsRenameParams`, `ConnectorsConnectParams`, `SessionBranchStoredParams`, `SessionOwner`). Following `$ref`s from every notification, method result and server-request parameter shows that only `SessionOwner` (`session_id`, `minLength` 1; the `session` variant of `ConnectionUpdatePayload.owner`) is reachable from received data. Ruling: a value that violates a constraint inside a received payload is a decode error for that payload (a known type with a bad payload: `EventFrame::from_params` returns `Err`, never `Unknown`); this is correct for a contract violation and is not softened. The generator holds a table of the received constrained types (`SessionOwner` only, at v0.22.4) and fails naming any other, so a new one is a decision (test 7). No `format` keyword occurs in `components.schemas` at v0.22.4 (checked), so `chrono`, `uuid` and `url` are not needed; the only extra crate the generated code may need is `regress`, for the four pattern types. If the build asks for any other crate, stop and report.

The result feeds `cargo typify`. u11 measured cargo-typify 0.8.0 emitting 925 types and 101,956 lines with builders, `cargo check` passing, incremental re-check 4.8 seconds. u11 also says generated discriminated unions become `#[serde(untagged)]` enums (for example `Owner`), and that `rustfmt` is found through `CARGO_HOME`, so a custom `CARGO_HOME` may need `RUSTFMT` set. None of this was re-run for this document. Install with `cargo install cargo-typify --version 0.8.0 --locked`. Cargo-typify 0.8.0 has `-B` / `--no-builder` to skip builder code (read from its source by a reviewer; confirm with `cargo typify --help`). Keep the version in one constant in `contract_gen.py` and repeat it in `tools/contract-gen/README.md`. Ruling on the mode: ship the default mode, with builders. It is the mode u11 measured (101,956 lines, `cargo check` passing), and the constructor in section 11 may use `Params::builder()`. Measure `-B` once as well and put both line counts and both clean and incremental `cargo check` times in the pull request. Use `-B` only if the default output fails to compile or would exceed 300,000 lines (the stop limit applies to the mode that ships); then `overrides.rs` builds the `Params` by struct literal. The contract has 5 `pattern` constraints; typify-impl 0.8.0 emits `regress::Regex` for a `pattern` (a reviewer's reading, verify), so the generated code may need the `regress` crate: add it as a workspace dependency entry in the root `Cargo.toml` (and to this crate) if the build asks, and say so in the pull request. Before writing any attribute, read the `[workspace.lints]` table that {{P0-02}} puts in the root `Cargo.toml`. Each generated file starts with scoped inner `#![allow(...)]` attributes for the rustc and clippy lints that `cargo clippy --all-targets -- -D warnings` reports on it (never for `unsafe_code`); the generator formats its output with the rustfmt of the toolchain {{P0-02}} pins, because `cargo fmt --check` also covers generated files.

### 4.1 Discriminated unions (ten sites at v0.22.4)

The generator holds a table of the discriminated unions (`discriminator.propertyName` sites) and a table of the constrained strings reachable from received data (section 4, item 5), and fails naming any new entry in either, so a new union is a decision, not a surprise. At v0.22.4:

| Site | Property | Variants | Direction |
|---|---|---|---|
| `ConnectorPolicyLayer.body` | `mode` | `unrestricted`, `deny-all`, `allow`, `deny` (`ConnectorPolicy*Body`) | received |
| `ConnectorPolicyGetResult.effective` | `mode` | same four (`ConnectorPolicyEffective*`) | received |
| `ConnectorPolicySetResult.effective` | `mode` | same types as the previous row | received |
| `ConnectionUpdatePayload.owner` | `type` | `account` (`AccountOwner`), `session` (`SessionOwner`) | received |
| `GoalSnapshot.wait_barrier` | `type` | `session` and `pid` (`WaitBarrierTarget`, whose `type` is an enum of the two), `until` (`WaitBarrierUntil`) | received |
| `ConnectionOperationParams.owner`, `ConnectionRespondParams.owner`, `ConnectorsConnectParams.owner`, `ConnectorsListParams.owner` | `type` | `account`, `session` | sent |
| `ConnectorPolicySetParams.change` | `type` | `connector` (`ConnectorChange`), `tools` (`ToolsChange`) | sent |

The received sites are tested (test 39). Serialising a variant writes that variant's own fields, so the sent sites need no decode test.

Why this matters: serde tries the variants of an untagged enum in declaration order and takes the first that fits. `ConnectorPolicyUnrestrictedBody` and `ConnectorPolicyDenyAllBody` require only `mode`. Before the closed-object markers are removed, the allow and deny bodies fail on `Unrestricted` because of the extra fields. After removal, `Unrestricted` swallows them unless typify keeps the `const` on `mode`. u11 section 3.4 measured the untagged output on an older revision, so measure it again. The approved fix for a red wrong-variant test is a function in `overrides.rs`, `decode_<site>(&serde_json::Value)`, that reads the discriminator string and deserialises into that variant's generated struct, then wraps it in the generated enum variant. It uses generated structs only, each such function carries a comment citing this section and a test, and nothing else (a custom typify template, a hand-written struct) is allowed without the operator.

Where decoding happens (ruling). A client decodes an event with `EventFrame::from_params` and a method result with `serde_json::from_value::<M::Result>`; both end in the generated `Deserialize`, so test 39 calls those entry points and not the override. Which received site is reached how was computed from the contract at v0.22.4 by following `$ref`s (recompute at the pin): `ConnectionUpdatePayload` is the payload of the `connection.update` event; `GoalSnapshot` is in the payload of the `session.control.update` event and in the results of the legacy methods `session.control` and `session.control.read`; `ConnectorPolicyGetResult` and `ConnectorPolicySetResult` (and `ConnectorPolicyLayer` inside the first) are results of the legacy methods `connectors.policy.get` and `connectors.policy.set`, and no event or server request reaches them. So: `owner` and `wait_barrier` are tested through `EventFrame::from_params` on a whole `params` object, and `wait_barrier` also through `from_value::<GoalSnapshot>`; the three connector-policy sites are tested through `from_value` of the generated result type. The `decode_<site>` functions are called by hand-written code on exactly one path: `EventFrame::from_params` decodes the payload, then replaces the site's field with `decode_<site>(raw payload field)`. They do not intercept a client's `from_value` of a method result, so a red site that is reached only as a method result cannot be repaired this way: stop and report (the operator then chooses between a generator rule that orders the variants and anything else). Each `decode_<site>` has its own test in `tests/overrides.rs`. Sites without a discriminator (`anyOf` unions such as `CanonicalSubmitResult`) are covered only where a recorded frame reaches them (test 31); the pull request says that the others are untested here.

## 5. Names

Method `a.b.c` becomes the snake-case module name `a_b_c`; an upper-case letter that follows a lower-case letter or digit starts a new word (`display.switchSandboxImage` becomes `display_switch_sandbox_image`). Event `a.b_c` becomes the Pascal-case variant `ABC` (`gateway.ready` becomes `GatewayReady`, `tool.output_risk` becomes `ToolOutputRisk`). Server request `approval` becomes `Approval`, `vault.save_login` becomes `VaultSaveLogin`.

A converted module name that is a Rust keyword (or starts with a digit) gets a trailing underscore. None of the names in the four catalogues needs this today: the closest case is `session.workspace.move`, whose module name is `session_workspace_move`, which is not a keyword. The generator must fail loudly on a collision rather than overwrite, and a test must prove it.

Sketch of the hand-written trait and one generated module (names are binding, bodies are illustrative):

```rust
// crates/hermes-contract/src/method.rs (hand-written)
pub trait Method {
    const NAME: &'static str;
    type Params: serde::Serialize;
    type Result: serde::de::DeserializeOwned;
}

// crates/hermes-contract/src/generated/methods.rs (generated)
pub mod canonical {
    pub mod prompt_submit {
        pub const NAME: &str = "prompt.submit";
        pub type Params = crate::schemas::CanonicalSubmitParams;
```

## 8. Which legacy methods the native socket serves

The native socket is the canonical `hermes-gateway-v1` WebSocket. `tui_gateway/ws.py` dispatches each request to the session authority first (`_dispatch_request`, `tui_gateway/ws.py` lines 358 to 371). Only when the authority answers `-32601` (unknown method), the method is registered in the older sidecar (`server._methods`), and `legacy_fallback_allowed` says yes, does the request reach the legacy handler.

`legacy_fallback_allowed(actor, method)` (`tui_gateway/ws_legacy_fallback.py:53`):

1. `False` if `method` is in `_PROCESS_GLOBAL` (line 46): `process.stop`, `delegation.pause`, `reload.mcp`, `reload.env`, `agents.list`.
2. `False` if `method` starts with one of `_SESSION_NAMESPACES` (line 32): `session.`, `prompt.`, `message.`, unless it is in `_SESSION_FALLBACK_ALLOWED` (line 33): `session.most_recent`, `session.active_list`, `session.events.stats`, `session.foreign.list`, `session.foreign.preview`, `session.foreign.import`.
3. Otherwise `True` only when the connection's grant covers the `interactive` purpose: `session:create`, `session:read`, `session:submit`, `session:control`, `session:approve`, `session:respond` (`gateway/runtime_bootstrap.py:9` to `:11`).

The authority itself serves a set of verbs without any fallback. ## 11. The prompt.submit correction

Hermes `gateway/session_controls.py`, method `submission` (line 747 onward):

```python
forbidden = set(params) - {'session_id', 'text', 'submission_id', 'input_id', 'queued', 'attachments', 'finite', 'unattended', ...}
if forbidden:
    raise RuntimeStoreError('invalid_params')
request_id = params.get('submission_id') or params.get('input_id')
if not isinstance(request_id, str) or not request_id:
    raise RuntimeStoreError('invalid_params')
```

Lines 751 to 758. The contract schema `CanonicalSubmitParams` (closed, 19 properties) requires only `session_id` and `text`. So a request without `submission_id` or `input_id` type-checks and then fails at run time with error 4001 `invalid_params` and no field named. Every bake-off builder hit this (u16 section 5, trap 1).

The correction lives in `crates/hermes-contract/src/overrides.rs`:

- `pub fn prompt_submit_params(session_id: impl Into<String>, text: impl Into<String>, submission_id: impl Into<String>) -> methods::canonical::prompt_submit::Params`, which always sets `submission_id` and leaves every other optional field unset. It never sets `unattended` to true (its value stays the generated default `false`, or the key is absent): that flag auto-approves every dangerous command in the turn (LEARNINGS 2026-10-22, "The Hermes gateway contract misled every bake-off builder in the same places").
- `pub fn check_prompt_submit(params: &methods::canonical::prompt_submit::Params) -> Result<(), OverrideError>`, which fails when neither `submission_id` nor `input_id` is a non-empty string. {{P1-02}} or {{P1-12}} calls it before sending.

What typify writes for unset fields (read from typify-impl 0.8.0, `structs.rs`; verify by running it): an optional property whose schema is nullable with default null becomes `Option<T>` and is skipped when `None`, but a property with a non-null default is a plain value with `#[serde(default = ...)]` and no skip. In `CanonicalSubmitParams`, `queued`, `finite`, `unattended`, `interrupted`, `voice_turn` and `clarify_batch` have the default `false` and are not required, so they are written as `false` on every request. Hermes accepts that: `submission` allows all six names (`gateway/session_controls.py:751-753`), and `admit_finite` (`gateway/session_finite.py:42-52`) takes a `bool` `unattended` and refuses it only when it is true without `finite` being true, or when the submitter is not the local command-line principal. So the invariant is that `unattended` is never `true` in the serialised JSON; an absent key and `false` both pass. `check_prompt_submit` also fails when `unattended` is `true`.

The exact generated field types depend on typify's output (an optional string is `Option<String>`). The test is written against the generated type; if the names differ, use the generated names.

## 12. Envelope and decode rules

An event arrives as `{"jsonrpc":"2.0","method":"event","params":{...}}`. `params` holds `type`, optional `session_id`, optional `payload`, optional `seq`, optional `replay_epoch`, and on canonical gateways optional `authority_epoch`, `execution_generation`, `admission_id` (`apps/shared/src/gateway-events.ts` lines 57 to 83). `seq` is "stamped by `tui_gateway/event_replay.py::_stamp_event`; absent on session-less broadcasts".

| Input `params` | Result of `EventFrame::from_params` |
|---|---|
| `type` is in the contract (or one of the five), payload decodes | `Ok(frame)` with the matching `Notification` variant |
| `type` is in the contract, payload missing a required field or wrong type | `Err(DecodeError { event_type, reason })`; never `Unknown`, never a panic |
| `type` is in the contract with no payload schema (`voice.interrupted`), payload absent, `null` or `{}` | `Ok`, a data-less variant |
| `type` not known | `Ok(frame)` with `Notification::Unknown(<the whole params object>)` |
| `type` missing or not a string | `Err(DecodeError)` |
| extra keys anywhere | ignored |

`EventFrame` holds `session_id: Option<String>`, `seq: Option<u64>`, `replay_epoch: Option<String>`, `authority_epoch: Option<i64>`, `execution_generation: Option<i64>`, `admission_id: Option<String>` and `notification: Notification` (types from `gateway-events.ts` lines 55 to 83: `authority_epoch` and `execution_generation` are numbers, `admission_id` and `replay_epoch` are strings). Client-local keys the gateway never sends (`replayed`, `replayEpoch`, `connectionId`) and the renderer-side `profile` key are ignored.

`DecodeError { event_type: String, reason: String, missing_fields: Vec<String> }`. Serde's derived deserialiser reports only the first missing required field, so the generator emits, for each `Notification` variant, the list of required top-level payload fields from the schema's `required`; on a serde failure, `from_params` fills `missing_fields` with every name on that list that the payload lacks. A recorded `gateway.ready` therefore names both `skin` and `replay_epoch`. This is why test 22 reads `missing_fields`.

What `DecodeError` holds in each failure (ruling). `event_type` is the wire `type` for an event and the method name for a server request (the field keeps its name; its doc comment says so); it is the empty string when the `type` key is missing or not a string. `missing_fields` lists, sorted alphabetically, every top-level required payload field from the constant list that the payload object lacks. It is empty when all required fields are present and the failure is a wrong type (`reason` names the field serde reports), when the payload is not an object (`reason` says so), when `type` is missing, and for envelope failures.

Absent payloads and envelope types (ruling). For a known type that has a payload schema, an absent or `null` payload is treated as an empty object: it decodes when the schema has no required fields and otherwise fails with `missing_fields` listing all of them. A wrong type on an envelope key (for example `seq` as text, or `session_id` as a number) gives `Err(DecodeError)` whose `reason` names the key; it is neither ignored nor `Unknown`.

The constant list: `generated/events.rs` holds `pub const REQUIRED_FIELDS: &[(&str, &[&str])]`, sorted by wire type name, one entry for every event type the `Notification` enum names, each inner list sorted alphabetically. It includes the five hand-written events (the generator holds their entries itself: `prompt_id` for `approval.request`, `approval.settled`, `clarify.request` and `clarify.settled`, none for `session.replay_gap`) and `voice.interrupted` (none).

`EventFrame::type_name(&self) -> Option<&str>` returns the wire `type` (for `Unknown`, read from the stored object) so a caller can report an unknown event once per connection (protocol rule in [../05-architecture.md](../05-architecture.md), "Protocol rules every client layer must keep").

serde design note (guidance, not a Hermes fact): an enum tagged by `type` with `payload` as content, flattened into the envelope struct, interacts badly with unknown variants and with `#[serde(other)]`. Decoding from a `serde_json::Value` by hand (match on the `type` string, then `serde_json::from_value` of the payload into the variant's type) is simpler and gives the `DecodeError` you need.

`ServerRequestFrame { id: serde_json::Value, request: ServerRequest }` carries the JSON-RPC `id` (number or string, kept as raw JSON) and the decoded request. `ServerRequestFrame::from_request(&serde_json::Value) -> Result<ServerRequestFrame, DecodeError>` takes the whole JSON-RPC request object: a method in `x-server-requests` with valid params gives its `ServerRequest` variant; an unlisted method gives `ServerRequest::Unknown(<params>)`; a known method with bad params gives `Err(DecodeError)` naming the method. `Unknown` lives on `ServerRequest` (and on `Notification`), never on the frame types.

The module name of a server request is its method name with dots replaced by underscores (`vault.save_login` becomes `vault_save_login`); the same keyword and collision rules as section 5 apply.

## 12a. The example's output

`examples/decode_recording.rs` reads the recording with `include_str!` (the crate does no input or output of its own beyond printing) and prints one line per distinct event type, in order of first appearance, then two lines about `prompt.submit`. UAT-5 compares these formats exactly: `<type>: ok <Variant>` (the `Notification` variant named by the section 5 rule, for example `ok MessageDelta`); `<type>: unknown` (for `agent.step`); `<type>: error missing <fields>` (the `missing_fields` joined by a comma and a space, for `gateway.ready`: `gateway.ready: error missing replay_epoch, skin`); `approval.request: ok ApprovalRequest choices=once, deny, session, always`; then `prompt.submit without submission_id: rejected` and `prompt.submit from prompt_submit_params: accepted`.

## 14. The CI workflow

One new file, `.github/workflows/contract.yml`, with two jobs. Follow the conventions of the workflow {{P0-02}} adds (action versions, runner names, caching, toolchain setup); read it before writing this one. Do not edit it.

- Job `contract-gen-check`: runs on pull requests and pushes to `main` that touch `tools/contract-gen/**`, `crates/hermes-contract/**`, this workflow, the root `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml` or `.gitattributes` (the crate depends on the last four). Steps: install `cargo-typify` at the pinned version, set `CONTRACT_GEN_REQUIRE_TYPIFY=1`, run the Python tests, run `contract_gen.py check --require-typify`, run `cargo test -p hermes-contract`.
- Job `contract-drift` (the name the roadmap gives): runs on a weekly schedule and on manual dispatch. Steps: resolve the newest stable tag with the API call in section 2 (`GH_TOKEN` from `github.token`), clone Hermes at that tag into a temporary directory, install `cargo-typify`, and run `contract_gen.py drift --tag latest --summary "$GITHUB_STEP_SUMMARY" --hermes-checkout <clone>`. The command fetches that tag's contract, recomputes the owner-served list from the clone (without `--hermes-checkout` it prints one line saying the list was not refreshed, and the summary says so), and regenerates into a temporary copy of the whole workspace: the crate cannot build alone, because it inherits `[workspace.package]` and `[lints]` from the root manifest ({{P0-02}}), so the copy holds the root `Cargo.toml` with `members` reduced to `crates/hermes-contract`, `Cargo.lock`, `rust-toolchain.toml` and the crate. It runs `cargo build -p hermes-contract` there, then two groups of tests. Binding tests decide the exit status: `cargo test -p hermes-contract --lib` plus one `--test <name>` for every file in `crates/hermes-contract/tests/` except `frames.rs` and `responses.rs`, and `cargo test -p hermes-contract --doc` (cargo refuses to mix `--doc` with the other selectors, so it is a second command). Recording tests are `--test frames --test responses`: they pin the outcomes of the recorded frames, which a newer release may change legitimately (for example by making `skin` optional), so they run, their result and the names of any failing tests go in the summary, and they never change the exit status.

  Exit status follows the steps, not the diff. It exits 1 only when generation, the build or a binding test fails, or the tag is unknown, or the network or `gh` is missing. A newer release that changes names but breaks nothing exits 0, so the weekly job does not turn red on every harmless release; the summary is how a person notices. When the newest tag equals the pin, the summary lists are empty. The command never edits the repository and never opens a pull request.

  The summary lists, for each of the four catalogues (legacy methods, canonical methods, notifications, server requests), the names added, the names removed and the names changed, where changed means the referenced schema's JSON (after the lift) differs, or the method's params or result `$ref` name differs; plus the counts of schemas added and removed, plus the owner-list names added and removed.

Required status checks are the operator's to change. These jobs are not required unless the operator adds them.

## 16. Design reasoning

- Why Python for the generator: it runs only when someone regenerates, it needs JSON manipulation and string templates, and Python 3 with only the standard library is available on every developer machine and CI runner. The roadmap allows it. A Rust generator would put the generator's own tests inside `cargo test --workspace`; the cost of Python is that those tests run in a separate command, which the new workflow covers.
- Why preprocessing is not an override: the override file is for protocol facts the schema cannot state (what Hermes enforces at run time). Lifting references and dropping rejected defaults are generator behaviour that the Python tests cover.
- Why the owner-method list is a committed file: the list lives in Hermes Python code that cannot be read from the contract. Making it a committed input keeps `generate` offline and deterministic, and lets the drift job show a diff when Hermes moves a verb.
- Why events are decoded by hand from `Value`: the envelope is not modelled in the contract (u04 section 4, item 3), and a `DecodeError` for a known type with a bad payload is information the caller needs.
- Why `Result` and `Params` are aliases: two methods can share one schema type, and an alias keeps one definition.
- Alternatives rejected: committing only the generated code without the contract (cannot detect drift); vendoring Hermes's TypeScript client (Talaria is Rust, ADR draft 0010); loosening `required` fields to make old recordings decode (hides real divergence).
- Pre-mortem: the most likely failure is a generator that works on the contract and produces code that compiles but decodes wrongly (untagged unions, dropped defaults). That is why the tests decode real frames and the union test exists.
