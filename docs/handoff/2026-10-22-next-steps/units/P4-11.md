## 1. What this unit adds, in one paragraph

One full-screen overlay with two tabs over the connected Hermes profile. **Connectors** manages
hosted connector accounts: outside services (for example a code host or a mail account) that Nous
Research's hosted tool gateway connects on the user's behalf and Hermes then offers to the model as
tools. The user sees which connectors are offered and connected, adds an account through a browser
sign-in link, renames, reconnects or removes an account, turns a connector on or off, and turns
single tools of a connector on or off. **Messaging** manages the chat platforms the Hermes gateway
answers on (Telegram, Discord, Slack, Signal, email and others): the user sees each platform's
state, turns it on or off, enters or clears its credentials and allowlists, tests it, and approves
or revokes the people who asked to pair with the bot. Connectors use typed gateway methods on the
WebSocket; messaging uses the dashboard REST routes through the REST client of `P4-01`.

Account rows: `active` is copied from the upstream account record without a documented meaning;
this unit decides "connected" from `status == "active"` and `disabled == false` only and never
reads `active` (`methods_connectors_account.py:105-119`). `label` is the upstream label after

`connectors.accounts`, and session owners.

### 2.8 Platform state vocabulary

The payload's `state` is computed at `messaging.py:243-257`: `disabled` when not enabled;
`not_configured` when enabled but a required key is missing; `pending_restart` when the gateway
runs but has no state for it; `startup_failed` or `gateway_stopped` when the gateway is not
running; otherwise the runtime's own state. Runtime states written by the gateway at v0.22.4:
`connected`, `connecting`, `retrying`, `fatal`, `disabled`, `paused`, `disconnected`
(`gateway/run_adapters.py:381-386`, `:755-772`, `:918`, `:1199-1230`; `gateway/status.py:1091-1145`).
Hermes Desktop's labels: Connected, Connecting, Disabled, Error (`fatal`), Messaging gateway
stopped, Needs setup, Restart needed, Retrying, Startup failed
(`apps/desktop/src/i18n/en.ts:2518-2528`).

### 2.9 Pairing

Unknown people who message the bot get a one-time code and land in `pending`; an admin approves
by `request_id`, never by the code, which the API never returns (`gateway/pairing.py:556-574`;
`apps/desktop/src/api/messaging.ts:107-136`). Rows written before hashed codes report an empty
`request_id`; they can only be approved with the code through
`hermes pairing approve <platform> <code>` (`hermes_cli/subcommands/pairing.py:17-22`). Approval
also adds the user to the platform's allowlist when one is configured (`gateway/pairing.py:431-440`).
Revoke removes the pairing approval and its allowlist mirror only (`gateway/pairing.py:442-455`,
`:224-236`). The gateway admits a sender through chat grants, platform allow-all, adapter role
authorization, the pairing store, platform and global allowlists, adapter policy or
`GATEWAY_ALLOW_ALL_USERS`, independently of pairing (`gateway/authz_mixin.py:658-694`). So a
revoke does not guarantee the person can no longer message the bot, and Talaria's text says so.

### 2.10 Change signals

Both are global events with an empty payload (`tui_gateway/contracts/events.py:836-844`; contract
48777, 48837), so the profile cannot be inferred from them: they are hints to refetch, not data.
The watcher home is the gateway process's active home (`tui_gateway/change_watcher.py:43-46`).

- `pairing.changed` (checked every 2 s) watches the `*-pending.json` and `*-approved.json` ledgers
  under `pairing/` and `platforms/pairing/` of the watcher home **and of every live named profile
  under its `profiles/` directory**; the profile list is cached up to 30 s
  (`change_watcher.py:303-313`, `:316-338`).
- `platforms.changed` (checked every 2 s, broadcast at most every 5 s) watches only the watcher
  home's `gateway_state.json` (`change_watcher.py:376-395`). A multiplexer writes its served
  profiles' platform status there as `<profile>:<platform>` entries
  (`gateway/run_adapters.py:1199-1230`), so a multiplexer-served named profile does produce the
  signal; a profile served by its own gateway process writes its own home and produces none for a
  watcher in another home.

On the Messaging tab Talaria refetches only the connected profile: `pairing.changed` →
`LoadPairing` and `LoadPlatforms` (an approval made elsewhere also adds the person to the
platform's allowlist when one is configured, `gateway/pairing.py:431-440`, and the platform card
shows allowlist entries); `platforms.changed` → `LoadPlatforms`. On the Connectors tab both
signals are dropped, because entering the Messaging tab refetches (4.3). Talaria never polls;
Ctrl+R or reopening the tab refreshes a profile the signals do not cover.

## 4. Design

### 4.1 Settled decisions (with reasons)

1. **One overlay, two tabs.** `/connectors` opens the Connectors tab, `/messaging` the Messaging
   tab; Tab switches. Both are "outside services Hermes talks to", and one overlay keeps one key
   context and one service. `/platforms` stays Hermes's.
2. **Connectors use the socket; messaging uses REST.** No socket method serves messaging
   platforms or pairing at v0.22.4; no REST route serves hosted connectors.
3. **Account owner only.** This unit never sends `owner: {type: "session"}`. In-chat connection
   cards (`connection.request` events) are not part of this unit.
4. **Consent before the first connectors call.** Opening the Connectors tab may create a Nous
   guest identity for the profile (H11). Talaria asks once per profile per Talaria process before
   sending any `connectors.*` call. The consent lives in one process-wide `ConnectorsConsent` (a
   set of profile names) in `talaria-app`, not in the overlay state, so reopening the overlay or
   reconnecting to the same profile does not ask again, and every caller (this overlay and
   `P4-09`'s gathering) obeys it. `ConnectorsService` refuses every `connectors.*` effect for a
   profile not in the set (defence in depth). `P4-09` never grants consent; before it, its
   connector section is unavailable. The Messaging tab needs no consent.
5. **No `profile` on the socket; the ticket's own profile on REST.** The socket fills it in from
   the ticket (H3). REST state is only correct when the profile is named (2.7), and naming the
   ticket's own profile is allowed (H6).
6. **Talaria never shows a stored value.** Hermes's `redacted_value` reveals the first and last
   four characters of a secret; Talaria shows only `set` or `not set`. Allowlist keys (`is_list`,
   which Hermes only sets for non-password keys matching `_ALLOWED(_[A-Z]+)?$`,
   `messaging.py:128-144`) are IDs that Hermes itself returns in plain text; they are shown and
   edited as lists inside the overlay.
7. **Two policies for typed messaging values.** Every typed value of a non-list field is a secret
   until it reaches the PUT body, whether or not Hermes marks it `is_password`: one rule, no
   per-field judgement. Allowlist entries are personal identifiers, not secrets: the overlay, its
   review and the core state may hold and show them; notices, tracing, history and recordings
   never do, and every `Debug` prints their count only.
8. **Saving never restarts the gateway.** When `hot_served` is false, the screen says a restart is
   needed and `R` opens `P4-10`'s doctor, which owns the confirmation and the restart.
9. **No polling except during a link wait.** Lists refresh on open, after each write, on `ctrl+r`
   and on change events. During a link wait one `connectors.operation.status` is in flight at a
   time, every 2 s. There is no timer refresh of the messaging list, even for a profile the change
   signals do not cover (2.10): Ctrl+R serves that case.
10. **The connect link is a credential.** It is shown on screen, opened with `o` (https only) and
    copied with `c`; it never reaches a notice, the transcript, history or tracing. In a recording
    it appears only as `[redacted]`: `P1-04`'s rules do not catch it (its URL rule leaves paths
    alone and no key-name pattern matches `connect_url`), so this unit adds one by-name entry,
    `connect_url` (reason `free-text`, `P1-04`'s existing reason, so its reason list, its format
    document and its test 12 stay unchanged), to `P1-04`'s free-text list in `redact.rs`, reviewed
    by `P1-04`'s owner. A by-name entry covers every position (results, events, replay snapshots).
11. **Rules writes change only the member layer** and carry its revision; they re-read the policy
    after every write and every conflict. No member layer: rules are read-only (there is no
    revision to send, H24; Hermes would otherwise compose a fresh deny-list, H28). Organization and
    role layers are read-only locks (H29); the switch sends the member intent, never the effective
    state.
12. **One write at a time** across the whole overlay; a second write request shows
    `Waiting for Hermes.` and sends nothing. A write holds the slot until its reply **and** its
    reloads have arrived. `connectors.connect` holds it only until its reply: the link wait and its
    polls do not. Which effects hold it, and until when: section 4.15.

### 4.4 The Connectors tab

Loading order after consent: `connectors.list` first. If `available` is false → T3, nothing else
sent. Otherwise send `connectors.catalog`, `connectors.accounts` and `connectors.policy.get`
together. A failure of catalog or policy degrades, never blocks: without catalog, names are slugs;
without policy, Space and tools saving answer T19 (rules unavailable), nothing sent; without
accounts, rows show no account counts and the card reads `Accounts unavailable: <message>`. A
4032 `NEEDS_NOUS_AUTH` answering `connectors.list` or `connectors.accounts` replaces the tab with
the unavailable screen showing T4 (`c` copies the command); a 4032 answering any other call
(policy, an action or a poll) is shown as T4 in a notice with no copy key, so `c` never has two
meanings on one screen (4.11). A 4032 from a poll ends the wait.

Rows: the union of `connectors.list` rows and catalog rows by slug (`connector` = `slug`). Display
name: catalog `name`, else the slug. Sort by display name, case-insensitive, then slug. Row:
`<name>` then the label from `connector_label`, first match:

0. an org or role layer does not allow the slug (H29) → `off by your organization`
1. the member layer does not allow the slug, or list row `enabled == false` → `off`
2. one or more accounts of this connector with `status == "active"` and not `disabled` →
   `connected · <n> account` / `accounts`
3. `connected == true` → `connected`
4. `connection_status == "pending"` → `connecting…`
5. `connection_status` one of `failed`, `expired`, `revoked`, `inactive` → `needs repair (<status>)`
6. catalog-only row (absent from the list) → `not offered`
7. otherwise → `not connected`

Typing `/` starts a filter over name, slug, category and description (every word must match,
case-insensitive); Esc clears the filter first.

Detail card (Enter): name, slug, category, description, state label, `status_reason` when
present, then the accounts of this connector from `account_view` (live accounts by name, retired
ones counted as `<n> retired (h shows)`), each `<name> · <status>`; name is `alias`, else
`<label> (unnamed)`, the label exactly as Hermes sent it. `<status>` is Hermes's `status` word as
sent (`pending`, `active`, `failed`, `expired`, `revoked`, `inactive`, or an unknown word as
is), or `retired` for a `disabled` account, as Hermes's terminal UI shows them
(`ui-tui/src/components/connectorsOverlay.tsx:78-79`; `ui-tui/src/i18n/en/connectors.ts:16-24`).
Order: live accounts by display name, case-insensitive, then `connection_id`; retired accounts
after them in the same order (`ui-tui/src/domain/connectorAccounts.ts:31-38`). Connected means `status == "active"`
and `disabled == false`; `active` is never read. Notices name an account by its alias when it has
one and otherwise by no name (labels are personal data, 4.13): for example `Account removed from
<app>.`, `An unnamed <app> account is connected.` Footer keys: `a add account · r rename · c reconnect · x remove · t tools ·
h retired · esc back` (only valid ones shown; `c` only when the selected account needs repair).

Account actions (on the selected account):

- **Add (`a`)**: name prompt `Name the new <app> account`, footer `enter connect · esc cancel`.
  `alias_problem`: invalid → `Use 1-32 lowercase letters, digits or -, starting with a letter or
  digit.`; taken (same connector, same alias, not retired, not this account) → `That name is
  already used.` Valid → `Connect { slug, Alias(name) }`.
- **Rename (`r`)**: prompt `Rename <app> account <name>` prefilled with the alias (empty when the account has none); same rules
  (own name allowed) → `RenameAccount`; reply → notice `Renamed to <alias> (<app>).`, reload accounts.
- **Reconnect (`c`)**: retired → `A retired account cannot be reconnected. Add another account
  instead.`; `active` → `<app> account <name> is connected.`; else `Connect { slug, Repair { id } }`.
- **Remove (`x`)**: confirmation `Remove <app> account <name>? This signs Hermes out of it.` with
  `y remove · n keep` (a confirmation is on screen only, so it may show the label); `y` →
  `RemoveAccount`; reply → `Removed <app> account <alias>.` or `Account removed from <app>.`,
  reload accounts and list.

### 4.5 The link state machine

```text
Idle --a/c--> Starting (Connect sent; card shows "Starting…")
Starting --reply settled or target state finished--> Idle + outcome notice + reload accounts, list
Starting --reply open--> Waiting(op_id, deadline_at, link?)
Starting --refusal--> Idle + error text
Waiting --every 2 s, none in flight--> PollOperation
Waiting --connection.update with this op_id--> PollOperation now (unless one is in flight)
Waiting --w--> WakeOperation, then PollOperation when it answers
Waiting --poll: finished--> Idle + outcome notice + reloads
Waiting --poll: transport error or code >= 5000--> stay, next poll in 2 s
Waiting --poll: 4004--> Idle, no error text, reload accounts and list
Waiting --poll: other code < 5000--> Idle + error text + reloads
Waiting --now > deadline_at--> Idle + T13 + reloads
Waiting --Esc / overlay closed--> Idle + T12 + reloads (no call: there is no cancel)
```

"Finished": `settled == true`, or `targets[0].state` in `connected`, `expired`, `failed`,
`not_connected`, `skipped`. Outcome notice: `connected` → `<app> account <alias> is connected.`
(no alias: `An unnamed <app> account is connected.`);
otherwise `targets[0].detail` if present, else `<app> did not connect. Try again.` Talaria sends
one slug, so only `targets[0]` is read; later targets are ignored. A reply whose `targets` is
missing or empty never finishes by target state and never panics: with `settled == true` it is
finished with `<app> did not connect. Try again.`; otherwise the wait continues (the card shows
`Starting…`) until a reply carries a target, the deadline passes, or Esc. The link is
`targets[0].connect_url` of the latest reply that carries one (connect or poll, H21); a reply
without one keeps the previous link; the card shows it only when it starts with `https://` (anything else:
`Hermes sent a link Talaria will not open.`). `o` → `OpenUrl` (P4-02's `opener_argv`); on failure
`The browser did not open. Copy the link above.` `c` → `CopyText(link)`. Over SSH (`SSH_CONNECTION`
or `SSH_TTY` set) the card adds: `This is a remote shell: open the link on any device where you
can sign in.` The countdown shows `mm:ss left`, repainting at 1 Hz only while waiting. Events
whose `owner` is not account, or whose `op_id` differs, are ignored (H19: broadcasts reach every
client).

The write slot (decision 12) is taken by `Connect` and released when `ConnectReply` arrives; the
wait, its polls and `w` never hold it, so a messaging save or a rules write may run during a link
wait. A second `a` or `c` while a wait runs is refused (`Already waiting for <app>.`).

`deadline_at` is a JSON number in the contract (`ConnectionOperationStatus`, required):
`talaria-app` accepts an integer or a float and drops the fractional part; a missing or
non-numeric value is `BadReply`. Deadline conversion happens in `talaria-app` when the reply is decoded: `deadline = Instant::now()
+ clamp(deadline_at − SystemTime::now() as epoch seconds, 0 s, 300 s)`. Core only sees the
`Instant`. Clock skew between Hermes and Talaria can make the countdown shorter or zero (then one
poll runs and T13 follows, section 7) but never longer than the operation's 300 s life.

### 4.13 Secrecy and personal data

- Typed values of non-list fields live only in the `talaria-tui` editor (`SecretField`, a
  `zeroize::Zeroizing<String>`), then in the wiring's `BTreeMap<String, Zeroizing<String>>` handed to
  `ConnectorsService::execute` for `UpdatePlatform` only, then in the PUT body. They never reach
  `Debug` (prints `[redacted]`), tracing, panics, notices, the transcript, history, the clipboard or
  a recording. `ForgetSecrets` zeroes them after the reply or on cancel.
- Accepted residual: `P4-01`'s `RestClient::request` takes `Option<&serde_json::Value>`, which
  cannot be zeroised and whose `Debug` would print the value. `update_platform` builds that
  `Value` immediately before the call, never logs or formats it, and drops it when the call
  returns; the `Zeroizing` originals are zeroed by `ForgetSecrets`. A zeroise-aware request path
  in `P4-01` would remove the residual; it is not part of this unit.
- The PUT goes over loopback HTTP, which `P1-04`'s recorder (WebSocket only) never sees. Test 33
  therefore checks the value only in the mock REST server's in-memory received request, and its
  absence from the recording file and captured tracing. This unit does not add REST recording.
- `connect_url` is held in core (it must be drawn), never in `Debug` output (`[link]`), notices,
  tracing, transcript or history, and only reaches the screen, `opener_argv` and `CopyText` on a
  key press. Recorded frames carry it as `[redacted]` through the by-name entry of decision 10;
  test 33 checks; a miss, or `P1-04`'s owner refusing the entry, is a stop condition.
- Allowlist entries (decision 7) may be shown in the overlay and its review; `Debug` prints their
  count; they never reach notices, tracing or history.
- `env_path` from the GET reply is dropped at decode time and never displayed (it is an absolute
  local path).
- Account `label` (often an email address), pairing `user_id` and `user_name` are third parties'
  personal data: on screen only (cards, rows and confirmations), never in notices, tracing or
  evidence. Notices use the account alias (a name the user chose, matching
  `^[a-z0-9][a-z0-9-]{0,31}$`) or no name. Evidence pane reads that contain them are redacted
  before they are attached.

Follow `P4-02`'s split. `talaria-core` holds the state machine and texts. `talaria-app` holds

### 4.15 The write slot

One write runs at a time across the overlay (decision 12). The table is the whole membership;
an effect not listed as holding the slot never takes it.

| Effect | Holds the slot | Released when these have answered (a reply or a failure) |
|---|---|---|
| `Connect` | yes | `ConnectReply` (the wait, its polls and `w` never hold it) |
| `RenameAccount` | yes | the reply and `LoadAccounts` |
| `RemoveAccount` | yes | the reply, `LoadAccounts` and `ListConnectors` |
| `SetConnector` | yes | the reply, `LoadPolicy` and `ListConnectors` |
| `SetTools` | yes | the reply and `LoadPolicy` |
| `UpdatePlatform` (save or toggle) | yes | the reply and `LoadPlatforms` |
| `ApprovePairing`, `RevokePairing` | yes | the reply, `LoadPairing` and `LoadPlatforms` |
| `ListConnectors`, every `Load*` (including `LoadTools { refresh: true }`), `PollOperation`, `WakeOperation`, `TestPlatform`, and the local effects (`OpenUrl`, `CopyText`, `OpenDoctor`, `EditSecret`, `ForgetSecrets`, `Notice`, `Close`, `GrantConsent`) | no | — |

- While the slot is held, a key that would emit a slot-holding effect shows T17 and emits
  nothing; non-holding effects still run. A second `t` while a test of the same platform runs is
  ignored.
- A refusal releases the slot once the refusal and any reload it names have answered (for
  example `POLICY_CONFLICT` → `LoadPolicy`, T25 → `LoadPlatforms`, T31 → `LoadPairing`).
- Sent or not is decided by the error type, never guessed: `ConnectorsFailure::NotSent` comes
  from `P4-02`'s mapping (`CallError::NotConnected`, `Encode`, `InvalidTimeout`;
  `RestError::{NotLoopback, TlsNotSupported, Ticket, Connect}`, `Timeout { sent: false }`,
  `Dropped { sent: false }`), so nothing changed: the slot is released at once, the reason is
  shown and drafts stay. `Unknown` comes from `CallError::TimedOut`, `Unknown`, `BadResult` and
  any `RestError` whose `outcome_unknown()` is true (`Timeout { sent: true }`,
  `Dropped { sent: true }`); a `BadReply` to a write counts as `Unknown`. Then T15 shows, the
  row's reloads are sent at once (if the socket is down they fail and `Reconnected` reloads the
  visible tab), the slot is released when they answer, and the write is never resent. `P1-02`
  and `P4-01` already record whether the request left, so this unit adds no transport hook.
- For a read, `NotSent` and `Unknown` are load failures (T6, T26, T27 or the screen's own text).

Error frame: `{"code":4090,"message":"That name is already used.","data":{"reason":"ALIAS_TAKEN"}}`.

### 5.2 REST

All requests: `P4-01`'s `RestClient::request`, fresh ticket, no `Origin`, `Content-Type:
application/json` on bodies, `profile` percent-encoded.

```text
GET  /api/messaging/platforms?profile=fixture
PUT  /api/messaging/platforms/signal?profile=fixture      {"env":{"SIGNAL_HTTP_URL":"<typed>"},"clear_env":[]}
PUT  /api/messaging/platforms/signal?profile=fixture      {"enabled":true}
POST /api/messaging/platforms/signal/test?profile=fixture
GET  /api/pairing?profile=fixture
POST /api/pairing/approve                                 {"platform":"telegram","request_id":"<id>","profile":"fixture"}
POST /api/pairing/revoke                                  {"platform":"telegram","user_id":"<id>","profile":"fixture"}
```

The PUT body omits `enabled` when unchanged, omits `env` entries for untouched keys, and sends
`clear_env: []` only when there is an `env`. List values are joined with `,` (no spaces).

## 6. Mock-server rules

- The mock gateway (`P1-12`'s, extended) answers only the 11 methods of section 5.1 with shapes
  from contract lines 568-748 and the schemas cited in 2.3; it rejects unknown params keys with
  4000 `INVALID_PARAMS` (as Hermes's pydantic models do, `additionalProperties: false`); it answers
  `-32601` for any other method; it can emit `connection.update` with `owner: {type: "account"}`
  and no `connect_url` (H19), and the empty-payload `platforms.changed` and `pairing.changed`.
- It never invents a cancel method, a `profile`-less refusal, or a field outside the schemas.
- The mock REST server (`P4-01`'s `MockRest::with_route`, created with `P4-05`'s
  `allow_own_profile_selector("fixture")`) serves the six routes of 5.2 with the shapes of 2.7.
  `P4-01`'s default mock answers every `profile` selector 403, so without the seam these routes
  never run. If `P4-05` has not merged, this unit adds the same opt-in with `P4-05`'s signature
  (`fn allow_own_profile_selector(self, profile: &str) -> Self`: the named profile, empty or
  `current` passes, another 403, default unchanged); whichever unit merges second rebases onto
  the first. The mock checks the ticket header is present and fresh, refuses a `profile` other
  than `fixture` with 403 `{"detail":"profile_scope_mismatch"}`, refuses a body value starting with
  `«redacted` with 400 and Hermes's text, and refuses a key outside the platform's `env_vars` with
  400.
- Fixture platforms come from a field-name capture of a live `GET` (test 38), with values replaced
  by placeholders; until that capture exists, from section 2.7 only.

## 7. Edge cases

| Case | Behaviour |
|---|---|
| Consent given, then the profile changes (`P1-12` reconnect to another profile) | consent is per profile name; the new profile asks again |
| `connectors.list` answers but `connectors.accounts` fails | rows show without account counts; card shows `Accounts unavailable: <message>` |
| Catalog has entries absent from the list | rows labelled `not offered`; `a` refused: `<app> is not offered to this profile.` |
| Two accounts with the same alias, one retired | allowed; retired rows never count as taken |
| Connect reply already settled (healthy account) | no card; outcome notice; reloads |
| Connect reply with no `connect_url` and not settled | card shows `Starting…`, polls until a link or an outcome appears |
| Connect or poll reply with empty or missing `targets` | not finished unless `settled` (then `<app> did not connect. Try again.`); never a panic |
| Account `status` word Talaria does not know | shown as sent; counts as needing repair (not `active`) |
| `connect_url` not https | not shown as a link; `o` and `c` refused with `Hermes sent a link Talaria will not open.` |
| Deadline in the past on arrival (clock skew) | one poll, then T13 |
| `connection.update` for another op or a session owner | ignored |
| Reconnect while a link wait for the same connector runs | refused: `Already waiting for <app>.` |
| Policy write reply arrives after the overlay closed | applied to state silently; the next open reloads |
| A tool is in the member list and also locked by an org layer | shown `off by your organization`; the member entry is kept untouched on save; nothing is added |
| An org or role layer denies a connector the member layer allows | row `off by your organization`; Space → T29 |
| Member layer `deny-all` | every row `off`; Space sends `enabled: true` for that slug (Hermes adds it to the allow list) |
| Space during a rules write's reloads | T17; nothing sent |
| A save or rules write with an unknown outcome | T15; drafts kept; reload after reconnect; never resent |
| Tools list empty | `<app> has no tools to choose.` |
| `GET /api/messaging/platforms` lists a plugin platform with no `docs_url` | no Docs line |
| `whatsapp_setup` present | ignored (QR onboarding is out of scope) |
| A required field cleared on an enabled platform | review row adds `(required; <name> will need setup)` |
| PUT 409 multiplex conflict | Hermes's detail; nothing else changes |
| Platform list reply without `platforms` | T26 with `the reply had no platforms` |
| Profile served by its own gateway process (no `platforms.changed`) | states refresh only on Ctrl+R, reopening or the next write |
| Pending row for a platform not in the list | shown under a `Other platforms` group in the Messaging list footer: `<n> waiting to pair on <platform>` |
| Change event while the card has drafts | refetch updates states; drafts kept; a field whose `is_set` changed under a draft gets ` (changed in Hermes)` |
| Reconnect after a dropped connection | `Reconnected` → reload the visible tab; an unknown write outcome is reported once (T15) |
