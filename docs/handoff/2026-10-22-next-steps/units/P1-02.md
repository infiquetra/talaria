## 1. What this unit is, and what it is not

Talaria is a Rust terminal client for Hermes. After unit P1-01 has found the gateway, minted a ticket, opened the WebSocket and finished the opening exchange (the handshake), the connection is a pair of WebSocket halves. This unit turns those halves into three things the rest of the client uses:

1. `Client::call::<M>(params)`: a typed request that returns the typed result or a typed error.
2. A stream of inbound items: notifications (events) and requests from the gateway to the client (server requests), each stamped with the number of the connection that carried it (the generation).
3. A rule for what a lost, late or unanswered message means: a call whose connection dropped has an unknown outcome and is never reported as success; a frame from a replaced connection is discarded.

It does not decide when to reconnect (P1-03), does not run the heartbeat (P1-03), does not track event sequence numbers (P1-03), does not record frames (P1-04), and does not decide how a person answers a question (P1-09, P1-12).

### 1.1 The hand-over from P1-01

P1-01 finishes with a `Connection` and offers `Connection::into_parts`, returning `ConnectionParts { sink, stream, instance_id, profile_id, next_request_id, buffered }`: the split WebSocket halves (`tokio_tungstenite` over a plain `TcpStream`), the instance identity, the profile identity, the next request id to use (3, because the handshake used 1 for `client.capabilities` and 2 for `runtime.describe`), and an ordered list of raw text frames that arrived during the handshake but were not consumed. This unit consumes that value by its owner's name and does not redefine it. If its fields differ from this description, adapt to what P1-01 merged; if something needed is missing, stop and report (issue, Stop conditions). The unit specification of P1-01 says `profile_id` may be an `Option`; adapt to what merged.

`ProfileId` has a private field. A test crate under `tests/` therefore cannot build `ConnectionParts` from a string. The test peer needs a `#[doc(hidden)]` constructor from P1-01 (suggested `ConnectionParts::for_test(sink, stream, next_request_id, buffered)`). This unit may not edit `connect.rs`; if no such constructor merged, stop and ask P1-01's owner for one (the issue's Dependencies and Stop conditions say so).

The handshake already sent `client.capabilities {server_requests: true}` (F-9). This unit must not send it again.

## 4. Frame classification

`rpc::classify(raw: &[u8]) -> FrameClass` is a pure, total function: it looks only at the bytes, never at the pending table, and never panics. `FrameClass` is `ServerRequest`, `Event`, `Reply` or `Malformed(MalformedKind)`. "Has a method" means a `method` key with a string value, as in Hermes' `isServerRequestFrame` (`json-rpc-channel.ts` L61-62); a null or non-string `method` counts as no method (so `{"id":3,"method":null,"result":{}}` is a `Reply`). The first matching row wins. This mirrors `isServerRequestFrame` and `handleFrame` in Hermes' channel (`json-rpc-channel.ts` L61 and L463-500) with the departures of section 6.3, and adds a place for everything else.

| # | Condition | Class |
|---|---|---|
| 1 | Not valid UTF-8, not valid JSON, or not a JSON object | `Malformed(NotJson)` (bytes or text that do not parse) or `Malformed(NotObject)` (valid JSON, not an object) |
| 2 | `id` is a string, `method` is a string, `method` is not `"event"` | `ServerRequest` |
| 3 | `method` is `"event"` and `params.type` is a string | `Event` (whatever the `id`) |
| 4 | a string `method` is present (any other case: a numeric id with a method; `"event"` without a string `params.type`) | `Malformed(UnexpectedRequest)` |
| 5 | No string `method`, `id` is an integer or a string, `result` or `error` is present | `Reply` |
| 6 | No string `method`, `id` is null or absent, `error` is present | `Malformed(GatewayError)` (for example the -32700 above) |
| 7 | Anything else | `Malformed(Unrecognized)` |

What the actor does next. A `Reply` whose id is an integer that waits in the pending table of the current generation completes that call. Any other `Reply` (an unknown integer, any string id) is an unmatched reply: counted in `unmatched_replies`, nothing else. A `Reply` counts as received traffic for the current generation (it moves `last_frame_at`) even when unmatched, because it proves the gateway is alive. `Malformed` frames also count as received traffic and in `malformed_frames`. A frame that arrives tagged with an older generation changes no counter except `stale_generation_frames`.

Counters across generations. `frames_received` and `last_frame_at` describe the current connection only: `begin_generation` sets them to 0 and `None`, and the buffered frames of the new parts are then counted as that generation's first frames. `unmatched_replies`, `malformed_frames`, `stale_generation_frames` and `dropped_without_decision` are totals for the whole life of the client and never reset. `pending_calls`, `open_server_requests` and `inbound_backlog` are gauges of the present moment. `inbound_backlog` is the number of items of any kind (`Event`, `ServerRequest`, `Malformed`, `Closed`) that sit in the inbound queue and that the consumer has not yet taken with `next()`; it is 0 once the `InboundStream` is dropped. P1-03 reads `frames_received` and `last_frame_at` as its liveness signal for the connection it just opened.

| `{"method":"event","id":"x","params":{"type":"message.delta","payload":{}}}`; `{"method":"event","id":5,"params":{"type":"message.delta","payload":{}}}` (a numeric id: Hermes would send it to the pending-call table; this unit delivers it as an event) | `Event` |

After classification, an `Event` is decoded with `EventFrame::from_params` and a `ServerRequest` with `ServerRequestFrame::from_request` (P0-03); their failures are `Malformed(BadPayload)`. The decoded items are produced by `channel::decode_frame` (section 7).

## 5. Call outcomes

| What happens | Error returned | Safe to retry? |
|---|---|---|
| No live connection when the actor takes the call command, or the sender task is already gone | `CallError::NotConnected` | Yes: nothing was registered or sent |
| `serde_json::to_value(params)` fails, or the value is neither an object nor null | `CallError::Encode` (no text) | Yes: nothing was sent |
| Timeout of zero | `CallError::InvalidTimeout` | Yes: nothing was sent |
| Reply with `result` that decodes into `M::Result` | `Ok(result)` | n/a |
| Reply with `result` that does not decode (a `null` counts when the type rejects null) | `CallError::BadResult { method, reason }`, `reason` the fixed phrase `result did not decode` | No: the gateway did the work |
| Reply with `error` (also when `result` is present too) | `CallError::Rpc(RpcError)` | Depends on `reason`; never by `code` alone |
| No reply before the timeout | `CallError::TimedOut { method, after }` | Not without an idempotency key: the gateway may still apply it |
| Connection closed, replaced, or write failed after the call was registered | `CallError::Unknown { method }` | Not without an idempotency key |
| Client closed with calls pending | `CallError::Unknown { method }` | same |

`CallError::outcome_unknown(&self) -> bool` is true for `TimedOut` and `Unknown`. The channel never retries a call on its own. A typed `null` params value (a method with no parameters) is sent as `{}`; any other non-object is `Encode` (F-2). The encoder does not remove `null` fields from an object; the generated parameter types decide what they serialize (P0-03), and a generated type that would send a `null` the gateway refuses is a P0-03 defect to report.

If the caller drops the future while the call is pending, the pending entry is removed at once (cancel safety). A reply that arrives later is an unmatched reply.

Two timing points. (1) `NotConnected` is decided by the actor when it takes the call command. With a current connection the call is registered and the frame is handed to the writer; the caller waits for the reply, not for the write result, and a write that fails afterwards makes the call `Unknown` (the frame may have reached the gateway). (2) The timeout clock starts when `call` starts, so a call queued behind a `replace_connection` spends that wait from its timeout.

## 6. Design

The exact structure is the builder's choice as long as the requirements in the issue hold. This shape is recommended because it follows the repository rule that application state is owned data passed through channels (no locks around the pending table).

```text
caller task                     actor task (one per Client)                 per-generation tasks
-----------                     ---------------------------                 --------------------
Client::call --Command::Call--> ChannelState: pending id -> {method, gen}   reader(gen N): next frame
   awaits oneshot / timeout     open requests: id -> Open|Answered|Cancelled   -> Command::Frame{N, bytes}
Responder::respond --Answer-->  generation: current                          -> Command::Closed{N, reason}
Client::replace_connection -->  inbound_tx: unbounded sender                writer(gen N): frames from actor
                                stats                                         -> Command::WriteFailed{N}
```

Rules the actor keeps:

1. Every `Command::Frame` and `Command::Closed` carries the generation of the task that produced it. The actor compares it with the current generation and discards a mismatch (counting it). The old reader may already have queued a frame when `replace_connection` bumps the generation, so this check, not the stopping of the old tasks, is what makes "a frame from a replaced connection changes nothing" true.
2. `replace_connection` order of operations: (a) bump the generation; (b) fail every pending call of the old generation with `Unknown`; (c) push `Inbound::Closed{generation: old, reason: Replaced}` if the old one had not already closed; (d) abort the old reader and writer; (e) start tasks for the new parts; (f) deliver the new parts' buffered frames first, in order, as generation-new frames. After (a), nothing from the old generation changes state. A closed client answers `Err(ClientClosed)` and never starts tasks.
3. `Closed` is the last inbound item for its generation, and it is delivered once.
4. Open server requests survive `replace_connection` (their answers are written to the current connection) until answered, ignored, dropped, cancelled by `request.cancel`, or `close()`. A `close()` of the whole client marks them `Cancelled`.
5. The request id counter is a single counter for the client's whole life, starting at the hand-over value, shared by typed calls and `call_raw`. It is not reset on `replace_connection`, so an id is never reused (defence in depth on top of rule 1). `Client::start` runs once per client life; a reconnect that built a new `Client` would restart both counters and break rules 1 and 5, so P1-03 must use `replace_connection`.
6. The inbound queue is unbounded. Reason: the gateway closes a peer that stops reading (F-20), and a bounded queue that blocks the reader would delay replies and pongs behind events. Its size is visible as `inbound_backlog`. If it becomes a problem, that is a finding for P1-11, not a reason to block the reader.
7. Timeouts are measured by the calling task with `tokio::time::timeout`; on expiry it sends a `Forget{id}` command so the table entry is removed, then returns `TimedOut`. A guard object sends `Forget{id}` on drop. `Drop` cannot await, so the guard and the `Responder` send on an unbounded command channel with a non-waiting send; the actor handles that command before the next `stats()` request, which is why `pending_calls` is already 0 right after a caller drops its future (test 12).
8. Outgoing frames go through one function, `channel::write_frame`, and incoming frames through one function, `channel::decode_frame`; both are named in the rustdoc and are the only places that touch the WebSocket halves' text. P1-04 adds its recording tap at exactly these two places and replays through `decode_frame` with `Responder::detached`. This unit adds no tap, but it makes the generation available at both.
9. A call made while a replace runs is queued behind the replace command (the actor handles commands in order) and goes to the new connection, or returns `NotConnected` if there is none. Its timeout clock started when `call` started (section 5).
10. `Responder::respond` and `fail` have no timer of their own. A stalled write ends when the connection ends (P1-03's heartbeat closes a connection that stops answering), and the waiting `respond` then returns `NotConnected`. A caller that wants a bound wraps the call in `tokio::time::timeout`.

### 6.1 Responder states

```text
Open --respond/fail--> Answered  (frame written, first wins; later calls return AlreadyAnswered)
Open --respond/fail, no connection or write failed--> Open  (returns NotConnected; the caller may retry after a reconnect)
Open --request.cancel event--> Cancelled  (later calls return Cancelled and write nothing)
Open --Responder dropped without a decision, connection current--> Answered(error -32603)  [counted as dropped_without_decision]
Open --Responder dropped without a decision, no connection--> Closed  [nothing written, open_server_requests falls, counted as dropped_without_decision]
Open --ignore()--> Ignored  (nothing written; used for requests another viewer owns)
Open --client close()--> Cancelled
```

`respond` and `fail` take `&self` and are async: each sends an `Answer` command to the actor and waits for the write result. Taking `&self` (not `self`) is deliberate: it makes "NotConnected leaves the request answerable" possible and makes `AlreadyAnswered` reachable through the public API. `ignore` takes `self`. `Responder` is not `Clone`; dropping it undecided sends the -32603 answer when a connection is current. With no connection, the -32603 answer cannot be written and the responder is gone, so no later retry is possible; the request is closed with nothing written (leaving it open would leak the entry for ever). The gateway then waits out its own deadline for that request, and the agent does not read the drop as a skip.

`respond` writes on whatever connection is current when it is called. The gateway accepts an answer only from a viewer that is attached to the session (F-13); after a reconnect the new connection is not attached until P1-03 re-attaches it (`session.resume`), and the gateway drops an unwanted answer silently (a debug log line only). So an answer written too early is lost without an error here. P1-03 re-attaches first.

An error answer, whatever its code, makes the owner settle the request as "no answer" for every viewer (F-12). For `sudo` and `secret` the agent reads an empty value as the person skipping. So a dropped responder, `fail`, and the automatic -32601 and -32603 answers described below all look like a skip to the agent. The rustdoc of `Responder` says this, and P1-09's author must know it: only `ignore()` leaves a request alone. This unit reads no `declines_not_shown` and sends no 4404 decline (Hermes' own channel does when the backend asks for it, `json-rpc-channel.ts` L387-391; P1-09 decides whether Talaria needs it).

### 6.2 What the typed layer takes from P0-03

P0-03's issue fixes these paths and this unit uses them as written: `hermes_contract::method::Method { const NAME: &str; type Params: Serialize; type Result: DeserializeOwned }`; `hermes_contract::native::NativeMethod: Method {}`, implemented on the `Marker` struct of each native method; `hermes_contract::methods::{legacy, canonical}::<method>::{NAME, Params, Result, Marker}`; `hermes_contract::events::{Notification, EventFrame, ServerRequest, ServerRequestFrame, DecodeError}`. `Client::call::<M: NativeMethod>(params: M::Params) -> Result<M::Result, CallError>` uses `M::NAME`. The compile-fail case is `hermes_contract::methods::legacy::session_compress::Marker` (a module path such as `hermes_contract::legacy::session_compress` is not a type). `EventFrame::from_params(&Value)` already carries the envelope fields and covers the five hand-written events (`approval.request`, `approval.settled`, `clarify.request`, `clarify.settled`, `session.replay_gap`), which are not in the contract's `x-notifications` (80 entries; `gateway-events.ts` L33-49 says they are "not part of the generated contract"). The channel wraps it in `InboundEvent { generation, frame }`. If the merged crate differs from this, stop and report (issue, Stop conditions).

### 6.3 Departures from Hermes' own channel

The roadmap says to match Hermes' behaviour; these seven are deliberate departures, listed with their `json-rpc-channel.ts` lines in the rustdoc of `rpc.rs` and `channel.rs` (F-29). Review checks the rustdoc text; no test does:

| # | Hermes | This unit | Why |
|---|---|---|---|
| a | A frame with a non-null id goes to the pending-call table (L470), also when it has a `method`; an unmatched one is dropped | A numeric id with a `method` other than a valid `event` is `Malformed(UnexpectedRequest)` (a valid `event` with a numeric id is departure b) | A frame that looks like a request must never settle a call whose id it happens to carry |
| b | An event with a non-null id goes to the pending-call table before the event branch (L470 before L500), so it is never delivered as an event | An event is an event whatever its `id` | Nothing is dropped; ids on events are not defined by Hermes |
| c | A timeout of zero or less sets no timer (L298): the call waits forever | `InvalidTimeout`, nothing sent | A call that can wait forever is the failure this unit exists to prevent |
| d | A responder is marked settled before its write (L371), so a failed write is final | A failed write is `NotConnected` and the request stays answerable | The person's answer is not lost to a dying socket |
| e | A reply with a non-null id and neither `result` nor `error` resolves the waiting call with `undefined` (L470, L493) | `Malformed(Unrecognized)`; the call stays pending until its timeout | `undefined` would read as success for a call whose outcome is unknown; no `Ok` without a `result` |
| f | A frame with `id: null` and an `error` (for example -32700) is ignored (L470 skips it, L500 does not match) | `Malformed(GatewayError)` is reported | A person can see that the gateway could not parse a frame |
| g | An event whose `params.type` is not a string is ignored (L500) | `Malformed(UnexpectedRequest)` is reported | Nothing is dropped without a trace |

The reference slice `proto.rs` is for shapes only: its `decode` keeps the first 80 characters of a non-JSON frame (L94; REQ-6 forbids keeping frame text), has no server-request branch, and its `EventFrame` lacks `replay_epoch`, `authority_epoch` and `admission_id`.

### 6.4 Debug, Display and error text

REQ-13 draws the boundary so every type is decided, not just the three the issue names:

| Type | `Debug` and `Display` show | They never show |
|---|---|---|
| `RpcError` | `code`, `reason` (a short token), the length of `message`, the length of `data` | `message` text, `data` content (the fields stay public: callers read them) |
| `CallError` | variant, method name, code, durations | any text from a reply; `Encode` and `BadResult.reason` are fixed phrases |
| `InboundEvent` | generation, event type name, `session_id`, `seq` | the payload |
| `MalformedFrame` | generation, kind, length, label (at most 64 characters of an event type) | frame text |
| `ServerRequest` | generation, id, kind, `session_id`, length of params | params content |
| `Responder`, `RespondError` | id, state | any answer |
| `ChannelStats`, `Generation`, `CloseReason` | all fields | n/a |

Test 5 puts a sentinel (`SENTINEL-TEXT-123`) only in the fields that the table says are hidden: `RpcError` `message` and `data`, an event payload, a server request's params (including its command) and an answer. It checks that no `Debug` or `Display` output contains the sentinel, and, as a separate positive check, that the fields printed by design (`reason`, event type, `session_id`, ids, method names, lengths) do appear, so an empty `Debug` cannot pass. The printed fields are short tokens chosen by the gateway; they are not placed under the sentinel. The channel's own `ServerRequest` hides params; its public field `request` is P0-03's generated type, whose derived `Debug` may print the command, so the rustdoc of `ServerRequest` says to log only the `kind`. A test failure message compares with a boolean and prints lengths, and the peer's receive helper panics with a fixed message, never with frame text.

## 9. Edge cases

| Case | Expected behaviour |
|---|---|
| Two replies arrive for one id | The first completes the call; the second is an unmatched reply (counted). |
| A reply is split across fragments | The WebSocket library delivers whole messages; if a library returns a fragment, that is a library bug, not handled here. |
| Binary message | If valid UTF-8, treat as text (Hermes' client does, `json-rpc-channel.ts` L175 `wireFrameText`); otherwise `Malformed(NotJson)`. |
| Frame over the size limit | The library fails the read; the connection closes with `CloseReason::Error`. P1-01 sets the 8 MiB limit. |
| `result: null` | Decode into `M::Result`; if the type does not accept null, `BadResult`. |
| Reply has both `result` and `error` | Treat as an error reply (Hermes checks `error` first, `json-rpc-channel.ts` L483-484). |
| Reply with an integer id that waits, and neither `result` nor `error` | `Malformed(Unrecognized)`; the call stays pending until its timeout. |
| Reply with a string id (for example a heartbeat id) | `Reply` class, then unmatched: counted, nothing else (this unit sends no string ids; P1-03 uses integer ids through `call_raw`). |
| Server sends an event with an unknown `type` | Delivered with `Notification::Unknown(value)`. P1-05 surfaces it once per connection. |
| Known event whose payload has a wrong type | `Malformed(BadPayload)` with `label` = the event type, capped to 64 characters. The payload text is not kept. |
| Server request with an unknown `method` | Not delivered as a request the application can answer. The channel answers `-32601` with message `no handler for server request: <method>` at once, counts it, and delivers `Malformed(UnknownServerRequest)` once per method per connection so a person can see that Hermes is newer than the pin. |
| Server request whose params do not decode | The channel answers with error code -32603 and message `server request params could not be read: <method>` and delivers `Malformed(BadPayload)`; no request is delivered. Hermes defines no invalid-params answer for this case; -32603 is what its own channel uses for a handler that failed (U-3). |
| `request.cancel` with a reason outside `timeout`, `interrupted`, `resolved` | Still cancels the matching responder: the schema types `reason` as a plain string (F-14). |
| `respond` called after the connection was replaced | Written on the current connection; the gateway may drop it unless that connection re-attached (section 6.1). |
| `respond` with no connection, or the write failed | `NotConnected`; the request stays open and answerable. `respond` has no timer of its own (section 6, rule 10). |
| `Responder` dropped while no connection is current | Nothing written; the request is closed; `dropped_without_decision` counts it (section 6.1). |
| `InboundStream::next()` after a `Closed` that is not the client's last | Waits for the next generation's items; it returns `None` only after `Closed{ClientClosed}` or when every `Client` clone is dropped. |
| `call` made while `replace_connection` is running | Queued behind the replace command; goes to the new connection, or `NotConnected` if there is none. The wait counts toward its timeout. |
| `replace_connection` on a closed client | `Err(ClientClosed)`; nothing starts. |
| `close()` while calls are pending | Each pending call returns `Unknown`; open responders become `Cancelled`; `Closed{ClientClosed}` is delivered once; later `call` returns `NotConnected`. |
| `replace_connection` with buffered frames | They are processed before any frame read from the socket, in order, with the new generation. |
| Socket ends with no close frame | `Closed{Error(UnexpectedEof)}`, unless the library reports an I/O error, then that kind. |
| Close frame with a code | `Closed{RemoteClosed{code}}`; code 1011 is `Overloaded`. |
| Event consumer dropped (`InboundStream` dropped) | The actor keeps working for calls; inbound items are discarded; server requests are answered `-32601` at once (nobody can answer them). |
| Timeout fires at the same moment as the reply | Whichever the actor sees first wins; the other is an unmatched reply. The call returns exactly one outcome. |
| Caller drops the call future | The entry is removed at once, nothing is returned, a later reply is unmatched. |

## 12. Design reasoning

- **Why an actor task and not a locked map.** The repository rules forbid `Rc<RefCell>` webs and ask for state owned by one task and changed by messages. A pending table behind a mutex also invites the exact bug the history report warns about: a late frame from an old connection updating state. With one task, "compare the generation, then act" is one place. Splitting the state into a socket-free `ChannelState` makes the rules unit-testable without sockets (tests 6 to 8).
- **Why a generation number on every frame.** The history report (`u03` section 3.1, lesson 13) records that ids and epochs restart on reconnect, so only a per-connection counter can tell a late frame from a live one. Lesson 13 says such a frame updates history but never liveness; this unit goes one step further and delivers nothing from a stale generation, because P1-03 replays the missed events from its last delivered `seq`, which keeps history complete. Hermes' TypeScript client avoids the problem by never matching across transports (`owns(transport)`, `json-rpc-channel.ts` L255-257); in Rust the equivalent is a number.
- **Why `TimedOut` is separate from `Unknown`.** Both mean the outcome is unknown, but the person needs different words: "no answer in 120 s" against "the connection dropped". `outcome_unknown()` joins them for code that only cares about retry safety.
- **Why `call_raw` exists.** It lets tests send a refused method (`session.compress`) without a typed binding, and lets P1-03 send `gateway.ping`, which is not a canonical method, using the same integer id counter. A string-id side channel for pings would need a second match table in this unit; one counter and one table is simpler, and the gateway echoes any id (F-30).
- **Why `respond` takes `&self`.** A responder that is consumed by a failed write cannot be retried, yet a person's answer must survive a dying socket. With `&self`, the first successful answer wins at run time (`AlreadyAnswered`), and `ignore(self)` and drop still end the request by construction.
- **Why a dropped responder sends -32603.** Hermes does the same when a handler throws (F-16). It frees the agent from a 120 s wait for a person who is not going to answer. The cost (F-12) is that sudo and secret prompts read as skipped; `ignore()` exists for requests that belong to another viewer.
- **Why the 300 s for `approval.respond`.** Both approval and clarification responses return at once on the gateway (F-30), so 300 s is not a wire need; it is parity with Hermes' named constant and with the architecture rule "approval responses may take up to 300 s". Keep it.
- **Rejected: bounded inbound queue.** It would stall replies and pongs behind events and, after 30 s, make the gateway close the connection (F-20).
- **Rejected: automatic retry inside `call`.** A retry of a call whose outcome is unknown can apply it twice. The caller knows which calls carry an idempotency key (for example `prompt.submit` needs `submission_id` or `input_id`; the generated override in P0-03 handles that).
- **Rejected: a separate "pending approvals" table in the channel.** Keying approvals by session, prompt and execution generation belongs to the reducer (P1-05), where the events are folded.
- **Rejected: a second `EventFrame` struct in this crate.** P0-03 already provides `hermes_contract::events::EventFrame`; a duplicate name would confuse every consumer. The channel type is `InboundEvent { generation, frame }`.

## 13. Notes for the owners of other units

These follow from this unit's decisions; the lead relays them.

- **P1-03 (heartbeat and reconnect).** Send the ping as `call_raw("gateway.ping", json!({}), CallOptions { timeout: Some(..) })` with the integer id this unit assigns, and treat its reply as the pong; do not send `hb-<n>` string ids (this unit counts a string-id reply as an unmatched reply and drops it). Reconnect through `replace_connection` on the one `Client`; never start a second `Client`. Read `stats()` (`frames_received`, `last_frame_at`) as the liveness signal. Re-attach to each session before P1-09 answers a server request, and verify at the pin that the re-attached session keeps the event stream the request went out on (U-7). `frames_received` and `last_frame_at` restart at 0 and `None` for each new generation, so the liveness signal always describes the connection just opened; the other counters are totals for the client's life.
- **P1-01 (connection).** Provide a `#[doc(hidden)]` constructor for `ConnectionParts` usable from `tests/` (`ProfileId` has a private field), and keep `WsSink`/`WsStream` over a plain `TcpStream`.
- **P1-09 (prompts).** A dropped `Responder` and `fail` both read as a skip for `sudo` and `secret` (F-12); only `ignore()` leaves a request alone. The result shapes of `approval`, `setup_beat` and `theme.pick` are P1-09's.
- **P1-04 (recording).** Call `channel::write_frame` and `channel::decode_frame` seams; replay with `Responder::detached(counter)`.
