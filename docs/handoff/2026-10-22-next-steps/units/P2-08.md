## 1. What the unit does, in one picture

```text
 keys / commands                                gateway frames
      │                                               │
      ▼                                               ▼
 talaria-tui queue::input ──QueueIntent──►  talaria-core (pure)
   (selection mode, edit       │             QueueState: rows, fences, ledger,
    mode, key routing)         │             selection, edit, plan, id map
                               │             reorder::plan_reorder, move_target
 talaria-tui queue::preview ◄──┤ QueueView   notices::refusal_notice
   (indicator, preview,        │             update_queue -> Vec<Effect>
    selection window)          ▼
                     talaria-app QueueService ──► hermes-client Client::call
                       makes one call per effect (the reducer steps plans):
                         prompt.cancel         {session_id, admission_id}
                         prompt.replace_queued {session_id, admission_id, submission_id, text}
                         prompt.steer_queued   {session_id, admission_id}
                         prompt.resolve_unknown{session_id, admission_id, execution_generation}
                         session.steer         {session_id, execution_generation, text}
                       (prompt.submit {session_id, text, submission_id} stays P1-05's
                        Effect::SendPrompt, executed by P1-12, retries included)
                       and turns replies into Events:
                         QueueCallResult | QueueCallRefused | QueueCallUnknown | SteerResult
                       (+ QueueReconcileDue, posted by the app 5 s after an unknown outcome)
 session.info / message.start / message.complete frames ──► P1-05's Event::Session ──► reducer
 send-now's interrupt ──► P1-05's Event::Interrupt transition ──► Effect::Interrupt ──► P1-12
```

The gateway owns the queue. Talaria projects it from two sources: the `pending` list of a `session.create` or `session.resume` snapshot, and the queue fanout (`session.info` frames whose payload has `pending`). Both reach the reducer through `P1-05`'s existing paths (`from_snapshot` and `Event::Session { session_id, frame, raw }`); `QueueState` lives inside `P1-05`'s `SessionState`, so plan stepping, reconciling and cell drawing are all decided in one pure reducer. Everything Talaria decides (what counts, what is stale, which rows to re-admit, which notice to show) is pure and lives in `talaria-core`. Calls live in `talaria-app`. Drawing and key routing live in `talaria-tui`. This follows the layer table in [05-architecture.md](../05-architecture.md#layers).

## 3. Request and result shapes

Values below are examples. Field sets are exact.

### 3.1 `prompt.submit` and its receipt

```json
{"jsonrpc":"2.0","id":41,"method":"prompt.submit",
 "params":{"session_id":"<sid>","text":"Reply with the word omega in capital letters.",
           "submission_id":"talaria-3f9a0c12d4e5b6a7-4"}}
```

This unit adds no key; the `submission_id` is the one `P1-12` makes (`talaria-<launch id>-<n>`). `queued` and `unattended` must be absent or `false` (`P0-03`'s constructor may serialise `false`, which Hermes accepts; `queued` is ignored, H21); `unattended: true` is never sent (it auto-approves every dangerous command in the turn); `profile` is never sent (H59); `display_kind` is never sent. `attachments` appears only when `P2-04` supplies a non-empty list, and a retry (REQ-9) resends the identical params. Result while a turn runs:

```json
{"admission_id":"a3f…","ref":{"profile_id":"<profile>","session_id":"<sid>"},"sequence":12,
 "status":"queued","outcome":null,"authority_epoch":3,"execution_generation":null}
```

When idle the receipt may already read `started` with an integer `execution_generation`. A voice stop reads `{"voice_stopped":true}`.

### 3.2 The queue fanout (`session.info`)

```json
{"jsonrpc":"2.0","method":"event","params":{
  "authority_epoch":3,"execution_generation":7,"admission_id":"9c1…",
  "type":"session.info","session_id":"<sid>","replay_epoch":"e41…","seq":233,
```

The envelope stamp (`authority_epoch`, `execution_generation`, `admission_id`) is whatever the stream's current execution stamp is (H41); read queue facts from the payload. ### 3.3 Edit and move: `prompt.replace_queued`

```json

  "submission_id":"<fresh uuid kept for retries>","text":"Reply with the word anchor in capital letters."}}
```

Result: the new admission's `AdmissionStatus` (new `admission_id`, a higher `sequence`, status `queued`). The old row disappears from the next fanout.

### 3.4 Remove: `prompt.cancel`; discard: `prompt.resolve_unknown`

```json
{"method":"prompt.cancel","params":{"session_id":"<sid>","admission_id":"a3f…"}}
{"method":"prompt.resolve_unknown","params":{"session_id":"<sid>","admission_id":"b77…","execution_generation":6}}
```

Cancel result: `status: "terminal"`, `outcome: "cancelled"` for a queued row; for an already terminal row the row as stored (another outcome). `resolve_unknown` sends exactly three keys (H34); the generation is the row's own integer `execution_generation`.

### 3.5 Steer: `prompt.steer_queued` and `session.steer`

```json
{"method":"prompt.steer_queued","params":{"session_id":"<sid>","admission_id":"a3f…"}}
{"method":"session.steer","params":{"session_id":"<sid>","execution_generation":7,"text":"The code word is HERON."}}
```

`prompt.steer_queued` result: the receipt, reading `status: "started"`, `outcome: null` (H26). `session.steer` result: `{"status":"queued"|"redirected"|"rejected","text":…,"execution_generation":7,"authority_epoch":3,"delivered":false|null}` or `{"voice_stopped":true}`. `redirected` answers only `session.redirect`, which this unit never sends; treat it as `queued` if it ever arrives.

### 3.6 Settlement frame of a steer, cancel or replace

```json
{"jsonrpc":"2.0","method":"event","params":{"authority_epoch":3,"admission_id":"a3f…",
  "type":"message.complete","session_id":"<sid>","replay_epoch":"e41…","seq":251,
  "payload":{"text":"","content":"","admission_id":"a3f…","outcome":"steered"}}}
```

No `execution_generation` in the envelope, no `status` in the payload. `content`, `admission_id` and `outcome` are not in `MessageCompletePayload` (H16); `P0-03` strips `additionalProperties: false`, so the decode succeeds and those fields are simply not typed. Classify by the envelope (section 6.6), never by the payload. The same frame, with `outcome: "cancelled"`, follows every cancel and every replace (an edit or a plan step) for the retired admission (H31); by then the fanout has already dropped that row.

## 5. State machines

### 5.1 One queued row, as Talaria sees it

```text
   (submit receipt queued, or fanout lists it queued)
                 │
                 ▼
             ┌────────┐ replace / move step ok ┌──────────────────────────────┐
             │ queued │───────────────────────►│ gone; id_map old -> new row  │
             └────────┘                        └──────────────────────────────┘
              │  │  │ cancel ok (terminal/cancelled): gone, text back in composer
              │  │  └──────────────────────────────────────────────────────────►
              │  │ steer_queued ok
              │  ▼
              │ ┌──────────────────────────┐ turn settles, delivered  ┌──────┐
              │ │ started + steering: true │─────────────────────────►│ gone │
              │ └──────────────────────────┘                          └──────┘
              │        │ undelivered: back to queued in its own place (returned_from_steer)
              │        └──────────────────────────► queued
              │ drain claims it
              ▼
         ┌─────────┐ turn completes ┌──────┐        ┌─────────┐ resolve_unknown ┌──────┐
         │ started │───────────────►│ gone │        │ unknown │────────────────►│ gone │
         └─────────┘                └──────┘        └─────────┘                 └──────┘
                (a gateway restart during a turn leaves an `unknown` row that pauses the FIFO)
```

### 5.2 Composer modes and key routing

Routing order for every key: global keys (`P2-11`'s Ctrl+T, looked up in `KeyContext::Composer` whatever has focus), then a focused `P1-09` card, then queue selection or edit mode, then `P2-03`'s palette, then the composer.

```text
 Composing ──Up (empty draft, caret on first line, a counted row, no focused card)──► Selecting
 Composing ──/queue alone with a counted row──► Selecting
 Selecting ──Up past oldest──► Composing with history (P1-08's Up)
 Selecting ──Down past newest / queue_leave / any key not bound in QueueSelection──► Composing (the key is typed)
 Selecting ──queue_edit on a row with replace──► Editing(row)
 Editing ──submit chord, text changed and non-empty──► Composing; ReplaceQueued, then a restore plan
 Editing ──submit chord, text unchanged──► Composing; no call
 Editing ──submit chord, text empty or blank──► stays Editing; "An empty edit…" notice; no call
 Editing ──Esc──► Composing (draft cleared, no call)
 Editing ──row starts (fanout lists it started) or leaves pending──► Composing with the text kept as a draft (notice)
 Any ──P1-09 card focused──► the card owns keys; Selecting cannot start
```

In Editing, the `submit` chord is taken before `P1-08`'s blank-draft rule, `P2-03`'s slash dispatch and `P2-05`'s `!` classification (P2-05's REQ-1 already places edit mode first), so an edited prompt that starts with `/` or `!` stays a prompt. `newline` still inserts a line break. Arrow keys move the caret only: no history, no selection. `composer_send_now`, `composer_steer` and the Esc interrupt are not reached while Editing (Esc cancels the edit instead). Selection and edit mode never start while a plan or edit save runs (`in_flight` or `plan` is Some): `Still moving prompts…`. The full list of what is refused and what is allowed while busy is section 13.6.

### 5.3 A move plan

```text
 Idle ──Move / SendNow / edit restore──► current = ids of `queued` rows (sequence order); target = move_target(current, id, placement)
      ├─ empty plan ──► Done at once (send-now still checks REQ-21 and may interrupt)
      ├─ a planned row lacks replace ──► Idle, unsupported_control notice naming the row, no call
      └─ emit ReplaceQueued(step 0); in_flight = step 0
 Running(i) ──QueueCallResult──► id_map[old]=new; known += new; i+1: emit step i+1, or Done
 Running(i) ──QueueCallRefused──► Stopped: notice of 6.11; compare final order
 Running(i) ──QueueCallUnknown──► Reconciling(i)
 Reconciling(i) ──fanout or snapshot lists a row with input_id = step i's submission_id──► treat as QueueCallResult
 Reconciling(i) ──QueueReconcileDue, or a fanout without it, not yet retried──► re-emit the identical step (same submission_id); retried = true
 Reconciling(i) ──retry lost or refused──► Stopped: "Hermes did not confirm the change. Check the queue."
 Done ──then_interrupt = Some(g), last result `queued`, P1-05's turn Running with generation g──► Event::Interrupt transition for g
 Done ──then_interrupt = Some(g), any check fails──► "The turn you meant to stop already ended. Your prompt is first in the queue."
 Done/Stopped ──order of the target's rows in the latest fanout ≠ target──► "The queue changed while moving prompts. This is the order Hermes holds."
```

The final-order check looks only at the target's admissions (through `id_map`); rows submitted during the plan land at the back and are ignored. Started, steering and `unknown` rows are never in `current` or `target`: re-admission puts a row after every existing row, so only the order of queued rows among themselves changes. An `unknown` row sits ahead of every queued row (it was claimed from the head), so a plan never needs to pass it.

## 6. Edge-case tables

### 6.1 What each row does (REQ-3, REQ-4)

| Row | Counted in `queued (n)` | Shown | Selectable | Actions |
|---|---|---|---|---|
| `queued`, controls `[steer, replace]` | yes | yes | yes | edit, remove, steer, move, send now |
| `queued`, controls null or `[]` (attachments, hidden display, automation, non-interactive source) | yes | yes | yes | remove only; others show `Hermes does not offer that action for this prompt.` |
| `unknown` | yes | yes, as `⚠ lost in a gateway restart · d to discard` | yes | discard (`prompt.resolve_unknown`) only |
| `started`, `steering: true` | no | the steering line | no | none |
| `started`, `steering` false or null | no | no (it is the running turn) | no | none |
| `Other(_)` (for example `terminal`) | no | no | no | none |

Only `queued` rows enter a move, send-now or restore plan. Edit, steer, move and send-now on an `unknown` row show `A lost prompt can only be discarded. Press d to discard it.` and make no call. When several rows are steering, the steering line shows the newest (highest `sequence`) and ends `(+k more)`.

### 6.2 Stale and partial frames (REQ-2, REQ-5)

| Case | Result |
|---|---|
| Fanout with `authority_epoch` equal to the fence's and `execution_generation` below the fence's | dropped |
| Fanout with a higher `authority_epoch` | applied; both fences reset to this frame |
| Fanout with a lower `authority_epoch` | dropped |
| Same `replay_epoch`, `seq` ≤ last applied queue `seq` | dropped |
| Different `replay_epoch` | applied (cannot be compared; the current owner wins, H52); the seq fence adopts the new epoch |
| Snapshot | replaces the rows; fences set to `(authority_epoch, execution_generation)` and `(replay_epoch, last_sequence)` |
| Frame `seq` 15 after a snapshot with `last_sequence` 20, same epoch | dropped |
| Settings `session.info` (no `pending`) | queue untouched; only present settings fields merge (H54) |
| Fanout `pending: []` | queue empty; the indicator and preview disappear |
| Fanout without `authority_epoch` or `execution_generation` (or null) | that comparison is skipped; the other fence still applies (at v0.22.4 both are integers in every fanout, H27) |
| Fanout without `replay_epoch` or `seq` in the envelope | the seq comparison is skipped |

### 6.3 When the user cell is drawn (REQ-8)

`P1-05` already draws an idle submit's cell at once (no turn running and no earlier submit waiting) and keeps that rule. For every other admission this unit replaces `P1-05`'s first-in-first-out match at `message.start` with matching by admission:

| Trigger, first one wins | Text source |
|---|---|
| `message.start` whose envelope `admission_id` is a known admission (or a ledger entry's `admission_id`) | the row's `text`, else the ledger |
| A fanout listing a non-steering `started` row that is known, or whose `input_id` is a ledger key | the row's `text` |
| `message.start` with no envelope `admission_id` (older recordings, hand-built frames) | `P1-05`'s first-in-first-out match, unchanged |
| A snapshot lists a `started` row | no cell; the history already holds the prompt |

- A **known** admission is one listed `queued` by a snapshot or a fanout, or returned by a submit or replace receipt (any status). Snapshot `queued` rows are known, so a prompt queued before `/quit` gets its cell when it starts after `talaria -c` (UAT-7).
- The ledger is keyed by `submission_id` and stores the text; the receipt adds its `admission_id`. Before the receipt arrives no `message.start` can match a ledger entry by admission, but `_stamp_claim` publishes the fanout right after `message.start` under the same lock (H40), and that fanout matches by `input_id`. This is the race of test 11.
- Rows from other clients are known through the fanout and get a cell with their own text when they start; they never take this client's ledger text.
- A cancelled or replaced row leaves the ledger and `known`; its replacement is known through its receipt.
- Each admission gets at most one cell (`drawn`). The cell goes after every cell of the reply that was streaming when it started.
- An idle submit's cell was drawn at submit, so its ledger entry has `cell_drawn: true`. Whatever trigger later matches that entry (its receipt's `admission_id`, a `message.start` naming it, or a fanout listing its `input_id`) adds the admission to `drawn` and draws nothing. So an idle prompt gets exactly one cell (test 11's `idle_submit_gets_one_cell`).
- A ledger entry leaves the ledger when its admission enters `drawn`, when its row is cancelled or replaced, on `P1-05`'s `Event::SubmitFailed` for its `submission_id`, and when a lost submit's text is returned (REQ-9). The ledger therefore holds only own submissions whose cells are not drawn yet; `drawn` keeps the admission so no later trigger draws it again (section 13.3).

`P1-05` tests that feed `message.start` without an envelope `admission_id` keep passing through the fallback. A `P1-05` test that turns red goes back to the test author with a written reason and is updated to feed receipts or fanouts; it is never deleted.

### 6.4 `plan_reorder` examples (tests 15 to 17)

### 6.8 Lost replies (REQ-9, REQ-18)

On an unknown outcome (`P1-02`'s lost reply) the reducer marks `in_flight.awaiting_reconcile` and waits for the first of: the next applied snapshot or queue fanout, or `Event::QueueReconcileDue` (posted by the app `RECONCILE_WAIT`, 5 seconds, after the unknown outcome; a deadline matters because an idle session that never committed the call publishes nothing). Then:

| Call | Committed when | Otherwise | After a lost or refused retry |
|---|---|---|---|
| `prompt.submit` | a row has `input_id` = the `submission_id` | retry once with identical params (text and any attachments; exact replay, H23) | text back to the composer; `Hermes did not confirm the prompt. It is back in the composer.` |
| `prompt.replace_queued` (edit save or plan step) | a row has `input_id` = the step's `submission_id`: map ids, continue the plan | retry once with the same params. This is safe whether or not the first call committed: Hermes answers an exact retry (same old admission, same new `submission_id`) with the same new admission (H32); if the old row started meanwhile it refuses `admission_started` | stop; `Hermes did not confirm the change. Check the queue.` |
| `prompt.cancel` | the row is gone from `pending` | never retried; row still `queued`: `Hermes did not confirm the removal. The prompt is still queued.`; row `started`: `That prompt had already started, so it was not removed.` | (no retry) |
| `prompt.steer_queued` | the row lists `steering: true` | never retried; row still `queued`: `The steer did not reach the turn. The prompt is back in the queue in its place.` | (no retry) |
| `session.steer` | cannot be told from the queue | never retried; text back in the composer; `The running turn did not confirm the steer. Your text is back in the composer.` | (no retry) |
| `prompt.resolve_unknown` | the row is gone | never retried; row still listed: `Hermes did not confirm the discard. Press d to try again.` | (no retry) |

When a cancel is confirmed this way, the row's text is taken back as for a `terminal`/`cancelled` result. Every "back in the composer" outcome in this document (tables 6.5, 6.7, 6.8, 6.11) follows the take-back rule of section 13.4 when the composer is not empty. While waiting, the composer keeps whatever the person typed; only a lost submit shows `Sending…` (as the composer title, while no edit is open), and the person may keep typing and sending prompts meanwhile (section 13.5). A `submission_id` is never reused for a different row: Hermes would answer `admission_conflict`.

- No unit in the v0.7.0 set owns a "working line" (the `✻ Working · 12s` line of the architecture's screen sketch), so the queue never depends on one. The label sits right-aligned on the first line of the queue's own section, whatever that line holds (the steering line or the first row), whether or not a turn runs; in selection mode it sits on the first line of the selection view, without `↑ select`. The caller passes `show_select_hint` true when the draft is empty, no `P1-09` card has focus and selection is not active. The label ends in the last column; the line's own text is cut with `…` so at least two spaces separate it from the label. Tests assert the label's text and its end column, not the spacing.
- The queue section is placed directly above the composer, where the merged code stacks live-region sections (`crates/talaria-tui/src/live.rs`, owner `P1-06`, minimal touch). If the merged code stacks sections in `P1-12`'s application view instead, touch that file minimally and name it in the pull request.
- The steering line shows the newest steering row; with more than one it ends `(+k more)`.
- Each row line shows the first line of the text, cut with `…` to fit, then ` (+N lines)` when the text has N further lines.
- Selection window: 8 rows; it scrolls minimally, so the selected row is always visible and the window moves only when the selection would leave it. The hint ends `(+k above, +m below)` only when rows lie outside the window.
- Hint line by width: 100 columns or more, `enter edit · d remove · s steer · n send now (stops the turn) · K/J move · esc back`; 60 to 99, `enter edit · d remove · s steer · n now · K/J move · esc`; below 60, `⏎ e · d · s · n · K/J · esc`. - Preview at most 5 lines and selection at most 10 lines at 60, 100 and 160 columns (`live_region_height_bounded`). Dimming is read from `vt100` cell attributes.

Row text passes through `P1-07`'s literal-text sanitiser before width cutting, so escape and bidirectional-override characters show as visible stand-ins.

### 6.13 Selection mode in detail (REQ-12)

- Entry: Up with an empty draft and the cursor on the first line, when at least one counted row exists and no `P1-09` card has focus. The newest counted row is selected first. The draft is always empty while selecting.
- Hint line: `enter edit · d remove · s steer · n send now (stops the turn) · K/J move · esc back`, ending `(+k above, +m below)` when rows lie outside the 8-row window. Total height with the steering line: at most 10 lines.
- Following a row: selection holds an `admission_id`. When a plan or edit re-admits the row, the id map moves selection to the new id. When the row leaves `pending`, selection moves to the row now at the same index among counted rows (the last row when the index is past the end), or ends when none is left. Test 18's `selection_after_removal` covers removal in the middle and at the end.
- Keys outside the queue bindings leave selection and are passed to the composer, so typing a letter starts a draft. Esc (`queue_leave`) only leaves selection; the Esc interrupt intent is reached only from the composer.
- `/queue` alone enters the same mode.
- Window and hint: section 6.10.

### 7.2 Notes for whoever runs the acceptance scenarios

- `herdr pane wait-output` also matches text already on screen, so every awaited word (`OMEGA`, `BRAVO`, `PELICAN42` and so on) is one that appears only in a reply, never in a prompt as typed: prompts spell the word in lower case and ask for capitals.

## 9. Design reasoning and rejected alternatives

1. **Reorder by re-admission.** Hermes has no reorder verb (H20). `prompt.replace_queued` retires a row and admits its text at the back in one write (H32), so re-admitting rows in the right order reaches any permutation. The minimal plan keeps the longest prefix of the target that is already in order. Rejected: a client-side queue that holds prompts back (it would race the gateway's drain and lose prompts on a crash); cancel-and-resubmit (two writes, so a crash between them loses the prompt); asking Hermes for a reorder verb first (blocks the parity row on an upstream change; it goes on the upstream list instead). Revisit when Hermes adds a reorder verb.
2. **Moves need `replace` on every planned row.** A plan that stops halfway leaves a worse order than no plan. Checking all controls up front makes refusals rare; the remaining race (a row starts mid-plan) stops the plan and shows the order Hermes holds.
3. **Send-now is "move to head, then interrupt".** Hermes Desktop does the same for its local queue (H53). The generation check prevents stopping a turn that already ended; the interrupt goes through the Esc intent so an open approval is answered first (the bake-off trap).
4. **The steer notice says "sent", never "delivered".** A latched steer can be lost if the turn never adopts an agent (H37), and the agent requeues a steer when its tool batch had no tool result (H39).
5. **A plain `rejected` is never resubmitted.** It can follow delivery (H36, H38); resubmitting could run the same instruction twice.
6. **Decode the queue fanout from raw JSON into an all-optional frame.** The contract's `SessionLiveInfo` defaults `running` to `false` and lacks the queue fields (H15), so decoding through the generated `Notification` would report "idle" on every queue change. `P0-03`'s `overrides.rs` holds request-parameter corrections only and has no hook for events; `P1-05` already reads payloads from raw JSON. So `SessionInfoFrame::from_payload` sits beside `P0-03`'s other hand-written events. Rejected: an `overrides.rs` entry (no event hook exists); a second settings store here (`P1-10`'s specification decision 5 puts settings in a store owned by `P1-12`, which merges `session.info` field by field).
7. **The busy-time user cell is drawn when the prompt starts, matched by admission.** Drawing it at submit puts it inside the reply that is still streaming; Hermes's terminal UI defers it the same way (H55). `P1-05` already defers it with a first-in-first-out match, which its own specification names as the single-viewer simplification; it draws the wrong text after a cancel, an edit, a move, or another client's prompt. Matching by `admission_id` and `input_id` is the refinement it anticipates. The idle rule (cell at once) is kept: there is no streaming reply to land inside, and the person sees the prompt immediately. Rejected: no cell until the receipt even when idle (slower feedback for no gain).
8. **Plans act on `queued` rows only.** `pending` lists the running turn's row and steering rows (H24, H25), which have no `replace` control; putting them in a plan would refuse every send-now at its first step. Re-admission lands a row after every existing row, so the relative order of the other rows is irrelevant to the plan.
9. **One source of "running".** `P1-05`'s turn state already holds running and the generation that `Effect::Interrupt` needs; a second flag from the fanout could disagree for a frame and pick the wrong path. The fanout's `running` and `execution_generation` are used only for the stale-frame fence.
10. **Reconcile, then retry once with identical params.** Hermes replays an exact retry of a submit (H23) and of a replace (H32), so a retry with the same `submission_id` is safe whether or not the first call committed. A 5-second deadline (`RECONCILE_WAIT`) covers an idle session that publishes no fanout. Cancel, steer and discard have no such replay guarantee for the person's intent (a retried cancel after a claim would stop a turn), so they are never retried.
11. **Remove keeps Hermes's meaning.** `prompt.cancel` on a row the drain claimed a moment earlier stops that exact turn (H33): the person asked that this prompt not run. Talaria reports it (`That prompt had just started, so Hermes stopped it.`). The alternative, refusing remove once a row might be claimed, cannot be decided client-side. The operator may revisit this on the parent.
12. **`/queue` and `/steer` need `P2-03`'s table, so `P2-03` is a merge gate.** The local command table is `P2-03`'s interface; registering elsewhere would create a second command path. `P2-03`'s body records this gate on this unit's side; the set inventory lists only phase 1 acceptance for this unit and needs the same correction.
13. **Queue keys get their own key context.** `P1-08` refuses plain letters in the composer context and resolves duplicates per context; its specification 3.2 names this unit as adding a context. Plain letters are the fastest keys in a mode the person entered on purpose.

## 10. How others present the feature

- **Claude Code** (research report `u12`, features `int.queue`, `int.send-now`, `int.take-back`): Enter during a turn queues the message; queued messages go out when the current tool calls finish, in order; Ctrl+Enter (or Ctrl+X Ctrl+S) sends queued messages and the draft right away, which can interrupt; Up from the first input line pulls queued messages back into the input for editing. Talaria's Up-to-select, `n` and `Ctrl+Enter`, and remove-as-take-back map to these.
- **Hermes Desktop** (catalogue row F18, "Stop, steer, redirect"): `session.steer` adds a note the model reads at its next tool step; the composer queue is server-owned for local sessions (H50); send-now promotes and interrupts (H53).
- **Hermes's terminal UI**: a three-row window, a header with the count, deferred bubbles, `queued` and `unknown` counted (H55, H56); no reorder.

### 13.1 Where this document lives

### 13.2 The queue label and `q(n)!`

The `!` in `q(n)!` means paused: it is the narrow form (below 60 columns) of `queued (n) · paused`, shown when the oldest counted row is `unknown`. The label sits right-aligned on the first line of the queue's own section, running or idle, because no unit owns a "working line" (section 6.10 has the full rules and the placement of the section).

### 13.3 The ledger and the idle cell

- Every own submit creates a ledger entry `submission_id → text` (plus its `attachments` once `P2-04` has merged, so the REQ-9 retry resends them unchanged), with `cell_drawn` equal to `P1-05`'s `placed` (true when the idle rule drew the cell at submit).
- Any later trigger of table 6.3 that matches an entry with `cell_drawn: true` (its receipt's `admission_id`, a `message.start` naming that admission, or a fanout listing its `input_id`) adds the admission to `drawn` and draws nothing. An idle prompt therefore gets exactly one cell.
- An entry leaves the ledger when its admission enters `drawn`, when its row is cancelled or replaced, on `P1-05`'s `Event::SubmitFailed` for its `submission_id`, or when a lost submit's text is returned. Decision 1's ledger is therefore "own submissions whose cells are not drawn yet", not "unconfirmed submissions".
- Test: `session_queue.rs::idle_submit_gets_one_cell` (section 8.1).

### 13.4 Take-back into a non-empty composer

Talaria never overwrites a draft and never merges text into one. Returned text (a cancelled row, a lost or refused submit, a plain `rejected` or lost typed steer) goes into the composer with `P1-08`'s `Composer::load` (caret at the end) only when the composer is empty and no edit is open. Otherwise the draft stays as it is, and Talaria shows the situation's notice up to its first full stop, then a transcript notice `Your draft was kept, so the returned prompt is shown here:` followed by the full returned text, every line sanitised by `P1-07`. Nothing is lost and nothing is sent. Test: `queue_intents.rs::take_back_keeps_a_draft`.

Submit refusals and voice stops keep `P1-12`'s path and notice (`Event::SubmitFailed`); this unit adds only the ledger removal and this take-back.

### 13.5 A lost submit reply

- "The next snapshot or fanout" in REQ-9 means the first snapshot or queue fanout applied after the unknown outcome, whoever caused it. A fanout lists the whole `pending` list, so if the first call committed before that fanout was published, the row is listed. If it is not listed, one retry with the identical params is safe either way: Hermes replays an exact retry (H23).
- Tests never depend on timing: they feed `Event::QueueReconcileDue` directly.
- While `Sending…` shows (the composer title, while no edit is open), the composer works normally: the person may type, and Enter submits a new prompt with its own ledger entry. If the lost prompt never reached Hermes, its retry lands behind prompts sent meanwhile; that order change is accepted and not reported.
- A lost submit never sets `in_flight` and never blocks anything (13.6).
- Test: `queue_intents.rs::lost_submit_shows_sending`.

### 13.6 The busy rule

A session is busy while `QueueState.plan` or `QueueState.in_flight` is `Some`. `in_flight` holds the one outstanding row call: a cancel, a replace (an edit save or a plan step), a `prompt.steer_queued`, a `prompt.resolve_unknown` or a `session.steer`, including while it waits to reconcile. Submits never use `in_flight`.

| While busy | Result |
|---|---|
| Enter on a draft, `/queue <text>`, `/queue add <text>` | allowed: a plain submit |
| typing; Up, Down and `queue_leave` inside a selection that is already open | allowed |
| entering selection (Up from the composer, `/queue` alone) | refused: `Still moving prompts…` |
| `queue_edit`, saving an edit, `queue_remove` (remove or discard), `queue_steer`, `queue_move_up`, `queue_move_down`, `queue_send_now` | refused: `Still moving prompts…`; no call |
| `composer_send_now` | refused before anything is submitted; the draft stays |
| `/steer <text>`, `composer_steer` | refused; the typed text stays in, or is loaded back into, the composer |

`one_plan_at_a_time` (test 18) walks this table.

### 13.7 Admission ids on events

A submit has no admission before its receipt, and `session.steer` names no row. So `InFlight.admission_id`, and the `admission_id` of `QueueCallResult`, `QueueCallRefused`, `QueueCallUnknown` and `QueueReconcileDue`, are `Option<AdmissionId>`: `None` for `Submit` and `SteerText`. A submit is identified by its `submission_id`. Section 4 shows the corrected shapes. `P1-12`'s submit path feeds a receipt as `QueueCallResult { action: Submit, admission_id: None, submission_id: Some(id), result }`.

### 13.8 Edit details

- The text loads with `Composer::load`, so the caret is at the end (UAT-2 and UAT-6 rely on that).
- In the title `editing queued prompt i of n`, `i` is the row's 1-based place among counted rows when the edit starts and `n` is the counted-row total then. The title does not change during the edit.
- The restore target is the old row's index among `queued` rows at save time, read just before the replace is sent. The restore plan then moves the new admission to that index through `id_map`. If the old row is gone at save time, Hermes refuses the replace and nothing is restored.
- An empty or blank text is refused with `An empty edit would remove the prompt. Press d on it to remove it instead.`; edit mode stays open; no call.
- If a planned row behind the edited one lacks `replace`, the edit is still saved, no restore plan runs, and the notice is `Saved. Hermes moved the edited prompt to the back of the queue.`

### 13.9 Other clients' rows

Rows whose `input_id` is not in this client's ledger are shown and counted like own rows and offer the same actions, by their `controls`. Hermes allows the change only when this client's connection holds `session:control` or the row is its own principal's; otherwise it refuses `permission_denied`, which maps to `Hermes does not let this client change that prompt.` (table 6.11, H63). A replacement is admitted under this client with this client's fresh `submission_id`, so after an edit or a move step the row is this client's. Its cell is drawn through its receipt (it is known), with the row's text. Whether Talaria's connection holds `session:control`: verify at the pinned commit before relying on it.

### 13.10 Frames

- A snapshot sets both fences: `(authority_epoch, execution_generation)` and `(replay_epoch, last_sequence)` (table 6.2).
- A frame is stale by generation when its `authority_epoch` equals the fence's and its `execution_generation` is lower than the fence's highest `execution_generation` for that authority epoch.
- A queue frame whose payload fails to decode (`SessionInfoFrame::from_payload` returns an error, for example a row without `text` or a `status` outside the contract's enum) is dropped and logged once per session; the last known queue stays and the session does not fail. A recorded fixture that fails to decode is a stop condition.
- A row lacks controls when `controls` is absent, null or `[]`. That is a valid state: only remove is offered. The stop condition about recordings concerns only a row without `input_id` or `text`, and a plain-text `queued` row in a Talaria session recorded without controls.

### 13.11 Selection and move ends

- When the selected row leaves `pending`, selection moves to the row now at the same index among counted rows, else to the last counted row, else ends (section 6.13).
- The ends for `queue_move_up` and `queue_move_down` are the first and last `queued` rows. `unknown` rows are never moved over and never moved.

### 13.12 Composer send now

`composer_send_now` (default Ctrl+Enter) arrives only when the terminal reports keyboard enhancement flags (`P1-08`'s `set_keyboard_enhancement`); without them the chord never reaches Talaria, and the way to send a draft now is Enter, then Up and `n`. Idle, it acts exactly like Enter (no interrupt). While busy it is refused before anything is submitted (13.6). Test: `queue_intents.rs::send_draft_now_idle_acts_like_enter`.

### 13.13 `/queue` and `/steer` while busy

`/queue <text>` and `/queue add <text>` are plain submits and always allowed. `/queue` alone and `/steer <text>` follow the busy rule (13.6).

### 13.14 Merge order with parallel units

When a parallel unit's pull request merged first and both touch `keys.rs`, `config.rs`, `docs/configuration.md`, submit routing or `Effect`, the later pull request keeps both sides: its enum variants and `Action::ALL` entries go after the earlier ones, and its `[keys]` entries in `docs/configuration.md` follow `Action::ALL` order. Without `P2-04` merged, `prompt.submit` carries no `attachments` key and the ledger stores no attachments.
