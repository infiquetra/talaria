## 1. What this unit is

When the developer types `/` at the start of the composer, Talaria shows a palette: a list of commands drawn from what the Hermes gateway reports (`commands.catalog` and `complete.slash`), plus the commands Talaria itself handles. Each row shows the command, its description and where it comes from. Choosing a row completes or runs it. Running a Hermes command goes through `slash.exec`; the reply is either text to show, or a directive to submit a prompt, prefill the composer or re-run an alias. When Hermes refuses a command, Talaria says so in plain words, with the hint Hermes supplies. When a skill is installed or removed elsewhere, Hermes sends `skills.changed` and the palette refreshes.

It is the roadmap's P2-03 row ([07 §Phase 2](../07-roadmap-and-work-units.md#phase-2--coding-parity)): "Commands from the backend catalogue with descriptions and provenance; local commands clearly marked; refusals shown in plain words", Hermes calls `commands.catalog`, `complete.slash`, `slash.exec`, `command.dispatch`, `skills.changed`. It covers the parity row "`@` file mentions, slash menu, custom commands, skills" ([04 §Claude Code parity checklist](../04-prior-art.md#claude-code-parity-checklist)) for its slash half; the `@` half is P2-04.

## 4. Mock-server rules

1. Every canned reply is copied from the committed fixture `fixtures/frames/slash-palette.jsonl` (section 14) or built from the contract schemas named in section 2, field for field. A mock that answers a field the contract does not declare, or a reason not listed in H4, H17, H18, H20, H22, H27, H34 or H35, is a defect.
2. The mock validates every request it receives the way the owner does: unknown keys, missing required keys and any non-string value (including `null`) are answered `invalid_params` (H5, H17). This is what makes the "no nulls" test meaningful. The allowed and required keys are read at test time from the vendored contract P0-03 commits (`crates/hermes-contract/vendor/gateway-contract.openrpc.json`, `components.schemas.<Name>Params`), never from a hand-written list, because the generated Rust types drop `additionalProperties: false`. ## 6. Parsing rules

`looks_like_slash_command(text)` is true exactly when C1's regular expression matches the start of `text`. `parse_slash_line(text)`:

1. If `looks_like_slash_command(text)` is false: `None` (the line is an ordinary prompt).
2. Strip every leading `/`. Split at the first run of whitespace (any Unicode whitespace, including `\n`): the first part is the name, the rest is the argument.
3. Lower-case the name (Unicode lower-case). Trim outer whitespace from the argument; keep its interior byte for byte.
4. If the name is empty: when the argument is empty too (the draft is `/` or `/   `), return `Some(SlashLine { name: "", arg: "" })` and the dispatcher does nothing; when the argument is not empty (`/ words`), return `None`, so it is sent as an ordinary prompt.

| Input | Result |
|---|---|
| `/help` | name `help`, arg `` |
| `/HELP  skills ` | name `help`, arg `skills` |
| `/goal line one\n  line two` | name `goal`, arg `line one\n  line two` |
| `/usr/local/bin` | `None` |
| `run /clean` | `None` |
| `//x` | `None` |
| `/` | name ``, arg `` |
| `/ ` (slash, one space) | name ``, arg `` (runs nothing; the palette stays closed, 8.1) |
| `/ words` | `None` |
| `/naïve arg` | name `naïve`, arg `arg` |

## 7. From catalogue to rows

### 7.1 Provenance

For each name, decide the source in this order. The first rule that matches wins. The order follows the owner's run order (H32), so the tag names what actually runs.

| Order | Rule | Source | Tag text (right column) |
|---|---|---|---|
| 1 | The name or an alias is in `LocalCommandTable` | `Talaria` | `talaria` |
| 2 | The name is in a category other than `"User commands"`, `"Plugin commands"` and `"TUI"` (a registry command) | `Hermes { category }` | `hermes` |
| 3 | The name is in the category `"User commands"` (a quick command) | `UserCommand` | `your command` |
| 4 | The bare name is a key of `plugin_commands` | `Plugin` | `plugin` |
| 5 | `"/name"` is a key of `skills` | `Skill { origin }` | `skill · hub`, `skill · bundled`, `skill · local`, or `skill` for any other origin |
| 6 | Only `complete.slash` knows it, `kind == "skill"` (a skill bundle) | `Skill { origin: Other("bundle") }` | `skill` |
| 7 | Only `complete.slash` knows it with any other kind, or it is in the category `"TUI"` | hidden: not shown | n/a |

Consequences: a quick command and a skill with the same name are tagged `your command` (Hermes runs the quick command); a plugin named like a registry command is tagged `hermes` (it is not in the `"Plugin commands"` category, H32); a name in `"Plugin commands"` is always a key of `plugin_commands` (H32), so rule 4 covers it. A skill cannot share a registry name (Hermes skips it, H40). Rule 7 hides the Ink-only extras (H9, H15) and `/details`, which the owner refuses because they are neither registry, quick, plugin nor skill commands (H22). The registry names Hermes leaves out of `pairs` (`/approve`, `/deny`, `/commands`, H9) are not listed either, but typing them still runs them (H20).

### 7.2 Browse order (draft is exactly `/`)

1. Group "Talaria": every local command, in table order.
2. One group per catalogue category, in the order of `categories`, excluding `"TUI"`; rows in the order Hermes gave them; local names removed (they are in group 1); names already placed by an earlier group (a quick command named like a registry command) not repeated.
3. Group "Skills": every key of `skills` not already placed, sorted by `usage` descending, then name ascending; skills whose origin is `bundled` and whose `usage` is 0 are left out (the same rule Hermes applies when browsing, H16).

A group left with no rows is omitted, header included (at v0.22.4 `"Exit"` holds only `/quit`, which moves to "Talaria", H41). Each group starts with a header row (not selectable). The first selectable row is selected.

### 7.3 Search order (draft is `/<query>` with no space)

Two phases, so the palette reacts on the same frame as the keystroke and still gets Hermes's ranking.

1. Immediately, filter locally: local commands, then catalogue entries (rules 1 to 5 above, skills included, each name once). A row matches when its name (without slash) equals the query (tier 0), starts with it (tier 1) or contains it (tier 2), case-insensitive; aliases of local commands and `canon` aliases count as the row's name for tier 0. Rows sort by tier, then by browse order. No headers.
2. Emit `RequestCompletion { text: draft as typed, not lower-cased, after: 60 ms }`. When the reply for the current request arrives, replace the backend rows with the reply's items in reply order (normalised as in 7.4), keep the local matches first, keep an exact-name row first, and keep the selection on the same name when it is still present, else row 0. Rows hidden by rule 7 are dropped.

### 7.4 Normalising a completion item

- Name: `item.text` trimmed of whitespace, with one leading `/` removed if present, then prefixed with `/` (H15).
- Description: the catalogue's description when the name is in the catalogue, otherwise `item.meta` with a leading `⚡ `, `▣ ` or `🔌 ` removed (the source column says what the glyph meant). Empty meta stays empty.
- Duplicate names keep the first occurrence.

### 7.5 Argument stage (draft is `/<name> <partial>`)

The stage starts when the draft has whitespace after the name (typed, or after Tab or Enter completed `/name `).

- Hint row: drawn at once, before any reply. Its text is `usage: /name <hint>`, where `<hint>` is the text inside the description's `(usage: /name …)` suffix (registry commands, H12) or a local command's `args_hint`. It is dim and not selectable. A command with neither has no hint row.
- Item rows: only from `complete.slash` (no local filtering), requested 60 ms after the last change as in 7.3. They appear under the hint row in reply order. An item row shows `item.display` (else `item.text`) as its name and `item.meta`, with a leading `⚡ `, `▣ ` or `🔌 ` removed, as its description; it has no tag (`source: None`), because it is an argument value, not a command. While the reply is pending, and after an empty reply, only the hint row is shown. Free text usually gets no items (H38).
- With no hint row and no items the palette draws nothing (height 0) but stays in the argument stage, so Enter still follows 8.3.
- `replace_from` is converted from code points to a byte index of the draft (H14). An item is accepted as `draft[..replace_from_bytes] + item.text`. A `replace_from` larger than the draft's length in code points makes the reply invalid: it is dropped (no items, no panic) and the hint row stays (test 16).
- A local command has no argument completions in this unit; its stage shows only its hint row.

## 8. The palette state machine

### 8.1 Open and closed

The palette is open when all hold: the draft has no `\n`; the draft is exactly `/`, or `parse_slash_line(draft)` returns a non-empty name (so `/ ` and `/ words` keep it closed); the word under the caret does not start with `@` (that word belongs to P2-04's mention list); the palette was not closed with Esc for this draft (8.3). Otherwise it is closed and draws nothing (height 0).

"The word under the caret" is the run of non-whitespace characters that touches the caret: the characters immediately before the caret back to the previous whitespace, joined with those immediately after it up to the next whitespace. The caret is P1-08's `Composer::caret()` (a byte offset on a grapheme boundary), passed in `DraftChanged`. With whitespace on both sides of the caret there is no word, so the `@` rule does not apply. Examples: `/plan fix @src` with the caret at the end: the word is `@src`, closed; the same draft with the caret after `fix`: the word is `fix`, open in the argument stage of `/plan`.

P1-09's approval and question cards take keys only while the draft is empty (P1-09 REQ-15: its key handler returns `NotHandled` when `draft_empty` is false), and P2-08's queue selection keeps the draft empty (P2-08 REQ-12). The palette needs a non-empty draft, so neither can hold focus while the palette is open; the routing order (card, queue selection, palette, composer) never has to choose between them. Test 40 consumes only P1-09's card stack (to set up a pending card) and P1-12's key routing; no new P1-09 interface is needed. P2-08's queue selection is not tested here, because it lands later; P2-08's own key-routing tests (its test 26) cover that step.

### 8.2 Stage

`Command` when the draft has no whitespace after the name; `Argument` when it does.

### 8.3 Keys (default chords; all configurable, section 8.4)

| Key | Command stage | Argument stage |
|---|---|---|
| Down, Ctrl+N (`completion_next`) | Select the next selectable row; wraps; sets `explicit_selection` | same |
| Up, Ctrl+P (`completion_prev`) | Previous; wraps; sets `explicit_selection` | same |
| Tab (`completion_accept`) | Replace the draft with `"/name"`, plus a trailing space when the row takes an argument; clears `explicit_selection` | Replace from `replace_from` with the item; clears `explicit_selection` |
| Enter (`submit`, routed here while open) | See 8.5 | With `explicit_selection` on an item row: accept the item, then run the line. Without: run the draft as typed |
| Esc (`completion_close`) | Close; remember the draft text; reopen only when the draft changes | same |
| Any other key | Goes to the composer; the palette re-derives on `DraftChanged`, which clears `explicit_selection` | same |

Tab always acts on the selected row, explicit or not, because pressing Tab is itself a choice: on a bare `/` it accepts row 0 (`/quit` at v0.22.4 gives `/quit`). With no selectable rows Tab does nothing (the palette stays as it is; the key is not passed to the composer).

`CatalogChanged` while the palette is open re-derives the rows from the new catalogue and keeps the selection on the same name when that name is still listed (with `explicit_selection` unchanged); otherwise it selects row 0 and clears `explicit_selection`.

A pending completion request never delays a key. Enter, Tab, Up and Down act on the rows shown at that moment; Enter and Tab also cancel the pending request (its reply is dropped by id). So a `/query` whose local filter found nothing runs as typed even if Hermes would have matched a description word (H16): Hermes then decides, usually with the "does not know" refusal. This is accepted; it never runs a command the person did not type.

### 8.4 Key actions

Four actions join P1-08's key map in a new context, `KeyContext::Completion` (P1-08's `KeyContext` has only `Composer` today): `completion_next` (`down`, `ctrl+n`), `completion_prev` (`up`, `ctrl+p`), `completion_accept` (`tab`), `completion_close` (`esc`). P1-08 checks conflicts per context, so they are checked against each other only; Up, Down and Esc keep their composer meaning when no list is open. They are configured as `[keys] completion_next = "..."` like P1-08's other actions (P1-08's parser takes the context, `KeyChord::parse(text, KeyContext::Completion)`).

The four actions are shared with P2-04's `@` list: P2-04's REQ-6 reuses exactly these names, active only while a list is open, and its specification (decision 12, "Shared completion actions") says the same. Whichever of the two units merges first adds the context and the four actions; the second reuses them and must not add a second set. The two lists never open together (8.1), so one set of actions serves both. If the other unit merged first, say so in the pull request and touch `keys.rs` only to route the actions to the palette.

Key routing order while Talaria is in the foreground: (1) a focused approval or question card (P1-09); (2) queue selection mode (P2-08); (3) the open palette (this unit), which consumes the four actions and Enter; (4) the composer. The routing lives in P1-12's application `update` in `talaria-app`; this unit adds step 3 there (test 40, `crates/talaria-app/tests/palette_routing.rs`).

### 8.5 Enter in the command stage

Apply the first row that matches.

| # | Situation | Result |
|---|---|---|
| 1 | Draft is exactly `/` and `explicit_selection` is off | Nothing (the palette stays open; nothing runs) |
| 2 | Draft is exactly `/` and `explicit_selection` is on | Act on the selected row by rows 5 and 6 (its typed name is empty, so it is a prefix) |
| 3 | No selectable rows (nothing matches) | Run the draft as typed (Hermes decides; usually a refusal, 10.1) |
| 4 | The typed name equals the name or an alias of any listed row (local alias, `canon` alias), and `explicit_selection` is off or on that same row | Run the draft as typed. This keeps `/plan` running `/plan` when `/plan-fast` is also listed |
| 5 | The selected row was chosen (the typed name is a prefix of its name, case-insensitive, or `explicit_selection` is on), and it takes no argument (`argument_mode` null; a user command, which has no `commands` entry; a local command with `takes_argument == false`) | Replace with `"/name"` and run |
| 6 | The selected row was chosen as in row 5, and it takes an argument (any non-null `argument_mode`, any skill, a plugin with `argument_mode`, a local command with `takes_argument == true`) | Replace with `"/name "` and enter the argument stage (7.5); do not run |
| 7 | Anything else: rows are listed, `explicit_selection` is off and the typed name is not a prefix of the selected row (it matched by substring locally, or by a description word in Hermes's reply) | Run the draft as typed (Hermes decides) |

Examples: `/vers` with `/version` selected by default: row 5, runs `/version`. `/ers` with `/version` listed by substring: row 7, sends `ers`, and Hermes answers with the "does not know" refusal. `/ers`, then Down onto `/version`: row 5. A row in the dimmed refused state still runs when chosen: Hermes gives the same refusal again, which is the honest answer.

### 8.6 Stale replies and load

Each `RequestCompletion` gets the next `request_id`; a reply or failure whose id is not the latest is dropped. The application loop owns the 60 ms trailing debounce (section 5): each new `RequestCompletion` replaces the pending one. A completion failure (an error or the 5 s timeout of section 5) keeps the local rows and sets the footer to `completion unavailable: <reason>` (reason cut at 60 characters). That footer stays until the next completion reply that arrives with the latest id, or until the palette closes. When it and the catalogue `warning` footer (10.2) both apply, the completion footer wins, because it describes the list on screen; the warning footer returns when the completion footer clears. The local filter over 2,000 entries must take under 2 ms at the 95th percentile (benchmark in section 15).

## 9. Running a slash line

### 9.1 Order

On `Submit(text)` from the composer (or `PaletteEffect::Run`):

1. `parse_slash_line(text)`; `None` means an ordinary prompt (unchanged P1-12 path).
2. Empty name (`/` or `/   `): do nothing (`CommandOutcome::Nothing`).
3. Local table hit: when the command has `takes_argument == false` and the argument is not empty, show the Error notice `/<name> does not take an argument.` and do nothing else; otherwise run the local action. Local wins over a Hermes command of the same name.
4. Otherwise, if no session is attached: the notice `No session is attached, so /<name> cannot run. Start one with talaria, talaria -c or talaria --resume <id>.` Nothing is sent. (P2-07 may mention `/resume` here once it adds that local command.)
5. Otherwise send `slash.exec {session_id, command: text without its leading slashes}`. The argument goes exactly as typed (interior newlines included).

`slash.exec` is sent whether or not a turn is running; Hermes decides (H33). A registry command refused mid-turn comes back as an `exec` reply and is shown like any output.

### 9.2 Reply

| Reply | Outcome |
|---|---|
| `type: exec` or `plugin` (or no `type` with `output`) | `Output`: the typed line as the first line, then `output`, or `(no output)` when empty or missing. A bare legacy reply's non-empty `warning` is shown as the first output line `warning: <text>` (the owner never sends it, H23). `interpret_result` cuts an `output` longer than 262,144 bytes (256 KiB) at the last character boundary at or below that length and appends a new line `(output cut: <n> more bytes)`, where `<n>` is the number of bytes removed. |
| `type: send` | `notice` (non-blank) as a System notice; then, when `message` is non-blank, `Submit { text: message, display }`, where `display` is the reply's `display` or, when blank or missing, the typed line; when `message` is blank, Error notice `/<name> returned an empty message.` |
| `type: skill` | As `send`; when `message` is missing or blank, Error notice `/<name>: the skill sent no instructions.` |
| `type: prefill` | `notice` as a System notice; the composer is loaded with `message` (Composer::load); nothing is sent. |
| `type: alias` | Inside the same `execute` call, re-run `/<target> <arg>` once from 9.1 step 3. A second alias in the same call: Error notice `/<name> points to another alias; Talaria stops after one.` |
| Any other `type`, or a result that is not an object | Error notice `Hermes answered /<name> in a form this version of Talaria does not understand.` |

### 9.3 What reaches the transcript

`outcome_actions` turns an outcome into session events for P1-12's loop:

- `Output`: `Event::Notice { kind: System, text }` whose text is the typed line, a newline, then the output (already cut by `interpret_result`, 9.2). The renderer passes it through P1-07's `sanitize_untrusted`.
- `Submit`: an optional `Event::Notice { kind: System, text: notice }`, then `Event::SubmitCommand { text: message, display, submission_id: fresh }` into the session reducer. The user cell shows `display`; `prompt.submit` carries `message`. A running turn means the prompt queues, exactly as a typed prompt does.
- `Prefill`: an optional System notice, then the composer load.
- `Refused`: `Event::Notice { kind: Error, text: message }`, and `CommandsInput::Refused { name }` when `dim` is true. `Failed` and `OutcomeUnknown`: an Error notice.
- The composer has already added the typed line to its history (P1-08).

### 9.4 The `command.dispatch` fallback

Only when `slash.exec` fails with code -32601: send `command.dispatch {session_id, name, arg}` once for that command (omit `arg` when empty), and handle its reply by 9.2. The fallback is decided per command, inside one `execute` call; nothing is remembered between commands, so the next command tries `slash.exec` first again (a gateway that gains the method mid-connection is used at once). If that is -32601 too: Error notice `This Hermes gateway does not run slash commands. Check that it is at the release Talaria is pinned to.` Never fall back on any other error: a refusal is the answer, and a timeout may have run the command.

## 10. Messages

### 10.1 Refusals and failures (exact text; `<name>` without the slash after the `/`)

"Catalogue held" means `describe_error` received `Some(catalog)`: a catalogue has arrived on this run, whatever `CatalogStatus` says now. A catalogue kept after a failed refresh (section 11) counts as held, so the known and unknown rows use it. The "catalogue not held" row applies only when no catalogue has ever arrived (`None`). "Known" means a catalogue is held and `CommandCatalog::knows(name)` is true (the name is in `pairs`, `canon` or `commands`, or is a skill). `<first word>` is the first whitespace-separated word of the argument.

| Condition | Text |
|---|---|
| `unsupported_command`, catalogue held, name not known | `Hermes does not know /<name>. Type / to see the commands you can use.` |
| `unsupported_command`, known name, empty argument | `/<name> is not available on the shared Hermes gateway.` and, when `detail` is present, a second line with `detail`. Dims the row (`dim: true`). |
| `unsupported_command`, known name, non-empty argument | `/<name> <first word> is not available on the shared Hermes gateway.` and `detail` on a second line when present. Does not dim (H34: the bare form may run). |
| `unsupported_command`, catalogue not held (`None`) | `Hermes refused /<name>: it is not a command this gateway runs.` and `detail` on a second line when present. Does not dim. |
| `permission_denied` | `/<name> was refused: this connection is not allowed to run it.` |
| `not_found` | `/<name> could not run: Hermes no longer has this session. Quit and start a new one with talaria, or open another with talaria --resume <id>.` |
| `profile_mismatch` | `/<name> was refused: the session belongs to a different profile.` |
| `session_superseded` | `/<name> did not run: this conversation has moved on to a newer session and is read-only.` |
| `invalid_params` with `field == "arg"` | `/<name> could not read its arguments: <detail>.` |
| `invalid_params`, other | `Hermes did not accept /<name> as sent. If it is one of your quick commands, check its alias target; otherwise this is a Talaria bug, please report it.` |
| `command_unavailable` | `/<name> could not be loaded. The skill may be empty or missing.` |
| `cwd_unavailable` | `/<name> could not run: the session's working folder no longer exists.` |
| `runtime_draining` | `Hermes is restarting, so /<name> did not run. Try again in a moment.` |
| code 5001 `storage_unavailable` | `Hermes could not read its session store, so /<name> did not run.` |
| any other reason with code 4001, or any other code (for example -32602 or -32603) | `/<name> failed: <reason>` plus `: <detail>` when present, where `<reason>` is `data.reason`, else the error's `message` when non-empty, else `code <code>` (for example `/version failed: code -32603`) |
| `TimedOut` or `ConnectionLost` (sent, no answer) | `The connection to Hermes was lost before /<name> answered. It may or may not have run; check before running it again.` |
| `NotConnected` (nothing sent) | `Talaria is not connected to Hermes, so /<name> did not run.` |
| `BadResult` (result did not decode) | `Hermes answered /<name> in a form this version of Talaria does not understand.` |
| `LocalBug` (`Encode`, `InvalidTimeout`; nothing sent) | `Talaria could not send /<name>. This is a Talaria bug; please report it.` |

`<detail>` and `<reason>` are untrusted text. `describe_error` in `talaria-core` only collapses them to one line (newlines become spaces) and cuts them at 160 characters; P1-07's `sanitize_untrusted` (in `talaria-tui`) is applied when the notice is drawn, because the core never imports terminal code. Test 24 compares the core strings; test 38 covers the drawing.

After a dimming refusal, `CommandsInput::Refused { name }` adds the canonical name to the refused set for this connection; the palette then draws that row dimmed with the tag `not available here`. The set is cleared on reconnect, because the gateway may have been updated. An unknown name is never added.

### 10.2 Palette lines

| Situation | Line |
|---|---|
| Footer, width 60 or more | `↑↓ choose · Tab complete · Enter run · Esc close` left, `<shown> of <total>` right |
| Footer, narrower | `<shown>/<total>` |
| Catalogue loading | header row `Loading Hermes commands…`; local rows still shown |
| Catalogue failed | dim row `Hermes commands unavailable: <reason>` (cut at 60) |
| Catalogue `warning` non-empty | footer replaced by dim `Hermes: <warning>` (cut to width) until the next catalogue; the completion-failure footer (8.6) wins while it applies |
| `plugin_discovery_error` non-empty | dim row at the end of browse mode: `Plugin commands unknown: <error>` |
| No rows match | dim row `No matching commands. Enter sends /<query> to Hermes as typed.` |
| Argument stage | dim row `usage: /name <hint>` (7.5) |
| Refused row | the row dim, tag `not available here` |

`<shown>` is the number of selectable rows in the current list (all matches, including rows scrolled out of the window). `<total>` is the number of selectable rows in browse mode (local commands, listed catalogue commands and listed skills). Headers, hint and status rows are never counted. In the argument stage the counts are of item rows. In browse mode the two numbers are equal (for example `57 of 57`); the footer is a count, not a position.

A local row's description is its `LocalCommand.summary`. This unit's one entry is `/quit`: alias `/exit`, summary `Leave Talaria; the session keeps running in Hermes`, `args_hint` empty, `takes_argument` false, action `Quit` (P1-12's detach).

## 11. Catalogue lifecycle

| Input | State change | Effect |
|---|---|---|
| `Connected` (every new connection generation, including reconnects) | clear `refused`, `retried` and `dirty`; cancel a pending delayed retry; `status = Loading` unless `Ready` (keep the old catalogue and rows meanwhile) | `FetchCatalog { after: 0 }` with the bound session and a new `request_id`, **at once**, even when a fetch is in flight: the old fetch is abandoned (its reply or failure has an older id and is ignored) |
| `ForegroundSession(id)` differing from `bound_session` | `bound_session = id`; clear `dirty`; cancel a pending delayed retry; `status = Loading` unless `Ready` | `FetchCatalog { after: 0 }` with a new `request_id`, at once, superseding any fetch in flight as for `Connected` (E5) |
| `SkillsChanged` | none if nothing is in flight; else `dirty = true` | `FetchCatalog` when nothing is in flight |
| `CatalogArrived` with the latest id | replace the catalogue; `status = Ready`; clear `retried` | `CatalogUpdated`; then, if `dirty`, clear it and `FetchCatalog` again |
| `CatalogArrived` with an older id | ignore | none |
| `CatalogFailed` with the latest id | keep the old catalogue if any; `status = Failed(reason)` | if `dirty`, clear it and fetch again; else, if not `retried`, set it and `FetchCatalog { after: 2 s }`; else nothing until the next trigger |

"In flight" means the latest `request_id` has neither arrived nor failed (a delayed retry counts as in flight). Only `SkillsChanged` waits for it (the `dirty` flag, at most one extra fetch however many signals arrive); `Connected` and a foreground change supersede it, because the old reply belongs to an old connection or session. A fetch that never answers ends at the 15 s timeout of section 5 as `CatalogFailed`, so a hung request cannot block refreshes for longer than that. Request counts for test 26: connect gives fetch 1; a foreground change while 1 is in flight gives fetch 2 at once (1's reply ignored); two `skills.changed` while 2 is in flight give exactly fetch 3, after 2's reply; a failure of 3 gives one retry, fetch 4, 2 s later; a failure of 4 gives nothing more. `skills.changed` is not replayed after a reconnect (H30), which is why `Connected` always fetches. The service routes `skills.changed` from the connection's inbound stream to this state machine; the session reducer never sees it (it drops events with an empty `session_id`, P1-05).

## 12. Rendering

The palette is a live-region section directly below the composer box and above the status line. It never enters the alternate screen and never commits anything to scrollback; when it closes, the live region shrinks and leaves no row behind ([05 §The screen](../05-architecture.md#the-screen); R2 in [01](../01-vision-and-requirements.md#what-the-operator-said-restated-as-testable-requirements)).

- Height: `min(lines needed, max(3, floor(terminal rows / 3)))`, where the lines needed are the list's lines (up to 8 selectable rows plus their headers, hint and status rows) plus 1 footer line. "At least 3" is a floor on the cap, not on the height: a palette that needs 2 lines (one status row and the footer) draws 2. On terminals shorter than 9 rows the cap of 3 wins. `terminal rows` comes from `PaletteSection::new(state, terminal_rows)`, which the application builds each frame from the terminal size it already tracks; P1-06's `height(width)` takes only the width. P1-06's own cap on the live region still applies on top.
- Window: a run of consecutive list lines (headers, rows, hint and status rows) holding at most 8 selectable rows and at most `height - 1` lines. When the selection moves, the window scrolls by the fewest lines that keep the selected row visible. A header scrolled out is not repeated.
- Row: two spaces, the name (bold), two spaces, the description, then the tag right-aligned with one space margin. The name column is as wide as the longest name in the current list (not only the window, so it does not jump while scrolling), capped at 28 cells; longer names are cut with `…`. The description is cut with `…`.
- Narrow terminals: below 80 columns the tag is dropped; below 50 columns the description is dropped too.
- Selected row: reverse video (works with `NO_COLOR`). Headers: bold, dim. Tag `talaria`: cyan. Other tags: dim. Refused rows: whole row dim, tag `not available here`. Hint and status rows: dim.
- All text from Hermes (names, descriptions, tags derived from origins, warnings, reasons) is sanitized with P1-07's `sanitize_untrusted` before layout: C0 controls become Control Pictures (ESC is `␛`), bidirectional controls such as U+202E become `‹U+202E›` (P1-07 REQ-20). Widths use `unicode-width`.
- Theme colours from P2-12, when it has landed, may replace the named colours; this unit uses named terminal colours.

## 16. Design reasoning

- **Why `slash.exec` first, `command.dispatch` only on -32601.** Both Hermes clients call `slash.exec` first (C2). On the owner the two methods run the same function (H17), so a second call after a refusal adds nothing and could run a command twice; Ink already refuses to fall back on `unsupported_command` (C3). -32601 is the one signal that the method is missing, which is the version-skew case.
- **Why the palette does not pre-filter commands the shared gateway refuses.** The list of what runs (H20) is Hermes logic in `gateway/session_commands.py`; copying it into Talaria would break the "thin cockpit" rule ([05 §Principles](../05-architecture.md#principles)) and drift on every Hermes release. Talaria instead learns refusals per connection (10.1). A catalogue field that says "runs on a shared gateway" would be the proper fix; it is a candidate for P6-08's upstream list.
- **Why local filtering plus `complete.slash`.** A network round trip per keystroke cannot meet the keystroke budget (≤ 16 ms at the 95th percentile, [05 §Performance budgets](../05-architecture.md#performance-budgets)). Local filtering gives a frame at once; Hermes's ranking (fuzzy description matches, usage) arrives about 60 ms later and refines it.
- **Why `display`, not `message`.** H24 and both clients: the skill body is model-facing scaffolding. Showing it would flood scrollback with text the user did not write. The model still receives `message` through `prompt.submit`. The `api_text` field of `prompt.submit` (classic CLI only, `gateway/session_cli_turn.py`) was considered and rejected: neither Desktop nor Ink uses it, so its effect on resumed transcripts is untested.
- **Why output becomes a System notice, not a new cell type.** It keeps the change to P1-05 additive and leaves rendering to the existing notice path; P2-15 may later give specific commands a richer display.
- **Why a reconnect or session change supersedes a catalogue fetch, but `skills.changed` waits.** A reply fetched for an old connection or another session's folder lists the wrong project skills (H6), so waiting for it only delays the right one; Ink also drops a reply for a session that is no longer live (C5). `skills.changed` asks for the same scope again, so one extra fetch after the current one is enough.
- **Why Enter runs the draft when the selected row only contains the typed text (8.5 row 7).** Completing a substring or description match without an explicit choice would run a command the person did not type, which is the same surprise as a unique-prefix auto-run.
- **Why no unique-prefix auto-run.** Ink runs `/hea` as `/heartbeat` when the prefix is unique. Here Enter with the palette open already completes the prefix (8.5), and silently running a different command than typed is a surprise with side effects.
- **Rejected: a full-screen command palette (Desktop F80).** That searches settings and screens too. No roadmap unit schedules it (phase 4, P4-01 to P4-10, has none); it is a candidate beside P4-01's settings work, at the operator's choice.
- **Out of scope: mid-prompt `/skill` completion.** Claude Code and Ink offer skills partway through a prompt (Ink filters to `kind == "skill"`, `ui-tui/src/hooks/useCompletion.ts` lines 49 to 65). It is a parity gap left for a later unit; the operator decides whether to schedule it.
