## 1. What this unit is, and what it is not

While an agent works, Hermes sometimes stops and asks the person something:

- **An approval**: "may I run this dangerous command?" (for example `rm -rf .pytest_cache`).
- **A clarification**: a question with optional choices.
- **A masked value**: a `sudo` password, a skill's missing secret (an environment variable such as an API key), or a password-manager code.

On the canonical gateway socket (`hermes-gateway-v1`) these reach a client in two different ways:

1. Approvals and clarifications arrive as **events** (`approval.request`, `clarify.request`) and are answered with ordinary **method calls** (`approval.respond`, `clarify.respond`).
2. Masked values and a family of Desktop-only requests arrive as **server requests**: JSON-RPC requests sent from the gateway to the client, which the client answers with a JSON-RPC response frame carrying the same `id`.

This unit draws the cards for both, takes the person's keys, and sends the answers. It also guarantees that no server request is ever left unanswered: every one of the sixteen kinds in the pinned contract gets either a card or an immediate error reply.

## 3. Wire shapes (examples the tests and the mock use)

All examples are built from the facts above. Session ids and prompt ids are placeholders.

### 3.1 Approval

Inbound event (F-1, F-2, F-3):

```json
{"jsonrpc":"2.0","method":"event","params":{
  "type":"approval.request","session_id":"<sid>","seq":41,"replay_epoch":"<epoch>","execution_generation":3,
  "payload":{"kind":"approval","prompt_id":"<pid>","execution_generation":3,
             "command":"rm -rf .pytest_cache","description":"recursive delete",
             "choices":["once","deny","session","always"],"timeout_s":300}}}
```

Card (F-33 order): `1. once`, `2. session`, `3. always`, `4. deny`. Key `2` sends the string `session`.

Outbound call (F-7, F-9), exactly four keys, the generation taken from the payload (the `PromptKey`):

```json
{"jsonrpc":"2.0","id":17,"method":"approval.respond",
 "params":{"session_id":"<sid>","execution_generation":3,"prompt_id":"<pid>","choice":"session"}}
```

Reply: `{"jsonrpc":"2.0","id":17,"result":{"status":"resolved","prompt_id":"<pid>"}}`, then an `approval.settled` event `{prompt_id, execution_generation}`.

With a note "use a dry run first", only after the `resolved` reply, `PromptService::execute` returns `Event::Submit { text: "use a dry run first", submission_id: <from the injected generator> }`. P1-05 answers it with `Effect::SendPrompt`, and P1-12 (or the demo's effect loop) sends:

```json
{"jsonrpc":"2.0","id":18,"method":"prompt.submit",
 "params":{"session_id":"<sid>","text":"use a dry run first","submission_id":"<id>"}}
```

No other key. In particular never `unattended`, which in Hermes auto-approves every dangerous command in the turn.

### 3.2 Clarification (single form)

```json
{"jsonrpc":"2.0","method":"event","params":{"type":"clarify.request","session_id":"<sid>","seq":12,
  "payload":{"kind":"clarify","prompt_id":"<cid>","execution_generation":2,
             "question":"Which environment?","choices":["staging","prod"],"multi_select":false}}}
```

Answers (F-8, F-12, F-13, F-14):

| Card action | `answer` string sent |
|---|---|
| Pick choice 2 | `prod` |
| "Other", type `qa` | `qa` |
| Multi-select, tick 1 and 2 | `["staging","prod"]` (compact JSON array, choice order) |
| Multi-select, tick 1 and 2, Other text `qa` | `["staging","prod","qa"]` (Other text last) |
| Multi-select, Other text `qa` only | `["qa"]` |
| Multi-select, nothing ticked, no Other text | empty string (skipped) |
| Esc | empty string (skipped) |
| No choices, type text | the text |

### 3.3 Server requests

Masked (F-17, F-22, F-23):

```json
{"jsonrpc":"2.0","id":"srq-0123456789ab","method":"sudo","params":{"session_id":"<sid>","command":"sudo apt-get install jq"}}
```

Answer: `{"jsonrpc":"2.0","id":"srq-0123456789ab","result":{"value":"<typed>"}}`. Esc answers `{"value":""}`. Serialize from a borrowed struct (`struct ValueResult<'a> { value: &'a str }`) so this unit makes no extra copy.

Unsupported (F-18, F-19): `{"jsonrpc":"2.0","id":"srq-...","error":{"code":-32601,"message":"talaria does not support server request: theme.pick"}}`.

Withdrawal (F-21): `{"jsonrpc":"2.0","method":"event","params":{"type":"request.cancel","session_id":"<sid>","payload":{"id":"srq-0123456789ab","method":"sudo","reason":"timeout"}}}`.

## 5. Card behaviour

### 5.1 Approval card

See section 5.6 for exact texts. Rules:

- Display order `once`, `session`, `always`, `deny`, filtered to the offered list (F-33). Any offered string outside these four is shown after them in payload order and sent verbatim (forward compatibility).
- The number sends the raw string shown next to it, never an index into the payload (the bake-off trap "map approval choices by the payload's order").
- `command`, `description` and each choice pass through P1-06's `sanitize` before drawing (control and bidirectional-override characters become visible stand-ins). The value sent is always the raw string from the payload: the gateway compares it with its offered list (F-11).
- Commands wrap to the card width; at most ten lines, then `… N more lines`.
- `timeout_s`, when present, is shown once as static text, rounded down to whole seconds. No countdown (an idle countdown would repaint every second and break the "zero frames when idle" budget).
- `edit` present: one line; the edit body is not drawn in phase 1 (its shape is not in the contract; U-3).
- Keys (F-40), with the focus on the choices: the highlight starts on the first shown choice. A digit 1 to N sends that choice; other digits (including 0) are consumed and do nothing. Enter sends the highlight. Up and Down move and stop at the ends. Esc sends `deny`. Tab moves focus to the note field.
- If `deny` is not offered (should not happen, F-3), Esc sends nothing, because the gateway refuses a choice it did not offer. `handle_key` returns `Consumed { intent: None, interrupt_requested: false, notice: Some("closed without an answer: Hermes did not offer deny") }`, and the stack hides that key from then on. `sync` forgets a hidden key once it is no longer among P1-05's open prompts.
- The note field: printable keys type into it (digits included, so a digit there is text, not a choice); Backspace deletes; a paste is inserted up to its first CR or LF; Enter sends the highlighted choice; Esc returns focus to the choices and keeps the note; Tab returns to the choices too. The note line shows the last characters that fit the width. There is no length limit.
- The note travels with whichever answer the card sends: a digit, Enter, or Esc's `deny` (a deny with a note is how a person says "do this instead"). The note is sent as typed, not trimmed. A note that is empty or only whitespace counts as no note. Ctrl+C sends no approval intent, so its note is dropped.
- While the prompt's P1-05 state is `Answering(choice)`, the hint line reads `sending <choice>…` and keys other than Ctrl+C are consumed and ignored. P1-05 would refuse a second answer anyway (`RefuseAnswer(AlreadyAnswered)`); the card must not even try. Ctrl+C there returns `interrupt_requested: true` with no intent; `deny_before_interrupt` skips the key because it is not `Open`, so the answer already in flight stands and the interrupt follows it.

### 5.2 Clarification card (single form)

- Shows `question` (sanitized, wrapped). With choices: a numbered list plus a last row `Other (type an answer)`, numbered N+1. Without choices: a text field, also when `multi_select` is true (F-4).
- The highlight starts on row 1. Up and Down move over all rows, Other included, and stop at the ends. Digits 1 to 9 address rows 1 to 9 (the Other row too when its number is 9 or less). Rows from 10 on are reached with Up and Down only. Digit 0 and digits past the last row are consumed and do nothing.
- Single select: a digit or Enter on a choice sends its label. A digit or Enter on the Other row opens the text field.
- Multi-select: Space or a digit toggles a choice. Space or the digit on the Other row opens the text field (Enter there does not; Enter always sends). Enter on the choices sends the JSON array of ticked labels in choice order, plus the Other text (when not blank) as the last element (F-13). Nothing ticked and no Other text sends the empty string.
- The text field (both modes): the line `answer: <text>`. Printable keys type (digits included); Backspace deletes; a paste is inserted up to its first CR or LF. Enter sends: in single select the text, in multi-select the whole answer (ticks and the text). Enter on a blank text in single select does nothing. Esc closes the field, keeps its text, and returns to the choices without sending.
- A card without choices is only the text field: Enter sends the text (nothing when blank); Esc sends the empty string.
- Esc on the choices sends the empty string (skipped).
- Blank means empty or only whitespace. Typed text is sent as typed, not trimmed. Up to the Other row, all typed state (ticks, text) is kept while the card stays open.
- An answer longer than 16,384 Unicode code points (`chars().count()`, F-42) is refused on the card with a line, and nothing is sent. Multi-select counts the length of the JSON string that would be sent, not the labels.
- Key path for the issue's test 5 (choices `staging`, `prod`; Other is row 3): `2`, `1` gives `["staging","prod"]` on Enter; `2`, `1`, `3`, type `qa`, Enter gives `["staging","prod","qa"]`; Enter alone gives the empty string. For the demo's `clarify-multi` scenario (choices `staging`, `prod`, `qa`): Space, Down, Space, Enter gives `["staging","prod"]`.
- The redacted label (F-41) is what the card shows and sends; that is Hermes behaviour and needs no client change.

### 5.3 Masked card

- Title and detail per kind in section 5.6. An absent or empty detail field draws no detail line (`sudo` may arrive without `command`, F-23).
- The field draws one `•` per character, at most 32 (a fixed number, so the drawn length stops telling the value's length past 32); the buffer keeps every character. The characters never reach a `String` that is drawn, logged, formatted with `Debug` or `Display`, or kept after the answer is written.
- The buffer holds at most 16,384 characters (F-42 applied to every answer). Further typed or pasted characters are dropped and the line `value too long (16,384 characters at most)` shows until the next Backspace.
- Enter sends `{value}`; Esc sends `{value: ""}` (declined). A paste is inserted up to its first CR or LF; the rest is dropped and never acts as Enter.
- The buffer is a `zeroize::Zeroizing<String>` created with `String::with_capacity(65_536)` (16,384 characters of at most 4 bytes), so it never reallocates and no earlier copy is left unzeroed. It is zeroed when the answer is written, when the card is withdrawn and when it is dropped. The guarantee covers this unit's buffer; the terminal library's paste string and `P1-02`'s serialized frame are outside it.
- A `secret` card adds the line `Hermes stores this value in the profile's .env file.` after its detail line (F-46), so the person knows the value is kept.

### 5.4 The card stack and focus

- Order: masked cards first (they block a tool call for at most 120 s), then the open prompts in P1-05's order.
- Only the first card takes keys. `(1 of N)` follows its header when N is more than 1.
- Focus: the first card takes keys only while the composer's draft is empty (`draft_empty`, from P1-08's `Composer::is_empty()`, passed in by P1-12). Otherwise `handle_key` returns `NotHandled` (P1-12 then gives the key to the composer) and the card's hint asks the person to send or clear the draft. P1-08's Ctrl+C on a non-empty draft clears it, so the person never needs a new key.
- Input guard: for 250 ms after a card takes focus (a new first card, or the draft just became empty), keys other than Ctrl+C are consumed and ignored. This stops a key typed a moment earlier from answering a card the person has not read. `handle_key` takes `now: Instant` so tests control time.
- A card for a session other than the foreground session shows the first 8 characters of that session's id in its header. It takes keys like any first card. Phase 1 normally has one session; the fleet arrives in phase 3.
- View state (highlight, note, ticks, typed text, masked buffer) is kept per prompt key or request id until that card leaves. A card pushed back by a newer masked card keeps what was typed; when it is first again it takes focus anew, with a fresh 250 ms guard.
- An unfocused masked card's hint is `Clear your draft to type the value here`, not the general draft hint: a person who types a password while the composer has the keys would send it as an ordinary prompt. That remaining risk is the composer's (`P1-08`) and is recorded in the issue's Risk section.
- Only the first card is drawn; `(1 of N)` counts the others.

### 5.5 Ctrl+C, Esc and interrupt with a card open

P1-08 routes keys to a focused card first, so Esc and Ctrl+C never reach the composer while a card has focus.

- Esc is the card's negative action only: deny, skip (empty answer) or decline (empty value).
- Ctrl+C is "refuse and stop". The card returns `KeyOutcome::Consumed { intent, interrupt_requested: true }` where `intent` is the empty answer for a clarification card, the empty value for a masked card, and `None` for an approval card. The stack then shows `stopping…` on the cards of that session and ignores keys until they leave.
- P1-12 sends any intent, then feeds P1-05's `Event::Interrupt`. Before it sends `session.interrupt` for `Effect::Interrupt`, it awaits `PromptService::deny_before_interrupt`.
- `deny_before_interrupt(client, state, session_id, wait)` sends `approval.respond {choice: "deny"}` (exact four keys, generation from each `PromptKey`) for every `Open` approval of the session that offers `deny`, concurrently. It returns when every reply or failure has arrived, or when `wait` (2 s) expires. A failure or expiry produces one notice that the deny was not confirmed. It remembers the keys it denied, so their later `.settled` produces no "answered elsewhere" notice.
- Clarifications and masked requests are not answered by `deny_before_interrupt`: Hermes withdraws them on interrupt (F-39), and Ctrl+C on such a card already sent the negative answer.
- Why deny first: interrupt publishes no `approval.settled` (F-32). At v0.22.4 the approval wait ends fail-closed about a second after an interrupt (F-39). But the bake-off, run at Hermes `22063fc09`, saw the tool block until the approval timed out (handoff `03-hermes-today.md` §2, which says 60 seconds; the default at v0.22.4 is 300 s, F-15). Denying first closes the card explicitly and does not depend on the wait's polling.
- If P1-05 emits no `Effect::Interrupt` (no running turn or unknown generation), nothing is interrupted; an approval card then stays open and keeps accepting keys once `stopping…` clears. P1-12 clears `stopping…` when it learns no interrupt was sent.
- `stopping…` shows on every card of the interrupted session (the session of the card that took Ctrl+C). P1-12 calls `PromptStack::stop_cleared()` in two cases: no interrupt was sent, or its `session.interrupt` call returned (a reply or an error). So the stuck time is bounded by the 2 s deny wait plus that one call; a card still open after that (for example an approval whose deny was not confirmed and whose wait did not end) takes keys again and can be denied with Esc.

### 5.7 Layout and the snapshot files

- A card is drawn as one P1-06 `LiveSection`. Only the first card of the stack is drawn.
- The card is as wide as the terminal. It has no border and no left indent. The only indents are the two spaces of a command's continuation rows and the two spaces of an unhighlighted choice (`  2. session`).
- Lines appear in the order of the tables in section 5.6. A line whose source is absent or empty (no description, no `timeout_s`, no `edit`, an empty note while the note field is not focused, an absent masked detail) is not drawn. There are no blank lines inside a card.
- Text wraps with P1-06's `wrap_lines` at the terminal width. The ten-row cap on the command counts displayed rows after wrapping (as Hermes's own terminal UI does: `ui-tui/src/components/prompts.tsx`, lines 112 to 132 at v0.22.4, wraps each line and then keeps the first ten rows). When more than ten rows result, the first ten are drawn and then `… N more lines`, where N is the number of rows hidden. Only the command is capped; the description and question wrap in full.
- The timeout line rounds `timeout_s` down to whole seconds.
- Snapshot sizes: 80 columns by 24 rows and 160 columns by 48 rows, through P1-06's vt100 test support, with the prompt section alone in an otherwise empty live region. An expected file holds the screen's rows from the first row of the section, each with trailing spaces removed, and with trailing empty rows dropped. If P1-06's support draws anything around a section (a border or a status row), stop and report rather than guess its shape.
- Stand-ins come from P1-06's `sanitize` table (P1-06 unit specification section 4.2): a C0 control becomes U+2400 plus its code (ESC is `␛`, BEL `␇`), DEL becomes `␡`, and a bidirectional control such as U+202E becomes `‹U+202E›`. Test 2's hostile command is `echo ` + ESC + `[2J` + U+202E + ` done`, drawn as `$ echo ␛[2J‹U+202E› done`. Use the names P1-06 merged; if its table differs, follow the merged table and say so in the pull request.

## 6. Design

```text
 network ──► Inbound::Event ──► app event channel ──► P1-05 reducer ──► prompt cells
         └─► Inbound::ServerRequest ──► PromptService (talaria-app) ──► MaskedRequestInfo
                                              │ refused: Responder::fail at once (+ notice once)
 keys ──► PromptStack::handle_key (talaria-tui) ──► KeyOutcome ──► app event channel
 Approve/Clarify intent ──► set_note + Event::AnswerApproval/AnswerClarify ──► reducer
         ──► Effect::RespondApproval/RespondClarify ──► PromptService::execute ──► Client::call
         ──► Executed { events: AnswerFailed | AnswerAlreadyResolved | Submit, notices }
 Masked intent ──► PromptService::answer_masked ──► Responder::respond ──► value dropped
 P1-12 converts: MaskedRequestInfo ──► MaskedView ; MaskedValue::into_inner ──► Zeroizing<String>
```

- Every source of change goes through the single application event channel (roadmap rule 6), except the masked value. `PromptStack::handle_key` returns `PromptIntent::Masked` to its caller; P1-12 (and the demo) passes it straight to `PromptService::answer_masked`, never putting the value on the application event channel. If P1-12 must signal "a masked answer was sent", it posts only the request id and the length. Any tracing or `Debug` on that path prints the kind and the length, never the value.
- The masked value never enters `talaria-core` and never enters an `Event` the reducer or recorder sees.
- The answer for an unsupported request is written inside the handler for that inbound item, before anything else is processed, so the 100 ms budget is met by construction; the notice is a separate, lower-priority message.
- `talaria-tui` cannot name `talaria-app` types and the reverse (P0-02's layering rule). The only types they share come from `talaria-core`, `hermes-client` and `zeroize`. P1-12 (in `talaria-cli`, which depends on both) and this unit's demo (an example of `talaria-app`, which may use `talaria-tui` as a dev-dependency) convert between `MaskedRequestInfo` and `MaskedView`, and unwrap `MaskedValue`.
- Notices for disappearing prompts come from `PromptService::on_prompts_changed(open_keys)`, which P1-12 calls after each reducer update with the keys of the open prompts. A key that left without this client answering it (through `execute` or `deny_before_interrupt`) gives one notice. Open prompts are few, so this is cheap.

- Replies to `approval.respond` / `clarify.respond`: `resolved`, `already_resolved`, or an error with `data.reason` `stale_generation`, `invalid_params`, `permission_denied` (F-10, F-11). Hermes declares no error code numbers (U-2); the mock uses the code P1-02's tests use. A "silent" mode never replies (for the 2 s bound in test 15).
- After a response frame the mock may publish `request.cancel` with `reason: "resolved"` to the same connection, as Hermes does (F-21); test 20 uses this.
- Replies to any other method the demo's effect loop sends (`prompt.submit`, `session.interrupt`) are built from the contract's result schema for that method in `x-canonical-methods` (every `required` property with a placeholder of the right type): `CanonicalSubmitResult` and `CanonicalSessionHandle` (required `ref`, `instance_id`, `authority_epoch`, `revision`, `execution_generation`, `execution_state`) at v0.22.4.
- Timing: the mock stamps the monotonic time when it writes each request and when it reads each answer; the 100 ms assertions use those stamps.

## 9. Edge cases

| Situation | Expected behaviour |
|---|---|
| Same `approval.request` delivered twice (replay) | One card (P1-05 dedupes by key) |
| Same `prompt_id`, new `execution_generation` | A new card; the old one closes when its `.settled` arrives |
| `approval.settled` before the operator answers | Card disappears; notice `answered elsewhere or timed out` |
| `approval.respond` returns `already_resolved` | `Event::AnswerAlreadyResolved`; one notice (with the unsent note, if any); the card leaves on `.settled` (F-5) |
| `approval.respond` fails (`stale_generation`, `Unknown`) | `Event::AnswerFailed` reopens the card; notice with the reason |
| A second key while `Answering` | Ignored by the card; no second frame |
| Offered `choices` without `deny` | Should not happen (F-3). Esc closes the card locally with a notice and sends nothing |
| Unknown extra choice string | Shown after the known four, sent verbatim |
| A choice containing a control character | Drawn with a stand-in; the raw string is sent |
| `clarify.request` with empty `choices` | Free-text field |
| `multi_select: true` with empty `choices` | Free-text field (Hermes copies the flag regardless, F-4) |
| Multi-select with Other text | Other text appended as the last array element |
| Answer of 16,385 code points | Refused on the card; nothing sent |
| Masked request, then `request.cancel` `timeout` | Card disappears; notice `timed out; the agent continued without it` |
| Masked request, then `request.cancel` `resolved` | Card disappears; notice `answered in another window` |
| Masked request, then `request.cancel` `interrupted` | Card disappears; notice `withdrawn: the turn was interrupted` |
| `request.cancel` with an unknown reason | Card disappears; notice naming the (sanitized) reason |
| `request.cancel` `resolved` for an id this client answered or refused | Silent (Hermes sends it to the answerer too, F-21) |
| `request.cancel` `timeout`/`interrupted` for an id this client answered | Notice that Hermes did not accept the answer (F-37) |
| Operator answers after `request.cancel` | Nothing is written (`RespondError::Cancelled`) |
| Connection replaced while a masked card is open | Card disappears; notice `lost when the connection dropped` (Hermes treats the request as unanswered until its own timeout, F-34) |
| Unsupported kind twice on one connection | Two error replies; one notice |
| Unsupported kind after a reconnect | Error reply; a new notice |
| `display.install.sudo` with empty `session_id` | Error reply; notice not tied to a session |
| Unknown method (not in the contract) | P1-02 answers -32601; this unit is not called |
| `sudo` without `command` | Card without a detail line |
| Paste of 10,000 characters into a masked card | All kept in the buffer; the field shows bullets up to its width |
| Paste containing a newline into a masked card | Text up to the newline kept; nothing sent |
| A card appears while the draft is non-empty | Card drawn unfocused with the draft hint; keys go to the composer |
| A key within 250 ms of a card taking focus | Ignored (except Ctrl+C) |
| Ctrl+C on an approval card | `interrupt_requested`; P1-12 runs deny-before-interrupt, then interrupt |
| Ctrl+C on a clarification or masked card | Empty answer or empty value sent, then interrupt |
| Ctrl+C when P1-05 emits no interrupt | P1-12 calls `stop_cleared`; cards accept keys again |
| Deny before interrupt: a reply never comes | Return after 2 s; notice; interrupt anyway |
| A shared session with a Desktop window | Refusals usually win (F-38); accepted in phase 1 |
| Approval note typed, then a digit on the choices | The choice is sent; the note goes as `Event::Submit` after `resolved` |
| Whitespace-only note | No note; no `Event::Submit` |
| Ctrl+C while an approval is `Answering` | `interrupt_requested`, no intent, no deny; the in-flight answer stands |
| A masked card arrives in front of a card with typed text | The typed text is kept; the pushed-back card regains focus later with a fresh guard |
| `request.cancel` for an id never received | Silent |
| `approval.respond` times out (`CallError::TimedOut`) | `Event::AnswerFailed`; notice `could not answer: no reply in time` |
| Choice 10 or later in a clarification | Reached with Up and Down only |

## 10. Test notes

- The test author writes the stubs and the tests in the issue's order and records the red run. Each test's "red" reason is in the issue table.
- Snapshot tests use P1-06's vt100 support at fixed sizes (80×24 and 160×48). The expected files are committed text written by hand from section 5.6 before any code exists; they are never produced by an "accept" step. A developer who thinks a file is wrong sends it back to the test author.
- The replay tests read `fixtures/frames/approval.jsonl` and `clarification.jsonl` through P1-04's `ReplaySource`. P1-04 REQ-18 records `approval.respond` with `choice: "once"` and `clarify.respond` with its `answer` withheld (P1-04's deny-set covers `clarify.respond` `answer`). The approval test compares the outbound params with the recorded ones; the clarification test compares the other three keys and checks `answer` equals the typed answer. If a fixture lacks the frame, stop (issue stop condition).
- Test 3 drives time explicitly: `sync(..., now)` then `handle_key(key, now + 300ms)` for normal keys, and `now + 100ms` for the guard case.
- The property test (24) generates sequences of: server request (random kind from the sixteen), `request.cancel` for an open id, operator answer, connection replaced. Each sequence ends with a drain step that declines every masked request still open. Invariant: each request id has at most one outbound answer frame; each id that was neither withdrawn nor orphaned by a replaced connection has exactly one.
- The secrecy test (23) types a marker (for example `TALARIA-MASK-7f3a`) into a masked card and searches: the vt100 screen, every log line and every tracing event captured by a test subscriber installed for the whole test, the `Debug` output of every public type on the path (`PromptIntent`, `MaskedValue` has none, `MaskedRequestInfo`, `PromptNotice`, `Executed`), every notice, and the P1-04 recording of the session. Only the outbound response frame may hold it; in the recording the result is `"[redacted]"`. The test cannot prove absence from process memory; zeroing is checked by code review of `MaskedValue`.
- Test 5 key paths are in section 5.2. Test 11 opens the text path (the Other row when the fixture has choices, else the text field), types `talaria-replay-answer`, and presses Enter; `answer` must equal `talaria-replay-answer`.
- Tests 10 and 11 convert a `PromptIntent` into P1-05's events with a helper in `crates/talaria-app/tests/support/convert.rs` (`apply_intent(&mut PromptService, &mut SessionState, PromptIntent) -> Vec<Effect>`: `set_note` then `Event::AnswerApproval` or `Event::AnswerClarify` into P1-05's reducer). The demo includes the same file by path. It is test support, not P1-12's production conversion.
- Test 21 also covers: an `already_resolved` key and a key whose deny was not confirmed give exactly one notice in total, not a second one on `.settled`.
- No test sends `unattended` on `prompt.submit`; test 13 asserts the returned `Event::Submit` carries only `text` and `submission_id`, and P1-12's tests assert the `prompt.submit` key set.

## 12. Design reasoning

- **Why cards live in two crates.** The layers table forbids the TUI from holding protocol state and the app from rendering. The card's view state (highlight, note text, ticks, masked buffer) is presentation; the open server requests and their responders are protocol state.
- **Why the shared types are so few.** P0-02 forbids normal edges between `talaria-app` and `talaria-tui`. A third-party zeroing type (`zeroize::Zeroizing<String>`) crosses the boundary without a new edge; plain strings carry everything else.
- **Why the masked value bypasses the reducer.** The reducer's events can be logged, snapshot-tested and recorded. Keeping the value out of them makes "never recorded" structural instead of a redaction rule that can be forgotten.
- **Why refuse instead of ignore.** An ignored request blocks the agent thread for its full deadline (up to 300 s for `theme.pick`). An error is settled at once and the agent continues (F-19). The cost is the shared-session preemption (F-38), accepted for phase 1.
- **Why display order differs from payload order.** Hermes's own terminal UI keeps "Deny last" (F-33) and the roadmap names that order. The trap the bake-off hit was mapping by position; sending the label removes it.
- **Why the highlight starts on `once`.** Hermes's own terminal UI does so (F-40), and P1-12's live scenario answers "once (Enter on the first choice)". The risk that brings, a key pressed just before the card appears, is handled by the focus rule and the 250 ms guard instead.
- **Why deny before interrupt.** See section 5.5: it does not rely on Hermes's interrupt polling, which the bake-off saw fail at an older revision.
- **Why the batch clarify form is not built.** The roadmap ships the single form in phase 1 and makes the batch form optional. The batch form needs `clarify_batch: true` on `prompt.submit` (P1-12's call path) and `clarify.lock` (F-27, F-29). A later unit that builds it adds its own tests, changes the `clarify` row of section 4 from "refuse" to "batch card", and narrows the issue's `clarify_batch` guard.

Related handoff sections: [roadmap P1-09](../07-roadmap-and-work-units.md#p1-09--questions-from-the-agent), [protocol rules](../05-architecture.md#protocol-rules-every-client-layer-must-keep), [layers](../05-architecture.md#layers), [security](../05-architecture.md#security), [what Hermes offers a client](../03-hermes-today.md#2-how-a-third-party-client-attaches-verified-live), [upstream proposals](../08-risks-and-open-questions.md#upstream-contributions-worth-proposing-to-hermes).

## 13. The demo (`crates/talaria-app/examples/prompt_cards.rs`)

The acceptance scenarios run this example, because the `talaria` binary arrives in P1-12. It uses the test mock in-process (section 8), draws cards inline through P1-06's live region, reads keys and pastes with crossterm (converting each key with P1-08's `Key::from` before it reaches `PromptStack`), and runs a small effect loop: it executes `Effect::RespondApproval` and `Effect::RespondClarify` through `PromptService::execute`, sends `prompt.submit` for `Effect::SendPrompt` (exactly `session_id`, `text`, `submission_id`), awaits `deny_before_interrupt` and then sends `session.interrupt` for `Effect::Interrupt`, then calls `stop_cleared`.

Command line: `prompt_cards --scenario <name> --log <file>`. Exit code 0 after `scenario done`; 2 for an unknown scenario name.

Output: each line below is printed above the live region and appended to the `--log` file (created fresh). Frames are compact JSON on one line.

| Line | When |
|---|---|
| `card shown: <header without counter>` | a card first becomes the drawn card |
| `card closed: <header without counter>` | the drawn card leaves |
| `out <frame>` | every outbound frame; a masked value is replaced by `[withheld, N characters]` |
| `in <frame>` | every reply and event the mock sends |
| `notice: <text>` | every `PromptNotice` and `KeyOutcome` notice |
| `refused <kind> in <N> ms` | after each refusal, N measured from the mock's write stamp to its read stamp (section 8), rounded down |
| `scenario done` | the scenario's script has finished and no card is open |

Scenarios (ids and session ids are placeholders; facts as in sections 2 and 3):

| Name | Script |
|---|---|
| `approval` | Replays `fixtures/frames/approval.jsonl` up to and including its `approval.request`, so P1-05 sees the recorded turn running. The mock answers `approval.respond` with `resolved` and then publishes `approval.settled`. |
| `approval-note` | `approval.request` for `git push --force origin main`, choices `once`, `deny`, `session`, `always`. The mock answers `resolved`, publishes `approval.settled`, and answers the `prompt.submit` from its result schema. |
| `clarify-multi` | `clarify.request` "Which environments?", choices `staging`, `prod`, `qa`, `multi_select: true`; after its `clarify.respond` is answered `resolved` and settled, `clarify.request` "Any notes?" with no choices. |
| `sudo` | `sudo` server request with `command: "sudo apt-get install jq"`. After the answer, `request.cancel` `reason: "resolved"`. |
| `unsupported` | `theme.pick`, `theme.pick`, `terminal.read` server requests, 200 ms apart; ends after the third refusal. |
| `interrupt` | Replays `fixtures/frames/approval.jsonl` up to and including its `approval.request` (a running turn with one approval). The mock answers the deny `resolved`, publishes `approval.settled`, and answers `session.interrupt` from its result schema. |
| `withdrawn` | An approval, then `approval.settled` for it after 2 s without an answer; then a `sudo` request, then `request.cancel` `reason: "timeout"` after 2 s. |

Screen reads in the issue's scenarios use `herdr pane read <pane> --source visible`; the log checks use the `--log` file, so they do not depend on which herdr read source shows scrollback. If a screen read does not show a line the log says was drawn, read again after one second and keep both reads as evidence.
