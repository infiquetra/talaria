## 1. What this unit adds, in one paragraph

`/configure <request>` lets a person describe a Hermes configuration change in plain words, for
example `/configure ring the terminal bell when a reply finishes` or `/configure add the deepwiki
MCP server`. Talaria reads the connected profile's current configuration and inventories, starts a
short-lived, hidden Hermes session that has no tool able to change anything, and sends it a brief:
Talaria's own configuration instructions (the "configuration skill"), the request, and the current
state. The agent answers with one structured block: a proposal of typed changes, a request for more
context, an answer, or a refusal. Talaria validates every proposed change against the configuration
schema and the inventories, withholds anything secret, and shows a review list of rows ("set
`display.bell_on_complete`: false → true · may need a restart", the label being `P4-01`'s
`apply_effect` label for that key). The person selects rows, confirms with
`y`, and Talaria applies each selected change through the service of the unit that owns that kind
of change (settings, main model, MCP servers, skills and toolsets, cron jobs), reads each result
back, and shows a summary. Keys, sign-ins, installs and connectors are never applied from a
proposal; they become "next step" rows that open the right screen. The roadmap row is in
[07 phase 4](../07-roadmap-and-work-units.md#phase-4--configure-hermes-from-talaria); the idea is in
[05 Configuration](../05-architecture.md#configuration) and pattern 9 of
[04 Patterns to take](../04-prior-art.md#patterns-to-take).

## 3. How others present the same feature

### 3.1 Hermes Desktop

Desktop has no general "describe a configuration change" command. Its nearest relative is the
`manage_catalog` tool, given only to desktop sessions through the `catalog` toolset: the model
sends catalog ids and an action, "nothing else: the pin, scan, target profile and activation are
the host's"; the host shows one approval card with a row per item and installs each row the user
approves ([`tools/connectors/catalog_tool.py` lines 1 to 8 and 36 to 48](https://github.com/NousResearch/hermes-agent/blob/v0.22.4/tools/connectors/catalog_tool.py);
[`toolsets.py` lines 71 and 149 to 152](https://github.com/NousResearch/hermes-agent/blob/v0.22.4/toolsets.py#L149-L152)).
The same principle governs this unit: the model proposes identifiers and values; the client owns
validation, secrets, the target and the apply. Desktop's first-run onboarding chat uses a
desktop-only `onboarding` toolset (`setup_beat`) to draw setup cards; it is not reachable from a
terminal client. Desktop's plumbing sessions are created `hidden: true` (H2).

### 3.2 Hermes's own terminal UI

It has no conversational configuration. `/config` shows the configuration (H30). An agent can
configure Hermes only through the bundled `hermes-agent` skill, which runs `hermes config set` and
edits files directly with no review step (H31). That is exactly what this unit avoids.

### 3.3 Claude Code

From the parity research ([u12](../research/u12-claude-code-parity.json), entries `/update-config`,
`/auto-mode-setup`, `/doctor`, `/statusline`):

- `/update-config` (a bundled skill): "Describe a settings change … and Claude edits the matching
  `settings.json` file." No separate review screen; the edit goes through Claude Code's normal
  file-edit permission prompt.
- `/auto-mode-setup`: "Draft … entries …, then review the draft and save it." This is the closest
  pattern: draft, review, save.
- `/doctor`: proposes fixes "that Claude applies after you confirm".
- `/statusline`: "Describe what you want."

Talaria takes the draft-review-save shape, with a typed row per change instead of a file diff,
because Hermes's configuration is spread over `config.yaml`, the key file, MCP, skills, plugins and
the cron store, and each has its own owning API.

## 4. Design

### 4.1 Settled decisions and why

- **D1. The model proposes; Talaria applies.** The session gets `toolsets: ["clarify", "no_mcp"]`.
  `clarify` lets the agent ask a question; `no_mcp` stops every enabled MCP server from being added
  (H5). Nothing in that session can write a file, run a command, edit a skill, touch memory or cron.
  Rejected: giving it `terminal` or `skills` and relying on approvals (an approval card is easy to
  wave through, and `skill_manage` writes without one).
- **D2. One write path per kind of change, owned by a sibling.** Settings go through `P4-01`'s
  write and read-back (`PUT /api/config`), not the socket `config.set`, which accepts only a fixed
  set of session keys (H22). Main model through `P4-03`; MCP servers through `P4-04`'s `McpService`;
  skills, toolsets and plugins through `P4-05`'s `CapabilitiesService::apply`; cron jobs through
  `P4-08`'s cron service. This unit adds no new route, method or write.
- **D3. Secrets never cross the model boundary.** The brief contains no secret value (secret keys
  are shown as `<secret>`, the key file is never read), every operator text that would be sent (the
  request, refine text, clarification answers) is refused if the detector finds a secret, and any
  change that would carry a secret is refused. Model and Hermes strings are checked before they
  are stored (4.10b). Keys, sign-ins,
  installs from the network and connectors become hand-off rows (`P4-05` decision D8 asks for the
  same: installs open its hub item).
- **D4. Nothing applies without the operator.** Rows are selected in the review list; destructive
  rows start unselected; `a` asks `Apply … ? y/n`; only `y` applies.
- **D5. A hidden, rule-free, short-lived session.** `hidden: true` keeps it out of the ordinary
  `session.list` pickers (H2, H12c). It does not hide it from `session.active_list`, so `P3-01`'s
  fleet may show it as an unlisted waiting row while a clarification is open; that is accepted
  (a waiting question deserves attention) and never claimed otherwise. `ignore_rules: true` keeps
  the project's AGENTS.md, SOUL.md and memory out of the prompt (H9, H12b), so a repository cannot
  steer a configuration change. Every exit sends one
  `session.detach` with `end_reason: "configure_closed"` (H20).
- **D6. The connected profile only.** `P4-04` sends no `profile` field (its decision 7), and the
  services are built per connection. A proposal that names another profile is refused with the
  command to start Talaria on that profile (operator question Q1).
- **D7. The configuration skill is Talaria's own text.** `crates/talaria-core/src/configure/skill.md`
  is compiled in with `include_str!` and sent as the start of the first prompt. Nothing is installed
  into Hermes, so the protocol and the parser always match. Rejected: the `skills` create field
  (needs an installed skill, H11); the bundled `hermes-agent` skill (it tells the agent to edit
  configuration itself, H31).
- **D8. The brief goes in `text`, not `api_text`.** `api_text` is bound to one admission (H14); a
  refine turn could then run without the brief. The hidden session's stored first row therefore
  holds the brief, which carries no secret (D3).
- **D9. A session, not `llm.oneshot`.** The roadmap names `session.create`; a session gives
  clarify questions and refinement turns, which `llm.oneshot` lacks (H32).
- **D10. Exactly one fenced block.** The reply protocol is one block whose info string is
  `talaria-configure` holding one JSON object. Prose outside it is shown, never parsed.
- **D11. Strict tool guard that fails closed.** The brief is submitted only when the snapshot
  positively lists `clarify` and no other tool. Any other tool, `yolo`, or an absent or empty
  `info.tools` (which Hermes also writes when its tool snapshot fails, H8) stops the run before
  anything is sent (H7, H8; operator question Q4). The runtime tool-event guard (4.8) is a second
  line, not proof that no tool ran.
- **D12. No toolset fallback.** An earlier draft retried a `toolsets` refusal with `["no_mcp"]`. That
  session would report `info.tools` `{}`, which D11 cannot accept, so the retry could never lead to a
  submit. A refusal whose `data.field` is `toolsets` (H12a) is reported with T26 instead.
- **D13. The secret detector is injected.** `talaria-core` never imports `hermes-client`, so the pure
  code takes a `SecretDetector` (`fn(&str) -> bool`). The application passes
  `|t| !hermes_client::redact::scan_for_secrets(t).is_empty()` (`P1-04`'s scanner; it returns line
  and rule hits, never spans). A string with a hit is withheld whole, so spans are never needed.
  `scan_literals` is not used: it checks supplied literals, not credentials.
- **D14. Connectors only after consent.** At Hermes v0.22.4, `connectors.list` with an account
  owner calls `ensure_guest_identity()`, which creates a Nous guest identity when the profile has
  none (`P4-11` H11; `tui_gateway/methods_connectors.py` lines 84 to 92 and 231 to 237). So
  `P4-11` keeps one process-wide `ConnectorsConsent` that every caller obeys (`P4-11` decision 4;
  `PH4B` decision 7).
  `SiblingBackends::read_context` gathers the connectors section only when
  `ConnectorsConsent::granted(<profile>)` is true; otherwise the section is `Unavailable`, with a
  reason saying that consent is given in `/connectors`, and no `connectors.*` frame is sent.
  This unit never calls `grant`: consent is given only in `P4-11`'s overlay. `P4-11`'s
  `ConnectorsService` also refuses every `connectors.*` effect without consent (defence in depth).

### 4.3 States

```text
          /configure <request>
                 │ (empty → T1; over 4,000 → T25; secret → T5; not connected → T6)
                 ▼
            Gathering ──GatherFailed (schema or config read)──► Failed
                 │ Gathered
                 ▼
            Starting ──CreateRefused──► Failed (T26 when field is toolsets, else T22; no retry)
                 │  └─ Esc ─► Closing (create outstanding: a late Created is detached, never submitted)
                 │ Created: info.tools non-empty, names clarify, nothing else, yolo false?
                 │          other tools or yolo ─► Failed (T7) + Detach
                 │          absent or {} ─► Failed (T7b) + Detach
                 ▼ yes: Submit(brief)
            Thinking ◄──────────────── Need (≤ 3 rounds per run: Submit(context reply))
              │  │  ├─ clarify.request ─► Question ─answer (detector clean)─► Thinking
              │  │  │                       └─ answer with a secret ─► T27, question stays open
              │  │  ├─ approval.request ─► DenyApproval, Interrupt ─► Failed (T8)
              │  │  ├─ tool.generating / tool.start not clarify ─► Interrupt ─► Failed (T8)
              │  │  ├─ Esc ─► Interrupt ─► Cancelled (T16)
              │  │  └─ TURN_TIMEOUT ─► Interrupt ─► Failed (T17)
              │  └ message.complete status error ─► Failed (T22) ; interrupted ─► Cancelled
              ▼ message.complete status complete: parse_reply(payload.text)
   Review │ Answer │ Cannot │ NoProposal (r: refine text, detector clean → Submit; deadline reset)
     │ a (≥1 selected)
     ▼
  Confirming ─n/Esc─► Review
     │ y
     ▼
  Applying (one step at a time; NeedsConfirm pauses for y/n)
     ▼
    Done ── Enter/Esc ──► Closing (Detach once, Notice once) ──► closed
```

Every terminal phase (Done, Answer, Cannot, NoProposal on Esc, Failed, Cancelled) goes through
Closing. Rules that make "exactly once" precise:

- "Once" counts `Detach` **effects**: one per created session, emitted on the first exit after
  `Created`. A run that never received `Created` emits none. If Esc (or Quit) arrives while the
  create is outstanding, the state enters Closing with `create_outstanding`; a later `Created`
  emits `Detach` at once and nothing else; a later `CreateRefused` or a create timeout emits
  nothing.
- `message.complete`, `message.delta` and tool events are read only in Thinking (and Question for
  tool events). In any other phase they are ignored, so a stale completion from an interrupted
  turn cannot become a proposal. Each accepted `Submit` starts a new `TURN_TIMEOUT`.
- In Closing every input except `Detached`, `Tick` and a late `Created` is ignored; `StepDone` cannot
  arrive there because Esc is ignored while Applying.
- `LinkLost`: the state still emits `Detach` if a session was created; `ConfigureService` sends it
  only when a connection exists and otherwise reports `Detached` at once (best effort; the hidden
  session is left to Hermes).
- Quit: in Thinking or Question the state emits `DenyApproval` for any open approval, then
  `Interrupt`, then `Detach`; `ConfigureService::close` runs them in that order and abandons
  whatever is still pending when `QUIT_DEADLINE` (2 s, which overrides the 10 s interrupt timeout)
  expires.

### 4.4 The reply protocol

The agent's final message of a turn must contain exactly one block:

````text
```talaria-configure
{ "kind": "proposal", ... }
```
````

- The opening fence is a line that, after trimming leading and trailing spaces and tabs and a
  trailing `\r`, is exactly ```` ```talaria-configure ````. The closing fence is the next line that,
  trimmed the same way, is exactly ```` ``` ````. An opening fence without a closing fence is
  `NoBlock`. Fixtures in test 1 freeze these rules.
- Zero blocks → `NoBlock`; two or more → `SeveralBlocks(n)`; content over 65,536 bytes →
  `TooLarge`. A ```` ```json ```` block is not a proposal.
- The JSON is one object with `kind` one of `proposal`, `need`, `answer`, `cannot`.

| kind | fields | meaning |
|---|---|---|
| `proposal` | `summary` (string, required, cut to 500 characters), `profile` (optional string), `changes` (array, required, 1 to 20) | typed changes to review |
| `need` | `sections` (array of strings, required), `why` (optional) | Talaria answers with those sections (4.7) |
| `answer` | `text` (string, required) | nothing to change; shown as is |
| `cannot` | `reason` (string, required) | the agent cannot do it; shown |

Change objects (`op` required; `why` optional on each, cut to 300 characters; unknown extra fields
are ignored). Whole-reply errors are only: not JSON, not an object, unknown or missing `kind`, a
missing or ill-typed reply-level field (`summary`, `changes` not an array, `sections`, `text`,
`reason`), or more than 20 changes. Inside one change, problems are row-level and are decided in
this order:

1. An `mcp_add` holding any of `env`, `headers`, `bearer_token`, `api_key`, or an `auth` other than
   `"oauth"` → `McpSource::Forbidden(<first such field name>)`, whatever else is wrong; no other
   field of that object is kept (the name is replaced by `WITHHELD` if the detector hits it).
2. A change that is not an object, or has no string `op` → `Unknown { op: "" }`.
3. An unknown `op` → `Unknown { op }`.
4. A known op with a required field missing or of the wrong JSON type (for example `enabled` as a
   string, `mcp_add` `args` not an array of strings, a `screen` not in the list, `repeat` not an
   integer in `1..=u32::MAX`), or `mcp_add` with zero or more than one source → `Malformed { op,
   field }` (for two sources, `field` is `source`).

| op | fields | maps to |
|---|---|---|
| `set` | `key` (dotted), `value` (any JSON) | `Change::Set` |
| `mcp_add` | `name`; exactly one of `preset` (catalogue name), `command` + `args` (array of strings), `url` (+ `auth: "oauth"` optional) | `Change::McpAdd`; any of `env`, `headers`, `bearer_token`, `api_key`, an `auth` other than `oauth` → `McpSource::Forbidden` |
| `mcp_enable` | `name`, `enabled` (boolean) | `Change::McpEnable` |
| `mcp_remove` | `name` | `Change::McpRemove` |
| `toggle` | `kind` (`skill`, `toolset`, `plugin`), `name`, `enabled` | `Change::Toggle` |
| `cron_add` | `name`, `schedule`, `prompt`, `repeat` (optional positive integer), `deliver` (optional string) | `Change::CronAdd` |
| `cron_pause`, `cron_resume`, `cron_remove` | `job_id` | `Change::Cron*` |
| `main_model` | `provider`, `model` | `Change::MainModel` |
| `open` | `screen` (`providers`, `mcp`, `capabilities`, `cron`, `profiles`, `connectors`, `settings`), `target` (optional) | `Change::Open` (hand-off) |
| anything else | | `Change::Unknown { op }` |
| a known op with a bad field | | `Change::Malformed { op, field }` |

### 4.5 Validation (one row per change, in proposal order)

`validate` first checks the proposal: `profile` present and not equal to `ctx.profile` →
`ProposalError::WrongProfile` (T19); more than 20 changes → `TooMany` (T11). Then per change, in
this order: (a) withholding (4.10b) replaces every string the detector hits; a hit in a `Set`
value or key, a `CronAdd` field, or an MCP name, command, argument or URL makes the row
`Refused(T23)`; (b) the inventory sections the change needs (table below) must be `Available`, else
`Invalid("could not read <section> before the proposal")`; (c) duplicates; (d) the per-op rules.

Sections each change needs (the schema, effective, raw and defaults reads are required for the whole
run, so `Set` only needs them):

| Change | Needs |
|---|---|
| `Set` | (required reads only) |
| `McpAdd` | `mcp_servers`; with a `Preset` also `mcp_catalogue` |
| `McpEnable`, `McpRemove` | `mcp_servers` |
| `Toggle` | `skills`, `toolsets` or `plugins` by `kind` |
| `CronAdd`, `CronPause`, `CronResume`, `CronRemove` | `cron_jobs` |
| `MainModel` | `main_model` and `routes` |
| `Open`, `Malformed`, `Unknown` | nothing |

Duplicates: each change has an identity; the first row with an identity wins and every later row
with the same identity is `Invalid("duplicate of row <n>")`. Identities: `Set` → the key;
`McpAdd`, `McpEnable`, `McpRemove` → the server name (so add-then-enable on one name is a
duplicate; rows are validated against the gathered inventory only, never against earlier rows);
`Toggle` → `(kind, name)`; `CronPause`, `CronResume`, `CronRemove` → the `job_id`; `CronAdd` → its
`name`; `MainModel` → one identity for all; `Open` → `(screen, target)`; `Malformed` and `Unknown`
have none.

| Change | Ready when | Otherwise |
|---|---|---|

### 4.6 The brief (first prompt)

`build_brief(ctx, request, detect)` concatenates, in this order, with one blank line between
sections:

1. `skill.md` (section 4.15), verbatim; at most `SKILL_MAX_BYTES` (6,000), checked by test 10.
2. `Profile: <profile>. Hermes <version or "version unknown">. Talaria applies changes to this
   profile only.`
3. `Request: ` and the request, with control characters replaced by `P1-06`'s stand-ins. The
   request has already passed the detector (T5) and is at most 4,000 characters (T25), so at most
   16,000 bytes.
4. `Current state:` one line per inventory section (`mcp_servers`, `mcp_catalogue`, `skills`,
   `toolsets`, `plugins`, `cron_jobs`, `providers`, `main_model`, `profiles`, `connectors`), each
   item `name (on|off)`; cron jobs `job_id name "schedule" state`; providers `slug (configured|not
   configured)`; main model `provider/model` (`none` when empty); `Unavailable(reason)` →
   `<section>: unavailable (<reason>)`. Each item is cut to 200 characters.
5. `Settings set in config.yaml:` the raw read flattened to `key = <json>`, schema order, then
   unknown keys alphabetically; a key with `is_secret_key` true, or whose value
   `contains_secret_key`, is written `key = <secret>`; a `${NAME}` value is written as is; values
   over 200 characters are cut with `…`.
6. `Setting keys:` every schema key, grouped by category in `category_order`, one line per category:
   `display: compact, bell_on_complete, …`.

Withholding is per field, not per span: every item of sections 4 and 5 (each rendered value, each
inventory name or description) is passed to `detect` before it is written; a hit writes `WITHHELD`
in its place and adds one to `withheld`. Section 1 is Talaria's own text; sections 2 and 3 have
already been checked.

Budget `BRIEF_MAX_BYTES` (49,152 bytes, UTF-8), measured on the whole final text including headers,
blank lines and every marker. The mandatory part (sections 1 to 3) is at most 6,000 + about 300 +
16,000 bytes, so it always fits; a debug assertion guards this. When the whole text is over, apply
these reductions in order, re-measuring after each, and stop as soon as it fits:

1. Remove whole category lines of section 6 from the last category backwards; a final line
   `[<n> setting keys omitted; ask with need settings:<prefix>]` counts them.
2. Cut each inventory list of section 4 to its first 50 items, adding `… <n> more` to its line.
3. Cut section 5 to its first 200 keys, with a final line `[<n> more settings set; ask with need
   settings:<prefix>]`.
4. Remove section 5 lines one at a time from the end (the same marker line counts them).
5. Remove inventory items one at a time, from the end of the last section backwards, updating each
   line's `… <n> more`.
6. Replace each remaining section 4 line, last first, with `<section>: omitted (ask with need
   <section>)`.

Each marker's bytes are counted when the decision to remove is made (the marker is reserved at its
widest form, with `<n>` as five digits). Cuts happen only at character boundaries (`char_indices`),
never inside a UTF-8 sequence. Same inputs give identical bytes; the iteration order is fixed
(schema order, then alphabetical).

### 4.7 Context replies (`need`)

Accepted section names: `settings:<prefix>` (every schema key starting with `<prefix>`, one line
each: `key | type | options | default | current`; `default` from `ctx.defaults`, `current` from
`ctx.effective`; secret keys `<secret>`; a key whose raw value holds a `${NAME}` or `${env:NAME}`
reference shows the raw text for `current`, never the expanded value, because the effective read
expands references (`P4-01` H19) and the expansion may be a secret the scanner does not recognise),
`mcp_servers`, `mcp_catalogue` (with descriptions cut to 120 characters and `requires`), `skills`,
`toolsets`, `plugins`, `cron`, `providers`, `main_model`, `profiles`, `connectors`. Unknown names
are listed back as `unknown section: <name>`. The reply starts `Talaria context (requested):`, ends
with the line `Reply with one talaria-configure block.`, is capped at 24,576 bytes (cut at a line
boundary with `[cut]`), and uses the same per-field withholding as the brief. It is submitted as
the next turn without asking the operator; the panel shows `Gave the agent: <sections>`. The count
of context replies is kept for the life of the run (refine never resets it); after
`MAX_CONTEXT_ROUNDS` (3), a fourth `need` shows T18 and waits for `r` or Esc.

| Signal | Action |
|---|---|

| snapshot `info.tools` is `{}`, absent, or lists no `clarify` | no submit; `Detach`; Failed with T7b (fails closed, D11; `{}` is also what a failed snapshot gives, H8) |

### 4.9 Apply plan and outcomes

`plan_apply` takes selected `Ready` rows and orders the steps: (1) one `Settings` step with every
selected `Set` (one `PUT`) and `baseline = ctx.effective` as gathered, (2) `MainModel` with
`baseline = ctx.inventory.main_model` and `base_url` = the chosen `routes` row's `api_url` (or
`""`), (3) MCP steps in proposal order, (4) `Capability` steps, (5) cron steps (`deliver` always
`"local"`). Steps run one at a time. `ConfigureBackends::apply` returns a `StepResult` with exactly
one `RowOutcome` per row index in the step; a row the result omits is treated as `Unknown("no
result")`.

| Step | Owner and path | Outcome per row |
|---|---|---|
| `Settings` | `P4-01` `SettingsService`: `FetchFresh`; `find_conflicts(changes, baseline, fresh)`; conflicting keys are dropped from the patch; `Write { patch: build_patch(rest) }` (one `PUT /api/config`, skipped when nothing is left); `ReadBack`; `classify_readback(sent, before = baseline[key], after)` per key | conflicting key → `Conflict("changed since the proposal: now <v>")`; `Applied` → Applied; `Adjusted(v)` → Adjusted; `NotApplied` → NotApplied (`P4-01` T14 or T33 text); `ChangedElsewhere(v)` → Conflict; write `Refused` → every sent key Failed with Hermes's `detail`; write outcome unknown → read back, then as above; `ReadBackFailed` → every sent key Unknown |
| `MainModel` | `P4-03` `ModelRolesService::execute`: `FetchFresh { section: Main }` (reads `main.provider`, `main.model`); a value different from `baseline` → Conflict, nothing written; else `Assign { step: MainModel, assignment: Assignment { scope: main, task: "", provider, model, reasoning_effort: unchanged, base_url, confirmed } }`; then `ReadBack { section: Main }` | `ConfirmRequired { message }` → `StepResult::NeedsConfirm`; `y` reruns the step with `confirmed: true` (sent as `confirm_expensive_model: true`); `n` or Esc → NotApplied("not confirmed"); read-back shows `provider/model` → Applied; shows another route → NotApplied("Hermes now uses <p>/<m>"); `RolesError::OutcomeUnknown` → read back, then as above; read-back fails → Unknown; `NotSent` → Failed("not sent: <reason>"); `Refused` → Failed(detail); `RestartRequired` → Failed(`P4-03`'s restart text) |
| `McpAdd` | `P4-04` `McpEffect::AddServer { name, preset, config, token: false }`; then `LoadList` and look for the name | `Added(Ok)` and listed → Applied; `Added(Ok)` but not listed → NotApplied("Hermes reported success but the server is not listed"); `Added(Err)` → Failed(Hermes's message); `Unknown`, or the list read fails → Unknown |
| `McpEnable`, `McpRemove` | `P4-04` `SetEnabled`, `Remove`; then `LoadList` | `Toggled(Ok)`/`Removed(Ok)` and the list agrees → Applied; the list disagrees → NotApplied; 4064 → NoChange("already gone"); list read fails → Unknown; else Failed |
| `Capability` | `P4-05` `CapabilitiesService::apply(profile, change)` (its own read-back) | `Applied` → Applied; `Unchanged` → NoChange; `Refused(t)` → Failed(t); `Unknown` → Unknown; `ReadBackMismatch` → NotApplied |
| `CronAdd`, `CronControl` | `P4-08`'s cron service with `AddRequest { name: Some(name), schedule, prompt, repeat, deliver: "local" }` or the control action; then a list | success and listed (or gone for remove, state changed for pause and resume) → Applied; success but the list disagrees → NotApplied; `CallFailure::Tool { job_saved: true, .. }` → Failed(`P4-08`'s T16 text: saved but not scheduled; do not create it again); other `Tool` or `Rpc` → Failed(`error`); `Unknown` or list read fails → Unknown; `NotSent` → Failed |

An `Unknown` outcome on any row, or a lost link, stops the run: rows of remaining steps are
`NotAttempted`. A `Failed`, `NotApplied` or `Conflict` row does not stop the run. Nothing is
retried automatically.

### 4.10 The screen and keys

An overlay of `P1-06` titled T2. Body by phase:

- Gathering, Starting: one line (T3, `Starting the configuration agent…`).
- Thinking: the agent's streamed prose (`message.delta` text accumulated, block hidden by
  `prose_without_block`, last 12 lines), then T4 with elapsed seconds (1 Hz tick).
- Question: `P1-09`'s prompt stack inside the panel.
- Thinking prose is line-buffered: `message.delta` text is appended to a buffer; only complete
  lines (up to the last `\n`) are candidates for display, and the trailing partial line is held
  until its newline or `message.complete`. Before display, `prose_without_block` removes the block
  (a held line that starts with three backticks is never shown), and each complete line passes the
  detector (a hit shows `WITHHELD`). So a token split across deltas is checked whole.
- Review: the summary (cut to 3 lines), then one line per row:
  `[x] ` selected, `[ ] ` selectable unselected, `  = ` NoChange, `  ✗ ` Invalid or Refused (reason
  after ` · `), `  → <n> ` HandOff (the first nine numbered 1 to 9; `1`-`9` open them from Review
  too, after closing the overlay; a tenth or later HandOff shows `  → ` with no number and its
  command, for example `next: open cron jobs (/cron)`, to type after closing); destructive rows show
  `!` after the box; `Set` rows end ` · <effect_label>`. Detail (`d`) is an inline toggle: it
  expands, under the selected row, `why`, the full value (JSON, withheld and sanitised) and the
  owner screen; `d` again, or moving the selection, collapses it. It is not a separate phase, so
  Esc in Review keeps its meaning (discard).
- Confirming: T14 under the list.
- Applying: each row's live mark (`…` running, `✓` applied, `~` adjusted, `=` no change, `✗` failed
  or not applied, `?` unknown, `-` not attempted, `!` conflict).
- Done: T15, then the rows with marks and reasons (4.9 table), then `Next steps:` listing every
  HandOff row (the first nine numbered `1` to `9`, later ones with their command), then the restart
  lines of 4.9.

| String | Source | Check |

### 4.12 `talaria configure --dry-run`

`talaria [--profile p] [--provider x --model y] configure --dry-run [--json] <request…>`: connects
like `P1-12`, gathers, creates the hidden session, submits the brief, answers `need` rounds
automatically (same cap), answers any `clarify.request` with an empty answer (H18: skipped), and
prints the validated rows. It never applies. Without `--dry-run` it prints T29 on stderr and
exits 2. Model selection: `--provider` and `--model` (both or neither) when given, else
`[configure]` (4.13), else both omitted (the command line has no foreground session).

Exit codes: 0 proposal with at least one `Ready` row; 3 `answer`, `cannot`, or a proposal with no
`Ready` row; 4 no block or unreadable; 1 connection, create or turn failure; 2 usage; 130 SIGINT
(after interrupt and detach). JSON (`--json`), version 1:

```json
{"version":1,"profile":"fixture","model":"ollama-cloud/minimax-m3.1-flash","kind":"proposal",
 "summary":"…","rows":[{"op":"set","status":"ready","text":"set display.bell_on_complete: false → true",
 "reason":null,"destructive":false}],"context_rounds":0}
```

`status` is `ready`, `no_change`, `invalid`, `refused` or `hand_off`. Text output prints the same
rows with the review marks.

Output per exit code:

| Exit | stdout (`--json`) | stdout (text) | stderr |
|---|---|---|---|
| 0, 3 | the JSON object above (`kind` `proposal`, `answer` with `summary` = the text, or `cannot` with `summary` = the reason; `rows` empty for the last two) | the rows, or the answer or reason | nothing |
| 4 | the object with `kind` `no_block` or `unreadable`, `summary` = T9 or T10's reason, `rows` empty | T9 or T10 | nothing |
| 1 | `{"version":1,"error":"<text>","exit":1}` (connection, create, guard, turn failure; text withheld per 4.10b) | the error text | nothing |

### 4.13 `~/.talaria/config.toml`

A `[configure]` table loaded by `P1-08`'s loader (never fatal): `provider` and `model` (strings,
both or neither). Precedence in the terminal UI: `[configure]`, else the foreground session's
provider and model, else both omitted (the profile default). Precedence in the dry run: 4.12. A bad
value (one of the two, or not strings) falls back to the next source with a notice.

### 4.14 Budgets and timeouts

- Overlay first frame within 50 ms of Enter (before any reply); keystroke to frame within 16 ms at
  the 95th percentile ([05 budgets](../05-architecture.md#performance-budgets)).
- No frames while idle, except a 1 Hz tick in Thinking and Applying.
- `build_brief` on the 825-key fixture: median at most 10 ms (bench).
- Timeouts: gathering reads use the sibling services' own (P4-01 reads 15 s); `session.create`
  30 s; `prompt.submit` 30 s; `session.interrupt` 10 s; `session.detach` 2 s; a turn
  `TURN_TIMEOUT` (300 s), restarted by each accepted submit; apply steps use the owner's write
  timeouts. On quit, `QUIT_DEADLINE` (2 s) bounds deny, interrupt and detach together and wins
  over the 10 s interrupt timeout.

### 4.15 The configuration skill (`skill.md`) outline

The file is plain English, under 6,000 bytes, and says, in order:

1. You are proposing changes to one Hermes profile for a person who will review each one. You
   cannot change anything yourself and you have no tools except `clarify`.
2. Reply with exactly one fenced block ```` ```talaria-configure ```` holding one JSON object, after
   at most a few sentences of explanation. Never two blocks.
3. The four kinds and every change op, with fields (section 4.4's tables), and one example each.
4. Never put a key, token, password or secret in any field. For keys use
   `{"op":"open","screen":"providers","target":"<slug>"}`; for sign-in, `screen: "mcp"`; for skill
   or plugin installs, `screen: "capabilities"`; for connectors, `screen: "connectors"`. Cron jobs
   are created with local delivery only; for any other delivery use `screen: "cron"`.
5. Use only setting keys listed or returned by `need`; ask with `need` before guessing a key.
6. Prefer the fewest changes that satisfy the request; never change unrelated settings.
7. If the request is ambiguous, ask one `clarify` question, or reply `answer`.
8. If the request is about another profile, reply `cannot` and name the profile.

The builder writes the final text; test 10 checks it starts the brief, contains every op name and
is at most `SKILL_MAX_BYTES`.

## 5. Exact requests and replies

Placeholders in angle brackets. All frames are JSON-RPC 2.0 over the canonical WebSocket.

Create (the key set is exact; `model` and `provider` appear only together and only when known):

```json
{"jsonrpc":"2.0","id":<n>,"method":"session.create","params":{
 "request_id":"<uuid>","toolsets":["clarify","no_mcp"],"hidden":true,"ignore_rules":true,
 "max_turns":8,"provider":"ollama-cloud","model":"minimax-m3.1-flash"}}
```

Never sent on create: `title` (H3), `yolo`, `api_key`, `base_url`, `skills` (H11), `safe_mode`,
`ignore_user_config`, `cwd_explicit`, `follow_profile_config`, `profile`, `client_env`, `editor`.
There is no fallback create (D12). A refusal (H12a) looks like:

```json
{"jsonrpc":"2.0","id":<n>,"error":{"code":4001,"message":"invalid_params",
 "data":{"reason":"invalid_params","field":"toolsets","detail":"not available on this surface: clarify"}}}
```

The service maps it to `CreateRefused { field: data.field, detail: data.detail, message }`; the
state shows T26 when `field == Some("toolsets")`, else T22 with `detail` or `message`.

Reply (abridged): `{"session_id":"<sid>","stored_session_id":"<sid>","subscription_id":"<sub>",
"execution_generation":0,"running":false,"info":{"tools":{"clarify":["clarify"]},
"enabled_toolsets":["clarify"],"yolo":false,"model":"minimax-m3.1-flash","provider":"ollama-cloud",
"profile_name":"fixture",…},…}`.

Submit (exact key set; never `unattended`, `api_text`, `finite`, `queued`, `model_override`):

```json
{"jsonrpc":"2.0","id":<n>,"method":"prompt.submit","params":{"session_id":"<sid>","text":"<brief>","submission_id":"<uuid>"}}
```

Clarify answer: `{"session_id","execution_generation","prompt_id","answer"}` built by `P1-09`.
Interrupt: `{"session_id":"<sid>","execution_generation":<g>}`. Detach:
`{"session_id":"<sid>","subscription_id":"<sub>","end_reason":"configure_closed"}`.

Events read (by `session_id` of the configuration session): `message.start`, `message.delta`
(`payload.text`), `message.complete` (`payload.text`, `payload.status`, `payload.error`,
`payload.failure_reason`), `tool.generating` (`payload.name`), `tool.start` (`payload.name`),
`clarify.request`, `approval.request`, `error` (`payload.message`). Everything else is passed to
`P1-05`'s reducer and otherwise ignored.
