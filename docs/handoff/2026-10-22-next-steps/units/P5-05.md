# P5-05: Workflow progress view (unit P5-05)

Status: `proposed`. The GitHub issue for this unit is the contract; this document is its reference specification. If they disagree, the issue wins and the disagreement is reported on the issue.

## How to use this document

Read the issue first: it lists the requirements, the tests to write first, the acceptance scenarios and the stop conditions. Come here for depth. Section 2 lists every Hermes fact this unit relies on, with the file and line at Hermes v0.22.4; section 2.1 lists what could not be confirmed there. Sections 3 to 8 define the tree, states, display, controls and request files exactly. Section 9 has the Rust interfaces, section 10 the mock and fixture rules, section 11 the test notes, section 12 the design reasoning. Links to the handoff are relative (for example [../06-workflows.md](../06-workflows.md#the-progress-view)); links to Hermes point at the v0.22.4 tag.

## 1. What this unit delivers

Three pieces, matching the architecture layers ([../05-architecture.md](../05-architecture.md#layers)):

1. `talaria_workflow::progress`: the journal projection (`RecordLine` values become a progress tree), offset tailing over `P5-02`'s reader, the run-control request files, and `progress::live`, the pure live state (tree plus selection, collapse, filter, pending controls, live-event merge, control effects). It never imports a terminal library and never calls Hermes. The live state lives here, not in `talaria-core`: `P0-02` declares `talaria-core` on `hermes-contract` only, while the journal and engine types it needs already live in this crate; no new core edge is created.
2. `talaria_app::workflow_progress` plus `talaria_tui::workflow_view`: the service that tails one run folder, attaches under section 6's policy and executes effects over the gateway client; and the alternate-screen overlay that draws the tree, the steer input and confirmations. The run picker renders `P5-06`'s `runner::discover_runs` rows; this unit builds no discovery of its own.

What it deliberately does not do:

| Concern | Owner |
|---|---|
| Script engine, engine events, call identity | `P5-01` |
| Journal records, writer, resume, attempts | `P5-02` |
| Hermes session creation, prompts, receipts, schemas | `P5-03` |
| Staffing, scheduling, budgets, money pricing | `P5-04` |
| `talaria workflow run/resume/list/stop`, runner processes, the default runs directory | `P5-06` |
| Subagent tracking, dock, tails (reused, not rebuilt) | `P3-04` |
| Answering approvals and questions | `P1-09` over `P3-01` |

## 2. Hermes facts (verified at v0.22.4)

Contract file below is `apps/shared/src/gateway-contract.openrpc.json` and generated types are `apps/shared/src/gateway-contract.generated.ts`, both at Hermes v0.22.4. Canonical methods are the `x-canonical-methods` entries; the view uses canonical shapes wherever one exists (the generated client from `P0-03` already does).

- H1. Canonical steer: `session.steer` takes `CanonicalCorrectionParams` (contract line 8545): required `session_id` (string), `execution_generation` (integer), `text` (string); optional `profile`. Result `CanonicalCorrectionResult` is `CanonicalCorrectionAck` (`tui_gateway/contracts/canonical_sessions.py` line 269: `status` of `queued`, `redirected`, `rejected`, plus `text`, `execution_generation`, `authority_epoch`, and `delivered: false` only on a rejection no agent saw) or `{voice_stopped: true}` (a bare stop phrase ending a local voice chat). `gateway/session_busy_controls.py` (lines 198 to 217) returns `queued` both when latching text before an agent exists and after the agent accepts it; there is no delivered acknowledgement, and a plain `rejected` may follow delivery, so clients never resend it. Hence the issue REQ-1 mapping. The view never sends `profile` (one connection per profile, as in `P5-03`).
- H2. Canonical stop: `session.interrupt` takes `CanonicalControlParams` (contract line 8467): required `session_id`, `execution_generation`; optional `profile`. Result `CanonicalSessionHandle` (required `ref`, `instance_id`, `authority_epoch`, `revision`, `execution_generation`, and `execution_state` of `idle`, `running`, `waiting`, `unknown`, `terminal`). The legacy `SessionInterruptParams` / `SessionInterruptResult` pair also exists in `components.schemas`; the canonical pair wins and the legacy pair is never sent.
- H3. Cancel a queued admission: canonical `prompt.cancel` takes `PromptCancelParams` (contract line 31719): required `session_id`, `admission_id`. Result is `AdmissionStatus` (contract line 4912): required `admission_id`, `ref`, `sequence`, `status` of `queued`, `started`, `unknown`, `terminal`, `outcome`, `authority_epoch`, `execution_generation`. Its summary in `x-canonical-methods` reads: retire a still-queued admission; a started one is unaffected.
- H4. Hand a queued admission to the running turn: canonical `prompt.steer_queued` takes `CanonicalSteerQueuedParams` (contract line 11194): required `session_id`, `admission_id`. The view does not use it: steering a workflow agent steers the running turn directly (H1), and a queued workflow agent has no admission of its own to hand over yet (it is refused, issue REQ-14). Named here so a builder does not reach for it by mistake.
- H5. Attach: `session.resume` takes a stored `session_id` (or an exact title); the reply's `session_id` is the runtime id, and attaching subscribes the caller (see `P5-02` REQ-5 and `P1-03`). `close_on_disconnect` defaults to false, so closing the viewer leaves the turn running. The view sends only `{session_id}`.
- H6. Subagent steer: `subagent.steer {session_id, subagent_id, text}` returns `{status, subagent_id, text}` with `status` of `queued` or `rejected` (generated types line 309). Queued text joins the child's next tool result; a child that finishes first reports it as missed, so the view words success as queued, never delivered (`P3-04` REQ-6).
- H7. Subagent stop: `subagent.interrupt {session_id, subagent_id}` returns `{found, subagent_id}` (generated types line 2375). Hermes's own terminal UI calls it exactly this way (`ui-tui/src/components/agentsOverlay.tsx` line 767). A queued (not yet registered) child answers `found: false`.
- H8. Subagent events share one payload, `SubagentEventPayload` (generated types line 5829): required `goal`, `task_count`, `task_index`; optional `subagent_id` (`sa-<task_index>-<8 hex>`), `parent_id`, `child_session_id`, `delegation_id`, `depth`, `model`, `tool_count`, `toolsets`, token counters, `files_read`, `files_written`, `output_tail`, `tool_name`, `tool_preview`, `text`, `status`, `summary`, `duration_seconds`. Statuses are `queued`, `running`, `completed`, `failed`, `error`, `timeout`, `interrupted` (line 2359). Event meanings (`P3-04` REQ-1): `spawn_requested` accepted, `start` running, `progress` batched tool names, `thinking` reasoning chunk, `tool` one tool call, `complete` finished. Full field caps are `P3-04` section H3; this unit reuses its row rules unchanged.
- H9. Turn events: `message.complete` payload (generated types line 5618) carries `text`, `usage`, `status` (`complete`, `error`, `interrupted`), `reasoning`, `warning`, `error` and billing fields; a turn's outcome comes from its `status`, never from an event's arrival (architecture protocol rules). `tool.start` (line 5717: `tool_id`, `name`, `context`, `args`, `args_text`, `preview`, `labels`) and `tool.complete` (`tool_id`, `name`, `args`, `duration_s`, `result`, `summary`, `result_text`, `inline_diff`) name the agent's current and last tool calls.
- H10. Usage scopes differ and must never add. (a) Receipt usage is per-turn: `gateway/run_turn_runner.py` captures a before-and-after difference (`input_tokens`, `output_tokens`, `total_tokens` for this turn only), and `P5-03` copies it into the journal's `turn_settled.usage` (its REQ-16), plus `session_cost: {estimated_cost_usd, cost_status, cost_source}` from the stored result when present — a session running total, not a turn amount (`agent/turn_usage.py`: each turn adds its amount only when known and always sets the status; statuses `actual`, `estimated`, `included` (a known zero) and `unknown` (0.0 then means not known)). (b) Live usage is session-cumulative: `gateway/session_usage.py` (line 1) projects session counters as `session.usage` (generated types line 5673), and `gateway/session_settlement_recovery.py` (lines 86 to 90) copies the same cumulative counters into `message.complete.usage` (the `Usage` type, line 558, whose optional `cost_usd` and `cost_status` at line 580 actual frames need not populate). The view therefore displays live money never and settled money from (a) under issue REQ-11 as a display policy, not because the contract forbids money fields.
- H11. Pending prompts (compatibility only): `approval.request` and `clarify.request` are client-local synthetic events in `apps/shared/src/gateway-events.ts` (lines 37 and 39), keyed by (`session_id`, `prompt_id`, `execution_generation`). For workflow runs they do not occur in v0.7.0: `P5-03` submits every workflow prompt with `finite: true` (its REQ-7 and REQ-8), under which a dangerous command is denied at once (`tools/approval_context.py` lines 203 to 212: a finite turn is single-query) and a clarifying question gets the headless undelivered answer (`gateway/session_finite.py` lines 22 to 24); the manifest records `approval_policy` mode `finite-only` (`P5-06` REQ-9a). The view keeps the waiting badge for these events as generic coverage and shows finite denials in the agent's tail and settled outcome; it never submits with `finite: false`.
- H12. Replay gap: `session.replay_gap` (gateway-events line 49) means a reconnect replay could not cover the gap; consumers re-resume the session for a snapshot. The view answers it by re-attaching (H5) and, for subagents, by the refresh `P3-04` already defines (`subagent.list`, generated types line 2340 for its result; `subagent.tail` result line 2380).
- H13. Delegation pause is not run pause. `delegation.pause {paused}` (Hermes UI call at agentsOverlay line 788; params at generated types line 302) blocks new `delegate_task` spawns gateway-wide and needs `session:control`. It must never be used to pause a workflow run: it would pause every session's spawning on the gateway. Run pause is the request file in section 7.
- H14. Hermes's terminal UI is the presentation reference: its agents overlay (`ui-tui/src/components/agentsOverlay.tsx`) builds a subagent tree with list, detail, steer and tail modes (mode state near line 662), interrupts with H7, and pauses spawning with H13. Talaria's fleet and subagent views (`P3-02`, `P3-04`) already parallel it; this view parallels it for workflow runs and adds the journal as the durable source the Hermes UI lacks (it has no run journal).

### 2.1 Facts that could not be confirmed at v0.22.4

- U1. Whether `session.steer` (H1) accepts a steer for a hidden `source: "tool"` workflow session mid-turn exactly as for an interactive session. The contract places no source restriction on the call, but no Hermes test at v0.22.4 steers a tool session. The view treats a refusal as a normal control outcome (issue REQ-20), and the live test (issue test 18) is the first proof; until it passes, steer on workflow agents is unverified live. Marked in the issue at REQ-1.
- U2. What a `voice_stopped` result (H1) means when the session has no voice chat. The view shows it as an error and never as success (issue REQ-1); verify at the pinned commit before relying on either reading.
- U3. Whether actual canonical `session.usage` and `message.complete` frames populate the optional `cost_usd` on this operator's providers (H10b). The view ignores live money either way (settled `session_cost` is its money source), so the answer changes no behaviour; it is recorded only so a later unit does not re-derive it.
- U4. The runner-side effect of pause, stop-run and restart requests (section 7) is Talaria runner behaviour: `P5-06` REQ-14 and REQ-15 already specify it against these files, but no merged runner exists yet. This unit proves the files, the states and the timeout with a harness consumer implementing exactly that contract; the live effect is proven only when `P5-06` merges (the issue's merge gate).

## 3. The tree

### 3.1 Nodes

```text
RunNode      name, started_at_ms, state, counts, settled tokens, money?, log lines (<= 50)
  ChildNode    workflow_path (one per nested workflow instance), meta name
    PhaseNode  title (first-seen order), counts
      AgentNode  key, call_id, label, phase, launch (model, provider, effort), attempt,
                 session ids, admission, state, usage, last tool, tail (<= 4 lines), subagents
        SubRow   P3-04's SubagentRow (keyed by subagent_id, nested by parent_id, then depth)
```

Build order (input is `&[RecordLine]`; variant fields through `line.record`, time through `line.at_ms`, order evidence through `line.seq`): `run_started` and the manifest open the run; `run_resumed` starts a new execution (section 4); each `engine` record applies its `EngineEvent` (`P5-01` section 9); `call_intent` binds label, phase, `workflow_path` and launch; `session_bound` binds the session; `turn_intent`, `turn_admitted` (status `queued`, `started`, `unknown`, `terminal`) and `turn_settled` advance the turn; `call_attention` (causes `unknown`, `lost`, `identity_conflict`) and `call_resolved` park and unpark; `call_finished` finishes the agent. An `AgentFinished` of `aborted` or `abandoned` with no `call_finished` marks the agent `ended` (section 4); a later `call_finished` (a resume settling the work) supersedes it. A new attempt reuses the node and updates attempt, session and state.

### 3.2 Identity and ordering

Agents are keyed by journal `key` (never by label, which scripts may repeat, and never by session id, which changes per attempt). Phases keep first-seen order: the order of the first `Phase` event or agent naming them; phases named in the script header (`meta.phases`, carried on `Started`) with no agents yet still show (issue REQ-22). Agents inside a phase keep `AgentStarted` order. Child instances keep `ChildStarted` order. Sorting is never alphabetical: resume must show the same tree the live run showed.

### 3.3 Tailing

`progress::tail` owns the offset. It starts at 0, applies whole `RecordLine` values in file order, and remembers the offset the reader returned. The reader drops a torn tail itself (`P5-02` section 4.1); the tail holds no partial state across reads. Polling is 500 milliseconds (the only trigger; no file-change API is consumed); an empty read costs one stat and no frame.

### 3.4 Blob-backed prompt text

`P5-02` stores a `turn_intent.text` over 256 KiB as `text_ref {sha256, bytes}` naming `blobs/<sha256>` and exposes no blob-loading function to readers. This unit therefore owns one small reader, `progress::blobs::load_text(run_dir, &BlobRef) -> Result<String, BlobError>`: read the file, verify its byte length and SHA-256 against the reference, decode as UTF-8. Any failure (missing, wrong size, wrong hash, invalid UTF-8) yields the detail block's `(prompt unavailable — journal blob missing)` line and one view warning, never a tree error. Inline text needs no load. Only the selected agent's current attempt is ever loaded.

## 4. States

Agent state derivation (issue REQ-9), evaluated for the latest attempt in this order; the first match wins:

| # | State | When (journal and live inputs) |
|---|---|---|
| 1 | `done` | `call_finished` outcome `completed` |
| 2 | `failed` | `call_finished` outcome `failed` (including an interrupted turn settled as failed) |
| 3 | `skipped` | `call_finished` outcome `skipped` |
| 4 | `unknown` | latest record `call_attention` with no later `call_resolved`, any cause (parked; needs-you) |
| 5 | `ended` | `AgentFinished` `aborted` or `abandoned` and no `call_finished` for the key |
| 6 | `waiting` | an outstanding approval or clarify request for its session (H11, compatibility only) |
| 7 | `stopping` | a stop or cancel control was sent and the turn has not settled (section 6) |
| 8 | `running` | `turn_admitted` with status `started`, or live turn activity after `session_bound` |
| 9 | `queued` | `AgentStarted` seen (or `call_intent` written) with nothing above true; a scheduler wait reason may annotate this row |

Run state is per execution: `run_started` opens execution 0; each `run_resumed` closes the previous execution (its `run_finished` outcome, if any, is kept as a `previous execution: <outcome>` line) and clears terminal and pending-control display; only a `run_finished` after the latest boundary terminates the current execution (`completed`, `failed`, `aborted`). Control overlays (`pausing`, `paused`, `stopping`, section 7) and the suffixes `resuming` (pause file removed, next `call_intent` not yet seen) and `no live runner detected` (60 seconds unchanged, no current `run_finished`) are display suffixes, not states. The run line is exactly `<name> · <state>[ · pausing|paused|stopping|resuming][ · no live runner detected] · agents <done>/<total>[ · <count> <name> ...] · <tokens> tokens · <money>`. Counts are `total`, `done`, `running` (including `stopping`), `needs_you` (`unknown` plus `waiting`), `failed`, `queued`, `skipped`, `ended`, printed when non-zero after `agents`. Subagents never count as agents.

## 5. Display

Row layout (one line, cut to terminal width, in this order): glyph (`✓` done, `✗` failed, `◐` running, `●` waiting or unknown, `○` queued, `—` skipped, `◌` stopping, `?` ended), label, `model on provider` (provider omitted when the launch has none), state text (with `attempt N` when N is above 0, the parked cause for `unknown`, `ended without a journal outcome` for `ended`, and any scheduler wait reason for `queued`), elapsed (running) or duration (finished), tokens by the format below, money (`$0.40`; `$0.00` only for a known zero under H10a; else `cost unknown`), then the last tool (`name preview`) or last streamed line, sanitised. Token format: under 1,000 the exact number; otherwise `(n * 10 + 500) / 1000` as an integer one-decimal `k` value (1,050 is `1.1k`, 1,049 is `1.0k`). Usage fields read: settled per-admission `total_tokens`, else `input_tokens + output_tokens`; live cumulative `total`, else `prompt + completion`, else `input + output`; money only from settled `session_cost` (section 2, H10a), displayed per agent as the last settled amount across attempts (the issue wording wins over any current-attempt reading) and summed for the run with `<n> unpriced` when any agent is unknown. The detail block adds: prompt first line (section 3.4), stored and runtime session ids, attempt and turn numbers, admission status and ids, settled and live usage as above, and the tail (newest four of streamed segments cut to 200 characters, interim commentary, subagent tails).

Elapsed time uses journal `at_ms` for finished spans and the view's clock only for the running span's end; durations never come from event arrival order. Everything untrusted is rendered literally through `P1-06`'s sanitiser.

## 6. Controls

Effects are data; `progress::live` emits them, `talaria_app` executes them, outcomes return as inputs. One control per row at a time; a second key press while one is in flight says `still working on it`. A control that times out (issue REQ-20) clears its pending state back to the derived state, shows its message once, and stays disabled for that row until a journal line with a higher `seq` arrives.

| Key | Row | Effect(s) | Success shown | Refusals (nothing sent) |
|---|---|---|---|---|
| `enter` | agent | attach (H5), then switch foreground | the session itself | no session bound yet; attach `not_found`: `session gone — it may have been pruned` |
| `enter` | subagent | open `child_session_id` (H5), else tail on the parent | session or tail | no child session and no tail available yet |
| `s` | agent | `session.steer` (H1) with the highest held generation | `steer queued for its next step` (or the `rejected` text) | queued, finished, parked, `ended`, no generation after refresh, disconnected |
| `s` | subagent | `subagent.steer` (H6) | `steer queued for its next step` (or Hermes `rejected`) | finished subagent; disconnected |
| `x` | agent | `session.interrupt` (H2) running; `prompt.cancel` (H3) queued | `stopping`, then the settled state | finished, `ended`; queued without an admission id |
| `x` | subagent | `subagent.interrupt` (H7) | `stopping`, then `interrupted` on `subagent.complete` | `found: false`: `already finished or not started` |
| `r` | agent | confirm; running: H2 plus restart file; failed, stopped or `ended`: restart file only | `restart requested — runs again on resume` until the resume's next attempt | done or skipped (issue REQ-17 text) |
| `p` | run | write or remove `pause.json` | `pausing`, `paused`, `resuming` (section 7) | run already finished |
| `shift+x` | run | confirm, write `stop.json` | `stopping`, then `run_finished` | run already finished |

Generation refresh (issue REQ-16): the held generation per session is the highest of the journal `turn_admitted.execution_generation`, any canonical handle, and any live envelope `execution_generation` (values compare by size; a higher envelope value replaces the journal's). On `stale_generation` (or no held value) the service attaches once (H5), takes the handle's generation, and retries once; a second failure marks the row controls-disabled until that session next speaks. Attach policy: on open and on reconnect the service attaches only to agents whose state is `running`, `waiting` or `stopping`. A dropped connection refuses every gateway control with the journal-only reason; request files still write.

Restart never interrupts twice: if the turn settles between the key press and the interrupt, the interrupt result's `execution_state` is already terminal and the view writes the restart file without claiming a stop happened.

## 7. Run-control request files

Layout, inside the run folder beside `resolutions/` (`P5-02`'s operator-answer folder, a different concern that this unit never touches):

```text
<run folder>/control/pause.json            {"v":1,"kind":"pause","at_ms":...}
<run folder>/control/stop.json             {"v":1,"kind":"stop","at_ms":...}
<run folder>/control/restart-<key>.json    {"v":1,"kind":"restart","key":"<32 hex>","at_ms":...}
```

Publication is atomic and never replaces: write the exact bytes (issue REQ-18) to a temporary file in `control/`, sync it, publish by `hard_link` to the final name (the `P5-02` blob pattern; an existing name fails with `AlreadyExists`, the temporary file is removed, and the caller reports `already requested` with the winning bytes preserved), then sync the containing folder. A check-then-rename implementation is forbidden (it races a second viewer). Consumption is `P5-06` REQ-15 as written there (poll every 250 milliseconds): `pause.json` is a held level — its presence pauses the gate, the runner never deletes it, and whoever resumes (any viewer, or `talaria workflow resume`) deletes it; the effect is the journal showing no new `call_intent` while it is present, which is why `paused` needs the one-second proof of issue REQ-19 and never follows from zero running agents. `stop.json` is deleted by the runner as the stop path completes (`P5-06` REQ-15 deletes the consumed files at the end of the path); completion is the journal's `run_finished` (aborted). `restart-<key>.json` is kept until the next resume, deleted there (after `P5-06` REQ-12 reads pending keys) before the journal opens; the key re-runs because its latest attempt is failed or interrupted-eligible, and a completed key is never restarted. This unit's test harness implements exactly this contract; it does not invent a second one. The 10-second no-runner warning covers `pause.json` and `stop.json` only; a restart request pending across a live run is normal and never warns. Every viewer re-reads `control/` on each poll, so concurrent viewers converge on the same pending set; a pause left by a closed viewer is resumed by any later viewer's `p`, and request files left by a dead runner stay visible on reopen until a runner or the operator removes them.

## 8. Picker, empty and error states

The picker is `P5-06`'s discovery, rendered: `talaria_workflow::runner::discover_runs(runs_dir) -> Vec<RunSummary>` (statuses `running`, `parked`, `completed`, `failed`, `aborted`, `interrupted`, `unreadable`; unreadable folders list with their one warning). The view renders each summary's fields unchanged and adds no scan, cache or liveness probe of its own. A `null` `money_spent_usd` (no known cost, or any settled turn's cost unknown) shows `cost unknown`, never `$0.00`, the same wording as the tree rows (section 5; issue settled decision 4). `/workflows` with no argument opens the picker over `runner::runs_dir` (its resolution order is `P5-06` REQ-5; not restated or reimplemented here); with a run-folder or run-id argument it opens that run directly, which is how tests and `progress_dump` drive it and how the view works before `P5-06` merges. Inside one run, control pause is a run-line suffix and never changes the picker's `parked` word, which means parked calls.

Error screens are exactly two: journal corrupt (line, reason, close only) and folder unreadable (reason, close only). Everything else is a banner or a row state (issue REQ-21, REQ-22). The picker and the tree show run folder names (the run id), never absolute paths, in line with the no-absolute-path evidence rule.

## 12. Design reasoning

Why the journal, not the gateway, is the tree's source: the runner outlives the viewer (workflows decision 3), sessions of finished agents may be pruned, and a resumed run must show the same tree (sections 3.2, 4). The gateway cannot answer "what did this run do"; the journal can, in one pass, within the open budget `P5-02` already proves (test 17 reuses its scale).

Why request files for run controls: the view must work detached, the journal is single-writer (the runner), and `P5-02` already proves the folder-as-channel pattern with `resolutions/`. `P5-06` REQ-14 and REQ-15 adopted exactly these files (its command line writes them with this serialisation), so no second protocol exists; the remaining cost is only the merge order, stated as the issue's gate. Why the picker is not this unit's: two discoveries would disagree about which runs exist and what state they are in (`P5-06` REQ-6), so the view renders the runner's summaries unchanged and keeps only the single-run projection as its own. Why the live state is not in `talaria-core`: `P0-02`'s declared edges give that crate `hermes-contract` alone, and every type the merge needs (journal lines, engine events, subagent rows through their session key) is reachable inside `talaria-workflow` without a new forbidden path.

Why steering uses the running turn (H1) and not a queued follow-up: a workflow agent's result is read from its prompt's receipt (`P5-03`); a second queued prompt would run after the turn and change what the receipt holds. Steering the live turn changes the work without changing the accounting. Opening never submits for the same reason.

Revisit conditions: if Hermes grows a native workflow-run API (workflows design, later item 2), this view should render from its events and the request files should retire; if `P5-06` gives the runner a control socket, section 7 moves to it and the files remain as the detached fallback. Either change is a new unit, not an edit here.
