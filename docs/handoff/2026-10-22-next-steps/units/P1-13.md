## 1. What this unit is for, in plain terms

Herdr is a terminal multiplexer for coding agents, comparable to tmux. It is the operator's daily environment. Its `herdr` command line can create a tab, type into a pane, read what the pane shows, and close the tab. That is enough to drive a terminal program the way a person would.

This unit builds a short program that does exactly that to the real `talaria` binary, started with `--no-ensure` so that the binary never starts a gateway. It starts `talaria` in a Herdr pane against the running Hermes gateway on a free model, asks a few things, checks what appears on screen, and closes the tab. The checks are the five behaviours the first usable binary must have: a plain answer, an approval, an interrupt, quit and resume.

It exists because unit tests and recorded-frame replays can all pass while the binary is broken on a real terminal. It is also the machine check that the Phase 1 acceptance issue runs on each release candidate before the operator spends a day coding with it. It must stay small. The Python client spent 44 percent of its added lines on acceptance records and process documents ([02-current-state.md](../02-current-state.md#why-it-ended-up-here), item 4); this unit writes none: no receipts, no evidence bundles, no schema, no signatures. The output is one line per step, one result line and, on failure, the pane text.

"Unattended" in the title means "runs without a person watching". It has nothing to do with the `unattended` field of Hermes's `prompt.submit`, which makes Hermes approve dangerous commands by itself. This unit never sends that field and a test proves the script never types the word.

## 3. Shape of the code

One new workspace member, `tools/smoke` (package `smoke`, `default-run = "smoke"`, a library with a thin binary). It uses blocking calls and threads, not an async runtime: every wait is a poll loop. It depends on no `hermes-*` or `talaria-*` crate; that independence is the point of a black-box check. Workspace rules come from unit P0-02: the root `Cargo.toml` lists `tools/smoke` in `members`; every external crate is pinned with `=` in `[workspace.dependencies]` and used as `<dep>.workspace = true`; the manifest has `[lints] workspace = true` and inherits `[workspace.package]`. Suggested crates: `clap`, `serde_json`, `regex`, `thiserror`, `rand` (tokens and run id), `signal-hook` (safe flag based handling of SIGINT and SIGTERM; the repository forbids `unsafe`); dev dependencies `proptest`, `tempfile`. `run_smoke` creates the scratch project under `cfg.temp_root`, creates the tab through `term`, runs the steps and returns the report; `seed` makes tokens and the run id repeatable in tests. The `stop` flag is the one the signal handlers set. `run_smoke` runs the steps inside `std::panic::catch_unwind` (do not set `panic = "abort"` in any profile): a panic becomes `FAIL <step in progress> (internal error: <message>)` (message scrubbed, cut to 200 characters), the guard closes the tab, and `run_smoke` returns normally. `main` builds `HerdrCli` and `SystemClock`, does the preflight, prints, and returns the exit code.

## 4. Flow, step by step

Defaults for waits are in section 6. All waits are poll loops at 250 ms using `Clock`; every loop also checks the stop flag and the run deadline. Reads that decide anything use the `visible` source; searches for text that may have scrolled away use `recent-unwrapped --lines 3000` (the constant `RECENT_LINES`; the interrupt step can print hundreds of counting lines between two tokens, and the most scrollback Herdr will return is **verify**).

### 4.1 Preflight (in `main`; exit 2, nothing created, one plain sentence, no result line)

1. `HERDR_ENV` equals `1` and `HERDR_WORKSPACE_ID` is non-empty. Message: "This test must run inside a Herdr pane (HERDR_ENV=1). Start it from a Herdr tab."
2. Option values: `--step-scale` finite and above 0, `--deadline-secs` above 0, `--report-dir` (if given) an existing directory. One sentence each.
3. The login name (from `USER`, then `LOGNAME`; there is no system user lookup) has four or more characters; with neither set the message is "Neither USER nor LOGNAME is set; the smoke test cannot scrub the login name from pane text." The home directory comes from `HOME` (absent: no home needle). Message for a short name: "Your login name is too short to scrub safely from pane text; run the smoke test from an account whose login name has four or more characters."
4. `herdr tab list --workspace <id>` succeeds (proves the CLI and the server answer). The message names the command and the first line of its error.
5. The `talaria` path (flag, then `TALARIA_SMOKE_BIN`, then the default) is made absolute with `canonicalize` against the folder `smoke` was started from, exists, and is an executable file. Message: "No talaria binary at <path>. Run `cargo build -p talaria-cli` or pass --talaria." From here on only the absolute path is used.
6. Both launch lines are under 600 characters: the start line (the longer one, because it carries `--model` and `--provider`) and the resume line. The over-long-line test passes a `--model` of 600 `a` characters. The figure is a conservative choice made by this unit, not a measured Herdr limit (the Herdr skill says only that a line longer than the terminal's line-input limit is rejected on macOS; the exact limit is **verify**).
7. Create the scratch project (7.1) and the tab, print `tab: <id>`, `talaria: <path>` and `herdr: <version>` (scrubbed).

Every FAIL reason printed by a step is the exact text of section 4.10; tests assert it character for character. A failing step ends the run (section 4.8).

### 4.2 Step `startup`

1. Wait for the shell (45 s): the foreground list holds one command line (the shell's) and the visible text is non-blank, on two reads 1 s apart. The text does not have to be unchanged: a themed prompt can redraw (an earlier measurement saw 9 to 19 s before a prompt on a loaded machine, [u14](../research/u14-baseline-timing.md)). If a live run shows this rule failing, record which rule worked in the journal.
2. `run` the line `'<talaria>' --no-ensure --profile <profile> --model <model> --provider <provider>; echo SMOKE_EXIT:$?`. The single quotes protect a path with spaces. `--no-ensure` stops the binary from running `hermes gateway ensure`, so a smoke run never starts a gateway (unit P1-12 REQ-1). The `echo` prints the exit status after `talaria` ends. The echoed command contains `SMOKE_EXIT:$?`, which does not match `SMOKE_EXIT:(\d+)`; only the real output does.
3. Pass when a foreground command line contains the absolute path of the binary (this also holds for a stub script in tests, whose process name would be `sh`) and the visible text has been unchanged for 1 s (30 s limit). Record the time as evidence; do not assert the 200 ms budget (the performance harness owns it).
4. Fail at once if `SMOKE_EXIT:<n>` appears before that: "talaria exited with code <n> before showing its screen". On the 30 s limit fail "startup did not show a stable screen within 30 s".
5. A prompt typed while Talaria is still connecting is held and sent when the session is ready (unit P1-12 REQ-5: "While connecting, typing works. Enter before the session exists holds the prompt"), so a stable screen that appears before the connection completes does not lose the first prompt. If a live run shows a lost prompt, stop and report to the owner of unit P1-12.
6. The script has no BLOCKED outcome. Unit P1-12 draws its first frame before it connects (REQ-4) and exits 1 with a two-line message on a missing gateway, so a gateway or profile problem shows as a startup failure with that message in the pane text, or as a later timeout. The README's "Reading a failure" tells the reader: if the pane text says the gateway or profile is unavailable, the UAT result is BLOCKED (environment), not FAIL. A fixed list of phrases is deliberately not coded: it would be a second place that depends on Talaria wording.

### 4.3 Step `plain-answer`

1. Pick a word from `maple, cobalt, juniper, saffron, tundra, walnut, harbor, quartz` and a number 1000 to 9999, redrawn if the pair equals an earlier token of this run. Token = `word-number` (for example `maple-4821`).
2. Submit (5.1): `Without using any tools, join these two words with a hyphen and reply with only the result: <word> and <number>`.
3. Pass when the token (case-insensitive, whole word) appears in the recent text AND the screen has been unchanged for 3 s. The submitted line contains `<word> and <number>`, not the token, so a match can only be the reply.
4. Fail on timeout with the pane text.

### 4.4 Step `approval`

Precondition (operator): the profile `fixture` sets `approvals.mode: manual`, and no hosted-room policy overrides it (F1 to F3, F13). The same precondition is defined by unit P1-04. With the default `smart` a guardian model may approve the command with no card, and the step skips (below). Note that in `smart` mode a guardian denial with a person present still raises a card with only `once` and `deny` (F3), which this step answers like any other.

1. Make sure `.pytest_cache/` exists in the scratch project (recreate it if missing).
2. Submit: `Run this exact shell command and then tell me its exit code: rm -rf .pytest_cache` (the same text unit P1-04 uses).
3. Poll up to 90 s. Each poll, in this order:
   a. Card visible (5.3): answer `once` (5.4) and go to step 4.
   a2. The numbered `once` and `deny` lines are visible but no line equals the exact command: fail "an approval card for another command is open; the script does not answer it". The script never answers a card whose command it did not ask for.
   b. No card seen, `.pytest_cache` gone, screen unchanged for 3 s: the command ran without asking. **Skip** with exactly `no approval card appeared and the command ran; the profile fixture must set approvals.mode: manual (the default is smart, in which Hermes may approve by itself; a hosted-room policy can also override the mode)`. Never a pass. With `TALARIA_LIVE_REQUIRE=1` the skip becomes `FAIL approval (skipped: <that reason>; TALARIA_LIVE_REQUIRE=1)`.
   c. No card, `.pytest_cache` still present, screen unchanged for 5 s: the model did not run the command. Attempt two with `Use your shell tool now and run exactly this command: rm -rf .pytest_cache`, with its own 90 s window (still inside the 300 s run deadline). Two attempts at most; then **Fail** "the model did not run the command in two attempts", or, when the visible text holds the whole word `withdrawn` or `blocked` (case-insensitive), fail "the approval was withdrawn or blocked" followed by that line. The second reason matters: an earlier Talaria drive (research report u13) saw an approval withdrawn because the client could not answer it, with the command blocked and the folder intact; blaming the model would hide that. A free model can ignore an instruction; that is a failure, not a skip.
   d. If the 90 s window ends with none of a, a2, b or c having happened (the screen keeps changing with no card and no outcome): **Fail** `no approval card and no outcome within 90 s`. For (c), the withdrawn or blocked test looks for the first visible line that holds the whole word `withdrawn` or `blocked` (case-insensitive), trimmed; it is appended to the reason after `: `.
   Branch (c) relies on T6 (a running turn changes the screen about once a second): 5 s of stillness then means the turn has finished. If a live run shows a running turn with a still screen, stop and report.
4. After answering, wait up to 60 s for `.pytest_cache` to be gone AND the screen unchanged for 3 s. Otherwise Fail.
5. The deletion on disk is the ground truth that the approval was applied. The script does not need Talaria's wording for it.

The submit fallback (5.1) never runs while any card words are visible, and nothing but the answer is typed while a card is open, so no stray Enter can land on a card. If the script fails or is stopped while a card is open it does not answer the card. Closing the tab ends the Talaria process; the Hermes session stays up with the question pending until `approvals.timeout` (F4, default 300 s) and then denies it. That is accepted.

### 4.5 Step `interrupt`

1. Submit `Count from 1 to 2000, one number per line, and do not stop early.` (unit P1-04 uses 500; 2000 leaves time to press Esc on a fast model.)
2. Wait up to 60 s until at least 15 counting lines are visible (5.5).
3. Prove the count is live: read the highest number twice, 1 s apart (M0, M1). Fail "the count was not running, or was nearly finished, when Esc was sent" if M1 is not above M0 or M1 is above 1500. This proves the count was running when Esc was sent. It does not by itself prove that Esc stopped it: the proof that Esc worked is the pass rule of step 6 (a screen that settles within 20 s and a final number below 1900). Known limit: a model that stopped counting by itself between M1 and 1900 inside those 20 s would also pass. The pull request records the final number of the first live run.
4. `send_keys esc`. Sleep 400 ms (H11). Send nothing else.
5. Wait up to 20 s for the screen to be unchanged for 3 s. If it never settles, Fail "output kept growing after Esc".
6. Read the highest number M2 from the `visible` text. If no counting line is visible, Fail "no counting output remained after Esc" (if Talaria drops the partial reply on interrupt, stop and report to the owner of unit P1-08; do not loosen the rule). If M2 is below M1, Fail "counting output vanished after Esc". If M2 is 1900 or more, Fail "the count finished before the interrupt; use a slower prompt". Otherwise pass.
7. Follow-up: submit a second token prompt as in 4.3 (token B). Pass when B appears and the screen settles. This shows the interrupt did not leave the session unusable (the interrupt latch must clear on the next turn).

The key is Esc, as unit P1-08 REQ-10 says. A report on the old Talaria 0.6.5 (u13) found that binary interrupted on another key and ignored Ctrl+C; it is not the binary under test. There is no fallback key: if the first live run shows Esc does nothing, stop and report.

### 4.6 Step `quit`

1. Submit `/quit` through `pane run`. Unit P1-12 REQ-15 makes `/quit` the only slash command and defines no command palette, so typing a slash does not open a menu in this version; if a live run shows one, stop and report. If within the 15 s limit there is no `SMOKE_EXIT` and the screen has been unchanged for 3 s, send one `enter`, once (5.1).
2. Wait up to 15 s for `SMOKE_EXIT:(\d+)`. Pass only for `0` and when the foreground list is back to the shell alone. (Unit P1-12 REQ-19 prints a resume hint after a quit when the session has a prompt; it contains no token and is ignored.)
3. Read the first pane's `recent-unwrapped --lines 3000` text: tokens A and B must both still be present (finished output stays in the terminal's scrollback after exit, T5), otherwise Fail "committed output vanished on exit". Record their counts nA and nB.

### 4.7 Step `resume`

1. Split a new pane to the right of the first (H8). The first pane's scrollback still holds the earlier transcript; the fresh pane has an empty scrollback. A right split probably halves the width (an inference; H8 records only the down split), so the resumed Talaria runs in a narrower pane; the script counts tokens in `recent-unwrapped` text, which is not affected by width.
2. Wait for the new pane's shell (as 4.2.1).
3. `run`: `'<talaria>' --no-ensure -c --profile <profile>; echo SMOKE_EXIT:$?`.
4. Wait up to 30 s for a foreground command line that contains the binary path and the screen unchanged for 2 s. Count tokens A and B in `recent-unwrapped --lines 3000`. Each must be at least 1 (zero: history lost) and at most the count of the first pane (nA, nB): more than before means history was printed twice. The upper bound is the first pane's own count, not 1, because a reasoning model may write the joined token in its reasoning as well as in its answer, and unit P1-05 and P1-07 draw reasoning cells that resume restores. The bound still catches a doubled transcript when a token appeared once. Fail with the counts.
5. Submit a third token prompt (C). Pass when C appears at least once and its count is the same on two reads 3 s apart.
6. Submit `/quit`. Require `SMOKE_EXIT:0`.

### 4.8 Output and exit codes

Example of a passing run (times will differ):

```text
tab: w1:t5
talaria: <path>
herdr: herdr 0.9.4
PASS startup 3.1 s
PASS plain-answer 9.4 s
PASS approval 21.0 s
PASS interrupt 17.2 s
PASS quit 1.3 s
PASS resume 18.9 s
SMOKE_RESULT: PASSED (elapsed 71 s)
```

Lines: `PASS <step> <seconds> s`; `SKIP <step> (<reason>)`; `FAIL <step> (<reason>)`; `NOTE submit fallback: sent Enter (step <name>)` for each fallback (printed even on a passing run, and counted in `SmokeReport.fallbacks`, because AC-12 needs the count). The last line is exactly one of `SMOKE_RESULT: PASSED (elapsed <n> s)`, `SMOKE_RESULT: PASSED WITH SKIPS (<steps>)`, `SMOKE_RESULT: FAILED (<step>)`, where `<step>` is the failing step, `interrupted`, or `cleanup`. Exit codes: 0 passed; 1 a step failed, the run was interrupted, or the tab could not be closed; 2 preflight failed (nothing was created, no result line); 3 passed with a skipped step. With `TALARIA_LIVE_REQUIRE=1`, a skipped step is a failure: `FAIL <step> (skipped: <reason>; TALARIA_LIVE_REQUIRE=1)`, `SMOKE_RESULT: FAILED (<step>)`, exit 1 (the convention of units P1-01 and P1-04). A skipped or blocked step is never a pass. If the deadline passes, the step in progress fails with `deadline exceeded in step <name>`.

Rules the lines above leave open:

- A failing step ends the run at once: later steps are not run and print no line. A skipped step does not end the run. The capture and the cleanup follow.
- Step lines show seconds with one decimal place (`PASS startup 3.1 s`). `elapsed` in the result line is whole seconds, rounded down, counted from the first `herdr` call to just before the result line prints; the 300 s check of the issue uses that number. `PASSED WITH SKIPS (<steps>)` lists the skipped step names separated by `, `.
- Which result line prints when several things went wrong: a tab that could not be closed always gives `SMOKE_RESULT: FAILED (cleanup)`, and the earlier lines still print; otherwise a signal gives `FAILED (interrupted)` (the step in progress prints `FAIL <step> (interrupted by a signal)`); otherwise the failing step; otherwise the skip or pass lines. A signal that arrives during the cleanup is ignored, so the cleanup always completes.
- Each `NOTE submit fallback` line is printed right after the step line of the step it happened in, and `SmokeReport.fallbacks` counts them. There is no table.
- A panic inside a step is a failing step with the reason `internal error: <message>` (section 3, `run_smoke`).


### 4.9 Cleanup (always)

Close the tab (this closes both panes) with `TabGuard::close`, confirm it is gone with `tab_exists`, remove the scratch project. Detail in section 7.

## 5. Helper rules

### 5.1 Submitting text to Talaria

`submit(pane, text)` is `Terminal::run(pane, text)` (as the roadmap says: `herdr pane run`). A real keyboard sends Enter as its own key event; `pane run` sends text and Enter in one write, and the paste-burst detector of unit P1-08 (REQ-12: an Enter within 120 ms of the last burst event is a line break) may read that Enter as a newline inside a burst. Rather than guess, the script applies a fallback:

- It applies only to prompts typed into Talaria, and to `/quit` (with its own condition, 4.6). It never applies to the shell launch lines.
- Window: the first 8 s after the submission. If in that window the screen is unchanged for 3 s while no token, card or counting line has appeared and neither the word `once` nor `deny` is visible, send one `enter`, print `NOTE submit fallback: sent Enter (step <name>)` and count it.
- Why it is safe: while a turn runs, something on screen changes about once a second (T6), so stillness means nothing is running; unit P1-08 REQ-9 makes Enter on a blank draft do nothing; and it never runs with card words visible, so Enter never lands on an approval card. Enter on a card would send the highlight, which starts on `once` (T4), but the script does not depend on that here.
- If the fallback fires in the live run, the builder adds the finding to the journal and to the issue for unit P1-08.

Prompts never begin with `/` except `/quit`, and never contain a newline.

### 5.2 Tokens and counting

- `Token::new(rng, used)` returns word and number, redrawn if the pair equals one in `used`; `join()` gives `word-number`; `prompt()` gives the sentence of 4.3.
- `count_token(text, token)`: case-insensitive, whole word (`\b`), counted over the text as read from `recent-unwrapped`. A token is never split by Talaria's own line wrapping in practice because it contains no space; if a line break inside it is ever seen, that is a finding.

### 5.3 Is an approval card visible?

Rule (`screen::approval_card(visible, "rm -rf .pytest_cache")`). First normalise: take the last 25 lines of the `visible` text, remove every box-drawing character (U+2500 to U+257F) from each line, then trim whitespace at both ends. Every test below, including the highlight test, runs on the normalised lines, so a bordered row such as `│ › 1. once │` reads as `› 1. once`.

- A *command line* is a normalised line equal to the command, or equal to the command after removing one leading `$ ` (unit P1-09 REQ-2 draws `$ <command>`). A longer command such as `cd ~ && rm -rf .pytest_cache` is not equal and is never approved by this rule. If several command lines exist, the last one is used.
- The *block* is the command line and the 12 normalised lines after it. The card shows the command first and its choices after it (T4); 12 lines is this unit's choice, wide enough for a description and four choices.
- `Card::Shown` when a command line exists and both whole words `once` and `deny` (case-insensitive) appear inside its block. The words are the labels the gateway sends (F5). A model reply that quotes the command and does not put both words within 12 lines after it is `Absent`.
- `Card::OtherCommand` when numbered `once` and numbered `deny` lines (5.4's pattern) are visible in the 25 lines but no command line exists.
- `Card::Absent` otherwise. A reply that merely mentions "once" does not make a card.

`Shown` also reports the digit of the first `once` line in the block (if any) and whether the first highlighted line of the block holds the whole word `once`. A highlighted line starts with `›`, `>` or `❯` (after the normalisation). This is the only place the script depends on Talaria wording; keep it in `screen.rs` with its tests.

Residual risk, accepted: a model reply that quotes the command and then, within 12 lines, uses both words would read as a card, and the script would type a digit into the composer. The step then ends by failing (the directory is still there, so step 4 of 4.4 times out with the pane text); the on-disk check means it can never pass falsely.

Known unknowns, to check on the first live capture and record in the journal: the real layout (unit P1-09's `› 1. once` is a plan until that unit merges); whether a long command wraps over two rows (this card's command is 22 characters and the live pane is wide, so it should not); whether the gateway's redaction changes the command text (`gateway/run.py:577-587` redacts only credential-shaped text, so it should not, F13).

### 5.4 Answering the card

Find the choice number: the first line in the card block (5.3) that matches `(?i)^\D{0,6}(\d)[.):]?\s+.*\bonce\b`. This accepts `1. once`, `1) once` and `› 1. once` but not `[1] once`. If none is found, Fail with the pane text ("card layout differs from unit P1-09; cannot find the number for 'once'"). Otherwise `send_text` the digit (unit P1-09 REQ-3: a digit sends that choice at once). Wait 1.5 s. If the card is still visible and the highlighted line holds `once`, `send_keys enter` once (Enter sends the highlight, so it is the same choice). If the highlight is on another choice, do not press Enter: Fail with the pane text. If the card is still visible 3 s later, Fail.

### 5.5 Counting lines and the highest number

A counting line holds a number and nothing else: up to six characters that are neither letters nor digits before it (a list marker, a dash), one to four digits, then an optional `.` or `)`. It matches `(?m)^[^\p{L}\d\n]{0,6}(\d{1,4})[.)]?\s*$` and its value is 1 to 2000, so `7.`, `- 12` and `1500` count (`-1500` reads as 1500; that is accepted). The pattern excludes letters, so a reply line `maple-4821` is not a counting line (the earlier pattern, `[^\d\n]{0,6}`, matched it: `maple-` is six non-digits). A reply of a bare `0` (an exit code) is outside 1 to 2000. Lines are taken only from the text after the last line that contains `Count from 1 to 2000` (the echo of the prompt); if the echo has scrolled off the screen, the whole `visible` text is used. The highest number is the maximum value. All counting reads use `visible`, not `recent`, so the number is the one on screen at the moment of the read. The count of at least 15 lines starts the interrupt.

### 5.6 Settled

`settled(term, clock, pane, quiet)` is true when every read of the `visible` text over `quiet` (polling every 250 ms) is identical. It relies on T6: while a turn runs, something on screen changes about once a second. Because a model can think silently for several seconds, `settled` alone never ends a step that waits for a reply; the token must also be present. For the interrupt it is the primary signal, so the 3 s quiet period is longer than the indicator's change interval. If a live run shows a running turn with a still screen for 3 s, stop and report (a T6 failure).

### 5.7 The exit marker

`exit_code(text)` returns the last capture of `SMOKE_EXIT:(\d+)` in the recent text, or none.

|---|---|---|

| `startup` | 30 s | scaled |

Quiet periods, the 400 ms wait, the poll interval and the deadline are never scaled. The README says so.

## 7. Cleanup, signals, scratch project, scrubbing

### 7.1 Scratch project

A new directory under the system temporary directory, mode 0700, named `talaria-smoke-<run id>`, where the run id is eight lowercase letters or digits from the random source. It holds only `.pytest_cache/CACHEDIR.TAG` (any small file); no other file is needed, because no prompt refers to one. It is the tab's working folder, so Talaria's session is created in it and `-c` finds that session (unit P1-12 REQ-9 is folder-strict). Removed at the end, also on failure.

### 7.2 The tab guard

A `TabGuard` value owns the tab id. `close(self)` closes the tab, calls `tab_exists`, and returns `Err(CleanupError)` if the tab remains; `main` turns that into `cleanup: tab <id> was not closed`, the result line `SMOKE_RESULT: FAILED (cleanup)` and exit 1, even when every step passed. `Drop` runs only if `close` was not called (a panic outside the steps, an early return; a panic inside a step is caught by `run_smoke`, section 3): it closes the tab and records any failure in a cell the report reads, because `Drop` cannot return an error. The guard is the only code that closes a tab. SIGINT and SIGTERM set an atomic flag (`signal-hook`) that every poll loop checks; the run then ends with `FAILED (interrupted)` through the normal return path and the guard runs. SIGKILL and power loss cannot be caught: the script prints `tab: <id>` right after creating the tab so a person can close it with `herdr tab close <id>`.

### 7.3 Scrubbing

Anything printed or written (the table, the pane text, the report file, the printed report path) goes through `Scrubber::scrub`. Needles, replaced in one regular-expression pass with the alternatives ordered longest first, and never rescanning the output: the scratch project path and its resolved real path become `<scratch>`; the system temporary directory and its real path (on macOS the resolved form begins with the private prefix) become `<tmp>`; the home directory becomes `<home>`; the login name becomes `<user>`; the Hermes home path, if known from `HERMES_HOME`, becomes `<hermes-home>`. `main` reads `HOME` and `USER` (then `LOGNAME`); there is no system user lookup; tests pass values to `Scrubber::new`.

A needle is skipped when it is shorter than four characters, or when it occurs inside one of the placeholder words (`scratch`, `home`, `user`, `hermes-home`, `tmp`) or contains `<` or `>`. Reason: a single pass that rescanned its own output would turn a login name of `user` into `<<user>>` on a second scrub, and a short name would damage ordinary words. Skipping a needle that sits inside a placeholder word makes `scrub(scrub(x)) == scrub(x)` true, and a login name that is itself an ordinary word such as `user` protects nothing. The preflight (4.1) already refuses logins under four characters, so the skip rule is a second line of defence.

The shell prompt in a Herdr pane often shows the login name, so the scrub matters: pane text that goes into a public issue or pull request comes from this output.

### 7.4 Report on failure

For the failing step the report holds: the step name, what was expected, how long it waited, the Herdr version, the Talaria path (scrubbed), the `visible` text of every pane of the tab, and 200 lines of `recent-unwrapped` text of the pane in use. It is printed to standard output between `----- pane text (step: <name>, pane: first|second) -----` lines and written to `<report dir>/smoke-report.txt` (default: a new directory under the system temporary directory, whose path is printed, scrubbed). The capture happens before the cleanup closes the tab. A passing run writes no report; its fallback count is in the printed `NOTE` lines and the table.

### 8.2 The screen script (one format for `FakeTerminal` and `fake-herdr`)

Steps and the binary-level tests need a terminal whose answers change as text is typed. Both are driven by one JSON document, parsed by `tests/support/script.rs` (copy this section into that file's doc comment before the red run):

```json
{"panes":{"first":{"initial":"$ ","foreground":["-bash"],"rules":[ ... ]},"second":{"initial":"$ ","foreground":["-bash"],"rules":[ ... ]}},
 "fail":[{"call":"pane read","code":"pane_not_found"}]}
```

A rule fires on typed input and changes the pane, step by step in time (time here is the number of reads of that pane since the rule fired):

| Field | Meaning |
|---|---|
| `on` | `run`, `send_text` or `send_keys` |
| `matches` | a regular expression over the typed text (for `send_keys`, the key name); capture groups are `$1`, `$2`; `$0` is the whole text |
| `once` | fire at most once (default true) |
| `after_polls` | the effects below appear only after this many reads of the pane (default 0) |
| `append` | text added to the pane text, with `$n` substituted |
| `churn_polls` | for this many reads after firing, every read appends one new distinct line (a running turn: the screen never settles); then it stops |
| `foreground` | the pane's foreground command lines become this list (`$0` allowed); an empty override means the shell alone |
| `remove_in_cwd` | delete this path under the tab's `--cwd` (what a real `rm` does) |
| `clear` | clear the visible screen first (the old text stays in `recent`) |

Rules are tried in file order; the first rule whose `on` and `matches` fit and which is not used up fires. The pane's `visible` text is the last 44 lines of its text; `recent` and `recent-unwrapped` return all of it; `process-info` answers from `foreground`. A typed key or text that matches no rule is logged and has no effect. `fail` makes the named call return the recorded error. The fake logs every call, one per line, to `$FAKE_HERDR_DIR/log` so tests can assert argument lists and order.

Example rules for the happy path (placeholders):

```json
{"on":"run","matches":"--profile fixture","foreground":["-bash","$0"],"append":"talaria ready\n"},
 {"on":"run","matches":"join these two words.*: (\\w+) and (\\d+)$","churn_polls":2,"after_polls":2,"append":"$1-$2\n"},
 {"on":"run","matches":"rm -rf .pytest_cache$","after_polls":3,"append":"<the captured approval card>\n"},
 {"on":"send_text","matches":"^1$","remove_in_cwd":".pytest_cache","clear":true,"append":"done\n"}
```

`FakeTerminal` is the same machine behind the `Terminal` trait, in process, recording every call as `Call::{Run, SendText, SendKeys, Read, ...}` with the `ManualClock` time. `ManualClock::sleep` advances time without waiting, so a 300 s scenario runs in milliseconds. Each reply screen is built from text a real Talaria could show; the approval screens come from the live run's captured card (record one during the live acceptance as `tests/fixtures/screens/approval_card.txt`, scrubbed). The first draft of that file uses the card layout from the unit P1-09 issue (`Approval needed`, `$ <command>`, `› 1. once`, and the other choices), marked as a placeholder in the file until the live run replaces it. After that capture, re-run the whole offline suite and say so in the pull request: until then the approval tests are green only against the planned layout.

### 8.3 `fake-herdr`

A small Rust binary (`tests/support/fake_herdr.rs`, built as the helper binary `fake-herdr`; tests find it with `env!("CARGO_BIN_EXE_fake-herdr")`). It reads `FAKE_HERDR_DIR` (log, state, the screen script as `script.json`, and the fixtures folder). It answers each call from the table in 8.1: fixed recorded JSON for `tab create` and `pane split`, the tab as present until `tab close` runs (state), `process-info` from the script's `foreground`, `pane read` from the script's text, and a logged no-op or rule firing for `run`, `send-text` and `send-keys`. Exit 1 with the recorded JSON on stderr for `fail` entries. At every `pane run`, before any rule fires, it writes `$FAKE_HERDR_DIR/cwd_at_run.txt`: the first line is the octal permission bits of the tab's `--cwd` folder (for example `700`), then one line per entry under it (paths relative to that folder, sorted). Tests read that file to check the scratch folder while the run is alive; the screen script has no action that reads files. The fake never reads `HERDR_ENV` or `HERDR_WORKSPACE_ID`. It is test support written by the test author; it needs no product code. It is what makes the binary-level tests (`cleanup.rs`, `cli.rs`) possible, because those runs need the process list to change after the launch line, the folder to vanish after an answer, and a reply to carry the random token.

## 9. Edge cases

| Situation | Expected behaviour |
|---|---|
| Not inside Herdr | exit 2, plain message, no tab created, no result line |
| `herdr` binary missing, or `herdr tab list` fails | exit 2, message names the command that failed |
| Talaria path missing or not executable | exit 2 |
| Relative `--talaria` path | made absolute before any use; the pane's working folder is the scratch project, so a relative path would fail there |
| Start or resume launch line over 600 characters | exit 2 (the start line is the longer one) |
| Login name under four characters | exit 2 |
| `--step-scale` zero, negative or not finite; deadline zero; missing report folder | exit 2, one sentence each |
| Shell never becomes ready in 45 s | Fail `startup`, capture, cleanup |
| `talaria` exits during startup | Fail `startup` with the exit code and the pane text |
| `talaria` stays up on an error screen after a gateway problem | startup passes if the screen is stable; the next step times out with the pane text; the README tells the reader to call it BLOCKED (environment) |
| No stable screen in 30 s | Fail `startup`: "startup did not show a stable screen within 30 s" |
| Model answers with different case or trailing punctuation | still a pass (case-insensitive whole word) |
| Model answers `maple 4821` (no hyphen) | no match; the step times out and fails; no automatic retry |
| Prompt echoed twice or wrapped | the token only exists in a reply, so echoes cannot match |
| Card appears while the script is already settling | the card check runs first each poll |
| Card appears but has no number for `once` | Fail with the pane text |
| Card shows a different command | Fail "an approval card for another command is open"; never answered |
| Card for `rm -rf .pytest_cache` but the highlight is on another choice | digit typed; Enter is not pressed; Fail if the card remains |
| `.pytest_cache` deleted and no card (smart or off mode) | Skip the approval step, exit 3 (exit 1 when `TALARIA_LIVE_REQUIRE=1`) |
| Approval withdrawn or the command blocked | Fail "the approval was withdrawn or blocked" |
| Count not growing at the moment of Esc | Fail "the count was not running, or was nearly finished, when Esc was sent" |
| Count finishes before Esc is sent | M1 is above 1500, or M2 is 1900 or more: Fail |
| Esc is ignored | output keeps growing for 20 s: Fail |
| Interrupt leaves no counting line on screen | Fail "no counting output remained after Esc" |
| A reply `maple-4821` or a bare `0` while counting | not a counting line |
| `/quit` leaves the process running | no `SMOKE_EXIT` within 15 s: Fail |
| Resume shows a token zero times, or more often than the first pane did | Fail with the counts |
| A token repeated in a reasoning cell | allowed up to the first pane's count |
| SIGINT or SIGTERM during the run | stop polling, report `FAILED (interrupted)`, close tab, remove scratch, exit 1 |
| Tab will not close | `cleanup: tab <id> was not closed`, `SMOKE_RESULT: FAILED (cleanup)`, exit 1 |
| Deadline passes mid-step | Fail `deadline exceeded in step <name>`, capture, cleanup |
| The pane text contains the login name, home path or temporary path | scrubbed before printing |
| A step fails | the run stops there; later steps print nothing; capture, cleanup, one result line |
| A step fails and the tab then cannot be closed | `FAIL` line, `cleanup: tab <id> was not closed`, `SMOKE_RESULT: FAILED (cleanup)`, exit 1 |
| A panic inside a step | `FAIL <step> (internal error: <message>)`, the tab is closed, exit 1 |
| No card, no outcome, screen still changing at 90 s | Fail `no approval card and no outcome within 90 s` |
| A reply quotes the command and mentions once and deny far from it | no card (block rule, 5.3) |
| Prompt typed while Talaria is still connecting | held and sent by Talaria (unit P1-12 REQ-5) |
| Two smoke runs at once | allowed; labels and scratch directories carry different run ids; the gateway sessions differ because the folders differ |

## 11. Why this shape (decisions and rejected alternatives)

- **Rust crate, not a shell script.** A shell script cannot be tested without a terminal, a clock and a gateway. A crate with a `Terminal` trait and a `Clock` trait runs every failure path in milliseconds. The other tools (`contract-gen`, `record-fixture`, `bench`) are Rust crates too.
- **Black box through Herdr only.** Linking `hermes-client` would let the script call `config.get` or read frames, but then a bug in that code could hide a bug in the binary. The script sees what a person sees.
- **Screen scraping kept to the minimum.** Counting a random token that exists only in the reply, checking a file on disk, reading a process list, reading an exit code and noticing that the screen stopped changing need no Talaria wording. Only the approval card needs wording, and it is isolated.
- **Quit in one pane, resume in another.** Reusing the pane doubles every token because the old transcript is still in the pane's scrollback. The roadmap entry says the script starts `talaria` in one pane; the second pane is a deliberate addition, and the pull request says so.
- **No BLOCKED outcome in the script.** A fourth outcome would need a list of Talaria error phrases (a second place that depends on Talaria wording) and its own exit code. The script reports a startup failure with the pane text and the README tells the reader how to classify it.
- **Rust crate over a shell script** is already recorded here and in the roadmap; add a `DECISIONS.md` entry only for a decision this document does not record.
- **One stateful fake.** A fake `herdr` that prints one canned answer per command cannot support the binary-level tests, which need the process list, the folder and the reply to change as the script types. One screen-script format (8.2) drives both the in-process fake and the executable.
- **No attempt to read Hermes configuration.** Agents never read or change profile configuration. Whether `approvals.mode: manual` is in force is detected by what happens (4.4), as unit P1-04 does when `config.get` cannot answer.
- **Recording the run with `talaria --record`** (unit P1-12 exposes it) and checking the outbound frames for `unattended` was considered and left out: it needs the recorder and replay reader (unit P1-04) and adds a second way to fail. The typed-input test proves the script never types the word, and Talaria's own tests own the frames. It can be added later without changing the steps.
- **Deny path.** A second approval answered `deny` is worth having, but the roadmap names one approval step and a free model needs a second long turn. Left to the Phase 2 acceptance work.

## 13. Stub scripts for the negative scenarios

Scenarios UAT-2 and UAT-4 of the issue need no gateway. They use a stub in place of `talaria`, made in a temporary directory (`STUB="$(mktemp -d)/talaria"`):

```bash
# exits at once with code 7 (UAT-2)
printf '#!/bin/sh\necho "stub: no gateway"\nexit 7\n' > "$STUB" && chmod +x "$STUB"
# stays up and never answers (UAT-4; also handy for a timeout check)
printf '#!/bin/sh\necho ready\nwhile read line; do :; done\n' > "$STUB" && chmod +x "$STUB"
```

The second stub shows up in the pane's foreground list under the shell interpreter's name, which is why the script matches the binary path in the foreground command line and not a process name. UAT-4 first builds the binary (`cargo build -p smoke`) so that pane `A` runs `target/debug/smoke` directly: under `cargo run` the foreground list holds both `cargo` and its child, and the signal must go to the child. It starts the smoke run in a second pane `A` (made with `herdr pane split "$HERDR_PANE_ID" --direction down --no-focus --cwd "$PWD"`, the documented form that takes a pane id; the form `herdr pane split --current` also exists in herdr 0.9.4 but is not used here), types the run line `target/debug/smoke run --talaria '$STUB'` with double quotes outside so the tester's shell expands `$STUB`, waits for `tab: ` with `herdr pane wait-output`, then presses Ctrl+C (and, in a second pass, sends SIGTERM to the foreground process whose `cmdline` starts with the `smoke` binary path, found with `herdr pane process-info --pane A`). With `--step-scale 0.1` the plain-answer limit becomes 6 s, so a stuck run fails within about 15 s of startup; UAT-4 instead stops the run with the signal. Both end with the tab gone.
