## 1. What this unit is, in one paragraph

Talaria writes each finished transcript cell once into the terminal's own scrollback and redraws only a small live region at the bottom of the screen. This unit is the terminal layer that makes that work: start-up and restore, the history writer, the live region, resize handling and an overlay mechanism for full-screen views. It is the only code in Talaria allowed to write escape sequences. It makes no Hermes call; its only contact with Hermes is that text from Hermes (replies, tool output, diffs) passes through it and must be written literally.

## 3. Start-up

### 3.1 The probe

Call order, always: `TerminalGuard::acquire()` (raw mode on), then `probe_startup`, then `terminal_size`, then `InlineTerminal::new`, then `spawn_input`. `probe_startup` takes no guard, so nothing enforces this; its doc comment must state the order, and the demo (section 9) follows it.

`probe_startup(deadline)`:

1. If standard input or output is not a terminal (`std::io::IsTerminal`), return `TerminalError::NotATerminal`, before writing anything.
2. Write `PROBE_QUERY` to standard output and flush. Raw mode must already be on (the guard), or the replies echo:

```text
ESC [ 6 n        cursor position
ESC [ ? u        keyboard enhancement flags (kitty protocol)
ESC [ ? 2026 $ p synchronized output mode report
ESC [ c          primary device attributes (end marker; every terminal answers)
```

3. Call `read_probe_reply(std::io::stdin().as_fd(), deadline)` (steps 3 and 4 are that function, public so test 33 can drive it through a pipe). Loop: `rustix::event::poll(&mut [PollFd::new(&fd, PollFlags::IN)], Some(&remaining))`; when readable, `rustix::io::read(fd, &mut buf)` (a 256-byte stack buffer) and append to an accumulator; feed the accumulator to `parse_probe_reply`. Stop when it returns `true` or the deadline passes. Never read through `std::io::stdin().read()`: `Stdin` is buffered and could keep bytes typed after the marker, which the key reader would then never see. Never read on a helper thread that could outlive the probe.
4. If the deadline passed without the marker, keep reading and discarding until 50 ms pass with no byte, at most 250 ms more. This removes most late replies (slow links, SSH) that would otherwise reach the key reader as keystrokes. A reply later than that still reaches the key reader; record this limitation in the journal entry. End of file (a read of 0 bytes) ends the loop and the drain at once.

`pub fn read_probe_reply(fd: impl std::os::fd::AsFd, deadline: Duration) -> io::Result<ProbeReply>` returns the parsed reply (defaults when no marker came). It never writes.

`parse_probe_reply(bytes) -> (ProbeReply, bool)` is pure:

| Input fragment | Result |
|---|---|
| `ESC [ r ; c R` | `cursor = Some((c - 1, r - 1))` |
| `ESC [ ? n u` | `keyboard_enhancement = true` |
| `ESC [ ? 2026 ; 1 $ y`, `; 2`, `; 3` | `synchronized_output = true` |
| `ESC [ ? 2026 ; 0 $ y`, `; 4` | `synchronized_output = false` |
| `ESC [ ? … c` or `ESC [ … c` | end marker; return `true` |
| Any other bytes | ignored (edge E3) |
| No end marker | `(defaults, false)`: everything unsupported, cursor unknown |

Why one probe and not crossterm's helpers: each helper waits up to 2 s through crossterm's internal reader (C9, C10), and there is no helper for mode 2026. One round trip costs one terminal response time, usually a few milliseconds locally, which keeps the 100 ms launch-to-first-frame budget reachable. The 200 ms deadline only applies to terminals that answer nothing.

### 3.2 Setup and placement

1. `TerminalGuard::acquire()`: check `IsTerminal` on standard input and output (else `NotATerminal`); enable raw mode; create the `RestoreLink`; install a panic hook (section 3.3) that captures a clone of the link and the previous hook.
2. `probe_startup(Duration::from_millis(200))`.
3. `let (cols, rows) = terminal_size()?` (a wrapper over `crossterm::terminal::size`, so callers need not import crossterm).
4. `InlineTerminal::new(stdout, (cols, rows), live_height, probe, guard.link())`: write `ESC [ ? 2004 h` (bracketed paste) and `ESC [ ? 25 l` (hide cursor); push `ESC [ > 1 u` only if `caps.keyboard_enhancement`; never write a mouse mode. Record in the link: active, flags pushed, paste on.
5. Place the viewport with `h = clamp(live_height, 1, max_live_height(rows))`:
   - rows below 3: "too small" (section 4.5); no placement;
   - cursor known, column not 0: write `\r\n`; `top = min(row + 1, rows - 1)`;
   - cursor known, column 0: `top = row`;
   - cursor unknown: move to `(0, rows - 1)`; `top = rows - 1`;
   - then `make_room(h)`: if `top + h > rows`, move to the last row, write `top + h - rows` newlines (`\n`), set `top = rows - h`.
   - Park the cursor at `(0, top + h - 1)` and record `top` in the link.
   - `viewport()` returns `Rect::new(0, top, cols, height)`. While the screen is too small (no placement yet) it returns `Rect::new(0, 0, cols, 0)`. `live_height` 0 is treated as 1.
6. Only now may `spawn_input` start the key thread. It checks `IsTerminal` on standard input (else `None`), then loops: if the stop flag is set, exit; `crossterm::event::poll(25 ms)`; on an event, `crossterm::event::read()` and call `forward(event)`; if `forward` returns `false` or `read` fails, exit. `InputThread::stop` sets the flag and joins; `Drop` does the same; `is_finished` reports whether the loop ended.

Examples for test 10 (24 rows, height 2, three shell rows above the cursor): cursor (5, 3) gives `\r\n` and top 4; (0, 3) gives top 3; (0, 23) gives top 23, then one newline and top 22; unknown gives top 23, then one newline and top 22. In each case the shell rows are still present (on screen or in history).

### 3.3 Restore

`RestoreLink` wraps `Arc<Mutex<RestoreState>>`. `RestoreState` (private): `active` (an `InlineTerminal` exists), `top`, `height`, `overlay_open`, `flags_pushed`, `sync_supported`, `in_sync`, `restored`. `InlineTerminal` updates it whenever one of these changes, holding the lock only to copy or assign fields, never across a write. `RestoreLink::detached()` creates a link with no guard (tests, or a caller without a terminal).

The restore sequence, built from a copy of the state:

1. If `in_sync`: `ESC [ ? 2026 l`.
2. If `overlay_open`: `ESC [ ? 1049 l`.
3. `ESC [ r`.
4. Move to `(0, top)` (`ESC [ top+1 ; 1 H`) and `ESC [ J` (removes the live region; the shell prompt follows the last committed line). Skipped while the screen is too small, since no viewport was placed.
5. `ESC [ ? 2004 l`; `ESC [ < 1 u` if `flags_pushed`; `ESC [ 0 m`; `ESC [ ? 25 h`; flush.

Callers:

- `InlineTerminal::restore()`: lock, return if `restored` or not `active`, set `restored`, unlock, write the sequence to its own writer.
- `RestoreLink::restore_into(w)`: the same, writing to `w`; returns `Ok(true)` when it wrote. The guard's `Drop` calls it with standard output, then leaves raw mode (once).
- The panic hook: `try_lock`. On success (or a poisoned lock, using its inner state), do as `restore_into(stdout)`. If the lock is busy, write only `ESC [ r`, `ESC [ ? 2004 l`, `ESC [ 0 m`, `ESC [ ? 25 h`. Then leave raw mode and call the previous hook.
- The hook is installed once, by `acquire`, and stays installed for the life of the process; the guard's `Drop` does not put the previous hook back (Rust cannot take a hook back out of a closure that owns it). Once `restored` is set, the hook writes nothing and only calls the previous hook. Leaving raw mode a second time is harmless.

`InlineTerminal` alone never touches raw mode, so every test runs without a terminal.

## 4. Committing history

### 4.1 Cells to lines

`commit(cells, render)` maps each cell to lines with `render.lines(cell, width)`, then calls `commit_lines` once for the batch. `PlainCellLines` is deliberately simple; it exists so P1-12 can ship before P1-07 and phase 2 replace parts of it:

Field names below are those of P1-05's unit specification, section 5 (`UserCell`, `AssistantCell` and the rest, each with `pub` fields). If the merged names differ, use the merged ones and say so in the pull request; the renderings stay the same.

| Cell variant (P1-05) | Plain rendering |
|---|---|
| `Cell::User(c)` | `> ` then `c.text`, bold |
| `Cell::Assistant(c)` | `c.text` as is, one line per source line |
| `Cell::Reasoning(c)` | `c.text`, dim |
| `Cell::Tool(c)` | one line: `⏺ ` + `c.name`, then `: ` + `c.summary` when it is `Some`, then ` (failed)`, ` (unfinished)` or ` (unknown)` when `c.status` is `Failed`, `Unfinished` or `Unknown`. `c.diff`, `c.result` and `c.args` are not shown (phase 2 owns tool detail). |
| `Cell::Notice(c)` | `· ` then `c.text`, dim |
| `Cell::Prompt(c)` | one line, dim: `? ` + the first present of `c.command`, `c.question`, `c.description` (else nothing), then ` → ` + the answer for `PromptState::Settled(Settlement::Answered(s))` (`s`) or `answered elsewhere` for `Settled(Settlement::Elsewhere)`. Open or answering prompts are not final, so they never reach `commit`. |

`PlainCellLines` splits cell text on `\n` first (`\r\n` counts as one break; a lone `\r` stays and becomes `␍`); each piece is one `Line`, and each span is then sanitized by `commit_lines`. Only `CellLines` implementations and `PlainTextSection` split on newlines. `commit_lines` never splits: a `\n` inside a span it receives shows as `␊` on one row (test 19 checks this). A blank row after an assistant cell is optional; the architecture's sketch shows none.

Finality: `Cell::is_final()` is defined in P1-05's specification, section 5 (user and notice cells are final when created; assistant and reasoning cells when `sealed`; a tool cell when its status is not `Running`; a prompt cell when `Settled`). P1-05's `SessionState::final_prefix_len()` counts the same leading final cells, so `take_ready` may compare against it; both give the same answer under P1-05's REQ-16.

### 4.2 Sanitize and wrap

`sanitize(text)` works on one line or one span and returns `Cow::Borrowed` when nothing changes. It is the same character table as P1-07's `sanitize_untrusted`, except that P1-07 keeps newline and tab (its input is a whole document):

| Input | Output |
|---|---|
| U+0000 to U+001F except tab | U+2400 plus the code (ESC `␛`, CR `␍`, LF `␊`, BEL `␇`) |
| tab | four spaces |
| U+007F (DEL) | U+2421 `␡` |
| U+0080 to U+009F (C1), U+061C, U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069, U+2028, U+2029, U+E0000 to U+E007F | `‹U+XXXX›` (U+2039, upper-case hex, at least four digits, U+203A) |
| Everything else | unchanged |

Compute Control Pictures as `char::from_u32(0x2400 + code)`; never write an ESC literal in `history.rs` (test 28).

`wrap_lines(lines, width)`: split each line into rows of at most `width` display columns, keeping span styles. Segment with `unicode-segmentation` extended graphemes (`graphemes(true)`) and never split one; a grapheme that does not fit moves to the next row whole; an empty line is one empty row.

The width rule: a grapheme's width is `ratatui::buffer::CellWidth::cell_width` of the grapheme string, the same function ratatui's `Buffer` uses for its cells (ratatui-core 0.1.2 `src/buffer/cell_width.rs`; it calls `unicode-width`'s `UnicodeWidthStr::width` on the whole grapheme, plus a fix for two halfwidth katakana marks). Using ratatui's function keeps the row count and the live region's cells in agreement; never sum per-character widths. Checked on 2026-10-22 with ratatui-core 0.1.2, `unicode-width` 0.2.2 and `unicode-segmentation` 1.13.3: the family emoji U+1F468 U+200D U+1F469 U+200D U+1F467 is one grapheme of width 2; U+2764 U+FE0F is one grapheme of width 2; U+1F642 is 2; `e` U+0301 is 1; U+200B is 0. A width-0 grapheme (a lone zero-width character) stays on the current row and takes no column. The workspace must resolve one `unicode-width` version (issue AC-4). A real terminal can disagree with this table for some emoji; that is a known limit for the journal, not a reason to change the rule.

"Width 0" in the issue means the `width` argument: `wrap_lines(lines, 0)` is treated as `wrap_lines(lines, 1)`, so `abc` gives 3 rows.

Expected counts for test 4 (width 10 unless stated): `""` 1; ten ASCII letters 1; eleven 2; nine letters then `界` 2 (`界` starts row 2); `界界界界界` (10 columns) 1; six `🙂` (12 columns) 2; five family emoji (10 columns) 1; six family emoji 2; six U+2764 U+FE0F 2; ten `e` U+0301 1 (combining marks stay with their letter); `abc` at width 0 gives 3.

### 4.3 The insertion algorithm

State: `cols`, `rows`, `top` (viewport's first row, 0-based), `height`, with `1 <= height <= rows - 2` and `top + height <= rows` whenever `rows >= 3`.

```text
commit_lines(lines):
  rows_out = wrap_lines(sanitize every span of lines, cols)
  n = len(rows_out); if n == 0 return            # zero bytes
  if overlay open or too small: queue rows_out; return
  begin synchronized update if supported
  old_top = top
  room = rows - (top + height)
  if room > 0:                                   # slide the viewport down
      shift = min(n, room)
      set scroll region (top + 1) ; rows         # 1-based: starts AT the viewport's top row
      move to (0, top)                           # on the region's top margin
      write ESC M shift times                    # each scrolls the region down one row
      reset scroll region
      top += shift                               # live content moved with it; bottom rows dropped
  if top >= 2: set scroll region 1 ; top        # rows above the viewport
  move to (0, old_top - 1), or (0, 0) when old_top == 0
  for i, row in rows_out:
      if not (i == 0 and old_top == 0): write "\r\n"
      write ESC [ 0 m, ESC [ K, then the row's spans with their styles
  write ESC [ 0 m; reset scroll region
  park the cursor at (0, top + height - 1)
  end synchronized update if supported
  flush; update top in the RestoreLink
```

Why the region is skipped when `top < 2`: scrolling inside it happens only when `n > shift` or `room == 0`, and both mean the viewport is bottom-anchored, so `top = rows - height >= 2`. When `top < 2`, every row lands in the rows the slide freed, and no scroll occurs.

Two details deserve care:

- After the slide, the rows from `old_top` to `top - 1` are blank (inserted by reverse index); the writes fill them from `old_top` downwards, then scroll the region for the rest. Test 15 checks the slide without any repaint.
- A row exactly `cols` wide leaves the cursor in the "pending wrap" state; the following `\r\n` clears it without an extra blank row. Tests 4 and 13 include such rows.

Rows below the viewport belong to Talaria and are assumed blank (the viewport starts at the shell's cursor). The slide pushes `shift` of them off the bottom of its region; they are discarded, not sent to scrollback.

A write error returns at once. The batch is not retried and the ledger is not rewound (section 4.4).

State after a write error, the same rule for `commit_lines`, `draw_live`, `resize`, the overlay calls and the queue flush:

1. The stored `top`, `height`, `cols` and `rows` keep the values the operation computed before it wrote (for a commit, the `top` after the slide). The terminal cannot know how many bytes arrived, so it assumes the planned state; usually a write error means the terminal is gone.
2. The batch being written is dropped, not re-queued (exactly-once beats completeness: a retry could duplicate lines).
3. The `RestoreLink`'s `in_sync` stays `true` if `ESC [ ? 2026 h` was written and its `l` was not. `overlay_open` is set only after `ESC [ ? 1049 h` or cleared only after `ESC [ ? 1049 l` was written in full.
4. A flag `dirty` is set. The next operation that writes begins with `ESC [ ? 2026 l` (only when `in_sync`), then `ESC [ r`, then `ESC [ 0 m`, clears `dirty` and `in_sync`, and treats the live region as needing a full repaint (move to the top, `ESC [ J`, then repaint at the next `draw_live`).
5. `restore` works as usual: its sequence already ends an open update and resets the region (section 3.3).

Test 13 checks rules 2, 4 and 5 with a `FailingWriter` that can be healed (section 8.1).

### 4.4 The commit ledger

`CommitLedger` stores `next: usize`, the index of the first cell not yet handed out. `take_ready(cells)` returns `cells[next..k]`, where `k` is the first index at or after `next` whose cell is not final (or `cells.len()`), and sets `next = k` before returning, so a failed write never leads to a second commit of the same cells. It assumes P1-05's cell list is append-only and that a final cell never becomes non-final; if P1-05 cannot promise that, stop (issue stop condition 3). `reset()` sets `next = 0`; P1-12 calls it when the foreground session changes and prints a separator first. The ledger lives with the application, one per foreground session; `InlineTerminal` holds none.

### 4.5 Too small

With fewer than three rows, no valid insertion region exists. The terminal is "too small": `max_live_height` is 0, the live region is not drawn (`draw_live` returns `drew: false, bytes: 0`), and `commit_lines` queues rows. On the first resize to three rows or more, the terminal places the viewport at the bottom (`h = clamp(height, 1, max_live_height(rows))`; move to the last row, write `h` newlines, `top = rows - h`), writes the queue once, in order, with the commit algorithm (section 4.3), and marks a full repaint, which the next `draw_live` paints (section 6.1).

## 5. The live region

### 5.1 Layout

`max_live_height(rows) = rows.saturating_sub(2)` (0 below 3 rows).

`LiveView::layout(width, max)`: ask each section for `height(width)`. Let `rest` be the sum of every section except the first.

- Sum at most `max`: stack them top to bottom at full height.
- Sum above `max`, `rest <= max`: every later section gets its full height; the first gets `max - rest`.
- `rest > max`: the first gets 0; walk the sections from the last to the second, giving each `min(its height, remaining)`.

The `Rect`s are relative to the viewport (`x = 0`, `y` from 0), full width, stacked in order. The live height is the sum of their heights, at least 1 (an empty view keeps one blank row). A section given fewer rows than it asked for must render its last rows (`PlainTextSection` does; P1-07's `MarkdownTailSection` does).

Live text wraps; it is never clipped. `PlainTextSection::new(text)` splits `text` on `\n` (as `PlainCellLines` does), sanitizes each line, and keeps the lines. `height(width)` is the number of rows `wrap_lines(lines, width)` gives, and `render` draws those wrapped rows (the last `area.height` of them), one `Buffer::set_line` per row, so ratatui never clips. `"\n\nNEW-3\nNEW-4"` is a four-row section whose first two rows are blank. Example for test 6 at rows 8 (cap 6) with tail 500, card 5, composer 3, status 1: tail 0, card 2, composer 3, status 1.

### 5.2 Drawing

`draw_live(view)`:

1. If an overlay is open or the screen is too small, return `drew: false, bytes: 0`.
2. Compute the new height. If it differs: when shrinking, keep `top`; when growing, `make_room` (newlines at the last row push history and the old live rows up, so `top` moves up). In both cases then move to `(0, top)` and write `ESC [ J`, which clears the whole new viewport and everything below it, and mark a full repaint. The clear matters on growth: the old live rows now sit inside the new viewport, and a repaint that diffs against a blank buffer never writes blank cells, so without the clear old text would survive wherever the new frame is blank (test 31).
3. Render each section into a fresh `Buffer` of the viewport's size at its `Rect`.
4. If no full repaint is pending and the buffer equals the previous one, return `drew: false, bytes: 0`.
5. Otherwise compute `prev.diff(&next)` (for a full repaint, `prev` is a blank buffer of the new size), map each `(x, y, cell)` to `(x, y + top, cell)`, and write them with `CrosstermBackend::draw` over a byte-counting wrapper of the writer. Wrap in a synchronized update when supported. Park the cursor at `(0, top + height - 1)`. Return `drew: true` and the bytes.

A pending full repaint (from a height change, `resize`, `close_overlay`, leaving "too small", or a write error) is painted by the next `draw_live`, which first moves to the top and writes `ESC [ J` if the operation that set it has not already cleared.

`FrameStats.bytes` counts every byte the call wrote: the synchronized-update wrapper (16 bytes when supported), clears, cursor moves, styles, cells and the cursor park. `drew` is `true` when any byte was written.

Because a full repaint diffs against a blank buffer after a clear, blank cells are never written, which keeps trailing spaces out of the terminal (and out of reflow on a width change). Bytes per frame depend only on the cells that changed (tests 22 and 23). Idle frames write nothing (test 21); this is the architecture's "zero frames when nothing changes" budget.

There is no hardware caret. The cursor stays hidden and parked on the viewport's last row, because REQ-15's resize model depends on where the cursor is. P1-08 draws its caret as a styled cell. A later wish to show the hardware cursor (for example for input method editors) must keep the resize model valid and goes to the lead.

## 6. Resize and overlays

### 6.1 Resize, by a stated model

The model, from `alacritty_terminal` 0.26.0 (C7), which says Terminal.app and iTerm2 behave the same. tmux is checked by test 30 and the issue's UAT-2; Herdr and one plain terminal are checked by hand in the operator's terminal matrix run (the issue's UAT-4, which includes a resize):

- **Shrink by `d` rows.** Rows below the cursor are dropped first; then rows from the top go into scrollback until the cursor's row fits.
- **Grow by `g` rows.** Up to `g` rows return from scrollback to the top of the screen, moving everything (and the cursor) down by the number returned; any remaining new rows are blank at the bottom.

Because the cursor is always parked on the viewport's last row, the model gives Talaria the new position without a query:

`resize` takes no `LiveView`, so it never paints the live region. It updates the model, clears from the new top down, and marks a full repaint; the caller's next `draw_live` paints it at the new size. The application calls `draw_live` after every `resize` and every `close_overlay`, and so do the tests and the demo. Between the two calls the live region is blank, which no test inspects.

```text
resize(new_cols, new_rows):
  if (new_cols, new_rows) == (cols, rows): return            # zero bytes
  if too small now:
      cols, rows = new_cols, new_rows
      if rows >= 3: place the viewport at the bottom and write the queue (section 4.5)
      return
  below = rows - (top + height)
  if new_rows < rows: top = top - min(top, (rows - new_rows).saturating_sub(below))
  if new_rows > rows: top = top + (new_rows - rows)           # assumes g rows of scrollback
  cols, rows = new_cols, new_rows
  if rows < 3: too small; return                              # zero bytes; queue from now on
  height = clamp(height, 1, max_live_height(rows))            # the last drawn height, re-capped
  if top + height > rows: top = rows - height
  mark a full repaint
  if overlay open: return                                     # model only; cleared on close
  begin synchronized update if supported
  move to (0, top); write ESC [ J                             # never above top: that is history
  park the cursor at (0, top + height - 1)
  end synchronized update; flush; update the RestoreLink
```

The height `resize` keeps is the height of the last drawn live region (before the first `draw_live`, the `live_height` given to `new`), capped at `max_live_height` of the new rows. It is not grown here: the next `draw_live` computes the view's height at the new width and grows or shrinks it as section 5.2 says.

Each resize event is applied in order, even during an overlay: a shrink followed by a grow is not the same as no change when rows below the viewport were dropped.

Known limits, recorded in the journal entry:

- With fewer than `g` rows of scrollback (a fresh terminal), the terminal returns fewer rows than assumed. Talaria repaints lower than the old live region, so stale live rows stay visible above the viewport, and later commits push them into scrollback. No committed line is lost or duplicated, because Talaria never clears above its assumed top. Assuming fewer rows would be worse: clearing from too high would erase visible history.
- A shrink to fewer rows than the rows above the viewport plus the live region pushes live rows into scrollback before Talaria hears of it.
- A width change can make a terminal reflow rows wider than the new width. Talaria writes no trailing blanks, which avoids most of it, but long committed rows can shift content. The terminal reflows its own scrollback; Talaria does not rewrite it.
- Several quick resizes may reach Talaria as one event while the terminal applied each step.

Why not Codex's rule ("keep the top unless the viewport was bottom-aligned"): `grow_lines` pulls history down whether or not the viewport was at the bottom, so keeping the top repaints over pulled-down history rows. Why no query: a query after start-up races the key reader (C9; bake-off fixes 3 and 4).

### 6.2 Overlays

```text
open_overlay():   flush nothing (the queue is empty); enter alternate screen (ESC [ ? 1049 h);
                  ESC [ 2 J; previous overlay frame = blank; overlay = open (link updated)
draw_overlay(f):  buffer = Buffer::empty(Rect(0, 0, cols, rows)) at the newest size;
                  f(area, &mut buffer); diff against the previous overlay frame; write
                  (synchronized when supported); return FrameStats
resize while open: apply section 6.1's model to the main-screen state; the next overlay
                  frame is a full repaint at the new size
close_overlay():  leave alternate screen (ESC [ ? 1049 l; the terminal restores the main
                  screen and the saved, parked cursor); overlay = closed (link updated);
                  move to (0, top); ESC [ J; write the queued rows with the commit
                  algorithm; mark a full repaint (the caller's next draw_live paints it)
```

`close_overlay` takes no `LiveView`, like `resize`, so it does not paint the live region; the caller draws next. Test 26 compares the screen before the overlay with the screen after `close_overlay` plus one `draw_live` of the same view.

Mouse capture stays off in overlays (ADR-0009 decision 4). A pager that wants mouse scrolling is a later unit's decision.

## 9. The demo program (`examples/inline_demo.rs`)

The test author writes the demo in the first commit, against the `todo!()` stubs: it is a test fixture for test 30 and the acceptance scenarios, not product code. The developer may fix it but must not change the behaviour below. Its hostile line may use `\x1b` literals (examples are outside test 28's scan, section 8.1). It calls `draw_live` after every key, commit tick, `resize` and `close_overlay`.

Flags: `--lines N` (default 100), `--interval-ms M` (default 10), `--hostile`. Behaviour:

1. `TerminalGuard::acquire()`; on `NotATerminal`, print `inline_demo: standard input or output is not a terminal` to standard error (no escape bytes) and exit 2. Any other error: print it and exit 1.
2. `probe_startup`, `terminal_size`, `InlineTerminal::new(stdout, size, 2, probe, guard.link())`, `spawn_input`, in this order (section 3.1).
3. Each tick, commit the next line `line 0001` … `line NNNN`. With `--hostile`, after `line 0005`, commit `HOSTILE ` + ESC + `[2J` + ESC + `[H` + BEL + U+202E + ` END`, which shows as `HOSTILE ␛[2J␛[H␇‹U+202E› END`.
4. The live region has two `PlainTextSection` rows: `LIVE# committed n of N` and `o overlay  +/- height  q quit`. `+` and `-` change the height (extra rows read `LIVE# padding`).
5. `o` opens an overlay whose only text is `OVERLAY - press Esc`; `Esc` closes it; resize events go to `resize`.
6. `q` stops the input thread, calls `restore`, drops the guard, exits 0.

It uses only this unit's public interfaces (no `queue!`, no raw mode), so it doubles as a worked example for later units.

## 10. Design reasoning and rejected alternatives

- **ratatui `Viewport::Inline` and `insert_before`**: rejected by the roadmap and the patterns guide, with the bake-off's evidence (fixes 3 to 5).
- **A ratatui `Terminal` for the live region**: rejected; its resize and clear paths are built for a viewport it owns, and `Buffer::diff` plus `CrosstermBackend::draw` gives the same diffing with full control.
- **A cursor query on every resize, as Codex does**: rejected because of the key-reader race. Section 6.1's model gives the same result when the terminal has enough scrollback.
- **Codex's "keep the top unless bottom-aligned" resize rule**: rejected (section 6.1).
- **A hardware caret**: rejected for now; the resize model needs the cursor parked (section 5.2).
- **Always wrapping frames in mode 2026, as the reference slice does**: rejected because the architecture asks for negotiation at start-up.
- **`vt100` alone for every test**: rejected because of C1; it would make the most important test vacuous.
- **Letting `history.rs` write bytes**: rejected; one writer of escape sequences keeps moderate builders out of terminal code.
- **A live-height cap of `rows - 1`**: rejected; at the cap the insertion region would be one row, which terminals reject (C2, C5).
- **Tab stops every eight columns**: rejected; `sanitize` sees one span without its column, and P1-07 already renders a tab as four spaces.
