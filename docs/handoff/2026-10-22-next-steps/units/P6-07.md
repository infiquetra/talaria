## 1. What the unit delivers

A pushed `v*` tag already runs `.github/workflows/release.yml` (unit P0-02), which checks the tag format, checks the tag against the workspace version, runs the project check and creates a release page with generated notes and no files. This unit adds:

- four release archives (`talaria-<v>-<target>.tar.gz`) and a `SHA256SUMS` file on every release page;
- build provenance attestations for the archives;
- a pull request to the operator's tap repository `infiquetra/homebrew-talaria` for every final (non-pre-release) tag;
- a dry-run workflow that proves all of it on a pull request, before any tag;
- `docs/install.md`.

Decision 3 of the handoff ([08-risks-and-open-questions.md](../08-risks-and-open-questions.md#decisions-the-operator-owns)) is the authority: keep the command name `talaria`, publish binaries through GitHub releases and a Homebrew tap, publish nothing to a package registry under that name. The collision itself is recorded in [04-prior-art.md](../04-prior-art.md). The roadmap line is in [07-roadmap-and-work-units.md](../07-roadmap-and-work-units.md#phase-6--later-in-the-order-the-operator-chooses).

## 3. Targets

| target | runner | kind | notes |
|---|---|---|---|
| `aarch64-apple-darwin` | `macos-14` | native | `check-binary` runs `--version` |
| `x86_64-apple-darwin` | `macos-14` | cross | `rustup target add`; `--version` not run (`version: not run (cannot run on this host)`); the header check proves the architecture |

| `aarch64-unknown-linux-musl` | `ubuntu-24.04-arm` | native | needs `musl-tools`; runs on the runner's glibc host (E21) |

`package.py targets` prints these four lines, space separated, in this order. `package.py targets --json` prints one line: a JSON array of objects with keys `target`, `runner`, `kind`, in this order, suitable for `fromJSON` in a matrix `include`.

"native" means the runner can execute the binary, decided by `can_run_on_host` (section 6.3), not that the triples are equal. The host triple is read from `rustc -vV` (the `host:` line); `PACKAGE_HOST_TARGET`, if set, overrides it, for tests only.

The live test (issue test 19) builds the host's package target: on macOS the host triple itself; on Linux the musl target of the host's CPU (`x86_64-unknown-linux-gnu` or `-musl` hosts build `x86_64-unknown-linux-musl`; `aarch64-unknown-linux-*` hosts build `aarch64-unknown-linux-musl`). Any other host is a skip with the message `no package target for host <triple>`. With `PACKAGE_LIVE=1` on Linux and no `musl-gcc`, the test fails (environment), it does not skip.

## 4. Version rules

- Every pattern in this document is matched with `re.fullmatch` (never `re.match` with `$`, which also accepts a value ending in a newline). Tests 2 and 13 include newline-ended values.
- Tag pattern (identical to P0-02's `resolve` step; test 2 reads it from `release.yml`): `v[0-9]+\.[0-9]+\.[0-9]+(-[0-9A-Za-z.]+)?`.
- Release version `<v>` = the tag without the leading `v`. Pre-release when it contains `-`.
- Base of a version = the part before the first `-`.
- Version pattern for `--version` and `--workspace-version`: `[0-9]+\.[0-9]+\.[0-9]+(-[0-9A-Za-z.]+)?`, at most 57 characters (section 6.2). Anything else is exit 2, `package.py: invalid version '<value>'` (value cut to 40 characters, control characters replaced by `?`).
- **Version gate** (`package.py version-gate --tag <tag> --workspace-version <w>`, run in the release workflow's `check` job with `<w>` the `talaria-cli` version from `cargo metadata`): prints `<v>`. A final tag needs `<w>` equal to `<v>` exactly, else exit 1 `final tag <tag> needs workspace version <v>, found <w>`. A pre-release tag needs equal bases, else exit 1 `tag <tag> and workspace version <w> have different base versions`. Reason: the formula's `test do` block asserts `talaria #{version}` exactly, and the tap is updated only for final tags; P0-02's own tag check compares bases only and would let `v0.7.1` build from `0.7.1-dev`.
- **check-binary's version rule**: for a final `<v>` the binary must print exactly `talaria <v>`; for a pre-release `<v>` the bases must match. In the dry run `<v>` is the workspace version itself (for example `0.8.0-dev`, a pre-release form), and the binary prints exactly that.

| tag | `<v>` | pre-release | workspace / binary | `version-gate` | `check-binary` |
|---|---|---|---|---|---|
| `v0.7.1` | `0.7.1` | no | `0.7.1` | pass | pass |
| `v0.7.1` | `0.7.1` | no | `0.7.1-dev` | fail | fail |
| `v0.7.1-rc.1` | `0.7.1-rc.1` | yes | `0.7.1-dev` | pass | pass |
| `v0.7.1-rc.1` | `0.7.1-rc.1` | yes | `0.8.0-dev` | fail | fail |
| `v0.7` | refused (exit 2) | | | | |

## 5. Formula template

`package.py formula` fills this template. `{v}` is the validated version; `{base}` is the validated base URL without a trailing slash; each `{sha:<target>}` is the 64-character hex digest from `SHA256SUMS` for `talaria-{v}-<target>.tar.gz`. Two-space indentation, a final newline, no trailing spaces.

```ruby
class Talaria < Formula
  desc "Terminal client for the Hermes agent gateway"
  homepage "https://github.com/infiquetra/talaria"
  version "{v}"
  license "MIT"

  on_macos do
    on_arm do
      url "{base}/talaria-{v}-aarch64-apple-darwin.tar.gz"
      sha256 "{sha:aarch64-apple-darwin}"
    end
    on_intel do
      url "{base}/talaria-{v}-x86_64-apple-darwin.tar.gz"
      sha256 "{sha:x86_64-apple-darwin}"
    end
  end

  on_linux do
    on_arm do
      url "{base}/talaria-{v}-aarch64-unknown-linux-musl.tar.gz"
      sha256 "{sha:aarch64-unknown-linux-musl}"
    end
    on_intel do
      url "{base}/talaria-{v}-x86_64-unknown-linux-musl.tar.gz"
      sha256 "{sha:x86_64-unknown-linux-musl}"
    end
  end

  def install
    bin.install "talaria"
  end

  def caveats
    <<~EOS
      Talaria needs a running Hermes gateway, v0.22.3 or newer.
      Run `talaria doctor` to check the connection and versions.
    EOS
  end

  test do
    assert_equal "talaria #{version}", shell_output("#{bin}/talaria --version").strip
  end
end
```

Rules:

- Default `{base}`: `https://github.com/infiquetra/talaria/releases/download/v{v}`.
- `--base-url` must fully match `(https://[A-Za-z0-9.-]+|file://)/[A-Za-z0-9._~/%-]*` (`re.fullmatch`) once one trailing slash is removed. A quote, `#`, a space, a backslash or a newline is exit 2 (`package.py: unsafe base URL`), so nothing reaches Ruby unescaped. The `#{...}` sequences in the template are Ruby interpolation that Homebrew evaluates; they are literal template text, never filled by `package.py`.
- Archive names come from the sums file. `formula` recovers each name's version and target as section 6.4 does; a version different from `--version` is exit 2, `package.py: SHA256SUMS names version <x>, not <v>`; a missing target is exit 1, `SHA256SUMS has no archive for <target>`. The `version` line and the URLs use `--version`.
- The golden file `tools/package/tests/data/talaria.rb.golden` is the template filled with `{v}` = `0.7.1`, the default base, and digests `1111…` (64 ones), `2222…`, `3333…`, `4444…` for the targets in section 3 order. The test author writes it by hand from this section, not by running the code.
- If real Homebrew (the dry run's `formula-install` job, UAT-3 or UAT-6) rejects the template, for example `brew audit --strict` calling the explicit `version` line redundant, the developer reports the message to the lead. If the template must change, the golden file goes back to the test author with the written reason, who updates it and test 12 first; nobody edits the golden file in place to make a test pass. Never add stanzas from memory.
- If unit P4-10's `talaria doctor` does not exist at scheduling (S5), the caveat's second line becomes `Run talaria --help for the connection options.` and the issue records why.

### 6.2 Archive format

- Name: `talaria-<v>-<t>.tar.gz`.
- Entries, in this order, all under the top folder `talaria-<v>-<t>/`: `talaria` (the binary, mode `0o755`), `LICENSE` (mode `0o644`), `README.md` (mode `0o644`), both read from the repository root. No directory entries.
- Tar: `tarfile.USTAR_FORMAT`; every `TarInfo` has `uid = gid = 0`, `uname = gname = ""`, `mtime = int(SOURCE_DATE_EPOCH)`, type regular file.
- Gzip: `gzip.GzipFile(filename="", mode="wb", fileobj=<file>, mtime=0, compresslevel=9)`, so no name and no time in the header.
- `SOURCE_DATE_EPOCH` must be set and be a non-negative integer; the workflows set it from `git log -1 --format=%ct` of the checked-out commit.
- Errors (exit 2): `package.py: version too long for the archive format (at most 57 characters)` (the longest member name, `talaria-<v>-aarch64-unknown-linux-musl/talaria`, is 43 characters plus the version and must fit USTAR's 100-character name field), `package.py: binary not found: <path>`, `package.py: binary is not executable: <path>`, `package.py: LICENSE not found at the repository root`, `package.py: unknown target '<t>'` (lists the four), `package.py: SOURCE_DATE_EPOCH must be a whole number of seconds`. The archive is written to a temporary name in `<dir>` and renamed only on success, so a failure leaves no file.

### 6.3 Reading the binary header

Read the first 4,096 bytes (more only to reach program headers).

| Bytes | Meaning | Result |
|---|---|---|
| `cf fa ed fe` at 0 | 64-bit Mach-O, little-endian | CPU type: little-endian `u32` at offset 4; `0x0100000c` is `arm64`, `0x01000007` is `x86_64`; other: fail `unknown Mach-O CPU type 0x<hex>` |
| `ce fa ed fe` at 0 | 32-bit Mach-O, little-endian | fail: `not a 64-bit Mach-O file` |
| `ca fe ba be` or `ca fe ba bf` at 0 | universal (fat) Mach-O | fail: `universal Mach-O files are not shipped; build one architecture per target` |
| `7f 45 4c 46` at 0 | ELF | byte 4 must be 2 (64-bit) and byte 5 must be 1 (little-endian), else fail `not a 64-bit little-endian ELF file`; machine: little-endian `u16` at 18, `62` is `x86_64`, `183` is `aarch64`; program headers: offset `u64` at 32, entry size `u16` at 54, count `u16` at 56; any entry whose `u32` type is `3` (`PT_INTERP`) means dynamic |
| anything else | | fail: `not a Mach-O or ELF executable` |

Architecture names are spelled exactly as in the table: Mach-O uses `arm64` and `x86_64`, ELF uses `aarch64` and `x86_64`. The success line is `arch: <name> (Mach-O)` or `arch: <name> (ELF)`.

Expected per target: Apple targets need Mach-O of the matching CPU (`aarch64-apple-darwin` needs `arm64`); Linux targets need ELF of the matching machine and no `PT_INTERP` (fail: `binary is dynamically linked (it names an interpreter); musl targets must be static`). A mismatch fails with `binary is <name>, target <t> needs <name>`.

`can_run_on_host(target, host)`:

| target | runs on host | does not run on |
|---|---|---|
| `aarch64-apple-darwin` | `aarch64-apple-darwin` | everything else |
| `x86_64-apple-darwin` | `x86_64-apple-darwin` | `aarch64-apple-darwin` (no reliance on Rosetta), Linux |
| `x86_64-unknown-linux-musl` | `x86_64-unknown-linux-gnu`, `x86_64-unknown-linux-musl` | any `aarch64-*`, any `*-apple-darwin` |
| `aarch64-unknown-linux-musl` | `aarch64-unknown-linux-gnu`, `aarch64-unknown-linux-musl` | any `x86_64-*`, any `*-apple-darwin` |

Version check (only when `can_run_on_host` is true): run `[<path>, "--version"]` with no shell, standard input from `/dev/null`, a 10-second timeout, and an environment of exactly: `PATH` copied from the parent; `HOME` copied from the parent if set (left out if not; that is not an error); `LANG=C.UTF-8`. Pass when the exit code is 0 and standard output is exactly one line (one trailing newline allowed) `talaria <w>` meeting section 4's rule. Failures: `--version did not finish within 10 s`, `--version exited <n>`, `--version printed '<text>', expected 'talaria <v>'` (text: first 80 characters of standard output, control characters replaced by `?`). When false, print `version: not run (cannot run on this host)` and do not fail.

In tests, `read_header(path)`, `can_run_on_host(target, host)` and `check_version(path, version)` are called directly; the command line joins them.

### 6.4 Checksums and plan-upload

- **Reading an archive name.** A name must start `talaria-` and end `.tar.gz`. Strip both, then strip one of the four known targets (section 3) from the right, preceded by `-`; what remains is the version, which must match section 4's version pattern. A name matching no target is "unknown target" (listed as extra in `checksums`, exit 2 in `formula` and `plan-upload`). This works for versions with hyphens: `talaria-0.7.1-rc.1-aarch64-apple-darwin.tar.gz` gives `0.7.1-rc.1` and `aarch64-apple-darwin`.
- `SHA256SUMS`: list the `talaria-*.tar.gz` files in `<dir>`, sorted by name. The version is the first readable archive's version; archives of any other version, and unreadable names, are extra. Exactly one archive per target at that version is required; otherwise exit 1 with `expected one archive per target; missing: <targets>; extra: <names>` (`missing: none` or `extra: none` when empty). On success, one line per archive, `<sha256 hex lower>␣␣<name>`, sorted by name, `\n` after each, nothing else.
- `plan-upload <sums> <existing>`: parse `<sums>` (exactly four lines, one per target, one version; else exit 2 `package.py: <sums> is not a four-target SHA256SUMS`); the tag is `v<version>`; the expected set is the four names plus `SHA256SUMS`. For each file in `<existing>`: a name outside the expected set is exit 1 `release <tag> has an unexpected file <name>`; an archive whose SHA-256 differs from its line, or a `SHA256SUMS` whose bytes differ from `<sums>`, is exit 1 `release <tag> already has <name> with a different checksum; not replacing it`. Nothing is printed on failure. Otherwise print each expected name not present in `<existing>`, archives first in `<sums>` order, then `SHA256SUMS`. An empty `<existing>` prints all five.

### 7.2 `package-build.yml`

```yaml
name: Package build
on:
  workflow_call:
    inputs:
      ref:
        type: string
        required: true
      version:
        type: string
        required: true
permissions:
  contents: read
jobs:
  plan:
    runs-on: ubuntu-latest
    outputs:
      matrix: ${{ steps.targets.outputs.matrix }}
    steps:
      - uses: actions/checkout@<hash> # <tag>
        with:
          ref: ${{ inputs.ref }}
      - id: targets
        run: echo "matrix=$(python3 -I tools/package/package.py targets --json)" >> "$GITHUB_OUTPUT"
  package:
    needs: plan
    name: package (${{ matrix.target }})
    strategy:
      fail-fast: false
      matrix:
        include: ${{ fromJSON(needs.plan.outputs.matrix) }}
    runs-on: ${{ matrix.runner }}
    steps:
      - uses: actions/checkout@<hash> # <tag>
        with:
          ref: ${{ inputs.ref }}
      - name: Install the pinned toolchain
        run: |
          rustup toolchain install
          rustup show active-toolchain
      - name: Install musl tools
        if: endsWith(matrix.target, '-linux-musl')
        run: sudo apt-get update && sudo apt-get install -y musl-tools
      - name: Build, check and pack
        env:
          TARGET: ${{ matrix.target }}
          VERSION: ${{ inputs.version }}
        run: |
          SOURCE_DATE_EPOCH="$(git log -1 --format=%ct)"
          export SOURCE_DATE_EPOCH
          bin="$(python3 -I tools/package/package.py build --target "$TARGET")"
          python3 -I tools/package/package.py check-binary --target "$TARGET" --version "$VERSION" "$bin"
          python3 -I tools/package/package.py archive --target "$TARGET" --version "$VERSION" \
            --binary "$bin" --out dist
      - uses: actions/upload-artifact@<hash> # <tag>
        with:
          name: talaria-${{ matrix.target }}
          path: dist/*.tar.gz
          retention-days: 7
          if-no-files-found: error
```

`inputs.version` reaches the shell through `env:`, never through `${{ }}` inside `run:`, for the same reason as P0-02's `resolve` step. `package.py` validates it again (section 4).

Note on "no release page until a re-run succeeds": this changes P0-02's behaviour, where the page appeared as soon as the project check passed. It is deliberate: a page without its binaries would be picked up by REL-03's and REL-02's checks as a release with no files. Report the change on unit P0-02 when merging.

## 13. Design reasoning and rejected alternatives

- **cargo-dist (dist) or GoReleaser.** Both generate the release workflow, the archives and a Homebrew formula with little code. Rejected because they own and regenerate `release.yml`, which would drop P0-02's two defences and the tag-against-version check, and because their generated formula and archive layout would be a second source of truth outside the tests. Revisit if the hand-written workflow needs more than two fixes in its first three releases.
- **glibc Linux builds.** Smaller risk of a dependency failing to build, but each binary then needs a glibc at least as new as the build machine's. musl gives one archive per architecture that runs everywhere. musl's allocator is slower; Talaria's budgets are generous for a terminal client, and a regression is reported rather than hidden.
- **A universal macOS binary.** One file for both Mac architectures, but twice the download, a different formula shape from Linux, and a fat header that `check-binary` would have to split. Rejected for symmetry.
- **Pushing the formula straight to the tap's `main`.** Faster, but a broken formula would reach users before anyone looked at it. The pull request keeps the operator as the last check at the cost of one click per release.
- **Building on pull requests in `ci.yml`.** Four extra runners on every pull request for a path that changes rarely. The path-filtered dry run gives the same proof when it matters.
- **Python for the tooling.** The repository already uses Python 3.9 standard-library tools (`tools/contract-gen/`, unit P0-03). A Rust tool would need a new crate or workspace member; a shell script could not be unit tested as cleanly (archive bytes, header parsing).
- **Notarisation.** Requires an Apple Developer account, a signing identity in CI secrets and a notary submission per release. Homebrew installs do not carry the quarantine mark, so the main path works without it; the install page explains the browser case.
