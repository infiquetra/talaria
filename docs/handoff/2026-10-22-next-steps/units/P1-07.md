## 2. Public interface

All paths are under `crates/talaria-tui/src/markdown/`. Names are this unit's; the types are ratatui's (`ratatui::text::Line`, `ratatui::style::Style`). Nothing in this module writes an escape sequence; the terminal module of {{P1-06}} owns that.

```rust
// mod.rs
#[doc(hidden)]
pub mod highlight;       // test hooks live here (see below); the rest of the module is private
pub mod cells;            // MarkdownCellLines (section 2.1)
pub mod section;          // MarkdownTailSection (section 2.1)
pub use highlight::warm_up;
pub use sanitize::sanitize_untrusted;
pub use theme::MarkdownTheme;

#[derive(Clone, Debug)]
pub struct MarkdownOptions {
    pub width: u16,              // terminal columns; values below 8 are raised to 8
    pub theme: MarkdownTheme,    // default: the table in section 4.2
    pub color: bool,             // false: modifiers only (bold, italic, underline, dim, strike)
    pub base_style: Style,       // patched under every span, e.g. dim for reasoning
}
impl Default for MarkdownOptions { /* width 80, default theme, color true, base_style default */ }

pub struct MarkdownStream { /* private */ }

#[derive(Clone, Debug, Default, PartialEq)]
pub struct StreamUpdate {
    pub committed: Vec<Line<'static>>, // new final lines; hand to scrollback exactly once
    pub tail: Vec<Line<'static>>,      // the whole current rendering of the unfinished block; replaces the previous tail
}
impl StreamUpdate { pub fn is_empty(&self) -> bool; }

impl MarkdownStream {
    pub fn new(options: MarkdownOptions) -> Self;
    pub fn push(&mut self, delta: &str) -> StreamUpdate;   // empty delta: returns an empty update, does no work
    pub fn set_width(&mut self, width: u16) -> StreamUpdate; // committed is always empty; tail re-wrapped
    pub fn finish(&mut self) -> StreamUpdate;              // everything left is committed, tail empty; the stream is reusable for the next message
    pub fn pending_bytes(&self) -> usize;                  // length in bytes of `pending`, the sanitized uncommitted text; a held `\r` is not counted
}

pub fn render_markdown(text: &str, options: &MarkdownOptions) -> Vec<Line<'static>>; // whole text, no streaming
pub fn sanitize_untrusted(text: &str) -> std::borrow::Cow<'_, str>;               // section 7
pub fn warm_up();                                                                  // section 8.3; returns at once
```

`StreamUpdate::tail` after `finish` is empty. A caller that has just committed lines and has a non-empty tail draws the tail in its live region; a caller with an empty tail draws nothing for the message.

The module also exposes `#[doc(hidden)]` hooks for tests only: `highlight::is_loaded() -> bool`, `highlight::force_not_ready(bool)` and `highlight::load_starts() -> u32` (all process-wide; the last counts how many times a background load was started), and `MarkdownStream::lines_highlighted(&self) -> u64` (per stream, so tests do not interfere; it counts the lines this stream has given to syntect's parser, whether for the tail or for a commit, and a commit of a block that was already the open block reuses the open-block cache, so its lines are not counted again). Integration tests in `tests/` reach them as `talaria_tui::markdown::highlight::...`; they are not part of the supported interface. While `force_not_ready(true)` is set, `is_loaded()` returns false, code renders plain even if the set is loaded, and `warm_up()` starts nothing.

`MarkdownTheme` has one public `Style` field per row of the table in section 4.2, named after the row: `heading1`, `heading2`, `heading3`, `strong`, `emphasis`, `strikethrough`, `inline_code`, `link_text`, `link_destination`, `image_alt`, `quote_bar`, `rule`, `code_label`, `table_border`, `table_header`. It derives `Clone` and `Debug`. The code colours (section 8.4) are fixed in `highlight.rs` and are not in the struct; {{P2-12}} may add a field later.

## 3. When is a block finished

### 3.1 What was verified

These behaviours were observed with a probe program on pulldown-cmark 0.13.4 (`default-features = false`, options tables, strikethrough and task lists), run on 2026-10-22 on the local machine. The dependency is pinned to exactly 0.13.4 for that reason; re-run the probe on any version change. (The research report's parse timings in section 9 were measured on 0.13.5.) `Parser::new_ext(src, opts).into_offset_iter()` yields each event with its byte range.

| Input | Observation |
|---|---|
| `para\n\nnext\n` | two top-level paragraphs, ranges `0..5` and `6..11`; the blank line is in neither range |
| `para\n***` | a paragraph `0..5` followed by a thematic rule `5..8` |
| `para\n***bold***\n` | one paragraph `0..16` (the same first line `***` means something else once the line is complete) |
| a complete fenced block, with or without a final newline | one code block; the range ends at the end of the closing fence line, excluding its newline |
| an unterminated fenced block | one code block whose range runs to the end of the input |
| `1. a\n\n2. b\n\npara\n` | one list `0..12` (trailing blank line included) and a paragraph `12..17` |
| a table followed directly by a line `foo` | one table that includes `foo` as a row; a table ends at a blank line or another block, not at the next ordinary line |
| `Title\n---\n` | one heading (setext) |
| a list with a blank line and an indented continuation | one list |
| `> a\n> > b` | one block quote holding a paragraph and a nested block quote |
| `see <https://example.org/y>` | a link event of type Autolink whose text is the URL |
| a table row with fewer cells than the header, then a row with more | the short row gets an empty cell; the extra cell is dropped |
| `- [ ] todo\n- [x] done` | a tight list; each item starts with a task-list marker event (false, true) |
| `1. a\n\n2. b` | a loose list: each item holds a paragraph; the tight list `- a\n- b` has text directly in the items |
| `[x]\n\n[x]: http://u` | one paragraph; the definition is not a block and no event is produced for it, but the whole-text parse turns `[x]` into a link |
| `a\n\n   \n\nb` | paragraphs `0..2` and `8..9` |

To re-run the probe, make a scratch crate (outside the repository) with `pulldown-cmark = { version = "=0.13.4", default-features = false }` and print, for each sample input, the events from `Parser::new_ext(src, Options::ENABLE_TABLES | Options::ENABLE_STRIKETHROUGH | Options::ENABLE_TASKLISTS).into_offset_iter()`, tracking depth (`Event::Start` adds one, `Event::End` subtracts one) and printing the range of each event at depth 0 and of each `End` that returns to depth 0.

The second and third rows are the reason for the rule "decide block boundaries only from complete lines": a half-typed line can look like a new block and then turn out not to be one.

### 3.2 The rule

State: `pending: String` (text not yet committed, always starting at the beginning of a line), `held_cr: bool` (a carriage return that ended the previous delta), `emitted_any: bool` (whether a block has been committed in this message).

On `push(delta)`:

1. If the delta is empty, return an empty update. Otherwise, if `held_cr` is set, prefix the delta with `\r` and clear it. If the delta now ends with `\r`, remove that `\r` and set `held_cr`. This happens before sanitizing, so a `\r` at the end of one delta can join a `\n` at the start of the next.
2. Sanitize the delta (section 7) and append it to `pending`.
3. Let `complete` be `pending` up to and including its last `\n` (empty when there is no newline).
4. Parse `complete` with the options above and list the top-level blocks with their byte ranges. A block is *top-level* when the event depth is 0.
5. A block is *closed* when either (a) another top-level block follows it in `complete`, or (b) it is a fenced code block whose last line is a closing fence (section 3.3). The last top-level block is closed only by (b). Blocks close in order: let `n` be the number of closed blocks at the front.
6. If `n > 0`, find the boundary `B`: when block `n` exists (the first block that stays open), `B` is the start of the line that holds the start of block `n`; when every block is closed (the last one by rule (b)), `B` is the end of the last block's closing fence line including its newline.
7. Render blocks `0..n` each from its own byte range inside `pending[..B]` (section 4), with one blank line before each block when `emitted_any` is true or it is not the first block of this call, and append the lines to `committed`. Blank lines and anything else between block ranges are never rendered, so a block never prints trailing separators. Drain `pending[..B]` and set `emitted_any`.
8. Render the remainder of `pending` (the whole remainder, including a partial last line) as the tail: one blank line first if `emitted_any` (or if blocks were committed in this call), then the lines of the remaining blocks. Return `StreamUpdate { committed, tail }`.

On `finish()`: if `held_cr` is set, append `␍` to `pending` first. Then parse and render all of `pending` as above, commit every line, clear `pending`, `held_cr` and `emitted_any`, and return an update with an empty tail. Calling `finish` twice in a row returns an empty update the second time.

The blank-line rule: exactly one blank line between two top-level blocks, none before the first block of a message and none after the last. The separator belongs to the start of the later block, so a committed block is never followed by a stray blank line when the message ends.

A line counts as complete only when it ends in `\n`. A line that has started but has no newline yet is never in `complete`, so it cannot start or close a block; this is the case whenever a test or a worked example below has no final newline.

### 3.3 Early commit of a closed fence

A top-level fenced code block is closed by rule (b) when its range has at least two lines and the last line, after removing up to three leading spaces and trailing whitespace, is a run of at least three of the same fence character (backtick or tilde) as the opening line, at least as long as the opening run, with nothing else on the line. Because the parse covers only complete lines, the closing line is complete. This lets a long code block move into scrollback as soon as it closes, instead of waiting for the next block. Example: `"```rust\nfn a(){}\n```\n"` is committed by a single `push`, with the tail empty.

A fence inside a list or quote is not top-level; it is committed with its container.

### 3.4 Properties the rule gives

- Equivalence. For text in which no link reference definition is separated from its use by a commit, concatenating every `committed` from `push` and the `committed` of `finish` gives the same lines as `render_markdown(whole_text)`, for any way of cutting the text into deltas, as long as the highlighter's readiness (section 8.3) does not change during the stream. Proof sketch: a block is committed only after the parser has seen a complete following line that starts a new top-level block (or its own closing fence), so no later input can change how that block was parsed. Limitation: committed text is drained from `pending`, so the parser never sees a link reference definition (`[x]: url`) that sat in committed text when it parses a later block, and a definition placed after its use changes how the earlier `[text][ref]` parses. Either way the stream renders the use as literal text where the whole-text render would make a link. This is documented and accepted; the property test and the replay test skip any text containing `]:`. (A later improvement could keep the definitions found in committed text and resolve them with `Parser::new_with_broken_link_callback`; it is not part of this unit.)
- No repeat. Every line appears in exactly one `committed`.
- Bounded work. Each push parses and renders only `pending`, which is the unfinished tail, not the whole message.

### 3.5 Worked examples

Width 80, each row is a sequence of pushes. `C` is what `committed` holds after the push, `T` the tail. Every input that is meant to commit ends in a newline (section 3.2).

| Pushes | After the last push |
|---|---|
| `"Hello wor"` | C: none. T: `Hello wor` |
| `"Hello world\n"` | C: none. T: `Hello world` (a lone block is never closed by rule (a)) |
| `"Hello world\n\nNext"` | C: none (the line `Next` has no newline yet, so it is outside `complete` and cannot close `Hello world`). T: `Hello world`, a blank line, `Next` (the tail renders all of `pending`, partial line included) |
| `"Hello world\n\nNext\n"` | C: `Hello world`. T: blank line, then `Next` |
| `"Hello\n***"` then `"bold***\n"` | after the first push nothing is committed (the half line is outside `complete`); after the second the whole text is one paragraph |
| ``"```rust\nlet a = 1;\n"`` | C: none. T: `rust` label and `let a = 1;` |
| then ``"```\n"`` | C: label and the code line. T: none |
| ``"```rust\nlet a = 1;\n``"`` then ``"`\n"`` | the partial closing line is outside `complete`; nothing is committed until the line is complete |
| `"- a\n\n- b\n\ntext\n"` | C: the list (two items, loose). T: blank line, `text` |
| `"- a\n\n- b\n\n  more\n"` | C: none. The indented line continues the second item, so the list is still the open block |
| `"a\r"` then `"\nb\n"` | the first push appends `a` and holds the `\r`; the second makes `\r\nb\n`, which sanitizes to `\nb\n`, so `pending` is `a\nb\n`: one paragraph of two lines, nothing committed |

## 4. Rendering rules

### 4.1 Parser options and inputs

Parser options: tables, strikethrough, task lists. Nothing else: no smart punctuation (it would change characters), no footnotes, no heading attributes, no metadata blocks, no math. Constructs that are not enabled are shown literally.

Events and how each renders:

| Construct | Rendering |
|---|---|
| Paragraph | words wrapped to the width (section 5) |
| Soft line break | a line break (the model's line structure is kept) |
| Hard line break | a line break |
| Heading 1 to 6 | the text without the `#` characters, styled per section 4.2; same block spacing as a paragraph |
| Emphasis, strong, strikethrough | style modifiers, nested styles combine |
| Inline code | the code text with the inline-code style; not parsed further; spaces preserved |
| Fenced or indented code block | the info string's first word as a dim label line (no label line when the info string is empty or has no first word, and none for indented code), then the code lines highlighted when the language is known, wrapped hard at the width, no gutter, no indent, no fences |
| Block quote | each line prefixed by the quote bar; nesting adds bars; a blank separator inside a quote is the bars alone with no trailing space |
| Bullet list | markers `•` (level 1), `◦` (level 2), `▪` (level 3 and deeper); each level indents by the marker width plus one space; wrapped lines hang under the item text |
| Ordered list | `N.` using the list's start number and counting up; continuation lines hang under the text; the marker column is as wide as the widest marker in that list, markers are left-aligned and padded on the right (`9.  a` above `10. b`), then one space |
| Task list item | `☐ ` or `☑ ` replaces the bullet |
| Tight list | no blank lines between items |
| Loose list | one blank line between items |
| Thematic rule | `─` repeated min(width, 80) times, dim |
| Link | link text with the link style, then ` (url)` dim; the destination is omitted when it equals the text or the link is an autolink (angle-bracket URL), in which case the URL is shown once |
| Image | `[image: alt]` then ` (url)` dim; the image is never fetched |
| Raw HTML (block or inline) | shown as literal text, unstyled |
| Table | section 6 |

Bare URLs in text are left as text. No escape sequence for hyperlinks (OSC 8) is emitted in this unit; terminals that detect URLs still make them clickable.

### 4.3 The dump format

Tests compare a text dump of the lines, not escape sequences. The helper `dump(&[Line]) -> String` (in `tests/markdown_support/mod.rs`, written by the test author; `tests/support/` belongs to {{P1-06}} and is not touched), together with `assert_dump(&[Line], &[&str])` that compares the dump rows with a literal list of expected rows (the repository's convention in `docs/agents/patterns.md`, Pattern 4: literal rows, no generated snapshot files) prints one output row per line: `|`, then the spans in order, then `|`. A span with no style prints its text; a styled span prints `<tags>text</>`, tags separated by commas in this order: `b`, `i`, `u`, `s`, `d`, `fg=<name>`. Colour names: `black`, `red`, `green`, `yellow`, `blue`, `magenta`, `cyan`, `white`, `gray`, `darkgray`. Adjacent spans with identical style are merged first, so the dump does not depend on how spans were split. Trailing spaces are visible because of the closing `|`.

Overhead is 7, so `available` is 23; natural widths 1 and 27 (sum 28) do not fit; minimums are `min(1,10)=1` and `min(27,10)=10`; the remainder 12 goes to the second column, so the widths are 1 and 22. Plain text of the rows:

```text
┌───┬────────────────────────┐
│ A │ Long header here       │
├───┼────────────────────────┤
│ x │ some long text in this │
│   │ cell                   │
└───┴────────────────────────┘
```

Table whose overhead exceeds the width, width 8, input `| a | b | c |\n|---|---|---|\n| 1 | 2 | 3 |`. Overhead is 10, so `available` is -2 and the fallback applies:

```text
|<b>a</>: 1|
|<b>b</>: 2|
|<b>c</>: 3|
```

A table with a header and no body rows (`| a | b |\n|---|---|`) prints the headers alone: `|<b>a</>|` then `|<b>b</>|`.

Unsupported extensions stay literal: `~~gone~~` is a strikethrough (enabled, style `s`), but a lone pair of tildes with no closing pair (`a ~~ b`), `[^1]`, `$x$` and `"smart" quotes` print as typed.

A code block with a Rust fence is checked by looking up spans, not by a whole-line expectation (section 8.5).

## 5. Wrapping

Width is measured in terminal columns with the `unicode-width` crate (pinned 0.2.2) applied to each whole grapheme (`UnicodeWidthStr::width` on the grapheme string); break positions are grapheme boundaries (`unicode-segmentation` 1.13.3), so a combining mark, a variation selector or a zero-width-joiner emoji sequence is never split. Wide characters count two columns. Verified with a probe on 2026-10-22: a family emoji joined with zero-width joiners measures 2 and is one grapheme, a heart with variation selector 16 measures 2, the same heart without it 1, an `e` with a combining acute accent 1, two CJK characters 4, a flag (two regional indicators) 2. Terminals can still disagree with the library for rare sequences; that is a known mismatch class, not handled.

Algorithm for a paragraph-like run of styled text, given the available width after prefixes (quote bars, list indent):

1. Split into words at spaces; a run of spaces is one separator; explicit line breaks end a line.
2. Greedy fill: a word goes on the current line if the line width plus one separator plus the word width is at most the available width.
3. A word wider than the available width is cut at the available width on a grapheme boundary (a URL is cut this way; nothing is hidden).
4. A separator at a wrap point is dropped, so no line starts or ends with a space created by wrapping.
5. Each output line keeps the styles of its pieces. Prefixes are repeated on every output line (quote bars) or replaced by blanks of equal width (list hanging indent).
6. A tab becomes four spaces at layout time.

An available width below 1 after prefixes (very deep nesting at a small width) is raised to 1 so the code cannot loop. The width given in the options is raised to 8 first, so this only happens with deep nesting.

Code lines are cut hard at the width (step 3 only), with no continuation marker and without dropping spaces.

Rules that close gaps in the steps above:

- Step 1 applies to ordinary text: a run of spaces prints as one space even when nothing wraps. Inline code and code blocks keep their spaces exactly.
- Inside block quotes and lists, every kind of line (paragraph text, code lines, table rows, thematic rules) uses the width left after the quote bars and list indent, not the full width. A rule is `─` repeated min(that width, 80) times; a table is laid out for that width (section 6.1).
- A grapheme wider than the room left (a two-column character where only one column remains, which needs about eight levels of nesting at the smallest width) is put alone on its own line and may overflow it. No error and no loop. The property test `no_line_wider_than_width` generates at most two container levels and ordered-list numbers below 10, so the room is never below 2 and the case does not arise there.

## 6. Tables

### 6.1 Layout

Input: header cells, alignments (left, centre, right, or none meaning left), body rows. Each cell is rendered as inline styled text (bold, code and links work inside cells) and measured in columns.

1. Natural width `w_i` of column `i` is its widest cell's width, at least 1.
2. Overhead is `ncols + 1` border characters plus 2 padding spaces per column. `available = width - overhead`, computed as a signed integer (it can be zero or negative at small widths).
3. If the sum of `w_i` is at most `available`, use `w_i`.
4. Otherwise each column has a minimum `m_i = min(w_i, 10)`, so every column up to 10 wide keeps its natural width at minimum. If `available` is less than the sum of `m_i` (this includes zero and negative values), use the fallback (6.3). Else give each column `m_i`, then share the remainder (`available - sum(m_i)`) in proportion to `w_i - m_i`, rounding down, giving any leftover columns one at a time from the left to the columns that are still below `w_i`.
5. Cells wrap inside their column width (section 5). A row is as tall as its tallest cell.
6. Alignment pads inside the column width; header cells are bold.

### 6.2 Drawing

Characters: `┌ ┬ ┐ ├ ┼ ┤ └ ┴ ┘ ─ │`. One border line above the header, one under it, one after the last row, and none between body rows. A body cell is padded by one space each side.

### 6.3 Fallback

When the minimum widths do not fit, print each body row as lines `<bold header>: <cell>` in header order, one line per column (wrapped under a hanging indent), with one blank line between rows. A table with no body rows prints the headers alone, one per line.

### 6.4 While streaming

The table is the open block until another top-level block follows it. A blank line after the last row ends the table for the parser but does not commit it: commit follows rule (a) of section 3.2, so the commit waits for a complete line of the next block. The table is re-laid-out on every push; column widths may change as longer rows arrive; nothing of it is in scrollback until it closes.

## 7. Untrusted text

`sanitize_untrusted(&str) -> Cow<str>` returns the borrowed input when nothing needs replacing. Replacement is one character at a time, so it is safe to apply to each delta separately, with one exception that the stream handles before calling this function: a `\r` at the end of a delta is held and prefixed to the next delta (section 3.2 step 1), and `finish` turns a held `\r` into `␍`, so `\r\n` split across two deltas is one newline. Called on its own, this function treats a trailing lone `\r` like any lone `\r`: it becomes `␍`.

| Characters | Replacement |
|---|---|
| `\n` | kept |
| `\t` | kept (expanded at layout, section 5) |
| `\r\n` | one `\n` |
| lone `\r` | `␍` (U+240D) |
| U+0000 to U+001F other than the three above (this includes ESC, U+001B, and BEL) | the matching Control Picture: U+2400 plus the code, for example ESC becomes `␛` (U+241B) |
| U+007F | `␡` (U+2421) |
| U+0080 to U+009F (the C1 controls, which include the 8-bit CSI U+009B) | `‹U+0085›` form: single angle quotes U+2039 and U+203A around `U+` and four upper-case hex digits |
| Bidirectional controls: U+061C, U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069 | the same `‹U+XXXX›` form |
| Line and paragraph separators U+2028, U+2029 | the same `‹U+XXXX›` form |
| Tag characters U+E0000 to U+E007F (invisible text that can carry hidden instructions) | the same form with five hex digits, for example `‹U+E0041›`; the form uses at least four digits |

The stand-ins use characters that mean nothing in Markdown, so replacing before parsing cannot change the structure of the document. (Square brackets would, since `[U+202E](...)` could form a link; angle brackets could form HTML.) Replacement runs on the delta before it is appended, and also on text passed to `render_markdown`.

Not replaced: U+200D (it joins emoji sequences), U+FEFF, U+200B, U+2060 and the variation selectors (U+FE00 to U+FE0F, which select emoji presentation). Whether to show these is an open question, listed in section 13. The tag block is replaced because it has no ordinary use in a chat reply (only rare subdivision-flag emoji use it) and it can hide text from a reader; this is a decision of this unit, also listed in section 13.

The source files of the module never contain an escape character as text: write the Control Picture as U+2400 plus the code point (for example `char::from_u32(0x2400 + c as u32)`), and keep hostile sample text only in files under `tests/`. {{P1-06}}'s escape custody test scans `crates/talaria-tui/src/` for `\x1b`, `\u{1b}` and `\033` and would fail otherwise.

Link destinations, image alt text, table cells, code and HTML are all text that has passed through this function, because it runs on the whole input first.

## 8. Highlighting

### 8.1 Library and features

`syntect` pinned to `=5.3.0` with `default-features = false` and the features `parsing`, `default-syntaxes` and `regex-fancy`. The pure-Rust regex engine (`fancy-regex`) avoids a C dependency and keeps cross-compilation simple. Do not enable `default-themes` or the HTML feature; the unit builds its own theme (8.4). Verified on 2026-10-22 with a scratch program: this combination compiles and runs; its licence is MIT and the crates it pulls in are MIT, Apache-2.0 or Unlicense (`fancy-regex`, `bincode`, `flate2`, `walkdir` and others); a stripped release build of the scratch program that loads the syntax set was 2,510,888 bytes against 342,064 bytes for a hello-world program, so syntect costs about 2.2 MB. The licences of the bundled syntax definitions themselves were not checked: check them at build time and add a `NOTICE` entry if one is required. Record the version, the features, the binary-size comparison and the licence check in the pull request. Procedure for the comparison (no Cargo feature is added, because that would widen the dependency surface that section 10 pins): build the demo as committed with `cargo build --release -p talaria-tui --example markdown_demo` and strip it; then, in a throwaway worktree that is never committed, remove `syntect` from the crate's dependencies, make `highlight.rs` a stub whose set never becomes ready, build and strip the demo the same way, and compare the two file sizes. The stop limit is 4 MiB more with syntect. The 2.2 MB figure above came from a scratch program, not from the demo.

### 8.2 Language choice

The language is the first word of the fence's info string, lower-cased (`Python` and `PYTHON` both work), with `shell` and `zsh` mapped to `sh`, looked up with `SyntaxSet::find_syntax_by_token`. Verified in the scratch program with `SyntaxSet::load_defaults_newlines()`: the lookup matches file extensions and names, case-insensitively. Results: `rust`, `rs`, `py`, `python`, `sh`, `bash`, `js`, `json`, `yaml`, `diff`, `go`, `c`, `cpp`, `html`, `md`, `sql`, `ruby` and `java` are found; `shell`, `toml`, `ts` and `typescript` are not (so `shell` needs the alias, and TypeScript and TOML stay plain). No match, an empty info string, or an indented code block gives plain code. Do not guess a language from the content. Extra syntaxes through the `two-face` crate (the research report names it as Codex's choice) would fill the gaps; that is an operator decision, listed in section 13.

Use `SyntaxSet::load_defaults_newlines()`, the variant whose grammars expect each line to end with its newline, and pass each complete line with its `\n`. Drop the trailing newline from the last span of the produced line before building the ratatui line.

### 8.3 Loading without a dropped frame

The launch budget is 200 ms, so the set is loaded lazily and never on the render path:

- `warm_up()` starts one background thread that builds the syntax set and the theme into a `OnceLock`, then highlights one short line each in Rust, Python and shell so that the grammars' first-use cost is paid there, then returns (the call itself returns at once). Ready means all of that is done: the thread sets the flag that `is_loaded()` reads last, after the three warm-up lines. Setting it at the `OnceLock` step would make the first real code block pay the first-use cost (about 14 ms in release) on the render path. Measured in the scratch program (release build, one development machine): building the set took about 0.7 ms, and the first two Rust lines together about 14 ms, because each grammar compiles its contexts at first use; after that a line took about 0.12 ms (1,000 lines in 121 ms). A debug build is slower and was not measured; `cargo test` builds debug, so the 10-second polling limit used by the highlight tests, the lazy test and the demo is unverified there. Record the debug load time (until `is_loaded()`) in the pull request, and stop and report if it exceeds 5 seconds. The binary ({{P1-12}}) calls `warm_up()` after the first frame.
- While the set is not ready, a fenced block renders as plain code. It is highlighted on a later push once the set is ready, because the open block is re-rendered each push. If readiness turns on while a code block is open, that push highlights the block's whole backlog in one pass. There is no per-push line limit: the backlog is only what arrived during the load (about 15 ms of model output), so it is a few lines, and a limit would also break equivalence (section 3.4) for a text pushed in large deltas. If {{P1-12}} calls `warm_up()` late, after a long block is open, the catch-up cost is its to handle. `markdown_lazy.rs` covers the flip (section 11.6). A block that was already committed plain stays plain, because committed lines are final. This is accepted: the load takes about 15 ms in total on the measured machine, which is far less than a model needs to produce its first fence. If this turns out wrong in live use, the fix belongs to {{P1-12}}: wait for `is_loaded()` before the first code block commits. Measure the load time again on the build machine and record it in the pull request.
- No code path calls anything that blocks on the load. Rendering a document without code never starts the load. `highlight::load_starts()` counts the loads started; `highlight::is_loaded()` reports readiness; `highlight::force_not_ready(true)` makes tests deterministic (while it is set, nothing starts and nothing renders highlighted).

### 8.4 Colours

The module builds its own syntect `Theme` in code. Verified types at 5.3.0: `Theme { name: Option<String>, author: Option<String>, settings: ThemeSettings, scopes: Vec<ThemeItem> }` (use `ThemeSettings::default()`), `ThemeItem { scope: ScopeSelectors, style: StyleModifier }` with `ScopeSelectors::from_str("comment")` (`FromStr`), `StyleModifier { foreground: Option<Color>, background: Option<Color>, font_style: Option<FontStyle> }`, and `Color { r, g, b, a }`. Each scope selector gets one of seven fixed RGB values (one per named colour in the table), and the renderer maps those exact values back to ratatui's named colours; any other value, including syntect's default foreground (black, `0/0/0`), means "no colour". So the output uses the user's terminal palette and needs no colour-depth detection. Pick the seven RGB values so that none equals `0/0/0` and none equals another.

| Scope selector | Named colour | Modifier |
|---|---|---|
| `comment` | darkgray | |
| `string` | green | |
| `constant.numeric` | yellow | |
| `constant.language`, `constant.character` | yellow | |
| `keyword`, `storage.modifier` | magenta | |
| `storage.type` | cyan | |
| `entity.name.function`, `support.function` | blue | |
| `entity.name.type`, `entity.name.class`, `support.type`, `support.class` | cyan | |
| `markup.heading` | | bold |
| `markup.inserted` | green | |
| `markup.deleted` | red | |
| `invalid` | red | |

The scope names are the TextMate/Sublime conventions; the bundled grammars may use more specific scopes, and a selector matches its descendants. Because the exact scopes the bundled grammars assign to a keyword differ by language, tests assert on strings, comments and numbers only (8.5). The scratch program confirmed that a `string` selector coloured a Rust string literal (`"a"`, quotes included) and a `constant.numeric` selector coloured `42`, and that a `comment` selector coloured `// note` including the following text.

### 8.5 What tests assert

The highlight tests need the set loaded, so each begins with `ensure_highlighter()` from `tests/markdown_support/mod.rs`: it calls `warm_up()` and polls `highlight::is_loaded()` for up to 10 seconds, failing with a plain message on timeout. Only `markdown_highlight.rs` and `markdown_lazy.rs` use the global hooks; `markdown_stream.rs` and `markdown_replay.rs` never call `warm_up()`, so the highlighter's state is the same for the whole process there.

For Rust, Python and shell fenced blocks, look up the span whose text is a string literal, the span for a comment, and the span for an integer, and assert `green`, `darkgray` and `yellow`. Example inputs: `let n = 42; // note` and `let s = "a";` for Rust, `n = 42  # note` and `s = "a"` for Python, `echo "a" # note` for shell. A token that is not asserted is free to have any colour. Plain code spans have no colour.

### 8.6 Cost control inside an open block

The open code block is re-rendered on every push, so highlighting must not re-highlight everything each time. Use syntect's `ParseState` and `HighlightState` directly (both implement `Clone`; verified) with `HighlightIterator::new(&mut highlight_state, &ops, line, &highlighter)` where `ops` comes from `parse_state.parse_line(line, &syntax_set)`, rather than `HighlightLines`, which cannot be cloned.

- Cache, per open block: the language, the list of complete source lines already highlighted with their span lists, and the two states positioned after the last complete line.
- On each push, compare the block's complete lines with the cache. If the cached lines are a prefix, highlight only the new complete lines, advancing and storing the states. Otherwise (the block changed under the cache, or a different block now holds the tail) rebuild.
- The partial last line is highlighted from a clone of the cached states and never stored.
- A line longer than 1,000 characters is not highlighted, and neither is any later line of the same block: from the first such line to the end of the block the lines are plain, so the states never have to be advanced across the long line, and one pathological line cannot stall a frame. Earlier lines of the block keep their colours. The whole-text render applies the same rule, so equivalence holds.
- `MarkdownStream::lines_highlighted()` counts lines passed to the parser, so the test can prove that a second push highlights only what was added.

## 9. The benchmark

`crates/talaria-tui/benches/markdown_stream.rs`, a Cargo bench target with `harness = false`, run with `cargo bench -p talaria-tui --bench markdown_stream`.

A frame is one call to `MarkdownStream::push` returning its `StreamUpdate`, timed with `std::time::Instant`. Terminal output is not included; {{P1-11}} measures the whole client. The budget is `MARKDOWN_FRAME_BUDGET_MS`, a constant of 16 in the benchmark source; there is no environment or command-line override. The program calls `warm_up()` and waits for `is_loaded()` (up to 10 seconds, with a note on failure) before the first scenario, so code is highlighted.

### 9.1 The documents

Generated deterministically by a function in `benches/support/doc.rs`; no random numbers. Each document is built by repeating its template with a counter `i` (starting at 1) until it holds at least 65,536 bytes, then cut to exactly 65,536 bytes at the last character boundary (the cut can leave a code block unclosed or a line unfinished, which is intended).

| Name | Template (repeated; `{i}` is the counter) |
|---|---|
| `mixed-64k` | the block below, which is about 1 KB |
| `paragraph-64k` | `The quick brown fox jumps over the lazy dog and keeps running far away, round {i}. ` (no newline anywhere) |
| `code-64k` | the first line ```` ```rust ```` once, then repeated lines `    let value_{i} = compute({i}, "text"); // step {i}` each ending in a newline; the fence is never closed |
| `table-64k` | the header and delimiter rows `\| Name \| Qty \| Notes \|` and `\|:-----\|----:\|-------\|` once, then repeated rows `\| item {i} \| {i} \| note for item {i} \|` |

The `mixed-64k` block, in order, separated by blank lines:

````text

  - nested bullet {i}
- second bullet

2. second step

> a quoted line that also wraps when it is long enough to pass the width of the terminal

| Name | Qty | Notes |
|:-----|----:|-------|
| apple | {i} | fresh |
| pear | 12 | ripe fruit |

    s = "text"  # comment {i}

```

```rust

````

### 9.2 Deltas, runs and the pass rule

Deltas: the document is cut into deltas whose sizes cycle through the fixed sequence 30, 100, 45, 85, 60, 70, 55, 80, 65, 65 bytes (average 65.5, so about 1,000 deltas for 64 KB), each cut moved forward to a character boundary; the last delta takes what remains.

Each scenario runs once cold (the first run of that scenario in the process, discarded; the scenario's four runs are not interleaved with another's), then three times measured, each on a fresh `MarkdownStream`. For each measured run the program records the maximum frame time. The reported value for the scenario is the median of the three maxima, and the scenario passes when it is at or below the budget. This is the only pass rule: a frame above 16 ms in one run passes if the median of the three maxima is at or below 16, and the program prints all three maxima so that such a frame stays visible. The percentile columns (p50, p95, p99) pool every measured frame of the three runs, and the table header says so.

The program prints a table (scenario, bytes, deltas, committed lines, p50, p95, p99 and reported max frame time in milliseconds, pass or fail) and exits non-zero when any scenario fails. It also prints the machine description it can read without special access (operating system, CPU model through `std::env::consts` and a platform file or command) and whether the build is a release build. The pull request records that table. The plan names no "reference machine" (the roadmap uses the term and no document defines it); until {{P1-11}} or the operator names one, the budget is enforced on the machine that runs the benchmark, and the pull request says which.

All four scenarios must pass at 16 ms. `mixed-64k` is the roadmap's done-when. The other three are the worst cases for the "only the trailing block re-renders" design; if one cannot pass after the cheap fixes (section 8.6 caching, avoiding per-push allocation, caching wrapped lines of the open block), stop and report with the numbers rather than raising the budget.

Reference numbers from the stack evaluation, for orientation only (not budgets and not measured on this code): pulldown-cmark 0.13.5 parsed a 64 KB document in 0.114 ms, and a 300-frame naive re-parse of a growing 64 KB prefix took 17 ms in total ([research/u11-language-framework.md](../research/u11-language-framework.md) section 3.3). The stream parses only the open block, so the parser cost is expected to be small; rendering, wrapping and highlighting are the unknowns.

## 11. Test notes

### 11.1 Order and the skeleton

The test author starts with a compiling skeleton commit: `markdown/mod.rs` and its submodules containing the public items of section 2 with bodies that are `todo!()` and no logic, the dev-dependencies, the bench target, and `pub mod markdown;` in `crates/talaria-tui/src/lib.rs`. Every test then fails with the skeleton's panic rather than a compile error. The developer replaces the `todo!()` bodies.

### 11.2 Expected output

The expected rows are literal strings in the test files, compared by `assert_dump` (section 4.3). They are written by hand from section 4.4 and the rules and committed with the tests. This follows the repository's patterns guide (`docs/agents/patterns.md`, Pattern 4: compare rows with a literal list through a small helper) and avoids snapshot files, whose generated header makes hand-written files awkward. A developer who finds an expected row wrong returns it to the test author with the reason; nobody edits an expectation to make a test pass.

### 11.3 Property tests

- `streamed_equals_whole`: a generator builds Markdown from a small grammar (paragraphs with emphasis and links, headings, bullet and ordered lists with nesting, quotes, fenced code in two languages, tables, rules, blank lines, hostile characters), never emitting the text `]:`. A second generator cuts the text at arbitrary character boundaries into 1 to 40 deltas. Assert the concatenated lines equal `render_markdown`'s lines (compare the dump). Use 64 cases per property to keep `cargo test` fast, and print the failing seed.
- `no_line_wider_than_width`: for any generated text and any width from 8 to 120, every output line's display width is at most the width.
- `output_has_no_forbidden_chars`: for any string, the output contains none of the replaced characters, and removing all stand-ins' source characters from the input leaves the other characters unchanged in order.
- `finish_leaves_no_tail`: over the same generator, the update returned by `finish` always has an empty tail, and calling `finish` again returns an empty update.

### 11.4 The emulator tests

A helper `to_ansi(&[Line]) -> Vec<u8>` in `tests/markdown_support/mod.rs` writes each line as SGR sequences for bold, italic, underline, dim, strikethrough and the named colours, followed by `\r\n`. It stands in for the terminal module of {{P1-06}}; it is test code and may contain escape sequences. The emulator is `vt100::Parser::new(24, 80, 0)`.

- Wrapped output stays within 80 columns for text with CJK, emoji and combining marks; the emulator reports no wrapped row (`row_wrapped`).
- Hostile text. Input contains `\x1b[2J\x1b[H`, `\x1b]0;title\x07`, `\x1b[31m` and an RLO (U+202E). After rendering and feeding the emulator, `screen().contents()` shows the stand-in text (`␛[2J`), `cursor_position()` is where plain printing would put it, and a marker line printed before the document is still on the screen.
- Attributes. A bold word's cells report `bold()`.

### 11.5 The replay test

`tests/markdown_replay.rs` reads every `fixtures/frames/*.jsonl` file recorded by {{P1-04}} (the shape is in `docs/formats/frame-log.md` at the time this unit starts; read that document, do not guess). It walks the frames in order and splits the text into segments: a null `text` on `message.delta`, a `message.start` and a `message.complete` each end the current segment. For each segment with text, it pushes the non-null `text` values one delta per push through a fresh `MarkdownStream`, calls `finish`, and asserts that all committed lines equal `render_markdown` of the concatenated text of that segment. A segment whose text contains `]:` is skipped with a printed note (section 3.4). It must not depend on `hermes-client`; it reads the JSON lines with `serde_json`. If no fixture contains a `message.delta` with text, the test fails with a plain message (that means the {{P1-04}} fixtures are wrong, which is not this unit's to fix). It never calls `warm_up()`.

### 11.6 The lazy-load test

`tests/markdown_lazy.rs` contains one test, because the highlighter state is process-wide and tests in one file run in parallel threads of one process (each integration-test file is its own process). In order: render a document with no code and assert `is_loaded()` is false and `load_starts()` is 0; call `force_not_ready(true)`, render a Rust block, assert it is plain, call `warm_up()` and assert `load_starts()` is still 0 and `is_loaded()` is false; call `force_not_ready(false)` and `warm_up()`, poll `is_loaded()` for up to 10 seconds, assert `load_starts()` is 1; render the block again and assert the string span is green. The flip is covered in the same test: while `force_not_ready(true)` is set, also open a `MarkdownStream`, push an opening Rust fence and two code lines (plain, in the tail); after the load, push one more code line on that same stream and assert that the string span of an earlier line in its tail is now green (that push highlighted the whole backlog).

### 11.7 The adapter tests

`tests/markdown_adapters.rs` builds the cell types of {{P1-05}} directly (as the merged code allows) and calls `MarkdownCellLines::lines` for an assistant cell, a reasoning cell and a user cell. The first two must equal `render_markdown` (the reasoning one with a dim `base_style`), the third must equal `PlainCellLines`. A second test builds a `MarkdownTailSection` from a five-line tail, asserts `height` is 5, draws it into a ratatui `Buffer` of height 3 and asserts the last three lines are shown, and draws it into a buffer of height 8 and asserts that nothing outside the five lines was written.

## 12. Edge cases

| Case | Behaviour |
|---|---|
| Empty delta | empty update, no parse |
| Delta of only `\n` while a paragraph is open | stays in the tail; a lone block is not closed |
| Text with no trailing newline at `finish` | rendered as if it had one |
| A started line without its newline | never closes a block (section 3.2) |
| Unterminated fence at `finish` | rendered as a code block with what arrived |
| Closing fence line half-typed | not in `complete`, so not seen; the fence stays open |
| Fence inside a list item | committed with the list |
| Indented code after a paragraph with no blank line | part of the paragraph (CommonMark rule) |
| A link reference definition after a use | documented limitation (3.4) |
| `set_width` on an empty stream | empty update |
| `set_width` smaller than 8 | raised to 8 |
| `push` after `finish` | starts a new message |
| Width change while a code block is open | the tail is re-wrapped; committed lines stay |
| Table with a row that has fewer cells than the header | missing cells are empty (the parser supplies an empty cell; verified) |
| Table with more cells than the header | extra cells are ignored (the parser drops them; verified) |
| Very deep nesting at width 8 | available width is raised to 1 per line; no loop and no panic |
| Zero-length inline code | renders nothing |
| Emoji with a variation selector or a zero-width joiner | one grapheme, measured as a whole (section 5: both measure 2); terminals can disagree for rare sequences, a known mismatch class not handled |
| A delta that contains a lone surrogate | impossible: `&str` is valid UTF-8 |
| A very long single line without spaces (a minified blob) | hard-cut at the width |
| A code line over 1,000 characters | that line and the rest of its block are plain (section 8.6) |
| A fenced block that closes before the syntax set is ready | committed plain and stays plain (section 8.3) |
| A table with no body rows | the headers alone, one per line |
| A table whose borders and padding are wider than the width | the fallback (section 6.1) |
| `\r` as the last character of a delta | held until the next delta; `finish` shows it as `␍` |

## 13. Open items for the operator and the planner

- Soft line breaks render as line breaks. CommonMark says a soft break is a space. Chat answers usually rely on the line structure, so this unit keeps it; reverse it by changing one rule if the operator disagrees.
- Code blocks have no gutter and no indent, so copying from the terminal gives clean code. A visible frame would look better and copy worse.
- Invisible characters: U+200B, U+2060, U+FEFF, U+200D and the variation selectors are not replaced (U+200D and the selectors build emoji). The tag block U+E0000 to U+E007F is replaced, which breaks the rare subdivision-flag emoji; the operator may exempt it or show the others as stand-ins too.
- Extra syntaxes: `two-face` (research report, Codex's choice) would add TypeScript, TOML and more; this unit does not add it.
- A fenced block that closes before the highlighter has loaded stays plain (section 8.3). If live use shows this matters, {{P1-12}} can hold the first code commit until `is_loaded()`.
- The two sanitizers: `markdown::sanitize_untrusted` and {{P1-06}}'s `history::sanitize` use different stand-ins for C1 and bidirectional controls and different tab widths. The lead should align them (the Markdown form keeps the code point visible and cannot form Markdown; the tab width should be one value crate-wide).
- Links print their destination in parentheses and do not use OSC 8 hyperlinks. Adding OSC 8 means a terminal-capability check in {{P1-06}}'s module and a decision about which schemes are safe.
- The "reference machine" for the 16 ms budget is not defined anywhere in the plan (section 9.2).
- Link reference definitions across a commit (section 3.4) render as literal text when streamed.

## 14. Design reasoning and rejected options

- Reparse the pending tail on every push versus a true incremental parser. The parser is fast enough for the tail alone, and an incremental parser would be a second parser to keep equal to the first. The equivalence property test is what keeps the cheap design honest.
- Commit when the next block starts, not on a timer or on a blank line. A blank line does not end a list or a table, and a timer would commit text that later input could change.
- Decide boundaries from complete lines only. The `***` probe in section 3.1 shows a half line changing meaning.
- Named terminal colours instead of true colour. The user's palette is respected, light and dark terminals both work, and there is nothing to detect.
- Reimplement wrapping instead of using a general wrapping crate. Styled spans, hanging prefixes and grapheme-safe cuts are easier to guarantee in about a hundred lines than to adapt around a crate that works on plain strings. If the developer prefers a crate, `textwrap` with the `unicode-width` feature could replace the plain-text part; the styled-span layer stays.
- Snapshot files (`insta`) versus literal expected rows. Literal rows follow the repository's patterns guide and can be written by hand; generated snapshot files carry a header and tempt a developer to accept whatever the code printed.
- Adding the highlighter's two-face syntaxes, holding code commits until the highlighter loads, and loading it before the first frame were all considered and left out: each costs launch time, a dependency or a rule that belongs to the wiring unit (section 13).
- A Codex-style approach was considered: the OpenAI Codex files named in the roadmap (`codex-rs/tui/src/markdown_stream.rs` and `markdown_render.rs`, Apache-2.0, <https://github.com/openai/codex>) could not be read when this was written. Read them at build time for ideas; if code is copied, keep the licence notice in `NOTICE` and the file header, as the roadmap says for {{P1-06}}.

## 15. The demo program (used by the acceptance scenarios)

`crates/talaria-tui/examples/markdown_demo.rs`. It is tooling, not product: it is the only place in this unit that writes escape sequences, and it says so in its header. At start it calls `warm_up()` and waits up to 10 seconds for `is_loaded()`, so code is highlighted; if the wait fails it prints a note to standard error and goes on. Arguments:

| Argument | Meaning |
|---|---|
| `<file>` | Markdown file to render; `-` reads standard input |
| `--width <n>` | columns, default 80; a value below 8 is raised to 8 and the demo prints exactly `note: width <n> raised to 8` to standard error |
| `--stream` | feed the input through `MarkdownStream` in deltas instead of rendering it whole |
| `--delta-bytes <n>` | bytes per delta in `--stream` mode, default 64; each cut is moved forward to a character boundary |
| `--delay-ms <n>` | pause between deltas, default 0 |
| `--no-live` | in `--stream` mode print only committed lines to standard output (the tail is never drawn) |
| `--trace` | print one line per push to standard error in the form `push=<i> committed=<n> tail=<m> micros=<t>` (committed and tail are line counts) |
| `--no-color` | set `color: false`; so does a non-empty `NO_COLOR` environment variable (the module never reads the environment, the demo does it as the caller; the real application's choice is {{P1-12}}'s) |
| `--generate <name>` | use the named benchmark document of section 9.1 (`mixed-64k` and the others) as the input in place of `<file>`. An example cannot import a bench module, so `examples/markdown_demo.rs` includes the generator with `#[path = "../benches/support/doc.rs"] mod doc;` (the file has no other dependency) |

When standard output is not a terminal the demo writes plain text only (no escape sequences at all). On a terminal it writes SGR sequences for the modifiers and, unless `--no-color` is given, the colours. An unreadable file prints `cannot read <name>: <reason>` to standard error and exits with code 2.

Without `--no-live`, `--stream` on a terminal redraws the tail like this (a saved cursor position would be wrong once output scrolls the screen, so it is not used): keep `rows_drawn`, the number of tail rows printed last time. For each push: move the cursor up by `rows_drawn` rows (`CSI <n> F`, skipped when it is 0), erase from there to the end of the screen (`CSI J`), print the newly committed lines each followed by a newline, then print the new tail with a newline after each line, but only its last `terminal_rows - 1` lines when it is longer, and set `rows_drawn` to the number printed. The demo uses a width of at most the terminal's column count (from `crossterm::terminal::size()`, falling back to 80 columns and 24 rows) so no printed line wraps physically. `crossterm` is not in section 10 and the demo adds no dependency: use `crossterm::terminal::size()` only when {{P1-06}} has already made `crossterm` a dependency of `talaria-tui` (read its `Cargo.toml`), and otherwise use 80 columns and 24 rows. At the end it erases the tail and prints the final committed lines.

Fixture documents (written by the test author; used by the tests and the scenarios), under `crates/talaria-tui/tests/fixtures/markdown/`:

- `sample.md`: every construct in section 4.1 once, including a Rust and a Python block, a nested list, and a table with the header cells `Name`, `Qty` and `Notes`, where the `Name` and `Notes` cells are at least 10 characters wide and the natural table width is at most 70, so that it fits at width 80 and falls back to rows at width 24. No other line of the file starts with `Name: ` or `Qty: ` (the scenarios count those lines), no line inside a code block starts with `#` (a Python comment or a Rust attribute at the start of a line would be counted as a heading mark), it contains no `]:` (so streaming equals whole rendering exactly, test 19), and it uses only single-width characters, so characters equal columns in the width check.
- `hostile.md`: at most 15 lines; the raw bytes named in section 11.4 (a clear-screen sequence, a window-title sequence, a colour sequence, a right-to-left override) inside ordinary Markdown text. The `BEFORE` marker line in the acceptance scenario is printed by the scenario, not stored in the file.
- `wide.md`: CJK, emoji (including a joined family and a variation-selector heart) and combining marks in paragraphs, a list and a table.

These three files are hand-written by design. They contain no absolute path, user name or profile name, and the escape bytes in `hostile.md` live only in this test fixture, never in `src/`.
