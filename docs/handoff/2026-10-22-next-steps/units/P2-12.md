## 1. Where this unit sits

Roadmap row ([07, phase 2](../07-roadmap-and-work-units.md#phase-2--coding-parity)): "P2-12 Themes. Apply Hermes skins; light and dark detection; reduced motion. Hermes calls: `gateway.ready` skin, `skin.changed`. Tier: Haiku xhigh." Parity row ([04, Claude Code parity checklist](../04-prior-art.md#claude-code-parity-checklist)): "Themes. Hermes skins arrive in `gateway.ready`; client applies them. Phase 2."

Claude Code's equivalent is `/theme`: an `auto` option that matches the terminal's light or dark background, light and dark variants, colour-blind variants, ANSI themes that use the terminal's palette, and custom themes (research report u12, features `int.theme` and slash command `/theme`). Talaria does not invent its own theme catalogue: the skin is Hermes's (principle "thin cockpit, thick backend", [05 §Principles](../05-architecture.md#principles)). What Talaria adds is what a terminal client must decide for itself: light or dark, how many colours the terminal has, readability against the real background, `NO_COLOR`, and reduced motion.

Hermes's own terminal UI has nine built-in skins with light-terminal detection ([03 §5](../03-hermes-today.md#5-hermess-own-terminal-ui-is-the-bar-to-clear); research report u07 §3.12). It has no reduced-motion setting (u07, comparison table). Talaria's Python client had `ui.reduced_motion` (the 0.6 configuration document); this unit carries that key name forward.

## 3. Wire shapes

Event envelope (every event): `{"jsonrpc":"2.0","method":"event","params":{"type":"<name>","session_id":"<id or empty>","payload":{...}}}`. The session id is `""` for the watcher's broadcast (H10) and the session's id for the per-session publish (H13).

`gateway.ready` example (default skin, abridged):

```json
{"jsonrpc":"2.0","method":"event","params":{"type":"gateway.ready","payload":{
  "skin":{"name":"default","colors":{"ui_accent":"#FFBF00","banner_border":"#CD7F32","ui_ok":"#4caf50"},
          "light_colors":{"ui_accent":"#D89B04","ui_ok":"#2E7D32"},"dark_colors":{},
          "branding":{"agent_name":"Hermes Agent"},"banner_logo":"","banner_hero":"",
          "tool_prefix":"┊","help_header":"(^_^)? Commands","customCSS":""},
  "change_events":true,"heartbeat":true,"replay_epoch":"<epoch>","session_authority":true}}}
```

`runtime.describe` request and result (abridged): `{"jsonrpc":"2.0","id":7,"method":"runtime.describe","params":{}}` returns `{"instance_id":"<id>","profile_id":"<profile>","authority_epoch":3,"capabilities":[...],"session_create":{"sources":[...],"parameters":[...]},"skin":{...}}`.

`config.set` for the skin: request `{"jsonrpc":"2.0","id":8,"method":"config.set","params":{"session_id":"<sid>","key":"skin","value":"ares"}}`; result `{"key":"skin","value":"ares"}`. Refusals (H27) arrive as `{"jsonrpc":"2.0","id":8,"error":{"code":4001,"message":"permission_denied","data":{"reason":"permission_denied"}}}`; the reason is one of `invalid_params`, `permission_denied`, `profile_mismatch`, `storage_unavailable` (code 5001 when SQLite fails, 4001 otherwise) or `runtime_draining`. P1-02 decodes it to `CallError::Rpc(RpcError)` whose `reason` is `data.reason`; Talaria branches on `reason`, never on the code.

`config.get` for the configured name: `{"jsonrpc":"2.0","id":9,"method":"config.get","params":{"key":"skin"}}` returns `{"value":"ares"}`.

`skin.changed` after `/skin ares`, per session: `{"jsonrpc":"2.0","method":"event","params":{"type":"skin.changed","session_id":"<sid>","seq":<n>,"replay_epoch":"<epoch>","payload":{"name":"ares",...}}}`. It carries `seq` and is kept for replay (H26), so P1-03 may deliver it again, marked `replayed`, after a reconnect. Hermes publishes it before it returns the `config.set` result (`await _broadcast_skin(connection)` precedes `return`, `gateway/session_tui_config.py` lines 198-200), so on the same socket the event normally arrives before the reply.

## 4. How Hermes's own clients use these calls

**Hermes's terminal UI (`ui-tui`).** In `ui-tui/src/app/createGatewayEventHandler.ts`: on `gateway.ready` it applies `payload.skin`, and on `skin.changed` it applies the payload (lines 1111-1121, 953); `themeForSkin` (lines 115-133) picks the polarity overlay, `light_colors` on a light terminal and `dark_colors` on a dark one, merged over `colors` only when non-empty. In `ui-tui/src/theme.ts`: `fromSkin` (lines 840-971) builds seeds from key chains such as `ui_accent` then `banner_accent`, derives secondary tones, and runs contrast floors with `liftForContrast` (H28) against the real or assumed background: display colours at least 1.45:1 on dark and 1.18:1 on light, semantic colours (ok, error, warn, status) at least 2.2:1 and 1.6:1 (lines 474-477, 517-543); the assumed background is `#101014` for dark and `#ffffff` for light (lines 548-556). Light detection (`detectLightMode`, `theme.ts` lines 687-770) checks, in order, `HERMES_TUI_LIGHT`, `HERMES_TUI_THEME`, a cached background hex (Rec. 709 luma at or above 0.6 means light, otherwise dark, and nothing later is read; lines 655, 664-685 and 731-734), `COLORFGBG` (last field 7 or 15 means light; any other 0 to 15 means dark), then a `TERM_PROGRAM` allow-list holding `Apple_Terminal` (line 648). Back in `createGatewayEventHandler.ts`: it queries OSC 11 (background) and OSC 10 (foreground) at start; an answer of exactly `#000000` is distrusted, because terminals built on xterm.js and tmux report it when they do not know (lines 233 and 315-360); a foreground answer infers polarity when the background is distrusted (lines 295-313: luminance at or above 0.45 means dark, at or below 0.2 means light, pure black or white ignored). When a skin authors `background`, the TUI repaints the whole terminal background and default foreground with OSC 11 and OSC 10 (`paintTerminalDefaults`, lines 194-215). It caches the last resolved theme on disk to avoid a flash on the next launch (`ui-tui/src/lib/themeBoot.ts`). `/skin` with no argument calls `config.get {key:"skin"}`; `/skin <name>` calls `config.set {key:"skin", value}` (`ui-tui/src/app/slash/commands/session.ts` lines 589-611).

**Hermes Desktop.** It records the skin from `gateway.ready` without applying it, and repaints only on a `skin.changed` whose name differs from what it last applied, so a reconnect never overrides the user's own desktop theme choice (`apps/desktop/src/themes/backend-sync.ts` lines 1-100; `apps/desktop/src/app/session/hooks/use-message-stream/gateway-event/lifecycle.ts` lines 67-74). Its visual theme settings are Electron-local (research report u06, rows F72 and F89: skip for a terminal client).

**What Talaria takes and what it leaves.** Takes: the payload as the single source of skin colours; the polarity overlay rule; key fallback chains; contrast floors and assumed backgrounds; the OSC 11 and OSC 10 probe with the pure-black distrust rule; `COLORFGBG` and the `Apple_Terminal` hint; `/skin` through `config.get` and `config.set`. Leaves: repainting the terminal's background (Talaria is inline-first, section 14), the on-disk theme cache, branding strings and banner art, `customCSS`, and the derived tone ladder (Talaria has fewer surfaces and no filled panels).

### 5.1 `talaria-core::appearance` (pure)

```rust
// crates/talaria-core/src/appearance.rs
pub type ColorMap = std::collections::BTreeMap<String, String>;

#[derive(Clone, Debug, PartialEq, Eq)]
pub struct Skin {
    pub name: String,              // "" when the payload had none
    pub colors: ColorMap,          // only string values are kept
    pub light_colors: ColorMap,
    pub dark_colors: ColorMap,
}
impl Skin {
    /// None for an empty payload (`{}`, H7) or one with no name and no colours.
    pub fn from_payload(payload: &hermes_contract::SkinPayload) -> Option<Skin>;
    /// Same rules over a raw JSON value (JSON `null` gives None); every non-string colour value
    /// is skipped and returned, in map order then key order.
    pub fn from_value(value: &serde_json::Value) -> (Option<Skin>, Vec<SkippedValue>);
}

/// A colour value that was not a JSON string (null, number, object, array, boolean).
#[derive(Clone, Debug, PartialEq, Eq)]
pub struct SkippedValue { pub map: SkinMap, pub key: String }
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum SkinMap { Colors, LightColors, DarkColors }

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum SkinSource { None, GatewayReady, RuntimeDescribe, Changed }

#[derive(Clone, Debug, Default)]
pub struct AppearanceState { /* skin: Option<Skin>, source; no pending request state */ }

pub enum AppearanceInput {
    // A new connection: the launch's OpenConnection.describe, or the describe called after a reconnect.
    // `ready` is the gateway.ready skin when the app has it (today it does not: None), `describe` the
    // describe result's `skin` value (None when the key is absent or null).
    Handshake { ready: Option<serde_json::Value>, describe: Option<serde_json::Value> },
    SkinChanged { payload: serde_json::Value, replayed: bool }, // from LinkEvent::Inbound { item, replayed }
    // The `skin` of a runtime.describe result outside a handshake: after `/skin` (requested: None)
    // or after `/skin <name>` succeeded (requested: Some(name)).
    Described { payload: serde_json::Value, requested: Option<String> },
}

#[derive(Clone, Debug, PartialEq, Eq)]
pub enum AppearanceChange {
    Unchanged,
    Changed,
    // Hermes fell back to `default` for a requested name; `redraw` says whether the colours changed.
    UnknownSkin { requested: String, using: String, redraw: bool },
}

impl AppearanceState {
    pub fn skin(&self) -> Option<&Skin>;
    pub fn source(&self) -> SkinSource;
    /// The non-string values of the payload that produced the current skin (empty when none).
    /// Replaced whenever the skin is replaced; kept when an input leaves the skin unchanged.
    pub fn skipped(&self) -> &[SkippedValue];
    pub fn update(&mut self, input: AppearanceInput) -> AppearanceChange;
}
```

`skipped` is how the `/theme` line `Ignored skin values` learns the keys of JSON `null` and number colours: `Skin` keeps only strings, so the skipped keys travel beside it, from `AppearanceState::skipped()` into `ThemeInputs.skipped` (5.2). `Skin` equality stays over its four fields.

The exact payload types come from P0-03's generated module; use whatever path it emits. If converting the generated `SkinPayload` is awkward, take the raw `serde_json::Value` of the payload (`OpenConnection.describe` and inbound items hold decoded types; the raw value is available through `serde_json::to_value`). Names in this block are this unit's and may be adjusted if rustdoc explains why; behaviour may not.

Rules for `update`:

1. `Handshake`: a new connection. If `describe` is `Some` (the result had a non-null `skin`, even `{}`), it decides; the source is `RuntimeDescribe`; `{}` gives no skin. Otherwise, if `ready` is `Some`, it decides; the source is `GatewayReady`. If both are `None`, the current skin is kept and the result is `Unchanged` (at launch the current skin is none, so the result is no skin). Hermes v0.22.4 always sends the describe `skin` key (H31), so the keep-current branch only matters for an older or different gateway. Otherwise the result is `Changed` when the resolved `Option<Skin>` differs from the previous one, else `Unchanged`.
2. `SkinChanged { replayed: false, .. }`: replace the skin (source `Changed`); `Unchanged` when equal. `SkinChanged { replayed: true, .. }`: always `Unchanged`, the skin is kept (the describe after the reconnect is newer; H26).
3. `Described { payload, requested }`: apply like a live `SkinChanged`, with source `RuntimeDescribe`. Then, when `requested` is `Some(name)`, the resolved skin's `name` is `"default"`, and `name` is not `"default"`, return `UnknownSkin { requested: name, using: "default", redraw }`, where `redraw` is whether the colours changed. Any other name difference (a user skin file whose YAML `name` differs from its file name, H17) is not an unknown skin. There is no pending request state, so an unrelated `skin.changed` can never produce a false notice. Hermes publishes the per-session `skin.changed` before it replies to `config.set` (section 3), so that event is applied as a plain change, and the describe result is the one checked.
4. `Skin` equality is field-wise over the four kept fields, so a repeated broadcast (H10 and H13 can both reach Talaria) is `Unchanged` and draws nothing.

## 6. Detection of the terminal background and colour depth

### 6.1 The probe

P1-06's start-up probe writes one combined query and reads replies until the primary device attributes reply or a 200 ms deadline. This unit inserts two queries before the device-attributes query: `ESC ] 11 ; ? ESC \` (background) and `ESC ] 10 ; ? ESC \` (foreground). Terminals that support them answer `ESC ] 11 ; rgb:RRRR/GGGG/BBBB` followed by `ESC \` or BEL (0x07); terminals that do not simply skip them, and the device-attributes reply still ends the wait, so the probe costs no extra time on any terminal that answers device attributes. `parse_probe_reply` learns the two replies in any order among the others and ignores garbage, exactly as it does today. A colour reply that arrives after the device-attributes reply or after the 200 ms deadline is discarded by P1-06's existing drain (it discards input until 50 ms pass quietly, at most 250 ms more; P1-06 REQ-1), so it never reaches the key reader as typed input and the colour counts as unanswered. Whether Herdr and tmux answer OSC 10 and 11 in time is recorded in the journal from UAT-6. `ProbeReply` gains `colors: TerminalColors` (both `None` when unanswered); add `Default` where needed so existing struct literals in P1-06's tests can use `..Default::default()` (the only edit to those tests).

### 6.2 Parsing a colour reply

`parse_osc_color` accepts `ESC ] <10|11> ; <spec> (BEL | ESC \)` where `<spec>` is:

- `rgb:<r>/<g>/<b>` with 1 to 4 hex digits per channel (each channel may have its own width). Scale each channel: `value * 255 / (16^digits - 1)`, rounded to nearest. `rgb:ffff/ffff/ffff` is white; `rgb:f/0/0` is red; `rgb:1e1e/1e1e/1e1e` is `#1e1e1e`.
- `#rrggbb` (some terminals answer this way).
- Anything else (including `rgba:`) is unknown: `None`.

### 6.3 Polarity order

First match wins:

| Step | Signal | Rule | Source shown by `/theme` |
|---|---|---|---|
| 1 | `/theme light` or `/theme dark` this session | as typed | `set with /theme` |
| 2 | `TALARIA_THEME` | `light` or `dark`, case-insensitive, trimmed; `auto` or empty falls through; anything else falls through with the notice of section 10 | `TALARIA_THEME` |
| 3 | `[theme] mode` | `light` or `dark`; `auto` falls through | `config.toml` |
| 4 | OSC 11 background | ignored when exactly `#000000` (xterm.js hosts and tmux report it when they do not know); otherwise it decides both ways: light when `luma709 >= 0.6`, else dark (H29); steps 5 to 8 are then never read | `terminal background #rrggbb` |
| 5 | OSC 10 foreground | used only when step 4 gave nothing; ignored when `#000000` or `#ffffff`; relative luminance `>= 0.45` means dark, `<= 0.2` means light, between is ignored | `terminal text colour #rrggbb` |
| 6 | `COLORFGBG` | last `;`-separated field, digits only: `7` or `15` means light; any other value from 0 to 15 means dark; anything else is ignored | `COLORFGBG` |
| 7 | `TERM_PROGRAM` | `Apple_Terminal` means light (its default profile is light; a dark profile normally sets `COLORFGBG`, which step 6 reads first) | `TERM_PROGRAM` |
| 8 | default | dark | `default (no signal)` |

Steps 4 to 7 come from Hermes's terminal UI (section 4, H29). Example: background `#1e1e1e` (luma about 0.12) with `COLORFGBG=0;15` is dark, source `terminal background #1e1e1e`; the same background with `TERM_PROGRAM=Apple_Terminal` is dark too. There is no on-disk cache and no operating-system appearance probe in this unit (section 14).

| Step | Signal | Result | `DepthSource` | Source shown by `/theme` |
|---|---|---|---|---|

## 7. Resolving a skin into Talaria's styles

### 7.1 Pipeline

1. Depth `None`: every component gets its default theme with every colour removed: `MarkdownOptions.color = false`, and every `Style` in `Theme.status`, `Theme.composer`, `Theme.reasoning` and `Theme.tool` (when present) has `fg`, `bg` and `underline_color` set to `None` (so the status line's phase 1 named colours go too). Modifiers stay. "Every component" means the themed components of 5.3; cells this unit does not theme are listed there.
2. No skin, `follow_hermes_skin = false`, or depth `Ansi16`: every component gets its own `Default` theme, byte for byte (test 14). This is the phase 1 look.
3. Otherwise build the effective map: `colors`, then the overlay for the polarity (`light_colors` for light, `dark_colors` for dark) merged over it when the overlay is non-empty.
4. For each role (7.2) take the first key in its chain whose value parses (H22). No parseable value: the role keeps its default style. **Ignored values** (the `/theme` line): the set of keys that appear in any 7.2 chain and either (a) hold a string in the effective map that does not parse, or (b) are in `ThemeInputs.skipped` for `colors` or for the overlay in use, unless the overlay in use supplies a string for that key. Keys outside every 7.2 chain are never counted (for example a `null` `completion_menu_bg`), whether or not the chain reached them. The count is the size of the set; the line lists the first three keys in byte order. Steps 1 and 2 report no ignored values (no skin is resolved).
5. Contrast: the reference background is the trusted terminal background when polarity came from step 4 of 6.3; in every other case (polarity pinned by steps 1 to 3, or decided by steps 5 to 8) use `#ffffff` for light and `#101014` for dark. Raise each foreground with `ensure_contrast` to at least the floor: display roles 1.45 (dark) or 1.18 (light); semantic roles 2.2 (dark) or 1.6 (light). These are Hermes's floors (section 4).
6. `Ansi256`: convert each colour with `to_ansi256` (6×6×6 cube 16-231 with levels 0, 95, 135, 175, 215, 255, and grays 232-255 at `8 + 10 n`; nearest by squared RGB distance; ties go to the lower index). `TrueColor`: `Color::Rgb`.
7. Modifiers from the default theme are kept (bold headings, underlined links, dim meta) unless a row below says otherwise. When a role takes a skin colour, a default `dim` on that element is dropped (the skin's dim colour replaces it).

`ensure_contrast(fg, bg, min)` is Hermes's `liftForContrast` (H28), copied exactly: if `contrast_ratio(fg, bg) >= min`, return `fg` unchanged. Otherwise, when `relative_luminance(bg) > 0.5`, repeat `r -= ceil(r * 0.1)` (and the same for `g`, `b`) while the ratio is below `min` and the colour is not black; else repeat `r = min(255, r + ceil((255 - r) * 0.1))` (and `g`, `b`) while below `min` and not white. Return the result. The direction depends on the background's luminance, not on polarity: a mid-grey `#999999` (luma 0.6, so light polarity; relative luminance about 0.32) is brightened toward white, as in Hermes. Only the floor depends on polarity. Worked values (test 8): `#FFF8DC` on `#ffffff` at 1.18 (ratio about 1.07) gives `#e5dfc6` after one step (ratio about 1.34); `#202020` on `#101014` at 1.45 gives `#373737` after one step; `#C0C0C0` on `#1e1e1e` at 1.45 (ratio about 9.2) is unchanged.

Worked values at resolve level (test 15b): `#F1E6CF` on `#ffffff` has ratio about 1.24, above the light display floor 1.18 and below the light semantic floor 1.6. As a display role (the prompt marker) it stays `#F1E6CF`; as a semantic role (status success) it becomes `#c2baa7` after two steps (ratio about 1.93). Against `#1e1e1e` its ratio is about 13.5, so a resolver that wrongly measured against the probe background after a `/theme light` override would leave it unchanged.

## 8. Reduced motion

Today no Talaria component animates: P2-01 (tool cells), P2-02 (pager) and P2-05 (shell rows) each chose a static glyph and a once-per-second seconds counter, and nothing redraws when nothing changes (budget "Idle: zero frames when nothing changes", [05 §Performance budgets](../05-architecture.md#performance-budgets)). Hermes's `thinking.delta` text (its kaomoji spinner text) is not shown by Talaria (P1-05 keeps it only as `activity()`). So this unit's job for reduced motion is:

1. Resolve `Motion` (`TALARIA_REDUCED_MOTION` beats `[ui] reduced_motion`, default full) and report it in `/theme`.
2. Make blinking impossible in both modes: `resolve` strips `SLOW_BLINK` and `RAPID_BLINK` from every style it emits, and a guard test (test 34) fails if any non-test source under `crates/` (`src/`, `examples/`, `benches/`) names those modifiers or writes an SGR sequence that turns blink on. Test files may name the modifiers, because test 19 checks for their absence.
3. Give later units one value to obey. The rule they must follow, written into `docs/themes.md`: under `Motion::Reduced`, no glyph or colour changes on a timer; elapsed-time numbers and real progress may still update, at most once per second; scrolling and overlay changes jump straight to their end state. Under `Motion::Full` the same is recommended; any future animation must be off under `Reduced` and must not break the idle budget.

### 9.1 `/skin`

`/skin` with no argument calls `config.get {key:"skin"}` (adding `session_id` of the foreground session if there is one), then `runtime.describe {}`, and feeds `Described { payload, requested: None }`. Let C be the configured name (H15: missing, `null` or blank means `default`) and R the resolved skin's `name`.

| Case | Shown |
|---|---|
| no skin (describe skin `{}`, `null` or absent) | `Skin: none. Hermes sent no skin, so Talaria uses its own colours.` |
| R is `default` and C is not `default` | `Skin: default. The profile asks for "<C>", which Hermes could not find, so it uses default.` |
| R differs from C otherwise (a user skin file whose YAML `name` differs from its file name, H17) | `Skin: <R> (Hermes profile <profile>, set as "<C>")` |
| R equals C | `Skin: <R> (Hermes profile <profile>)` |
| `config.get` or `runtime.describe` refused | `Talaria could not read the skin from Hermes (<reason>).` |
| either call's outcome unknown | `Hermes did not answer. Run /skin again.` |

Which `CallError` gives which row, for every call in this section: `Rpc(e)` is "refused"; `TimedOut`, `Unknown` and `BadResult` (a reply arrived but did not decode, so a write may have happened) are "outcome unknown"; `NotConnected`, `Encode` and `InvalidTimeout` (nothing reached Hermes) show `Talaria could not reach Hermes, so nothing was changed. Try again when the status line shows it is connected.` for `config.set`, and the "refused" line with the reason `not connected` for `config.get` and `runtime.describe`.

`<reason>` in every line of this section is `RpcError.reason` when it is `Some` (P1-02 gives `reason: Option<String>`); otherwise `RpcError.message` when it is not empty; otherwise the words `no reason given`.

`/skin <name>`:

| Input or result | Calls | Shown |
|---|---|---|
| bad name | none | `Usage: /skin [name]. A skin name is letters, digits, dot, dash or underscore, up to 64 characters.` |
| `config.set` succeeds | `config.set {session_id?, key:"skin", value:<name>}`, then `runtime.describe {}` | `Skin set to "<value>" for profile <profile>. Hermes windows with a session open on this profile change too.` |
| then describe gives `UnknownSkin` (R is `default`, value is not) | | adds `Hermes has no skin named "<name>"; it is using "default". Run /skin default to clear the setting.` |
| then describe gives another R that differs from the value | | adds `Hermes calls this skin "<R>".` |
| then describe gives no skin (`{}`, `null` or absent: Hermes's skin engine failed, H7) | | adds `Hermes sent no skin for "<value>", so Talaria uses its own colours.` The skin becomes none (phase 1 colours); it is not `UnknownSkin`. |
| then describe is refused or unanswered | | adds `Talaria could not fetch the new skin (<reason>). Run /skin to refresh.` (`<reason>` is `no answer` for an unknown outcome). The per-session `skin.changed` normally arrived already and was applied. |
| `config.set` refused (H27) | | `Hermes refused to change the skin (<reason>).`; for `permission_denied` a second line `This connection may not change settings.` |
| `config.set` outcome unknown (`CallError::Unknown`, `TimedOut` or `BadResult`) | | `The skin change may or may not have been saved. Run /skin to check.` |
| `config.set` not sent (`NotConnected`, `Encode`, `InvalidTimeout`) | | `Talaria could not reach Hermes, so nothing was changed. Try again when the status line shows it is connected.` |

Valid name: `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`. The profile name is P1-01's display name (`default` for the Hermes home). The "Hermes windows with a session open" wording follows H30: only sessions of this authority with subscribers receive the per-session event.

Agents and tests never run `/skin <name>` against a live gateway unless the operator has allowed it for the throwaway `fixture` profile (it writes that profile's `config.yaml`).

## 14. Design reasoning and rejected options

- **Do not repaint the terminal background (rejected: Hermes's OSC 11 and OSC 10 repaint).** Talaria's finished output lives in native scrollback (ADR draft 0009). Repainting the background changes the look of everything above, including other programs' output, and must be undone on every exit path, including crashes. Without a painted background, body text keeps the terminal's own foreground and stays readable whatever the skin. The cost: skins that rely on their own background (for example a dark skin on a light terminal) look less like Hermes's terminal UI. Raised to the operator.
- **Skin from `runtime.describe` over `gateway.ready`.** H5 and H6: for a served profile that is not the launch home, only describe is resolved for the right profile. The roadmap P2-12 row and the parity "Themes" row still say the skin arrives in `gateway.ready`; this decision supersedes them, and the handoff documents are not edited by this unit.
- **`{}` means no skin.** Hermes's comment says its clients treat `{}` as "the default theme" (H7). For Talaria the default theme is its phase 1 look, so drawing phase 1 colours is the same intent. Recorded in `DECISIONS.md`.
- **Journal entries (issue AC-9).** `DECISIONS.md` gains at least three entries whose `###` titles contain these words exactly: `Skin from runtime.describe` (decision 2 of the issue), `never repaints the terminal background` (decision 3), `Sixteen colours means no skin` (decision 7). `docs/themes.md` states the reduced-motion rule of section 8, including the words `at most once per second`.
- **Copy Hermes's colour parser and contrast lift exactly (rejected: a simpler linear mix and a stricter parser).** A user skin that Hermes draws must not be counted as "ignored" by Talaria (bare hex is common in YAML), and the same skin should come out the same colour in both clients.
- **Unknown skin only when Hermes fell back to `default`.** Hermes finds user skins by file name but reports the YAML `name` (H17), so comparing names would warn falsely about every renamed user skin.
- **No pending request state.** The requested name travels with the describe result (`Described { requested }`), so an unrelated `skin.changed` can never be compared with it, and nothing needs clearing when a call fails.
- **One retry for the reconnect describe (rejected: retry until success; rejected: rely on the next `skin.changed`).** The watcher broadcasts only on change (H30), so waiting for an event can leave the skin wrong indefinitely; unlimited retries add load during an outage. One retry plus `/skin` as a manual refresh is the bounded middle.
- **No on-disk theme cache (rejected: Hermes's boot cache).** The handshake completes before Talaria commits any history, so committed lines never flash. Only the composer and status line can show default colours for the tens of milliseconds before the handshake, and they are redrawn. A cache adds a file to write, invalidate and keep private.
- **No operating-system appearance probe (rejected for now).** Hermes runs `defaults read -g AppleInterfaceStyle` 1.5 s after start on macOS. That is a subprocess and a late re-theme. Raised to the operator.
- **Polarity is decided once (rejected: re-deciding on P2-13's re-probe).** A re-theme in the middle of a session would recolour only part of the screen and confuse the reader; `/theme` is the explicit way to change it.
- **`/theme light|dark` is session-only.** P1-08 leaves writing `config.toml` out of scope; a command that silently edits the user's file would surprise them.
- **Hermes's `display.tui_theme` is not read.** It is the Hermes terminal UI's pin; Talaria has its own `[theme] mode`. Raised to the operator.
- **Sixteen colours means no skin.** Mapping hex to the user's 16 palette entries would guess at colours the user configured differently.
- **Reduced motion scope.** No current component animates, so this unit's deliverable is the setting, the no-blink guard and the written rule; each later unit that adds motion tests its own compliance against `Theme.motion`.
