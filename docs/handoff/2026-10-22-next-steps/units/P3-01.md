## 0. What this unit is, in one paragraph

Talaria needs to know, at every moment, which Hermes sessions exist on this machine, what each is doing, and which of them is waiting for the operator. The fleet registry is that knowledge: a pure state machine in `talaria-core` (`talaria_core::fleet`), fed by an application service in `talaria-app` (`talaria_app::fleet`) that holds one long-lived, host-scoped connection to the Hermes gateway, lists sessions per served profile, polls their liveness, reads pending approvals of sessions nobody in this Talaria is attached to, and folds in the live state of sessions this Talaria is attached to (the foreground session today; peeked or launched sessions later). It draws nothing in the terminal UI: the fleet overlay is `P3-02`, notifications and counters are `P3-06`. It ships one command, `talaria fleet list`, so the registry is observable and scriptable (the counterpart of Claude Code's `claude agents --json`).

What it does not deliver, for the parent to record: requirement R6's per-session cost for sessions nobody attached (Hermes lists carry no cost), requirement R5's "what finished while Talaria was closed" across restarts (no disk state), and workflow agents (`source: "tool"`, [workflows decision 2](../06-workflows.md)), which Hermes's live feeds skip (F35); the workflow runner reports its own sessions through `observe_subscribed`.

## 3. Design: where each piece of knowledge comes from

### 3.1 Why the registry does not attach to every session

Events (approvals, outcomes, activity) reach only attached transports (F16). Attaching every session would be the simplest way to know everything, but at v0.22.4 every attach returns the whole history (F17), cancels the session's pending close and re-reads its settings. With dozens of sessions across many profiles that is megabytes per refresh and it changes Hermes's own housekeeping. So:

- **Attached sessions** (today the foreground session; later sessions `P3-02` peeks or `P3-03` launches; workflow sessions) are reported to the registry by their owner as a `SubscribedView`, derived from `P1-05`'s `SessionState`. These rows have exact prompts and exact outcomes.
- **Everything else** is read with cheap reads that have no side effect on a live session: `session.list` (membership and labels), `session.active_list` (liveness), `approval.pending` (what an unattached waiting session asks), `session.events.since` (the outcome of an unattached turn that just ended).

Two architecture rules are adapted, and the adaptations are recorded in `DECISIONS.md` (section 15): the rule "after a reconnect, call `session.resume` when the gateway says a snapshot is required" applies to attached sessions only; for an unattached session `snapshot_required` means the outcome is `Unknown`. The rule "replies from a replaced connection never update state (per-connection generation)" is kept in the service (5.7).

### 3.2 Why polling is needed at all

`sessions.changed` fires when the session table's digest moves (F24): a new session, a new message, a title, an end. It does not fire when a running turn starts waiting for an approval, because nothing in the table changes. So liveness must be polled. Talaria polls in two tiers: "hot" profiles (a row in `NeedsYou` or `Working`, or an outcome probe in flight) every 2 s, and every other in-scope profile every 4 s, spread evenly over the interval so the calls do not bunch. A 30 s backstop re-discovers profiles and re-reads rosters. `Done` and `Failed` rows do not make a profile hot: polling them finds nothing new.

Why a cold tier rather than "hot only": in an idle profile the first sign of a new turn would otherwise be `sessions.changed`, which may not reach the fleet link for a sibling profile (U1), and a short turn can start and end between two polls. With 4 s cold polls, a new approval in an idle profile reaches the queue within about 4 s plus two calls, whatever U1 says.

Load: with 30 served profiles, all cold, 7.5 `session.active_list` calls a second. `session.list` answered in about 1 ms on the test machine with 26 served profiles ([03-hermes-today.md](../03-hermes-today.md#2-how-a-third-party-client-attaches-verified-live)); `session.active_list` reads the same rows (F35) but was not timed. Operator question 2 on the issue asks whether this is acceptable; `cold_poll_ms` is configurable (section 7).

### 3.3 Cadence compared with Hermes's clients

Desktop: 1.5 s without change events; with them, 30 s plus a re-pull on each `sessions.changed` (F30). Desktop sees approvals of its own sessions as events, because it is attached to them. Ink terminal UI: 1.5 s, with `session.list`, which has no waiting status. Talaria: 2 s hot, 4 s cold, 30 s backstop, plus an immediate refresh on `sessions.changed`.

### 3.4 Why one long-lived host-scoped connection

Listing other profiles needs a host-scoped ticket (F6, F31). `P1-12`'s foreground link is profile scoped; `P2-07`'s side connection is short-lived and exposes no event stream. The registry needs `sessions.changed` and heartbeats, so it owns its own long-lived connection, the "fleet link". Draft decision 0007 says one connection per process, with a second as an exception path; `P2-07` raised the first exception (operator question 4 on `PH2B`); this unit extends it and asks the operator again (issue, operator question 1). If the operator prefers to host-scope the foreground link instead, `FleetService::start` takes a client instead of dialing; that change is a stop condition, not an improvisation.

Draft decision 0007's point 3 says Talaria answers every server request. The fleet link attaches to no session, so Hermes sends it none (F33). A request that arrives anyway is refused at once with `P1-09`'s not-supported reply, whatever `policy_for` returns (it would return `Masked` for sudo, secret and vault kinds), and one diagnostic is recorded per connection. This exception is part of the `DECISIONS.md` entry for the fleet link.

## 5. State rules

### 5.1 Row membership

- A row exists for every `(profile, session_id)` in the latest successful roster of an in-scope profile, and for every key a subscriber reported (`Subscribed`), even before the roster lists it.
- The registry keeps the latest successful liveness items of each profile. When a roster creates a row, the kept item for it (if any) is applied at once, as if the liveness reply had arrived after the roster. So the order in which roster and liveness replies arrive does not matter.
- A liveness item with status `waiting` and no roster row (a hidden chat, or a session past the 200-row cut) creates a row with `unlisted: true`, `title` and `model` from the item, and the normal `waiting` effects. From then on an `unlisted` row follows the same state rules (5.2) as a listed row, so a turn it finishes gives `Done` or `Failed` with attention, like any other row. It is removed silently, with its items, as soon as its state is `Idle` (no unacknowledged outcome held), or when it is acknowledged. A `Done` or `Failed` unlisted row stays until acknowledged and counts toward the cap of 50 kept rows below. If a roster lists it, `unlisted` becomes false and the ordinary membership rules apply. Other liveness items without a row create nothing and are counted in `Diagnostic("<n> live sessions in <profile> are not in its list")` once per profile per registry.
- A row absent from **two consecutive** successful rosters of its profile, not subscribed and not `unlisted`, is removed, unless its state is `Done` or `Failed` and not acknowledged: then it stays with `gone: true` until acknowledged. `Acknowledge` on a gone row removes it. At most 50 gone rows and unacknowledged `Done`/`Failed` unlisted rows are kept together (oldest `state_since` dropped first, silently).
- A profile that leaves `served` at a discovery (parked or gone) drops its rows silently and gets `Parked { reason }` or `OutOfScope`.

### 5.2 Row state (unsubscribed rows)

Inputs per row: the latest status `s` from a successful liveness reply, the item's `message_count`, and the row's memory: `turn_seen` (a running status, `working`, `starting`, `waiting` or other, seen since the last outcome), `last_live_count` (the `message_count` of the previous applied liveness item, absent at first sight), `outcome`, `acknowledged`.

| Latest status | Effect on the row |
|---|---|
| `waiting` | `turn_seen = true`; effect `FetchApprovals` (rate: `approvals_gap` per row, 6.2); state `NeedsYou` if the row has a queue item, else `Working` until the approvals reply (or its failure) gives it one (5.4). The gap is one call; it keeps the invariant below and lets the first item arrive with its detail |
| `working`, `starting`, `Other(_)` | `turn_seen = true`; state `Working`; `Other` also gives one `Diagnostic` per distinct value |
| `idle` with `turn_seen` | the row's non-exact items are settled (5.4); state stays as it was until `OutcomeProbed`, except that a `NeedsYou` row left with no item shows `Working` meanwhile (invariant below); effect `ProbeOutcome` once (reason: turn ended); `turn_seen = false` |
| `idle` without `turn_seen`, `message_count > last_live_count` | a turn started and ended between two polls: state stays; effect `ProbeOutcome` once (reason: count rose) |
| `idle` otherwise | `Done`/`Failed` if an unacknowledged outcome is held, else `Idle` |
| missing from a successful liveness reply, `turn_seen` | the session left the live listing (closed, F34): its non-exact items go; state `Done`, outcome `Unknown`, not acknowledged, attention `Done`, `turn_seen = false`; **no probe** (read guard, 6.3) |
| missing from a successful liveness reply, no `turn_seen` | no change |

A row entering `Working` or `NeedsYou` clears its held `outcome` and acknowledgement (a new turn).

**Invariant: a row is `NeedsYou` exactly when it has at least one queue item** (test 14 checks it after every input). When a row's last item leaves, its state is recomputed at once: latest status `waiting`, `working`, `starting` or `Other`, or a probe in flight, gives `Working`; otherwise the `idle` rows of the table apply. So `rows()` can always order `NeedsYou` rows by their lowest `seq` (5.6), and `counts()` never counts a needs-you row with an empty queue. A `waiting` row whose approvals reply removed its last item (the operator just answered) therefore shows `Working` until the next liveness reply decides. A row whose profile has no approvals method (-32601) gets its `Waiting` item in the liveness reply itself (5.4), since no approvals reply will come.

**Foreground row (issue decision 7).** The row named by the latest `Foreground { key }` never enters `Done` or `Failed`, under polled or subscribed rules, whether or not it is subscribed yet (for example just after `set_foreground` on a switch): wherever a rule would give `Done` or `Failed`, it gives `Idle`, stores no outcome, emits no `Done`/`Failed` attention and no `ProbeOutcome` (`P2-13` alerts for the foreground session). Polled `waiting` still gives `NeedsYou`, with items flagged `foreground` (5.4). When `Foreground` names a row that is `Done` or `Failed`, that row becomes `Idle` and counts as acknowledged. An `OutcomeProbed` that arrives for a row that has since become the foreground row is applied as `Idle`.

**Subscribed rows take no polled effects.** While a row holds a subscribed view (5.3), liveness, approvals and probe replies change neither its state nor its items, and the registry emits no `FetchApprovals` or `ProbeOutcome` for it; only `last_live_count` and `message_count` are recorded. An `OutcomeProbed` for a row that became subscribed meanwhile is ignored.

`OutcomeProbed { outcome, found_complete }`:
- Probe for "turn ended": `Failed` gives state `Failed`; `Completed`, `Interrupted`, `Unknown` give `Done`; `outcome` is stored; attention `Failed` or `Done` (section 5.5).
- Probe for "count rose": if `found_complete` is false, the row stays as it was (normally `Idle`), nothing is stored and no attention is emitted (the count rose without a finished turn); else as for "turn ended".
- The service sends `OutcomeProbed { outcome: Unknown, found_complete: false }` itself when the probe fails or `probe_deadline` passes.

**Failed liveness** (`LivenessFailed`, any `CallError` except `UnknownMethod`): no row changes state; the profile's rows get `stale: true` until the next successful liveness or roster of that profile; one `Diagnostic` per distinct reason. **No liveness method** (`LivenessFailed { error: UnknownMethod }`): one `Diagnostic`; from then on that profile's rows follow the roster's `running` flag (true behaves as `working`, false as `idle`), and no `FetchApprovals` is emitted for them.

### 5.3 Row state (subscribed rows)

A `Subscribed` view replaces the polled status as the source of state for that row until `Unsubscribed`; polled replies have no effect on it meanwhile (5.2, "Subscribed rows take no polled effects"), and the foreground rule of 5.2 applies:

| View | State |
|---|---|
| any `needs` | `NeedsYou` |
| `Running` | `Working`, `state_since` = `started_at` when given |
| `Finished(o)`, not foreground | `Failed` for `Outcome::Failed`, else `Done`; attention once per finished turn |
| `Finished(_)` or `Idle`, foreground | `Idle` (the operator is looking at it; `P2-13` alerts for the foreground) |
| `Idle` | `Done`/`Failed` if an unacknowledged outcome is held, else `Idle` |

`activity`, `cost_usd`, `model` and `title` (when `Some`) overwrite the roster's values. On `Unsubscribed` the row keeps its state and outcome and goes back to polled rules (`turn_seen` is set when the last view was `Running` or had needs). Its exact items are **downgraded**: same `NeedId`, `seq` and `since`, `exact: false`, `execution_generation` set to `None`. From then on they are polled items and settle by 5.4's polled rules: the next liveness reply that shows the row not `waiting` removes them; an approvals reply removes approval items it does not list. Question and masked items are not listed by `approval.pending`, so they stay until liveness settles them.

### 5.4 The needs-you queue

- **Identity.** `NeedId { key, slot }`. A prompt (approval or clarification) is `NeedSlot::Prompt(prompt_id)` whatever its source; `approval.pending`'s `request_id` is that `prompt_id` (F13). A masked request (sudo, secret, vault) is `NeedSlot::Masked(request id)`. A session known to be waiting without detail is `NeedSlot::Waiting`. The identity has no `execution_generation` because polled approvals carry none (F13); see section 17 for what that means for answering.
- **Sequence.** `seq` is assigned once, from a registry counter that only rises, when an id first enters the queue. `since` is the `at` of that input.
- **Where `Waiting` items come from.** Only from these, each for an unsubscribed row whose latest liveness status is `waiting` and which has no queue item: an approvals reply with no usable approval (empty, or only null ids) that removed no item; an `ApprovalsFailed` other than `NotFound`; a liveness reply in a profile whose approvals method is unknown (-32601). A new `Waiting` item gets a new `seq` and a `NeedsYou` attention.
- **Refinement.** When a session has a `Waiting` item and its first `Prompt` or `Masked` item arrives, the new item takes the `Waiting` item's `seq` and `since`, the `Waiting` item is removed, and no attention is emitted. Later items of the same session get new `seq` values.
- **Polled sources.** `Approvals` for a row whose latest status is `waiting`:
  - each approval with a `prompt_id` becomes or updates `Prompt(prompt_id)` with `Known(NeedSummary::Approval(command, else description, else ""))`, `choices`, `exact: false`, no generation; if an item with that id is exact, the reply changes nothing about it (a poll never downgrades an exact item);
  - an approval with a null `prompt_id` has no identity: it creates no item and gives one `Diagnostic`; it counts as "something unknown is waiting" for the `Waiting` rule;
  - non-exact `Prompt` items of that session whose summary is an approval and which are not in the reply are removed (non-exact question items stay; `approval.pending` does not list questions);
  - if after this the session has no `Prompt` or `Masked` item: one `Waiting` item is created **only if** this reply removed no item (the first observation of this waiting episode, for example an unattached clarification or a null id); an existing `Waiting` item stays. If the reply removed the session's last item (the approvals were just answered), no `Waiting` item is created, the row shows `Working` (5.2 invariant), and the next liveness reply decides (still `waiting`: another `FetchApprovals`, whose empty reply then creates the `Waiting` item).
  - Known gap, recorded in `LEARNINGS.md`: an approval answered between the liveness read and the `approval.pending` call of a first observation gives a `Waiting` item (and one `NeedsYou` attention) that the next liveness removes.
- **`ApprovalsFailed`**: `NotFound` (the session just left) changes nothing; the next liveness settles it. `UnknownMethod`: one `Diagnostic`, no more `FetchApprovals` for that profile, and a waiting row with no item gets a `Waiting` item (then and at each later `waiting` liveness). Others: a waiting row with no item gets a `Waiting` item (so a failing read never hides a need); one `Diagnostic` per reason, retried at the next `waiting` liveness after `approvals_gap`.
- **Subscribed sources.** Each `SubscribedNeed` becomes or updates its item with `exact: true` and its generation and timeout. Subscribed items not in the latest view are removed. A polled item for the same id is upgraded in place (same `seq`).
- **Settling by liveness.** A successful liveness reply in which the row's status is not `waiting` removes that row's non-exact items (polled, downgraded and `Waiting`), never exact items held by an attached owner (the owner's view settles those).
- **Foreground.** Items of the foreground row carry `foreground: true`; they are in `queue()` but not in `counts()`.
- **Gone rows.** Removing a row removes its items silently.

### 5.5 Attention effects (consumed by `P3-06`)

- `NeedsYou`: when an id enters the queue, except by refinement or upgrade. One per id.
- `Done` / `Failed`: once per finished turn of a row: for polled rows at `OutcomeProbed` (or at the "left the live listing" rule of 5.2); for subscribed rows at the first view with `Finished(_)` after a `Running` view.
- Rows first seen **waiting** when the registry starts do emit `NeedsYou` (requirement R5: a question that waited while Talaria was closed must be shown). Rows first seen idle emit nothing.
- `foreground` is copied into the effect; `P3-06` decides whether to ring.

### 5.6 Order

`rows()`: by `RowState` in the order `NeedsYou`, `Working`, `Failed`, `Done`, `Idle`; inside `NeedsYou` by the lowest `seq` of the row's items; inside the others by `state_since` newest first; ties by profile, then `session_id`. `queue()`: ascending `seq`.

### 5.7 Staleness, stale replies and versions

- `ConnectionLost` marks every row `stale: true` and every `Listed` profile `Loading`; rows are kept. The next successful roster of a profile clears `stale` for its rows.
- **Replies from a replaced connection** (the architecture's protocol rule) are handled in the service: every call is tagged with `P1-03`'s link generation (`LinkState::Connected { generation }`) when sent, and a reply or failure whose generation is not the current one is dropped before it becomes a `FleetInput` (test 37).
- **Request numbers** come from one `u64` counter per `FleetService` (and per `list_once`), rising across link generations. In the core, a reply whose `request` is not greater than the last applied `request` of the same kind for the same profile (or row, for approvals) is dropped without effect (test 15).
- `version()` rises by exactly one per `update` call that changed anything visible in `rows()`, `queue()`, `counts()` or `profiles()`. An identical poll reply changes nothing and does not raise it. Field changes that are not visible (an internal watermark, `last_live_count`) do not raise it. A new diagnostic does not raise it.
- `state_since` changes only when `state` changes.

### 5.8 State diagram (one unsubscribed row)

```text
          first seen idle                     first seen working/starting
 (new) ───────────────────► Idle ◄──────┐    (new) ─────────────► Working
                              │         │ acknowledge                 │ ▲
                 working /    │         │                     waiting │ │ working
                 starting     ▼         │                             ▼ │
                           Working ──waiting──► NeedsYou ──────────────┘
                              │                    │

   Done / Failed ── acknowledge ──► Idle (a gone row is removed);  Done / Failed ── working ──► Working
```

## 6. The fleet service and its schedule

### 6.1 Connection

`HostDial::dial` (an implementation of `P1-03`'s `Dial`): fresh discovery with `P1-01`'s `discover_with` and `EnsurePolicy::Never` (the fleet never starts a gateway; `P1-12` does that at launch), `resolve_profile` for the foreground profile, `mint_ticket` with `Scope::host(Purpose::Interactive)`.

- If the mint fails with `TicketError::BindingRejected` or `TicketError::Refused(_)`, it mints `Scope::profile()` for the same profile and records `SideScope::ProfileOnly { profile, why: "the gateway refused a host-scoped ticket" }`.
- Any other `TicketError` (for example `Timeout`, `Io(_)`, `CapacityExhausted`) is a dial failure: `P1-03`'s backoff retries it, with host scope.
- Every reconnect starts again with host scope; a profile-only fallback lasts for one link generation.

Then `connect_with`, `handshake_with` (which sends `client.capabilities {server_requests: true}`, as on every Talaria connection; this unit does not change `P1-01`'s handshake), and returns `Dialed`. Declaring `server_requests: true` on a link attached to no session changes nothing about where Hermes sends prompts: Hermes records the declaration per transport (`advertise`, `tui_gateway/server_requests.py:30-34`, `:136-143`) and consults it only for the WebSocket clients attached to the session a request belongs to (`_session_client_answers_requests` and `_session_answering_clients`, `tui_gateway/session_transports.py:58-77`); the fleet link is attached to none (F33). So the declaration and the refusal path below do not conflict: the declaration is inert here, and the refusal is a defence for a request Hermes should never send. The link is a `P1-03` `Link` started with this dial and `LinkConfig::default()`; it tracks no session. Server requests on this link: see 3.4 (refused at once with the not-supported reply whatever `policy_for` returns; one diagnostic per connection).

### 6.2 Triggers

| Trigger | Work |
|---|---|
| Link `Connected` (first or after reconnect) | `Profiles` from the dial's endpoint (narrowed to `only_profile` when set); then, for every in-scope profile, the roster, and the liveness call as soon as that roster call is sent |
| `sessions.changed` event on the link | after `coalesce` (250 ms, later events in the window join it): liveness for every in-scope profile; roster for every in-scope profile whose last roster started at least `roster_gap` (3 s) ago, else one trailing roster when the gap ends |
| Hot timer (`hot_poll`, 2 s) | liveness for each hot profile (`hot_profiles()`) |
| Cold timer (`cold_poll`, 4 s, spread) | liveness for each in-scope profile that is not hot; with `n` cold profiles, one profile every `cold_poll / n`, round robin |
| Either timer | skips a profile whose last liveness started less than `liveness_gap` ago (`min(1 s, hot_poll / 2)`, so a 1 s `hot_poll` is never skipped by its own previous tick) |
| Backstop timer (`backstop`, 30 s) | fresh discovery (`discover_with`, `EnsurePolicy::Never`) for `Profiles`; roster and liveness for every in-scope profile |
| `FetchApprovals { key }` | `approval.pending {session_id, profile}`; if one for that key started less than `approvals_gap` (2 s) ago, the read is deferred to the moment the gap ends (at most one deferred read per key), never dropped; when it comes due it passes the read guard (6.3) again |
| `ProbeOutcome { key }` | the two-step probe (6.4); `OutcomeProbed { Unknown, found_complete: false }` after `probe_deadline` (3 s) |
| `refresh_now()` | as the backstop, at once |
| Link `Reconnecting` | `ConnectionLost` |

Concurrency: at most one roster and one liveness call in flight per profile (a trigger during a flight sets "again" and re-issues when it ends), at most `max_in_flight` (8) calls in flight in total, each with `call_timeout` (10 s). A call that times out or whose connection dropped gives `RosterFailed`/`LivenessFailed`/`ApprovalsFailed` with `CallError::NoReply` or `ConnectionDropped` (an unknown outcome, never success), and frees its slot at that moment.

Queueing when all slots are busy (no trigger is ever dropped):
- Work waits in a pending set keyed by (kind, profile) for rosters and liveness and by (kind, session) for approvals and probe steps. A second trigger for a key already pending joins it (coalesced); it never adds a second call.
- When a slot frees, the next call is chosen by class, in this order: (1) probe steps and approval reads; (2) liveness of hot profiles; (3) rosters and liveness from `Connected`, `sessions.changed`, the backstop or `refresh_now`; (4) cold liveness. Within a class, the key that has waited longest goes first.
- **Suspect profiles.** A profile whose latest call ended with `NoReply` is suspect until one of its calls succeeds. Calls to suspect profiles may hold at most `suspect_in_flight` (2) of the 8 slots together, so up to 4 profiles that never answer cannot starve the others (issue REQ-6: one failing profile never hides the others). Test 36 covers it.
- A probe step that waits in the pending set still counts against its `probe_deadline`.

Decoding: the service takes the raw `result` of `session.list` and `session.active_list` as `serde_json::Value`, maps each element of `sessions` through `RosterRow::from_value` / `LiveItem::from_value`, and passes the count of `None` results as `malformed` (the core emits one `Diagnostic` per profile when it is above 0).

Event handling on the link: `sessions.changed` is the only event acted on. Other session-less broadcasts (`skin.changed`, `cron.changed`, `projects.changed`, `skills.changed` and the rest of `x-notifications`) are ignored silently. An event type not in the contract is logged once per connection at debug level.

### 6.3 Read guard

`approval.pending` and `session.events.since` are sent only for a `session_id` present in the latest successful liveness reply of its profile, and only while that reply's link generation is current. A session that is not live is restored by `session.events.since`, and the dispatcher's adoption step runs for either read (F23); this guard is what keeps the registry free of side effects. It is also why a row that left the live listing gets no probe (5.2).

### 6.4 Outcome probe

1. `session.events.since {session_id, profile, last_sequence: 0}`. The reply has no events (no epoch was sent, F19) but carries `replay_epoch` and `latest_seq`.
2. If `latest_seq` is 0: `Unknown`, `found_complete: false`. Else `session.events.since {session_id, profile, last_sequence: max(0, latest_seq - 64), replay_epoch}`.
3. If `truncated` or `snapshot_required`: `Unknown`, `found_complete: false` (no `session.resume`: decision 2 of the issue). Else scan `events` from the end for the last item whose `type` is `message.complete`; `Outcome::from_turn_status(payload.status)` with `found_complete: true`; none found: `Unknown`, `found_complete: false`.

Both calls pass the read guard again before they are sent. The reply is at most one session's ring (4 MiB, F21), below the 8 MiB message limit `P1-01` enforces. A probe of a session whose ring was dropped (more than 64 sessions active in the process) gives `Unknown`.

### 6.5 Wiring in `app.rs` (minimal touch of `P1-12`'s file)

- After the first frame of an interactive launch (never in `-p` headless mode, which therefore mints no host-scoped ticket, and never when `[fleet] enabled = false`), call `FleetService::start` with `P1-12`'s home and foreground profile.
- After each foreground `SessionState` update, compute `SubscribedView::from_state(&state, &masked)` and call `observe_subscribed` only when the view differs from the last one sent.
- On a foreground switch (`P2-07`'s `switch_foreground`): `set_foreground(Some(new))`, `observe_unsubscribed(old)`.
- `AppMessage::Fleet(FleetNotice)`: store the latest `Arc<FleetSnapshot>` in `AppState`; schedule no render (nothing is drawn by this unit).
- On exit, `close()` the handle without waiting more than 200 ms.

Test 42 (`crates/talaria-app/tests/fleet_app.rs::app_wiring_and_config`) drives `P1-12`'s app loop against `P1-09`'s mock and asserts each bullet: no fleet connection before the first frame; none with `-p` (and no host ticket requested) or with `enabled = false`; one `observe_subscribed` per changed view and none for an unchanged one; the two calls on a switch; `close` returns within 200 ms with a mock that never answers; and the clamping notices of section 7.

## 10. `talaria fleet list`

```text
talaria fleet list [--json] [--profile <name>] [--watch [--for <seconds>]]
```

- One-shot (default): `list_once`: discovery with `EnsurePolicy::Never`; attach as 6.1; roster and liveness for every in-scope profile (with `--profile`, only that one: `FleetConfig::only_profile`); `approval.pending` for each waiting session; print; close; exit 0. A one-shot run has no history, so it never shows `DONE` or `FAILED`: idle sessions show as `IDLE`. It ignores `[fleet] enabled`.
- `--watch`: runs the full `FleetService` (with `only_profile` from `--profile`, so other profiles are not even polled); prints the first snapshot, then one line per change; `--for <seconds>` (1 to 3600) stops after that long with exit 0; Ctrl+C stops with exit 130. `--for` without `--watch` is a usage error (exit 2). A newly started watch has no history either: a row it first sees idle is `idle` (first sight records `last_live_count` but starts no probe). After first sight the registry's rules of 5.2 apply unchanged: a turn that ends is reported `done` or `failed` whether the watch saw it running or saw only a `message_count` rise between two polls (test 5, E23, live test 51).
- **When output starts** (one-shot and the first watch snapshot): when every in-scope profile has answered (or failed) its first roster and its first liveness, **and** every unattached row that this first liveness showed `waiting` has had its first `approval.pending` reply or failure (so an approval prints with its command, not as `waiting for an answer`), or 10 s (`call_timeout`) after the link connected, whichever is first. A profile whose approvals method is unknown (-32601) does not hold output back. A one-shot run that cannot connect within `connect_timeout` (15 s) exits 1 with the attach message of 10.4.
- **Errors** are plain text on standard error, also under `--json`; standard output then holds nothing.
- `--profile <name>`: only that profile's rows, items and profile status are printed; other profile names never appear in the output (evidence privacy).

### 10.1 Text output (one-shot and the first watch snapshot)

Groups in the order `NEEDS YOU`, `WORKING`, `FAILED`, `DONE`, `IDLE`; a group with no rows is not printed. Header `<GROUP> (<n>)`. Row: two spaces, then columns separated by two spaces: profile; title or `(untitled)`, cut to 40 characters with `…`; model or `-`; detail; age (`P2-07`'s `format_age` of `state_since`); then ` (stale)`, ` (gone)` or ` (hidden)` (for `unlisted`) when set. Columns are padded to the widest value in the output, measured in terminal cells with the `unicode-width` crate's `UnicodeWidthStr::width` through one function, `pad_cells(text, width)` (wide characters count two, combining characters zero). Detail by state: `approval: <command>`, `question: <question>`, `sudo password`, `secret`, `waiting for an answer`; `working` or `starting`; `failed`; `completed`, `interrupted` or `finished`; `idle`. Detail is cut to 60 characters with `…`. Every printed value goes through `P1-06`'s `history::sanitize` first (control and bidirectional characters become visible stand-ins).

After the groups, one line per profile that is not `Listed`: `not listed: <profile> (<reason>)` (only the filtered profile with `--profile`). The reason is the status's `reason` for `failed` and `parked`, `loading` for `loading`, and the fixed text `outside the profile-only view` for `out_of_scope` (which happens only under the profile-only fallback, E1). Then one line per `Listed { truncated: true }` profile: `truncated: <profile> (only its 200 newest live sessions are listed; working sessions beyond them are not shown)`. Sessions past the 200-row cut get a row only while waiting (`unlisted`, 5.1); a working one past the cut has no row, and this line is the only sign of it. With a profile-only scope, a first line: `Showing profile <profile> only: the gateway refused a host-scoped ticket.`

No rows: `No live sessions in <the served profiles | profile <name>>.`

### 10.2 Watch text lines

After the first snapshot (printed as 10.1, which already shows the needs open at that moment, so no `needs you:` lines repeat them), these are the only text lines; every other change prints nothing. Each starts with the local time `HH:MM:SS.mmm`:
- `<time> <profile> <title> <old state> -> <new state>` for a row state change, with states written `needs you`, `working`, `failed`, `done`, `idle`;
- `<time> <profile> <title> new -> <state>` for a row that appears after the first snapshot;
- `<time> needs you: <profile> <title> <detail>` when an item enters the queue (not on refinement or upgrade);
- `<time> cleared: <profile> <title>` when an item leaves the queue while its row remains (answered here or elsewhere, timed out, withdrawn);
- `<time> link: <connected | reconnecting: <reason> | failed: <reason>>` when the snapshot's `link` changes after the first snapshot.
Nothing is printed when a row is removed (its items go with it silently), nor for changes of `stale`, `gone`, `unlisted`, title, model or a profile's status (JSON carries those). Values are sanitized and cut as in 10.1; an empty title prints as `(untitled)` here too (fixture sessions are untitled, so UAT-2's `<title>` is `(untitled)`).

## 17. Notes for consumers

- `P3-02` (fleet view) draws `FleetSnapshot`; calls `acknowledge` when the operator opens or peeks a `Done`/`Failed` row; when it attaches a session for peeking it must report the session with `observe_subscribed` and `observe_unsubscribed`. Caution: `P1-03`'s replay sends `session.events.since` without `profile`, so a session of another profile tracked on the fleet link would fail replay; attach such sessions on a link for their own profile, or raise it with `P1-03`'s owner.
- **Answering.** A queue item with `exact: false` (polled or downgraded) has no `execution_generation`, and the architecture requires all three of (`session_id`, `prompt_id`, `execution_generation`) on every response. A consumer must never answer such an item as is: it attaches the session (which turns the item exact through `observe_subscribed`) and answers from the exact `approval.request`. `P3-02` and `P3-06` (answering from the peek panel) own that path; the phase 3 parent decides which unit provides it before either is built.
- `P3-03` (background launch) reports the sessions it creates with `observe_subscribed` while it holds them and `refresh_now()` after a create.
- The workflow runner (phase 5) creates `source: "tool"` sessions, which Hermes's live feeds skip (F35); it must report them with `observe_subscribed` for them to appear in the fleet.
- `P3-06` (attention) consumes `FleetNotice::Attention` and `FleetCounts`.
- `P3-07` (review) may add a pull-request label beside a row; it keys on `RowKey`.
- `P3-09` (resident agents, only if adopted) needs hidden sessions; this unit lists with `include_hidden: false` (hidden waiting sessions still appear as `unlisted` rows); adding a second list call is that unit's change.
