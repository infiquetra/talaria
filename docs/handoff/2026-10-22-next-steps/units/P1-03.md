## 1. What this unit is for, in one paragraph

A Talaria session is a viewer of a session that lives in the Hermes gateway. The gateway keeps running
the agent when the viewer's connection goes away (laptop sleep, Wi-Fi change, gateway restart). This
unit makes the connection notice that it has died (heartbeat), come back on its own (reconnect with
backoff and a fresh ticket), and catch up on what it missed (replay) so that the session reducer
(unit P1-05) sees every event of every session it watches exactly once and in order. When the gateway
can no longer replay what was missed, the unit says so once per session (a replay gap), and the
session service (unit P1-12) rebuilds that session from a fresh snapshot. The roadmap section is
[07 §P1-03](../07-roadmap-and-work-units.md#p1-03--liveness-reconnect-and-replay); the protocol rules
are in [05 §Protocol rules](../05-architecture.md#protocol-rules-every-client-layer-must-keep); the
research is [u04 §3](../research/u04-hermes-client-surfaces.md#3-event-replay-reconnect-and-whether-sessions-keep-running-with-no-client).

  A re-attach therefore returns the full transcript. Do not send either key expecting a lighter
  reply; verify at the pinned commit before relying on it.
- **Contiguous numbering per viewer** (fact R29) is read from code, not from a documented guarantee.
  Talaria relies on it only in the safe direction: a jump raises a gap and a fresh snapshot, never a
  silent hole. If a live run shows `GAP reason=seq_jump`, the builder stops and reports (the issue's
  stop condition 9); verify at the pinned commit before relying on it.
- **Frames with `seq` but no `replay_epoch`.** The legacy stamping paths (`tui_gateway/server.py`
  `write_json`, line 697, and `tui_gateway/tool_progress.py:260-279`) stamp a `seq` from a different
  counter and add no `replay_epoch`. Whether such frames ever reach a canonical viewer was not
  checked. The tracker never gates them: a frame missing any of `session_id`, `seq`, `replay_epoch`
  passes through untouched and is not remembered (verify at the pinned commit before relying on it).
- **Session ids survive a gateway restart.** `session.resume {session_id}` restores a stored session
  from `state.db` through `authorize` ([`session_authority.py:190-205`](https://github.com/NousResearch/hermes-agent/blob/v0.22.4/gateway/session_authority.py#L190-L205)).
  Not exercised live, because agents do not restart the gateway.
- **`session.resume` side effects on re-attach** (fact R30) run on every re-attach, as they do for
  Desktop. The issue accepts them: whatever frames or server requests they produce reach the
  consumer like any other (P1-12 and P1-09 already handle a pick question and a notice). Their exact
  frames were read, not tested; verify at the pinned commit before relying on it.

## 3. Request and result shapes

### 3.1 `gateway.ping` (wire convention, not in the contract)

```json
{"jsonrpc":"2.0","id":57,"method":"gateway.ping","params":{}}
{"jsonrpc":"2.0","result":{"ok":true},"id":57}
```

The id is whatever integer P1-02's counter gives the `call_raw` request; the gateway echoes it (H3).

### 3.2 Canonical `session.events.since`

Params (`CanonicalEventsParams`, `additionalProperties: false`, required `session_id`), reached through
P0-03's `methods::canonical::session_events_since` (fact R28):

| Key | Type | Default | Talaria sends |
|---|---|---|---|
| `session_id` | string | required | the tracked session id |
| `last_sequence` | integer | 0 | the cursor's `last_sequence` |
| `last_seen` | integer | 0 | never (legacy name) |
| `replay_epoch` | string or null | null | the cursor's `replay_epoch`, always |
| `profile` | string or null | null | never (a profile-scoped ticket routes implicitly) |

Result (`CanonicalEventsResult`, all required): `events` (array of `CanonicalReplayEvent`),
`latest_seq` (integer), `last_sequence` (integer), `epoch` (string), `replay_epoch` (string),
`truncated` (boolean), `snapshot_required` (boolean), `count` (integer).

`CanonicalReplayEvent`: required `type`, `session_id`, `payload` (object), `replay_epoch`, `seq`;
optional `authority_epoch`, `execution_generation`, `admission_id` (integers or string, nullable).
These are the event objects (the `params` of an `event` notification), not whole JSON-RPC frames.
The link turns each into the same item type as a live event (decode it with the same decoder P1-02
uses for `params`) before giving it to the tracker.

### 3.3 Canonical `session.resume` (as used for a re-attach)

Params (`CanonicalResumeParams`, no required keys, `additionalProperties: false`): Talaria sends
exactly `{"session_id": "<id>"}` for a re-attach. Result (`CanonicalSnapshot`) required keys:
`session_id`, `stored_session_id`, `messages`, `message_count`, `running`, `authority_epoch`,
`replay_epoch`, `last_sequence`, `subscription_id`, `revision`, `execution_generation`, `pending`,
`prompts`, `info`. The re-attach uses `session_id`, `replay_epoch`, `last_sequence` and
`subscription_id`; the rest is dropped (the session service gets its own snapshot when it handles a
gap). `session.create` returns the same `CanonicalSnapshot`, so a new session is tracked from its
create result in exactly the same way.

### 3.4 `session.replay_gap` sent by the server

```json
{"jsonrpc":"2.0","method":"event","params":{"type":"session.replay_gap","session_id":"<id>",
 "payload":{"replay_epoch":"<session epoch>","latest_seq":42}}}
```

No `seq`, no top-level `replay_epoch`. P0-03 types it by hand as `canonical_events::SessionReplayGap`.

## 4. Design

### 4.1 Pieces and where they live

| Piece | File | Pure? | Purpose |
|---|---|---|---|
| `Backoff`, `Jitter` | `liveness.rs` | yes | the delay ladder and its random draw |
| `HeartbeatClock` | `liveness.rs` | yes | when to ping and when the link is dead, given instants |
| `DialFailure::from` | `liveness.rs` | yes | maps P1-01 errors to `Retry` or `GiveUp` (§4.6) |
| `Link` and its task | `liveness.rs` | no | owns the one P1-02 `Client`, the heartbeat timer, the reconnect loop and the replay calls; emits `LinkEvent`s |
| `Dial`, `GatewayDial` | `liveness.rs` | trait, no | one fresh attach per call |
| `ReplayTracker<T>` | `replay.rs` | yes | per-session cursors, holds, deduplication, gap decisions |

`ReplayTracker<T>` is generic over the item type so it does not depend on P1-02's item shape; the
caller passes a `Stamp` (session id, `seq`, `replay_epoch`, `server_gap`) with each item. The link
builds the stamp from P1-02's `EventFrame` (`session_id`, `seq`, `replay_epoch`; `server_gap` when
the decoded notification is P0-03's `SessionReplayGap`). `ServerRequest` and `Malformed` items get
an empty stamp (pass through). `Inbound::Closed` is consumed by the link, never forwarded.

### 4.2 Backoff ladder

`ceiling(k) = min(cap, floor × 2^(k-1))` for reconnect attempt `k` = 1, 2, ... counted since the last
stable connection (exponent clamped at 32; production `floor` 1 s, `cap` 30 s). `delay(k, draw) = lo +
draw × (ceiling(k) - lo)` with `lo = max(floor, ceiling(k) / 2)`. With `floor` and `cap` both 30 s every
delay is 30 s, which test 43 uses. Draw 1.0: 1, 2, 4, 8, 16, 30, 30 s. Draw 0.0: 1, 1, 2, 4, 8, 15, 15 s.
`Jitter::Random` draws with `fastrand`; tests use `Jitter::Fixed`.

Counting: the connection made by `Link::start` is not an attempt. When a connection ends, the next
dial is attempt `k + 1` if that connection was not stable, else attempt 1 (`k` reset to 0). A
connection is stable once it finished its handshake and stayed open `stable_open` (5 s; fact C3).
Each failed dial also adds one. `LinkState::Reconnecting.attempt` is `k`.

Why not Hermes's full jitter: full jitter allows a zero delay, and the roadmap fixes a 1 s floor.
"Half jitter" keeps the floor and still spreads a fleet of Talaria panes that lost the same gateway.

### 4.3 Heartbeat clock

```text
on connect (gateway.ready.heartbeat == true):
    last_inbound = connected_at; last_ping = never; last_tick = connected_at
    ticks: tokio::time::interval_at(connected_at + interval, interval), MissedTickBehavior::Skip
at every tick, now:
    s = client.stats().await
    if s.generation == current and s.last_frame_at is Some(t): on_inbound(Instant::from_std(t))
    on_tick(now):
      late = now - last_tick > 2 * interval;  last_tick = now
      if !late and last_ping > last_inbound and now - last_inbound >= deadline: DEAD
      else: SendPing (spawn call_raw("gateway.ping", {}, timeout = interval); ignore the outcome);
            last_ping = now
```

`last_frame_at` counts every frame of the current generation, replies and pongs included (P1-02's
REQ-12 and its spec §4: "a reply counts as received traffic ... even when it is unmatched"). The link
reads it only at ticks, so a death is judged at the first tick at or after 45 s of silence and lands
45 to 60 s after the last frame. An idle healthy link: the pong to a ping sent at tick `t` arrives at
`t + ε`, so at `t + 45` the age is `45 - ε` and the link lives; a blackhole that starts just after
that pong is declared dead at `t + 60`.

Lifecycle: the heartbeat timer and its clock belong to one generation. They stop when that generation
ends (a `Closed`, a heartbeat death, or `close()`); the outcome of a ping still in flight is discarded and
never touches the clock (the clock reads only `last_frame_at` of the current generation). The next
connection starts a fresh `HeartbeatClock` if its `gateway.ready` advertises `heartbeat: true`.

The grace tick (`late`) is a Talaria addition (fact H12): after a sleep the first tick only pings, and
death is judged at the next tick, 15 s later.

Why not `start_paused` in socket tests: tokio's `time::pause` documentation says a paused clock
auto-advances to the next timer whenever the runtime has nothing ready to run, which includes a task
waiting on a socket, so replay and dial timeouts would fire while a loopback reply is in flight. And
P1-02's `last_frame_at` is a `std::time::Instant`, which a paused tokio clock never moves. The pure
`HeartbeatClock` tests pass instants built as `base + Duration`, so they need no clock at all.

### 4.4 Per-session state machine (`ReplayTracker`)

```text
             track(cursor)                    reconnect, same process epoch
  (absent) ───────────────► Tracking ───────────────────────────────► Replaying{hold, token}
                              │  ▲                                        │
     live frame: new epoch    │  │ resync(cursor) flushes hold            │ resume+since ok: deliver window,
     or seq jump, server      │  │ (a hole left: new gap, stays)          │ flush hold, back to Tracking
     replay_gap, process      │  │                                        │
     epoch changed ─────────► ▼  │                                        │
                          AwaitingSnapshot{hold, reason} ◄────────────────┘ snapshot_required / truncated /
                                                                            epoch or id mismatch / jump /
                                                                            hold overflow / failure / timeout
  untrack(), or not_found on resume or since ───► (absent), SessionGone emitted
  connection drops while Replaying ───► Tracking (hold discarded, cursor unchanged, token retired)
```

Rules in each state:

| State | Live frame, same epoch, `seq` ≤ cursor | Same epoch, `seq` > cursor | Other epoch | Server `session.replay_gap` | No `seq` | Replay reply (any) |
|---|---|---|---|---|---|---|
| Tracking | drop, count a duplicate | `cursor + 1`: deliver, advance; higher: gap `SeqJump`, to AwaitingSnapshot, hold the frame | gap `EpochChanged`, to AwaitingSnapshot, hold the frame | gap `ServerOverflow`, to AwaitingSnapshot | deliver | ignore |
| Replaying | hold | hold | hold | gap `ServerOverflow`, retire the token, to AwaitingSnapshot | deliver | apply if the token matches, else ignore |
| AwaitingSnapshot | hold | hold | hold | absorb | deliver | ignore |

"No `seq`" means a frame missing any of `session_id`, `seq` or `replay_epoch`. A server
`session.replay_gap` for an untracked session passes through as an ordinary item (it ends a
subscription the tracker does not own).

Flush at the end of a successful replay: deliver the window above the cursor in order (`replayed:
true`), then take held frames in arrival order, all through one gate: same epoch and `cursor + 1`,
deliver and advance; same epoch at or below, drop as a duplicate; same epoch and above `cursor + 1`,
raise one `SeqJump` gap; another epoch, raise one `EpochChanged` gap. After either gap, move to
AwaitingSnapshot and keep this frame and every later one held.

`resync(session_id, cursor)` (in any tracked state): sets the cursor, drops held frames of another
epoch or at or below the new cursor, then flushes the rest in arrival order through the gate. If the
first remaining frame is `cursor + 1` (or none remain), every frame is delivered in order and the
session returns to Tracking. If the first remaining frame is above `cursor + 1`, frames are missing:
raise one gap (`HoldOverflow` when the hold dropped frames since the last gap, else `SeqJump`), deliver
nothing, keep the hold, and stay in AwaitingSnapshot; the consumer resumes again. On an untracked
session `resync` behaves like `track`.

Incident: from a gap to the next `resync`. Within an incident the tracker raises one gap, except that
each new connection re-raises it once with the original reason (below). A `resync` that cannot close
the hole starts a new incident with its own gap.

Passed-through memory: for frames of untracked sessions that carry `session_id`, `seq` and
`replay_epoch`, keep the last `(replay_epoch, seq)` per session id, at most 1,024 ids, the oldest
forgotten. `track(id, cursor)` sets the cursor to the remembered value when its epoch equals the
cursor's and its `seq` is higher, then forgets the entry. Reason: the consumer receives the
`session.create` reply and the event stream on different channels, so events can be delivered
before `track`; without this, the next replay would deliver them again. P1-12 gates its own copy by
the snapshot (its REQ-13).

`on_new_connection(process_epoch)`, called once per successful dial: the first call records the
epoch only. A different epoch gives every Tracking session one `BackendRestarted` gap (to
AwaitingSnapshot). Every session already in AwaitingSnapshot gets its gap raised once more, with the
reason it already has, because the consumer's `session.resume` may have died with the old
connection. `begin_replay` returns Tracking sessions only, so an awaiting session is never
re-attached by the link; the consumer's resume re-attaches it.

Hold bound: 10,000 items per session. On overflow in Replaying, go to AwaitingSnapshot with gap
`HoldOverflow` (drop the oldest held item and mark the hold as having dropped frames). In
AwaitingSnapshot drop the oldest held item and set the same mark, with no new gap: the snapshot the
consumer takes usually covers it, and `resync` raises `HoldOverflow` when it does not. `resync` and a
new gap clear the mark. Frames without a session id never enter a hold.

`on_new_connection` and the replay steps apply to sessions in Tracking only: `BackendRestarted` and
`ReplayUnsupported` gaps go to Tracking sessions, and an AwaitingSnapshot session is re-raised with its
original reason instead.

### 4.5 The reconnect sequence

1. The generation ends: `Inbound::Closed(ClosedConnection { generation: current, reason })` from
   P1-02, or a heartbeat death. The tracker gets `on_connection_lost` (Replaying sessions back to
   Tracking, holds discarded, tokens retired); running replay tasks are aborted. On a `Closed`, P1-02
   has already failed that connection's pending calls with `Unknown` (P1-02 specification §5, test
   15). After a heartbeat death the link ignores every item of that generation. P1-02 has no call that
   drops one connection and keeps the client (its only ways are `replace_connection` and `close()` of
   the whole client, and this unit may not edit `channel.rs`), so the dead connection stays open until
   the next `replace_connection`, which fails its pending calls with `Unknown` and delivers
   `Closed { old, Replaced }`, which the link ignores. Calls made meanwhile are written to the dead
   socket and end `Unknown` there or `TimedOut` at their own timeout (up to 300 s for
   `approval.respond`); both report `outcome_unknown()`, and the consumer sees `Reconnecting`. The
   parent issue (PH1A) records this choice.
2. Reason text: `RemoteClosed { .. }` is `socket closed`; `Error(_)` is `read failed`; `Overloaded` is
   `gateway closed a slow reader`; heartbeat death is `heartbeat timeout`. A TCP drop without a
   closing handshake may surface as either `RemoteClosed { code: None }` or `Error(_)`, depending
   on P1-02; scenarios accept both.
3. `LinkState::Reconnecting { attempt, retry_in, reason }` is emitted; the delay elapses (cancellable
   by `close`); `Dial::dial(next_generation)` runs under `dial_timeout`. Failure: `Retry` emits the
   next `Reconnecting` with the failure's reason; `GiveUp` emits `Failed { reason, next_step }` and
   the task waits only for `close`.
4. Success: `client.replace_connection(dialed.parts)` (the first connection used `Client::start` in
   `Link::start`); `LinkState::Connected { generation }`; the heartbeat restarts if advertised.
5. `tracker.on_new_connection(dialed.process_epoch)`. If it produced `BackendRestarted` gaps, no
   replay calls. Else, if `capabilities` lacks `event-replay-v1`, `on_replay_unsupported`.
6. Else, for every `(id, cursor, token)` from `begin_replay`, a separate task: `session.resume
   {session_id}` through P1-02's `client.call_with::<methods::canonical::session_resume>(params,
   CallOptions { timeout: Some(replay_timeout) })`. If the snapshot's `session_id` differs from `id`
   (fact R25), `on_replay_failed(Other)`: no `Reattached`, no `session.detach`; the gateway has
   subscribed this connection to the other session, whose frames now pass through untracked, and the
   consumer's redirect rule (§4.8) takes it from there. Else `on_reattached(token,
   snapshot.replay_epoch)` (epoch mismatch gives `EpochChanged`, no `Reattached`). Else emit
   `Reattached { session_id, subscription_id }` and call `session.events.since {session_id,
   last_sequence, replay_epoch}` the same way (`session_events_since`, same timeout). Decode each
   item of `events` with P0-03's `EventFrame::from_params` and wrap it as
   `Inbound::Event(InboundEvent { generation: current, frame })`; if any item fails to decode, the
   whole window is `on_replay_failed(Other)`. Then `on_replay_window`. Results return to the link
   task through a channel, carrying the token.
7. A refusal whose `RpcError.reason` (P1-02's `Option<String>` field, taken from `data.reason`) is
   `Some("not_found")` on either call is `ReplayFailure::NotFound`
   (`SessionGone`, cursor forgotten). Any other error, `TimedOut`, `Unknown` or `BadResult` is
   `Other` (gap `ReplayFailed`).

Why resume first, then since: `attach` fixes the snapshot cursor and starts live delivery atomically
(fact R13). Asking the ring afterwards covers every event after the old cursor; the hold and the
cursor gate remove the overlap with live frames. Asking the ring first and attaching second would lose
the events published between the two calls.

Why a timeout or error becomes a gap: Hermes's client swallows replay errors and lets REST history
re-sync the view. Talaria has no such backstop in phase 1, and the plan's rule is never to show a
transcript it cannot prove complete; a gap makes the session service fetch a snapshot.

The client handle: `Link::client()` returns the one `Client`. While P1-02 has no open connection
(after a `Closed`, during backoff, after `Failed` or `close`), calls return `NotConnected` and nothing
is sent (P1-02 REQ-11). After a heartbeat death, see step 1.

### 4.6 Errors the reconnect loop does not retry

`DialFailure::from` maps each P1-01 error by variant (names from P1-01's unit specification §11.1;
if the merged crate differs, map by meaning and say so in the pull request). `reason` is the
error's `Display` text; `next_step` is its `next_step()`. P1-01 already keeps paths out of both
(its §7.5 scrub and §11.2 texts). Two P1-01 messages name a profile: `ProfileLookupError::NeverDiscovered`
("the gateway never discovered a profile named `<name>`") and `Parked` ("profile `<name>` is parked
by the gateway: `<reason>`"). For these, `from` replaces every occurrence of the variant's `name` with
`<profile>` unless the name is `default` or `fixture` (the issue's REQ-11 and REQ-23); test 8 checks it
with the placeholder `p3probe`.

| Meaning | `GiveUp` variants |
|---|---|

### 4.7 The example `reconnect_watch`

Options: `--home <dir>` (default P1-01's `default_home()`), `--profile <name>` (default `default`),
`--model`, `--provider`, `--prompt <text>`, `--resume <id>`. It first runs P1-01's `discover_with`
(`EnsurePolicy::Never`) to learn the gateway's WebSocket port, starts a fault relay (§5.2) in front
of it, builds `GatewayDial` with `via_origin`, and calls `Link::start`. A failure of either step
prints the two `START FAILED` lines (using `DialFailure::from` for the discovery error). Then it creates a session with `session.create` (`cwd` a
new temporary folder, `model`, `provider`) or resumes `--resume`, calls `track` with the result,
then `prompt.submit` built with P0-03's `prompt_submit_params(session_id, text, submission_id)`.

Exact output lines (the scenarios match them): two lines `START FAILED reason=<reason>` and
`next=<next_step>`, then exit 1, when start-up fails; `STATE connected generation=<n>`; `STATE
reconnecting attempt=<k> retry_in=<s with one decimal>s reason=<plain words>`; `STATE failed
reason=<reason> next=<next_step>`; `STATE closed`; `REATTACHED`; `REPLAYED <n> events` (once per
re-attach, `n` the replayed events of the window); `GAP reason=<GapReason as snake_case>`;
`RESYNCED at seq <n>`; streamed text as it arrives; `TURN COMPLETE status=<payload.status of
message.complete>`; `SEQ CHECK delivered=<n> duplicates=<n> missing=<n>`; `RESULT PASS` or
`RESULT FAIL`. On every `GAP` it acts as the consumer: `session.resume {session_id}`, then
`resync` with the snapshot's `replay_epoch` and `last_sequence`, then prints `RESYNCED`. If the
snapshot names another session, it calls `untrack` on the old id and `track` with the new id instead
(§4.8), and prints `RESYNCED` with the new cursor.

`SEQ CHECK` counts, per session and epoch, the events delivered, the `seq` values seen twice, and the
numbers skipped between consecutive delivered events, not counting a jump across a `RESYNCED` line.
`RESULT PASS` needs `duplicates=0` and `missing=0`. Standard input commands: `drop`, `blackhole`,
`refuse`, `restore` (forwarded to the relay), `quit` (calls `close`, prints `STATE closed`, exits 0).

(`tokio::sync::Mutex<()>` in a `static`), and every test in `tests/reconnect.rs` holds its guard for
the whole test. The scaled margins (ping 150 ms against a 450 ms deadline, 100 ms replay timeout,
300 ms dial timeout) are wide enough alone but not under parallel load. No retry rule: a flaky test is
a defect to fix, not to retry.

**Event back-pressure.** `Link::start` returns `mpsc::Receiver<LinkEvent>` with capacity
`event_buffer` (1,024). The link task sends each event with `send().await` inside a `select!` that
also listens for `close()`; while it waits it handles nothing else. It never drops an event and never
fails because of a slow consumer. P1-02 keeps reading the socket meanwhile (its inbound queue is
unbounded, P1-02 rule 6), so the gateway sees no slow reader and the backlog grows in P1-02, visible as
`inbound_backlog` (a finding for P1-11 if it matters). Heartbeat ticks missed while blocked are
skipped; the first tick after is late and only pings (REQ-4). Test 27 runs with `event_buffer` 8 and a
consumer that stops reading for 200 ms (scaled) after event 60.

**Live jumps.** Within one epoch a tracked session's next frame must be `cursor + 1` (fact R29). A
higher `seq` raises one `SeqJump` gap and the frame is held, like an epoch change. This keeps the
Objective's promise: never a silent hole. If the gateway ever numbers non-contiguously on purpose, a
live run shows `GAP reason=seq_jump` and the builder stops (stop condition 9).

**Redirect (resume names another session).** The link raises `ReplayFailed` for the old id, sends no
`session.detach`, and does not track the new id; the other session's frames pass through untracked
(and the passed-through memory remembers their `seq`). The consumer (P1-12, and the example) resumes
the old id itself on the gap; when its snapshot names another session, it calls `untrack(old)` and
`track(new, cursor)` (not `resync`), records the new `subscription_id`, and from then on uses the new
id. `track` adopts any higher `seq` already passed through.

**`untrack` and detach.** `untrack` changes only the tracker and sends nothing. The consumer sends
`session.detach {session_id, subscription_id}` (both required, `SessionDetachParams`) when it wants the
gateway to stop sending. Frames of a session that is untracked but still subscribed pass through.

**Replay calls.** Both replay calls go through P1-02's typed `call_with` with
`CallOptions { timeout: Some(replay_timeout) }` and P0-03's canonical method markers
(`methods::canonical::session_resume`, `methods::canonical::session_events_since`). Pings use
`call_raw("gateway.ping", json!({}), CallOptions { timeout: Some(ping_interval) })` because
`gateway.ping` is not in the contract.

**Long transcripts.** Every re-attach returns the whole transcript (§2.4). A session whose resume takes
longer than `replay_timeout` (10 s) gets `ReplayFailed` on each reconnect; the consumer's own resume
(with P1-02's default timeout for `session.resume`) then rebuilds it. If that becomes common, the
remedy is upstream (§8).

### 5.1 `MockDial`

`MockDial` implements `Dial` for the mock tests, inside `replay_mock.rs`. Per attempt it: takes a

### 5.2 The fault relay (`tests/support/fault_relay.rs`)

The live tests and the example reach the real gateway's WebSocket port through a loopback TCP relay
on `127.0.0.1:0` (identify and ticket minting use the Unix control socket and never pass through it).
It forwards bytes to the target port taken from the first discovery, never parses or logs them (the
ticket travels in the upgrade request), and offers:

- `drop()`: close both sides of every open connection now (no WebSocket close frame).
- `blackhole()`: keep open connections open but forward nothing either way; accept new connections
  and hold them without forwarding.
- `refuse()`: accept each new connection and close it at once.
- `restore()`: close every connection held or blackholed since `blackhole()`, then forward new
  connections normally.

The gateway's `Host` check ignores the port (fact C7) and its loopback-peer check sees the relay's
`127.0.0.1` (fact C6), so the upgrade passes; if it does not, that is a stop condition. The dial
through the relay uses `GatewayDial::via_origin`, which needs P1-01's `Endpoint::with_api_origin`
(one `#[doc(hidden)]` accessor beside `with_instance_id`).

  above the cursor (or `SnapshotRequired` when the cursor is below the watermark) via
  `on_replay_window`; and, on a gap, `resync` with the cursor `(epoch, latest published seq at that
  moment)`. Oracle per session: delivered `seq` strictly increasing; with no gap, delivered equals the
  published list; at most one gap per incident (gap to next `resync`); deliveries before the first
  gap are a prefix of the published list; and the deliveries between each `resync` and the next gap
  (or the end) are a contiguous run starting at that `resync` cursor + 1.

## 8. Design reasoning worth keeping

- The roadmap says "for every subscribed session, `session.events.since`". At v0.22.4 that alone would
  leave the new connection with no live events (fact R12). The re-attach call is therefore part of
  replay, not an extra feature. Record this as a learning in the journal.
- One `Client` for the life of the link, with `replace_connection` per reconnect, keeps every clone
  held by P1-12 valid, keeps open server requests answerable (P1-02 REQ-10), and keeps P1-02's
  request ids unique across connections.
- The first connection is not retried. A person starting Talaria with no gateway should see "no
  Hermes gateway is running" and the next step at once, not an endless "reconnecting". P1-12 decides
  what to do with the error.
- The recorder hook (`on_connect`) keeps this unit independent of P1-04, which builds in parallel, and
  still lets P1-12 record the handshake frames of every connection with the right generation.
- A full transcript comes back on every re-attach (§2.4). That is the price Desktop pays too. If it
  proves slow for long sessions, the remedy is upstream (a subscribe-only verb, or honouring
  `omit_messages` on the canonical resume), not a workaround in Talaria.
- Talaria tracks only sessions it attached, so the number of cursors is bounded by what the user
  opened; Hermes's cap of 256 cursors ([`json-rpc-gateway.ts:125-132`](https://github.com/NousResearch/hermes-agent/blob/v0.22.4/apps/shared/src/json-rpc-gateway.ts#L125-L132))
  is not needed in phase 1. The fleet phase re-checks this.
- Journal. `LEARNINGS.md` gets one entry for the re-attach finding, with **Evidence** (facts R12 and
  R13, the pull request and `file:line` of the re-attach call), **Mechanism** (a subscription belongs to
  its connection; `session.events.since` only reads the ring) and **Generalizable rule** ("a replay
  buffer is not a subscription; re-attach before replaying"). `DECISIONS.md` gets one entry per
  departure from Hermes's client, each with rationale, the rejected alternative and a "revisit when"
  condition; the headings carry the words the acceptance check searches for:
  - "Half-jitter backoff, 1 to 30 s" (rejected: Hermes's full jitter from 0; revisit when a floor of 1 s
    proves too slow on a local gateway).
  - "Grace tick after a late heartbeat tick" (rejected: Hermes's immediate death on a late tick;
    revisit when sleep detection becomes available from the platform).
  - "Replay failure becomes a gap" (rejected: swallowing replay errors as Hermes does; revisit when
    Talaria gains a history backstop).
  - "No retry of the first connection" (rejected: retrying from start-up; revisit when Talaria gains a
    background mode that should wait for a gateway).
