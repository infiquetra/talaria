## 1. What this unit adds, in one paragraph

Two small conveniences that Claude Code users type every day. A draft that starts with `!` runs one shell command through Hermes (`shell.exec`) in the session's working folder on the gateway host, and shows its output in a local transcript cell; the agent never sees it. `/btw <question>` asks a side question about the current conversation (`prompt.btw`); Hermes answers it from a snapshot of the conversation, with tools denied, without adding anything to the conversation or interrupting a running turn, and the answer arrives later as a `btw.complete` event that Talaria shows as a side-answer cell. Neither is queued behind a turn. Neither has a cancel call in Hermes. One trap shapes the design: Hermes serves one connection's requests one at a time, so a running `!` command delays every later request on the same socket (S16).

## 3. Design

### 3.1 Settled decisions and why

1. **Output stays local.** Hermes keeps `!` output out of the conversation (S14). Claude Code puts it in and lets the model answer. Copying Claude Code would need a second, client-made prompt, which is agent logic in the client (principle 1 of [05-architecture.md](../05-architecture.md#principles)). The composer's shell-mode title says plainly that the agent does not see the output. Whether to forward output (or support `{!cmd}`) is an operator question: the builder raises it as a comment on the parent issue, never by editing the handoff.
2. **Not queued behind turns.** Hermes keeps `shell.exec` and `prompt.btw` out of its admission queue (S14, B6), and Ink also runs a typed `!` at once while busy (2.3). `/btw` is useful precisely while the agent works. "Not queued" is not "parallel": the connection's request lane (S16) still runs one request at a time, so four `!` commands finish one after another, and a running `!` delays a later interrupt by up to 30 s. A second connection for `!` would remove that delay; it is out of scope and raised as an operator question on the parent issue.
3. **One final cell per action, placed so it never waits.** A pending action is not a cell. It is a row in a small "side tasks" section of the live region. When the result arrives, one final cell is inserted at `final_prefix_len()` (the first non-final position of the session's cell list, or the end when every cell is final). `P1-06`'s commit ledger writes "the longest final prefix", so a pending cell in the list would block every later commit. A `btw.complete` may never arrive (B8), so a pending cell could block scrollback forever.
4. **`/btw` never goes through `slash.exec`** (B13). It is a local command in `P2-03`'s table (`LocalAction::Btw`) whose app-side arm calls this unit's `btw_command`.
5. **No retries, no cancel.** A shell command may have side effects; an unknown outcome is shown as unknown. A side question costs model tokens; an unknown outcome waits for a matching answer instead of asking again. Hermes has no cancel for either (B9). Esc and Ctrl+C keep their `P1-08` meanings and do not touch side tasks.
6. **Pure core.** The reducer allocates request ids and never reads a clock or writes a log (ignored results are dropped silently; the app may count them, never log their text, because a command can hold a typed secret): the app passes `now_ms` inside events (`started_ms`, `accepted_ms`, `duration_ms`, `SideClock { now_ms }`). The 300-second side timeout is decided by the reducer when the app sends `SideClock` at the deadline `side::next_tick` gives (at most once a second while anything is pending, none while idle), so no service holds a timer and nothing needs cancelling when the answer arrives first.
7. **Two kinds of text.** Shell output is untrusted text: it is written literally, never interpreted as markup ([05-architecture.md, Security](../05-architecture.md#security)). A side answer is model output of the same kind as an assistant reply, which the architecture renders as Markdown; it goes through `P1-07`'s `render_markdown`, which applies `sanitize_untrusted`. Both pass `clean_output` first.

### 3.2 Submission routing

`talaria_core::side::classify(raw_draft: &str) -> Submission`, on the raw draft (before `P2-04` expands mentions or image tokens):

| Draft (exact) | Result | Reason |
|---|---|---|
| `!git status` | `Shell("git status")` | `!` is the first character; rest trimmed (as Ink does). |
| `!  ls -la  ` | `Shell("ls -la")` | Trim both ends. |
| `!` or `!   ` | `ShellEmpty` | Hermes would refuse a blank command (S5); say so locally. |
| `!echo a\necho b` | `Shell("echo a\necho b")` | Multi-line text is one `/bin/sh` script (S11). |
| `!!` | `Shell("!")` | No special case; the shell decides. |
| ` !ls` (leading space) | `Prompt` | The rule is the first character only; this is also how to send the agent a prompt that starts with `!`. |
| `please run !ls` | `Prompt` | `!` not first. |
| `/btw x` | `Prompt` here; `P2-03`'s slash dispatch sees it next | This unit's classifier only knows `!`. |

Routing order in the app's submit path (`talaria-app/src/app.rs`, `P1-12`'s submit handling):

1. `P2-08`'s queued-row edit mode, if `P2-08` has merged and edit mode is on (with `P2-08` unmerged, edit mode is always off): its submit goes to `prompt.replace_queued`, never here. If `P2-08` has not merged, there is no edit mode and this step is skipped (no hook is needed). This departs from Ink, which checks `!` first (2.3); Talaria keeps edit mode first so an edited queued prompt stays a prompt. State the departure in the pull request.
2. `classify`. `ShellEmpty`: emit `ShellEmpty` (the hint), with or without a session. `Shell(cmd)`: if no session is open (`AppState` has no `OpenedSession`), show the no-session notice and keep the draft; else emit `ShellRequested { command: cmd, started_ms: now }`.
3. `P2-03`'s slash dispatch. Its `LocalAction::Btw` arm calls `btw_command(arg, now)`. `SideUsage` (blank argument) is shown with or without a session. A `SideAsked` with no session open is replaced by the no-session notice, and the draft is kept.
4. `P1-12`'s held-prompt rule (prompts typed while the session is still opening are held).
5. `prompt.submit`.

Composer and history, per outcome: a sent `!` or `/btw` (an effect was emitted) clears the composer and enters its history like any other submit; the blank hint and the usage notice clear the composer and add no history; the no-session notice keeps the draft in the composer and adds no history. `!` and `/btw` are never held by step 4, because they are handled before it.

Base branch: `LocalAction::Btw` lives in `P2-03`'s table, so until `P2-03` merges the builder branches from `P2-03`'s branch and rebases onto `main` after it merges; its types are never stubbed.

`Effect::RunShell { session_id: SessionId, request_id: RequestId, command: String }`; `Effect::AskSide { session_id: SessionId, request_id: RequestId, question: String }`.

```rust
pub enum ShellOutcome {
    Ok { stdout: String, stderr: String, code: i64 },
    Refused { reason: String, detail: Option<String>, rpc_code: i64 },
    Unknown,                       // TimedOut, Unknown: may or may not have run
    Unreadable,                    // BadResult: ran, reply did not decode
    NotSent { not_connected: bool }, // NotConnected (true); Encode, InvalidTimeout (false)
}
pub enum SideOutcome {
    Answered { text: String },     // cleaned at render time
    Failed { text: String },       // the rest after "error: "
    Refused { reason: String, detail: Option<String> },
    NotSent { not_connected: bool },
}
pub enum Origin { Here, Elsewhere }
pub struct ShellCell { pub command: String, pub outcome: ShellOutcome, pub duration_ms: u64 }
pub struct SideCell { pub question: String, pub outcome: SideOutcome, pub origin: Origin, pub late: bool }
```

`P1-05`'s own `Event::Interrupt` leaves `SideTasks` untouched (test 43). Notices are `P1-05`'s `Cell::Notice` with `NoticeKind::System` or `NoticeKind::Warning`.

`side::carry_over(old, new)` moves `old.side_mut()` into `new` with `std::mem::take` (pending rows, `answered`, `unconfirmed`, `timed_out`, `last_request_id`). The app calls it whenever it replaces the session state from a snapshot (`P1-03` REQ-22: after a replay gap, `session.resume` and `SessionState::from_snapshot`), so pending rows keep their timeout and a late answer still matches.

`shell_outcome_text(&ShellOutcome) -> Option<String>` returns the 3.6 text for every outcome except `Ok` (refusals through `shell_refusal_text`); `side_outcome_text(&SideOutcome) -> Option<String>` does the same except for `Answered`. The colour is chosen in `talaria-tui` (warning for `Unknown` and `Unreadable`, error otherwise); core knows no colours.

`Cell::Shell(ShellCell)` and `Cell::Side(SideCell)` are final when created. Every insert goes through one helper added to `P1-05`'s session module, `fn insert_final(&mut self, cell: Cell)`, which inserts at `final_prefix_len()`. Notices made by this unit use the same helper.

### 3.5 Matching `btw.complete`

Let `q` be `payload.question` trimmed (absent when `null`).

1. If `task_id` is in `answered`, ignore the event (dedupe; replay after reconnect is exactly once by `P1-03`, but two windows or a resubscribe can repeat).
2. Else if a pending Side row has this `task_id`: remove it, insert `SideCell { question: row.question, origin: Here, late: false }`.
3. Else if `q` is present and a pending Side row with `task_id: None` has `question == q`: remove the **oldest** such row, insert `SideCell { origin: Here }`. Its later `SideAccepted` finds no pending row and is ignored (B14).
4. Else if `q` is present and `unconfirmed` holds `q`: remove the **oldest** such entry, insert `SideCell { origin: Here }`.
5. Else if `task_id` is in `timed_out`: remove it there, insert `SideCell { question: q or "(question not given)", origin: Here, late: true }`.
6. Else insert `SideCell { question: q or "(question not given)", origin: Elsewhere }`.
7. In every case except 1, add `task_id` to `answered`.

Outcome: `text` starting with the exact prefix `error: ` is `Failed { text: rest }`; an empty `text` is `Answered { text: "" }` rendered as `(no answer)`; anything else `Answered`. Known limit: a genuine answer that begins with `error: ` would be shown as a failure; Hermes uses that prefix as its only failure signal (B5).

`btw.complete` never changes turn state: no user cell, no change to the live assistant cell, the interrupt latch, `execution_generation`, the outcome of `message.complete`, or the replay cursor beyond what `P1-05` already does for every event. `background.complete` and `preview.restart.complete` stay silent (they belong to later phases).

### 3.7 Rendering

Shell cell (example at 80 columns):

```text
! echo oops >&2; exit 3                                                     0.2s
  oops                                                                (warning colour)
  exit 3                                                              (error colour)
```

- Header: `! ` plus the first line of the command; when the command has more lines, ` (+N lines)` where N is the number of lines after the first (` (+1 line)` for one). Row 1 reserves the duration's display width plus one space at its right end; the header text wraps by character into the rest of row 1 and then into full-width continuation rows indented two spaces. The dim duration is right-aligned on row 1.
- `format_duration(ms)`: below 9,950 ms, one decimal rounded half up (`(ms + 50) / 100` tenths: 0 → `0.0s`, 49 → `0.0s`, 50 → `0.1s`, 9,949 → `9.9s`); from 9,950 ms, whole seconds rounded half up (`(ms + 500) / 1000`: 9,950 → `10s`, 12,400 → `12s`, 12,500 → `13s`). The duration includes any wait behind an earlier request on the lane (S16).
- Body: the trim line if due, standard output lines, then the standard-error trim line if due and standard error lines in the warning colour; each line indented two spaces and wrapped by character with `P1-06`'s `wrap_lines`. Everything Hermes returned is shown (at most 6,000 characters in total, S13); no collapsing.
- Exit line and `(no output)` as in 3.6. Refused, unknown, unreadable and not-sent cells: header, then the 3.6 text (error colour unless 3.6 says warning).
- Colours come from `SideTheme::default()` (warning yellow, error red, dim modifier); `P2-12` may replace the theme.

Untrusted text, in two stages:

1. `clean_output(text)` (pure, in `talaria_core::side::text`) runs on `stdout`, `stderr` and the side answer and failure text: remove CSI (`ESC [` up to a final byte 0x40 to 0x7E) and OSC (`ESC ]` up to BEL or `ESC \`); an unterminated CSI or OSC is removed to the end of its line; any other `ESC` is removed with the next character (a whole character, never half of a multi-byte one); `\r\n` becomes `\n`; each line keeps only the text after its last lone `\r` (`abc\rxy` becomes `xy`); trailing empty lines are dropped. A line (or a whole text) is empty when only whitespace is left (`str::trim().is_empty()`); the same rule decides `(no output)` (both cleaned streams empty) and `(no answer)`. So `a` followed by a line of spaces cleans to `a`. Single-byte C1 controls (U+0080 to U+009F, including U+009B and U+009D) are left for stage 2.
2. At render time every line goes through `P1-06`'s `history::sanitize`, which turns C0 and C1 controls, tabs and bidirectional overrides into visible stand-ins. The side answer goes through `P1-07`'s `render_markdown`, which applies `sanitize_untrusted`. `clean_output` lives in core because it is pure text work; `sanitize` stays in the terminal crate, so core never imports it.

Known limit: Hermes's tail cut can split an escape sequence; the fragment after the cut (for example `[31m`) has no `ESC` and shows as text.

Side cell:

```text
btw · what file did I ask you to edit?
  You asked me to edit **calc.py**, to fix the average function.   (Markdown)
  side answer · not part of the conversation                        (dim)
```

- Header `btw · ` plus the question, wrapped and sanitised, plus the markers in 3.6.
- Body: the cleaned answer through `render_markdown` at the cell width minus 2, each line indented two spaces, then the footer. Header continuation rows are indented two spaces. Failure, refused and not-sent cells: their 3.6 text, no footer.
- Colours: `SideTheme` implements `Default` by hand (warning `Style::default().fg(Color::Yellow)`, error `Style::default().fg(Color::Red)`, dim `Style::default().add_modifier(Modifier::DIM)`).

Side-tasks live section (`SideTasksSection`, a `P1-06` `LiveSection` placed between the live tail and the composer):

```text
 ◌ ! cargo test -q · running · 4s
 ◌ btw · what did the last test print? · answering · 12s
 ◌ +2 more
```

At most three task rows plus one `◌ +N more` row; height 0 when nothing is pending. Rows longer than the width are cut with `…`. The glyph is static (no animation, so reduced motion needs nothing). Elapsed seconds are `(now_ms - started_ms) / 1000`, rounded down. `talaria_core::side::next_tick(&SideTasks, now_ms)` returns the absolute app-clock time in milliseconds of the next whole-second change of any row (`started_ms + 1000 * (elapsed_s + 1)`, the minimum over rows), or `None` when nothing is pending; `SideTasksSection::next_tick` delegates to it.

Wake-up: while `next_tick` is `Some(t)`, the app loop wakes at `t` and handles it as `P1-12`'s `AppMessage::Tick`: it sends `SideClock { now_ms }` to the reducer and redraws. If the merged `P1-12` loop has no deadline-driven wake-up, this unit adds one `tokio::time::sleep_until(t)` in `app.rs`, re-armed whenever `next_tick` changes. With nothing pending this unit arms no wake-up, sends no `SideClock` and asks for no redraw, so it adds nothing to the idle budget (zero frames when nothing changes, [05-architecture.md](../05-architecture.md#performance-budgets); `P1-11`'s `bench` idle row watches 30 s for zero frames). Test 44 checks this through `P1-12`'s pure `update(&mut AppState, AppMessage) -> Vec<AppEffect>`. A `P1-12` loop that redraws while idle is `P1-12`'s defect: report it there.

Composer title: while `P2-08`'s edit mode is off (always, when `P2-08` is unmerged), on every draft change and after a submit, the app calls `P1-08`'s `set_title(Some(...))` with the 3.6 title when the draft's first character is `!`, and `set_title(None)` otherwise. While edit mode is on, this unit never calls `set_title`, so edit mode's own title is never cleared by it. After a submit the composer is empty, so the title is cleared.

### 3.8 The app service

`talaria_app::side::SideService` holds `P1-02`'s `Client` and executes the two effects. `execute(&self, effect, now_ms)` returns the events to feed back through the app's single channel. The mapping from a call result to an outcome is two pure functions in the same module, so test 37 can build every `CallError` variant directly (they are public, `P1-02` spec section 7) without a server: `shell_outcome(Result<ShellExecResult, CallError>) -> ShellOutcome` and `side_reply_event(RequestId, Result<TaskIdResult, CallError>, now_ms) -> Event`. `execute` calls the client, then these.

- `RunShell` → canonical `shell.exec` with exactly `{session_id, command}`. Never `profile`: the connection is already scoped to its profile, and the dispatcher drops an own-profile value anyway (S4). Per-call timeout: the client default (120 s). That covers Hermes's 30 s plus up to three earlier `!` commands waiting on the lane. A `!` queued behind four or more running ones can reach 120 s and show the `Unknown` text while Hermes still runs it; this is accepted (UAT-5 queues four), and it is never retried. `duration_ms = now_ms()` after minus before.
  - `Ok(result)` → `ShellFinished(Ok { stdout, stderr, code })`.
  - `Err(Rpc(e))` → `ShellFinished(Refused { reason, detail, rpc_code: e.code })` (reason by the 3.6 extraction rule).
  - `Err(TimedOut | Unknown)` → `ShellFinished(Unknown)`.
  - `Err(BadResult)` → `ShellFinished(Unreadable)`.
  - `Err(NotConnected)` → `ShellFinished(NotSent { not_connected: true })`; `Err(Encode | InvalidTimeout)` → `NotSent { not_connected: false }`.
- `AskSide` → legacy `prompt.btw` through its generated `NativeMethod` type (B2), exactly `{session_id, text: question}`.
  - `Ok(TaskIdResult)` → `SideAccepted { request_id, task_id, accepted_ms: now_ms() }`.
  - `Err(Rpc)` → `SideRefused`. `Err(NotConnected)` → `SideNotSent { not_connected: true }`; `Err(Encode | InvalidTimeout)` → `SideNotSent { not_connected: false }`.
  - `Err(TimedOut | Unknown | BadResult)` → `SideUnknown` (with `BadResult` Hermes accepted the question but the id is unreadable; the answer can still match by question, rule 4).
- Never send `unattended`, `submission_id` or any other key: both handlers refuse extra keys (S5, B3). No retries. No timer (decision 6).
- The service never touches a session the connection has not subscribed to: the foreground session was opened by `session.create` or `session.resume`, both of which subscribe (B16), and `P1-03` re-attaches with `session.resume` after every reconnect.
- One session: phases 1 and 2a have no in-app session switch (`P1-12` opens one session per process), so every result belongs to the foreground session. Effects carry `session_id` so a later unit that adds a switch can route results by it.

### 3.9 Things that stay true across the rest of the client

- **Resume.** Shell and side cells are local: a later `session.resume` snapshot does not contain them (S14, B11). They remain in the terminal's own scrollback from before. `P2-02`'s pager shows them only for this run.
- **Reconnect.** At v0.22.4 a subscription belongs to its connection: only `session.resume` writes it (`gateway/session_controls.py:614-615`), detach removes it (`:675`), and `session.events.since` does not subscribe (`:679-686`). `P1-03` re-attaches each tracked session with `session.resume` before replaying, so `/btw` works again after a reconnect. A `btw.complete` published while the socket was down arrives through `session.events.since` (B11) and matches by `task_id`. If the replay ring was truncated, `P1-12` rebuilds the state from a snapshot and calls `side::carry_over`; the answer is lost and the 300 s timeout reports it. A shell call in flight when the socket dropped is `Unknown`.
- **Several windows.** Every subscribed window sees a `btw.complete` (B12); the asking window shows it as its own, others mark it "asked in another window".
- **Esc while `!` runs.** `P1-08`'s Esc interrupts only a running turn; with no turn it only clears a visible exit hint (`P1-08` REQ-9), so a bare `!` is never interrupted and nothing is sent. During a turn the interrupt is sent at once, but Hermes handles it only after the running command returns (S16).
- **Recording.** `P1-04`'s recorder records `shell.exec` and `prompt.btw` frames like any other and applies its own redaction rules to every frame before writing. The recording scenario's commands and questions are fixed, non-sensitive strings.

## 4. Mock-server rules

A mock built for these tests (handlers added to `crates/talaria-app/tests/support/mock_gateway.rs`) must answer only what the pinned contract and the source in section 2 allow, and builds every payload through `P0-03`'s generated types:

- `shell.exec` request: accept only `session_id`, `command`, optional `profile`; reply `{"stdout": "...", "stderr": "...", "code": n}` with all three keys; refusals as `{"code": 4001, "message": "<reason>", "data": {"reason": "<reason>"}}`, adding `"field": "terminal.backend", "detail": "docker"` for `unsupported_terminal_backend`; unknown method as `{"code": -32601, "message": "unknown method: shell.exec", "data": {"reason": "unknown_method"}}`; storage as `{"code": 5001, "message": "storage_unavailable", "data": {"reason": "storage_unavailable"}}`. Reasons allowed: those in S5 to S12 and S15.
- `prompt.btw` request: accept only `session_id`, `text`, optional `profile`; reply `{"task_id": "btw_1a2b3c"}` (prefix `btw_` and six lowercase hex digits); refusals as above with the B3 reasons.
- `btw.complete` event: `{"jsonrpc":"2.0","method":"event","params":{"type":"btw.complete","session_id":"<sid>","seq":<n>,"replay_epoch":"<epoch>","payload":{"task_id":"btw_1a2b3c","question":"<q>","text":"<answer>"}}}`. Either order relative to the reply is real (B14); a test that is not about ordering sends it after the reply.
- Hermes serves one connection's requests one at a time (S16). Do not change the shared mock's existing behaviour to imitate that; a test that needs the ordering, such as test 38's single-request count, asserts on what the mock received.
- Scripted modes, opt-in per test, default behaviour unchanged: for `shell.exec` and `prompt.btw`, reply with a given result, refuse with a given code, reason and detail (test 36 loops over the reasons), or close the socket before replying (test 38); for `prompt.submit` (test 40), accept the submit and send no `message.complete`, so the turn stays open.
- Never invent a cancel method, a progress event for `/btw`, or a streaming shell output event; Hermes has none at v0.22.4.
