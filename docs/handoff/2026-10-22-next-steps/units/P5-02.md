# P5-02: Workflow journal and resume that never re-runs a finished agent (unit P5-02)

Status: `proposed`. The GitHub issue for this unit is the contract; this document is its reference specification. If they disagree, the issue wins and the disagreement is reported on the issue.

## 1. The design in one page

A workflow run is a script (unit `P5-01`'s engine) that calls `agent()` many times. Each call becomes one Hermes session with one or two prompts (unit `P5-03`'s binding). This unit makes that durable:

1. **One run folder per run.** It holds `manifest.json` (written once, atomically), `journal.jsonl` (append-only, one record per line), `run.lock` (the single-writer lock), `scripts/<sha256>.js` (every script version that ran), `blobs/<sha256>` (large payloads, immutable and content-addressed) and `resolutions/` (operator answers for parked calls). The caller chooses where run folders live (unit `P5-06` owns the runs directory).
2. **Write-ahead.** Before every Hermes call that creates something (a session, a prompt), the journal records the intent, with the exact identifier and payload it will send, and waits until the record is on disk. After the call answers, the journal records what came back. A crash at any point leaves a journal from which the next run can tell exactly what to do.
3. **Identifiers that Hermes deduplicates.** The session's `request_id` and each prompt's `submission_id` are derived from the run id and a journal key. Hermes treats a repeated `request_id` from the same principal and profile as the same session, and a repeated `submission_id` with the same text as the same admission. So a retry after a crash never creates a second session or a second prompt.
4. **Resume is re-executing the script, with ordered replay.** The engine runs the script again from the top, with the same start time, seed and arguments, and with a replay log (`P5-01`'s `ReplayLog`): the finished results, in the order the earlier run delivered them to JavaScript. `P5-01` replays those without calling the backend, in that order, so every later call gets the same `CallId` it had before. For every other `agent()` call the backend's journal state says: finished (return the stored result), in flight (re-attach with `session.resume` and `prompt.receipt`), half-started (repeat the exact create or submit), unknown (park and ask the operator), or new (run it).
5. **Delivery order is durable before it matters.** A new call's backend future first waits until the engine's `AgentStarted` event for that call is on disk. Engine events are journaled in stream order, so every delivery that led to the call is on disk before the call writes anything or reaches Hermes.
6. **Unknown is never re-run.** If Hermes restarted while a prompt was running, Hermes marks that admission `unknown` and never replays it. This unit does the same: the call waits for an operator decision (fail it, re-run it, or abort the run), or fails at once if the run's policy says so. A result Hermes still holds is always kept.

```text
           ┌────────────── journal says ──────────────┐
agent() ──►│ in the replay log → engine replays it    │──► value to the script
           │ finished          → stored result        │
           │ in flight         → session.resume, receipt
           │ half-started      → exact retry          │
           │ unknown           → park, ask the operator
           │ new               → gate, create, submit │
           └──────────────────────────────────────────┘
```

What this unit does not do: it does not build session parameters, prompt text, schema checks or the correction turn (`P5-03`), staffing or scheduling (`P5-04`), the progress view (`P5-05`), the `talaria workflow` commands or the runs directory (`P5-06`), or worktrees (`P5-07`). It defines the traits those units implement, and it tests them with a fake gateway built from the Hermes rules in section 8.

## 3. The run folder

```text
<run folder>/              mode 0700 on Unix
  manifest.json            written once (temp file, sync, rename), never changed
  journal.jsonl            created empty by create; append-only; one JSON object per line
  run.lock                 held with an exclusive lock by the one live writer
  scripts/<sha256>.js      every distinct script source that ran in this run
  blobs/<sha256>           payloads too large to inline (section 4.3); immutable, never deleted here
  resolutions/             operator answers for parked calls (section 7.2), written by other processes
```

Every file this unit creates has mode 0600 on Unix (`OpenOptionsExt::mode`, `DirBuilderExt::mode`). The run folder is private local data: it holds exact prompts and results, because exact retries need them (H11). It is never evidence; public evidence goes through the `P1-04` recorder's redaction.

### 3.1 Run id

26 characters of Crockford base32 (`0-9`, `A-Z` without `I`, `L`, `O`, `U`), time-ordered like a ULID: 48 bits of creation time in milliseconds, 80 random bits. Created once by `RunDir::create`; never derived from the script. `RunId::parse` refuses anything else. `RunDir::create_with_id` (`#[doc(hidden)]`, for tests) takes the id from the caller; a folder that already exists is `JournalError::Exists`.

### 3.2 `manifest.json`

```json
{
  "v": 1,
  "run_id": "01JB2X9Q4M8Z7K3T5V6W8Y0A1C",
  "created_at_ms": 1792627200000,
  "workflow": {"name": "review-branch", "script_sha256": "<64 hex>"},
  "args": {"branch": "main"},
  "started_at_ms": 1792627200000,
  "seed": 4242,
  "profile": "fixture",
  "on_unknown": "wait",
  "talaria_version": "0.7.0",
  "hermes": {"describe": {}},
  "roster": {},
  "approval_policy": {}
}
```

- `started_at_ms` and `seed` feed `EngineConfig::new(run_id, started_at_ms, seed)` on every resume (unit `P5-01` REQ-18), so `now()` and `random(key)` return the same values.
- `args` is stored once; a resume uses it unchanged.
- `on_unknown` is `wait` (default) or `fail` (section 7).
- `hermes`, `roster` and `approval_policy` are opaque JSON supplied by the caller (`P5-06` passes `runtime.describe` output, `P5-04` the roster snapshot). This unit never interprets them, but `RunDir::create` refuses a manifest in which any of them, or `args`, holds a credential: an object key that, lower-cased with `-` and `_` removed, is `token`, `accesstoken`, `refreshtoken`, `ticket`, `secret`, `clientsecret`, `password`, `apikey`, `authorization` or `cookie`, or a string value starting with `hermes-gateway-ticket`. The error is `JournalError::Manifest("manifest field <json pointer> looks like a credential")`, and nothing is written. Tickets and keys never reach this unit: the port holds the connection.
- `created_at_ms` is the wall clock (`SystemTime::now()`, milliseconds) when `RunDir::create` runs, for display only; `started_at_ms` is the caller's value (`P5-06` normally passes the same instant).
- Writing: serialise, write `manifest.json.tmp`, `sync_all`, rename over `manifest.json`, `sync_all` the folder. The manifest is never changed after `create`; there is no update API.

### 3.3 Lock, and who takes it

`RunDir` is an unlocked handle: `create`, `open`, `manifest`, `store_script` and `request_resolution` take no lock, so another process (the operator answering a parked call) can use it while a runner holds the run. `RunJournal::open` takes the lock before it reads or changes `journal.jsonl`: it opens `run.lock` (created if absent) and locks it with `std::fs::File::try_lock` (stable since Rust 1.89). Failure is `JournalError::Locked { run_id }`, printed as "run <id> is already open in another runner". The lock is held for the life of `RunJournal` and released by the operating system if the process dies. No stale-lock cleanup is needed or allowed. `store_script` is create-new by content hash, so a concurrent call is harmless.

`RunDir::open(path)` takes the run folder itself (`<parent>/<run_id>`), not its parent. It returns `BadRunId` when the folder name is not a run id or differs from the manifest's `run_id`; `Manifest(reason)` when `manifest.json` is missing, is not JSON, has `v` other than 1 or lacks a field; `Io` otherwise. `RunDir` is `Clone` (a path, the id and the parsed manifest), and `RunJournal::dir()` returns the handle it was opened with, so a runner holding the journal can still call `request_resolution`.

Toolchain: `File::try_lock` needs Rust 1.89 or later. The Talaria repository had no workspace or toolchain pin when this was written; if the pinned toolchain (`rust-toolchain.toml` or `rust-version`) is older, that is stop condition 7.

## 4. The journal format (version 1)

Every line is one JSON object, UTF-8, newline-terminated, at most 1 MiB. Common fields:

| Field | Type | Meaning |
|---|---|---|
| `v` | integer | always 1 |
| `seq` | integer | 1, 2, 3 ... in file order, no gaps |
| `t` | string | the record type below |
| `at_ms` | integer | wall-clock time of writing, for display only; never used for identity or decisions |

In Rust a line is `RecordLine { v: u32, seq: u64, at_ms: i64, record: Record }`, with `record` flattened (`#[serde(flatten)]`). `Record` is the enum of the types below (serde tag `t`, snake_case); its variants carry only the further fields, never `v`, `seq` or `at_ms`. Callers hand the writer a `Record`; the writer stamps `v: 1`, the next `seq` and `at_ms` (`SystemTime::now()` in milliseconds) and writes one flat object, keys in the order `v`, `seq`, `at_ms`, `t`, then the variant's fields in declaration order. Golden tests build `RecordLine` values with `at_ms: 0`; engine-driven tests never compare `at_ms`.

Record types (`key` is the journal key of section 5.1; `attempt`, `turn` and `episode` are integers from 0; a `*_ref` field replaces its inline field when the payload is large, section 4.3):

| `t` | Further fields | Written |
|---|---|---|
| `run_started` | `run_id`, `script_sha256` | once, first line, by the first `RunJournal::open` (on the empty journal) |
| `run_resumed` | `script_sha256`, `resume_count` | by every later `RunJournal::open`; it starts a new execution |
| `engine` | `event` or `event_ref` (a serialised `P5-01` `EngineEvent`) | as engine events arrive, in stream order |
| `call_intent` | `key`, `attempt`, `call_id` (`digest`, `occurrence`), `label`, `phase`, `workflow_path`, `launch` (section 5.2), `request_id` | before `create_session` |
| `session_bound` | `key`, `attempt`, `session_id`, `stored_session_id` | after `create_session` answers |
| `turn_intent` | `key`, `attempt`, `turn`, `submission_id`, `text` or `text_ref` (the full text) | before `submit` |
| `turn_admitted` | `key`, `attempt`, `turn`, `admission_id`, `status`, `outcome`, `execution_generation`, `authority_epoch` | after `submit` answers |
| `turn_settled` | `key`, `attempt`, `turn`, `admission_id`, `outcome`, `final_text` or `final_text_ref`, `result_meta`, `usage` | after a terminal receipt read with `include_result` |
| `call_attention` | `key`, `attempt`, `episode`, `cause` (`unknown`, `lost`, `identity_conflict`), `turn`, `admission_id`, `execution_generation`, `detail` (at most 4,096 characters, cut) | when a call parks |
| `call_resolved` | `key`, `attempt`, `episode`, `resolution` (`fail`, `rerun`, `abort`), `source` (`operator`, `policy`) | when a parked call is answered |
| `call_finished` | `key`, `attempt`, `outcome` (`completed` with `value` or `value_ref`, `failed` with `reason`, `skipped`), `turns` (count) | when the call's outcome is returned to the engine |
| `run_finished` | `outcome` (`completed`, `failed`, `aborted`), `summary` (below) | by `finish()`, at the end of an execution |

`result_meta` copies only these fields of the saved result when present: `completed`, `failed`, `interrupted`, `turn_exit_reason`, `model`, `provider` (H19), each cut to 1,024 characters when a string. `final_text` is `result.final_response` when it is a string. `usage` is copied verbatim (H29). `reason` is cut to 4,096 characters.

Every cut in this document counts Unicode scalar values and keeps the first N of them, with no ellipsis or marker (`s.chars().take(n).collect()`): `detail`, `reason` and the `result_meta` strings.

`summary` is `{"completed": n, "failed": n, "skipped": n, "parked": n, "unfinished": n}`, counting the keys encountered in this execution (section 6.4) by their latest attempt: its `call_finished` outcome; `parked` for an unresolved `call_attention`; `unfinished` for anything else (a call the engine dropped, or one the run aborted).

### 4.1 Reading rules

The reader splits the file at newline bytes. Four cases, checked in this order:

1. **Incomplete bytes.** Bytes after the last newline (no terminating newline, whatever they contain) are a torn tail from a crash. The reader drops them and reports `JournalWarning::TornTail { line, bytes }`; `RunJournal::open` truncates the file to the end of the last newline before appending. `JournalReader` never truncates.
2. **Invalid JSON** on a newline-terminated line, the last one included: `JournalError::Corrupt { line, reason }`. Every append writes the line and its newline in one write, so a complete line was written whole; a bad one is damage, not a crash.
3. **Valid JSON with an invalid record:** `v` other than 1, unknown `t`, a missing or mistyped field, a `seq` gap, or no `run_started` on line 1: `Corrupt`. Unknown extra fields are ignored (forward compatibility).
4. **A semantic error:** a record that breaks the grammar of section 6.1, a `*_ref` whose blob is missing or has the wrong size, or an execution whose `agent_finished` engine records with a non-null `completion_seq` are not 0, 1, 2 ... in file order (section 6.7) (all checked at open): `Corrupt`. A blob whose SHA-256 does not match when it is loaded is `Corrupt` naming the referencing line: `engine_config` returns it as `Err` and the run does not start; inside a running execution it aborts the run ("journal blob <sha> failed its hash check").

On `Corrupt` the run refuses to resume; nothing is truncated or rewritten.

### 4.2 Writing rules

- One writer task owns the file. Callers send a record and await a reply that comes only after the record is written and `sync_data` has returned. Records that arrive while a sync is in flight are written together and share the next sync (group commit). `seq` is assigned by the writer.
- A write or sync failure is fatal for the run: every waiting caller gets `JournalError::Io`, and `JournaledBackend` turns it into `AgentOutcome::Abort { reason: "journal write failed: ..." }`. Never continue past an unrecorded step.

### 4.3 Large payloads (blobs)

The unbounded payloads are `engine.event`, `turn_intent.text`, `turn_settled.final_text` and `call_finished.value`. Each is inline when its serialised JSON is at most 256 KiB; otherwise the record carries the sibling field `event_ref`, `text_ref`, `final_text_ref` or `value_ref` instead: `{"sha256": "<64 hex>", "bytes": <n>}`, naming `blobs/<sha256>`.

- Blob bytes: for `text` and `final_text`, the string's UTF-8 bytes exactly; for `value` and `event`, the `serde_json::to_vec` bytes of the value. The SHA-256 is over those bytes.
- A blob is written before the record that names it: write `blobs/<sha256>.tmp`, `sync_all`, `hard_link` to `blobs/<sha256>` (an existing file with that name already holds the same bytes, so `AlreadyExists` is success), remove the temp file, `sync_all` the folder. Blobs are immutable and content-addressed, so two attempts with different large results never share a name, and nothing ever overwrites a referenced blob. This unit never deletes a blob.
- After externalising, a record whose line would still exceed 1 MiB is refused with `JournalError::RecordTooLarge { t, bytes }` before any Hermes call it guards. The backend finishes the call `failed` ("journal record too large: <t>"), which needs no Hermes call (section 6.1, short attempt). An `engine` record over the limit after externalising cannot happen (the whole event becomes a blob).
- Retries read the exact stored bytes back, so a large prompt is resent byte for byte (H11).

## 5. Keys and identifiers

### 5.1 Journal key

```text
key = first 32 hex characters of SHA-256( canonical JSON of
        {"v":1, "call":{"digest":<CallId.digest>,"occurrence":<CallId.occurrence>},
         "launch":<launch without cwd>} )
```

Canonical JSON is the same as unit `P5-01` section 7.1: keys sorted by code point, no whitespace, absent options omitted. The key includes the resolved launch, so editing the staffing table (a different model for a tier) makes a new key and the call runs again on the new model; the old record stays as an orphan (section 6.4), and the replay log leaves it out (section 6.7). `cwd` is left out of the key because a worktree path (`P5-07`) may differ between runs, but it is stored in `call_intent.launch`, and a retry of an existing intent always reuses the stored launch, `cwd` included, so the create retry is the same frozen request (H4).

### 5.2 Launch

```rust
pub struct ResolvedLaunch {
    pub profile: String,
    pub model: String,
    pub provider: Option<String>,
    pub effort: Option<Effort>,          // P5-01's enum
    pub toolsets: Vec<String>,
    pub skills: Vec<String>,
    pub max_turns: Option<u32>,
    pub isolation: Option<Isolation>,    // P5-01's enum
    pub cwd: Option<String>,             // stored, not keyed
}
```

Filled by the `LaunchResolver` (`P5-04` resolves tiers, `P5-03` the rest). The resolver must be a pure function of the request and the run's staffing snapshot: the replay check (section 6.7) calls it again for logged calls. This unit never maps it to Hermes parameters.

### 5.3 Hermes identifiers

| Identifier | Attempt 0 | Attempt n ≥ 1 |
|---|---|---|
| `request_id` | `wf:<run_id>:<key>` | `wf:<run_id>:<key>:a<n>` |
| `submission_id` for turn t | `wf:<run_id>:<key>:<t>` | `wf:<run_id>:<key>:a<n>:<t>` |

Lengths with a `u32` attempt (at most 10 digits) and turn 0 or 1: `request_id` at most 3 + 26 + 1 + 32 + 2 + 10 = 74 characters, `submission_id` at most 76, well under the 256 limit for `request_id` (H2) and 1,024 for `submission_id` (H10). The attempt-0 forms match the design in `06-workflows.md`. A new attempt means a new session, so it never queues behind a paused `unknown` admission (H21).

Attempts increase only in three ways: the operator answers `rerun` for a parked call and Hermes holds no result, a resume meets a call whose last attempt finished `failed`, or a resume meets a call whose last record is a `call_resolved(abort)` written by an earlier execution, with no saved result (sections 6.2, 6.3). Within one execution a key never starts a second attempt on its own.

## 6. The call state machine

### 6.1 Record grammar (what a strict reader accepts)

Records for one key, in file order, form attempts 0, 1, 2 ... (each record's `attempt` equals the current attempt; a new attempt's number is the last one plus 1). The table lists, for the last record of the key, which records may follow it for the same key. Anything else is `Corrupt`.

| Last record for the key | May be followed by |
|---|---|
| none | `call_intent(a=0)`; or a short attempt `call_finished(a=0)` with `skipped` or `failed` |
| `call_intent` | `session_bound`; `call_attention`; `call_finished(failed)` (create refused) |
| `session_bound` | `turn_intent(0)`; `call_attention`; `call_finished(failed)` |
| `turn_intent(t)` | `turn_admitted(t)`; `call_attention`; `call_finished(failed)` (submit refused) |
| `turn_admitted(t)` | `turn_settled(t)` with the same `admission_id`; `call_attention`; `call_finished(failed)` |
| `turn_settled(t)` | `turn_intent(t+1)` if t = 0; `call_finished` (any outcome); `call_attention` |
| `call_attention(e)` | `call_resolved(e)` |
| `call_resolved(e)` | `turn_settled(t)` for the parked turn and admission (Hermes held a result, section 7.3); `call_attention(e+1)` (stale generation, section 7.3); `call_finished(failed)` (answer `fail`); the next attempt (`call_intent(a+1)` or a short attempt) after `rerun` or `abort` |
| `call_finished(failed)` | the next attempt (a resume runs failed calls again) |
| `call_finished(completed or skipped)` | nothing |

- A short attempt is a lone `call_finished` with `skipped` (the gate said skip) or `failed` (the resolver refused the request, or a record was too large), written with no `call_intent` and no Hermes call.
- At most two turns (`MAX_TURNS_PER_CALL`); `turn_intent(1)` only after `turn_settled(0)`.
- At most one unresolved `call_attention` per key. `turn_settled` after a `call_resolved` continues as after any `turn_settled`.
- `run_started`, `run_resumed`, `engine` and `run_finished` carry no key and may appear anywhere after line 1; `run_started` only on line 1.

### 6.2 What a call does in each state (live run and resume alike)

**Executions.** Every record belongs to the execution opened by the nearest `run_started` or `run_resumed` before it (execution 0, 1, 2 ..., equal to `resume_count`). The journal's index keeps, per key, the execution that wrote its latest record. In the table, "in the same execution" means the running execution wrote it; "in a resume" means an earlier one did. This is what makes a failure, or an `abort` answer, written before a stop or a crash lead to the next attempt instead of repeating forever.

Every live `run_agent` future starts with two steps: the durability barrier (wait until this execution's `AgentStarted` for `request.call_id` is on disk, section 6.7), then the key (`journal_key(call_id, resolver.resolve(request))`; a resolver error is a short attempt `failed` with its message). Then:

| State found (latest attempt) | Action | Hermes calls |
|---|---|---|
| none, or the next attempt is due | gate `Fresh`; `Skip` writes the short attempt `skipped`; `Proceed` writes `call_intent`, creates | `session.create` |
| `Intent` | gate `Reattach`; exact retry of create with the stored launch and `request_id` | `session.create` (returns the same session, H4) |
| `Bound`, no turn | ask `TurnPolicy::first_turn`, write `turn_intent(0)`, submit | `prompt.submit` |
| `TurnIntent(t)` | attach, exact retry of submit with the stored text and `submission_id`; write `turn_admitted` | `session.resume`, `prompt.submit` (returns the existing admission in its current state, H11) |
| `Admitted(t)`, status `queued` or `started` | attach, read the receipt with result; if not terminal, `wait_settled` | `session.resume`, `prompt.receipt` |
| `Admitted(t)`, status `terminal` (also straight from a submit answer) | read the receipt with result (H27), write `turn_settled` | `prompt.receipt` |
| `Admitted(t)`, status `unknown` | park, cause `unknown` (section 7) | none |
| `Settled(t)` | ask `TurnPolicy::after_turn` with all settled turns of the attempt | none, or the next turn |
| `Parked`, unresolved | re-send the notice; consume a resolution file if one is waiting; else wait, or apply `on_unknown = fail` | none |
| `Resolved(e)` | the resolution procedure of section 7.3 (an `abort` from an earlier execution starts the next attempt there) | `prompt.resolve_unknown`, `prompt.receipt` (cause `unknown` only) |
| `Finished(completed or skipped)` | return the stored outcome; no gate | none |
| `Finished(failed)` in a resume | the next attempt is due | as for none |
| `Finished(failed)` in the same execution | return the stored failure | none |

"Attach" means `GatewayPort::attach` (`session.resume`) once per session per connection; the port tracks connections and returns at once when already attached. After any transport error the backend attaches again before its next submit, receipt or wait on that session. A `Receipt` with status `terminal` but no `result` from `receipt` (a terminal admission that saved nothing, such as `interrupted`) settles with `final_text: null`.

The `call_finished` record is written, and synced, before the outcome is returned to the engine.

### 6.3 Why a failed call runs again on resume

Claude Code's workflow resume returns cached results for completed calls and runs other calls again. A failed call (provider error, rate limit, schema invalid after the correction turn) produced nothing the script can use, and resuming is how a person retries. An `unknown` call is different: it may have done work (edits, tool calls), so it is never re-run without the operator. An `abort` answer ends the execution; the aborted turn is then terminal in Hermes (section 7.3), so a later resume treats the call like a failed one. These rules are settled by the issue (settled decision 8; REQ-15, REQ-18).

### 6.4 Orphans, in-flight work and usage

- **Provisional and final.** `RunJournal::open` cannot know which keys the resumed script will ask for (a script can branch). So at open `ReplaySummary::orphans` and `running_orphans` are empty. The journal marks a key as encountered when the backend computes it in this execution, or when a replay-log entry for it is built (section 6.7) and the engine's `AgentStarted { replayed: true }` for that `CallId` is recorded. `summary()` is provisional while the run is going and final once `finish()` has returned: every key with records that was not encountered is an orphan.
- **Counts.** At open and in `summary()`, over every key with records: `finished` counts keys whose latest attempt ended `call_finished` with `completed` or `skipped`; `in_flight` counts keys whose latest attempt has a `call_intent` and neither a `call_finished` nor an unresolved `call_attention`; `parked` lists the unresolved `call_attention`s. A key whose latest attempt failed is in none of them (it runs again). `resume_count` is the number of `run_resumed` records, the one this open wrote included (0 for a fresh run).
- **Finish.** The caller (`P5-06`, the example, the harness) calls `finish(outcome)` once, after `engine::run` returned and the `forward_events` task ended, so every engine event is recorded. It writes `run_finished` (section 4), marks the summary final and closes the writer: a later append, `record_engine_event`, `started_durable` or second `finish` returns `JournalError::Closed`. A `RunJournal` dropped without `finish` writes nothing, exactly like a crash.
- `OrphanCall` gives the key, label, latest attempt, last record type, session id, admission id and the last journaled admission status. `running_orphans` are the orphans whose last journaled status is `queued` or `started`: journal state, not a live receipt (`P5-06` may read receipts to show them, and offers to stop them). This unit never interrupts anything.
- **Usage.** `ReplaySummary::settled_usage` lists one `TurnUsage { key, attempt, turn, admission_id, outcome, usage }` for every `turn_settled` record in the journal: every attempt and turn, failed, parked, unfinished and orphaned calls included, each admission once (an admission settles once, section 6.1). `usage` is `None` when the settling receipt had no `usage` field and `Some(v)`, Hermes's object verbatim, otherwise (`Some({})` included). `unsettled` lists every admitted turn with no `turn_settled` (`UnsettledTurn { key, attempt, turn, admission_id, last_status }`), whose spend is not known: parked turns included, and turns resolved without a saved result stay there for good, because Hermes never reports their spend. `last_status` is the latest status the journal holds for the admission: `turn_admitted`'s, or `Unknown` once a `call_attention` with cause `unknown` names it. Replayed and cached calls add nothing. A consumer that restores spent totals by summing `settled_usage` must not count an admission twice when an unsettled turn later settles: each settlement in the running execution also sends `JournalNotice::TurnSettled { key, attempt, turn, admission_id, usage }`. (`P5-04` instead folds the `turn_settled` records it reads with `JournalReader`, each record once.)

### 6.5 Crash-point table

A crash can happen between any two steps. "Effect" is what Hermes holds; "Resume" is what the next execution does. Test 14 (section 10) injects a crash at every one of these points.

| # | Crash after | Journal last record for the key | Effect in Hermes | Resume |
|---|---|---|---|---|
| C1 | gate acquired, before `call_intent` | none | none | fresh start |
| C2 | `call_intent` written, before create sent | `call_intent` | none | create with stored `request_id`: new session, same id it would have had |
| C3 | create answered, before `session_bound` | `call_intent` | session exists | create retry returns the same session (H4) |
| C4 | `session_bound`, before `turn_intent` | `session_bound` | idle session | first turn text computed and journaled, submit |
| C5 | `turn_intent`, before submit sent | `turn_intent` | idle session | submit with stored text: new admission |
| C6 | submit answered, before `turn_admitted` | `turn_intent` | admission queued, running or already terminal | submit retry returns the same admission (H11); if terminal, receipt with result and settle (H27); no second prompt |
| C7 | `turn_admitted`, turn running | `turn_admitted` | turn running | attach, receipt, wait |
| C8 | turn finished, before `turn_settled` | `turn_admitted` | terminal admission with saved result | receipt with result; settle |
| C9 | `turn_settled(0)`, before the decision | `turn_settled` | idle session | `after_turn` decides again (it is pure) |
| C10 | `turn_intent(1)` (correction), before submit | `turn_intent` | idle session | submit correction with the stored text |
| C11 | `turn_settled(1)`, before `call_finished` | `turn_settled` | idle session | `after_turn` decides; turn cap reached means finish |

| C16 | `resolve_unknown` committed in Hermes, before its reply | `call_resolved` | `terminal` | `resolve_unknown` again returns the row (H22); receipt; act |

| C19 | short attempt `call_finished(skipped)`, before the value reaches the script | `call_finished` | none | stored `skipped` returned; no gate, no Hermes call |

### 6.6 Refusals and transport errors

| Port error | Where | Handling |
|---|---|---|
| `Transport`, `Timeout`, refusal `runtime_draining` | any step | outage handling below |
| `admission_conflict` | submit retry | park, cause `identity_conflict` (the stored text and Hermes disagree; never resubmit under a new id by itself) |
| `invalid_params` with field `request_id` | create retry | park, cause `identity_conflict` |
| `not_found` | attach or receipt of a known session or admission | park, cause `lost` (the session was deleted or pruned) |
| `queue_full` | submit | finish `failed` ("queue full"); workflow sessions should never reach 32 queued |
| `permission_denied` | submit or receipt | attach once more, then retry; a second refusal finishes `failed` |
| `stale_generation` | resolve_unknown | section 7.3 |
| any other refusal | any | finish `failed` with the reason; journal it |

Outage handling. `RetryPolicy::max_outage` (default 120 s) is an outage budget, not a turn budget. An outage starts at a call's first `Transport`, `Timeout` or `runtime_draining` error after a success, and ends at that call's next successful port call of any kind. The clock is per call: each `run_agent` future keeps its own, and only its own port successes reset it, so a healthy call never shields a dead one. While it lasts, the backend retries the same step (every step is idempotent) after 0.5 s, 1 s, 2 s, 4 s, 8 s, then every 15 s, attaching again first when the step needs a subscription. When the outage of one call reaches `max_outage`, that call returns `Abort { reason: "gateway unavailable: <last error>" }`; everything stays journaled and the next resume continues. A healthy `wait_settled` that is simply waiting for a long turn is not an outage, however long it takes: the port returns `Timeout` only when the gateway stops answering, never because inference is slow.

### 6.7 The replay log and the durability barrier

`P5-01` (its section 7.2) delivers backend outcomes to JavaScript one at a time, numbering each delivery with `completion_seq`, and replays a `ReplayLog` given in `EngineConfig::replay` in that order. This unit builds the log and makes the order durable.

**Barrier.** The caller forwards every engine event, in stream order, to `RunJournal::record_engine_event` (or calls `RunJournal::forward_events`, which does that for a receiver). Every live `run_agent` future first awaits `RunJournal::started_durable(&request.call_id)`. It resolves once an `engine` record holding `AgentStarted { replayed: false }` whose `request.call_id` equals that `CallId` (both `digest` and `occurrence`), written in this execution, is synced, and at once if that record was synced before the call. `P5-01`'s `AgentRequest` carries `call_id` and `workflow_path` (its specification section 8, which its issue makes binding), and a `CallId` is unique within one execution (the digest covers the workflow path; `occurrence` numbers repeats), so exact equality is the whole matching rule: nothing counts events or compares prompts. If the merged `AgentRequest` has no `call_id`, that is stop condition 3; there is no workaround. `P5-01` emits `AgentFinished` before the promise it settles, and a call is invoked only after the deliveries it depends on, so when the barrier opens, every delivery that led to this call is on disk. Only then does the call compute or write anything for its key, consult the gate, or reach Hermes. The 30 s limit belongs to the backend: it wraps the wait in `tokio::time::timeout(Duration::from_secs(30), ..)` and on expiry returns `Abort { reason: "engine events are not being journaled" }` (a wiring bug, never a normal path). `started_durable` itself waits without limit; it returns `Closed` after `finish()` and `Io` after a write failure. Replayed calls never reach the backend and need no barrier.

**Delivery history.** For each execution (from `run_started` or a `run_resumed` to the next), its deliveries are its `agent_finished` engine records with a non-null `completion_seq`, in `completion_seq` order; they must be 0, 1, 2 ... without gaps, else `Corrupt` (checked at open, section 4.1). The history H after execution k is: if execution k recorded `replay_diverged`, or its deliveries and the previous H do not agree position by position on `CallId`, its own deliveries; otherwise the longer of the two (one is a prefix of the other).

**Log.** `RunJournal::engine_config(&self, resolver: &dyn LaunchResolver) -> Result<EngineConfig, JournalError>` returns `EngineConfig::new(run_id.as_str(), started_at_ms, seed)` (the manifest's values; every limit stays `P5-01`'s default) with `args` from the manifest and `replay: Some(ReplayLog { entries })`, where the entries are H's deliveries, in order, keeping only those for which all of these hold:

1. the request of that `CallId` (from its most recent `AgentStarted` engine record) resolves with `resolver` to a launch whose key equals the key the call was journaled under; a changed launch or a resolver error leaves the entry out, so the call runs again under its new key;
2. that key's latest attempt finished `completed` (entry outcome `AgentOutcome::Completed(value)`, the value loaded from `value` or its blob) or `skipped` (`AgentOutcome::Skipped`).

It loads the blobs it needs (`AgentStarted` events and kept values); one that fails its hash check is `Err(Corrupt { line, reason })` naming the referencing line, and the caller must not start the engine. Failed deliveries are left out, so failed calls run again (REQ-14). Leaving an entry out can make the engine report `ReplayDiverged`; from there `P5-01`'s cache mode applies, with its documented limit (two identical calls with different stored results may swap). For a fresh run `replay` is `None`.

**The crash window.** If a crash comes after a `call_finished` is synced but before its `AgentFinished` record is, the delivery is not in H. On resume the call is invoked again with the same `CallId` (everything before it is replayed in order), goes to the backend as a live call, and gets the stored value from the journal with no Hermes call. Nothing written after that delivery existed, because of the barrier, so a different delivery position harms nothing.

## 7. Parked calls and operator answers

### 7.1 Parking

- A parked call writes `call_attention` with the next `episode` number for that key and attempt, drops its gate permit, and sends `JournalNotice::NeedsOperator { key, label, attempt, episode, cause, session_id, admission_id }`. Other branches of the script keep running.
- `on_unknown = "fail"`: the call is answered at once with `fail`, `source: policy`. This suits scripts and continuous integration.
- `on_unknown = "wait"` (default): the call waits for a resolution file (section 7.2).
- A runner that stops while calls are parked leaves them parked; the next resume finds `call_attention` without `call_resolved`, re-sends the notice, consumes a waiting file, and otherwise waits again. It writes no new record.
- `call_attention` and `ParkedCall` carry `turn`, `session_id` and `admission_id` exactly when the journal holds them for that attempt at parking time, and `execution_generation` only for cause `unknown`. So `unknown` has all four; `lost` has the session and, when a receipt was refused, the turn and admission; `identity_conflict` on a create retry has none, and on a submit retry the session and turn but no admission.
- An `unknown` receipt without an `execution_generation` (Hermes always sets one; this is defensive) parks with `execution_generation: null`; its answers then skip `resolve_unknown` and act as for cause `lost`.

### 7.2 Resolution files

- Name `resolutions/<key>.<attempt>.<episode>.json`; content exactly `{"v":1,"key":"<key>","attempt":<n>,"episode":<e>,"resolution":"fail"|"rerun"|"abort"}`.
- `RunDir::request_resolution(key, attempt, episode, resolution)` writes a temp file in `resolutions/`, syncs it, `hard_link`s it to the final name and removes the temp file, then syncs the folder. An existing final name is `JournalError::ResolutionPending` (first writer wins; two operators cannot both answer). It needs no lock.
- `RunJournal` owns the polling. `open` reads `resolutions/` once before it returns; then a task it spawns reads it every second (`tokio::time::interval`, so paused-time tests advance it) while the journal holds a parked call. A call is parked when the journal holds a `call_attention` for it with no matching `call_resolved`, whichever execution wrote it, so files for calls parked before a stop are consumed at open, before the script runs. A parked backend future never reads files: it waits on the journal's signal for its key, attempt and episode, then runs section 7.3.
- `request_resolution` names its temp file `resolutions/.tmp-<key>.<attempt>.<episode>.<16 random hex>`. The reader skips, and never touches, every name starting with `.tmp-` or ending `.rejected`. For each other file: a name or content that does not parse, has other keys, a `v` other than 1, an unknown resolution, or content that disagrees with the name is renamed to `<name>.rejected` with `JournalWarning::BadResolution { file, reason }`; a file for an episode already answered in the journal is deleted silently (crash C15); a file for a key, attempt or episode that is not currently parked is deleted with `JournalWarning::StaleResolution { key }`; a matching file is consumed: write `call_resolved` (synced), delete the file, run the procedure below.
- An answer applies to one episode only. A call that parks again gets a new episode, and an old answer never applies to it.

### 7.3 The resolution procedure (every answer)

For cause `unknown` (with a generation):

1. `resolve_unknown(session, admission, generation)`. A repeat on an already resolved row returns the row (H22), so this step is safe after any crash.
2. On `stale_generation`: read the receipt. If it is `terminal`, go on to step 3 with it. If it is still `unknown` with another generation, write `call_attention(e+1)` with the receipt's generation and park again (the consumed answer does not carry over). Anything else: `call_attention(e+1)`, same rule.
3. Read the receipt with `include_result: true` (H27: the resolve answer carries no result). If it has a saved result (H28, or a turn that settled while the runner was away), write `turn_settled` for the parked turn. The answer was produced and is never thrown away: the call acquires the gate with `Reattach` (its permit was dropped when it parked) and goes on as after any `turn_settled` (`after_turn` decides), whatever the answer, except that `abort` still ends the execution once the settlement is synced (a later resume continues from `Settled`). No new session, no new admission.
4. With no saved result, act on the answer. `fail` writes `call_finished(failed)` with the reason for the cause, "operator marked an unknown turn as failed" (`unknown`), "operator marked a lost session as failed" (`lost`) or "operator marked a conflicting retry as failed" (`identity_conflict`), or "on_unknown is fail" for `source: policy` whatever the cause, and returns `Failed`. `rerun` starts the next attempt (gate `Fresh`, new session, `:a<n+1>` identifiers), exactly once. `abort` written by this execution returns `AgentOutcome::Abort { reason: "operator aborted the run" }`; written by an earlier execution (that run already ended for it), it starts the next attempt, as `rerun` does.

For cause `lost`, `identity_conflict`, or `unknown` without a generation: no Hermes call; step 4 directly.

| F12 | `resolve_unknown` with a wrong generation or a non-`unknown` row is `stale_generation`, except a repeat with the same generation on a row it already resolved, which returns the row. Success makes the row `terminal`: outcome `completed` with the captured result when the current epoch holds one (F14), else `interrupted` with no saved result. The answer carries no result (H27). | H22, H27, H28 |
| F13 | `delete_session(id)` makes later `attach` and `receipt` answer `not_found`. | H12, H17 |
| F14 | A scripted turn marked `settlement_lost` finishes, keeps its result in the current epoch, and shows `unknown` with its generation, pausing the session. | H28 |

Connection model: the fake has one current connection, like the port (`GatewayPort` has no connection parameter; the real port holds one connection and replaces it on reconnect). Subscriptions (F4, F5) belong to the current connection; `disconnect()` and `restart()` end it and start a new one with none, so a submit without a new `attach` is `permission_denied`.

Gate rules: `acquire(.., Fresh)` before the first record of a new attempt; `acquire(.., Reattach)` when picking up an attempt in `Intent` to `Settled` state, or continuing after a saved result was recovered (section 7.3), which must answer `Proceed` without waiting (the work is already in Hermes; the gate only counts it). `Skip` writes the short attempt `call_finished(skipped)`; `Abort` returns `AgentOutcome::Abort` and writes nothing. The backend holds the permit through every turn of the attempt, receipt waits and the correction turn included, and drops it when it writes `call_finished`, when it parks (`call_attention` synced), or when the engine drops the future (abandoned or aborted calls). A stored `completed` or `skipped` result never touches the gate.

Budget: `JournaledBackend`'s `AgentBackend::budget()` returns `gate.budget()`, so the engine's budget check (`P5-01` section 6.1) reads the gate's snapshot; with `NoGate` the budget is unlimited.

Turn cap: if `after_turn` returns `Turn` after `MAX_TURNS_PER_CALL` settled turns, the call finishes `failed` with reason "turn limit reached" and the journal records it; the policy is not asked again.

`unattended`: no type here has such a field, and no field this unit generates (port requests, record fields) is named `unattended`. Caller data stored verbatim (prompt text, script values, `usage`, the manifest's opaque objects) is not inspected for it.

32. `journal_unknown::saved_results_are_kept`: (a) a turn that finishes while the runner is away after crash C6: the submit retry answers `terminal` with no result, the backend reads the receipt and settles, one admission; (b) for each answer `fail`, `rerun`, `abort`, a `settlement_lost` turn (F14) is answered: the saved result is settled, no new session or admission, and the call completes (for `abort`, after the resume); (c) `stale_generation` with a still-`unknown` receipt parks episode 1 and ignores the old answer.
33. `journal_unknown::resolution_files_are_validated`: invalid JSON, an extra key, an unknown resolution and a name that disagrees with the content are renamed `.rejected` with `BadResolution`; a stale episode is deleted with `StaleResolution`; a second `request_resolution` for the same episode gives `ResolutionPending`; a crash after `call_resolved` is synced and before the file is deleted (C15) resumes with the answer applied once.
34. `journal_resume::settled_usage_survives_crash`: a schema call settles turn 0 with usage, crashes before its correction turn settles; on resume `settled_usage` holds turn 0's usage once and `unsettled` the correction's admission; after the run, each admission appears exactly once across `settled_usage` and the `TurnSettled` notices.
35. `journal_privacy::credentials_refused_and_files_private`: a manifest whose `roster` holds `{"apiKey": "x"}`, or whose `hermes` holds a string starting `hermes-gateway-ticket`, is refused naming the field, and no folder is left; on Unix the run folder is mode 0700 and every file 0600.
36. `journal_retry::outage_budget_is_not_turn_time`: a turn that takes 10 virtual minutes with a healthy gateway completes; a 60 s outage, a success, then another 60 s outage completes (the budget resets); a continuous 121 s outage aborts; after each reconnect the fake sees `attach` before the retried submit or receipt.

## 11. The demonstration example

`crates/talaria-workflow/examples/journal_resume.rs` (needs features `mock` and `fake-gateway`) runs a script against a `FakeGateway` whose state is saved to a file after every change, so a real `kill -9` keeps it:

```text
journal_resume run    --runs <dir> --gateway-state <file> --script <path> [--hold <label>] [--on-unknown wait|fail]
journal_resume resume --runs <dir> --gateway-state <file> --run <run id> --script <path>
journal_resume restart-gateway --gateway-state <file>
journal_resume resolve --runs <dir> --run <run id> --key <key> --attempt <n> [--episode <e>] --as fail|rerun|abort
journal_resume stats  --gateway-state <file>
```

Output is one JSON line per event, in this order:

1. `{"event":"run","run_id":"<id>","resume_count":<n>}` first, before any call.
2. `{"event":"call","label":...,"key":...,"attempt":<n>,"source":"cache"|"reattach"|"retry"|"fresh"}` when a call starts: `cache` for a replayed call (`AgentStarted { replayed: true }`) or a stored result, `reattach` for an admitted turn, `retry` for an exact create or submit retry, `fresh` for a new attempt.
3. `{"event":"call_finished","label":...,"key":...,"outcome":"completed"|"failed"|"skipped"}` when the engine's `AgentFinished` for that call is recorded (the value has reached the script).
4. `{"event":"needs_operator","label":...,"key":...,"attempt":<n>,"episode":<e>,"cause":...}` when a call parks.
5. `{"event":"finished","outcome":...}` last.

`stats` prints `{"sessions":n,"admissions":n,"receipts":n,"resolves":n}`. `--hold <label>` makes that agent's turn wait until the process is killed or the gateway is restarted, so scenarios are deterministic. When a later process loads the saved state, a turn that was `started` keeps running and completes (the simulated gateway outlived the runner, as Hermes does, H24), unless `restart-gateway` ran in between, which turns it `unknown` (F11). `--hold` applies only to the process that was given it. `--episode` defaults to 0. Messages: a corrupt journal prints `journal is corrupt at line <n>: <reason>`; a dropped torn tail prints `warning: dropped a torn last line (line <n>, <bytes> bytes)`; a lock refusal prints `run <id> is already open in another runner`. Exit codes: 0 completed, 1 failed or a corrupt journal, 3 aborted, 4 interrupted while calls were parked (waiting is printed and the process waits for a resolution file; Ctrl+C ends it with 4), 5 locked, 64 usage.

The example script `tests/scripts/three_reviewers.js` has three `agent()` calls in a `parallel`, labels `correctness`, `security`, `simplicity`, then a `synthesis` agent. It passes no `schema`, so no correction turn runs and each agent is one session and one admission (the 4 and 4 of UAT-1). `resolve` takes the run folder as `<runs>/<run id>`, opens it with `RunDir::open` and calls `request_resolution`. JSON event lines go to standard output; the messages above and every error go to standard error.

## 12. Design notes and rejected alternatives

- **SQLite instead of JSON Lines.** Rejected: a second storage engine for an append-only log; the progress view and people can read JSON Lines directly; Claude Code and the u15 survey both use a JSONL journal.
- **Journal only terminal results (the 06 sketch).** Rejected: a crash between submit and the journal write would leave no admission id to re-attach to. The idempotency keys make a blind retry safe, but write-ahead records make every retry an exact retry with the stored payload, which is the only safe kind (H11).
- **Make `CallId` independent of arrival order.** Not needed: `P5-01` keeps invocation-order occurrences and reproduces the order through ordered delivery and replay; this unit supplies the log and the barrier (section 6.7).
- **Write the delivery order from the backend.** Rejected: only the engine knows `completion_seq` (it can hold outcomes), so the order comes from its `AgentFinished` events, made durable by the barrier.
- **Result files named by key and turn.** Rejected: a later attempt would overwrite a blob an earlier record names. Content-addressed blobs never collide.
- **Re-run unknown calls automatically.** Rejected: Hermes's own rule is never to replay started work (H20, H21), and the agent may have edited files.
- **Re-use the old session for a rerun.** Rejected: its queue is paused behind the unknown head until resolved (H21), and a fresh session keeps the audit trail clean.
- **Lock with a PID file.** Rejected: stale PID files need cleanup logic; an operating-system lock dies with the process.
- **Redact secrets inside prompts before writing.** Rejected: a retry must resend the exact bytes (H11). Instead the run folder is private (0700, 0600), the manifest refuses credentials, tickets never reach this unit, and `docs/workflows/journal.md` warns script authors that prompts and results are stored as written.
- **Interpret `usage` here.** Rejected: accounting is `P5-04`'s; this unit stores the H29 keys verbatim.
