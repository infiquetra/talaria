## 1. What this unit adds, in one paragraph

Claude Code lets a developer go back: pick an earlier prompt, drop it and everything after it from the conversation, optionally put the files back the way they were, and see what the agent changed (`/rewind`, double Esc, `/diff`). Hermes already does the work. It keeps file checkpoints per working folder (a hidden git store; off by default) and serves them as `rollback.list`, `rollback.diff`, `rollback.restore` and `rollback.session_diff`; it rewinds a conversation with the revision-fenced `session.mutate` operation `rewind`. This unit gives Talaria the screens and commands for both: a Rewind overlay (opened by `/rewind`, its alias `/checkpoint`, or Esc twice on an empty, idle composer), a Checkpoints overlay (`/rollback`), a diff view (`/diff`, `/rollback diff <n>`), and the typed commands `/undo [N]`, `/retry` and `/rollback <n> [file] [--all]`, which the shared Hermes gateway refuses through `slash.exec`. Two Hermes behaviours shape the design and must be shown honestly: a whole-folder restore always also removes the newest exchange from the conversation, chosen by Hermes's own rule (H17, H46), and a rewound turn cannot be erased from the terminal's own scrollback, so Talaria prints a clear marker instead (ADR draft 0009).

## 3. Design

### 3.1 Settled decisions and why

1. **Read before every conversation write.** Every rewind, every whole-folder restore and the rewind step after a restore start from a fresh `session.resume` poll (H35), and take `expected_revision`, `expected_generation`, the target row and the idle check from that one snapshot. This is how Hermes's terminal UI works (H45); it needs no revision tracking. A one-file restore is not preceded by a read: it never touches the conversation, and Hermes allows it while a turn runs (H17, the handler's comment "a file-scoped restore only touches disk"). That risk (the running agent may write the file again) is accepted and named in the pull request.
2. **Hermes decides; Talaria shows.** No client-side snapshotting, file copying or git. The only client-side logic is choosing which checkpoint corresponds to a prompt (3.3.3), and the confirmation names that checkpoint so the person sees what they get.
3. **Conversation-only is the default action.** "Restore files" is a second, explicit choice, shown only when checkpoints are on and one matches. A whole-folder "files only" restore that leaves the conversation alone does not exist in Hermes (H17); it is not offered. One-file restore is the typed `/rollback <n> <file>`.
4. **Restore first, re-read, then rewind to the chosen prompt only if it is still there.** Hermes's whole-folder restore removes the newest exchange by its own rule (H17, H46), which can differ from Talaria's. So after every successful whole-folder restore Talaria re-reads the session. If the chosen prompt is still an active row, it rewinds to it with the new fences; if it is gone, nothing more is sent. If an eligible prompt older than the chosen one is also gone, Talaria says so (T32). The reverse order (rewind, then restore) would make Hermes remove one exchange too many.
5. **Scrollback is never rewritten.** Rewound turns stay visible above a marker line that says they are no longer part of the conversation. The state is rebuilt from a fresh snapshot without printing anything again (3.9.2).
6. **The rewound prompt returns to the composer** (Claude Code behaviour), but only into an empty draft; a draft is never overwritten.
7. **Typed commands act at once; overlay actions confirm.** `/undo`, `/retry` and `/rollback <n>` ask no question (Hermes's own commands act at once). They still check the local turn state, and the `/rollback` forms first call `rollback.list` to detect checkpoints that are off. A typed target is sent as typed: Hermes resolves a number against its list at the moment of the call (H13), as its own terminal UI does (H43); the result names the checkpoint restored. Overlay actions (`f`, `d`, `r`) always send the full hash of the row on screen, never a number.
8. **No automatic retries.** A write whose reply is lost is an unknown outcome (architecture protocol rule). For a rewind, Talaria re-reads the session and reports what it can tell. For a restore it says the outcome is unknown and, for a whole-folder restore, re-reads and shows any conversation change. Nothing is re-sent. Reads are not retried automatically either; a failed read shows a text and the person tries again.
9. **`/diff` is the session diff.** It shows what changed since the oldest kept checkpoint (H22), the closest Hermes view to "what did the agent change", and says that it includes everyone's edits in the folder (C13). It shadows Hermes's git `/diff` (H42); `!git diff` (`P2-05`) remains for git's view. This is an operator question on the issue.
10. **The `rendered` field of `rollback.diff` is ignored.** It is ANSI text sized to 80 columns (H16); Talaria renders `diff` itself with `P2-01`'s `parse_diff` and `diff_lines`, and untrusted text never reaches the terminal unsanitised.
11. **Pure core.** The overlay state machine and every text live in `talaria-core` and read no clock, no network and no composer: the application supplies `now_ms`, call results and the turn state as inputs, and applies effects.
12. **One mutation sender.** `session.mutate` goes through `P2-06`'s `MutationRequest` and `MutationClient::send` (which never retries) and its `MutationOutcome`. This unit does not use `MutationLedger`: its tracked fences, `retry_after_fence` and exact resend contradict decisions 1 and 8. The fences come from the fresh read; the request id comes from `new_request_id()`.

### 3.2 Surfaces and flows

**Rewind overlay** (alternate screen, `P1-06` `open_overlay`/`draw_overlay`/`close_overlay`):

```text
Open(/rewind | /checkpoint | Esc Esc)
  turn running (P1-05 turn state)? -> notice T1, stay closed
  -> Loading -> ReadSession -> ListCheckpoints -> Turns (newest first, newest selected)
       Enter -> Actions(turn)
                 c -> Confirm(Conversation) -- Enter --> Working: ReadSession -> Mutate -> ReadSession -> Rebuild
                 f -> Confirm(Files) -- Enter --> Working: ReadSession -> Restore(full hash) -> ReadSession
                         -> chosen row still active? Mutate -> ReadSession -> Rebuild : Rebuild
                 d -> Diff(checkpoint vs now) -- Esc --> Actions
                 Esc -> Turns
       Esc -> Closed
```

**Checkpoints overlay** (`/rollback`, `/rollback list`, `/rollback ls`): `Loading -> ListCheckpoints -> Checkpoints`; Enter or `d` opens the diff of the selected checkpoint; `r` asks to confirm a whole-folder restore; Enter then runs `ReadSession` (idle and queue check), `Restore(full hash)`, `ReadSession`, `Rebuild`; Esc closes.

**Diff view** (`/diff`, `/diff --stat`, `/rollback diff <n|hash>`, `d` in the overlays): one scrollable view; Esc returns to the screen it came from, or closes when opened by a command.

**Typed commands** (no overlay; result as notices): `/undo [N]`, `/retry`, `/rollback <n|hash> [file] [--all]`.

### 3.3 Algorithms

#### 3.3.1 Eligible prompts (`rewind_turns`)

This is Talaria's own rule. It starts from Hermes's terminal UI rule (H37) and is stricter: compaction markers are also checked in text parts, and `row_id` must be above 0 because `session.mutate` refuses anything else (`hermes_state_mutations.py:44-48`). A `null` `display_kind` counts as absent, as in both Hermes rules (JavaScript `!row.display_kind`, Python's falsy check).

Input: the raw `messages` array of the snapshot (`serde_json::Value`s, H36). Keep a row when all hold: `role == "user"`; `row_id` is a JSON integer `> 0`; `archived` is absent or not `true`; `display_kind` is absent, null or `"steer"`; the content's text (string, or the joined `text` of its parts) contains none of the three compaction markers (H37). Number them `ordinal` 1, 2, ... in transcript order (1 = oldest); return them newest first.

For each kept row:

- `preview`: the first line of the text that is not blank, trimmed; `(no text)` when none.
- `prompt_text`: the lossless text, or `None` when a part is not exactly a text part (H37 rules). A string content is used as is.
- `text_parts`: the joined text of every text part (used when `prompt_text` is `None`); `attachments`: true when any part is not a text part.
- `timestamp`: `timestamp` as `f64` when it is a JSON number, else `None`.
- `window_start`: `None` when `timestamp` is `None`; else the larger of `floor(timestamp)` and `floor` of the newest numeric `timestamp` among active rows before it (so a prompt stored early can never open its window before the previous turn's rows; H55).
- `window_end`: `floor(timestamp)` of the next eligible prompt, or `None` for the newest.
- `edits_files`: true when an active row after it and before the next eligible prompt is an assistant row whose `tool_calls` hold a call named `write_file` or `patch` (name read only as `tool_calls[i].function.name`, H52; an entry without it counts as no edit; test 5 uses that shape, and the fixture confirms it in test 54).
- `later_count`: the number of rows in `messages` that are not `archived` and whose `row_id` is an integer `>= row_id` of this prompt (the target included). The confirm text shows it; the result's `rewound_count` is what the done notice reports.

#### 3.3.2 Checkpoint list

`CheckpointList::from_result(enabled, rows)`: `Off` when `enabled` is false; `Empty` when true with no rows; else `Rows(Vec<Checkpoint>)` with `index` 1.. in list order (newest first, H12), `short` = the first 8 characters of `hash` (matching `restored_to`, H20), `message`, `raw_time`, `time` = `parse_checkpoint_time(raw_time)`. A failed `rollback.list` gives `Unavailable(reason text)`.

`parse_checkpoint_time(s)`: accepts exactly `YYYY-MM-DDTHH:MM:SS` followed by `Z` or `+HH:MM` / `-HH:MM`; returns Unix seconds (`i64`); anything else `None`. `clock_text(s)` returns characters 11 to 16 (`HH:MM`) of a string that parses, else the empty string (the time as the gateway host wrote it; no time-zone conversion).

#### 3.3.3 Which checkpoint belongs to a prompt (`checkpoint_for_turn`)

A checkpoint is taken just before the agent's first file edit in a step (H23), and skipped when nothing changed or the folder is empty (H47). So "the files as they were before prompt K's edits" is the **oldest** checkpoint taken at or after prompt K, provided one was taken inside K's own turn whenever K edited files. Rule, with `t = window_start` and `u = window_end`:

1. List `Off`: `NoMatch::Off`. `Unavailable`: `NoMatch::Unknown`. `Empty`: `NoMatch::NoChanges`. `timestamp` is `None`: `NoMatch::NoTime`.
2. Candidates: rows whose `time` is `Some(c)` with `c >= t`. None: `NoMatch::NoChanges` ("no file changes recorded since this prompt").
3. Match = the candidate with the smallest `time`; ties go to the larger `index` (the older row in list order).
4. If `edits_files` is true and the match's time is not below `u` (no checkpoint inside K's turn; `u` absent means no upper bound, so this step never applies to the newest prompt when a candidate exists): `NoMatch::NoCheckpointForEdits`. Hermes skipped the checkpoint before K's edits (H47), so every later checkpoint already contains them, and restoring one would not undo K.
5. `oldest_kept` = true when no row has `time < t`, that is, the match is the oldest checkpoint Hermes still keeps. Pruning (H12) may then have dropped an earlier checkpoint taken after prompt K, so the confirm screen shows W1. This is a warning on a match, never a reason for no match.

Known limits (W2 on the confirm screen): checkpoints belong to the folder, so a checkpoint from another session in the same folder can match; whole-second precision can, in theory, pick a checkpoint from the previous turn taken in the same second as the prompt; a skipped checkpoint before a destructive terminal command is not detected (only `write_file` and `patch` are checked).

#### 3.3.4 Restore files and rewind

1. Confirm read (decision 1): `running` gives T21, a blocking `pending` count gives T23; nothing is sent. The changed-count rule of 3.3.7 applies.
2. `Restore { hash: <full hash>, file_path: None, all: false }`.
3. `success: false`: T20, nothing else is sent.
4. `success: true`: `ReadSession` (the after-restore read).
5. In that read, the chosen `row_id` is still an active eligible row: `Mutate` to it with the read's fences, then the rebuild read and `Rebuild { notice: T4f + restore_summary }`. A refused `Mutate` gives T14 (the files stay restored; Hermes removed its newest exchange).
6. The chosen row is gone: `Rebuild { notice: T4f + restore_summary }` from the after-restore read; nothing more is sent. `<n>` in T4f is `history_removed`.
7. In either case, when an eligible prompt that was older than the chosen one in the confirm read is not active in the after-restore read, add T32 naming the newest such prompt.

The Checkpoints overlay's `r` and the typed whole-folder `/rollback <n>` run steps 1 to 4, then, from the after-restore read: `Rebuild { notice: restore_summary }` when `history_removed > 0`, else `Notice(System, restore_summary)` only. They never send `Mutate`, never return a prompt and never add T32 (the person chose no prompt). State table rows: `Working(AfterRestoreRead)` with origin `CheckpointRestore` or `TypedRestore`.

#### 3.3.5 `/undo [N]` and `/retry`

Both check the local turn state first (`turn_running`: T1, nothing sent).

`/undo N` (N defaults to 1, a whole number 1..=999): read the session; target = the Nth newest eligible prompt; fewer than N eligible: T26. Then the same rewind as "Rewind the conversation" without confirmation; the target's text returns (decision 6).

`/retry`: read the session; target = the newest eligible prompt; none: T27; `prompt_text` is `None`: T28 and nothing is sent; `prompt_text` is empty: T27. Then rewind; after the rebuild, submit the text through the normal submission path (`P1-12`'s submit, a fresh `submission_id`, never `unattended`). The text prefers the result's `target_message.content` (H30, the live ask of a compaction carrier) when it yields lossless text, else the snapshot's `prompt_text`. The state machine has no input for the submit's result and is already `Closed` when `Submit` is applied: the app runs it through `P1-12`'s `SessionService::execute(Effect::SendPrompt)` and handles the `ExecuteOutcome` itself. `Sent`: nothing more. `Refused { reason }`: `P1-12`'s own refusal notice, then T35 with that `reason`, then the `ReturnPrompt` rule of 3.3.6 with the text (`attachments: false`). `OutcomeUnknown`: `P1-12`'s own unknown-outcome notice only (no T35, because the prompt may have been sent), then the same `ReturnPrompt` rule, so the person can check the transcript and send it again by hand; nothing is resent automatically.

#### 3.3.6 Which path returns the prompt

| Path | Prompt returned |
|---|---|
| Overlay `c`, `/undo N` | `ReturnPrompt` with the target's text |
| Overlay `f` | `ReturnPrompt` when the chosen row is gone at the end (removed by Hermes's restore or by the `Mutate`) |
| Lost rewind reply, row gone (T9) | `ReturnPrompt` |
| `/retry` | none; `Submit(text)`; when `P1-12` reports the submit `Refused` or `OutcomeUnknown`, the app applies `ReturnPrompt` (3.3.5) |
| Checkpoints `r`, typed whole-folder or one-file `/rollback` | none |

`ReturnPrompt { text, attachments }`: `text` is the lossless text, or `text_parts` when the prompt had attachments. The app reads `Composer::is_empty()` when it applies the effect (after the rebuild): empty and `text` not empty: `Composer::load(text)`; not empty: notice T5. When `attachments` is true it also shows T6.

#### 3.3.7 The conversation changed between the confirm screen and Enter

The Confirm screen (both kinds) shows `later_count` from the loaded read; Enter sends from the confirm read. When the confirm read is clean (not running, no blocking pending, target still active) but the target's `later_count` there differs from the loaded read's, nothing is sent: the screen returns to the same Confirm with the confirm read as the new loaded read, the counts redrawn, and the warning line T36 above the key line. Enter then confirms again with a fresh read. CheckpointConfirm shows no count and is not affected; neither are typed commands (`/undo`, `/retry`, `/rollback`), which have no confirm screen.

### 3.4 State machine (core, `rewind::state`)

Screens: `Closed`; `Loading(Purpose)`; `Turns`; `Actions`; `Confirm(Kind)`; `Checkpoints`; `CheckpointConfirm`; `Diff { back: Back, loading: bool }`; `Working(Step)`. `Purpose` is `Rewind | Checkpoints | TypedRestore { target, file_path, all } | TypedDiff(String)`. `Kind` is `Conversation | Files`. `Back` is `Actions | Checkpoints | Close`. `Step` is `ConfirmRead | Mutating { row_id, sent_generation, after_restore } | Restoring { whole_folder } | AfterRestoreRead | RebuildRead | Verifying { row_id, sent_generation } | LostRestoreRead | ExternalRebuildRead`. `Origin` (kept in the state while Working) is `Conversation | Files | Undo | Retry | CheckpointRestore | TypedRestore`.

**Tickets.** Every effect that calls Hermes is `Call { ticket, call }` with a new `ticket` from a counter in the state. `RewindService::execute` returns `Reply { ticket, reply }` with the same ticket. `update` ignores a `Reply` whose ticket is not the one the current screen waits for. That is how a late reply for a closed or replaced view is dropped (E28, E35).

**Failures.** A `Reply` carrying `Failed(f)` maps by step. For a read (`ReadSession` outside `Verifying`, `ListCheckpoints`, `CheckpointDiff`, `SessionDiff`): `NotSent` gives F1, `Unreadable` gives F2, `Unknown` gives F3, `Refused` gives the R table; the overlay closes (a failed list in `Loading(Rewind)` is the exception: it opens Turns with `Unavailable`). **`reload_pending`** is set by every T33 row. While it is set, the first `SessionRead` reply of any origin that reads the session (`Open` from `/rewind`, `/checkpoint` or Esc Esc; `Undo`; `Retry`; a whole-folder restore from `r` or typed `/rollback <n>`) is handled in one of two ways, and the flag is cleared: when that read's own row already ends in a `Rebuild` (RebuildRead, Verifying, ExternalRebuildRead, an after-restore read that rebuilds), that rebuild serves and no T34 is added; otherwise `Rebuild { snapshot: r.raw, notice: [T34] }` is emitted first, then the row's own effects. The Checkpoints overlay, `/diff`, `/rollback diff` and a one-file restore read no session and leave the flag set.

`last_rebuild_revision` is recorded from every `Mutated.revision` and from every `SessionRead` taken in Working. Our own `session.updated` frame therefore never triggers a second rebuild: it arrives either while Working (ignored) or after a read whose revision already includes it (E19, E36).

`is_open()` is true for every screen except `Closed` and except `Working` started by a typed command; Working started from an overlay keeps the overlay open with body C14.

### 3.7 Layouts

All overlay text is laid out by display columns. Row grammar for the Turns screen at width `W`: one space; `›` on the selected row, else a space; one space; `#<k>` left-aligned and padded to `1 + digits(largest ordinal)`; two spaces; the age left-aligned and padded to 8, the length of `just now`, the longest age (blank when `timestamp` is `None`); two spaces; the preview cut with `…` and padded to fill; two spaces; the tail (`files` when `checkpoint_for_turn` matches, `·` when checkpoints are on with no match, blank when `Off` or `Unavailable`) right-aligned in 5 columns; one space. The preview width is what is left. Example, 80 columns:

```text
 Rewind · choose a prompt to go back to
 › #3  2m ago    change alpha to beta in notes.txt                        files
   #2  5m ago    create notes.txt with the line alpha                     files
   #1  9m ago    hello                                                        ·

 ↑↓ choose · enter open · esc close
```

The footer is `↑↓ choose · enter open · esc close`, followed by ` · ` and C10 when `Off` or C12 when `Unavailable`, cut to the width.

Actions screen: the title `Prompt #<k> · <age>`, up to six lines of the prompt text (wrapped, sanitised), a blank line, then:

```text
 c  Rewind the conversation to before this prompt (files stay as they are)
 f  Also restore files to checkpoint <h> · <t> · <m>
 d  Show file changes since this prompt
 esc back
```

When there is no match, `f` is drawn dim with its NoMatch text (3.6) and `d` is omitted.

Confirm screen: `Remove prompt #<k> and everything after it (<later_count> messages) from the conversation?`, then `Files stay as they are.` or `Files go back to checkpoint <h> (<t>, <m>).`, then W1 when `oldest_kept`, W2 for the files action, then T36 (warning colour) after a changed count (3.3.7), then either `enter confirm · esc back` or, when the read shows `running` or `pending > 0`, the warning-coloured line `Hermes will not rewind while a reply runs or prompts are queued (<pending> queued).` and `esc back` only.

Checkpoints screen: title `Checkpoints · newest first`; rows: one space, mark, one space, the index padded to `digits(largest index)`, two spaces, `short` (8), two spaces, age (8), two spaces, `HH:MM` (5), two spaces, the message cut with `…`; footer `↑↓ choose · enter diff · r restore · esc close`. Restore confirm: `Restore the files to checkpoint <index> (<short>, <t>, <m>)?`, `Hermes also removes the last exchange from the conversation.`, W2, `enter confirm · esc back`.

Diff view: title line (`Changes since the oldest kept checkpoint` with C13 below it, or `Checkpoint <short> compared with the files now`), the `stat` lines (dim), a blank line, the diff drawn by `P2-01`'s `diff_lines(parse_diff(diff), DiffRenderOptions { width, indent: 1, max_rows: None, .. })`, then the cut note (C8 or C9) when due; footer `↑↓ scroll · pgup/pgdn page · home/end · esc back`. `--stat` omits the diff body. `DiffDoc::Off`, `Empty` and `Failed` draw C1, C5 or C6, or C7 as the only body line (C5 and C6 wrap). While loading the body is C11.

Narrow terminals: below 50 columns the age and clock columns are dropped; below 30 only `#<k>` (or the index) and the preview or message; an area under 3 rows draws nothing and never panics. The footer is always the last row. A resize makes the app send `Viewport(visible_rows(area))` and redraw; the selection clamps.

### 3.9 The application side

#### 3.9.1 Calls

| Call | Request (exact keys) | Timeout |
|---|---|---|
| `ReadSession` | `session.resume {session_id, display_projection: true}` | `P1-02` default (120 s) |
| `ListCheckpoints` | `rollback.list {session_id}` | `P1-02` default (120 s) |
| `CheckpointDiff` | `rollback.diff {session_id, hash}` | 240 s (H25: 210 s worst case at the default git timeout) |
| `SessionDiff` | `rollback.session_diff {session_id}` | 240 s (same reason) |
| `Restore` | `rollback.restore {session_id, hash}` plus `file_path` when present, plus `all: true` only when set | `P1-02` default (120 s); no fixed bound exists (H25), and a timeout is reported honestly as T11 or T11w |
| `Mutate` | `session.mutate {session_id, request_id, expected_revision, expected_generation, operation: "rewind", payload: {target_message_id}}` through `P2-06`'s `MutationClient::send` | `P2-06`'s (the `P1-02` default) |

A call that runs past its timeout (`CallError::TimedOut`) is `Unknown`: for a read that is F3 and the view closes (or, for a diff opened from an overlay, goes back). The connection's one request lane (H40) stays busy until Hermes answers, and that late reply is dropped by its stale ticket. 240 s covers the default git timeout (210 s worst case); a gateway whose operator raised `HERMES_CHECKPOINT_TIMEOUT` to its 60 s top can take 420 s, and then the diff shows F3. That is accepted, not retried.

Never `profile` (the connection is profile-scoped), never `preserve_compaction_handoff`, never `null` for an absent field. Use `P0-03`'s generated types: `methods::legacy::{rollback_list, rollback_diff, rollback_restore}` and `methods::canonical::{rollback_session_diff, session_resume}` (H54), through `P1-02`'s `Client::call_with` with the timeout above; `session.mutate` only through `P2-06`. `ReadSession` keeps the raw result `serde_json::Value` in `SessionRead.raw`: `messages` is read raw, and the same value decodes into `CanonicalSnapshot` for a rebuild (H53). Request ids: `new_request_id()`, a fresh 32-character lowercase hex string per `Mutate`, never reused.

A `session.resume` poll may also make Hermes re-ask a guarded model pick (H51); `P2-06`'s card may then appear. This unit neither answers nor dismisses it.

#### 3.9.2 Rebuild without reprinting

`P1-12`'s gap recovery (its specification 6.10) is extracted into one function in `app.rs`, `rebuild_foreground(snapshot, mode)`, with `RebuildMode::AfterGap` (unchanged behaviour, its tests unchanged) and `RebuildMode::AfterRewind { notice }`. If the gap read itself lives in `sessions.rs` (`SessionService::recover`), it stays there; only the part after the read moves.

1. `new = SessionState::from_snapshot(snapshot)` (decoded from the same raw value).
2. Let `shown` be `AppState`'s committed-cell record (6.10 step 3). Split the new state's final cells into "already shown" and "not shown" by one in-order scan: a new cell is already shown when it equals (`PartialEq`, as 6.10 compares) a cell of `shown` at or after the scan position, and the scan position then moves past that cell. A rewind only removes cells, so normally every new cell is already shown. `ledger.reset()`, then mark the already-shown cells with `ledger.take_ready` and discard the result: they are in scrollback above, so nothing is printed again.
3. `term.commit_lines(notice lines)`, each through `history::sanitize`.
4. Then commit the not-shown cells, in order, through `ledger.take_ready` as normal output. These are cells this pane never printed: for example, another window rewound and submitted a new prompt before this pane's rebuild read, so the snapshot holds a turn this pane has not shown. They appear once, below the marker. Replace `AppState`'s committed-cell record with all the new final cells, so a later gap compares against the rewound conversation.
5. Replace the stored state, keep the snapshot's `subscription_id`, call `Link::resync` once with its `replay_epoch` and `last_sequence` (as 6.10 step 4).
6. `rebuild_foreground` is the one place the app replaces the state from a snapshot, so `P2-05`'s `side::carry_over(old, new)` is called here when it exists on `main` (that unit adds the call to whichever replacement path exists when it merges). This unit never defines the hook.

Local-only cells (for example `P2-05`'s shell cells) leave the state at a rebuild; they stay in scrollback. The new state holds the new `execution_generation`, so a later Esc interrupt uses the right number. Hermes refuses a rewind while a turn runs (H29), so a rewind always lands between turns; if this window started a turn before the rebuild read returned, the snapshot's live turn replaces the local one, as 6.10 says for a gap.

#### 3.9.3 `session.updated`

The app observes every `session.updated` frame for the foreground session and still passes it to `P1-05`'s reducer unchanged (the replay cursor must advance; `P1-05` already lists `session.updated` as a known silent type). When `payload.operation == "rewind"`, it sends `SessionUpdated { operation, revision: payload.revision, rewound_count: payload.rewound_count }` to the rewind state; the state decides (3.4). Other operations are ignored by this unit (`workspace` from `/cd` included, H48).

### 3.10 Local commands (appended to `P2-03`'s table)

| name | aliases | summary | args_hint | takes_argument | action |
|---|---|---|---|---|---|
| `rewind` | `checkpoint` | `Go back to an earlier prompt: rewind the conversation, and restore files when checkpoints are on` | | false | `LocalAction::Rewind` |
| `undo` | | `Remove your last N prompts and their replies (default 1)` | `[N]` | true | `LocalAction::Undo` |
| `retry` | | `Remove the last prompt and its reply, then send the prompt again` | | false | `LocalAction::Retry` |
| `rollback` | | `List, compare or restore file checkpoints` | `[list] | diff <n> | <n> [file] [--all]` | true | `LocalAction::Rollback` |
| `diff` | | `Show what changed since Hermes's oldest kept checkpoint` | `[--stat]` | true | `LocalAction::Diff` |

`P2-03`'s rule "local wins over a Hermes command of the same name" applies: `/undo`, `/retry`, `/rollback` and `/diff` are in Hermes's catalogue (H41). `/undo`, `/retry` and `/rollback` would otherwise be refused (H42); `/diff` would otherwise run Hermes's git view (decision 9).

Grammar:

- `parse_rollback`: trim the argument. Empty, `list`, `ls` (case-insensitive, nothing after): `List`; `list x`: `Usage`. `diff` followed by exactly one word: `Diff(word)` when `is_checkpoint_target(word)`, else `BadTarget(word)`; `diff` with none or more words: `Usage`. Otherwise the first whitespace-separated word is the target (`BadTarget` when it fails `is_checkpoint_target`). Flag words `--all` and `--force` are taken only directly after the target or at the very end (repeatedly); the raw text between them, trimmed at both ends, is `file_path` with its inner whitespace kept exactly; an empty rest is no file. `all` is true only when a flag is present and there is no `file_path`.
- `is_checkpoint_target`: 1 to 6 ASCII digits (Hermes reads it as a row number, H13), or 4 to 64 hexadecimal characters (H21). A `-` start, a sign, an underscore or any other character fails. `BadTarget(t)` shows C3 and sends nothing.
- `parse_undo`: empty gives 1; a whole number 1..=999 gives it; anything else (0, negative, words, two numbers) gives `Err` (T25).
- `parse_diff`: empty, `session`, `--stat`, `stat`, or `session` with `--stat` in any order give `Session { stat_only }`; anything else gives `GitView` (T30, nothing sent).
