## 1. What this unit is, in one paragraph

The composer is the box at the bottom of the screen where the person types. This unit builds everything about it that does not touch Hermes: a multi-line editor, a history of earlier prompts, safe handling of pasted text, the rules for Enter, Shift+Enter, Esc and Ctrl+C, the table of key bindings that a person can change in `~/.talaria/config.toml`, and the configuration loader that reads that file. The composer never calls Hermes and never writes an escape sequence. It turns keys into small results (`Submit(text)`, `Interrupt`, `ExitRequested`) that the application, built in `P1-12`, turns into Hermes calls.

### 2.3 Terminal protocol facts

- The Kitty keyboard protocol says that with only the "disambiguate escape codes" flag, a modified Enter (for example Shift+Enter) is sent as `CSI 13 ; 2 u` while a plain Enter stays the legacy carriage return. **Not verified in this session against a running terminal; scenario UAT-5 and the pull request's terminal matrix verify it.** If a terminal sends Shift+Enter as plain Enter, Shift+Enter submits in that terminal; the fallbacks are Ctrl+J and Alt+Enter, which is why they are defaults.
- Alt+Enter in a legacy terminal is the two bytes `ESC` `CR`; crossterm reports `Enter` with `ALT`.
- Bracketed paste mode is mode 2004: the terminal wraps pasted text in `ESC [ 200 ~` and `ESC [ 201 ~` when the application turned the mode on. `tmux paste-buffer -p` sends the markers only if the inner application turned the mode on, which makes it a faithful test of the path.

## 3. Keys

### 3.1 Actions and defaults

Twenty actions, all in the key context `KeyContext::Composer` (section 3.2). A person can bind each to zero or more chords. **No default chord is F1, F2, Ctrl+B or Ctrl+S** (macOS takes F1 and F2 before the program sees them; Herdr takes Ctrl+B when nested; Ctrl+S is the old flow-control stop; see [02-current-state.md](../02-current-state.md#what-to-carry-into-the-rewrite)).

| Action (`ACTION` in `[keys]`) | Default chords | What it does |
|---|---|---|
| `submit` | `enter` | Send the draft (REQ-8). |
| `newline` | `shift+enter`, `alt+enter`, `ctrl+j` | Insert a line break at the caret. |
| `interrupt` | `esc` | Stop the running turn; keep the draft. Does nothing when no turn runs. |
| `cancel` | `ctrl+c` | Clear the draft, else stop a running turn, else arm exit (REQ-9). |
| `move_left`, `move_right` | `left`, `right` | By grapheme cluster; wrap to the previous or next line at the ends. |
| `move_up`, `move_down` | `up`, `down` | By visual row, keeping the preferred column; at the first or last row they walk the history (REQ-7). |
| `line_start`, `line_end` | `home`, `ctrl+a`; `end`, `ctrl+e` | Start or end of the logical line. |
| `buffer_start`, `buffer_end` | `ctrl+home`; `ctrl+end` | Start or end of the whole draft. |
| `word_left`, `word_right` | `alt+left`, `ctrl+left`, `alt+b`; `alt+right`, `ctrl+right`, `alt+f` | By word (REQ-6). Some macOS terminal profiles send `ESC b` and `ESC f` for Option plus an arrow (not verified here; UAT-5 checks it); those arrive as `alt+b` and `alt+f`. |
| `delete_backward` | `backspace`, `ctrl+h` | Delete the grapheme before the caret. |
| `delete_forward` | `delete` | Delete the grapheme after the caret. |
| `delete_word_backward` | `ctrl+w`, `alt+backspace` | Delete the word before the caret into the kill buffer. |
| `kill_to_line_end` | `ctrl+k` | Delete from the caret to the end of the logical line (or the line break if already at the end) into the kill buffer. |
| `kill_to_line_start` | `ctrl+u` | Delete from the start of the logical line to the caret into the kill buffer. |
| `yank` | `ctrl+y` | Insert the kill buffer at the caret. |

`Tab` is not bound (completion belongs to `P2-03` and `P2-04`). A `Tab` character inside a paste is kept.

### 3.2 Chords, keys and contexts

**Key context.** Every action belongs to one context: `Action::context() -> KeyContext`. This unit has one, `KeyContext::Composer`. Later units add contexts (`P2-08`'s queue rows, `P2-03` and `P2-04`'s menus) in `keys.rs`. Two things are decided per context: the plain-letter refusal below, and the conflict check (section 3.3). Actions in different contexts may share chords, because the application routes a key to one context at a time (REQ-14).

**The plain key value.** The composer never sees a terminal-library type. `keys.rs` defines:

```rust
pub struct Key { pub code: KeyCode, pub mods: Mods, pub kind: KeyKind }
pub enum KeyCode { Char(char), Enter, Esc, Tab, Backspace, Delete, Insert, Up, Down, Left, Right, Home, End, PageUp, PageDown, F(u8), Other }
pub struct Mods { pub ctrl: bool, pub alt: bool, pub shift: bool, pub super_key: bool, pub other: bool }   // other: HYPER or META
pub enum KeyKind { Press, Repeat, Release }
impl From<crossterm::event::KeyEvent> for Key { /* HYPER or META set mods.other; every code crossterm has and the list lacks becomes Other */ }
```

The application converts each crossterm key event with `Key::from` before it crosses the message channel, so `talaria-app` never depends on crossterm (`P0-04`, pattern 1). How a `Key` reaches the application's message type is `P1-12`'s decision. Tests build keys with `Key::from(KeyEvent::new(..))`.

**Chord grammar.** A chord is a string: zero or more modifiers, then one key, joined by `+`, case-insensitive; spaces around `+` are trimmed. `KeyChord::parse(text, context) -> Result<KeyChord, String>`; the `Err` text is the reason.

- Modifiers: `ctrl` (alias `control`), `alt` (alias `option`), `shift`, `super`. A repeated modifier is an error.
- Keys: a single character (`j`, `/`, `1`); `enter`, `esc` (alias `escape`), `tab`, `backspace`, `delete`, `insert`, `up`, `down`, `left`, `right`, `home`, `end`, `pageup`, `pagedown`, `space`, `plus` (the character `+`), `f1` to `f24`. The `+` character is written `plus`: `ctrl++` is refused.
- Reasons (exact): the text is trimmed first, so `""`, `" "` and any whitespace-only text give `empty`; any empty part between plus signs (`ctrl+`, `ctrl++`, a bare `+`) gives `missing key`; `unknown key "{k}"`; `unknown modifier "{m}"`; `repeated modifier "{m}"`; and, in the composer context only, `a plain letter would stop that key from typing` for a printable key (a character or `space`) with no `ctrl`, `alt` or `super`. Shift alone does not make a printable key acceptable (`shift+x` is refused).
- `shift+a` and an uppercase `A` are the same chord. Matching a `Key` against a chord: for a character key, compare lower-cased characters; `ctrl`, `alt` and `super` must match exactly; the chord's `shift` must equal (the key has shift, or its character is uppercase). For other keys, compare all four modifiers exactly. A `Key` with `mods.other` set matches nothing. Shift+Tab (crossterm's `BackTab`) has no entry in the list, so it becomes `Other` and does nothing; that is intended. `KeyKind::Release` never matches; `Press` and `Repeat` both do.
- `KeyChord::label()` prints the chord for display: title-case modifiers joined by `+`, then the key: `Shift+Enter`, `Ctrl+C`, `Esc`, `F5`, `Ctrl+O` (single characters upper-cased).
- `KeyChord::needs_enhancement()` is true for a chord a terminal cannot send without the keyboard enhancement protocol: `enter` combined with `shift`, `ctrl` or `super`, and any chord that uses `super`. The placeholder (section 5.7) uses it.
- A chord is "risky" when it is exactly `f1`, `f2`, `ctrl+b` or `ctrl+s` (section 3.3).

### 3.3 Building the key map from the file

`KeyMap::from_entries(entries)` takes the `[keys]` table after `config.rs` has turned each value into a list of strings (a TOML string becomes a one-item list; an array of strings stays; an empty array means "unbound"; non-string items in an array are dropped by the loader with their own notice, section 4.3). The map is a `BTreeMap`, so entries arrive in key-name order. The `toml` crate used here keeps tables sorted by key (no `preserve_order` feature), so file order is not available; notices follow key-name order.

1. Start from the defaults for every action. Remember which actions the file sets ("explicit").
2. For each entry, in key-name order:
   - A name that is not an action: `unknown_action`; skip it.
   - Otherwise parse each string with `KeyChord::parse(text, action.context())`. Each failure gives one `bad_chord` notice. Each chord that parses and is risky gives one `risky_chord` notice (the binding is kept). A chord repeated inside one list is kept once, silently.
   - An empty list: the action is explicit and unbound.
   - A non-empty list with no chord that parsed: keep the defaults and add one `all_invalid` notice (after that entry's `bad_chord` notices). The action is not explicit.
   - Otherwise the parsed chords replace the defaults; the action is explicit.
3. Resolve conflicts, per context, walking `Action::ALL` in the order of the table in section 3.1. A chord held by more than one action goes to one winner:
   - If exactly one holder is explicit, it wins. Every other holder (a default holder) loses the chord silently. If a loser is left with no chord at all, add one `default_lost` notice for it.
   - If more than one holder is explicit, the earliest in `Action::ALL` wins. Each later explicit holder loses the chord and gets one `conflict` notice (even if that leaves it unbound). Remaining default holders lose it as in the first case.
4. Return the map and the notices: first the step 2 notices in entry order, then the step 3 notices in `Action::ALL` order of the loser. Each problem produces exactly one notice; an all-invalid list therefore produces its `bad_chord` notices and one `all_invalid`.

Notice texts (tests compare them exactly; `~/.talaria/config.toml` is literal text, never the real path; `{label}` comes from `KeyChord::label`):

- `unknown_action`: `Ignoring [keys] {name} in ~/.talaria/config.toml: it is not a known action. Known actions: {config names in Action::ALL order, separated by ", "}.`
- `bad_chord`: `[keys] {action} in ~/.talaria/config.toml: "{text}" is not a key Talaria understands ({reason}); ignoring it.`
- `all_invalid`: `[keys] {action} in ~/.talaria/config.toml has no usable key; using the default ({the default labels in chords() order, separated by ", "}).`
- `risky_chord`: `[keys] {action} in ~/.talaria/config.toml: {label} may not reach Talaria in some terminals (the system, Herdr or terminal flow control can take it); the binding is kept.`
- `conflict`: `[keys] {action} in ~/.talaria/config.toml: {label} is already bound to {other}; keeping it on {other} only.`
- `default_lost`: `[keys] {action} in ~/.talaria/config.toml lost its default key {label} because {other} now uses it; {action} has no key until you bind one.`

**Worked example for test `from_entries_reports_each_problem_once`.** Input (as a table of lists):

```toml
[keys]
bogus = "x"
delete_forward = "ctrl+s"
line_start = ["hyper+a"]
move_left = ["banana", "left"]
submit = ["alt+enter"]
word_left = ["ctrl+o"]
word_right = ["ctrl+o"]
yank = []
```

Expected notices, in this order (six):

1. `unknown_action` for `bogus`.
2. `risky_chord` for `delete_forward`, `Ctrl+S`.
3. `bad_chord` for `line_start`, text `hyper+a`, reason `unknown modifier "hyper"`.
4. `all_invalid` for `line_start` (default labels `Home, Ctrl+A`).
5. `bad_chord` for `move_left`, text `banana`, reason `unknown key "banana"`; `left` is kept.
6. `conflict` for `word_right`: `Ctrl+O` is already bound to `word_left`.

Also expected: `submit` is `Alt+Enter`; `newline` keeps `Shift+Enter` and `Ctrl+J` with no notice; `yank` is unbound; `word_right` is unbound. A second call, `submit = ["esc"]` alone, gives exactly one notice: `default_lost` for `interrupt` (`Esc`, because `submit` now uses it).

## 4. Configuration (`crates/talaria-app/src/config.rs`)

### 4.1 What the file contains in v0.7.0

Only three tables are read. Everything else is reported and ignored, so a person arriving from the 0.6 line sees why a setting did nothing.

```toml
[keys]
# every action in section 3.1; a string or an array of strings; [] unbinds
submit = "enter"
newline = ["shift+enter", "alt+enter", "ctrl+j"]

[status]
# command = "~/.talaria/status.sh"   (a plain command line; no shell; split by P1-10)
interval_seconds = 5

[environment]
allowlist = []
```

- `[status]` and `[environment]` are the tables of the frozen status-line contract in [docs/formats/status-line.md](../../../formats/status-line.md) (`command`, `interval_seconds`, `allowlist`). The roadmap's wording is "the `[status_line]` table", but the frozen document it cites uses `[status]`; this unit follows the document, chosen by the issue author. The operator may overturn it (stop condition 5 in the issue).
- `status.command` is stored as the raw string. Splitting it into arguments, the timeout, the environment filter and the run schedule belong to `P1-10`.
- `status.interval_seconds`: an integer from 1 to 3600, default 5 (the range the 0.6 documentation used).
- `environment.allowlist`: an array of strings, default empty. The credential-name filter is `P1-10`'s.
- Side effect to report in the pull request: the frozen document says the file may also live at `./.talaria/config.toml` and lists `TALARIA_STATUS_INTERVAL_SECONDS` in the override chain (its configuring section). This unit reads neither, so those lines become wrong at merge. This unit does not edit the frozen file; `PH1B` decides how it is corrected.

`Config` implements `Default` (empty `keys`, `command: None`, `interval_seconds: 5`, empty allow-list). All types derive `Debug`, `Clone`, `PartialEq`, `Eq`. `load_file` exists so the demo and the application share one reader; its notices always use the literal text `~/.talaria/config.toml`, whatever file was read.

### 4.3 Parsing rules

Use `toml::from_str::<toml::Table>(text)` and walk the table by hand, so each problem can produce its own notice. (A derive-based parse would fail the whole file on the first bad key.) The error accessors were read in `toml` 1.1.8: `de::Error::message(&self) -> &str` and `de::Error::span(&self) -> Option<Range<usize>>` (`src/de/error.rs` lines 64 and 69); the table type is backed by a sorted map unless `preserve_order` is enabled. The error's `Display` text can quote file content and must not be used.

| Situation | Result | Notice (exact text, `{...}` filled in) |
|---|---|---|
| File missing | `Config::default()` | none |
| File unreadable (permissions, a directory, not UTF-8) | defaults | `Talaria could not read ~/.talaria/config.toml ({reason}). Using the default settings.` where `{reason}` is `error.kind().to_string()` (a directory gives `is a directory`; a file that is not UTF-8 gives `invalid data`), never the path |
| TOML syntax error with a span | defaults | `Talaria could not read ~/.talaria/config.toml (line {l}, column {c}): {message}. Using the default settings.` `{l}` and `{c}` are one-based and counted in characters, computed from the byte offset `span.start` in the file text (an error at the end of the file reports the last line); `{message}` is the error's `message()` cut to 120 characters |
| TOML syntax error without a span | defaults | `Talaria could not read ~/.talaria/config.toml: {message}. Using the default settings.` |
| Unknown top-level table or key (any name but `keys`, `status`, `environment`) | ignored | `Ignoring [{name}] in ~/.talaria/config.toml: Talaria does not read it yet.` (for a non-table key: `Ignoring {name} in ...` with the same ending) |
| Unknown key inside `[status]` or `[environment]` | ignored | `Ignoring {table}.{key} in ~/.talaria/config.toml: it is not a known setting.` |
| `keys`, `status` or `environment` present but not a table | defaults for that table | `{name} in ~/.talaria/config.toml must be a table; using the defaults for it.` |
| `status.command` not a string | `None` | `status.command in ~/.talaria/config.toml must be a text string; the status command is off.` |
| `status.command` empty or only spaces | `None` | `status.command in ~/.talaria/config.toml is empty; the status command is off.` |
| `status.interval_seconds` not an integer, below 1 or above 3600 | 5 | `status.interval_seconds in ~/.talaria/config.toml must be a whole number from 1 to 3600; using 5.` |
| `environment.allowlist` not an array of strings | empty | `environment.allowlist in ~/.talaria/config.toml must be a list of variable names; using an empty list.` |
| A `[keys]` value that is neither a string nor an array | entry dropped | `[keys] {name} in ~/.talaria/config.toml must be a key name or a list of key names; using the default.` |
| A `[keys]` array with non-string items | the string items stay; if no string item remains in a non-empty array the entry is dropped (defaults) | one notice per non-string item: `[keys] {name} in ~/.talaria/config.toml: item {n} is not a key name; ignoring it.` (`{n}` is one-based). Only a truly empty array `[]` unbinds; an array with items but no string item gives one notice per item and keeps the defaults. For `environment.allowlist` a mixed array gives one notice (the table row above) and an empty list |

Order of notices: the tables in the order `keys`, `status`, `environment`, then unknown top-level names sorted by name; inside a table, in key-name order. Because the table is sorted, a notice about a name that sorts first can precede one about an earlier line. None contains an absolute path, a home directory or a user name; the tests use inputs without paths in them, and stop condition 4 of the issue covers a `message()` that echoes file content.

### 5.1 Public surface

The application owns the key routing order and feeds the composer only the keys it should see: (1) a focused approval or question card from `P1-09`; (2) queue selection mode from `P2-08`; (3) the composer. One press goes to exactly one of them (H8). `P1-09`'s body says Ctrl+C with a card shown "first answers the card's negative action; `P1-08`'s Ctrl+C sequence then continues". Read it as "on the next press": if the card consumed the press, the composer must not also clear or interrupt on it. If `P1-09` means both on one press, report the conflict on `P1-09`; this unit's table (section 5.5) applies to each press that reaches the composer.

### 5.2 Buffer and caret

- The draft is a `String`; the caret is a byte index on a grapheme-cluster boundary (`unicode-segmentation`). Moves and deletes act on whole clusters. A property test asserts the caret is always on a boundary.
- Display width of a cluster is `unicode-width`'s width of the cluster string; a tab counts as 4 cells (drawn as four spaces, section 5.7).
- Filtering on every insert path (typed character, paste, burst flush, `load`; exact rule in 13.4): drop the controls named in section 5.6, and drop a cluster that stands alone with width 0, for example a zero-width space or a bidirectional override (`U+200B`, `U+200E`, `U+200F`, `U+2060`, `U+FEFF`, `U+202A` to `U+202E`, `U+2066` to `U+2069`). `unicode-width` gives these width 0 in the versions checked; a unit test over this list confirms it, and a character on the list is dropped whether or not the table says 0. A joiner or combining mark attached to a base character stays inside that cluster.
- Word motion: a word is a run of alphanumeric characters (Unicode `Alphabetic` or `Numeric`) or underscore; `word_left` skips non-word characters, then the word; `word_right` is the mirror; both stop at the start or end of the text. `delete_word_backward` deletes the same span into the kill buffer and does nothing at the start of the text.
- The kill buffer holds the latest killed span only. A kill that removes nothing leaves the buffer as it was. `kill_to_line_end` at the end of a line kills the line break; `kill_to_line_start` at the start of a line kills the line break before it; at the very end or start of the text they do nothing. `yank` inserts the kill buffer. Replacing the draft after a submit does not clear it (X1).
- Vertical moves keep a `preferred_col` (display column) set by the last horizontal move or edit; a vertical move to a shorter row puts the caret at the row's end and keeps the preferred column.

### 5.3 Wrapping

`wrap(text, width) -> Vec<Row>` where `Row { start, end, hard_break_after }` are byte ranges: `end` is exclusive and never includes the `\n` that follows a row with `hard_break_after` set (that byte lies between the rows). The coverage property is therefore: the rows in order, with one `\n` added after each row that has `hard_break_after`, rebuild the text exactly. The caller passes the width already reduced by one cell (the caret cell, X2); a `width` below 1 is treated as 1, so the function always terminates.

1. Split the text at `\n` into logical lines; an empty logical line is one empty row.
2. Greedy fill by display width. When the next cluster does not fit: if the row holds a space, break after the last space in the row (the space stays at the row's end); otherwise break before that cluster. A run of spaces that does not fit simply starts the next row. A tab is not a break point. A cluster wider than `width` gets its own row and is clipped on screen.
3. Property tests: the rows cover the text exactly once, in order; no row is wider than `width` except a single over-wide cluster; no row boundary falls inside a cluster.

Cache the rows keyed by (draft revision, width). The cache is rebuilt in `section`, once per redraw at most.

### 5.4 History

- `entries: Vec<String>`, oldest first, at most 1,000; the oldest is dropped when full. An entry is never empty or whitespace-only, and equal to the previous entry is not added twice. Only consecutive duplicates are dropped: `a`, `b`, `a` stays three entries. `with_history` seeds through the same rule and keeps the newest 1,000.
- State: `browsing: Option<usize>`, `scratch: Option<String>` (the draft as it was before the first Up) and `edits: BTreeMap<usize, String>` (the edited text of a recalled entry, by index).
- `move_up` when the caret is on the first visual row: if there are entries, then if not browsing, save the draft in `scratch` and show the newest entry; if browsing and not at the oldest, first store the buffer in `edits` if it differs from the entry shown, then show the next older (its edited text if it has one). At the oldest entry nothing happens (the caret stays). If there are no entries, move the caret to the start of the draft. The caret lands at the end of the shown text's first row (the first logical line's end, or the first visual row's end if that line wraps).
- `move_down` when the caret is on the last visual row: if browsing and not at the newest, store any edit, then show the next newer entry (or its edited text) with the caret at the end of its last row; if browsing at the newest, store any edit, restore `scratch` (caret at the end) and stop browsing; the stored edit stays in `edits` until the browse ends. If not browsing, move the caret to the end of the draft.
- On any other visual row, `move_up` and `move_down` move the caret within the draft.
- A person's edit to a recalled entry is therefore never lost: it stays in the buffer, and it comes back when they return to that entry within the same browse. The browse ends, and `browsing`, `scratch` and `edits` are cleared, on a submit or on a cancel that clears a non-empty draft. A submit adds the text sent as a new entry; the older entry it was recalled from stays as it was. (This replaces the earlier idea that going through history again replaces the buffer; that would have lost the edit.)
- A cancel that clears a non-empty draft adds that draft to the history (so Up brings it back).
- `P2-08` needs `is_empty()` and `cursor_on_first_row()` to decide whether Up selects a queued prompt; they are public.

### 5.5 Enter, Esc and Ctrl+C: the decision table

`submit` and `newline` on their own:

| Situation | Result |
|---|---|
| `submit`, draft has non-whitespace text, not in a paste burst window | `Submit(text)` with trailing whitespace removed (leading whitespace kept); clear the draft; add to history |
| `submit`, draft empty or only whitespace | `Unchanged` |
| `submit`, inside a paste burst or its 120 ms window (REQ-11) | insert a line break (as if `newline`) |
| `newline` | insert `\n` at the caret; `Changed` |

`interrupt` (Esc) and `cancel` (Ctrl+C), with `ctx.turn_running` and the draft:

| Key | Draft | Turn running | Exit armed | Result |
|---|---|---|---|---|
| `cancel` | non-empty | any | any | clear the draft, add it to history, disarm exit; `Changed` |
| `cancel` | empty | yes | any | disarm exit; `Interrupt` |
| `cancel` | empty | no | no | arm exit for 2 seconds from `now`; `Changed` (the hint shows) |
| `cancel` | empty | no | yes, not expired | disarm; `ExitRequested` |
| `cancel` | empty | no | yes, expired | arm again for 2 seconds; `Changed` |
| `interrupt` | any | yes | any | draft untouched; disarm exit; `Interrupt` |
| `interrupt` | any | no | yes | disarm exit; `Changed` |
| `interrupt` | any | no | no | `Unchanged` |

Any other key that changes the draft or caret also disarms exit. `tick(now)` disarms an expired exit hint and returns `Changed` when it did. A second Esc while the first interrupt is still being processed produces a second `Interrupt`. What the application does with it is for `P1-05` and `P1-12`: `P1-05`'s interrupt latch (its REQ-14) is described as set by `Event::Interrupt` with a running turn, and that body does not say a second event while latched is dropped, so this document does not claim it is harmless. If `cancel` is unbound, nothing in this unit exits Talaria; `P1-12` must provide another way out (for example a `/exit` command from `P2-03`, or closing the terminal), and the document says so.

### 5.6 Pasting

Two ways in, one path out.

1. `handle_paste(text)` (a bracketed paste): normalise `\r\n` and `\r` to `\n`; remove every control character except `\n` and `\t` (ESC, DEL, and the C1 controls U+0080 to U+009F are among them, so a pasted escape sequence cannot reach the terminal or the model); apply the section 5.2 filtering; insert at the caret as one edit; clear the burst detector. Return `Changed`, or `Unchanged` when nothing was inserted (an empty paste, or one made only of removed characters). The draft is never submitted by a paste, even if it ends with a newline. There is no size limit; collapsing big pastes is `P2-04`.
2. Burst detection for terminals without bracketed paste: a pure state machine `PasteBurst` in `composer/paste_burst.rs`, driven by the caller's clock.

```rust
pub struct PasteBurst { /* consecutive count, last time, active buffer, window end */ }
pub enum CharStep { Insert, TakeBack(usize), Append }   // type it normally; remove that many characters before the caret and start a buffer; append to the buffer
pub enum EnterStep { Submit, Newline, Append }          // Submit only when no burst is active and the window is closed
impl PasteBurst {
    pub fn new() -> PasteBurst;
    pub fn on_char(&mut self, c: char, now: Instant) -> CharStep;
    pub fn on_enter(&mut self, now: Instant) -> EnterStep;
    pub fn on_other_key(&mut self) -> Option<String>;   // flush: the buffered text, if any; resets the count and the window
    pub fn tick(&mut self, now: Instant) -> Option<String>;
    pub fn next_due(&self) -> Option<Instant>;
}
```

   - Counted events are plain characters (no ctrl, alt or super; shift is fine), counted as Unicode scalar values (what a key event carries). `consecutive` counts characters whose gap to the previous one is at most 8 ms; a longer gap resets it to 1. Any event that is not a counted plain character resets the count to 0, so "the two characters before the caret" are always the last two typed.
   - On the third consecutive character (`BURST_MIN_CHARS = 3`) the burst begins: the two characters already inserted are taken back out of the draft and join the buffer together with the third. While the burst is active every plain character, and every `submit` or `newline` key, appends to the buffer (a line break for Enter). No character is held back before the third arrives (X5).
   - The buffered characters are not drawn until the flush, which comes at most 8 ms after the last one. That is the cost of the design, and it is why the application must wake at `next_tick()`.
   - `tick(now)` flushes: if the burst is active and `now` is at least 8 ms after the last event (13.3), insert the buffer as one paste (through the same normalising path) and end the burst.
   - `Enter` that arrives less than 120 ms after the last burst event, even after the flush, inserts a line break instead of submitting (13.3, 13.4).
   - Any non-character key first flushes the buffer through the paste path, then is handled normally, and the burst window is cleared.
   - `next_tick()` returns the instant the burst becomes due (last event plus 8 ms; `tick` at exactly that instant flushes), or the instant the exit hint expires, whichever is earlier, or `None`.
3. Typing at human speed never triggers a burst: the gap between keystrokes is far above 8 ms. Held-down key repeat is about 30 ms between characters (typical operating-system behaviour, not measured here). A slow link that delivers typed characters in one network packet can look like a burst; the text arrives intact, only the Enter after it is delayed by the 120 ms window. The acceptance scenarios therefore wait 0.3 seconds between `send-text` and `enter`.

### 5.7 Rendering

`ComposerSection` draws into the area `P1-06` gives it. Styles use only terminal-default colours and the modifiers `BOLD`, `DIM` and `REVERSED`, so the composer is readable on light and dark terminals (themes arrive with `P2-12`).

- **Box** (width at least 20 and `max_rows` at least 3). Top border `╭`, `─`, `╮`; bottom `╰`, `─`, `╯`. A content row is: `│`, one space, the two-cell prompt (`> ` bold on the first row, two spaces on later rows), the text area (`T = width - 7` cells, padded with spaces), two spaces, `│`; that is 1 + 1 + 2 + T + 2 + 1 = width. The wrapping width is `T - 1` (the caret cell). Height = content rows + 2.
- **Borderless** (width below 20, or `max_rows` below 3). A content row is the prompt (two cells), the text area (`T = width - 3` cells, padded) and one space; the wrapping width is `T - 1`. Hidden-row counts and the exit hint share one dim row at the bottom, drawn in place of the last content row when there is something to say (`↑ N more · ↓ M more`, or the exit text) and when `max_rows` is at least 2.
- **Content rows** = min(wrapped rows, `MAX_COMPOSER_ROWS = 8`, `max_rows - 2` for a box or `max_rows` borderless), at least 1. `section` stores `scroll_top` so the caret row is visible with the least scrolling, and never leaves blank rows at the bottom when the draft is longer than the window.
- **Hints.** When rows are hidden, the box's top border carries `↑ {n} more` and the bottom border `↓ {m} more` (dim), where `n` and `m` count hidden rows. Example for test `scrolling_hints_and_exit_hint`: 30 lines loaded, caret at the end, window rows 23 to 30, so `↑ 22 more`; then Up 15 times moves the caret to row 15 and the window to rows 15 to 22: `↑ 14 more` and `↓ 8 more`.
- **Caret** is a reversed cell: the cluster under the caret, or a reversed space at the end of a row. The hardware cursor is not moved (`P1-06` does not expose it); a later unit wanting it for input methods changes `terminal.rs`, owned by `P1-06`.
- **Empty draft**: the placeholder `Type a message. {submit} sends, {newline} adds a line.` in dim, using the first configured chord of each action (`Enter`, `Shift+Enter`). When `set_keyboard_enhancement(false)` was called, the newline label is the first `newline` chord for which `needs_enhancement()` is false (by default `Alt+Enter`), because Shift+Enter would submit there. If an action has no chord, its half is dropped: `Type a message. Enter sends.`, `Type a message. Shift+Enter adds a line.`, or `Type a message.`. The caret is a reversed cell over the first placeholder character.
- **Title and hints on the top border** (box only; the borderless layout shows no title): the title from `set_title` is left-aligned after one space, the `↑ N more` hint is right-aligned, and the title is cut with `…` if both do not fit, so the hint always wins. Content rows of a box are hint-free.
- **Exit hint**: when exit is armed, the bottom border carries `Press Ctrl+C again to exit` (using the configured `cancel` chord's label). It replaces the `↓` hint while shown.
- **Text drawn.** A tab is drawn as four spaces. Every cluster is passed through `P1-06`'s `sanitize`, then measured: layout uses the width of what is drawn. Because insertion removes controls and lone zero-width characters (section 5.2), `sanitize` changes nothing for text in the buffer; it is defence in depth (`load` and future insert paths). Test 28 therefore asserts that a pasted U+202E and U+200B never reach `text()`; it does not assert a stand-in.

## 6. The demo program `crates/talaria-tui/examples/composer_demo.rs`

Used by the acceptance scenarios and the pseudo-terminal tests, because the `talaria` binary arrives in `P1-12`. It uses `P1-06`'s `TerminalGuard`, `InlineTerminal`, `spawn_input` and `commit_lines` and this unit's `Composer`. No Hermes, no network.

```text
composer_demo [--running] [--config <file>] [--history <a|b|c>]
```

- `--running`: `ctx.turn_running` is true for the whole run (to try Esc and Ctrl+C).
- `--config <file>`: load that file with `talaria_app::config::load_file` and use its `[keys]` through `KeyMap::from_entries`; both notice lists are committed as `NOTICE:` lines. `talaria-app` is a development-only dependency of `talaria-tui` (examples and tests), so the shipped dependency graph is unchanged; it is allowed because `talaria-app` does not depend on `talaria-tui`, and `P0-02`'s layering test ignores development edges (stop condition 5 of the issue if it does not). Without the flag: built-in defaults; the demo never reads the real home directory.
- `--history`: seed the history, entries separated by `|`, oldest first.
- Not a terminal: print one plain line saying standard input or output is not a terminal, no escape bytes, exit code 2 (same as `P1-06`'s demo).
- The demo draws the composer with `section(terminal width, 10)`, so the box is at most 10 rows (8 content rows plus two borders). The loop: convert each crossterm key event with `Key::from`; call `set_keyboard_enhancement` with the probe's `keyboard_enhancement`; wait for input with a timeout taken from `Composer::next_tick()` (no timeout when it is `None`); when the timeout fires, call `tick(Instant::now())`. Redraw after any `Changed`. This is what makes the exit hint disappear after 3 seconds without a key (UAT-3) and flushes a burst.
- At start it commits one `NOTICE: <text>` line per notice: first the loader's notices (`config::load_file`), then the key map's (`KeyMap::from_entries`), each list in its own order. The application (`P1-12`) merges them the same way. In the first commit of the test author the demo is a stub whose `main` is `todo!()`; that is what makes tests 30 to 32 fail for the right reason (a panic at `todo!()`, no output) instead of a missing binary.
- On `Submit(text)`: commit `SUBMITTED lines={n} chars={m} text={text:?}` (Rust debug escaping of the text; `lines` counts `\n` plus one; `chars` counts Unicode scalar values).
- On `Event::Paste`: commit `PASTE-EVENT chars={m}` (counted before the composer normalises it), then give it to the composer.
- On `Interrupt`: commit `INTERRUPT`. On `ExitRequested`: commit `EXIT-REQUESTED` and exit with code 0.
- The composer is drawn as the live region and nothing else is.

### 7.1 Support code (`crates/talaria-tui/tests/composer_support/mod.rs`)

- `rows(section, width, height) -> Vec<String>`: draws a `ComposerSection` into a ratatui `Buffer`, and returns each row as a string of cell symbols (the "rows helper" of the patterns guide). `style_at(x, y)` returns the cell's modifier set.
- Snapshot convention: the one the patterns guide (`P0-04`) names. Compare literal row lists written by the test author, never generated from the code under test.

### 7.2 Pseudo-terminal tests (`tests/composer_pty.rs`)

Dependencies (development only): `portable-pty`, `vt100` (the version `P1-06` pins; it is already a development dependency there) and optionally `escargot` to build the example. Spawn the built demo (`env!("CARGO_BIN_EXE_...")` does not apply to examples; build with `escargot` or locate `target/<profile>/examples/composer_demo` from `CARGO_TARGET_DIR` or `current_exe`), inside a pseudo-terminal opened with `portable-pty`, at 80 by 24.

- A reader thread drains the master's output continuously into a shared buffer and a `vt100::Parser`. Without it, writing 10,000 bytes while nobody reads the output can block both sides.
- Write input in chunks of at most 1,024 bytes, flushing between chunks.
- Skip with the exact line `SKIP: no pseudo-terminal` (to standard error) when none can be opened; the tmux test prints `SKIP: tmux not found`. The acceptance checks AC-5 and AC-11 fail when that line appears, so a skip never counts as a pass.
- The terminal does not answer the start-up probe, so `P1-06`'s 200 ms deadline applies; wait for the first frame before typing.

Byte strings: bracketed paste is `ESC [ 200 ~` + text + `ESC [ 201 ~`; Ctrl+J is `0x0A`; Enter is `0x0D`; Esc alone is `0x1B` then nothing; Alt+Enter is `0x1B 0x0D`; Ctrl+C is `0x03`.

The 10,000 character paste is `("x" * 99 + "\n") * 99 + "x" * 100`: 99 lines of 99 characters with a line break each, then a final line of 100, 10,000 characters in all.

Test `ctrl_j_alt_enter_lone_esc_and_no_terminal`: type `a`, `0x0A`, `b`, `0x1B 0x0D`, `c` as separate writes 50 ms apart (so no burst starts), wait 200 ms, write `0x0D`: expect `SUBMITTED lines=3 chars=5 text="a\nb\nc"`. Bytes that carry only line breaks would not do: a draft of line breaks alone is blank and does not submit.

## 8. Edge cases

| Case | Behaviour |
|---|---|
| Submit with text then Enter while a turn runs | `Submit` is returned; the application decides (H3). |
| Esc while the exit hint is armed, no turn | Hint disarms; no exit. |
| Ctrl+C with a draft, turn running | Draft cleared; no interrupt (H4). A second Ctrl+C interrupts. |
| Up with one history entry that equals the current draft | Shows the entry (no special case). |
| Paste of only control characters, or an empty paste | Nothing is inserted; `Unchanged`. |
| Paste while browsing history | Inserts into the recalled text at the caret. |
| `\r` alone in a paste | Becomes `\n`. |
| A paste containing `ESC [ 2 J` | The ESC is removed; the remaining `[2J` is inserted as text. |
| Zero-width joiner emoji | One cluster; deleting it with one Backspace removes the whole cluster. |
| A lone zero-width space or bidirectional override typed or pasted | Not inserted (section 5.2). |
| Draft wider than the area with no spaces | Hard-wrapped at cluster boundaries. |
| Resize narrower while a long draft is open | Re-wrapped at the next `section` call; the caret stays on the same byte. |
| Release or repeat events | Release ignored; Repeat handled as Press. |
| A mouse or focus event | Not given to the composer (the application ignores them; mouse reporting is off). |
| A very long draft (1 MB) | Layout is linear in the draft length once per redraw; only visible rows are drawn. `P1-11` measures keystroke latency. |
| `cancel` unbound | No exit key from the composer; `P1-12` provides one (section 5.5). |
| `submit` and `newline` both bound to the same chord by the person | The earlier action in `Action::ALL` (`submit`) keeps it; `newline` gets a `conflict` notice. |

## 9. Design reasoning and rejected alternatives

- **One Esc interrupts (roadmap), not Hermes's double Esc.** A single press is faster and matches Claude Code's habit; the cost is an accidental interrupt. The draft is kept and the turn can be re-asked from history. Raised to the operator in the issue.
- **Ctrl+C asks before exiting.** Hermes exits at once on an idle empty composer (H4). Talaria's lesson list says people press Ctrl+C by habit; a second press within 2 seconds is a cheap confirmation and needs no extra screen.
- **No held first character in the paste detector** (X5): protects the 16 ms echo budget. The price is that burst characters appear at the flush, not one by one.
- **Software caret.** The hardware cursor would need a cursor API in `terminal.rs`; adding one is a change to `P1-06`'s module. A reversed cell works in every terminal and in the emulator tests.
- **Hand-walked TOML, not derive.** One bad key must not discard the whole file (the roadmap: "a parse error starts with defaults and one plain-language notice", but a type error in one key should only affect that key).
- **Keys stay strings in `Config`.** `talaria-app` must not depend on the terminal crate, and `talaria-tui` must not depend on the application in the shipped graph; the raw entries pass through the binary (`P1-12`) into `KeyMap::from_entries`. The demo and test 10 use `talaria-app` as a development-only dependency to share the one loader instead of writing a second reader of the same table.
- **A plain `Key` type, not crossterm's.** `P0-04` (pattern 1) says the key reader converts the event before sending and that no terminal-library type crosses the channel; `talaria-app` is forbidden from reaching crossterm (`P0-02`, REQ-13). Owning the type in `keys.rs` is the least surprising place.
- **Key contexts.** `P2-08` adds queue actions whose defaults are plain letters (`e`, `d`, `s`, `n`) and reuses Enter, Delete and Esc; `P2-03` and `P2-04` add menu actions on Enter, Esc and the arrows. A single global namespace with a plain-letter ban and a no-duplicate rule would refuse or silently strip all of them. Contexts keep the rules for typing keys in the composer and let the others coexist.
- **An explicit entry beats a default, and silent loss is limited.** A person who writes `submit = ["alt+enter"]` asked for it; making them also rebind `newline` first would be a trap. If the default holder is left with no key at all, a notice says so (`default_lost`).
- **Risky chords are kept, with a notice.** A carried 0.6 file binds `interrupt` to Ctrl+S, which the new defaults avoid on purpose. Refusing it would break a stated person's choice; silence would leave interrupt on a key that may not arrive.
- **A recalled prompt's edit is kept (overlay), not discarded.** The Objective says a person must never lose a draft. The overlay costs a small map and gives readline-like behaviour.
- **History is in memory.** A history file would store prompts, which can hold secrets, in plain text; that needs a decision (raised in the issue).
- **Notices follow key-name order.** The `toml` table and `Config.keys` are sorted maps. Keeping file order needs the `preserve_order` feature and an ordered map; the value is small, so the simpler choice stands.
- **No vim mode, no mouse.** Phase 6 and a deliberate non-goal (native selection must keep working).

## 13. Rulings that close builder questions

These rulings were added after a second builder tried to plan from the issue. They fill gaps and the issue points here. Where they differ from an earlier section, they win.

### 13.1 Vertical moves before the first draw

`Composer` keeps a prepared wrap width, set by each `section(width, max_rows)` call. Before the first `section` call there is none, and each logical line counts as one visual row (no soft wrapping). So in key tests that never draw, "first row" means the first logical line and "last row" the last. After a resize the next `section` call changes the width.

### 13.2 Empty, blank and the other draft-replacing calls

- "Empty" (the Ctrl+C table, `is_empty()`) means the draft has no characters. A draft of only spaces is not empty: Ctrl+C clears it and arms nothing; submit treats it as blank and does nothing; the history rule skips it.
- `clear()` removes the draft, ends any history browse (drops `scratch` and `edits`), disarms exit, discards an active burst buffer and window, keeps the kill buffer, adds nothing to the history and returns nothing. `load(text)` does the same, then inserts the filtered text with the caret at the end. A burst buffer is part of the draft, so replacing the draft replaces it.
- `handle_paste` while a burst buffer is active inserts the buffered text first (as one paste), then the pasted text; it closes the 120 ms Enter window.
- `set_title` and `set_keyboard_enhancement` change only drawing.

### 13.3 Time boundaries

Times are compared with `>=` on the side that fires, so a reported deadline always fires:

- The burst flushes when `now - last_event >= 8 ms`; `tick` at exactly `next_tick()` flushes. A character that arrives with a gap of exactly 8 ms while the buffer is still active appends to it (the machine has not been ticked yet).
- Exit expires when `now - armed_at >= 2 s`; a second `cancel` at exactly 2000 ms re-arms instead of exiting.
- Enter is a line break when `now - last_burst_event < 120 ms`; at exactly 120 ms it submits.

### 13.4 What counts as a burst event, and what a paste does to the window

A burst event is a plain character taken into an active burst (the third character that starts it included) or an Enter appended to the buffer. The 120 ms window runs from the last burst event and survives the flush. It is closed by any other key, by a bracketed paste and by `clear` or `load`. Characters typed slowly never open it. So a bracketed paste followed at once by Enter submits (this is how UAT-2 and test 30 work, with no wait).

Known limit, accepted: without bracketed paste, a paste whose first line has two characters or fewer submits that line at its line break (for example `hi`, a line break, `there` submits `hi`), because the burst starts only at the third character. Bracketed paste is the main path; the journal entry says so.

### 13.5 The zero-width filter, exactly

On every insert path a character is dropped when the cluster that starts at it has display width 0, or when that cluster consists only of characters on the explicit list of section 5.2 (the list wins if the width table ever disagrees):

- A typed character is inserted, and if the grapheme cluster that starts at the insertion point is the character itself with width 0 it is removed again. So `e` then U+0301 (combining acute) attaches and stays; U+0301 typed first on an empty draft, a lone U+200D, U+200B, U+200E, U+200F, U+2060, U+FEFF, U+202A to U+202E and U+2066 to U+2069 are dropped.
- Pasted, burst and loaded text is filtered cluster by cluster as if it were inserted into an empty draft (so a leading combining mark at the start of a paste is dropped even if the draft's last character could have taken it). A joiner or mark inside the text stays with its base: a family emoji joined with U+200D is one kept cluster.
- The unit test over the list (section 11, item 8) asserts every listed character is dropped when alone.

### 13.6 Action order and conflicts

`Action::ALL` follows the order of the table in section 3.1 (`submit`, `newline`, `interrupt`, `cancel`, `move_left`, `move_right`, `move_up`, `move_down`, `line_start`, `line_end`, `buffer_start`, `buffer_end`, `word_left`, `word_right`, `delete_backward`, `delete_forward`, `delete_word_backward`, `kill_to_line_end`, `kill_to_line_start`, `yank`). That order decides conflicts and the `unknown_action` list.

### 13.7 Render test sizes

Every render test and the demo use `max_rows = 10` unless the row says otherwise (so content rows are at most 8). Width is 60 unless the row says otherwise. The exit hint cannot appear together with hidden-row hints through the public interface, because Ctrl+C on a non-empty draft clears it and `load` disarms exit; test 27 therefore checks the exit hint on an empty draft.

### 13.8 Test 29 oracle

The test loads 50,000 lines labelled `L00001` to `L50000`, draws once into a buffer with exactly `height(width)` rows, asserts that height is at most 10, that the rows contain exactly the labels of the eight visible lines and no other label, and that `section` returns without the test measuring time.
