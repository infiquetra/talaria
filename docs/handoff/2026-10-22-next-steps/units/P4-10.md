## 1. The doctor at a glance

The doctor answers one question: "why is Talaria not working with my Hermes, and what do I do about it?" It runs seven checks, prints one row per check with a severity word and a one-line summary, and puts one concrete fix under every row that is not `ok`. It offers exactly one action of its own: restarting the gateway, after an explicit confirmation that says what will be interrupted.

```text
 Doctor: 4 ok, 1 warning, 1 failure
 ok    Talaria         0.7.0, built for Hermes v0.22.4 (4d043038)
 ok    Gateway         ready · instance 9f2c41aa · epoch 3 · launchd service
 warn  Hermes version  0.22.4 at commit 1a2b3c4d; Talaria was built for v0.22.4 (4d043038)
       Fix: Talaria usually works with this build. If something misbehaves, install Hermes v0.22.4 and restart the gateway.
 ok    Capabilities    all 3 capabilities Talaria needs are offered
 FAIL  Profiles        fixture is parked: session store unusable: <path> did not open: database is locked
       Fix: Fix the cause the gateway reports, then run hermes gateway status.
 skip  Attach          needs the profile to be served
 ok    Runtime health  healthy · 0 agents working
 For provider keys, tools and dependencies, run hermes doctor.
 ↑↓ select · Enter details · r check again · R restart gateway · Esc close
```

Two surfaces show the same report:

- `/doctor` in the terminal UI opens an overlay (the screenshot above). It is a Talaria-handled local command, like `/quit`.
- `talaria doctor` prints the same rows to standard output and exits with a code a script can test. `talaria doctor --json` prints a JSON document instead. `talaria doctor --restart` adds the restart action, asking for confirmation on a terminal.

This mirrors Claude Code, where `/doctor` "runs a checkup that proposes fixes and applies them after you confirm" and `claude doctor` "prints read-only diagnostics without starting a session" (the parity research, `util.doctor` in [u12](../research/u12-claude-code-parity.json)). Hermes Desktop keeps "Restart gateway" visually separate from the harmless reconnect button (`apps/desktop/src/app/shell/gateway-menu-panel.tsx:185-200`), and its shared restart helper asks "Restart the shared gateway? All bots on this device reconnect" before restarting, but only when the gateway serves several profiles; a gateway serving one profile restarts silently (`apps/desktop/src/store/system-actions.ts:77-121`, `apps/desktop/src/i18n/en.ts:2427-2430`, `apps/desktop/src/app/command-center/index.tsx:302-310`). Talaria is stricter: it always asks.

### 1.1 Where the facts come from

```text
 doctor                              control socket                 gateway HTTP (api_origin)
 ------                              --------------                 -------------------------
 1. identify (read-only, once) -----> {"protocol":1,"verb":"identify","id":1}
                               <----- state, capabilities, code_version, code_sha,
                                      served_profiles, parked_profiles, launch_supervisor
    Endpoint::from_identify on that same reply (no second identify)
 2. only when ready or in a restart wait, and the selected profile is served:
    attach (ticket purpose interactive) -> WebSocket -> gateway.ready -> client.capabilities
                                        -> runtime.describe (capabilities) -> close
 3. only when ready or in a restart wait:
    GET /api/status (public path; NO ticket header) ------------->  components, config_version,
                                                     <-----------  heartbeat staleness, active_agents
 4. diagnose (pure function) -> Report -> overlay rows / text / JSON

 restart (only after confirmation, only when state is ready):
 a. active-work (read-only) ----------> {"protocol":1,"verb":"active-work","id":1}
                            <---------- active_agents, active_work[{kind,...}]   (for the confirmation text)
 b. after confirmation: identify again; still ready with the same instance_id? else nothing is sent
 c. mint ticket purpose native-http for the root profile
    POST /api/gateway/restart  header x-hermes-gateway-ticket ------>  {"ok":true,"pid":...,"name":"gateway-restart"}
 d. identify once a second, up to 90 s, until instance_id changes and state is ready
```

### 3.1 The one addition to `{{P1-01}}`'s discovery module

The doctor must read the `identify` reply even when `Endpoint::from_identify` refuses it (`starting`, `failed`, `incompatible`), and must send the read-only `active-work` verb. `{{P1-01}}` keeps its control exchange private and has no public read-only verb call, so this unit always adds exactly this to `crates/hermes-client/src/discovery.rs`, reusing the private exchange (same node checks, peer check, 64 KiB request limit, 524,288-byte reply limit, one deadline). If `{{P4-06}}` already made that exchange `pub(crate)`, build on it; never change a public signature of `{{P1-01}}`.

```rust
/// A control-socket verb that changes nothing. There is deliberately no way to name any other verb.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum ReadVerb { Identify, ActiveWork }

impl ReadVerb { pub fn as_str(self) -> &'static str; }   // "identify", "active-work"

/// Sends `{"protocol":1,"verb":<verb>,"id":1}` and returns the reply's `result` object.
/// Never runs `ensure`. Errors are `DiscoveryError` variants with their existing texts;
/// an `ok: false` reply is `DiscoveryError::ControlRefused`.
pub async fn control_query(home: &Path, verb: ReadVerb, options: &DiscoverOptions)
    -> Result<serde_json::Value, DiscoveryError>;
```

No `params` are sent (the unscoped `active-work` answer is the one the confirmation needs). The deadline is `options.control_timeout` (`{{P1-01}}`'s default 5 s). `DoctorService::active_work` passes 8 s instead, so that Hermes's own 5 s limit on `active-work` (H19) answers first with `ok: false`; either failure gives `Err(())` and the card's "could not find out" line (section 7.2). `probe` passes 2 s.

The doctor sends exactly three kinds of control request: `identify` and `active-work` through `control_query`, and `session-ticket` inside `{{P1-01}}`'s `mint_ticket` (the attach ticket, purpose `interactive`; the restart ticket, purpose `native-http`, minted through `{{P4-01}}`'s `NativeHttpMinter`). `mint_ticket` sends no `identify` of its own (`{{P1-01}}`'s spec section 8), so test 19's "one `identify`" holds. If adding this needs more than this enum and this function, stop and report (stop condition). `{{P4-06}}` never adds a verb to `ReadVerb`.

### 3.2 The two REST calls, beside `{{P4-01}}`'s route modules

`{{P4-01}}`'s `RestClient::request` already sends any method with or without a body and takes a per-request deadline, and `{{P4-01}}` tells later units to add route modules beside `config_api.rs` through `request`. This unit adds no method to `RestClient`. It adds:

```rust
// crates/hermes-client/src/gateway_api.rs (new; shared with P4-06, see below)
/// GET /api/status, public path: no ticket header (H10, H26), 8 s whole-request deadline (H25).
pub async fn gateway_status(rest: &RestClient) -> Result<serde_json::Value, RestError> {
    rest.request(Method::Get, "/api/status", None, RequestOpts { ticket: false, deadline: Some(Duration::from_secs(8)) }).await
}
/// POST /api/gateway/restart, no query, no body, one native-http ticket, 10 s whole-request deadline.
pub async fn restart_gateway(rest: &RestClient) -> Result<serde_json::Value, RestError> {
    rest.request(Method::Post, "/api/gateway/restart", None, RequestOpts { ticket: true, deadline: Some(Duration::from_secs(10)) }).await
}
```

`gateway_api.rs` is shared with `{{P4-06}}`, which needs the same `gateway_status`. `scrub_text` rules, applied in this order:

1. Every control character (U+0000 to U+001F, U+007F to U+009F) and every bidirectional formatting character (U+061C, U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069) becomes `?`.
2. When `home` is given, every occurrence of the home text, together with whatever follows it up to (not including) the next whitespace or one of `" ' ) ] , ;` or the end of the text, becomes `<path>`. This step runs **before** the path-run step because a home may contain a space (for example a home under a folder named `Application Support`): a path run stops at the first space, so running it first would leave the home's tail behind and the home text could then no longer be found whole.
3. A path run becomes `<path>`. A path run starts at a `/`, or at `~/`, that is at the start of the text or right after whitespace or one of `" ' ( [ = : , <`; it continues up to (not including) the next whitespace or one of `" ' ) ] , ;` or the end of the text. So `/a/b`, `open:/var/x`, `"/var/x"`, `(/var/x)` and `path=~/c` all lose their path. (The `<path>` written by step 2 starts with `<`, not `/`, so it is not touched again.)
4. Runs of whitespace collapse to one space; the result is trimmed.
5. Cut to 200 characters on a character boundary; when cut, append `…` (so at most 201 characters).

Examples: `/srv/hh/state.db did not open: database is locked` with the home `/srv/hh` gives `<path> did not open: database is locked`. With the home `/tmp/t a b/hh` (a space inside), `/tmp/t a b/hh/state.db did not open` gives `<path> did not open`, and `x=/tmp/t a b/hh` gives `x=<path>`. A path that is not under the home and contains a space keeps only the part after the space (`/opt/My Apps/x` gives `<path> Apps/x`); this is accepted, because the private part, the home, is caught whole by step 2.

`StatusPage` and `IdentityFacts` are built by `talaria-app` from the replies, never from text the doctor parses itself. Every `String` in `DoctorFacts` has passed `scrub_text` with the Hermes home before it is stored; the app layer is the only place the home is known and replaced. `diagnose` scrubs every output string again with `home: None` (steps 1, 3, 4, 5), so a missed call still cannot leak a path. Every string means every string, including `{{P1-01}}`'s error texts and next steps: `scrub_text` keeps backticks, and those texts contain no path, so they come out unchanged.

## 6. Gathering the facts (`DoctorService::gather`)

### 6.1 Order and early exits

1. `control_query(home, ReadVerb::Identify)` once. On error: `GatewayFacts::Unreachable` from the error's `Display` and `next_step()`, identity `None`, attach `NotTried`, status `NotTried`. Stop. No other control request is sent for identity during `gather`.
2. Build `IdentityFacts` from that raw `result`: `code_version` and `code_sha` (strings, else `None`), `capabilities` (strings only), `served` (section 5.5), `parked` (string values only, each reason through `scrub_text` with the Hermes home).
3. `Endpoint::from_identify(result, home)` on the same reply. `Ok` with state `Ready` → `GatewayFacts::Ready`; `DrainingForRestart` → `RestartWait`. `Err(NotReady { .. })` or `Err(InvalidState)` → `NotReady` with the raw `state` and `drain_reason` (scrubbed, cut to 40 characters). `Err(Incompatible)` → `Incompatible`. Any other error (for example `HomeNotServed`) → `Unreachable` from its texts. Only `Ready` and `RestartWait` continue.
4. If the selected profile is served (`resolve_profile` gives a `ProfileId`), attach: `mint_ticket(home, endpoint, profile_id, Purpose::Interactive, Scope::profile())`, `connect`, `handshake`, then close the connection. Step 1's duration is the `identify` timing; the others are timed as `{{P1-01}}`'s live test does. The `runtime.describe` capabilities come from the handshake.
5. Only when step 3 gave `Ready` or `RestartWait` (the early exit of step 3 already ends `gather` otherwise; no HTTP request is ever sent to a gateway in any other state), and in parallel with step 4 (both only need the endpoint): `gateway_status(rest)` (section 3.2): no ticket header, no `Origin`, 8 s whole-request deadline. Mapping of the result:

   | Result | `StatusFacts` |
   |---|---|
   | `Ok(value)` with `value` a JSON object | `Read(StatusPage)`, taking only the fields of section 4.1 (unknown fields ignored; a field of the wrong type is `None`; `components.dashboard.selftest` → `dashboard_selftest`) |
   | `Ok(value)` not an object, `Err(BadBody(_))`, `Err(BodyTooLarge)` | `Unreadable { "not JSON" }` |
   | `Err(Server { status: 503 })` | `NotReady` (H12: `gateway_not_ready`) |
   | `Err(Timeout { .. })` | `Unreadable { "timed out after 8 s" }` |
   | `Err(Unauthorized)`, `Err(Forbidden { .. })`, `Err(NotFound { .. })`, `Err(Refused { status, .. })`, `Err(Server { status })` (not 503) | `Unreadable { "HTTP <status>" }` (401, 403, 404 for the first three) |
   | `Err(Connect(_))`, `Err(Dropped { .. })`, `Err(Ticket(_))`, `Err(NotLoopback)`, `Err(TlsNotSupported)` | `Unreadable { "connection failed" }` |

   If the merged `RestError` differs from these names, map by meaning and say so in the pull request.
6. Return `DoctorFacts`.

`gather` never returns an error and never panics on a malformed reply. It never runs `ensure`, never starts, stops or restarts anything, never writes a file, and never logs a reply body. The only side effect any doctor read can cause on the Hermes side is H28 (the status route may create `install_id` on its first call); this is accepted and recorded in DECISIONS.

### 6.2 Privacy rules

- Never shown, stored in `DoctorFacts`, printed or logged: the Hermes home path, any profile `home` or `profile_id` (both are paths), `hermes_home`, `config_path`, `env_path`, `gateway_pid`, `gateway_health_url`, `gateways`, `install_id`, `argv`, `pid`, tickets, session keys, delegation goals, models from `active-work`.
- Shown: profile names, the first 8 characters of `instance_id`, `code_sha` and `COMMIT`, version strings, counts, state words, scrubbed reasons. The full `COMMIT` appears only in the JSON field `talaria.hermes_commit`.
- The ticket for the attach and the ticket for the restart live only inside `{{P1-01}}`'s `Ticket` and `{{P4-01}}`'s client; the doctor never formats them.

### 6.3 The selected profile

## 7. Restart

### 7.1 The state machine

| State | Input | Next state | Effects |
|---|---|---|---|
| `Idle` or `Done(_)` | `Ask { gateway_ready: false, .. }` | `Done(NotReady)` | none |
| `Idle` or `Done(_)` | `Ask { gateway_ready: true, instance_id, profiles }` | `Asking { old_instance: instance_id, profiles }` | `QueryActiveWork` |
| `Asking { old_instance, profiles }` | `ActiveWork(r)` | `Confirming { old_instance, profiles, work: r.ok(), restart_selected: false }` | none |
| `Asking` / `Confirming` | `Cancel` | `Done(Declined)` | none |
| `Confirming` | `Toggle` | same, `restart_selected` flipped | none |
| `Confirming { old_instance, .. }` | `Confirm` | `Requesting { old_instance }` | `Post { old_instance }` |
| `Requesting { old_instance }` | `Posted(Accepted)` | `Waiting { old_instance, elapsed: 0, unknown_request: false }` | `ProbeAfter(1 s)` |
| `Requesting { old_instance }` | `Posted(Unknown)` | `Waiting { old_instance, elapsed: 0, unknown_request: true }` | `ProbeAfter(1 s)` |
| `Requesting` | `Posted(Refused { s, d })` | `Done(Refused { s, d })` | `Notice(<outcome text>)` |
| `Requesting` | `Posted(Changed)` | `Done(Changed)` | `Notice(<outcome text>)` |
| `Waiting` | `Tick(t)` | same, `elapsed = t` | none |
| `Waiting` | `Probe(Ready { id })` with `id != old_instance` | `Done(Restarted { seconds: elapsed rounded up to whole seconds, old_instance, new_instance: id })` | `RerunChecks`, `Notice(<outcome text>)` |
| `Waiting` | `Probe(Ready { same id })` with `elapsed < RESTART_DEADLINE` | `Waiting` | `ProbeAfter(1 s)` |
| `Waiting` | `Probe(NotAnswering)` or `Probe(NotReady)` with `elapsed < RESTART_DEADLINE` | `Waiting` | `ProbeAfter(1 s)` |
| `Waiting` | `Probe(Ready { same id })` with `elapsed >= RESTART_DEADLINE` | `Done(DidNotRestart)` | `RerunChecks`, `Notice(..)` |
| `Waiting` | `Probe(NotAnswering)` or `Probe(NotReady)` with `elapsed >= RESTART_DEADLINE` | `Done(NotBack)` | `RerunChecks`, `Notice(..)` |
| any other pair | | unchanged | none |

Notice rule: every move from `Requesting` or `Waiting` into `Done(_)` emits exactly one `Notice(<outcome text of 7.4>)`, because the overlay may have been closed during those two states (section 9) and the person must still learn the outcome; the application turns it into a notice cell only when the overlay is closed (section 4.4). Moves into `Done` from `Idle`, `Asking` or `Confirming` (`NotReady`, `Declined`) emit no notice: the overlay cannot be closed in those states, so it shows the outcome itself.

The executor always sends `Tick` just before each `Probe` (section 4.4), so the deadline is decided on the probe that follows the 90 s mark; with a 2 s probe timeout the wait ends at most about 93 s after the POST was answered. `Confirm` from `y` works whichever button is selected; the Enter key sends `Confirm` when Restart is selected and `Cancel` when Cancel is selected. The machine never emits `Post` except on `Confirm` in `Confirming`, so at most one `Post` follows each confirmation, and a second `Ask` while not `Idle` or `Done` is ignored.

`Posted(Unknown)` is what a transport failure after the request was sent maps to: the restart may have started, so the doctor waits and lets the instance id decide (the protocol rule "a call whose connection dropped has an unknown outcome, never success").

### 7.2 The confirmation texts

```text
 Restart the Hermes gateway?
 It serves 2 profiles: default, fixture. Every session on them reconnects.
 3 running jobs will be interrupted: 2 chat turns and 1 other job.
 [ Cancel ]  [ Restart ]
```

- Line 2: `It serves <n> profiles: <names>. Every session on them reconnects.`; names as in 5.5's `served` order, at most five, then `and <k> more`; one profile: `It serves 1 profile: <name>. Every session on it reconnects.`
- Line 3, from `WorkSummary { chat, other }` (chat = units whose `kind` is `chat`; other = every other unit; when `active_work` is absent or not a list, chat = `active_agents` and other = 0): total 0 → `Nothing is running right now.`; otherwise `<total> running jobs will be interrupted: <chat> chat turns and <other> other jobs.` with singulars (`1 running job will be interrupted: 1 chat turn and 0 other jobs.`). When `active-work` failed: `Talaria could not find out what is running; anything running will be interrupted.`
- The counts are a snapshot taken when the card opened. The card is not refreshed while it is open. At Confirm, `post_restart` re-reads `identify` and sends nothing if the gateway is no longer ready with the same `instance_id` (`Changed`); it does not re-count running work (rejected alternative, section 13).
- Buttons: `Cancel` is selected when the card opens. The selected button is drawn in reverse video.

Command line. `run_doctor` drives the same machine: after the first report it feeds `ask_input(&facts)` to `restart_update` (a not-ready gateway ends here with `Done(NotReady)`), sends `active-work`, feeds `ActiveWork(..)`, then decides:

- On a terminal without `--yes`: lines 1 to 3 to standard error, then `Type yes to restart: `; one line is read; only `yes` (trimmed, any case) feeds `Confirm`; anything else, or end of input, feeds `Cancel` (`Declined`).
- With `--yes` (terminal or not): lines 1 to 3 still go to standard error, as a record of what was interrupted; no prompt is printed and nothing is read; `run_doctor` feeds `Confirm`. `--yes` is the scripted confirmation decision 3 allows; it is not a way around the fresh check at Confirm, which still runs.
- Without `--yes` and with standard input or standard error not a terminal: `NeedsConfirmation`, decided before `ask_input`, so nothing is asked or sent (section 8.3).

After `Confirm`, `run_doctor` calls `post_restart` and feeds `Posted(..)`, then loops: sleep 1 s, `probe()`, feed `Tick(elapsed)` and `Probe(..)`, until `Done(_)`.

### 7.3 The request and the wait

- Fresh check: `post_restart(old_instance, selected)` first sends `control_query(Identify)` and `Endpoint::from_identify`. Not `Ready`, or a different `instance_id`, or an error → `PostResult::Changed`, and nothing else is sent.
- Ticket: `{{P4-01}}`'s `NativeHttpMinter` for the root profile of that fresh endpoint (section 3.2). No `profile` query parameter is sent (H15).
- Request: `restart_gateway(rest)` (section 3.2): `POST <api_origin>/api/gateway/restart`, no body, 10 s whole-request deadline, one `x-hermes-gateway-ticket` header, no `Origin`.
- Mapping:

  | Result | `PostResult` |
  |---|---|
  | `Ok(value)` with `value.ok == true` | `Accepted` |
  | `Ok(other)`, `Err(BadBody(_))`, `Err(BodyTooLarge)` | `Unknown` (a 2xx came back, so the route may have run) |
  | any `Err(e)` with `e.outcome_unknown()` (timeout or drop after the request was written) | `Unknown` |
  | `Err(Unauthorized)` | `Refused { Some(401), "Unauthorized" }` |
  | `Err(Forbidden { detail })` | `Refused { Some(403), scrub_text(detail) }` (Hermes's `profile_scope_mismatch`, H18) |
  | `Err(NotFound { .. })` | `Refused { Some(404), "" }` (the route is absent: a different Hermes) |
  | `Err(Refused { status, detail })` | `Refused { Some(status), scrub_text(detail or "") }` |
  | `Err(Server { status })` | `Refused { Some(status), "" }` (500 is a failed spawn, H14; 503 is `gateway_not_ready`, H12). `{{P4-01}}`'s `Server` variant keeps no detail, so Hermes's `Failed to restart gateway: <exception>` text, which can hold a path, never reaches Talaria |
  | any other `Err(e)` (nothing was sent: connect refused, ticket refused, not loopback) | `Refused { None, scrub_text(e.to_string()) }` |
- Probe: `probe()` sends one `control_query(Identify)` with a 2 s control timeout and runs `Endpoint::from_identify`: `Ok` with state `Ready` → `Ready { instance_id }`; `Err(NoGateway)` or a timeout → `NotAnswering`; anything else (including a restart wait) → `NotReady`.
- Progress text while waiting: `Restart requested. Waiting for the gateway to come back (<n> s)`, `<n>` the whole seconds of `elapsed`. The overlay redraws only when this text changes.

### 7.4 Outcome texts

| Outcome | Severity | Text | Fix |
|---|---|---|---|
| `Restarted` | ok | `Gateway restarted in <n> s (instance <old8> → <new8>).` | none |
| `Refused` with status and detail | fail | `The gateway refused the restart (HTTP <s>: <detail>).` | `Run hermes gateway restart in a shell and read its output.` |
| `Refused` with status, empty detail | fail | `The gateway refused the restart (HTTP <s>).` | as above |
| `Refused` without status | fail | `The restart request failed: <detail>.` | as above |
| `Changed` | warn | `The gateway changed while the confirmation was open, so nothing was sent.` | `Check again, then restart if it is still needed.` |
| `DidNotRestart` | fail | `The gateway did not restart within 90 s.` | `Run hermes gateway restart in a shell and read its output.` |
| `NotBack` | fail | `The gateway did not come back within 90 s.` | `Run hermes gateway status; if the gateway is stopped, run hermes gateway ensure --json.` |
| `NotReady` | fail | `The gateway is not ready, so Talaria cannot ask it to restart.` | `Run hermes gateway restart in a shell.` |
| `Declined` | info | `Not restarted.` | none |
| `NeedsConfirmation` | info | `Refusing to restart without confirmation: run in a terminal or add --yes.` | none |

When the overlay is closed while requesting or waiting, the restart continues (the state lives in `AppState.doctor_restart`) and every outcome, `Refused` and `Changed` included, arrives as a notice cell `Doctor: <text>` through `Event::Notice` (the notice rule of 7.1). The main connection reconnects by itself (`{{P1-03}}`); the doctor does not touch it.

## 8. Output formats

### 8.1 Text (`talaria doctor`)

```text
Talaria doctor (profile fixture)
ok    Talaria         0.7.0, built for Hermes v0.22.4 (4d043038)
ok    Gateway         ready · instance 9f2c41aa · epoch 3 · started by hand
...
FAIL  Profiles        the gateway never discovered a profile named nosuch
      Fix: Create the profile, or check the name with hermes profile list.
...
warn  Runtime health  the gateway's housekeeping has not run for 125 s
      Fix: Restart the gateway: press R here, or run talaria doctor --restart.
      also: Hermes configuration is at version 22; this Hermes expects 23. Fix: Run hermes config migrate.
Result: 4 ok, 1 warning, 1 failure.
For provider keys, tools and dependencies, run hermes doctor.
```

Columns: the severity word left-aligned in 6 characters (`ok`, `warn`, `FAIL`, `skip`, `info`), the check name in 16 (`Talaria`, `Gateway`, `Hermes version`, `Capabilities`, `Profiles`, `Attach`, `Runtime health`), then the summary. A `Fix:` line follows every `warn` and `FAIL` row, indented 6 spaces; then the row's `also:` detail lines, indented 6. Other details are not printed in text mode (they are in JSON and in the overlay). Plural rules: `1 warning`, `2 warnings`, `1 failure`, `0 failures`. All output is plain: no colour and no escape sequences when standard output is not a terminal; when it is, only the severity word may be coloured.

With `--restart`, the order on standard output is: the report; then, if a restart was attempted or refused, one line `Restart: <outcome text>` (section 7.4), plus `Fix: <fix>` when the outcome has one; then, only after `Restarted`, a second report headed `Talaria doctor (profile <p>), after the restart`. On a terminal the confirmation lines and prompt go to standard error between the first report and the `Restart:` line.

### 8.2 JSON (`talaria doctor --json`), documented in `docs/formats/doctor-v1.md`

```json
{"format":"talaria-doctor-v1","overall":"warn","profile":"fixture",
 "talaria":{"version":"0.7.0","hermes_tag":"v0.22.4","hermes_commit":"4d04303818b61bf3aa09278af48356315515965b"},
 "checks":[{"id":"gateway","severity":"ok","summary":"ready · instance 9f2c41aa · epoch 3","details":[],"fix":null}],
 "restart":null}
```

`checks` holds all seven, in order; after a `Restarted` outcome they are the checks run after the restart, otherwise the first run. `restart` is `null` without `--restart`; otherwise `{"outcome":<o>,"seconds":<n or null>,"http_status":<n or null>,"text":<outcome text>}` with `outcome` one of `restarted`, `refused`, `changed`, `did_not_restart`, `not_back`, `not_ready`, `declined`, `needs_confirmation`. `seconds` is a number only for `restarted`; `http_status` is a number only for `refused` with a status; otherwise both are `null`. One JSON object on one line, then a newline. Nothing else on standard output.

### 8.3 Exit codes

| Code | When |
|---|---|
| 0 | No check failed (warnings allowed); with `--restart`, the outcome is `restarted` and the checks run afterwards have no failure |
| 1 | At least one check failed, or the restart outcome is `refused`, `changed`, `did_not_restart`, `not_back` or `not_ready` |
| 2 | Usage error: `--yes` without `--restart`, a blank `--profile`, an unknown flag |
| 3 | `--restart` without `--yes` when standard input or standard error is not a terminal: nothing was restarted |
| 4 | The person declined the restart: nothing was restarted |

Precedence when several apply: 2, then 3, then 4, then 1, then 0. Code 2 is decided while parsing, before anything else runs. Code 3 is decided before any restart step: with no terminal and no `--yes`, `run_doctor` still runs and prints the checks (read-only), then prints `Restart: Refusing to restart without confirmation: run in a terminal or add --yes.`, never sends `active-work`, never builds a restart request, and exits 3 even if a check failed. `exit_code(report, restart)` in `talaria-core` implements codes 0, 1, 3 and 4 with this precedence; `talaria-cli` adds 2.

Codes 3 and 4 follow `{{P2-14}}`'s meaning ("input required", "nothing ran").

`talaria doctor` is dispatched in `talaria-cli`'s `main.rs` right after argument parsing, before `{{P1-12}}`'s terminal check (which exits 2 without a terminal), like `{{P2-14}}`'s `-p` branch. It needs no terminal; only `--restart` without `--yes` looks at whether standard input and standard error are terminals.

## 11. Mock and fixture rules

- `identify` replies are built from `{{P1-01}}`'s spec section 5 shape (the ready reply), changing only the fields a test needs (`state`, `drain_reason`, `instance_id`, `capabilities`, `code_version`, `code_sha`, `served_profiles`, `parked_profiles`, `launch_supervisor`). Paths inside them are built at run time from the test's temporary directory, so the privacy tests have something to catch; no path is written into a source or fixture file.
- `active-work` replies use H19's shape: `{"active_agents":3,"active_work":[{"kind":"chat","session":"agent:main:x","pid":1},{"kind":"chat","session":"agent:main:y","pid":1},{"kind":"delegation","delegation_id":"d1","goal":"secret goal text","pid":1}],"pid":1}`. The goal text and session keys exist so a test can assert they never appear.
- `GET /api/status`: the mock asserts zero `x-hermes-gateway-ticket` headers and no `Origin`, and serves `fixtures/rest/doctor/api-status-ready.json`. That file holds only the keys the doctor reads (section 4.1's `StatusPage` sources, H11) plus `hermes_home`, `config_path` and `env_path` whose values start with the literal placeholder `TEMP_HOME_PLACEHOLDER` (for example `TEMP_HOME_PLACEHOLDER/config.yaml`). The mock replaces the placeholder with the test's temporary directory when it serves the file, so the privacy tests can catch a leak while the file itself holds no absolute path and passes `{{P4-01}}`'s scan of every file under `fixtures/rest/` (no user-folder path, no `~/`, no `@` domain, no 40-character token run). Key names come from H11 and are checked against the live gateway by test 26. Values are made up and documented as made up in `fixtures/rest/doctor/README.md` (a subfolder this unit owns inside `{{P4-01}}`'s `fixtures/rest/`).
- `POST /api/gateway/restart`: the mock answers `{"ok":true,"pid":4242,"name":"gateway-restart"}` and records the request line, the headers (it asserts exactly one `x-hermes-gateway-ticket`, no `Origin`), the query string (must be empty), the body (must be empty) and the ticket's minted purpose (`native-http`) and profile (`default`). A knob makes it answer 401 `{"detail":"Unauthorized"}`, 503 `{"error":"gateway_not_ready","state":"starting"}`, or 500 `{"detail":"Failed to restart gateway: boom at <temp path>"}` (H14's shape, the temporary path inserted at run time), or drop the connection after reading the request.

It lives in `crates/talaria-app/tests/support/mock_gateway.rs`, created by `{{P1-09}}` and extended by later units; if `{{P4-01}}` or `{{P4-06}}` added HTTP routes there, reuse them. ## 12. Edge cases

| Case | Behaviour |
|---|---|
| Hermes home missing or relative | `{{P1-01}}` gives `NoGateway`; the gateway row fails with its texts |
| Socket exists, nothing listening | as above (`NoGateway`) |
| Gateway in restart wait | gateway `warn`; capabilities, attach and runtime health still run (H9, H12 allow these reads); `R` answers `Done(NotReady)` with its message, because a restart is already happening |
| `identify` answers but `from_identify` says `HomeNotServed` | gateway row fails with `{{P1-01}}`'s texts; profiles row still shows the served list (raw-entry rule, 5.5) |
| `parked_profiles` holds a non-string reason | that entry is skipped |
| `code_sha` is not a string | treated as absent |
| `/api/status` takes longer than 8 s | `Unreadable { timed out after 8 s }`, warn; the other rows are unaffected |
| A client's idle-exit gateway gets its first HTTP request | the dashboard mounts during that request, which is then served (H27); a slow mount can hit the 8 s deadline (`timed out after 8 s`); a failed mount is 500 `dashboard_unavailable` (`HTTP 500`). Neither is a 404 |
| `/api/status` lacks `components` | the problems that need it are not raised; the row can still be `ok` |
| `heartbeat_stale_s` is `null` | not a problem |
| The selected profile is typed `Default` | matches `default` |
| Restart pressed twice | the second `R` is ignored while not `Idle` or `Done` |
| A restart within 10 s of another | Hermes reuses the first (H16); the doctor waits for the instance change as usual |
| The gateway restarts by itself while the card is open | `post_restart`'s fresh identify sees a new instance: `Changed`, nothing sent |
| The POST reply never arrives | `Unknown`, then the instance id decides |
| The new gateway comes back with the same instance id | impossible by H22; if seen, it is `DidNotRestart` at the deadline |
| The overlay is closed during the wait | the wait continues in `AppState.doctor_restart`; the outcome is a notice cell |
| `talaria doctor --json --restart` without `--yes` on a terminal | the confirmation lines go to standard error; standard output holds only the JSON |
| `talaria doctor --restart` with no terminal and no `--yes` and no gateway | the checks print, then the refusal line; exit 3 (precedence, 8.3) |
| `talaria doctor --restart --yes` and no gateway | the checks print, then `Restart: The gateway is not ready, so Talaria cannot ask it to restart.`; exit 1 |
| The Hermes home contains a space | `scrub_text` replaces the whole home before cutting path runs (4.1 step 2); test 8 covers it |
| The overlay is closed while the restart request is in flight and it is refused | the refusal arrives as a notice cell `Doctor: The gateway refused the restart (HTTP <s>).` (7.1 notice rule) |

## 13. Design reasoning and rejected alternatives

- **Read `/api/status`, not the control socket's `status` verb.** The `status` verb returns the raw runtime file, including `argv`, `hermes_home` and per-platform `error_message` texts (`gateway/control_socket.py:189-193`, `gateway/status.py:826-832`, `:1089-1150`). `/api/status` is the curated public probe: "counts and status enums only (public payload — no messages, paths or other detail that could carry secrets)" for its components (`status.py:421-423`). The doctor still ignores the path fields `/api/status` adds on a loopback bind.
- **Send no ticket to `/api/status`.** It is public (H10); Hermes Desktop fetches it ticketless (H25); a ticket header can only add a 401 (H26). `{{P4-01}}`'s `RequestOpts { ticket: false }` exists for exactly this.
- **Accept the status route's one possible write.** H28: the first `/api/status` after a start may create `install_id`. No other read-only source gives the component health; the write is Hermes's own bookkeeping, not a change the doctor makes to configuration or the gateway. Recorded in DECISIONS.
- **Confirm a restart by a new instance id, not by the action status route.** H21.
- **Check the instance again at Confirm; do not re-count work.** The card can stay open for minutes. Re-reading `identify` catches the case that matters (the gateway already restarted or stopped) at the cost of one request. Re-counting running work at Confirm was rejected: changed numbers would need a second confirmation, and the restart interrupts whatever is running at that moment anyway; the card says what was running when it opened.
- **Never run `ensure` from the doctor.** A doctor that starts a gateway changes the thing it is diagnosing. It prints the command instead. Whether to offer "start it" as a confirmed fix is an operator question.
- **Use `hermes gateway restart`'s own source of truth for the confirmation.** The `active-work` verb is what Hermes's command line asks before it refuses to restart live work (H19), so the number Talaria shows matches what Hermes would say.
- **Always confirm, even for one profile.** Desktop confirms only for a shared gateway; Talaria always confirms because every restart interrupts running turns (H17).
- **Rejected: run `hermes doctor` or `POST /api/ops/doctor`.** Hermes's doctor checks the install, provider keys and tool dependencies; it prints text into an action log (`hermes_cli/web_routers/ops.py:563-566`). Talaria's doctor is about the client-to-gateway link; it points to `hermes doctor` in its footer.
- **Rejected: compare the installed Hermes command line with the running gateway.** It would catch "updated but not restarted", but the only cheap source (`hermes --version`) also checks for updates over the network (`hermes_cli/main.py:2195-2202`). A later unit can add it when Hermes offers a side-effect-free source.
