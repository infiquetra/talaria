## 1. What this unit delivers

`P5-02` provides `JournaledBackend<P, T, L, G>`, which implements `P5-01`'s `AgentBackend` and owns
the journal, the identifiers, the crash-point table, parking of `unknown` admissions and operator
answers. It calls four traits. This unit implements three of them over the Hermes gateway:

```text
 P5-01 engine ──agent()──► JournaledBackend (P5-02)
                             │ resolve launch ───► ExplicitLaunch      (this unit: LaunchResolver)
                             │ first/after turn ─► SchemaTurnPolicy    (this unit: TurnPolicy)
                             │ admission gate ───► P5-04 (or NoGate)
                             │ Hermes calls ─────► HermesPort          (this unit: GatewayPort)
                             ▼                       │ one Wire per profile (P1-03 Link)
                          journal.jsonl              ▼
                                               Hermes gateway
```

`hermes::backend(journal, port, defaults, gate, retry)` builds the composition. This unit never
computes a `request_id` or `submission_id` (they arrive in `CreateSession` and `SubmitTurn`), never
writes the journal, and never decides to retry, park or resume.

| Concern | Owner |
|---|---|
| The script engine, `AgentRequest`, `CallId`, `AgentOutcome`, `null` for `Failed` | `P5-01` |
| The journal, keys, identifiers, resume, parking, operator answers, retries of transport errors | `P5-02` |
| Tiers, the roster, per-provider scheduling, the cap of 10, money and token accounting | `P5-04` |
| The progress tree (it attaches sessions on the terminal UI's own connection and does not read `AgentFeedItem`) | `P5-05` |
| `talaria workflow run/resume/list/stop` | `P5-06` |
| Creating worktrees for `isolation: 'worktree'` (`WorktreeProvider`) | `P5-07` |
| Frames, the wait, the prompt text, the schema rule, launch completion, stop | this unit |

## 3. Request and result shapes

All frames are JSON-RPC 2.0 requests sent through `P1-02`'s `Client::call_raw` on the profile's link.
Params are built here from allow-lists, never by serialising a generated struct, because the
generated types write `false` defaults (for example `"unattended": false`).

### 3.1 `runtime.describe` (once per wire)

`{"method": "runtime.describe", "params": {}}`. Required: `durable-admission-v1` in `capabilities`;
`tool` in `session_create.sources`; each of `request_id`, `source`, `model`, `provider`, `reasoning`,
`cwd`, `cwd_explicit`, `toolsets`, `skills`, `max_turns` in `session_create.parameters` (all are in
`CREATE_FIELDS`, H13). The refusal lists every missing item, comma-separated.

### 3.2 `session.create`

```json
{"method": "session.create", "params": {
  "request_id": "wf:01JB7Q...:3f9c...e1",
  "source": "tool",
  "model": "minimax-m3.1-flash",
  "provider": "ollama-cloud",
  "reasoning": "high",
  "cwd": "/abs/path/to/run/folder",
  "cwd_explicit": true,
  "toolsets": ["file", "web"],
  "skills": ["example-skill"],
  "max_turns": 40
}}
```

Keys are inserted in the order above (`CREATE_KEYS`), but key order is not part of the contract:
Hermes matches a repeated create by its sorted-keys frozen request (H38). `create_params` returns a
`serde_json::Map`, and this unit adds no `serde_json` feature (not `preserve_order`, which would
change other units' JSON output), so with the default features the wire shows the keys in
alphabetical order. Tests 1 and 21 compare key sets, not positions; test 3 compares the bytes of
calls in one build, which match whichever `Map` backing feature unification selects. Optional keys (`reasoning`, `skills`, `max_turns`) are omitted, never
`null`. `toolsets` is always present (it may be an empty list, which gives a session with no tools).
Kept from the result: `session_id`, `stored_session_id`, `execution_generation`, `info.model`,
`info.provider`, `info.reasoning_effort`, `info.source`, `info.config_warning`. `SessionBound` is
`{session_id, stored_session_id}`.

### 3.3 `prompt.submit`

```json
{"method": "prompt.submit", "params": {
  "session_id": "<from create>",
  "submission_id": "wf:01JB7Q...:3f9c...e1:0",
  "text": "<first_turn or correction text>",
  "finite": true
}}
```

Exactly these four keys in this order. Result: `AdmissionStatus` (H18) as `Receipt` with `result`
and `usage` `None`; or `{"voice_stopped": true}`, which becomes `PortError::Refused { reason:
"voice_stopped", field: None, detail: Some("Hermes treated the prompt as a voice stop") }`.

### 3.4 `prompt.receipt`

Poll: `{"session_id", "admission_id"}`. Final read and `GatewayPort::receipt`: `{"session_id",
"admission_id", "include_result": true}`. `Receipt.result` is `result` unchanged. `Receipt.usage`:

```json
{"input_tokens": 812, "output_tokens": 64, "total_tokens": 876,
 "session_cost": {"estimated_cost_usd": 0.0, "cost_status": "estimated", "cost_source": "..."}}
```

The three token keys come from the receipt's `usage` when present; `session_cost` holds whichever of
the three cost keys `result` carries, and is omitted when it carries none. A receipt without
`result` gives `usage: None`.

### 3.6 Errors

| Wire outcome | `PortError` |
|---|---|
| 4001 with `data: {reason, field, detail}` | `Refused { reason, field, detail: Some("<method>: <detail>") }` (`detail` part omitted when absent) |
| 4001 with `data: {reason, fields}` | `Refused { reason, field: None, detail: Some("<method>: fields=<a,b>") }` |
| Another error code | `Refused { reason: "rpc_error_<code>", field: None, detail: Some("<method>: <message>") }` |
| Connection closed or replaced mid-call | `Transport("<method>: connection lost")` |
| RPC timeout | `Timeout` |
| Unreadable result | `Refused { reason: "unreadable_result", detail: Some("<method>: <decode error>") }` |
| Profile not served (dial gives up) | `Refused { reason: "profile_unavailable", field: Some("profile") }` |
| Describe check fails | `Refused { reason: "unsupported", detail: Some("missing: <list>") }` |

`reason` stays Hermes's own code, because `P5-02` acts on `admission_conflict`, `invalid_params`
with field `request_id`, `not_found`, `queue_full`, `permission_denied`, `runtime_draining` and
`stale_generation` (its section 6.6). `P5-02` writes the call's failure text from these fields
(its section 6.6 row "any other refusal") and does not pin how; this unit guarantees only the
fields above, which test 24 checks. UAT-5 therefore checks only that the reason names
`invalid_params`.

## 4. Launch resolution (`ExplicitLaunch`)

Order of checks in `resolve`, each failing with the message shown and no network call:

| Check | Message |
|---|---|
| `model` absent, `tier` present | `tier '<tier>' needs the staffing table; name model and provider, or run with staffing` |
| `model` absent, no `tier` | `no model: name model and provider, or run with staffing` |
| `provider` absent | `model '<model>' needs a provider` |

`complete(request, model, provider, effort)` then fills, failing as shown:

| Field | Source | Failure message |
|---|---|---|
| `profile` | `request.profile`, else `defaults.profile` | none |
| `toolsets` | `request.toolsets`, else `defaults.toolsets` | `name toolsets for this agent, or set a run default` |
| `cwd` | `isolation: Worktree`: `defaults.worktrees?.worktree_for(request)`; else `defaults.cwd` | `worktree isolation needs a worktree provider (P5-07)`; `cwd must be an absolute path to an existing directory`; a provider error is passed through |
| `skills` | `request.skills` or empty | none |
| `max_turns`, `effort`, `isolation` | the request (`effort` from `complete`'s argument) | none |
| `schema` (checked, not copied) | `validate::check_schema(request.schema)` when present | `schema does not compile: <crate error>` |

`cwd` is checked with `Path::is_absolute` and `is_dir` and stored as a string. `ResolvedLaunch.provider`
is always `Some`. The `WorktreeProvider` must return the same folder for the same call on every
execution (`P5-02` keys the call without `cwd` and re-uses the stored `cwd` on resume).

## 5. Exact texts

### 5.1 The output contract block (`brief`)

`brief(prompt, None)` returns `prompt` unchanged. `brief(prompt, Some(schema))` returns
`prompt.trim_end() + "\n\n" + block` (the block alone when the trimmed prompt is empty, as
Hermes does), where `block` is (copied from H32, `append_output_contract`):

```text
OUTPUT CONTRACT (machine-validated):
Your FINAL response must be ONLY the JSON value that validates against this JSON Schema — no prose before or after it, no code fence, no explanation. Anything else costs a correction turn and, if it fails again, is handed to the caller unvalidated.
<schema as JSON, two-space indent, non-ASCII kept>
```

Keep the sentence exactly, including "handed to the caller unvalidated", even though Talaria
returns `null`: changing the wording changes model behaviour, and the script author sees a failed
call either way. Serialise the schema with `serde_json::to_string_pretty` (two-space indent and the
separators of Python's `json.dumps(indent=2)`). Its key order is the `Map`'s (section 3.2) and may
differ from the script's; the wording is what is copied, not the key order.

Test 9's golden file, `tests/data/hermes/golden/contract_block.txt`, is `brief("Report one
finding.", <schemas/finding.json>)`, written by hand from this section. `finding.json` has its keys

## 6. The validator

`extract_json_candidate(text)`:

1. `raw = text.trim()`.
2. If `raw` starts with three backticks: drop the first line; if the rest (right-trimmed) ends with
   three backticks, drop them; trim; if it then starts with `json` and a newline (case insensitive),
   drop that line.
3. Build spans in this order: brace (`{` first, `}` last), then bracket (`[` first, `]` last); keep a
   span only when its start is before its end.
4. Try the kept spans sorted by start; return the first that parses as JSON.
5. If none parses, return the first span in build order (the brace span if kept, else the bracket
   span); with no span, return `raw`.

| Input | Candidate |
|---|---|
| `{"a":1}` | `{"a":1}` |
| fenced, with a `json` line, then `{"a":1}` | `{"a":1}` |
| `Here you go: {"a":1} thanks` | `{"a":1}` |
| `[{"a":1},{"a":2}]` | the whole array |
| `{"a": [1,2]}` | the whole object |
| `[1, {"a": oops}` (nothing parses, `[` first) | `{"a": oops}` (the brace span) |
| `no json here` | `no json here` |
| empty | empty |

`validate_output(text, schema) -> Result<serde_json::Value, Vec<String>>`:

- Empty candidate: `Err(["Response was empty — expected a JSON object matching the schema."])`.
- Parse error: `Err(["Response is not valid JSON: <serde_json error text>"])`.
- Validate with the `jsonschema` crate, pinned to an exact version in `Cargo.toml` (`=x.y.z`, the
  newest at build time, recorded in the pull request). The draft comes from `$schema`; without it,
  set Draft 2020-12 explicitly through the crate's options, never by relying on its default.
- Collect every error. Order: compare instance paths segment by segment; a path that is a prefix of
  the other comes first; at the first differing segment a property name comes before an index;
  names compare by Unicode code point, indexes by number. Render `$`, then `.name` or `[n]` per
  segment, then `: ` and the crate's message. Keep the first 10. No errors: `Ok(value)`.
- Python sorts by `list(e.absolute_path)` and would raise on a name-versus-index tie; the rule above
  is Talaria's choice for that case and matches Python everywhere else.
- Crate message text differs from Python's and may change with a version bump: tests match the
  path prefix and a keyword (`required`, `type`), never the whole message. No golden file contains a
  crate message.
- Hermes skips validation when its `jsonschema` import fails; Talaria always validates.
- `check_schema(schema) -> Result<(), String>` builds the validator with the same options. A schema
  the pinned crate refuses to build (for example `{"type": "no-such-type"}`, which a structural
  check can let through) gives `Err("schema does not compile: <crate error>")`. `ExplicitLaunch::complete`
  calls it, so such a call fails before any network call (section 4). `after_turn` calls it before
  validating and maps an error to `Finish(Failed(<that text>))`, never to a correction turn.

## 7. The turn policy (`SchemaTurnPolicy`)

`first_turn(request, launch)` returns `brief(&request.prompt, request.schema.as_ref())`.

`after_turn(request, turns)` is pure. It reads the last `SettledTurn { turn, outcome, final_text,
result_meta, usage }`:

| `outcome` | Condition | Next step |
|---|---|---|
| `completed` | schema present and `check_schema` fails | `Finish(Failed("schema does not compile: <crate error>"))` |
| `completed` | `result_meta` empty and `final_text` `None` | `Finish(Failed("terminal without a stored result"))` |
| `completed` | `result_meta.failed` true | `Finish(Failed("agent failed: <turn_exit_reason or 'no reason given'>"))` |
| `completed` | blank text, no schema | `Finish(Failed("agent returned an empty reply"))` |
| `completed` | non-blank text, no schema | `Finish(Completed(Value::String(text)))` |
| `completed` | schema, valid | `Finish(Completed(object))` |
| `completed` | schema, invalid, turn 0 | `Turn { text: correction_message(errors) }` |
| `completed` | schema, invalid, turn 1 | `Finish(Failed("schema validation failed after one correction: <first three errors joined by '; '>"))` |
| `failed` | any | `Finish(Failed("agent failed: <turn_exit_reason or 'no reason given'>"))` |
| `interrupted`, `cancelled` | any | `Finish(Failed("stopped in Hermes (outcome '<value>')"))` |
| any other (`steered` ...) | any | `Finish(Failed("unexpected outcome '<value>'"))` |

A blank text with a schema goes through the validator ("Response was empty ...") and so gets the
correction turn. The correction is recomputed from turn 0's stored `final_text`, so asking twice
gives byte-identical text; `P5-02` journals that text before submitting, and its resume re-uses the
stored copy. `P5-02`'s `SettledTurn` has no `error` field, so failure text uses `turn_exit_reason`
from `result_meta`; if `P5-02` later adds `error` to `result_meta`, prefer it.

`usage::call_usage(turn_usages: &[Value]) -> AgentUsage`:

```rust
pub struct AgentUsage { pub input_tokens: Option<u64>, pub output_tokens: Option<u64>,
    pub total_tokens: Option<u64>, pub cost_usd: Option<f64>, pub cost_status: Option<String> }
```

Tokens: per field, `Some + Some` adds, `Some + None` keeps the `Some`, `None + None` stays `None`.
Cost: `session_cost.estimated_cost_usd` and `cost_status` of the last turn that has them (H28 says
it is the session's running total; U2). Non-numeric values are ignored and logged once per call (`tracing::warn!`).

## 9. How each `P5-02` step maps to Hermes

`P5-02`'s section 6.2 decides the step; this table says what the port sends for it.

| `P5-02` calls | The port sends | Returns |
|---|---|---|
| `create_session(CreateSession { request_id, launch, label })` | wire for `launch.profile`; `session.create` with `create_params(&launch, &request_id)`; `track` with the snapshot's cursor; `resumed_on` = the wire's generation | `SessionBound { session_id, stored_session_id }` |
| the same, as an exact retry (journal state `Intent`) | the same bytes (H6 returns the same session) | the same `SessionBound` |
| `attach(profile, session_id)` | `session.resume {session_id}` unless `resumed_on` equals the wire's generation; then `track` with the snapshot's cursor | `()` |
| `submit(SubmitTurn { profile, session_id, submission_id, text })` | `prompt.submit` with `submit_params` | `Receipt` (status from Hermes; H17 returns the existing admission on a repeat) |
| `receipt(profile, session_id, admission_id)` | `prompt.receipt` with `include_result: true` | `Receipt` with `result`, `usage` when terminal |
| `wait_settled(profile, session_id, admission_id)` | the poll loop (REQ-15), then one final read | `Receipt`, `status` `Terminal` or `Unknown` |
| `resolve_unknown(profile, session_id, admission_id, generation)` | `prompt.resolve_unknown` | `Receipt` |

The poll loop: wait `start` (250 ms); read the receipt; if `queued` or `started`, double the wait up
to `cap` (2 s); a `message.complete` event for the session wakes the loop at once and resets the
wait to `start`. `terminal`: one final read with `include_result`. `unknown`: return at once. A wire
error returns at once as a `PortError`; `P5-02` retries the step, which calls `wait_settled` again
from a fresh loop. The submit's own `Receipt` may already be `terminal` (a repeat of a finished
admission); `P5-02` then calls `receipt` or `wait_settled`, which reads it directly.

The final read is an ordinary call: its wire error returns as a `PortError` (`P5-02` retries
`wait_settled`, whose fresh loop reads `terminal` on its first poll and reads again). Its receipt
is returned as received, even if (not expected) its status is not `terminal` or it has no
`result`; `P5-02` and the policy handle those ("terminal without a stored result").

## 10. Events and the feed

`LinkWire` turns `P1-03`'s `LinkEvent` stream into `WireEvent`s; the scripted wire produces the same
`WireEvent`s from its script.

| `LinkEvent` | `LinkWire` produces |
|---|---|
| `Inbound { item: Inbound::Event(InboundEvent { frame, .. }), .. }` with `frame.session_id` set | `Event { session_id, frame }`; replayed frames too (the link has already dropped duplicates) |
| the same with no `session_id` | nothing |
| `Inbound::Malformed`, `Inbound::ServerRequest` | nothing; counted in `PortStats.dropped_items`. `P1-02` decodes payloads, so an undecodable one arrives as `Malformed` and the wire never decodes |
| `Gap(ReplayGap { session_id, reason, .. })` | `Gap { session_id, reason: reason.as_str() }` |
| `SessionGone { session_id }` | `Gone { session_id }` |
| `Reattached { session_id, .. }` | `Reattached { session_id }` |
| `State(Connected { generation })`, generation above 1 | `Reconnected { generation }` |
| `State(Connected { generation: 1 })`, `State(Reconnecting { .. })` | nothing |
| `State(Failed { reason, .. })` | nothing; later calls on this wire return `WireError::NotServed(reason)` (`profile_unavailable`) |
| `State(Closed)` | nothing; later calls return `WireError::Closed` |

The forwarder (one task per wire, which loops on `recv` and never awaits anything else, so the
link's bounded queue never fills because of Talaria) handles each `WireEvent` for a session in the
table; events for other sessions are ignored:

- `Event`: wake that session's poller when `frame.type_name()` is `message.complete`, then send
  `AgentFeedItem::Event` on the unbounded feed.
- `Gap`: send `AgentFeedItem::Gap`, then spawn one task that sends `session.resume {session_id}`,
  sets `resumed_on`, calls `Wire::resync` with the snapshot's cursor (`P1-03`'s consumer contract,
  its REQ-22) and sends `AgentFeedItem::Resynced` with the snapshot; a feed reader rebuilds that
  session's view from it. If the resume fails, the session stays without events until the next
  `attach`; the receipt path is unaffected. A snapshot naming another session id is logged and
  treated as `Gone` for the old id.
- `Gone`: send `AgentFeedItem::Gone`; drop the session's cursor.
- `Reattached`: set the session's `resumed_on` to the wire's current generation, so the next
  `attach` sends no second `session.resume`. An `attach` that races ahead of `Reattached` sends one
  redundant resume; the link's cursor drops the duplicate frames (`P1-03` REQ-14).
- `Reconnected`: nothing beyond the generation change (`attach` compares `resumed_on` with it).

No lossy step exists between the wire and the feed. The feed is unbounded on purpose: a viewer that
stops reading costs memory, never receipts. A closed feed (receiver dropped) is ignored. No other
phase 5 unit reads the feed: `P5-05` runs in the terminal UI's process and attaches sessions on
that process's own gateway connection for live events, and `P5-06`'s runner drops the receiver.

## 11. Stop

`stop(profile, session_id)` reads the latest admission from the session table and acts once; every
re-read is one `prompt.receipt` without `include_result`.

| Latest status | Sends | Answer | Result |
|---|---|---|---|
| none, or `terminal` | nothing | — | `NotRunning` |
| `unknown` | nothing | — | `Unknown` |
| `started`, generation g | `session.interrupt {session_id, execution_generation: g}` | a `CanonicalSessionHandle` (H39), whatever its `execution_state` | `Sent` |
| `started`, g | the same | refused `stale_generation` | re-read: `terminal` gives `NotRunning`; `started` with another generation gives `NotRunning` and no second interrupt; `started` with g, `queued` or `unknown` gives `Unknown` |
| `queued` | `prompt.cancel {session_id, admission_id}` | receipt `terminal`, outcome `cancelled` | `Sent` |
| `queued` | the same | receipt `terminal`, another outcome | `NotRunning` (it finished on its own) |
| `queued` | the same | receipt `started`, generation g2 (claimed during the cancel; Hermes has already interrupted it, H24) | one `session.interrupt` with g2, which repeats that stop; `Sent` |
| `queued` | the same | refused `stale_generation` (it started before Hermes read it) | re-read: `started` with g2 gives one `session.interrupt` with g2 and `Sent` (a second `stale_generation` gives `Unknown`); `terminal` is judged by outcome as above; anything else gives `Unknown` |
| `queued` | the same | receipt `queued` (not expected, H24) or `unknown`; refused `unknown_execution` | `Unknown` |
| any | any | another refusal, `Transport` or `Timeout` | `Unknown` |

The call then ends through `P5-02`'s normal path: the receipt settles `interrupted` or `cancelled`
and the policy returns `Failed("stopped in Hermes (outcome '<value>')")`.

5. Ids in fixtures are placeholders; paths are `/work/proj`. The wire never invents a field the
   contract lacks.
6. `track` and `resync` calls are logged in a second list (session id and cursor); test 28 reads it.

## 15. Edge cases

| Case | Behaviour |
|---|---|
| `request_id` over 256 or `submission_id` over 1,024 characters | `FrameError`, mapped to `Refused { reason: "invalid_params", field: "request_id" or "submission_id" }`; no frame sent |
| `isolation: 'worktree'` with no provider | section 4 message; no network call |
| `effort: none` | `reasoning: "none"` |
| `toolsets: []` from the script | sent as `[]` (a session with no tools) |
| Hermes answers `{voice_stopped: true}` | section 3.3 refusal |
| `info.config_warning` present | logged once per session; not a failure |
| `info.provider` absent or different from the launch | logged once per session; not a failure |
| A schema property named `token`, `password`, `secret` ... | Hermes masks its value (H27); the masked string is validated as received; documented for schema authors |
| The gateway restarts while queued | stays `queued` and runs later |
| The gateway restarts while started | `unknown`; returned to `P5-02`, which parks it |
| A receipt read from a new ticket after a gateway restart | allowed: same OS user gives the same subject (H22), and native grants hold `session:control` (H21) |
| The schema answer is an array but the schema root is an object | validation error at `$`, then correction |
| `delegate_task` inside a workflow agent | runs synchronously inside the turn (H30) |

## 16. Decisions the operator owns

1. **Finite-only workflow agents (start gate).** With `finite: true` a dangerous command is denied at
   once unless the profile allows it (H29), and no approval reaches the needs-you queue.
   `06-workflows.md` describes approvals going to the queue and timing out, which only
   `finite: false` would give. The operator records on `PH5` that v0.7.0 workflow agents are
   finite-only before this unit starts; choosing an attended mode edits this issue first.
2. **Profiles that auto-approve.** `approvals.single_query_mode` set to `approve`, `off`, `allow` or
   `yes`, `approvals.mode: off`, or yolo make every finite turn in that profile auto-approve. That is
   the operator's profile-wide choice, never Talaria's; the run manifest should show it (`P5-06`).
3. **Explicit provider.** Every call names a provider (or gets one from `P5-04`'s staffing). The
   operator may relax this later.

## 18. Design reasoning and rejected alternatives

- **Implementing `P5-02`'s traits, not a second backend.** `P5-02` already owns write-ahead
  intents, attempts, parking and operator answers; a second resumable backend would duplicate them
  and disagree on crash points. Rejected: this unit's first draft, with its own `CallLedger`,
  `RouteResolver` and backend.
- **One connection per profile, no `profile` key.** A profile-bound ticket naming another profile is
  refused (H23), and even a host-scoped create would subscribe a sibling connection that a later
  submit does not reach.
- **Explicit toolsets.** Without them a `tool` session gets the profile's whole CLI tool list (H10).
- **Receipt polling over event-only completion.** Events are a hint; receipts are the record
  (H33). A replay gap or a replaced connection cannot fool a receipt.
- **Allow-list frames over generated params structs.** The generated structs serialise defaults
  (`"unattended": false`, `"yolo": false`); `unattended` must never appear, and byte-stable create
  params make resume safe.
- **`source: "tool"` without `hidden`.** `tool` is already left out of human lists (H35); `hidden`
  is a bot-chat flag and not in `CREATE_FIELDS` (H13).
- **No `title`.** A titled create first resolves an existing session with that title (H4).
- **Explicit provider.** `info.provider` is optional (H2), so a call without one could not be
  recorded or costed reliably.
- **Copying Hermes's output contract wording and its single retry** (H32).
- **`Failed` after the second schema failure, `null` in the script** (`P5-01` REQ-11), not Hermes's
  unvalidated hand-back. Claude Code's contract returns `null` when a call failed after retries.
- **A lossless feed.** A lossy broadcast between the wire and a feed reader would hide gaps that the link
  already reports precisely.
- **Rejected: polling `session.events.since` for completion.** It duplicates `P1-03`'s replay and
  still needs the receipt for the stored result.
- **Rejected: sending `run_budget`.** It is a wall-clock budget, not money; budgets are `P5-04`'s.
- **Rejected: a per-agent deadline in the port.** `P5-02` treats a port timeout as a transport
  error and retries; a stalled agent is stopped through `stop`.
