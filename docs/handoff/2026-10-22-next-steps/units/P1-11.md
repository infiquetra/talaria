## 1. What this unit is for, in plain terms

The operator's complaint about the Python client was that it felt slow: slow to launch, slow to echo a keystroke while a reply streamed, and heavy on the processor. The architecture turned that complaint into numbers (the budgets). A number nobody measures is a wish. This unit builds the thing that measures them: a program that starts the real `talaria` binary inside a pseudo-terminal (a software terminal the program controls), plays a recorded Hermes reply into it, types keys while it plays, watches what the binary writes, and compares the measurements with the budgets. It exits non-zero when one is exceeded, and a continuous-integration job runs it on every pull request.

The harness measures from the outside, as a user would see it, because the Python client's own gate passed in August while launch, keystroke latency and processor use were not measured at all (u02, section 6).

Why a median for M1 and not the minimum or the maximum: the minimum hides a regression, the maximum on a shared runner is mostly noise. u11 and u02 both reported ranges; the budget needs one number, and the median of 15 is stable enough to fail on a real regression.

Why 1-second windows for the CPU peak: u02 sampled every 2 seconds and found 77.5%. A shorter window is stricter and still wide enough that a single 16 ms frame cannot reach 15% by itself.

Why the idle check also counts bytes: a binary that writes without the synchronized-output markers would escape the frame count. Zero bytes closes that gap.

Why a ratio and not a slope for M4: it is easy to explain in a failure message ("the last fifth of the frames wrote 3.4 times as many bytes as the first fifth").

### 3.1 Clocks, windows and the attempt rule (the choices the issue leaves to this document)

- **Start frame.** The first frame that leaves a non-blank cell on the emulator screen. Every later phrase "end of the first frame" or "after start-up" means the end of the start frame. A binary whose very first frame is blank therefore starts its clocks later, never earlier.
- **End of the replay.** The harness always passes `--bench-report <file>` to the binary. The appearance of that file is the end-of-replay marker for every scenario. The harness polls for it every 10 ms. **Report deadline:** the replay's expected length (the last record's `tMs` in the file divided by the speed, 0 for `instant`) plus `--report-grace-seconds` (default 10), counted from the end of the start frame. A binary that exits without a report fails at once; a binary that stays alive without one fails when the deadline passes. Either way the row is FAIL, "binary report missing", the child is killed and the run goes on to the next row.
- **Keystroke time origin.** All key offsets count from the end of the first frame (the same instant M1 stops its clock). The binary starts the replay right after its first frame, so the origin is the replay start to within a few milliseconds, which is small next to the 0.5 to 3 s offsets.
- **Keystroke schedule (`keystroke_schedule(&Budgets, speed) -> Vec<Duration>`).** Speed 1: forty keys, the first at 3,000 ms and then every 150 ms (the last at 8,850 ms). Speed 10: forty keys, the first at 500 ms and then every 100 ms (the last at 4,400 ms). Reason for the second schedule: the reference stream is 60 s long, so at 10× it lasts 6 s, and 150 ms spacing from 1 s would put the last six keys after the stream has ended. The schedule is in wall-clock time, so a 10× replay is typed over at the same human pace as a 1× replay, only earlier. The numbers live in `budgets.toml` (`interval_ms`, `start_ms`, `interval_ms_fast`, `start_ms_fast`).
- **Write lag.** A key is written on the main thread when it is due, so a busy main thread (parsing a large chunk) can write it late, and that delay is not part of the latency. The harness records each key's scheduled offset and prints the largest write lag (actual minus scheduled) as one informational count; it never changes a verdict.
- **A key that never shows.** If a key's prefix is not visible within 1 s of its write, the keystroke row for that speed is FAIL, reported as "key <n> not visible within 1 s" with no percentile.
- **A key written after the report appears.** The row is FAIL: "stream ended before the last keystroke". Test 33 proves that, for the real and the test budgets, the last key is at least 0.5 s before the replay ends; the check guards against a regression in the generator's length.
- **CPU window.** From the end of the first frame until the report file appears. Samples are the CPU seconds consumed in each 100 ms step divided by the wall seconds of that step. Peak windows are ten consecutive samples and slide by one sample. A window's value is the mean of its ten samples (equal to the processor time of that second divided by one second); the peak is the highest window value, never the largest single sample.
- **Idle window.** Starts 2 s after the report appears and lasts `idle.seconds` (30). Frames and bytes counted in it must both be zero. Mean CPU over it is printed as the informational row "idle CPU mean (not enforced)".
- **Memory windows.** M7a: one sample 1 s after the first frame of `empty.jsonl`. M7b: samples every 100 ms from process spawn until 2 s after the report appears; the highest is compared.
- **The attempt rule (timing budgets: M1, M2, M3 and M5).** A budget is measured up to `attempts` times (default 3); it passes if any attempt passes; every attempt is printed as an indented line under its row. One attempt means the whole scenario run behind that row. A retry repeats only the run behind a failing row. M4, M6 and the M7 rows are measured once: bytes per frame, idle and the cross-check come from the first M3 run (so the idle watch happens once, after the first CPU attempt), and memory has its own runs. The worst-frame row (M5) is read from the report of each CPU attempt, so it is retried together with M3.
- **Expected job length.** One pass is about 170 s: launch 16 runs of under 1 s, keystroke 60 s at 1× and 6 s at 10×, CPU 60 s plus 2 s plus 30 s idle, memory about 10 s. If every timing row failed all three attempts it would be about 7 minutes of replays. A cold release build on a shared runner adds several minutes. The workflow timeout is 30 minutes.
- **Frame-count cross-check.** The harness counts every complete synchronized frame from process start until 2 s after the report appears (launch frames included). The binary's `frames_drawn` (6.4) must be within 1% of that count, rounded up to a whole frame. For a short scenario (under 100 frames) this means the counts must be equal.

## 4. The harness

### 4.1 The child process

- Spawn the binary with `portable-pty` (or the equivalent chosen in T7) at 160×48. The binary path comes from `--binary`.
- Environment: clear it, then set `TERM=xterm-256color`, `COLORTERM=truecolor`, `LANG=C.UTF-8`, `PATH` (inherited unchanged from the harness, so a child that runs a helper still finds it), and `HOME` set to a fresh empty temporary directory. This keeps the binary away from the real `~/.talaria/config.toml` and from any Hermes variable. No variable that names a Hermes home or profile is passed.
- Arguments: `--bench-replay <file> --bench-report <file>` and, when the speed is not 1, `--bench-speed <value>`, then the arguments given with `--binary-arg` (section 7.4). Before measuring, run `<binary> --version` once to fill `binary_version` in the JSON report. Store only the first line of its standard output, and only when that line is under 100 characters and holds no `/` and no `\`; otherwise (a failure, a long line, a path) store `unknown`. No other test is needed for "a path".
- A guard kills the child (and waits for it) when the measurement ends, on success, failure or panic. A test proves no child survives.
- The clock for M1 starts immediately before the spawn call.

### 4.2 Threads and clocks

```text
child  --pty master bytes-->  reader thread  --(Instant, chunk)-->  channel
                                                                      |
   writer (keystrokes, query replies) <-- main thread (frame splitter, responder, emulator, schedule)
```

- The reader thread does nothing but read and stamp each chunk with `Instant::now()` on arrival. It never parses.
- The main thread does everything else, in stream order: split frames (4.4), feed the chunk to the `vt100` parser, answer queries (4.3), check echoes (4.5), and write the keystrokes when they are due (it waits on the channel with a timeout equal to the time to the next due key). There is no separate emulator thread: the cursor reply must come from an emulator that has parsed every byte before the query, and one thread makes that true by construction. Parsing happens after the arrival stamp is taken, so a slow parse never inflates a latency.
- A keystroke's start time is taken immediately after the `write` returns. Its end time is the arrival stamp of the chunk that completed the frame in which the echo became visible.
- If `/dev/tty` is unavailable inside the child (T6), crossterm falls back to standard output for the keyboard query (T2). Either way the harness sees the bytes on the master side.
- The PTY helper is public in the library, `talaria_bench::pty::run_in_pty(binary, args, env, size) -> PtyRun { output: Vec<u8>, exit_code: Option<i32> }`, so test 32 can run a short-lived child to completion.

### 4.3 Answering capability queries

The responder is `answer_queries(state, chunk, emulator) -> Answers` (section 13). It feeds the chunk to the emulator itself, piece by piece: the bytes up to and including each query's last byte go in first, then the reply is built from the emulator's cursor at that point, then the rest of the chunk goes in. So a query followed by more bytes in the same read still gets the cursor of the moment the query ended. The caller must not feed the same chunk to the emulator again. The responder scans the stream for these byte sequences (it keeps up to 16 trailing bytes of every chunk so a sequence split across two reads is still found) and writes the reply to the master. It must not reply to a sequence twice.

| Query the binary sends | Reply the harness writes | Notes |
|---|---|---|
| `ESC [ 6 n` | `ESC [ <row> ; <col> R`, 1-based | Row and column are the emulator's cursor at the moment the query ended, after all earlier bytes were fed to it (4.2). At launch this is `ESC [ 1 ; 1 R`. |
| `ESC [ ? u` | `ESC [ ? 0 u` | Kitty keyboard protocol supported, no flags active. (verify at build time that the composer still receives plain letters after the binary pushes its flags; plain characters are not changed by the "disambiguate" flag) |
| `ESC [ ? 2026 $ p` | `ESC [ ? 2026 ; 2 $ y` | Mode known and currently reset; `{{P1-06}}` treats 1, 2 or 3 as supported. |
| `ESC [ c` | `ESC [ ? 62 ; c` | Primary device attributes. The end marker of the start-up probe. |

Any other `ESC [ … n`, `ESC [ ? … $ p` (another mode number), `ESC [ … c` (with parameters) or `ESC ] … ?` query is returned in `Answers::seen` as `Query::Other(<type>)` and not answered. The type is the sequence with its numbers removed, for example `CSI ? $ p` for `ESC [ ? 9999 $ p`; the payload is never kept. The report lists these under `unanswered_queries`. This is informational and never changes the exit code: if a later unit adds a query that blocks until answered, the launch row shows the timeout and the 5-second message lists the queries seen; the fix is to extend the responder in this unit.

The **no queries after start-up** check: record the arrival time of every query. Any query that arrives after the start frame ends is a harness failure named `query_after_startup`, with the query's name. This catches the bake-off trap (`crossterm::cursor::position()` while the key reader runs) in the real binary, which `{{P1-06}}`'s REQ-1 forbids.

### 4.4 Counting frames

A frame is the bytes from `ESC [ ? 2026 h` through the next `ESC [ ? 2026 l`, inclusive. The splitter is a small state machine over the byte stream:

- state `Outside`: bytes are counted in `bytes_outside_frames` (a closing marker seen here is also counted as outside bytes). On the 8-byte opening marker, go to `Inside` and start a new frame (start time = arrival stamp of the chunk holding the marker's last byte).
- state `Inside`: bytes are counted into the current frame. On the closing marker, finish the frame (end time = arrival stamp of the chunk holding the marker's last byte) and go to `Outside`.
- markers may be split across chunks; the splitter keeps a tail of up to 7 bytes.
- a nested opening marker inside a frame is counted as ordinary bytes (the frame still ends at the first closing marker) and recorded as `nested_markers`.
- at the end of the run, an open frame is discarded and counted as `unterminated_frames`. The harness kills the child at the end of a measurement, so a frame cut by the kill is expected and harmless.

Frame size = bytes including both markers. A run with zero frames is a failure ("no synchronized frames seen; the binary did not use synchronized output or never drew"), not a pass. `bytes_outside_frames`, `nested_markers`, `unterminated_frames` and `unanswered_queries` are informational: they are printed on one line under the table and written to the JSON, and they never change the exit code.

### 4.5 Deciding a keystroke was echoed

Feed every byte to a `vt100::Parser` of 48 rows by 160 columns on the main thread. After each completed frame, ask the emulator for the visible text of every row. After k keystrokes have been written, the echo of key k is visible when `typed_prefix_visible(&emulator, probe, k)` is true, which means some row (or, if rows wrap, the joined text of adjacent rows) contains the typed prefix as a substring: the first k characters of the probe text `^kbdprobe-0123456789-abcdefghijklmnopqrs` (40 characters). The generated reference stream never contains the character `^`, so no streamed line can contain any non-empty prefix of the probe text, including the one-character prefix `^`. Because every prefix starts with `^`, the matcher can never match the tail of the probe without its caret: a row `> kbdp` does not match k = 5, and a row `> ^kbdp` matches k = 5 but not k = 6. (The first version of this rule used a probe that began with a letter, and the prefixes `k`, `kb` and `kbd` could then be found in ordinary text; `^` closes that hole.) A test asserts that no generated delta contains `^`, `kbdprobe` or a control character other than newline (newline is allowed: the text is Markdown). Verify at build time that the composer of `{{P1-08}}` draws a typed `^` literally; if it does not, pick another ASCII character the generator never emits (for example `~`) and change the generator's excluded set and the probe together.

The probe text is 40 characters, below the width of the screen, so it never wraps. The harness never sends Enter, so nothing is ever submitted.

When a frame completes, the highest k whose prefix is visible marks every pending key up to k as echoed at that frame's end (a key echoed in the same frame as the previous key counts for both, each from its own write time).

Edge: if a frame completes while the parser is still working on earlier bytes, the check waits for the parser to catch up to that frame's last byte before looking at the screen (it is the same thread, so this is automatic). The latency is the arrival stamp of the frame's closing marker, not the time the check ran.

### 4.6 Sampling the child

- Linux: CPU time from `/proc/<pid>/stat` fields 14 and 15 (user and system time, in clock ticks; read the tick rate once with the command `getconf CLK_TCK`), resident memory from the `VmRSS` line of `/proc/<pid>/status` (kibibytes).
- macOS: `ps -o rss=,time= -p <pid>`; `rss` is kibibytes, `time` is `M:SS.hh`.
- Either platform may use the `sysinfo` crate instead if its accumulated CPU time and memory calls exist at the resolved version (T7). No `unsafe` code, no `libc` calls.
- Sample every 100 ms. CPU percent for a step = CPU seconds used / wall seconds elapsed × 100. The binary is single-process; if it spawns children, their time is not counted, and the report says so.

## 5. The replay files the harness generates

The harness needs a long, Markdown-heavy reply to stream. The recorded fixtures from `{{P1-04}}` are short (one word, a count to 30). The Python-era recording that u02 used (5,773 frames over 131 s) is not available in the new repository. So the generator builds long files from the recorded ones: **the frame shapes are copied from recorded frames, and only the text of `message.delta` and `message.complete` frames, the sequence numbers, the timestamps, the tool ids and the session stamps are generated.** This keeps the rule that stubs come from recordings, not from imagination.

`talaria-bench generate [--fixtures <dir>] --out <dir>` writes, deterministically (no random numbers, no clock), these frame logs (version 3, see `docs/formats/frame-log.md`, created by `{{P1-04}}`; read it before writing the generator):

| File | Content | Used by |
|---|---|---|
| `empty.jsonl` | the header record only (valid per `{{P1-04}}`: "a header-only file is valid and yields nothing") | M1, M7a |
| `reference-stream.jsonl` | two assistant turns of `scenario.turn_seconds` (30) each at the recorded pace (60 s in all). | M2, M3, M4, M5, M6 |
| `long-session.jsonl` | `scenario.long_session_turns` (1,000) turns, each one assistant message and one tool call (2,000 transcript cells) | M7b |

The first line of every file is the header record, copied byte for byte from the first line of `fixtures/frames/plain-answer.jsonl` and identical across the three files and across runs. Templates are read at run time from `fixtures/frames/plain-answer.jsonl` (`message.start`, `message.delta`, `message.complete`) and `fixtures/frames/tool-diff.jsonl` (`tool.start`, `tool.complete`). If a template frame is missing, stop with the message "template frame <type> not found in <file>" (exit 2).

Record shape (copied; `tMs`, `seq` and the stamped fields are generated):

```json
{"kind":"frame","seq":7,"tMs":231,"generation":1,"dir":"in","frame":{"jsonrpc":"2.0","method":"event","params":{"type":"message.delta","session_id":"<session id of the first event of plain-answer.jsonl>","seq":4,"payload":{"text":"Hello"}}}}
```

Two numbers called `seq` exist: the record's `seq` (position in the file, gapless from 1) and `params.seq` (the gateway's per-session counter, H2). Both are renumbered; `params.seq` runs from 1 across the whole file.

**Session stamps (H7).** The two fixtures were recorded in different sessions, so their `session_id` values (and, when present, `replay_epoch` values) differ. The reducer of `{{P1-05}}` would drop every frame whose `session_id` differs from its state's, and would refuse to apply a frame whose `replay_epoch` differs from its cursor's. So the generator sets, on every generated event frame, `params.session_id` to the first event's `session_id` in `plain-answer.jsonl`; `params.replay_epoch` to that same event's value, when the key exists there; `params.authority_epoch` and `params.admission_id` likewise, copied from that first event when it has them; and `params.execution_generation`, when the key exists there, to one value per turn (that event's value for turn 1, then rising by 1 per turn). `bench_replay` builds its `SessionState` with the same session id (6.2). Test 10 asserts one session id, one epoch, one authority epoch and one admission id per generated file, and a generation that rises by 1 per turn, and test 29 asserts that the report's `cells` equals 2,000 for `long-session.jsonl`, which would be about 1,000 if tool frames were dropped.

### 5.1 Reference stream

- Pace: one batch every 33 ms (H3), alternating one and two `message.delta` frames per batch (about 45 frames per second, close to the 44 per second of the u02 recording). Frames in one batch share a `tMs`. A turn is `turn_seconds` of batches, so about 1,360 delta frames per turn at 30 s (batch number 1 holds one frame, batch 2 holds two, and so on, which is 1,363 frames in 909 batches).
- Turn 1, "line heavy": the first line is `## Reference turn 1`; then a repeating template of headings, short bullet lists, numbered lists, a table and one-line paragraphs, about 120 lines and 6.8 KB in all (u02's heavy turn 2 had 118 lines and 6,415 characters and drove 54% to 77.5% of a core in the Python client); the last line is `End of reference turn 1.`
- Turn 2, "code": the first line is `## Reference turn 2`; then paragraphs and exactly three fenced code blocks (Python-like text, about 100 lines inside fences), about 6.8 KB; the last line is `End of reference turn 2.`
- The text uses only letters, digits, space, newline (allowed inside deltas) and the punctuation `# * - | . , ; : ( ) _ = < > / " ' \`` (the backtick for fences). It never contains `^`, `~`, `kbdprobe` or a control character. **Cutting rule (exact).** The text is cut into deltas by the repeating length cycle 3, 5, 7, 4, 6 (mean 5), counted in characters, ignoring word boundaries; the last delta takes whatever remains. Deltas are grouped into batches of 1, 2, 1, 2 ... frames, 33 ms apart, so a turn lasts (number of deltas / 1.5) x 33 ms. **Sizing rule.** The generator builds the turn from whole blocks: it needs `frames x 5` characters, where `frames` is the count for `turn_seconds` (1,363 at 30 s), and it adds whole blocks until the text reaches that length, then adds the last line. So a turn lasts `turn_seconds` within 5% (test 11 accepts 28.5 s to 31.5 s), the text never runs out before the batches do, and no delta is empty. Turn 1's blocks are a repeating cycle of a numbered heading, a short bullet list, a numbered list, a table of three rows, and a one-line paragraph; each repetition has its own counter so lines differ. Turn 2's blocks are numbered paragraphs with the three fenced code blocks inserted after the first quarter, half and three quarters of the paragraphs (so exactly three fences, none cut). The block wording is the builder's, from the character set above, fixed in source. Each fenced block holds `round(1.1 x turn_seconds)` lines (33 at 30 s, 7 at 6 s), so a short test turn still fits its three fences and lasts its `turn_seconds` within 5% by the same sizing rule.
- Each turn: one `message.start` (copied), the deltas, one `message.complete` with `status: "complete"` (copied, `text` set to the full turn text, which equals the concatenation of the turn's delta texts).
- Test 11 asserts, at the default knobs: turn 1 has 100 to 140 lines; turn 2 has exactly three fences; each turn's text is between 5 KB and 9 KB; batches are 33 ms apart.

### 5.2 Long session

`long_session_turns` (1,000) repetitions of: `message.start`, three `message.delta` frames of about 80 characters, `message.complete`, `tool.start` (fresh `tool_id` such as `bench-000001`), `tool.complete` with the recorded `inline_diff` (same `tool_id`). Pace: instant file (`tMs` all 0 after the first frame); the harness plays it at `--bench-speed instant`. 2,000 cells: 1,000 assistant plus 1,000 tool.

### 5.3 Extra scenarios

`--extra-fixture <path>` (repeatable) and every `*.jsonl` file in `--scenario-dir` (default `tools/bench/scenarios`, which holds a README and no scenario at first) add a file to the streaming checks M2 (1× only), M3, M4, M5 and M6, with rows labelled by the file name. This is the extension point for later units that need their own streaming case (for example the queue-preview scenario in `{{P2-08}}`, which builds a file from recorded `queue-*.jsonl` frames and drops it in `tools/bench/scenarios/`, so it never edits `bench.yml`). The harness does not interpret the file; it plays it. A scenario file must carry the same session id as its own first event and stay within one epoch; the harness does not rewrite it.

## 6. The `--bench-replay` entry point

Owned by this unit in `crates/talaria-cli/src/bench_replay.rs`; kept by `{{P1-12}}`.

### 6.1 Command line

```text
talaria --bench-replay <fixture> [--bench-speed <value>] [--bench-report <path>]
```

- `<fixture>`: a frame log version 3 file.
- `--bench-speed`: `instant`, `recorded` (same as `1`), or a finite positive number (`10` plays ten times faster). Default `recorded`. Maps to `hermes_client::replay_source::Speed::{Instant, Recorded, Factor(f)}`. Zero, negative, not a number, infinite (`inf`, `1e400`) or `NaN`: exit 2, message "--bench-speed must be instant, recorded or a positive number".
- `--bench-report`: where to write the report file (6.4). Optional.
- `--bench-replay` is a measurement aid, not a feature. It is not documented in the user guide and is not listed in the placeholder help of `{{P0-02}}` (that unit's test 10 fixes the placeholder help to exactly three lines). Whether the final `--help` of `{{P1-12}}` lists it is that unit's decision; its REQ-1 says the flag is "kept unchanged" and its AC-5 expects `--help` to list it, so `{{P1-12}}` un-hides it. That is a conflict to report to the lead, not to resolve here.

A pure function `parse_args(&[String]) -> Result<Option<BenchReplayArgs>, ArgError>` returns `Ok(None)` when `--bench-replay` is absent, so `main` can fall through to the normal path. `main.rs` calls `parse_args` first, before any other argument handling, because the placeholder parser of `{{P0-02}}` rejects unknown flags (`unknown argument`, exit 2). Read `main.rs` at build time and keep the change to a few lines: call `parse_args`, and when it returns `Some`, return `bench_replay::run(args)`.

### 6.2 What it does

1. Parse the arguments. A bad speed or a missing value exits 2 with one plain line.
2. Open the fixture with `ReplaySource::open`. On error print one plain line naming the problem (the path as given, never made absolute) and exit 2, before touching the terminal and before checking for one. No escape byte is written.
3. If standard input or output is not a terminal, print "talaria: --bench-replay needs a terminal" to standard error and exit 2 (the "not a terminal" path of `{{P1-06}}`'s `TerminalError::NotATerminal`). Opening the fixture first means test 27 can check both messages without a pseudo-terminal.
4. Probe the terminal, acquire the terminal guard, create the inline terminal over a byte-counting writer (all `{{P1-06}}`). The counting writer is a small struct that implements `io::Write` around the real writer and adds the length of every successful write to a counter.
5. Start the key thread (`spawn_input`, `{{P1-06}}`) and the replay task; both send messages into the single application event channel.
6. Build the state: `SessionState::empty(<session id of the first event frame in the fixture>)`; when the fixture has no event frame (`empty.jsonl`) use the id `bench`. The composer is `Composer::new(KeyMap::defaults())` (`{{P1-08}}`); no configuration file is loaded.
7. Loop: receive one message, then drain whatever else is queued without waiting; apply replay frames to the state through `talaria_core::session::update` (frames whose `method` is not `event`, or that have no `session_id`, are counted as skipped and otherwise ignored); route keys to the composer; commit the cells the commit ledger releases; draw the live region once for the whole batch; record the elapsed time of this pass. The live view is the streaming Markdown tail (`{{P1-07}}`) plus the composer (`{{P1-08}}`) only. The status line (`{{P1-10}}`), the prompt cards (`{{P1-09}}`) and the connection are not drawn, so the budgets measured here cover that screen and not the finished application's; `{{P1-12}}` adds the status section to this view so the budgets cover what it ships. The first line of the harness table says so (`bench wiring: streaming tail and composer only (no status line, no prompt cards)`).
8. When the replay source finishes it sends one end-of-replay message through the same event channel, after its last frame. The loop handles that message as an ordinary pass: it applies nothing, commits and draws what is pending, records the pass time, and only then writes the report file (6.4), so the report counts every frame drawn and the last replayed frame is on screen before it appears. Then it keeps running with the composer idle (so the harness can measure idle frames and memory). The process ends when the harness kills it, or when the composer's quit gesture (`{{P1-08}}`) is used. On exit it restores the terminal through `TerminalGuard` and `InlineTerminal::restore`.

The wiring is deliberately small: the real application wiring (connection, sessions, effects) is `{{P1-12}}`. The helper that turns a replayed frame into a `talaria_core::session::Event::Session` is private to `bench_replay.rs`. If it needs more than a few hundred lines in total, stop and report (it means the interfaces of `{{P1-05}}` to `{{P1-08}}` do not fit together as planned). Read the merged code of those units first; the composer must accept and show typed text while a reply streams, and if it does not, stop.

### 6.3 What it must not do

No network, no Hermes call, no read of `~/.talaria/config.toml`, no auto-approve flag on any request, no submission of the composer's text (the replay has no gateway; if the composer reports a submit, drop it). It does not call `execute!`, `queue!`, `enable_raw_mode`, `disable_raw_mode` or `EventStream` itself (T9); the terminal module of `{{P1-06}}` does that. The string for the auto-approve flag is not written in any `.rs` file under `crates/` outside a `tests/` folder; describe it in words.

### 6.4 Report file

Written once, when the replay finishes, atomically (write a temporary file in the same directory, then rename):

```json
{
  "format": 1,
  "replay_frames": 5400,
  "frames_skipped": 3,
  "cells": 2,
  "loop_passes": 1370,
  "frames_drawn": 1331,
  "bytes_written": 412345,
  "worst_pass_us": 2310
}
```

Field meanings: `replay_frames` is every frame the replay source delivered (applied and skipped); `frames_skipped` is those that were not `event` frames or had no `session_id`; `cells` is the number of transcript cells in the session state when the report is written (committed to the scrollback or not), which is 2,000 for `long-session.jsonl`; `loop_passes` is the number of loop passes, including the end-of-replay pass. `worst_pass_us` is the longest single loop pass, in microseconds, measured with `std::time::Instant` around the apply, commit and draw of step 7. `frames_drawn` is the number of `draw_live` calls that returned `drew = true` plus the number of `commit` or `commit_lines` calls that wrote at least one byte (each such call is one synchronized batch, `{{P1-06}}` REQ-14; the commit calls return no `FrameStats`, so the byte test uses the counting writer's counter before and after the call). `bytes_written` is the counting writer's final count. The harness cross-checks `frames_drawn` against the number of frames it counted from outside (3.1); a difference above 1% (the allowed difference is 1% of the harness count, rounded up to a whole frame, so counts under 100 frames must be equal) is reported as `frame_count_mismatch` and fails the run (it means the frame splitter or the synchronized-output wrapping is wrong). Verify at build time that `commit` wraps each batch in one marker pair; if a commit with no lines writes nothing, the byte test already skips it. If the report file is missing when the harness expects it (the binary exited early, or the deadline of 3.1 passed), the worst-frame row is FAIL with "binary report missing" and the run exits 1.

## 8. The `bench` workflow (draft)

File `.github/workflows/bench.yml`. It is a separate file so that it does not touch the job names of `ci.yml` (`{{P0-02}}`), which are load-bearing for branch protection. Follow the pinning style of `ci.yml`: the same `actions/checkout` hash, the same toolchain install, and for the upload the same `actions/upload-artifact` hash that the `rust-coverage` job of `ci.yml` uses for its `lcov` artifact (`{{P0-02}}` pins third-party actions by full commit hash with the tag in a comment). If `ci.yml` pins no upload action, pin the newest stable release's commit hash and record it in the pull request.

```yaml
name: Bench
on:
  pull_request:
  workflow_dispatch:
    inputs:
      runner:
        description: Runner image
        type: choice
        options: [ubuntu-latest, macos-14]
        default: ubuntu-latest
permissions:
  contents: read
jobs:
  bench:
    name: bench
    runs-on: ${{ inputs.runner || 'ubuntu-latest' }}
    timeout-minutes: 30
    steps:
      - uses: actions/checkout@<same pinned hash as ci.yml>
      - name: Install the pinned toolchain
        run: |
          rustup toolchain install
          rustup show active-toolchain
      - name: Build the binary
        run: cargo build --release -p talaria-cli -p talaria-bench
      - name: Measure
        run: >
          target/release/talaria-bench run
          --binary target/release/talaria
          --report bench-report.json
      - name: Keep the report
        if: always()
        uses: actions/upload-artifact@<same pinned hash as the lcov upload in ci.yml>
        with:
          name: bench-report
          path: bench-report.json
```

The measure step fails the job when the harness exits 1 or 2. `if: always()` keeps the report when it does. The `timeout-minutes: 30` leaves room for a cold release build plus the replays and their retries (3.1). Scenarios in `tools/bench/scenarios/` run without any change to this file. The job is not added to the required checks by this unit; that is the operator's call. Test 30 asserts the triggers, the job name, `macos-14`, `contents: read`, the timeout, the checkout hash and the upload hash.

## 9. The test double (fake client)

Tests of the harness need a client whose behaviour is known. `tools/bench/src/bin/fake_tui.rs` is a tiny program that writes raw escape sequences (it does not use ratatui or crossterm). It copies the real query byte strings from section 4.3 (T1, T2, T3). Flags:

## 10. Test notes

Order of writing (the issue lists the tests; this is the reasoning):

1. Pure parts first: responder, frame splitter, echo detection, budgets, generator. They need no pseudo-terminal, so a red run fails for the stated reason and not for an environment reason.
2. The fake client next, then the harness end to end against it, one test per budget that must fail.
3. The real binary last, because it depends on four other units. These tests run the debug build of `talaria` through the same harness, assert behaviour (the reply text appears, the typed text echoes, the report file exists, the report counts match) and **do not assert budgets** (debug builds are slow; budgets are asserted by the `bench` job on the release build).

Test numbers in the issue: 1 to 2 responder; 3 frames; 4 to 5 echo and generator text; 6 to 8 and 33 budgets; 9 to 12 generator; 13 sampler; 14 to 25 and 34 to 36 harness; 26 to 27 `talaria-cli`; 28 to 29 and 31 to 32 real binary; 30 workflow.

### 10.1 Helper notes

- `tools/bench/tests/support/mod.rs`: `fake_tui_path()` returns `env!("CARGO_BIN_EXE_fake-tui")`; `test_budgets()` loads `tests/data/budgets-test.toml`.
- Idle windows in tests use `--idle-seconds 2`; one test asserts the default taken from `budgets.toml` is 30.
- Fixtures for the generator tests: a copy of the template frames in `tools/bench/tests/data/templates/` taken from the real `fixtures/frames/` files once `{{P1-04}}` has merged. Do not write them by hand.
- Tests never contain an absolute path, a home directory, a user name or a profile name other than `default` or `fixture`; use `tempfile` directories, and compute the workspace root at run time from `env!("CARGO_MANIFEST_DIR")` joined with `../..`.
- Failing-budget tests pass `--only <row>` for the row they target, so each runs in seconds, not minutes.

### 10.2 `tests/data/budgets-test.toml`

The test file has the same keys as `budgets.toml`. Values: launch `median_ms` 1500, `runs` 3, `warmups` 1; keystroke `p95_ms` 100, `max_ms` 150, `keys` 10, `interval_ms` 100, `start_ms` 500, `interval_ms_fast` 40, `start_ms_fast` 50, `visible_within_ms` 1000; cpu `mean_pct` 50, `peak_pct` 50; worst frame `max_ms` 40; idle `seconds` 2; memory `start_max` 100, `long_session_max` 100; `unit_choice` `bytes_median` 4096, `late_over_early` 3.0; scenario `turn_seconds` 6, `long_session_turns` 100. The replay is then 12 s at 1× and 1.2 s at 10×; the last test key is at 1.4 s at 1× and 0.41 s at 10×.

Each passing run must stay under half of its limit with `fake-tui`; each failing flag must exceed its limit by at least a factor of two: `--startup-delay-ms 3000` (limit 1500), `--echo-delay-ms 300` (limit 150), `--spin` (about 100% against 50), `--slow-pass-ms 80` (limit 40), `--frame-bytes 9000` (limit 4096), `--grow-bytes 64` (a ratio well above 6 against 3.0), `--ballast-mib 250` (limit 100), `--frames-drawn-skew-pct 5` (limit 1%). This keeps a failing test failing for the intended reason and a passing test from flaking on a busy machine.

### 10.3 Building and finding the real binary (tests 28, 29, 31 and 32)

`talaria-bench` does not depend on `talaria-cli`, so `env!("CARGO_BIN_EXE_talaria")` does not exist in its tests. Tests 28, 29 and 32 build the debug binary themselves: run `std::process::Command::new(env!("CARGO")).args(["build", "-p", "talaria-cli"])` from the workspace root and assert it succeeds (a build failure fails the test), (verify at build time that this nested build does not wait on the build-directory lock of the outer `cargo test`; if it does, build `talaria-cli` in its own step before `cargo test` and make the tests use that binary, failing with "build the debug binary first" when it is absent, and say so in the pull request) then use `<target directory>/debug/talaria`, where the target directory is `CARGO_TARGET_DIR` when set and `<workspace root>/target` otherwise. Test 31 (`release_budgets_hold`, `#[ignore]`) uses `<target directory>/release/talaria` and fails with "build the release binary first" when it is absent; it never skips, because a skip would report ok without measuring. It expects exit 0, so it passes only when the binary meets the budgets; settled decision 5 says that may honestly not hold at merge, so record the result in the pull request either way.

### 10.3a Wall-clock tests in the project check

Tests 14 to 22, 28, 29, 32 and 34 to 36 run inside `cargo test --workspace`, which is part of the required `rust-check` jobs. They are written to be insensitive to a slow runner (every passing run stays under half its limit, every failing flag exceeds its limit at least twice, 10.2). If one of them fails on a required runner with no code change, do not add retries, loosen a limit, mark it `#[ignore]` or remove it: stop and report to the operator, who decides whether such tests move to the `bench` job only.

### 10.4 Terminal-only checks

`talaria-cli` takes no pseudo-terminal crate, not even as a dev-dependency (settled decision 6). Its tests (26 and 27) therefore cover argument parsing and the piped paths with `std::process::Command`. The checks that need a terminal live in `tools/bench/tests/real_binary.rs`: test 32 runs `talaria --bench-replay <missing path>` in a 160×48 pseudo-terminal through `run_in_pty` and asserts one plain line, exit 2 and no `ESC` byte (0x1b) anywhere in the output. Because the fixture is opened before the terminal is touched (6.2), no byte of terminal control is written, which proves the terminal was left as it was found without inspecting terminal modes from outside.

## 11. Edge cases

| Case | Required behaviour |
|---|---|
| The binary prints nothing for 5 s | Fail with "no frame within 5 s; did the binary answer the capability queries?" and the list of query types seen |
| The binary exits before the first frame | Fail with "the binary exited with status <n> before its first frame". Never echo the child's output: a panic message can hold an absolute path |
| The binary exits during a measurement | Fail the budget being measured with "the binary exited with status <n>" |
| The binary exits without writing its report, or stays alive without one past the deadline of 3.1 | The worst-frame row is FAIL, "binary report missing"; the child is killed; exit 1 |
| A query reply is lost | The harness writes each reply once; a test with a one-byte chunk size proves split queries are answered once |
| Keystroke typed while a frame is in flight | Latency runs to the end of the next frame in which the echo is visible; a key echoed in the same frame as the previous key counts for both, each from its own write time |
| A key's prefix never shows | The row is FAIL, "key <n> not visible within 1 s", no percentile |
| The emulator screen is wider than the probe text | Fine. If the prefix wraps (not possible at 160 columns for 40 characters), the check searches the joined text of adjacent rows |
| A template frame is missing | Exit 2 naming the missing template; never fall back to invented frames |
| Replay ends before the 40 keystrokes are sent | Not possible by construction on the 60 s file (last key at 8.85 s at 1×, 4.4 s at 10× against a 6 s replay); the harness still checks: if the report appears before the last key is written, fail with "stream ended before the last keystroke" |
| Two harness runs at once on one machine | Allowed, results are noisy; the output never prints a host name |
| `GITHUB_STEP_SUMMARY` unset | Skip the summary silently |
| Windows | Unsupported: exit 2 "unsupported operating system" |
| Clock steps backwards | Not possible: only `Instant` is used |
| The report file is a symlink or already exists | The binary writes to a fresh temporary file and renames; the harness uses a new empty work directory per run |
| `<binary> --version` fails, prints a long line or a line with `/` or `\` | `binary_version` is `unknown` |

## 12. Choices made here, open points and design reasoning

Choices the issue left open, settled so a builder does not ask:

- **Exit code.** Any FAIL row makes exit 1, including the two check rows and either unit-choice limit. Informational counts (`unanswered_queries`, `unterminated_frames`, `nested_markers`, `bytes_outside_frames`) and the INFO and SKIPPED rows never do.
- **Unit-choice limits (2,048 bytes median, 1.5 late over early).** The architecture row says "proportional to changed cells; never growing with transcript length" and gives no number. The ratio is how this unit enforces "never growing"; the median is the "typical" target of u02 section 8. Both are enforced and labelled "(unit choice)". A builder may not change either after seeing a measurement to make a run pass; the pull request records the first release measurements, and if a legitimate recorded frame exceeds the median the builder stops and asks the operator (the issue's stop conditions). They are not architecture-table values, so settled decision 1 is not what protects them: the operator's written reply is.
- **Where the scenario files come from.** `run` generates them itself into a temporary directory. `generate` exists for people who want to replay a file by hand (UAT-3).
- **`message.complete` text.** The generator sets it to the full turn text (REQ-12 lists it among the generated fields).
- **Session stamps.** Section 5 rewrites `session_id`, `replay_epoch` and `execution_generation`; section 6.2 gives `bench_replay` the same session id.
- **`frames_drawn` counts commit batches too** (6.4), and the harness count is every complete frame from process start to 2 s after the report.
- **Keystroke schedule at 10×** differs from 1× (3.1), because the same wall-clock schedule outlasts the 6 s replay.
- **Echo rule.** Any emulator row containing the typed prefix, with a probe that begins with `^`, a character the generator never emits (4.5).
- **Machine line.** Line 1 of the output, exactly as in 7.1.
- **`--only`.** Prints only the selected rows plus the live-gateway SKIPPED row.
- **Attempts.** Section 3.1: each attempt is a whole scenario run; retries repeat only failing rows; bytes, idle and the cross-check come from the first CPU attempt.
- **Operator questions, built as written and open to the operator's written reply.** The issue treats both readings as settled for the build; the operator may overrule either, and neither stops the work. (1) The architecture's "2,000-message session" is read as 2,000 transcript cells (1,000 assistant plus 1,000 tool rows), because `{{P1-05}}` builds one cell per message row of a snapshot, tool rows included. If the operator means 2,000 assistant messages, set `long_session_turns` to 2,000 and say so in the pull request (the long-session file then holds 4,000 cells, and test 29's expected `cells` becomes `2 x long_session_turns`, which the test reads from the budgets file). (2) "MB" in the table is read as mebibytes; 40 MiB is about 4.9% looser than 40 MB (41.9 MB). The numbers 40 and 100 are the architecture's and are not changed; only the unit is a reading. If the operator says megabytes, change `unit` to `MB` and the divisor to 1,000,000 in one commit, and test 6's expected unit with it. Test 6 asserts the unit string `MiB` so the change is deliberate. (3) The two unit-choice limits above. (4) Whether the macOS run is advisory.

Design reasoning:

- **Why from the outside, in a pseudo-terminal.** In-process benchmarks (Criterion) measure a function, not the product; the Python client's gate was in-process and said nothing about what the operator felt (u02 section 6). The cost is noise and a dependency on a terminal emulator crate. The in-process worst-frame number is the one exception because the outside cannot see compute time.
- **Why not hyperfine or a shell script.** They cannot answer terminal queries or type keys at a measured moment.
- **Why a Rust harness and not Python.** The repository drops Python in `{{P0-02}}`; a second language in CI is a second toolchain.
- **Noise policy (best of 3).** A regression that fails all three attempts is real; a noisy runner that fails one is not. The cost is that a 20% regression hidden by one lucky attempt passes. The operator may prefer a stricter rule; the number of attempts is a flag.
- **Statistic for launch.** Median of 15. The operator may prefer the 95th percentile.
- **The reference stream is synthetic text on recorded frame shapes.** A real long Markdown reply recorded live would be better evidence. If the operator wants one, `{{P1-04}}`'s recording tool can add a scenario and the generator can read it instead of building text; that is a change to `{{P1-04}}`'s files and is not made here.
- **Launch to a usable composer with a gateway (200 ms).** The requirements document (R1) says the harness of this unit measures it, and `{{P1-12}}`'s REQ-4 says the budget is measured by this unit's `bench` job, but `{{P1-12}}`'s acceptance criteria only check that the job is green, which passes while the row is SKIPPED. This unit cannot measure the row because it needs a running gateway and the real connection code. It prints the row as SKIPPED and `{{P1-12}}` owns the measuring row, for example by adding a launch-to-composer row to `talaria-bench` that runs against a mock gateway. The conflict is reported on the issues, not resolved here.
- **Coverage of the real screen.** The `--bench-replay` view leaves out the status line (whose external command refreshes on a timer, a cause of idle CPU in the Python client per u02 section 4) and the prompt cards. `{{P1-12}}` must add the status section to the view before its done condition ("the bench budgets pass") means what it says; the table's second line states the limit of what was measured.
- **Platform differences.** macOS runners are slower and noisier than Linux; budgets are the same. The operator decides whether the macOS run is advisory.
- Verify at build time: T6 and T7, the `vt100` API for reading screen text, that crossterm 0.29's key reader accepts plain bytes written to the pseudo-terminal after the binary pushes keyboard enhancement flags, that the composer draws `^` literally and accepts input while a reply streams, and that `commit` writes one marker pair per batch.

## 13. Public interface (signatures)

These are the names the independent test author writes against, before any code exists. A builder may add lifetimes, derives or error detail, but may not rename an item or remove a capability. Every item is `pub` in the library `talaria_bench` (`tools/bench/src/lib.rs`, modules named in the issue's file list) and re-exported at the crate root. Bodies start as `todo!()`.

// ---- errors (exit 2 when returned from run or generate; Display is the one plain line) ----
pub enum BenchError {
    BinaryNotFound(String),                          // path as given
    FixturesMissing(String),                         // directory as given
    TemplateMissing { file: String, frame_type: String },
    BudgetsInvalid(String),                          // file as given plus the reason
    PtyUnavailable(String),
    UnsupportedOs,

    Io(String),                                      // never holds an absolute path
}

// ---- budgets (budgets.rs): public fields named exactly as the TOML keys ----
pub struct Budgets { pub terminal: TerminalSize, pub launch: Launch, pub keystroke: Keystroke,
    pub cpu: Cpu, pub worst_frame: WorstFrame, pub idle: Idle, pub memory: Memory,
    pub live_gateway: LiveGateway, pub unit_choice: UnitChoice, pub scenario: Scenario }
// e.g. budgets.launch.median_ms: f64, budgets.keystroke.p95_ms: f64, budgets.idle.frames: u64,
// budgets.memory.unit: String ("MiB"), budgets.memory.start_max: f64, budgets.live_gateway.composer_ms: f64.

pub fn keystroke_schedule(budgets: &Budgets, speed: f64) -> Vec<Duration>;
    // speed <= 1.0 uses start_ms/interval_ms; any larger speed uses the _fast pair; length = keystroke.keys

pub fn last_t_ms(fixture: &Path) -> Result<u64, BenchError>;         // last record's tMs, 0 if none

// ---- statistics and verdicts (budgets.rs) ----

pub fn window_means(samples: &[f64], window: usize) -> Vec<f64>;      // mean of each run of `window` samples, sliding by one

pub fn verdict(measured: f64, limit: f64) -> Status;                  // Pass when measured <= limit, else Fail
pub fn best_of(attempts: &[f64], limit: f64) -> (Status, f64);        // Pass when any attempt <= limit; the f64 is the best (lowest) attempt

impl Row { pub fn info(name: &str, measured: &str) -> Row; pub fn skipped(name: &str, limit: &str) -> Row; }

How the tests use these (the independent test author's map):

- Test 1: `answer_queries` on `hello` + `ESC[6n` gives reply `ESC[1;6R`; a second case feeds `ESC[6n` + `xyz` in one chunk and expects `ESC[1;1R` (the cursor at the moment the query ended).
- Test 2: feed the four queries and `ESC[?9999$p` one byte at a time; the concatenated replies hold each reply once, `seen` holds four known `Query` values once each and `Query::Other("CSI ? $ p")` once.
- Test 3: `FrameSplitter::push` over chunks cut at every byte position; `Frame::bytes` includes both markers; `counts()` gives outside bytes, `nested_markers` 1 and `unterminated_frames` 1 for the stray, nested and open cases.
- Test 4: an `Emulator` fed `> ^kbdp`: `typed_prefix_visible(.., probe, 5)` true, `6` false; an emulator fed `> kbdp`: `5` false.
- Test 5: read the generated files and check every `message.delta` text.
- Test 6: `Budgets::load` of the shipped file; fields compared with ten constants and `memory.unit == "MiB"`.
- Test 7: `median`, `percentile_nearest_rank`, `peak_window` (mean of each ten-sample window), `verdict` on both sides of a limit, `Row::info` and `Row::skipped` never counted by `exit_code`.
- Test 8: `best_of(&[90.,140.,150.], 100.)` is `(Pass, 90.)`; `best_of(&[140.,150.,160.], 100.)` is `(Fail, 140.)`.
- Test 13: spawn `fake-tui --spin` (or `--ballast-mib 64`) with `std::process::Command` and null stdio, call `sample` twice about 1 s apart, check `cpu_percent` above 80 or `rss_bytes` above 64 MiB; kill the child.
- Tests 14 to 22, 24 (first half), 25, 34 to 36 (and 23 and 35 above): call `run` with `RunOptions::new(fake_tui_path(), test_budgets())` and the stated `binary_args`; check `Report::rows`, `render()`, `to_json()` and `exit_code`. Test 24's exit code 2 and one-line message are checked by running the `talaria-bench` binary (`env!("CARGO_BIN_EXE_talaria-bench")`) with `--binary ./no-such-binary`; test 12's exit 2 the same way with an empty `--fixtures` directory, besides the `BenchError::TemplateMissing` check on `generate`.
- Test 35: `--exit-before-first-frame` gives a launch row FAIL whose text holds "the binary exited with status 3 before its first frame" and nothing else from the child; `--exit-after-ms 800` with `--only cpu` gives a CPU row FAIL "the binary exited with status 4".
- Test 36: `--early-report-ms 300` gives a keystroke row FAIL "stream ended before the last keystroke" (the last test key is at 1.4 s at 1x).
- Test 23: after a failing run, each pid in `Report::child_pids` is gone (for example `ps -p <pid> -o pid=` prints nothing); the test never searches by name.
