## 1. What this unit delivers

The `talaria-workflow` crate gains an `engine` module that runs one workflow script to completion
inside an embedded QuickJS JavaScript engine, through the `rquickjs` Rust bindings. The engine:

1. Parses the script's `export const meta = {...}` header as a pure literal, without running any code.
2. Runs the script body in a sandbox: no filesystem, network, timers, modules, clock or randomness;
   memory, stack and synchronous run-time limits.
3. Exposes Claude Code's workflow API (`agent`, `parallel`, `pipeline`, `phase`, `log`, `args`,
   `budget`, `workflow`) plus Talaria's options and two deterministic helpers (`now`, `random`).
4. Hands every `agent()` call to an `AgentBackend` trait object as an `AgentRequest` with a stable
   `CallId`, and turns the backend's `AgentOutcome` back into a JavaScript value, one outcome at a
   time in a recorded order, so that a resumed run given a replay log repeats the original run
   exactly (section 7).
5. Emits `EngineEvent`s (phases, logs, agent start and finish, child workflows) on a channel.
6. Ends with a `RunOutcome`: completed with a JSON result, failed with a located script error, or
   aborted.
7. Ships a `MockBackend` (feature `mock`) driven by a JSON rules file, used by this unit's tests and by
   every later phase 5 unit, and a `dry_run` example that prints the run as JSON lines.

What it deliberately does not do, and who does:

| The `talaria-workflows` Hermes skill and ultracode | `P5-09` |

## 3. The Claude Code contract the engine copies

Source: Claude Code's public workflow documentation (<https://code.claude.com/docs/en/workflows>) and
its workflow-authoring reference, summarised in [../06-workflows.md](../06-workflows.md#script-api-version-1)
and in the parity rows of [../04-prior-art.md](../04-prior-art.md#claude-code-parity-checklist).
Talaria keeps these rules unchanged:

| Rule | Talaria engine |
|---|---|
| A script begins with `export const meta = {...}`, a pure literal: no variables, calls, spreads or template interpolation. Required `name`, `description`; optional `whenToUse`, `phases` (each `{title, detail?, model?}`). | Same. Section 4. |
| Plain JavaScript, not TypeScript. The body runs in an async context; top-level `await` and top-level `return` work. | Same: the body is wrapped in an async function. |
| `Date.now()`, `Math.random()` and argument-less `new Date()` throw. No filesystem or Node.js API. | Same, plus the further closures in section 5. |
| `agent(prompt, opts)` returns the final text, or the validated object when `schema` is given, or `null` if the agent was stopped or hit an unrecoverable error. | Same. Talaria adds options (section 6.1); Claude Code's `stallMs` is accepted and ignored. |
| No module loading: "a script that contains `import()` fails before the run starts". | Same: `parse_script` refuses it (section 4.4), with a run-ending backstop. |
| The schema is checked before the agent starts; when Claude Code can prove it contradicts itself (its example: a `required` key that `additionalProperties: false` rules out) the call fails. Output that fails validation after five attempts fails the call. | Structural checks only (section 6.1.1), which include that example; no deeper contradiction analysis. Result validation, with one correction turn, is `P5-03`'s. Both are documented differences. |
| `parallel(thunks)` is a barrier; a thunk that throws resolves to `null`; the call never rejects. | Same, except an abort ends the run (section 6.2). |
| `pipeline(items, ...stages)` has no barrier; each stage gets `(prevResult, originalItem, index)`; a stage that throws drops that item to `null` and skips its remaining stages. | Same. |
| At most 4,096 items per `parallel` or `pipeline` call; more is an explicit error. | Same. |
| At most 1,000 agents per run, children included. | Same, configurable. |
| `phase(title)` groups later agents; `opts.phase` assigns one call explicitly. | Same. |
| `log(message)` emits a narrator line. | Same. |
| `args` is the run's input value, verbatim; `undefined` when none. | Same. |
| `budget.total` is a token target or `null`; `spent()`, `remaining()` (Infinity with no target); once spent reaches total, further `agent()` calls throw. | Same, plus `budget.money` (section 6.6). |
| `workflow(nameOrRef, args)` runs another workflow inline, one level deep; the child shares the parent's agent counter, abort and budget; nesting deeper throws; unknown name, unreadable path or a child syntax error throws. | Same. |
| Up to 16 concurrent agents by default, fewer with fewer CPUs, configurable. | **Different by design:** the engine imposes no width limit; `P5-04` wraps the backend with the scheduler and the global cap of 10. |
| Resume replays "in the order agents start"; the first agent whose prompt differs, and every agent after it, runs again. | **Different by design:** content plus occurrence identity with ordered replay (section 7); after a change, unchanged later calls still reuse their results. |
| `opts.agentType` picks a Claude Code subagent type. | **Refused** with a message that names `tier`, `toolsets` and `skills` (Hermes has no agent types). |

## 4. Script format and parsing

### 4.1 The header

`parse_script(source)` finds the first statement after any leading whitespace and comments (`//` and
`/* */`; a leading `#!` line is not allowed). That statement must be `export const meta =` followed by
an object literal and a statement boundary (section 4.2). Anything else is
`ScriptError::MetaMissing { line }`, where `line` is the line of the first significant token found
(or of an unterminated block comment). `MetaMissing` carries no column.

The literal is parsed by hand in `engine/meta.rs`; no JavaScript is evaluated. Positions in every
`ScriptError` are 1-based lines and 1-based columns counted in Unicode scalar values of the original
source (a tab counts as one column).

```text
value      := object | array | string | number | 'true' | 'false' | 'null'
object     := '{' [ member (',' member)* [','] ] '}'
member     := key ':' value
key        := identifier | string                    (computed keys [x] are refused)
identifier := [A-Za-z_$] [A-Za-z0-9_$]*              (ASCII only; quote any other key)
array      := '[' [ value (',' value)* [','] ] ']'   (holes such as [1,,2] are refused)
number     := ['-'] ('0' | [1-9][0-9]*) ['.' [0-9]+] [('e'|'E') ['+'|'-'] [0-9]+]
string     := single | double | backtick
comments and whitespace may appear between any two tokens
```

- Numbers: no leading zeros (`01`), no leading or trailing dot (`.5`, `5.`), no `+`, `NaN`,
  `Infinity`, hexadecimal, octal, binary, `_` separators or `BigInt` suffix.
- Escapes allowed in all three string forms: `\'` `\"` `` \` `` `\\` `\/` `\b` `\f` `\n` `\r` `\t`
  `\v`, `\0` when not followed by a digit, `\uXXXX`, and `\u{X...}` up to `10FFFF`. Any other escape,
  a line continuation (backslash then newline) and a lone surrogate from `\uD800`-style escapes are
  refused.
- Single and double quoted strings may not contain a raw line terminator.
- Backtick strings may contain raw newlines (CRLF becomes LF, as in JavaScript). `${` anywhere in a
  backtick string is refused; a `$` not followed by `{` is an ordinary character.
- An unterminated string or block comment inside the literal is refused at the opening quote or `/*`.

Anything else inside the literal is `ScriptError::MetaNotLiteral { line, column, found }`, where
`found` names the offending token, for example `identifier N`, `call`, `spread`, `template ${`,
`computed key`, `number 01`, `unterminated string`.

### 4.2 Statement boundary

After the closing `}` of the literal, the next significant token (skipping spaces, tabs and
comments) must be `;`, a line terminator, or the end of input. When it is a line terminator, the next
significant token after it must not continue the expression. These first characters continue it and
are refused as `MetaNotLiteral { found: "expression continues after the meta literal" }`, at that
token: `(` `[` `.` `?` `+` `-` `*` `/` `%` `,` `=` `<` `>` `&` `|` `^` `` ` `` `!` and the words `in`
and `instanceof`. So `export const meta = {...} + x` and the same split across two lines are both
refused.

### 4.3 Field rules

| Field | Rule | Error |
|---|---|---|
| `name` | Required string, 1 to 64 characters from `A-Z a-z 0-9 . _ -`, not starting with `.` (it becomes part of file names in `P5-06`). | `MetaField { field: "name", problem }` |
| `description` | Required non-empty string after trimming. | `MetaField { field: "description", ... }` |
| `whenToUse` | Optional string. | `MetaField` if not a string |
| `phases` | Optional array of objects; each has a non-empty string `title`, optional string `detail`, optional string `model`; titles are unique. | `MetaField { field: "phases[2].title", ... }` |
| Any other key | Kept out of `WorkflowMeta`; reported once in `ParsedScript.warnings` ("unknown meta key `x` ignored"). | none |

Duplicate keys in the literal are refused (`MetaField { field: <key>, problem: "duplicate key" }`),
at the top level and inside a `phases` entry. An unknown key inside a `phases` entry is treated like
an unknown top-level key: it is left out of `PhaseMeta` and reported once in `warnings` as "unknown
meta key `phases[0].x` ignored". The 64 of `name`, like every length limit in this document (label
120, default label 60, log 4,000), counts Unicode scalar values, not bytes.

### 4.4 Module syntax is refused before running

Claude Code refuses "a script that contains `import()`" before the run starts (its documentation,
"Behavior and limits"). Talaria does the same, inside `parse_script`, so nothing runs and no
`Started` event is sent.

The scan (`engine/scan.rs`) walks the body's tokens, skipping comments, string literals, the text
parts of template literals (but not their `${...}` expressions) and regular-expression literals. A
`/` starts a regular-expression literal when the previous significant token is not an identifier,
a number, a string, `)`, `]` or `}`; otherwise it is division. The scan refuses the word `import`
when it is not directly preceded by `.` or `?.` (a property name such as `x.import` is fine) and is
followed by `(` or `.` (dynamic import and `import.meta`). The result is
`ScriptError::ImportNotAllowed { line, column }`.

- A method named `import` in an object literal (`{ import() {} }`) is also refused. This false
  positive is deliberate; write `{ 'import'() {} }`. The script API document says so.
- A static `import` or `export` statement in the body is left to the JavaScript compiler: it is a
  `SyntaxError` with its original line, reported as `RunOutcome::Failed`.
- Backstop: because the regular-expression rule is a heuristic, the engine also installs a module
  loader (`set_loader`) whose resolver refuses every specifier. If an `import()` ever reaches it, the
  engine ends the run as `RunOutcome::Failed` with name `ImportNotAllowed` and the message "modules
  are not available in workflow scripts". This is not a catchable rejection: the resolver sets a
  flag that the run loop checks after every job, exactly like a cancel.

### 4.5 The body and source positions

`ParsedScript.body` is the original source with every character of the meta statement (from
`export` to the closing `}` and an optional `;`) replaced by a space, except line terminators, which
stay. Lines and columns of every later character are therefore unchanged.

The engine evaluates, as a classic script named `<meta.name>.js`:

```text
(async function () {"use strict";<body>
})()
```

The prefix `(async function () {"use strict";` is 33 characters long and sits on line 1. Line 1 can
hold body code (a one-line header followed by code on the same line), so for any error located on
line 1 the engine subtracts the prefix length from the reported column before it builds a
`ScriptFailure`. This applies to runtime errors (from the stack trace) and to `SyntaxError`s from the
compiler. The engine converts QuickJS's column to Unicode scalar values of the original line. If the
bundled QuickJS reports no column for an error, `column` is `None`; the planner checks this before
building (section 14), and test 4 asserts columns only for the error kinds the build reports them
for.

- Top-level `await` and `return` work. The returned value is the workflow's result.
- Strict mode applies, as it would in a module.
- TypeScript annotations are syntax errors, as in Claude Code.

## 5. The sandbox

### 5.1 Runtime limits

Set on the `rquickjs::AsyncRuntime` before any code runs. Checked on docs.rs for rquickjs 0.14.0 on
2026-10-22: `AsyncRuntime` exists only with the crate feature `futures`; `set_loader` exists only
with the feature `loader`; `set_memory_limit`, `set_max_stack_size`, `set_interrupt_handler`,
`idle`, `drive`, `execute_pending_job` and `is_job_pending` need no further feature. Re-check against
the newest release before building.

| Limit | Default (`EngineConfig`) | Behaviour when hit |
|---|---|---|
| Heap | `memory_limit_bytes = 256 MiB` | The run fails: `RunOutcome::Failed`, message contains `out of memory` |
| Stack | `max_stack_bytes = 1 MiB` | The run fails; message contains `stack overflow` |
| Synchronous slice | `max_sync_slice = 5 s` | The run fails; message "the script ran JavaScript for more than 5 s without waiting for an agent or a child workflow" |
| Agents per run | `max_agents = 1000` | `agent()` rejects with `AgentLimitError` (catchable) |
| Items per call | `max_items_per_call = 4096` | `parallel`/`pipeline` reject with `ItemLimitError` (catchable) |

Only the first three end the run outside the script's control. The last two are ordinary promise
rejections that a script may catch.

The synchronous slice is measured in real time (`std::time::Instant`), per turn. A turn starts when
the run loop resumes JavaScript (the first evaluation, or delivery of one host result) and ends when
QuickJS has no runnable job left (`is_job_pending()` is false) and the loop waits on host futures.
Time spent waiting for the backend or the resolver never counts. A chain of already-resolved
promises (`for (;;) await null`) never leaves its turn, so it is stopped like a plain `while (true)`.

The interrupt handler returns true when the slice is exceeded, when the cancel token is cancelled,
or when the import backstop flag is set, so all three stop even a script that never awaits.

### 5.2 What the global scope contains

The engine creates the context with the standard ECMAScript intrinsics only, and installs the
refusing module loader of section 4.4.

The prelude (`engine/prelude.js`, embedded with `include_str!`, run before the body) then:

```js
"use strict";
(() => {
  const RealDate = Date;
  const fail = (what, hint) => { const e = new Error(`${what} is unavailable in workflow scripts (it would break resume); ${hint}`); e.name = "DeterminismError"; throw e; };
  function SafeDate(...a) {
    if (!new.target) fail("Date()", "pass timestamps in through args, or use now()");
    if (a.length === 0) fail("new Date() without arguments", "pass timestamps in through args, or use now()");
    return Reflect.construct(RealDate, a, new.target);
  }
  SafeDate.prototype = RealDate.prototype;
  Object.defineProperty(RealDate.prototype, "constructor", { value: SafeDate });
  SafeDate.UTC = RealDate.UTC;
  SafeDate.parse = RealDate.parse;
  SafeDate.now = () => fail("Date.now()", "pass timestamps in through args, or use now()");
  Object.defineProperty(globalThis, "Date", { value: SafeDate, writable: false, configurable: false });
  Object.defineProperty(Math, "random", { value: () => fail("Math.random()", "use random(key) or vary prompts by index"), writable: false, configurable: false });
  for (const name of ["performance", "Intl", "WeakRef", "FinalizationRegistry", "navigator", "console"]) {
    if (name in globalThis) delete globalThis[name];
  }
})();
```

Why each removal: `performance.now()` and `Intl.DateTimeFormat().format()` read the clock;
`WeakRef` and `FinalizationRegistry` expose garbage-collection timing; `navigator` is host
information; `console` is not part of the script API (section 3 does not list it) and its output would bypass the
event stream. Whether the bundled QuickJS defines each of these was not checked (no Rust toolchain
was run while drafting); the test asserts each is absent, whatever the build.

`eval` and `Function` stay: they only compute, inside the same sandbox. Code they build is not
covered by the `import()` scan, which is why the loader backstop exists.

Globals that must be absent (asserted by a test): `require`, `process`, `fetch`, `XMLHttpRequest`,
`WebSocket`, `setTimeout`, `setInterval`, `setImmediate`, `std`, `os`, `Deno`, `Bun`, `crypto`,
`performance`, `Intl`, `WeakRef`, `FinalizationRegistry`, `navigator`, `console`.

`console` being absent is deliberate: a transferred script that calls `console.log` fails at that line
with a `ReferenceError` (QuickJS's message), located like any uncaught error. The script API document
lists this difference and says to use `log()`.

The determinism guard is not a security boundary against a hostile script author; the security
boundary is that no host capability exists. Its purpose is to stop honest scripts from breaking
resume by accident.

## 6. Host functions

The root body sees the host functions as non-writable globals installed after the prelude. Errors
are `Error` objects whose `name` is listed in section 10, so a script can test `e.name`.

### 6.0 JSON conversion

Values cross between JavaScript and Rust as JSON in four places: the workflow's result, a child's
`args`, a child's result, and an agent's `Completed` value going into JavaScript. The first three use
strict conversion, defined as `JSON.stringify` with a replacer that throws on:

- a function or a symbol at any position;
- a number that is `NaN`, `Infinity` or `-Infinity`;
- `undefined` as an array element.

`JSON.stringify`'s own behaviour applies otherwise: `BigInt` and cycles throw; `toJSON` is honoured
(a `Date` becomes its ISO string); an object property whose value is `undefined` is omitted; an array
hole becomes `null`. A root value of `undefined` converts to `null`.

| Place | Conversion failure |
|---|---|
| Workflow result | `RunOutcome::Failed`, message "the workflow result is not JSON-serialisable: <reason>" |
| Child `args` | `workflow()` rejects with `WorkflowOptionError` ("workflow(): args is not JSON-serialisable: <reason>"), catchable |
| Child result | `workflow()` rejects with `WorkflowScriptError` ("workflow `x` returned a value that is not JSON-serialisable: <reason>"), catchable |
| Agent value into JavaScript | cannot fail: a `serde_json::Value` always converts |

### 6.1 `agent(prompt, opts?)`

Steps, in order. Each failing step rejects the returned promise.

1. `prompt` must be a string with at least one non-whitespace character (`WorkflowOptionError`).
2. `opts` may be `undefined` or `null`, both meaning "no options", or a plain object. Anything else
   (an array, a string, a function) is `WorkflowOptionError`.
3. Each key of `opts` must be one of the allowed keys below; any other key is refused with a message
   listing the allowed keys. `agentType` has its own message: "agentType is a Claude Code option;
   Hermes has no agent types. Use tier, toolsets or skills."
4. Each value is checked against the table. A key whose value is `undefined` counts as absent. A key
   whose value is `null` is refused, to catch `model: config.model` where the config lacks the key.
5. If `schema` is present, it is checked for well-formedness (section 6.1.1).
6. If the run is stopping (cancel, backend abort, import backstop), no request is made; the run ends.
7. If the run has already started `max_agents` agents, `AgentLimitError`. Replayed calls count, as
   they did in the earlier run, so an unchanged script stays within the same limit on resume.
8. The `CallId` is computed (section 7). If the replay log holds it (section 7.2), the call is
   replayed: no budget check and no backend call. It passed the budget check in the earlier run, and
   a restored spent total at or above the budget must not refuse work that is already paid for.
9. For a live call, the backend's `BudgetSnapshot` is read; if a token or money total is set and
   spent is at or above it, `BudgetExhaustedError` naming which budget. Otherwise the backend is
   called. `AgentStarted` is emitted for every call that gets past this step, with `replayed` set
   accordingly. A call rejected at any step before this one gets no `CallId` and consumes no
   occurrence number (section 7.1).
10. The outcome is mapped when the run loop delivers it (section 7.2): `Completed(value)` becomes the
    value (a string stays a string, an object becomes a JavaScript object); `Failed` and `Skipped`
    become `null`; `Abort` ends the run (section 6.9). `AgentFinished` is emitted before the promise
    settles.

| Key | Type and rule | Into `AgentRequest` |
|---|---|---|
| `label` | non-blank string, at most 120 characters | `label` (default: section 6.1.2) |
| `phase` | non-blank string | `phase` (default: the current `phase()` title, or none) |
| `schema` | object, well-formed (6.1.1) | `schema` |
| `tier` | non-blank string | `tier` (resolved by `P5-04`) |
| `model` | non-blank string | `model` (overrides `tier`, resolved by `P5-04`) |
| `provider` | non-blank string | `provider` |
| `effort` | one of `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`, `ultra` (H3) | `effort: Effort` |
| `profile` | non-blank string | `profile` |
| `toolsets` | non-empty array of non-blank strings, no duplicates (H6) | `toolsets` |
| `skills` | non-empty array of non-blank strings, no duplicates (H7) | `skills` |
| `isolation` | exactly `'worktree'` | `isolation: Some(Isolation::Worktree)` |
| `maxTurns` | integer from 1 to 10,000 (H5) | `max_turns` |
| `stallMs` | a Claude Code option; accepted when it is a positive integer, otherwise refused | nothing: it is dropped, excluded from the digest, and the first use in a run emits one `Log` "stallMs is ignored: Talaria does not restart stalled agents" |

Value rules common to every key:

- A non-blank string has at least one character for which Rust `char::is_whitespace` is false, so
  `"   "` is refused for `label`, `phase`, `tier`, `model`, `provider`, `profile` and each element of
  `toolsets` and `skills` alike. Values go into `AgentRequest` exactly as given, untrimmed.
- Lengths count Unicode scalar values.
- Duplicates in `toolsets` and `skills` compare as exact strings: `"Web"` and `"web"` are distinct.
- `maxTurns` and `stallMs` must satisfy `Number.isInteger`. JavaScript cannot tell `5.0` from `5`, so
  `5.0` passes; `1.5` is refused.

`maxTurns` left out means no workflow override: the session inherits the profile's turn-limit policy
(H13), which may be a finite cap. It does not mean "unlimited". A script cannot ask for unlimited
turns; that needs an unlimited profile policy, set by the operator.

#### 6.1.1 Schema well-formedness

The engine guarantees exactly these structural checks, each failing with `SchemaError` and the
reason:

1. The root is an object with `type: "object"`.
2. The root has `properties`, an object.
3. `required` is optional. If present, it is an array of strings, each a key of `properties`
   (`required: []` is fine). This also covers the contradiction Claude Code's documentation gives as
   its example, a `required` key that `additionalProperties: false` rules out.
4. The schema is plain JSON data. The engine walks the JavaScript value before converting it: every
   value at any depth must be `null`, a boolean, a finite number, a string, an array, or a plain
   object (prototype `Object.prototype` or `null`) whose properties are data properties. Refused,
   each with the path of the offending value (for example `properties.when`): a function, a symbol,
   a `BigInt`, `NaN` or an infinity, `undefined` as a property value or array element, an array hole,
   an accessor property, an object with a `toJSON` member (own or inherited), any other object (a
   `Date`, a `Map`, a class instance), and a cycle. A schema that passes converts to JSON with nothing
   dropped or transformed, which is what "unchanged" means here.

The engine does no deeper contradiction analysis; a schema with contradictory constraints that passes
these checks is forwarded. This is a documented difference from Claude Code. The engine does not
validate results against the schema; `P5-03` does, with one correction turn (Claude Code makes up to
five attempts; also documented).

#### 6.1.2 Default label

The prompt is split on line feed (`\n`) only. The first piece that has a non-whitespace character
(Rust `char::is_whitespace`) is trimmed with Rust `str::trim`, which also removes a trailing `\r`,
then cut to 60 Unicode scalar values with `…` appended when cut (61 in all). Step 1 guarantees such a
piece exists.

### 6.2 `parallel(thunks)`

- `thunks` must be an array (`WorkflowOptionError`), of at most `max_items_per_call` elements
  (`ItemLimitError`), each a function (`WorkflowOptionError` naming the first bad index). These
  checks happen before any thunk is called.
- Each thunk is called once, in index order, synchronously, before `parallel` returns its promise; so
  every thunk's first `agent()` call is issued before any of them completes.
- The result is an array in index order. A thunk that throws, or returns a promise that rejects,
  yields `null` in its slot. The call never rejects for those reasons.
- A stop (cancel, backend `Abort`, import backstop) is not a thunk failure: the whole run ends.
- An empty array resolves to `[]` immediately.

### 6.3 `pipeline(items, ...stages)`

- `items` must be an array (`WorkflowOptionError`), of at most `max_items_per_call` elements
  (`ItemLimitError`). At least one stage is required, and every stage must be a function
  (`WorkflowOptionError`).
- For each item `i`, independently: `r = item`; for each stage `s`: `r = await s(r, item, i)`. The
  first stage therefore receives `(item, item, i)`.
- A stage that throws (or rejects) sets item `i`'s result to `null` and skips its remaining stages.
  A stage that returns `null` passes `null` on; only a throw drops the item.
- No barrier: item `i` may be in stage 3 while item `j` is in stage 1.
- The result is the array of final values in item order. An empty `items` resolves to `[]`.

### 6.4 `phase(title)` and `log(message)`

- `phase(title)`: `title` is converted with `String()`, trimmed, and must be non-empty
  (`WorkflowOptionError`). It becomes the current phase of the calling workflow instance for later
  `agent()` calls that give no `opts.phase`, and emits `EngineEvent::Phase`. A title not in
  `meta.phases` is allowed; it simply has no detail line.
- `log(message)`: converted with `String()`; cut to 4,000 characters with `…` when longer; emits
  `EngineEvent::Log`. Returns `undefined`.

The current phase belongs to one workflow instance (section 6.7): a child starts with no current
phase, and the parent's current phase is unchanged by anything a child does.

### 6.5 `args`

The JSON value from `EngineConfig::args`, converted through `JSON.parse`. `undefined` when the
config holds `None`. A child instance's `args` is the value its caller passed, after strict
conversion (section 6.0); `undefined` when the caller passed none.

### 6.6 `budget`

```text
budget.total          → number | null      tokens_total from the backend's BudgetSnapshot
budget.spent()        → number             tokens_spent
budget.remaining()    → number             max(0, total − spent), or Infinity when total is null
budget.money.total    → number | null      money_total (US dollars; accounting is P5-04's)
budget.money.spent()  → number
budget.money.remaining() → number          as above, Infinity when null
```

`total` is a getter, read from the snapshot each time. The engine itself never counts tokens or
money. Reading `spent()` makes control flow depend on live usage; as in Claude Code, a loop that
depends on it may run a different number of iterations after a resume. The script API document says
so. A snapshot with a negative or non-finite money value is treated as a backend defect: the engine
reports it as `RunOutcome::Failed` ("backend budget snapshot is invalid").

### 6.7 `workflow(nameOrRef, args?)` and workflow instances

- `nameOrRef` is a non-empty string (a saved workflow's name) or `{ scriptPath: string }` with a
  non-empty path and no other key (`{scriptPath: 'a.js', name: 'a'}` is refused); anything else is
  `WorkflowOptionError`.
- The engine asks `WorkflowResolver::resolve(&WorkflowRef)` for the source. `NotFound` and
  `Unreadable` reject with `WorkflowNotFoundError`. The child source is parsed with `parse_script`; a
  `ScriptError` (including `ImportNotAllowed`), or a `SyntaxError` when compiling the child body,
  rejects with `WorkflowScriptError` carrying the child's line and column. All of these are
  catchable by the parent. Warnings from parsing the child (unknown meta keys) are carried by
  `ChildStarted.warnings` (section 9).
- Each `workflow()` call creates a new workflow instance. The child body is compiled as
  `(async function (agent, parallel, pipeline, phase, log, args, budget, workflow, now, random) {"use strict";<child body>\n})`
  and called with functions bound to that instance. Because the bindings are function parameters,
  they are lexical: every call the child body makes, before or after any `await`, reaches its own
  instance. No mutable "current child" global exists. The child prefix (everything before
  `<child body>`) is longer than the root's; for an error on the child's line 1 the engine subtracts
  its length from the column, as section 4.5 does for the root.
- The instance owns its `args`, its current phase and its `workflow_path` (section 7). Its
  `workflow` binding always rejects with `NestedWorkflowError` ("workflows nest one level only").
- Children share the run's agent counter, budget, limits, cancel token, replay log and backend.
- Concurrent children are supported, for example
  `parallel([() => workflow('a', {x: 1}), () => workflow('b', {x: 2}), () => agent('parent')])`.
  Each child's calls carry its own path; the parent's calls carry `[]`.
- Events carry the `workflow_path` of the instance that produced them. `ChildStarted` and
  `ChildFinished` mark a child's start and end in time; events of the parent or of a sibling may
  appear between them. Consumers group events by `workflow_path`, never by position.
- The promise resolves to the child's return value after strict conversion. An uncaught error in the
  child rejects the parent's promise with that error (catchable).
- Attribution of a run failure. When a child body rejects with an object, the engine records the
  child's `workflow_path` for that object in an engine-held `WeakMap` the script cannot reach, unless
  the object already has one. If that object then fails the run uncaught (directly or rethrown by the
  parent), `ScriptFailure` reports the line, column and stack from the object's own stack trace (the
  child's source position) and `workflow_path` set to the child's path. A rejection with a
  non-object (a thrown string) has no position: `line`, `column` and `stack` are `None` and
  `workflow_path` is the path of the instance whose body rejected. Errors the engine raises for a
  `workflow()` call (`WorkflowNotFoundError`, `WorkflowScriptError`, `NestedWorkflowError`, conversion
  errors) belong to the calling instance; the child's line stays in their message.
- Two concurrent children with the same name and the same `args` have the same path; their identical
  calls are told apart by occurrence, like any identical calls.

### 6.8 `now()` and `random(key)`

Deterministic helpers in place of the clock and `Math.random`:

- `now()` returns `EngineConfig::started_at_ms`, the run's start time in milliseconds since the Unix
  epoch, the same number for the whole run. `P5-02` stores it in the run manifest so a resumed run
  sees the same value.
- `random(key)` requires a non-empty string `key` (`WorkflowOptionError` otherwise) and returns a
  number in `[0, 1)`: the first 53 bits of `SHA-256(seed as 8 big-endian bytes ‖ workflow_path joined
  by "/" ‖ 0x00 ‖ key)` divided by 2^53, with the joined path and the key as UTF-8 bytes (the root's
  empty path contributes no bytes). The same key gives the same number in the same instance
  path, whatever the order of calls. `EngineConfig::seed` is stored by `P5-02` in the manifest.

These replace the "journaled helpers" sketched in [../06-workflows.md](../06-workflows.md#script-api-version-1):
deriving them from two manifest values gives the same guarantee with nothing to journal and no
dependence on call order. This is a design refinement the operator may overrule (it is listed as a
question on the issue).

### 6.9 How a run ends, and what happens to unfinished work

A run ends in one of these ways. In every case each `AgentStarted` gets exactly one
`AgentFinished`, each `ChildStarted` gets exactly one `ChildFinished`, and `Finished` is the last
event.

| Ending | Outcome | Unfinished agents and children |
|---|---|---|
| The root body returns | `Completed { result }` | Agents still pending (started and never awaited) are abandoned: their backend futures are dropped and each gets `AgentFinished` with kind `abandoned`, in invocation order. Pending children get `ChildFinished { ok: false }`. The result stands. |
| The root body throws, or a run-ending limit is hit | `Failed { error }` | As above: abandoned. |
| The caller cancels the token | `Aborted { reason: "cancelled" }` | Futures dropped; each gets `AgentFinished` with kind `aborted`. |
| The backend returns `Abort { reason }` for any call | `Aborted { reason }` | As for cancel. |
| The import backstop fires | `Failed` with name `ImportNotAllowed` | As for cancel, kind `aborted`. |

- The first ending wins. An `Abort` that arrives after the root body has settled is ignored, as is
  any outcome of an abandoned call.
- On cancel, abort or backstop: no further `AgentStarted`, the runtime is dropped, and what dropping
  a future means for work already in Hermes is the backend's business (`P5-06` owns stopping
  sessions). `P5-02` parks an admission whose outcome is unknown for the operator (never treating it
  as a failure) and returns `Abort` only when the run must end, for example on an operator's `abort`
  answer or a gateway outage longer than its budget.
- None of these endings is visible to the script as an exception: `try`/`catch` and `parallel`'s
  null-on-throw cannot swallow them.
- Abandoning is not an error. The script API document recommends awaiting every agent.

## 7. Call identity and replay

`P5-02` keys the journal with the call's identity and resumes a run by handing the engine a replay
log. Together, identity (7.1) and ordered replay (7.2) must ensure that resuming an unchanged script
with the same inputs reuses every finished result, in the same places, with no new backend call for
finished work, whatever order concurrent calls completed in.

### 7.1 `CallId`

`CallId { digest: String, occurrence: u32 }`:

- `digest` is lower-case hexadecimal SHA-256 of the canonical JSON of this object, with absent
  options omitted (never written as `null`), so that a future option does not change existing
  digests:

  ```json
  {"v":1,"workflow_path":[...],"prompt":"...","schema":{...},"tier":"...","model":"...",
   "provider":"...","effort":"...","profile":"...","toolsets":[...],"skills":[...],
   "isolation":"worktree","max_turns":5}
  ```

  Canonical JSON: object keys sorted by Unicode code point, no insignificant whitespace, strings
  escaped as `serde_json` escapes them, numbers as `serde_json` prints them. `label`, `phase` and
  `stallMs` are excluded: renaming a label must not re-run work. Consequence for `P5-03`: label and
  phase must not change what the backend computes (they may name the session, never enter the prompt).
- `occurrence` counts earlier started `agent()` calls (those that emitted `AgentStarted`) in this run
  with the same digest, starting at 0, in the order `agent()` was invoked. A call rejected before it
  starts (section 6.1 steps 1 to 9) consumes no number.
- `workflow_path` is `[]` for the root workflow. Inside a child it is `[<child>]`, where `<child>` is
  `name:<name>@<h>` or `path:<scriptPath>@<h>`, and `<h>` is the first 12 hexadecimal characters of
  the SHA-256 of the canonical JSON of the child's converted `args` (`null` when absent).
- Display form: `<first 12 hex of digest>#<occurrence>`.

Invocation order is not stable by itself under concurrency: in a `pipeline`, item B can reach a call
before item A on one run and after it on the next. When two identical calls (same digest) return
different results, numbering them by invocation order alone would let a resumed run hand item A the
result item B received. Section 7.2 removes that risk by making invocation order reproducible.

### 7.2 Ordered delivery and replay

Delivery rule (every run). The run loop resolves host results one at a time: it delivers exactly one
outcome to JavaScript, then runs JavaScript until no job is runnable, then delivers the next. Each
delivered outcome gets the next `completion_seq` (0, 1, 2, ...), carried by its `AgentFinished`.
When several backend futures are ready at once, they are delivered in invocation order. Because the
script cannot read a clock or randomness, the sequence of delivered outcomes fully determines every
later `agent()` invocation, and so every `CallId`.

Replay (resume). `EngineConfig::replay` may hold a `ReplayLog`: the finished calls of an earlier run
of the same script, in that run's `completion_seq` order, each with its `CallId` and outcome. `P5-02`
builds it from its journal and decides which outcomes to include (for example, it may leave out
failed calls so they run again).

1. When `agent()` computes a `CallId` that is in the log and not yet used, the call is replayed: no
   backend call, `AgentStarted { replayed: true }`.
2. Any other call is live: the backend is called at once, so live work starts early, but its outcome
   is held while the log still has undelivered entries.
3. The loop delivers log entries strictly in log order. It delivers the next entry as soon as its
   call has been invoked.
4. Divergence: if JavaScript has no runnable job, the next log entry's call has not been invoked, and
   no other log entry can be delivered, the replay has diverged (the script, its inputs or a
   non-replayed outcome changed what runs). The loop emits `ReplayDiverged { at_seq }` and switches
   the rest of the log to cache mode: a remaining entry is delivered as soon as a call with its
   `CallId` is invoked, in any order, and held live outcomes are released in arrival order (ties in
   invocation order). Before divergence only the next entry is ever deliverable (rule 3), so the
   condition is exactly: JavaScript idle and the next entry's call not invoked. `at_seq` is the
   0-based index in the log of that next undelivered entry; it equals the number of outcomes
   delivered so far, which is also the `completion_seq` the next delivery receives. From divergence
   on nothing is held: each live outcome is delivered as soon as it is ready (ties in invocation
   order), whether or not cache entries remain.
5. When every log entry is delivered, held live outcomes are released in arrival order and the run
   continues as a normal run.
6. Replayed outcomes cost nothing; the engine does not change `BudgetSnapshot`. Restoring spent
   totals on resume is `P5-02`'s and `P5-04`'s job. Replayed calls skip the budget check but count
   toward `max_agents` (section 6.1 steps 7 to 9), so a resumed run restored at or above its budget
   still replays every logged call, and only its first live call is refused.

Why this works: in the earlier run, every logged outcome was delivered before any outcome that is
not in the log (which had not finished). Holding live outcomes until the log is exhausted reproduces
the original delivery order, so the original interleaving, invocation order and occurrences repeat
exactly. Rule 4 prevents a deadlock when the script has changed.

Limits that remain, documented in the script API: after a divergence (cache mode), two identical
calls with different stored results may be handed out in a different order than before; and a
script whose control flow reads `budget.spent()` may diverge.

```rust
pub struct RunHandle { pub events: tokio::sync::mpsc::UnboundedReceiver<EngineEvent>,
                       pub cancel: tokio_util::sync::CancellationToken,
                       pub outcome: tokio::sync::oneshot::Receiver<RunOutcome> }
pub fn spawn(parsed: ParsedScript, config: EngineConfig, backend: std::sync::Arc<dyn AgentBackend>,
             resolver: std::sync::Arc<dyn WorkflowResolver>) -> RunHandle;
```

Notes:

- `run` may return a future that is not `Send` (the QuickJS runtime lives on one thread). Tests call it
  on a current-thread Tokio runtime. `spawn` starts a dedicated operating-system thread with its own
  current-thread Tokio runtime (time enabled) and runs `run` there; `P5-06` uses `spawn`.
- `AgentBackend::run_agent` returns a `Send` future. It must not assume which Tokio runtime polls it,
  beyond Tokio's timers and channels being available.
- `MapResolver` answers `WorkflowRef::Name(n)` only from `with_name` entries and
  `WorkflowRef::ScriptPath(p)` only from `with_path` entries; `Name("x")` and `ScriptPath("x")` never
  alias.
- The crate has a `mock` feature exposing `talaria_workflow::mock` (section 11) and
  `talaria_workflow::dry_run` (section 13). Neither is in the default feature set; tests enable
  `mock` through `required-features` or a dev-dependency on the crate itself.
- Suggested dependencies (verify current versions at build time): `rquickjs = { version = "0.14",
  features = ["futures", "loader", "macro"] }` (`loader` is required for `set_loader`; the resolver
  refuses everything, so enabling it adds no file or native-module loading), `tokio` (`rt`,

## 9. Events

```rust
#[derive(Clone, Debug, PartialEq, serde::Serialize, serde::Deserialize)]
#[serde(tag = "event", rename_all = "snake_case")]
pub enum EngineEvent {
    Started { meta: WorkflowMeta, warnings: Vec<String> },
    Phase { title: String, workflow_path: Vec<String> },
    Log { message: String, workflow_path: Vec<String> },
    AgentStarted { request: AgentRequest, replayed: bool },
    AgentFinished { call_id: CallId, completion_seq: Option<u64>, outcome: OutcomeKind },
    ChildStarted { workflow_path: Vec<String>, meta: WorkflowMeta, warnings: Vec<String> },
    ChildFinished { workflow_path: Vec<String>, ok: bool },
    ReplayDiverged { at_seq: u64 },
    Finished { outcome: RunOutcomeKind },
}
#[serde(tag = "kind", rename_all = "snake_case")]
pub enum OutcomeKind { Completed, Failed { reason: String }, Skipped, Aborted, Abandoned }
#[serde(rename_all = "snake_case")]
pub enum RunOutcomeKind { Completed, Failed, Aborted }
```

`completion_seq` is set for delivered outcomes (`completed`, `failed`, `skipped`) and is `null` for
`aborted` and `abandoned`, which were never delivered. `WorkflowMeta` and `PhaseMeta` serialise with
snake_case field names (`when_to_use`).

Exact JSON (one line each; the digest shortened here as `D`), asserted by test 33:

```json
{"event":"agent_finished","call_id":{"digest":"D","occurrence":0},"completion_seq":3,"outcome":{"kind":"completed"}}
{"event":"agent_finished","call_id":{"digest":"D","occurrence":1},"completion_seq":4,"outcome":{"kind":"failed","reason":"provider error"}}
{"event":"agent_finished","call_id":{"digest":"D","occurrence":2},"completion_seq":5,"outcome":{"kind":"skipped"}}
{"event":"agent_finished","call_id":{"digest":"D","occurrence":3},"completion_seq":null,"outcome":{"kind":"aborted"}}
{"event":"agent_finished","call_id":{"digest":"D","occurrence":4},"completion_seq":null,"outcome":{"kind":"abandoned"}}
{"event":"child_finished","workflow_path":["name:child@0123456789ab"],"ok":true}
{"event":"replay_diverged","at_seq":7}
{"event":"finished","outcome":"completed"}
```

Ordering guarantees: `Started` first; `Finished` last and exactly once; each `AgentFinished` after its
`AgentStarted`, exactly once; each `ChildFinished` after its `ChildStarted`, exactly once; events of
one sequential lane of one workflow instance in program order; `AgentFinished` events with a
`completion_seq` in increasing `completion_seq` order. A send error (receiver dropped) is ignored:
the run continues.

## 10. Errors a script or a caller can see

| `name` | Raised by | Message (prefix; tests match with `contains`) |
|---|---|---|
| `DeterminismError` | `Date.now()`, `Date()`, `new Date()`, `Math.random()` | "`<what>` is unavailable in workflow scripts (it would break resume)" |
| `WorkflowOptionError` | bad `agent` prompt or option, bad `parallel`/`pipeline`/`phase`/`random`/`workflow` argument, unconvertible child `args` | "agent(): unknown option `modle`; allowed: label, phase, schema, tier, model, provider, effort, profile, toolsets, skills, isolation, maxTurns, stallMs" and similar |
| `SchemaError` | malformed `schema` | "agent(): schema root must have type 'object'" and similar |
| `AgentLimitError` | 1,001st agent | "the run has started 1000 agents, the limit" |
| `ItemLimitError` | 4,097 items | "parallel(): 4097 items, the limit is 4096" |
| `BudgetExhaustedError` | spent ≥ total | "token budget exhausted (spent 120000 of 100000)" or "money budget exhausted ..." |
| `NestedWorkflowError` | `workflow()` in a child | "workflows nest one level only" |
| `WorkflowNotFoundError` | resolver `NotFound`/`Unreadable` | "workflow `x` not found" |
| `WorkflowScriptError` | child parse, import or syntax error; unconvertible child result | "workflow `x` line 3: ..." |
| `SyntaxError`, `TypeError`, others | the script itself | QuickJS's own message |

All of the above are catchable. Caller-visible outcomes: `ScriptError` from `parse_script` (nothing
has run); `RunOutcome::Failed` for an uncaught error, a run-ending limit (memory, stack, synchronous
slice), the import backstop (name `ImportNotAllowed`), an invalid budget snapshot, or a result that
fails strict conversion; `RunOutcome::Aborted` for a cancel or a backend abort. A return value of
`undefined` is `Completed { result: null }`.

## 11. The mock backend

`talaria_workflow::mock::MockBackend` implements `AgentBackend` for tests. It mocks this crate's own
trait, not Hermes, so the rule "mocks come from the contract or recorded fixtures" is met by
construction; it must not grow Hermes method names or fields.

Rules file (JSON), also accepted by the dry-run example:

```json
{
  "default": {"text": "ok"},
  "rules": [
    {"match": {"prompt_contains": "Review"}, "outcome": {"object": {"findings": []}}, "delay_ms": 200},
    {"match": {"label": "verify-2"}, "outcome": {"failed": "provider error"}},
    {"match": {"prompt_contains": "skip me"}, "outcome": "skipped"},
    {"match": {"prompt_contains": "lost"}, "outcome": {"abort": "outcome unknown after a restart"}}
  ],
  "budget": {"tokens_total": null, "tokens_per_agent": 1000, "money_total": null, "money_per_agent": 0.0}
}
```

- `match` keys (all given keys must match): `prompt_contains`, `prompt_equals`, `label`, `phase`,
  `tier`, `model`, `occurrence`. The first matching rule wins. No match and no `default`: `Failed {
  reason: "mock: no rule matched" }`. Matching on `label` or `phase` exists for test convenience only;
  production backends must not let them change results (section 7.1).
- `delay_ms` (a non-negative integer) is applied with `tokio::time::sleep`, so paused-time tests are
  exact.
- Outcomes: `{"text": s}` gives `Completed(String)`, `{"object": v}` gives `Completed(v)`,
  `{"failed": r}`, `"skipped"`, `{"abort": r}`; exactly one form per rule.
- Budget: each `Completed` adds `tokens_per_agent` and `money_per_agent` to spent. Charges are
  non-negative; money values are finite and non-negative.
- Validation: `MockBackend::from_json(&str) -> Result<MockBackend, MockRulesError>`. Every object
  refuses unknown keys (`#[serde(deny_unknown_fields)]`). A rule with no outcome or two outcomes, an
  empty `match`, a negative or fractional delay, a negative or non-finite charge or total all give
  `MockRulesError` with a message naming the rule index and field. `MockRulesError` implements
  `std::error::Error` and `Display`.
- Builder, the stable API for later units. Every method takes `self` and returns `Self`, for
  chaining:
  `MockBackend::builder() -> MockBuilder`; `MockBuilder::default_outcome(self, MockOutcome) -> Self`,
  `rule(self, MockRule) -> Self` (rules keep the order added), `budget(self, MockBudget) -> Self`,
  `build(self) -> MockBackend`; `MockRule::new(MockMatch, MockOutcome) -> MockRule` and
  `MockRule::delay_ms(self, u64) -> Self`;
  `MockMatch { prompt_contains: Option<String>, prompt_equals: Option<String>, label: Option<String>,
  phase: Option<String>, tier: Option<String>, model: Option<String>, occurrence: Option<u32> }`
  (`Clone, Debug, Default`); `MockOutcome::{Text(String), Object(serde_json::Value), Failed(String),
  Skipped, Abort(String)}` (`Clone, Debug, PartialEq`); `MockBudget { tokens_total: Option<u64>,
  tokens_per_agent: u64, money_total: Option<f64>, money_per_agent: f64 }` (`Clone, Copy, Debug,
  PartialEq, Default`; the default is no totals and zero charges). A builder without a default
  outcome behaves like a rules file without `default`. `build` panics, with the message `from_json`
  would give, on a negative or non-finite money value or an empty `MockMatch`, the only malformed
  cases the builder's types can express.
- Inspection: `requests() -> Vec<AgentRequest>` in arrival order; `calls() -> Vec<(AgentRequest,
  AgentOutcome)>`, one entry per request whose future ran to completion, in completion order, with
  the outcome the mock returned (a future dropped first appears in `requests()` only);
  `max_in_flight() -> usize`; `in_flight() -> usize`.
- Building a `ReplayLog` in tests (test 39): take run 1's `AgentFinished` events that have a
  `completion_seq`, in `completion_seq` order, and pair each `call_id` with the outcome `calls()`
  recorded for the request with that `call_id`. Events carry only the outcome kind, so `P5-02` must
  likewise record outcome values itself, at the backend layer. The in-flight count is released by a drop guard inside the returned
  future, so a future dropped by an abort, a cancel or abandonment still decrements it.

## 13. The dry-run example

`crates/talaria-workflow/examples/dry_run.rs` is a thin wrapper over `talaria_workflow::dry_run`
(feature `mock`). It is a developer and acceptance tool; `P5-06` owns the real `talaria workflow`
commands and may later fold this in as `--dry-run`.

```rust
pub struct DryRunOptions { pub script: std::path::PathBuf, pub mock: std::path::PathBuf,
                           pub args: Option<serde_json::Value>, pub max_sync_ms: Option<u64>,
                           pub seed: u64 }
pub fn parse_args(argv: &[String]) -> Result<DryRunOptions, String>;   // Err → exit 64
pub async fn run(opts: &DryRunOptions, out: &mut dyn std::io::Write,
                 cancel: tokio_util::sync::CancellationToken) -> i32; // the exit code
```

```text
cargo run -q -p talaria-workflow --features mock --example dry_run -- \
  <script.js> --mock <rules.json> [--args '<json>'] [--max-sync-ms <n>] [--seed <n>]
```

- `parse_args` receives the arguments after the program name (the example's `main` passes
  `std::env::args().skip(1)`). Grammar: exactly one positional argument, the script path, before or
  after the flags; `--mock <path>` is required; `--args <json>` (must parse as JSON),
  `--max-sync-ms <n>` (positive integer) and `--seed <n>` (`u64`, default 0) are optional; each
  flag at most once; `--flag=value` is not accepted. A missing script, a missing `--mock`, an unknown
  or repeated flag, a flag without its value, a second positional or an unparsable value is `Err`
  (exit 64). `parse_args` does not touch the file system.
- `run` writes one JSON line per `EngineEvent` (the serde form of section 9), then a final line
  `{"result": ...}`, `{"failed": {...}}`, `{"aborted": "..."}` or
  `{"refused": "<ScriptError message>"}`. The `failed` object is `ScriptFailure` serialised by its
  derive, keys in declaration order and `None` as `null`:
  for example `{"failed":{"name":"DeterminismError","message":"…","line":4,"column":1,"stack":"…","workflow_path":[]}}`.
  When `run` itself finds a usage error (unreadable script, malformed rules file) it writes nothing
  to `out`, prints the message to standard error and returns 64.
- `started_at_ms` is fixed at `0` and the seed defaults to `0`. With the delivery rule of section 7.2
  (ties in invocation order) and the delays in the fixture rules files, output is
  byte-for-byte repeatable for the fixtures below; a rules file whose delays race closely in real
  time is not guaranteed repeatable.
- Child workflows: a name `x` resolves to `x.js` in the script's directory, a `scriptPath` relative to
  the script's directory.
- Exit codes: 0 completed; 1 failed; 2 refused before running; 3 aborted; 64 usage error (bad
  arguments from `parse_args`; unreadable script or malformed rules file from `run`).
- The example binary maps Ctrl+C (SIGINT) to the cancel token; `run` then prints
  `{"aborted": "cancelled"}` and returns 3.

## 15. Design reasoning

- **Content-plus-occurrence identity with ordered replay, not call order alone or a call path.**
  QuickJS has no asynchronous context propagation that this unit can rely on, so the engine cannot
  tell which `parallel` thunk or `pipeline` item an `agent()` call after an `await` belongs to.
  Content identity survives edits to unrelated parts of the script (Claude Code's call-order replay
  re-runs every agent after the first changed one). Content identity alone is not enough: two
  identical calls with different results could be handed to the wrong items on resume (a reviewer
  reproduced this with the earlier draft's algorithm). Ordered replay (7.2) makes the invocation
  order, and so the occurrences, repeat exactly for an unchanged script. Rejected alternative:
  QuickJS promise hooks (`set_promise_hook`) to carry a branch path across awaits; their behaviour
  for async functions was not verified, and ordered replay needs no engine internals.
- **Per-instance parameter bindings for child workflows.** Binding `agent`, `phase` and the rest as
  parameters of the child's function makes attribution lexical, so concurrent children cannot be
  confused. A mutable "current child" global was rejected: it is wrong after the first `await`.
- **A hand-written literal parser for `meta`, not a JavaScript parser crate.** The grammar is tiny,
  and a hand-written parser gives exact line and column errors and no new heavy dependency. Evaluating
  the literal in QuickJS was rejected: it would run code before the header is known to be pure.
- **A token scan for `import()`, with a loader backstop.** Claude Code refuses such scripts before
  running; a scan gives that behaviour and a located error. The scan's regular-expression rule is a
  heuristic, so the refusing loader turns any miss into a run failure rather than a catchable error.
- **A wrapped async function, not an ES module.** Claude Code scripts use top-level `return`, which
  is a syntax error in a module. Blanking the header keeps lines exact; line 1 columns are corrected
  by the known prefix length.
- **No width limit in the engine.** `P5-04` owns scheduling, including halving the global cap on rate
  limits. A second semaphore inside the engine would make the cap impossible to change at run time and
  would collide with `P5-04`'s files.
- **Endings outside JavaScript.** A cancel implemented as a thrown exception would be swallowed by
  `parallel`'s null-on-throw and by any `try`/`catch`, so a stopped run would keep going.
- **Abandon unawaited work at the end.** Waiting for it would let a finished script keep spending;
  failing the run would punish a harmless pattern. Abandoning with an explicit event keeps every
  start paired with a finish for the journal and the progress view.
- **Strict option checking.** A misspelt option (`modle`) would otherwise silently run the agent on
  the default model and spend money on the wrong thing. `stallMs` is the exception: it is a known
  Claude Code option, so accepting it as a no-op keeps Claude Code scripts transferable.
- **Strict JSON conversion.** `JSON.stringify` silently turns `NaN` into `null` and drops functions;
  a workflow result or child input changed silently is worse than a located failure.
