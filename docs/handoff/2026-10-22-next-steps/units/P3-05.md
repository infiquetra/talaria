## 0. What this unit is, in one paragraph

Two kinds of work run beside a Hermes conversation without being part of it. The first is a background process: the agent ran a shell command with the `terminal` tool and `background=true` (a dev server, a watcher, a long test run), and Hermes keeps it running after the tool call returns. The second is a `/bg` task: the operator typed `/bg <prompt>`, and Hermes ran that prompt on a fresh agent, detached from the conversation, and reports the answer later. The Python Talaria lost every `/bg` answer ([02-current-state.md](../02-current-state.md#what-a-hands-on-drive-found), finding 2), and it never showed background processes at all. This unit adds both to the Rust client: a pure model in `talaria-core` (`talaria_core::background`), a small service in `talaria-app` (`talaria_app::background`), a live-region section and a full-screen `/processes` overlay in `talaria-tui`, and three local commands: `/bg` (alias `/background`), `/processes` and `/stop`.

### 4.1 How calls run and how replies find their session

This follows `P2-05`'s `SideService` (its specification, section on the app service): effects carry no session id inside the pure core, because each `BackgroundWork` lives inside one `SessionState`.

1. The app calls `P1-05`'s `update` for one session and receives that session's `Effect::Background(effect)` values. It knows the session id because it made the call.
2. For `ListProcesses`, `KillProcess`, `StopProcesses` and `StartBackground`, the app spawns a task (`tokio::spawn` or the runtime `P1-12` uses) that runs `BackgroundService::execute(session_id, effect, now)`. The service holds a clone of `P1-02`'s `Client` (cheap to clone; `P1-02` specification section 7). That `Client` survives a reconnect (`P1-03` replaces the connection under it), so the app keeps one service, built once from the foreground client; if the merged app instead builds a new `Client` on reconnect, it builds a new service from it at the same point. It never awaits the call on the input loop; a 60-second `process.stop` must not freeze the screen.
3. The task is tagged with `(session_id, connection_generation)`, read when the task is spawned. The connection generation is `P1-02`'s `Client::generation()`, which rises each time `P1-03` replaces the connection (check the merged name). If the merged app has no such number, add one `u64` in `sessions.rs` (a minimal touch), raised on every reconnect; if that is not possible as a minimal touch, stop (issue stop condition 9).
4. The returned event goes back through the app's single channel. The app delivers it as `Event::Background(event)` to the session with that id, whether or not it is still foreground. If no state exists for that id any more, or the generation is older than the current one, the event is dropped.
5. A dropped reply would leave in-flight flags set forever. So whenever the app re-attaches sessions after a reconnect it sends `Attached` to each of them, which resets in-flight state (section 5.7); only the foreground one lists.
6. `InsertNotice` and `InsertResult` are applied by the session module itself (section 4). `Interrupt` maps to `P1-05`'s interrupt. `Log` is written to the app's log. `Signal` is ignored in this unit. `Redraw` marks the frame dirty.

## 5. State rules for processes

### 5.1 Status

`status_of` reads one listed entry:

| `status` | `completion_reason` | `exit_code` | `ProcessStatus` | Label |
|---|---|---|---|---|
| anything except `exited` | any | any | `Running` | `running` |
| `exited` | `killed` | any | `Killed` | `killed` |
| `exited` | `lost` | any | `Lost` | `lost` |
| `exited` | `failed_start` | any | `FailedToStart` | `failed to start` |
| `exited` | other or null | `0` | `Done` | `exit 0` |
| `exited` | other or null | `n` not 0 | `Failed { code: n }` | `exit n` |
| `exited` | other or null | null | `Ended` | `ended` |

A `status` value other than `running` or `exited` counts as `Running` and emits `BackgroundEffect::Log { text: "unknown process status <value> for <id>" }` once per session (a private flag); the app writes it to its log, never on screen. Desktop's rule (exit code 0 or null is done) differs: Talaria shows `ended` when the code is unknown, because "done" would claim a success nobody saw. Missing keys take the `from_entry` defaults of section 4 (a missing `status` is `running`, the contract's default); extra keys are ignored, because `ProcessEntry` is open (H2).

### 5.2 Reconciling a list reply

Applied to `Listed { request, processes, now_ms }` only when `request` is the list request this session has in flight; older replies are dropped silently. (Replies from an older connection generation never reach the core: the app drops them, section 4.1.)

1. For each entry in reply order: an id not known adds a row at the end (`first_seen_ms = now_ms`); a known id updates `command`, `status`, `exit_code`, `started_epoch_s`, `exited_at_s` in place and resets `misses` to 0. `output_tail`, when present and non-empty, goes through `merge_snapshot` (section 6.2); a chunk buffer held for this id under "pending unknown" (section 6.3) is moved to the row first.
2. A row whose status goes from `Running` to anything else sets `finished_seen_ms = now_ms` and emits `Signal(ProcessFinished { id, status })` once.
3. A known row absent from the reply: a finished row is removed at once (Hermes pruned it). A running row increments `misses`; at 2 it is removed. A removed row's output buffer is dropped.
4. Ids in the dismissed set that the reply no longer contains are forgotten (Desktop's rule, D2). Dismissed ids present in the reply stay hidden.
5. `ListState` becomes `Fresh { at_ms: now_ms }`.
6. `version` rises by one if and only if any visible field changed (a row added, removed, status, exit code, command, output appended, list state from stale to fresh). An identical reply changes nothing and emits nothing.

### 5.3 Live line

`live_line` is the text the live-region row shows after `last:`. It is recomputed from `ProcessOutput::last_line()` on `Clock` only (at most once a second), never on a chunk. A chunk raises `version()` only while the overlay is open and the chunk is for the overlay's selected process; with the overlay closed a chunk changes the buffer but not `version()`. So output chunks never cause a frame while the overlay is closed (budget "idle: zero frames when nothing changes", and keystroke latency while a process is chatty). While the overlay is open, the app also redraws on every `Clock` (section 9), so elapsed times repaint each second.

### 5.4 Order

Overlay order: running rows first, oldest `started_epoch_s` first (longest running first); running rows with no start time come after those with one, oldest `first_seen_ms` first. Then finished rows, newest `exited_at_s` first; finished rows with no exit time come after those with one, newest `finished_seen_ms` first. Ties by id. Wall-clock seconds and app milliseconds are never compared with each other. The selection follows the selected id, not the position, so a re-sort never moves the cursor to another process. When the selected row is removed, the selection moves to the row that now has its position, else the last row.

### 5.5 Kill and stop

- `KillRequested { id }` on a running row whose `kill` is not `Sending`: allocate a request id, set `kill = Sending`, emit `KillProcess`. On any other row: set the row's note to the text in 10.3 and emit nothing.
- `KillReplied`: `Killed` sets the status to `Killed` and `exit_code = -15` at once (H11); every outcome, `Killed` included, sets `kill = Note(kill_note_text(outcome))`, so `Killed` shows `Killed. Hermes will not tell the agent about this process's exit.` (10.3). Every outcome then emits `ListProcesses` (a refresh), even a failure, because the outcome of an unknown or failed call is unknown.
- `StopAllRequested` (overlay) and `StopCommand` (`/stop`): `StopCommand { turn_running: true }` first emits `Interrupt`, then `StopProcesses`; with `turn_running: false` only `StopProcesses`. `StopAllRequested` never interrupts the turn (the overlay's `S` is about processes only). The in-flight stop remembers its `StopOrigin`. `StopReplied` then emits a refresh and shows the `stop_notice_text` text: origin `Command` as an `InsertNotice` (a transcript cell); origin `Overlay` only as `overlay_note()` (the overlay's note row, because the transcript is hidden while the overlay is open). The overlay note is cleared by the next key in the overlay or when it closes.
- Only one kill per process and one stop per session can be in flight. A second kill of that process while its kill is in flight sets the note `Already killing this process; waiting for Hermes.`; a second stop while a stop is in flight sets the note `Already stopping; waiting for Hermes.`. Neither emits anything.
- **The overlay has one note row.** It draws, in this order of priority: the view's own note (a confirm prompt or a refusal the view made without an intent, such as `x` on a finished row), which the view clears on the next key; else `overlay_note()`, which the core clears on the next intent event (`KillRequested`, `StopAllRequested`, `Dismiss`, `RefreshRequested`, `Selected`) and on `OverlayClosed`; else the selected row's `KillState::Note`, which stays until that row's next `KillRequested` or until the row is removed. Only one note shows at a time.

### 5.6 Dismiss and close view

`Dismiss { id }` on a finished row adds the id to the dismissed set and hides it in the overlay and the live row; on a running row it sets the note in 10.3. `TerminalClosed { process_id }` sets `agent_closed_view = true` on that row (or remembers the id until the row appears); it never changes the status, never removes the row and never stops polling.

### 5.7 `Attached` and in-flight state

`Attached` means the app has (re)established this session's subscription. It:

1. clears `ListState::Stopped` (any reason; a reconnect can reach a different gateway), leaving `Never` or the last `Fresh`/`Stale` state;
2. forgets a list or stop in flight (its reply, if any, came from a replaced connection and is dropped by the app), and clears the "again" flag;
3. turns every row whose `kill` is `Sending` into `Note("Hermes did not confirm. Refreshing the list.")`;
4. turns every `Starting` `/bg` task into `ReplyLost` (its reply is lost; its answer can still be matched, rule 7.2 step 4), then turns held early results into `Elsewhere` cells only if no task is `Starting` any more;
5. emits `ListProcesses` only when the session is already foreground (a reconnect); on launch and on a switch the following `ForegroundChanged { foreground: true }` lists (section 9).

### 5.8 Private fields of `BackgroundWork`

Fields are private; tests observe them only through `update`, the accessors and the effects. Suggested fields, so a builder does not have to invent homes: `rows: Vec<ProcessRow>`; `outputs: HashMap<ProcessId, ProcessOutput>`; `output_total_chars: usize`; `pending_unknown: Vec<(String, ProcessOutput)>` (at most 8); `closed_view_ids: HashSet<String>`; `dismissed: HashSet<ProcessId>`; `selected: Option<ProcessId>` (set by `Selected`, kept after the overlay closes); `overlay_open: bool`; `overlay_note: Option<String>`; `foreground: bool`; `list_state: ListState`; `list_in_flight: Option<RequestId>`; `list_again: bool`; `last_list_sent_ms: Option<u64>`; `last_unknown_list_ms: Option<u64>`; `stop_in_flight: Option<(RequestId, StopOrigin)>`; `bg_tasks: Vec<BgTask>`; `early_results: VecDeque<(String, String)>` (at most 16); `shown_task_ids: HashSet<String>`; `unknown_status_logged: bool`; `next_request: u64` (or `P2-05`'s allocator if it exposes one); `version: u64`.

## 6. The output buffer

### 6.1 Chunks

`push_chunk(chunk)` appends `chunk` to `raw`. When `raw` exceeds `OUTPUT_CAP_CHARS` scalar values, the front is cut so that `raw` keeps the last `OUTPUT_CAP_CHARS` characters and then starts after the first `\n` in the kept text (if there is one in the first 4,096 kept characters); `trimmed_front` becomes true. Cutting is by `char`, never inside a UTF-8 sequence. The snapshot fence (6.2) is left as is.

### 6.2 Snapshots

`merge_snapshot(tail)` follows Desktop's rules (D4), with `body = raw`:

1. `tail` empty: nothing.
2. `tail == fence`, or `tail == body`, or `body` ends with `tail`: set `fence = tail`; nothing else.
3. `tail` starts with `body`: set `fence = tail`, append `tail[body.len()..]` to `raw`. When `body` was empty and `tail` has exactly 32,768 characters, set `trimmed_front = true` (Hermes cut the front).
4. `tail` starts with `fence` (and `fence` non-empty): set `fence = tail`, append `tail[fence_old.len()..]`.
5. Otherwise (Hermes's rolling tail slid, or Talaria missed chunks): reset `raw = tail`, `fence = tail`, `trimmed_front = true` when `tail` has 32,768 characters (Hermes cut it).

Bytes and characters: the slices in cases 3 and 4 use byte offsets (`str::len()` of a whole prefix, or `strip_prefix`), which always fall on a character boundary because the prefix is a complete string. Caps and the 32,768 test count characters (`chars().count()`), never bytes. Never slice at a character count.

Cases 3 and 4 then apply the cap as in 6.1. Property (test 13), with an exact expected value. Generator: 1 to 400 chunks; chunk `i` is the marker `\u{1}<i>\u{2}` followed by 0 to 200 characters drawn from ASCII letters, multi-byte letters and `\n` (never `\u{1}`), so no chunk boundary can be confused with another; `k` in `0..=n`; cases where `F` has exactly 32,768 characters are discarded (test 8 covers that boundary). Let `F = concat(c)` and `s` = the last 32,768 characters of `F`. Push `c[..k]`, then `merge_snapshot(s)`. Expected: if `F` has fewer than 32,768 characters, or `k == n`, then `raw == F` and `trimmed_front == false`; otherwise `raw == s` and `trimmed_front == true`. (`F` stays under 80,000 characters, so the 256,000 cap never applies here; test 7 covers the cap.) Test 14: the starting state is built through `update` only: `Attached`, `ForegroundChanged { foreground: true }`, then a generated list reply `L0` (0 to 10 entries) applied to the list request that emitted. Then a generated reply `L` (0 to 20 entries with random ids from a pool of 30, random statuses and tails). Before each apply, send `RefreshRequested` and take the request id of the `ListProcesses` it emits, so each apply is accepted as the reply in flight (otherwise the second apply is dropped for its request id and the test passes vacuously). Assert: after applying `L` a second time with its own fresh request, `rows()` (collected) and `version()` equal their values after the first apply, and the second apply returns no effect. Generate `L` so that every id that is running in `L0` also appears in `L` (finished `L0` rows may be absent; the first apply removes them), so the two-miss rule (5.2 step 3) cannot change the second apply.

### 6.3 Chunks for ids not yet listed

A chunk whose `process_id` matches no row goes to a pending buffer for that id (capped like a row's output). At most `MAX_PENDING_UNKNOWN` ids are held; the least recently written is dropped first. The first such chunk, and any later one at least `UNKNOWN_CHUNK_LIST_MS` after the previous list request, emits `ListProcesses` (only for the foreground session, section 9). When a list reply contains the id, the pending buffer becomes the row's output before the snapshot is merged.

### 6.4 Memory and drawing

Outputs are bounded per session by `OUTPUT_TOTAL_CHARS` and `MAX_TRACKED_OUTPUTS`: when either is exceeded, the output of the least recently written process is dropped (its row stays; its next snapshot re-seeds it), except the protected one: the process last named by `Selected`, whether or not the overlay is still open; before any `Selected`, the first row in overlay order while the overlay is open. `visible_tail(max_chars)` takes the last `max_chars` characters of `raw`, starts after the first `\n` in that slice when one exists, and passes the result through `P2-05`'s `clean_output` (removes CSI, OSC and other escape sequences, resolves `\r\n` and lone `\r`, drops trailing empty lines). Drawing then passes every line through `P1-06`'s `history::sanitize`, so control and bidirectional-override characters become visible stand-ins. The overlay asks for `max(65,536, rows * cols * 4)` characters.

## 7. `/bg` tasks

### 7.1 Round trip

1. `BgCommand { text }`: the text is trimmed. Blank: the usage notice (10.2), no effect. With no session attached, the command never reaches here: the app shows the no-session notice (10.2). Otherwise allocate a request id, add a `BgTask { state: Starting }`, emit `StartBackground { request, text }`. The text sent is the whole draft after `/bg ` (trimmed), including any lines entered with `P1-08`'s newline key.
2. `BgAccepted { request, task_id }`: the task becomes `Running { task_id, accepted_ms }`; an info notice `Background task <task_id> started. Its answer appears here when it finishes; it is not part of the conversation.`. If an early result (7.2) holds this `task_id`, it is applied at once.
3. `BgFailed { request, failure }`: `Refused`, `MethodMissing`, `Storage`, `NotSent` remove the task and add one error-level notice with `bg_failure_text`; `Unknown` and `Unreadable` turn it into `ReplyLost` and add a warning notice (10.2).
4. A `BgAccepted` or `BgFailed` for a request no longer pending is ignored silently.

### 7.2 Matching `background.complete`

For `BgCompleted { task_id, text }`, in order:

1. `task_id` already shown (a set of ids for which a result cell was inserted): ignore (a replayed or duplicated event).
2. A `Running` task with that `task_id`: insert `BackgroundCell { origin: Here, prompt: Some(text of the task) }`, remove the task.
3. Some task is still `Starting` (its reply has not arrived): hold `(task_id, text)` as an early result (at most `MAX_EARLY_RESULTS`; when a 17th arrives, the oldest held one becomes an `Elsewhere` cell at once). When no task is `Starting` any more (after the last reply, failure, or an `Attached` reset), every early result still held becomes an `Elsewhere` cell. This waits on any `Starting` task, not only a related one, on purpose: Talaria cannot tell which task a result belongs to until the replies arrive, and a reply normally arrives within milliseconds (Hermes replies right after starting the thread, H18). So an unrelated `/bg` still in flight can delay another window's result by that long; test 18 pins it (no `Elsewhere` cell before the waiting reply, one after).
4. Some task is `ReplyLost`: the oldest one takes it (`origin: Here`, its prompt); remove that task. Accepted risk: a result from another window can take a lost-reply task's prompt as its header; the cell's footer still shows the real `task_id`, so the mix-up is visible.
5. Otherwise: an `Elsewhere` cell with `prompt: None` (started in another window, or before this Talaria attached).

`text` starting with exactly `error: ` gives `BgResult::Failed(rest)`; any other text gives `Answer(text)` (an empty or whitespace-only text is an empty answer, drawn `(no answer)`). Every inserted cell emits `Signal(BgFinished { task_id, failed })` and adds the id to the shown set. A result never changes turn state: no change to the turn, its outcome, `execution_generation`, the interrupt latch or the queue.

### 7.3 Lifetime

There is no timeout and no cancel (H19). A running task shows its elapsed time until its result arrives. Quitting Talaria drops the rows. `background.complete` frames that `P1-03`'s replay delivers after a reconnect or on attach go through the same rules (7.2, in order): a shown id is ignored, a known running task takes its own result, a result is held while a task is `Starting`, the oldest `ReplyLost` task takes it, and anything else becomes an `Elsewhere` cell. A `ReplyLost` task whose result never arrives stays, with its row, until Talaria quits (as E-16); it counts toward the two task rows and the `+n more` row. A result published while no Talaria is subscribed and never replayed to one stays only in the replay ring and the side agent's own stored session (U3); Talaria does not recover it. This is an accepted gap, recorded as a decision (section 18). After a replay gap, `carry_over` keeps tasks, early results and the shown set.

| Command | Session needed | What happens |
|---|---|---|
| `/processes` | yes | Opens the overlay for the foreground session; emits `OverlayOpened`, which emits `ListProcesses` at once unless the list is `Stopped` (then the overlay shows the stopped text of 10.3 and sends nothing) |
| `/bg <prompt>` (alias `/background`) | yes | `BgCommand`; the composer is cleared and the line enters history (blank: usage notice, draft cleared) |

## 9. Poll schedule and wake-ups

`ListProcesses` is emitted only for the foreground session (the session on screen; `ForegroundChanged` sets it). While the list is `Stopped`, no trigger in this table lists; `OverlayOpened` and `RefreshRequested` then only show the stopped text. Only `Attached` clears `Stopped` (section 5.7).

| Trigger | Condition |
|---|---|
| `Attached` (create, resume, switch to it, reconnect re-attach) | clears `Stopped`; lists only when the session is already foreground (a reconnect) |
| `ForegroundChanged { foreground: true }` | always (unless `Stopped`) |
| `ToolCompleted { name }` | `is_process_tool(name)`: `terminal`, `process_manage`, or `process` (Desktop's name, kept for older and newer Hermes) |
| `TerminalOutput` for an unknown id | at most once per `UNKNOWN_CHUNK_LIST_MS` |
| `OverlayOpened`, `RefreshRequested` | always, when foreground |
| `KillReplied`, `StopReplied` | always, when foreground (a background session's reply updates its state and lists nothing) |
| `Clock` | `PROCESS_POLL_MS` since the last list request while any row is `Running`; `OVERLAY_POLL_MS` while the overlay is open and the selected row is `Running`; both stretched by the backoff below |

Event order (section 4.2): launch and switch send `Attached` and then `ForegroundChanged { foreground: true }`, a reconnect sends only `Attached`, so each gives exactly one `process.list` (test 41 counts them).

Single flight: while a list request is in flight, a trigger sets an "again" flag; when the reply or failure arrives, one more request is sent if the flag is set. Client timeouts: `process.list` 10 s, `process.kill` 30 s, `process.stop` 60 s, `prompt.background` 15 s (H27 bounds a kill at about 20 s with default settings; a stop timeout is an unknown outcome followed by a list). Each timeout is passed as `P1-02`'s `CallOptions.timeout`; its clock starts when `call` starts (`P1-02` REQ-5), not when the gateway reaches the request. Because the gateway socket runs one request at a time (H23), a list can wait behind a slow `process.stop` or `shell.exec` (`P2-05`) and time out at 10 s; that is a `Stale` list with the "did not answer" note, which is accurate and accepted. The single-flight rule keeps polls from piling up.

Backoff: after `k` consecutive failed list requests of one session (any `ListFailed` that leaves the list `Stale`), the `Clock` poll interval is `min(base * 2^k, MAX_POLL_BACKOFF_MS)`, where `base` is `PROCESS_POLL_MS` or `OVERLAY_POLL_MS` (5, 10, 20, 40, 60, 60 s ... for the 5 s base). A successful `Listed` or an `Attached` resets `k` to 0. Explicit triggers (`OverlayOpened`, `RefreshRequested`, a process tool, a kill or stop reply) still list at once. `Log` effects for list failures are emitted once per session per reason (a private set of logged reasons), not once per failure.

`next_deadline(now_ms)` returns the earliest of: the next whole second after `now_ms` while any running row, finished row still in the live window, or `Starting`/`Running`/`ReplyLost` bg task is shown in the live section, or while the overlay is open; `finished_seen_ms + FINISHED_ROW_MS` of each finished row in the live window; the next poll due time per the table; `now_ms + 33` while the overlay is open and its selected process received output since the last frame. It returns `None` when nothing is shown and nothing is due; then the app adds no wake-up and draws nothing. The app wakes at the deadline (`P1-12`'s tick, or one `sleep_until` in `app.rs` as `P2-05` added), sends `Clock { now_ms, wall_s }` (wall-clock seconds since the Unix epoch, for elapsed times against Hermes's `started_epoch`), and redraws only if `version()` changed, the live section's text changed, or the overlay is open (then every `Clock` redraws, so its elapsed times move).

## 10. Every user-visible text

`<cmd>` is the first line of the process command (`background process` when it is empty), cut to 60 characters with `…` in live rows, notes and notices (in the overlay's list row it is cut to the remaining width instead, 13.2); `<prompt>` is the first line of the `/bg` text, cut to 60 characters with `…`; `<n>` and `<m>` are integers; `<reason>` is the refusal reason cut to 64 characters.

Plural rule, for every text below: a count of exactly 1 takes the singular noun (`process`, `task`, `delegation`), any other count the plural (`processes`, `tasks`, `delegations`). ### 10.4 `format_elapsed`

The argument is whole seconds, floored: `floor(wall_s - started_epoch_s)` for a process, `floor((now_ms - accepted_ms) / 1000)` (or `sent_ms` while `Starting`) for a `/bg` task, and the same differences for "ago". `secs < 60`: `<s>s`; `secs < 3600`: `<m>m<ss>s` (`3m05s`); otherwise `<h>h<mm>m` (`1h02m`, `27h00m`). Negative differences (clock skew between Talaria and Hermes) clamp to 0.

Why not `P2-05`'s `format_duration(ms)`: that formatter shows tenths of a second below 10 s and whole seconds above, which suits shell commands that end in seconds. Background processes run for minutes or hours, where `3725s` would be unreadable. So a `/bg` row and a `!` shell row format the same 12 seconds alike (`12s`), but below 10 s the shell row shows tenths (`4.2s`) and this unit's rows whole seconds (`4s`).

## 11. Request and reply shapes

### 13.2 The `/processes` overlay

Regions from the top: row 0 header; list rows (at most `min(8, rows / 3)`, scrolling to keep the selection visible); a separator; the output pane (all remaining rows but two); a separator; one note row; one footer row. Worked example at 80 by 20:

```text
 Background processes · 2 running · 1 finished
 ▸ ● running         3m05s   sh tick.sh
   ● running           42s   npm run dev
   ✓ exit 0      ended 40s   pytest -q
 ──────────────────────────────────────────────────────────────────────────────
 $ sh tick.sh
   tick 183
   tick 184
   tick 185
 ...
 ──────────────────────────────────────────────────────────────────────────────
 Press x again within 3 s to kill: sh tick.sh
 ↑↓ select · PgUp PgDn scroll · End follow · x kill · S stop all · d dismiss · r refresh · esc close
```

List row: marker (`▸` on the selected row, else space), glyph (`●` running, `✓`, `✗`, `■`, `?`), the status label padded to 12 columns (`killing…` while a kill is in flight), the elapsed time while running or `ended <ago>` when finished, padded right-aligned to 10 columns, then `<cmd>` cut to the width. The selected row uses `BackgroundTheme::selected`. The output pane shows `$ <command first line>` (dim), then `visible_tail` wrapped at width minus 2 and indented two spaces, pinned to the bottom while following. The footer is cut from the right with `…` on narrow screens; `esc close` is never cut.

The overlay belongs to the foreground session. When the foreground changes (a switch, `P2-07`) or that session's state is dropped, the app closes the overlay first (`close_overlay`, then `OverlayClosed` to the session that owned it). Keys cannot switch sessions while it is open, but a non-key event can. An `Attached` re-list while the overlay is open simply refreshes it.

### 13.3 Keys in the overlay

| Key | Action |
|---|---|
| `↑` or `k` / `↓` or `j` | Previous / next row (no wrap); returns `Select(<new id>)` when the selection moved |

| `Home` or `g` | Top of the kept output (stops following) |
| `End` or `G` | Bottom, follow on |
