## 1. What this unit is

Claude Code's `claude -p "prompt"` runs one prompt without a screen and exits, so a shell script, a `Makefile` or a continuous-integration job can use the agent. Talaria gets the same: `talaria -p "prompt"` opens a Hermes session (new, the most recent one of this folder with `-c`, or one by id with `--resume <id>`), submits one prompt marked as a finite turn, waits for that turn to settle, prints the answer as plain text or as one JSON object, detaches, and exits with a code a script can branch on. It never draws a terminal user interface, never needs a terminal, and never asks a person anything.

The unit adds little protocol: the calls are the ones [`P1-12`](https://github.com/infiquetra/talaria/issues/209) already makes, plus `prompt.receipt`, `prompt.cancel` and the `finite` flag on `prompt.submit`. Its value is in four promises: the exit code tells the truth about the turn; nothing ever waits for a person who is not there; nothing that might have run is ever sent twice; and a stopped script stops its own turn and nobody else's.

## 3. Command line, exit codes and messages

### 3.1 Grammar

```text
talaria -p | --print [PROMPT] [--output-format text|json] [--timeout SECONDS]
        [ -c | --continue | --resume ID ]
        [--model NAME] [--provider NAME] [--effort LEVEL]      new session only (P1-12 (#209) rules)
        [--profile NAME] [--no-ensure] [--record PATH]
```

- `-p` is a flag (`--print` is its long form); `PROMPT` is one optional positional argument.
- **Validation is by hand, after clap.** Clap declares `PROMPT`, `--output-format` and `--timeout` as plain optional strings: no `requires`, no `value_parser` or `possible_values` restriction, no `conflicts_with` for them. After clap returns, `args.rs` runs `validate_print_options(&Cli) -> Result<(), UsageError>` on every launch, with or without `-p`, and prints the section 3.4 texts itself (exit 2, standard output empty). Order of checks: a print-only option without `-p` (prompt first, then `--output-format`, then `--timeout`; the first found is reported); then, with `-p`, `--output-format` (`stream-json` row first, then other values), `--timeout`, `--resume` without an id. Clap's own errors stay for what clap still checks (an unknown option, a missing option value, a prompt argument that is not valid UTF-8 when the field is a `String`): they keep clap's text and exit 2, and no test asserts their wording. Reason: test 2 asserts this unit's exact texts, which clap's `requires` and value parsers would replace.
- If [`P1-12`](https://github.com/infiquetra/talaria/issues/209)'s merged `Cli` already has a positional argument or subcommands that a `PROMPT` positional would shadow or conflict with, stop and report (issue, Stop conditions); do not rename or reorder them.
- `--output-format` takes exactly `text` (default) or `json`, lower case. `stream-json` is refused with its own message (phase 6, [`P6-05`](https://github.com/infiquetra/talaria/issues/278)).
- `--timeout` takes an integer number of seconds from 1 to 86400 (parsed by hand: only ASCII digits; a sign, a decimal point or a space is refused). It measures the whole run from process start.
- With `-p`, `--resume` needs an id (no list picker). `-c` and `--resume` exclude each other. `--model`, `--provider` and `--effort` are refused with `-c` or `--resume`, as [`P1-12`](https://github.com/infiquetra/talaria/issues/209) does.
- Every [`P1-12`](https://github.com/infiquetra/talaria/issues/209) rule for empty or blank values applies (`--resume ""` is a usage error).
- `--bench-replay` keeps [`P1-11`](https://github.com/infiquetra/talaria/issues/208)'s precedence in `main.rs` and is not combined with `-p` (unchanged; no test here).
- The flag letter differs from Hermes's own CLI, where `-p` names a profile. `talaria -p fixture` sends the word `fixture` as a prompt. The help text says so (failure modes).

### 3.2 The prompt text

Pure function `assemble_prompt(arg: Option<&str>, stdin: Option<&[u8]>) -> Result<String, PromptError>`:

| `PROMPT` | Standard input | Text sent |
|---|---|---|
| given | a terminal | `PROMPT` |
| given | not a terminal, empty | `PROMPT` |
| given | not a terminal, `S` | `PROMPT` + `"\n\n"` + `S` |
| absent | not a terminal, `S` | `S` |
| absent | a terminal | usage error `Empty` (exit 2, no read) |

- Standard input is read to its end only when it is not a terminal (`std::io::IsTerminal`). It is never read when it is a terminal.
- More than `MAX_STDIN_BYTES` (1,048,576) bytes of standard input: `StdinTooLarge` (stop reading at the limit plus one byte). The same cap applies to the assembled text: an assembled text longer than 1,048,576 bytes is `PromptTooLarge`, whatever its parts. Not valid UTF-8: `NotUtf8`. A NUL byte is allowed (JSON carries it).
- The assembled text is sent byte for byte: no trimming, no newline added or removed.
- When the assembled text is empty or only whitespace: `Empty`.
- An open pipe that never closes blocks the read. That is documented in `--help` ("pass `< /dev/null` when standard input is an open pipe you do not mean to send"). The signal handlers and the `--timeout` deadline are installed before the read (section 6.1), and the read runs on a blocking thread raced against them, so `--timeout` bounds it (exit 124) and `SIGINT` during it exits 130 with nothing opened. A timer on the first byte was rejected because it makes the result depend on timing.
- Without `--timeout`, nothing bounds the wait for the turn itself: a turn may legitimately run for hours. `--help` and `docs/formats/print-result-v1.md` say: "Without --timeout, talaria -p waits as long as the turn runs; set --timeout in unattended jobs." A default bound is an operator decision, not this unit's.

### 3.3 Exit codes

| Code | Status (`status` in JSON) | Meaning | Was anything run? |
|---|---|---|---|
| 0 | `completed` | The turn settled completed and its result does not say failed, partial or `completed: false`. | yes |
| 1 | `failed` | The turn ran and failed, stopped partway or hit a budget (`partial`, `completed: false`), or the owner settled it `failed`. | yes |
| 1 | `unknown` | The prompt may have been admitted but its outcome cannot be known: the connection dropped or the call timed out after `prompt.submit` was sent, the link failed before settlement, or the owner settled it `unknown`. Never resent. | maybe |
| 2 | (no JSON) | Usage error. Standard output stays empty. | no |
| 3 | `input_required` | The session waits for an answer from a person, or for an earlier turn with an unknown outcome, so this prompt cannot run. Talaria submitted nothing, or cancelled its own queued prompt. | no |
| 4 | `not_started` | Talaria could not start the turn: no gateway, profile not served, `oneshot` not offered, session create or resume refused, `prompt.submit` refused, or the text was taken as a voice stop phrase. Nothing was admitted, so a retry is safe. | no |
| 124 | `timed_out` | `--timeout` expired. Talaria cancelled or interrupted its own turn (or submitted nothing). | maybe partly |
| 129, 130, 143 | `interrupted` | `SIGHUP`, `SIGINT`, `SIGTERM`: Talaria cancelled or interrupted its own turn. | maybe partly |
| 130 | `interrupted` | The turn was interrupted by someone else (another viewer, a gateway restart or shutdown), or someone else withdrew our queued prompt before it ran. | partly, or no |

**Who decides the exit.** Two places, never both for one run:

- The state machine (section 6.3) decides, with fixed texts and without calling `judge`, every exit where no turn of ours settled: 2 (before the machine runs), 3 (blocked before submit, rule 1; our own withdrawal, rule 6), 4 (open failed, submit refused, voice stop, `oneshot` missing), 1 `unknown` when the settlement cannot be read (lost submit reply, submit reply `unknown`, link failure or session gone before our completion, withdrawal not confirmed, gap with a lost completion or an unreadable receipt), a second stop, and an expired stop budget or a link failure while stopping (except in `Reading`, where `judge` rules 2 to 5 judge the completion in hand).
- `judge` decides every exit where a settlement of ours is in hand (our completion, or a terminal receipt), and every stop exit (rule 1 below). Test 9 covers `judge` and `effective_outcome`; tests 10 to 20 cover the machine's own exits.

**The effective outcome.** `effective_outcome(completion_outcome, receipt_outcome, completion_status) -> Option<String>` (in `output.rs`) returns the completion's `outcome`; when the completion has none, the terminal receipt's `outcome`; when neither has one, the outcome derived from the completion's `status`: `complete` gives `completed`, `interrupted` gives `cancelled`, `error` or any other string gives `failed`, and a missing status gives `None`. The caller (the machine) passes the three values; `judge` receives the result of `effective_outcome` as its `outcome` argument and the completion's `status` as its `status` argument. `None` means "a settlement Talaria cannot read": `judge` rule 3 makes it 1 `unknown`, never 0. Hermes's own client uses the completion's outcome only and counts a missing one as failed (H16); Talaria reads the receipt next because the owner always sends `outcome` (H12, H30), so a missing one means a frame Talaria does not know, and the receipt is the durable record.

**Outcome over status.** The architecture's protocol rule says "a turn's outcome comes from `message.complete`'s status, never from an event's arrival". Its point is the second half: settle on the completion, not on timing. The owner derives `status` from `outcome` (H12: `complete` for completed, `interrupted` for interrupted, `error` for everything else), so `outcome` is the finer value and governs when both are present: outcome `unknown` with status `error` is JSON `unknown` (rule 3 runs before rule 4), never `failed`. The pull request notes this reading on the issue so the architecture document can be aligned later.

The order of judgement (mirrors H16, with Talaria's own stop first):

1. Talaria stopped the run (timeout or signal) and the turn did not settle on its own before the stop took effect, that is: nothing was submitted, the submit outcome is unknown, Talaria's cancel retired the admission, or the settlement is `cancelled`, `interrupted`, or missing: 124 or the signal code (129, 130, 143).
2. `result.interrupted` true, or outcome `cancelled`, or status `interrupted`: 130 `interrupted` by someone else. When our admission never started (no `message.start` of ours, no `started` reply) and Talaria sent no cancel, someone else withdrew our queued prompt: still 130 (Hermes's `chat -q` also gives 130 for `cancelled`), but with the "withdrawn by someone else" text of section 3.4, which says nothing ran.
3. Outcome `unknown`, or no effective outcome (`None`): 1 `unknown`.
4. `result.failed`, `result.partial` or `result.completed == false`, or outcome `failed`, or status `error`, or any outcome outside `completed` and `cancelled`: 1 `failed`.
5. Otherwise 0 `completed`. An empty answer with status `complete` is still 0, as `chat -q` does.

A turn that settled `completed` or `failed` before Talaria's stop reached Hermes is judged by rules 2 to 5: the script gets the real result, and the stop changes nothing.

### 3.4 Message texts owned by this unit

The built strings are stored once in `HeadlessResult`, so standard error and the JSON `error` and `warnings` carry the same text. The answer (`text`) is never cut or neutralised in JSON.

## 5. Request and result shapes

All frames are JSON-RPC 2.0 over the WebSocket. Placeholders in angle brackets.

### 5.1 Open

New session: [`P1-12`](https://github.com/infiquetra/talaria/issues/209)'s create with `source` changed:

```json
{"method":"session.create","params":{"request_id":"<32 hex>","source":"oneshot","cwd":"<absolute launch folder>"}}
```

`model`, `provider`, `reasoning` appear only when given (or filled by [`P2-06`](https://github.com/infiquetra/talaria/issues/230)'s saved default). `-c` and `--resume <id>`: [`P1-12`](https://github.com/infiquetra/talaria/issues/209)'s `session.resume` frames, unchanged (`latest: "tui"` with `workspace`; or `session_id`; both with `display_projection: true`).

### 5.2 Submit

```json
{"method":"prompt.submit","params":{"session_id":"<sid>","text":"<assembled text>","submission_id":"talaria-<16 hex>-1","finite":true}}
```

Exactly these four keys. Never `unattended` (a test asserts the key is absent), never `input_id`, never `clarify_batch`. Send it with `call_raw` and read the reply as JSON, because `{voice_stopped: true}` (H28) is outside the typed receipt. Receipt example:

{"admission_id":"<aid>","ref":{"profile_id":"<pid>","session_id":"<sid>"},"sequence":4,"status":"queued","outcome":null,"authority_epoch":1,"execution_generation":null}

### 5.3 Events of interest

```json
{"jsonrpc":"2.0","method":"event","params":{"authority_epoch":1,"execution_generation":7,"admission_id":"<aid>","type":"message.start","session_id":"<sid>","payload":{},"replay_epoch":"<e>","seq":12}}
{"jsonrpc":"2.0","method":"event","params":{"authority_epoch":1,"execution_generation":7,"admission_id":"<aid>","type":"message.complete","session_id":"<sid>","payload":{"text":"5555","content":"5555","admission_id":"<aid>","outcome":"completed","status":"complete"},"replay_epoch":"<e>","seq":19}}
```

Read the admission id from the envelope first, then from the payload. Read every payload field from raw JSON with absent-tolerant accessors (H13: the contract's payload type is closed and omits `admission_id`, `outcome`, `content`). The answer is `text`, else `content`, else `""`, as Hermes's own client does (H16); no warning when both are absent.

The completion that cancelling a queued admission publishes (H30), sent before the `prompt.cancel` reply:

```json
{"jsonrpc":"2.0","method":"event","params":{"authority_epoch":1,"admission_id":"<aid>","type":"message.complete","session_id":"<sid>","payload":{"text":"","content":"","admission_id":"<aid>","outcome":"cancelled"},"replay_epoch":"<e>","seq":13}}
```

Approval and question events (`approval.request`, `clarify.request`, `approval.settled`, `clarify.settled`) carry `prompt_id` and `execution_generation` in the payload ([`P1-09`](https://github.com/infiquetra/talaria/issues/206)'s facts, H26); their envelope carries the stamp of the admission that asked (H11). ### 5.6 The JSON result (Talaria's own format, version 1)

One line on standard output, then `\n`. Keys always present, in this order; an unknown value is `null`, never `0` or `""` (except `text`, which is `""` when there is none, and `warnings`, which is `[]`).

```json
{"type":"result","version":1,"status":"completed","exit_code":0,"text":"5555","session_id":"<id>","profile":"fixture","model":"minimax-m3.1-flash","provider":"ollama-cloud","admission_id":"<aid>","duration_ms":4210,"outcome":"completed","turn_exit_reason":"text_response(stop)","usage":{"input_tokens":812,"output_tokens":4,"cache_read_tokens":null,"cache_write_tokens":null,"reasoning_tokens":null,"total_tokens":816,"api_calls":1,"estimated_cost_usd":0.0,"cost_status":"<status>"},"warnings":[],"error":null}
```

- `status` is one of `completed`, `failed`, `unknown`, `input_required`, `not_started`, `timed_out`, `interrupted`; `exit_code` equals the process exit code.
- `text` is the live `message.complete.text`; after a gap, the stored `result.final_response` (with a warning).
- `session_id` is the `stored_session_id` of the opened session (`null` when none was opened).
- `model` and `provider` prefer the result's values (the model that actually answered) over the snapshot's `info`.
- `usage` holds exactly nine keys: the eight token and cost fields `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`, `reasoning_tokens`, `total_tokens`, `estimated_cost_usd`, `cost_status`, plus `api_calls`, in the order shown. They come from the receipt's `result`; each is `null` when absent or of the wrong type (a numeric string is not converted). They are the figures "as Hermes reports them" (U5).
- `error` is `{"what": "...", "next_step": "..."}` when the exit code is not 0, else `null`.
- `version` changes only when a key is removed or its meaning changes; adding a key keeps version 1. [`P6-05`](https://github.com/infiquetra/talaria/issues/278) (streaming JSON) reuses this object as its final record.

## 6. Behaviour step by step

### 6.1 Start-up sequence (`talaria-cli`)

1. `main.rs`: take `started = Instant::now()`; call [`P1-11`](https://github.com/infiquetra/talaria/issues/208)'s `bench_replay::parse_args` first (unchanged); parse with clap. If `-p` is set, call `print::run_print(&cli, started)` and exit with its code. Nothing else of [`P1-12`](https://github.com/infiquetra/talaria/issues/209)'s path runs: no terminal check, no terminal set-up, no first frame.
2. `run_print`: validate the print options (section 3.1 refusals, exit 2); resolve the launch folder and check a `--record PATH` ([`P1-12`](https://github.com/infiquetra/talaria/issues/209) failures map to exit 4 here).
3. Build the tokio runtime. Install handlers for `SIGINT`, `SIGTERM` and `SIGHUP` that send a `StopCause` into one channel, and start the `--timeout` deadline (if any) from `started`, sending `StopCause::Timeout` into the same channel. This happens before anything blocks.
4. When standard input is not a terminal, read it on a blocking thread (`spawn_blocking`) raced against the stop channel. A stop during the read ends the run at once with the stop's code (124, 129, 130 or 143) and `StopPoint::BeforeSubmit`: nothing was opened. Standard output: nothing in text mode; the one JSON line in JSON mode (status `timed_out` or `interrupted`, `session_id` `null`). Standard error, in both modes: the two failure lines of the matching "before the prompt was sent; nothing ran" row of section 3.4 (timeout or signal wording), no resume block. The blocked thread is abandoned: after writing, `run_print` calls `Runtime::shutdown_background()` on its tokio runtime instead of dropping it, because dropping a runtime waits for its blocking threads, and the read would hold the process open until standard input closed. `run_print` uses the same shutdown on every path, so no path can hang on the read. Test 39 checks it.
5. `assemble_prompt` (exit 2 on error, standard output empty).
6. Call `run_headless` with the stop channel.
7. Write standard output (text or JSON), then standard error, ignoring `BrokenPipe` on either; return `result.exit_code`.

### 6.2 `run_headless`

1. `ConnectionService::open` (the connection open: one `ensure` at most, `--no-ensure` honoured), raced against the stop channel. A stop drops this connection open at once and finishes with the stop's code and `BeforeSubmit` (nothing was opened, so there is nothing to detach). Failure: `NotStarted`, exit 4, the failure's own two lines.
2. `plan_headless`: [`P1-12`](https://github.com/infiquetra/talaria/issues/209)'s `plan` (option checks, effort, folder) then `source = "oneshot"` on a new session, after checking `describe.session_create.sources` contains `oneshot`. `HeadlessStartError::OneshotMissing` gives exit 4 with the section 3.4 text; `HeadlessStartError::Plan(f)` renders `f` with its own text and exit code.
3. `SessionService::open` (the session open). A stop that arrives during it is fed to the machine at once (`Stop`), but the session open itself runs to its end, bounded by the stop budget (the budget covers the session open; when it expires first, the service drops the call and feeds `StopBudgetExpired`), so a subscription that opens is detached. Failure: exit 4 with [`P1-12`](https://github.com/infiquetra/talaria/issues/209)'s text (`OpenFailed`). Success: feed `Opened` with `open_prompts` from the snapshot's `prompts` rows (`prompt_id`, `kind`, `execution_generation`, admission id where present) and `unknown_admissions` = the count of `snapshot.pending` rows with `status == "unknown"`.
4. Drive the machine: every `HeadlessEffect` is executed and its reply fed back as an input. Each `LinkEvent` for this session is mapped as follows; events for other sessions are ignored.

   | Link event | Machine input or service action |
   |---|---|
   | `Inbound { item: Event, .. }` (live or replayed) | `Event` (the link already removes duplicates) |
   | `Inbound { item: ServerRequest, .. }` | `ServerRequest` (below) |
   | `Gap(_)` | `Gap` |
   | the snapshot that `Recover` returns | `Recovered`, with our own `pending` row's `status` and `execution_generation` (`None` when the row is absent) and the snapshot's `prompts` |
   | `Reattached { subscription_id, .. }` | No input. The service keeps the new `subscription_id` for the detach, unless [`P1-12`](https://github.com/infiquetra/talaria/issues/209)'s `OpenedSession` already follows it (check the merged code). |
   | `SessionGone` | `SessionGone` |
   | `State(Failed { reason, next_step })` | `LinkFailed { reason, next_step }` |
   | `State(Closed)` not caused by this unit's own `close` | `LinkFailed { reason: "the connection closed", next_step: "Check the gateway with talaria, then check the session." }` |
   | `State(Reconnecting { .. })`, `State(Connected { .. })` | No input. Calls made while reconnecting fail with `NotConnected`, which reaches the machine as `CallReply::Failed` or `SubmitReply::Unknown`; events lost meanwhile arrive as a `Gap`. |

   Every server request for this session becomes `ServerRequest { request_key, kind }`; the service keeps its responder in a map by `request_key`. `RefuseServerRequest { request_key }` answers it with `Responder::fail(-32601, "talaria -p cannot answer server request: <kind>")`. A responder the machine never refuses is left unanswered: confirm in [`P1-02`](https://github.com/infiquetra/talaria/issues/199)'s merged code that dropping a responder sends nothing; if it sends an answer, keep the responders alive until exit instead.
5. On `Detach`: `SessionService::detach` (2 seconds, no `end_reason`), close the link. On `Finish`: return the result. On `ExitNow(result)`: return that result at once, skipping the detach.

### 6.3 The state machine

Phases: `Starting` (before `Opened`), `Submitting` (submit sent, no reply yet), `Waiting` (our admission is queued or started), `Reading` (our completion seen, receipt requested), `Stopping` (a stop is being carried out), `Done`.

```text
Starting ──Opened(prompts>0 | unknown>0)──► Detach, Finish(input_required 3)      [no Submit]
Starting ──Opened──► Submit ──► Submitting
Submitting ──Admitted(queued|started)──► apply held own events ──► Waiting
Submitting ──Admitted(terminal)──► own completion held? Reading : ReadReceipt (gap rules)
Submitting ──Admitted(unknown) | Unknown──► Finish(unknown 1)          [never resent]
Submitting ──Refused | VoiceStopped──► Detach, Finish(not_started 4)
Waiting ──own message.start──► record generation g, started
Waiting ──own message.complete──► ReadReceipt ──► Reading ──ReceiptRead──► Detach, Finish(judge)
Waiting ──foreign prompt open, ours not started──► Cancel (withdrawal)
Waiting ──Gap──► Recover ──► Recovered(queued|started: wait | unknown: Finish(unknown 1) | absent: ReadReceipt)
Waiting ──Stop──► started? Interrupt g : Cancel ──► Stopping
any ──second Stop──► ExitNow(code of the second stop)
any after a stop ──StopBudgetExpired──► Finish(stop code), no Detach
```

**Started, and our generation `g`.** Our admission is *started* from the first of: our own `message.start` (envelope admission id equals ours); a submit reply with status `started`; a `prompt.cancel` reply with status `started`; a `Recovered` input whose own `pending` row has status `started`. Once started, it stays started. `g` is recorded from the first source that carries a non-null value: the `message.start` envelope's `execution_generation`, the submit or cancel reply's `execution_generation`, the recovered `pending` row's `execution_generation`, or a receipt read under rule 13. A started admission whose `g` is still unknown (a `started` reply with `execution_generation: null`) is started for rules 6 and 8 (no withdrawal; server requests are ours), but cannot be interrupted until `g` is known: rule 13 handles that case. "Started" means the same thing everywhere in this unit, including REQ-11(b) and rule 8.

Rules, in the order a builder meets them:

1. **Opened.** If `open_prompts` is non-empty or `unknown_admissions > 0`: `Detach`, then `Finish(input_required, 3)` with the matching section 3.4 text; no `Submit`. Otherwise emit `Submit`. `OpenFailed`: `Finish(not_started, 4)`.
2. **Control events are never held.** `approval.request` and `clarify.request` add an `OpenPrompt` (keyed by `prompt_id`, with the envelope's admission id and the payload's `execution_generation`) to the open-prompt set in every phase; `approval.settled` and `clarify.settled` remove it (H31). A prompt is **ours** when its admission id equals ours, or its `execution_generation` equals our recorded generation; otherwise it is **foreign**. Before the submit reply, ownership is undecided and is judged right after the reply.
3. **Our prompts are declined.** Each prompt of ours is answered once with `DenyApproval` or `SkipClarify` (our generation, its `prompt_id`) and removed from the set; the warning of section 3.4 is added once per kind per run. H3 and H5 say this should not happen on a finite turn.
4. **Other events are held until the submit reply.** Events with an admission id (other than the control events) that arrive in `Submitting` are held in arrival order, at most `MAX_HELD_EVENTS`. One more drops all held events and marks a gap pending (the held list can no longer be trusted to contain our completion). A `Gap` in `Submitting` also marks a gap pending. Server requests in `Submitting` are held by `request_key`. Events without an admission id (session-level events such as `session.info`) are never held; the machine ignores them, because only the control events of rule 2 and our own events matter to it.
5. **Submit reply.** `Admitted`: record the admission id, status and generation (a `started` reply with a generation records `g`). Apply held events of our admission in order; drop the rest. If a gap is pending, emit `Recover`. Judge prompt ownership (rule 2) and held server requests (rule 8). Then by status: `queued` or `started`: `Waiting`. `terminal`: if our completion was among the held events, continue as for a completion (rule 9); otherwise `ReadReceipt` and finish by the gap receipt rules (rule 11). `unknown`: `Finish(unknown, 1)`, never resent. `VoiceStopped` or `Refused`: `Detach`, `Finish(not_started, 4)` (reason from `data.reason`, else `no reason given`). `Unknown` (a lost reply): `Finish(unknown, 1)`, never resent.
6. **Withdrawal (another person's question blocks the queue).** In `Waiting`, while our admission is not started (no `message.start` of ours, and the submit reply was not `started`) and the foreign set is non-empty: emit `Cancel` once. Then:
   - Our completion with outcome `cancelled` while not started is the cancel's own settlement (H30, published before the reply), or the `CancelReplied(Ok)` reply is `terminal` with outcome `cancelled`: `Detach`, `Finish(input_required, 3)`. Whichever comes second is ignored. The run never reads this as "interrupted by someone else".
   - `CancelReplied(Ok)` `terminal` with another outcome: the turn ended first; `ReadReceipt` and finish by rule 10.
   - `CancelReplied(Refused { reason: "stale_generation" })`, or `Ok` with status `started`: our turn has started; carry on waiting (no exit 3).
   - `CancelReplied(Refused { reason: "unknown_execution" })`, any other refusal, or `Failed`: `Detach`, `Finish(unknown, 1)` with the "Withdrawal not confirmed" text of section 3.4.
   - Exit 3 here is set by the machine, not by `judge` (section 3.3, "Who decides the exit"); the JSON `outcome` is `cancelled`.
7. **Our own events.** `message.start` of our admission records `execution_generation` as `g` and marks us started. Events of another admission change nothing except through rule 2.
8. **Server requests.** They carry no admission id (H32). While our admission is started and our completion is not yet seen, a server request for this session belongs to our turn: `RefuseServerRequest` at once, with the warning once per kind per run. In any other state (before the reply, queued, after our completion) it belongs to another viewer's turn: Talaria does not answer it and does not withdraw for it; the asking viewer answers it, or Hermes's own limit ends it (120 seconds for `sudo`). Held server requests are judged by this rule right after the submit reply.
9. **Our completion.** `message.complete` of our admission (not the cancel settlement of rule 6 or rule 13) records the answer (`text`, else `content`, else `""`), `status`, `outcome`, `warning` and `failure_reason`; emit `ReadReceipt`; phase `Reading`. A second completion of ours is ignored.
10. **Reading.** `ReceiptRead(Ok)` with `status == "terminal"`: take `result` and the receipt's `outcome` (used when the completion had none, section 3.3); `Detach`; `Finish(judge)`. `Ok` with another status, `Refused` or `Failed`: finish from the completion alone, with the usage warning.
11. **Replay gap** (in `Waiting` or `Stopping`; in `Reading` a gap changes nothing, because the completion is already in hand): emit `Recover`. `Recovered` first records our `pending` row's `status` and `execution_generation` (a `started` row marks us started and sets `g` when it was unknown), then replaces the open-prompt set with the snapshot's `prompts`. Snapshot prompt rows carry no admission id (H40), so a row is ours only when its `execution_generation` equals `g`. Then rules 3 and 6 run again over the new set, exactly as if each row had just arrived as an `approval.request` or `clarify.request`: each prompt of ours is declined (rule 3, without repeating a warning already given), and, in `Waiting` while we are not started, a non-empty foreign set emits `Cancel` (rule 6, at most once per run; skip it when a cancel was already sent). Then by our `pending` row: `queued` or `started`: keep waiting (the completion follows on the new subscription, H25). `unknown`: `Finish(unknown, 1)` with the "Hermes lost the end of this turn" text (Hermes's own rule, H25). Absent: `ReadReceipt`, then the gap receipt rules: `terminal` with `result`: the answer is `result.final_response`, with the stored-copy warning, judged normally. `terminal` without `result` and outcome `cancelled`, `interrupted` or `failed`: finish from the outcome with empty text and the usage warning. `terminal` without `result` and any other outcome: `Finish(unknown, 1)`. Not terminal: keep waiting. `Refused` or `Failed`: `Detach`, `Finish(unknown, 1)` with the "receipt could not be read" text of section 3.4.
12. **Link failure, and a gone session.** `LinkFailed` before `Opened`: `Finish(not_started, 4)`. In `Submitting` (the submit was sent, no reply yet) and after the reply before our completion: `Finish(unknown, 1)` with the "link failed after submit" text, the link's next step and the resume block, because the prompt may have arrived. `SessionGone` in the same phases: `Finish(unknown, 1)` with the "session is gone" text of section 3.4, no `Detach`. In `Reading` (either input): finish from the completion alone, with the usage warning. In `Stopping` (either input): finish as for `StopBudgetExpired` in rule 13 (the first stop's code, the point from its table), with `Hermes no longer knows this session.` or the link's reason as a warning in place of the budget warning. No `Detach` after a link failure or a gone session (the link or the session is gone).
13. **Stop.** The first `Stop` records its cause and emits `StartStopBudget`. Then, by phase:
    - `Starting`: wait for `Opened` or `OpenFailed` (the service bounds this, section 6.2). `Opened`: `Detach`, `Finish(stop, BeforeSubmit)`. `OpenFailed`: `Finish(stop, BeforeSubmit)`.
    - `Submitting`: wait for the submit reply (the stop budget bounds it; `prompt.cancel` needs the admission id). `Admitted` `queued` or `started`: stop as in `Waiting`. `Admitted` `terminal`: rule 5. `Unknown`, `Admitted` `unknown`: `Finish(stop, WhileSending)`. `Refused` or `VoiceStopped`: `Detach`, `Finish(stop, BeforeSubmit)`.
    - `Waiting`, our admission started (`g` known): `Interrupt { g }` and `StartSettleTimer`; phase `Stopping`.
    - `Waiting`, not started: `Cancel`; phase `Stopping`. The cancel settlement (H30) or a `terminal`/`cancelled` reply: `Detach`, `Finish(stop, Withdrawn)`. `Ok` `terminal` with another outcome: `ReadReceipt`, judged by rules 2 to 5 of section 3.3. `Ok` with status `started` (the gateway stopped the claim itself, H19): `StartSettleTimer`. `Refused { "stale_generation" }`: our turn started; if `g` is known by now, `Interrupt { g }` and `StartSettleTimer`; otherwise `ReadReceipt` once and use its `execution_generation`; when that is `null`, `Detach` and `Finish(stop, WhileSending)`. `Refused { "unknown_execution" }`, other refusals or `Failed`: `Detach`, `Finish(stop, WhileSending)`.
    - `Stopping` after an interrupt: `InterruptReplied` of any kind keeps waiting for our completion (a `stale_generation` refusal means the turn already ended or is ending). Our completion: `ReadReceipt`, then finish; the run is judged by section 3.3 (rule 1 when it settled `cancelled` or `interrupted`). `SettleDeadline` without a completion: `ReadReceipt` once; `terminal` with `result`: the stored answer with its warning; otherwise empty text; `Detach`; `Finish(stop, AfterStart)`.
    - `Reading` (our completion already seen): no cancel and no interrupt; the receipt read goes on and the turn is judged by its own result (the stop came after it ended).
    - A second `Stop` in any phase: `ExitNow(result)`, no `Detach`. The result: `exit_code` is the second stop's code; `status` is `timed_out` for 124, else `interrupted`; `text` is our answer when our completion was already seen, else `""`; `outcome` is the effective outcome when a settlement was seen, else `null`; `usage` from a receipt already read, else all `null`; `error` is the "Second stop" row of section 3.4; `warnings` are those gathered so far; `session_id` is set when a session was opened.
    - `StopBudgetExpired`: finish with the first stop's code, the budget warning and no `Detach`. The text row depends on the phase when the budget ran out:

      | Phase when the budget expires | Point used for the section 3.4 row |
      |---|---|
      | `Starting`, the connection open or the session open still running | `BeforeSubmit` ("nothing ran") |
      | `Submitting` (no submit reply yet) | `WhileSending` ("it may be running") |
      | `Stopping` after `Cancel`, no answer yet, not started | `WhileSending` ("it may be running") |
      | `Stopping` after `Interrupt`, or started with `g` unknown | `AfterStart` ("the turn was stopped") |
      | `Reading` (our completion already seen) | no stop row: finish from the completion alone (judged by section 3.3 rules 2 to 5) with the usage warning and the budget warning |
14. Every finish after `Opened` is preceded by `Detach`, except `ExitNow`, a link failure and an expired stop budget.

Stop codes: `Timeout` 124; `Signal(1)` (`SIGHUP`) 129; `Signal(2)` (`SIGINT`) 130; `Signal(15)` (`SIGTERM`) 143.

### 6.4 Time limits

| Call or wait | Limit |
|---|---|
| `prompt.submit` | [`P1-02`](https://github.com/infiquetra/talaria/issues/199) default (120 s); after a stop, the stop budget also bounds it |
| `prompt.receipt` | 10 s |
| `prompt.cancel` | 5 s |
| `session.interrupt` | 2 s |
| settle wait after an interrupt or a started cancel reply | 10 s (H21) |
| `session.detach` | 2 s |
| approval and clarify declines | 300 s, the architecture's protocol rule ("Approval responses may take up to 300 s; the client timeout must not be shorter"); never awaited before other work, abandoned at exit |
| stop budget | 25 s from the first stop; covers every call and wait after it, the detach included |

These values are `HeadlessTimings::default()` (section 4); the `prompt.submit` limit stays [`P1-02`](https://github.com/infiquetra/talaria/issues/199)'s and the decline limit is not a field. `HeadlessTimings::scaled_for_tests()` divides each by 100 (stop budget 250 ms, settle wait 100 ms, receipt 100 ms, cancel 50 ms, interrupt and detach 20 ms) for the flow tests.

From a stop to exit: at most 25 seconds (the stop budget), plus the time to write the output. The common path after a started turn (interrupt 2 s, settle up to 10 s, receipt up to 10 s, detach 2 s) fits inside it; longer paths (a stop during `prompt.submit`, a `stale_generation` cancel refusal that needs a receipt read) are cut by the budget. With `--timeout T`, the run ends within `T + 25` seconds. A second signal exits at once.

## 7. Output rules

Two neutralising functions, both T11's rule ([`P0-02`](https://github.com/infiquetra/talaria/issues/195)'s: every Unicode Cc character and the twelve `Bidi_Control` characters become `?`), differing only in what they keep:

- `neutralise_line` keeps nothing: newline, carriage return and tab become `?` too, so a warning or a failure line stays one line. It is applied, always (whether or not standard error is a terminal), to every Hermes-supplied piece of a `what`, a next step or a warning when that text is built (section 3.4). The resulting strings are what both standard error and the JSON `error` and `warnings` carry.
- `terminal_safe` keeps `\n` and `\t` and is applied only to the answer, only in text mode, only when standard output is a terminal.

If the merged code offers a public function with exactly T11's rule, `neutralise_line` calls it; `terminal_safe` is then that rule with newline and tab kept.

- Text mode, standard output: the answer, then `\n` if it does not already end with one; nothing when the answer is empty. On a terminal, `terminal_safe`; otherwise the bytes are written unchanged (scripts get the exact answer).
- JSON mode, standard output: exactly one line for every exit except 2. `serde_json` escapes every string. The answer (`text`) is otherwise unchanged; `error` and `warnings` hold the already neutralised, cut strings.
- Standard error, both modes: the two failure lines when the exit code is not 0, then the resume block when a session was opened, the exit code is 1, 3, 124, 129, 130 or 143, and the section 3.4 row asks for it (the "nothing ran" stop rows do not); warnings one per line.
- Never print a ticket, a home path, or an escape byte that Talaria made. `--help` lists the exit codes, the JSON keys' document `docs/formats/print-result-v1.md`, the `< /dev/null` sentence (section 3.2), the no-default-bound sentence (section 3.2), and that `-p` takes no profile name.
- No bell, no desktop notification, no terminal mode change, no alternate screen, no cursor query ([`P2-13`](https://github.com/infiquetra/talaria/issues/228) says headless never alerts).

## 11. Decisions and the reasons for them

1. **Finite turns.** `finite: true` is the only switch Hermes offers that makes approvals, clarifications and elicitations resolve without a person (H3, H5). Without it a headless run would hang until the approval timeout. `unattended` is never sent: it auto-approves every dangerous command.
2. **Source `oneshot`.** It is what Hermes's own finite runs use (H9), it keeps scripted sessions out of human pickers and out of `-c` (H8), and it marks the session as a classic CLI surface, whose turns carry the receipt fields scripts need.
3. **Exit codes.** 0, 1 and 130 match Hermes's `chat -q` (H16); 3 matches its "input required" detach (H18). Talaria adds 4 so a script can tell "nothing ran, retry is safe" from "it ran and failed", and 124 (the convention of `timeout(1)`) for its own time limit. Two deliberate differences from Hermes's own finite client (H16), recorded in `DECISIONS.md`: a voice stop phrase exits 4, not 0, because no answer was produced and a script must not read the empty output as one; and a completion without `outcome` takes the receipt's outcome before it is derived from `status`, where Hermes counts it as failed.
4. **Nothing waits for a person, and nobody else's question is answered.** Talaria declines every question that belongs to its own turn (approvals deny, clarifications skip, server requests of its running turn error) and withdraws its queued prompt when someone else's approval or question blocks the queue. A server request that arrives while our prompt is not running belongs to another viewer's turn (server requests go to every viewer and carry no admission, H32), so Talaria leaves it to that viewer and to Hermes's own time limit; answering it would take a decision away from a person who may be at their screen. The rule "while our turn runs, a server request is ours" rests on two facts (H38): every server-request sender runs inside a turn of its session, and a session runs one turn at a time. If a later Hermes sends a server request outside a turn, or runs two turns of one session at once, this rule is wrong: that is a stop condition, found by the planner's re-verification of H38.
5. **A stopped script stops its own turn.** On a signal or a timeout, Talaria interrupts its running turn with its own generation, which the gateway refuses for any other turn (H20), or cancels its prompt while it is still queued (`prompt.cancel` refuses a started admission, H19). A stop budget of 25 seconds bounds everything after the stop, so a script's own time limit stays meaningful. Hermes's own `chat -q` detaches instead (H22); a scripted job that is cancelled should not keep editing files. The operator may reverse this (issue questions).
6. **Never resend.** An unknown submit outcome or a lost link ends the run `unknown` with the resume command; it never submits again.
7. **The answer is the live text.** The stored copy is redacted (H15), so it is used only after a replay gap, with a warning.
8. **One JSON object, stable keys.** Streaming JSON is [`P6-05`](https://github.com/infiquetra/talaria/issues/278)'s. The object is shaped so that [`P6-05`](https://github.com/infiquetra/talaria/issues/278) can reuse it as its final record.
