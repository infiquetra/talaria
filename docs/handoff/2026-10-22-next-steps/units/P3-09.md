## 0. What this unit is, in one paragraph

A resident agent is a Hermes profile plus one hidden, persistent chat that is always there to message. Hermes already has exactly this object: Hermes Desktop's "Bot Mode" treats the session titled exactly `Bot Chat` on a profile as that profile's one forever-chat, and Hermes core protects that title (a hidden `Bot Chat` cannot be renamed, the idle-archive sweep skips it, the roster reports it). This unit adopts that model unchanged. It reads the roster from `profiles.list`, pins each profile's resident chat as a row at the top of the fleet view (`P3-02`), lets the operator make a served profile resident (`session.create` with `title: "Bot Chat"`, `hidden: true`), rename the agent's friendly name (`profiles.configure` on `ui_meta["hermes-bots"].title`), and reuses `P3-02`'s peek, reply, stop and open paths to message and open it. Because the chat is hidden, Hermes keeps it out of every session picker and out of `P3-01`'s session roster. The same agent is visible in Hermes Desktop's bot roster and reachable with `hermes -p <profile> chat -c "Bot Chat"`. The research behind it is feature F34 "Bot Mode roster" in [u06](../research/u06-hermes-desktop-catalog.md) (verdict "nice"); [03-hermes-today.md](../03-hermes-today.md) section 7 does not mention Bot Mode.

## 3. Design and reasoning

### 3.1 Identity is a name, never a stored id

A resident agent is identified by `(profile, "Bot Chat")`. Talaria stores no session id for it anywhere: not in its configuration, not in a state file, not in Hermes's `ui_meta`. Every roster read asks Hermes (`profiles.list`), and every row's key is the tip id Hermes reported in that read. Hermes Desktop learned this the hard way: five hardening rounds guarded a stored pointer that dangled or was stolen, then the pointer was removed (H26, `apps/desktop/src/AGENTS.md:78-90`). The key a row carries can go stale when Hermes compresses the chat (a new tip id); `session.resume` of the old id still reaches the tip (H18), and the next roster read replaces the key.

### 3.2 Creating fails closed

Talaria sends `session.create` for a resident chat only from the operator's explicit create action, never from open, peek, reply or a refresh. The create is safe to repeat because Hermes resolves the title first under a lock (H3), so Talaria never decides "absent, so create" on its own evidence. A profile is offered for creation only when its roster row says explicitly that it has no resident chat (`canonical_session: null`, H30). A row without session fields (a profile Talaria cannot read) is "unknown" and never offered (Desktop's failure: an empty answer read as "no chat" forked the forever-chat, H26). After a create, Talaria believes only what the next roster read shows (section 5.5): a resumed archived chat (H34) is reported, not pinned.

### 3.3 No kick-off message

Desktop sends a greeting turn ("Hey, tell me about yourself!") when it creates a bot, partly so older gateways persist the row. On the canonical socket the row exists and is titled at creation (H4), so Talaria sends nothing: no model turn is spent and nothing is written on the operator's behalf. The operator speaks first.

### 3.4 Rename changes the friendly name, not the chat title

The chat's title is its identity and Hermes refuses to rename it (H8). The agent's visible name is `ui_meta["hermes-bots"].title` on the profile (H20, H27), the same field Hermes Desktop shows, so a rename in Talaria shows in Desktop and the reverse. Talaria reads the current object and its revision, writes the object back with only `title` changed, and uses the revision as a compare-and-swap so a concurrent edit from Desktop is never overwritten. The cost: Talaria writes a key named after Desktop's plugin. Operator question 2 asks whether that is acceptable; the alternative (a Talaria-only key) would make the two clients disagree about the agent's name. `profiles.configure` is sent with `name` only: `name` already selects the folder under the Hermes home whatever the link's profile (H19), and adding `profile` would route a legacy method to a sibling authority for no benefit.

Name rule (recorded in `DECISIONS.md`): trim Unicode whitespace first (so a leading tab is trimmed away). Then, in order: a result equal to the prefilled text is "unchanged" (the view closes the line with `Name unchanged.` and sends nothing, so an untouched prefill never writes the profile name into Desktop's field); empty clears the name; more than 64 Unicode scalar values is `TooLong` (length is checked before characters, so a long name with a tab reports `TooLong`); then refuse any remaining character for which Rust's `char::is_control` is true (general category Cc, which includes tab and line feed inside the name) or that is in Hermes's invisible title set (H33) as `ControlCharacter`. Hermes does not sanitize `ui_meta` (H33), so this rule also protects Desktop's display.

### 3.5 Where state comes from

| Knowledge | Source | Owner |
|---|---|---|
| which profiles have a resident chat, its tip id, preview, last activity, friendly name | `profiles.list {include_sessions: true}` on a short-lived resident link | this unit (`ResidentService`) |
| working, needs you, done, failed for the resident chat | `P3-01`'s liveness polling (`session.active_list`, which includes loaded hidden chats, H31) of the pinned key, plus approvals and the outcome probe | `P3-01` registry, extended by this unit with pinned keys |
| live output, reply, answer, stop, open | `P3-02`'s peek link and actions, with the pinned key | `P3-02` |
| attention (bell, notification, counters) | `P3-01`'s `FleetNotice::Attention` and `FleetCounts`, which include pinned rows | `P3-06` |

`P3-01` lists sessions with `include_hidden` false, so the hidden resident chat is never a roster row. Its liveness read includes hidden live sessions, but without a roster row an item only creates an `unlisted` row when it is `waiting` (`P3-01` REQ-4). This unit adds a pinned set to the registry: a liveness item whose key is pinned updates (and if needed creates) a pinned row, and roster absence never removes it. That gives the resident row every state, alert and queue rule `P3-01` already has, with no second polling loop.

### 3.6 The resident link

`P3-01`'s fleet link refuses every method outside its list, and `P3-02`'s peek link never creates sessions. So this unit opens its own short-lived connection per operation, exactly as `P3-03`'s launch connection does: `P1-01` discovery with `EnsurePolicy::Never`, a ticket with `Scope::host(Purpose::Interactive)`, falling back to `Scope::profile()` for the foreground profile only on `TicketError::BindingRejected` or `Refused(_)`, the handshake, one or two calls, then close. A refresh is a handful of milliseconds on a local gateway; the roster changes rarely (a create, a rename, a compression). This is a further exception to [draft decision 0007](../adr-drafts/0007-attach-to-the-hermes-session-authority.md) points 2 (one connection per process) and 3 (answer unsupported server requests with an error), of the same kind as `P3-02`'s peek link; it is settled by `P3-02`'s operator question 1 on the phase 3 capability and recorded in this unit's `DECISIONS.md` entry. `session.create`, `session.list`, `session.detach` and the rename read always carry `profile`: H15 makes that correct on both link scopes (routed on a host link, stripped when it names the link's own profile), which removes any need to know "the link's own profile". On the profile-scoped fallback only the foreground profile is offered (E11), so `profile` always names the link's own profile there. Because the contract's closed `SessionDetachParams` has no `profile` field (H22), the detach is sent with `P1-02`'s `Client::call_raw` and the exact JSON object, as `P3-03`'s launch connection does for a routed detach; every other call uses the generated types, which declare `profile`. The handshake is `P1-01`'s, so it declares `server_requests: true`. A server request that arrives while the link is attached (between the create reply and the detach, one call long) is left alone with `Responder::ignore()`, never answered with an error (an error answer reads as "skip" for every viewer); another attached viewer, such as `P3-02`'s peek link or Desktop, can answer it, and otherwise it waits for its own timeout. A rename of a non-foreground profile on the fallback link is refused by Hermes with 4001 `profile_mismatch` and reported as `Refused { reason: "profile_mismatch" }`.

### 3.7 Hidden from pickers; the `source` choice

Hermes hides the chat from every listing that does not ask for hidden rows (H17), so `P2-07`'s session picker and `P3-01`'s roster never show it without code changes. This unit adds no filter to those units; the acceptance scenarios check the result. A visible session someone titled exactly `Bot Chat` is reported as the canonical chat (H13); Talaria pins it like Desktop and cannot hide it (`session.set_hidden` is unreachable, H21), so it stays in pickers (E15). "Continue the latest session" has no hidden filter (H25). Desktop creates its bots without `source`, so they are stored with the default `cli` and classic `hermes -c` can land in them; Talaria does the same (decision 9 of the issue), which keeps them out of `talaria -c` (family `tui`). An earlier draft sent `source: "tui"`, which would have made `talaria -c` able to open the resident chat.

### 3.8 Keeping residents and pinned rows

A roster read can be partial: an empty `profiles` array, the profile-only fallback scope (other profiles carry no session fields), or a sibling whose store failed (H14). Treating such a read as "the resident is gone" would drop a pinned row that may be waiting for an approval. So `merge_roster` removes a resident only on positive evidence (an explicit `canonical_session: null` for that profile in a successful read), and a key leaving the pin set keeps its row while it is `NeedsYou` or `Working` (section 5.3).

### 3.9 One operation at a time

The service task processes refreshes, creates and renames from one queue, so writes never overlap each other or a refresh. This mirrors `P2-07`'s "one session action at a time" rule and makes the create's follow-up refresh read the state the create produced.

## 5. State rules

### 5.1 Reading the roster (`roster_from_profiles_list`)

0. `bot_mode_protocol` must be `true`; false or missing is `RosterError::NotBotMode` (the service reports `Unsupported`).

For each element of `result.profiles`:

1. Skip (counting `malformed`) anything that is not an object with a non-empty string `name`.
2. Session fields are present when the object has the key `canonical_session` (null or object). Absent key: `Candidacy::Unknown` (never a candidate, never a resident).
3. `canonical_session` is an object: it is a resident chat only if `root_title == "Bot Chat"`, or `root_title` is missing or empty and `title == "Bot Chat"`, and `resolved_id` is a non-empty string. Otherwise add one diagnostic (`profile <p>: canonical_session is not a usable "Bot Chat"`) and treat the profile as `Unknown`. There is no fallback to `id`: the contract requires `resolved_id` and Hermes always fills it (H13), and a key that is not the tip would never match liveness.
4. `canonical_session` is null: record the profile in `explicit_none`; a candidate when `name` is in `served`, else `NotServed`.
5. Name: `display_name(ui_meta["hermes-bots"].title if a string, display_name if a string, name)`: the first one that is non-empty after trimming. Control characters are not removed here; drawing sanitizes. No "Hermes" for `default` and no capitalising (H27).
6. A profile appearing twice keeps the first occurrence (the answering profile is first, H14).

### 5.1b Keeping residents (`merge_roster`)

Start from `next`. For each resident of `previous` whose profile is not a resident in `next`: keep it (append to `next.residents`, remove it from `next.candidates` and `next.not_offered`) unless the profile is in `next.explicit_none`. A resident whose profile is a resident in `next` with another chat is replaced by the new one. Re-sort by section 5.2. With `previous` `None`, return `next` unchanged.

### 5.2 Order

Residents: by `name` compared case-insensitively, then by profile. Candidates: `default` first, then served order. The fleet view draws residents in this order regardless of state.

### 5.3 Pinned rows in the registry (`FleetInput::Pinned`)

| Situation | Rule |
|---|---|
| A pin's key has no row | create a row: `title = pin.name`, `state = Idle`, `pin = Some(PinInfo)`, `unlisted = false`, `message_count` from the roster |
| A pin's key has a row (for example an `unlisted` waiting row) | set `pin`, `title = pin.name`, `unlisted = false`; queue items and their `seq` are kept |
| A liveness item for a pinned key | applies `P3-01`'s REQ-9 state rules as for any row (approvals, outcome probe, attention); its `title` never replaces the pin's name |
| Roster (`session.list`) absence | never removes a pinned row (exempt from `P3-01`'s REQ-15) |
| A key leaves the pin set, row `NeedsYou` or `Working` | `pin = None`, `unlisted = true`; state, queue items and `seq` kept; from then on `P3-01`'s REQ-4 applies (it leaves silently once `Idle` or acknowledged) |
| A key leaves the pin set, any other state | `pin = None`; if the key is not in the latest roster: removed silently, unless unacknowledged `Done`/`Failed` (then `gone: true`, as `P3-01`'s REQ-15) |
| Identical pins resent | no change; `version()` does not rise |
| Order and counts | in the registry, pinned rows sit in `rows()` in their state group like any row and `FleetCounts` counts them as background rows (test 19); only the fleet view separates them: `FleetViewState` draws a row whose `pin` is set in the `RESIDENT AGENTS` section and leaves it out of its own state groups (test 20) |
| A pin moves (same profile, a new tip key after a compression) | if the new key has no row, the old row is re-keyed to it: state, queue items and `seq` kept, so a `Working` or `NeedsYou` row never splits in two; if the new key already has a row (liveness made it first), that row takes the pin and the old row follows the "key leaves the pin set" rules above (test 19a) |

### 5.4 Classifying a create reply

1. `classify_create`: `info.title` is a string: equal to `Bot Chat` gives `Created` when `message_count` is 0, `Adopted` otherwise; any other string gives `NotResident { title }`. Missing or null: `NeedsLookup`. Hermes gives no signal that tells a new chat from a resumed empty one (H35), so the split is by message count only: `Created` means "a resident chat with no messages yet", and its text (`is now a resident agent`) is true whether this create or an earlier one made the chat. A repeat create on a still-empty chat is `Created` again; once the chat has messages it is `Adopted`.
2. On `NeedsLookup` the service sends `session.list {profile, title: "Bot Chat", limit: 200, include_hidden: true}` (Desktop's exact lookup, `PROFILE_SESSION_LIST_LIMIT` = 200, H26; the title branch ignores `limit` and `include_hidden`, H16; they are sent so a later Hermes that honours them still finds the hidden chat). `classify_lookup`: one row whose `session_id` equals the snapshot's `session_id` (both are the tip, H32) and whose `root_title` (or, when empty, `title`) is `Bot Chat` gives `Created` or `Adopted` (same `message_count` rule); a row titled otherwise gives `NotResident { title: <that title> }`; no row, or a row with another `session_id`, gives `Unconfirmed`, reported as `CreateOutcome::Unknown { why: "Hermes did not confirm the chat" }`.

`NotResident` means Hermes resumed a visible session (for example `Bot Chat #2`, H7). The service detaches it without an end reason and reports the title; it never renames or hides it.

### 5.5 Service rules

- **Start.** After `P3-01`'s `FleetService` starts, on an interactive launch: one that draws the full-screen interface (with or without `--profile`, `-c` or `--resume`). Never with `-p` (`P2-14`'s headless print mode; `--profile` has no short form), `--bg` (`P3-03`), a subcommand such as `talaria fleet list`, `[fleet] enabled = false` or `[resident] enabled = false` (`Off` status then). `start` sends nothing on the caller's turn; the service task begins the first refresh right after it returns.
- **One queue.** One task takes commands (refresh, create, rename) in order and runs one at a time. A create or rename arriving while another write is running or queued is answered at once with `Refused { reason: "busy" }`. Refresh triggers arriving during any operation are folded into one refresh after it.
- **Refresh triggers.** Every `refresh` (60 s); `refresh_now()` (the fleet view opening, peek or open of a pinned row, the view's `RefreshResidents` effect); immediately after a create or rename finishes (not subject to `min_gap`). Other triggers inside `min_gap` (5 s) of the last refresh start are coalesced into one trailing refresh.
- **A refresh.** Open the resident link (section 3.6), send `profiles.list {include_sessions: true}` (no `profile`), close. Build the roster with `served` from the fleet snapshot's `Listed` profiles, then `merge_roster` with the previous roster. Note `fallback_profile` when the link fell back to profile scope. Publish a snapshot and one `ResidentNotice::Changed` only if the roster or status changed. Then `fleet.set_pinned(pins)` with one `Pin` per resident (only when the pins changed).
- **Failure.** Connect failure, timeout, drop or refusal: keep the last roster, status `Stale { reason }`; pins are kept. -32601 on `profiles.list`, or `NotBotMode`: status `Unsupported`, pins cleared, and no further refresh from any trigger (periodic, `refresh_now()`, after a write) until Talaria restarts. `Stale` reasons use `P3-02`'s rule: `data.reason`, else `unknown method <m>`, else `error <code>`, else `no reply` / `connection dropped` / `no gateway`.
- **Create.** Open the link; a connect failure here is `Refused { reason: <connect reason> }` (nothing was sent). `session.create` with `create_params`; classify (5.4); `session.detach {profile, session_id, subscription_id}` with no `end_reason` (failure ignored); close; refresh. If the class was `Created` or `Adopted` but the refreshed roster has no resident for the profile, report `NotListed` (H34) and pin nothing; otherwise report the class. A drop or timeout after sending the create is `Unknown`; it is not retried automatically; a refresh follows so the row appears if Hermes created it. Error mapping: `profile_mismatch`, `admission_conflict` (refresh first), other 4001 reasons with `data.field`, or `data.fields` joined with `, `, 5001 and -32601 are `Refused`.
- **Rename.** Validate first (`validate_new_name`; nothing is sent on error). Open the link (connect failure: `Refused`); `profiles.list {profile, include_sessions: false}` (the first row must have `name == profile`, else `NoProfile`); read `rev = ui_meta_revisions["hermes-bots"]` (0 when absent, H20) and `current = ui_meta["hermes-bots"]`; send `profiles.configure {name: profile, ui_meta: {"hermes-bots": rename_value(current, name)}, ui_meta_expected_revisions: {"hermes-bots": rev}}` (never `profile`, section 3.4); close; refresh; report. 4001 `profile_mismatch` on the read (a non-foreground profile on the fallback link) is `Refused { reason: "profile_mismatch" }`.
- **Methods.** The resident link sends only the handshake's methods, the heartbeat, `profiles.list`, `session.create`, `session.list` (only for 5.4 step 2), `session.detach` (through `Client::call_raw`, section 3.6) and `profiles.configure`. Never `session.mutate`, `session.title`, `session.set_hidden`, `session.resume`, `prompt.submit`, `approval.respond`, `clarify.respond`, `session.interrupt`, `profiles.create`, `config.set`; never `source`, `model`, `provider`, `cwd`, `finite`, `unattended` or `end_reason`.
- **Server requests** arriving on the resident link (it is attached to a fresh chat between create and detach; the handshake declares `server_requests: true`) get `P1-02`'s `Responder::ignore()`, never an error answer (section 3.6).

## 9. Mock-gateway rules (new handlers in `P1-09`'s mock)

Each rule follows the contract and the code in section 1.

1. `profiles.list`: refuse any key other than `profile` and `include_sessions` with 4001 `invalid_params`; refuse a non-bool `include_sessions` the same way (H11). Answer the configured rows with `bot_mode_protocol: true` (configurable false). With `profile` naming a configured sibling on a host-scoped mock connection, answer that profile's row first with its `ui_meta_revisions` (H14, H15); `profile` naming the connection's own profile is accepted; on a profile-scoped mock connection naming another profile, 4001 `profile_mismatch`. Readable profiles carry `canonical_session` (null when none, H30); unreadable ones carry no session keys; rows other than the first carry no `ui_meta_revisions` (H14).
2. `session.create`: strip `profile` when it names the connection's own profile, route it otherwise (as rule 1); refuse unknown keys with 4001 `invalid_params` and `data.fields` (contract closed set); refuse a non-bool `hidden`. With `title`: resolve an exact title first, archived and hidden rows included, else the newest `"<title> #N"` (for `Bot Chat` the exact title wins) (H7); if found, answer its snapshot and create nothing, without changing its hidden or archived flags (H4, H34); else create one, title it, set hidden when asked, and answer a snapshot with `session_id == stored_session_id` (H32) and `info.title` (configurable absent, U6). Configurable faults: drop after receiving, `admission_conflict`, 5001.
3. `session.list`: accept only `limit` (1 to 200), `title`, `include_hidden`, `scope` and `profile` as in rule 2; refuse `scope` together with `title`; with `title`, resolve as rule 2, ignore `limit` and `include_hidden`, and answer one row (tip ids, `id`, `title`, `root_title`) or none (H16).
4. `session.detach`: require `session_id` and `subscription_id`; record whether `end_reason` was present.
5. `profiles.configure`: implement H19 and H20 exactly: `name` required (4063), unknown (4064), `name` selects the profile whatever the connection's profile, per-key compare-and-swap with absent revisions counted as 0 and `ui_meta_conflicts`, key-wise merge, null deletes, 65,536-byte cap gives `applied.ui_meta: false`. Configurable: answer -32601 (no legacy fallback).
6. Archived rows: a configured archived hidden `Bot Chat` is found by rules 2 and 3 but reported as `canonical_session: null` by rule 1 (H13, H34).
7. Every request is recorded with its method and params, so tests can assert exact key sets and forbidden methods.
