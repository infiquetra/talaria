## 3. Request and result shapes

All socket calls go through `Client::call_with` (unit P1-02) on the foreground connection, which holds a profile-scope `interactive` ticket. The scope comes from the ticket (H2, H10); this unit never sends `profile` with a value.

**Generated params and unset keys.** Unit P0-03 generates the param types from the contract, where every optional key is nullable (H6). If the generated type writes an unset key as `null`, that is accepted (Hermes treats `null` as absent); test 14 asserts the set of **non-null** keys exactly and that no forbidden key (issue REQ-12) has a non-null value. If a generated type writes a default other than `null` (for example `false`) for a key this unit must not send, stop and report on the issue; do not hand-build JSON around `Client::call_raw`, which is a hidden test hook.

### 3.6 Host topology (VERIFY, H18)

`GET <api_origin>/api/status` through `gateway_api::gateway_status(rest: &RestClient) -> Result<serde_json::Value, RestError>` (the signature unit P4-10 owns; whichever unit merges first adds it in `crates/hermes-client/src/gateway_api.rs`). It calls unit P4-01's `RestClient::request(Method::Get, "/api/status", None, RequestOpts { ticket: true, deadline: Some(Duration::from_secs(8)) })`: the usual `native-http` ticket (harmless on a public path, unit P4-01's H9 and H35) and an 8 s deadline, Hermes Desktop's value and unit P4-10's. Talaria reads only `parked_profiles` (list of names), `gateway_mode`, `multiplex_standalone_reason` and `gateways[].profile`, and drops the rest while parsing (the reply holds paths and a process id).

`HostTopology.own_gateway` is `None` when the reply has no `gateways` key (a listener that requires sign-in) and `Some(names)` otherwise. A reply that is not a JSON object, or whose `parked_profiles` is not a list of strings, is a topology failure. `gateway_mode` is always present at v0.22.4 (`hermes_cli/web_routers/status.py` line 567); a missing or non-string value parses as `None`. The parse is `talaria_app::profiles::parse_topology(reply: &serde_json::Value, home: &Path) -> Result<HostTopology, String>`; it passes `multiplex_standalone_reason` through `control_verbs::scrub_reason` (decision 8: no path is ever shown, whatever Hermes puts in that text).

**Building the REST client.** Follow unit P4-01's specification section 4.13 ("Where the inputs come from in production"): the service handles `Topology` by running its own `discover_with` with `EnsurePolicy::Never` (one `identify`, so the three effects stay independent and run in parallel), then builds `RestClient::new(endpoint.api_origin(), minter, RestOptions::default())` with `minter` = `NativeHttpMinter::new(home, endpoint, endpoint.resolve_profile(<connected profile>))`, the construction unit P4-01's `MinterFactory` uses. `<connected profile>` is unit P1-12's `OpenConnection.profile_name` (for the command: `default` or `--profile`); `home` is the Hermes home the connection was opened with. If that discovery fails, `api_origin` is absent or the profile does not resolve, the topology fails with `<words>` = `no ticket`. Tests construct the client directly against unit P4-01's mock REST server.

### 3.7 Failure words

Text J's `<words>`, from `RestError` (unit P4-01's variants): `Timeout` → `no answer within 8 s`; `NotFound` → `not found`; `Unauthorized`, `Forbidden` → `refused`; `Server { status }` → `server error <status>`; `BadBody`, `BodyTooLarge`, a non-object reply → `unreadable reply`; `Connect`, `Dropped` → `connection failed`; `Ticket` → `no ticket`; any other → `request failed`. Text I's `<words>`, from `CallError`: unknown outcome → `no answer`; refused → `<code> <data.reason or message>`; unreadable → `unreadable reply`.

## 4. Classifying a profile

Inputs: the roster (3.1, optional when it failed), the endpoint from a fresh `identify` (served names and the parked map, required), the host topology (3.6, optional), and the names this Talaria process created, each with its creation time.

The first matching row wins. Names are compared after Hermes's normalisation (trim, lower-case; `default` in any case is `default`).

| # | Condition | State | Label | Tone |
|---|---|---|---|---|
| 1 | name is a served name in `identify` | `Served` | `served` | muted |
| 2 | name is a key of `identify`'s parked map | `Parked { reason }` | `parked` | warning |
| 3 | topology present and name in its `parked_profiles` list | `Stopped` | `stopped` | warning |
| 4 | topology present, `own_gateway` is `Some`, and it holds the name | `OwnGateway` | `own gateway` | warning |
| 5 | topology present, `gateway_mode` is present and not `multiplex`, and `multiplex_standalone_reason` (after `scrub_reason`) is non-empty | `HostSingle { reason }` | `not served` | warning |
| 6 | created by this process and `now − created_at < 40 000 ms` | `Starting` | `starting` | muted |
| 7 | otherwise | `NeverDiscovered` | `not discovered` | warning |

Row 5 with an absent `gateway_mode` (`None`) never matches; test 2 pins both `None` and `Some("unknown")` (the latter matches when a reason is present).

Row 6's window is 40 s: the last follow-up discovery runs at 35 s (REQ-7) and its answer lands inside the window, so the row never falls to `not discovered` before that answer. At exactly 40 000 ms the row falls through. Time comes from the caller: `ProfilesState::update(&mut self, input, now_ms)` takes a monotonic clock in milliseconds (in `app.rs`, milliseconds since the process started, from one `std::time::Instant`); `created_at` is the `now_ms` of the successful `CreateAnswered`. Every `update` re-classifies the rows with its `now_ms`, and the create follow-up's last tick at 40 000 ms (section 4.1, Timers) guarantees an `update` exactly when the window ends, so an unserved new profile leaves `starting` without a key press.

When `identify` itself fails, no row is classified: the screen shows the failure (section 5, text H) and the last roster, every state `Unknown` (label `unknown`).

Rows come from the union of the roster names, the served names, the parked names and, when the topology arrived, its stopped names and its `gateways[].profile` names. So when the roster fails, a stopped or own-gateway profile still gets a row. A name missing from the roster still gets a row, with details shown as `-` and the detail note `Hermes did not list this profile's details.` (until a describe fills them).

Sort order: `default` first, then served rows by name, then every other row by name.

Timers. `ScheduleTick` asks `app.rs` to deliver `Tick { token }` after `after_ms`. The state schedules exactly two kinds: the describe delay (150 ms after the last selection move; a newer move replaces the token) and the create follow-up (ticks at 0, 5 000, 15 000, 35 000 and 40 000 ms after a successful create; the first four each start a full refresh (section 6.8); the 40 000 ms tick only re-classifies, so `starting` ends on time). A tick whose token is stale does nothing. A tick emits `Redraw` only when `view()` changed. `Closed` emits `CancelTicks`. With no describe pending and no follow-up running, nothing is scheduled, so the idle budget (zero frames) holds.

Lifetime. `app.rs` owns one `ProfilesState` for the process lifetime. The `created` list (name, creation time) and the kept soul edits (section 6.6) live in it, so `starting` survives closing and reopening the overlay; data and caches are refreshed on every open.

`ProfilesEffect::Notice(String)` is used only while the overlay is closed (a late create answer, section 6.8); `app.rs` sends it to unit P2-03's notice cell (`Event::Notice`). While the overlay is open, notices live in `ProfilesView.notice` (section 6.2).

### 6.1 Entry

`/profiles` (a local command registered with unit P2-03's palette) opens the overlay. ### 6.2 Layout

These rules decide every snapshot; the test author writes the expected screens from them.

- **Header (line 1).** Left: `Profiles (<n> on disk · <s> served)`, where `<n>` is the number of roster rows (`-` when the roster failed) and `<s>` the number of `Served` rows. Right-aligned: the key hints `r refresh · R rescan · n new · e describe · s soul`, dropped whole from the right end until at least two spaces separate them from the left part. Under 40 columns no hints show.
- **Wide (100 columns or more).** Under the header, the list takes `L = max(1, min(rows, (H − 2) / 2))` lines (integer division, `H` the height); then one line of `─` across the width; then the detail fills the remaining lines.
- **Narrow (under 100 columns).** The list fills every line under the header. Enter replaces it with the detail at full height (title on line 1, no header); Esc returns to the list.
- **List row.** Two characters of marker (`▸ ` for the selection, else two spaces), then cells separated by two spaces: name (the name, or `display (name)` when `display_name` differs), width `min(longest, 24)`; label, width 14; model (`model · provider` when known, else `-`), width `min(longest, 34)`; next step, the rest of the line. Model is known from the roster's own row or from a cached describe (3.2). Columns by width: 80 or more, all four; 40 to 79, name, label and next step; under 40, name and label. A cell wider than its column is cut to width − 1 and `…` is added. The view scrolls by the least amount that keeps the selection visible; there is no scroll indicator.
- **Detail.** Line 1: `<name> · <label>`. Then the state text (section 5) wrapped to the width. Then, in this order, one line each: `Model: <provider> · <default>` (`Model: not set` when described with an empty `default`; `Model: reading...` while the describe call runs); `Skills: <on> of <total> on`; `Toolsets: <enabled labels joined by ", ">` or `Toolsets: default set` when `toolsets_pinned` is false; `MCP servers: <name> (<on|off>, <transport>)` joined by ` · `, or `MCP servers: none`; `Description: <text>` or `Description: none`; `Soul:` then up to 6 lines of the soul. Each line is cut with `…` to the width. Lines past the bottom are not drawn. A describe failure replaces the lines after the state text with text P. No path is ever shown.
- **Loading.** Until the first load completes (section 6.8) the line under the header reads `Loading profiles...` and nothing else is drawn below it. Later refreshes keep the previous rows on screen until the new set is complete.
- **Notices and the confirmation** are drawn at the bottom of the screen in both layouts, over whatever is there (the detail's last lines when wide, the list's when narrow; the list scrolls so the selection stays above them). The text is wrapped at spaces to the full width (a word longer than the width is broken), at most `H − 2` lines; if more are needed the last drawn line ends with `…`. Text K (the rescan confirmation) is drawn the same way, so `Press y to confirm, any other key to cancel.` is always visible at the UAT size (about 2 lines at 100 columns, 5 at 38). Notices queue in arrival order and the oldest is shown; each key press removes the shown notice and is then handled normally. While the confirmation is open, it is drawn instead of the notice, and the next key answers it and does nothing else.
- **Filter.** While typing and while a filter is active, the header's key hints are replaced by `/<filter text>` (cut with `…` from the left when too long). A filter that matches nothing shows `No profile matches "<text>".` on the first list line, and the detail is empty.
- **Panels** (the create form, a review, the description input). Wide: the panel replaces the detail under the `─` line and the list above is unchanged. Narrow: the panel replaces the list under the header. Line 1 of a panel is its title (`New profile`, `Review`, `Description of <name>`); its last line is its key hint (`Enter next · Tab move · Esc cancel` for the form, `Enter apply · Esc back` for a review, `Enter review · Esc cancel` for the input). Form lines, in field order: `▸ ` before the focused field, else two spaces, then `Name: <text>`, `Description: <text>`, `Start from: ‹ <choice> ›`, `[x] Copy provider keys from <profile>` (`[ ]` when off); a name error is the line directly under `Name:`, indented four spaces. The input line is `> <text>`, its error the line under it. The terminal cursor is shown at the insertion point of the focused text field, and hidden otherwise. A review lists its lines (section 6.5 or 6.6) between title and hint.

### 6.6 Editing

**Description.** `e` opens an inline one-line input prefilled with the described description (if the selected profile has not been described, `e` sends the describe first and opens the input when it answers; a describe failure shows text P, Q or X as a notice, per section 6.8's describe row, and opens nothing; the same holds for `s`). The prefill is the described description with each run of `\r` and `\n` characters replaced by one space (the input is one line). On Enter the input text is trimmed and compared with the trimmed prefill: equal gives `No change.` and sends nothing, so an untouched multi-line description is never rewritten; otherwise the review `description: "<old>" -> "<new>"` (both as compared); Enter sends the trimmed text. Empty text is allowed and clears the description. More than 200 Unicode scalar values after trimming is refused under the input: `Use at most 200 characters.`

**Soul.** `s` sends a fresh `profiles.describe` (not the cache) and opens its `soul` text, or the profile's kept edit after text T (below). A text longer than 262 144 bytes of UTF-8 is not opened (`This soul file is too large to edit here (<n> KiB).`); 262 144 bytes is allowed. The editor runs through `ProfilesEffect::OpenEditor(text)`, which `app.rs` executes the way unit P2-13 runs its composer hand-off, but with a raw edit in place of `edit_draft`:

Who does what. `app.rs` performs the terminal hand-off; the editor function only handles the file and the process. On `OpenEditor(text)`, `app.rs` does, in order: unit P2-13's `InputThread::pause`; `InlineTerminal::release` (the overlay's alternate screen too); `TerminalGuard::leave_raw`; the raw edit below on a blocking thread; `TerminalGuard::enter_raw`; `InlineTerminal::reacquire`; `InputThread::resume`; a full redraw of the overlay; then `EditorReturned(result)` to the state. The hand-off steps run whatever the edit returns.

- If unit P2-13's merged editor module offers a raw mode (exact bytes in and out, no cleaning) that does not do the hand-off itself, use it in place of `edit_text_raw`. If it does the hand-off itself, use it whole and skip the steps above.
- Otherwise `edit_text_raw(argv, text, cwd, tmp_dir, 262_144)` in `crates/talaria-app/src/profiles_editor.rs`, which never touches the terminal: write `text` byte for byte to a new 0600 file `SOUL.md` in `tmp_dir`; run `argv` plus the file path with inherited streams and `cwd` as the working directory, and wait; read the file back as bytes; always delete it. `argv` comes from P2-13's `resolve_editor` (its error gives P2-13's own notice and nothing is sent; `app.rs` checks this before the hand-off). `cwd` and `tmp_dir` are the same new private (0700) directory that `app.rs` creates under `std::env::temp_dir()` for this edit and removes afterwards: never the profile's home (Talaria does not keep it, decision 8) and never the session folder. Non-zero exit or a signal: `Failed("The editor exited with an error; nothing was sent.")`. Over `max_bytes`: `Failed("The edited soul is larger than 256 KiB; nothing was sent.")`. Not UTF-8: `Failed("The edited soul is not UTF-8 text; nothing was sent.")`. Byte-equal to `text`: `Unchanged`. Else `Changed(exact text)`. No line-ending change, no control-character removal, no trimming.

The edit's base and the opened text. Normally the editor opens the fresh soul, and the base is that same text. After text T (below), the next `s` on that profile opens the operator's kept edit instead, and the base is the fresh soul read by that `s`. When the editor returns, the result text is the `Changed` text, or the opened text for `Unchanged`. Result equal to the base: `No change.` and nothing is sent. Otherwise the review shows `+<a> −<d> lines` (the minus sign is U+2212 `−`, not a hyphen) and `first_lines` from `line_diff(base, result)`, plus the U+FFFD note when it applies. `line_diff` uses the `similar` crate's `TextDiff::from_lines` with its default algorithm (Myers); a hand-written quadratic diff is not acceptable, because a 262,144-byte soul of short lines would stall the update thread. It counts inserted lines as `added` and deleted lines as `removed` (a changed line is one of each), and returns the first 10 inserted or deleted lines in diff order, each prefixed `+ ` or `- ` with its line ending removed. A missing or added final newline changes the last line. Test 11 pins `first_lines` only on inputs with one changed block, where every diff algorithm agrees.

Saving. Enter on the review sends a fresh `profiles.describe`. If its `soul` equals the base exactly, it sends `profiles.configure {name, soul}` with the result text unchanged. Otherwise nothing is sent, text T is shown, and the result text is kept in memory as that profile's kept edit (in `ProfilesState`, for the process lifetime, never in a file). The kept edit is replaced by the next edit of that profile and cleared when that profile's soul is saved (text R). This gives the operator two choices after text T: press `s`, see their own text in the editor, and review it against the new version (the review's `-` lines show what would be overwritten); or leave it unsaved.

Line endings (H27). Hermes's describe turns every `\r\n` and lone `\r` into `\n`, so the editor opens LF text and a save writes LF endings, even for a soul stored with CRLF on disk. A `\r` the operator types survives into the sent frame (test 11 asserts the outbound frame only); a later describe reads it back as `\n`. The review adds no warning for this; the limit is recorded in `LEARNINGS.md` (issue AC-11).

### 6.7 Command output

`talaria profiles` connected on `default`, with synthetic data (scripted roster: `default`'s own row has model `minimax-m3.1-flash`, provider `ollama-cloud`):

```text
$ talaria profiles fixture default
NAME     STATE   MODEL                              NEXT STEP
fixture  served  -                                  talaria --profile fixture
default  served  minimax-m3.1-flash · ollama-cloud  talaria --profile default
```

The rule is authoritative and the example follows it exactly: column width is the widest value in the column including the header, counted in Unicode scalar values (`chars().count()`; `·` counts 1); two spaces between columns; the last column is not padded. Here the widths are 7, 6 and 33, so `STATE` starts at offset 9, `MODEL` at 17 and `NEXT STEP` at 52. Rows follow the order typed (normalised, duplicates dropped); without NAMEs they follow the screen's sort. A NAME not in the roster shows MODEL `-`. A NAME counts as known when it is in any source: roster, served, parked, or (when the topology arrived) the topology's stopped names or `gateways[].profile` names.

**Command failures.** Every message goes to standard error as one line starting `talaria profiles: `; standard output holds only the table or the JSON.

| Case | Standard error | Standard output | Exit |
|---|---|---|---|
| Any `DiscoveryError` (no gateway, not ready, unsafe control socket, ...) | text H: the error's `Display`, then a second line `Next step: <next_step()>` | nothing, also with `--json` | 1 |
| WebSocket connect or ticket fails, or `profiles.list` fails | text I (the connect failure's words are `could not connect`) | the table or JSON from `identify` and the topology | 0 |
| Topology fails or has no `gateways` | text J (the matching form) | the table or JSON | 0 |
| One or more NAMEs in no source | one line `no profile named <name>` per unknown NAME, in typed order | nothing | 2 |

Checks run in this order: discovery, then the three sources, then the NAME check; the first failing exit code wins. `--json` always prints `{"profiles":[...],"warnings":[...]}`: `warnings` holds texts I and J in that order (an empty list when there are none), so a script can see a degraded answer.

```text
$ talaria profiles --json fixture-b fixture-c fixture-d
{"profiles":[{"name":"fixture-b","state":"parked","reason":"session store unusable: <home>/profiles/fixture-b/state.db","next_step":"fix the reason, then rescan with R in /profiles"},{"name":"fixture-c","state":"stopped","next_step":"hermes -p fixture-c gateway start"},{"name":"fixture-d","state":"not_discovered","next_step":"rescan with R in /profiles"}],"warnings":[]}
```

JSON states: `served`, `parked`, `stopped`, `own_gateway`, `not_served`, `starting`, `not_discovered`. `reason` only for `parked` and `not_served`; `model` and `provider` only when known. One line, no trailing spaces. The command creates no session and starts no gateway.

**Reason text, one rule per surface.** Both kinds of reason (`identify`'s parked reasons and the topology's `multiplex_standalone_reason`) are first passed through `hermes_client::control_verbs::scrub_reason(text, home)`, which calls unit P1-01's crate-private `scrub_peer_text(text, home, 500)`: paths become `<home>` or `<path>`, length at most 500 characters. The JSON `reason` is that scrubbed text, not sanitised further (`serde_json` escapes control characters). The screen (texts B and E in the detail) passes it through unit P1-06's `history::sanitize` and cut it to 300 characters (REQ-11 of the issue).

### 6.8 Loading, selection, refresh and outcomes

**When rows first draw.** A load (open, `r`, a create follow-up tick, the refresh after a write or a rescan) starts one refresh: the state increments its single `generation` counter and emits `Discover`, `List` and `Topology` with it. The refresh is complete when `Discovered` has arrived and `Listed` and `Topology` have each answered or failed (their own deadlines: 10 s and 8 s; discovery's is unit P1-01's). Only then are the rows replaced, all at once, and the notices of that refresh queued (text I before text J). This avoids drawing a stopped profile as `not discovered` before the topology arrives. Until the first refresh completes the screen shows `Loading profiles...`; later refreshes keep the old rows until the new set is complete.

**Generations.** Every answer carries the generation of the refresh that asked for it (`Discovered`, `Listed`, `Topology`, `Described`). An answer from an older generation is dropped, including an old `Described` that would refill the cache a refresh just cleared (test 8). A follow-up tick's refresh therefore drops the in-flight answers of an earlier refresh; its own answers replace them. `CreateAnswered`, `ConfigureAnswered` and `RescanAnswered` carry no generation: they answer writes, are always applied, and each starts a refresh.

**Selection and describe.** The selection follows the profile name across refreshes, sort and filter changes. If the selected name is gone or filtered out, the first visible row is selected. On the first load the connected profile's row is selected (else the first row). When a refresh completes, the describe cache is empty and the selected row is described at once (no delay), in both layouts. After that, a selection move schedules the 150 ms describe delay; Enter describes at once. One describe per name per generation.

**Create follow-up.** After a successful `CreateAnswered`, the state records `(name, now_ms)`, queues text N, and schedules ticks at 0, 5 000, 15 000, 35 000 and 40 000 ms. Each of the first four starts a full refresh (all three sources, so the new profile's roster row and the header count `<n>` are fresh). The 40 000 ms tick only re-classifies and redraws if the view changed. Closing cancels these ticks; on `Open`, for each created name still inside its 40 s window, the state schedules one re-classify tick at the end of that window, so a reopened `starting` row also ends on time.

**Late answers while closed.** A `CreateAnswered` that arrives after the overlay closed still records `(name, now_ms)` when it succeeded, so the row reads `starting` on a reopen inside 40 s; it schedules no ticks (the reopen refreshes) and its text (N, O, P, Q or W) goes out as `ProfilesEffect::Notice` to unit P2-03's notice cell. A late `ConfigureAnswered` or `RescanAnswered` does the same with its text. A late `Described`, `Discovered`, `Listed` or `Topology` is dropped.

**Outcomes of a call** (`CallFailure`, per call):

| Call | `Unknown` | `NotSent` | `Unreadable` | `Refused` (any code except -32601) | -32601 |
|---|---|---|---|---|---|
| describe | text X in the detail | text X (`not connected`) | text X | text P in the detail | text Q (describe) |
| create | text O, then refresh, no retry | text W; the form reopens, fields kept | text O, then refresh | text P; the form reopens with fields kept (4001, 4061, 4062, 5062 alike) | text Q (create); the form closes |
| configure | text V, then refresh, no retry | text W; the review reopens | text V, then refresh | text P; the input or review reopens | text Q (change) |

**Rescan precedence.** `RescanAnswered` is read in this order, first match wins: `ok: false` with an `unknown verb` error → text M; any other failure → text U; `multiplex: false` → `SingleProfile` (text L, third form); `pending: true` → `Pending` (text L, second form); otherwise (`multiplex: true`, `pending` absent or false) → `Finished` (text L, first form). `rescanned` and `reason` are not shown. Every outcome, failures included, then starts one refresh.

## 10. Design reasoning

- **Why socket first.** Desktop's Bots plugin creates and configures profiles over its socket (H10), and the socket path needs no new ticket purpose. REST `POST /api/profiles` needs a `native-profile-create` ticket that unit P1-01 does not expose (H20). If P4-00 finds the socket path refused, the planner switches create to REST and this unit adds `Purpose::NativeProfileCreate` to unit P1-01's ticket module (a minimal touch named in the pull request).
- **Why the topology is optional.** `identify` alone separates "parked" from "never discovered", which is what the handoff asks for. `/api/status` adds the "stopped", "own gateway" and "serves one profile" reasons, but its live reachability on the gateway's listener is unproven (H18).
- **Why `/api/status` is ticketed and 8 s.** Unit P4-10 reads the same route with the usual ticket and Desktop's 8 s; one `gateway_status` in one module keeps the two units from diverging. The ticket costs one control-socket call and is harmless on a public path.
- **Why a missing `gateways` gets its own notice.** Without it an own-gateway profile would fall to row 7 and get text G, which names a fix that does not apply. The second form of text J tells the operator that reason is unavailable.
- **Why no polling.** No event announces a profile change (H1). Desktop polls every 5 s; a terminal overlay refreshes on open, on `r`, and after its own writes, so the idle budget (zero frames when nothing changes) holds. The two timers stop on their own.
- **Why 40 s for `starting`.** Hermes's watcher rescans every 30 s; the follow-up discoveries at 0, 5, 15 and 35 s cover that, and the window is wide enough for the 35 s answer. Since Hermes already rescans on create (H25), `starting` is the exception.
- **Why a raw editor for the soul.** A soul is written back verbatim (H27). Unit P2-13's `edit_draft` cleans composer text (line endings, control characters, trailing whitespace), which would silently rewrite the operator's SOUL.md and turn the cleaning into counted edits.
- **Why no home path.** `profiles.describe` has none (H5), the roster's `path` is an absolute home path, and the screen's job is to say what to do, which never needs the path.
- **Why model, skills, toolsets and MCP servers are read-only here.** Units P4-03 (model roles), P4-04 (MCP servers) and P4-05 (skills and toolsets) own those writes; two writers of one setting would race. Unit P4-03's non-goals also say the profile list does not open its page in v0.7.0.
- **Why `not discovered` says "rescan" even on a one-profile host.** H23: a rescan is what moves a single-profile gateway to multiplexing once a second profile exists, so the same fix applies; `/api/status` never reports that case as a reason (H24).
