## 1. What this unit is, in one paragraph

Talaria's screen has a live region at the bottom (drawn by unit `P1-06`). The last row of it is the status line. This unit builds that row as a pure function from plain data to text (`plan`), a ratatui widget that draws it (`StatusSection`), and the optional external command that adds one more segment at the right: the document it receives, the environment it gets, the way it is run and killed, the way its output is read, and the rule for when it runs again. It makes no Hermes call and runs no `git`. Its caller (unit `P1-12`) fills `StatusInputs` from session state and owns the timer.

## 4. The native line

### 4.1 Segment text

| Segment | Shown when | Text | Examples |
|---|---|---|---|
| Connection | connection is not `Connected` | `disconnected`, `connecting…`, `reconnecting…`, `auth failed` | `reconnecting…` |
| Model | model non-empty | text after the last `/` of the model, then ` <effort>` when effort is non-empty (trim, lower-case), or ` <effort>→<wire>` when wire is non-empty and differs; an empty effort shows no effort and no arrow, whatever the wire level holds | `opus-5.5 high`, `minimax-m3.1-flash`, `x ultra→max`, `x none` |
| Folder | folder or branch present | folder text, then ` (<branch>)`; with a branch and no folder just `(<branch>)` | `~/proj (main)`, `/work/demo`, `(main)` |
| Context | percent present | `ctx <n>%` or `ctx ~<n>%` when estimated; `n` clamped to 0..=100 | `ctx 34%`, `ctx ~34%` |
| Cost | cost present, finite, not negative, status not `unknown` or `included` | `$` and two decimals; `~$` when status is `estimated`; `<$0.01` (`~<$0.01` when estimated) when above 0 and below 0.01; no thousands separator | `$0.12`, `~$0.12`, `<$0.01`, `~<$0.01`, `$0.00`, `$1234.50` |
| Needs you | count above 0 | `⚑ <n> need you`; for 1: `⚑ 1 needs you` | `⚑ 2 need you` |
| Working | count above 0 | `<n> working` | `3 working` |
| External | an `ExternalSegment` is given | the text, trimmed | `tests: 296 passing` |

Folder rules. If `home_dir` is set (trailing `/` removed) and the folder equals it, show `~`; if the folder starts with `home_dir` followed by `/`, replace that prefix with `~`; a sibling that merely shares the prefix (`/h/dev2` against home `/h/dev`) is not abbreviated. Only `/` separates components. If the result is wider than 32 display columns, split it on `/` (empty parts skipped, the `~` counted as a component) and keep the most trailing components that fit with a `…/` prefix inside 32 columns; if even the last component does not fit, show `…/`, the first 29 columns of the last component, and `…` (32 columns). The branch alone is cut at 24 display columns: when longer, its first 23 columns and a `…`, so the `…` counts inside the 24. The parenthesised ` (<branch>)` can therefore reach 27 columns, which is intended. All cuts use the rule of section 4.3 (by `char`). In tests, build the paths from parts (see section 11) so no test holds an absolute path.

Effort shown is always the Hermes value when set, including `medium` (unlike Hermes's own bar, H10), because the architecture sketch shows `opus-5.5 high` and a reader should not have to guess what an absent word means. This is a settled display choice of this unit.

### 4.2 Order and priority

| Segment | Position (left to right) | Priority (1 is kept longest) |
|---|---|---|
| Connection | 1 | 1 |
| Model | 2 | 3 |
| Folder | 3 | 5 |
| Context | 4 | 4 |
| Cost | 5 | 7 |
| Needs you | 6 | 2 |
| Working | 7 | 6 |

Reasoning for the order of priority: a lost connection or an unanswered question blocks the operator, so they last longest; the model and context decide what the next prompt can do; the folder and the working count are context the operator usually knows; the cost is often absent; the external segment is the operator's garnish. ### 4.3 The algorithm

```text
plan(inputs, external, cols):
  segs = every segment that is shown (4.1), as (Segment, text, Tone)
  text of each = sanitize(text)                      // P1-06; before measuring
  avail = cols.saturating_sub(1)                     // one blank column on the left; cols is u16, so no underflow at 0
  loop:
    need = sum(width(text)) + 3 * (len(segs) - 1)    // separators are " │ ": 3 columns
    if need <= avail: break
    if len(segs) == 1: cut segs[0].text (see below) to avail columns, ending with "…" (avail 0: drop it, so pieces is empty); break
    remove the segment with the numerically largest priority
  order segs by position
  return LinePlan { pieces }
```

The cut works by `char`, without a grapheme crate: take characters in order while the running width stays within `avail - 1`, stop at the first character that does not fit whole (a two-column character against one free column is dropped, and nothing after it is taken), then append `…`. Zero-width characters that follow a kept character stay with it. The cut text, `…` included, is at most `avail` columns, and may be one column short when a two-column character was dropped (the row is padded with blanks). The folder and branch cuts of section 4.1 use the same rule with their own budgets.

When `avail` is 0 (width 0 or 1) `pieces` is empty and nothing is drawn; `LinePlan::text()` is then the empty string. With `avail` 1 and one segment left the cut leaves only `…`, so width 2 gives ` …`. `LinePlan::text()` joins the texts with ` │ ` and puts one space at the start. `StatusSection::render` writes the same pieces into the buffer: the leading blank, each text with its tone's style, each separator with the `separator` tone, then blanks to the end of the area. Width is `UnicodeWidthStr::width` (the non-CJK width: `│`, `…` and `→` are one column; `⚑` is one column).

## 5. The standard-input document and the environment

### 5.1 The document (version 1)

Serialised with serde in this field order, compact, then `\n`:

```json
{"version":1,"mode":"live","connection":"connected","session":{"id":"sess-1","title":null},"turn":"idle","pending_prompts":0,"subagents":{"active":0,"terminal":0},"usage":null}
```

`mode`: `live` or `replay`. `connection`: `disconnected`, `connecting`, `connected`, `reconnecting`, `auth_failed`. `turn`: `idle`, `streaming`, `waiting`, `cancelled`. `usage` is `{"input_tokens":120,"output_tokens":340}` when the caller supplies `Some`, else `null`; a supplied `Some(0, 0)` is encoded as zeros (the caller's rule for when to supply `Some` is in section 3). `session.title` is a string or `null`. No other field is ever added. `from_inputs` returns `None` when `session` is `None`; then the command does not run on that tick.

`pending_prompts` is the count for the focused session only. The format document explains why: a script reading version 1 treats the number as "the session I am looking at is blocked on me N times", and the install-wide count lives on Talaria's own needs-you surface. A prompt belonging to a session no longer shown does not count. `needs_you` (display) and `pending_prompts` (document) are separate fields on purpose; test 19 pins that.

### 5.2 The environment

`build_child_env(parent, allowlist, is_credential_name)` returns the child's whole environment, sorted by name. The child is started with `env_clear()` and exactly these.

1. Candidate names, in order: `PATH`, `HOME`, `SHELL`, `TERM`, `TMPDIR`; `LANG`; every name starting `LC_`; `TALARIA_CONFIG_DIR`, `TALARIA_GATEWAY_URL`, `TALARIA_PROFILE`, `TALARIA_LOG_LEVEL`, `TALARIA_STATUS_INTERVAL`; then each name on the allow-list. Only names present in `parent` are considered. The issue's REQ-11 governs: a `TALARIA_*` name that is not one of the five is never a candidate, so an allow-listed `TALARIA_OTHER` is skipped; an allow-list entry equal to one of the five, or to a name already listed, adds nothing.
2. For each candidate: if its upper-case form is `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `AWS_ACCESS_KEY_ID` or `GITHUB_PAT`, skip it. If `is_credential_name(name)` is true, skip it. Otherwise forward it with its value passed through the by-name cleaner.
3. The cleaner: for `TALARIA_GATEWAY_URL` only, parse the value as a URL and rebuild it from scheme, host (IPv6 in brackets), port and path, with no query, fragment or user information. A value that does not parse as a URL is not forwarded at all. The format file says "scheme, host, and path only"; the port is read as part of the host, as the Python client does (`talaria/status/contract.py` lines 262 to 271 rebuild the value from `hostname` and `port`, with no query, fragment or user information). Tests 27 and 54 and UAT-3 require the port. If the operator wants the port dropped, that is a one-line change to this rule and those three checks; until then the Python reading stands (question 11).
4. Names that are empty or contain `=` or a NUL byte are ignored.

The deny list of four names is defence in depth. Under `P1-04`'s rule (its REQ-6: for example `^(.*[-_])?(api|private|public|access|secret|signing)[-_]?keys?$`, `^(.*[-_])?pass(word|phrase)$`, `^(.*[-_])?token$`) `OPENAI_API_KEY`, `ANTHROPIC_API_KEY` and `LANGCHAIN_API_KEY` are flagged, but `AWS_ACCESS_KEY_ID` and `GITHUB_PAT` are not, and the shared rule lives in another crate and can change; a fixed list here does not depend on it. The format file defines the credential shapes as "the same pattern set Talaria's recorder uses", so whatever `P1-04` flags is the contract. `LANG` must match exactly: matching it as a prefix would forward `LANGCHAIN_API_KEY` and `LANGSMITH_TRACING`. Tests 24 and 29 use a check that flags nothing, so they prove this unit's own rules and not `P1-04`'s. The cleaner is keyed by name and runs on every path so that the allow-list cannot re-forward the raw URL (the Python client had exactly this bug).

`is_credential_name` is the recorder's `is_suspicious_key` from `P1-04` (module `redact` of crate `hermes-client`). The format document names the shapes it covers: `*_token`, `*_secret`, `*password*`, `*_api_key`. This crate does not depend on `hermes-client` at run time; `P1-12` passes the function in. Tests use it through a dev-dependency (test 30). Its exact signature is unverified until `P1-04` merges (section 14).

## 6. Output, process and refresh

### 6.1 Reading and parsing output

Limits (`CommandLimits::default()`): 2 seconds, 16384 stdout bytes, 4096 stderr bytes, 8 rows.

Before the text is split, remove one `\r` immediately before each `\n` (and one at the very end), so output written for Windows does not show `␍`. A row is blank when it is empty after trimming whitespace, tested on the raw row; `sanitize` turns a tab into four spaces, so a tab-only row is blank either way. Empty output means zero bytes (`NoOutput`). Output of only newlines or blanks is not empty: it is one or more blank rows, `external_segment` returns `None`, and the segment clears with no marker (the Python client behaves so: its empty check is `text == ""`). The format file's "empty output produces a marker" is read as zero bytes.

```text
parse_output(raw, byte_limit, row_limit):
  cut = raw.len() > byte_limit; raw = raw[..min(len, byte_limit)]
  text = if !cut: utf8(raw) or Failure::InvalidUtf8
         else: the longest valid prefix; a sequence that is only incomplete at the very end is tolerated,
               a genuinely invalid byte is Failure::InvalidUtf8
  if text is empty: Failure::NoOutput
  if !cut:
    parse the whole text as JSON (serde_json). If it is an object:
       require "version" == 2, only keys {version, rows}, "rows" a list;
       each entry a string, or an object with only {text, color?}; text a string; color a string
       any violation: Failure::InvalidDocument(reason)
       rows = entries (colour name -> Tone::from_token; default Text)
       then apply the row bound; return Rows
    otherwise (JSON scalar, array, or not JSON): plain text
  lines = text.split('\n'); drop one trailing empty entry when text ends with '\n'
  rows = lines as ExternalRow { text, tone: Muted }
  if rows.len() > row_limit: keep the first row_limit - 1, then a row "… truncated (<total> rows)"
  Rows { rows, truncated: cut || row bound applied }
```

Bound for document rows is the same (first 7 plus marker `… truncated (<n> rows)`, tone `Text`). An empty `rows` list is a valid document and yields no rows; the external segment then disappears. A text of just `\n` is one blank row; `external_segment` returns `None` when no row is non-blank after trimming. `external_segment(&CommandResult)` returns, for `Rows`, the first non-blank row's trimmed text and tone; for `Failure(f)`, `ExternalSegment { text: f.marker(), tone: Warning }`.

`Failure::marker()` text, exactly:

| Failure | Marker |
|---|---|
| `NoOutput` | `status: no output` |
| `InvalidUtf8` | `status: invalid output (not UTF-8)` |
| `InvalidDocument(_)` | `status: invalid script document` |
| `NonzeroExit { code: Some(n), stderr_line }` | `status: command failed (exit n)` plus `: <stderr_line>` when present |
| `NonzeroExit { code: None, .. }` (killed by a signal) | `status: command failed (signal)` plus the same suffix |
| `TimedOut` | `status: command timed out` |
| `NotFound` | `status: command not found` |
| `SpawnFailed(_)` | `status: could not start command` |

`external_segment` is stateless and used by the demo. The application uses `ExternalDisplay`, which keeps the last good segment so that a failure never blanks the line (the format file: "output problems never blank it"):

```text
ExternalDisplay { last_good: Option<ExternalSegment>, shown: Option<ExternalSegment> }
apply(result):
  Rows with a non-blank row: last_good = shown = that row's segment
  Rows with none (empty list, or only blank rows): last_good = shown = None   // an explicit empty list clears it
  Failure(f): shown = Some { text: last_good.text + " · " + f.marker() (just the marker when last_good is None), tone: Warning }
              last_good is unchanged
segment() -> shown
```

The reason strings inside `InvalidDocument` and `SpawnFailed` are kept for logs and are not shown (the Python client appended them; the status row is too narrow and a spawn error can hold a path). `stderr_line` is the first non-blank line of stderr, decoded lossily from at most 4 KiB. When stderr passes its cap the group is killed, the exit status is ignored (it is Talaria's doing) and stdout is parsed as for a good run, so a command that prints nothing to stdout and floods stderr gives `status: no output`.

Output of exactly 16384 bytes is not past the cap: it is not cut, not flagged, and parses normally. The cap applies from 16385 bytes.

The format file says "only the first 8 lines are shown" and "both truncations are marked visibly"; seven rows plus the marker row satisfy both, which is what the Python client does (`talaria/status/runner.py` lines 350 to 356).

### 6.2 Running the command

```text
run_command(spec, env, stdin, limits):
  cmd = Command::new(argv[0]).args(argv[1..]).current_dir(launch_dir).env_clear().envs(env)
        .stdin(piped).stdout(piped).stderr(piped).process_group(0).kill_on_drop(true)
  spawn: NotFound -> Failure::NotFound; any other error -> SpawnFailed
  record the child's pid in the shared state before the first await   // so shutdown can always find it
  if the stopping flag is set: kill the group, reap, return           // shutdown won the race while the child was starting
  within limits.timeout (one deadline for all of this):
     concurrently:
       a. write stdin, ignore broken pipe, close it
       b. read stdout and stderr, each up to cap + 1 bytes; when a stream passes its cap, kill the group at once
       c. wait for the leader to exit, then kill the group at once   // closes pipes that a helper holds open
     when all three are done, the pipes have reached end of file
  on timeout: Failure::TimedOut
  always, on every path (success, failure, timeout, cancel): kill the process group, reap, then clear the recorded pid (drop guard)
  exit status nonzero and no cap overflow: NonzeroExit { code, stderr_line }
  otherwise parse_output(stdout)
```

Notes that matter: the child leads its own group (`process_group(0)`), so the group id equals its pid and killing the group reaches helpers it started. Kill the group on every path, not only on timeout: a command such as `worker & echo ok` exits at once with status 0 while the worker holds the pipes open. Step c is what makes that run finish at once: the leader exits, the group is killed, the pipes close, and the reads end, so the run returns `Rows` with `ok` in milliseconds, not `TimedOut` after 2 seconds. The kill cannot lose output: bytes the leader already wrote stay in the pipe and are read to the end. A process group exists while any member lives, so the kill still works after the leader was reaped; test 51 proves it on both platforms. The kill is safe code: `let pid = Pid::from_raw(i32::try_from(id).ok()?)?; let _ = rustix::process::kill_process_group(pid, rustix::process::Signal::KILL);` where `id` is tokio's `Child::id()` (`None` once the child is reaped, so keep the id recorded at spawn). In rustix 1.1.4, `kill_process_group(pid: Pid, sig: Signal) -> io::Result<()>` is a safe function (`src/process/kill.rs` line 35) and `Pid::from_raw(raw: RawPid) -> Option<Pid>` is a safe `const fn` that returns `None` for 0 (`src/pid.rs` line 43); only `Pid::from_raw_unchecked` is `unsafe`. Ignore `ESRCH` (the group is gone) and `EPERM` (the id was recycled by a group this user cannot signal), as the Python client does. Clearing the recorded id when the run ends matters for the same reason: `shutdown` or `Drop` hours later would otherwise signal a group id the kernel may have given to an unrelated process. After a cap overflow the exit status is Talaria's doing, not the command's, so report the bounded output, not a failure.

### 6.3 Refresh policy and the service

```text
decide(now, document, running):
  changed = (document != last_document)         // a policy that never ran counts as changed
  pending = changed                             // recomputed at every call, never sticky: a change
                                                // that is undone leaves nothing pending
  if running: return Skip(Running)
  match last_start:
    None: Run
    Some(s): if now - s >= interval: Run
             else if changed: if now - s >= 1 s: Run else: Skip(TooSoon)
             else: Skip(Unchanged)
  on Run: last_start = now; last_document = document; pending = false

RefreshPolicy::next_wake(now):                  // the earliest time decide could say Run if nothing runs meanwhile
  never run: Some(now)
  pending: Some(last_start + min(1 s, interval))
  else: Some(last_start + interval)
```

`StatusCommandService::next_wake(now)` returns `None` while a command runs, because nothing can start until it ends and an instant already in the past would make the application ask again at once, in a loop, for up to 2 seconds. When the command ends, `done` fires; `P1-12` then asks `next_wake` again and calls `on_tick` at once if the instant is not in the future. An application that is idle (no command running, nothing pending, interval not reached) sleeps until `next_wake` and makes no other wake-ups.

The format file says the command runs "on every tick" and that the interval "sets the tick cadence". This policy keeps that: with an unchanged document it runs once per interval, exactly as before, and the interval is the maximum wait. The extra run on a change, at least 1 second after the last start, is an addition to that behaviour, not a replacement of it, and no command that exits promptly can tell the difference. The roadmap's text for this unit ("refreshed only when its inputs change or on its interval") asks for it. Question 7 in section 13 records it for the operator.

The minimum gap of 1 second is this unit's choice, justified by H8 (usage changes about once a second while a reply streams) and by the cost of starting a process: without it a streaming reply would start the command on nearly every token tick. The interval is a maximum wait; it never delays a change that is at least one second old. The policy compares the encoded document bytes, not `StatusInputs`, so a change to something the command cannot see (cost, folder) never starts it.

The caller's side of the contract (for `P1-12`): call `on_tick` on every change of the document and again at each instant `next_wake` reports. An application that wakes only at `next_wake` would otherwise never see a change. While `from_inputs` returns `None` (no session) there is no document, the caller does not call `on_tick` and does not consult `next_wake` (a fresh policy reports "now" and would make it wake in a loop). A test drives the policy only at the instants `next_wake` reports (test 44).

`StatusCommandService::on_tick(now, doc, done)` encodes the document, asks the policy, and on `Run` marks itself running, spawns (with `tokio::spawn`, so it must be called inside a Tokio runtime; tests use `#[tokio::test]`) a task that runs the command (`env` is `build_child_env` over the parent environment captured at construction) and, when finished, clears the running flag first and then calls `done(result)`. The task clears the flag even if it is cancelled (use a drop guard). `done` is where `P1-12` sends the result into the application event channel, which then updates an `ExternalDisplay`. `shutdown().await` sets a stopping flag, kills the recorded group if one is still recorded, waits for the task to end, and is safe to call twice or after a finished run (it signals nothing then). The task checks the stopping flag before it starts the child and again right after it records the child's pid; if the flag is set it kills the group and returns, so a shutdown that arrives while the child is starting cannot leave it running or make `shutdown` wait out the 2 second timeout. `Drop` kills the recorded group synchronously (if still recorded) and does not wait. After `shutdown` has been called, `on_tick` starts nothing and returns `Skip(Stopped)`.

## 8. What the Python client learned (port these, with their tests)

Each item was a real defect found in the Python status runner (`talaria/status/runner.py`, `contract.py`) and fixed.

1. **The group kill must not depend on the leader being alive.** An early version swept the group only while the leader was unreaped; `worker & echo ok` reaps the leader at once and the worker leaked every tick. Kill on every path. Rust tests 50, 51.
2. **Cap while reading.** `communicate()` read until end of file and truncated afterwards; one flooding command took resident memory from 28 MB to over 3 GB in a single tick. Read one byte past the cap, then kill the group. If one stream passes its cap, kill at once, or the other pipe never reaches end of file and the tick deadlocks into a timeout. Test 53.
3. **A child that exists but is not yet recorded is a child nothing can kill.** Spawn returns while setup continues; a shutdown in that window left the child alive. Record the pid before the first await after spawn. Test 56 includes a shutdown during start-up.
4. **Descriptors leak when a timeout kill does not free the pipes.** Two per tick, steady. Close the pipe handles explicitly; in Rust, dropping the `Child` and its stream handles does it. Test 57.
5. **A repeated sanitiser in one branch is not a boundary.** The gateway URL was cleaned inside the `TALARIA_*` loop, then the allow-list loop re-forwarded it raw. Clean by name, on every path. Test 27.
6. **`LANG` is an exact name, `LC_` a prefix.** Test 24.
7. **Userinfo is credential material.** Rebuilding the URL from its netloc forwarded `user:password@` while carefully removing the query. Rebuild from host and port. Test 27.
8. **Do not double the timeout budget.** Waiting again after the timeout fired both doubled the wait and leaked descriptors. One deadline for the whole run.
9. **Bad argv never reaches the kernel in some cases** (an embedded NUL). It must still produce a marker, not a panic. Test 52.
10. **Version 2 documents are detected on the whole text before splitting lines**, because a pretty-printed document spans lines. A byte-cut output skips the document branch. Tests 36, 37.
11. **A recorded process id must not outlive its run.** Clear it when the run ends, ignore `ESRCH` and `EPERM`, and check the stopping flag before the child starts and right after its pid is recorded. Test 56.
12. **A "change pending" flag must be recomputed, not latched.** A latched flag that survives a reverted document leaves `next_wake` in the past and the application asking again at once. Recompute it at every call and let the service report no wake-up while a command runs. Tests 43, 55.

`render` prints `LinePlan::text()` and a newline. No other output.

`document` prints the encoded document (one line, ends with a newline).

`run-command` builds a `CommandSpec` (launch directory is the current directory; allow-list from `--allow`), takes the parent environment from the real process environment, passes `is_suspicious_key`, builds the `full` fixture's document, runs once with the default limits (timeout from `--timeout-ms` when given), and prints these lines, then exits 0 whatever the outcome:

```text
outcome=<ok|no_output|invalid_utf8|invalid_document|command_failed|timed_out|not_found|spawn_failed>
elapsed_ms=<integer>
marker=<marker text, or - when the outcome is ok>
rows=<count>
truncated=<true|false>
row[0]=<row text, sanitized>        (one line per row, up to 8)
line=<the status line at --render-cols, with this result as the external segment>   (only with --render-cols)
```

Row text and the line are passed through `sanitize` before printing, so the program never prints a raw escape byte. `rows` and `truncated` are `0` and `false` for failures.

`watch` builds a `StatusCommandService`, ticks it every 100 ms at offsets 0, 100, ..., `seconds * 1000 - 100` ms (no tick at the end time) for `--seconds` seconds with the `full` fixture's document, changing `pending_prompts` every `--change-every` seconds (0 means never; each change adds 1, starting at 0), and prints one line `spawn offset_ms=<n>` for each time `on_tick` returned `Run`. After the time is up it waits for any command in flight and prints `spawns=<n>`.

## 12. Design reasoning and rejected alternatives

- **Drop whole segments by priority; no per-segment shrinking tiers.** Hermes's bar tests each tail segment against the remaining space in priority order, which lets a short low-priority segment reappear after a longer high-priority one is gone. A prefix of the priority list is easier to predict, to test as a property, and to explain to a user. Cost: at some widths a short, unimportant segment is dropped although it would fit. Accepted.
- **One external row.** The Python client had an in-body region of up to 8 rows and a bottom bar of rows. The new design has one status row (requirement R2: one status line). The first non-blank row is shown; the other rows are read, bounded and ignored. Showing the rest would need an overlay and is not in the roadmap.
- **The caller fills `StatusInputs`.** If this unit read `SessionState` it would depend on `P1-05` and on Hermes types, and the terminal crate must hold no protocol or session state. A plain struct keeps the unit buildable alone, which the roadmap wants (a Haiku-tier unit).
- **Dependency injection for the credential check.** `P1-04` owns the one copy of the credential-name rule. A copy here would drift. A normal dependency from the terminal crate on `hermes-client` would break the layering. A function passed in by the wiring unit keeps one copy and the layering.
- **A 1 second minimum gap.** See 6.3. Alternatives: only the interval (what Python did; ignores "when its inputs change"), or every change (spawns per token). The gap is a constant, not a setting, to keep the surface small; if the operator wants it configurable that is a separate change.
- **Markers without detail.** Spawn errors and document reasons can carry paths or document content; the row is narrow. They go to the log, not the row.
- **A failure keeps the last good text.** The format file promises that output problems never blank the bar, and that every failure produces a marker. With one row both are met only by showing the two together (`<last good text> · <marker>`). Cost: the pair is long, and the external segment is the first to be dropped on a narrow terminal, so the marker can be hidden at narrow widths. Accepted: the marker is a notice, and the line is not the only place a failure can be shown.
- **Policy state is recomputed, not latched.** A flag set when the document changes and cleared only on a run made the application ask again at once after a change that was undone. The policy now compares the document at every call, and the service reports no wake-up while a command runs.
- **No second ratatui `Paragraph`-style widget.** `StatusSection` writes cells directly into the buffer, one style per piece, so a snapshot test can check the style of a named cell.

## 13. Decisions the operator owns

1. **Configuration table name.** The roadmap's text for `P1-08` says the table is `[status_line]`; the frozen format document, `docs/configuration.md` and the Python code use `[status]` with `command` and `interval_seconds`. Recommendation: keep `[status]`, since the format document is the contract and existing user files use it. It affects `P1-08`, not this unit.
2. **Session cost has no live source in Hermes v0.22.4** (section 2.2). Options: accept a segment that stays hidden until Hermes fills `cost_usd`; propose the change upstream (it belongs on the upstream list in `08-risks-and-open-questions.md`); or compute cost in the client from stored session rows later. Recommendation: accept now, propose upstream.
3. **Rows beyond the first.** The format document says up to 8 rows are shown, and that an invalid document leaves the previous good rows in place. One status row shows one row: the first non-blank one. The other rows are still read, validated and bounded to 8 (the first 7 plus a truncation marker when there are more), so the contract's limits hold, but they are not drawn. For a failed run the segment shows the last good text and the marker together (section 6.1, `ExternalDisplay`), which keeps the promise that output problems never blank the bar. Recommendation: this, for phase 1; show more rows only with an overlay, as a later unit.
4. **Matching Claude Code's status JSON.** Claude Code's status script receives context use, cost, rate limits, cache and worktree (parity row `sl.bar`). The frozen Talaria document does not carry them. Matching it means a version 2 input document and a new unit. Recommendation: not in phase 1; ask again at the phase 2 re-plan.
5. **Where the session settings live.** The session reducer (`P1-05`) keeps no model setting, effort, folder or branch. Options: extend `P1-05` before it merges; keep a small `SessionInfo` store in `talaria-app` fed by the snapshot `info`, `session.info` events (merged field by field) and a `session.info` call after each turn. Recommendation: the second, owned by `P1-12`. This is a planning decision, listed here because this unit cannot make it.
6. **What the working count counts in phase 1.** With one session it would always read 1 while a turn runs. Recommendation: pass 0 until a second session exists, so the segment stays hidden until the fleet exists.
7. **When the command runs.** The format document says the command runs "on every tick" and that `interval_seconds` "sets the tick cadence". The roadmap says the command is "refreshed only when its inputs change or on its interval". This unit does both: it runs at least once per interval and also runs earlier, no sooner than 1 second after the last start, when the encoded document changed (section 6.3). The extra run is an addition, so the unit does not edit the frozen file. The alternatives are interval only (the Python client's behaviour; ignores the roadmap) and every change (a process start per streaming token). Recommendation: keep the policy. If you want the format document to say it, that is a one-sentence edit under the file's own change rule, and it is yours to approve.
8. **Wording inside the frozen format document.** Lines 90 to 92 say anything that is not a JSON object stays plain text and "a script printing a bare number or a bare word never trips this protocol"; line 111 says a document that is `null` is rejected. A JSON `null` is a scalar. This unit follows the first rule, which is also what the Python client does (`talaria/status/contract.py`: scalars and arrays return plain text), so `null` is a plain row. Recommendation: fix line 111 in a future edit of the file to say "an object that is wrong-typed, version-jumped or carries unknown fields".
