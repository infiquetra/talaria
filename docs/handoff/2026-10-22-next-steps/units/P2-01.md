## 1. What this unit adds, in one picture

Today (after phase 1) a tool call is one plain line from `PlainCellLines` in `crates/talaria-tui/src/history.rs` ({{P1-06}}). After this unit, a turn like the recorded ones reads like this at 100 columns:

```text
⏺ Search(*)  ✓ · 6.5s
⏺ Shell(rm -rf .pytest_cache && ls -a)  ✓ · 0.8s
  ⎿  .
     ..
     .git
     … +2 lines (Ctrl+O to view)
⏺ Edit notes.txt  ✓ +1 -1 · 0.1s
    1   alpha
    2 - beta
    2 + gamma
⏺ Shell(ls /nonexistent-dir)  ✗ exit 1 · 0.1s
  ⎿  ls: /nonexistent-dir: No such file or directory
⏺ Preparing Shell…                                   (live region only, dim)
```

The diff rows use the line numbers from the hunk header, the sign column is plain ASCII so a copied row is still a diff row, and colour is an aid, never the only signal. The `(Ctrl+O to view)` hint appears only once {{P2-02}} has merged (issue, Dependencies).

This refines the architecture's screen sketch ([05-architecture.md](../05-architecture.md#the-screen)), which shows `Bash(pytest -q)  ✗ 1 failed`, U+2212 minus signs and "expandable output". Talaria shows `Shell`, ASCII signs, Hermes-derived headlines only (REQ-13; "1 failed" is output text, shown in the body), and expansion in {{P2-02}}'s pager.

## 5. The diff model and parser (`crates/talaria-core/src/diff.rs`)

### 5.1 Types

```rust
pub struct DiffModel { pub files: Vec<DiffFile>, pub notes: Vec<String> }   // notes: model-level lines that are not diff rows
pub struct DiffFile  { pub old_path: Option<String>, pub new_path: Option<String>, pub hunks: Vec<DiffHunk> }
pub struct DiffHunk  { pub header: String, pub old_start: Option<u32>, pub new_start: Option<u32>, pub rows: Vec<DiffRow> }
pub struct DiffRow   { pub kind: RowKind, pub old_no: Option<u32>, pub new_no: Option<u32>, pub text: String }
pub enum RowKind { Added, Removed, Context, Note }
pub struct DiffStats { pub files: usize, pub added: usize, pub removed: usize }

pub fn parse_diff(text: &str) -> DiffModel;
impl DiffModel {
    pub fn stats(&self) -> DiffStats;            // Added and Removed rows only; files = files.len()
    pub fn is_empty(&self) -> bool;              // no file and no note
    pub fn display_path(&self) -> Option<&str>;  // single file: new_path, else old_path, with a leading a/ or b/ removed
    pub fn row_count(&self) -> usize;            // rows plus one per hunk header after the first plus one per file when files > 1
}
```

Paths are stored as written (`a/notes.txt`); only `display_path()` removes the prefix. `DiffRow.text` excludes the sign character. The model holds no styles: {{P2-09}} (checkpoint diffs) and {{P2-02}} (pager) reuse it. All types derive `Debug`, `Clone`, `PartialEq`, `Eq` (and `Copy` for `RowKind` and `DiffStats`).

### 5.2 Parsing rules, line by line

Input is text with escape sequences already removed. Split on `\n`; strip one trailing `\r` per line; drop the final element when it is empty (the text after the last newline). The parser keeps: the open file (if any), the open hunk (if any), and for the open hunk its remaining old and new counts, or "unknown" when its header did not parse.

**Inside an open hunk**, try these first:

1. Counts known and at least one remaining:
   - a line starting with `-` while old remaining is above 0: `Removed` row with `old_no`; old remaining minus 1. This holds even when the line starts `--- ` (a removed line whose text starts `-- `).
   - `+` while new remaining is above 0: `Added` row with `new_no`; new remaining minus 1 (also for `+++ `).
   - a space, or an empty line, while both are above 0: `Context` row with `new_no` and `old_no`; both minus 1 (an empty line is a context row with empty text; some generators drop the leading space).
   - `\` (for example `\ No newline at end of file`): `Note` row with no numbers.
   - anything else: close the hunk and continue with the outside rules.
2. Counts known and both spent: a `\` line is a `Note` row of this hunk; anything else closes the hunk and continues with the outside rules.
3. Counts unknown (the header did not parse): a line starting with `+`, `-`, space or `\`, or an empty line, is a row as above but with no numbers, except that a line starting `--- ` or `+++ ` closes the hunk and continues with the outside rules. Anything else closes the hunk and continues.

**Outside a hunk**, the first rule that matches:

1. Before any file or hunk, a line whose first non-space character is `┊`: the Hermes header. Drop it. Never read its words (they are localised).
2. A line starting `@@`: open a hunk (opening an anonymous file with both paths `None` if none is open). When the line matches `^@@ -(\d+)(?:,(\d+))? \+(\d+)(?:,(\d+))? @@`, set `old_start` and `new_start` and the remaining counts (a missing count means 1, as in Hermes's `@@ -1 +1 @@`); numbers that overflow `u32` count as not parsed. Otherwise both starts are `None` and the counts unknown. The header text is the whole line.
3. A line starting `diff --git `: open a new file. Its paths come from splitting the rest at the last ` b/` (old is the part before, new is `b/` plus the part after); if there is no ` b/`, both are `None`. Mark the file as "git header, no hunk yet".
4. File metadata lines, dropped: lines starting `index `, `new file mode `, `deleted file mode `, `old mode `, `new mode `, `similarity index `, `dissimilarity index `, `copy from `, `copy to `. Lines starting `rename from ` and `rename to ` set the open file's old and new path.
5. `--- <path>`: remember the old path. `+++ <path>`: when the open file is marked "git header, no hunk yet", set its paths (old from the remembered `---` line) and clear the mark; otherwise open a new file with the remembered old path and this new path. Paths are the text after the four-character prefix, cut at the first tab, trimmed; `/dev/null` becomes `None`.
6. A line containing ` → ` (U+2192 with a space on each side; Hermes's file line, H11): open a new file. The old path is the text before the first ` → `, the new path the text after it, both trimmed; `/dev/null`, `a/?` and `b/?` become `None`. Paths may contain spaces.
7. Any other non-empty line (for example Hermes's localised `… omitted 12 diff line(s)`, or `Binary files a/x and b/x differ`): push it to `DiffModel.notes`. Empty lines are dropped.

Line numbers never decrease and never overflow (`checked_add`; on overflow stop numbering that hunk, leaving `None`). A row is numbered from the counters of its hunk; a context row increments both counters, an added row the new one, a removed row the old one.

Why counts: a raw diff's hunk header states how many old and new lines follow (difflib and `git diff` always write exact counts, H13). Using them is the only way to tell a removed `-- comment` row from a new file header. Hermes's rendered form has already lost such a row (H11); the parser then simply sees one row fewer, and the hunk closes at the next non-row line.

### 5.3 Why one parser for three dialects

The gateway sends Hermes's rendered form (H11). A `patch` result carries a raw unified diff (H13). {{P2-09}} will receive `git diff --cached --no-color` output from the checkpoint manager (`tools/checkpoint_manager.py:1066`), which adds `diff --git`, `index` and mode lines. One parser keeps the three consistent, and file metadata never shows up as notes.

### 6.2 Result parsing

`ToolCell.result` is a string (H5). Parse it once with `serde_json`.

- A JSON object: the output text is the first string field among `output`, `stdout`, `output_preview`, `content`, `result`, `message`. `exit_code` counts when it is a JSON integer (`true`/`false` never count). `tool_note` is a string `truncation_note`. `cut_by_hermes` is `truncated == true`.
- A cut result (`truncated == true`): take the string under `output` or `error`. If it starts with `{"K": "` where K is one of the output keys above, decode the rest as the body of a JSON string, leniently: `\n`, `\t`, `\r`, `\"`, `\\`, `\/`, `\b`, `\f` and `\uXXXX` (with surrogate pairs joined; a lone surrogate becomes U+FFFD) are unescaped; decoding stops at the first unescaped `"` or at the end of the text; an escape cut short at the end is dropped. The result is the output text and the exit code is `None` (it came after the output and was cut, as did `error`, `user_summary` and every other key). Otherwise (the inner text does not start with that form) the inner string is the output text as it is, exactly as for a result that is not JSON. The headline rule for a failed cut result is in 6.3.
- Any other JSON value, or text that is not JSON: the output text is the raw string.

Output text cleanup, in order: remove escape sequences with the same rules {{P1-05}} uses for `inline_diff` (reuse its function if public; otherwise copy the rules into this module with a test); turn `\r\n` into `\n`; on each line keep only the text after the last lone `\r` (what a terminal would show after a progress bar); drop trailing empty lines. Control characters left over are replaced at render time by {{P1-06}}'s `history::sanitize`.

`lines` is the number of lines after cleanup (0 for empty text), counted with a scan for `\n`, never by building wrapped rows: the number of `\n` characters plus 1 when the text does not end with `\n`. A partial last line (for example the end of a cut result, which usually stops partway through a line) counts as a line.

### 6.3 Outcome

| `ToolCell.status` ({{P1-05}}) | `OutcomeView` |
|---|---|
| `Running` | `Running` |
| `Succeeded` | `Succeeded { headline }`: `summary` when non-blank (H9: only from the in-process gateway, so normally absent); else `exit N` when the output's `exit_code` is a non-zero integer; else none. Hermes marks any non-zero `terminal` exit as a failure (H17), so `exit N` on a success appears only for other tools that report an integer `exit_code`. |
| `Failed` | `Failed { headline, detail }`: see below |
| `Unfinished` | `Unfinished` |
| `Unknown` | `Unknown` (rows from resumed history, H20) |

Failed headline: the failure text is the first non-blank string among the result object's `user_summary`, `error`, `exit_code_meaning`, `message`, `reason`; for a result that is not a JSON object, the raw text. For a Hermes-cut result (`truncated: true`): when the inner text was decoded as output (it started `{"K": "`), there is no failure text, so the headline is `failed` (the keys that would explain the failure came after the output and were cut); when the inner text was kept as it is, that text is the failure text, as for a result that is not JSON. A cut result never has an exit code, so its header never shows `exit N`. The headline is the first non-blank line of the failure text. If `exit_code` is a non-zero integer, prefix `exit N: ` (or use `exit N` alone when there is no text). If nothing is found, `failed`. `detail` is the whole failure text when it has more than one line or more than 60 characters.

Examples (section 4 payloads): plain `ls` failure gives `exit 1` (the message is in `output`, shown in the body); the `grep` shape gives `exit 1: No matches found (not an error)`; the launch failure gives `exit -1: Failed to execute command: boom`; the `user_summary` shape gives `exit 1: Command denied by the user`; raw text `permission denied\nmore` gives `permission denied` with that detail; `{}` gives `failed`; section 4's cut result with `is_error: true` (outer key `error`) gives `failed` with no detail, and its body shows the decoded output.

### 6.4 Diff selection

1. `ToolCell.diff` (already escape-stripped by {{P1-05}}): parse; use it when not empty.
2. Else, when the name is `patch` and the result object has a non-blank string `diff`: strip escapes, parse, use when not empty.
3. Else none.

An "edit cell" is any cell whose view has a diff, whatever its status. Every edit cell uses the edit header form (7.2: no parentheses) and, when `context` is blank, the subject `display_path()`. A succeeded, unfinished or unknown edit cell also shows the stat and the diff rows. A failed edit cell shows neither: its header is `✗ <headline>` and its compact body follows the failed rows (7.3); it keeps its diff in the view for the pager's full detail (7.5).

### 6.5 Duration and progress

`format_duration(s)`: negative or not finite gives `None`. `s < 10.0`: `format!("{:.1}s", s)`. `s < 60.0`: `format!("{}s", s.round_ties_even())`. Else `let total = s.round_ties_even() as u64`, minutes `total / 60`, seconds `total % 60`, `Xm Ys`, or `Xm` when seconds are zero. This matches H18 for every finite, non-negative value in issue test 20. It deliberately differs for the two other values there: for -1 Hermes prints `-1.0s` (Python's format keeps the sign) and for NaN Hermes's `round()` raises `ValueError` (both checked against `tui_gateway/tool_progress.py:72-80`); Talaria returns `None` for both, because a real duration is never negative or NaN and a wrong number is worse than none.

`format_progress`: with `percent` an integer in 0 to 100: `42%`; else with `total` above 0: `3/10` (each number printed without a trailing `.0` when it is whole, else with up to one decimal); else nothing for the number. Then ` · <message>` when the message is non-blank (first line only). `None` when both parts are empty.

### 7.2 Header line (always exactly one row in compact form)

```text
⏺ <title>(<subject>)  <outcome segment>        a subject, no diff
⏺ <title> <subject>  <outcome segment>        edit cells (6.4: the view has a diff, any status): no parentheses
⏺ <title>  <outcome segment>                  no subject (quiet tools, label titles, a blank command and context)
```

Examples: `⏺ Tasks  ✓` (a quiet `todo_list` call); `⏺ Linear: create issue +1  ✓ · 0.4s` (a label title); `⏺ Edit notes.txt  ✗ old_string not found · 0.1s` (a failed edit: edit form, no stat). The unknown state's dim row with no mark is `⏺ <title> <subject>  +A -R` for an edit and `⏺ <title>(<subject>)` (no segment, no trailing spaces) otherwise.

| State | Segment |
|---|---|
| Running | `… running`, then ` Ns` when `elapsed` is at least 1 s (whole seconds, rounded down), then ` · <progress>` when present |
| Succeeded, no diff | `✓`, then ` <headline>` when present, then ` · <duration>` when present |
| Succeeded, diff | `✓ +A -R` (one file) or `✓ F files +A -R`, then ` · <duration>` |
| Failed (with or without diff) | `✗ <headline>`, then ` · <duration>` |
| Unfinished | `◌ not finished` (a diff, if any, adds ` +A -R`) |
| Unknown | no mark; an edit shows `+A -R`; the whole row is dim |

Glyph `⏺` style: running `glyph_running`, succeeded `glyph_ok`, failed `glyph_failed`, unfinished and unknown `glyph_muted`. `✓` uses `glyph_ok`, `✗` uses `glyph_failed`; the rest of the segment uses `meta`, except a failed headline, which uses `error`.

Fitting to `width` (columns counted with `unicode-width`, after `history::sanitize`): the two spaces before the segment shrink to one first. Then cut in this order until it fits: the subject (to a minimum of 8 columns, ending in `…`), the headline (to 12 columns), the duration and progress, the subject entirely, the headline entirely (and the stat), then the title (ending in `…`, down to nothing). The glyph, one space and the mark (`✓`, `✗`, `…`, `◌`) are kept at every width of 3 or more; at widths 1 and 2 only the glyph is drawn. Unknown cells have no mark; at width 3 or more they keep the glyph and as much title as fits. No header is ever wider than `width`.

### 7.3 Compact body

| Cell | Body |
|---|---|
| quiet tool | none |
| running | none (progress lives in the header) |
| succeeded, unfinished or unknown edit (has diff) | diff rows (7.4) with `max_rows` 40; when rows were hidden, `    … +N more diff lines` plus ` (<hint>)` when `expand_hint` is set; then the model's `notes`, dim, always |
| failed edit (any tool with a diff) | the failed rows below for its tool (shell or other); no diff rows |
| shell (`terminal`, `execute_code`), succeeded | output non-empty: first row prefixed `  ⎿  `, next rows `     `; at most 3 logical lines and 6 screen rows; then `     … +N lines` plus the hint when lines remain. Output empty: `  ⎿  (no output)` |
| shell, failed | output non-empty: as above with at most 6 logical lines and 10 screen rows. Output empty: up to 6 lines of the failure text (6.3) in `error` style, same prefixes; nothing when there is no failure text |
| any other tool, failed | when `detail` is set: up to 6 lines of it in `error` style, same prefixes; then `     … +N lines` when more remain |
| any other tool, succeeded | none |

Logical lines and the row limit: lines are laid out in order until the next one does not fit in the rows left. A line that only partly fits is cut, not hidden: its rows up to the limit are shown, and the last shown row ends with `…` (replacing its last column, so the row stays within `width`). That line counts as shown. `N` counts the logical lines after it (or after the line limit) that are not shown. So a 64 KiB output that is one logical line shows its first rows up to the row limit (6 on success, 10 on failure), the last ending `…`, and no more-line, because no further line exists. Lay out lazily: stop wrapping when the row limit is reached, so a long line is never wrapped whole in compact mode.

The hint: `expand_hint` is the whole text that goes inside the parentheses (for example `Ctrl+O to view`); the renderer adds only ` (` and `)`. `app.rs` builds it as `format!("{} to view", label)` from the `transcript_open` key's label (issue, Dependencies).

The cut note: when `cut_by_hermes` is true, the more-line (or, when there is none, the last output row) ends with ` (cut by Hermes at 32,768 characters)`. The note is part of that row's text for fitting (7.8): it is kept whole when the row fits, otherwise the row is cut with `…` like any fixed-text row.

Wrapping: by the rules in 7.8 (hard wrap at grapheme boundaries, continuation rows indented 5 spaces). {{P1-06}}'s `wrap_lines` takes no continuation indent, so this unit writes its own private wrapper in `tool_cell.rs` and `diff_view.rs` uses the same function.

### 7.4 Diff rows

```text
<indent><number right-aligned to W> <sign> <text>
```

- `indent` 4 spaces in a tool cell. `W` is the number of digits of the largest line number among the rows shown (at least 1).
- `Added`: number `new_no`, sign `+`, style `diff_added` for sign and text. `Removed`: `old_no`, `-`, `diff_removed`. `Context`: `new_no`, a space, `diff_context`. `Note`: no number, no sign, `diff_note`.
- Hunk header rows: `<indent><W spaces>   <header>` in `diff_hunk` style, shown before every hunk except the first hunk of the first file (the first hunk's position is already in its numbers).
- File rows: when the model has more than one file, `<indent><display path of that file>` in `diff_file` style before each file's hunks.
- Numbers use `line_number` style. A row without a number shows `W` spaces.
- Wrapped continuation rows: `<indent><W spaces>   <rest>` (number and sign columns blank), same style as the row. Only `Added`, `Removed`, `Context` and `Note` rows wrap; hunk header rows, file rows and model notes are fixed-text rows, cut to the width with `…` and never wrapped (7.8).
- The sign is plain ASCII so a row copied from scrollback still reads as a diff line; colour is never the only signal.

`max_rows` counts screen rows (after wrapping, including hunk header and file rows). A diff row is shown whole or not at all, with one exception: when the very first diff row alone needs more than `max_rows` rows, its first `max_rows` rows are shown, the last ending `…`, and it counts as shown. The function returns how many diff rows (`Added`, `Removed`, `Context`, `Note` rows) it did not show, which is the `N` of the more-line. Narrow widths: 7.8.

### 7.5 Full detail (for the pager, {{P2-02}})

Header as 7.2, but the subject is never cut: the header wraps instead. Then:

1. `  Arguments` (dim) and the `args` value pretty-printed with `serde_json::to_string_pretty`, each row prefixed 4 spaces (omitted when `args` is absent or an empty object). Keys appear in the order the `serde_json::Value` holds them; this unit does not change `serde_json` features, so tests use a one-key object or keys already in alphabetical order.
2. `  Output` (dim) and the whole cleaned output text (6.2), prefixed 4 spaces; for a JSON object with no text field, the pretty-printed object, with its `diff` key removed when the cell's diff came from it (6.4 step 2), so the diff is not printed twice. A failed cell shows `  Error` and the whole failure text instead when there is no output text.
3. `tool_note` (the terminal's `truncation_note`) as a dim row, when present.
4. The full diff (no `max_rows`), then notes.
5. ` (cut by Hermes at 32,768 characters)` when `cut_by_hermes`.

No row cap here; the pager virtualises. `expand_hint` is ignored. {{P2-02}}'s `Details::Expanded` corresponds to `Detail::Full` and `Details::Compact` to `Detail::Compact`. ### 7.6 Live region pieces

- Running cells reach the live region through the same `CellLines` the streaming tail uses ({{P1-06}}), so wrapping the application's renderer in `ToolCellLines` covers both scrollback and live region. Confirm this in {{P1-06}}'s merged code before Step 0 (issue stop condition 3).
- `DraftingLine`: `⏺ Preparing <title>…` (title by 6.1 from the drafted name) in `meta` style; height 0 when `SessionState::drafting_tool()` is `None`. In the application's `LiveView` it is the section directly after the streaming tail, before prompt cards, the status line and the composer.
- `ToolClock::observe(cells, now)` adds each running tool cell's id with `now` the first time it is seen and drops ids whose cell is no longer running. `elapsed(id, now)` is `now - first_seen`. The header shows whole seconds rounded down. `next_tick(now)`: for each running cell, `first_seen + (floor((now - first_seen) in seconds) + 1) s`; the earliest of these; `None` when nothing runs. So an idle screen schedules no frames (budget "Idle: zero frames when nothing changes", [05-architecture.md](../05-architecture.md#performance-budgets)). No spinner animation: the glyph is static, only the seconds change, which also suits reduced motion ({{P2-12}}).
- Wiring in `crates/talaria-app/src/app.rs` ({{P1-12}}'s `run`): on each state change call `clock.observe`, then `tool_cell_lines.set_clock(&clock, now)`, then draw; ask the existing redraw timer for a wake-up at `clock.next_tick(now)` when it is `Some`. Before Step 0, read {{P1-12}}'s merged `app.rs` and name, in the pull request, the call that schedules a wake-up at a given instant (for example a `tokio::time::sleep_until` arm in its event loop). The idle half is guarded by {{P1-11}}'s `bench` check (zero frames when nothing changes); the running half by UAT-4 (the seconds advance).

### 7.8 Fitting every row to the width

Every row `tool_lines` and `diff_lines` return is at most `width` columns, counted with `unicode-width` after `history::sanitize`. Rows are of three kinds.

1. **The header**: 7.2's cut order.
2. **Wrapped rows** (output and failure lines in the body, `Added`, `Removed`, `Context` and `Note` diff rows, and in full detail the argument, output and error lines, plus the full-detail header, whose continuation rows are indented 2 spaces): a fixed prefix (body: `  ⎿  ` on a line's first row, 5 spaces after, 5 columns either way; diff: `<indent><number to W> <sign> `, `indent + W + 3` columns, and `<indent><W spaces>   ` on continuation rows) followed by the text. The text area is `avail = width - prefix columns`.
   - Hard wrap (character wrap, not word wrap): split the text into grapheme clusters (`unicode-segmentation`) and fill each row up to `avail` columns; a cluster is never split; a cluster that does not fit in the rest of a row starts the next row. A cluster wider than `avail` itself (a two-column character when `avail` is 1) is drawn as `…`, one column. Each row therefore takes at least one cluster, so wrapping always ends.
   - Narrow fallback, body: when `avail` is less than 1 (width 5 or less), the prefix is dropped and the text wraps at `width` with no prefix.
   - Narrow fallback, diff: when `avail` is less than 1, the row falls back to the raw unified form: the sign (`+`, `-`, or a space for context and note rows) as a one-column prefix, the text after it, continuation rows with one space. At width 1 only the sign column is drawn and the text is not drawn (nothing to wrap, so nothing loops).
3. **Fixed-text rows** (the more-lines, `(no output)`, `Preparing`, hunk header rows, file rows, model notes, `  Arguments`, `  Output`, `  Error`, the `truncation_note` row): never wrapped. When one is wider than `width`, it is cut at a cluster boundary and its last kept columns are replaced by `…`, so the row is exactly `width` columns or fewer. At width 1 such a row is `…`.

"Ends with `…`" anywhere in this document (7.3, 7.4) means the same replacement: drop clusters from the end of the row until `…` fits within `width`, then append it.

Issue test 34 checks the hard wrap at width 40; issue test 35 checks every width from 1 to 200, including fixed cases at widths 1, 2, 5 and 8 with the two-column character `审` in the subject, the output and a diff row.

## 12. Design reasoning

- **Hermes's verdict decides success.** `is_error` is the executor's judgement (H5, H17). Recomputing it in the client would be a client-side imitation of agent logic ([05-architecture.md](../05-architecture.md#principles), principle 1). Hermes already explains informational exits (`exit_code_meaning`); Talaria shows those words in the headline instead of re-judging.
- **Expansion lives in the pager.** A finished cell is written once into native scrollback ([ADR draft 0009](../adr-drafts/0009-finished-output-lives-in-native-scrollback.md)); it cannot be expanded in place afterwards. So compact cells carry a "more" line with the key hint, and {{P2-02}}'s pager shows `Detail::Full`. This unit owns the content of both forms; {{P2-02}} owns the key and the overlay. The roadmap's "expandable output" is met when both have merged; this unit's acceptance is compact-only plus a tested full form.
- **Line numbers come from hunk headers**, which survive Hermes's rendering (H11). No file is read on the client.
- **Hunk counts over line shapes**, because only the counts can tell a removed `-- ` row from a file header (5.2).
- **ASCII signs** keep copied rows meaningful and keep meaning without colour.
- **The diff model is in `talaria-core`** because it is pure data shared by the pager and by rewind ({{P2-09}}); only styling is in `talaria-tui`.
- **No tool-name parsing beyond a title table.** Hermes asks clients not to parse names (H16); the table only chooses a short word to show.
