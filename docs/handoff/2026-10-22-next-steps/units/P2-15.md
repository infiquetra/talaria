## 1. What this unit adds, in one paragraph

Hermes already runs `/plan`, `/goal`, `/subgoal`, `/loop`, `/heartbeat`, `/yolo`, `/fast` and `/reasoning` for a Talaria session: unit P2-03 sends them through `slash.exec` and shows Hermes's reply as a plain System notice. That reply was written for chat platforms (Telegram, Discord), so it arrives as Markdown with emoji (`⚡ YOLO mode **ON** for this session — …`), and the standing state it creates (a goal Hermes keeps working toward, a loop that wakes the session every 45 minutes, a heartbeat, the session's approval bypass, fast mode) is invisible afterwards. This unit makes that clean: the replies of these commands render as formatted text instead of raw asterisks; a small "automation" section above the composer shows the standing goal, loop and heartbeat from Hermes's own `session.control.read` snapshot and `session.control.update` events (the same data Hermes Desktop and Hermes's own terminal interface paint their goal and loop bars from), plus a YOLO and fast-mode row read back with `config.get`; the goal judge's verdicts (`status.update` with kind `goal`) become transcript notices; and resumed transcripts show `/plan <task>`, "goal continues" and "loop run" lines instead of Hermes's multi-paragraph scaffolding prompts.

## 3. Design

### 3.1 Settled decisions and why

1. **Hermes runs every command; Talaria presents.** The commands stay on `P2-03`'s `slash.exec` path. Talaria never parses Hermes's reply text for state: state comes from `session.control.read`, `session.control.update` and `config.get` (architecture principle 1).
2. **Never `session.automation`** (H17): it would silently switch the gateway's goal judge off for this session. The parity checklist row that names it is wrong; this unit does not edit `docs/handoff/` (the operator decides on a separate documentation change), and the pull request records the correction.
3. **Read once per attach, then follow events** (H13, H15): one `session.control.read` per attach, then `session.control.update`. No polling.
4. **A read overtaken by an update is dropped** (H16): the event is newer by construction.
5. **Rows use the layout and glyphs of Hermes's terminal interface** (`goalStatus.ts`, `loopStatus.ts`, section 2.7) with three deliberate differences, each recorded in `DECISIONS.md`: (a) cadences use Hermes's `format_interval` (`every 1h30m`, `every 1h1m1s`), the wording of Hermes's own replies (`↻ Loop set (every 1h30m)`), where the terminal interface writes `every 90m` and `every 3661s`; (b) a parked goal with an `until` barrier shows time left (`12m left`) where the terminal interface shows a local clock time (`until 14:05`), because the pure core has no time zone; (c) a heartbeat row (Desktop shows one) and a modes row are added. Done goals and loops are hidden; their verdict is in the transcript.
6. **Replies render as Markdown like assistant text** (H26), through `P1-07`'s `render_markdown`, which applies `sanitize_untrusted` and shows raw HTML literally (P1-07 REQ-14, REQ-21). P1-07's "untrusted text is rendered literally" means control characters become visible stand-ins; Markdown is still rendered. Bare `<word>` placeholders are escaped first so no renderer can drop them. U+FE0F is dropped (P1-07 keeps variation selectors), so `⚠️` measures one cell everywhere.
7. **The goal verdict is a transcript notice** (H31), as in Hermes's terminal interface. `P1-05` records `status.update` notes only in its state (`status`, `status_log`); no unit draws them as transcript cells, so each verdict appears once.
8. **Snapshot scaffolds are folded at display time only** (H35, H36). The persisted rows and what the model sees are unchanged; `api_text` is not used (H37).
9. **Pure core, clock from the app.** The reducer never reads a clock; countdowns take `now_ms` (wall-clock milliseconds since the epoch, because `next_due_at` is an epoch time) from the app; wake-ups only when a row's text will change (idle budget: zero frames).
10. **Two views of one YOLO value.** This unit draws the section's YOLO row from its own `config.get yolo` reads. `P2-16` reads the same key itself for its status-line `approvals: off (this session)` segment, on its own triggers (its REQ-1). Neither unit gates the other, neither must remove the other's marker, and `P2-16` may read `AutomationState::modes()` instead if it prefers. The two may briefly disagree after a change until both reads return; both show an unknown state rather than a guess. `P2-16`'s body declares a content conflict over this reading and proposes owning it (`PermissionsState::session_off()`); the `PH2B` planner's ruling, edited into both bodies, wins, and an unsettled conflict is a stop condition of the issue.

`ControlView::decode(&serde_json::Value) -> Result<ControlView, DecodeError>` goes through `P0-03`'s generated `SessionControlSnapshot` type (never a hand-written mirror). What fails decoding is what the generated type refuses: a missing required field or a wrong JSON type. `P0-03` removes every `additionalProperties: false` (its REQ-4; its settled decision 3: unknown fields never fail decoding), so an unknown extra key decodes and is ignored. Hermes Desktop's exact-shape rejection (H16) is therefore not copied. After the generated decode, the conversion to `ControlView` adds one check: a negative epoch time in `next_due_at`, `created_at`, `last_fired_at` (goal, loop or heartbeat) or `until_at` is a `DecodeError`. The top-level `updated_at` is not checked (it only feeds the replay test's clock). A non-finite number cannot come out of parsed JSON, so there is no non-finite case. Epoch seconds become milliseconds with `(secs * 1000.0).round()` clamped to `u64`. `next_due_ms` for a heartbeat is `((last_fired_at if > 0 else created_at) + interval_seconds) * 1000`. `target` of a wait barrier is shown as given (an integer printed in decimal). A status word outside the listed ones decodes, and its part shows no row.

"Redraw if the rows changed" in the table below means: the state that `rows` reads changed, that is, whether a view is shown, the shown view's `revision`, or a mode value. `update` never reads a clock and never calls `rows` with a time; countdown text changes are the app ticker's job (3.9).

`CommandResult` from `P2-03`'s `CommandOutcome`: `Output { .. }` (any text, blank included) is `Output`; `Submit { .. }` is `Submit`; `OutcomeUnknown { .. }` is `Unknown` (the connection may have dropped after Hermes ran the command); `Refused`, `Failed`, `Prefill`, `Nothing` are `NotRun`.

Transition table (first matching row wins). "New token" means `next_token += 1` and use the new value.

| Event | Condition | State change | Effects |
|---|---|---|---|
| `Attached{s}` | any | `session_id = s`; `control = Reading`; `pending_control = new token`; `yolo = fast = NotRead`; `pending_mode` = a new token each, `after_command: false`. `next_token` and `plan_noted` are kept. | `ReadControl{s, t}`, `ReadMode{s, Yolo, t}`, `ReadMode{s, Fast, t}`, `Redraw` (in this order) |
| `Detached` | any | `session_id = None`, `control = NotRead`, modes `NotRead`, pending cleared (`next_token`, `plan_noted` kept) | `Redraw` if any row was visible |
| `ControlRead{t, Ok(v)}` | `pending_control == Some(t)` | `control = Ready(v)` (keep the old view if the revision is equal); `pending_control = None` | `Redraw` if the rows changed |
| `ControlRead{t, Err(MethodMissing or Refused(r))}` | `pending_control == Some(t)` | `control = Unavailable(r or "unknown_method")` (modes untouched: the modes row stays) | `Redraw` if goal, loop or heartbeat rows were visible |
| `ControlRead{t, Err(TimedOut, Lost, BadResult)}` | `pending_control == Some(t)` | `control = NotRead` (modes untouched) | `Redraw` if goal, loop or heartbeat rows were visible |
| `ControlRead{t, _}` | otherwise (overtaken or from before an attach) | none | none |
| `ControlUpdated{s, raw}` | `Some(s) != session_id` | none | none |
| `ControlUpdated{s, raw}` | decode fails | none (keep the old view) | none |
| `ControlUpdated{s, raw}` | decodes | `pending_control = None`; `control = Ready(v)` (same revision as a `Ready` view: keep old). This replaces `Reading`, `NotRead` and `Unavailable` alike. | `Redraw` if rows changed |
| `StatusNote{s, k, t}` | `Some(s) == session_id`, `k` is `goal`, `loop` or `heartbeat`, `t.trim()` not empty | none | `Notice{t}` |
| `StatusNote` | otherwise | none | none |
| `CommandFinished{s2, _, _}` | `Some(s2) != session_id` (the user switched session while the command was in flight) | none | none |
| `CommandFinished{s, "yolo" or "fast", r}` | `r` is `Output`, `Submit` or `Unknown` | `pending_mode[key] = {new token, after_command: true}` | `ReadMode{s, key, t}` |
| `CommandFinished{s, "plan", Submit}` | `s` not in `plan_noted` | insert `s` into `plan_noted` | `Notice{PLAN_MODE_NOTE}` |
| `CommandFinished{_, _, _}` | otherwise (includes `plan` with `Output`, any `NotRun`) | none | none |
| `ModeRead{s, key, t, _}` | `Some(s) != session_id` or `pending_mode[key]` is not `Some` with token `t` | none (stale) | none |
| `ModeRead{Yolo, .., Ok(Some("1" or "0"))}` | matches | `yolo = Known(true or false)`; clear pending | `Redraw` if the rows changed |
| `ModeRead{Fast, .., Ok(Some(v))}` | matches, `v` in `normal`, `fast`, `ultrafast` | `fast = Known(..)`; clear pending | `Redraw` if the rows changed |
| `ModeRead{key, .., Ok(other) or Err(_)}` | matches, pending `after_command` true | value = `Unknown`; clear pending | `Redraw` if the rows changed |
| `ModeRead{key, .., Ok(other) or Err(TimedOut, Lost, BadResult)}` | matches, pending `after_command` false (from `Attached`) | value = `Unknown`; clear pending | `Redraw` if the rows changed |
| `ModeRead{key, .., Err(MethodMissing or Refused(_))}` | matches, pending `after_command` false (from `Attached`) | value stays `NotRead` (an older or refusing Hermes: show nothing); clear pending | none |

"Ok(other)" means `null` or a value outside the listed words. Why a failed attach read shows `Unknown`: YOLO may already be on from another window or an earlier run, and a silent `NotRead` would hide an approval bypass; a method-missing or refused read means this Hermes does not offer the value, and a permanent warning there would be noise. Two quick `/yolo` commands give two reads; only the newer one's result is applied (the first is stale by token), so a failure of the newer read always shows `Unknown`.

### 3.4 The automation section (rows)

`automation::rows(state, now_ms) -> Vec<AutomationRow>` with `AutomationRow { tone: Tone, label: String, detail: String, tail: String }` and `pub enum Tone { Accent, Warning }`. Order: modes, goal, loop, heartbeat. A row exists only when listed below. `detail` and `tail` may be empty.

**Modes row**:
- `yolo == Known(true)`: label `⚠ YOLO`, detail `commands run without approval in this session`, tone Warning.
- `yolo == Unknown`: label `⚠ YOLO`, detail `state unknown: Hermes did not answer`, tone Warning.
- In either YOLO case, when `fast` is `Known(Fast)` or `Known(Ultrafast)`, the tail is `⚡ fast mode` or `⚡ ultrafast mode`.
- No YOLO row and `fast == Known(Fast)`: label `⚡ fast mode`, empty detail and tail, tone Accent (`⚡ ultrafast mode` likewise).
- `fast == Unknown` or `NotRead` adds nothing (fast mode is not a safety setting). `yolo == NotRead` or `Known(false)` adds nothing.

**Goal row** (status `active` or `paused` only):
- detail parts in order: `<used>/<max> turns`; `<n> subgoal(s)` when `n > 0` (`1 subgoal`, `2 subgoals`); `<n> gate(s)` when `n > 0`.
- active, no wait: label `⊙ goal`, Accent, `detail = parts`.
- active with `wait`: label `⏳ goal parked`, Warning; detail `<when> · <reason> · parts` (reason omitted when empty). `<when>`: `Until`: `<countdown> left` while `until_ms > now_ms`, else `due now`; `Session`: `on session <target>`; `Pid`: `on pid <target>`.
- paused: label `⏸ goal paused`, Warning; detail `<paused_reason> · parts` (reason omitted when absent).
- tail: the title.

**Loop row** (status `active` or `paused` only):
- runs: `times > 0`: `<fired>/<times> runs`; else `<fired> run` when 1, `<fired> runs` otherwise (`0 runs`).
- cadence: `self-paced` when `self_paced`; else `every <format_interval(interval_seconds)>`.
- `format_interval` is Hermes's (`hermes_cli/loops.py:128-137`): round to whole seconds, then `<h>h` if hours, `<m>m` if minutes, `<s>s` if seconds or nothing else (`90` → `1m30s`, `2700` → `45m`, `3600` → `1h`, `5400` → `1h30m`, `3661` → `1h1m1s`, `0` → `0s`).
- active: label `↻ loop`, Accent; detail `<cadence> · <runs> · <when>`; `<when>`: `running now` if `awaiting_response`; else `deferred to the goal` if `deferred_by_goal`; else `next in <countdown>` while `next_due_ms > now_ms`; else `due, waiting for idle`. A loop just created shows `0 runs · due, waiting for idle` (H38) until the wakeup fires.
- paused: label `⏸ loop paused`, Warning; detail `<paused_reason> · <runs>` (reason omitted when absent).
- tail: the prompt.

**Heartbeat row** (status `active` or `paused`):
- active: label `♥ heartbeat`, Accent; detail `every <format_interval> · <n> sent · <when>`, `<when>` = `next in <countdown>` while due is ahead, else `due, waiting for idle`.
- paused: label `⏸ heartbeat paused`, Warning; detail `<n> sent`.
- tail: the prompt.

**Countdown** (`countdown(remaining_ms)`), as Hermes's terminal interface (`loopStatus.ts:36-49`) but in milliseconds: `left = ceil(remaining_ms / 1000)` (at least 0); `left < 60`: `<left>s`; else `minutes = ceil(left / 60)`, `hours = minutes / 60` (integer division): `hours > 0`: `<hours>h<minutes % 60 as two digits>m` (`1h05m`); else `<minutes>m`. Examples: 0 → `0s`; 1 ms → `1s`; 59,000 → `59s`; 59,001 → `1m`; 60,000 → `1m`; 60,001 → `2m`; 2,700,000 → `45m`; 3,600,000 → `1h00m` (`minutes` is 60, so `hours` is 1); 3,600,001 → `1h01m`; 3,900,000 → `1h05m`.

**Next change** (`automation::next_tick(state, now_ms) -> Option<u64>`): the earliest app-clock time at which any row's text changes, among: each countdown shown (loop `next in`, heartbeat `next in`, goal `<countdown> left`). For a countdown with `remaining = due_ms - now_ms > 0`: when `remaining > 60,000`, the text changes when `ceil(remaining / 60,000)` drops, at `now_ms + (remaining - (ceil(remaining / 60,000) - 1) * 60,000)`; when `remaining <= 60,000`, at `now_ms + (remaining - (ceil(remaining / 1,000) - 1) * 1,000)`. When `remaining <= 0` the text is stable (`due…`) and contributes nothing. `None` when no countdown is shown. Example: due in 2,700,000 ms → next change in 60,000 ms; due in 61,500 → in 1,500 ms (text goes from `2m` to `1m`); due in 30,400 → in 400 ms.

### 3.5 Rendering the section

`talaria_tui::automation::AutomationSection<'a> { state: &'a AutomationState, now_ms: u64, theme: &'a AutomationTheme }`, implementing `P1-06`'s `LiveSection`:
- `height(width)` = number of rows (0 to 4); 0 when there are none, so the section takes no space.
- Each row is one terminal line: label (tone colour, bold), then ` · ` and the detail (dim), then ` · ` and the tail (default style, no colour). A separator is written only before a non-empty part, so `⚡ fast mode` has no trailing ` · ` and an empty title leaves none either.
- The detail and the tail carry Hermes text (titles, prompts, paused reasons, wait reasons and targets). Each is made single-line (every run of `\r`, `\n`, `\t` becomes one space) and passed through `P1-07`'s `sanitize_untrusted` before measuring. Labels are fixed text.
- The tail is cut with `…` so the whole row fits `width`; when the label plus detail alone exceed `width`, the row is cut at `width - 1` cells and ends with `…` (no tail). Width is measured with the same `unicode-width` rules as `P1-06`. All width arithmetic saturates: width 1 draws `…` alone, width 0 draws nothing (and never panics).
- `AutomationTheme::default()`: accent cyan, warning yellow, dim modifier. `P2-12` may replace it.
- Place the section in `P1-12`'s `LiveView`. Top to bottom: the live tail, this section, `P2-05`'s `SideTasksSection` (P2-05 places it between the live tail and the composer, so it sits directly above the composer), the composer. Without `P2-05`, this section sits directly above the composer.

### 3.6 Presenting command replies

```rust
pub const PRESENTED_COMMANDS: &[&str] = &["plan", "goal", "subgoal", "loop", "heartbeat", "yolo", "fast",
    "reasoning", "busy", "verbose", "footer", "approvals", "personality", "codex-runtime"];
pub fn canonical_name(typed: &str, catalog: Option<&CommandCatalog>) -> Option<String>;

pub fn clean_command_text(text: &str) -> String;
pub struct HermesCommandCell { pub typed: String, pub body: String, pub warning: bool }
pub enum Presentation { Output(HermesCommandCell), Submit { cell: Option<HermesCommandCell>, text: String, display: String } }
```

- `canonical_name`: parse with `P2-03`'s `parse_slash_line`; resolve the name with `CommandCatalog::canonical(name)` when a catalogue is held (`/proactive` → `loop`, `/hb` → `heartbeat`; P2-03 keeps its `canon` map private and exposes this method); else the lower-cased typed name. `None` when the line is not a slash command.
- `present_command` returns `None` (P2-03's normal handling applies) unless `canonical` is in `PRESENTED_COMMANDS` and the outcome is `Output` whose cleaned text is non-blank, or `Submit`. For `Output { text, .. }`: `Output(cell)` with `body = clean_command_text(text)`. For `Submit { text, display, notice }`: `Submit { cell, text, display }` where `cell` is `Some` when the cleaned notice is non-blank. P2-03's `interpret_result` already gives an empty or missing `exec` output the text `(no output)` (P2-03 specification 9.2, its test 19), so an empty reply is non-blank here and becomes a cell reading `(no output)`; an `Output` is blank only when its text is blank after cleaning (for example spaces or U+FE0F only). The read-back of REQ-6 follows either way. The `PH2B` planner confirms this against P2-03's merged code. `typed` is the line exactly as the user typed it (it already starts with `/`).
- `warning`: true when the cleaned body's first non-space character is `⚠`, `⛔` or `⏸`; that character (and only it) is drawn in the warning colour.
- `clean_command_text` rules, in order: drop every U+FE0F; normalise `\r\n` and lone `\r` to `\n`; drop trailing blank lines; outside code spans, write `<` and `>` as `\<` and `\>` (so `<prompt>` stays visible); keep everything else, including `**`, `_`, backticks and control characters (the renderer's `sanitize_untrusted` turns those into stand-ins). Code spans follow CommonMark: a run of N backticks opens a span that closes at the next run of exactly N backticks; a run with no matching closer is literal text, and the escaping continues after it. Blankness (for `present_command`) is decided on the cleaned text, so a reply that is only U+FE0F is blank.
- The app, at the single place it calls `P2-03`'s `outcome_actions`, asks `present_command` first. P2-03's `outcome_actions` turns `Output` into exactly one `Event::Notice { kind: System, text }` (P2-03 specification 9.3), so replacing it loses nothing. `Output(cell)`: send `Event::HermesCommand { cell }` instead of `outcome_actions`. `Submit { cell, text, display }`: send the cell (when present), then the same submission `outcome_actions` would make for `Submit { text, display, notice: None }` (`prompt.submit` with `session_id`, `text`, `submission_id` only, as P1-12 REQ-14; never the `unattended` key). `None`: call `outcome_actions` as before. Then, for every command whose canonical name is in `PRESENTED_COMMANDS`, whatever `present_command` returned (a blank reply, a refusal, a failure and an unknown outcome included), send `AutomationEvent::CommandFinished { session_id, canonical, result }` with the mapping of 3.3, where `session_id` is the session the `slash.exec` was sent to. The `CommandResult` decides whether a read follows; the presentation does not. Effects of that event (a `ReadMode`, the plan note) therefore come after the cell and the submission.

`HermesCommandCell` rendering (`talaria_tui::automation::hermes_command_lines(cell, width, theme) -> Vec<Line<'static>>`): row 1 is `typed` exactly as stored (no extra `/`), dim bold, sanitised, cut with `…`; then the body rendered by `P1-07`'s `render_markdown(body, &MarkdownOptions { width: width.saturating_sub(2).max(1), .. })`, each line indented two spaces. When `warning`, the first body line's first non-space character is drawn in the warning colour. The cell is final when created and is inserted where `P2-03`'s notices go.

Examples (after rendering, styles in brackets):

### 3.9 The app service

`talaria_app::automation::AutomationService` holds `P1-02`'s `hermes_client::Client` and runs effects. The app starts the effects of one `update` call in the order returned, each on its own task, without waiting for any reply. Spawning tasks in order does not fix the order in which their frames reach the socket, so nothing may depend on wire order: tokens and session ids make every result order-safe, and test 36 asserts only that all three requests arrive before any reply.

- `ReadControl{s, t}`: `session.control.read {session_id: s}` (omit `profile`; `methods::legacy::session_control_read`), timeout 5 s through `call_with`. `Ok(result)`: decode `result.control`; a decode error is `BadResult`. `CallError::Rpc` with `-32601`: `MethodMissing`; other `Rpc`: `Refused(reason)` (`data.reason`, else `message`); `TimedOut`: `TimedOut`; `Unknown`, `NotConnected`, `Encode`, `InvalidTimeout`: `Lost`. Sends `ControlRead{t, ..}`. Never retried.
- `ReadMode{s, key, t}`: `config.get {session_id: s, key: "yolo" | "fast"}` (`methods::canonical::config_get`), timeout 5 s; `Ok(r)` gives `r.value`; errors map as above. Sends `ModeRead{s, key, t, ..}`. Never retried.
- `Notice{text}`: `P2-03`'s `Event::Notice { kind: NoticeKind::System, text }` into the session reducer (its renderer sanitises).
- `Redraw`: the loop's normal redraw request.

Routing in the app (`P1-12`'s loop; minimal):
- Attach points, each sending `Attached { session_id }` once: a successful `session.create` or `session.resume` for the foreground session; `P1-03`'s re-attach after a reconnect; a rebuild from a snapshot after a replay gap.
- `Detached`: when `P1-12`'s foreground session becomes `None` with no replacement (the session is closed, or `P1-03`'s recovery gives up). A replacement sends only `Attached` (which resets). Quitting sends nothing.
- For every inbound session event frame of the foreground session with type `session.control.update`, send `ControlUpdated { session_id, raw: payload.control }`; with type `status.update`, also send `StatusNote` (the session reducer keeps its own note).
- After every command whose canonical name is in `PRESENTED_COMMANDS`, `CommandFinished { session_id, canonical, result }` (3.6), whatever `present_command` returned.
- Clock and wake-ups. `P1-12` has no clock seam, so this unit adds a small one in `crates/talaria-app/src/automation.rs`:

  ```rust
  pub fn wall_clock_ms() -> u64;   // SystemTime::now() since UNIX_EPOCH in ms (0 if before the epoch); the only clock read of this unit
  #[derive(Default)] pub struct AutomationTicker { last_text: Option<Vec<String>> }
  pub struct Wake { pub redraw: bool, pub next_in: Option<std::time::Duration> }
  impl AutomationTicker { pub fn on_wake(&mut self, state: &AutomationState, now_ms: u64) -> Wake; }
  ```

  `on_wake` computes the plain text of `rows(state, now_ms)` (label, detail, tail joined as drawn), sets `redraw = (text != last_text)`, stores the text, and sets `next_in = next_tick(state, now_ms).map(|t| Duration::from_millis(t.saturating_sub(now_ms)))`. The app calls `on_wake(&state, wall_clock_ms())` after every `AutomationEvent` it feeds to `update` and at every wake-up. It redraws when `update` returned `Redraw` or `Wake.redraw` is true. It keeps one deadline, `tokio::time::Instant::now() + next_in`, replaced at every call and dropped on `None`; the epoch instant is never converted directly, only the remaining duration, so a wall-clock jump is corrected at the next wake. Deliver the wake-up as `P1-12`'s `AppMessage::Tick`; if its loop cannot wake at an arbitrary instant, add one `tokio::time::sleep_until` deadline in `app.rs`, shared with `P2-05` and `P2-01` (whoever lands first adds it; the others reuse it; keep one copy). Tests drive `AutomationTicker` with hand-picked `now_ms` values; no test of this unit moves tokio's clock for wake-ups, and tests that use real sockets never pause tokio's clock (P1-03 REQ-25).
- Headless mode (`P2-14`, `crates/talaria-app/src/headless/`) is a separate path: it never constructs an `AutomationService`, and this unit does not edit it.

### 3.10 What stays true elsewhere

- `P2-03`'s outcome texts for refusals, failures and unknown outcomes are unchanged for these commands.
