# P0-04: Write the patterns guide that every later unit copies (unit P0-04)

Status: `proposed`. The GitHub issue for this unit is the contract; this document is its reference specification. If they disagree, the issue wins and the disagreement is reported on the issue.

for depth: the verified facts behind each requirement (with file and line), the outline and line

## 1. What this unit is for

Four agents built the same small Hermes client in the stack bake-off
([research/u16-stack-bakeoff.md](../research/u16-stack-bakeoff.md)). The Rust builder at the Sonnet
tier needed 11 fixes. Six of them were terminal-library or language fixes (section 3 of that
report): a borrow-checker error (fix 1), a panic from crossterm's event stream without a terminal
(fix 2), two cursor-query timeouts from ratatui's inline viewport (fixes 3 and 4), history that did
not reach scrollback through `Terminal::insert_before` (fix 5), and a lost first line (fix 6). So
three of the eleven came from the two interfaces the specification had steered both Rust builders
towards. The report states a hypothesis: a patterns guide that names the working approach removes
most of that friction. This unit writes the guide and tests the hypothesis with a fresh agent at the
Haiku tier.

The guide is the second thing every later builder reads, after its own issue. Rule 6 of the
roadmap ([07-roadmap-and-work-units.md](../07-roadmap-and-work-units.md#rules-for-every-unit)) takes
its coding rules from this guide. Units P1-05 (session reducer) and P1-06 (inline renderer) cannot
start before this unit merges.

### 2.4 Toolchain facts verified by experiment (Rust 1.98.1, clippy 0.1.98, 2026-10-22)

A throwaway workspace with ratatui 0.30.2 and crossterm 0.29.0 established these. Re-run the canary
(section 7, test 13) with the pinned toolchain.

1. `clippy.toml` `disallowed-methods` accepts the ten re-exported paths of section 5, and
   `disallowed-types` accepts `ratatui::DefaultTerminal`. With all eleven configured, a crate calling
   each item failed `cargo clippy -- -D warnings` with 12 errors: one per item, plus one for a direct
   `crossterm::cursor::position()` call, which clippy reports as
   "use of a disallowed method `ratatui::crossterm::cursor::position`" (the same function). Each
   error carried a `note:` line with the configured `reason`.
2. **A misspelled path is only a warning.** With `ratatui::Terminal::insert_beforx` configured,
   clippy printed "warning: `ratatui::Terminal::insert_beforx` does not refer to a reachable
   function" with "help: add `allow-invalid = true`", and `cargo clippy -- -D warnings` **exited 0**:
   `-D warnings` does not make this configuration warning fatal. A typo therefore disables a ban
   while the build stays green. (A crate that does not depend on ratatui prints nothing at all.)
3. A library crate whose root is `#![doc = include_str!("../../../docs/agents/patterns.md")]` turns
   every fenced Rust block of that Markdown file into a doctest; `cargo test -p <crate> --doc` and
   `cargo test --workspace` compile and run them. A failing doctest is named
   `tools/patterns-check/src/../../../docs/agents/patterns.md - (line N)`, with N the line of the
   block's opening fence in the guide.
4. **A fence with no language tag is compiled as Rust.** An untagged block of prose failed with
   "expected one of `!` or `::`".
5. **`cargo test --workspace` stops at the first failing test binary.** With a failing integration
   test, the doctests never ran ("error: test failed, to rerun pass `--test guide_rules`"). With
   `--no-fail-fast`, both failures appeared.
6. The round-trip sketch in section 4.5 passed as a doctest against fixture line 20.
7. The canary works: a standalone crate (its `Cargo.toml` has an empty `[workspace]` table so no
   parent workspace claims it) depending on exact ratatui and crossterm versions, checked with

8. Enum variants such as `Viewport::Inline` cannot be banned through `clippy.toml`; only methods,

### 3.1 The stand-in and naming rule

Each example is a self-contained doctest. It defines local stand-ins named exactly as the
roadmap's P0-04 entry names them (the architecture document names neither `State` nor `update`), so a
reader learns the real shape:

- `update(&mut State, Event) -> Vec<Effect>` (roadmap P0-04 content; the real reducer is
  `update(&mut SessionState, Event) -> Vec<Effect>` in `crates/talaria-core/src/session/`).
- `Event` and `Effect` (the real ones live in `talaria-core`); protocol events enter the real `Event`
  as `Event::Session(SessionId, <generated notification type>)`
  ([05-architecture.md](../05-architecture.md#layers)). The generated type's module path is set by
  unit P0-03 and is not confirmed yet, so examples use a stand-in payload there.
- `Client::call::<M: NativeMethod>(params) -> Result<M::Result, CallError>` and `CallError::Unknown`
  belong to `crates/hermes-client`.
- `ReplaySource` and `Recorder` belong to `crates/hermes-client`'s recorder module.

Stand-ins are never imported by a crate. Every other name in the guide is illustrative, and the
opening paragraph says so. The guide names owners by crate and file (for example "the terminal
module, `crates/talaria-tui/src/terminal.rs`"), never by roadmap unit code: through `include_str!`
the guide becomes crate documentation, and roadmap rule 7 keeps planning codes out of source. One
link to the roadmap is allowed; links to research reports (the bake-off report, which section 3.3
requires) do not count against it. Unit codes in the issue and in this document (for example "P1-06's
REQ-4") tell the builder where a fact comes from. The guide's text never carries them: it says "the
terminal module's restore routine and panic hook", not "P1-06's REQ-4". The guide uses the stand-ins whether or not unit P0-03 has merged, so
its text does not depend on merge order.

Example bodies count as test code for rule 12: `unwrap` in the test part is fine. Parts of an
example that stand for library code (the reducer, a render function, the executor) use `?` or
`match`, never `unwrap` or `expect`.

## 4. What each worked example must show

Each pattern section has: two to four sentences of why, which crate and file the real code lives
in, one Rust block tagged plain `rust` that runs and calls `assert!`, `assert_eq!` or `assert_ne!`,
and one sentence on how to test the real thing. No hidden doctest lines (a line that is `#` or starts
with `# `): GitHub shows them and the reader would be confused. An example that needs async code
builds its own runtime (`tokio::runtime::Builder::new_current_thread().enable_all().build()`, then
`block_on`), so it runs as a plain doctest.

### 4.1 Pattern 1: the application event enum and the single channel

- One `tokio::sync::mpsc::unbounded_channel` of the application message type. The loop owns the
  receiver. Every source holds a clone of the sender.
- Unbounded, as in the reference slice and in Codex: a source must never block or drop input, and a
  burst costs one frame because the loop drains before drawing.
- A blocking source (the key reader calls crossterm's blocking `read`) runs on `std::thread` and
  calls the sender's non-async `send`. A timer is a tokio task.
- The key reader converts crossterm's key event into a plain key value before sending. No
  terminal-library, socket or channel type crosses the channel, so `talaria-app` never depends on
  crossterm. (The real key type belongs to `crates/talaria-tui/src/keys.rs`; how it reaches the
  application message type is decided by the issue that owns `crates/talaria-app/src/app.rs`.)
- The loop: `recv().await` one message, then `try_recv()` until empty, apply each through `update`,
  then draw once if something visible changed.
- Real code: `crates/talaria-app/src/app.rs`.
- Assertions: every sent message arrives in order; a burst of N messages produces fewer than N
  draws; no draw happens for a message that changes nothing visible.

Shape (illustrative):

```rust
let (tx, mut rx) = tokio::sync::mpsc::unbounded_channel::<Event>();
let keys = tx.clone();
std::thread::spawn(move || { /* blocking reader */ let _ = keys.send(Event::Key(Key::Char('h'))); });
while let Some(first) = rx.recv().await {
    let mut visible = apply(&mut state, first);
    while let Ok(next) = rx.try_recv() { visible |= apply(&mut state, next); }
    if visible { draws += 1; }
    if state.quit { break; }
}
```

### 4.2 Pattern 2: the pure reducer

- `fn update(state: &mut State, event: Event) -> Vec<Effect>`: no input or output, no clock, no
  randomness. Time arrives inside events (for example `Event::Tick { now_ms }`).
- Identifiers that must be stable across retries are minted from state: a prefix passed in when the
  state is created (`State::new(prefix)`) plus a counter. The real application uses
  `talaria-<16 hex launch id>-<n>` for `submission_id`. Never the process id or the clock: the
  reference slice's `state.rs` builds an `input_id` from `std::process::id()` inside its state
  code, which a replay cannot reproduce; do not copy it.
- The reducer bumps a visible revision (or returns a flag) when something on screen changed.
- Show one Hermes-shaped transition with three cases, matching the real reducer (P1-05 issue, REQ-4):
  a non-empty string `text` appends to the live tail; null `text` seals the reply segment and makes no
  cell; an empty string changes nothing. Hermes publishes null only on a local-viewer route (section
  2.1), so the stand-in state needs no authority flag: a connection that never receives null never
  seals on it. Assert state and returned effects for each case.
- Tests feed events and assert both the returned effects and the state. Mention that the real
  reducer is tested by replaying whole recorded fixtures.

### 4.3 Pattern 3: the effect executor

- Effects are data. `talaria-app` executes them; the executor never touches state.
- Each call runs in `tokio::spawn`. The task awaits the client call and sends the outcome back as a
  message carrying the correlation key (the `submission_id`). The loop never waits.
- A dropped connection gives an unknown outcome, never success (`CallError::Unknown` in
  `hermes-client`). Timeouts belong to the client (120 seconds by default, 300 for
  `approval.respond`).
- The example's client is a stand-in named so (for example `FakeClient`). It records each method and
  its parameters and returns the `result` object of fixture line 6 (section 2.2), parsed from a raw
  string copied from the line's unescaped `frame` value. The real executor is
  `SessionService::execute` in `crates/talaria-app/src/sessions.rs`, calling `Client::call::<M>`.
- The example sends the canonical `prompt.submit` with exactly `session_id`, `text` and
  `submission_id`. Never `unattended`.
- Assertions: the fake saw `prompt.submit` with `session_id`, `text` and the reducer's
  `submission_id`; the message that came back carries the same key and the receipt's `status`
  (`queued`).
- Testing the real executor: the same fake approach, with replies taken from recordings or from the
  pinned contract's schemas, never invented.

### 4.4 Pattern 4: a render function and its snapshot test

- A render function takes state by shared reference and a `Frame` (or an area and a `Buffer`). It
  reads state only. It writes no escape sequences; the terminal module flushes frames.
- Width-aware: measure with `Line::width()` or `Span::width()` (section 2.3); never assume one byte
  or one char is one column. No extra dependency is needed.
- Snapshot test: `Terminal::new(TestBackend::new(width, height))`, draw, then compare the rows of
  symbols with a literal list of expected strings, using a small helper:

```rust
fn rows(t: &Terminal<TestBackend>) -> Vec<String> {
    let b = t.backend().buffer();
    (0..b.area.height)
        .map(|y| (0..b.area.width).map(|x| b[(x, y)].symbol()).collect::<String>().trim_end().to_string())
        .collect()
}
```

- Check styles separately at named cells (`b[(x, y)].fg == Color::Red`). Explain that
  `assert_buffer_lines` builds its expected buffer from the given lines, styles included, so
  plain-string expectations fail for any styled render (section 2.3).
- Test at 40 columns (the narrowest the guide shows, and the trial's width) and at 100 columns. This
  is the guide's choice; each unit's issue sets its own widths (the status line uses 60, 100 and
  160).
- One sentence: byte-level tests of the terminal module use terminal emulators that `talaria-tui` adds
  as its own dev-dependencies (the P1-06 issue: `vt100` 0.16.2 for screen snapshots,
  `alacritty_terminal` 0.26.0 for scrollback); render functions never need them. No guide example
  uses an emulator, so `patterns-check` does not depend on one and the pinned-versions section does
  not list them.

### 4.5 Pattern 5: a transport round-trip test from a recorded frame

- Copy the unescaped `frame` value of one recorded line into the test as a raw string literal. Name
  the recording and line. Never type a frame from memory, and never copy the `{"frame", "t_ms"}`
  wrapper.
- Decode it into local stand-in types, labelled as stand-ins in a comment, assert the fields that
  matter, re-encode, and compare **as `serde_json::Value`**, never as strings: recordings use
  Python's separators.
- Keep fields the type does not model with `#[serde(flatten)] rest: serde_json::Map<String, Value>`,
  and skip absent optional fields when encoding, so the round trip is exact. Never use
  `deny_unknown_fields` on a wire type: Hermes adds fields often.
- In real tests, frames come from `fixtures/frames/` through the replay source in `hermes-client`,
  and the types come from `hermes-contract`. The shape of the test does not change.

Verified sketch (passed as a doctest on 2026-10-22; the two structs are stand-ins):

```rust
use serde::{Deserialize, Serialize};
use serde_json::{Map, Value};

// Stand-ins for teaching. Real code decodes into hermes-contract's generated types.
#[derive(Debug, Deserialize, Serialize)]
struct Envelope { jsonrpc: String, method: String, params: EventParams }

#[derive(Debug, Deserialize, Serialize)]
struct EventParams {
    #[serde(rename = "type")]
    kind: String,
    #[serde(skip_serializing_if = "Option::is_none")]
    session_id: Option<String>,
    #[serde(skip_serializing_if = "Option::is_none")]
    seq: Option<u64>,
    #[serde(default)]
    payload: Value,
    #[serde(flatten)]
    rest: Map<String, Value>,
}

// The frame value of reference-slices/rust/tests/fixtures/live_two_turns.jsonl, line 20.
let recorded = r#"{"jsonrpc": "2.0", "method": "event", "params": {"authority_epoch": 1, "execution_generation": 1, "admission_id": "id-0004", "type": "message.delta", "session_id": "local-session-1", "payload": {"text": null}, "replay_epoch": "id-0002", "seq": 12}}"#;
let frame: Envelope = serde_json::from_str(recorded).unwrap();
assert_eq!(frame.params.kind, "message.delta");
assert_eq!(frame.params.payload["text"], Value::Null);
assert!(frame.params.rest.contains_key("replay_epoch"));
let again = serde_json::to_value(&frame).unwrap();
assert_eq!(again, serde_json::from_str::<Value>(recorded).unwrap());
```

### 4.6 Pattern 6: adding an overlay

- An overlay is a variant of an enum held in `talaria-tui`'s view state (illustrative:
  `Option<Overlay>`). The view state holds no protocol or session state.
- Intents that only open or close views stay in `talaria-tui`. They are never added to
  `talaria-core`'s `Event`, which carries domain changes only.
- The example opens the overlay with a method call, `view.open(Overlay::About)`, and feeds keys
  through a local stand-in key type (`enum Key { Esc, Char(char) }`), labelled as a stand-in for the
  real key type in `crates/talaria-tui/src/keys.rs`.
- While it is open, every key goes to the overlay first, Esc included. Esc closes it and produces no
  effect; it never reaches the composer, where Esc interrupts a running turn. Other keys it does not
  use are dropped, not passed to the composer.
- Its render function draws the whole area it is given. Entering and leaving the alternate screen is
  the terminal module's job (`open_overlay`, `draw_overlay`, `close_overlay` in
  `crates/talaria-tui/src/terminal.rs`); overlay code never does it.
- The section ends with the steps to add one: add the variant; add the method or intent that opens
  it; handle its keys; write its render function; write its snapshot test and a test that Esc closes
  it.
- Assertions in the example: the open overlay's rows match a literal list; after Esc the overlay is
  closed and no effect was returned.

  bans only inline-viewport resizing after start-up, while the P1-06 issue (and this guide) use a
  fixed viewport the terminal module moves and never `Viewport::Inline`. The issue is the contract;
  the operator may want the roadmap and the ADR wording aligned before P1-06 starts.
- The P1-06 issue does not list `tools/patterns-check/tests/boundaries.rs` in its work surface; if it
  needs to widen `TERMINAL_MODULE`, that file becomes a minimal touch for it.

## 11. Design reasoning

- **Compile the guide.** A guide whose examples do not compile teaches the wrong code to every later
  unit. Including the Markdown as crate documentation makes `cargo test --workspace` compile and run
  every example, with no extra tool. The cost is one small crate under `tools/`.
- **Ban interfaces mechanically.** Three of the bake-off's eleven Rust fixes came from two
  interfaces a builder reached for by default, and one more from `EventStream`. A clippy ban turns
  that mistake into a build error that names the guide. Because clippy only warns about a misspelled
  path and `-D warnings` does not fail on it (section 2.4), an exact-list test and a canary guard the
  ban list itself.
- **Scan text for what clippy cannot ban.** Enum variants and lint switches cannot be listed in
  `clippy.toml`, so a cheap text scan covers them.
- **One dependency guard.** P0-02 already checks dependency edges; a second checker here would
  disagree with it on edge kinds and crate lists.
- **Unbounded channel.** Producers must never block or drop keys; the loop drains before drawing,
  so a burst costs one frame. The performance harness measures memory and latency under load;
  revisit if a budget fails.
- **Rows of symbols for snapshots.** They keep the expected screen in the test source, readable
  without tools, and they do not fail on style; styles are checked at named cells.
- **Values, not strings, in round trips.** Recordings use Python's separators, and field order is
  not part of the protocol.
- **Stand-ins with the real names.** The guide fixes shapes, not the names that later units own;
  where the architecture fixed a name, the stand-in uses it exactly, and the guide does not change
  when the generated crate merges.
