## 1. What this unit is for, in plain terms

Talaria talks to Hermes in JSON-RPC (a request and reply protocol) over a WebSocket. A frame is one JSON message on that socket. Three later jobs depend on having frames on disk:

1. **Tests.** The session reducer (`P1-05`), the screen snapshots (`P1-06` onward) and the performance harness replay recorded frames instead of talking to a live gateway.
2. **Debugging.** `talaria --record <path>` (added by `P1-12`) lets a user capture a bad session and attach it to an issue.
3. **Drift detection.** Fresh recordings against a newer Hermes show what changed.

The danger is that the repository is public and the frames carry credentials in plain text in a few places. So the recorder redacts before it writes, the fixtures are scanned before they are committed, and the tests search the raw bytes of the files for secrets the tests planted.

## 3. The frame log, version 3

Version 3 replaces the single-connection and multi-profile shapes of versions 1 and 2. It is a plain JSON Lines file: UTF-8, one JSON object per line, appended and never rewritten. The first line is the header; every later line is a record. Readers ignore fields they do not know and skip records whose `kind` they do not know. The writer in `record.rs` and the reader in `replay_source.rs` are the reference implementation; the document `docs/formats/frame-log.md` is the contract and is updated in the same pull request.

### 3.1 Header

```json
{
  "kind": "header",
  "version": 3,
  "startedAt": "2026-10-23T09:14:02.331Z",
  "endpoint": "ws://<gateway>/api/ws",
  "subprotocols": ["hermes-gateway-v1"],
  "gateway": { "codeVersion": "0.22.4", "codeSha": "<sha>" },
  "scenario": "approval",
  "expectedStatuses": ["complete"]
}
```

| Field | Meaning |
|---|---|
| `version` | Always 3 for this layout. A reader that sees another number stops with a clear error. |
| `startedAt` | When recording began, ISO 8601 in UTC with milliseconds. Written once; frames carry `tMs`, not a clock time. |
| `endpoint` | The WebSocket URL dialled, passed through `redact_url` (userinfo, credential-named query values and any fragment withheld; scheme, host, port and path kept). A withheld endpoint is written as the marker with no redaction entry (the header has none); the format document says so. |
| `subprotocols` | The subprotocols offered, with every entry that starts with `hermes-gateway-ticket.` removed. Never contains a ticket. |
| `gateway` | Optional. `codeVersion` and `codeSha` as `identify` reported them (public build identifiers). |
| `scenario`, `expectedStatuses` | Optional. Written by the fixture script: the scenario name and the `message.complete` status each turn is expected to end with, in order. |

### 3.2 Records

```json
{"kind":"frame","seq":3,"tMs":152,"generation":1,"dir":"in","frame":{"jsonrpc":"2.0","method":"event","params":{}}}
```

| Field | Meaning |
|---|---|
| `kind` | `frame`, `dropped` or an unknown kind (skipped by readers). |
| `seq` | Position among non-header records, starting at 1, gapless. Dropped-frame notes take a number. |
| `tMs` | Milliseconds since the recorder was created, from a monotonic clock (`std::time::Instant`). Never decreases. Used for replay pacing. |
| `generation` | The connection generation the frame crossed. The first connection is generation 1 (a generation is the per-connection counter owned by `P1-02`; the recorder only copies it). |
| `dir` | `in` from the gateway, `out` from Talaria. |
| `frame` | The decoded JSON-RPC frame after redaction and path substitution; `null` when the text was not valid JSON. |
| `redactions` | Present only when something was withheld: a list of `{path, reason}`. `path` is a dotted path from the frame root: object keys joined by `.`, array indices as plain numbers (`params.attachments.0.path`); a `.` or `\` inside a key is written `\.` or `\\`. |
| `parseError` | Present only when `frame` is `null`: the JSON parser's message (position and expectation only; a test proves it never contains payload text). The payload itself is withheld. |
| `count` | Only on `dropped` records: how many frames were not written because the queue was full. A `dropped` record is written before the next frame, or by `finish()` when no later frame comes. |

A value `"[redacted]"` is a marker, not data. Readers must never treat it as real text, and a frame with `redactions` is not complete.

### 3.3 Reasons

`deny-set:<method>` (a method-keyed rule), `suspicious-key` (the key-name net), `url-credential` (a URL carried a credential by position), `ticket` (a string contained `hermes-gateway-ticket.`), `server-response:<method>` (the answer to a server request of that method), `server-response:unknown` (an answer whose request this recorder never saw). Inbound `answers` of a `clarify` request use `deny-set:clarify`.

### 3.4 What changed from versions 1 and 2

`at` (wall-clock time per frame) is replaced by `tMs`; `profile` (the observing connection's name) is replaced by `generation`; `endpoint` and `subprotocols` replace the multi-connection list. `ReplaySource` reads version 3 only. The old corpora were recorded against an older protocol, are git-ignored or removed with `docs/acceptance/` in `P0-02`, and nothing needs them. `docs/formats/frame-log.md` keeps a short "Earlier versions" section so the history is written down. Recording several gateways into one file (the fleet view) is out of scope here; phase 3 decides it.

## 4. Redaction rules

All redaction is a pure function over a decoded frame; the recorder calls it before anything reaches the writer. Nothing is redacted at read time, because by then the secret would already be on disk.

### 4.1 Method deny-set

Each entry lists keys whose values are withheld wherever they appear below that method's `params` (any depth). The method is read from each object that has one, so a batch, a wrapper, a server request frame or an `open_requests` entry (all of which carry `method` and `params`) does not disarm the rule. Only a method that is in the table takes over the rule; an inner `{"method":"GET"}` under another key must not clear it. When a listed method sits inside another listed method, the rules **combine** (union): replacing the outer rule would let a crafted nested object swap in a weaker one.

Contract lookup (test 4): a deny-set method must appear in `methods` (legacy), `x-canonical-methods` or `x-server-requests`. The contract has two schemas for some names (`prompt.submit` has a legacy `PromptSubmitResult` and a canonical `AdmissionStatus`); this unit reads only parameter names, and where both lists hold the method it uses the canonical one. `clarify.respond`, `clarify.lock` and `prompt.replace_queued` are canonical-only. The three old-gateway methods are exempt from the lookup.

| Method | Keys withheld | Why |
|---|---|---|
| `clarify.respond`, `clarify.lock` | `answer` | Free text the user typed; "paste the token here" is an ordinary question. `clarify.lock {request_id, question_id, answer, profile?}` locks one answer of a batch clarify and is in both `methods` and `x-canonical-methods`. |
| `clarify` (the server request, and its `open_requests` entries) | `answers` | Hermes echoes locked batch answers back: `ServerRequest.snapshot()` adds `params["answers"]` (`tui_gateway/server_requests.py:92-98`; schema `ClarifyRequestParams {session_id, questions, answers}`). The name `answers` is not in the key-name net. Reason `deny-set:clarify`. |
| `sudo.respond` | `password` | Older gateways. Absent at v0.22.4. Keep the rule. |
| `secret.respond` | `value` | Older gateways. Absent at v0.22.4. |
| `terminal.read.respond` | `text` | Older gateways. A captured terminal buffer. Absent at v0.22.4. |
| `model.save_key` | `api_key` | Provider key (also caught by the key-name net). |
| `mcp.servers.set_api_key` | `value` | The name `value` is innocent, so only this rule catches it. |

It does not cover every free-form object in the contract: the rest are the open positions of section 4.8. Besides the deny-set, the key-name net (4.2), the URL rule (4.3), the ticket rule (4.5), the answer rule (4.4) and the fixture scan (section 7) apply to every frame. The claim "no secret reaches disk" is therefore bounded by those rules and by 4.8, and the format document says so.

The prompt text (`prompt.submit` `text`) is **not** withheld: fixtures need it, and the fixture prompts are written for the purpose. A user who records a real session should know that what they typed is recorded; the `--record` option (`P1-12`) states this in its help text.

### 4.2 Key-name net (any frame, any depth)

A key is suspicious when any of these patterns matches either the camel-normalized form (insert `_` at each boundary where a lower-case letter or digit is followed by an upper-case letter, regex `([a-z0-9])([A-Z])`, as the Python rule does; then lowercase) or the squashed form (lowercase, every non-alphanumeric character removed). On the camel form the patterns below apply as written. On the squashed form the same patterns apply with the optional prefix group `(.*[-_])?` removed, so they match as suffixes: a squashed name has no separator left, and a prefix with no separator (`dbpassword`, `openaiapikey`) must still match. All patterns are case-insensitive.

1. `^(.*[-_])?pass(word|phrase)$`
2. `secret` (anywhere in the name)
3. `^(.*[-_])?credentials?$`
4. `^(.*[-_])?authorization$` (squashed: `authorization$`)
5. `^(.*[-_])?(api|private|public|access|secret|signing)[-_]?keys?$` (the optional prefix is the fix: the Python pattern was anchored at the start, so `openai_api_key`, `OPENAI_API_KEY`, `anthropicApiKey`, `provider_api_key` and `X-Api-Key` all passed it, and a scan using the same net would have missed them too)
6. `^(.*[-_])?token$` (singular only: `access_token` is a credential, `max_tokens` is a counter)
7. `^(.*[-_])?ticket$` (`DisplayObserveResult.ticket` is a credential-shaped field; harmless fields lost to this are accepted)

Worked examples for test 1. Withheld: `password`, `db_password`, `DBPASSWORD`, `adminpassword`, `passphrase`, `client_secret`, `credentials`, `mycredentials`, `Authorization`, `proxy-authorization`, `api_key`, `openai_api_key`, `OPENAI_API_KEY`, `openaiapikey`, `anthropicApiKey`, `X-Api-Key`, `privateKey`, `access_token`, `accesstoken`, `sessiontoken`, `authtoken`, `ticket`, `sessionticket`. Kept: `max_tokens`, `maxtokens`, `input_tokens`, `session_total_tokens`, `tokens_per_delta`, `tokenizer`, `prompt_id`, `request_id`, `submission_id`, `execution_generation`, `replay_epoch`, `monkey`, `turkey`, `keyboard`, `passage`.

A suspicious key has its value replaced by `"[redacted]"` whatever the value's type. At v0.22.4 this also withholds a few harmless fields: `mirror_credentials` (`profiles.create`), the `secret` flag in a connection target's env field, and the `token` of the pet methods. That is accepted: a marked hole is safe, a leak is not.

**Names withheld in any position (reason `free-text`).** `system_prompt`, `credential_hint` and `launch_request` are withheld by exact name at any depth. They fill the snapshot's `info` block (F23) with free text or a free-form object written by a profile's author, and neither the key-name net nor the scan can recognise such text as personal. The reducer needs `info.model`, `info.provider` and `info.cwd`, which stay. Everything else in `info` is kept; the operator reads the `info` block of the first live recording before any fixture is committed (the issue's stop conditions).

Over-redaction controls (these must stay untouched): `input_tokens`, `output_tokens`, `total_tokens`, `max_tokens`, `session_total_tokens`, `tokens_per_delta`, `prompt_id`, `request_id`, `submission_id`, `execution_generation`, `replay_epoch`. A usage frame must round-trip numerically intact.

### 4.3 URLs, by position

A string value is examined as a URL when it contains `://`, parses as an absolute URL with a scheme and host (use the `url` crate; parsers differ on edge cases), and has a credential in one of three places: userinfo (`user:pass@host`, withheld whole, written as `%5Bredacted%5D@host`), a query value whose key is suspicious or is `token`, `ticket` or `internal` (compared lower-cased; value written as `%5Bredacted%5D`), or a fragment (any fragment, withheld whole, written as `%5Bredacted%5D`). A URL with none of these is left byte for byte as it was. A string that looks like a URL but cannot be parsed is left to the key-name net. **Exact outputs.** The `url` crate only decides whether the string is an absolute URL; the result is made by editing the original string, never by re-serializing it, so the host's case, a missing trailing slash and percent-escapes elsewhere stay as written. The authority is the text after `://` up to the first `/`, `?` or `#`; userinfo is the part before the last `@` in it. Any non-empty userinfo counts, a user name with no password included (a token is often sent as the user name). The query is split on `&`; each pair is split at its first `=`; the key is percent-decoded and lower-cased before it is compared; a pair with no `=` is left alone; the key keeps its original spelling. A non-empty fragment counts; an empty one is left alone. Examples (test 2 asserts these bytes):

| Input | Output |
|---|---|
| `ws://127.0.0.1:9119/api/ws` | unchanged |
| `wss://%5Buserinfo%5D@host:9119/api/ws?mode=1` | `wss://%5Bredacted%5D@host:9119/api/ws?mode=1` |
| `https://tok@Host/Path` | `https://%5Bredacted%5D@Host/Path` |
| `ws://host/api/ws?token=abc&mode=1` | `ws://host/api/ws?token=%5Bredacted%5D&mode=1` |
| `ws://host/api/ws?Ticket=abc` | `ws://host/api/ws?Ticket=%5Bredacted%5D` |
| `ws://host/api/ws?api_key=k&internal=i` | `ws://host/api/ws?api_key=%5Bredacted%5D&internal=%5Bredacted%5D` |
| `https://host/page#frag` | `https://host/page#%5Bredacted%5D` |
| `https://host/page?a=1&b` | unchanged |
| `not a url` (through `redact_url`) | `[redacted]` |

The function `redact_url(&str) -> String` returns the input unchanged when nothing was withheld, and the marker `[redacted]` when given something that is not an absolute URL (used for the header endpoint only). The path of a URL is **not** covered: a bearer capability in a path (a Chrome DevTools socket URL is the known example) is recorded as is. The old Python recorder documented the same limit and why; keep that note in `docs/formats/frame-log.md`.

### 4.4 Answers to server requests (client to server, by correlation)

The recorder remembers the method of each inbound server request. An inbound frame with a string `id`, a string `method` and an object `params` and **no** `result` is a server request (a notification has no `id`). The map `request id -> method` is filled from:

1. every inbound server request frame; and
2. every `open_requests` entry (F6) found in an inbound response's `result`.

A `request.answer` is handled in two steps: first the remembered method for `params.id` is looked up (it decides whether `params.result` is kept, as for `approval`), then the entry is removed. It is emptied of an entry when the answer for that id is written (an outbound response frame, or an outbound `request.answer` naming it in `params.id`), and when an inbound `request.cancel` **event frame** (`params.type == "request.cancel"`, id in `params.payload.id`, F5) names the id. It holds at most 1,024 entries; at the limit the oldest is dropped, which can only make a later answer fail closed (below).

An outbound frame with an `id` and a `result` or `error` and **no** `method` is a response to a server request. Apply:

| Remembered method | Treatment of `result` |
|---|---|
| `approval` | Kept, reduced to `choice` and `all`: any other key is withheld (reason `server-response:approval`), and the key-name net still runs over what is kept. |
| any other method (including `sudo`, `secret`, `clarify`, `vault.code`, `vault.save_login`, `vault.unlock_prompt`, `display.install.sudo`, `terminal.read`, `preview.read`, `preview.act`, `window.read`, `setup_beat`, `theme.pick`, `theme.apply`, `tour`) | Whole `result` replaced by `"[redacted]"`; reason `server-response:<method>`. |
| not in the map | Whole `result` replaced; reason `server-response:unknown`. The recorder may have started late or evicted the entry; it cannot tell what the answer is. |

An `error` object (code and message written by Talaria itself, for example `-32601`) is kept. Inbound, the `answers` of a `clarify` request are covered by the deny-set row in 4.1. The roadmap names `sudo`, `secret`, `vault.*` and `clarify`; withholding every method except `approval` is the same rule applied fail-closed, so a server request added by a later Hermes cannot leak an answer. Canonical approvals and clarifications are not server requests on the canonical gateway (F8); their answers are the method calls in 4.1.

### 4.5 Tickets

A ticket is the single-use credential for the WebSocket upgrade. It travels as a WebSocket subprotocol named `hermes-gateway-ticket.<ticket>`, never in a frame. The recorder never receives it, with two safety nets: the header's `subprotocols` list drops any entry with that prefix, and any string value anywhere in a frame that contains `hermes-gateway-ticket.` is replaced by `"[redacted]"` with reason `ticket`. Error text from a failed upgrade may contain the subprotocol; the reference slice's `redact()` in `net.rs` is the precedent.

### 4.6 Unparseable text and binary

Text that is not valid JSON is recorded with `frame: null` and `parseError`; the text is withheld. A binary WebSocket message is not recorded as a frame; the caller passes only text. Valid JSON that is not an object (an array batch, a bare string) is walked like any value.

### 4.7 Path substitution (fixtures)

After redaction, and before the line is written, the recorder applies `RecorderOptions.substitutions`, a list of `(needle, replacement)` pairs, to every string value and every object key in the frame and in the header endpoint. Pairs are applied longest needle first. The fixture script supplies: the profile id (P1-01 `ProfileId` is the profile's absolute home path) to `<profile>`; the user's home directory to `<home>`; the scratch project directory (and the resolved real path of that directory, which on macOS has a different prefix) to `<tmp>`; the gateway's host and port to `<gateway>`; and the login name to `<user>`. A needle shorter than four characters is refused by the recorder, and the script refuses to record (exit 2) when the login name or host name is shorter than four characters, because it could be neither replaced nor proved absent. The profile name `fixture` is public and is not substituted. Allowed profile values in the fixtures: fields `profile`, `profile_id`, `profile_name` hold `fixture`, `default` or `<profile>`; a `/profiles/<name>` segment holds `fixture` or `<profile>`. The substitution is applied in the recorder, not in the script, so there is exactly one place where a line is produced.

## 5. The recorder

### 5.1 Behaviour

- `Recorder::create(path, options)` creates the file with `OpenOptions::create_new(true)` (it never overwrites) and, on Unix, mode `0o600`. It writes the header as the first line.
- `record_inbound(generation, text)` and `record_outbound(generation, text)` take the raw text. They never block the caller: they push onto a bounded queue (default capacity 4,096) feeding one writer thread. When the queue is full the frame is not queued; a counter is incremented, and the writer writes one `dropped` record with the count before the next frame it does write, or `finish()` writes it when no later frame comes. A recording therefore states what it lost.
- The writer thread owns the redactor and the correlation map, so frames are processed in arrival order. For each item it parses the text, redacts, substitutes, assigns `seq`, serialises one line, writes and flushes. Raw text exists only in memory.
- `finish()` closes the queue **for every clone** (a later `record_*` call on any clone is a no-op), joins the writer and returns a summary `{frames, redactions, dropped}`: `frames` counts frame records written (null-frame records included, `dropped` records excluded), `redactions` counts redaction entries written, `dropped` counts frames not queued. Dropping the last handle does the same. A write error ends the recording: the next `record_*` call is a no-op, `finish()` returns the error, and the application is not interrupted.
- The handle is cheap to clone and is `Send + Sync`.
- `Recorder::from_writer(writer, options)` exists for tests: it takes any `Write + Send`. Like `create`, it writes the header before returning, so a test's gated writer must let its first write (the header) through and gate later ones.

### 5.2 Why a writer thread

The performance budgets (keystroke to frame at most 16 ms at the 95th percentile) must hold while recording. Parsing and redacting every frame on the task that reads the socket would add work to the hot path; a bounded queue keeps the cost to one allocation and a send. Rejected: an unbounded queue (a stalled disk would grow memory without limit); blocking on a full queue (recording would stall the session); redacting on the caller's thread (simpler, but the cost lands on the path that serves the screen).

### 5.3 Where the Recorder plugs in

Text crosses the socket in two places, and both must record (the roadmap expects the fixtures to replace P0-03's recorded `gateway.ready`, which crosses during the handshake, before P1-02's `Client` exists).

1. **Before hand-over (`connect.rs`, owned by P1-01).** P1-01 REQ-16 sends every handshake frame (`gateway.ready`, `client.capabilities`, `runtime.describe`) through one private pair, `send_text` and `next_text`, and hands frames it read but did not consume to P1-02 as an ordered buffer. Give `connect_with`'s options two optional fields, `recorder: Option<Recorder>` and `generation: u64` (default 1, the first connection), and make those two functions call the recorder. `Connection::into_parts` passes the recorder on in `ConnectionParts`.
2. **After hand-over (`channel.rs`, owned by P1-02).** P1-02 REQ-14 routes every outbound frame through one function and every inbound frame through another, and says this unit adds its tap there. Record each frame read from or written to the socket, with the generation P1-02 holds. Frames that P1-02 re-processes from the hand-over buffer were already recorded in step 1 and must **not** be recorded again. P1-02's `decode_frame` is also the function that processes buffered frames (its REQ-10 and test `buffered_handshake_frames_are_delivered_first_in_order`), so the tap goes where the actor takes text from the socket stream, one line before `decode_frame`, and the buffered path calls `decode_frame` without it. If both paths reach `decode_frame` through one function that cannot tell them apart, add one boolean argument there (a minimal touch of `channel.rs`, said in the pull request). The test `handshake_frames_recorded_once_with_generation_1` decides whether the placement is right.

The `Client` keeps the recorder, so it survives `replace_connection` (P1-02 bumps the generation there). P1-03 must pass the recorder to each new connection's connect call (P1-12 REQ-6 gives P1-03's `Link` the recorder); if P1-03 offers no way to do that, stop and report on P1-03. Each change is one optional field and one call, with no behaviour change when the field is `None`, proved by a test. Test 7 asserts `gateway.ready` is recorded exactly once with generation 1.

## 6. The replay source

`ReplaySource::open(path)` reads the whole file, checks the header (`version == 3`, else `ReplayError::UnsupportedVersion {found}`; a first line that is not a header is `NotAHeader`; a complete line that does not parse is `Corrupt {line}`), and parses each record. A final line without a newline (a recording cut short) is ignored with a `truncated: true` flag on the source rather than an error. A header-only file is valid and yields nothing. `seq` must be gapless; a gap is `ReplayError::SeqGap {at}`.

It offers:

- `header() -> &FrameLogHeader`.
- `inbound() -> impl Iterator<Item = &ReplayFrame>` and `outbound()` for assertions; a `ReplayFrame` has `seq`, `t_ms`, `generation` and the frame as `serde_json::Value`.
- `run(speed, sink)`: an async method that sends each inbound frame in `seq` order into `sink: tokio::sync::mpsc::Sender<ReplayItem>`, where `ReplayItem { generation: u64, text: String }` holds the frame as JSON text and its generation. `Speed::Instant` sends without sleeping. `Speed::Recorded` sleeps until `tMs` of each frame, measured from the start of the run, with `tokio::time` (so tests use paused time). `Speed::Factor(f)` divides the gaps by `f` (`f > 0`; 10.0 is ten times faster).

Details the tests assert. A record whose `frame` is `null` (text that was not JSON) has no text to send: `run` and `inbound()` skip it, and it is not counted. `ReplayItem.text` is the stored frame re-serialized (`serde_json::to_string`); the original text is never kept, so a round trip compares decoded results, not bytes. `run` returns `Result<usize, ReplayError>`, the number of frames sent; the speed is checked before the first send; when the sink is closed `run` stops and returns the count so far without an error. `open` fails with `ReplayError::Io(String)` when the file cannot be read (the message holds the error kind, never the path). The fixture script's `replay` command prints that count as `<n>` and builds `final statuses` from the `payload.status` of every inbound `message.complete` event, in order, joined by `, `; its default `--speed` is `instant`.

The sink receives text, not decoded values, because the live socket reader hands text to the same decode function behind `P1-02`'s inbound frame function (`channel.rs`, its REQ-14; the decode itself is in `rpc.rs`). The **consumer** of the sink calls it, not `run`; the round-trip test does the same. Feeding text through that function is what "drives the same pipeline with no socket" means, and it is why the round-trip test decodes through the real decoder rather than comparing JSON. If `P1-02` exposes no public decode function, the smallest change is to make the existing one `pub(crate)` and re-export it for tests; if no such function exists, stop and report.

Replay of a server request needs a responder with no socket behind it. In replay mode the responder handle given to the consumer swallows the answer and counts it, so a test can assert that an approval was answered. The test builds that responder with P1-02's test support; if P1-02 offers no way to make a responder without a socket, stop and report.

Redacted markers can sit where a typed field expects a number or object. Decoding must degrade to the contract's `Unknown` variant (or a decode error that is counted), never panic; a test feeds a frame whose `token` field became a string.

## 7. The secret scan

`scan_for_secrets(text) -> Vec<ScanHit>` where `ScanHit {line: usize, rule: &'static str}`. It never returns or prints the matched text, because the output of a failing continuous-integration job on a public repository is itself public. Rules:

| Rule id | Pattern (summary) |
|---|---|
| `ticket-subprotocol` | `hermes-gateway-ticket\.` |
| `bearer` | `(?i)\bbearer\s+[A-Za-z0-9._~+/=-]{16,}` |
| `sk-key` | `\bsk-[A-Za-z0-9_-]{20,}` |
| `github-token` | `\bgh[pousr]_[A-Za-z0-9]{30,}` and `github_pat_[A-Za-z0-9_]{20,}` |
| `aws-access-key` | `\bAKIA[0-9A-Z]{16}\b` |
| `slack-token` | `\bxox[abprs]-[A-Za-z0-9-]{10,}` |
| `jwt` | `\beyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}` |
| `private-key` | `-----BEGIN [A-Z ]*PRIVATE KEY-----` |
| `url-userinfo` | `://[^/\s:@]+:[^/\s@]+@` |
| `url-secret-query` | a query key `token`, `ticket`, `internal`, `api_key`, `apikey`, `access_token` or `password` whose value is not `%5Bredacted%5D` or `[redacted]` |
| `unredacted-suspicious-key` | walking each line as JSON: a suspicious key (4.2) whose value is a non-empty string other than `[redacted]` |

`scan_literals(text, forbidden: &[String]) -> Vec<ScanHit>` reports a line containing any forbidden literal (the home directory, the login name, the host name and the name of every other profile the gateway reported, never `fixture` or `default`; each at least four characters) with rule `forbidden-literal`. The fixture test (`fixture_scan.rs`) also walks every frame for `profile`-shaped names: a string in a field named `profile`, `profile_id` or `profile_name` must be `default`, `fixture` or `<profile>`, and a `/profiles/<name>` path segment must be `fixture` or `<profile>`. That test can check only these positions; any other foreign profile name is caught at record time by the script's literal scan (section 8.6).

What a scan reads. `scan [<dir>]` reads the `*.jsonl` files directly inside the directory (not recursively, `README.md` is skipped), in name order. Lines are numbered from 1. Within a file, `scan_for_secrets` runs on the whole text and `scan_literals` on the same text.

**Where the forbidden literals come from.** `pub fn local_forbidden_literals() -> Vec<String>` in `redact.rs` builds the list from the machine the scan runs on: the user's home directory from `HOME`, the login name from `USER` (else `LOGNAME`), and the host name from the `gethostname` crate. A value that is unset or shorter than four characters is left out and the caller prints one line `note: <label> not checked (unset or under four characters)` naming the label (`home`, `login`, `host`), never the value. The `scan` subcommand applies this list, so on the operator's machine it also checks those three; it cannot know other profile names (only the record run does, section 8.6). `fixture_scan.rs` uses the same function. A continuous-integration runner has no operator home or login name, so `no_home_login_name_or_host_name` prints `SKIPPED: <label>` lines there and checks only what it can. That gap is covered by a second test with no environment input, `no_home_directory_shaped_paths`: no string value in any fixture starts with a user-directory root of macOS or Linux (a first path segment of `Users`, `home` or `root`) or a temporary-directory root (first segments `private/var` or `var/folders`), or contains the Windows form `C:` followed by `\Users\`. A failure prints file name, line and rule only.

Output rule: a scan prints each hit as `<file>:<line> <rule>`, where `<file>` is the path **relative to the scanned directory** (for example `plain-answer.jsonl:12 sk-key`), never an absolute path, because a failing run's output is public and an absolute path holds the operator's home directory.

Tests that need secret-shaped samples build them at run time (`format!("sk-{}", "a".repeat(24))`) so the source file does not itself contain a string that GitHub's push protection or the project's own scan would flag.

## 8. The fixture-recording script

### 8.1 Shape

`tools/record-fixture/` is a workspace binary crate (add it to the workspace `members` list in the root `Cargo.toml`; if the list is a glob that already covers `tools/*`, change nothing). It depends on `hermes-client` for `discover`, `mint_ticket`, `connect`, `handshake`, `Client::call`, the inbound stream and the `Recorder`; it adds no second WebSocket stack.

```text
record-fixture record [--out fixtures/frames] [--scenario <name>]... [--home <path>] [--profile fixture]
                      [--model minimax-m3.1-flash] [--provider ollama-cloud] [--attempts 3] [--attempt-timeout-s 120]
record-fixture replay <file> [--speed instant|recorded|<factor>]
record-fixture scan [<dir>]            # default fixtures/frames
```

The crate has a library (`src/lib.rs`) and a thin `src/main.rs`. The library holds what tests call: `preflight`, `run_scenario`, `check_evidence`, `build_substitutions` and `ScratchDir` (section 14.2). The word "home" means two directories in this unit: the **Hermes home** (`--home`, default `~/.hermes`, where discovery looks for the gateway) and the **user's home directory** (`HOME`, replaced by `<home>` in recordings).

Crates (the pull request lists the versions it picked): `url`, `regex`, `gethostname`, `time` (the header's ISO 8601 time) and `clap` (command line); dev dependencies `proptest`, `rand`, `tempfile`; `tokio` with its `test-util` feature for paused time.

Exit codes: `0` success; `1` failure (a scenario could not be produced, or the scan found something); `2` precondition absent or gateway unreachable (a plain message says what the operator must set up; nothing was written). Exit 2 is immediate: it is not an attempt and is never retried. A gateway that is present but refuses the connection or fails `identify` is also exit 2, printing the discovery error's `next_step()`.

Discovery uses `discover_with(home, EnsurePolicy::Never)` (P1-01). The default `discover` would run `hermes gateway ensure --json` when no gateway answers, which can start a gateway; agents never start one, and test 11 and UAT-2 prove no `hermes` process is run (a stub `hermes` on `PATH` logs any call).

### 8.2 Preconditions (the operator sets them up; agents do not)

- A Hermes gateway at the pinned release, restarted since the update. The script compares `identify`'s `code_sha` (via P1-01's discovery result) with `hermes_contract::pinned::COMMIT` (P0-03; prefix match, at least 7 characters) and exits 2 on a mismatch or when `code_sha` is null (F18).
- A throwaway profile named `fixture`, listed in the gateway's `served_profiles`, whose `config.yaml` sets `approvals.mode: manual`. A gateway whose `identify` lists no `served_profiles` (it is not in multiplex mode) is accepted only when `identify`'s `profile` equals `--profile`; this also covers the roadmap's alternative of a separate throwaway Hermes home with its own gateway, passed as `--home`. Under the default `smart` mode a guardian model may approve a flagged command and no approval card appears (F17).
- A scratch project directory under the system temporary directory, created by the script and removed when the script's guard is dropped, including on an error exit or an interrupt (Ctrl-C). If removal fails the script says so without printing the path. It contains `notes.txt` with the lines `alpha` and `beta`, and a directory `.pytest_cache`.
- A login name and a host name of at least four characters each (section 4.7).
- A provider key for `ollama-cloud`, already in the `fixture` profile. The script never reads, prints or records it.

The script never calls `config.set`, never runs `hermes update`, never starts or restarts a gateway, and never sends `unattended`. Each `prompt.submit` carries exactly `session_id`, `text` and a unique `submission_id` (F12).

### 8.3 Detecting the approval precondition

The script calls `config.get {key: "approvals.mode"}` without `profile` (the ticket already binds the connection to the profile) and exits 2 unless `value` is `manual` (V2, resolved at v0.22.4; verify live that it reads the fixture profile's value). It also keeps a second guard by behaviour: when the approval scenario's turn ends with a completed shell tool call for `rm -rf .pytest_cache` and no `approval.request` was seen, the script discards the attempt and exits 2 at once (a precondition failure found by behaviour, not a failed attempt: no further attempts, nothing written) with the message "no approval card appeared; the profile `fixture` must set `approvals.mode: manual`".

### 8.4 Scenarios

Each scenario opens a new session with `session.create {source: "cli", cwd: <scratch directory>, model, provider}` (these four fields exist in `CanonicalCreateParams`; `source` is one of `cli`, `tui`, `gui`, `acp`, `tool`, `oneshot`; the model and provider come from `--model` and `--provider`; the script sends no `profile`, V6). The attempt fails unless the returned snapshot's `info` (F23) shows `provider` equal to `--provider`, `model` equal to `--model` or whose last `/`-separated segment equals it (**verify** the exact form of `info.model` live; if neither fits, stop and report), and `cwd` equal to the scratch directory after both are resolved with `std::fs::canonicalize` (on macOS the temporary directory is a symbolic link, so a plain string comparison would fail every attempt); a null field fails the check. So a fixture's provenance is true. The scenario then runs, detaches (`session.detach`), and is recorded to its own file. Names are the file names.

The driver answers an unexpected `approval.request` at once with `approval.respond {choice: "deny"}` and an unexpected `clarify.request` with `clarify.respond {answer: "skip"}` and marks the attempt failed (an unanswered approval would hold the turn for the approval timeout, and REQ-21 forbids interrupting while one is pending). It answers an expected approval or clarification within 30 s of the request.

| File | Prompt (exact text) | Driver steps | Required evidence | `expectedStatuses` |
|---|---|---|---|---|
| `plain-answer.jsonl` | `Reply with exactly the single word: pong. Do not use any tools.` | submit; wait for `message.complete` | at least one `message.delta`; no `tool.start` | `complete` |
| `tool-diff.jsonl` | `In notes.txt change the word beta to gamma. Use your file editing tool, then reply with the single word: done.` | submit; wait | a `tool.complete` whose `inline_diff` is non-empty (V5) | `complete` |
| `approval.jsonl` | `Run this exact shell command and then tell me its exit code: rm -rf .pytest_cache` | submit; on `approval.request` call `approval.respond` with choice `once` and the event's `session_id`, `execution_generation` and `prompt_id`; wait | an `approval.request`, then `approval.settled` | `complete` |
| `clarification.jsonl` | `Before anything else, use the clarify tool to ask me which colour I prefer, with the choices red and blue. Then tell me the colour I chose.` | submit; on `clarify.request` call `clarify.respond` with answer `blue`; wait | a `clarify.request`, then `clarify.settled`; the answer is withheld in the file (`deny-set:clarify.respond`) | `complete` |
| `interrupted.jsonl` | `Count from 1 to 500, one number per line, and do not stop early.` | submit; on the first `message.delta` call `session.interrupt` with the current `execution_generation`; wait | `message.complete` with status `interrupted` | `interrupted` |
| `subagent-batch.jsonl` | `Use the delegate_task tool to run two subagents in parallel: one lists the files in the current directory, the other reads notes.txt. Then summarise both results in one sentence.` | submit; wait | at least one `subagent.start` and one `subagent.complete` | `complete` |
| `queued-prompt.jsonl` | first: `Count from 1 to 30, one number per line.` second: `Reply with the single word: second.` | submit the first; on its first `message.delta` submit the second (V4); wait for two `message.complete` | the second `message.start` comes after the first `message.complete` | `complete`, `complete` |

A pending approval is a seen `approval.request` (its `prompt_id`) with no later `approval.settled` for that `prompt_id` and no `approval.cancelled` for that `session_id`; a pending clarification is a `clarify.request` with no later `clarify.settled`. Both `approval.settled` and `approval.cancelled` clear a pending approval for the driver's rules (F22). Only `approval.settled` counts as the approval scenario's required evidence.

**Every attempt ends the same way, whatever the outcome.** Deny any pending approval (`choice: "deny"`) and answer any pending clarification (`answer: "skip"`) first; then, only if a turn is still running (no `message.complete` since the last `message.start`), call `session.interrupt`; then call `session.detach`. Never interrupt while an approval is pending (F21). The `interrupted` scenario's own interrupt happens after the first `message.delta`, when nothing is pending.

### 8.5 Attempts and cleanliness

A free model does not always follow instructions (V3). An attempt is also failed when it runs longer than `--attempt-timeout-s` (default 120), so a stalled model never hangs the script. Each scenario records each attempt to a hidden temporary file in the output directory. If the required evidence is present and the final statuses equal `expectedStatuses`, the file is scanned (section 7) and renamed into place. Otherwise it is deleted and the next attempt starts, up to `--attempts` (default 3). A scenario that never succeeds is a failure (exit 1) and leaves no file. A precondition failure (section 8.1, and the approval guard of 8.3) is exit 2 at once and does not count as an attempt. A failed scan fails the script and leaves no file. Nothing that failed a check is ever left in `fixtures/frames/`.

### 8.6 Substitutions

The script builds the pair list of section 4.7 from discovery (profile id, which is the profile's home path, and the gateway `api_origin` authority), `$HOME`, the scratch project path and the login name, and passes it in `RecorderOptions.substitutions`. After a recording it runs `scan_literals` with the home directory, login name, host name and the name of every other profile `identify` reported (served or parked, other than `--profile` itself and `default`), and fails if any remains.

- A mock gateway is a WebSocket server on `127.0.0.1` built from the pinned contract or from a recorded fixture. Its event frames use the envelope of F15 and payload fields from `apps/shared/src/gateway-contract.generated.ts` at the pinned tag. The four canonical prompt events (`approval.request`, `approval.settled`, `clarify.request`, `clarify.settled`) are not in the contract file; build them from P0-03's hand-written types (`canonical_events.rs`), whose only source is `ClientLocalGatewayEventMap` in `apps/shared/src/gateway-events.ts` (F8). Before fixtures exist, use the scrubbed bake-off recording in the handoff (`reference-slices/rust/tests/fixtures/live_two_turns.jsonl`); it has a different on-disk shape (a `frame` string and `t_ms`), so write a small converter in the test and say so.
- A server request in a test is a frame `{"jsonrpc":"2.0","id":"srq-<12 hex>","method":"<m>","params":{"session_id":"s1", ...}}` whose `<m>` and params follow the contract's `x-server-requests` entry. Never invent a method; the test table of methods is generated by reading `x-server-requests` from the vendored contract at test time.
- The script's driver tests (test 11) need a scripted gateway. The seam is a real `hermes_client::Client` connected to an in-process mock gateway on `127.0.0.1` (section 14.2), not a trait over the client. Each mock reply is shaped by the contract (`session.create` snapshot, `prompt.submit` admission receipt, event frames from F15 and the hand-written prompt events); the mock invents no method. If P1-01 or P1-02 already ship a mock server in their test support, reuse it.
- Secret sentinels are random per run (for example 16 hex characters from `rand`), placed in the exact positions of section 4, and searched for in the raw bytes of the output file with a plain substring search, not through the JSON parser.
- Tests never contain an absolute path, the home directory, a login name or a profile name other than `default` or `fixture`. Use `tempfile` directories and placeholders.

## 10. Edge cases

| Case | Required behaviour |
|---|---|
| Server request id is a number | Key the map by the id's JSON text; a numeric id is an unknown answer unless remembered. |
| A response to a server request arrives before the request is remembered (tasks racing) | Impossible by construction (the writer thread sees frames in order, and the request is read before it is answered). If the answer is still unknown, withhold it. |
| `request.answer` for an id never seen | Withhold `params.result` (`deny-set:request.answer`). |
| `request.answer` for a remembered id | The map entry is removed, as for a response frame. |
| `request.cancel` | An event frame (`params.type`); the id is `params.payload.id`. A frame whose own top-level `method` is `request.cancel` is not what Hermes sends. |
| `clarify.lock` (batch clarify) | `answer` withheld; the inbound echo of locked answers is `params.answers` of the `clarify` request and of `open_requests` entries, withheld by the `clarify` row of 4.1. |
| Same request id re-delivered after a reconnect (via `open_requests`) | The map entry is refreshed; the remembered method is unchanged. |
| An outbound request (has `method`) that also has a `result` key | Treat as a request; walk normally. |
| An `error` response from Talaria | Keep `error`; there is no `result` to withhold. |
| A frame with a suspicious key inside a withheld `result` | Not walked (the whole result is already withheld). |
| Duplicate JSON keys | The parser keeps the last; the recorder records what the parser saw. |
| A 40 MB frame | Recorded whole; no truncation. The queue counts frames, not bytes; the report says so. |
| Queue full | Drop, count, and write a `dropped` record (5.1). |
| Disk full or file removed | Recording stops; the application continues; `finish()` reports the error. |
| Target file exists | `RecordError::AlreadyExists`; never overwritten. |
| Generation goes backwards | Recorded as given. The recorder does not own the counter. |
| Clock steps backwards | Not possible: `tMs` comes from `Instant`. |
| A string equals the placeholder `<home>` in the real data | Allowed; the placeholder is not a secret. |
| Needle shorter than four characters | Refused with an error before any frame is written. |
| Replay of a file whose last line is cut short | Ignored, `truncated: true`. |
| Replay at `Speed::Factor(0.0)` or negative | `ReplayError::BadSpeed`. |
| `billing.step_up.verification` `user_code` | Recorded as is (F20): a short-lived code shown to the user. Revisit if it proves reusable. |
| `config.set` with any `value` | Withheld (`deny-set:config.set`), a deliberate fail-closed decision: its `key` and `value` are free, so a secret under an innocent key cannot be told from a setting. `config.get` results are not covered (a read-only result carrying a secret has not been seen; revisit if one appears). |
| A frame field named `ticket` | Withheld by key-name pattern 7. A string containing the ticket subprotocol prefix is withheld by REQ-8. |
| Short login or host name (under four characters) | The script exits 2 before recording: such a name cannot be replaced by the recorder or proved absent by the scan. |
| Interrupt (Ctrl-C) during a record run | The scratch directory is removed by a drop guard; the hidden temporary recording is deleted; no file is left in `fixtures/frames/`. |

## 11. Notes for each test

- **Port the Python cases.** The tests in `tests/recorder/test_redact.py` and `tests/recorder/test_attachment_redact.py` at the repository tag `python-final` (created by `P0-02`) are the best list of cases: bridge methods, the key-name net and its camel and squashed forms, nested depth, arrays, non-object frames, the URL forms, the over-redaction controls, and "does not mutate its input". Port the case tables to Rust; do not port the code line by line (the Python module has a long history of fixes; the rules above are its conclusions).
- **Disk, not memory.** Every redaction test that matters writes through `Recorder` to a temporary file and searches the file's bytes. A test that only calls the pure function does not prove the property.
- **Property test.** With `proptest`: generate arbitrary JSON values, inject a sentinel at a random deny-set path or under a random suspicious key or into a random URL position, record it, and assert the sentinel is absent from the bytes and `redactions` is non-empty. A second property: a frame with no secret positions round-trips to an equal JSON value. Dev dependencies: `proptest` and `rand`. Numbers are limited to integers in `-(2^53)..2^53` (the round trip must not depend on `serde_json`'s 64-bit limits) and finite floats are excluded. The position list for `every_listed_secret_position_never_reaches_disk` is copied by hand from the table in 4.1 into a constant in the test (the contract cannot name absent methods); test 4 keeps that list honest. Its generator must exclude everything the recorder withholds by design: no outbound object with an `id` and a `result` or `error` and no `method` (an answer, withheld by design); no key the net matches (including `token`, `secret`, `ticket`) and none of `system_prompt`, `credential_hint`, `launch_request`; no string containing `://` or `#`-fragments that parse as URLs, no `hermes-gateway-ticket.` prefix, no object whose `method` is a deny-set method, and no `[redacted]` value; otherwise the property fails for correct behaviour.
- **Test 4 walk.** `contract_params_matching_the_net_are_withheld` walks every method's parameter schema to full depth through `$ref`, `anyOf`, `oneOf`, `allOf`, `items` and `properties`, and the result schemas the same way. For each property name that `is_suspicious_key` matches, it builds a frame with a random string sentinel at that exact path (an array with one element where the path crosses `items`), records it through a `Recorder` (parameters on an outbound request, results on an inbound response with an `id`), and asserts the sentinel is absent from the file bytes. Every pair the walk finds must pass on the first run; a pair that fails is a rule bug, fixed in the rule.
- **Printing.** `sudo_exchange_answer_never_reaches_disk` prints the recorded lines to standard output (UAT-4 reads them with `--nocapture`).
- **Test 11 names.** The recorder refuses a needle under four characters (test 6, `short_needle_refused`); the script refuses to record at all when the login name or host name is under four characters (`short_login_name_is_exit_2`); `substitution_pairs_cover_home_tmp_gateway_user_profile` checks the pair list the script builds from a stubbed discovery result.
- **Hook.** `handshake_frames_recorded_once_with_generation_1` records through an in-process mock and counts `gateway.ready` lines: exactly one, generation 1 (a tap in `channel.rs` alone would miss it; a tap in both without the buffer rule would write it twice).
- **Sudo exchange.** The roadmap's named test: record an inbound `sudo` request (`id` `srq-...`, `params {session_id, command}`), then an outbound `{"jsonrpc":"2.0","id":"srq-...","result":{"value":"<sentinel>"}}`; assert the sentinel is not in the file and the line has a `server-response:sudo` redaction. Repeat for `secret`, `vault.code`, `vault.save_login`, `vault.unlock_prompt`, `display.install.sudo`, `clarify` (answers), and an answer with an unknown id.
- **Non-blocking.** Use `from_writer` with a writer that waits on a channel. Call `record_inbound` far more times than the queue capacity; assert every call returns, then release the writer and assert the summary's `dropped` equals the number of frames not queued and the file contains a `dropped` record with that count. Do not assert wall-clock times.
- **Replay speeds.** Use `tokio::time::pause()`; assert `Instant` advances no virtual time, `Recorded` advances virtual time to the last frame's `tMs`, and `Factor(10.0)` to a tenth of it.
- **Live tests.** Test 15 is the only live test: it records `plain-answer` and replays it. The other six scenarios are checked live only by UAT-1 (and offline by tests 13 and 14 once the files exist).
- **Fixture tests read the real files.** They are red until the fixtures exist, and they fail with "expected seven fixtures in fixtures/frames, found N", which is the right reason.
- **Failure messages.** No test or scan prints a matched secret, a path, a login name or a host name. They print the file name and line number and the rule id.

## 12. Design reasoning and rejected alternatives

- **Redact at write time, not read time.** A file that contains a secret is a leak even if every reader hides it.
- **Withhold answers to server requests by default, not by list.** The roadmap lists `sudo`, `secret`, `vault.*` and `clarify`. The contract lists 16 server requests and Hermes adds more every release; four of the 16 (`terminal.read`, `preview.read`, `window.read`, `preview.act`) return the content of a screen or page. A deny-list would have to be right about all of them forever. Only `approval`, whose result is a choice word, is kept because the reducer's tests need it.
- **No hash chain.** The Python format did not have one either, and the format document says why it would conflict with redaction. A later decision.
- **Raw text in, not decoded values.** The recorder must record what arrived, including text that is not valid JSON, and it must not depend on the typed decode that `P1-02` owns.
- **One substitution site.** Applying placeholders in the recorder rather than in the script keeps one place that produces a line, and lets `talaria --record` offer the same option later.
- **HTTP bodies.** The Python recorder redacted dashboard HTTP exchanges by route. No unit before phase 4 makes HTTP calls, so this unit does not include it; the first unit that adds an HTTP client must add the route rules, and `docs/formats/frame-log.md` says so.

### 14.3 Decisions, by the question that prompted each

1. Red runs in Rust: a missing module is a compile error, so the first commit holds stubs (bodies `todo!()`), and a red test panics `not yet implemented`. The issue's test-first rule says so.
2. Squashed key names are matched as suffixes (4.2).
3. Deny-set scope and the open positions (4.1 and 4.8), with a contract-walking test that forces a decision for a new free-form parameter.
4. A withheld header endpoint is written as `"[redacted]"` with no `redactions` entry (3.1 wins over the shorter wording of the issue's REQ-1).
5. URL outputs, byte examples and the user-name-only rule (4.3).
6. The approval guard is exit 2 at once (8.3, 8.5).
7. Forbidden literals: `local_forbidden_literals()` (section 7), a shape test with no environment input, and the record run's profile names (8.6).
8. The driver seam: a real `Client` over an in-process mock gateway (14.2).
9. The `info` block: `system_prompt`, `credential_hint` and `launch_request` are withheld by name (4.2); everything else is kept; the operator reads the first live recording's `info` before commit.
10. Differences from the roadmap, for the lead to reconcile: the roadmap entry says the script "skips with a plain message" when the precondition is absent, and the issue says exit 2 with nothing written (the issue wins); the roadmap lists only `P1-02` as a dependency and the issue adds start gates on `P0-02`, `P0-03` and `P1-01`; the roadmap's done-when names `$HOME` and the operator's username and the issue adds the host name and foreign profile names; the architecture document's security section mentions route-aware HTTP body redaction, which this unit defers (section 12).
