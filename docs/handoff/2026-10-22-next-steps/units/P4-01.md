## 1. What this unit adds, in one paragraph

A developer wants to read and change any Hermes setting from inside Talaria, the way Claude Code's `/config` screen works, without opening `config.yaml`. Hermes already publishes the form: `GET /api/config/schema` returns every setting as a dotted key with a type, a description, a category and, for some, a list of allowed values. Talaria adds a full-screen settings overlay (`/config`) generated from that schema: categories on the left, fields on the right, a filter, typed editors with validation, masked secrets with a one-shot reveal, a label saying whether a change applies now or may need a restart, and a review screen showing exactly which keys will change before anything is written. Writes go through `PUT /api/config`, which deep-merges, so Talaria sends only the keys that changed. After every write Talaria reads the settings back and reports, per key, whether Hermes kept the new value, because Hermes can silently drop a write (a package-managed install, or a key an administrator pins). The unit also adds the small loopback HTTP client, authenticated with a single-use `native-http` ticket per request, that the other phase 4 units reuse for Hermes's dashboard routes. `/config key=value` sets one or more settings from the composer through the same review.

## 3. How others present the same feature

### 3.1 Hermes Desktop

- One configuration record per gateway and profile, read with `GET /api/config` and shared by every settings screen; a write goes to the profile the record was read from, never to whichever profile is active when the save happens ([`apps/desktop/src/app/hooks/use-config-record.ts` lines 15 to 51](https://github.com/NousResearch/hermes-agent/blob/v0.22.4/apps/desktop/src/app/hooks/use-config-record.ts#L15-L51); [`apps/desktop/src/api/config.ts` lines 156 to 190](https://github.com/NousResearch/hermes-agent/blob/v0.22.4/apps/desktop/src/api/config.ts#L156-L190)). Talaria copies this: the profile is fixed when the overlay opens.
- Autosave, debounced, with a structural diff against the record as it was when the draft was seeded, so a key the user never touched is never resent with a stale value; saves are queued so an older save cannot land after a newer one ([`apps/desktop/src/app/settings/helpers.ts` lines 119 to 150](https://github.com/NousResearch/hermes-agent/blob/v0.22.4/apps/desktop/src/app/settings/helpers.ts#L119-L150); [`config-settings.tsx` lines 159 to 276](https://github.com/NousResearch/hermes-agent/blob/v0.22.4/apps/desktop/src/app/settings/config-settings.tsx#L159-L276)). Talaria keeps the diff but replaces autosave with an explicit review (the roadmap's "diff before apply").
- A warning before an edit empties the `toolsets` list, because that silently turns off most tools ([`helpers.ts` lines 152 to 176](https://github.com/NousResearch/hermes-agent/blob/v0.22.4/apps/desktop/src/app/settings/helpers.ts#L152-L176)). Talaria shows the same warning in the review.
- Hand-curated sections choose which schema keys appear, and some keys get special editors (memory provider sign-in, voice provider sub-fields). Talaria uses the schema's own categories instead, so new keys appear without a release, and leaves special editors to the typed screens of later units.

## 4. Design

### 4.1 Settled decisions and why

1. **Read and write over REST, not the socket** (H18 to H21 against H29 to H31). This changes draft ADR 0007 item 4 ("Dashboard REST is used only for what has no RPC") and the architecture's Configuration section ("reads values with `config.get`, writes with `config.set`"). Both are operator-owned, so the unit starts only after the operator has accepted `P4-00`'s proposed decision (or an amended ADR 0007 item 4) that configuration values are read and written with `GET` and `PUT /api/config`. If `P4-00` finds that the socket accepts dotted schema keys with full data, the planner edits the issue before work starts.
2. **One fresh `native-http` ticket per ticketed request, profile scope, never reused, never logged** (H2 to H7). No unit ever sends a `profile` selector, in a query or a body (H6, H7): the ticket's profile decides. The only exception is in phase 4b: where `PH4B` settles that a route needs a selector (its stop condition C-1), the unit names the connected profile, never another. At v0.22.4 the `/api/cron/jobs` routes refuse a ticketed request that names no profile with 403 `profile_scope_mismatch` ([`native_http.py` lines 75 to 78](https://github.com/NousResearch/hermes-agent/blob/v0.22.4/hermes_cli/dashboard_auth/native_http.py#L75-L78), mapped to 403 at lines 277 to 278). This unit's own requests never carry one (test 8).
3. **Send only changed keys, nested** (H21, H22). Never the whole record.
4. **Read back after every write, and after any write whose outcome is unknown** (H25). The read-back fetches both the effective and the raw configuration, so the `set` or `default` column is current too (H26). The per-key result is what the user sees, not the `{"ok": true}`.
5. **Check for outside changes just before writing** (Desktop's stale-snapshot lesson, section 3.1).
6. **No autosave.** Edits are pending until the review screen's Enter.
7. **"Applies now" only with evidence** (H15). A Talaria-owned table names the keys with evidence; every other key is labelled "may need a restart".
8. **Mask secrets completely** (H32 to H34), reveal once on request, never show them in the review, a notice, a log or a fixture.
9. **Keys this screen must not edit are read-only, not hidden**: `model` and `model_context_length` (H23; the model roles unit `P4-03` owns them), fields whose raw value holds a `${VAR}` reference anywhere (H19, H26, H39), values that hold a secret-named key inside them, and fields of a kind the screen cannot edit (`text`, `object`, unknown types).
10. **Hand-written HTTP/1.1 is not allowed**; use `hyper` 1.x as a plain HTTP/1.1 client over a `tokio::net::TcpStream` dialled to the loopback `api_origin`. Do not use `reqwest`: it reads proxy environment variables by default, which could route a ticket through a proxy.
11. **The overlay is full-screen** (architecture principle 2), drawn with `P1-06`'s overlay API.
12. **The REST client is the one HTTP seam for phase 4.** It sends `GET`, `PUT`, `POST` and `DELETE`, ticketed by default, with an opt-out for public paths, and a per-request deadline. Sibling units add route modules beside `config_api.rs`; they never change its headers, ticket rule or error mapping.

```rust
                         pub max_body: usize /* 8 MiB */ }

pub struct RequestOpts { pub ticket: bool /* default true */, pub deadline: Option<Duration> /* None: RestOptions by method */ }
impl Default for RequestOpts { /* ticket: true, deadline: None */ }
pub struct RestClient { /* origin: LoopbackOrigin, minter: Arc<dyn TicketMinter>, options */ }
impl RestClient {
    pub fn new(api_origin: &str, minter: Arc<dyn TicketMinter>, options: RestOptions) -> Result<Self, RestError>;
    pub async fn request(&self, method: Method, path_and_query: &str, body: Option<&serde_json::Value>,
                         opts: RequestOpts) -> Result<serde_json::Value, RestError>;
    pub async fn get_json(&self, path_and_query: &str) -> Result<serde_json::Value, RestError>;      // request(Get, .., None, default)
    pub async fn put_json(&self, path: &str, body: &serde_json::Value) -> Result<serde_json::Value, RestError>; // request(Put, .., Some, default)
    #[doc(hidden)] pub async fn probe_ticket_reuse(&self, path: &str) -> Result<(u16, u16), RestError>; // live test 35 only
}
#[derive(Debug, thiserror::Error)] // Display texts never contain a ticket
pub enum RestError {
    NotLoopback, TlsNotSupported,
    Ticket(TicketError),
    Connect(std::io::Error),           // nothing was sent
    Timeout { sent: bool },            // the whole-request deadline passed
    Dropped { sent: bool },            // connection closed before a complete reply
    Unauthorized,                      // 401 (after one retry with a fresh ticket when ticketed)
    Forbidden { detail: String },      // 403
    NotFound { route: String },        // 404; route = "<METHOD> <path without query>", e.g. "PUT /api/config"
    Refused { status: u16, detail: Option<String> }, // other 4xx
    Server { status: u16 },            // 5xx
    BodyTooLarge, BadBody(String),
}
impl RestError { pub fn outcome_unknown(&self) -> bool; } // true exactly for Timeout{sent:true} and Dropped{sent:true}
```

Rules for `RestClient`:

- **Deadline**: one whole-request deadline, from the start of the connect to the last byte of the reply body: 15 s for `GET`, 30 s for `PUT`, `POST` and `DELETE`, unless `RequestOpts.deadline` overrides it (sibling units use 5 s, 8 s and 10 s).
- **`sent`**: true once any byte of the request has been written to the socket. The client wraps the `TcpStream` in a small IO type that counts written bytes (hyper's high-level `send_request` does not report this). A partial write counts as sent on purpose: the conservative reading makes the caller read back rather than claim a result.
- **Tickets**: with `ticket: true` (the default) every attempt mints a fresh ticket and sends it in `x-hermes-gateway-ticket`; a 401 is retried once with a new ticket (the route never ran, H5). With `ticket: false` no ticket header is sent and there is no retry: a 401 is `Unauthorized` at once. A ticketless request to a non-public path gets 401 (H8), so `ticket: false` is only for the public paths (H9, H38).
- **`probe_ticket_reuse(path)`** exists only so the live test 35 can check Hermes's single-use rule (H3) without the ticket text leaving the crate: `P1-01` REQ-12 keeps the `Ticket` accessor crate-private and gives `Ticket` no `Display` or `Clone`, and an integration test is outside the crate. It mints one ticket, sends `GET <path>` with it on one connection, then sends the same ticket again on a second connection, with no retry, and returns the two HTTP status codes (Hermes answers `(200, 401)`). It is the only place a ticket is sent twice; application code never calls it (a `git grep probe_ticket_reuse crates/talaria-*` check finds nothing), it never formats the ticket, and it is `#[doc(hidden)]`. The mock test (test 5) checks it returns `(200, 401)` with one mint.
- **Replies**: a 2xx with an empty body is `Value::Null`; a 2xx body that is not JSON is `BadBody`; a body over `max_body` is `BodyTooLarge`. For 4xx the `detail` field is read when it is a string, cut to 200 characters and sanitised by the caller before drawing.

### 4.5 Keys

Key routing: when `SettingsView.screen` is `Browsing` and `text_focus` is false, the terminal layer resolves the key through `KeyContext::Settings` and sends `SettingsKey::Action(..)`, dropping keys with no binding. On every other screen, and whenever `text_focus` is true (filter line, line editor, option list), it sends `Char`, `Edit` or `Paste` without consulting the key map, and the reducer interprets the fixed keys below. Rebinding therefore applies to the browse actions only.

Precedence over the composer's keys. `P2-13` binds Ctrl+R (`history_search`), Ctrl+G (`open_editor`) and Ctrl+Z (`suspend`) in `KeyContext::Composer`, and its pure `route` picks in this order: `Suspend` first; then the search box, a card, the queue selection, an open overlay; then `OpenEditor` and `HistorySearch` with composer focus only; then the composer. So while the settings overlay is open, every key except Ctrl+Z goes to the settings route described above and never triggers a `KeyContext::Composer` action: Ctrl+R is `settings_reload`, Ctrl+G has no settings binding and is dropped, Ctrl+Z still suspends (`P2-13` releases and re-enters the overlay's alternate screen), and Ctrl+C is handled by the application as everywhere. Test 33 asserts that Ctrl+R with the overlay open yields `SettingsAction::Reload` and no history search. If the merged `route` does not give an open overlay the key ahead of `HistorySearch`, stop and report.

### 4.6 Secrets

- A field is secret when `is_secret_key` (H32) says so and the key is not `voice.record_key` (H33).
- A secret value is drawn as `••••••••` (eight bullets whatever its length) followed by T28; an empty secret is drawn as `(not set)`.
- A value of any field that holds, at any depth, an object key for which `is_secret_key` is true (`contains_secret_key`) is drawn as T28 too and is read-only with T36. No default has this shape at v0.22.4, but an effective value can.
- `r` reveals: the detail line shows the plain value with "(hidden on the next key)" and the reducer emits `ScheduleReveal { id, after: 10 s }`. The next key press of any kind hides it and is then handled normally; `RevealTimeout(id)` hides it when `id` is the current reveal, and a stale id is ignored. Reveal draws only into the overlay, which leaves nothing in scrollback.
- The editor for a secret draws each typed character as `•`; reveal works in the editor too.
- The review shows `•••• → •••• (changed)`; notices show `<key> = (secret)`.
- A field whose raw value holds a `${...}` reference anywhere is read-only with T6. Its value column draws the raw text (for example `"${EXAMPLE_API_KEY}"`), never the expanded effective value, whether or not the key is secret-named (variable names are not secrets; the expanded value can be, H19). The keys screen of `P4-02` owns environment values.

### 4.7 Value kinds and validation

`value_kind` decides by the first non-null of: the current effective value, the default value; else by the schema type.

| Schema type | Rule | Editor | Accepts |
|---|---|---|---|
| `boolean` | always `Bool` | toggle | `true`/`false`; command line also `on/off/yes/no/1/0`, case-insensitive |
| `number` | `Integer` if the decided value is a JSON integer, else `Float` | line | Integer: optional sign then digits, within `i64` (T8a). Float: a finite decimal or exponent number; no `NaN`, `inf` (T8b) |
| `select` | `Choice` | option list | one of `options` (compared as JSON values), or `""` when `clearable` (T8c) |
| `string` | `Text`; if both current and default are `null`, `Nullable` | line | Text: one line, no control characters (T8f). Nullable: empty means `null`; otherwise the text parsed as a JSON scalar (number, `true`, `false`, a quoted string), else as a plain string; the hint shows "saved as <kind> <value>" |
| `text` | read-only `Unsupported("text")` in this unit | — | T7 |
| `list` | `StringList` when every element of the decided list is a string without a comma; else `JsonList` | line | StringList: comma-separated, items trimmed, empty items dropped. JsonList: a JSON array whose elements have the same JSON kinds as the decided list's (T8d, T8e) |
| `object`, unknown | `ReadOnly(Unsupported(type))` | — | T7 |

Before any of these, in this order: `ReadOnly(OwnedElsewhere)` when the key is `model` or `model_context_length` (T5); `ReadOnly(EnvReference(names))` when the raw value holds `${` in any string at any depth (T6); `ReadOnly(HoldsSecret)` when `contains_secret_key` holds for the current value (T36).

`env_reference_names(raw)`: every match of `\$\{([^}]+)\}` in every string at any depth (H39), inner text trimmed, a leading `env:` removed, duplicates dropped, in order of appearance. Examples: `"${EXAMPLE_API_KEY}"` → `EXAMPLE_API_KEY`; `"${env:EXAMPLE_API_KEY}"` → `EXAMPLE_API_KEY`; `"prefix-${X}-${Y}"` → `X, Y`. T6 lists them comma-separated.

A value equal to the baseline (the effective value at load, or at the last successful read-back, or the fresh value adopted by `t`) removes the pending change rather than pending a no-op.

`parse_input(kind, field, text)` has no command-line flag; the rules that look command-line-only are safe for both sources: `Bool` text always accepts `true/false/on/off/yes/no/1/0`, case-insensitive (only the command line feeds `Bool` text; the editor toggles); `Choice` text is matched against each option's string form (a string option's own text, any other option's compact JSON text, so `3` matches the number option `3`), and empty text means `""` when `clearable` (the option list chooses a value directly and never calls `parse_input`). The `<key>: ` prefix on T8 is added by the reducer for command-line errors, not by `parse_input`. Quotes around a command-line value are removed by `parse_config_command` before `parse_input` sees it.

### 4.8 Review, conflicts, apply and read-back

1. **Review** lists pending keys in category order with `review_rows`: key, `old → new` (secrets masked), the apply-effect label, and warnings: T27a when a non-empty list becomes empty, T27b additionally for `toolsets`.
2. **Enter** sends `FetchFresh`: one `GET /api/config` (effective). `find_conflicts` compares, per pending key, the baseline value with the fresh value. Outside changes to keys with no pending change update the baseline and the form, with T26 in the banner. Equal for every pending key: go on to Write. Different for some: the Conflict screen (T11) shows `key`, `yours`, `now`.
   - `o` keeps yours: those keys' baseline becomes the fresh value, and the Write is sent at once with no second fetch.
   - `t` takes theirs: those keys leave the pending set and their baseline becomes the fresh value. If keys remain pending, the Review screen opens again (Enter re-checks). If none remain, Browsing with T26 and no Write.
   - Esc goes back to Review with the pending set unchanged.
   - `FreshFailed`: Review with T35; nothing was sent.
3. **Write** sends `PUT /api/config` with `{"config": build_patch(pending)}`.
4. **Write results**:
   - `Ok` → read back.
   - `Refused` 400 → T17 with Hermes's `detail`, Review, pending kept, no read-back.
   - `Unauthorized` (401 after the one retry) → T35 with the reason `the gateway refused the request (401); it may be restarting`, Review, pending kept, no read-back (H5: refused before the route ran).
   - `Forbidden` (403), `Refused` 422, or `Refused` with any other 4xx status (405, 409, 413 and so on) → T32 (a Talaria defect: no selector is ever sent, and the body shape is fixed), Review, no read-back.
   - `NotFound` → T29 with route `PUT /api/config`, Review, no read-back.
   - `Server` 5xx → T18, then read back.
   - `Unknown` (timeout or drop after any request byte was written, or a reply too large or not JSON) → T19, then read back. Never report success or failure without the read-back.
   - `NotSent(reason)` → T35 with the reason, Review, pending kept, no read-back.
5. **Read-back** sends `ReadBack`: `GET /api/config` and `GET /api/config?include_defaults=false` concurrently, each with a fresh ticket. Per sent key, with `before` = the key's baseline at the moment the Write was sent (after any `o` or `t`), `sent` = the value in the patch, and `after` = the key's value in the effective read-back (`None` when absent, compared as `null`), `classify_readback` applies this rule and no other:
   1. `after == sent` → `Applied`.
   2. else `after == before` → `NotApplied`.
   3. else, `after` has the same JSON kind as `sent` (both strings, both numbers, both booleans, both arrays, both objects, both null) → `Adjusted(after)`.
   4. else → `ChangedElsewhere(after)`.
   A value Hermes normalised and a value another client wrote during the PUT look the same from outside when the kind is unchanged; T15's wording says so rather than guessing.
6. **After read-back**: the baseline becomes the effective read-back and the raw record becomes the raw read-back (so a key written for the first time now shows `set`). Applied and Adjusted keys leave the pending set. NotApplied and ChangedElsewhere keys stay pending, marked `!`. The banner, in order:
   - When at least one key was Applied or Adjusted: T13 with the count, then one restart line per effect present among those keys (T13's sub-lines); when none was: T34.
   - One line per other key: NotApplied after an `Ok` write → T14; NotApplied after a `Server` or `Unknown` write → T33; Adjusted → T15; ChangedElsewhere → T16.
   The overlay stays open, except after a Review opened by `/config k=v` from a closed overlay with at least one Applied or Adjusted key: then `CloseOverlay` and `Notice(T25)`.
   - `ReadBackFailed`: T20; the baseline is unchanged; every sent key stays pending, marked `?` (unverified).
7. **Notice**: on close (Esc, or the automatic close above) after at least one Applied or Adjusted key since the overlay opened, one `Notice(T25)` is emitted, once.

### 4.10 `/config` from the composer

`P2-03`'s local command table gains one entry: name `config`, summary `Show and change Hermes settings for this profile`, `args_hint` `[filter | key=value …]`, `takes_argument: true`, action `LocalAction::Config` (no payload: `P2-03`'s `LocalAction` is a plain enum held in a static table; the argument text reaches the action through `P2-03`'s dispatch, as for every argument-taking local command). The local entry wins over any backend `/config` (H41; `P2-03`'s local-wins rule). The application turns it into `SettingsInput::Command { profile, args }`.

**Secret check first.** `secret_key_in_args(args)` runs on the raw argument text before any other parsing, whatever the quoting or syntax:
- Split on ASCII whitespace. For each token, strip leading `"` characters.
- A token containing `=`: its key is the text before the first `=`. When `is_secret_key(key)` is true (and the key is not `voice.record_key`), the result is that key.
- A token with no `=` for which `is_secret_key(token)` is true and which is followed by another token (the `key value` form): the result is that token.
- A single bare secret-shaped word with nothing after it (for example `/config api_key`) is a filter and is allowed.
A result gives `CommandError::Secret { key }`; the reducer then emits exactly `[Notice(T22), ForgetHistoryLine]`, sends nothing, and never opens the overlay. T22 names only the key. Examples refused: `delegation.api_key=sk-x`, `delegation.api_key="sk-x` (unterminated quote), `delegation.api_key sk-x`, `display.compact=true delegation.api_key=x`.

The over-refusal is deliberate. Bare `key` and `token` are secret words (H32), so a multi-word filter whose non-final word is secret-shaped (`/config key binding`, `/config token count`) is refused with T22 (`key is a secret; …`) and dropped from history. Talaria cannot tell such a filter from `/config api_key <value>`, and the safe mistake is a refused search, not a secret in the history file. The user can type `/config` and filter with `/` instead. A secret-shaped word in the last position (`/config binding key`) is a filter. Test 24 has the rows `/config key binding` → `Secret { key: "key" }` and `/config binding key` → `Open { filter }`.

**History.** `is_secret_config_line(text)` is true when `text`, after leading whitespace, is `/config` followed by whitespace or the end, and `secret_key_in_args` of the rest is `Some`. Two places use it:
- The composer's in-memory history (`P1-08`): on `ForgetHistoryLine` the application calls the composer's new method `forget_newest_history(&text)`, passing the exact `text` from the `Submit(text)` it dispatched; the method removes the newest entry only when it equals `text`.
- The saved history file (`P2-13`'s `~/.talaria/history.jsonl`, one appended line per submit): the application's submit path calls `talaria_app::settings::append_history(history, text, ..)` instead of `PromptHistory::append` directly. It forwards the same arguments unchanged, and skips the append (file and in-memory snapshot) when `is_secret_config_line(text)` is true. So the secret line never reaches disk and Ctrl+R history search never finds it, even after a restart.

**Parsing** (`parse_config_command`, after the secret check):
- `/config` → `Open { filter: None }`: open at the first category.
- `/config <text>` where no token contains `=` → `Open { filter: Some(text) }`. The overlay opens with the filter applied, the filter line not focused (`text_focus` false), and the cursor on the first match, so the next Enter edits that field; with no match, T30 shows and the cursor is on nothing.
- `/config k=v [k=v …]` → `Set`. Tokens are separated by spaces; a value may be double-quoted to hold spaces, with `\"` and `\\` escapes. A mix of tokens with and without `=`, an empty key, a repeated key, or an unterminated quote is `Syntax` → `[Notice(T24)]`.

**Set**: the overlay opens in Loading (`Load`). When loaded, each key is looked up; if any key is unknown (T23), read-only (T5, T6, T7, T36) or fails to parse with the command-line rules of section 4.7 (`<key>: ` + T8 text), nothing is pended, the overlay shows Browsing with those lines in the banner and the filter set to the first failing key. Otherwise all pairs are pended and the Review screen opens directly. Enter applies; after the read-back with at least one saved key the overlay closes by itself and T25 is committed. Esc from that Review discards the command's pending changes and closes the overlay.

### 4.13 The services in `talaria-app`

```rust
// crates/talaria-app/src/settings.rs
pub type MinterFactory = Arc<dyn Fn(&str /* profile */) -> Arc<dyn TicketMinter> + Send + Sync>;
pub struct SettingsService { /* api_origin, served profiles, factory */ }

    pub fn new(api_origin: Option<String> /* None: not connected */, served_profiles: Vec<String>,

    pub async fn execute(&self, effect: SettingsEffect) -> Vec<SettingsInput>; // only Load, FetchFresh, Write, ReadBack

pub fn append_history(/* P2-13's PromptHistory and its append arguments */) /* section 4.10 */;
```

Where the inputs come from in production. `P1-12`'s `OpenConnection` (its unit specification's listing: `link`, `inbound`, `describe`, `profile_name`) carries no `api_origin`, home or `Endpoint`, so the application does not read them from it. When it handles `SettingsEffect::Load`, the application runs `P1-01`'s `discover_with` on the Hermes home it connected with (the home `P1-12`'s `ConnectionService::open` received), with `EnsurePolicy::Never`, and builds a new `SettingsService` from the `Endpoint` it returns: `api_origin` = `endpoint.api_origin()`; `served_profiles` = the `name` of each entry of `endpoint.profiles()`; the factory = `|name| Arc::new(NativeHttpMinter::new(home.clone(), endpoint.clone(), endpoint.resolve_profile(name)?))` with `endpoint: Arc<Endpoint>` (a profile that does not resolve was already refused as `ProfileNotServed`). The overlay keeps that service for its `FetchFresh`, `Write` and `ReadBack` effects. Re-discovering on every `Load` costs one control-socket `identify` (1 to 3 ms) and picks up a gateway restart on a new port; after a restart mid-edit, T35 or T20 tells the user to retry, and Ctrl+R (a `Load`) rebuilds the service with pending changes kept. A discovery failure is `LoadFailed(NotConnected)` (T2). The profile is `OpenConnection.profile_name` for `/config`, or the one in `SettingsInput::Open`. Tests construct `SettingsService::new` directly with the mock's origin and a factory returning a counting fake minter. `execute` runs on a background task; results return to the application's single event channel as messages.

- `Load { profile }`: not connected → `LoadFailed(NotConnected)`; profile not in `served_profiles` → `LoadFailed(ProfileNotServed)` (T4); else builds a `RestClient` for that profile and runs `config_schema`, `config_defaults`, `config_read(true)` and `config_read(false)` concurrently, returning `Loaded` or the first `LoadFailed`.
- `FetchFresh`: `config_read(true)` → `Fresh` or `FreshFailed`.
- `ReadBack`: `config_read(true)` and `config_read(false)` concurrently → `ReadBack { effective, raw }` or `ReadBackFailed`.
- Read failures (`Load`, `FetchFresh`, `ReadBack`) map `RestError` to `FailReason`: `Unauthorized` → `Unauthorized`; `Timeout { .. }` → `Timeout { secs }`, where `secs` is the deadline that applied, in whole seconds rounded up (15 for a default `GET`); `Dropped { .. }` → `Dropped`; `NotFound { route }` → `NotFound { route }`; `Forbidden` → `Http { status: 403 }`; `Refused { status, .. }` and `Server { status }` → `Http { status }`; `BodyTooLarge` and `BadBody` → `BadData`; `Ticket(e)` → `Ticket(<e's Display text>)`; `NotLoopback` and `TlsNotSupported` → `NotLoopback`; `Connect` → `NotConnected`. On `Load` this gives T2 for `NotConnected` and T3 with the matching reason otherwise; on `FetchFresh` and `ReadBack` the same reason text goes into T35 or T20.
- `Write { patch }`: `config_write`, mapping `RestError` to `WriteResult`: `outcome_unknown()` → `Unknown`; `Unauthorized` → `Unauthorized`; `Forbidden` → `Forbidden`; `NotFound { route }` → `NotFound { route }`; `Refused` → `Refused`; `Server` → `Server`; `Connect`, `Ticket`, `NotLoopback`, `TlsNotSupported`, `Timeout { sent: false }`, `Dropped { sent: false }` → `NotSent`; `BodyTooLarge` and `BadBody` on a write reply → `Unknown` (the write may have happened).

The application handles the other effects itself: `Notice` (one `NoticeCell`), `ScheduleReveal` (a one-shot timer that sends `RevealTimeout(id)`), `ForgetHistoryLine`, `OpenLocal` (runs the local action) and `CloseOverlay`. The profile is the foreground session's profile (`OpenConnection.profile_name`), or the one given in `SettingsInput::Open` by another unit (for example `P4-06`).

The `talaria-app` test reaches the mock server with `#[path = "../../hermes-client/tests/support/mock_rest.rs"] mod mock_rest;` (no shared dev crate).

## 5. Exact requests and replies

Every request: HTTP/1.1, one TCP connection per request, dialled to the host and port of the loopback `api_origin` (`http://127.0.0.1:<port>` or `http://[::1]:<port>`), headers exactly:

```text
<METHOD> <path> HTTP/1.1
Host: <host>:<port>
Accept: application/json
x-hermes-gateway-ticket: <fresh ticket>        (absent when RequestOpts.ticket is false)
Connection: close
[Content-Type: application/json]
[Content-Length: <n>]
```

No `Origin`, `Cookie`, `Authorization`, `Referer` or `User-Agent` carrying a user name. No query `profile`, no body `profile`.

| Call | Request | Success reply |
|---|---|---|
| Schema | `GET /api/config/schema` | 200, `{"fields": {...}, "category_order": [...]}` |
| Defaults | `GET /api/config/defaults` | 200, nested object |
| Effective | `GET /api/config` | 200, nested object |
| Raw | `GET /api/config?include_defaults=false` | 200, nested object |
| Write | `PUT /api/config`, body `{"config": <nested patch>}` | 200, `{"ok": true}`; Talaria ignores extra keys |

Example patch for pending `display.compact = true` and `display.skin = "mono"`: `{"config": {"display": {"compact": true, "skin": "mono"}}}`.

Error replies: 401 `{"detail":"Unauthorized"}`; 403 `{"detail":"profile_scope_mismatch"}`; 400 `{"detail":"<message>"}`; 422 `{"detail":[...]}` (validation list); 500 `{"detail":"Internal server error"}`. Talaria reads `detail` when it is a string and shows at most 200 characters of it, sanitised.

401 handling: for a ticketed request the client mints a fresh ticket and retries the same request once, because a 401 is returned before any route runs (H5). A second 401 is `Unauthorized`.

## 6. Mock server rules (tests)

`crates/hermes-client/tests/support/mock_rest.rs`, test code only:

- A `tokio::net::TcpListener` on `127.0.0.1:0`; parses one HTTP/1.1 request per connection; records method, path with query, every header and the body for assertions.
- Serves the recorded fixtures: `fixtures/rest/config-schema.json`, `fixtures/rest/config-defaults.json`, `fixtures/rest/config-effective.json`, `fixtures/rest/config-raw.json` (section 8.1).
- Checks the ticket header on every route except the two public ones: exactly one; each ticket value accepted once (a reuse gets 401); a request with an `Origin` header gets 401 (H5); a `profile` query or body field gets 403 by default (no phase 4a request sends one; the phase 4b exception of decision 2 needs an opt-in on this mock, which `PH4B` settles as its stop condition C-2, leaving this default unchanged). On the public routes a missing ticket is accepted (H35) and a present one is checked as above.
- `GET /api/config?include_defaults=false` returns the in-memory raw record; `GET /api/config` returns the effective record.
- `PUT /api/config`: validates the body is an object with a `config` object (else 422), deep-merges it into its in-memory raw record with the H22 rule (minus `managed_keys`), recomputes the effective record (rule below), and replies `{"ok": true}`.
- The effective record, at start and after every write, is: defaults deep-merged with raw (H22 rule), then the H18 normaliser (a mapping-form `model` flattened to its name; `model_context_length` added, 0 when absent), then the H19 expansion of `${NAME}` and `${env:NAME}` (H39 pattern, every string at any depth) from a fixed map, never the process environment: `EXAMPLE_API_KEY` → `expanded-test-value-1111`, `EXAMPLE_URL` → `http://expanded.invalid/expanded-test-value-2222`; a name not in the map stays as written. Section 8.1's `config-effective.json` is derived with exactly this rule, which is what test 1 compares.
- Switches, each off by default: `managed_keys` (a set of dotted keys stripped from every write, H25); `fail_status` per route (to return 400 with a detail, 404, 422 or 500); `drop_after_request` (close without replying after reading the whole request: `Dropped { sent: true }`); `delay` per route (for `Timeout { sent: true }`); `external_write` (applies a given patch to the raw record between two named requests, to simulate another writer); `first_401` (reject the first ticket on a route).
- A refused connection (`Connect`, so `NotSent`) is produced by binding a listener, reading its port and dropping it before the client dials; no switch is needed. `Timeout { sent: false }` and `Dropped { sent: false }` cannot be produced reliably on loopback (the kernel accepts a small request before any peer action); they are covered by unit tests of `outcome_unknown()` and of the `WriteResult` mapping on constructed values, never by a mock switch that pretends to produce them.
- `MockRest::with_route(method, path, handler)` lets sibling units (`P4-02`, `P4-03`, `P4-06`, `P4-10`) add handlers built from their own recorded fixtures without editing the configuration handlers.
- The mock never invents a route or a field that sections 2 and 5 do not list.

### 8.1 Fixtures

Test 36 is a recording tool: it is exempt from the red run.
