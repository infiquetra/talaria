## 1. The attach sequence at a glance

```text
 Talaria                          control socket                 gateway HTTP/WebSocket
 -------                          --------------                 ----------------------
 discover():
   check home, find socket
   connect, check peer UID  ----> (one connection per request)
   identify  ------------------>  {"protocol":1,"verb":"identify","id":1}
                            <---  {"ok":true,...,"result":{ api_origin, instance_id,
                                                            served_profiles, ... }}
   (no answer? run `hermes gateway ensure --json` once, then discover again)
 resolve_profile(name) -> ProfileId
 mint_ticket():
   session-ticket  ------------>  new connection, one line
                            <---  {"ok":true,...,"result":{"ticket":"<token>", ...}}
 connect():
   GET <api_origin as ws>/api/ws  with subprotocols
     hermes-gateway-v1, hermes-gateway-ticket.<token>   ------------>
                                                         <------------  101 Switching Protocols,
                                                                        subprotocol hermes-gateway-v1
 handshake():
                                                         <------------  event gateway.ready
   client.capabilities {server_requests:true}  ------------------------>   (id 1)
                                                         <------------  result
   runtime.describe {}  ----------------------------------------------->   (id 2)
                                                         <------------  result
 -> Handshake { ready, describe, server_requests, timings }
 -> Connection::into_parts(): sink, stream, identity, next id 3, buffered raw frames
```

Warm-path timings measured by hand on 2026-10-22 (from the Hermes-today document, section 2): identify 1 to 3 ms, ticket about 1 ms, WebSocket upgrade 17 to 20 ms, `gateway.ready` about 5 ms, `runtime.describe` 5 to 9 ms; the first upgrade after the gateway had been idle took 771 ms. These are context for the live test's printed timings, not budgets; this unit owns no performance budget. Do not assert any of them in a test.

## 2. Traps this unit exists to avoid

1. The ticket is a bearer credential valid for 30 seconds. It reaches Talaria in a JSON reply and leaves it in a WebSocket header. Every other place it could appear (a `Debug` print, an error from the WebSocket library that quotes the request, a panic message, a test failure diff, a recorded fixture) is a leak.
2. A socket left over from a crashed gateway is a normal state. It must read as "no gateway" (so `ensure` can run), never as a hang or a panic.
3. A socket with open permissions is not trusted, and a real gateway socket is never refused because of a too-strict rule. The real gateway creates its socket with mode 0600 (control_socket.py:249-255). A socket made by a plain `bind` in a test gets mode 0755 under the usual umask, so a mock that forgets to set umask and mode will be refused by this unit's own check.
4. `hermes gateway ensure` on an older gateway stops and replaces it (gateway_runtime.py:372-387). That can cut another client's running turn. This unit never calls `ensure` for an incompatible gateway, and no test may call the real `ensure`.
5. Every failed WebSocket upgrade looks the same to the client (HTTP 403 as far as the code shows), so the unit cannot tell "expired ticket" from "wrong profile" from "gateway restarting". Its error text must therefore not claim a cause it cannot know.
6. A gateway that is starting answers `identify` with empty `capabilities` and `served_profiles` (run_runtime.py:144-149). Checking the served profiles before the state, as Hermes does, reports a profile mismatch instead of "wait".
7. The prototype recording `reference-slices/rust/tests/fixtures/live_two_turns.jsonl` was scrubbed: its `gateway.ready` lacks `skin` and `replay_epoch` and its `runtime.describe` lacks `skin`. A mock or a decoder built to match it will be wrong against a real gateway.

## 4. Home, discovery and the pointer file (REQ-1 to REQ-3)

### 4.1 `default_home_from`

| Input (`HERMES_HOME`, other env) | Result |
|---|---|
| unset | `<user home>/.hermes` |
| `""` or only spaces | `<user home>/.hermes` |
| `/example-home` | `/example-home` |
| ` /example-home ` | `/example-home` (trimmed) |
| `~/hh` | `<user home>/hh` |
| `$ROOT/hh` with `ROOT=/example-root` | `/example-root/hh` |
| `${ROOT}/hh` with `ROOT=/example-root` | `/example-root/hh` |
| unset, `HERMES_DATA_DIR_SUFFIX=-alt` | `<user home>/.hermes-alt` |
| `/example-home`, `HERMES_DATA_DIR_SUFFIX=-alt` | `/example-home` (the suffix applies to the default only) |

Signature: `pub(crate) fn default_home_from(env: impl Fn(&str) -> Option<String>, user_home: Option<&Path>) -> PathBuf`. It takes the environment as a function and the user home as a path so that no test reads or changes the real environment. `default_home()` is the thin wrapper over the real environment (`std::env::var`) and the user home (`std::env::var_os("HOME")` on Unix).

Decisions for the corners (Hermes uses Python's `expanduser` and `expandvars`; this unit copies the common cases and fixes the rest):

| Input | Result |
|---|---|
| a bare `~` or `~/...` | the user home, then the rest |
| `~name/...` (another user's home) | left as written (Python would look the user up; Talaria does not), so the home is a relative path and discovery returns `NoGateway` |
| `$VAR` or `${VAR}` anywhere in the text (`/x/$ROOT/y`, not only at the start) | replaced, then a leading `~` is expanded: the order of Hermes (`expanduser(expandvars(path))`, `hermes_constants.py:46-48`), so the same text names the same home |
| an unknown `$VAR` or `${VAR}` | left as written, as Python's `expandvars` does |
| `HERMES_DATA_DIR_SUFFIX` | the value is used exactly as given (no trimming; unset or empty adds nothing), as Hermes does (`hermes_constants.py:51-58`); it applies to the default home only |
| no user home found (`HOME` unset or empty) | `default_home()` returns the relative path `.hermes`; a relative home is never used (4.2) |

Add rows `~`, `~/`, `~other/hh`, the unset-home case, `/x/$ROOT/y` and an empty suffix to test 1.

### 4.2 Discovery in order

```text
discover_with(home, options):
  if home is relative, or canonicalize(home) fails:   NoGateway        # no ensure: there is no Hermes home to ensure
  home = canonicalize(home)
  check_home(home)                     # REQ-3 (a): UnsafeNode{Home, ...}
  named = the canonical home's parent directory is named exactly "profiles" (case-sensitive, canonical path;
          REQ-6 names served entries from the served text instead)
  path = symlink_metadata(home/gateway.sock)
  if exists (even a dangling symlink):  node = home/gateway.sock           -> check_socket (REQ-3 b)
  else read pointer home/gateway.sock.path:
         missing                        -> NamedProfileHome if named, else NoGateway
         present                        -> validate (4.3), node = target
                                           (target missing -> NamedProfileHome if named, else NoGateway)
  connect(node)                         # missing or refused -> NamedProfileHome if named, else NoGateway
  peer uid check                        # REQ-3 (d)
  identify                              # REQ-4
  Endpoint::from_identify               # REQ-5
  first result NoGateway, or NotReady{Starting}, or NotReady{Draining, idle_exit: true}:
      run ensure once if the policy allows, then repeat the whole of discover once (7.1)
```

`NamedProfileHome` means: this home belongs to a named profile, and a live socket is the only thing this unit follows there (a profile may run its own gateway; Hermes serves most named profiles from the default gateway's socket instead, which this unit does not follow). A named-profile home with a stale socket (nothing listening) is `NamedProfileHome`, not `NoGateway`, and `ensure` is never run for it: running `ensure` there would start or replace a gateway for a profile the user did not name. A named-profile home with a live private socket and a mock behind it succeeds.

A dangling symlink at `gateway.sock` counts as "exists" (Hermes uses `os.path.lexists`, `gateway_runtime_discovery.py:146`); it then fails the type check (REQ-3 b) and is `UnsafeNode`, not `NoGateway`. A regular file or directory named `gateway.sock` is likewise `UnsafeNode { node: Socket, problem: WrongType }`.

### 4.3 The pointer file

Valid pointer content example (the socket path and the directory name are made up; the hash is the real SHA-256 prefix for the home string `/example-home`):

```text
/example-tmp/hermes-gw-29e84367be239308/control.sock
```

(with or without a trailing newline). Checks, in order, each with its error:

| Check | Error |
|---|---|
| open with the `NOFOLLOW` and `NONBLOCK` flags fails because the pointer is a symlink (the open reports a symlink loop) | `UnsafeNode { node: PointerFile, problem: WrongType }` |
| not a regular file (for example a FIFO), not owned by this user, or any group or other permission bit set (for example mode 0644) | `UnsafeNode { node: PointerFile, problem: WrongType / WrongOwner / OpenToOthers }` (Hermes: `unsafe_control_pointer`) |
| more than 4,096 bytes | `BadPointer(TooLarge)` (read 4,097 to tell; Hermes: `invalid_control_pointer`) |
| not valid UTF-8 | `BadPointer(NotAbsolute)` |
| not an absolute path after trim | `BadPointer(NotAbsolute)` |
| file name is not `control.sock`, or the parent directory name is not exactly `hermes-gw-<hash>` with `<hash>` the hash of THIS home (a name with 16 hex digits that belong to another home is wrong too) | `BadPointer(WrongLeaf)` |
| parent directory is not a private directory owned by this user | `UnsafeNode { node: PointerDir, ... }` |
| target is not a private socket owned by this user | `UnsafeNode { node: Socket, ... }` |
| target does not exist | `NoGateway` |

The hash of the canonical home string: SHA-256 over the UTF-8 bytes of the canonical path, first 16 lower-case hex digits. Worked example: for `/example-home` it is `29e84367be239308` (asserted in test 9 as a pure function). On macOS the temporary directory is reached through a system symlink, so `canonicalize` returns a longer real path; the hash is of the canonical string, which is what the gateway computes with `resolve(strict=False)` (`control_socket.py:41`), so pass the canonical path.

The real gateway's fallback socket lives under `$XDG_RUNTIME_DIR`, the temp directory or `/tmp` (`control_socket.py:65-74`); Talaria does not need to know which, it follows the pointer. If the fallback directory had been squatted, the gateway uses a different parent but keeps the leaf `hermes-gw-<hash>/control.sock` (`:82-91`), which is why the leaf check looks at the last two components only.

### 4.4 The checks before any byte is sent (REQ-3)

| Node | Rule | Failure |
|---|---|---|
| Home | directory (not symlink at the final component after canonicalising), owner is this user, `mode & 0o002 == 0` | `UnsafeNode { Home, WrongType / WrongOwner / WritableByOthers }` |
| Socket | `S_ISSOCK`, owner is this user, `mode & 0o077 == 0` | `UnsafeNode { Socket, WrongType / WrongOwner / OpenToOthers }` |
| Pointer file | regular file, this owner, `mode & 0o077 == 0` | `UnsafeNode { PointerFile, ... }` |
| Pointer directory | directory, this owner, `mode & 0o077 == 0` | `UnsafeNode { PointerDir, ... }` |
| Peer | after `connect`, `peer_cred().uid() == getuid()` | `UnsafeNode { Socket, PeerIsAnotherUser }`, no byte sent |

Mode examples for the pure function (test 2): sockets 0600 and 0700 private; 0755, 0660, 0606, 0666 not. Homes 0700, 0750, 0775 safe; 0777, 0757, 0702 not. Hermes also rejects group-write on a home whose group is shared (F6); this unit does not (it authenticates the peer instead, REQ-3 d), and says so in rustdoc. Consequence (F49): on a home with shared group-write the gateway itself refuses to mint tickets, so the user reaches `TicketError::NotAuthenticated`. Matching Hermes' rule needs the passwd and group databases, which the Rust standard library does not read, so the unit accepts the home and makes the `NotAuthenticated` message cover this case ("the Hermes home may be writable by its group": section 11.2 gives the exact step, which mentions `chmod g-w`). Test 19 asserts that step text.

Why the peer check matters: `lstat` runs before `connect`, and `connect` follows a symlink swapped in between, so only the kernel-reported peer user id proves who is listening (comment at `gateway_runtime_discovery.py:124-128`). The UID comes from tokio's `UnixStream::peer_cred()`; the current user from `rustix::process::getuid()`. Put the comparison in a pure function `peer_is_self(peer_uid, my_uid) -> bool` so test 2 can exercise the "another user" path without a second user.

Platform: macOS and Linux, both of which tokio's `peer_cred` supports. Windows named pipes are out of scope; the discovery code may be `#[cfg(unix)]`.

## 5. `identify` on the wire and how to validate it (REQ-4, REQ-5)

Request, exactly (then `\n`):

```json
{"protocol":1,"verb":"identify","id":1}
```

A ready gateway's reply (one line; values made up, shape from F11, F14, F16):

```json
{"ok":true,"protocol":1,"id":1,"result":{"protocol":1,"kind":"gateway","pid":4242,"start_time":1790000000.5,"hermes_home":"/example-home","profile":"default","supervisor":"none","launch_supervisor":"manual","code_sha":"0123456789abcdef0123456789abcdef01234567","code_version":"0.22.4","instance_id":"0123456789abcdef0123456789abcdef","runtime_protocol":1,"authority_epoch":3,"state":"ready","api_origin":"http://127.0.0.1:43521","served_profiles":[{"profile_id":"/example-home","home":"/example-home"},{"profile_id":"/example-home/profiles/fixture","home":"/example-home/profiles/fixture"}],"parked_profiles":{},"capabilities":["session-authority-v1","durable-admission-v1","event-replay-v1"]}}
```

Keys not listed in REQ-5 (`kind`, `pid`, `start_time`, `hermes_home`, `profile`, `launch_supervisor`, `protocol`) are ignored. Extra keys must never fail parsing. A starting gateway's `result` has `state: "starting"`, `capabilities: []`, `served_profiles: []` and no `authority_epoch` (F15); that must produce `NotReady { state: Starting, idle_exit: false }`.

Line framing: read until the first `\n`; keep reading in chunks. The limit is on the content before the newline: more than 524,288 content bytes is `ReplyTooLarge`, whether or not a newline follows (a 524,289-byte line that ends in a newline is also `ReplyTooLarge`; stop reading as soon as the count passes the limit). A reply of exactly 524,288 content bytes before its newline is accepted (the gateway's own limit is "more than 524,288", F12). If the connection closes before a newline, `InvalidReply`. If the line holds a JSON object with `ok == false` it is `ControlRefused { code, text }` whether or not it has `protocol` and `id` (the real oversize reply has both; `{"ok":false,"error":"x"}` has neither); `code` is the string `code` field if present, `text` is the `error` string scrubbed and cut to 200 characters. Everything else that is not a good reply (not JSON, not an object, wrong `protocol`, wrong `id`, `result` not an object) is `InvalidReply`.

One deadline (default 5 s, `DiscoverOptions::control_timeout`) covers connect, send and read together; use one `tokio::time::timeout` around the whole exchange. Expiry is `ControlTimeout`. An I/O error that is not "not found" or "refused" is `Io(kind)` with the error kind only (no path).

## 6. Profile naming (REQ-6)

`served_profiles` holds `{profile_id, home}`, both the profile's home path (F16). Talaria derives a short name for display and for `--profile`:

| Served `home` | Name |
|---|---|
| `/example-home` (a Hermes root; parent directory is not `profiles`) | `default` |
| `/example-home/profiles/fixture` | `fixture` |
| `/example-home/profiles/Mixed` | `Mixed` (as stored; lookup normalises the typed name) |

The parent directory is read from the served `home` text exactly as the gateway gave it (not from a canonicalised copy). Two entries that get the same lower-cased name make `from_identify` fail with `InvalidIdentity` (5.1 row 6b).

`resolve_profile(name)` normalises the typed name as Hermes does (`normalize_profile_name`, F22): trim, lower-case, and the word `default` in any case is `default`. Then:

1. a served entry whose name (also lower-cased) equals it: its `ProfileId` (the exact `profile_id` string);
2. else a key of `parked_profiles` equal to it after the same normalisation: `Parked { name, reason }` with the reason scrubbed and cut to 500 characters (Hermes cuts at 500, F22);
3. else `NeverDiscovered { name }`.

Test 7 rows: `fixture`, `Fixture`, ` fixture `, `default`, `Default` succeed; a parked name returns `Parked`; `""` and `nosuch` return `NeverDiscovered`. No mock is needed; build the `Endpoint` with `from_identify`.

The default profile is not a directory named `default`; calling the Hermes root "default" is Talaria's convention, matching Hermes' own `default` alias. A user with `HERMES_HOME` pointing at a named profile home cannot reach other profiles through this unit (REQ-2, named-profile home).

The roadmap's phrase "unknown profile ('bootstrap binding rejected')" refers to the gateway's reply when a ticket is requested for a profile it does not serve (F29). With `resolve_profile` the unit normally stops earlier, with `NeverDiscovered` or `Parked`. `BindingRejected` still occurs when the served list changed between `identify` and the ticket request, or when a caller passes a `ProfileId::from` text it did not get from `resolve_profile`; test 19 covers the text-to-variant mapping.

## 7. Ensure and scrubbing (REQ-7, REQ-8)

### 7.1 When to run it

| First discovery result | Run `ensure` once? |
|---|---|
| success | no |
| `NoGateway`, and the home exists and is absolute | yes |
| `NoGateway` because the home is missing or relative | no (there is no Hermes home to ensure; `HERMES_HOME` could not name a canonical home) |
| `NotReady { Starting, .. }` | yes (wait for it) |
| `NotReady { Draining, idle_exit: true }` | yes (the gateway is leaving by itself; a new one is needed) |
| `NotReady { Draining, idle_exit: false }`, `NotReady { Conflict, .. }` | no |
| `ControlTimeout` | no (ensure would only report a deadline) |
| `Incompatible` | no (settled decision 3: `ensure` would stop and replace an older gateway) |
| `UnsafeNode`, `BadPointer`, `InvalidReply`, `ReplyTooLarge`, `ControlRefused`, any `Invalid*`, `HomeNotServed`, `NamedProfileHome`, `Io` | no |

After the single `ensure` run: success exit then discovery again; `NoGateway` the second time is `StillUnreachableAfterEnsure`; `NotReady` the second time is returned as `NotReady`; any other error is returned as is. Never run `ensure` a second time in the same `discover` call. `discover()` itself is `discover_with(home, &DiscoverOptions::default())`, whose policy is `Run`; the default `program` is `hermes` and the timeout is 90 s. Code that must not start a gateway passes `EnsurePolicy::Never` through `discover_with`: a reconnect loop ({{P1-03}}) does, and so does every test. This single repeat of discovery after `ensure` is the one exception to "no retry" in the issue's settled decision 5.

### 7.2 The command

- Program: `hermes` resolved by the operating system from `PATH`, or `EnsurePolicy::Run { program }`.
- Arguments: exactly `gateway`, `ensure`, `--json`. Leave `--timeout` at its default (60 s, F24). Never `--idle-exit` (F24; it is not an `ensure` flag anyway).
- Environment: inherit, then set `HERMES_HOME=<canonical home>`, then remove these 14 variables (the same list Hermes' own launcher removes, `ui-tui/scripts/gateway_bootstrap.py:66-71`): `HERMES_MODEL`, `HERMES_INFERENCE_MODEL`, `HERMES_TUI_PROVIDER`, `HERMES_INFERENCE_PROVIDER`, `HERMES_TUI_TOOLSETS`, `HERMES_TUI_SKILLS`, `HERMES_CWD`, `TERMINAL_CWD`, `HERMES_YOLO`, `HERMES_ACCEPT_HOOKS`, `HERMES_TUI_CHECKPOINTS`, `HERMES_TUI_PASS_SESSION_ID`, `HERMES_KANBAN_BOARD`, `HERMES_TUI_CLIENT_ENV`. With `tokio::process::Command` this is `env_remove` for each; test 4 reads `Command::get_envs()` and sees `None` for each removed key.
- Standard input closed (`Stdio::null()`), standard output and error piped. The deadline below covers the whole run including the reads. After the child exits, keep reading the pipes for at most 2 more seconds and then stop (a process the child started may keep a pipe open); take what was read.
- Deadline: 90 seconds in all (the 60 s default plus 30 s margin; this unit's choice, not Hermes'). On expiry call `Child::kill()`, wait for the child so no zombie remains, and abandon the pipes without waiting for end of file (a grandchild holding a pipe would otherwise hold the call open): `EnsureError::TimedOut`. Killing only the direct child is deliberate; the unit does not manage process groups.
- Hermes' own TUI runs ensure with a 30 s budget and `idle_exit=True` (`gateway_bootstrap.py:72`); Talaria deliberately does neither (decision 3).

### 7.3 Reading the result

`cmd_gateway_ensure` redirects any legacy printing to stderr and prints one compact JSON object as the last thing on stdout (F25). Take the last non-empty line of stdout and parse it as a JSON object; ignore everything before it (test 14's script prints a banner line first to prove it).

```json
{"client_code_sha":"0123456789abcdef","detail":null,"endpoint":null,"reason_code":null,"state":"ready"}
```

- `reason_code`: keep only when it is a string matching `[a-z0-9_]{1,64}`; otherwise `None`.
- `detail`: when a string, scrub (7.5) and cut to 500 characters.
- `state`: a string or `None`.
- `endpoint`, `client_code_sha`: ignored.
- Exit 0 is success only when the JSON `state` is `"ready"`. Exit 0 with non-JSON, empty output or another state is `EnsureError::UnreadableOutput`.
- Standard error is read so the child cannot block on a full pipe, and then discarded. It is never stored, shown or copied into any error (`EnsureError` has no stderr field). An earlier draft showed the last 2,000 characters on failure; that is dropped because it adds a leak path and the next step already tells the person to run `ensure` themselves.

Exit codes (F25, `ensure_exit_code`):

| Exit | Meaning in Hermes | `ExitKind` | Notes |
|---|---|---|---|
| 0 | ready | (success) | needs JSON `state: "ready"` |
| 2 | invalid invocation (`ValueError` or `TypeError` in the command) | `InvalidInvocation` | a Talaria bug |
| 3 | state `incompatible` | `Incompatible` | message also says "incompatible" |
| 4 | reason `authorization`, `profile_mismatch`, `gateway_elevated` or `gateway_other_session` | `Authorization` | step text depends on `reason_code` |
| 5 | reason `deadline`, or state `starting` or `absent` | `Deadline` | |
| 6 | state `draining` (including update paused) | `Draining` | |
| 7 | state `inaccessible` or `conflict` | `Inaccessible` | |
| other | not produced by Hermes | `Other` | |
| killed by signal | | `Exit { code: -1, kind: Other }` | no exit code available |

The exit code alone decides the error (exit 5 is `Deadline` whatever the JSON `state` says, so the spec's mention of `starting` or `absent` in the table only describes why Hermes exits 5); the JSON only adds `state`, `reason_code` and `detail` to `EnsureError::Exit`. Exit 3 with non-JSON output is still `Exit { code: 3, kind: Incompatible, state: None, .. }`. A missing program (`ErrorKind::NotFound` from spawn) is `NotInstalled`; any other spawn failure is `Io(kind)`.

### 7.4 Why Talaria runs the command line

Hermes' own clients call the Python function `ensure_gateway_runtime(home, timeout=30, idle_exit=True)` in process (`ui-tui/scripts/gateway_bootstrap.py:72`). Talaria is not Python, so the command line is its interface: the exit code and the one JSON line are the contract, and the output must be parsed defensively.

### 7.5 `scrub_peer_text(text, home, limit)`

Applied to every piece of text that came from Hermes or a child process before it can reach an error value, a log line or the example's output: `ensure` `detail`, `ControlRefused` and `Refused` text, parked reasons.

1. Replace every occurrence of the canonical home string, and of the home string as the caller gave it, with `<home>` (longest first).
2. Replace every other absolute path with `<path>`: a run that starts with `/` and goes on until whitespace or one of `"` `'` `,` `;` `:` `)` `]` `}` `<` `>` (the stop characters are not part of the path). The run must start at the beginning of the text or right after whitespace, a quote (`'` or `"`), `(`, `[`, `=`, `,` or `:`, and must not start with `//`. A URL such as `http://127.0.0.1:9` has `//` after `:` and is left alone.
3. Replace each control character (including newline and tab) with one space.
4. Cut to `limit` characters (not bytes), at a character boundary.

Test 3 cases (use made-up paths): `see /sample/dir/file now` becomes `see <path> now`; `"/sample/x"` becomes `"<path>"`; `path=/sample/x,` becomes `path=<path>,`; `(/sample/x)` becomes `(<path>)`; `failed: /sample/x: no` becomes `failed: <path>: no`; `http://127.0.0.1:9` is unchanged; `/example-home/run.log` with home `/example-home` becomes `<home>/run.log`; `a\nb\tc` becomes `a b c`; a 600-character text with limit 500 yields 500 characters. This rule is the contract of the function (the issue's "exact path rule"). It is a heuristic filter and says so in rustdoc: it reduces accidental leaks, it is not a security boundary; the real boundary is that no error variant stores raw peer text.

## 8. Minting a ticket (REQ-9 to REQ-12)

Request, one line, exactly these keys (order does not matter to the gateway; tests compare as a parsed value and compare the key sets):

```json
{"protocol":1,"id":2,"verb":"session-ticket","params":{"profile_id":"/example-home","instance_id":"0123456789abcdef0123456789abcdef","purpose":"interactive","scope":"profile"}}
```

Why exactly these keys: the gateway rejects top-level keys other than `protocol`, `verb`, `id`, `params` ("invalid bootstrap envelope"), `protocol` other than 1, and `params` that lack `profile_id`, `instance_id` or `purpose`, or hold anything beyond those plus `scope` and `subject` ("invalid bootstrap parameters") (F27). `subject` is never sent: it would let a same-user peer name another principal, and only a structured login subject is accepted (`control_socket.py:358-368`).

Each mint opens a new control connection (F10) and runs the REQ-3 checks again (the home or socket could have changed since discovery). The control deadline is 5 s, set by `TicketOptions { control_timeout }` (`mint_ticket_with`; `mint_ticket` uses the default), and expiry is `TicketError::Timeout`. Replies over the control line limit are `ReplyTooLarge` (Hermes' own ticket reader caps at 65,536 bytes, F30; this unit applies the one control-reply limit of REQ-4 to all control traffic, a deliberate simplification). Reply parsing is the same envelope check as `identify` with `id` 2.

Scope and purpose:

| `purpose` | wire | `scope` allowed |
|---|---|---|
| `Interactive` | `"interactive"` | `"profile"`, `"host"` |
| `NativeHttp` | `"native-http"` | `"profile"` only |

`Scope::host(Purpose)` returns `Err(ScopeError)` for any purpose except `Interactive`, so a host scope cannot be built for `NativeHttp`. `mint_ticket` re-checks (a caller could build `Scope::host(Interactive)` and pass `Purpose::NativeHttp`) and returns `TicketError::ScopeMismatch` before opening any connection (test 17 asserts no connection was seen by the mock). Other purposes (`native-profile-create` and so on) are not exposed; they belong to later phases.

Success reply (F27):

```json
{"ok":true,"protocol":1,"id":2,"result":{"ticket":"<43 token characters>","expires_in_seconds":30,"instance_id":"0123456789abcdef0123456789abcdef","profile_id":"/example-home","runtime_protocol":1}}
```

Checks in order: envelope (`InvalidReply` for non-JSON, wrong `protocol`, wrong `id`, `result` not an object); the `ok:false` branch (below); `expires_in_seconds` is read by nobody (the unit ignores it, and says so in rustdoc: the gateway enforces the lifetime); `instance_id` and `profile_id` equal the request's and `runtime_protocol == 1`, else `IdentityChanged` (Hermes' client says "Gateway bootstrap identity changed; retry launch", `gateway_client.py:254-257`); `ticket` a string of 1 to 256 characters from letters, digits, `-` and `_`, else `Malformed`. The ticket never reaches a header (REQ-13) until it has passed `Ticket::parse`.

Failure replies: `{"ok":false,"error":"PermissionError: stale runtime instance","protocol":1,"id":2}` and so on. A failure reply whose `error` is missing, not text, or empty is `InvalidReply`. Otherwise split `error` at the first `": "` (a colon followed by a space; if there is none, use the whole text) and classify the remainder:

| Text after the colon | Variant | Cause (F27, F29) | Next step (section 11) |
|---|---|---|---|
| `stale runtime instance` | `StaleInstance` | the gateway restarted since `identify` | discover again |
| `bootstrap binding rejected` | `BindingRejected` | profile not served, unknown purpose or scope, or host scope without interactive | check the profile list |
| `authenticated runtime bootstrap unavailable` | `NotAuthenticated` | the gateway could not prove the caller is the same user (home symlinked, wrong owner, wrong peer) | run Talaria as the gateway's user |
| `bootstrap capacity exhausted` | `CapacityExhausted` | 1,024 unredeemed tickets | wait and retry |
| `invalid bootstrap envelope`, `invalid bootstrap parameters`, `invalid bootstrap subject` | `InvalidRequest` | Talaria sent a malformed request: a bug | report a bug |
| anything else | `Refused(text)` | unknown | scrubbed text, cut to 200 |

These strings are exception messages in Hermes code (U2). Match on the whole trimmed text, case-sensitively; keep the catch-all so a changed message degrades to `Refused` rather than a misleading variant. Live test 32 (a made-up all-zero instance id) is the drift detector for `stale runtime instance`.

`Ticket`:

```rust
pub struct Ticket { value: String, purpose: Purpose, identity: Option<(String, ProfileId)> }   // all private
impl Ticket { pub fn parse(value: String) -> Result<Ticket, TicketError> }       // value rule above; identity None; purpose Interactive
impl std::fmt::Debug for Ticket { /* writes exactly "Ticket(<redacted>)" */ }
// no Display, no Clone, no Copy, no Serialize
pub(crate) fn expose(&self) -> &str                                              // used only by connect
```

`Ticket::parse` is for tests and for the live made-up-ticket test. A parsed ticket has no identity (`None`), so `connect` copies the endpoint's `instance_id` into the `Connection` and leaves the profile unknown; `handshake` then compares the `runtime.describe` `instance_id` with that one, skips the profile comparison, and takes the connection's profile from the describe result (10.3). A minted ticket carries the `instance_id` and `ProfileId` of the request, and `handshake` compares both. A ticket also keeps its purpose, so `connect` can refuse one that can never open the socket (F48, section 9.1). A ticket is consumed by `connect(endpoint, ticket)` (moved, not borrowed), because it is single-use. Test 18 combines `static_assertions::assert_not_impl_any!(Ticket: std::fmt::Display, Clone, serde::Serialize)` (compile-time, passes on the stub) with a runtime assertion that `format!("{ticket:?}")` and `format!("{ticket:#?}")` equal `Ticket(<redacted>)` (fails red on the stub).

## 9. Opening the WebSocket (REQ-13, REQ-14)

### 9.1 URL and request

| `api_origin` | `ws_url()` |
|---|---|
| `http://127.0.0.1:4567` | `ws://127.0.0.1:4567/api/ws` |
| `http://[::1]:4567` | `ws://[::1]:4567/api/ws` |
| `https://127.0.0.1:4567` | `wss://127.0.0.1:4567/api/ws` (and `connect` returns `TlsNotSupported` without any connection attempt) |

Request headers: `Host` equal to the `api_origin` authority (the library sets this from the URL; the test checks it against the origin), `Sec-WebSocket-Protocol: hermes-gateway-v1, hermes-gateway-ticket.<ticket>` (one header, two values), the usual upgrade headers. No `Origin`, no cookie, no `Authorization`. Do not read `HTTP_PROXY` and similar variables (Hermes' own client turns proxies off because a proxy that cannot reach 127.0.0.1 turns every launch into a timeout, `gateway_client.py:300-305`): open the `TcpStream` yourself (`TcpStream::connect` to the address from `api_origin`) and hand it to the library's client handshake with a config (`client_async_with_config`), so no proxy or name lookup can occur and one 15 s deadline covers the TCP connect and the upgrade together.

`connect` returns `ConnectError::WrongPurpose` before opening any connection when the ticket's purpose is `NativeHttp` (F48: the WebSocket route redeems only `interactive` and `worker-adoption` tickets, so such a ticket would be refused and the refusal would look like an expired ticket). Test 20 has a row for it.

Limits: `WebSocketConfig { max_message_size: Some(8 MiB), max_frame_size: Some(8 MiB), .. }` (F31, Hermes' own client).

### 9.2 Checking the echoed subprotocol

After the upgrade, read `Sec-WebSocket-Protocol` from the response yourself and require exactly `hermes-gateway-v1` (F31). Missing, `hermes-gateway-v2`, or the ticket subprotocol are each `SubprotocolMismatch`. The `tungstenite` library may itself refuse a response that selects a subprotocol the client did not offer; in that case map its error to `SubprotocolMismatch` too (test 21 uses a mock that echoes a subprotocol the client did not offer, and one that echoes nothing). The text for this variant says "update or restart required" because it means the gateway speaks a different protocol.

### 9.3 Refusals

What the gateway does at `/api/ws` before accepting, and what the client sees:

| Condition | Gateway action (F35, F36) | Client sees |
|---|---|---|
| gateway not ready, or draining other than a restart wait | close 1013 before accept | upgrade rejected (HTTP 403 expected, U1) |
| request has an `Origin` header, or no ticket subprotocol | handed to the dashboard route (F34), which closes 4401, 4403 or 1013 before accept | upgrade rejected or a dashboard response |
| embedded chat disabled in the gateway (F46) | close 4403 before accept | upgrade rejected |
| the dashboard application fails to load (F47) | close 1011 before accept | upgrade rejected (a 1011 before accept never reaches the client as a close code) |
| bad subprotocol set (two ticket entries, no `hermes-gateway-v1`, empty ticket) | close 4403 before accept | upgrade rejected |
| peer is not loopback, or the host/client checks fail | close 4403 | upgrade rejected |
| ticket unknown, already used, or expired | handed to the dashboard route, which closes 4401 or 4403 before accept | upgrade rejected |
| ticket valid but the profile authority is gone | close 4403 | upgrade rejected |

All of these close before accept, so the client cannot read a close code. The deadline is `ConnectOptions { timeout }` (15 s). `ConnectError::UpgradeRejected { status: Option<u16> }` carries the HTTP status when the library reports one (`tungstenite::Error::Http(response)` gives `response.status()`), else `None`. Never map to a close code; never put the response body, headers or reason phrase in the error (a hostile or buggy server could echo the request, which contains the ticket). Test 22's mock does echo the ticket in body, header and reason phrase to prove the error type holds none of it. The next step text must fit every cause: "The gateway refused the connection. Try again with a new ticket; if it keeps failing, run `hermes gateway status`."

REQ-14 of the issue states the same mapping by cause; the two agree, and an HTTP response is the only case that gives `UpgradeRejected`. Library errors (`tungstenite::Error`) map to variants with no inner text (confirm the library's variant names at the version used): `Io(kind)` for I/O errors; `UpgradeRejected` for HTTP errors; `SubprotocolMismatch` for protocol errors about the subprotocol; `Timeout` when the 15 s deadline expires (a mock that accepts TCP and never answers); other protocol errors map to `Io(ErrorKind::InvalidData)`. Do not use `{error}` or `{error:?}` of a `tungstenite::Error` in any message: its `Display` can include header values.

After the upgrade, 1011 means the gateway cannot keep up with this client (F44); during the handshake it maps to `HandshakeError::Closed(Closed::Overloaded)`; any other close, or the stream ending without a close frame, is `Closed::Dropped`. Reconnecting is {{P1-03}}'s job.

## 10. The handshake (REQ-15, REQ-16)

All frames are WebSocket text frames holding one JSON value. Events use the notification envelope (F39):

```json
{"jsonrpc":"2.0","method":"event","params":{"type":"gateway.ready","payload":{"skin":{"name":"default","colors":{}},"change_events":true,"heartbeat":true,"replay_epoch":"0123abcd","session_authority":true}}}
```

`replay_epoch` is a string. A `gateway.ready` payload must decode into the generated `GatewayReadyPayload` (F40); `session_authority` is `Some(true)` on the native socket and missing or `false` means this is not a session-authority connection (`NotSessionAuthority`). Frames may arrive before `gateway.ready` (for example `sessions.changed`); the unit keeps them (REQ-16) and keeps waiting.

### 10.1 Sequence

1. Read frames until one is the event `gateway.ready` or the deadline (15 s, `HandshakeOptions::ready_timeout`) passes (`ReadyTimeout`). Frames read on the way are saved raw, in order, in the buffer.
2. Send `{"jsonrpc":"2.0","id":1,"method":"client.capabilities","params":{"server_requests":true}}`. Wait up to `call_timeout` (15 s) for the frame whose `id` is 1. Result decoded into `ClientCapabilitiesResult` (`{"server_requests":["approval.request",...],"declines_not_shown":true}`; names of server requests are whatever the gateway lists). An error reply, an undecodable result, or no reply in time gives `server_requests: None`, and the handshake continues. A connection close while waiting is not one of these: it is fatal (`Closed(Overloaded)` or `Closed(Dropped)`), since the connection is gone.
3. Send `{"jsonrpc":"2.0","id":2,"method":"runtime.describe","params":{}}`. Wait for `id` 2. A result is decoded into `RuntimeDescribeResult` (F43): `instance_id`, `profile_id`, `authority_epoch`, `capabilities`, `session_create` required. Compare `instance_id` and `profile_id` with the connection's identity (8): a difference is `IdentityChanged`. No decode is `BadDescribe`. A reply with neither `result` nor `error` is `BadDescribe`. An error reply is `DescribeFailed { code, reason }` with `code` from `error.code` (an integer; an error with no integer code is `BadDescribe`) and `reason` from `error.data.reason` only if it is a string matching `[A-Za-z0-9_]{1,80}` (Hermes does the same, `gateway_client.py:62-63`; the free-text `message` is never copied). No reply is `CallTimeout { method: "runtime.describe" }`.
4. Return `Handshake { ready, describe, server_requests, timings }` with the three step durations.

Both calls are built from the generated types. {{P0-03}} publishes these paths (use them; if the merged crate differs, stop and report): `hermes_contract::schemas::{GatewayReadyPayload, RuntimeDescribeResult, RuntimeDescribeParams, ClientCapabilitiesParams, ClientCapabilitiesResult}`; `hermes_contract::methods::legacy::client_capabilities::{NAME, Params, Result, Marker}` and `hermes_contract::methods::canonical::runtime_describe::{NAME, Params, Result, Marker}` (`Params` and `Result` are aliases of the schema types above); `hermes_contract::native::NativeMethod`; `hermes_contract::pinned::live_skip_reason`. The first call is `ClientCapabilitiesParams` with `server_requests` set to true (`true` or `Some(true)`, whichever type {{P0-03}} generates), serialised, and the `NAME` constants of each method, so a renamed method in a later contract breaks the build instead of the run. The `NativeMethod` bound check is test 29: a function `fn assert_native<M: NativeMethod>() {}` called for both methods compiles only if the generated marker is implemented (F42: `client.capabilities` is a legacy method the native socket serves; the roadmap's P0-03 step 3 says the marker covers it).

### 10.2 Matching replies and odd frames

| Frame | Handling |
|---|---|
| text frame, JSON object with `id` equal to the awaited id, `result` or `error`, and no `method` | the reply (a "reply" in the issue's words) |
| text frame, JSON with `method: "event"` | buffer raw text (before and after the awaited reply) |
| text frame, JSON with `method` and an `id` that is a string such as `"srq-1"` | a server request: buffer raw, never answer in this unit |
| text frame, JSON object with any other `method` (with or without an `id`, even a numeric one) | never a reply: buffer raw, never answer. A frame with a `method` is not matched against the awaited id |
| text frame, JSON object with an `id` and none of `method`, `result`, `error` | `HandshakeError::BadFrame` |
| text frame, JSON that is neither of the above (no `method`, no `id`, no `result`, no `error`, or not an object, for example an array) | `HandshakeError::BadFrame` |
| text frame, a reply (`result` or `error`, no `method`) whose `id` is not the awaited number | ignore: not buffered, not an error (nobody can be waiting for it; a late reply to id 1 that arrives while id 2 is awaited lands here). The recording tap in `next_text` still sees it |
| text frame, a reply whose `id` is a string such as `"1"` | ignore (ids are matched as JSON numbers only) |
| text frame that is not valid JSON | `HandshakeError::BadFrame` |
| binary frame | ignore |
| ping or pong frame | handled by the library; not buffered |
| close frame with code 1011 | `Closed(Overloaded)` |
| close frame with any other code, or the stream ends | `Closed(Dropped)` |

"Buffer raw" means the exact text of the frame, unparsed (REQ-16). Two reasons: the recorder in {{P1-04}} must see exactly what the gateway sent, and {{P1-02}} must decode events in order with its own typed decoder. Do not remove frames that arrived "too early" and do not reorder them.

### 10.3 The hand-over (REQ-16)

```rust
pub struct ConnectionParts {
    pub sink: WsSink, pub stream: WsStream,        // aliases over tokio-tungstenite's split halves
    pub instance_id: String, pub profile_id: Option<ProfileId>,   // Some once the ticket was minted or the handshake succeeded
    pub next_request_id: u64,                       // 3: ids 1 and 2 were used here
    pub buffered: Vec<String>,                      // raw text frames not yet delivered, in arrival order
}
```

Every text frame this unit sends or reads (the handshake frames) goes through one private pair of functions on `Connection`: `async fn send_text(&mut self, text: String) -> Result<(), FrameError>` and `async fn next_text(&mut self) -> Result<Option<String>, FrameError>`, where `FrameError` is a private enum `{ Closed(Closed), Io(ErrorKind) }` that the handshake converts into `HandshakeError`. The rustdoc of `Connection` names them as the place a recording tap can be added for handshake frames ({{P1-04}}). After `into_parts`, frames flow through the channel functions of {{P1-02}} (its REQ-14), so a recording tap that sees every frame needs both places. Control-socket traffic does not use either: it carries tickets. {{P1-02}} receives `buffered` first and then continues reading `stream`.

`buffered` holds the raw text frames that were read but not consumed: early events and server requests, in arrival order. The three frames the handshake consumed (`gateway.ready` and the two replies) are not in it, and neither are ignored frames. `ConnectionParts.profile_id` is `Option<ProfileId>`: `Some` when the ticket was minted (it is the ticket's) or once the handshake has succeeded (it is the describe result's); `None` for a parsed ticket whose handshake has not run.

Types (private details are suggestions): `pub type WsStreamInner = tokio_tungstenite::WebSocketStream<tokio::net::TcpStream>` (TLS is refused, so the stream is always a plain `TcpStream`); `pub type WsSink = futures_util::stream::SplitSink<WsStreamInner, tungstenite::Message>`; `pub type WsStream = futures_util::stream::SplitStream<WsStreamInner>`. `Connection` and `ConnectionParts` are `Send`, so they can move into a spawned task. All `ConnectionParts` fields are public, so a test builds one by struct literal. Because {{P1-02}}'s tests also need one from a made-up socket pair, add `#[doc(hidden)] pub fn ConnectionParts::for_test(sink: WsSink, stream: WsStream, next_request_id: u64, buffered: Vec<String>) -> ConnectionParts` (identity `instance_id` empty, `profile_id` `None`); this settles the parent's item C-1 for this issue.

| `TicketError::ScopeMismatch` | a host ticket needs the interactive purpose | Report a bug. |
| other `TicketError` variants | plain sentences | non-empty steps |
| `ConnectError::UpgradeRejected` | the gateway refused the connection (with `HTTP <status>` if known) | The gateway refused the connection. Try again with a new ticket; if it keeps failing, run `hermes gateway status`. |
| `ConnectError::SubprotocolMismatch` | the gateway answered with a different protocol | Update or restart Hermes and Talaria so their versions match. |
| `ConnectError::WrongPurpose` | the ticket was made for dashboard requests, not for the session socket | Report a bug. |
| `ConnectError::Timeout`, `TlsNotSupported`, `Io` | plain sentences | non-empty steps; `TlsNotSupported`: "Talaria supports only a gateway on this machine over plain HTTP." |
| `HandshakeError::*` | plain sentences naming the step (for example "the gateway did not send gateway.ready in time") | non-empty steps, one per variant |
| `Closed::Overloaded` | the gateway closed the connection because it could not keep up | Try again; if it repeats, run `hermes gateway status`. |
| `Closed::Dropped` | the connection ended during the handshake | Try again. |

Steps may repeat across variants where the remedy is the same (two variants say "Discover the gateway again." and two say "Report a bug."); the tests assert each exact text, not that steps differ. Constraints common to all: no absolute path, no ticket, no profile name other than the typed one in `Parked` and `NeverDiscovered`. `next_step()` returns `&'static str`, so steps cannot hold runtime text.

### 13.1 Rules for `tests/support/mod.rs`

The mock is built from the Hermes v0.22.4 source and the contract schemas, never from imagination (the issue's test-first rule 4; the v0.6.2 defect was a stub that invented an interface).

- Its `gateway.ready` has every required field: `skin` as an object (`{"name":"default"}` is enough: `SkinPayload` has no required fields), `change_events`, `replay_epoch` as a string; plus `heartbeat: true` and `session_authority: true`. Take example values from the shapes in section 10 and from the contract, not from the prototype recording (trap 7 of section 2).
- The mock sets `umask(0o077)` once in the test process (`rustix::process::umask`, safe), binds each control socket, then sets it to 0600; it creates each home with mode 0700 (set explicitly after creation). - Control side: a `tokio::net::UnixListener` per test. For each connection it reads one line (at most 64 KiB, as F10), records it, writes one reply line, closes. Scripts for each test choose the reply: a good `identify` result, a closing-before-newline, an oversized line, two lines, silence, a ticket reply. It counts connections so tests can assert "no connection" and "two connections".

It marks a ticket used after one upgrade and answers 403 for an unknown, used or expired ticket, as the dashboard route does (F36, U1). After a good upgrade it sends scripted frames: optional early events, `gateway.ready`, replies to `client.capabilities` and `runtime.describe`, odd frames, a close with a chosen code.

### 13.2 Live tests

Command: `cargo test -p hermes-client --test live_attach -- --ignored --nocapture`. Each test prints exactly one `LIVE_ATTACH_RESULT: PASSED` or `LIVE_ATTACH_RESULT: SKIPPED (<reason>)`, so a reader can never mistake a skip for a pass (a lesson of earlier Talaria runs). With `TALARIA_LIVE_REQUIRE=1` a skip panics, which is how the acceptance command fails when a precondition is missing. The preconditions live in one helper, `tests/support/mod.rs`: `pub async fn live_preconditions() -> Result<LiveEnv, String>` with `pub struct LiveEnv { pub home: PathBuf, pub endpoint: Endpoint, pub fixture: ProfileId }`. It runs `discover_with(default_home(), policy Never)`, then `resolve_profile("fixture")`, then `hermes_contract::pinned::live_skip_reason(endpoint.code_sha())`, and returns `Err(reason)` for exactly these three cases, in this order: no gateway (`NoGateway`), `fixture` not served (`NeverDiscovered`), `live_skip_reason` returns `Some`. So `Err` is a skip and nothing else, and the signature stays `Result<LiveEnv, String>`. The test turns `Err(reason)` into a `SKIPPED (<reason>)` line, or a panic under `TALARIA_LIVE_REQUIRE=1` (a shared function `report_skip(prefix: &str, reason: &str)` in `tests/support/mod.rs` prints the line and panics when the variable is `1`; {{P1-02}} and {{P1-03}} pass their own prefix). Every other error (`NotReady`, `ControlRefused`, `Incompatible`, `NamedProfileHome`, `ControlTimeout`, `UnsafeNode`, a `Parked` fixture and so on) makes the helper itself panic, with the error's `Display` and `next_step()` in the message (both are path-free and ticket-free), whether or not `TALARIA_LIVE_REQUIRE` is set: a gateway that answers but is not usable is a finding, not a missing precondition. A parked `fixture` is therefore a failure, not a skip. Later units' live tests ({{P1-02}}) call the same helper.

Test 31 mints with `Purpose::Interactive` and `Scope::profile()` (F50). It prints, for each step, `step <name> ok <n> ms` with `<name>` one of `identify`, `ticket`, `upgrade`, `gateway.ready`, `client.capabilities`, `runtime.describe` and `<n>` the elapsed whole milliseconds. How each is timed: `identify` is the elapsed time of the `discover_with` call (policy `Never`, so no `ensure` can be inside it); `ticket` is `mint_ticket` (`resolve_profile` reads memory and is not timed); `upgrade` is `connect`; the last three come from `HandshakeTimings`. If the handshake returns `server_requests: None`, the test fails (the `client.capabilities` step did not work on a live gateway) and prints `step client.capabilities failed <n> ms` instead of an `ok` line. The test prints nothing but the six step lines and its result line: never `code_sha`, never the home, never a profile other than `fixture`. It then scans everything it printed (collect the lines in a buffer) for `hermes-gateway-ticket` and for any run of 40 or more characters from the token alphabet (a real ticket is 43); either fails the test. It never prints the ticket, the home path or any profile name other than `fixture`. No live test calls `session.create`, `prompt.submit` or any method other than the two handshake calls, and none sends `unattended` (it auto-approves dangerous commands, so it is never used in any test or scenario).

```text
step runtime.describe ok 7 ms
served profiles: default, fixture and 2 others
gateway code_version=0.22.4 code_sha=0123456789ab
ATTACH OK
```

The `served profiles:` line names only `default`, `fixture` and the typed name, if served; every other profile is counted in `and <n> others` (a real machine's profile names are private, and the example's output is pasted into public pull requests). `code_sha` shows the first 12 characters. Formats, so no builder has to guess: the word is always `others` whatever the count (`and 0 others`, `and 1 others`); `default` and `fixture` are listed only when served, in that order, then the typed name if it is neither; `code_version` or `code_sha` shows `unknown` when the gateway sent null or nothing. The tester compares the printed `code_sha` with the first 12 characters of `commit=` in `PINNED` (the issue's operator precondition 3).

On failure, exit code 1, two lines (plus the `step ... ok` lines that succeeded before it):

```text
ATTACH FAILED at <step>: <Display of the error>
Next step: <next_step() of the error>
```

The example cannot tell whether `ensure` ran, because `discover` returns only an `Endpoint`; it times `discover_with` as one step, `identify`, and prints no `step ensure` line. The other steps are timed as in 13.2. When `client.capabilities` gets no usable answer (`Handshake.server_requests` is `None`; the handshake itself succeeded) the example prints `step client.capabilities failed <n> ms` in place of the `ok` line and carries on to `ATTACH OK`: the issue says that failure is not fatal. A run of the example with that line is not a pass for UAT-1.

`<step>` is `discovery` (identify is part of it; also `NamedProfileHome` and the `HomeNotServed` family), `ensure` (for `DiscoveryError::Ensure(_)` and `StillUnreachableAfterEnsure`), `profile lookup` (`ProfileLookupError`), `ticket`, `upgrade` (`ConnectError`), `gateway.ready`, `client.capabilities` (never fails the run) or `runtime.describe` (the `HandshakeError` is assigned to the step that was running). The example never prints a ticket, an absolute path, or a profile name other than `default`, `fixture` or the typed one. With a gateway reporting only `fixture` and `default`, the typed name is one of them, so nothing else can appear.

## 14. Dependencies, design reasoning and open points

Versions: exact `=` pins under `[workspace.dependencies]`, as {{P0-02}} requires. {{P0-02}} already pins `tokio-tungstenite =0.26.2` and `futures-util =0.3.34` (which this unit uses as they are) and `tokio`, `serde` and `serde_json`. For `rustix`, `sha2`, `thiserror`, `proptest`, `tempfile` and `static_assertions`, which no issue pins yet, the builder takes the newest stable release at least two weeks old and lists every version chosen in the pull request. Suggested crates: `tokio` 1 (features `net`, `io-util`, `time`, `process`, `rt`, `macros`), `tokio-tungstenite` 0.26 with `default-features = false` and feature `connect` (U4: confirm the feature names, and the names `client_async_with_config`, `WebSocketConfig` and `tungstenite::Error::Http`, at the version the unit uses; the prototype used default features and `connect_async`. Whether the library accepts one comma-joined `Sec-WebSocket-Protocol` request header and a matching echo is also unverified: test 20 settles it. If the library rejects a valid echo, stop and report; do not quietly split the header), `futures-util` 0.3, `serde` and `serde_json`, `thiserror`, `sha2` (the home hash), `rustix` (feature `fs` and `process`: `getuid`, `open` with `OFlags`, `umask`); dev-dependencies `proptest`, `tempfile`, `static_assertions`. `unsafe` is forbidden (rule 6 of the roadmap); `rustix`'s safe API covers every call.

Design reasoning for the points where this unit differs from Hermes or the prototype:

| Choice | Reason | Revisit when |
|---|---|---|
| State checked before served profiles | A starting gateway would otherwise read as a profile mismatch, and the user would be told to fix a profile instead of waiting | Hermes changes its check order |
| Group-write on the home accepted | The peer user id check authenticates the listener; Hermes' stricter home rule needs the passwd and group databases and has no equivalent in the Rust standard library | Hermes adds a ticket binding that depends on the home's mode |
| No `ensure` for an incompatible gateway | `ensure` stops and replaces it (F23), possibly cutting another client's turn; the user restarts it by hand | The operator decides replacement is acceptable |
| 90 s `ensure` deadline | The 60 s default plus margin; Hermes' own client uses 30 s because it also retries; Talaria runs it once | Cold starts get slower |
| 15 s connect deadline | The shared TypeScript client's value (F32); Hermes' Python client uses 10 s (F31) | Measured upgrade times exceed 1 s |
| One control-reply limit (524,288 bytes) for tickets too | Simpler than a second limit; a ticket reply is small and a larger one is harmless | A hostile gateway is in scope |
| Hand-written `api_origin` parser | `url` drops an explicit default port, so "port required" cannot be enforced | The `url` crate keeps it |
| Typed errors with no inner text | The ticket or a path could ride in a library error; typed variants cannot | Never |
| A named-profile home with a stale socket is `NamedProfileHome`, never `ensure` | `ensure` there could start or replace a gateway for a profile the user did not name; Hermes serves most named profiles from the default gateway | The operator wants Talaria to start standalone profile gateways |
| Missing or relative home is `NoGateway` with no `ensure` | `HERMES_HOME` for `ensure` must be a canonical home, and a home that does not exist means Hermes was never set up there | Talaria is asked to set Hermes up |
| `ensure` standard error is discarded | it adds a leak path and the next step already tells the person to run `ensure` themselves | A diagnosis needs it |
| Group-writable home accepted | see 4.4; the cost is a `NotAuthenticated` at mint time with a step that names `chmod g-w` | Hermes' rule becomes cheap to match |
| A failed upgrade maps by cause (HTTP response, I/O error, deadline, subprotocol), not all to `UpgradeRejected` | The cause is known for everything except an HTTP response, and the next step for `Io` or `Timeout` can then say "try again" truthfully; only an HTTP response is ambiguous (REQ-14 of the issue) | The library exposes a status for every failure |
| The example's default policy is `Run`; agents pass `--no-ensure` | A person at a terminal wants a gateway started; no agent may start one (settled decision 3) | The operator wants the example to default to `Never` |
| `live_preconditions` returns `Err` for a skip only and panics on every other error | The `Result<LiveEnv, String>` type cannot carry a failure, and a failure must never read as a skip | A later unit needs a typed outcome |
| `Scope` as a struct with a fallible constructor | The invalid pair (host with native-http) cannot be built | Hermes allows more host purposes |

Open points the builder reports instead of deciding: any difference between the values in sections 5 to 10 and the pinned Hermes; any status other than 403 for the unknown-ticket upgrade (U1); any Hermes change that moves `client.capabilities` or `runtime.describe` off the native socket; anything needing a file owned by another issue.

| Choice | Reason | Revisit when |
|---|---|---|
| A pointer file with open permissions or a symlink is `UnsafeNode { PointerFile }`, not `BadPointer` | Hermes separates `unsafe_control_pointer` (type, owner, mode) from `invalid_control_pointer` (size, path form, leaf), and REQ-3 applies the "private" rule to the pointer file. An earlier draft of the test list put mode 0644 and a symlink under `BadPointer`; this document and the issue's requirements agree on the split above | Hermes merges the two codes |
