Status: `proposed`. The GitHub issue for this unit is the contract; this document is its reference specification. If they disagree, the issue wins and the disagreement is reported on the issue.

## 1. What this unit delivers, in one picture

```text
developer types T in Talaria (ultracode on)
  route_submit(T, on) ──► Workflow { "/talaria-workflows T" }
  P2-03 command service ──► slash.exec {session_id, command: "talaria-workflows T"}   (P2-03 sends the line without "/")
  Hermes owner ──► {type:"skill", name:"talaria-workflows", message:"[IMPORTANT: The user has invoked the ...<skill body>... T",
                    display:"/talaria-workflows <T with whitespace runs collapsed>"}
  accept only type skill + name talaria-workflows
  P2-03 SubmitCommand ──► prompt.submit {session_id, text: message, submission_id}
  user cell shows display; lead model reads SKILL.md body
lead session (its own terminal tool; HERMES_HOME there names the profile folder):
  HERMES_HOME='<root>' talaria workflow roster --profile <p> --json        (this unit)
  asks the developer: plan + estimate, go ahead?   (every run)
  terminal(command="HERMES_HOME='<root>' talaria workflow run --profile <p> --json <path>", background=true, notify=true)
     → returns process session_id; process_manage(action="wait", session_id=<it>, timeout=<s>) until exited
  reads the final {"event":"run_finished","run_id",...,"outcome","result","spend"} line (P5-06 REQ-10), reports
```

Three deliverables: the skill files and their installer, the roster command, and the toggle.

### 4.6 Rendering

`render(profile, command, hermes_root)`:

1. `profile` must match H20's pattern after lower-casing; else `SkillError::InvalidProfile`.
2. `command` must be a bare name matching `^[A-Za-z0-9._-]{1,64}$`, or an absolute path whose characters are in `[A-Za-z0-9._/-]`, at most 1,024 bytes; else `SkillError::InvalidCommand`.
3. `hermes_root` must be absolute, at most 1,024 bytes, valid UTF-8, with no `'` and no control character (newline included); else `SkillError::InvalidRoot` (exit 2, `Hermes root '<path>' cannot be written into the skill`).
4. Replace every `@@TALARIA_PROFILE@@` with the profile and every `@@TALARIA_COMMAND@@` with `HERMES_HOME='<hermes_root>' <command>`; any remaining `@@` is `SkillError::Template` (a build defect; test 8).
5. Return files in `SKILL_FILES` order with their bytes; line endings are `\n`.

Test goldens render with root `<ROOT>`-replaced output: the test renders with a fixed root `/h` and compares against goldens containing `HERMES_HOME='/h' talaria`.

## 5. The installer

### 5.1 Target and root resolution

```text
resolve(profile):
  name = lowercase(trim(profile)); check H20 pattern                → exit 2 "invalid profile name '<raw>'"
  discovery (`P1-01`) with EnsurePolicy::Never for <name>; ticket; Client::call("profiles.list", {"include_sessions": false}), 5 s
     ok   → row = profiles[0]; row.name != name → exit 1 "gateway serves '<row.name>', not '<name>'"
            home = row.path; root = home if name == "default" else parent(parent(home))
            (a row path for a named profile whose parent is not named `profiles` → exit 1 "unexpected profile folder <path>")
     NoGateway / NamedProfileHome / profile not served / NotReady → fallback
     other error → exit 1 "<plain error>"
  fallback: h = `P1-01` default_home()
            root = hermes_root_of(h, native_home)        (H21's rule exactly; native_home = `P1-01`'s <user home>/.hermes)
            home = root if name == "default" else root/profiles/<name>
            warning "gateway not running; using the local profile folder"
  home must be a directory                                            → exit 2 "profile '<name>' not found (<home>)"
  target = home/skills/talaria-workflows
```

The `profile` key is not sent (the ticket already names the profile; H19 says a mismatching `profile` is `profile_mismatch`). `EnsurePolicy::Never` means no command of this unit ever runs `hermes gateway ensure` (test 21 puts a recording fake `hermes` first on `PATH` and asserts zero runs). `hermes_root_of(home, native_home) -> PathBuf` is a pure function implementing H21's rule (a path under `native_home` gives `native_home`; else a parent named `profiles` gives the grandparent; else the path itself), compared lexically after `P1-01`'s canonicalisation; it never creates anything.

### 5.2 States

```text
            ┌──────────┐ install            ┌─────────┐
            │ missing  │───────────────────►│ current │◄──────────┐
            └──────────┘                    └─────────┘           │ install (replace)
                 ▲ uninstall(current|outdated)  │ new render      │
                 │                              ▼ (version/cmd)   │
                 │                         ┌──────────┐           │
                 └─────────────────────────│ outdated │───────────┘
                                           └──────────┘
   any difference from the record ─► modified ─(--force: backup, replace or remove)─► current | missing
   no record, or a link            ─► foreign  ─(--force: backup, replace or remove)─► current | missing
```

Inspection, in order (no link is ever followed; `symlink_metadata` throughout):

1. Nothing at the target path (not even a dangling link) → `missing`.
2. The target itself is a symbolic link → `foreign`.
3. No record entry for the canonical target path → `foreign` (even if byte-identical to a render).
4. Walk the folder: each regular file gives `<relative path>` and its SHA-256; a symbolic link gives `link:<path>`; any other non-folder entry `other:<path>`. Compare with the record's `files` map:
   - same set of paths and every hash equal → the folder is as recorded; then `current` if the recorded hashes equal `render(profile, cmd, root)`'s, else `outdated`;
   - anything else → `modified`, with `changed_files` entries `changed:<path>`, `added:<path>`, `removed:<path>`, `link:<path>`, `other:<path>`, sorted by path.

The render used for comparison: `install` uses the requested `--command` (default `talaria`) and the resolved root; `status`, `uninstall` and roster use the record's `command` and `hermes_root` (for an unrecorded folder the state is `foreign` regardless). So an install with a custom absolute `--command` reports `current` in `status`.

### 5.3 Install record

`<Talaria home>/skills/installs.json`, mode 0600:

```json
{"version":1,"installs":[{"target":"<canonical skill folder>","profile":"fixture","hermes_root":"<root>","skill_version":"1.0.0","command":"talaria","files":{"SKILL.md":"<sha256 hex>","references/commands.md":"<sha256 hex>","references/examples.md":"<sha256 hex>","references/script-api.md":"<sha256 hex>"},"installed_at":"2026-10-22T12:00:00Z"}]}
```

An unreadable or unparsable record file is an error (exit 1, naming the file); it is never silently replaced. A missing file is an empty record. One entry per canonical target; a reinstall replaces the entry; entries for other targets are preserved byte-for-byte in meaning (re-serialised in the same order). Saving writes `installs.json.tmp-<16 hex>` in the same folder, `fsync`s it, renames it over `installs.json`, and removes the temporary file on any failure.

### 5.4 The transaction (install and uninstall)

`--dry-run` and `status` take no lock and write nothing (they may see a change in progress; re-running gives the settled answer). Every other `install` and `uninstall`:

```text
 1. mkdir -p <home>/skills/.locks (0700 when created)
 2. target lock: open-or-create <home>/skills/.locks/talaria-install.lock; std::fs::File::try_lock every 100 ms, up to 10 s
       timeout → exit 1 "another talaria skill command is changing profile <p>; try again"
 3. record lock: mkdir -p <Talaria home>/skills (0700); same with <Talaria home>/skills/installs.lock
 4. recover() (below), then load the record, inspect (5.2), decide; a refusal releases the locks, exit 1
 5. forced: backup (5.5) before anything moves; a backup failure changes nothing, exit 1
 6. S = <home>/skills/.locks/talaria-staging-<16 hex>/ ; write S/intent.json {kind, target, had_old, new_files: {path: sha256}}
    install: write S/new/talaria-workflows/<files> (0644; folders 0755)
 7. if the target exists: rename target → S/old
    install: rename S/new/talaria-workflows → target
       failure → rename S/old back (if moved), remove S, exit 1 "cannot write <path>: <io error>"
 8. save the record (5.3) with the entry replaced (install) or removed (uninstall)
       failure → install: rename target → S/discarded; rename S/old back (if any); uninstall: rename S/old back;
                 the record file is untouched; remove S; exit 1 "cannot save <record path>: <io error>"
 9. remove S (a failure is a warning only; the next recover() removes it)
10. release the record lock, then the target lock
```

`recover()`, run under both locks before inspection, for each `<home>/skills/.locks/talaria-staging-*` folder:

- if the record (as now on disk) describes the target as it is now (entry present and the folder matches it, or entry absent and the target absent): the change was committed; remove the folder;
- else if it holds `old/`: move the target (if present) to `discarded/`, rename `old/` back to the target; remove the folder; warning `recovered an interrupted change in profile <p>`;
- else (a fresh install interrupted after publishing): if the target's files equal `intent.json`'s `new_files` exactly, remove the target (it is this unit's own unrecorded copy); otherwise leave the target alone; remove the folder.

Every lock is an operating-system advisory lock (`std::fs::File::try_lock`, as ``P5-06`` REQ-6a uses; no new dependency), so a crashed process releases it. Two writers to one target are serialised from inspection to cleanup; a staging folder is only ever removed by a process holding the target lock, so no command removes another's live staging. Staging and rollback copies sit under `.locks`, which both Hermes scanners skip (H7, H28), so no second discoverable `SKILL.md` exists at any moment. A rename across file systems (a `skills` folder that is a mount point) fails with an error and the step's rollback applies.

### 5.5 Backups

`<Talaria home>/skills/backups/<UTC yyyymmddThhmmssZ>-<profile>/talaria-workflows/`: regular files copied byte for byte with their mode; symbolic links recreated with the same link text and never followed (so a link cycle is copied as links); folders recursed; any other entry type (FIFO, socket, device) refuses the whole command before anything moves (`cannot back up <path>: not a file, folder or link`, exit 1). A target that is itself a link is backed up as a link; `--force` then removes the link (never its destination) and installs a real folder. If the backup folder exists (two forced installs in one second), append `-2`, `-3`. Backups are never removed by Talaria.

### 5.7 Edge cases

| Case | Behaviour |
|---|---|
| A recorded folder with `references/` missing, `SKILL.md` removed, or a file added | `modified` (5.2 step 4) |
| A byte-identical folder with no record (record file lost) | `foreign`; `--force` backs up and records it |
| Target is a symbolic link | `foreign`; backup keeps the link; `--force` replaces the link, never writes through it |
| A link or FIFO inside the folder | `modified` or `foreign` with `link:`/`other:`; FIFO refuses backup (5.5) |
| Skills folder not writable | Exit 1 `cannot write <path>: <io error>`; staging removed; record unchanged |
| Record not writable | Exit 1 `cannot save <path>: <io error>`; old folder back; record unchanged (test 16) |
| Two commands at once | Serialised by the target and record locks (5.4); the second waits up to 10 s |
| Profile `Default` | Lower-cased to `default` |
| `--command ./talaria` | Refused (relative path), exit 2 |
| `HERMES_HOME` is itself `<root>/profiles/fixture` | Root found by 5.1's fallback rule; target `<root>/profiles/fixture/skills/...`, never `.../profiles/fixture/profiles/fixture` (test 19) |
| A project-local `talaria-workflows` skill in the session's repository | Hermes uses it instead (H3). `status` cannot see it; `/ultracode status` shows the catalogue's `origin` |
| Hermes Desktop or `hermes skills` disables the skill | The catalogue omits it; `/ultracode on` refuses with the install message; documented in `ultracode.md` as "check that the skill is enabled" |

### 7.4 Turning on, and submit interception

`/ultracode on` (and a bare toggle that would turn it on), for foreground session S:

```text
no session → N8
call commands.catalog {session_id: S} through `P1-02`'s Client::call (15 s), parse with `P2-03`'s CommandCatalog::from_result

```

The fresh call is needed because the canonical gateway sends no `skills.changed` (H9); test 30 seeds ``P2-03``'s cache with a catalogue lacking the skill and a mock whose fresh reply has it, and expects N1. `/ultracode status` uses the same fresh call. This unit does not write into ``P2-03``'s cached catalogue.

```text
on Event::Submit { text } for session S:
  match route_submit(text, state.is_on(S)):
    Plain → existing path, unchanged
    Workflow { command_line, one_shot }:
      if one_shot: notice N7
      composer is cleared exactly as for a slash command (`P2-03`)
      command service runs command_line for S  (its outbound `command` is `P2-03`'s normalised form, without "/")
        Skill { name == "talaria-workflows", message, display, notice? } → (notice?) → Event::SubmitCommand { text: message, display, submission_id: fresh }

        Err(command_unavailable)                                        → N6, restore composer

```

"Restore" puts the original `text` (not the command line) back byte for byte with the caret at the end. No `prompt.submit` is sent on any error path (test 33). An `exec` outcome means a quick or plugin command already ran inside `slash.exec` (H13); the turn-on check refuses that case before any prompt is routed, and the submit path reports it if the command appeared later. The user cell shows Hermes's `display` verbatim; Talaria never recomputes it (test 32).

## 9. Design reasoning and rejected alternatives

1. **Route through the skill slash command (chosen)** versus:
   - `api_text` on `prompt.submit` with a hidden preface: rejected; ``P2-03`` already rejected it, neither Hermes client uses it, and it would hide what happened.
   - `skills: ["talaria-workflows"]` on `session.create`: rejected as the toggle mechanism, because preloads are frozen at creation (H29). It remains a good later option for "new session in ultracode".
   - A visible text preface typed into the prompt: rejected; it pollutes the transcript with Talaria's words as if the developer typed them.
2. **One skill load per routed prompt.** Cost grows with skill size, hence the 8 KiB cap and the `references/` split (H17). Hermes's cache boundary sits before the user instruction (H16), so the repeated scaffold is cache-friendly.
3. **Direct file install (chosen)** versus REST `POST /api/skills` (writes `SKILL.md` only, needs a native HTTP ticket; ``P4-05`` deliberately never calls it) and `skills.manage install` (hub identifiers only, H11). Direct writes also work with no gateway running. Hermes notices on lookup (H8).
4. **Profile and root rendered into the skill.** The lead's terminal sees the profile folder as `HERMES_HOME` (H22), where ``P1-01`` cannot find the root gateway; the installer knows the root, so it writes `HERMES_HOME='<root>'` before every command. Rejected: changing ``P1-01``'s discovery to climb to the root (a sibling interface change affecting every command) and relying on the terminal's environment (it names the profile folder, not the root). One install per profile is natural, because skills are per profile.
5. **The lead asks before every run.** Claude Code's workflow tool has an approval prompt (u12). Talaria's lead is a model following a skill, so the ask is an instruction (S5), backed by ``P5-06``'s preflight estimate and budgets. A session-wide waiver is not authorised (operator decision 2).
6. **Foreground run in a background terminal (default) versus `--detach`.** The foreground run's `run_finished` line carries the result. `--detach` survives the session; its result comes from completed-run replay (``P5-06`` REQ-12, REQ-12a), because `list` carries no result.
7. **Parked calls go to the developer.** ``P5-06`` keeps a parked runner alive holding its lock, so `resume` would be refused; `resolve` is the only answer path, and choosing `rerun` can pay twice, so the lead never chooses it alone.
8. **Toolsets from ``P5-08``'s closed list.** Hermes has no read-only file toolset (H27); worktree isolation plus a no-edit instruction is the honest best, matching ``P5-08`` decision 4. Rejected: claiming read-only reviewers.
9. **A transaction with two locks and staging under `.locks`.** Rejected: staging beside the target (a discoverable duplicate `SKILL.md` can make the name ambiguous, H28); a record-only lock (two writers could publish different renders and record the other's hashes); deleting the old folder before the record is saved (a failed save would lose it).
10. **Accept only the `talaria-workflows` skill outcome.** A quick or plugin command can take the name first (H13); forwarding its result would submit something the developer did not ask for.
11. **No persistence of the toggle.** A process flag covers the daily case; persisting is an operator question.
