## 1. What this unit adds, in one picture

```text
script: agent("fix test A", { isolation: 'worktree' })   agent("fix test B", { isolation: 'worktree' })
            | CallId full digest D1, occ 0                       | CallId full digest D2, occ 0
            v                                                    v
  GitWorktrees::worktree_for  ->  <run data>/worktrees/<D1>-0      <run data>/worktrees/<D2>-0
                                  branch talaria/wf/<run>/<D1>-0   branch talaria/wf/<run>/<D2>-0
            \________________  {{P5-03}} sends each as cwd + cwd_explicit: true on session.create  ____/
                                                 v
                              two Hermes sessions, two folders, no shared files
```

The operator's own checkout is never a session folder for an isolated call. Its working tree is never modified by creation; `git worktree add` necessarily writes administrative data under the source repository's `.git/worktrees/` and the new folder, which is expected. Terms: source folder is the launch folder; run data folder is `<runs directory>/<run id>/`. Worktrees live under the run data folder.

## 4. Design (normative)

### 4.1 Names

- Call name: `format!("{}-{}", digest, occurrence)` with the full `digest`. `{{P5-01}}` guarantees 64 lower-case hexadecimal characters; validate that shape (64 characters, all `0-9a-f`) and fail with `invalid call identity: digest must be 64 lower-case hexadecimal characters` on any other value. Never slice with an index that can panic (use `get(..)`-style checked access anywhere a length is assumed). Never sanitise by replacing characters: digest and run id are already safe, and replacement could collide two calls. The display form `<first 12 hex>#<occurrence>` is for logs only.
- Folder: `<run_dir>/worktrees/<call name>`. Branch: `talaria/wf/<run_id>/<call name>`. `WorktreeInfo.call` is exactly this call name.
- Sidecar: `<run_dir>/worktrees/<call name>.json`, with exactly six fields `call_digest` (full digest), `occurrence`, `branch`, `base_commit`, `repo_root`, `base_dirty`. First written provisionally before the git creation command, then finalised after it (section 4.4), each time by temp file plus rename in the same folder, like the journal's manifest writes. A 12-character prefix alone must never name a folder or branch: digests `a1b2c3d4e5f6` followed by 52 zeroes and the same prefix followed by 52 ones are different calls and must not collide (issue test 3).

### 4.2 Why the run folder, and why `HEAD` with no fetch

Placing worktrees under the repository pollutes the operator's checkout, shows up in their status, and entangles two owners' cleanup. The run data folder (`{{P5-02}}`) is already private (0700), already per-run, and already where the journal points; deleting a run's data deletes its worktrees' provenance with it. `git worktree add` accepts an absolute path anywhere. The cost: worktrees do not appear in the operator's usual in-repo listing; `list()` and `git -C <repo> worktree list` both still show them. Keeping the run data folder outside the source repository (as the acceptance scenarios set up) also keeps `git status` in the source checkout empty, which UAT-1 asserts.

Base `HEAD` with no fetch keeps each creation pinned to the SHA captured at that call's creation, offline, and resume-stable for already-created worktrees. New calls created later use the source `HEAD` at their own creation; there is no run-wide single base. The fleet view's interactive launch (`{{P3-03}}`) fetches because a human explicitly asks for fresh code once; a workflow may create ten worktrees in a second and must not mutate the operator's remote-tracking refs as a side effect. A script that needs fresh `origin` fetches in a non-isolated agent and isolates afterwards.

### 4.4 Creation and reuse procedure

All steps run under the provider's single mutex, with `git` invoked as an argument vector (never through a shell). The mutex guards every mutable field including the cached repository root, covers `worktree_for`, `list()` and `remove()`, and is recovered when poisoned (`unwrap_or_else(|e| e.into_inner())`), so a panic during one git invocation cannot fail every later call. The provider is therefore `Send + Sync + 'static`.

Canonical-form rule (normative): the run data folder is canonicalised at construction where it exists; the source folder is canonicalised before discovery and error formatting; the repository root is the canonical `rev-parse --show-toplevel` output; the created folder is canonicalised after creation. Every message, sidecar value, returned path, listed path and comparison uses that one form. For a folder that no longer exists, `list()` uses the derived path (canonical run data folder plus `worktrees/<call name>`) instead of attempting a canonicalisation that would fail.

1. Discover once: `git -C <canonical source folder> rev-parse --show-toplevel` → `repo_root`. Failure → issue REQ-7's exact composed message (the expected value in tests is built by running the same git command in the test). Cache the root.
2. Compute folder, branch and sidecar path (4.1). Create `<run_dir>/worktrees`.
3. Decide by what exists (the decision table; every git check that exits non-zero counts as failing that check and is never surfaced as a separate git error):
   - Folder exists and both ownership checks pass — (a) `git -C <folder> rev-parse --path-format=absolute --git-common-dir` equals `git -C <repo_root> rev-parse --path-format=absolute --git-common-dir` after trimming and canonicalising the printed path where it exists (comparing the owner's relative `.git` output literally would never match a worktree's absolute output, which is why the absolute form is required), and (b) `branch --show-current` equals the expected branch — then validate the sidecar (digest, occurrence, branch and repository root must match). Valid: return the folder untouched. Missing sidecar: reconstruct it (`base_commit` = folder `HEAD`, current `base_dirty`) atomically before returning; unwritable provenance fails with `worktree provenance cannot be recovered for <folder>: <reason>`. Mismatched sidecar: REQ-9 failure.
   - Folder exists and any check fails (including a plain directory, or a folder inside a different repository) → `worktree path exists but is not this run's worktree: <folder>`, folder never modified.
   - Folder missing, sidecar exists, branch missing → lost worktree: `worktree for call <call name> was lost: folder and branch are both missing (sidecar at <sidecar path>)`. Create nothing; leave the sidecar. Fresh creation is only for a call with no sidecar.
   - Folder missing, branch exists (`git show-ref --verify refs/heads/<branch>`) → confirm with `git worktree list --porcelain` that a stale administrative entry names this exact folder, only then `git worktree prune`, then `git worktree add <folder> <branch>`. Prune is repository-wide: it can also clear other stale entries for folders already deleted by hand. It never deletes a branch or a live folder; that side effect is accepted and declared in the pull request. Afterwards ensure the sidecar is final: an existing sidecar keeps its original `base_commit`; a reconstructed one records the branch tip (`git rev-parse <branch>`). Unrecoverable provenance fails as above.
   - Neither folder, branch nor sidecar → capture `base_commit` (`rev-parse HEAD`) and `base_dirty`, write the provisional sidecar atomically, then `git worktree add -b <branch> <folder> <base_commit>` (the captured SHA, never the literal `HEAD`, so a commit landing between capture and creation cannot split the recorded base from the worktree's real `HEAD`), then finalise the sidecar atomically with the same six fields. On git failure, report `cannot create worktree <folder>: <first stderr line, trimmed>` and remove the provisional sidecar when no folder was created.
4. Canonicalise the folder path, assert it is absolute, a directory, and not equal to the canonical source folder. Return it.

`list()` holds the same mutex, reads sidecars (a malformed one is skipped, never fatal), and derives each path by the canonical-form rule above. `call` is the section 4.1 call name. Dirtiness is `status --porcelain` non-empty in the worktree; a git error on an existing folder counts as dirty, while a vanished folder reports `dirty: false` at its derived path. A worktree whose sidecar is missing is never listed: there is no fallback discovery from git, so the provider cannot adopt a folder it cannot prove it owns.

`remove(path, force)` holds the same mutex and finds the owning sidecar by canonical path equality (canonicalised input, or its absolute form when it no longer exists, compared with each derived sidecar path). Without a match it refuses with `not a workflow worktree: <path>`, including a path git knows as a worktree of the same repository but that has no sidecar. Dirtiness follows the `list()` rule. A clean removal runs `git worktree remove <path>`, then deletes the sidecar and leaves the branch. A forced removal runs `git worktree remove --force <path>`, then `git branch -D <branch>`, then deletes the sidecar last. Both successful paths delete the sidecar, so the entry disappears from `list()` and carries no stale provenance into a later call. A folder that already vanished is handled by pruning its confirmed entry, deleting the sidecar, and deleting the branch only when forced.

#### 4.6 Where `source_cwd` comes from (runner wiring)

`source_cwd` is the absolute canonical launch-process folder captured once at new-run start: `{{P5-06}}`'s `--cwd` (defaulting to the current directory made absolute), stored as `launch.json`'s `cwd`. The runner constructs `GitWorktrees::new(run_dir, source_cwd, run_id)` from that stored value in `crates/talaria-workflow/src/runner/execute.rs` and installs it as `LaunchDefaults.worktrees`. On resume the runner reads the stored `launch.json` value back; the resume command's `--cwd` override applies to non-isolated sessions for that execution only and never changes provider discovery. A run resumed from inside a different repository therefore still discovers and creates worktrees in the original repository. This unit owns that construction, its import, the `LaunchDefaults` value and the resume read-back; the provider implementation itself can land before `{{P5-06}}`, but the wiring change merges only after it (merge gate). The runner-level proof is issue test 17.

### 4.5 What the agent sees

Hermes runs the session's tools with the worktree as the working folder. Committed files at the base commit are present; the operator's uncommitted edits, untracked files, ignored files (build output, local environment files) and submodule contents beyond git's defaults are not specially handled. Prompts that depend on an ignored local file will fail inside the agent; that is visible in the transcript and is the script author's to fix (fetch or generate it in the worktree). Document this in `docs/workflows/` only if `{{P5-06}}`'s runner documentation establishes the file first; otherwise the example's help text carries it.

## 5. Edge cases

| Case | Behaviour |
|---|---|
| Source folder is a subdirectory of a repository | The repository root owns the worktree; the session folder is the worktree root, not the subdirectory. Scripts that need a subfolder say so in the prompt. |
| Source repository has a detached `HEAD` | Allowed. `HEAD` still names a commit; the new branch starts there. |
| Base repository is dirty | Allowed; `base_dirty: true` recorded. The worktree starts clean from `HEAD`. |
| Two runs, same repository | Disjoint by run folder and by the `talaria/wf/<run_id>/` branch prefix. Neither provider instance sees the other's sidecars. |
| Operator deletes a worktree folder by hand | Next call reattaches the surviving branch (issue REQ-10). If the branch is also gone and a sidecar remains, the call fails with the lost-worktree error and creates nothing: the earlier work is unrecoverable and must not be hidden behind a fresh tree. A call with no sidecar is simply never-created and follows fresh creation. |
| Operator renames or moves the run folder | Stored launches point at the old absolute path; resume fails creation checks with REQ-9's message rather than creating a twin. Moving run data is unsupported, as with the journal. |
| Crash between branch creation and folder creation | The next call takes the branch-exists path (REQ-10). Prune runs only after confirming a stale entry names this run's folder; its repository-wide clearing of other stale entries is accepted, declared, and never deletes a branch or live folder. |
| Crash after git creation, before the sidecar is final | The provisional sidecar (written before git ran) plus the folder checks let the next call validate or reconstruct provenance before returning. Success without a listable, removable sidecar is forbidden; unrecoverable provenance fails plainly (issue test 13). |
| Sidecar deleted by hand from a live worktree | The worktree becomes invisible to `list()` and refused by `remove()`. It is never adopted from git output. Deleting provenance is an operator action with that stated cost. |
| Resume launched from a different repository | The provider is rebuilt from the stored `launch.json` folder (section 4.6), so discovery still finds the original repository. The resume `--cwd` does not affect worktree calls. |
| Very long run ids or digests | The full 64-character digest plus occurrence is used in folder and branch names (under 90 characters of name), staying below git and filesystem limits. |
| Two digests sharing their first 12 characters | Distinct folders and branches, because the full digest names both (issue test 3). |
| Run data folder reached through a symlink | One canonical representation is returned, listed and compared everywhere, including the macOS temporary-directory symlink resolution (issue test 12). |
| Git check command fails on an existing folder | Counts as failing the ownership check and yields the REQ-9 message; the folder is never modified. A folder inside a different repository is reported the same way, as a foreign folder. |
| `git` output is localised | Parse exit codes and the machine-stable subcommands' output (`rev-parse`, `branch --show-current`, `status --porcelain`) only. Human sentences from `git` are surfaced in errors, never parsed. |

## 7. Reasoning and rejected alternatives

- **Copy the repository per agent.** Simple, and wrong at scale: no shared object store, no branch to review, huge for large repositories. Worktrees share the object store and give each agent a real branch.
- **One worktree per run, shared by its agents.** Defeats the purpose: parallel editors still collide. Per-call is the unit the journal and `CallId` already give us.
- **Reuse the fleet view's worktree code (`{{P3-03}}`).** Different owner, different base rule (fetched `origin`), different lifecycle (a human opens and reviews it). Sharing would couple a headless runner to an interactive surface; the two may converge later behind this same trait if the operator asks.
- **Delete worktrees when the run finishes.** Finished-agent output is often the deliverable (`fix-failing-tests` results, reviewer patches). Deletion stays explicit and dirty-aware.
- **Reuse Hermes CLI worktree creation, or move the session afterwards with `session.mutate` workspace.** The first belongs to an interactive process and the second would make the folder a later, mutable property. The workflow contract needs one final folder, chosen before create, owned by the run — so both are rejected here.
- **Silently recreate a lost worktree, or discover sidecar-less worktrees from git.** Both hide data loss or adopt folders the provider cannot prove it owns. The first is an explicit error; the second is invisible-by-design.
- **Short (12-character) folder names.** Shorter paths, but two full digests can share the prefix and collide. The full digest costs a longer name and removes the collision class entirely.
