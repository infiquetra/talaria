## 1. What this unit is, and what it is not

When several Hermes sessions work in the background, the operator is typing in one of them and is not watching the others. This unit makes the others reach the operator: a terminal bell and an OSC 9 desktop notification (OSC 9 is the escape sequence `ESC ] 9 ; <text> BEL` that asks the terminal to show a system notification) when a background session needs an answer, finishes or fails; four counters in the status line (needs you, failed, working, done); one key that jumps to the oldest background request; and one notice after start-up when requests were already waiting.

It **is**:

- a pure tracker in `talaria-core` (`crates/talaria-core/src/fleet_attention.rs`) that turns the fleet registry's attention notices (unit P3-01) into alerts, with the rules of section 5;
- a pure, shared rate gate (`crates/talaria-core/src/alert_gate.rs`) through which every alert passes, the foreground alerts of unit P2-13 included, so two sources never ring twice in a burst;
- glue in `talaria-app` (`crates/talaria-app/src/fleet_attention.rs` plus a minimal touch of `app.rs`) that feeds the tracker, holds attention notices until their snapshot arrives, builds the status-line counts, schedules one-shot wakes, and turns the jump key into P3-02's "open the fleet view on this row";
- a minimal touch of the terminal holder (`crates/talaria-cli/src/run.rs` in P1-12's plan) that copies the counts into `StatusInputs` and forwards the jump key to the application;
- two new status-line segments (failed, done) in unit P1-10's `status/segments.rs` and two new `StatusInputs` fields;
- one key action (`attention_next`, default `alt+a`) and two configuration keys (`[notifications] fleet_needs_you`, `fleet_finished`).

It is **not**:

- a Hermes client: it calls no Hermes method and handles no Hermes event. Everything it knows comes from P3-01's `FleetSnapshot` and `FleetNotice::Attention`. (The roadmap row lists no Hermes calls for this unit.)
- the foreground alerts: those stay P2-13's (`AttentionTracker`). This unit ignores every notice flagged `foreground: true`.
- the place where an approval is answered: answering from the peek panel calls `approval.respond`, which P3-02 builds (its REQ-11; its body records on PH3 that it builds what the roadmap's P3-06 row mentions, and that this unit reuses it). This unit owns the path to that panel (the alert, the counter, the jump key) and proves it end to end in UAT-2.
- Herdr pane state for background sessions. The architecture's Notifications bullet says Talaria reports "its own pane state (working, blocked, idle)"; P2-13 does that for the screen's session (its decision 8). Whether a background wait should also count is operator question Q2.

## 4. Interfaces (Rust)

Names are binding where a test uses them. Plain value types derive `Debug`, `Clone`, `PartialEq` (and `Eq`, `Copy` where possible). Times are `std::time::Instant` supplied by the caller: the core reads no clock. Source comments carry no planning codes (roadmap rule 7); the codes in the comments below are for this document only.

```rust
// crates/talaria-core/src/fleet_attention.rs  (pure: no I/O, no clock, no terminal library, no hermes-client)
use crate::attention::{Alert, AlertKind, NeedSummary};                          // P2-13
use crate::fleet::{FleetRow, NeedDetail, NeedId, Outcome, RowKey};              // P3-01 (RowKey from P2-07)

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum FleetScope { All, Watched, Off }

#[derive(Clone, Debug, PartialEq)]
pub struct FleetAttentionConfig {
    pub bell: Vec<AlertKind>,            // [notifications] bell
    pub desktop: Vec<AlertKind>,         // [notifications] desktop
    pub done_after: Duration,            // done_after_seconds
    pub needs_you: FleetScope,           // fleet_needs_you, default All
    pub finished: FleetScope,            // fleet_finished, default Watched
}
pub const QUIET_AFTER_CONNECT: Duration = Duration::from_secs(4);
pub const QUIET_AFTER_SETTLED: Duration = Duration::from_secs(3);
pub const QUIET_CAP: Duration = Duration::from_secs(15);

pub struct FleetAttention { /* cfg, foreground profile, connected flag, window { opened_at, end, settled },
                               watched keys (newest 512), turn marks: key -> Known(Instant) | Unknown (at most 512),
                               alerted need ids (newest 512), suppressed_needs flag */ }

impl FleetAttention {
    pub fn new(cfg: FleetAttentionConfig, foreground_profile: String) -> FleetAttention;
    pub fn set_foreground_profile(&mut self, profile: String);
    /// Link state. A transition from not connected to connected opens a window and returns its provisional end (the cap).
    pub fn observe_link(&mut self, connected: bool, at: Instant) -> Option<Instant>;
    /// Called for every snapshot whose profile list is non-empty and has no Loading profile.
    /// The first call inside an open window fixes its end (section 5.6) and returns it.
    pub fn observe_settled(&mut self, at: Instant) -> Option<Instant>;
    /// Every Changed snapshot: updates the watched set and the turn marks (5.3, 5.4).
    pub fn observe_rows(&mut self, rows: &[FleetRow], at: Instant);
    /// One attention notice, after the hub's hold (5.7). `detail` is the queue item's detail when the item is
    /// in the latest snapshot; `row` is the row from the latest snapshot.
    pub fn on_attention(&mut self, kind: AlertKind, key: &RowKey, need: Option<&NeedId>,
                        detail: Option<&NeedDetail>, foreground: bool, row: Option<&FleetRow>,
                        at: Instant) -> Option<Alert>;
    /// A wake. Returns the start-up notice at most once per window (5.6).
    pub fn on_wake(&mut self, at: Instant, sessions_needing_you: usize, key_label: Option<&str>) -> Option<String>;
}

pub fn row_label(key: &RowKey, title: &str, foreground_profile: &str) -> String;      // 6.1
pub fn need_phrase(summary: &NeedSummary) -> String;                                 // 6.2
```

## 5. Alert rules

### 5.1 Decision order for one attention notice (`on_attention`)

1. `foreground == true`: no alert; nothing remembered, no mark touched (P2-13 alerts for the foreground). Stop.
2. `kind` is `Done` or `Failed`: take the key's turn mark now, before any filter, so a notice dropped by its scope still clears it (5.4).
3. Scope: `NeedsYou` uses `cfg.needs_you`; `Done` and `Failed` use `cfg.finished`. `Off`: no alert. `Watched` and the key is not in the watched set (5.3): no alert. `All`: continue.
4. `kind == NeedsYou` and `need` is `Some(id)`: if `id` is in the alerted-id memory, no alert; otherwise remember it (newest 512). The id is remembered whether or not the queue item was found and whether or not a later step drops the alert (as P2-13 does). A notice already dropped by step 3 never reaches this step, so its id is not remembered; that is harmless because P3-01 emits each id once. With `need == None` this step is skipped (P3-01 sends an id with every `NeedsYou`, S2).
5. `kind == Done`: if the row's `outcome` is `Some(Interrupted)`: no alert. If the mark taken in step 2 was `Known(t)` and `at - t < cfg.done_after`: no alert. If there was no mark at all: no alert (the fleet never saw the turn `Working` or `NeedsYou`, so it ran between two snapshots and was shorter than one registry refresh; the counter still shows it). `Unknown`: continue.
6. `kind == Failed`: continue.
7. Quiet window: if `at < end` of an open window: no alert; when `kind == NeedsYou`, set `suppressed_needs = true`.
8. Channels: `bell = cfg.bell.contains(kind)`, `desktop = cfg.desktop.contains(kind)`; both false: no alert.
9. Text: `fleet_alert_text(kind, row_label(..), detail, row.outcome)`; `None` gives no alert. Build `Alert { kind, bell, desktop, text }`.

The hub passes the alert through `AlertGate::admit` (5.5) and, when admitted, `app.rs` emits P2-13's "send alert" effect with that `Alert` and `urgency(kind)`.

### 5.2 Scopes

| `fleet_needs_you` / `fleet_finished` | Meaning |
|---|---|
| `all` | every background row of the fleet |
| `watched` | background rows this Talaria process has watched (5.3) |
| `off` | never |

Defaults: `fleet_needs_you = "all"` (Hermes denies the command after 300 s by default, H1, whoever started the session); `fleet_finished = "watched"` (scheduled `cron` runs and other clients' sessions finish all day, H3 to H5, and Desktop suppresses background completions for the same reason, D2).

### 5.3 The watched set

A key enters the watched set when any `Changed` snapshot shows its row with `foreground == true` or `subscribed == true` (S14). That covers: the session the operator started or resumed here, a session switched away from (it was foreground), a session peeked or replied to from the fleet view, and a session a launcher reports. The set holds the newest 512 keys (insertion order; re-insertion refreshes). Nothing is persisted.

### 5.4 Turn marks (for the done threshold)

Marks are `Known(Instant)` or `Unknown`. `observe_rows(rows, at)`:

- For each row with `state` `Working` or `NeedsYou` and no mark: insert `Known(at)`, or `Unknown` when the link is not connected or a quiet window is open (the fleet is still learning what was already running; such a turn's length is not known).
- For each row with `state` `Idle`: remove its mark.
- Rows with `Done` or `Failed` keep their mark (the attention may arrive after the snapshot that shows `Done`).
- Keys absent from `rows`: remove their marks.
- At most 512 marks; the oldest inserted is dropped first.

Taking the mark (5.1 step 2): if the row in the latest snapshot is `Working` or `NeedsYou`, a new turn has already started and owns the mark: leave it and treat this notice's length as `Unknown`. Otherwise remove the mark and use it. An `Unknown` mark counts as long enough (the alert fires); no mark at all counts as too short (no `done`; `failed` is not affected). So a turn that was already running when Talaria connected rings `done` when it ends (if its scope allows), like P2-13's restored turn, while a turn the fleet never saw running stays silent. Because the tracker only removes marks in `observe_rows`, a caller that passes `row: None` without first feeding a snapshot that lacks the row still has the mark (test 5 relies on this); in the hub, a row that vanished from the snapshot has lost its mark, so its `Done` stays silent (E26).

### 5.5 The shared gate

`AlertGate::admit(alert, at)` with `window = 2 s`:

- No previous emitted alert, or `at - last_at >= window`: emit; remember `(at, kind)`.
- Otherwise emit only if `urgency(alert.kind) > urgency(last_kind)`; a dropped alert does not move the window.

Every alert passes the gate: fleet alerts and P2-13's foreground alerts (P2-13's own 2 s rule runs first, inside its tracker). P2-13's tracker applies the same window and the same urgency rule to its own emitted alerts, so a foreground-only sequence that the tracker emitted is admitted in full, and P2-13's tests pass unchanged. A foreground `needs you` at 0 s and a background `needs you` at 1 s give one alert; a background `done` at 0 s and a foreground `needs you` at 0.5 s give two.

### 5.6 The quiet window

`observe_link(connected, at)`: a transition from "not connected" (initial state, `Connecting`, `Reconnecting`, `Failed`) to `Connected` opens a window: `opened_at = at`, `settled = false`, `end = at + 15 s` (the cap, provisional until settled), `suppressed_needs = false`; returns `Some(end)`. `Connected` again while connected returns `None`. A transition to not connected leaves an open window as it is.

`observe_settled(at)`: inside an open window (`at < end`) with `settled == false`: `settled = true`; `end = min(max(opened_at + 4 s, at + 3 s), opened_at + 15 s)`; returns `Some(end)`. Later calls, and calls outside an open window, return `None`. So the window lasts 4 s when the first full listing arrives within 1 s of connecting, 3 s past the first full listing when it arrives later, and never more than 15 s. Why: Desktop's 4 s covers prompts that its socket replays on open (D5), but Talaria's fleet learns of an already-waiting request only after `session.list`, liveness and `approval.pending` for each profile (S21). The 3 s after the first full listing covers liveness and one approvals round trip; the 15 s cap keeps a broken profile from muting alerts indefinitely.

The window is half open: an alert at exactly `end` is not quiet.

`on_wake(at, n, key_label)`: when no window is open or `at < end`, return `None` and keep the flag. Otherwise, the first wake at or after `end` closes the window and clears `suppressed_needs`; if it was set and `n > 0`, return `Some(startup_notice_text(n, key_label))`; else `None`. Later wakes return `None`. `n` is `counts.needs_you` (sessions) of the latest snapshot. Only an in-scope `NeedsYou` sets the flag (scope is step 3, the window step 7 of 5.1), but `n` counts every background session needing you, the same set the counter shows. This is intended: the notice tells the operator what the counter already shows, and under `fleet_needs_you = "off"` the flag is never set, so no notice appears.

### 5.7 Holding a notice until its snapshot (`AttentionHub`)

An `Attention` notice is held when, in `latest`:

- its row is missing; or
- `kind == NeedsYou`, `need` is `Some(id)` and the queue has no item with that id; or
- `kind` is `Done` or `Failed` and the row's `state` is neither `Done` nor `Failed`.

`foreground: true` notices are dropped before this check and never held (they take no slot and create no wake). Each held notice keeps its arrival `at` and a deadline `at + 1 s`. At every `Changed`, after the tracker has seen the snapshot, each held notice for which none of the three conditions is true any more is decided, in arrival order, at the `Changed`'s time. At a wake, each held notice past its deadline is decided with the latest snapshot as it is: a missing row gives the label `#` plus the last six characters of the key's session id, with the profile prefix from the key (6.1 step 2); a missing item gives `<label>: needs you`; a `Done` row whose `outcome` is still `None` gives `finished`. A `Done` whose row is missing has no mark left (5.4), so it gives no alert (E26); a `Failed` whose row is missing gives `<label>: failed` with that `#` label. At most 64 notices are held; a 65th makes the oldest be decided at once.

## 6. Texts

Cut rule (P2-13's, S7): a cut "to N characters" counts Unicode scalar values; a longer text becomes its first N − 1 characters followed by `…`, so the result is exactly N characters.

### 6.1 Labels (`row_label`)

1. `name` = the row title with C0 controls, DEL, C1 controls and the zero-width and bidirectional characters P2-13's `alert_bytes` drops removed, then leading and trailing whitespace removed.
2. When `name` is empty: `#` followed by the last six characters of `session_id` (all of it when shorter), as Desktop does (D4, minus the preview step).
3. When `key.profile != foreground_profile`: `prefix` = the profile cut to 12, then `/`; `label = prefix + name`.
4. Cut the whole label to 32.

Examples: title `api-refactor`, same profile: `api-refactor`. Empty title, id ending `9f3c2a`, profile `default` while the foreground is `fixture`: `default/#9f3c2a`. A title of only `\u{1b}\u{202e}  `: `#9f3c2a`. A 40-character title, same profile: its first 31 characters and `…`. A 21-character profile built at run time as `"fixture".repeat(3)` (so no other profile name is written in a test, issue test rule 3) with title `x` while the foreground is `fixture`: `fixturefixt…/x`.

### 6.3 Alert texts (`fleet_alert_text`)

| Kind and input | Text (before P2-13 adds `Talaria: `) |
|---|---|
| `NeedsYou`, `detail = Some(Known(summary))` | `<label>: needs you: <need_phrase(summary)>` |

## 13. Design reasoning and rejected alternatives

- **Why a separate tracker instead of feeding P2-13's `AttentionTracker`.** P2-13's tracker models one session (one turn, pane state for Herdr). Feeding it several sessions would break its pane rule and its "session changed clears needs" rule. A second, fleet-shaped tracker plus one shared gate keeps both correct.
- **Why `watched` for finished turns.** Rejected: alert for every background finish (Desktop's comment D2 names the spam: messaging, kanban, cron). Rejected: never alert background finishes (Desktop's choice); the operator asked for agents in the background and needs to know when the one they dispatched is done (pattern 5, C3). `watched` keys on what this Talaria process touched, which needs no new state from P3-01.
- **Why `all` for needs-you.** Hermes denies a blocked command after 300 s by default (H1) whoever started the session; Desktop also breaks through for off-screen attention kinds (D2).
- **Why a quiet window that waits for the first listing.** Desktop's 4 s (D5) assumes prompts arrive with the socket's replay. Talaria's fleet needs several calls per profile before an already-waiting request is known (S21); a plain 4 s would let those ring at start-up. The extension is bounded (15 s) so a broken profile cannot mute alerts.
- **Why hold notices until the snapshot.** The text needs the row and the item; P3-01 does not order `Changed` against `Attention`. A 1 s hold costs nothing visible and makes UAT-1's text deterministic.
- **Why marks are taken before the scope filter.** Otherwise a dropped notice leaves a stale mark that makes the next short turn look long (E19).
- **Why no mark means no `done`.** A turn the fleet never saw `Working` began and ended between two snapshots, so it was shorter than one registry refresh; ringing `done` for it is the two-second-reply failure. Rejected: treating no mark like `Unknown` (it would ring for exactly those short turns). `Unknown` stays "long enough" because it marks a turn that was already running when the fleet connected, whose length really is unknown and may be long.
- **Why the gate is shared and drops rather than queues.** A burst of bells is the failure mode people turn notifications off for. The counter holds the information a dropped alert carried.
- **Why `alt+a`.** Free in every drafted unit (S11; P3-04 moved to `alt+s` and records this unit's binding); a composer-safe chord (P1-08 refuses plain letters in the composer). `ctrl+n` and `ctrl+p` are left for list navigation conventions.
- **Why the app emits an `Alert`, not bytes.** `talaria-app` cannot depend on `talaria-tui`, where `alert_bytes` lives (S16).
- **Rejected: a Herdr `blocked` state for background requests.** P2-13 decision 8 ties the pane state to what the screen shows. Raised as an operator question instead.
- **Rejected: terminal focus tracking** (suppress alerts while the terminal has focus, as Desktop does). It needs focus-event mode in `terminal.rs` (P2-13 lists focus tracking as a non-goal) and tmux and Herdr support for it, which nobody has verified.
