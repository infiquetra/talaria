## 1. Scope map

The reducer is the only place that interprets a session's events. It sits between the transport and the screen:

```text
hermes-client (P1-01..P1-04)   frames in, calls out        no state about a transcript
        |  talaria-app wraps frames as Event, executes Effect values   (P1-12, P1-09)
talaria-core::session (this unit)   update(&mut SessionState, Event) -> Vec<Effect>
        |  reads cells(), final_prefix_len(), live_tail(), open_prompts(), usage()
talaria-tui (P1-06..P1-10)     draws; commits final cells to scrollback
```

| Concern | Owner | What this unit does about it |
|---|---|---|
| Wrapping, Markdown, colours, scrollback | P1-06, P1-07 | Stores raw text only. |
| Approval card, masked `sudo` and `secret` input, `request.cancel` | P1-09 | Provides the prompt registry and the exact response effects. `request.cancel` ids are server-request ids (F32), so the reducer ignores that event. |
| Reconnect, heartbeat, `session.events.since`, gaps | P1-03 | P1-03 turns `session.replay_gap` and an epoch change into one `Gap`; the application then resumes (P1-12 REQ-18). The reducer keeps its own epoch guard as a second line of defence (it sets `needs_resume` and applies nothing). |
| Recording and replay source | P1-04 | Consumes its fixtures and its frame-log format; does not import its code. |
| Queue display, steer, replace, cancel | P2-08 | Keeps submission entries only to order user cells; ignores a snapshot's `pending` list. |
| Checklist item model | P2-11 | Stores `todos` as raw JSON with the highest `revision`. |
| Subagent rows | P3-04 | Treats `subagent.*` as known and ignores them. |
| Notifications such as the low-disk question | later phase | Ignores `notification.show` and `notice` (F31). |
| Many sessions | P3-01 | One `SessionState` per session; an event for another session changes nothing. |

Who sends each local event (the application, never the reducer): `Event::Session` by P1-12 and by P1-11 (its replay bench); `Event::ConnectionOpened` by P1-12 (on each `LinkEvent::Connected`); `Event::Submit`, `Event::SubmitFailed`, `Event::Interrupt`, `Event::InterruptFailed` by P1-12; `Event::AnswerApproval`, `Event::AnswerClarify`, `Event::AnswerFailed`, `Event::AnswerAlreadyResolved` by P1-09. P1-12 and P1-09 do not list all of these yet; the parent records that as a conflict to resolve (see the issue, Interfaces). The reducer also needs the whole `params` object of each event (section 5.1); P1-02's `InboundEvent` carries only the decoded frame.

`is_final()`: user and notice cells are final when created; assistant and reasoning cells when `sealed`; a tool cell when its status is not `Running`; a prompt cell when `sealed` (section 9: sealed when `Settled(Elsewhere)`, and `Settled(Answered)` at the end of the turn; never while `Open` or `Answering`). `CanonicalSnapshot` rows give final cells.

### 5.1 What an `Event::Session` carries, and why

`raw` is the event's whole `params` object: the same value that was given to `EventFrame::from_params`. `frame` is its decoded form. The reducer uses them like this:

- The event type is `frame.type_name()`. The `Unknown` variant is how it tells a type the contract does not know from one it does (section 6.3).
- The envelope fields (`seq`, `replay_epoch`, `execution_generation`, `authority_epoch`, `admission_id`) come from `frame`.
- Every payload field comes from `raw["payload"]`, through small total accessors (`str_field`, `bool_field`, `i64_field`, `f64_field`, `obj_field`) that return `None` for a missing key, `null` or a wrong type. The reducer never reads a payload field from the typed `Notification`.

Why not the typed payload: the generated structs drop every key the contract does not declare, and the contract leaves out fields the gateway sends: `is_error` and `context` on `tool.complete` (F9), `admission_id`, `content` and `outcome` on `message.complete` (F13). They also default absent usage counters to 0, which cannot be told from a real 0 (section 10).

A frame that `EventFrame::from_params` refuses (`Err(DecodeError)`: a known type with a wrong-typed or missing required field) is never turned into an `Event`. P1-02 reports it as a malformed frame, and `tests/support/frames.rs` skips it and counts it. Wrong-typed fields in keys the contract does not declare, and in nested objects the decoder does not look into, do reach the reducer, and the accessors make them harmless.

Until P1-02's `InboundEvent` carries `raw` as well as `frame` (one added field, no change in behaviour), P1-12 cannot build this event. The parent records that as a cross-issue gap. This unit does not edit `hermes-client`.

## 6. Event-by-event rules

"Latched" means the interrupt latch is set (section 8). "Open" means not final. "The turn's cells" are the cells created since the current turn started (`message.start`, or the first turn event when none was seen).

| Event | Rule |
|---|---|
| `message.start` | Apply the scope and cursor rules (section 6.1). Set `Running`, store the event's `execution_generation`, clear the latch and `activity`, and start a new tool-id map (the turn's cells). `seal_all` (section 6.0). If `display_text` is non-blank add an `Automation` notice (kind `Diagnostic` when `notification_category` is `diagnostic`). Take the oldest entry of the submission queue, if any; if its user cell is not yet placed, add it now. |
| `message.delta` | Latched: nothing. Text null: seal the open assistant segment. Text empty: nothing. Otherwise: if no turn is running set `Running` (no `message.start` was seen). Seal an open reasoning cell (this happens even when the whole chunk is then dropped). While the open assistant segment is empty (or none is open), drop leading `\r` and `\n` characters from the chunk; spaces and tabs are kept. If the result is empty do nothing; else append to the open assistant cell or create it. |
| `message.interim` | Latched: nothing. Section 7.2. |
| `reasoning.delta`, `reasoning.available` | Latched: nothing. Seal an open assistant cell. Append to the open reasoning cell or create it. Empty text does nothing. |
| `thinking.delta` | Latched: nothing. Set `activity` to the text, or clear it when empty. |
| `tool.start` | Latched: nothing. Seal open assistant and reasoning cells. If one of the turn's cells has this `tool_id`, change nothing. Else add a `Running` tool cell. Clear `activity`. |
| `tool.progress` | Latched: nothing. Update the running cell with this id among the turn's cells; otherwise ignore. |
| `tool.complete` | Latched: nothing. Seal open assistant and reasoning cells. Find the cell by `tool_id` among the turn's cells. Final already: ignore. Running: fill the fields (section 6.2) and set the status. None: add a final cell built from the payload. |
| `todo.updated` | Replace the checklist unless `revision` is lower than the stored one. Never latched. |
| `status.update` | Empty `text` clears the note and adds nothing to the log; a note equal to the latest (same `kind` and same `text`) changes nothing; else set it and append it to the log (the last 50 notes are kept). Never latched. |
| `session.usage` | Merge (section 10). Never latched. |
| `approval.request`, `clarify.request` | Section 9. Never latched. |
| `approval.settled`, `clarify.settled` | Section 9. Never latched. |
| `approval.cancelled`, `request.cancel` | Silent (section 6.3): F25 and F32. They change nothing. |
| `message.complete` | Section 7.3. Latched: only usage merges and the turn ends `Interrupted`. |
| `error` | Add an `Error` notice with `message`. Never latched. Does not change the turn. |
| `session.replay_gap` | Set `needs_resume`. Apply nothing else. Not subject to the cursor rules (it has no `seq`). Normally never seen here (P1-03 absorbs it). |
| silent events | Section 6.3: no change, no notice. |
| anything else | Section 6.3: noted once. |
| `Event::ConnectionOpened` | Clear the set of noted unknown types. Do not touch cells. |
| `Event::Submit` | Blank text: nothing. Else emit `SendPrompt` and push `{submission_id, text, placed}` on the submission queue. `placed` is true, and the final user cell is added now, only if the turn is not `Running` and the queue was empty; otherwise `placed` is false and the cell is added at its `message.start` (oldest first). The `turn` value does not change here. |
| `Event::SubmitFailed { submission_id, reason }` | Remove the queue entry with that id, whether or not its user cell was already placed (a stale entry would be taken by the next `message.start` and shift every later user cell); add an `Error` notice with `reason` (plain text from the application). Nothing if no entry matches. A user cell already placed stays. The application sends it whenever a submit will start no turn: an error reply, a call that ended `Unknown`, or a `{voice_stopped: true}` reply (F20). For receipts with status `unknown` or `terminal` see section 13. |
| `Event::InterruptFailed` | Clear the latch. |
| `Event::Interrupt` | Section 8. |
| `Event::AnswerApproval`, `AnswerClarify`, `AnswerFailed`, `AnswerAlreadyResolved` | Section 9. |

### 6.0 Which events seal which cells

This table is the whole list; a rule elsewhere that seems to add a trigger is a mistake in that rule. "Seals" means the open assistant cell, reasoning cell or both become sealed (final).

| Trigger | Assistant cell | Reasoning cell | Running tools |
|---|---|---|---|
| `message.delta` with null text | sealed | not touched | not touched |
| `message.delta` with text (even when every character is then dropped) | not touched (it grows) | sealed | not touched |
| `message.interim` | sealed (then the interim cell is added) | not touched | not touched |
| `reasoning.delta`, `reasoning.available` | sealed | not touched (it grows) | not touched |
| `tool.start`, `tool.complete` (any, including one that finds no cell or a final cell) | sealed | sealed | the matching one changes status; others not touched |
| `message.start`, `message.complete` (also the latched one) | sealed | sealed | become `Unfinished` |
| `Event::Interrupt`, `thinking.delta`, `tool.progress`, `todo.updated`, `status.update`, `session.usage`, prompt events, `error` | not touched | not touched | not touched |

`seal_all` is the `message.start` and `message.complete` row plus prompt cells: a `Settled(Answered)` prompt becomes sealed; one that is `Open` or `Answering` stays open.

### 6.1 Scope, cursor and repeats

Order of checks for an `Event::Session`:

1. The outer `session_id` field of the `Event::Session` (not the one inside `raw`) is the one compared: when it differs from the state's, or is empty, ignore the event completely. The reader (12.2) fills it from the frame's own `session_id`, so the two agree for real events.
2. `session.replay_gap`: handle (above) and stop.
3. If the event has `replay_epoch` and the cursor has an epoch and they differ: do not apply; set `needs_resume`; stop.
4. If the cursor has no epoch yet, adopt the event's.
5. If the event has `seq`: if `seq <= last_seq` the event is a repeat, ignore it; else apply it and set `last_seq = seq`.
6. An event without `seq` is applied and leaves the cursor alone.

`needs_resume` clears only when a new `SessionState` (from a snapshot) replaces the old one; the application owns that replacement. The reducer never calls `session.resume` and emits no effect for it: the live application resumes on P1-03's `Gap` (P1-12 REQ-18), so these two checks matter only for recorded or hand-built logs, and as a second line of defence.

Why `last_seq` can be compared with `<=`: F3 and F4. A new epoch restarts `seq`, so comparing `seq` without the epoch check would drop real events after a backend restart.

### 6.2 Tool fields

All read from `raw["payload"]`. On `tool.complete` for a known cell: `status = Failed` only if `is_error` is the JSON boolean `true`; otherwise `Succeeded` (a missing or non-boolean `is_error` counts as `Succeeded`). Copy `summary`, `duration_s` and `result` when they have the right type (`result` unchanged: the reducer cuts nothing, because the gateway already cuts `result` at 65,536 characters, F10); copy `inline_diff` after stripping terminal escape sequences (CSI sequences `ESC [ ... final byte`, and any other `ESC` plus the byte after it) and when the stripped text is not blank. Everything else in the stripped text is kept as sent, including the `review diff` header line and the `a/path -> b/path` lines the bake-off saw (trap 8): the reducer stores what Hermes sent, and P1-07 decides what to draw. `context`, `args` and `labels`: the start event's non-empty value is kept; the completion's value fills only when the start had none. Bake-off finding (u16 trap 7): the completion's `context` can read like `rm -rf .pytest_cache + 1 command`, so the start's value is the better label.

### 6.3 Known, silent and unknown event types

The built-in silent list is: every `name` in the vendored contract's `x-notifications` (this includes `notice`, `notification.show`, `approval.cancelled`, `request.cancel`, `session.info`, `session.title`, `message.reaction` and the `subagent.*` names), plus `approval.request`, `approval.settled`, `clarify.request`, `clarify.settled`, `session.replay_gap`, plus `agent.step`, `session.updated`, `session.tools_changed`, plus any type starting `subagent.`. In the reducer the generated `Notification` variants (every `x-notifications` name the generator knows) are known by definition and only the fixed extras above are a hand-typed list; the reducer reads no file. Test 48 reads the vendored contract and fails when an `x-notifications` name is neither a generated variant nor on that list. `frame.type_name()` gives the name for `Unknown`. If the name is not on the silent list, add it to the connection's noted set and add a `Diagnostic` notice `Hermes sent an event this version of Talaria does not recognise: <name>. It is ignored.` where `<name>` is the type name if it matches `[A-Za-z0-9._-]{1,64}`, else the words `an unnamed type`. At most 8 types are noted per connection: the ninth and later are ignored with no notice. The `unknown event types` line of the example lists the noted set only. Test 48 reads the vendored contract file at test time, so a contract bump keeps the list honest.

Silent does not mean unimportant. The low-disk auto-prune question arrives as `notification.show` (F31) and is not shown by this unit; Talaria has no slash command to answer it in this phase, and Hermes snoozes it. A later unit adds a notification surface.

## 7. Assistant text

### 7.1 Segments

A turn's assistant output is a sequence of segments. A segment is open from its first character that is not `\r` or `\n` until a boundary: a null `message.delta`, a `tool.start`, a `message.interim`, a reasoning event, or a `message.complete` (an interrupt is not a boundary; section 8). An open segment is the only open assistant cell. Segment text is the concatenation of its deltas, where leading `\r` and `\n` are removed from each chunk while the segment is still empty (so the chunks `"\n"`, `"\n"`, `"Hi"` give `Hi`). Spaces and tabs are kept, so a first chunk made only of spaces or tabs opens a cell holding them: dropping them would make the result depend on how Hermes chunked the text (test 63). Do not trim trailing text or interior blank lines: they are Markdown.

### 7.2 `message.interim`

`text` is a string (else the event does nothing); `already_streamed` that is missing or not a boolean counts as false; "equal" below means equal after trimming whitespace at both ends.

| `already_streamed` | Open segment | Action |
|---|---|---|
| false | none or empty | Add a sealed assistant cell with the text, `interim = true`. |
| false | has text | Seal it, then add the sealed interim cell. |
| true | has text equal to the interim text (after trimming) | Seal it; mark it `interim`. |
| true | has different text | Replace its text with the interim text, seal it, mark it `interim`. |
| true | none | Add a sealed interim cell (the text was streamed before this client attached). |

### 7.3 `message.complete`

Fields are read from `raw["payload"]`.

1. If latched: merge `usage`; set the turn to `Finished(Interrupted)`; `seal_all` (tools `Unfinished`); add the `Interrupted` notice if this turn has none; stop. Exactly one `Interrupted` notice per turn.
2. If the turn is `Finished` and no `message.start` has arrived since it finished: merge `usage` only; stop (a repeat). If the turn is `Idle` the frame is a turn of its own (a client that attached late): continue.
3. Map `status`: `error` gives `Failed`; `interrupted` gives `Interrupted`; `complete`, or a missing or null `status`, gives `Completed` (the contract makes `status` nullable); any other string, or a value that is not a string, gives `Failed` with the notice text `Hermes ended the turn with a status this version of Talaria does not recognise.` (the gateway sends only the three, F13, so this is a guard for hostile input).
4. Seal the open reasoning cell. If the turn made no reasoning cell and `reasoning` is non-blank, add a sealed reasoning cell.
5. For `Completed`, text. Let `t` be `text` when it is a string, else empty.
   - `response_transformed` is true and `t` is non-blank: the text is the authoritative replacement (F29). If the last assistant cell of the turn is still open, replace its text with `t` (leading `\r\n` removed), seal it and mark it `transformed`. Otherwise add one sealed assistant cell with `t`, marked `transformed`. Never run the containment check. Earlier sealed segments stay as they are (a final cell never changes); the screen units may label a `transformed` cell. Skip the other bullets of this step.
   - Otherwise compare without whitespace: let `t'` be `t` with every whitespace character removed and `shown'` the same for the concatenation of the turn's streamed assistant segments (cells with `interim == false`), plus its interim segments only when `response_previewed` is true. Removing all whitespace makes the check independent of whatever separator Hermes puts between segments (R2 does not pin it).
   - If `t'` is empty: nothing to add.
   - Else if `shown'` is empty: add a sealed assistant cell with `t` (leading `\r\n` removed).
   - Else if `t'` is a substring of `shown'`: add nothing.
   - Else if `shown'` is a prefix of `t'`: walk the characters of the original `t`, counting non-whitespace characters; the remainder is what follows the `len(shown')`-th non-whitespace character, with leading whitespace removed. Add it as a sealed assistant cell.
   - Else: add a sealed assistant cell with the whole `t` (the reply differs from what was shown; showing it once is safer than hiding it).
   - `response_reused` needs no rule of its own: when the reply is already shown, the containment check adds nothing; when nothing was shown the text is the only copy.
6. For `Failed`: the open assistant segment seals. Add an `Error` notice whose text is the first non-blank of `error`, `text`, `failure_reason` (or the sentence from step 3); attach `error_surface` as `detail`. On an error outcome `text` is the gateway's own error copy, not model prose (for a gateway refusal it is "already their copy": `gateway/session_settlement_recovery.py:64-66` at Hermes v0.22.4), so it is shown in the notice; it is never added as an assistant cell.
7. For `Interrupted`: seal; add the single `Interrupted` notice.
8. `warning` non-blank: add a `Warning` notice (after the above). `billing` and `persisted_turn` are ignored in this unit.
9. Running tools become `Unfinished`. Seal all open cells (`seal_all`, section 6.0: prompt cells that are `Open` or `Answering` stay open). Set `Finished(outcome)`. Clear `activity`.
10. Merge `usage`.

Worked examples (collapsed to one space for reading; the check removes all whitespace):

| Streamed segments | `text` | Result |
|---|---|---|
| `["Hello world"]` | `Hello world` | nothing added |
| `["Hello world"]` | `Hello  world\n` | nothing added (whitespace does not count) |
| `[]` | `Hello world` | one assistant cell |
| `["Checking.", "Done."]` (tool between) | `Done.` | nothing added (contained) |
| `["Checking.", "Done."]` | `Checking.Done.` or `Checking. Done.` | nothing added (the separator does not matter) |
| `["Checking."]` | `Checking. Done.` | cell `Done.` added |
| `["Hi"]`, interim `["Done."]`, `response_previewed` false | `Done.` | `Done.` is added: interim text is not in the check |
| same, `response_previewed` true | `Done.` | nothing added |
| `["abc"]` | `xyz` | cell `xyz` added |
| `["draft"]` open, `response_transformed` true | `final` | the open cell now reads `final`, sealed, marked `transformed` |
| `["draft"]` sealed (a null delta came last), `response_transformed` true | `final` | a second sealed cell `final`, marked `transformed` |

The row with `response_previewed` false is deliberate. Hermes sets the flag only when it delivered the final reply as an interim (F29), so when it is false the interim text was commentary and an equal final text is a separate reply: the flag, not a text comparison, decides (test 23). If a P1-04 fixture shows the flag false while the final text equals an earlier interim, stop and report (issue, Stop conditions); that call is the operator's.

Remainder and mismatch (steps 5, fourth and fifth bullets), with the whitespace removed for the comparison only: streamed `["Checking."]` and `text` `Checking. Done.` add one cell `Done.`; streamed `["abc"]` and `text` `xyz` add one cell `xyz`. Tests 20 and 21 assert these two cases as well.

## 8. Interrupt latch

| Situation | Result |
|---|---|
| `Event::Interrupt`, turn `Running`, generation known | Latch set; `Effect::Interrupt` emitted. Nothing is sealed yet: the open assistant and reasoning cells stay open and running tools stay `Running` until the turn ends (section 7.3), so a refused interrupt leaves no trace and the reply is not split in two. The `Interrupted` notice is added when the turn ends. |
| `Event::InterruptFailed` (the call was refused, for example `stale_generation`) | Latch cleared; the turn goes on and its later events apply again, to the same open cells. |
| `Event::Interrupt`, turn not `Running` | Nothing. |
| `Event::Interrupt`, running, generation unknown (no `message.start` seen yet) | Nothing; the application may retry after the turn starts. |
| Second `Event::Interrupt` while latched | A second `Effect::Interrupt` is emitted (the first may have been lost); no second notice. |
| Suppressed while latched | `message.delta`, `message.interim`, `reasoning.delta`, `reasoning.available`, `thinking.delta`, `tool.start`, `tool.progress`, `tool.complete`. |
| Applied while latched | `approval.request`, `clarify.request`, `*.settled`, `status.update`, `todo.updated` (the checklist is session state, not transcript), `session.usage`, `error`, `message.complete`, `session.replay_gap`. |
| `message.complete` while latched | Section 7.3 step 1; the outcome stays `Interrupted` whatever `status` says. A reply that finished just before Hermes saw the stop is therefore not shown (it is stored in the session and appears after a resume). The person asked to stop, and the Python client's mistake was reporting a cancelled turn as finished. |
| New `message.start` | Latch cleared. |
| Open prompts | Untouched. Hermes does not settle them on interrupt (F21); the application denies first, then interrupts. |

If the gateway interrupts the turn without a local `Event::Interrupt` (another viewer pressed stop), `message.complete` arrives with `status: interrupted` and the normal path adds the notice.

## 9. Prompt registry

Key: `PromptKey { session_id, prompt_id, execution_generation }`. A prompt cell exists once per key.

When is a prompt cell final? A prompt cell has a `sealed` flag and is final exactly when it is sealed. `Open` and `Answering` cells are never sealed (a card may still be needed, and a turn that ends or is interrupted does not close them). `Settled(Elsewhere)` is sealed at once. `Settled(Answered(v))` is sealed at the next `seal_all` (`message.start` or `message.complete`, section 6.0), or at once when the settle arrives while the turn is not `Running`. Until it is sealed it is still the live tail, which leaves room for Hermes's `already_resolved` reply, which can arrive after the `settled` event (F18, F19); once sealed it never changes, which is what the property test of final cells (test 62) requires. A reply that arrives after the seal changes nothing.

```text
          request (new key)                 Event::Answer* accepted
(none) ------------------------> Open ---------------------------> Answering(value)
                                   |  \                                  |   \
                                   |   \ Event::AnswerFailed             |    \ *.settled
                                   |    <--------------------------------+     v
                                   | *.settled (not by us)               Settled(Answered(value))
                                   v                                          |
                          Settled(Elsewhere) <----- Event::AnswerAlreadyResolved (from Answering, or Settled(Answered) not yet sealed)
```

| Input | Registry state | Result |
|---|---|---|
| `*.request`, key new | - | Add prompt cell `Open`. |
| `*.request`, key exists | any | Nothing. |
| `*.request` with a missing or non-integer `prompt_id` or `execution_generation` | - | Add a `Diagnostic` notice saying Hermes asked a question this client cannot answer; no registry entry. |
| `*.settled`, key matches | `Open` | `Settled(Elsewhere)`, sealed. |
| `*.settled`, key matches | `Answering(v)` | `Settled(Answered(v))`, not yet sealed unless the turn is not `Running` (Hermes publishes `settled` before it returns our reply, F18, so this is our answer unless the next row follows). |
| `*.settled`, key matches | `Settled` (either kind) | Nothing: a repeated settle never turns `Answered` into `Elsewhere`. |
| `*.settled`, no match | - | Nothing. |
| `Event::AnswerAlreadyResolved { key }` | `Answering(_)`, or `Settled(Answered(_))` not yet sealed | `Settled(Elsewhere)`, sealed: Hermes's reply said `already_resolved`, so another viewer or a timeout settled the prompt and our choice was not applied (F19). |
| same | `Open`, `Settled(Elsewhere)`, a sealed cell, no entry | Nothing. |
| `Event::AnswerApproval { key, choice }` | `Open`, approval, `choice` in `choices` | `Answering(choice)`; emit `RespondApproval`. |
| `Event::AnswerClarify { key, answer }` | `Open`, clarify | `Answering(answer)`; emit `RespondClarify` (a clarify answer may be free text, so there is no choice check). |
| `Event::AnswerFailed { key }` | `Answering` | back to `Open`. |
| same | other | Nothing. |

Refusals. For an answer event the checks run in this order, and the first that fails gives the reason: (1) no entry for the key: `NoSuchPrompt`; (2) the prompt is of the other kind: `WrongKind`; (3) the state is `Answering` or `Settled`: `AlreadyAnswered`; (4) an approval whose `choice` is not in `choices`: `ChoiceNotOffered`. A refusal emits `Effect::RefuseAnswer { key, reason }` and changes nothing.

The key's `execution_generation` is part of equality: an answer built with the current generation after the prompt's generation moved on matches nothing and is refused (F18 sweeps stale prompts the same way). A prompt whose `choices` is empty and kind approval accepts no answer (every choice is "not offered"). A clarification `answer` is sent exactly as given, the empty string included: the reducer does not refuse it, and the screen unit decides what the person may submit. (The contract types `answer` as a plain string with no description; whether an empty answer means "skip" to Hermes is not stated in v0.22.4: verify at the pinned commit before relying on it. The recorder uses the text `skip`.)

The reducer never times a prompt out. `timeout_s` is stored for the application's countdown.

## 10. Usage merge

`Usage` has one `Option` per kept field. Intake of a frame, from `raw["payload"]`: take the nested object (`payload.usage` for `session.usage`; the `usage` object of `message.complete`) and, for `session.usage` only, the top-level counters. For each kept field, in this order:

1. The nested object has the key with a non-null value of the right type: store it, whatever it is (zero is a reading).
2. Else the field has a top-level alias with a non-null value of the right type, and the stored field is still empty (`None`): store it.
3. Else leave the stored value alone.

So a top-level counter only ever fills a gap; it never overwrites a stored value, which matters because the top-level counters are zero before the first API call (F15) and a later frame with top-level zeros must not reset a stored total. Alias table (nested name from the top-level name): `input` from `input_tokens`; `output` from `output_tokens`; `reasoning` from `reasoning_tokens`; `prompt` from `prompt_tokens`; `completion` from `completion_tokens`; `total` from `total_tokens`; `calls` from `api_calls`; `cache_read` from `cache_read_tokens`; `cache_write` from `cache_write_tokens`; `compressions` from `compression_count`; `context_max` from `context_length`; `model` from a top-level `model`. The remaining kept fields (`context_used`, `context_percent`, `cache_hit_pct`, `cost_usd`, `cost_status`) have no alias.

What the rule means in practice. The nested view always carries `model` and the seven core counters (F15), so for those eight fields the nested value always replaces the stored one and a top-level counter never gets a turn. The top-level fallback can fire only for `cache_read`, `cache_write`, `compressions` and `context_max` (the other aliases are shadowed), which is where test 60 aims. A zero in the nested view is stored: the counters are cumulative for the session and Hermes sends zeros only before the first model call, so a zero after a non-zero total is not expected; if a fixture shows one, report it rather than add a rule. One exception for `model`: an empty string is absent (Hermes writes `""` when the model is unknown, `gateway/session_usage.py:114`).

Rules that tests pin:

- A key absent from the frame leaves the stored value alone (test 39).
- A key present with value 0 in the nested object stores 0: zero is a reading. Note the nested view always carries `model` and the seven core counters, 0 when unknown (F15).
- A key present with `null` leaves the stored value alone.
- A wrong-typed value is ignored.
- Read the raw JSON. The schema declares `default: 0` on `input`, `output`, `reasoning`, `prompt`, `completion`, `total`, `calls`, so a decoded struct cannot tell absent from zero; do not merge from it.

## 11. Snapshot and the resume equivalence rule

Construction (`from_snapshot`, which takes the typed `CanonicalSnapshot`: unlike events, a snapshot has no raw-JSON path, so all reads below go through the typed row fields; a detach reply does not decode as one, F26):

1. Rows: `display_messages` when present and not null, else `messages`. Each row is a `TranscriptMessage` (`role` required; optional `text`, `content`, `name`, `context`, `tool_call_id`, `args`, `labels`, `reasoning`, `display_kind`, ...).
2. `user`: user cell with `text` (else `content` when it is a string). Skip a row whose text is blank.
3. `assistant`: if `reasoning` is a non-blank string add a sealed reasoning cell; then if `text` (else `content` string) is non-blank add a sealed assistant cell.
4. `tool`: final tool cell: `tool_id` from `tool_call_id`, `name`, `context`, `args`, `labels`, status `Unknown`, no summary or diff (`write_file`, `patch` and `skill_manage` rows may carry `content`; store it as `result` when it is a string).
5. `system`: `System` notice.
6. Any other role: skip.
7. Prompts: each entry of `prompts` becomes an `Open`, unsealed prompt cell keyed (snapshot `session_id`, entry `prompt_id`, entry `execution_generation`), appended after the rows. Fields: `kind` (`approval` gives `Approval`, `clarify` gives `Clarify`; any other string skips the entry), `command`, `description`, `question`, `choices`, `multi_select` (null is false), `edit`, and `timeout_s` converted to `f64`. `pending` is not read for cells; count it for the example's `queued admissions ignored: <n>` line.
8. Cursor: `last_sequence`, `replay_epoch`. Store `execution_generation`, `subscription_id`, `stored_session_id`, `todo_state` as the checklist.
9. Turn: `Running` if `running` is true, else `Idle`. No open cell and no latch.
10. `needs_resume` false; noted-unknown set empty; submission queue empty.

The replacement of a live state by a snapshot state is the application's act. A user cell that was created locally and also appears in the snapshot is therefore not duplicated: the old state is discarded whole.

Equivalence rule for test 10. Both sides produce a list of cells; map each to a comparable item and compare the lists:

| Cell | Item |
|---|---|
| User | `("user", text.trim())` |
| Assistant | `("assistant", text.trim())` |
| Tool | `("tool", name, tool_id)` |
| Reasoning, Notice, Prompt | dropped (reasoning display is optional, notices are local, prompts are checked by test 13) |

Where the snapshot comes from. P1-04 records seven scenarios and none is a `session.resume` result. The test author therefore hand-builds the snapshot, `tests/data/resume_snapshot.jsonl`, from the `tool-diff` fixture: one user row with the text the fixture's outbound `prompt.submit` carried, one assistant row per streamed text segment of its turn (text as `message.complete.text` and the deltas show it), one tool row with the fixture's `tool_id` as `tool_call_id` and its `name` and `context`, built by reading the fixture and writing the rows by hand; `last_sequence` is the fixture's last event `seq` and `replay_epoch` its epoch; `running` is false; every required field of section 12.6 is present. If P1-04 (or a later change of it) has put a recorded `session.resume` result with `display_messages` under `fixtures/frames/`, test 10 uses that recording instead and the hand-built file is kept for tests 11 to 14. This unit does not edit `tools/record-fixture/` or `fixtures/frames/`. The replayed side starts from `SessionState::empty` and applies the recorded outbound `prompt.submit` as `Event::Submit` so that user cells exist. A fixture with an interrupted or failed turn does not qualify, because the stream and the stored rows differ in text rules there. A skill invocation (`/skill args`, F23) does not occur in these fixtures; if a prompt starts with `/`, compare after the same projection or pick another fixture.

### 12.2 Reading frames

`tests/support/frames.rs` reads the frame-log format of P1-04 (`docs/formats/frame-log.md`, version 3; R16). One JSON object per line. Line 1 is `{"kind":"header","version":3,...}`. Then `{"kind":"frame","seq","tMs","generation","dir":"in"|"out","frame":<JSON or null>,"redactions"?,"parseError"?}` and `{"kind":"dropped",...}`. Unknown fields are ignored. For each `frame` record in file order:

| Record | Becomes |
|---|---|
| `dir: "in"`, `frame.method == "event"` | `EventFrame::from_params(&frame.params)`; on `Ok(f)`: `Event::Session { session_id: f.session_id or "", frame: f, raw: frame.params }`; on `Err`: skipped and counted as undecodable |
| `dir: "out"`, `method` `prompt.submit` | `Event::Submit { text, submission_id: submission_id or input_id }` |
| `dir: "out"`, `method` `session.interrupt` | `Event::Interrupt` |
| `dir: "out"`, `method` `approval.respond` | `Event::AnswerApproval { key from params, choice }` |
| `dir: "out"`, `method` `clarify.respond` | `Event::AnswerClarify { key from params, answer }` |
| `dir: "in"`, a reply (`result`, no `method`) | its method is the `method` of the earlier outbound frame with the same `id` and `generation`. `session.create` or `session.resume`: the result is a snapshot, kept for the snapshot tests, and `SessionState::from_snapshot` when it is the first frame record. If no outbound frame matches (a hand-built file), a result that is an object with a string `session_id`, an array `messages` and a string `replay_epoch` counts as a snapshot. |
| `dir: "in"`, a reply with an `error` member to an earlier outbound `prompt.submit`, `session.interrupt`, `approval.respond` or `clarify.respond` (matched by `id` and `generation`) | `Event::SubmitFailed { submission_id, reason }` (the error `message`), `Event::InterruptFailed`, `Event::AnswerFailed { key }`, `Event::AnswerFailed { key }`; a `result` whose `status` is `already_resolved` to either respond call gives `Event::AnswerAlreadyResolved { key }`. This is what the application would send (P1-12, P1-09). |
| `frame: null`, `parseError`, `dropped`, any other record | skipped and counted |

A line that is not JSON, or a first line that is not a version 3 header, is a read error for the whole file (`REDUCE FAILED`). The header check runs first, so a file whose only line is `not json` fails there. The one exception is the last line of a file whose first line is a valid version 3 header: if it is cut short (not valid JSON, no final newline) it is ignored, as P1-04's `ReplaySource` does. The recorder withholds every outbound `clarify.respond` `answer` (P1-04 REQ-5; its test `clarify_answer_is_withheld`), so the clarification fixture's recorded answer is a marker (`[redacted]`) or absent. Test 4 (approval) compares the whole effect with the recorded `approval.respond` params, `choice` included, because the recorder keeps `choice`.

The helper is also included by the example through `#[path = "../tests/support/frames.rs"] mod frames;`, and `describe.rs` the same way (`#[path = "../tests/support/describe.rs"] mod describe;`), so that the example and the tests read and print frames identically. Neither imports `hermes-client`.

### 12.3 Golden files

One file per fixture, `tests/golden/<fixture stem>.cells.txt`, produced by `tests/support/describe.rs::describe(&SessionState) -> String`. The test author writes each golden by reading the fixture, not by running the code. Format, one line each, in this order:

### 12.7 Property tests

Generators produce sequences over this alphabet, with random ids drawn from a small pool so that collisions occur: `message.start`, `message.delta` (text, null or empty, chunked arbitrarily), `message.interim`, `message.complete` (each status and an unknown status string, text random or equal to the streamed text, random subsets of `response_*` flags), `reasoning.delta`, `thinking.delta`, `tool.start`, `tool.complete`, `tool.progress`, `todo.updated`, `status.update`, `session.usage` (random subsets of keys), `approval.request`, `clarify.request`, `*.settled`, `error`, `Submit`, `SubmitFailed`, `Interrupt`, `InterruptFailed`, `Answer*`, `ConnectionOpened`, an unknown type, an event of another session, a duplicate of an earlier event. Events are built as raw JSON and turned into `Event::Session` through `EventFrame::from_params`; a value it refuses is dropped from the sequence (as the application would). Properties:

1. No sequence panics. Include wrong-typed values in fields the contract does not declare (`is_error`, `context`, usage values) and in nested objects.
2. `final_prefix_len()` never decreases between steps, and every cell inside the prefix is equal (value equality) before and after each later step.
3. Splitting the same text into different delta chunks (same boundaries between segments) gives equal cells.
4. At most one assistant cell and at most one reasoning cell is open; each open prompt cell has exactly one registry entry and the reverse; no two prompt cells share a key.
5. Re-applying the same inbound event frame twice in a row, when it carries a `seq`, equals applying it once. Local events (`Submit`, answers) are outside this property.

### 12.8 Cost test

`session_cost.rs` (`#[ignore]`, release mode only). It checks growth, not a budget: the reducer must not clone or rescan the cell list. Expected cost per delta is one `String::push_str` on the open cell plus a constant amount of bookkeeping. Only the delta loop is timed (building the snapshot and the events happens before the clock starts); each measurement is the median of five runs on fresh states.

- Assertion A (the one that catches a rescan of the transcript): apply 10,000 `message.delta` events of 50 bytes each (the same 50-byte text every time, no `\n`, so all go into one segment), once on a state built from a 2,000-row snapshot and once on one built from an 8,000-row snapshot. It fails when the 8,000-row time is at least 2 times the 2,000-row time.
- Assertion B (catches quadratic growth of the segment text): on 2,000-row states, 10,000 deltas then 20,000 deltas (two separate runs on fresh states, same delta text). It fails when the second time is at least 3 times the first. Timing on a loaded machine can fail a correct reducer: the test first runs the loop once untimed to warm up; if an assertion fails, run the test once more on an otherwise idle machine; two failures are a failure. Never raise a ratio or drop an assertion to get a pass: report it.

| `message.complete` with the turn `Idle` and nothing streamed | Treated as a turn: sets `Finished`, adds text as a cell (7.3 step 5, `shown'` empty). | A client attached late. |
| `message.complete` with the turn `Finished` and no `message.start` since | Merges usage only. | A repeat. A genuinely missed `message.start` after a finished turn loses that reply's text; the snapshot after a resume restores it. |
| `tool.complete` after the cell is final, or for an `Unfinished` cell | Ignored. | Repeats; a final cell never changes. |
| Same `tool_id` in two turns | Each turn looks tools up among its own cells, so the second turn's `tool.start` makes a new cell. | F34: uniqueness across turns is not verified. |
| Parallel tools finish out of order | Each completes by `tool_id`; the final prefix advances only past leading final cells. | Scrollback order equals cell order. |
| Assistant text after `tool.start` of a running tool | New assistant cell after the tool cell. | Order of arrival. |
| `reasoning.delta` while an assistant segment is open | Seals the segment; reasoning cell follows. | Order of arrival. |
| Prompt request while latched | Applied. | A hidden prompt would hang the turn until Hermes times it out. |
| `.settled` before its `*.request` | Nothing; a later request for the same key still creates an `Open` prompt. | Cannot happen in order; a sequence repeat is filtered by `seq` anyway. |
| Submit with the same `submission_id` twice | Two effects and two queue entries. | The reducer does not de-duplicate; Hermes is idempotent per id. The application chooses ids. |
| Another viewer's turn starts while our entries wait | The oldest entry is taken for it, so user cells can pair with the wrong turn. | Known limit of first-in-first-out matching; the refinement is in section 14. P2-08 owns the queue. |
| Submit refused by Hermes, a call that ended `Unknown`, or a `voice_stopped` reply | The application sends `SubmitFailed`; the entry is dropped so later turns pair correctly. | Without it every later start would take a stale entry, and every later user cell would sit one turn late. |
| Submit whose receipt says `unknown` or `terminal` | Not covered by `SubmitFailed` here. Whether such a receipt starts a turn is not verified at v0.22.4 (F20); verify before relying on it. | Do not drop an entry that may still get its turn. |
| A queued submit cancelled or replaced (`prompt.cancel`, `prompt.replace_queued`) | Not used by Talaria in this phase. P2-08 must send `SubmitFailed` (or its own event) for the entry. | Otherwise the entry strands. |
| Snapshot `running: true` and later `message.complete` | Normal completion; the text from before the attach is in `messages` if Hermes persisted it. | The reducer cannot recover unpersisted text. |
| `usage` values of the wrong type | Ignored per field. | Section 10. |
| Event type string longer than 64 characters or with other characters | Diagnostic notice with `an unnamed type`. | Untrusted text rule. |
| `inline_diff` that is only escape sequences | Stored as `None`. | Nothing to show. |
| `todo.updated` with `revision` equal to the stored one | Replaces (same revision, newer content wins). | Hermes may re-send. |
| `message.complete` after a latch, `status: complete` | Outcome `Interrupted`, text not shown. | Section 8. |

## 14. Design reasoning

- **Pure, with effects as data.** Hermes' own clients mix state and calls. A reducer that returns `Effect` values can be tested by comparing them to recorded outbound frames (tests 4 and 5), which is how the Python client's wrong-prompt bugs would have been caught.
- **Cells, not lines.** The reference slice's state wraps text to the terminal width inside the state, so a resize or a theme change cannot re-flow finished text. Raw cells let P1-06 wrap at commit time and P2-02 search the whole transcript.
- **Outcome from `status`.** The Python client inferred outcomes from event arrival and misreported cancelled turns. F13 gives a single authoritative field.
- **Prompts from `prompts`.** The roadmap's word `pending` matches the older sketch; F22 shows the contract separates queued submissions (`pending`) from open questions (`prompts`). A card built from `pending` would show a queued sentence as a question.
- **Why the unknown list is explicit.** F24: the gateway emits `agent.step` every turn and the contract omits it. The decoded `Unknown` variant would otherwise raise a notice per turn, the exact failure the Python catalogue's RR-24 recorded for `platforms.changed`.
- **Why the payload is read from raw JSON.** F9, F13, F15 and section 5.1: the generated types cannot carry what the contract leaves out, and cannot tell an absent counter from zero. Total accessors make a wrong-typed field harmless instead of fatal.
- **Why whitespace-free comparison for the final text.** Hermes's separator between streamed segments is not pinned (R2). Removing all whitespace makes the reply-shown-twice check immune to it, at the price of a negligible chance that two different replies differ only in whitespace.
- **Why a queue for user cells.** If a user cell were created at submit time while a turn runs, later assistant cells of the running turn would be appended after it and the transcript would interleave. Creating it at the next `message.start` keeps arrival order. The simple first-in-first-out match is right while one viewer submits; matching by `admission_id` through the receipt and `session.info.pending[].input_id` is the refinement if two viewers share a session (P3).
- **Why the latch suppresses `tool.complete`, and does not seal.** A cell that is already cancelled must not change when a late result arrives (a final cell never changes). The cell ends `Unfinished` at the turn end. Sealing at the interrupt would split the reply in two if Hermes refused the interrupt.
- **Why `AnswerAlreadyResolved`.** Hermes publishes `settled` before it returns the reply, so a state of `Answering` plus `settled` looks like our own answer whether it is or not. The reply's `already_resolved` is the only signal that it was not.
- **Rejected: depend on `hermes-client` for replay in tests.** It would let a convenient helper leak into the domain crate and break the layer rule; the frame reader is about 60 lines.
- **Rejected: generate goldens from the code.** They would encode the code's mistakes. Hand-written goldens plus the independent snapshot comparison (test 10) give two sources.
- **Rejected: reading `rendered`.** It is an incremental ANSI fragment (Python catalogue RR-15). Appending raw `text` is correct.
- **Rejected: truncating reasoning** as the Python catalogue's RR-21 notes Hermes does. Requirement R6 of the project forbids dropping content; memory is bounded by the session length and the gateway.
- **Rejected: an `Effect::ResumeSession`.** P1-03 and P1-12 already own resume on a `Gap`; a second trigger in the reducer would race them.

## 15. Differences from the roadmap and open questions

0. **Decisions recorded for the engineering journal.** Append to `docs/engineering-journal/DECISIONS.md` in the same pull request: (a) the reducer takes `Event::Session { session_id, frame, raw }`, where the architecture layers table sketches `Event::Session(SessionId, Notification)`, with the reason in item 3 below; rejected: the sketch's shape (it loses `seq`, the epoch and fields the contract omits); revisit when the contract declares those fields. (b) Effects are data returned by `update`; rejected: calling the transport from the reducer. Revisit when more than one session is driven at once (P3-01).

1. **`pending` versus `prompts`.** The roadmap sentence "restores open approval and clarification prompts from `pending`" does not match the v0.22.4 contract (F22). The issue follows the contract. Operator or planner: correct the roadmap.
2. **No recorded resume snapshot in P1-04.** The roadmap says P1-05 needs "a snapshot fixture (a recorded `session.resume` result)", but P1-04's seven scenarios include none. This unit hand-builds one (section 11) and does not touch `tools/record-fixture/`. Proposed fix: P1-04 adds an eighth scenario (`session.resume` with `display_projection: true` after the `tool-diff` turn); test 10 then switches to it. Operator or planner: decide.
3. **Event envelope.** The architecture sketch `Event::Session(SessionId, Notification)` omits `seq`, `replay_epoch` and `execution_generation`, which the reducer needs, and the raw payload, which it needs for fields the contract omits. This unit takes `frame: EventFrame` and `raw: serde_json::Value` (section 5.1). P1-02's `InboundEvent` must carry `raw`; the parent records it.
4. **Local events nobody lists yet.** `ConnectionOpened`, `SubmitFailed`, `InterruptFailed` (P1-12) and `AnswerAlreadyResolved` (P1-09) have no sender in those issues' requirements. The parent records it.
5. **Dev-dependency on `hermes-client`.** Not allowed by the issue (layer table). If the planner prefers sharing P1-04's `ReplaySource` in tests, that is an architecture change to raise with the operator, not a local decision.
6. **`status.update` is not a transcript cell.** Kinds seen at v0.22.4 include `goal`, `loop`, `heartbeat`, `process`, `compacting` (`gateway/run_turn_progress.py:997`, `gateway/run_goals.py:231-237`, `tui_gateway/session_notifications.py:206`, `284`, `518`). A heartbeat would flood the transcript; a goal verdict may deserve a cell. This unit keeps a bounded log (`status_log()`) and the latest note; the screen units decide what to show. Operator: say if goal verdicts must always be committed to scrollback.
7. **Synthetic turn without notice.** The Python catalogue (RR-31) wanted a visible note when text arrives with no start. This unit stays silent because a resumed running session legitimately has no start.
8. **Reasoning cells are per run.** One reasoning cell per contiguous run, not per turn, so scrollback order matches arrival order.
9. **Notification count.** The handoff text says 79 notifications and 47 canonical methods; v0.22.4 has 80 and 48. Re-count at the pinned commit; nothing in this unit depends on the exact number.
10. **A reply that finished just before an interrupt arrived.** It is not shown by this unit (section 8). Operator: say if it should be.
