## 2. Hermes facts with evidence (Hermes v0.22.4)

### 2.1 What a kanban task is

| Fact | Evidence |
|---|---|
| A task row carries `title`, `body`, `assignee` (a profile name), `status`, `priority`, `parents` through a link table, `idempotency_key`, `max_runtime_seconds`, `max_retries`, `skills`, `model_override`, `provider_override`, `reasoning_effort`, `goal_mode`, `completion_contract`, `session_id`, `result`, plus workspace and claim fields. `session_id` is the originating session and is null for dashboard-created tasks. | `hermes_cli/kanban_db.py:594` (`class Task`), fields to `:640`; `session_id` comment at `:635` |
| `create_task` returns the existing non-archived task id when the `idempotency_key` already exists, instead of creating a duplicate. | `hermes_cli/kanban_db.py:1156`, docstring `:1175`; lookup before insert |
| A provider override requires a model override; a reasoning effort outside Hermes's value set is refused, never silently dropped. The accepted values are `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`, `ultra`. Assignees are canonicalised lower-case on write and lookup (`_canonical_assignee`), so the compiler canonicalises both sides of its assignee comparison the same way. | `hermes_cli/kanban_db.py:1010` (`_validate_model_override`), `:118` (`normalize_reasoning_effort`); `hermes_constants.py:1077` (`VALID_REASONING_EFFORTS`) |
| Workspace kinds are `scratch`, `worktree`, `dir`. A new task with parents that are not all `done` starts as `todo` and promotes to `ready` when every parent completes (an `archived` parent also satisfies the gate; section 2.7). | `hermes_cli/kanban_db.py:115` (`VALID_WORKSPACE_KINDS`); `hermes_cli/kanban_db_graph.py:25` (`initial_task_state`); `hermes_cli/kanban_db.py` (`recompute_ready`: parents `done`/`archived` promote) |
| The REST create shape (`CreateTaskBody`) has **no** `initial_status`, **no** per-card `toolsets` and **no** `max_turns` field. The kernel defaults apply: with no parents and no triage flag the card lands in `ready`. Toolsets belong to profile configuration, not to cards. | `plugins/kanban/dashboard/plugin_api.py:414-432` (`CreateTaskBody`); `hermes_cli/kanban_db.py:1143-1151` (toolsets note) |
| The model-facing create tool requires `title` and `assignee`; a task without an assignee is never dispatched. Its parameters mirror the database function (parents, tenant, priority, workspace, triage, idempotency key, skills, model, provider). | `tools/kanban_tools_schemas.py:395` (`KANBAN_CREATE_SCHEMA`) |
| **The dispatcher auto-assigns unassigned ready cards.** When `kanban.default_assignee` names a real profile, each tick persists it on unassigned ready rows and dispatches them. This is why the compiler gates on the setting (issue REQ-12) and why an unassigned root is safe only while it is unset. | `hermes_cli/kanban_db_dispatch.py:2105-2110`, `:2180` (`_apply_default_assignee`), `:2426-2443`; `gateway/kanban_watchers_dispatcher.py:100-114` |
| Many boards can exist per install, each with its own database; `default` is the first board. Board slugs are lower-cased, stripped and validated (1–64 characters, lowercase alphanumerics, hyphens, underscores, never starting with `-` or `_`). Tenants are a soft namespace inside a board; boards are the hard boundary. | `hermes_cli/kanban_db.py:376-385` (`_normalize_board_slug`); `website/docs/user-guide/features/kanban.md:125-145` |

### 2.2 Columns, manual moves and completions

| Fact | Evidence |
|---|---|
| One module defines board columns and human moves; the database status set, the CLI and the dashboard all derive from it. | `hermes_cli/kanban_workflow.py:1-20` (module docstring) |
| Default columns in order: `triage`, `todo`, `scheduled`, `ready`, `running`, `blocked`, `review`, `done`. `scheduled` and `running` are not drag targets; `archived` is outside the columns and reachable from anywhere. | `hermes_cli/kanban_workflow.py:114` (`DEFAULT_WORKFLOW`) |
| The manual allow-list is explicit per source column. `done` is a destination only from `ready`, `running`, `blocked` and `review` — never directly from `triage`, `todo` or `scheduled`. The `archived` source maps back to (`triage`, `todo`, `ready`). The issue's rule "offered = `manual[source]` plus `archived`" is exactly this table plus the one client-added destination. | `hermes_cli/kanban_workflow.py:114-145`; `can_move` above it |
| One measured quirk: `review` → `todo` actually lands in `ready` (the reopen path ignores the requested target). The view therefore always shows the server's returned status after a move, never the requested one. | `hermes_cli/kanban_workflow.py:132-134` (comment); `plugins/kanban/dashboard/plugin_api.py` (`_drag_to`, `reopen_review_task` path) |
| `GET /workflow` returns exactly this shape (`columns` with key, label, icon, drag target, plus `manual` as a JSON object keyed by source status, and `archived`). Every board uses the default workflow today. | `plugins/kanban/dashboard/plugin_api.py:1625` (`get_workflow`); `hermes_cli/kanban_workflow.py:81-90` (`to_dict`) |
| **A completion needs evidence.** Completing from `running`, `ready`, `blocked` or `review` requires a substantive new `result`/`summary` or a stored result; empty evidence raises `EmptyCompletionError` ("completion blocked: <id> has no result or summary evidence"), a `ValueError` the plugin maps to HTTP 400. Review approvals are exempt. This is why a done move and the root completion both send a `summary`. | `hermes_cli/kanban_db.py` (`complete_task` at `:2639`, status set in its SQL `status IN ('running', 'ready', 'blocked', 'review')`, `_gate_empty_completion`); `EmptyCompletionError` definition above it |
| **An open-parent refusal is a 409 with a long detail.** When `complete_task` or the review path returns false for dependency reasons, PATCH raises a conflict whose detail reads `cannot move <task_id> to 'done': unsatisfied parent dependencies: <parent_id> (<status>); complete the parents first (done or archived)`. The ready path has its own 409 naming blocking parents. | `plugins/kanban/dashboard/plugin_api.py` (`_patch_status`, `_open_parent_refusal`, `_conflict`) |
| PATCH dispatches status through verb handlers: `done` completes with the payload's `result`/`summary`/`metadata` (with `force=True`, a human override of a live claim), `review` requests review, others go through the drag path. A direct `running` status is rejected with its own message. | `plugins/kanban/dashboard/plugin_api.py` (`_STATUS_HANDLERS`, `_apply_status`) |

### 2.5 Dispatcher and execution

| Fact | Evidence |
|---|---|
| The dispatcher runs inside the gateway by default (`kanban.dispatch_in_gateway`, default true) with a tick of `kanban.dispatch_interval_seconds` (default 60). One dispatcher sweeps all boards. | `gateway/kanban_watchers.py:231`, `:258-264`; `gateway/kanban_watchers_dispatcher.py:50` |
| Concurrency caps: an unset `kanban.max_in_progress` is **derived from system memory** (roughly total memory / 512 MiB, clamped to 2–8; no cap only when memory cannot be read, e.g. macOS/Windows). An unset `kanban.max_in_progress_per_profile` means no per-profile cap. Never quote "unlimited" for the global cap. | `hermes_cli/config_defaults.py:1934-1947`; `gateway/kanban_watchers_dispatcher.py:61-71`; `hermes_cli/kanban_db_dispatch.py:1863-1885` (`derive_default_max_in_progress`, `resolve_max_in_progress`) |
| When the dispatcher claims a card, the profile owner admits it through `kanban.run` — the contract's only kanban method, marked "Native-owner only: admit the dispatcher's current claim on a kanban task", with params `{board, task_id, run_id, claim_lock}` and result `{session_id, receipt}`. A stale claim is refused. | `apps/shared/src/gateway-contract.openrpc.json` (`x-canonical-methods`, `kanban.run`); `gateway/session_kanban.py` (`build_kanban_policy`, `run_task`) |
| The admitted policy is built from the card: `model_override`, `provider_override` and `reasoning_effort` become the session's model, provider and reasoning; workspace, branch, tenant, skills and goal settings travel with it; the kanban toolset is added. The policy carries `kanban_json`, which routes execution to a managed out-of-process worker supervised by the owner. The user-visible guarantee is only that work continues without Talaria; do not claim the model runs inside the owner process. | `gateway/session_kanban.py:51-70`; `gateway/session_managed_worker.py:36-47` (`managed_policy`: a policy with `kanban_json` executes out of process) |
| The worker subprocess the dispatcher spawns only submits the claim to its profile owner; the owner owns the durable admission. | `hermes_cli/kanban_worker_client.py:1`; research u15 section 1.3 |

### 2.6 The swarm pattern (the root card precedent, and its limit)

| Fact | Evidence |
|---|---|
| `hermes kanban swarm` writes one graph atomically: a root "blackboard" card, N parallel worker cards, a verifier gated on all workers, a synthesizer gated on the verifier. Shared context lives as structured comments on the root. No second scheduler exists. | `hermes_cli/kanban_swarm.py:1-13`, `create_swarm` at `:106` |
| The swarm root is created **blocked inside the same write transaction** and activated inline, so no dispatcher tick can ever claim it and no reader sees a half-built graph. Talaria cannot copy that over REST: `CreateTaskBody` has no `initial_status` (section 2.1), and a create-then-block PATCH is not atomic. The compiler therefore stages differently: a plain root (which lands in `ready`) is safe only while `kanban.default_assignee` is unset, because an unassigned ready card is otherwise skipped by the dispatcher. The REQ-12 preflight gate on the explicit setting is the load-bearing guard; the partial graph (root plus early cards) is visible to board readers during emission, which is accepted and documented, exactly as the view shows live boards. | `hermes_cli/kanban_swarm.py:188-197` (blocked root); `plugin_api.py:414-432`; `hermes_cli/kanban_db_dispatch.py:2426-2443` (unassigned skipped when no default) |

### 2.7 How results travel, and their caps

| Fact | Evidence |
|---|---|
| Before a worker runs, Hermes builds its context: task header and body, attachments, prior attempts, **done-parent handoffs** (summary and metadata), role history and comments. Caps: task body 8,192 characters (`_CTX_MAX_BODY_BYTES = 8 * 1024`), each summary/result/metadata field 4,096 (`_CTX_MAX_FIELD_BYTES`), each comment 2,048, at most 30 comments and 10 prior attempts. Truncation appends a visible "chars omitted" note. These caps are why card bodies are contract-first and size-gated, and why large results travel as artifacts. | `hermes_cli/kanban_db.py:3899` (`build_worker_context`); `hermes_cli/kanban_db_context.py:22-27` (caps), `:50-57` (`_ctx_cap`), `:67-71` (metadata line) |
| Parent handoffs include only parents whose status is `done`. An `archived` parent satisfies the dependency gate (the child promotes) but contributes **no** handoff. Hence the missing-handoff rule in every compiled card body and the view's archive warning. | `hermes_cli/kanban_db_context.py:157-193` (`_ctx_parent_results`, skips non-`done` at `:165-168`); gate side in `hermes_cli/kanban_db.py` (`recompute_ready`, parents `done`/`archived`) |
| The worker finishes with `kanban_complete`: a human-readable `summary` (1–3 sentences) plus free-form `metadata`; at least one of summary or result is required. Deliverable files are declared in `artifacts` and copied to durable attachment storage before cleanup. | `tools/kanban_tools_schemas.py` (`KANBAN_COMPLETE_SCHEMA`); `hermes_cli/kanban_db.py:2639` (`complete_task`), artifact staging `:2810` |
| Workspace lifetime at completion: `scratch` is removed; `worktree` is removed only when provably free of work (clean tree, every commit reachable from a remote-tracking ref) and cleanup is deferred while any child is not yet terminal; `dir` is intentionally preserved. Never promise permanent worktree storage. Every deliverable therefore travels as a declared artifact whatever the kind. | `hermes_cli/kanban_db_workspace.py:362-395` (`_cleanup_workspace`), `:426-452` (`_cleanup_worktree_workspace`); `website/docs/user-guide/features/kanban.md:135` |
| A worktree card needs an anchor. With `workspace_path` it must be absolute and inside a git repository; without it, the board's `default_workdir` anchors the worktree (`<repo>/.worktrees/<task id>`) and dispatch fails loudly when neither exists. A board default can silently anchor on the wrong repository, which is why the compiler requires its own validated `--repo` and passes it as `workspace_path`. | `hermes_cli/kanban_db_workspace.py:715-744` (`_resolve_worktree_workspace`) |
| Hermes does **not** validate a completion against any schema. The workflow `completion_contract` field is about pull-request acceptance, not result shape. | `hermes_cli/kanban_db.py:594-640`; research u15 section 4.11 |
| A kanban worker can block its own card: `kanban_block` is one of the tools Hermes marks visible to dispatcher-spawned workers (with `kanban_complete` and `kanban_heartbeat`). The card body's missing-handoff instruction (comment, then block) is therefore executable by the worker, not aspirational. | `tools/kanban_tools.py:110-114` (kanban lifecycle tools for workers); `tools/kanban_tools_schemas.py` (`KANBAN_BLOCK_SCHEMA`) |
| Context caps are byte-named (`_CTX_MAX_BODY_BYTES`, `_CTX_MAX_FIELD_BYTES`) and applied to text; the compiler gates on UTF-8 byte length (stricter for non-ASCII text), so a body can never be silently truncated in context. | `hermes_cli/kanban_db_context.py:22-27`, `:50-57` |

### 2.8 Security posture Talaria must respect

| Fact | Evidence |
|---|---|
| The kanban documentation's older security note says the dashboard middleware skips `/api/plugins/`. At v0.22.4 that blanket exemption no longer describes the code: ordinary unauthenticated plugin HTTP requests are not exempt, and a native principal (the ticket grant) bypasses the session-token check in both listener modes. Talaria always presents its native grant and never relies on any skip. Board contents remain readable by any local process that can legitimately reach the routes, so card bodies must hold nothing secret. | `hermes_cli/web_server.py:455-493`; `hermes_cli/dashboard_auth/native_http.py` (`authenticate_native_http`); `website/docs/user-guide/features/kanban.md:913-925` (partly stale; the shared-board warning still holds) |
| The board is shared by every profile on the host on purpose. Card bodies and comments are the collaboration surface. | `website/docs/user-guide/features/kanban.md:921-925` |

```text
POST  <api_origin>/api/plugins/kanban/tasks/<id>/comments?board=<slug>  {"body": "...", "author": "talaria"}
POST  <api_origin>/api/plugins/kanban/links?board=<slug>  {"parent_id": "...", "child_id": "..."}
POST  <api_origin>/api/plugins/kanban/dispatch?board=<slug>

WS   ws://<api_origin host>/api/plugins/kanban/events?since=<id>&board=<slug>
  header: x-hermes-gateway-ticket: <fresh native-http ticket>
  <- {"events": [{"id": 124, "task_id": "t_...", "kind": "status", ...}], "cursor": 124}
  -> {"type": "ping"} after 30 s idle
```

The `board` query parameter goes on board-scoped routes only; `GET /boards`, `GET /workflow` and `GET /orchestration` take no board parameter. The dispatch call sends no `max` and no `dry_run` (the server defaults apply; Talaria never dry-runs a dispatch). Every HTTP call carries the ticket header through `{{P4-01}}`'s `RestClient`. Error bodies are FastAPI-shaped (`{"detail": "..."}`) or the gateway's `{"detail": "Unauthorized"}`; Talaria shows the plain text and never a body that might echo a credential.

## 4. Compile identity and emission (binding; cited by issue REQ-12)

Versioned recipe `kanban-compile/1`:

```text
inputs (canonical text, one value per line, in this order):
  "kanban-compile/1"
  sha256_hex(script_source)
  canonical_json(args)                      (object keys sorted, no whitespace; absent --args means {})
  for each captured call in capture order:
    "<digest>:<occurrence>|<assignee>|<tenant or ->|<model or ->/<provider or ->@<effort or ->|<workspace_kind>:<workspace_path or ->|<workflow_path joined by />"
    (route fields are the resolved override strings; effort lower-cased; absent values are "-";
     the root contributes no line - its workflow path is the empty string and it is not a call;
     the board slug is deliberately not an input: boards are separate databases and preflight is per board)
  for each child workflow source in first-capture-appearance order: sha256_hex(child_source)
compile_id = first 16 hex of SHA-256(inputs joined by "\n")
staffing_resolution_text = the per-call route fields above (already inside the per-call lines)
card key   = "wf:" + compile_id + ":" + digest + ":" + occurrence    (root: "...:root")
```

Preflight (no writes): (1) `GET /orchestration` — a non-empty explicit `default_assignee` refuses (issue REQ-12); (2) roster snapshot and route resolution (issue REQ-11) — unusable routes refuse; (3) `GET /board`, match this compile's keys, fetch `GET /tasks/{id}` for each match (parents comparison needs its `links`), and compare the full planned payload field by field: title, body, assignee, tenant, `model_override`, `provider_override`, `reasoning_effort`, skills, `workspace_kind`, `workspace_path`, parents (as a set). Any difference is a conflict refusal naming the key. Archived matches do not count (Hermes dedups only non-archived keys). Preflight detects them on a separate board read with archived cards included, used for key matching only (the view never uses that read); a recompile after archiving creates fresh cards, prints `recreating <n> archived card(s)`, and that is intended.

Emission order (only the missing work): root create, then card creates in capture order (the `parents` field links at create; parents always precede children in capture order by construction), then `POST /links` for edges still missing on resumed cards, then the root PATCH to `done` with summary (skipped when the root is already `done`), then one `POST /dispatch` when anything changed. A complete match performs no POST or PATCH at all and prints `already compiled`.

## 5. Capture and the subset guard (binding detail for issue REQ-9/REQ-10)

### 5.1 The lexical subset guard

The guard scans the script source before any capture. It tracks identifiers bound by `const`/`let`/`var` from `agent(...)`, `parallel(...)`, `pipeline(...)`, array destructuring of those, and pipeline stage-function parameters. Rules (each refusal names the rule and, where known, the line):

- **G1 (conditions):** a tracked identifier (or a member/index of one) appears in an `if`/`while`/`for` condition, a ternary condition, a `switch` discriminant, or a loop bound. Refused.
- **G2 (options):** a tracked value appears anywhere inside an `agent()` options object (second argument), including nested. Refused.
- **G3 (computation):** a tracked value is an operand of arithmetic, comparison outside G1's positions, `.length`, or an index expression that selects calls (array index into a call table). Refused. (Index/member access whose value flows directly into a prompt string is allowed: it is interpolation.)
- **G4 (transformation):** a method call on a tracked string value (`replace`, `split`, `slice`, `toUpperCase`, …) or `JSON.stringify` of a tracked value anywhere except directly inside a prompt argument. Refused. (A transformation inside a prompt argument is also refused: it can destroy the marker, section 5.3.)
- **G5 (helpers):** the identifiers `now` or `random` are called as functions. Matching is on identifier boundaries (a call is an occurrence of the identifier not preceded or followed by an identifier character, followed by `(`), so `snow(` and `renown(` never match while `Date.now(` still refuses (a compiled graph has no journal to replay helpers against). Capture seed/time divergence (5.2) is the backstop for computed helper names.
- **G6 (shape):** `agent()` calls inside a loop whose bound is not a literal number or an `args`-derived array length visible in the source, and calls whose count depends on a tracked value in any way the rules above cannot classify. Refused as unclassifiable.

Allowed by construction: fixed sequential calls; `parallel` over an `args`-derived array with a stage/prompt built per item; `pipeline` over an `args`-derived array; prompts built by template interpolation or concatenation of literals, `args` fields and tracked results (whole or field access). The guard is lexical and conservative: it refuses some compilable scripts (a false refusal costs a runner run; a false acceptance costs a wrong unattended graph). Scripts that move results through helper functions the guard cannot see through are refused as unclassifiable only when a tracked identifier reaches a forbidden position through a plain assignment chain (one hop is tracked); deeper hiding is the documented blind spot the always-printed caveat covers. This is a guard, not a proof, and the issue says so.

### 5.2 Capture

1. Parse through the engine's parser (metadata, phases). A parse failure is a usage refusal (exit 2).
2. Run the engine with `CapturingBackend`. Run A: `EngineConfig` seed 11, `started_at_ms` 0. Run B: seed 99, `started_at_ms` 86,400,000. The backend answers each call at once with a stub derived from the request's `call_id`. That field is confirmed present on the request the backend consumes: `{{P5-01}}`'s specification defines `AgentRequest` with `pub call_id: CallId` (digest and occurrence computed over the canonical request). If the merged type lacks it, that is an issue stop condition — the backend does not recompute digests itself:
   - text call: the string `⟨wf:<digest first 12>:<occurrence>⟩` (the sentinel);
   - schema call: a stub object built leaf by leaf: string leaves the sentinel, number leaves the numeric marker `900000000 + occurrence`, boolean leaves `true`, array leaves a one-element array of the element stub, object leaves recursed, `null` leaves stay `null` (a script may legitimately branch on null-ness only through the forbidden positions G1-G3 anyway), other leaves the sentinel string.
   The backend records label, phase, prompt, schema, tier, model, provider, effort, profile, toolsets, skills, isolation, `max_turns`, workflow path, `call_id`, and whether any earlier call was still outstanding when this one started (the batch input, 5.3). It defers each stub reply by one engine yield so concurrent calls are all seen outstanding together.
3. Normalise both captures by replacing each sentinel with `⟨wf-result⟩`. Compare count, order and every recorded field, prompts after normalisation. First difference: refuse, naming the first differing call (label or digest). This catches helper-dependent prompts (different start times), seed-dependent branching the guard missed, and any non-determinism.
4. Unsupported-option gate (issue REQ-11): any recorded call with explicit `toolsets` or `max_turns` refuses here, before any board write. (`max_turns` is recorded precisely so this gate and the capture comparison see it; `goal_max_turns` on a card is a different feature and is never substituted.)

### 5.3 Edges

- **Data edges:** scan each surviving prompt for sentinels `⟨wf:<digest>:<occurrence>⟩` and numeric markers `900000000 + occurrence` (word-boundary match). Each hit adds that call as a data parent. At emission the marker text is replaced by the REQ-10 line naming the real card id. A marker produced by a schema stub's number/boolean/array leaves travels inside JSON or text the script interpolates; when the script instead computes with it, G3/G4 have already refused. A transformed result (upper-cased, sliced) destroys the marker: G4 refuses, so no edge is ever silently lost.
- **Control edges (batches):** calls that were outstanding together (started before any of them was answered, possible because the backend defers replies one yield) form one batch per workflow path, in start order. Every call in batch *k+1* gains every call of batch *k* as a control parent. Awaiting a single call therefore chains it; awaiting `parallel([...])` joins the whole group; calls inside one batch gain no edges among themselves. Batches are computed per workflow path so a nested `workflow()` lane does not chain onto its parent lane's calls (the child's own first batch parents onto the root like any first batch; ordering between parent-lane and child-lane calls is not representable on one board and is a documented limit — nested scripts whose child must wait for a parent-lane result must pass it through a prompt, which creates a data edge).
- Parents of a card = data parents ∪ control parents ∪ {root for first-batch calls}. The root is created before all cards, so parent ids always exist at create time; capture order (a parent, by data or control, always completes before the child starts) guarantees creates can carry the `parents` field directly.

## 7. Edge cases

| Case | Expected |
|---|---|
| Script has zero agent calls | Compile prints `nothing to compile: the script starts no agents` and exits 0, creating not even the root |
| Two calls with identical prompts | Distinct cards: occurrence differs, so keys and edges differ (the engine's call identity already does this) |
| A prompt uses two earlier results | Two data parents; both replacement lines appear, in call order |
| A nested `workflow()` call | Children flatten into the same board; titles gain the workflow path prefix `<child>/<label>`; ordering across lanes is data-edges only (5.3); nesting past one level is the engine's own error |
| Tier route limited but usable | Compiles; the roster state is printed with the card line. Missing or unauthenticated model: refusal before writes (issue REQ-11) |
| Staffing file changed, same script and args | New compile id (routes are identity inputs), new cards; the old graph stays untouched for the operator to archive |
| `--profile` or `--tenant` changed, same script | New compile id (both are identity inputs, section 4); never a silent reuse of the old cards |
| Create fails on card 3 of 5 | Root and cards 1–2 stay (root not yet `done`); the message names card 3's call; a recompile finishes the graph (test 18) |
| Root already `done` on recompile | No PATCH is sent (Hermes would refuse a second completion); a complete graph prints `already compiled` with zero POST/PATCH (test 17) |
| A compiled parent is archived mid-run | Its children promote with no handoff for that parent; their card bodies tell them to report the missing input and block (issue REQ-13); the view warned before archiving (issue REQ-6) |
| Board has another team's cards | The view shows them (the board is shared); compile touches only its own keys; the tenant flag narrows the view filter, never other people's cards |
| Events cursor from another board | Never reused: switching boards refetches and restarts the tail from the new snapshot's `latest_event_id` |
| Body over 8,192 characters | Refused before writes, call named (the worker would only see a truncated body) |
| Result JSON over 3,500 characters | The card body routes it to a declared artifact with `result_artifact` metadata (issue REQ-13); downstream workers fetch the parent's attachments through the kanban show tool the worker already has |
| Root patch refused at a future Hermes | Compile reports "cards created; root left in `<status>`" and exits 1; the graph itself is complete and dispatchable |

## 9. The board view layout (binding; cited by issue REQ-7)

```text
 kanban: <board slug>  <shown>/<total> cards  live:<cursor id|parked|off>   <- header, 1 line
 Ready (3)          Running (1)         Blocked (1)        ... one column per
 > fix the parser    worker on docs      ! waiting input      workflow column,
   review copy       write tests           deploy plan        then Other
```

- Columns render in `GET /workflow` order, `Other` last; each column header is `<label> (<count>)`. Column width is the terminal width divided by the column count, minimum 18 characters; columns that do not fit scroll horizontally with `h`/`l`.
- A card line is `<marker><title> <assignee> <age>`: marker `> ` for the selected card, `  ` otherwise, plus `! ` before the title when the card is `blocked` or in `review`. Age is the time since `created_at` (or since `started_at` when running), rendered as `12s`, `3m`, `2h` or `1d` (largest whole unit). Titles truncate to the column width with a final `>`.
- An empty column shows `(empty)`. A board with no cards shows the columns and `(no cards on this board)` in the first. While the first snapshot loads, the view shows `loading board <slug>...`; a failed load shows the REQ-1 error text and `press r to retry, Esc to close`.
- The status line (last line) shows, in order: the tail state (`live:<cursor>`, `tail parked`, or `connecting...`), then any transient refusal or notice (`nudge: dispatcher nudged`, a refusal detail, the read-only notice), cleared on the next keypress.
- The detail pane replaces the columns (Esc returns to them). Its fields render in REQ-4's order, one `Label: value` line each, with `Parents:`/`Children:` as comma-joined `title (status)` lists (`(none)` when empty) and comments as `<author> · <age>` over the comment text. No pane edits stored text; long values use REQ-4's truncation rule.
- The move menu and board menu are lists drawn over the lower half of the view: one ` <n>  <label>` line per destination or board in workflow order, the current selection marked `> `. A digit key selects directly (1 to 9); `j`/`k` move the selection and Enter confirms; Esc cancels. A destructive destination's line ends with ` (asks first)`.

## 10. Design reasoning

- **REST over a new RPC:** Hermes's kanban already has three surfaces (CLI, dashboard plugin, agent tools) over one database module. A fourth, Talaria-specific RPC would need an upstream change; the plugin REST is shipped and documented. The cost is no generated types, which is why the client parses tolerantly (issue REQ-2) and the fixture is key-compared per pinned release.
- **Root staging without atomicity:** the swarm's blocked-root-in-one-transaction cannot be expressed through the REST create shape, and inventing a create-then-block sequence would still leave a window and a misleading status. The honest equivalent is the preflight gate on `kanban.default_assignee` plus the fact that an unassigned ready card is skipped by the dispatcher. The visible partial graph during emission is accepted: the board is a live collaboration surface, and the root's body says the graph is being compiled.
- **Guard plus double capture, neither alone:** static analysis of arbitrary scripts cannot prove shape, and two agreeing stub runs cannot either (stub values can take the same branch a real value would not). The lexical guard refuses the result flows that make shape unknowable; the double capture catches what the guard cannot classify; the printed caveat covers the residue. Each layer's test proves a different failure (tests 10 and 11).
- **Control edges as well as data edges:** the handoff mapping ("pipeline → parent links, parallel → siblings") describes data flow only. Awaiting is also ordering: releasing a sequential second call immediately would change concurrency, side effects in shared workspaces, and cost. Batch control edges keep the board faithful to the script's execution order while leaving true siblings parallel.
- **No result validation:** adding a Talaria-side watcher would recreate the runner this unit avoids. The schema-in-body contract plus parent-handoff context is what Hermes offers today; enforcement belongs to the upstream proposal in the handoff's later list.
- **Per-request board slug over the shared pointer:** the pointer is global to the install. A terminal client that flips it would move the operator's other tools (dashboard, CLI) mid-work.
