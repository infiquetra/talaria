## 1. What this unit adds, in one picture

```text
vim off (default)                vim on
┌──────────────────────┐         ┌──────────────────────┐
│ > type here          │ bound key│ > type here          │
│                      │ ──────> │ -- NORMAL --         │
└──────────────────────┘         └──────────────────────┘
  today's composer,                i -> INSERT (today's composer + Esc exits)
  unchanged                        Esc -> NORMAL (never interrupts from INSERT)
```

## 4. Design (normative)

### 4.1 State, caret mapping and invariants

State held by the composer when vim is enabled (in `vim.rs`, beside the existing draft state):

```text
VimState {
  mode: Normal | Insert | Visual | VisualLine,
  anchor: Option<caret byte index>,        // VISUAL start; None outside VISUAL
  pending_count: Option<u32>,              // digits typed, saturated at 9999
  pending_operator: Option<d | c | y>,
  pending_find: Option<f | F | t | T>,     // waiting for its character
  pending_g: bool,                         // a single `g` waiting for the second
  last_find: Option<(kind, cluster)>,      // for ; and ,
  last_change: Option<RecordedChange>,     // for dot; section 4.6
  insert_start_snapshot taken on entering INSERT (for the undo group, section 4.6)
}
```

`VimMode` derives `Clone, Copy, PartialEq, Eq, Debug` (tests compare modes and print them on failure). The composer caret is always a byte index on a grapheme-cluster boundary between clusters (the existing invariant; `caret()` returns it). Vim's NORMAL and VISUAL caret is thought of as "on" a cluster. The mapping is:

- The displayed NORMAL or VISUAL caret is the cluster that starts at the caret index, except when the caret is at the end of a logical line (or the draft is empty or a line is empty), where the displayed caret is on the last cluster of that line (or on an empty reversed cell for an empty line) and the caret index stays where it is.
- Motions below are specified as movements of the caret index between clusters. After any NORMAL or VISUAL motion or edit, the caret index is clamped to the current logical line: it may sit at the line's end only when the line is empty; otherwise it is at most the start of the line's last cluster. Entering INSERT (`i` at that clamped position, or `a` stepping one cluster forward first, section 4.3) lifts the clamp, so INSERT editing at a line end works exactly as today.
- Entering NORMAL or VISUAL (by Esc from INSERT, by toggling vim on, or by leaving VISUAL with Esc, Enter, `v` or `V`) applies the same clamp at entry: the caret index moves back to the start of the current logical line's last cluster when it sits at that line's end and the line is non-empty, so the caret is never past a non-empty line's last cluster on entry and `x` always has its cluster. VISUAL cancel keeps that clamped caret. Toggling on with a plain caret at a line end therefore lands on the last cluster.
- Blank means a space or a tab cluster. `$` on an empty line does not move (there is no cluster to land on).
- A logical line is the text between line breaks (`\n`). A visual (wrapped) row is what the existing wrapping produces. Vertical vim motions use logical lines and reuse the composer's `preferred_col`, which is a display column (the existing buffer field, not a cluster count), never wrapped rows, and never history. The rendered NORMAL or VISUAL caret is a reversed cell over the cluster that starts at the caret index (over an empty cell at an empty line), exactly the composer's existing reversed-cell caret; VISUAL draws every selected cluster reversed in addition to it. The existing INSERT-mode Up and Down keep their history meaning on the first and last visual rows, unchanged.
- Text changes always go through the existing buffer paths, so the existing filtering (no control characters other than `\n` and `\t`, no lone zero-width clusters), grapheme, word and wrapping rules apply to vim edits without a second implementation. Vim code never holds a second copy of the draft.

A word (`w`, `b`, `e`) is one run of word characters (Unicode alphabetic or numeric, or underscore — the composer's existing word definition), or one run of other non-whitespace characters (punctuation), skipping whitespace and line breaks between runs. A WORD (`W`, `B`, `E`) is one run of non-whitespace characters. Motion targets: `w` and `W` go to the start of the next run; `b` and `B` to the start of the current or previous run; `e` and `E` to the end (last cluster) of the current or next run. Crossing a line break is allowed for all six; at the buffer ends they stop at the first or last caret position.

### 4.2 NORMAL motions (no text change)

| Key | Target (caret index after the move) |
|---|---|
| `h`, Left | One cluster left, stopping at the logical line start. |
| `l`, Right | One cluster right, stopping on the logical line's last cluster (section 4.1 clamp). |
| `j`, Down | One logical line down, keeping the preferred display column; on the last line, no move. Never history. |
| `k`, Up | One logical line up, keeping the preferred display column; on the first line, no move. Never history. |
| `0` | Start of the logical line. |
| `^` | First non-blank (blank = space or tab) cluster of the logical line, else the line start. |
| `$` | On the logical line's last cluster (on an empty line: no move); with a count `n`, the last cluster of the line `n - 1` lines down, stopping on the draft's last line when the count runs past it (the extra count is consumed there). |
| `w`, `b`, `e`, `W`, `B`, `E` | Section 4.1 word and WORD rules. |
| `gg` | Start of the first cluster of the draft; with a count, the start of that logical line (clamped to the last). |
| `G` | Start of the first cluster of the last logical line; with a count, that logical line (clamped). |
| `f<x>` | On the next occurrence of cluster `x` on the same logical line; no occurrence, no move. |
| `F<x>` | On the previous occurrence of `x` on the same logical line. |
| `t<x>` | One cluster before the next occurrence of `x` (if the next caret position already sits just before an occurrence, it still advances to the following one, as Vim does); no occurrence, no move. |
| `T<x>` | One cluster after the previous occurrence of `x`, mirroring `t`. |
| `;` | Repeat the last `f`, `F`, `t` or `T` in the same direction. |
| `,` | Repeat it in the opposite direction. |

Arrows in NORMAL are the `h`, `l`, `j`, `k` motions (Up in NORMAL therefore never recalls history; history lives in INSERT and in the plain composer). Every motion accepts a preceding count and repeats the move that many times, stopping at the pinned boundary instead of failing.

### 4.3 NORMAL entries and edits

Insert entries (each records the undo snapshot, section 4.6, then enters INSERT). Count rule for every entry in this table (`i`, `a`, `I`, `A`, `o`, `O`): a pending count is discarded and the entry happens once, so `3i` then typing `ab` then Esc inserts `ab` once, never three times. `v` and `V` likewise ignore a pending count on entry (section 4.4).

| Key | Entry |
|---|---|
| `i` | INSERT at the caret. |
| `a` | One cluster forward (not past the logical line end, where it lands at the line end), then INSERT. |
| `I` | At the first non-blank cluster of the logical line (else its start), then INSERT. |
| `A` | At the logical line end, then INSERT. |
| `o` | Insert a line break at the logical line end, then INSERT at the new line's start. One undo group for the whole following insert session, including this break. |
| `O` | Insert a line break at the logical line start and move to the new empty line above, then INSERT. |

Single edits in NORMAL (each is one undo group and sets the kill buffer when it removes text, except `r`). Count rules: `x`, `X`, `r` and `s` repeat like each other — a count deletes or replaces that many clusters on the same logical line only, clamped at the line edge (`3rX` replaces 3 clusters; fewer available clusters means fewer replaced). `S` takes a line count: it clears that many logical lines into one empty line (section 4.3 `cc` rule) and enters INSERT at its start; without a count it clears one line. `D` and `C` take the `$` count rule (target line `n - 1` lines down, clamped to the last line). On an empty line `r` does nothing and stays in NORMAL, and `s` enters INSERT deleting nothing.

| Key | Edit |
|---|---|
| `x` | Delete the cluster at the caret (a count deletes that many clusters on the same logical line only: the count is consumed at the line end and never carries to the next line, and `x` never deletes a line break). Empty line: nothing. |
| `X` | Delete the cluster before the caret (stopping at the logical line start; never joins lines). |
| `r<x>` | Replace the cluster at the caret with the one grapheme cluster `x` the next key carries (a combining or joined sequence arrives as one cluster key payload where the terminal reports it as one key; through the text filter, and a filtered-out `x` changes nothing). Stays in NORMAL. Esc instead of `x` cancels. |
| `s` | Delete the cluster at the caret (as `x`) and enter INSERT. |
| `S` | Delete the whole logical line's text (not its line break), enter INSERT at the line start. |

Doubled `cc` is carved out of the literal doubled-operator rule: `cc` acts as `S` over the counted lines — it deletes the counted logical lines' text but keeps one empty logical line and enters INSERT at its start, so on `a\nb` `cc` on line 1 then typing `x` gives `x\nb`, never `xb`. Its kill buffer holds the deleted lines' text with the linewise flag set. Every other doubled form keeps the linewise rule in the next paragraph. Over-count linewise operations clamp to the available lines (Vim-style): `2dd` on a one-line draft deletes that line's text leaving one empty line, `dj` on the last line and `dk` on the first line act on the lines that exist, and `d2j` near the end deletes to the last line. An operator cancels with no change only when its clamped span is empty (no line or cluster exists to act on).

Operators `d` (delete), `c` (change: delete then INSERT), `y` (yank: copy only), each followed by a motion, a find motion, the same operator letter (linewise, whole logical lines including the trailing line break, except that deleting the last line without a following break also removes the preceding break so no empty phantom line remains), or the end shortcuts `D` (same as `d$`) and `C` (same as `c$`, entering INSERT). Rules:

- The affected span for a motion is from the caret to the motion's target, following Vim's inclusive and exclusive convention as pinned here: `w`, `W` and `l` are exclusive (the target cluster is not included); `e`, `E`, `$` and find motions are inclusive (the target cluster is included); `b`, `B`, `h`, `0` and `^` work backwards to the target cluster inclusive of it and exclusive of the starting cluster; `j` and `k` with an operator are linewise (whole logical lines from the first to the last line touched); `gg` and `G` with an operator are linewise to the draft start or end line.
- Cross-line characterwise spans include the intervening line break. Word and WORD motions (section 4.1) may cross lines, so on `one\ntwo` at the first cluster, `dw` deletes `one\n` (its exclusive target is the start of `two`) and `db` from the start of `two` deletes the same span backwards. Only `x`, `X` and motions explicitly confined to one logical line (`h`, `l`, `0`, `^`, `$` as caret motions) never delete a line break.
- Counts multiply: a count before the operator and a count before the motion multiply (each saturating with the other at 9999). `2dd` and `d2d` are the same.
- Vim's `cw` special case applies: `cw` and `cW` with the caret on a word or WORD cluster behave as `ce` and `cE` (they change to the end of the current run, not to the start of the next), so `cw` on `aa` in `aa bb` plus typed `1` gives `1 bb`. `dw` and `yw` keep the exclusive `w` rule above.
- After `d`, the caret stays at the span start, clamped to the (possibly shortened) line. After `c`, INSERT starts at the span start. After `y`, the caret returns to the span start (for a forward yank) or stays at its target end for a backward yank — pinned as: the caret ends at the start of the yanked span in all directions, so put tests are deterministic. The kill buffer holds the span exactly (linewise spans include their line break; section 4.5).
- Cancellation is about the span, not the caret landing position. An operator cancels and changes nothing only when its motion is unsuccessful (it cannot move at all under section 4.2) or its exclusive span is empty. A successful inclusive motion whose target is the starting cluster still acts: `d$` on the last cluster of `ab` deletes `b`, `de` on a one-cluster word deletes that word, and `cw` on a one-cluster word deletes it and enters INSERT for its replacement. The no-op cases are the unsuccessful ones (`dw` at the very end of the draft, `db` at its start). Tests must cover both families (issue test 5). An operator waiting for its motion renders the pending segment (issue REQ-11) and is cancelled by Esc, Ctrl+C, an unknown key, or any key that cannot continue it (which is then discarded, not reinterpreted). The same discard rule covers every pending state: pending find (`f`, `F`, `t`, `T` awaiting its cluster), pending `r` (awaiting its replacement cluster) and pending `g` (awaiting the second `g`). In each, Enter, Ctrl+R, an arrow, a mode key (`i`, `v`, `V`, Esc excepted as the cancel itself), or any other key that cannot continue the pending state cancels it and is itself discarded, never reinterpreted and never submitted. `g` followed by any key other than `g` discards both keys and starts no new command.
- `p` and `P` are section 4.5. `u`, dot and Ctrl+R are section 4.6.

### 4.4 VISUAL

- Entry counts are ignored: `3v` and `2V` enter VISUAL once with the pending count cleared. `v` anchors a characterwise selection at the displayed caret cluster; `V` anchors a linewise selection covering the caret's whole logical line. Motions and counts move the active end exactly as in NORMAL (with the section 4.1 clamp lifted for the line end cluster, so the selection can include a line's last cluster and, with `j` and `k`, further lines). The selection is every cluster from the anchor to the active end inclusive, and a characterwise selection spanning lines includes the intervening line breaks (so `d`, `x` and `c` delete them and `y` copies them, mirroring section 4.3 cross-line spans); linewise selection extends to whole logical lines at both ends, including trailing line breaks on all but a final line without one, mirroring linewise operators.
- `d` and `x` delete the selection into the kill buffer, return to NORMAL with the caret at the selection start (clamped). `y` copies it, returns to NORMAL with the caret at the selection start. `c` on a characterwise selection deletes it and enters INSERT at its start; `c` on a VISUAL LINE selection deletes the selected lines but keeps one empty logical line and enters INSERT at its start (Vim-like, never joining the surrounding lines). `p` replaces the selection with the kill buffer (characterwise text lands at the selection start with the caret on the last inserted cluster; a linewise buffer replaces whole lines with the caret on the first cluster of the first put line; a characterwise buffer over a linewise selection deletes the selected lines and lands at the start of the first selected line with the caret on the last inserted cluster), returns to NORMAL, and the replaced text becomes the new kill buffer with the linewise flag set if and only if the selection was linewise (VISUAL LINE), as Vim does. Ctrl+R is a supported VISUAL key with the section 4.6 transition (selection cleared to NORMAL before a successful redo; an empty redo stack leaves the selection and the mode untouched and does nothing). Supported VISUAL keys are motions, counts, `d`, `x`, `y`, `c`, `p`, `v`, `V`, Esc, Enter (clears the selection, issue REQ-7), Ctrl+C (cancels, issue REQ-7) and Ctrl+R. An unknown key in VISUAL clears any pending count or operator, keeps the selection intact, and returns the changed result if and only if a pending label was visible (otherwise unchanged), so a stray key cannot drop a selection silently. Any other unsupported key (including `o` and `u` while selecting) follows that same rule. In NORMAL and VISUAL no other key-map chord acts (issue REQ-5): dispatch is the toggle claim, then these tables, then nothing, and Tab does nothing there. Text typed in VISUAL never enters the draft.
- Rendering: every selected cluster is drawn reversed, in addition to the caret cell.

### 4.5 Kill buffer and put

The kill buffer is the composer's existing one span (the latest killed or yanked text). Vim delete, change and yank overwrite it, except an empty-motion cancel never touches it. A linewise span is the whole lines plus their trailing line breaks (with the last-line adjustment of section 4.3). Put:

- Characterwise buffer: `p` inserts it after the displayed caret cluster and leaves the caret (insertion index) on the last inserted cluster, i.e. at that cluster's start byte offset; `P` inserts it before the caret cluster with the caret likewise on the last inserted cluster. A count inserts the span that many times end to end (three copies for a count of 3), with the caret on the final copy's last cluster. A counted linewise put likewise inserts that many whole-line copies end to end, with the caret on the first cluster of the last put line.
- Linewise buffer: the kill buffer carries one extra boolean, `linewise`, and that flag is the only criterion (never the span's ending). It is set by the vim linewise operators (`dd`, `yy`, `cc` and the VISUAL LINE forms, and a linewise VISUAL put's replaced text) and cleared by every other kill, yank or delete, including the plain composer's Ctrl+K, Ctrl+U and Ctrl+W kills (which therefore always produce a characterwise buffer, even when the killed span ends with a line break, and even when a characterwise vim yank crosses a line break). `p` inserts a linewise buffer as whole lines below the caret's logical line and leaves the caret at the first cluster of the first put line (for a counted put, of the last put line's first cluster; see below); `P` inserts it above. Putting into an empty draft: a linewise `p` or `P` makes the draft exactly the put lines with no leading or trailing empty line and leaves the caret at their first cluster; a characterwise `p` or `P` inserts at byte 0 with the caret on the last inserted cluster. Counted `P` carets: linewise `2P` above leaves the caret on the first cluster of the first (topmost) put line; characterwise `3P` before leaves it on the last cluster of the final copy, the copy adjacent to the original caret cluster (copies sit end to end between the insertion point and that cluster).
- An empty buffer (nothing ever killed or yanked in this composer) makes `p` and `P` no-ops. INSERT yank (Ctrl+Y by default) inserts the same span at the insertion caret, as today, regardless of its linewise flag.

### 4.6 Undo, redo, find state, pending and dot

- Undo groups (issue REQ-8), with one precedence rule where candidates overlap: an open insert session absorbs everything typed, deleted or pasted inside it. An insert session opens one group on entry (its snapshot is the state before the entry edit, so a `c`, `s`, `S`, `o` or `O` edit, any bracketed paste inside the session, and all typing undo together) and closes on leaving INSERT. Only outside an open insert session is a bracketed paste its own group. A NORMAL operator, `x`, a put (`p` or `P`, NORMAL or VISUAL), a VISUAL edit, a dot repeat and a `clear` that changes text are each one closed group (test 8 undoes a put). `load` is special, because tests and the application both load drafts: it clears both stacks and then records the pre-load (text, caret) as the single remaining group even when the loaded text is identical to the current text (unlike `clear`, which groups only when it changes text), so one `u` after a load restores the previous draft and a second `u` does nothing — and tests therefore build each case on a fresh composer (section 6 preamble) instead of assuming a load left an empty stack. `y` and motions open no group. The stack holds at most 100 groups (oldest dropped). A new group clears the redo stack. `u` pops one group, pushes the current (text, caret) to redo, and restores; Ctrl+R in NORMAL does the reverse, and in VISUAL it clears the selection and returns to NORMAL before applying a redo (an empty redo stack does nothing and leaves the selection in place). Both return the composer's changed result, never submit or interrupt. Submitting a draft and `set_vim_enabled(false)` clear both stacks, while a submit's internal draft clear is not itself a group.
- Count rules for this section: `u`, Ctrl+R redo and dot (`.`) each ignore a pending count — the count is discarded and the command runs once (`2u` undoes once, `3.` repeats once). `;` and `,` with no last find, and dot with no last change, are no-ops returning unchanged. Undo and redo never update `last_change` and never clear the redo stack; only a new change (a closed group that actually changed the text) clears redo, so a failed operator, an unsuccessful motion, or a no-op edit (`x` on an empty line) leaves both `last_change` and the redo stack untouched.
- Dot (`.`): `last_change` records the last closed edit group as a replayable description: for an operator change, the operator, its motion (or linewise form), both counts and the target cluster of a find motion if any, plus the exact text inserted during a following insert session (for `c` forms), captured cluster by cluster until Esc. The change-entry forms `s`, `S`, `o` and `O` are recorded forms too: dot replays their deletion or line break and then the captured inserted text (so dot after `o`, typed text and Esc opens the same new line with the same text below the new caret line). A bare insert entry (`i`, `a`, `I`, `A`) with typing is not recorded, because it has no edit command to repeat — this is the only unrecorded insert session. VISUAL edits (`d`, `x`, `c`, `p` in VISUAL) are not recorded for dot. For `x`, `r` and puts, the key form and count (and any replacement cluster) are recorded. Pressing dot re-runs that description at the current caret as one new group (and it becomes the new `last_change`, so dots chain). If the replayed motion is unsuccessful or its find character is absent, dot changes nothing.
- Pending and counts: digits `1` to `9` start a pending count and `0` continues it (a leading `0` is the line-start motion, never a count). The count saturates at 9999 (`pending_count = min(9999, pending_count * 10 + digit)`). The pending label rendered is the typed digits, then the operator letter, then the second count and motion letters exactly as typed so far, for example `d`, `2d`, `d2`, `2df`. A pending `r` shows `r` and a lone pending `g` shows `g` until the next key resolves or cancels them. Esc, Ctrl+C, completion, or an unknown key clears all pending state. A pending find (`df` waiting) shows `df` and waits for exactly one cluster; Esc cancels it.
- History recall and mode switches: Up and Down recall in INSERT is absorbed into the open insert session's single group (it opens no group of its own), so after Esc one `u` restores the state before the insert session was entered, not the pre-recall text; undo restores text and caret only, never the history-browse position. Any mode change (INSERT to NORMAL by Esc, VISUAL to NORMAL, toggling vim off or on) disarms a P1-08 armed exit hint, so the hint never survives into NORMAL to hide the mode segment; the disarming key itself returns changed (or its pinned mode result), never `Interrupt` or `ExitRequested` for that reason.
- Last find: set by every completed `f`, `F`, `t`, `T` (including inside an operator); `;` and `,` use it and keep it.

### 4.7 INSERT, submit keys and routing

INSERT delegates every key to the existing composer handling first, with the two issue REQ-4 exceptions (Esc enters NORMAL; text changes feed the undo group), so newline chords, history, paste bursts, the exit-arming Ctrl+C table, placeholder behaviour and keyboard-enhancement labels are inherited, not reimplemented. NORMAL and VISUAL keys never reach that path.

Per-mode key outcomes (all pinned; the application routing before the composer is unchanged and listed for completeness):

| Key reaching the composer | Vim off | INSERT | NORMAL | VISUAL |
|---|---|---|---|---|
| Enter | submit | submit | submit (blank: nothing) | clear selection only |
| Esc | `{{P1-08}}` table | enter NORMAL | cancel pending or selection; else interrupt when a turn runs; else nothing | cancel selection |
| Ctrl+C | `{{P1-08}}` table | `{{P1-08}}` table | cancel pending; else interrupt when the draft is empty and a turn runs; else nothing | cancel selection |
| Ctrl+R | history search (routing) | history search (routing) | redo | redo |
| Ctrl+G | external editor (routing) | external editor | external editor | external editor |
| printable character | text | text | vim command or nothing | vim command or nothing |
| bracketed paste | paste | paste (one group) | paste at caret, stay NORMAL (one group) | replace selection, go NORMAL (one group; caret on the last inserted cluster, or at the selection start clamped when the paste inserts nothing) |

Routing order at scheduling is whatever the merged application has (R3), with exactly one owned change. The application's key dispatch (in `crates/talaria-app/src/app.rs`, `{{P1-12}}`'s construction and routing file; the planner confirms the merged function name before Step 0) gains this claim, evaluated in that dispatch before `comfort_route::route` is consulted: the predicate is exactly (the resolved action is the history-search action) and (the focus is the composer) and (the composer is vim-enabled with mode NORMAL, VISUAL or VISUAL LINE). When the predicate holds, the raw key is delivered to the composer (which treats it as redo) and no history search opens and `route` is not called for that key. `comfort_route::route` (`{{P2-13}}`'s pure function, signature unchanged) is never modified. In INSERT, with vim off, and in every other focus, the claim does not fire and existing routing is byte-for-byte the merged behaviour; the history-search action being rebound or unbound moves or removes the claim with it, because the claim keys on the resolved action, not on the literal Ctrl+R chord. The same construction site passes the loaded `[composer] vim` boolean into the composer once at startup (the way the key map is already passed). If the merged dispatch has no place where that claim can be evaluated before the comfort route, that is an issue stop condition, not a reason to change `comfort_route` behind its owner or pick a different redo key. Inside the composer, dispatch with vim on is: the toggle claim first, then INSERT delegation or the NORMAL and VISUAL tables, then nothing (no other key-map chord is consulted there, and Tab does nothing). Plain letters in NORMAL and VISUAL never enter the burst detector at all: the detector's inputs are characters the composer inserts, which in vim modes exist only in INSERT. A bracketed paste is not burst input in any mode. An Enter pressed in NORMAL while a paste-burst window inherited from INSERT typing is still open submits under the section 4.7 table (the vim table wins); the 120 ms window rule applies only where Enter would insert text (INSERT and vim-off), never to a NORMAL submit.

The composer demo change is likewise two parts: the `--vim` flag, and reading `[composer] vim` from the configuration file the demo already loads and passing it the same way, which is what makes UAT-2 work with no flag. ## 7. Edge cases

| Case | Behaviour |
|---|---|
| Draft is empty in NORMAL | Every motion and operator is a no-op; `i`, `a`, `I`, `A`, `o`, `O` enter INSERT on the empty line; the caret cell renders reversed and empty. |
| Operator at a line or buffer edge | Section 4.3's clamp rule: linewise spans clamp to the available lines; `x` and `X` never delete a line break, while characterwise word spans may (section 4.3's cross-line rule); `dd` on the only line leaves one empty line (its break handling removes the line's text and leaves no phantom). |
| A count on `0` | `0` alone is the line-start motion; a count ending in 0 (`10l`) is ten steps, because after a nonzero first digit `0` continues the count (4.6). |
| Find character is a digit, space or combining cluster | Find takes the next whole cluster as its target, whatever it is, including a space; a combining sequence is one cluster and matches as one. |
| Very large pasted replacement in VISUAL | The paste path's existing rules (no size limit, filtering) apply; the group is one undo entry, and the 100-group cap still holds. |
| Undo after the draft was submitted | Impossible: submit clears the stacks (4.6), so `u` on the next draft cannot resurrect a sent prompt. `load` is undoable instead, because it is an edit, not a send. |
| Toggling off mid-pending or mid-VISUAL | Pending, selection and stacks clear; the draft and caret stay (4.8). Toggling back on starts in NORMAL. |
| Turn finishes while in NORMAL | Nothing in vim state depends on a turn except the Esc and Ctrl+C interrupt cells, which read the context per key, as today. |
| Terminal sends Esc with a following key (an Alt sequence) | Crossterm reports Alt plus key, not Esc (the `{{P1-08}}` C6 fact), so it never leaves INSERT by accident; a lone Esc is required, as UAT-6 records per terminal. |
| History entry recalled in INSERT, then Esc, then NORMAL edits | Leaving INSERT for NORMAL does not end the browse by itself; the recalled text is the draft and NORMAL edits apply to it like any draft, keeping `{{P1-08}}`'s rule that an edited recalled entry survives the browse. A submit or an INSERT Ctrl+C clear ends the browse, as today. If the merged history implementation cannot express browsing across a mode switch, the builder stops (issue stop conditions) rather than dropping the edit. |

## 8. Reasoning and rejected alternatives

- **A separate vim editor widget.** Rejected: it would duplicate the buffer, wrapping, history, paste and rendering contracts and drift from every composer fix. The mode is a dispatch layer over the one buffer.
- **Vim keys as configurable `[keys]` chords.** Rejected: the composer's key map refuses plain-letter chords in the composer context by design (they must type), and making hundreds of vim combinations configurable multiplies conflicts. One toggle action is configurable; the command set is fixed, like Vim's defaults.
- **Starting in INSERT when vim is on.** Vim itself starts in NORMAL, and starting in NORMAL is what makes an accidental typed command visible instead of surprising. The mode segment makes the state explicit.
- **Esc interrupts from INSERT as today.** Rejected: it would make NORMAL unreachable by the key every vim user presses, and a toggle whose Esc does two things depending on timing is worse than the pinned two-press path from INSERT to interrupt, which UAT-5 rehearses.
- **Full Vim (macros, registers, ex commands, search, text objects).** Deferred by decision: each multiplies the operator, count and VISUAL combination space. The closed tables fail safe (an unsupported key does nothing), so the subset can grow later by adding rows, with the parity remap setting (`jj` to Esc) and text objects as deferred follow-ups (no operator answer is awaited by this unit).
- **Undo for everyone.** Tempting, but it changes non-vim behaviour and group expectations (what is a group for plain typing?) deserve their own decision. It stays scoped to vim sessions here.
