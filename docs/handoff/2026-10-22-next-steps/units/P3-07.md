## 0. What this unit is, in one paragraph

A background agent that edits code is only useful if its work can leave the machine. `P3-03` starts an agent in a fresh git worktree (a second checkout of the same repository on its own branch, `talaria/<slug>`, under `<main root>/.worktrees/talaria-<slug>`) and records the tree, branch, base and session in the repository's git configuration. This unit gives the operator the rest of the loop without leaving Talaria: a review screen that lists the changed files of a session's folder with their diffs, stages and unstages files, discards one file's changes after a confirmation, commits (with an optional message drafted by the session's own model through Hermes's `llm.oneshot`), pushes the branch to `origin`, and opens a draft pull request with the GitHub command-line tool `gh`. It also puts a small pull-request label (number, draft or state, check result) on fleet rows (`P3-02`) and in the status line, the way Claude Code's agent view and footer show one. Hermes provides no remote procedure call for any of the git work: Hermes Desktop does it in its Electron main process, so a terminal client does it itself (roadmap row "P3-07 Review": "Local `git` and `gh`").

## 3. Design decisions and the reasons for them

### 3.1 Local git and gh, run by Talaria

Hermes has no gateway method for git work (H1). Its REST facade (H2) exists for Desktop on a remote gateway, but Talaria attaches only to a local gateway (the ticket path is loopback-only), would need a second authenticated HTTP client for it, and would inherit Hermes's choice to blank the user's global git configuration (H8), which breaks HTTPS credential helpers and commit signing for pushes. Talaria therefore runs `git` and `gh` itself, through `P3-03`'s `GitRunner` (non-interactive, global configuration kept), in the session's folder on this machine. The roadmap row says the same: "Local `git` and `gh`".

### 3.2 Which folder is reviewed

A fleet row has no folder (H20). The folder is resolved in this order, first hit wins:

1. A `P3-03` worktree record whose `talaria-session` equals the row's session id and whose `talaria-profile` equals the row's profile, in any known repository (section 3.8).
2. **Only when the row is the foreground session** (same `RowKey`): the folder the foreground already knows (`info.cwd` of its snapshot, as `P1-10` shows in the status line). For any other row this step is skipped, so a row can never show the foreground's repository.
3. Otherwise `session.info {session_id}` (plus `profile` when routed, see below) on a short-lived link, and its `cwd` (H19). One call per review opening; never per row.

"Routed" means `P3-03`'s `LaunchConn::routed_profile(row_profile)` returns `Some`: the link is host-scoped and the row's profile differs from the link's own profile. Hermes then dispatches to the sibling owner (`gateway/session_controls.py:258-271`); on the link's own home it removes `profile` before the exact-key check because `session.info` is in `_PROFILE_IMPLICIT` (`:90-94`). A `session.info` refused with any 4001 other than `not_found` (for example U1's cross-profile case) means step 3 found nothing: the row has no folder unless step 1 matched.

The folder must exist on this machine and be inside a git work tree; otherwise Talaria says why (section 10). Talaria never falls back to its own working folder, for a fleet row or for `/changes`: reviewing the wrong repository is worse than reviewing none.

`/changes` reviews the foreground session: step 1 (its record, if any), step 2, then step 3. For a session Talaria creates or resumes at launch, `info.cwd` is the folder `P1-12` sent as `cwd` (the launch folder), so in the UAT panes `/changes` reviews the folder `talaria` was started in. No-folder texts by entry point: `v` in the fleet view shows `Talaria cannot find this session's folder.`; `/changes` shows `Hermes did not report a folder for this session.`; `/changes` with no foreground session (for example after a detach) shows `No session in the foreground, so there is no folder to review.`

`session.info` fields: `cwd`, `branch` and `model` are string or null in the contract; null and an absent key mean the same; an empty or null `branch` means no branch name. Where the failure texts appear: opened from the fleet view, on `P3-02`'s notice line (its screen row 6), and the fleet list stays; opened with `/changes`, on the main screen through `P1-12`'s notice path, and no overlay opens.

### 3.3 Names: `v` in the fleet view and `/changes` in the foreground

Hermes owns `/review` and `/diff` (H21), and `P2-09` uses `/diff` for the session diff. Talaria's local command is `/changes` (no Hermes command or alias has that name at v0.22.4: `hermes_cli/commands.py` has no `changes` entry, and `ui-tui/src` has no `/changes`; checked by text search; `P2-03`'s rule "local wins" applies if one appears). In the fleet view the action `fleet_review` is bound to `v` ("view changes"); the keys `P3-02` and `P3-03` use (`enter`, `space`, `r`, `x`, `a`, `/`, `tab`, `n`, `w`, the movement keys) are untouched. Both keys are configurable under `[keys]`.

### 3.4 Two scopes

- **Uncommitted** (default): staged, unstaged and untracked changes against `HEAD`. All actions are available.
- **Branch** (read-only): the commits on this branch since its base, `git diff <base>...HEAD`. The base is the record's `base_commit` for a Talaria tree, else the merge base with `origin`'s default branch (H5 order). Every action is refused there with `Branch view is read-only: press tab for uncommitted changes.`: stage, unstage, discard, commit, and also push (`p`) and the pull request (`shift+p`). This follows the issue's settled decision 4 and Desktop, whose ship bar works only in the uncommitted scope (H3). (An earlier draft of this document let push and the pull request run in both scopes; the issue wins.) The read-only refusal is checked before every other refusal. `o` (open the known pull request in the browser) and `r` work in both scopes because they change nothing.

Desktop's third scope, "last turn", needs a per-turn baseline; `P2-09`'s checkpoints already answer "what did this turn change", so it is a non-goal here.

### 3.5 Discard is one file at a time, confirmed twice

Discarding deletes work, and an untracked file's discard is not recoverable from git. The review offers discard for the selected file only, behind a second keypress (the same double-key pattern as `P3-02`'s stop), and never "discard all" (Desktop has it, H9). Any key other than `shift+x` only cancels (`Discard cancelled.`) and does not also perform its own action, so `j` after the first press leaves the cursor where it was. Commands by row kind (section 5.4): a tracked file `git checkout HEAD -- :(literal)<path>`; a staged new file (in the index, not in `HEAD`) `git rm -q -f -- :(literal)<path>`; a staged rename or copy restores both paths (G6 d); an untracked file `git clean -f -- :(literal)<path>` (`-d` only for an untracked folder row, whose trailing `/` stays, G6 b). Never `git reset --hard` or `git clean` without a path. The `.worktrees/` row is never discarded (section 3.6).

### 3.6 Commit is the operator's own git commit

`git commit` runs with the operator's global and repository configuration (identity, hooks, signing), standard input closed and a 120-second timeout. Talaria adds nothing to the message: no trailers, no attribution, no sign-off. When nothing is staged, the commit stages every change first, as Desktop and VS Code do (H10); the editor's header says so before the operator confirms. Stage all is `git add -A -- ':(top)' ':(top,exclude).worktrees/'`: Hermes and `P3-03` keep linked worktrees under `.worktrees/`, `P3-03` excludes that folder only in repositories where it launched a tree, and a plain `git add -A` would record each checkout as an embedded repository (G6 c). For the same reason `space` and `shift+x` on a row whose path is `.worktrees/` or starts with `.worktrees/` answer `Talaria does not stage or discard .worktrees/: it holds other checkouts.` A commit on a detached `HEAD`, or with conflicted files, is refused.

Conflicted rows (status `U`): `space` and `shift+x` on a `U` row, and `a` (stage all) while any `U` row is listed, are refused with `Resolve the <k> conflicted files first.` (`<k>`: the number of `U` rows). Staging a conflicted file would mark it resolved with its conflict markers inside, and discarding it would lose one side of the merge; conflict resolution is out of scope.

The working warning (`The agent is still working in this folder; edits after this commit are not in it.`) comes from `ReviewInput::SessionWorking(bool)`. The app sends it when the review opens and whenever the value changes: true when `P3-01`'s `FleetSnapshot` has a row for the target's `RowKey` whose `state` is `RowState::Working` or `RowState::NeedsYou` (a running turn); for a `/changes` target without a fleet row, true when the foreground session has a turn in progress (the session reducer of `P1-05`, read through `P1-12`'s app state; check the name in merged code). A target with no session sends false.

Editor life cycle: success closes the editor, forgets the remembered text for this folder and shows the commit notice; failure keeps the editor open with its text; Esc closes it and keeps the text in memory for this folder (for this process only). While a commit runs, `ctrl+s` and `ctrl+d` answer `Wait for commit to finish.`

### 3.7 Push and pull request rules

- Never force. Never push a detached `HEAD`, the repository's default branch, a branch named `main` or `master` (they always count as default branches for this rule), or a branch whose name equals the pull request's base. When the default branch cannot be found, refuse: fail closed (section 5.5). Never merge, never mark a pull request ready, never close one.
- Order of checks for `p`: Branch scope (read-only text, section 3.4), detached `HEAD`, no `origin`, default branch, base branch. For `shift+p`: the same local refusals; then an open pull request already known; then gh readiness; then commits ahead of the base. Local refusals come first so the text does not depend on whether `gh` is installed or signed in.
- **Where the fail-closed guarantee lives.** The core (`can_push`, `can_open_pr`) refuses whatever the listing already knows: detached, no origin, a branch named `main` or `master`, a branch equal to `Listing.default_branch` when that is `Some`, a branch equal to the base. When `Listing.default_branch` is `None` ("not known yet": the listing never runs the network step), the core returns `Ok` and emits `Run(Push)` or `Run(CreatePr)`. The app's `git_ops::run_action` for `Push` and `CreatePr` then resolves the default branch in full (section 5.5, including `ls-remote`) and refuses before spawning any `git push` when the branch is the default, the base, or the default is unknown; the refusal comes back as `ActionDone { result: Err(<refusal text>) }`. So decision 7 ("never ship when the default branch is unknown") is guaranteed by `run_action`, and test 24 proves it with real git (no `push` argument list is ever logged). Test 18's property covers only what the core can know.
- `shift+p` decides from the pull-request status already cached; it does not wait for a refresh. When the cache is stale or not loaded and a pull request already exists, `gh pr create` fails with gh's own message, shown as `gh pr create failed: <last stderr line>`; that is accepted.
- `shift+p` after Enter runs the push first (section 6.4). **A failed or refused push stops the action**: its text is shown (rejected, no origin, a refusal, or git's first error line) and `gh pr create` does not run. (Desktop ignores push errors here, `apps/desktop/electron/git-review-ops.ts:747`; Talaria deliberately does not.)
- Push always names the remote and the ref: `git push --porcelain --set-upstream origin refs/heads/<b>:refs/heads/<b>`. A Talaria tree's branch has no upstream (`P3-03` creates it with `--no-track`), so a bare `git push` would fail or, with some `push.default` settings, target the wrong branch.
- The pull request is always a draft: `gh pr create --draft --base <base> --head <branch> --fill`. The base is the record's `base_ref` without `origin/`, else `origin`'s default branch (section 5.5). Creating one always runs the push first: the push is idempotent (`=` up to date), so Talaria never needs to know whether `origin` already has the branch.
- Commits ahead: `git rev-list --count origin/<base>..HEAD` (G6 e); `origin/<base>` is the ref the pull request is based on, so a stale local `main` does not change the count. Zero gives `No commits between origin/<base> and <b>: commit first.`
- One pull request per branch: when the status query (section 6.3) knows an **open** pull request (draft or ready) for the branch, `P` shows its URL instead of creating another. A merged or closed one does not block a new draft (E16).

### 3.8 Known repositories, and where pull-request labels come from

Talaria keeps no new disk state. It knows a repository (by its main root) when: it is the repository of Talaria's launch folder; it holds the foreground session's folder; `P3-03` launched a tree in it during this process; or it was reviewed during this process. For each known repository it reads `P3-03`'s records (`records_in`), which map `talaria/*` branches to sessions. A row's label is the pull request of the branch mapped to that row: from a record, or from the branch seen when that row was reviewed. Rows with no known branch get no label. This is deliberately narrower than "every session": calling `session.info` for every fleet row to learn its folder would cost one inventory build per row per refresh (H19).

### 3.9 Drafting a message uses the session's own model, never a fallback

`llm.oneshot` is always sent with the reviewed session's `session_id`, so the diff goes to the same provider and model that already wrote the code (H15). Sending the `session_id` is not enough on its own: Hermes falls back to its auxiliary backend when the session has neither a resident agent nor a launch policy (H15). Talaria therefore gates drafting on `session.info` (H19):

- When a review opens for a target with a session, Talaria calls `session.info` once (reusing the reply from section 3.2 step 3 when that step ran) and delivers `ReviewInput::SessionInfo { model, can_draft }` with `can_draft = (!lazy || cwd.is_some()) && model is a non-empty string`. The first two tests are the ones `_session_runtime` makes (`gateway/session_llm_oneshot.py:208-230`). The model test is added because `_session_runtime` also returns no runtime when the launch route resolves to no model and no provider keys (`:219-229`), and a session whose `session.info` reports no model is the visible sign of that case. It is not a perfect sign: `session.info`'s lazy `model` comes from `_lazy_model` (`gateway/session_local.py:350-361`, `policy.current_model`), while the one-shot resolves `policy.effective` (`gateway/run_turn_prepare.py:42-64`, `_resolve_policy_agent_runtime`); verify at the pinned commit before relying on the two agreeing. A route that `session.info` names but that resolves to nothing at call time stays inside the known limit below.
- A `session.info` refused with a 4001 other than `not_found` gives `can_draft` false and keeps the reason: `ctrl+d` then sends nothing and shows `Drafting failed: <reason>`.
- `ctrl+d` with no session, or with `can_draft` false, sends nothing and shows `This session has no model of its own to draft with.` A `session.info` that answers `not_found` gives the "session gone" text.
- A live session is one whose id Talaria knows and for which Hermes has not answered `not_found`. An ended session whose row is still stored qualifies, because `authorize` restores it (H23); UAT-2 drafts for a session that is already `done`.
- The model name in `Drafting a message with <model>…` and in the editor footer is `session.info`'s `model`; when null it reads `the session's model`.
- Known limit, accepted: if a session with no launch policy unloads its agent between the check and the call, Hermes falls back silently, and the `{text}` reply cannot show it. Locally created sessions, including every `P3-03` launch, always have a launch policy (`P3-03` F7), so the gap concerns only sessions created by other surfaces. The journal records it (section 16).

Drafting interactions (section 9.2): while a draft runs, the text area does not take input and `ctrl+s` answers `Wait for drafting to finish.`; Esc abandons the draft (the reply is ignored by sequence number) and leaves the editor open. Definitions: **typed text** is any editor text that differs from the last draft Talaria put into the editor (including text typed into an empty editor and an edited draft); an **unchanged earlier draft** is editor text exactly equal to that last draft. When the editor holds typed text, the first `ctrl+d` asks `Replace your message with a draft? Press ctrl+d again; any other key cancels.`; an empty editor or an unchanged earlier draft drafts at once. `avoid` is the editor text at the moment of the press that sends the request. When the new draft, trimmed, equals `avoid` trimmed, the editor is left as it was and `The model returned the same message.` is shown (Hermes asks for a different message but cannot enforce it).

`-32601` (method not found) shows `This Hermes does not offer message drafting.` once, on that press, and then hides the draft key and its footer hint for the rest of the process. `runtime_draining` shows `Hermes is shutting down; try drafting again after it restarts.`

### 3.10 `gh` is slow and rate-limited: bounded polling

Pull-request status is fetched only while there is demand: the fleet view is open, a review screen is open, or the status line's `PullRequest` segment has a target (the foreground folder is in a known repository and its branch is mapped). On a new demand, once at once; then at most once every 60 seconds per repository; and at once after a push or a pull-request action. At most one `gh` process runs at a time per repository: a refresh's GraphQL requests (50 branches each, section 6.3) run one after another, and a refresh due while one runs is skipped. A failed refresh keeps the previous labels. A label is **stale** when the last successful refresh that produced it finished more than 5 minutes ago (by the service's clock); a stale label is drawn `Muted`. The pull request's own update time is not used.

The status-line segment's branch: at each refresh of the foreground folder's repository (so at most once every 60 seconds, on a task, never per tick or per frame), `PrStatusService` runs `git branch --show-current` in the foreground folder through `run_read_only`. The segment shows a label only when that branch is mapped (a record, or a branch reviewed in this process) and a pull request is known for it. `session.info`'s `branch` is not polled for this.

`PrStatusService` reads time only through the clock it is given (`new(gh, git, clock, notify)`) and starts due refreshes only in `tick()`, which `P1-12`'s once-per-second timer calls. Test 27 passes a fake clock and calls `tick()` directly.

### 3.11 Untrusted content

Everything shown comes from files an agent wrote: file names, diffs, commit subjects, gh's error text. All of it passes `P1-06`'s `history::sanitize` before drawing. Every diff-rendering git call carries `--no-ext-diff --no-textconv --no-color` (H7). Paths reach git only after `--`, so a file named `-rf` is never read as an option. Tracked paths are `:(literal)<path>` pathspecs, so `*` is never a pattern; the untracked `--no-index` diff takes plain file names instead, because no-index does not read pathspecs (G6 a). Diffs of files over 8 MiB (the file on disk, or `git cat-file -s HEAD:<path>` for a deleted file) are not run, because `P3-03`'s `GitRunner` reads all of a command's output into memory. Commit hooks still run (decision 3.6): they live in the main repository's `.git/hooks` or a configured `core.hooksPath`, which a session's agent could have changed; the commit editor therefore shows `Hooks: <n> active` when any of `pre-commit`, `prepare-commit-msg`, `commit-msg`, `post-commit` is executable in the effective hooks folder, so a surprise is visible before confirming.

Repository-configured programs. A session's agent can write the repository's `.git/config` (linked worktrees share it), and an agent in a sandboxed terminal backend may reach the folder but not the host; anything Talaria's own git runs on the host from that config escapes the sandbox. Hermes's own plumbing therefore disables `core.fsmonitor`, `core.hooksPath`, `diff.external` and named clean, smudge and process filters (`hermes_cli/_subprocess_compat.py:284-303`, `:492-522`). Talaria's choices, by program:

| Program | Talaria | Why |
|---|---|---|
| Diff drivers (`diff.<name>.command`, `.textconv`) | disabled: `--no-ext-diff --no-textconv` on every `git diff`, numstat included (observed on git 2.55.0: `git diff --numstat` runs a `textconv` driver) | no function lost |
| `core.fsmonitor` | disabled: `-c core.fsmonitor=false` before the subcommand on every git call Talaria makes (observed: `git status` runs a configured fsmonitor command; with the override it does not) | no function lost (fsmonitor only speeds up status) |
| Commit hooks | run, with the `Hooks: <n> active` line | settled decision 6 |
| Clean, smudge and process filters (Git LFS uses them) | run on `status`, `add`, `checkout` and `commit` | settled decision 1 keeps the operator's git configuration; disabling them breaks Git LFS. Recorded as an accepted risk in `DECISIONS.md` and as an operator question on the issue |

Environment. The architecture's security rule gives "the status-line command and any user scripts" an allow-listed environment. Git hooks, filters and `gh` are exempt: they are the operator's own tools and need the operator's agent sockets, signing agent and credential variables, exactly as in a shell (settled decisions 1 and 6). Talaria passes the process environment plus the fixed keys of `review_env` (section 5) or `gh_env` (section 6.1) and nothing else. `DECISIONS.md` records the exemption.

## 5. Git commands

All run through `GitRunner::run` (reads through `run_read_only`) with `cwd` set to the work tree root from `git rev-parse --show-toplevel`, and `review_env` (P3-03's `git_env` plus `GIT_PAGER=cat`, `PAGER=cat`, `GIT_EDITOR=true`; `GIT_OPTIONAL_LOCKS=0` on reads only). Every argument list starts with `-c core.fsmonitor=false` before the subcommand (section 3.11), and every `git diff`, numstat included, carries `--no-ext-diff --no-textconv` (`--no-color` too where it prints a patch). `<p>` is always passed as `:(literal)<p>` after `--`, except for the untracked `--no-index` diff (section 5.3). Timeouts: reads 10 s; `add`, `reset`, `checkout`, `clean` 30 s; `commit` 120 s (hooks); `push` 60 s; fetch is not used by this unit.

### 5.1 Listing, Uncommitted scope

1. `git rev-parse --show-toplevel` (the work tree root; the folder may be a subfolder).
2. `git status --porcelain=v2 -z --branch --untracked-files=normal` gives `BranchHead` and the rows (`1`, `2`, `u`, `?`; `!` never requested).
3. `git diff --numstat -z --no-renames --no-ext-diff --no-textconv HEAD` would mix staged and unstaged; instead two calls, `git diff --cached --numstat -z --no-ext-diff --no-textconv` and `git diff --numstat -z --no-ext-diff --no-textconv`, merged per path (Desktop's rule, H4). On an unborn branch (`# branch.oid (initial)`), the staged call uses `--cached` against the empty tree, which git does by default.
4. Untracked files: `count_lines` on the file's bytes when it is a regular file of at most 1 MiB; otherwise `None` (drawn as `+?`). An untracked folder (path ends with `/`) is `is_dir: true`, counts `None`.
5. Sort by path (byte order), cap at `REVIEW_FILE_CAP`; `total` keeps the full count.
6. `default_branch`: the local steps of section 5.5 only (`origin/HEAD`, a cached `ls-remote` answer, the record's base), else `None`. The listing never runs the network step, so it stays inside the 300 ms budget.
7. `hooks`: the effective hooks folder is `git rev-parse --git-path hooks`; count the executable files named `pre-commit`, `prepare-commit-msg`, `commit-msg`, `post-commit`.
8. `has_origin`: `git remote get-url origin` exits 0.
9. Status letter per row (Desktop's rule, `apps/desktop/electron/git-review-ops.ts:273-284`): untracked `?` wins; a conflicted (`u`) row is `U`; otherwise the index code of the `XY` pair unless it is `.`, else the work-tree code. `staged` is true when the index code is not `.`; `unstaged` when the work-tree code is not `.` or the row is untracked.

### 5.2 Listing, Branch scope

Base: record `base_commit`, else the first of `origin/HEAD`, `origin/main`, `origin/master`, `main`, `master` for which `git merge-base HEAD <ref>` succeeds (H5; a ref that exists but shares no history with `HEAD` is skipped). No base: the listing is empty with `No base to compare with: origin has no default branch here.` This base is only for showing committed work; the push and pull-request rules use section 5.5.
Files: `git diff --name-status -z --no-ext-diff --no-textconv -M <base>...HEAD` and `git diff --numstat -z --no-ext-diff --no-textconv -M <base>...HEAD`. `staged` and `unstaged` are false.

### 5.3 One file's diff

| Scope and row | Command |
|---|---|
| Uncommitted, tracked | `git diff --no-ext-diff --no-textconv --no-color HEAD -- :(literal)<p>` (staged and unstaged together); unborn branch: `git diff --cached ...` then `git diff ...` concatenated |
| Uncommitted, untracked file | `git diff --no-ext-diff --no-textconv --no-color --no-index -- /dev/null <p>` with `<p>` the plain repository-relative path, never `:(literal)` (G6 a). Exit 1 with empty standard error is success; any standard-error text, or an exit status above 1, is a failure showing git's first error line |
| Uncommitted, untracked folder | no diff; the panel says `Untracked folder: stage it to see its files.` |
| Renamed | the diff of the new path with `-M`, so the rename header shows |
| Branch | `git diff --no-ext-diff --no-textconv --no-color -M <base>...HEAD -- :(literal)<p>` |

Before running a diff, a file over 8 MiB (`DIFF_MAX_FILE_BYTES`; the file on disk, or `git cat-file -s HEAD:<p>` when deleted) shows `File too large to show here (<size>). Run git diff in a shell.` and no diff runs. The text goes to `P2-01`'s `parse_diff` and `diff_lines`. Over `DIFF_MAX_LINES` lines, the first 20,000 are kept and the panel ends with `Diff cut at 20,000 lines; <n> more. Run git diff in a shell for the rest.` Binary files show git's own `Binary files ... differ` line.

### 5.4 Actions

| Action | Commands | Success notice |
|---|---|---|
| Stage one (`space` on a row with no staged change) | `git add -- :(literal)<p>` (a rename: both paths) | `Staged <p>.` |
| Stage all | `git add -A -- ':(top)' ':(top,exclude).worktrees/'` (G6 c) | `Staged <n> files.` |
| Unstage one (`space` on a row with any staged change, `●` or `◐`) | `git reset -q HEAD -- :(literal)<p>` (a rename: both paths); unborn branch: `git rm -q --cached -- :(literal)<p>` | `Unstaged <p>.` |
| Unstage all | `git reset -q HEAD`; unborn branch: `git rm -r -q --cached -- .` | `Unstaged <n> files.` |
| Discard tracked | `git checkout HEAD -- :(literal)<p>` | `Discarded changes to <p>.` |
| Discard staged new file (in the index, not in `HEAD`) or copy | `git rm -q -f -- :(literal)<p>` | `Discarded changes to <p>.` |
| Discard staged rename `<o> → <p>` | `git reset -q HEAD -- :(literal)<p> :(literal)<o>`, then `git checkout HEAD -- :(literal)<o>`, then `git clean -f -- :(literal)<p>` (G6 d); a failing step stops the sequence and shows its error | `Discarded the rename <o> → <p>.` |
| Discard untracked | `git clean -f -- :(literal)<p>`, `-d` added for a folder row (trailing `/` kept, G6 b) | `Deleted untracked <p>.` |
| Commit | when `stage_all`: stage all as above; then `git commit -m <message>`; then `git rev-parse --short HEAD` | `Committed <sha> on <branch>: <subject>` |
| Push | `git push --porcelain --set-upstream origin refs/heads/<b>:refs/heads/<b>` | `Pushed <b> to origin.` (`Already up to date on origin.` for `=`) |

After every action the list is reloaded; the cursor stays on the same path, or the next row when the path left the list. Stage one and discard refuse a row whose path is `.worktrees/` or under it (section 3.6).

### 5.5 The default branch (push and pull-request guard)

1. `git symbolic-ref --quiet --short refs/remotes/origin/HEAD` prints `origin/<b>`; remove `origin/` (output without that prefix counts as unset). This is `P3-03`'s section 7.4 step 1.
2. When unset: `git ls-remote --symref origin HEAD` through `run_read_only` with `P3-03`'s `git_prefix_args` (30 s); the line `ref: refs/heads/<b>\tHEAD` gives `<b>` (G5). The answer, found or not, is cached per main root for 10 minutes; `r` clears it.
3. Else the record's `base_ref` without `origin/`.
4. Else unknown: push and pull request are refused with `Talaria cannot tell origin's default branch, so it will not push.`

The branch is refused when it equals the resolved default branch or is named `main` or `master` (`DefaultBranch`), or equals the pull request's base (`BaseBranch`). `run_action(Push)` and `run_action(CreatePr)` run steps 1 to 4 and these comparisons before spawning any `git push`.

The commit message: the editor text with trailing whitespace removed from each line and leading and trailing blank lines removed; it must keep at least one non-blank character. It is passed as one `-m` argument with no `--cleanup` option, so git's own cleanup applies. With `-m` and no `commit.cleanup` setting that is the `whitespace` mode: it strips trailing spaces, collapses runs of blank lines into one and keeps lines starting with `#` (observed on git 2.55.0: `subj\n\n\n\nbody` is stored as `subj\n\nbody`). An operator's `commit.cleanup` setting applies as in their shell. Talaria adds nothing; test 22 runs with isolated configuration and expects the text after the `whitespace` rule.

## 6. GitHub command line (`gh`)

### 6.1 How gh is run

`GhRunner::run` spawns `gh` (from `PATH`, or `TALARIA_GH_BIN` when set, which tests use) with standard input closed, `cwd` set to the main root, a 30-second timeout (60 seconds for `pr create`), and `gh_env`: the process environment plus `GH_PROMPT_DISABLED=1`, `GH_NO_UPDATE_NOTIFIER=1`, `NO_COLOR=1`, `CLICOLOR=0`, `GIT_TERMINAL_PROMPT=0`. That list is exhaustive: nothing else is added or removed. Error text shown is the last non-empty line of standard error, sanitised, cut to 200 characters. At most one `gh` process runs at a time per main root (a per-repository async lock in `GhRunner` callers: `PrStatusService`, readiness, create, view).

### 6.2 Readiness

1. `gh` not found: `GhReady::NotFound`.
2. `gh auth status` non-zero: `NotSignedIn(<last stderr line>)`.
3. `gh repo view --json nameWithOwner -q .nameWithOwner` non-zero or not `owner/name`: `NotGitHub(<reason>)`.
4. Else `Ready { repo }`. Cached per repository for 10 minutes; `r` in the review screen clears it.

### 6.3 Pull-request status query

```text
gh api graphql -f query=<pr_query(owner, name, branches)>
```

`pr_query` builds, for branch `i`:

```graphql
b<i>: pullRequests(headRefName: "<branch, JSON-escaped>", first: 5, orderBy: {field: CREATED_AT, direction: DESC}) {
  nodes { number state isDraft isCrossRepository url headRefName reviewDecision
          commits(last: 1) { nodes { commit { statusCheckRollup { state } } } } } }
```

inside `query { repository(owner: "<owner>", name: "<name>") { ... } }`. Branches are de-duplicated, capped at 300, sent 50 per request (H12); the requests of one refresh run one after another, never in parallel. `parse_pr_reply` takes, per alias, the first node with `isCrossRepository == false`, whatever its state (nodes come newest first, so a newer merged pull request wins over an older open one); `state` `OPEN`, `CLOSED`, `MERGED`; check state `SUCCESS` gives `Passing`, `FAILURE` or `ERROR` `Failing`, `PENDING` or `EXPECTED` `Pending`, null or missing `None`; `reviewDecision` maps one to one. A chunk that fails or does not parse drops its branches and keeps the rest (Desktop's rule). Field names are G1: re-record before relying on them.

### 6.4 Create

The push of section 5.4 runs first, every time (with the full default-branch check of section 5.5). If the push is refused or fails, its text is shown and the action ends there: no `gh pr create` runs (section 3.7). Then `gh pr create --draft --base <base> --head <branch> --fill`. Success: the URL is the last non-empty stdout line that starts with `https://`; no such line is a failure `gh pr create printed no URL.`. Failure: `gh pr create failed: <last stderr line>`.

### 6.5 Open in the browser

`gh pr view <number> --web`, for the open, merged or closed pull request known for the selected review's branch. When none is known, nothing runs and the notice reads `No pull request is known for <b> yet.` Failure text: `Could not open the browser: <last stderr line>` (over SSH there is often no browser; the URL is also shown in the header, so the terminal's own link handling works).

## 7. Hermes calls

### 7.1 `llm.oneshot` (drafting a commit message)

Sent only when the target has a session and `can_draft` is true (section 3.9). Sent on a short-lived link opened with `P3-03`'s `LaunchLink::open(home, foreground_profile)` (the Hermes home the app gives `LaunchService::new`), closed after the reply; `profile` is added only when `LaunchConn::routed_profile` says the row's profile differs from the link's. Client timeout 90 seconds (Hermes's model timeout is 60, H17).

The `diff` variable: the names of up to 80 untracked files (one per line, under a line `Untracked files:`), then a blank line, then what will be committed: the staged diff (`git diff --cached` with the section 5 flags) when anything is staged, else `git diff HEAD`; on an unborn branch, `git diff --cached` (against the empty tree). The whole string is cut to `DRAFT_DIFF_MAX_CHARS` (12,000 Unicode scalar values), because Hermes cuts it there anyway (H17) and the rest would cross the socket unused; the names come first so the cut never drops them. Desktop sends up to 120,000 characters; Talaria deliberately does not. `recent_commits` is `git log -n 10 --pretty=format:%s`, or empty on an unborn branch (the command fails there).

```json
{"jsonrpc":"2.0","id":7,"method":"llm.oneshot","params":{
  "session_id":"<session id>","template":"commit_message","temperature":0.8,
  "variables":{"diff":"<untracked names, then what will be committed; at most 12,000 characters in all>",
               "recent_commits":"<git log -n 10 --pretty=format:%s>","avoid":"<current editor text or empty>"}}}
```

Reply: `{"jsonrpc":"2.0","id":7,"result":{"text":"feat(core): ..."}}`. The text is trimmed and replaces the editor text; an empty text is `DraftError::Failed("the model returned nothing")`.

Errors: 4001 `not_found` gives `SessionGone`; 4001 `oneshot_busy` gives `Busy`; 4001 `runtime_draining` gives `Draining`; -32601 gives `Unsupported` (the draft key is then hidden for the rest of the process); timeout or dropped connection gives `NoReply`. Everything else gives `Failed(<text>)`: 4001 `permission_denied`, `profile_mismatch` or `invalid_params` (the reason, plus `field` when present), 5030 (its message), and any other code (its message); the text is sanitised and cut to 200 characters. Never `unattended`, never `finite`: those are `prompt.submit` keys and this unit never submits a prompt.

### 7.2 `session.info` (finding a row's folder)

Same link rules. `{"method":"session.info","params":{"session_id":"<id>"}}` plus `"profile"` when routed (removed by Hermes before its exact-key check, H19). Talaria reads `result.cwd`, `result.branch` and `result.model` (each string or null; null and absent mean the same; an empty `branch` means none) and `result.lazy` (boolean; a missing `lazy` counts as `true`, which fails closed). Called at most once per review opening: for locating (section 3.2 step 3) and for the draft gate (section 3.9), one reply serves both. 10-second timeout. `not_found` gives `This session no longer exists on the gateway.` Any other 4001 refusal (for example `permission_denied` or `profile_mismatch`) is `SessionInfoError::Refused(<reason>)`: locating continues as if no folder were reported (section 3.2) and drafting is off for that review (section 3.9).

## 8. The screen

The review is drawn in `P1-06`'s overlay. Opened from the fleet view it replaces the fleet list inside the same overlay, and Esc returns to the fleet list with its cursor unchanged. Opened with `/changes` it opens the overlay and Esc closes it. Nothing is written to scrollback.

Rows from the top:

1. Header: `Review · <title> · <branch or "detached at <sha>"> · <n> files · +<added> −<removed>`; right-aligned: `↑<ahead> ↓<behind>` against the upstream, or `not on origin`; then the pull-request label (section 9.3) when known.
2. Scope line: `Uncommitted changes` or `Branch changes since <base short> (<base ref>)`, then ` · read-only` in Branch scope, then ` · review: approved | changes requested | review required` when known.
3. The file list: one row per file: cursor (`›` or space), status letter (`M`, `A`, `D`, `R`, `C`, `T`, `?`, `U`), staged mark (`●` staged, `◐` staged and changed again, space otherwise), path (renames `old → new`), counts `+<a> −<r>` right-aligned (`+?` when unknown, `bin` for binary). Folders end with `/`.
4. `── <path> ──` and the diff panel: the lower half of the screen when the screen has at least 24 rows. Below 24 rows the list fills the screen; `enter` (`review_show_diff`) shows the selected file's diff in its place (focus `DiffOnly`) and Esc returns to the list.
5. The notice line.
6. The footer: bound key hints for the focus (section 9).

Before the first listing arrives, rows 3 and 4 show `Loading changes…`.

Commit focus replaces rows 3 and 4 with the editor: a header line (`Commit <k> staged files on <branch>` or `Nothing is staged: this commit will include all <n> changed files on <branch>.`), optional warning lines (`The agent is still working in this folder; edits after this commit are not in it.`, `Hooks: <n> active (they run as in your shell).`), then the message text area (at least 5 rows), then the footer `ctrl+s commit · ctrl+d draft with <model> · esc back` (`<model>` from `session.info`, else `the session's model`; the draft hint is absent when drafting is not possible).

Too small (below 60 columns or 12 rows): `Window too small for the review. Esc goes back.` (Esc returns to the fleet list or closes the overlay, whichever opened it.)

Empty states: no changes in Uncommitted: `No uncommitted changes in <folder>.`; Branch with no commits: `No commits on <branch> since <base short>.`

### 9.2 One mutation at a time

One at a time means one per Talaria process: `ReviewService` holds a single mutation slot, shared by every review opened in the process. While a stage, unstage, discard, commit, push or pull-request action runs, the other mutation keys answer `Wait for <action> to finish.` (in the editor, `ctrl+s` and `ctrl+d` too); movement, scope, refresh of the diff and Esc keep working. Drafting runs separately: while it runs, typing and `ctrl+s` answer `Wait for drafting to finish.`, and Esc abandons the draft (its reply is ignored by sequence number) without leaving the editor.

Esc while a mutation runs unwinds as usual (it may close the screen) but never cancels the running git or gh process: killing a commit or a push half-way is worse than letting it finish. The action runs to its end; its success or failure notice goes to `P1-12`'s notice path (the fleet view's notice line when the fleet view is open, else the main notice line), and the slot frees. Reopening a review meanwhile shows the busy text for mutation keys.

## 11. Stub and fixture rules

- **Git** is never stubbed: tests use real `git` in temporary folders. App tests use `P3-03`'s `crates/talaria-app/tests/support/git_fixture.rs` (a bare `origin.git`, a clone, commits with `-c user.name=fixture -c user.email=fixture@example.invalid`, `HOME` and `GIT_CONFIG_GLOBAL` pointing inside the temporary folder). - **Dev-dependencies.** `proptest` (talaria-core), `vt100` (talaria-tui, `0.16.2` as `P2-02` pins it) and `tempfile` (talaria-core, talaria-app) are added as dev-dependencies of a crate that does not already declare them, at the version an earlier unit already pinned in the workspace (check `Cargo.toml` in merged code; never a new version). No new normal dependency; `async-trait` is not used (section 4 uses a boxed future).
- **gh replies: the file format.** Each reply is one file `fixtures/gh/<name>.json`: `{"args_prefix": ["auth", "status"], "exit": 0, "stdout": "...", "stderr": "..."}`. `args_prefix` is the start of gh's argument list that the reply answers (for `api graphql` the query text is not part of the prefix). Names: `auth-status-signed-in`, `auth-status-signed-out`, `repo-view-github`, `repo-view-not-github`, `pr-create`, `api-graphql-status`.
- **gh stub.** A stub executable, written by the test into its temporary folder, is given an ordered list of reply files (through the environment of the stub process only). It appends its argument list to a log file in the temporary folder and answers with the first reply whose `args_prefix` starts its argument list; with no match it exits 127 and prints `stub: no recorded reply for <args>`, which fails the test. Every reply file is a recording from the real `gh` (live test L3); no reply is written by hand.
- **Argument-logging stub (no reply).** A test that asserts only an argument list or a timing, and never parses gh's output, may use a stub that logs its arguments and exits 0 with empty output, optionally after a fixed sleep. This invents no interface, because nothing reads its output. Allowed for test 42 (sleeps 2 s), test 49 (`pr view <n> --web`) and the closed-standard-input and timeout halves of test 25. Any test that parses a reply uses a recorded one.
- **No test runs the operator's `gh`.** Every app test builds `GhRunner::with_binary(<stub, or a path that does not exist inside the temporary folder>)` and passes it to `ReviewService::new` and `PrStatusService::new`; `GhRunner::from_env` is never called in a test, so a review opening (which refreshes pull-request status) never reaches a real `gh`. The only exception is live test L3 (test 41).
- **Recording and redaction (test 41).** Test 41 drives the real `gh` and `git` through `std::process::Command` with literal argument lists copied from section 6 (the GraphQL query is the section 6.3 text for its one branch, written out in the test), so it needs no Talaria code and can run before the implementation exists. When `TALARIA_GH_RECORD_DIR` names a folder, it writes each reply there in the format above after a fixed substitution list, applied in code in this order: the repository's `owner/name` becomes `fixture-owner/fixture-repo`; the owner alone becomes `fixture-owner`; the signed-in login (from `gh api user -q .login`) becomes `fixture-user`; the temporary folder's path becomes `<tmp>`. Pull-request numbers and the branch's 8-hex suffix are kept. The operator reviews the files, copies them into `fixtures/gh/` and commits them; test 50 then checks them.
- **Allowlist check (test 50, `review_gh.rs::recordings_are_public_safe`).** For every file under `fixtures/gh/` and every `fixtures/frames/review-*.jsonl`: the file parses (reply format above, or one JSON frame per line); every `https://` URL starts with `https://github.com/fixture-owner/fixture-repo`; every `nameWithOwner` value and every `repository(owner:, name:)` pair is `fixture-owner/fixture-repo`; every login in `auth status` output (`account <x>`) is `fixture-user`; every `profile` value is `default` or `fixture`; every `cwd` value is `<tmp>`; and every token that starts with `/` followed by a letter (after start of text, whitespace, a quote, `=`, `(` or `:`) is exactly `/dev/null`. Anything else fails with the file and line. The operator's extra check `git grep -n "$(gh api user -q .login)" fixtures/gh` (prints nothing) stays.
- **Red runs and recordings.** The red run never records a missing recording as a failure reason. Order: (1) the test author writes every test, including test 41; (2) the red run of every test that needs no recording; (3) the operator runs test 41 with `TALARIA_GH_RECORD_DIR` set and commits the redacted replies; (4) the red run of tests 16, 25, 26, 27 and 50, which now fail on the stubs (`todo!()` or `stub`), not on the recording. The developer may build everything else meanwhile, but writes `pr.rs`'s `parse_pr_reply` and `gh.rs`'s `readiness`, `pr_statuses` and `create_draft` only after step 4. A test that still finds no recording fails `BLOCKED: fixtures/gh/<file> not recorded` and never returns early, so cargo cannot count it as passed; this guards the merge, not the red run.
- **Hermes** calls go to `P1-09`'s mock gateway (`crates/talaria-app/tests/support/mock_gateway.rs`, as extended by `P3-03`): `llm.oneshot` follows H14 and H16 (closed keys, `template` known, reply `{text}` from `fixtures/frames/review-oneshot.jsonl`, switches for 4001 `not_found`, `oneshot_busy`, `runtime_draining`, `permission_denied`, 5030, -32601 and no reply); the mock fails the test if `session_id` is absent. `session.info` follows H19 (exactly `session_id` after removing `profile`; reply from `fixtures/frames/review-session-info.jsonl` with `cwd` stored as `<tmp>` and replaced by the test's temporary folder at run time).

## 16. Journal entries (same pull request)

Each `LEARNINGS.md` entry is dated and has the three labelled parts the repository's journal rule requires: **Evidence**, **Mechanism**, **Generalizable rule**.

- `LEARNINGS.md`, "Hermes has no git remote procedure call". Evidence: H1, H2 (`apps/desktop/electron/git-ipc.ts:67-105`, `hermes_cli/web_routers/git.py:125-197`) and this unit's pull request. Mechanism: Desktop runs git in its Electron main process and offers REST routes only for remote gateways, so a local client must run git itself. Generalizable rule: when Hermes's own client does machine work outside the gateway, Talaria does it locally too.
- `LEARNINGS.md`, "A one-shot needs the session's own route". Evidence: H15, H19 (`gateway/session_llm_oneshot.py:208-230`, `gateway/session_local.py:406-419`). Mechanism: `llm.oneshot` without `session_id`, or for a session with neither a resident agent nor a launch policy, or whose route resolves to nothing, uses the auxiliary backend; `session.info`'s `lazy`, `cwd` and `model` show which case applies. Generalizable rule: bind a one-shot to the session whose data it carries, and check that the session has its own route first.
- `LEARNINGS.md`, "An empty clone has no origin/HEAD". Evidence: G5 and test 24. Mechanism: cloning an empty repository leaves `refs/remotes/origin/HEAD` unset, so a default-branch guard built only on it passes everything. Generalizable rule: a safety guard that cannot find its reference fails closed.
- `LEARNINGS.md`, "numstat runs textconv drivers". Evidence: test 20 (observed on git 2.55.0). Mechanism: `git diff --numstat` computes a diff and so runs a configured `textconv` program; only `--no-textconv` stops it. Generalizable rule: put `--no-ext-diff --no-textconv` on every `git diff`, not only on the ones that print a patch.
- `DECISIONS.md`: `/changes` and `v` (Hermes owns `/review` and `/diff`); draft-only pull requests; no discard-all; Branch scope read-only for every action; filter drivers and hooks run with the operator's configuration (accepted risk, section 3.11) and are exempt, with `gh`, from the allow-listed environment; revisit when the operator asks for them.
