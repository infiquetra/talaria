## 1. What this unit adds, in one paragraph

Hermes decides whether a dangerous shell command needs the developer's approval. Two separate settings feed that decision: the profile's approval mode (`manual`, `smart` or `off`, saved in the profile's configuration and shared by every session of that profile) and a per-session bypass (Hermes calls it `yolo`) that turns approvals off for one session only. Talaria today shows neither. This unit shows the effective setting for the session in front of the developer as one status-line segment, lets Shift+Tab switch this session's bypass on and off (the same thing Hermes's own terminal UI does with Shift+Tab), adds `/permissions` to show both settings and to change the profile's mode with its scope said out loud, and adds `/cd <folder>` to move the session to another working folder through the revision-fenced `session.mutate` operation `workspace`. Hermes does all of the work; Talaria sends exactly the documented requests, reports every outcome in plain words, and never guesses a setting it has not read.

### 2.6 How Hermes's own clients present it

- **Hermes's terminal UI.** Shift+Tab sends `config.set {key: "yolo", session_id}` with no value (a toggle), skipped while a completion menu is open; without a session it prints "yolo needs an active session"; the reply prints `yolo on` or `yolo off`. The source comment says "shift-tab flips yolo without spending a turn (claude-code parity)". `/yolo` sends the same request. The terminal UI does not show the bypass in its status bar. ([`ui-tui/src/app/useInputHandlers.ts` lines 834 to 853](https://github.com/NousResearch/hermes-agent/blob/v0.22.4/ui-tui/src/app/useInputHandlers.ts#L834-L853); [`ui-tui/src/app/slash/commands/session.ts` lines 650 to 662](https://github.com/NousResearch/hermes-agent/blob/v0.22.4/ui-tui/src/app/slash/commands/session.ts#L650-L662).)
- **Hermes Desktop.** The approval menu (Desktop catalogue feature F14) reads and writes `approvals.mode` with `config.get` and `config.set`, naming the profile. It shows the new mode at once, keeps a per-profile counter so an older reply never overwrites a newer choice, and goes back to the last confirmed mode when the write fails; with nothing read yet it displays `smart`. ([`apps/desktop/src/store/approval-mode.ts` lines 16 to 26, 43 to 45, 62 to 113](https://github.com/NousResearch/hermes-agent/blob/v0.22.4/apps/desktop/src/store/approval-mode.ts#L62-L113).) The working-folder change (F17) is H27.
- **Claude Code** ([research u12](../research/u12-claude-code-parity.json), entries `int.perm-modes`, `int.accept-edits`, `int.plan-mode`, `/cd`): Shift+Tab cycles permission modes (default, accept edits, plan, auto, and others); `/cd` moves the session to a new working directory and keeps the conversation, with directory suggestions on Tab. Hermes v0.22.4 has no accept-edits or plan permission mode and no per-session `manual`/`smart` choice, so Talaria's Shift+Tab can only switch the bypass (section 10).

## 4. Design

### 4.1 Settled decisions and why

These numbers are the issue's Intent numbers; every "decision N" in this document means the same decision as in the issue.

1. **Hermes holds both settings and the folder; Talaria reads them and shows only confirmed values.** No Talaria file stores an approval setting or a folder. A value is shown only while Hermes's last answer for it was a success: no optimistic display, and no default standing in for an unread value. The indicator is a safety signal, so it never claims a state Hermes has not confirmed: when a read fails (even after an earlier success), or a write's or a Hermes command's outcome cannot be confirmed, the segment says `unknown`; while the first reads are in flight it stays hidden; it never says `manual` or `smart` unless both the mode and "bypass off" are confirmed. A refused or not-sent write keeps the last confirmed value, because nothing changed. Rejected: caching the mode across launches (stale after another client's change, H17); keeping the last value after a failed re-read (it would show a state Hermes just failed to confirm, and P11 says the status line shows `unknown`).
2. **Shift+Tab switches this session's bypass only. This departs from the roadmap row,** which says the key cycles the approval mode (`manual`, `smart`, `off`) and lists `config.set` `approvals.mode`. Reasons: the profile mode is shared by every session of the profile, background ones included (H5), so one stray key press could silence approvals for unattended work; Hermes's own terminal UI binds the same key to the same session toggle (2.6). Rejected: cycling the profile (shared blast radius); cycling Claude Code's modes (Hermes has no equivalent, section 10). **Provisional until the operator answers question 1**; the row's other demand (say whether a change applies to the session or the profile) is kept by every notice.
3. **The profile mode changes only through `/permissions manual|smart|off`,** which names the profile and the scope in its notice, and asks for a second identical command within 30 seconds before turning approvals `off` for the whole profile. It works with no session open (H7).
4. **`/permissions`, not `/approvals`.** Hermes already has `/approvals` (H13); `P2-03` lets a Talaria command shadow a Hermes command of the same name, and Hermes's own `/approvals` should stay reachable as a pass-through (`P2-15` displays it). Operator question 2 may choose `/approvals` instead.
5. **Explicit values only, the latest intent wins.** Talaria sends `value: "1"` or `"0"` for `yolo`, never an absent value (an absent value toggles, H11, so a retried request would undo itself) and never `scope` (H8). While a bypass write is in flight, further presses only change the wanted state; when the reply arrives, Talaria sends one more write if the wanted state differs (Desktop solves the same race with a revision counter, 2.6). Writes are sent even when the last reading already matches, because that reading may be stale (H17) and writing the same value is harmless.
6. **The bypass is read only through `config.get yolo`.** The snapshot's and `session.info`'s `yolo` report the in-memory flag only and can say `false` after a gateway restart while the stored bypass is on (H12b).
7. **`/cd` resolves `~` and relative paths itself,** against the session's folder, because Hermes resolves them against the gateway process's own folder (H22). It checks the folder exists before sending (the gateway is on the same machine: tickets are loopback-only), and lets Hermes make the final decision.
8. **`/cd` is refused locally while a turn runs,** with the reason, as Desktop disables its item (H27). Hermes refuses it anyway (H21). Rejected: holding the move until the turn ends (a hidden queue the developer cannot see or cancel). Operator question 3 may choose to hold it.
9. **Pure core.** Every decision lives in `talaria-core` (no I/O, no terminal library); `talaria-app` executes the effects; `talaria-tui` draws and sanitises.
10. **One fenced-mutation helper, a separate ledger instance.** `/cd` uses `P2-06`'s `MutationLedger` and `MutationClient` types (or those of the owner the `PH2B` planner names). The `P2-06` issue assigns the helper to itself, beyond its roadmap row. This unit never builds its own request type. It holds its own ledger instance, created as `MutationLedger::new(&format!("{launch_id}-cd"))`, so its request ids (`<launch_id>-cd-m<n>`) never collide with the model picker's (`<launch_id>-m<n>`, H28). `P1-12`'s launch id is 16 lower-case hex characters from `getrandom`, made once per launch (its `new_launch_id`), so ids from different launches do not repeat in practice.
11. **Shift+Tab acts only in the composer context** (section 4.7).
12. **The session bypass has one owner.** `P2-15` also reads `yolo` and draws a `⚠ YOLO` row. Proposed (the `PH2B` planner confirms before either unit starts and edits both bodies): this unit owns reading and writing the bypass, and exposes `PermissionsState::session_off()`; `P2-15`'s row is drawn from that value instead of its own `config.get yolo`; the status segment (the effective approval state) and `P2-15`'s row (what the bypass does) may both show, which amends `P2-15`'s decision 9. Whichever unit merges second does the wiring in `app.rs`.

**Operator questions.** The `PH2B` planner asks all five before the build. Question 1 (decision 2) must be answered first; an answer against decision 2 is a stop condition. Questions 2 to 5 do not block the start: while unanswered, the drafted decision is the plan. An answer that differs from the draft and arrives before the start is applied by the planner as an edit to the issue and this document; one that arrives after the build started is a stop condition.

### 4.3 States

**Permissions state** (one foreground session at a time):

```text
profile_name: String              (from new(); never changes)
session_id: Option<String>
profile: Reading<ApprovalMode>    session_off: Reading<bool>
next_gen: u64                     (one counter for every request; never reset, not even on a session change)
profile_read_gen, session_read_gen: Option<u64>   (the read in flight of each kind, if any)
profile_floor, session_floor: u64 (a reply whose generation is below the floor is stale)
reread_profile, reread_session: bool  (a trigger arrived while a read of that kind was in flight)
set_in_flight: Option<(u64, bool)>    (generation and value of the bypass write in flight)
wanted: Option<bool>              (the latest intended bypass while set_in_flight)
profile_set_in_flight: Option<(u64, ApprovalMode)>
off_confirm_until: Option<Instant>
read_failure_noticed: bool        (P11 already shown; see rule 4)
profile_unknown, session_unknown: bool  (an outcome that may have changed that setting could not be
                                  confirmed; each is cleared only by the next successful read of its kind)
```

Rules, in the order `update` applies them:

1. `ConnectionOpened` (first connection and every reconnect): clear `off_confirm_until`; read the profile mode (rule 2); when a session is open, read the bypass too. `SessionOpened { session_id }`: set `session_id`; `session_off = Pending`; clear `set_in_flight`, `wanted`, `off_confirm_until`, `read_failure_noticed`, `session_unknown`; raise both floors to `next_gen` (so every reply sent for the previous session is stale); read both. The profile reading and `profile_unknown` are kept while the new read is in flight (same profile, same connection). `SessionClosed`: clear the session fields and `off_confirm_until`, raise the session floor; the segment is hidden. There is **no input for the snapshot's or `session.info`'s `yolo`** (decision 6, H12b).
2. Reading procedure (for kind K): if a read of K is in flight, set `reread_K = true` and send nothing; if a write of K is in flight, send nothing (its reply is newer). Otherwise take `g = next_gen; next_gen += 1`, record it as the read in flight, and emit the read effect with `g`. At most one read of each kind is ever in flight.
3. Triggers: `TurnCompleted` for the current session; `ConnectionOpened`; `HermesCommandFinished` for the current session whose `name` (lower-case, without the slash) is `yolo` or `approvals`: `Ran` reads both kinds; `Unknown` sets `profile = Pending`, `session_off = Pending`, `profile_unknown = true`, `session_unknown = true`, then reads both; `NotRun` does nothing. Each read goes through rule 2.
4. Read replies. A reply for another session, or with a generation below the kind's floor, or that is not the read in flight, is dropped (no effect, no notice). Otherwise clear the read in flight. Success sets `Known(v)`, clears that kind's unknown flag and `read_failure_noticed`. Failure (any `CallFailure`) sets that reading to `Failed`, **even when it was `Known`** (decision 1); if a session is open and `read_failure_noticed` is false, emit P11 and set it. A profile read that fails with no session open emits nothing (P3 then says `unknown`, and opening a session reads again). Then, if `reread_K` is set, clear it and read again once.
5. `ToggleKey`: clear `off_confirm_until`. No session gives P12. Profile `Known(Off)` gives P7 and sends nothing. `session_off` not `Known` gives P13 (and a read through rule 2). A bypass write in flight: `wanted = Some(!wanted.unwrap_or(sent))`, where `sent` is the value of the write in flight; in words, each press flips the latest intended value; nothing is sent. Otherwise take a generation, record `set_in_flight = (g, !current)` where `current` is the value shown (it may be stale, E2; the notice states the confirmed result), raise the session floor to `g` (an earlier read's reply is now stale), and emit `SetSessionOff { off: !current }`.
6. `SessionOffSet` reply. Dropped when it is for another session or not the write in flight (no state change, no notice). Otherwise clear `set_in_flight`. Success: `session_off = Known(result)`, clear `session_unknown`; if `wanted` is set and differs from `result`, send it as in rule 5 and clear `wanted`; else clear `wanted` and emit the P1 form (bypass on) or the P2 form (bypass off) for the current profile reading (4.8). `Unknown` or `Unreadable`: clear `wanted`, `session_off = Pending`, `session_unknown = true`, emit P9, read through rule 2. `Refused`: clear `wanted`, keep the last known value, emit P10. `NotSent`: clear `wanted`, keep the last known value, emit P16.
7. `Command(Show)` emits P3 (any state, with or without a session). `Command(SessionOff)` and `Command(SessionDefault)`: no session gives P12; `session_off` not `Known` gives P13; a write in flight sets `wanted` to the fixed target; otherwise send as rule 5 with the fixed target, **even when the reading already equals it** (decision 5). **These two commands are sent even when the profile is `Known(Off)`** (they change the stored bypass for later; edge case E1); only `ToggleKey` refuses with P7.
8. `Command(Profile(m))` (with or without a session): a profile write in flight gives P14. For `Off`: when `off_confirm_until` is unset or passed, set it to `now + 30 s`, emit P4, send nothing; when still open, clear it and send. `Manual` and `Smart` send at once, even when the reading already equals `m` (decision 5). Sending takes a generation, records `profile_set_in_flight`, raises the profile floor to it, and emits `SetProfileMode`. **The confirmation window** is cleared by any `Command` other than a second `Profile(Off)` inside it, by `ToggleKey`, `SessionOpened`, `SessionClosed` and `ConnectionOpened` (rules 1, 5); replies, triggers, `/cd` and prompts do not reach this state and do not clear it.
9. `ProfileModeSet` reply (dropped when not the write in flight): success sets `profile = Known(result)`, clears `profile_unknown`, and emits P5 (plus the P5 suffix for the bypass reading, 4.8); `Unknown` or `Unreadable` sets `profile = Pending`, `profile_unknown = true`, emits P9, reads through rule 2; `Refused` emits P10 and keeps the last known mode; `NotSent` emits P16 and keeps it.
10. After every input, emit `Redraw` exactly when `segment()` differs from its value before the input.

```text
                   ─ resolve error ────────► C3b / C3c / C3d
                   ─ same folder ──────────► C6
                   ─ else ─────────────────► CheckFolder(sid, target)   (state: checking (sid, target))
Checked(sid', target', check):
   not the check in progress (other target) ───► dropped
   sid' is not ctx.session_id (session switched) ► C8                  (state: idle; nothing sent)
   Directory ─ ledger.build(sid, "workspace", {cwd}, true)
             ─ Err(NotSent) ───────────────► C18                       (state: idle)
             ─ Ok(request) ────────────────► Send(request) + C20       (state: in flight)
   Missing | NotADirectory | Unreadable ───► C3 | C4 | C5              (state: idle)
Outcome(...) for a request other than the one in flight ─► dropped
Outcome(...) whose request.session_id is not ctx.session_id ─► settle (no fence retry); C8b; no UpdateFolder
Outcome(Committed) ─ settle; UpdateFolder (both fields) + C1
Outcome(FenceRefused) ─ retry_after_fence ─ Some(r) ─► Send(r) (stays in flight)
                                          ─ None ───► settle; C13
Outcome(Refused{reason}) ─ settle; C7b (session_busy) | C9 | C10 | C11 | C16 | C14 (-32601) | C17 (other)
Outcome(Unknown) ─ settle (the ledger keeps the request); C12
Outcome(Unreadable | OtherStatus | Deferred | NeedsConfirmation | NotSent) ─ settle; C17
```

Every outcome ends the in-flight state (only a fence retry keeps it), so a repeated `/cd` after `Unknown` is not refused with C19: it goes through the checks again, and `ledger.build` returns the kept identical request. **Exact repeat** means the same session, operation `workspace` and the same normalised `{cwd}` payload (`P2-06`'s `build` matches on those three); the kept request is resent byte for byte, including its original `request_id`, `expected_revision` and `expected_generation`, even when the fences moved since (snapshots, `session.info`). That is what Hermes's receipt needs (H28): if the first attempt committed, Hermes answers the stored receipt; if it never arrived, the old fences draw `revision_conflict` or `stale_generation`, and the one fence retry sends a new request at the new fences. A different `/cd` discards the kept request (E19). `Deferred` and `NeedsConfirmation` are not expected for `workspace` (H30). `NotSent { reason }` from `send` is C17 with the not-connected words.

**Session switch during `/cd`.** The check carries the session it was started for; a reply for a session that is no longer in front prints C8 and sends nothing, so a move is never sent for a session the developer did not choose. A request already sent carries its own `session_id`, so Hermes moves that session; its outcome is settled in the ledger (no fence retry, because the developer is no longer looking at it), changes no folder in the foreground session, and prints C8b. Reopening that session shows its folder from the snapshot.

### 4.4 The segment

Evaluate the rows top to bottom; the first that matches wins.

| # | Condition | Text | Tone |
|---|---|---|---|

| 2 | Profile `Known(Off)` (any bypass) | `approvals: off` | warning |
| 3 | Bypass `Known(true)` (any profile but `Known(Off)`) | `approvals: off (this session)` | warning |

So `approvals: manual` or `approvals: smart` appears only when Hermes confirmed both the profile mode and that the bypass is off. A re-read in flight never hides a shown segment, because the `Known` value stays until the reply; a failed reply turns it into `approvals: unknown` (rule 4, decision 1). Rows 2 and 3 stay true whatever the other reading is: a profile at `off`, or a confirmed bypass, means approvals are off either way.

The segment goes into `P1-10`'s line after the model segment. Layout order: connection, model, approvals, folder, context, cost, needs you, working, external. Priority (dropped last first): connection 1, needs you 2, approvals 3, model 4, context 5, folder 6, working 7, cost 8, external 9. The relative order of `P1-10`'s segments is unchanged; with `approvals: None` every `P1-10` test passes unchanged. `P1-10` sanitises every segment's text when it draws (its REQ-6).

### 4.5 Commands

```text
/permissions                    show both settings (P3)
/permissions manual|smart|off   the profile's mode, every session of the profile (no session needed)
/permissions session off        approvals off for this session only
/permissions session default    this session follows the profile again
/cd                             show the session's folder (C2)
/cd <folder>                    move the session (section 4.6)
```

Words are case-insensitive and separated by any whitespace; extra words give P8. Both are `P2-03` local commands (tag `talaria`). `/permissions` and `/cd` do not exist in Hermes's registry (H13), so nothing is shadowed.

### 4.6 Resolving a `/cd` argument

1. Take the text after `/cd`, trimmed. Empty: `CdCommand::Show`.
2. If it is at least two characters long and starts and ends with the same quote (`'` or `"`), remove that one pair. No other unescaping: spaces inside the path are kept as typed.
3. `~` alone is the home folder; `~/rest` is the home folder joined with `rest`; `~name...` is `CdTargetError::TildeUser` (C3c). With no known home folder, `~` and `~/rest` are `CdTargetError::NoHome` (C3d).
4. An absolute path is used as is. A relative path is joined onto the session's folder; with no known folder it is `CdTargetError::RelativeWithoutFolder` (C3b).
5. Normalise lexically: remove `.` components, let `..` remove the previous normal component (never above the root), collapse repeated separators, and remove a trailing separator (except for the root).
6. If the result equals the session's folder after the same normalisation: C6, nothing sent.
7. The app checks the folder with `tokio::fs::metadata` (which follows symbolic links) inside `tokio::time::timeout` of 5 seconds: a directory is `Directory`; a file or other non-directory `NotADirectory`; "not found" `Missing`; any other error, or the timeout (a hung network mount), `Unreadable`. So a check always ends and never leaves `/cd` stuck in C19. The path sent is the normalised one, not a canonical one, matching Hermes's `abspath` (H22).

The home folder is the one `P1-12` puts into `P1-10`'s `StatusInputs` (one source for the status line and `/cd`). `display_path` replaces a leading home folder with `~` by whole components (`/work` under home `/wor` is not shortened); with no home folder it returns the path unchanged. It does not sanitise: notices are drawn through `P1-07`'s `sanitize_untrusted` (as `P2-03` draws every notice) and the status line through `P1-06`'s `history::sanitize` (`P1-10` REQ-6). `history::sanitize` lives in `talaria-tui`, which `talaria-core` must not import (roadmap rule 6).

### 4.7 Keys

`approvals_toggle` belongs to `KeyContext::Composer` and defaults to `shift+tab`. It is configurable in `[keys]` of `~/.talaria/config.toml` (`P1-08`'s loader; `approvals_toggle = ["ctrl+t"]` rebinds it, `[]` unbinds it). With no binding, the texts that name the key use their unbound forms (4.8).

The application routes a key to one context at a time (`P1-08`'s key contexts and `P1-12`'s routing). So:

- **A completion list is open** (`P2-03`'s slash palette or `P2-04`'s `@` list, `KeyContext::Completion`): Shift+Tab goes to that context, which binds nothing to it by default, so nothing happens. Hermes's own terminal UI also skips its Shift+Tab while a completion list is open (2.6).
- **An approval card has focus** (`P1-09`: a card takes keys only while the draft is empty): Shift+Tab goes to the card, not to this action. To change the bypass while a card is open, the developer types `/permissions session off` (typing makes the draft non-empty, so keys go to the composer, `P1-09` REQ-15). This unit must not change what a focused card or a menu does with Shift+Tab: if `P1-09`'s card or a menu matches `KeyCode::Tab` without checking the shift modifier, so that the new mapping makes Shift+Tab open the card's note field, stop and report.
- **An overlay** (for example `P2-07`'s session picker, which binds `shift+tab` for its own use) keeps its own Shift+Tab.

crossterm reports Shift+Tab as `KeyCode::BackTab`, usually with the shift modifier. `P1-08` maps it to `Other` today. This unit maps it to `Key { code: Tab, mods.shift: true }` whatever modifiers crossterm reports, so the chord `shift+tab` parses (`P1-08`'s grammar has `tab` and `shift`) and matches. If `P2-07` merged first and added the same mapping, keep one copy.

### 4.9 Budgets and idle

- No timer. Reads happen only on the triggers of rule 3 in 4.3: an idle application makes no request and draws no frame.
- A read that returns the same values draws nothing (`Redraw` is emitted only on a change).
- Timeouts (`P1-02`'s `call_with`): `config.get` and `config.set` 10 s; the local folder check 5 s (4.6); `session.mutate` `workspace` 60 s (Hermes runs up to three `git` commands and may tear down a remote terminal environment, H22, H25). A timeout is an unknown outcome, never success. C20 tells the developer a move is running.
- Effects run on a background task and return as messages; nothing waits on the network inside the event loop. The `P1-11` keystroke budget (16 ms at the 95th percentile while streaming) must still hold.

## 5. Request and result shapes

Talaria uses the canonical method markers (`methods::canonical::{config_get, config_set, session_mutate}`) through `P1-02`'s `Client::call` or `call_with`; never `call_raw`, never `profile`, never `scope`.

```json
{"result":{"value":"manual"}}

{"result":{"key":"yolo","value":"0","scope":"session"}}

{"method":"config.set","params":{"session_id":"<sid>","key":"yolo","value":"1"}}
{"result":{"key":"yolo","value":"1","scope":"session"}}

{"method":"config.set","params":{"key":"approvals.mode","value":"smart"}}
{"result":{"key":"approvals.mode","value":"smart"}}

{"method":"session.mutate","params":{"session_id":"<sid>","request_id":"<launch_id>-cd-m1",
  "expected_revision":12,"expected_generation":4,"operation":"workspace",
  "payload":{"cwd":"/work/proj-b"}}}
{"result":{"session_id":"<sid>","revision":13,"execution_generation":5,"operation":"workspace",
  "cwd":"/work/proj-b","branch":"main","git_repo_root":"/work/proj-b"}}

{"error":{"code":4001,"message":"session_busy","data":{"reason":"session_busy"}}}
{"error":{"code":4001,"message":"revision_conflict",
  "data":{"reason":"revision_conflict","revision":14,"execution_generation":5}}}
{"error":{"code":-32601,"message":"unknown method: session.cwd.set","data":{"reason":"unknown_method"}}}
```

Reading results: for `approvals.mode`, `value` must parse with `ApprovalMode::parse`, else `Unreadable`. For `yolo`, `value` must be `"1"` or `"0"`, else `Unreadable`. A `config.set` result's `value` may be typed as a string or a boolean in the generated `ConfigSetResult`; only the strings above count. A refusal of a bad argument arrives as `{"code":4001,"message":"invalid_params","data":{"reason":"invalid_params"}}` (H31); classify by `data.reason` first, then by code.

Events: the bypass is never taken from an event or a snapshot (H12b). For the folder, read `cwd` from a `session.info` event only when the frame's `params.session_id` is the foreground session (H31; a background session's event changes nothing shown) and the raw `payload` object (the `serde_json::Value` handed to `EventFrame::from_params`) contains the key `cwd` with a non-empty string (the contract's `SessionLiveInfo` defaults it to `""`, H15), and apply it with `SessionFolder::apply_info_cwd` (a different folder clears the branch: Hermes never sends `branch` in the event, H14). The snapshot's `info.cwd` and `info.branch` seed `SessionFolder::from_snapshot`.
