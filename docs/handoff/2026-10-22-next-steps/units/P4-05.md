## 1. The feature in one page

Requirement R7 asks that skills, toolsets and plugins be readable and editable from Talaria. Hermes already does all the work; Talaria presents it. This unit adds one overlay, **Capabilities**, opened with the local command `/capabilities [skills|hub|toolsets|plugins]`, with four tabs:

| Tab | What it shows | What it changes | Calls (section 3) |
|---|---|---|---|
| Skills | Installed skills of the profile, grouped by category, with on or off, where each came from, and how often it was used | Turn a skill on or off; read its `SKILL.md` | REST `GET /api/skills`, `PUT /api/skills/toggle`, `GET /api/skills/content` |
| Skill hub | Skills available from Hermes's skill hub, paged, and a search across hub sources | Install a skill, after Hermes's security scan allows it and the operator confirms | Socket `skills.manage` (`browse`, `install`); REST `GET /api/skills/hub/search`, `/preview`, `/scan`; socket `skills.reload` afterwards |
| Toolsets | Configurable toolsets, on or off, tool counts, whether keys or setup are missing | Turn a toolset on or off | REST `GET /api/tools/toolsets`, `PUT /api/tools/toolsets/{name}`, `GET /api/tools/toolsets/{name}/config` |
| Plugins | Plugins installed in the profile (or all, including bundled), with status, version, source and their servers | Turn a plugin on or off; install from the Hermes catalog or a repository address; remove a user install | Socket `plugins.manage` (`list`, `toggle`, `install`, `remove`), `plugins.catalog.lookup`; REST `GET /api/dashboard/plugins/catalog` |

A read-only command, `talaria capabilities <skills|toolsets|plugins> [--json] [--profile <p>]`, prints the same lists for scripts and for evidence.

The split between socket and REST follows section 11, decision D2. It departs from draft ADR 0007 item 4 ("Dashboard REST is used only for what has no RPC"); D11 records why and the issue gates the start on the operator's acceptance.

## 3. Exact requests and replies

Socket calls go through [`P1-02`](https://github.com/infiquetra/talaria/issues/199)'s `Client::call_with(params, CallOptions { timeout: Some(..) })` with `methods::legacy::<name>::Marker` types from [`P0-03`](https://github.com/infiquetra/talaria/issues/196). REST calls go through [`P4-01`](https://github.com/infiquetra/talaria/issues/250)'s `RestClient::request` (or its `get_json`, `put_json` wrappers) with a `NativeHttpMinter` for the target profile. `<p>` is the target profile name (section 11, D5); every request names it except the catalog route and `skills.reload`.

### 3.1 Reads

```text
GET  /api/skills?profile=<p>                                              deadline 30 s
GET  /api/skills/content?name=<name>&profile=<p>                          deadline 30 s
GET  /api/skills/hub/search?q=<q>&source=all&limit=20&profile=<p>         deadline 45 s
GET  /api/skills/hub/preview?identifier=<id>&profile=<p>                  deadline 45 s
GET  /api/skills/hub/scan?identifier=<id>&profile=<p>                     deadline 45 s
GET  /api/tools/toolsets?profile=<p>                                      deadline 30 s
GET  /api/tools/toolsets/<name>/config?profile=<p>                        deadline 30 s
GET  /api/dashboard/plugins/catalog                                       deadline 45 s
socket skills.manage   {"action":"browse","page":<n>,"page_size":20,"profile":"<p>"}   timeout 45 s
socket plugins.manage  {"action":"list","profile":"<p>"}                               timeout 30 s
socket plugins.catalog.lookup {"name":"<name>","profile":"<p>"}                       timeout 20 s
```

Query values are percent-encoded. Every REST deadline is passed per request as `RequestOpts { deadline: Some(..), ..Default::default() }` ([`P4-01`](https://github.com/infiquetra/talaria/issues/250)'s per-request override; its defaults are 15 s for `GET` and 30 s for `PUT`).

### 3.2 Writes

```text

PUT  /api/tools/toolsets/<name>        body {"enabled":true|false,"profile":"<p>"}                   deadline 30 s
socket skills.manage   {"action":"install","query":"<identifier or name>","profile":"<p>"}          timeout 120 s
socket skills.reload   {"session_id":"<foreground session id>"}                                     timeout 30 s
socket plugins.manage  {"action":"toggle","key":"<key>","enable":true|false,"profile":"<p>"}         timeout 30 s
socket plugins.manage  {"action":"install","catalog_name":"<name>","enable":true,"profile":"<p>"}    timeout 120 s
socket plugins.manage  {"action":"install","identifier":"<https url>","enable":true,"profile":"<p>"} timeout 120 s
socket plugins.manage  {"action":"remove","name":"<name>","profile":"<p>"}                          timeout 30 s
```

Never sent, by any code path (test 13 asserts it on every outbound frame and body, at any depth, including a key whose value is `null`): `force`, `accept_capabilities`, `ref`, `repo`, `values`, `unattended`, actions `update`, `settings`, `onboarding`, `presence`, and the methods `tools.configure`, `tools.list`, `toolsets.list`, `reload.mcp`. Never requested: `/api/skills/hub/install`, `/uninstall`, `/update`, `POST /api/skills`, `PUT /api/skills/content`. The list is spelled only in tests (test 13 and mock rule M18); the source never spells these names, not even in comments, so the issue's verification `grep` stays meaningful.

### 3.3 Replies used, by field

Talaria decodes only these fields and ignores the rest (unknown fields never fail decoding):

- Skills row (H11, H37): `name`, `description` (null decodes as empty), `category` (nullable), `enabled`, `usage`, `provenance`.
- Skill content (H13): `content` only. `path` is discarded at decode time.
- Browse (H15): `items[].{name, description, source, trust, identifier}`, `page`, `total_pages`, `total`.
- Search (H17): `results[].{name, description, source, identifier, trust_level}`, `timed_out`, `installed` (keys only).
- Preview (H18): `name`, `description`, `source`, `identifier`, `trust_level`, `tags`, `skill_md`, `files`.
- Scan (H19): `name`, `identifier`, `source`, `trust_level`, `verdict`, `summary`, `policy`, `policy_reason`, `findings[].{severity, category, file, line, description}`, `severity_counts`.
- Install skill (H16): `installed`, `name` (not shown; T18 uses the matched Skills row's name); error `code`, `message`, `data.log` (null when Hermes captured nothing: `log or None`, `tui_gateway/methods_tools.py:1384-1389`; the message is then `skill install failed`).
- Reload (H20): `output` (last non-empty line only), `result.total`.
- Toolset row (H23): `name`, `label`, `description`, `platform`, `platform_label`, `enabled`, `configured`, `tools`.
- Toolset toggle (H24): `ok`, `enabled`, `post_setup_started`.
- Toolset config (H25): `has_category`, `active_provider`, `providers[].{name, is_active, status, env_vars[].{key, is_set}}`.
- Plugin row (H28, H38): `name`, `key`, `version`, `description`, `source`, `status`, `servers[].{name, state, sentence}`, `catalog_name`, `catalog_tier`, `update_available`, `settings_schema[].{key, label, type, has_value, value}` (a `secret` field's `value` is never read). `install_dir` is discarded at decode time.
- Plugin toggle (H29): `ok`, `unchanged`, `restart_required`, `activation.live_now`, `activation.deferred`, `name`, `plugin`.
- Plugin install (H30): `ok`, `plugin_name`, `warnings`, `missing_env`, `enabled`, `known_issues`, `restart_required`, `activation.live_now`, `activation.deferred`. `after_install_path` is discarded.
- Plugin remove (H31): `ok`, `name`, `cleared_memory_provider`.
- Lookup (H32): `status`, `entry.{name, repo, sha}` (`sha` may be absent).
- Catalog (H33): `entries[].{name, title, description, tier, sha_short, installed, platforms}`.

**Absent or null fields.** A row's `name` (every list) and `enabled` (skills, toolsets) are required: a row where either is absent, null or of the wrong type fails the whole read as T21 `unreadable reply`, because a guessed on or off state would mislead a toggle. Every other field decodes leniently when absent or null: strings empty, `usage` 0, `configured` and `update_available` false, lists (`tools`, `servers`, `settings_schema`, `findings`, `tags`, `files`) empty, `key`, `category` and `trust` `None`, `provenance` `Other("")` (label `-`), plugin `status` `Other("")` (`[?]`, read-only). A present field of the wrong type (for example `usage: "3"`) fails the read like a missing `name`. Test 4 covers one absent and one null case per rule.

**Where the inputs come from.** The profile goes only to `CapabilitiesState::new`. `/capabilities` passes [`P1-12`](https://github.com/infiquetra/talaria/issues/209)'s `OpenConnection.profile_name`; another unit that wants the overlay for another profile builds a new state with that profile. `CapInput::Open(CapTab)` carries only the tab. `foreground` is `Some(SessionRef { session_id, profile: OpenConnection.profile_name })` when a foreground session exists (the foreground session lives on the open connection, so its profile is the connection's), else `None`.

The app builds `CapabilitiesService` the way [`P4-01`](https://github.com/infiquetra/talaria/issues/250) builds `SettingsService` (its specification, "Where the inputs come from in production"): when the overlay opens it runs [`P1-01`](https://github.com/infiquetra/talaria/issues/198)'s `discover_with(home, EnsurePolicy::Never)` on the Hermes home the connection used, then `api_origin` = `endpoint.api_origin()`, `served_profiles` = each `endpoint.profiles()` name, `make_minter` = `|name| Arc::new(NativeHttpMinter::new(home.clone(), endpoint.clone(), endpoint.resolve_profile(name)?))`, `socket` = the open connection's `Client`, `hermes_home` = that home as a string, `user_home` = the `HOME` environment variable (empty when unset). Tests construct it directly with the mock's origin, a counting fake minter and a mock gateway client.

**`CapInput` and `CapEffect`.** The issue fixes these variants; the rest are the test author's (tests 4 to 12 pin behaviour, not names):

- `CapInput`: `Open(CapTab)`, `Close`, `Key(KeyAction)`, `Char(char)` and `Backspace` (text keys, 6.4), `SetForeground(Option<SessionRef>)`, `Tick`, `SkillsChanged`, `Loaded { tab, generation, result }`, `WriteDone { op_id, result }`, `ReadBack { op_id, result }`, and replies for scan, preview, lookup, catalog and reload.
- `CapEffect`: `Fetch { tab, generation }`, `FetchDetail { tab, key, generation }`, `HubBrowse { page, generation }`, `HubSearch { q, generation }`, `HubPreview { identifier }`, `HubScan { identifier }`, `ToggleSkill { op_id, name, enabled }`, `ToggleToolset { op_id, name, enabled }`, `TogglePlugin { op_id, key, enable }`, `InstallSkill { op_id, install_key }`, `ReloadSkills { session_id }`, `LookupPlugin { name }`, `InstallPlugin { op_id, target }`, `RemovePlugin { op_id, name }`, `FetchCatalog { generation }`, `ScheduleTick { after_ms: u64 }` (the app sends one `Tick` after the delay; one-shot), `Notice(String)`, `Dispose` (the app drops the state).

**First load and the foreground.** `new` emits nothing. **`apply` outcome table** ([`P4-09`](https://github.com/infiquetra/talaria/issues/261)'s seam; installs are not exposed, D8):

| Situation | Sent | Outcome |
|---|---|---|
| `profile` not in `served_profiles` | nothing | `Refused(T33)` |
| Pre-read of the list fails | nothing | `Unknown` when lost after sending; else `Refused(<error text>)` |
| Pre-read: the name or key is not listed | nothing | `Refused("<name> is not listed in profile <p>.")` |
| Pre-read: already in the requested state (for a plugin: `enabled` for on; `disabled` or `not enabled` for off) | nothing | `Unchanged` |
| Plugin row without `key`, or with an `Other` status | nothing | `Refused(T32)` |
| Write not sent (7.6's T37 row) | nothing reached Hermes | `Refused(T37)` |
| Write refused (REST 4xx, 5xx; socket error) | the write | `Refused(<mapped text from 7.6>)` |
| Write outcome unknown | the write, never resent | `Unknown` |
| Plugin reply `unchanged: true` | the write | `Unchanged` |
| Write ok, read-back agrees | write and read | `Applied` |
| Write ok, read-back disagrees or the row vanished | write and read | `ReadBackMismatch` |
| Write ok, read-back fails | write and read | `Unknown` |

`apply` for a profile other than the connection's: REST uses `make_minter(profile)`; socket calls go on the open connection with `profile: <p>`. A host-scope ticket is routed to that profile by the authority (H35); a profile-scope ticket gets 4001 `profile_mismatch`, mapped to `Refused(T33)`. It never falls back to another route.

`apply` does not take the overlay state's write lock: the service holds no state, and [`P4-09`](https://github.com/infiquetra/talaria/issues/261) serialises its own changes. An `apply` and an overlay write may therefore overlap. That is accepted because each write sets an absolute state and each is read back: if [`P4-09`](https://github.com/infiquetra/talaria/issues/261) changes a row the overlay just wrote, the overlay's read-back reports T12 and `apply` reports what it read.

## 5. Exact texts

`<p>` is the profile, `<name>` a skill, toolset or plugin name. Every Hermes-provided text (`<message>`, `<reason>`, `<detail>`, descriptions, findings) first passes [`P1-06`](https://github.com/infiquetra/talaria/issues/203)'s `history::sanitize`, then `redact_paths`, then is cut to 300 Unicode scalar values (`char`s), the last being `…` (U+2026) when cut. Each value is cleaned and cut on its own, before it is put into its text; the composed text is never cut. Example: a 5026 `message` of 400 characters becomes its first 299 characters plus `…` inside T19, so the whole T19 line is longer than 300. `SKILL.md`, preview `skill_md` and the install `data.log` are not cut to 300; they are capped at 256 KiB (cut at a `char` boundary) with T34 after. List cells are cut to their column width in terminal cells, ending `…`. Test 2 pins T1 to T45 and the variants character for character.

List placeholders: `<ids>` (T7) is `timed_out` in reply order, joined with `, `. In T11 and T28, `Live now: <items>.` lists the `activation.live_now.mcp_servers[].name` values, then the `live_now.skills[].name` values, in reply order, joined with `, `; the line is left out when both lists are empty or `live_now` is absent or null. `From the next session: <items>.` lists the names of every `activation.deferred` list (`{kind: [names]}`, `tui_gateway/contracts/tools_mcp_plugins.py:734-756`), kinds in reply order, joined with `, `; left out when all are empty. `<ENV, ...>` (T28) is `missing_env` joined with `, `. Example: `live_now {mcp_servers: [{name: "fixture-mcp", connected: true, tools: []}], skills: [{name: "guide"}]}` and `deferred {tools: ["fixture_tool"]}` give `Live now: fixture-mcp, guide.` and `From the next session: fixture_tool.` Each part of a multi-part text (T11, T18, T28, T30) is its own line of the notice.

Each text column is padded to its widest value plus two spaces; the last column is not padded. Unserved profile: T33 on standard error, exit 1. A refused or failed call: the 7.6 text (T20, T21, T36, T37, T39) on standard error, exit 1. Unknown list: `talaria capabilities: unknown list <arg>; use skills, toolsets or plugins`, exit 2. The command never runs `hermes`.

### 6.4 Input lines, the filter and the detail focus

- Three input lines exist, one open at a time: `Filter: ` (Skills, Toolsets, Plugins), `Search: ` (Skill hub) and `Install: ` (Plugins).
- While an input is being typed, keys are text, not commands: every printable character (letters such as `n`, `i`, `y`, digits and Space included) is appended at the end; there is no cursor. Backspace removes the last character; Enter submits; Esc cancels. Every other key (arrows, Tab, Page keys, Home, End, Ctrl+ keys) is ignored. These keys are fixed, not rebindable. While `CapView` reports an input being typed, the app sends typed characters as `CapInput::Char(char)` and Backspace as `CapInput::Backspace` instead of looking them up in `KeyContext::Capabilities`. - Filter: `/` opens `Filter: ` holding the tab's kept filter text (empty when none). ## 7. State machines

### 7.1 Loading

Each tab has `NotLoaded → Loading(generation) → Ready | Failed(text)`. A tab loads on its first visit, on `r`, after a write's read-back, and (Skills) on the change signal (7.8). Opening the Skill hub also loads Skills once if it is `NotLoaded` (for the installed marks). A reply whose generation is older than the tab's current one is dropped. Opening the overlay never loads a tab the operator did not visit. `Failed` stays until `r`; nothing reloads a failed read on its own. While nothing is loading or in flight, `update` returns no effect. A failed detail read (content, preview, toolset config) is shown in the detail pane and leaves the tab `Ready`.

### 7.2 Toggle (skills, toolsets, plugins)

```text
Ready --Space--> [no write in flight?] --> InFlight(op_id, intended)
                  [write in flight]     --> notice T13, nothing sent
InFlight --reply ok--> ReadingBack(op_id) --list reply--> Ready + T8/T9/T11, or T12 if the row disagrees
InFlight --plugin reply unchanged:true--> Ready + T44
InFlight --refused--> Ready + 7.6 text, row unchanged
InFlight --unknown (timeout after send, dropped, unreadable reply)--> ReadingBack + T14 (never re-sent)
ReadingBack --read failed--> Ready + T40
```

Only one write is in flight across all tabs. Plugin on/off mapping: `enabled` is on; `not enabled` and `disabled` are off; an `Other` status, or a row without `key`, is read-only (T32 on Space). Space on an off plugin sends `enable: true`; on an on plugin `enable: false`. The read-back for a plugin uses the toggle reply's `plugin` row when present, else a fresh `list`; after enable it expects `enabled`, after disable `disabled` or `not enabled`.

### 7.3 Skill install

```text
Hub Ready --i--> Scanning(key) --scan reply--> Confirm(report)              [policy allow]
                                           --> Refused(T16 + findings)       [policy ask, block or other]
                               --404--> T42
                               --502/timeout--> T22
Confirm --y--> Installing (T17) --ok--> ReadingBack (reload Skills)
                                         --listed--> T18 --> ReloadSkills(foreground session, if same profile)
                                         --not listed--> T38
                                         --read failed--> T40
                                --5031--> T19 with data.log in the detail pane
                                --5024 or other refusal--> T19 with the message
                                --unknown--> T14, refresh Skills and hub marks
Confirm --any other key--> Hub Ready, nothing sent
```

Findings are ordered critical, high, medium, low, then any other severity, keeping Hermes's order within a severity; at most five are listed below T15 or T16 as `<severity> <category> <file>:<line> <description>`, followed by `and <n> more` when there are more. "Listed" means a Skills row whose `name` equals the hub item's `name`, or equals the last `/`-separated segment of the install key (the installed folder may carry the identifier's name rather than the display name: verify at the pinned commit before relying on it). T18 names the matched row. A row that existed before the install also counts: T18 then says the profile holds the skill, which is what Hermes itself answers for an active built-in (H16), not that new files arrived. A hub item with `identifier: null` installs by its `name`. Hermes may refuse an ambiguous bare name: `do_install` prints a `Multiple skills named '<name>' found:` table and the install fails with 5031, its message the log's last line (`hermes_cli/skills_hub.py:238`; `tui_gateway/methods_tools.py:1384-1389`). Talaria shows T19 with that message and the log, and never retries with another key. A bare-name scan may answer 404 (T42): verify at the pinned commit before relying on it. `skills.reload` runs only when `foreground` is `Some` and its `profile` equals the target profile; its failure is one line (T18's second form) and never undoes the install.

### 7.4 Plugin install and the input grammar

```text
Plugins Ready --i--> Input --Enter--> classify_install_input
   CatalogName(n) --> Lookup --found--> Confirm(T23) --y--> Installing --ok--> T28 --> ReadingBack(list)
                            --unknown--> T26        --invalid_name--> T25   --unavailable--> T27
   Repository(url) --> Confirm(T24) --y--> Installing --ok--> T28 --> ReadingBack(list)
   Err --> T25 (input kept open with its text, 6.4)
ReadingBack --plugin_name listed--> Ready   --not listed--> T38   --failed--> T40
Installing --5026--> T19 (with the plugin name or the input) --unknown--> T14 + refresh
Plugins Ready --c--> Catalog list --Enter on an entry--> Lookup(entry.name) (same path as CatalogName)
              --c, catalog route Unauthorized (after P4-01's one retry) or NotFound--> T35
```

`classify_install_input(input)`, hand-rolled (no URL crate in `talaria-core`):

1. Trim leading and trailing whitespace (Unicode `char::is_whitespace`).
2. **CatalogName** when the whole trimmed input matches `^[a-z0-9_-]{1,64}$` (Hermes's `_NAME_RE`, H40).
3. **Repository** when all of these hold: it starts with exactly `https://` (lower case); the rest is printable ASCII (U+0021 to U+007E, so no whitespace and no control characters) with none of `@`, `?`, `#`, `\`, `[`, `]`; the authority (up to the first `/` after the scheme) is a host of one or more labels of `[A-Za-z0-9-]` separated by single `.`, not starting or ending with `.` or `-`, optionally followed by `:` and 1 to 5 digits whose value is 1 to 65535; a `/` follows the authority and at least one character follows that `/`. A trailing `.git` is allowed. The value is returned as trimmed.
4. Anything else is an error: empty input, upper-case or mixed-case names, `.` in a name, `http://`, `HTTPS://`, `git@...`, `ssh://`, `file:`, local paths, `owner/repo` shorthand, IPv6 hosts, non-ASCII (IDN) hosts, user information, query, fragment, a missing path.

### 7.7 Closing with a write in flight

`Esc` on the overlay (nothing else open) makes the reducer handle `CapInput::Close`: it marks the state closed and, when no write or read-back is in flight, emits `Dispose`. When a write is in flight, the state stays alive and hidden; the app keeps routing that write's results to it. Every write outcome is emitted as `CapEffect::Notice(text)`; the app draws it in the overlay while open, and while closed sends it as [`P2-03`](https://github.com/infiquetra/talaria/issues/223)'s `Event::Notice { kind, text }` (System for success texts, Error for refusals) into the transcript. When the last in-flight operation finishes while closed, the state emits `Dispose` after the notice. Reopening `/capabilities` while a hidden state exists reuses it (the write lock and loaded tabs persist); a different target profile builds a new state only after the hidden one disposed, and until then `/capabilities` shows the hidden state's profile in the title.

### 7.8 Change signal and the debounce

[`P2-03`](https://github.com/infiquetra/talaria/issues/223) handles `skills.changed` in [`P1-12`](https://github.com/infiquetra/talaria/issues/209)'s loop; this unit adds one line there that sends `CapInput::SkillsChanged` to a live (open or hidden) Capabilities state. The reducer:

- With no write or read-back in flight: if no tick is pending, emit `ScheduleTick { after_ms: 500 }` and record `due = now_ms + 500`; further signals before the tick change nothing. On `Tick` with `now_ms >= due`, reload Skills if it was ever loaded (the hub marks follow the Skills list).
- With a write or read-back in flight: set a flag; when the read-back completes, run exactly one more Skills load (so a burst during a write costs the read-back plus one load).
- Tick edge cases: a `Tick` with `now_ms < due` emits `ScheduleTick { after_ms: due - now_ms }` and keeps `due`; a `Tick` with no tick pending is ignored; a `Tick` that arrives while a write or read-back is in flight clears the pending tick and sets the flag above instead of loading. A hidden state (7.7) follows the same rules; if it disposes first, nothing more happens.
- `now_ms` is the app's monotonic clock in milliseconds since the overlay state was created; tests pass any non-decreasing values.

## 11. Design reasoning (settled decisions)

- **D1. One overlay, four tabs, one local command.** Desktop puts skills, toolsets, connectors and plugins on one Capabilities page; Claude Code splits `/skills` and `/plugin`. One overlay keeps one key map and one write lock. The command is `/capabilities` because [`P2-03`](https://github.com/infiquetra/talaria/issues/223)'s rule makes a local command shadow a Hermes command of the same name, and Hermes's `/skills` carries subcommands Talaria does not reimplement (`audit`, `pending`, `approve`, `reject`, `diff`, H22). Shadowing `/skills` is operator question 1.
- **D2. Calls.** Skills and toolsets over REST (profile-scoped through the `native-http` ticket and an explicit `profile`), plugins over `plugins.manage`, as Desktop does. Hub browsing uses `skills.manage browse` because REST has no paged browse across sources (Desktop lists `/api/skills/hub/official` instead, 2.5). Hub search uses REST because the socket search returns no identifier (H14); preview and scan have no socket method.
- **D3. Never `tools.configure` or `tools.list`.** The static reading in H6 says both may act on the launch profile on a multi-profile gateway, and `tools.configure` cannot find an authority session. REST `PUT /api/tools/toolsets/{name}` is profile-scoped and is what Desktop sends. Per-tool selection of MCP server tools (`tools.include`, `tools.exclude`, `server:tool`) is not built in v0.7.0: [`P4-04`](https://github.com/infiquetra/talaria/issues/256) shows it read-only, and the conflict between the two issues' non-goals is reported to [`PH4B`](https://github.com/infiquetra/talaria/issues/217).
- **D4. Skill installs go through `skills.manage install`, never the REST hub install.** The socket call is synchronous, returns Hermes's own refusal text, and is scoped by `profile` (H5, H16). The REST routes spawn a background `hermes` process that needs separate status polling and resolves the ambient home when `profile` is missing (H10).
- **D5. Every request names the profile.** The profile is given to `CapabilitiesState::new` only (`OpenConnection.profile_name`, or another unit's choice). Explicit names defend against a host-scope ticket ([`P3-01`](https://github.com/infiquetra/talaria/issues/239)) and against the launch-profile fallbacks in H4, H10 and H41; an explicit name equal to the ticket's profile passes H8's check.
- **D6. Scan before install, and never override.** Talaria shows the scan from `/api/skills/hub/scan` and asks `y` only when the policy is `allow`; `ask` and `block` end with T16, because Hermes refuses them anyway (H16) and Talaria never sends `force`. Plugin installs show their source and commit and never send `force`, `ref` or `accept_capabilities`.
- **D7. Read back every write, installs included.** A toggle reply is not proof: the toggle route does not check existence (H12), a platform-restricted toolset can land elsewhere (H24), and a skill install answers `installed: true` for a built-in nothing installed (H16). The overlay re-reads the list and compares.
- **D8. [`P4-09`](https://github.com/infiquetra/talaria/issues/261) gets toggles only.** Installing code from the network deserves the full scan-and-confirm screen; a conversational proposal that wants an install opens this overlay at the hub item instead (the [`P4-09`](https://github.com/infiquetra/talaria/issues/261) planner decides).
- **D9. Out of scope:** skill uninstall and hub update (REST spawn routes and status polling), plugin update (consent and scan dialogs), plugin settings forms, per-toolset provider, model and key configuration ([`P4-01`](https://github.com/infiquetra/talaria/issues/250)'s settings and [`P4-02`](https://github.com/infiquetra/talaria/issues/251)'s key entry), creating or editing skills, the star map, connectors ([`P4-11`](https://github.com/infiquetra/talaria/issues/260)), MCP servers ([`P4-04`](https://github.com/infiquetra/talaria/issues/256)), removing a Python package plugin (H39).
- **D10. Own-profile selectors, and [`P4-01`](https://github.com/infiquetra/talaria/issues/250)'s rule.** [`P4-01`](https://github.com/infiquetra/talaria/issues/250)'s decision 2 forbids a `profile` selector except the connected profile's, on the phase 4b routes [`PH4B`](https://github.com/infiquetra/talaria/issues/217) settles (its stop condition C-1), and its mock answers any selector 403 by default. That rule is safe for config routes, but the toolset PUT needs a named profile to pass `-p` to its spawned child (H41). The rule this unit needs, and Hermes enforces (H8), is "never a selector naming another profile than the ticket's". The opt-in `allow_own_profile_selector` keeps [`P4-01`](https://github.com/infiquetra/talaria/issues/250)'s tests unchanged; the [`PH4B`](https://github.com/infiquetra/talaria/issues/217) planner's settled C-1 names this unit's routes.
- **D11. Departure from draft ADR 0007 item 4.** Item 4 keeps REST for "what has no RPC". This unit uses REST for skills, toolsets and hub search, preview and scan, where legacy socket methods exist (`skills.manage`, `tools.list`, `tools.configure`) but either act on the wrong profile (H6) or lack the fields needed (H14). The issue gates the start on the operator's acceptance, as [`P4-01`](https://github.com/infiquetra/talaria/issues/250) does for config values.
- **D12. Plugin "installed" count.** The tab counts non-bundled rows (the same as Hermes's `user_count`, H38), labelled `installed`, not `yours`, because package plugins are counted too; rows still say `yours` only for `user` and `git`.
