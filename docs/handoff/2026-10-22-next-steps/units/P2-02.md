## 2. Why the pager makes no Hermes call

The roadmap row names "`session.resume` snapshot for history beyond what was streamed". The snapshot is already taken when Talaria attaches ([`P1-12`](https://github.com/infiquetra/talaria/issues/209) creates or resumes the session) and [`P1-05`](https://github.com/infiquetra/talaria/issues/202) already builds cells from it. The pager therefore has everything Hermes will safely send. The alternatives were weighed as follows.

| Option | Why rejected |
|---|---|
| Call `session.resume` again when the pager opens | Not a pure read (F4): policy refresh, re-asked deferred picks, a notice task; Hermes Desktop single-flights it to avoid orphan runtimes. It returns the same 3 MiB-bounded history the first call did. |
| Call `session.history` when the pager opens or on a key | Excludes compaction-archived rows (F6), so it cannot recover what `archived_truncated` left out; has no byte budget, so a long lineage can exceed the 8 MiB message limit and close Talaria's whole connection (F3); tool rows still have no output (F7). |
| Call the dashboard REST route Desktop uses (F12) | Bounded and paged, but it is a dashboard REST surface, not the gateway socket; the architecture allows REST only for calls with no RPC (config schema, `.env`). A later unit may add it once the operator decides (an operator question raised through the parent issue). |
| Keep a client-side copy of every event ever received, across restarts | Duplicates Hermes's store; violates "thin cockpit, thick backend" ([05-architecture.md, Principles](../05-architecture.md#principles)). |

Consequence: the pager shows the cells the session state holds. When Hermes said it left older summarized history out, a banner says so. When a resumed tool cell has no output, the cell says so. Nothing is fetched, so opening the pager costs no network time and cannot fail on the network.

## 4. Screen layout and rendering

### 4.1 Regions (alternate screen, `cols` by `rows`)

| Rows | Content |
|---|---|
| 1 | Header (4.2) |
| 0 to 3 | Banners, one line each, in this order: waiting prompt, connection, truncated history |
| rest minus 1 | Body: rendered cells from the anchor down |
| 1 | Footer (4.4) |

Body height `h = rows - 2 - banners`. If `cols < 20` or `h < 2`, the whole screen is the single line `Window too small for the transcript. q closes.` (cut to `cols`), and every key except the close keys (section 5) does nothing. The issue's REQ-7 uses the same rule.

### 4.2 Header and banners

Left: ` Transcript · <title> · <N> cells`, where `<title>` is the session title or `untitled session` when the context title is empty, and `<N>` is `cells.len()`. Right: `working` when `running`, else `idle`. No animation (no spinner): the pager must draw nothing while idle. When the left and right do not fit, the title is cut with `…` first, then the cell count is dropped.

Banner text, exactly:

- `needs_answer`: `⚑ Hermes is waiting for your answer. Press q to go back and answer it.`
- `Reconnecting`: `Connection to Hermes lost; reconnecting. The transcript may be behind.`
- `Disconnected`: `Disconnected from Hermes. This is what Talaria received before the connection dropped.`
- `history_truncated`: `Older summarized history was left out by Hermes to keep the resume reply small.`

Banners are cut with `…` to the width; they never wrap.

Key names on screen (the `q` in the waiting banner and the too-small line, and the footer hints of 4.4) are the default keys, fixed in this unit, even when the person rebinds a pager key. `docs/configuration.md` says so in one line. Building them from the key map is a later change, not this unit's.

### 4.3 Cells in the body

Every text that came from Hermes or the user passes through [`P1-06`](https://github.com/infiquetra/talaria/issues/203)'s `history::sanitize` (or [`P1-07`](https://github.com/infiquetra/talaria/issues/204)'s `sanitize_untrusted` inside `render_markdown`) before it is drawn: control characters and bidirectional overrides become visible stand-ins. No raw escape byte from a cell ever reaches the terminal.

| Cell | Expanded (default) | Compact |
|---|---|---|

Tool output (F8, F13): the pager draws `ToolCell.result`, an `Option<String>`. Resumed tool cells carry a result only for `write_file`, `patch` and `skill_manage`.

`format_duration_fallback(d)`: `None` when `d` is absent, negative or not finite. Otherwise `t = (d * 10).round()` (round half away from zero). ### 4.4 Footer

Not searching (left part), by width:

- 100 columns or more: `/ search · n N next/prev · { } prompts · g G top/bottom · t details · q close` (77 characters)
- 60 to 99 columns: `/ search · n N · { } · g G · t · q close` (40 characters)
- under 60 columns: no hints.

Right part: `cell <i>/<N>` where `i` is the 1-based index of the cell at the top of the body (`cell 0/0` when empty); then ` · following` when follow is on; else ` · ↓ new output · End` while the new-output mark is set (section 8); else nothing. Right after `g` with no new content the right part is `cell 1/<N>` alone. It is at most 35 characters (`cell 1234/2000 · ↓ new output · End`).

Typing a search: left `/<query>▏`; right `<k> of <n>`, `no match`, or empty while the query is empty.

Search active (after Enter): left `"<query>" <k> of <n> · n N · Esc clears`, or `no match for "<query>" · Esc clears`.

Transient notices replace the left part until the next key: `search wrapped to the top`, `search wrapped to the bottom`, `no earlier prompt`, `no later prompt`, `transcript reloaded from Hermes`.

Overflow rule (all footers): the right part always wins and is drawn whole, right-aligned (cut with `…` only when it alone is wider than `cols`). The left part gets `avail = cols - width(right) - 1` display columns; if it is wider it is cut with `…` to `avail`; if `avail < 2` the left part is empty. Widths are display widths (`unicode-width`). Worked example at 100 columns with the 35-character right part: `avail = 64`, so the 77-character hints are cut to 63 characters plus `…`. At 60 columns: `avail = 24`, so the short hints are cut to 23 characters plus `…`.

### 4.5 Default theme

`header`: reversed; `footer`: reversed; `banner`: bold; `user`: bold; `dim`: dim; `tool_ok`: green; `tool_failed`: red; `diff_add`: green; `diff_del`: red; `search_match`: reversed; `search_current`: reversed, bold and underlined; `gutter_mark`: bold. With colour disabled ([`P1-07`](https://github.com/infiquetra/talaria/issues/204)'s `color: false`) every colour is dropped and only modifiers remain, so matches stay visible.

## 5. Keys

Every key is configurable under `[keys]` in `~/.talaria/config.toml`, loaded by [`P1-08`](https://github.com/infiquetra/talaria/issues/205)'s `crates/talaria-app/src/config.rs` and documented in `docs/configuration.md` ([`P1-08`](https://github.com/infiquetra/talaria/issues/205)'s REQ-5). This unit adds one key context, `KeyContext::Pager`, to [`P1-08`](https://github.com/infiquetra/talaria/issues/205)'s `keys.rs`. [`P1-08`](https://github.com/infiquetra/talaria/issues/205) decides two things per context: the plain-letter refusal (composer context only) and the conflict check. Actions in different contexts may share chords because the application routes each key to one context at a time. So `up`, `down`, `home`, `end` and `ctrl+u` can be both composer and pager keys, and the pager's plain letters never capture composer typing.

That is 16 config names: `transcript_open` and 15 names starting `pager_`. `KeyChord::parse(text, KeyContext::Pager)` accepts printable keys and refuses `esc` and `ctrl+c` with the reason `reserved in the transcript pager`, which [`P1-08`](https://github.com/infiquetra/talaria/issues/205)'s loader reports as its `bad_chord` notice. No default is F1, F2, Ctrl+B or Ctrl+S ([`P1-08`](https://github.com/infiquetra/talaria/issues/205)'s rule; a user binding to one gets its `risky_chord` notice).

Conflicts follow [`P1-08`](https://github.com/infiquetra/talaria/issues/205)'s REQ-3 and specification section 3.3 unchanged, per context, walking `Action::ALL` (the pager actions after the composer actions, in the table's order): if exactly one holder of a chord is explicit it wins, and a default holder left with no chord gets the `default_lost` notice; if two explicit holders share a chord the earlier one in `Action::ALL` keeps it and the later one gets the `conflict` notice. Example: `pager_search = "q"` gives `/` and `q` to nothing else: `pager_close` loses `q` and gets `[keys] pager_close in ~/.talaria/config.toml lost its default key q because pager_search now uses it; pager_close has no key until you bind one.` Esc and Ctrl+C still close.

Routing while the pager is open. It receives every key event; the composer, [`P1-09`](https://github.com/infiquetra/talaria/issues/206)'s cards and [`P1-08`](https://github.com/infiquetra/talaria/issues/205)'s interrupt never see them. Order:

1. Ctrl+C: close.
2. Typing a search: Esc cancels, Enter confirms, Backspace edits, a paste inserts its first line, and **every printable character, including `q`, `n`, `j`, `g`, space, `{` and `}`, is query text**. Every other key (arrows, Page Up, Ctrl+O, Ctrl+D) does nothing.
3. Not typing: Esc follows the ladder; then a chord of `transcript_open` closes; then the `KeyContext::Pager` map; anything else does nothing. `transcript_open` is checked first so the open key always closes, even when a person binds it to a pager key such as `g` ([`P1-08`](https://github.com/infiquetra/talaria/issues/205)'s per-context check cannot see that overlap). `docs/configuration.md` says so in one line. Test 29 covers it.
4. Too small (4.1): only steps 1, Esc, `pager_close` and `transcript_open` act.

Mouse capture stays off ([ADR 0009](../../../../platform-specs/04-architecture/adrs/0009-finished-output-lives-in-native-scrollback.md), decision 4); terminals that turn the wheel into arrow keys in the alternate screen will scroll the pager line by line, and selection and copy work on the visible screen.

Tests of [`P1-08`](https://github.com/infiquetra/talaria/issues/205): one is extended in place, never weakened (the test author does it and says so in the red-run log): `src/keys.rs::tests::defaults_are_safe_and_unambiguous` goes from 20 to 36 names round-tripping and checks "no chord on two actions" per context. Two are not edited and must keep passing: `tests/keymap_doc.rs::doc_keys_equal_defaults` (it compares the document's `toml` block with `KeyMap::defaults()`, so it fails once the defaults exist until `docs/configuration.md` lists the 16 new names, one `name = [...]` line each) and `app: tests/config_doc.rs::doc_default_shape_loads_cleanly`. The document stays under 200 lines (if it cannot, issue stop condition 5). `ctrl+o` is not among [`P1-08`](https://github.com/infiquetra/talaria/issues/205)'s 20 composer defaults; the pager's `ctrl+u` and `ctrl+d` share chords with the composer only across contexts, which [`P1-08`](https://github.com/infiquetra/talaria/issues/205) allows.

## 6. Scrolling model

### 6.1 The anchor

The view position is an anchor `(cell_index, line_in_cell)`: the body's top row shows that line of that cell. There is no global line number, so nothing outside the visible cells (and the cells walked past by a move) is rendered. `follow` is a separate flag meaning "the last line of the document is on the last body row". The "bottom snap" is the anchor that puts the last line on the last body row (or `(0, 0)` when the whole document fits in `h` lines).

### 6.2 Moves and the follow rule

One rule, used by the issue's REQ-14 and the state diagram:

- Any upward move (line, page, half page up) turns follow off, even when it ends inside the bottom page.
- A downward move that reaches the bottom snap turns follow on; otherwise follow stays off.
- Top, a prompt jump and a match move turn follow off, unless their target is clamped to the bottom snap (then follow is on). Top therefore keeps follow on only when the whole document fits in `h` lines.
- Bottom goes to the bottom snap and turns follow on.
- Turning follow on, by any of these moves, clears the new-output mark (section 8). No other move sets or clears it.

Walking: down by `d` lines walks forward through rendered cells; up by `d` walks backward, rendering previous cells as needed (cache), and stops at `(0, 0)`.

### 6.3 Opening

The pager opens at the bottom snap with follow on and details expanded. It keeps no position from a previous opening. The last confirmed search query is remembered for the life of the process (for Enter on an empty query, section 7.4). Opening renders only the cells that fill the body from the end backward.

### 6.4 Prompt jumps

`{`: the target is the last user cell with index below the anchor cell, or the anchor cell itself when it is a user cell and `line_in_cell > 0`. `}`: the first user cell with index above the anchor cell. The target's first line goes to the top of the body (clamped to the bottom snap). With no target: the notice `no earlier prompt` or `no later prompt`, and no move.

### 6.5 Resize

`resize(cols, rows)` drops the render cache (widths changed), keeps `cell_index`, sets `line_in_cell` to `min(line_in_cell, new height of that cell - 1)`, keeps follow, and re-applies the bottom snap when follow is on. [`P1-06`](https://github.com/infiquetra/talaria/issues/203)'s REQ-16 says that while the overlay is open each resize updates the main-screen model at once and the overlay draws at the newest size, so no change to `terminal.rs` is expected. If the merged overlay still draws at the old size, stop and report.

## 7. Search

### 7.1 What is searched

`cell_search_text(cell, other)` builds one string per cell, fields joined with `\n`, after `sanitize`:

| Cell | Fields, in order |
|---|---|
| User | text |
| Assistant | text (the Markdown source, markup included) |
| Reasoning | text |
| Tool | name, context, args as the same pretty JSON the fallback body shows, summary, result, diff (absent fields skipped) |
| Notice | text |
| Prompt | command, description, question, choices (one per line), answer (the `a` of `Answering(a)` or `Answered(a)`) |
| Any other kind | the plain text of `other.lines(cell, u16::MAX)`, lines joined with `\n` (span contents concatenated) |

Labels drawn by the pager (`args:`, `output:`, `∴ thinking`, `⚑ approval:`) are not searched. Markdown markup is searched because the search text is the source; a match that exists only in markup (for example `**`) still counts and still lands on its cell (7.6). Matches never cross cells, and a query cannot contain a newline, so a match never crosses fields.

### 7.2 Case and offsets

`fold(c)`: if `c.to_lowercase()` yields exactly one character, that character; otherwise `c` unchanged. This keeps one folded character per source character, so **character** offsets map one to one. Byte lengths can change (`Ⱥ` U+023A is 2 bytes and folds to `ⱥ` U+2C65, 3 bytes; `ẞ` U+1E9E is 3 bytes and folds to `ß` U+00DF, 2 bytes), so every offset in `Match` is a character index, and `find_all` compares `Vec<char>` sequences (or iterates `char_indices` of both texts in step), never byte slices of the folded text. Smart case: `Query::new` sets `case_sensitive = query.chars().any(char::is_uppercase)`. A case-insensitive query compares folded text with the folded query; a case-sensitive one compares raw text with the raw query. Matching is literal substring, non-overlapping, left to right. No regular expressions.

### 7.3 The index

`SearchIndex` stores raw and folded text (as `Vec<char>` or an equivalent character-indexed form) for final cells, keyed by `(source_epoch, CellId)`, built the first time a search needs it. Non-final cells (the live tail) are folded on every search. When the epoch changes, entries of older epochs are dropped. `build_count()` counts entries built, for test 6. Memory: about twice the transcript's text (four bytes per character when stored as `Vec<char>`; the [`P1-11`](https://github.com/infiquetra/talaria/issues/208) memory budget still applies).

### 7.4 The search prompt

- `/` opens the prompt with an empty query and remembers the anchor and the previous query.
- Each character re-runs the search incrementally and moves to the first match at or after the remembered anchor's cell (wrapping to the top if none, with the wrap notice). Backspace on an empty query closes the prompt and restores the anchor.
- Paste inserts the first line of the pasted text only; the query is capped at 256 characters (extra input ignored).
- Enter confirms. Enter on an empty query runs the last confirmed query of this process exactly as if it had been typed (searching from the anchor remembered at `/`) and confirms it; with none, it closes the prompt with no search and restores the anchor.
- Esc cancels: the anchor and the previous query (and its highlights) come back exactly.
- While typing, printable keys are query text (section 5); Ctrl+C closes the pager.

### 7.5 Navigation

Matches are ordered by `(cell_index, char_start)`. `k` is the 1-based position of the current match, `n` the total. `n` goes to the next match; past the last it goes to the first with `search wrapped to the top`. `N` goes to the previous; before the first it goes to the last with `search wrapped to the bottom`. With no matches, `n` and `N` show `no match for "<query>"` and do not move. With no confirmed search (none yet, or cleared with Esc), `n` and `N` do nothing and return `Stay { redraw: false }`. Follow follows section 6.2.

### 7.6 Placing and highlighting the current match

The footer count always comes from the search text (7.1). The highlight comes from the rendered lines. They are tied together per cell like this:

1. For the current match `(cell, j)` (the `j`-th match in that cell, 0-based), render the cell and scan its rendered lines' plain text (span contents concatenated, folded the same way) for occurrences of the query, line by line, left to right. Let `r` be the number found and `s` the cell's match count in the search text.
2. If `r == s`, the current match is the `j`-th rendered occurrence. If that line is visible, do not scroll; otherwise put it at body row `h / 3`. It is drawn with `search_current`.
3. If `r != s` (a match only in markup, a match split by wrapping, or a drawn label or rendered link text that contains the query), **or the cell is a tool cell** (its drawn field order belongs to [`P2-01`](https://github.com/infiquetra/talaria/issues/221) and differs from the search-text order of 7.1: the header shows the summary before the arguments), no rendered occurrence is called current: put the cell's first line at body row `h / 3`, draw `▸` in `gutter_mark` in column 0 of that line, and draw every rendered occurrence of the cell with `search_match` only.

Every visible body line gets every occurrence of the query highlighted with `search_match`; only rule 2 adds `search_current`. `highlight_line` splits spans by character index and patches the style; it never changes the text. A phrase split across two rendered lines by wrapping is not highlighted (documented limitation; the cell is still reached).

Worked example for test 23: an assistant cell whose Markdown source is `**a** c **` renders as `a c **` (a closing `**` with nothing after it is literal text in CommonMark). Query `**`: the search text holds 3 matches (characters 0, 3 and 8), the rendered line holds 1, so `r != s`. For each of `1 of 3`, `2 of 3` and `3 of 3` the cell's first line carries `▸` and the rendered `**` is drawn with `search_match`, not `search_current`. A second assistant cell `bold bold` with query `bold` gives `r == s == 2`, and the current occurrence moves between the two words.

### 7.7 Content changes during a search

On `content_changed`, an active search re-runs. The current match is kept by `(cell_index, ordinal_in_cell)` when it still exists, else the next match after it, else the last. The footer count updates.

## 8. Live updates, epochs and frames

- The application calls `content_changed` whenever the foreground `SessionState` changed (a cell appended, a live cell grew, a cell became final, a prompt opened or settled). With follow on, the view stays at the bottom. The new-output mark: every `content_changed` call while follow is off sets it; only turning follow on clears it (6.2). While it is set and follow is off, the footer's right part ends ` · ↓ new output · End` (4.4).
- Non-final cells are never cached: they are re-rendered on each draw that shows them.
- Frames: a key that changes the view draws at once. Content changes draw at most once per 50 ms (the application coalesces them with its timer). With no key and no content change, the pager draws nothing (the "Idle: zero frames" budget of [05-architecture.md, Performance budgets](../05-architecture.md#performance-budgets)).
- When the application replaces the `SessionState` (resume, a snapshot after a replay gap, a new foreground session), it bumps `source_epoch`. The pager drops its render cache, clamps `cell_index` to the new cell count, keeps follow, re-runs any active search, and shows `transcript reloaded from Hermes`. Cell ids are per `SessionState` and restart, which is why the epoch, not the id alone, keys the caches.
- While the overlay is open, [`P1-06`](https://github.com/infiquetra/talaria/issues/203) queues commits to native scrollback and writes them once, in order, on close. The pager never commits anything.
- Closing drops the render cache and keeps the `SearchIndex`.

## 10. Performance budgets and the benchmark

Budgets owned by this unit, measured by `crates/talaria-tui/benches/pager.rs` (`harness = false`, release build), at 160 by 48, drawing into ratatui's `TestBackend` and timing `handle_*` plus `draw` (terminal input and output are excluded, and the program says so in its output). Percentiles are nearest-rank over the stated samples. The budgets are enforced where [`P1-11`](https://github.com/infiquetra/talaria/issues/208)'s `bench` job runs (`.github/workflows/bench.yml`, `ubuntu-latest` by default, `macos-14` on demand); a local run prints the same table for information.

| Measure | Samples | Budget |
|---|---|---|
| Open plus first frame | 30 opens of a fresh `Pager` (index kept) | max ≤ 50 ms |
| Open plus first frame with a 64 KiB tool result as the last cell | 30 opens | max ≤ 50 ms |
| Line, page, half-page, top and bottom moves | a fixed sequence of 1,000 actions, including 200 that walk through the 1 MiB cell | p95 ≤ 16 ms, max ≤ 33 ms |
| First search keystroke (builds the index) | 30 runs, each with a fresh `SearchIndex` | max ≤ 50 ms |
| Later incremental keystrokes (`e`, `er`, `err`, `erro`, `error` after `e`) and `n`/`N` | 30 runs × 4 keystrokes plus 200 `n`/`N` | p95 ≤ 16 ms, max ≤ 33 ms |
| Idle | 1 s with no input and no content change | 0 frames |

The document is synthetic and deterministic, built from [`P1-05`](https://github.com/infiquetra/talaria/issues/202)'s public cell structs (no fixture loop, so it always terminates):

- 1,000 turns. Turn `i` has a user cell `Question <i>: please check the error handling in module <i % 37>.` and an assistant cell made from a fixed 4,096-byte Markdown template (a heading, a five-item list, an 8-line fenced code block and paragraphs) with `<i>` substituted once. That is 2,000 user and assistant cells and more than 4 MiB of text.
- Every 20th turn adds a final tool cell (`Succeeded`, a 2 KiB `result` of numbered lines, a 30-line `diff`).
- One extra tool cell with a 1 MiB `result` of numbered lines is inserted after turn 500 (the middle), so opening at the bottom does not render it and the move sequence walks through it.
- The 64 KiB case appends one tool cell with a 65,536-character result (Hermes's live cap, F13) at the end.

No warm-up is excluded: the first walk through the 1 MiB cell (its first render) counts in the move budget, and the index build counts in the first-keystroke budget. Neither figure is measured yet, so the developer writes these two benchmark rows first and runs them before tuning anything else; if either is over budget with the anchor model and caches described, that is issue stop condition 3.

The program prints a table (measure, samples, p50, p95, max, budget, pass) and exits non-zero when a budget is exceeded. One step is added to `.github/workflows/bench.yml`'s `bench` job: `cargo bench -p talaria-tui --bench pager` ([`P1-11`](https://github.com/infiquetra/talaria/issues/208) owns the file; `ci.yml` and the required checks are not edited). The resident-memory budget (≤ 100 MB after a 2,000-message session) stays with [`P1-11`](https://github.com/infiquetra/talaria/issues/208)'s harness; this unit must not break it.

## 15. Prior art

- Claude Code (research report [u12](../research/u12-claude-code-parity.json), features `int.tool-display` and `int.transcript`): Ctrl+O opens a detailed transcript with timestamps and the model per message; in full-screen mode `/` searches it, braces jump between user prompts, `[` writes it to native scrollback and `v` opens it in an editor. Talaria takes Ctrl+O, `/`, `n`/`N` and the braces. Talaria's finished output is already in native scrollback, so `[` has no purpose. `v` belongs with the external editor of [`P2-13`](https://github.com/infiquetra/talaria/issues/228). Timestamps and the model per message need fields the cells do not carry (non-goal).
- Hermes's terminal UI (F11, and the [Hermes terminal UI report u07](../research/u07-hermes-ink-tui.md)): its line pager's keys are kept; its close-at-end on Space is not.
- Hermes Desktop (F12, and row F03 of the [Desktop catalogue](../research/u06-hermes-desktop-catalog.md)): bounded history pages and a single-flight resume, both reasons for section 2.
- OpenAI Codex's transcript overlay and Claude Code's full-screen mode are the "optional full-screen view with virtualized history" pattern of [04-prior-art.md, Patterns to take](../04-prior-art.md#patterns-to-take), item 3.
