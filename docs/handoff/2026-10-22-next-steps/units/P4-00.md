# P4-00: Find out which configuration calls work on the gateway socket and which need the dashboard API (unit P4-00)

Status: `proposed`. The GitHub issue for this unit is the contract; this document is its reference specification. If they disagree, the issue wins and the disagreement is reported on the issue.

## How to use this document

This exploration has no product code. It produces a call matrix, a live probe, offline checks and a
finding. The issue says what to deliver and when to stop. This document gives the evidence behind
every static reading (`path:line` at Hermes v0.22.4), the exact list of matrix rows with their
parameters and expected outcomes, the matrix format, the probe's recording rules, the write-probe
protocol, and the exact rules each offline test enforces. Read section 1 before probing, section 3
while writing test 2, and sections 4 to 6 while writing the probe.

Hermes links point at the v0.22.4 tag. If `crates/hermes-contract/PINNED` names a later tag, read the
same paths at that tag (replace `v0.22.4` in the URL) and re-check every line number below; lines
move between releases. Background reading: the roadmap's
[phase 4](../07-roadmap-and-work-units.md#phase-4--configure-hermes-from-talaria), the architecture's
[configuration section](../05-architecture.md#configuration), and
[draft ADR 0007](../adr-drafts/0007-attach-to-the-hermes-session-authority.md) (item 4: "Dashboard
REST is used only for what has no RPC (the config schema, `.env`)").

## 2. The matrix format

`fixtures/configuration-surface/matrix.json` is one JSON object:

```json
{"hermes_release": "v0.22.4", "rows": [ { ...row... } ]}
```

The release tag comes from `crates/hermes-contract/PINNED`. The full commit ID appears only in the
finding, never in the matrix. Every row has exactly these 15 keys, always present (use `null` where
the table says so):

| Key | Type and allowed values |
|---|---|
| `id` | `C01` to `C61`, from section 3; unique |
| `question` | the Key Question number, 1 to 17 |
| `call` | the method name (`config.get`) or `VERB /route` (`GET /api/config`), or the control verb (`identify`) |
| `transport` | `socket`, `rest` or `control` |
| `ticket` | `{"purpose": "interactive" or "native-http", "scope": "profile" or "host", "profile": "fixture"}`, or `null` for a request sent with no ticket |
| `request_shape` | a JSON string: the parameter or selector names in sorted order, joined by `,` with no spaces, with values only for fixed Hermes key names and the allowed profile placeholders, for example `key=full`, `profile=default`, `profile=<unserved>`, `include_defaults=false,profile=fixture`, `api_key,slug`. A row that sends no parameters has the empty string `""` (written `(none)` in the section 3 table). Never a secret or a user value. The section 3 table is the exact value for every row |
| `outcome` | `ok` (a JSON-RPC `result`, or HTTP 2xx), `unknown_method` (JSON-RPC -32601), `rpc_error:<code>` (any other JSON-RPC error), `http:<status>` (a non-2xx HTTP status), `timeout` (no reply within 30 s), `connection_lost` (the connection dropped before a reply: outcome unknown, never success), or `not-probed` |
| `reason` | for `rpc_error` and `unknown_method`: `data.reason` when the reply has it, else `null` (legacy errors have none; never copy the message, which can echo input). At v0.22.4 the authority's -32601 carries `data.reason` `unknown_method` (`gateway/session_controls.py:305-310`), so C59's reason is expected to be `unknown_method`. For `http:<status>`: `Unauthorized`, `profile_scope_mismatch` or `no_such_api_endpoint` when the body's `detail` is one of those (the 404 detail starts `No such API endpoint`), else `null`. For `ok`, `timeout`, `connection_lost`: `null`. For `not-probed`: a short plain reason, required |
| `result_keys` | sorted top-level key names of the result or JSON body; `[]` for a non-object or an error; `null` when not probed and on every `static` row. Exception: when the top-level keys are names an operator chooses (environment variable names, provider ids, profile names, server names), record `[]` and put `entries: <n>` and `entry-fields: <sorted field names of one entry>` in `notes`. At v0.22.4 the only read row this applies to is C29 (`GET /api/env` is keyed by variable name, `hermes_cli/web_routers/config_env.py:259-325`); the builder re-checks every read row's handler at the pin. Extra shape facts (one level down, counts, classes) go in `notes` |
| `latency_ms` | the median of the timed runs as an integer when `evidence` is `live`; `null` when `static` |
| `side_effect` | `none`, `write-restored`, `write-residue` (restored but the file differs, see section 5), or `not-probed` (every `static` row) |
| `live_effect` | one of `applies-now`, `next-session`, `needs-restart` or `unknown` only on a W row (C10, C19) whose `evidence` is `live`; `null` on every other row, including static write rows and W rows the operator has not run. A static write row's predicted effect goes in `notes` as `predicted-effect: <value>` (for example C39: `predicted-effect: next-session`) |
| `evidence` | `live` or `static` |
| `source` | Hermes repository-relative `path:lines` at the pinned release, for example `gateway/session_config.py:65-113`; never a leading `/` |
| `notes` | plain text, no values; fixed phrases listed in section 4 |

A row whose `evidence` is `static` (every S row, and a W row before the operator's run) follows these
rules: `outcome` is the outcome predicted from the source when the source settles it, else
`not-probed`; `reason` follows the `outcome` rules above (so a predicted `ok` has `null`, a predicted
`http:403` has `profile_scope_mismatch`, `not-probed` has its plain reason); `result_keys`,
`latency_ms` and `live_effect` are `null`; `side_effect` is `not-probed`; and `notes` starts with a
sentence `not sent: <why>`. A W row before the operator's run is `outcome: not-probed` with reason
`write run not yet done by the operator`.

## 4. Probe rules

### 4.1 Connections and timing

- Socket rows: mint with `mint_ticket(home, &endpoint, &fixture, Purpose::Interactive,
  Scope::profile())` (IP) or `Scope::host(Purpose::Interactive)?` (IH), `connect`, `handshake`, then
  `Client::start`. `P1-01`'s handshake already sends `client.capabilities
  {server_requests: true}` once; the probe never sends it again. Send each method with
  `client.call_raw(method, params, CallOptions { timeout: Some(Duration::from_secs(30)) })`.
- Map the result: `Ok(_)` is `ok`; `Err(CallError::Rpc(e))` with `e.code == -32601` is
  `unknown_method`; other `Rpc(e)` is `rpc_error:<e.code>` with `reason = e.reason`;
  `TimedOut` is `timeout`; `Unknown` is `connection_lost`; any other `CallError` stops the probe with
  the error's `next_step()`.
- REST rows: one fresh `native-http` ticket per request (`Scope::profile()`), minted immediately
  before the request. One `tokio::net::TcpStream` per request to the host and port of
  `endpoint.api_origin()`. Send exactly:
  `<VERB> <path?query> HTTP/1.1`, `Host: <host>:<port>`, `Connection: close`,
  `Accept: application/json`, the ticket header when the row has one, and for a body
  `Content-Type: application/json` and `Content-Length: <n>`. Never an `Origin` header except in C22.
  Read until end of stream (`Connection: close` guarantees it), parse the status line, and decode the
  body by `Content-Length` or `Transfer-Encoding: chunked` (handle both). Wrap the whole request in
  `tokio::time::timeout(30 s)`.
- Latency span: socket rows from just before `call_raw` to its return; REST rows from just before
  the TCP connect to the end of the body (the mint is excluded and timed separately in `notes` as
  `mint_ms`). Each read row runs four times: the first is a warm-up and is discarded, the median of
  the other three is `latency_ms`. Ticket-rule rows (C16, C21 to C24) and controls (C59 to C61) run
  once. Write rows run once each way and record the write's latency. A run that times out counts as
  30000 ms in the median; a `connection_lost` run counts as its elapsed time.
- When the three timed runs of a row agree, record that outcome, its `reason` and its
  `result_keys`. When they differ, record the first non-`ok` outcome among them (with its `reason`
  and `result_keys`) and add the note `outcomes-differ: <outcome> <count>, ...` listing every outcome
  seen in the timed runs. When the discarded warm-up's outcome differs from the recorded one, add
  `warm-up: <outcome>` (a cold dashboard mount can show here).
- The three live tests share the gateway and the temporary matrix file, so each holds one lock for
  its whole run: `static PROBE_LOCK: tokio::sync::Mutex<()> = tokio::sync::Mutex::const_new(());` in
  `live_config_surface.rs` (a `tokio` mutex, because the guard is held across `.await` and clippy
  refuses a `std` guard there). Running the binary with no name filter is then safe. The first REST request after a gateway start (cold
  dashboard mount, S1) is reported only in the finding, with the source version, and only if the
  operator provides a freshly started gateway; write the gateway's `supervisor` beside it if the
  operator knows how it was started (`P1-01`'s `Endpoint` does not expose `supervisor`).
- On any 401, run discovery again and append `gateway-state: ready` or the discovery error's kind
  to `notes`, so a refusal is not confused with a draining or restarting gateway.
- Every discovery the probe runs (the 401 re-check above and C54) is
  `discover_with(&env.home, &DiscoverOptions { ensure: EnsurePolicy::Never, ..Default::default() })`,
  the same policy `live_preconditions()` uses (`P1-01` unit specification section 13.1). Never call
  `discover()`: its default policy `EnsurePolicy::Run` runs `hermes gateway ensure`, which can start a
  gateway, and agents never start or restart the gateway.

### 4.2 Recording shapes, not values

- Keep the status, the outcome class, the `reason` per section 2, the sorted top-level key names and
  the latency. Drop the body after the classification steps below.
- A body may be held in memory only to compute a class or a comparison (4.3, 4.4, 5). Nothing from a
  body is printed, logged or written except those classes, counts, booleans and key names.
- Key-name guard (`config_probe::key_name_is_safe`): a recorded key name must be 1 to 64 characters,
  contain no `/`, `\`, `~` or whitespace, and not be a run of 40 or more token characters
  (`[A-Za-z0-9_-]`). An unsafe name is replaced by `<unsafe-key>` and the row gets the note
  `unsafe key name dropped`.
- C01: also record the sorted keys of `result.config` as `config-keys: a, b, c`.
- C11/C12: in the finding (not the matrix), record the number of `fields`, the `category_order`
  list, the union of attribute names across all field entries, and whether any entry carries
  `default` or a restart flag. These are fixed Hermes names, not values.
- C29 (`GET /api/env`): the reply is one object keyed by environment variable name
  (`config_env.py:259-325`), and an operator can choose those names. `result_keys` is `[]`; `notes`
  holds `entries: <n>; entry-fields: <sorted field names of the first entry>` (at v0.22.4 the fields
  are fixed names such as `is_set`, `redacted_value`, `category`). Never record a variable name.
- C41, C42: record `profiles: <n>`, `same-as-served: true|false`, `includes-parked: true|false`.
  Compare by profile name in memory: the served names are `endpoint.profiles().iter().map(|p| &p.name)`
  (`ServedProfile { name, id }`), the parked names are the first element of each
  `endpoint.parked()` pair (`P1-01` unit specification section 11.1; re-check at its merge). Never
  write a name. At v0.22.4 the top-level keys are fixed: `GET /api/profiles` returns `{profiles}`
  (`hermes_cli/web_routers/profiles.py:796-804`).
- C43: the result can list MCP server names; record top-level keys only.
- C48: compare `result.home` in memory with the id of the served profile named `default`
  (`ProfileId` implements `AsRef<str>`); record `home-matches-default: true|false`.
- C54 (`identify` through discovery): `result_keys` is the sorted subset of this fixed list of
  `Endpoint` accessor names whose value is present: `api_origin`, `authority_epoch`, `capabilities`,
  `code_sha`, `code_version`, `instance_id`, `parked`, `profiles`, `runtime_protocol`, `state`.
  "Present" means `Some` for the two `Option` accessors, non-empty for the three slices, and always
  for the other five. Only names are recorded, never a value (the commit ID stays in the finding).
  `Endpoint` has no `supervisor` accessor, so it is not in the list.

### 4.3 Secret classes for C15

Walk the `GET /api/config` body in memory the way Hermes's own masker `redact_config_value` walks a
configuration (`hermes_cli/config.py:2974-2990`): for each object entry, test the entry's key name
alone (one segment, never a dotted path) with `is_credential_key`; recurse into objects and lists;
an entry whose key is credential-shaped and whose value is a string or `null` is classified, one
whose value is an object or list is walked into, and one whose value is a number or boolean is
skipped. `is_credential_key(name: &str) -> bool` is an exact port of Hermes's
`_is_secret_config_key` (`config.py:2965-2971`) together with `_is_env_config_key`
(`config.py:871-881`) and the set `_ENV_CONFIG_KEYS` (`config.py:858-868`, copied name for name):

1. Let `leaf` be the name lower-cased with `-` replaced by `_`.
2. If the name has no `.` and its upper-cased form is in `_ENV_CONFIG_KEYS`, or ends with
   `_API_KEY`, `_TOKEN` or `_SECRET`, or starts with `TERMINAL_SSH`, it is an environment-routed
   key: it is credential-shaped unless `leaf` ends with `_url`, `_host`, `_user`, `_id`, `_domain` or
   `_scheme`.
3. Otherwise it is credential-shaped when `leaf` is one of `api_key`, `apikey`, `key`, `token`,
   `access_token`, `refresh_token`, `id_token`, `secret`, `client_secret`, `password`, `passwd`,
   `authorization`, `private_key`, `bearer`, `jwt`, or ends with `_api_key`, `_token`, `_secret`,
   `_password`, `_key`, `_access_key`.

So an `mcp_servers.<name>.env` entry counts only when its own name passes this rule (`FOO_URL` does
not). Classify each credential-shaped leaf as exactly one of:

| Class | Rule |
|---|---|
| `empty` | empty string or null |
| `env-reference` | matches `^\$\{[A-Za-z_][A-Za-z0-9_]*\}$` |
| `masked` | starts with `«redacted:`, equals `***`, or matches `^.{4}\.\.\..{4}$` |
| `plain` | anything else |

Record in `notes` only `secret-leaves: <n>; empty <a>, env-reference <b>, masked <c>, plain <d>`.
The static reading S13 predicts `plain` for any secret written in the file. The fixture profile may
hold none, in which case `secret-leaves: 0` is the honest result and the finding says the masking
question stays open on this profile.

### 4.4 Fixed note phrases

`config-keys: ...`, `entries: <n>`, `entry-fields: ...`, `profiles: <n>`, `same-as-served: ...`,
`includes-parked: ...`, `home-matches-default: ...`, `secret-leaves: ...`, `mint_ms: <n>`,
`gateway-state: ...`, `outcomes-differ: ...`, `warm-up: <outcome>`,
`refutes: expected <predicted outcome>` (section 6.2), `predicted-effect: <value>`,
`optional: <names>` (static rows), `unsafe key name dropped`; for static rows and unrun W rows a
sentence starting `not sent:`. `unlisted` is never used (test 3 computes it). Separate phrases with
`; `.

## 5. The write protocol (operator only)

`probe_writes_round_trip_on_fixture` checks the opt-in first, before `live_preconditions()` and
before any discovery: when `write_probe_allowed("fixture", std::env::var("TALARIA_PROBE_WRITES").ok().as_deref())`
is `Err`, it prints `LIVE_CONFIG_SURFACE_RESULT: SKIPPED (write opt-in not set)` and
`requests sent: 0` with its own `println!` (not `report_skip`, which would panic under
`TALARIA_LIVE_REQUIRE=1`), sends nothing at all (not even `identify`), and passes. Only with the
opt-in set does it call `live_preconditions()`; a missing gateway then goes through `report_skip`
and panics under `TALARIA_LIVE_REQUIRE=1`. `requests sent` counts every request the test sends:
control-socket requests, socket calls and REST requests.

Guards, in `crates/hermes-client/tests/config_probe/mod.rs` and tested offline:

- `write_probe_allowed(profile: &str, writes_env: Option<&str>) -> Result<(), String>`: `Ok` only
  when `writes_env == Some("1")` and `profile == "fixture"`.
- `config_set_allowed(key: &str, write_allowed: bool) -> bool`: `false` for every key in S8's
  accepted set (section 1) unless `write_allowed`; `true` otherwise. The probe calls it before every
  `config.set` (so C08 and C09 pass, C10 needs the opt-in).

Operator preconditions for the write run: the `fixture` profile's `config.yaml` sets
`display.skin` and `display.show_cost` explicitly (any values). The reason: `save_config` strips a
value equal to its default unless the key was already explicit (S5), and a deep merge cannot delete a
key, so a restore can return an explicit key to its value but cannot return an absent key to absent.

Steps for each of C10 and C19:

1. Read `GET /api/config?profile=fixture&include_defaults=false` into memory (document A). If the
   key is not present in A, do not write: mark the row `not-probed`, reason
   `not sent: key not explicit in fixture configuration`.
2. Write the new value (C10: the skin named above; C19: the opposite boolean). Record outcome,
   reason, latency.
3. Read the value back through the socket (`config.get key=skin` for C10) or REST (C17 shape for
   C19) and record `live_effect`: `applies-now` when the next read returns the new value. The probe
   creates no session, so the effect on a running session is not probed; the finding states it from
   the source (S5: only `approvals.mode` triggers a `session.info` broadcast; S8: `skin` broadcasts
   `skin.changed`; S15: `POST /api/model/set` applies to new sessions).
4. Write the original value back.
5. Read document B as in step 1. `side_effect` is `write-restored` when B equals A, else
   `write-residue` with the note `restore left the file different`, and the probe fails.

The operator then opens the fixture profile's `config.yaml` and notes whether its comments survived
(S5 predicts they do). That answer is an open question in the finding; it does not block the merge or
`P4-01`.

### 6.2 What makes a live test pass (tests 9 to 11)

The probe exists to record what the gateway does, including where it contradicts a static
reading. So a live result that differs from the section 3 prediction is never a test failure:

- For every row it owns, the test prints one line
  `ROW <id> <outcome> <reason or -> <latency_ms> as-predicted` or the same line ending
  `REFUTED (expected <predicted outcome>)`, and adds the note `refutes: expected <predicted outcome>`
  to a refuted row. It then prints the row as `MATRIX_ROW <one-line JSON>`.
- A test prints `LIVE_CONFIG_SURFACE_RESULT: PASSED` and passes when every row it owns has a live
  outcome (none `not-probed`), the temporary matrix was written, and its own printed output passes
  the privacy scan of test 4 (no ticket, no path).
- It fails (prints `LIVE_CONFIG_SURFACE_RESULT: FAILED (<reason>)` and panics) when a row could not
  be recorded (a `CallError` the mapping in 4.1 does not cover, a ticket that cannot be minted, a
  matrix that cannot be written), when its output fails the privacy scan, when a write round trip
  ends `write-residue`, or when a control row differs: C59 must be `unknown_method`, C60 `http:404`,
  C61 `http:401`. The controls check the probe itself (a wrong header or framing shows there first),
  so a differing control is investigated, not recorded as a finding; if the probe is right and the
  pinned gateway answers differently, that is a stop condition in the issue.
- Ticket rules (C16, C21 to C24) are findings, not controls: a 2xx or other status there is
  recorded, printed as `REFUTED`, and reported in the finding as a security observation; the test
  still passes. Their bodies are dropped unread like every other body.

## 7. Producing the committed matrix

`fixtures/configuration-surface/static-rows.json` holds the 11 static rows (S in section 3), written
by hand from the source with `evidence: "static"` and the static-row rules of section 2.

Each live test, while holding `PROBE_LOCK` (section 4.1), does this with the temporary file
`$CARGO_TARGET_TMPDIR/config-surface/matrix.json`:

1. If the file exists, read it. Otherwise start from `{"hermes_release": <PINNED tag>, "rows": []}`
   plus every row of `static-rows.json`, and add C10 and C19 as unrun W rows (section 2:
   `not-probed`, reason `write run not yet done by the operator`).
2. Replace, by `id`, only the rows the test owns (section 3, "Which live test sends which row");
   leave every other row as it is.
3. Sort rows by `id`, write the whole document to a sibling temporary file and rename it over the
   original, so a crash never leaves half a file.

The agent tester runs `probe_reads_on_fixture` and `probe_ticket_rules` in the builder's clone, so
both land in one file there. The operator runs the write test in their own terminal and clone, so the
builder does not rely on that file: the write test prints each of its rows as
`MATRIX_ROW <one-line JSON>`, the operator pastes those two lines into a pull request comment, and the
builder replaces C10 and C19 in the committed matrix with them by hand. The builder then copies the
temporary file to `fixtures/configuration-surface/matrix.json`, reads the diff by eye, and commits
it. The committed `matrix.json` is the source of record. Test 1 also asserts that every row in
`static-rows.json` appears unchanged in `matrix.json`.

At the timebox (the issue's "Timebox"), rows not yet run stay `not-probed` with a reason, and the
pull request is opened as a draft: test 2 stays red because R rows are not `live`, and nobody edits
