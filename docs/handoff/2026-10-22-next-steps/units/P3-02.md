## 0. What this unit is, in one paragraph

`P3-01` gives Talaria a fleet registry: every live Hermes session across the served profiles, grouped by state, with one "needs you" queue. This unit draws it and makes it actionable. `/fleet` opens a full-screen overlay (the alternate screen, leaving nothing behind) listing the registry's rows grouped `NEEDS YOU`, `WORKING`, `FAILED`, `DONE`, `IDLE`. On any row the operator can **peek** (Space: a panel with the session's latest output, or the open approval or question, updated live), **reply** (`r`: a prompt that Hermes queues behind a running turn instead of interrupting it), **answer** (`a`: the approval or question card in the peek panel), **stop** (`x`, confirmed with a second `x`: interrupts the running turn), **open** (Enter: the session becomes the foreground session, through `P2-07`'s `switch_foreground`) and **filter** (`/` for text, Tab for profile). It is Talaria's counterpart of Claude Code's agent view (peek with Space, attach with Enter) and of Hermes Desktop's chat tiles (each tile attaches a session with `session.resume` and stops it with `session.interrupt`).

## 3. Design

### 3.1 A peek attaches the session

Everything a peek must do needs an attachment on some connection: `prompt.submit` and `approval.respond` refuse callers that are not subscribers (F2, F5); the latest output and the open prompt come from the resume snapshot and the session's events, which reach only attached connections (`P3-01` specification F16). `session.interrupt` does not need an attachment, but it needs the current `execution_generation`, which only the snapshot and the session's events carry (`session.info` and `session.active_list` do not; F4, F13). Hermes Desktop does the same: a tile attaches with `session.resume` and tracks the generation (F13). This departs from the prior-art pattern "peek and reply without attaching" ([patterns to take](../04-prior-art.md#patterns-to-take), pattern 5), which describes Claude Code's local agents; under Hermes a peek must attach.

So **Space attaches the row's session; moving the cursor never does.** An attach is not free (F7): it returns the whole history, cancels a pending close and re-reads the session's settings. That is acceptable for an explicit operator action on one session, and wrong for every row the cursor passes over. Only one session is peeked at a time; peeking another row detaches the first (no `end_reason`, F8).

`P3-01` decided the registry reads without attaching (its decision 2). This unit does not change that: the registry stays read-only, and the peek reports its live view to the registry with `FleetHandle::observe_subscribed` while it is attached, exactly as `P3-01` section 17 asks.

### 3.2 The peek has its own connection

The peek uses a **peek link**: a profile-scoped connection for the peeked row's profile, opened with `P1-12`'s `ConnectionService::open` (a copy of the launch with the row's profile and no gateway start), the same way `P2-07` opens a link for a switch to another profile. Reasons:

1. `P1-03`'s replay sends `session.events.since` without `profile` (`P3-01` specification section 17), so a session of another profile cannot be tracked on the foreground link or on `P3-01`'s host-scoped fleet link.
2. Events of the peeked session must not reach the foreground's reducer. A separate link keeps `app.rs`'s routing unchanged: everything on the foreground link is the foreground session.
3. `P3-01`'s fleet link must stay free of attachments (its allow-list test forbids `session.resume`).

The peek link is opened on the first peek, reused while the operator peeks rows of the same profile, replaced when a row of another profile is peeked, and closed (after a detach) when the overlay closes. It never starts a gateway. This is a third connection while the overlay is open, after the foreground link and the fleet link, and a further exception to draft decision 0007 point 2 ("one connection per process"); the issue asks the operator (question 1, which also covers the ignore rule of 3.4, `P3-03`'s launch connections and `P3-09`'s resident link, further exceptions of the same kind). The alternative, tracking a same-profile peek on the foreground link, needs `app.rs` to route events by session and is rejected for this unit.

The foreground row is never attached again: its peek reads the foreground `SessionState`, and its reply, stop and answer use the foreground's own paths (`P1-12`, `P1-09`).

### 3.3 Reply is a queued prompt

A reply is `prompt.submit` on the peek link. Hermes builds every submission as a queue admission (F2): a reply to a running session waits for the current turn, then runs; a reply to an idle session starts a turn. It never interrupts. This matches Claude Code's agent view ("replies to a working session are queued, not interrupting"). Steering a running turn (`session.steer`) is `P2-08`'s feature inside an open session and is not offered here.

The reply goes through the peeked session's own `P1-05` state, like the foreground composer: `Event::Submit { text, submission_id }` gives `Effect::SendPrompt`, which `SessionService::execute` sends. The submission id comes from `P1-12`'s generator (`talaria-<launch id>-<n>`), so ids are unique across the foreground and the peek. A reply whose outcome is unknown (the connection dropped, no reply in time) is kept with its submission id; sending it again resends the identical params, and Hermes answers the first admission again instead of queueing twice (F3).

### 3.4 Server requests on the peek link

Because the peek link is attached, Hermes writes the session's server requests to it too (F11). The first answer from any viewer settles a request, and an error answer settles it as a skip. `P1-09`'s rule for the foreground, refusing kinds it cannot show, would therefore skip a request that another window (Desktop, another Talaria pane) is about to answer. So the peek link:

- hands `sudo`, `secret`, `vault.code` and `vault.unlock_prompt` (the kinds `P1-09`'s `policy_for` maps to `Masked`) to a `P1-09` `PromptService` owned by the peek, so the peek panel shows the masked card and the operator can answer it;
- leaves every other kind alone with `P1-02`'s `Responder::ignore()`, which writes nothing (the request stays open for other viewers or ends at its own timeout);
- never sends -32601, -32603 or any other error answer, and never drops a responder undecided (that writes -32603 while connected, `P1-02` section 6.1).

Which kinds are ignored in practice: the Desktop-window kinds (`theme.*`, `preview.*`, `window.read`, `terminal.read`, `tour`, `setup_beat`, `display.install.sudo`, `vault.save_login`), the batch `clarify` request (sent only for turns whose submitter committed `clarify_batch`, for example Hermes's own terminal UI; that viewer answers it) and `approval` (never sent by the canonical gateway). Approvals and single questions are events (F17) and are answered through the peek's card, so UAT-3 does not depend on any server request.

This rule is a second exception to draft decision 0007, point 3 ("answers every server request at once ... every other request gets a JSON-RPC error"). Operator question 1 covers it, and the `DECISIONS.md` entry of section 16 names point 3. Declaring `server_requests: false` on the peek link would not avoid it: the canonical gateway writes requests to every attached transport regardless (F18).

Costs of ignoring: when no other viewer is attached, an ignored request waits for its own timeout (120 s for `sudo` and `secret`, which the peek shows anyway; the clarify timeout for a batch clarify) before the agent goes on. The pull request and the operator notes say so.

`P1-09`'s foreground policy still answers unshowable kinds with an error at once (its F-38, accepted in phase 1). When the foreground pane of another Talaria process is attached to the same session, that error can settle a request this peek would have left open (edge E2). This unit does not change `P1-09`'s policy (its `prompts` modules are outside this unit's work surface); the issue lists it as a non-goal.

A masked request that Hermes sent before the peek attached is not re-sent (F11: one write at request time); it is invisible to the peek. `P3-01` already records that an unattached session blocked on sudo reads `working`; the journal entry in section 16 adds this.

### 3.5 Keys and focus

The overlay owns every key while it is open (like `P2-07`'s picker); nothing reaches the composer and nothing interrupts the foreground agent. Focus is one of:

| Focus | Entered by | Keys go to | Left by |
|---|---|---|---|
| `List` | opening the overlay | the fleet key map (`KeyContext::Fleet`) | Esc unwinds (kept filter, then peek, then overlay; 5.6); Ctrl+C closes the overlay at once |
| `Filter` | `/` | the filter line (printable text, Backspace, Enter keeps, Esc clears) | Enter (keeps), Esc or Ctrl+C (clears) |
| `Reply` | `r` | the reply editor (printable text, paste, Backspace, Left, Right, Home, End; Enter sends) | Enter (sends), Esc or Ctrl+C (keep the draft for that row) |
| `ConfirmStop` | `x` on a running row | the next key | `x` stops; any other key, Esc and Ctrl+C included, cancels with `Stop cancelled.` |
| `Answer` | `a` while the peek shows an open card | the peek's `P1-09` `PromptStack` (digits, arrows, Enter, **Esc deny/skip**, Tab note), after its 250 ms guard | the card leaves (answered, settled elsewhere, withdrawn) or Ctrl+C (back to `List`, nothing sent) |

In `Answer` focus Esc belongs to the card, exactly as on the foreground (`P1-09` F-40: Esc denies an approval, skips a question, declines a masked prompt); it never unwinds the overlay. Ctrl+C in `Answer` focus is intercepted before the card: in the overlay, Ctrl+C never stops anything. This differs from the foreground card, where Ctrl+C is "deny and stop" (`P1-09` 5.5); the overlay's only stop is `x`. The footer in `Answer` focus shows the card's hint with its `Ctrl+C …` part replaced by `ctrl+c back to list`.

### 3.6 Where the code lives

- `talaria-core::fleet_view` (pure): view state, inputs, effects, row text, filter, grouping. No input/output, no clock reads (time comes in as `now: f64`), no terminal library.
- `talaria-app::peek` and `talaria-app::fleet_actions`: the peek session (link, resume, detach, events, reply, stop, answer, server requests) and the execution of `FleetViewEffect`s. `app.rs` (owned by `P1-12`) is touched minimally: open and close the overlay, route keys and peek events, run effects.
- `talaria-tui::fleet_view`: drawing the list and the peek panel into `P1-06`'s overlay buffer, and the `KeyContext::Fleet` entries in `P1-08`'s `keys.rs`.

## 5. State rules (`talaria_core::fleet_view`)

### 5.1 Rows, groups and the cursor

- `Snapshot` replaces rows, queue and profiles. Rows are grouped by `RowState` in `P3-01`'s order (`NeedsYou`, `Working`, `Failed`, `Done`, `Idle`) and keep `P3-01`'s order inside a group (its `rows()` is already canonical). Groups with no visible row are omitted.
- The profile column is shown only when the snapshot has more than one profile with rows.
- The cursor is a `RowKey`, never an index. After a snapshot it stays on the same session if that row is still visible; if not, it moves to the row now at the old row's position in the visible list (or the last row); with no visible row it is `None`.
- The first snapshot after opening puts the cursor on the first `NeedsYou` row, else the first row.
- Up and Down move within the visible list and stop at the ends; PageUp and PageDown move by `page` rows; Home and End go to the first and last.

### 5.2 Filters

- `/` enters `Filter` focus with the current text. Printable characters append; Backspace deletes the last character; Enter keeps the text and returns to `List`; Esc clears the text and returns to `List`. The filter applies on every keystroke.
- A row matches when the lower-cased query is a substring of the lower-cased title, profile, short model (text after the last `/`), `session_id`, or the row's detail. An empty query matches every row.
- Tab cycles the profile filter `All`, then each profile in `P3-01`'s `profiles()` order, then `All`; Shift+Tab cycles backwards. A profile filter naming a profile that left the snapshot falls back to `All`.

### 5.3 Peek

- Space on a row emits `OpenPeek(key)` and sets `peek = (key, Opening)`. Space on the peeked row emits `ClosePeek`. Space on another row emits `OpenPeek(other)`; the service detaches the first.
- `Peek { key, status }` updates the status only when `key` is the peeked key (late results for an earlier peek are dropped).
- Peeking a `Done` or `Failed` row also emits `Acknowledge(key)` (`P3-01` section 17).
- A peeked row that leaves the snapshot keeps its peek panel open until the operator moves or closes it; the panel header shows `(ended)`.

### 5.4 Reply

- `r` on a row enters `Reply` focus with that row's saved draft (empty at first). If the row is not peeked, `OpenPeek(key)` is emitted first (a reply needs the attachment).
- Text, Paste, Backspace, Left, Right, Home, End edit the draft. A paste is inserted whole; line breaks are kept in the text and drawn as `↵`.
- The editor's prompt line is section 8's `Reply to <title>: ` followed by the draft.
- Enter on a blank draft (empty or only whitespace) does nothing. Otherwise it emits `SendReply { key, text }` with the text as typed, sets the row's in-flight flag, clears the draft and returns to `List`.
- Esc keeps the draft for that row and returns to `List`. Drafts live until the overlay closes.
- At most one reply per row is in flight; `r` on a row with a reply in flight shows `Sending the last reply…` and opens nothing.
- **Unconfirmed replies are kept per row**, in the view (`RowFlags::unconfirmed`) and in the service (text and submission id by `RowKey`). Moving the peek to another row, or replacing the peek link for another profile, keeps them; only a definite outcome or the overlay closing ends them. A row with an unconfirmed reply shows `r` as "resend": `r` (which emits `OpenPeek(key)` first when the row is not peeked), then Enter on a blank draft emits `ResendReply(key)` and sets the in-flight flag; the service resends the identical params on the row's peek. Enter on a non-blank draft sends nothing, keeps the draft and shows `The last reply to "<title>" may not have been sent. Clear this line and press enter to resend it.` (sending new text while the first may have landed could queue two prompts).
- `ReplyDone { key, outcome }` clears the row's in-flight flag and sets the outcome text (section 8). `Refused` and `NotAttached` put the reply's text back into the row's draft. `Unknown` marks the row unconfirmed. Any definite outcome of a resend clears the mark.
- **The may-not-have-been-sent scrollback notice fires only when the overlay closes** (Esc or Ctrl+C from the list, `Open`, `a` on the foreground row): the executor of `Close` reads `unsettled_replies()` and writes one section-8 notice per row. Closing or moving a peek writes no notice.
- `r` on a row whose peek is still `Opening` works as usual; the executor holds the `SendReply` until the open finishes (section 9.1).

### 5.5 Stop

- `x` on a row whose state is `Working` or `NeedsYou` (the foreground row included) enters `ConfirmStop` and shows the confirmation text (section 8). The next key: `x` emits `Stop(key)` (preceded by `OpenPeek(key)` when it is not peeked) and returns to `List`; any other key, Esc and Ctrl+C included, shows `Stop cancelled.` and returns to `List` without acting on that key.
- `Stop(key)` for a row whose peek is `Opening` is held by the executor until the attach succeeds; it is never sent with a guessed generation, and a failed attach gives `StopDone { NotAttached }` with nothing sent.
- Emitting `Stop(key)` sets the row's stop latch (`RowFlags::stop_in_flight`). While it is set, `x` on that row shows `Stopping "<title>"…` and emits nothing (no confirmation, no second stop).
- `StopDone { key, outcome }` clears the stop latch and sets the outcome text.
- `x` on a `Failed`, `Done` or `Idle` row shows `Nothing is running in "<title>".` and emits nothing.
- A stop never answers an open masked request (`sudo`, `secret`, vault). Its card stays in the peek until Hermes withdraws it with `request.cancel` (reason `interrupted` after the stop, F20; or `timeout`), or the peek closes, which ignores it (9.8).

### 5.6 Open, answer, close

- Enter on a row emits `Acknowledge(key)` when the row is `Done` or `Failed`, then `Open(key)`. The executor closes the peek and the overlay before calling `switch_foreground` (section 9.6).
- `a` acts on the peeked session (the panel), wherever the cursor is. When the peek is `Open { has_open_prompt: true }`: for a background row it emits `FocusAnswer` and enters `Answer` focus; for the foreground row it emits `Close` (the foreground card then takes the keys, 9.7). In every other case (no peek, peek opening or failed, no open card, on any row including the foreground row) it shows `Nothing to answer in this session.` and emits nothing. For the foreground row the executor feeds `Peek { key, status: Open { has_open_prompt, running } }` from the foreground `SessionState` and `PromptStack`.
- In `Answer` focus every key, Esc included, goes to the peek's card (the app forwards it); Ctrl+C returns to `List` and sends nothing; `AnswerFocusEnded` returns to `List`.
- Esc unwinds one layer: `Reply` (draft kept), `Filter` (text cleared) or `ConfirmStop` (`Stop cancelled.`) to `List`. In `List`: a kept filter text is cleared first; then an open peek closes (`ClosePeek`); then the overlay closes (`Close`). Ctrl+C acts as Esc in `Reply`, `Filter` and `ConfirmStop`; in `List` it closes the overlay at once (`ClosePeek` when needed, then `Close`); in `Answer` it returns to `List`.
- No input ever produces an effect that interrupts or changes the foreground session, except `Open` and the foreground row's `Stop`/`SendReply`.

### 5.7 Open at a row (`open_at`, for `P3-06`)

`open_at(key)` is applied right after the overlay opens and the latest snapshot is fed. When no snapshot has arrived yet (the view shows `Looking for sessions…`), `open_at` emits nothing, shows no notice and holds the key; the first `Snapshot` input then applies the rules below to the held key instead of placing the cursor on the first needs-you row, and drops it. A later `open_at` replaces a held key. When the row is in the snapshot: the cursor moves to it and the rules of Space apply (`OpenPeek(key)`, plus `Acknowledge(key)` for a `Done` or `Failed` row). When it is not: the notice `That session is no longer in the fleet.` and no effect. `fleet_actions::open_fleet_view_at(app, key)` is the app entry point `P3-06` calls.

### 5.8 Redraw

`needs_redraw()` is true after an input that changed anything drawn: the visible rows and their texts, the cursor, focus, the notice, the peek status, the size, or a `Tick` that changes any age text (ages are minute-grained, so at most one frame per minute when nothing else changes). A snapshot whose visible rows are identical, or whose version equals the last drawn version, does not set it.

## 6. Layout

The overlay fills the screen (P1-06's `open_overlay`/`draw_overlay`/`close_overlay`). Screen rows from the top:

1. Header: `Fleet · <n> sessions` (`<n>` is the total row count before filters), then ` · profile <p>` when the profile filter is set, then ` · filter "<q>"` when a filter is kept. Right-aligned: the link note (`connecting…`, `reconnecting: <reason>`, `fleet connection failed: <reason>`).
2. When the scope is one profile: `Showing profile <p> only: the gateway refused a host-scoped ticket.`
3. The list: group headers (`NEEDS YOU (<n>)` and so on, counting visible rows) and rows.
4. When the peek is open: a separator line `── peek ──` and the peek panel.
5. `not listed: <profile> (<reason>)` lines for profiles that are not `Listed` (at most two lines; then `… and <k> more profiles not listed`).
6. The notice line (empty when none).
7. The footer: the key hints of the bound actions, `enter open · space peek · r reply · x stop · / filter · esc close`, plus `a answer` when the peek shows an open card. In `Reply` focus: `enter send · esc keep draft`. In `Answer` focus: the card's own hint with its `Ctrl+C …` part replaced by `ctrl+c back to list`. In `ConfirmStop`: the confirmation text replaces the notice.

**Peek panel height.** When the screen has at least 20 rows, the panel takes the lower half (at least 8 rows) and the list keeps the cursor row visible in the upper half. Below 20 rows the panel replaces the list while open.

**Row columns**, left to right, separated by two spaces: cursor (`›` or space), glyph, title (`(untitled)` when empty; ` (here)` for the foreground row; ` (ended)` for a `gone` row; ` (hidden)` for an `unlisted` row, as `P3-01`'s list output), profile (only per 5.1), short model (`-` when none), detail, age (`P2-07`'s `format_age` of `state_since`), cost (`$<0.00>` only when `cost_usd` is `Some`). Widths: title 28, profile 12, model 18, age 4, cost 7, detail takes the rest. Values longer than their column are cut with `…`. Below 100 columns the cost column is dropped; below 80 the profile column; below 60 the model column. When the window is narrower than 40 columns **or** shorter than 10 rows, only `Window too small for the fleet view. Esc closes.` is drawn. Stale rows (`stale: true`) are drawn with the dim style; their text is unchanged.

**Peek panel content** (from the peeked `SessionState`, or the foreground state for the foreground row):

1. Header: `<glyph> <title> · <profile> · <model> · <state word> <age>`.
2. When `P1-09`'s `PromptStack` (synced with the peeked session's open prompts and the peek's masked requests) has a first card: that card, drawn as on the foreground, followed by `a answer` in the footer.
3. Otherwise the tail of the transcript: the cells of the latest turn, drawn with the same cell-to-lines functions the inline history uses (`P1-06`, `P1-07`, `P2-01`), keeping the last lines that fit. While a turn runs, the last line is the activity line (`✻ <activity>` or `✻ working`).
4. A finished turn ends with its outcome line: `✓ completed`, `■ interrupted` or `✗ failed: <error text>` (from the turn's `message.complete`).
5. `Opening <title>…` while opening; the failure text of section 8 when it failed.

Every Hermes string drawn passes `P1-06`'s `history::sanitize`; widths use `unicode-width`'s non-CJK width, as `P2-07`.

## 9. The peek session (`talaria_app::peek`)

### 9.1 Open

1. If a peek is open on another key: `close` it (9.5), keeping the link when the new key has the same profile.
2. If no link is open for the key's profile: `ConnectionService::open` with a copy of the launch whose profile is the key's profile and whose gateway start is off (`EnsurePolicy::Never`); the ticket is profile scoped (`Scope::profile()`); `P1-01`'s handshake sends `client.capabilities {server_requests: true}`.
3. A `SessionService` over that link; `open(SessionRequest::ById(session_id))`, which sends `session.resume` with exactly `{session_id, display_projection: true}` (`P1-12`'s `resume_params_id`; no `profile`, since the link is profile scoped).
4. `SessionState::from_snapshot` (`P1-05`); `Link::track` for replay; a new `PromptService` (`P1-09`) with the shared submission-id generator; `PromptService::on_prompts_changed` with the snapshot's open prompts.
5. Report `SubscribedView::from_state(&state, &masked)` to `P3-01` with `observe_subscribed(key, view)`. `masked` is `P3-01`'s second argument, `&[(String, NeedSummary)]`: the peek's open masked requests as (request id, summary) pairs, empty when none.
6. `Peek { key, status: Open { .. } }` to the view.

Timeouts: connect and handshake as `P1-12`; resume 120 s (`P1-02`'s default); all from `PeekTimeouts` (section 4), so tests use `PeekTimeouts::scaled_for_tests()`. The view shows `Opening…` meanwhile and keeps working; Esc during opening closes the peek and the late result is discarded (its attachment is detached at once).

The executor runs the effects of one batch in order. A `SendReply` or `Stop` for a key whose open is still in progress waits for that open: on success it is sent with the snapshot's generation; on failure nothing is sent and the view gets `ReplyDone { NotAttached }` (the text returns to the draft) or `StopDone { NotAttached }`. The view never blocks while it waits.

### 9.2 Events

Each `LinkEvent` of the peek link goes to `P1-05`'s `update` on the peek state. After each, the service recomputes the `SubscribedView` and calls `observe_subscribed` only when it differs from the last one sent, and syncs the peek's `PromptStack`. Reconnects and replay gaps follow `P1-03` and `P1-12` (a gap re-resumes). Peek frames are coalesced to at most one per 33 ms.

### 9.3 Reply

`Event::Submit { text, submission_id }` on the peek state, then `SessionService::execute(Effect::SendPrompt)`: `prompt.submit` with exactly `{session_id, text, submission_id}`. Never `profile`, `queued`, `unattended`, `attachments`, `clarify_batch` or `display_kind`. Outcome, from Hermes's reply (never from local state): `AdmissionStatus.status` `started` gives `Sent`, `queued` gives `Queued`, `terminal` gives `AlreadyRan`, `unknown` gives `StateUnknown`; `{voice_stopped: true}` gives `VoiceStopped`. A refusal gives `Refused { reason }` (and `Event::SubmitFailed`); a dropped connection or a timeout gives `Unknown`, and the text and submission id are kept, by `RowKey`, for `resend_unconfirmed(key)`. A reply still in flight when its peek link is closed (a peek of another profile replaces the link) gives `Unknown { why: "connection dropped" }`; a peek move within one profile keeps the link and lets the call finish. `ResendReply(key)` runs `resend_unconfirmed(key)` once the peek is on `key` (the executor holds it while that peek opens, as for `SendReply`); it sends `prompt.submit` with the stored text and submission id over the current peek link (U6 covers a link that changed in between). The executor feeds `ReplyDone { key, outcome }` to the view. Texts: section 8.

### 9.4 Stop

1. If the peek state has no running turn: `NothingRunning`, nothing sent.
2. `PromptService::deny_before_interrupt(client, state, session_id, 2 s)` (`P1-09` REQ-14): `approval.respond {choice: "deny"}` for each open approval that offers `deny`. A failure or expiry gives `P1-09`'s notice and the stop continues to step 3: the operator asked to stop.
3. `Event::Interrupt` on the peek state gives `Effect::Interrupt { session_id, execution_generation }`; `SessionService::execute` sends `session.interrupt` with exactly those two keys.
4. The turn's end arrives as `message.complete` with status `interrupted` on the peek link; `P3-01`'s registry moves the row through the subscribed view.
5. Refusals: `stale_generation` (no automatic retry) and others give `Refused`; a drop or timeout gives `Unknown`. `Event::InterruptFailed` is fed on any failure so the reducer clears its latch. The executor feeds `StopDone { key, outcome }` to the view.
6. Queued prompts then start (F16); live test 46 confirms on the pinned release.
7. Open masked requests (`sudo`, `secret`, vault) are not answered by the stop. The peek's `PromptService` closes their card when `request.cancel` arrives (F20, U7); otherwise the card stays until Hermes's 120 s timeout or until the peek closes (9.8).

### 9.5 Close

`Link::untrack`, `session.detach` with exactly `{session_id, subscription_id}` (no `end_reason`, not even null; `detached: false` counts as done), `observe_unsubscribed(key)`, close the link when the profile changes or the overlay closes. The whole close is capped at 2 s; past that, the link is closed anyway (the gateway drops the subscription when the connection closes). Closing a peek keeps the service's unconfirmed replies (5.4). When the **overlay** closes, and only then, the executor of `Close` writes one section-8 notice per entry of `FleetViewState::unsettled_replies()` to the main scrollback through `P1-12`'s notice path, then drops the unconfirmed entries, so a prompt that may have been queued never disappears without a trace.

### 9.6 Open as foreground

`fleet_actions::execute(Open(key))`: if the key is the foreground, close the overlay and show `You are already in this session.` (`P2-07`'s `AlreadyHere` text). Otherwise close the peek (9.5), close the overlay (`P1-06`'s `close_overlay`, writing the unsettled-reply notices exactly as `Close` does), then `switch_foreground(app, key)`; its outcome text (`Switched…`, a refusal) is committed as `P2-07` does. A peek of the same session is always closed first, so the foreground link attaches it fresh.

### 9.7 The foreground row

Peek: the panel reads the foreground `SessionState` and the foreground `PromptStack`; no resume. Reply: `Event::Submit` through `P1-12`'s foreground path. Stop: the overlay's confirmation (5.5), then `Event::Interrupt` through `P1-12`'s path (which awaits `deny_before_interrupt`); results and refusals use the foreground's texts. Answer: the foreground card already takes keys once the overlay closes; `a` on the foreground row closes the overlay so the card has focus.

### 9.8 Server requests on the peek link

`policy_for(method)` (`P1-09`): `Masked(_)` goes to the peek's `PromptService::on_server_request`, and its answer is written only on the peek link's responder; `Refuse` becomes `responder.ignore()` (this includes the batch `clarify` and `approval` kinds, F17). `request.cancel` events reach the peek's `PromptService::on_request_cancel`. On close, open masked requests are ignored, never answered (the client's `close()` cancels its responders without writing).
