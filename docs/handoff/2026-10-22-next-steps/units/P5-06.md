# P5-06: Workflow runner lifecycle: run, detach, resume, list and stop (unit P5-06)

Status: `proposed`. The GitHub issue for this unit is the contract; this document is its reference specification. If they disagree, the issue wins and the disagreement is reported on the issue.

## How to use this document

Read the issue first: it lists the requirements, the tests to write first, the acceptance scenarios and the stop conditions. Come here for depth. Section 2 lists every Hermes fact this unit relies on, with the file and line at Hermes v0.22.4. Sections 3 to 7 define the runs directory, composition, the commands, detach, the joint control protocol and discovery exactly. ## 1. What this unit delivers

The `talaria-workflow` crate gains a `runner` module and the `talaria` binary gains a `workflow` subcommand with five verbs:

| Command | Does |
|---|---|
| `talaria workflow run [--detach] <script.js>` | Preflight, create a run folder, execute to completion here or in a detached child |
| `talaria workflow resume <run-id\|folder>` | Continue a run without repeating finished agents; replay a completed run |
| `talaria workflow list` | Print every run in the runs directory from files only |
| `talaria workflow stop <run-id\|folder>` | Request a graceful stop and report it confirmed or unconfirmed |
| `talaria workflow resolve <run-id\|folder> --key ... --resolution ...` | Answer one parked call while its runner is alive |

Plus `runs_dir` / `workflows_dir` / `discover_runs`, the discovery the terminal UI uses through P5-05, so UI and command line can never disagree.

What it deliberately does not do:

| Concern | Owner |
|---|---|
| Script engine, `agent()` semantics, saved-workflow trait | P5-01 |
| Journal and run-folder formats, lock, replay, resolution-file procedure | P5-02 |
| Hermes frames, receipts, one session's stop, approval rules | P5-03 |
| Staffing, roster, tier check, budgets, scheduler, drift, money accounting while running | P5-04 |
| Progress tree, control-file writer, steering on screen | P5-05 |
| Worktree creation | P5-07 |
| Built-in workflow files, roster command, skill, ultracode | P5-08, P5-09 |

## 3. Folders and runner-owned files

```text
<runs dir>/                        from runner::runs_dir (issue REQ-5)
  <run_id>/                        P5-02 RunDir, mode 0700
    manifest.json                  P5-02's, written once (on_unknown may be updated atomically)
    journal.jsonl                  P5-02's, append-only, one writer (run.lock)
    launch.json                    this unit: {v, script_path, script_dir, cwd, workflows_dir}
    outcome.json                   this unit: latest execution's outcome (section 6)
    runner.json                    {"pid": N, "started_at_ms": N} while a detached child runs
    runner.log                     detached child's output, appended
    control/                       P5-05's request files (section 6)
      pause.json  stop.json  restart-<key>.json
    scripts/, blobs/, resolutions/   P5-02's
```

Rules:

1. Resolvers never create folders. `run` creates the runs directory (0700 on Unix); `list` treats a missing one as empty. A missing workflows folder makes every saved-workflow name not found; nothing creates it implicitly.
2. `launch.json` is written once at creation, atomically (temp file, sync, rename), and read by detach children and every resume. It stores no credential, only paths the operator already named.
3. `runner.json` is written by the detaching parent after a successful spawn. The child deletes it on exit only when the stored pid equals its own pid, so a fast-failing child cannot leave or remove another runner's file. Discovery ignores stale files; status never comes from the pid (section 7).
4. Nothing in this unit writes `manifest.json` or `journal.jsonl` except through P5-02's `RunDir`, `RunJournal` and its one allowed manifest update (`on_unknown`).

## 4. Composition (the only supported wiring)

New run and resume share one composition sequence. Differences are marked.

```rust
// (1) staffing + budget, before any folder exists
let table = StaffingTable::load(staffing_path)?;              // absent file = empty table
let budget = RunBudget::resolve(cli_tokens, cli_usd, &table);
// (2) roster through P5-04's source (model.options, plain method)
let wires: Arc<dyn WireFactory> = /* P5-03's live factory */;
let cache = RosterCache::new(Arc::new(LinkRosterSource::new(wires.clone())),
                             Arc::new(SystemClock), Duration::from_secs(30));
let roster = cache.load(&profile).await?;                     // fetch failure: exit 1
let check = check_tiers(&table, &roster, &budget, clock_now); // problems: print all, exit 2
print!("{}", estimate_run_cost(&table, &roster, &budget));    // stdout; range or unknown
// (3) folder (new run only) + journal
let dir = RunDir::create(&runs_dir, NewManifest { /* below */ }, &script_source)?;
write_launch_json(&dir, &launch)?;                            // atomic, this unit
let (journal, _summary, _warnings) = RunJournal::open(dir, &script_source).await?; // Locked: exit 1
let journal = Arc::new(journal);
// (4) port: one handle for the backend, one retained clone for stop
let (port, feed) = HermesPort::connect(port_config, &profile).await?;
drop(feed);   // nothing in the runner reads P5-03's event feed (P5-05 uses the terminal UI's connection);
              // a receiver kept alive but never read would hold every event in memory for the run
let stop_port = port.clone();                                 // shared Arc<Inner>; see the issue stop condition
// PortConfig: home is the Hermes home (HERMES_HOME, else ~/.hermes), poll start 250 ms capped at 2 s,
// timeouts as merged from P5-03 section 3.7 (describe 10 s). With --record, the WireFactory is built
// with P1-04's recorder on P1-03's on_connect hook (H10); an existing record path is refused before preflight, exit 1.
// The operator finite-only decision is a launch gate on PH5, checked procedurally before a run is staffed;
// there is no runtime API for it, so the runner performs no runtime check and no test asserts one.
// (5) scheduler wrapped in the pausing gate, launch resolver twice (pure, identical)
let (scheduler, scheduler_events) = Scheduler::start(
    SchedulerConfig::from_table(&table, budget, &profile, prices),
    cache.clone(), journal_path(&dir), Arc::new(SystemClock)).await?;
let gate = PausingGate::new(scheduler);
let launch_for_config = StaffedLaunch::new(StaffingResolver::new(Arc::new(table.clone()), roster.clone()),
                                           ExplicitLaunch::new(defaults.clone()));
let engine_config = journal.engine_config(&launch_for_config)?; // limits stay P5-01 defaults
let launch = StaffedLaunch::new(StaffingResolver::new(Arc::new(table), roster),
                                ExplicitLaunch::new(defaults));
let backend = JournaledBackend::new(journal.clone(), port, SchemaTurnPolicy, launch, gate, RetryPolicy::default());
// P5-04's staffed_backend is this same construction with a concrete Scheduler gate;
// it cannot take PausingGate, so the runner calls JournaledBackend::new directly (SchemaTurnPolicy is P5-03's, JournaledBackend P5-02's). The drained scheduler_events stream is forwarded as RunnerEvent::Scheduler lines by the output task; it is never dropped.
// (6) execute: spawn engine with FilesystemResolver, forward events in order,
//     poll control/ every 250 ms, consume resolutions through the backend,
//     on finish: journal.finish(kind), then write outcome.json (section 6).
```

`NewManifest` fields and their sources (P5-02 owns the shape): `workflow_name` from `parse_script` metadata; `args` from `--args` or `--args-file` (JSON value, else `None`); `started_at_ms` and `created_at_ms` the same `SystemTime` instant in milliseconds; `seed` the first 8 bytes of SHA-256 over the decimal bytes of `started_at_ms` followed by the script's SHA-256 hex, read big-endian (both known before creation; `RunDir::create` mints the run id internally, so the seed must not depend on it) — generated once, stored, and reused verbatim by every resume so `now()` and `random(key)` reproduce; `profile`; `on_unknown`; `talaria_version` from `env!("CARGO_PKG_VERSION")` of the `talaria-cli` crate, passed in on `RunRequest`; `hermes` the object `{"describe": <result>}` with the result fetched as H10 describes, before the folder is created; `created_at_ms` is not a caller field — `RunDir::create` stamps it from its own clock; `roster` from `roster.snapshot_with(&table, &budget)`; `approval_policy` the object `{"mode": "finite-only", "source": "operator decision on PH5"}` (a record of intent, H8).

`LaunchDefaults` is `{profile: run profile, cwd: absolute --cwd, toolsets: None, worktrees: None}`. `prices` on a new run comes from the fresh snapshot; on resume, `PriceBook` is rebuilt from the stored snapshot so folded spend does not move when live prices change (P5-04 section 9.3). `engine_config` is called with the `StaffedLaunch` (the staffing launch resolver), never with this unit's `FilesystemResolver` (the saved-workflow resolver); the two traits are different and both are required.

## 5. Commands

### 5.1 `run`

Flags are the issue's REQ-7. `--cwd` defaults to the current directory made absolute and feeds `LaunchDefaults.cwd` and `launch.json`. `--json` selects the machine output (issue REQ-10). Hidden flags `--foreground-child` and `--run-dir <folder>` exist only for detach (section 5.3); giving either without the other, or with a script argument, is a usage error (exit 2). Numeric grammars are clap value parsers (usage errors exit 2, rendered by P1-12's neutralised error path): `--budget-tokens` is a `u64` of 1 or more, `--budget-usd` a finite `f64` above 0, `--timeout` a `u64` of seconds (0 allowed: poll once, then report), `--limit` a `u64` (0 prints nothing). Validation order is fixed: clap shapes, then `--args` JSON, then `parse_script`, then staffing load, then the budget, then the roster. A check therefore reports the first failure in that order when several inputs are bad. Problems and check warnings go to standard error, one per line; the estimate, drift lines and all run output go to standard output.

### 5.2 `resume`

Semantics are the issue's REQ-12. The exact sequence is: resolve the target; `RunDir::open(folder)`; determine the source (with `--script`, read that file and call `dir.store_script(&source)` first — create-new by content hash, taking no lock — and use its returned hash; without it, take the `script_sha256` field of the latest `run_resumed` record, else the manifest's `workflow.script_sha256`, and read `<folder>/scripts/<hash>.js` directly, since P5-02 exposes no read-back method); when that stored file is missing, print `stored script for run <id> is missing: scripts/<hash>.js` on standard error and exit 2 without opening the journal; delete any pending `control/` files (they predate this execution) and any stale `runner.json`; then `RunJournal::open(dir, &source)`, which writes the new `run_resumed` carrying the hash actually used. `--cwd` overrides `launch.json`'s `cwd` for this execution only; `launch.json` itself is never rewritten. Drift uses `staffing_drift(stored_snapshot, &current_table)` only; the fresh roster serves the tier check and the new execution's routes, and never enters the drift comparison. Drift lines print the stored `before` and `after` strings verbatim (P5-04's `model on provider (effort)` form) on standard output, so both units print identical bytes without a new `Display` implementation. The stored `on_unknown` governs; resume offers no override, because P5-02's manifest has no update API after creation.

### 5.3 Detach

`--detach` runs preflight and folder creation in the parent, then spawns the current executable with `workflow run --foreground-child --run-dir <folder>` plus `--staffing`, `--budget-tokens`, `--budget-usd`, `--workflows-dir` and `--runs-dir` (mock selection travels by inherited environment only, section 10; no mock flag exists). The child entry point is `runner::execute::run_child(run_dir)`: it opens the folder with `RunDir::open`, reads `launch.json` and the manifest, deletes any stale `runner.json` once it holds the journal lock, and executes the stored script `scripts/<manifest workflow.script_sha256>.js` (never re-read from `launch.json`'s `script_path`, so an edit between spawn and start cannot change what runs). It does not repeat the tier check or the estimate: the parent already refused a bad start before creating the folder. It does rebuild the roster cache and load the roster (routes need it); a fetch failure there writes one plain line to `runner.log` and exits 1, leaving the folder `interrupted`. `--args`, profile and `on_unknown` come from the manifest. The child always renders the human output format (section 5.1's pinned lines) into `runner.log`, even when the parent was invoked with `--json`; the parent's own line is the only detached output the operator sees live. On Unix the child is spawned in its own process group with stdin from null; on Windows the implementation uses the detached creation flag, and the process tests in continuous integration cover each supported platform (the issue's stop condition covers a platform where this proves impossible). The parent writes `runner.json` after the spawn returns, prints one line (`run <run_id> detached in <folder>`, or the JSON object of section 8), and exits 0 without waiting. The workflow dispatch in `main.rs` runs before P1-12's terminal check and before any terminal initialisation, on the binary's existing tokio runtime, with signals from `tokio::signal`; a workflow verb therefore runs with stdin from null or piped, which P1-12's session path would refuse.

### 5.4 `list`

Semantics are the issue's REQ-16. Sorting is by the summary's `started_at_ms` descending, ties by `run_id` ascending, then truncation to `--limit` — identical for the human lines and the `--json` array. The separator is exactly two spaces; a name or `run_dir` containing spaces is rendered as-is with no quoting (the line is for reading and for the golden comparison, not for shell parsing); money renders as `$` plus the amount with two decimals (`$1.20`), unknown spend as `-`; the start time is RFC 3339 in UTC at second precision (`2026-10-22T16:00:05Z`); `run_dir` is absolute because the CLI absolutises the runs directory before discovery. `--limit 0` prints nothing (or `[]`); a non-numeric limit is a clap usage error, exit 2.

### 5.5 `stop` and the runner's control loop

The file protocol is P5-05 REQ-18 byte for byte: files in `<folder>/control/`, written create-new through temp file, sync and rename, body `{"v": 1, "kind": "pause" | "stop" | "restart", "key": <restart only>, "at_ms": <ms>}` named `pause.json`, `stop.json`, `restart-<key>.json`. The CLI's `stop` writes `stop.json` with that exact writer (shared code in `runner::control`, the same serialisation the runner's tests pin). The runner polls `control/` every 250 ms:

| File | Runner action | Acknowledgement |
|---|---|---|
| `pause.json` appears | `PausingGate` stops admitting new calls; admitted calls finish | file deleted by whoever resumes (P5-05) or by resume here; journal shows no new `call_intent` while present |
| `pause.json` removed | gate admits again | next admission in the journal |
| `restart-<key>.json` | kept until the next resume, deleted there before the journal opens; the key re-runs because its latest attempt is failed or interrupted-eligible | deletion at resume plus the new attempt's `call_intent` |
| `stop.json` | stop path (below) | file deleted by the runner as it starts the stop path; completion is the journal's `run_finished` |

`PausingGate` is this unit's `AdmissionGate` wrapper around P5-04's `Scheduler`: `Fresh` questions block while paused (the wrapped scheduler is not asked, so no permit is consumed), `Reattach` questions and `budget()` delegate immediately (re-attaching parked or live work is never paused), and every other decision delegates. It holds no state beyond an atomic flag driven by the control poll.

Stop path (also the first Ctrl+C or SIGTERM; a detached runner treats SIGTERM identically):

1. Set the engine cancel token; delete `stop.json` (the request is being honoured).
2. From the journal fold, take every session whose latest admission is `started` or `queued`, in journal order, and call `stop_port.stop(profile, session_id)` once per session (H7: per session, never per admission — a session's two turns share its latest admission).
3. Poll each targeted admission with `prompt.receipt` through the backend's port path until `terminal`, at most 30 seconds in total. `NotRunning` counts as settled. `Unknown`, a refusal, or the bound expiring leaves that session unsettled.
4. `journal.finish(Aborted)`, then write `outcome.json` with reason `stopped` (all settled) or `stopped-unconfirmed` (any unsettled, listed in `runner.log`), delete `runner.json` (pid-checked), and exit 3.

The waiting `stop` command polls the journal incrementally (`JournalReader::read_from` with a saved offset, every 250 ms, the same interval the runner uses for receipts, polled every 250 ms within the 30-second bound). Its decision procedure is: while the latest execution has no `run_finished`, keep waiting (a natural `completed` or `failed` finish in the meantime reports `already finished (<outcome>)`, exit 0, with the outcome string verbatim `completed`, `failed` or `aborted`); once an aborted `run_finished` is seen, read `outcome.json` — it is written after `finish` returns, so it may lag by one poll — and accept it only when `finished_at_ms` is at or after the stop request's `at_ms`: reason `stopped` prints `stopped <run_id>`, exit 0; reason `stopped-unconfirmed` prints `stop requested; run <id> is still finishing — stop not confirmed`, exit 1 at once without waiting out the timeout; no fresh outcome file by the timeout (default 35 s, chosen to cover the 30-second settle bound plus the finish writes) also exits 1 with that line. The 30-second bound and the 250 ms poll are fields on `RunRequest` and `ResumeRequest` (`settle_bound`, `receipt_poll`) with those defaults, so tests set them to hundreds of milliseconds instead of waiting. Target resolution is shared by `stop`, `resolve` and `resume`: an unknown id prints `unknown run '<id>' (searched <runs_dir>)`, exit 2; a path that is not a run folder prints `'<path>' is not a run folder`, exit 2. Live sessions for step 2 come from the journal fold: the profile and launch from each key's `call_intent`, the `session_id` from its `session_bound`, and the admission from its latest `turn_admitted`; a receipt error other than `NotRunning` counts as unsettled, and in a foreground run the unsettled sessions are printed on standard error as `stop unconfirmed: session <id> still <status>` (a detached run writes the same lines to `runner.log`). At finish the runner deletes `stop.json` (already deleted at step 1), any remaining `pause.json` and `restart-<key>.json`, and `runner.json`, so no stale request leaks into the next execution. A second Ctrl+C during steps 2 to 3 exits 3 immediately and writes nothing further — no `outcome.json` update either; the folder is then `interrupted` and resumable.

### 5.6 `resolve`

`resolve` is the issue's REQ-17. It is the only verb that answers a parked call. It resolves the folder with shared target resolution, opens it with `RunDir::open` (no journal lock), maps `--resolution` to P5-02's `Resolution::{Fail, Rerun, Abort}`, and calls `request_resolution(key, attempt, episode, resolution)` once. `ResolutionPending` prints `already answered for <key> attempt <n> episode <n>` and exits 1. Target errors are section 5.5's two lines, exit 2. The live runner's backend polls `resolutions/` at open and once a second while any call is parked (P5-02 section 7), consumes the file, and proceeds without any second process taking the journal lock. `resume` is never part of answering: on a live (locked) run it exits 1 by design, and the parked notice never names it.

## 6. `outcome.json` (durable final outcome)

The journal's `run_finished` carries only an outcome and summary counts (P5-02 section 4). The runner therefore writes its own outcome file at every execution finish, after `journal.finish` returns, atomically and with mode 0600:

```json
{"v": 1, "outcome": "completed", "result": <full JSON result or null>,
 "error": {"name": "...", "message": "..."} or null,
 "reason": "stopped" | "stopped-unconfirmed" | "operator-abort" | null,
 "finished_at_ms": 1792627200000,
 "summary": {"completed": 0, "failed": 0, "skipped": 0, "parked": 0, "unfinished": 0}}
```

`result` is present only for `completed`, `error` (always, as `{name, message}`) only for `failed`, `reason` only for `aborted`. The writer table is closed: `completed` writes the engine result; `failed` writes the engine error; an abort from the stop path or a first signal writes `stopped` or `stopped-unconfirmed` (section 5.5); an abort from a `resolve --resolution abort` answer writes `operator-abort`; a second signal writes nothing, so the previous execution's file remains and discovery's execution-aware fold (not this file) decides the state. `summary` is `RunJournal::summary()` called after `finish` returns (its final counts), never the return value of `finish`, which is only a success marker. `finished_at_ms` is the wall-clock instant of the write and is what `stop` correlates against (section 5.5). The file is replaced on every execution, so it always describes the latest one (which is also what execution-aware discovery reports). Resume's completed fast path reads only this file (plus the journal fold that proves the completed state) and prints `result` without opening the journal for writing or calling the gateway. When the file is absent for a completed run (a folder written before this unit, or a crash between `finish` and the outcome write), resume prints the outcome and the `run_finished` summary counts and exits 0, and the missing result is named in `remaining_concerns` on the pull request — the script is not re-run to recover it.

## 7. Discovery (`discover_runs`)

```text
for each entry of read_dir(runs_dir), one level, folders only:
  if none of manifest.json / journal.jsonl / run.lock exists: skip silently
  manifest = parse manifest.json
    missing        -> unreadable("missing manifest.json")
    parse failure  -> unreadable("corrupt manifest.json: <reason>")
  records = JournalReader::read_from(journal.jsonl, 0)
    Err(Corrupt { line, reason }) -> unreadable("corrupt journal.jsonl at line <n>: <reason>")
    missing file (manifest present) -> unreadable("missing journal.jsonl")
    (read_from returns no partial records, so no counts survive a corrupt line;
     a torn tail is dropped by the reader itself and cannot be surfaced here)
  fold records in order (execution-aware):
    on run_started / run_resumed: terminal = None; keep counts cumulative over all executions
    on run_finished: terminal = its outcome
    per key: finished = latest call_finished in {completed, skipped};
             total_known = distinct keys in any keyed record;
             parked = keys whose latest call_attention has no later call_resolved / call_finished
    tokens = sum over turn_settled usage (total_tokens, else input_tokens + output_tokens);
             no settled usage at all -> null
    money  = sum over (key, attempt) of the last turn_settled's usage.session_cost.estimated_cost_usd
             (P5-03 puts session_cost in the receipt usage; P5-02 stores usage verbatim);
             null when no turn_settled exists, or when any turn_settled lacks usage.session_cost,
             has a cost_status other than actual / estimated / included, or an amount that is not
             a number >= 0 (P5-04's rule: unknown cost is never shown as zero);
             file-only discovery never prices tokens itself
  status = terminal, else parked (parked > 0), else running (lock probe), else interrupted
sort by started_at_ms descending, then run_id ascending
```

Entries that are symlinks to folders are followed; entries whose names are not valid UTF-8 are skipped silently (no run id can be formed for them). When `read_dir` on the runs directory itself fails, `discover_runs` returns an empty vector and the `list` verb separately reports `cannot read runs directory <dir>: <error>` on standard error with exit 1, so an unreadable directory is never shown as an empty history. Name, profile and `started_at_ms` always come from the manifest (the journal carries no competing copies of them), even when journal records disagree. A record counts as keyed for `agents_total_known` exactly when its serde `t` tag is one of `call_intent`, `session_bound`, `turn_intent`, `turn_admitted`, `turn_settled`, `call_attention`, `call_resolved`, `call_finished`. Money per call is the `estimated_cost_usd` inside the last `turn_settled`'s verbatim `usage.session_cost` for that (key, attempt) — Hermes's per-session running total, so only the last turn of a call contributes, exactly as P5-04's Hermes-sourced accounting reads it; money P5-04 derives by pricing tokens live is not in the journal and is never reconstructed here, so discovery money is the Hermes-reported part of the scheduler's spend and may be lower while a run is live. The run's money is `null` whenever any settled turn it folds lacks `session_cost` or reports a `cost_status` other than `actual`, `estimated` or `included` (even with an amount of `0.0`): one number cannot say "plus n unpriced turns", and unknown cost is never shown as zero (P5-04's settled decision 6 and money text; P5-05's REQ-11). `list` prints such a run's money as `-`.

The lock probe opens `run.lock` with `OpenOptions::new().read(true).write(true).create(false)`: `try_lock` success means no writer (unlock at once by dropping); `WouldBlock` means a writer; `NotFound` means no writer yet; any other error yields an `unreadable` summary with warning `lock probe failed: <error>`. I/O errors are thus never mistaken for a running run. Unreadable summaries use the fallback identity from the issue (folder name as `run_id`, `(unreadable)` as name, empty profile, `started_at_ms` 0, zero counts, `null` spend, the exact warning). `RunSummary.warning` is always present in JSON (`null` when there is nothing to warn about); torn tails and stale `runner.json` files produce no warning because the merged reader gives discovery no channel for them.

Coordination note: this unit reports a folder holding run artifacts (including a lone `run.lock`) as one `unreadable` row and skips bare unrelated folders silently. P5-05 renders these rows unchanged (its test 6, `picker_renders_discovery_rows_unchanged`, and its section 8: unreadable folders list with their one warning), so the two units already agree and neither implements discovery twice.

Status precedence example (tested): execution 0 `failed`, then a resumed execution holding the lock lists `running`; the same folder with the lock free and no new `run_finished` lists `interrupted` — never the stale `failed`.

## 9. Edge cases

| Case | Behaviour |
|---|---|
| Runs directory missing | `list` prints no runs, exit 0; `run` creates it 0700 |
| Two `run` commands at once | Different folders, both proceed; the lock is per folder |
| `resume` or `resolve` on a running run | `resume` exits 1; `resolve` works (no lock needed) — the only answer path while live |
| `resume` on a completed run | `outcome.json` result replayed, exit 0, no lock, no gateway |
| `resume` on a failed or aborted run | New execution; completed calls served from the journal, the rest run again |
| `stop` twice | Second finds `stop.json` present, keeps waiting on the same acknowledgement |
| `stop` on an interrupted run (no live runner) | File written; no `run_finished` arrives, so timeout, exit 1, file stays; the next resume deletes it as predating (section 5.2) |
| Stale `pause.json` from a dead execution | Deleted by resume before opening; never pauses the new execution |
| Manifest present, journal missing | Lists `unreadable` with warning `missing journal.jsonl` (section 7) |
| Runner killed with -9 | `interrupted` (lock free, no `run_finished`); agents keep running in Hermes; resume re-attaches (attach before receipt, H4) |
| Gateway down at `run` or `resume` | Roster fetch failure exit 1 (one plain line, no folder touched); a tier-check refusal at resume exits 2 |
| Script or staffing edited before resume | Allowed; drift printed; only changed launches re-run (their journal keys changed) |
| Detached child fails to spawn | Parent exits 1; folder `interrupted` and resumable; `runner.json` is never written |
| Parked call, nobody answers | Runner blocks holding the lock, other branches finish, status `parked`; `stop` still aborts it through the control file |
| `list` over hundreds of folders | One pass; each journal folded once from offset 0; no gateway; probe never creates `run.lock` |
| Stop races an admission settling | Receipt poll sees `terminal` and it counts as settled; `stale_generation` inside `stop` is P5-03's handled case (H7) |

- Unit and execution tests (issue tests 1 to 16) need no gateway. The roster comes from P5-04's `FixtureRosterSource`. `HermesPort::stats` is asserted as a second, independent counter where the port is in-process.
- Process tests (issue tests 17 to 19) run the real binary built with `cargo build -p talaria-cli --features workflow-mock`. Feature edges are fixed: `talaria-cli`'s `workflow-mock` enables `talaria-workflow`'s `mock` feature, and `talaria-workflow`'s `mock` feature (the name P5-01 and P5-03 already use) gates `runner::mock_support`. When the binary is started with the environment variable `TALARIA_WORKFLOW_MOCK=1`, `run`, `resume` and the detached child (which inherits the environment, so detach forwards no mock flag or argument) select P5-03's `mock_wire::ScriptedWire`, constructed from the file named by `TALARIA_WORKFLOW_MOCK_WIRE` exactly as its example's scripted mode constructs it, plus P5-04's `FixtureRosterSource` fed from `TALARIA_WORKFLOW_MOCK_ROSTER`, instead of `HermesPort::connect`. Tests also point `HERMES_HOME` at an empty folder and assert the three tests pass with gateway discovery unavailable, proving the mock selection — not a hidden live gateway — drives them. This mechanism is test-only: it is compiled out of the default binary and named in no help text.
- Golden files: the human `list` output and the `--json` event stream live in `tests/data/runner/golden/`. Before comparison the harness replaces the 26-character run id and every RFC 3339 timestamp with placeholders; nothing else is normalised, and goldens are never edited to make a diff pass.
- The live test (issue test 20, ignored) uses the `fixture` profile and the free model `minimax-m3.1-flash` on `ollama-cloud`, records both directions through P1-04's recorder, counts outbound frames per method for the completed call's key, and prints `skipped: <precondition> not met` when the gateway or profile is absent. Evidence for resume claims always comes from frame counts, never from the session count (an idempotent duplicate would keep it unchanged). ## 11. Design notes and rejected alternatives

- **One control protocol (P5-05's files) instead of a second stop file.** The view and the command line are two writers of the same request; two protocols would let them disagree about whether a stop was requested. Acknowledgement is defined by the consumer (deletion plus the journal effect), so both writers observe the same truth.
- **`outcome.json` instead of widening the journal.** P5-02 froze `run_finished` as outcome plus counts, and this unit must not touch the journal. The result, failure detail and abort reason are runner-owned data, so they live in a runner-owned atomic file, read by resume and nobody else's folding.
- **Status from the journal plus a lock probe, not from the pid and not from `ReplaySummary`.** `ReplaySummary` is produced only behind the journal lock, which discovery must never take; folding `Record` lines directly gives the same counts without it. The pid lies after a crash; the lock says whether a writer is alive now.
- **Money in discovery only from the settled cost field.** The journal carries no priced money computation (that is the running scheduler's job in P5-04). Discovery sums the settled cost the journal already stores and reports `null` when it stores none or any settled turn's cost is unknown, rather than re-pricing tokens with a price book a file-only reader should not trust.
- **Answering parked calls as its own verb.** `resume` cannot answer a live run (it is locked by design), and the progress view has no resolution writer. A small verb over P5-02's `RunDir::request_resolution` is the only path that works while the runner waits, and it reuses the exact file format the backend already polls.
- **No run pruning here.** Deleting folders destroys the only record resume and accounting trust. A later housekeeping unit can add pruning behind an operator decision.
