## 1. What this unit delivers

A full-screen overlay, opened with the local command `/memory-settings` or from the `More` list of
the settings screen, for the foreground profile. It has three sections:

1. **Memory provider.** Hermes's built-in memory is on by default (`memory.memory_enabled` and
   `memory.user_profile_enabled`, both default `true`, turn it off; `GET /api/memory` does not report
   them, H28). At most one external provider plugin adds to it. The section lists "built-in only"
   plus every provider Hermes discovers, with its readiness; it lets the user switch provider, open
   a provider to read and edit its settings, and save them.
2. **Built-in memory.** The two files Hermes injects into sessions while those keys are on
   (`MEMORY.md`, the agent's notes; `USER.md`, the user profile), with their sizes, and a confirmed,
   irreversible delete of either or both.
3. **Skill curator.** Hermes's background skill maintenance: on, paused or off; its schedule; pause
   and resume; a confirmed "run now" whose output Talaria follows until it ends.

The plain configuration keys under `memory.` and `curator.` (character limits, write approval,
intervals) are already editable in the schema-driven settings screen of `P4-01`; this overlay links to
it with a filter instead of duplicating it.

Not in this unit: reading, editing or deleting single memory entries. Hermes serves those as
"journey nodes" (H33: `GET /api/learning/graph`, `GET`/`PUT`/`DELETE /api/learning/node`, and the
socket methods `learning.detail`, `learning.edit`, `learning.delete`). They are queued in
`QUEUED.md`; this unit deletes only whole files.

## 3. Requests and replies

All requests go through `P4-01`'s `RestClient::request(method, path_and_query, body, opts)` with a
fresh ticket (`opts.ticket = true`). `<p>` is the connection's profile name
(`OpenConnection.profile_name`, `P1-12`), percent-encoded. `<name>` is a provider name that already
matched H16 locally.

```text
GET  /api/memory                                         deadline 45 s   → MemoryStatus
PUT  /api/memory/provider            {"provider": ""|"<name>"}           deadline 45 s   → {"ok", "active"}
POST /api/memory/reset?profile=<p>   {"target": "memory"|"user"|"all"}   deadline 15 s   → {"ok", "deleted"}
GET  /api/memory/providers/<name>/config?surface=declared               deadline 15 s
GET  /api/memory/providers/<name>/config                                 deadline 45 s   (only when declared fields are empty; runs dependency checks, H9)
PUT  /api/memory/providers/<name>/config?surface=declared {"values": {..}} deadline 45 s
PUT  /api/memory/providers/<name>/config                  {"values": {..}} deadline 45 s
GET  /api/curator                                        deadline 15 s
PUT  /api/curator/paused             {"paused": true|false}              deadline 15 s   → {"ok", "paused"}
POST /api/curator/run?profile=<p>    {}                                  deadline 15 s   → {"ok", "pid", "name"}
GET  /api/actions/curator-run/status?lines=40                            deadline 5 s    → {"name", "running", "exit_code", "pid", "lines"}
```

Deadlines are longer than `P4-01`'s defaults for the routes that run dependency checks (H9): 45 s
covers two hanging 20 s checks plus 5 s. No other request carries a `profile` selector, in a query or
a body.

Bodies are shown above in compact JSON. Tests compare them as parsed JSON (`serde_json::Value`
equality, so key order and spacing do not matter, and no extra key is allowed), never as bytes:
`P4-01`'s `RestClient` serialises the body.

The empty provider name: `set_memory_provider(rest, "")` is valid and sends `{"provider": ""}`
(built-in only). Every function that puts a name in a path (`provider_config`,
`save_provider_config`) refuses `""` with `BadProviderName`, as `is_valid_provider_name("")` is
false. `set_memory_provider` refuses any other name that fails H16.

Typed replies (`crates/hermes-client/src/memory_api.rs`, hand-written because REST routes are not in
the contract; unknown fields ignored; a missing optional field takes the default in brackets):

### 4.6 Saving (Ctrl+S on the card)

1. Nothing pending: `No changes to save.`
2. Plain surface and a visible required field is neither `is_set` nor pending: T30, nothing sent.
3. The provider is not the active one: confirmation T10 with Cancel selected.
4. Build `values`: each pending key; booleans as JSON `true`/`false`; secrets as the typed text;
   every other kind as the text the user typed (Hermes coerces, H17 and H18). Empty secrets are never
   sent.
5. Send the PUT on the surface that answered the read. Then always read back
   (`provider_config(name)` and `memory_status()`), except for outcomes where nothing reached the
   route (401, 403, 404, not sent), which keep the edits and show the error.
6. Per sent key, compare (T12), in this order. Text values are compared trimmed; bools as bools.
   - Non-secret, sent blank: `<label>: cleared; Hermes now shows <after>` (`(empty)` when empty).
     Hermes stores the field default (plain) or removes the key (declared), and Talaria cannot know
     the default in advance.
   - Non-secret, `after == sent`: `saved`.
   - Non-secret, `after == before`: `not saved`.
   - Non-secret, anything else: `Hermes stored <after>`.
   - Secret, `before.is_set` false and `after.is_set` true: `stored`.
   - Secret, `before.is_set` true and `after.is_set` true: `<label>: set (Hermes does not show
     whether the new value replaced the old one)`. `is_set` checks presence only
     (`_field_is_set`, `web_server_memory.py` L289-L292), so Talaria cannot confirm a replacement.
   - Secret, `after.is_set` false: the "did not store" line.
   Then the active-provider line:
   `<name> is now the memory provider for profile <p>.` or `<name> is not the memory provider:
   <detail>` (a 400 on the plain surface, H18).
7. Saved keys leave the pending set; the rest stay marked `!`.
   A plain-surface save also writes every visible field that was not edited, with its existing value
   or its default (H18). Talaria does not hide this: on the plain surface, when any visible field
   that was not edited has `is_set` false, T10 (if shown) and the T11 result both carry the line
   T39, and `docs/configuration.md` says so.
8. One `NoticeCell` (`P1-05`) is committed with the head line of T11.

### 4.7 Switching provider (`u`)

Checks run in this order:

- On the active row (including the built-in row when `active` is `""`, and an active provider that is
  no longer ready): `<name> is already in use.`, nothing sent.
- On a provider row whose status is not `ready` (and not the built-in row): T6, nothing sent.
- Else confirmation T7 (Cancel selected), then `PUT /api/memory/provider`, then `memory_status()`.
  `active` equal to the target: T8 and a `NoticeCell`; otherwise T9.
- 400: `Hermes refused: <detail>` then read back (another client may have changed readiness).

### 4.8 Deleting built-in memory (`d` on a file row, `D` anywhere in the section)

- `d` on a file whose size is 0: T16, nothing sent. `D` when both are 0: T16 with both names.
- `D` when exactly one file has content: T14 names only that file (`Delete MEMORY.md for profile
  <p>?`), and the request still sends target `all` (deleting an empty or absent file loses nothing).
  `D` when both have content: T14 names `MEMORY.md and USER.md`.
- Else confirmation T14 (Cancel selected). Delete sends `reset_memory(profile, target)` with
  `Memory` for `MEMORY.md`, `User` for `USER.md`, `All` for `D`.
- Reply: T15 with the `deleted` list (empty list: `Nothing was deleted: the file did not exist.`),
  a `NoticeCell`, then `memory_status()` to refresh the sizes.
- 400 naming "requires an explicit profile" cannot happen when Talaria sends the profile; if it
  does, show it as `Hermes refused: <detail>` and report it (it means H5 changed).
- 500: `Hermes could not delete the file.` (the detail can hold a path: never shown), then read back.

### 4.9 Curator

- Row text (T17): status word `active`, `paused`, or `off`; schedule line; last-run line.
  Numbers: rounded to one decimal (ties away from zero), trailing `.0` dropped (`12.5`, `2`).
  `interval_hours` that is a whole multiple of 24 is `every <n/24> days` (`every day` for 24), else
  `every <n> h` with the number rule (`every 12.5 h`). `min_idle_hours`, `stale_after_days` and
  `archive_after_days` use the number rule. A null value drops its clause. `last_run_at` is parsed
  as RFC 3339 and drawn in UTC: `Last run or first check: YYYY-MM-DD HH:MM UTC`; unparsable text is
  drawn sanitised and cut to 40 characters after the same prefix; null is exactly
  `Last run or first check: none yet`.
- `p`: off → T19; else `PUT /api/curator/paused` with the opposite of the shown state, then
  `curator_status()`; T18 when the read-back matches, else the mismatch text. Pausing while a run is
  followed adds `A run already going is not stopped.` to T18 (H37).
- `R`: off → T19; a run being followed → T33 `A curator run is already being followed.`; else a
  pre-check: `action_status("curator-run", 40)` (`PollAction { follow, after: 0 }` with a new
  follow id, state `CheckingRun`). Hermes refuses nothing here (H26), so the pre-check is Talaria's
  guard against starting a second run, including after the overlay was closed and reopened mid-run
  or when Desktop, the CLI or another profile started one.
  - The pre-check answers `running: true`: T36, and Talaria follows that run (its `pid` becomes the
    followed `pid`; the elapsed seconds count from now). No confirmation, nothing written.
  - It answers `running: false`: T20 (Cancel selected), then `run_curator(profile)`.
  - It fails: `Could not check for a curator run: <reason>.`, nothing sent (the guard fails safe).
- Following (after a started run or T36): poll `action_status("curator-run", 40)` every 1.2 s, one
  request at a time. Show the elapsed seconds and the tail:
  - When a line starting with `=== curator-run started` is in the tail: the last 8 lines after the
    last such line (earlier runs share the file, H26).
  - When no header line is in the tail: the header has scrolled out of the 40 lines, so every line
    belongs to the newest run (H26): show the last 8 lines.
  - Each line sanitised and cut to the width.
  - `pid` in a poll differs from the followed `pid` (both present): T23, stop.
  - `running` false with an `exit_code`: T22, a `NoticeCell`, then `curator_status()`.
  - `running` false with `exit_code` null: T37 (Hermes no longer has the process, for example after
    a gateway restart, H26), a `NoticeCell`, then `curator_status()`. Never "finished".
  - 240 polls (Desktop's limit, H26; about 4.8 minutes): T24, stop.
  - A poll that fails: keep polling; three failures in a row: `Lost track of the curator run: <reason>.`, stop.
  - Closing the overlay stops following: `NoticeCell` `Curator run continues in Hermes; Talaria stopped following it.`
    A poll reply that arrives later carries an old follow id and is dropped. Reopening and pressing
    `R` finds the run through the pre-check.
- Timing: there is no separate timer. `MemoryService::execute(PollAction { follow, after })` sleeps
  `after` (tokio), then calls `action_status` and returns `ActionPolled { follow, result }`. The app
  runs every `execute` call as its own task, so a sleeping poll blocks nothing. The view's elapsed
  seconds come from `now` and the follow start; the screen redraws when a poll answers (about every
  1.2 s), so the seconds advance at that pace. Not following, `view(now)` does not depend on `now`,
  so nothing repaints while idle.
- `k` and `s`: emit `CloseOverlay` and `OpenSettings { profile, filter: "curator." }` or
  `"memory."`. The filter is `P4-01`'s substring filter (each term a substring of
  `"<key> <description> <category>"`), not a key prefix. With pending card edits, the discard
  confirmation comes first.

## 5. States

```text
Closed ─Open──► Ready(loading sections) ──replies──► Ready
Ready ─enter on provider──► Card(loading) ──► Card ─enter──► Editing ─enter/esc──► Card
Card ─ctrl+s──► [ConfirmSave if not active] ──► Saving ──► Verifying ──► Card(result lines)
Ready/Card ─u──► ConfirmSwitch ──► Switching ──► Verifying ──► Ready(result)
Ready ─d/D──► ConfirmReset ──► Resetting ──► Verifying ──► Ready(result)
Ready ─p──► Pausing ──► Verifying ──► Ready(result)
Ready ─R──► CheckingRun ─running──► Following
                        └─not running──► ConfirmRun ──► Starting ──► Following (polls) ──► Ready(result)
Card ─esc (pending)──► ConfirmDiscard ─Discard──► Ready
Ready ─esc──► Closed (stops following; NoticeCell when it was following)
```

- One write at a time: `Switching`, `Saving`, `Resetting`, `Pausing` and `Starting` block every other
  write key and Ctrl+R with T25. `Following` is not a write: pause, switch and delete still work;
  another run does not (T33).
- Every confirmation's default is Cancel, and confirmations are modal (4.10).
- Unknown outcome (`RestError::outcome_unknown()`, `P4-01`): T26, then the read-back for that route
  below; never resent.

| Write | Read-back after an unknown outcome | What it proves |
|---|---|---|
| Switch | `memory_status()` | `active` shows whether the switch happened |
| Save | `provider_config(name)` and `memory_status()` | per-key T12 lines and the active provider |
| Reset | `memory_status()` | file sizes (0 after a delete) |
| Pause | `curator_status()` | `paused` |
| Run | `action_status("curator-run", 40)` | `running: true` with a `pid`: the run started, and Talaria follows it (T36). Otherwise T38: the status cannot show whether the POST was processed (a run may already have ended), so Talaria says it cannot confirm |

## 7. Privacy and secrets

- A typed secret lives only in `P1-09`'s `MaskedValue` inside the editor, the pending set and the
  `SaveConfig` effect. It never appears in `Debug`, tracing, notices, the transcript, composer
  history, the clipboard or a recording; it reaches only the `values` map of the PUT body.
- Hermes never returns secret values (H13, H14); Talaria never asks for them.
- The reset 500 detail and every action log line are untrusted: the detail is never drawn; log lines
  are sanitised.
- No fixture holds an absolute path, a user name, or a profile other than `default` and `fixture`.

## 11. Design reasoning

- **REST only.** H1 leaves no choice.
- **`/memory-settings`.** Hermes's `/memory` reviews staged memory writes and `/curator` runs skill
  maintenance (H27); shadowing either would remove a Hermes feature from Talaria users. A longer
  name is the boring, safe choice.
- **`PUT /api/memory/provider` instead of `PUT /api/config`.** The dedicated route refuses a provider
  that is not ready (H11); the generic write would store a broken setting. Desktop uses the generic
  write; this is the one place Talaria is deliberately stricter. The strictness covers switching
  only: a save through the declared surface activates the provider with no readiness check (H17). No
  bundled provider has a declared surface at v0.22.4, so this has no effect today; T10 still asks
  before such a save. `/config` can also write `memory.provider` directly (section 2's follow-up).
- **Plain surface fallback.** Desktop shows nothing for the two bundled providers because neither has
  a declared schema (H13, H14). The plain surface is what `hermes memory setup` itself reads, so a
  terminal user can configure `retaindb` without leaving Talaria.
- **Saving activates.** Both PUTs set `memory.provider` (H17, H18). Hiding that would surprise the
  user, so T10 says it before the write.
- **`?profile=` on two routes.** Without it Hermes refuses the request on every gateway Talaria is
  meant for (H5, H6). Sending the ticket's own profile is accepted by the scope check (H4) and is
  exactly what Desktop does (H32). It narrows `P4-01`'s no-selector rule, whose decision 2 leaves
  phase 4b selectors to `PH4B`'s stop condition C-1, so the issue reports it to the parent.
- **No setup install, no OAuth.** Setup runs install commands such as `curl … | sh` on the gateway
  host (H30); OAuth needs a provider no bundled plugin offers and opens a browser on the gateway
  host (H29). The command line is shown instead. Both are queued for a later unit if the operator
  wants them.
- **Read back after every write.** Desktop trusts its own request for the pause toggle (H31); Talaria
  reads back, the same rule `P4-01` set for configuration writes.
- **A pre-check before "run now".** Hermes starts a second curator process when asked while one runs
  and drops its handle on the first (H26). Desktop guards this only with its own in-page state.
  Talaria reads the action status first, so a reopened overlay or a run started elsewhere is found
  and followed instead of doubled.
- **Polls at Desktop's pace and limit.** 1.2 s and 240 polls (H26): the same load on the gateway as
  Desktop, and no reason to differ.
- **Secrets cannot be cleared here.** Both routes skip a blank secret (H17, H18), so offering a
  "clear" action would claim something Hermes does not do.
