## 0. What this unit is, in one paragraph

The operator wants to hand a task to an agent and keep typing. Hermes already runs sessions inside its gateway (the one background Hermes process per machine that owns every session), so a session keeps working when no client is attached. This unit gives Talaria three ways to start such a session without staying attached to it: `talaria --bg "prompt"` from a shell (it returns as soon as Hermes has accepted the prompt), `n` in the fleet view (a small dialog), and `w` in the fleet view or `--bg --worktree` on the command line, which first creates a git worktree (a second checkout of the same repository on its own branch) from a freshly fetched `origin`, so the agent's edits never touch the operator's own checkout. The launch creates the session with that folder as its working directory, submits the prompt as an ordinary (not finite) turn so approvals wait for the operator, detaches, and tells the fleet registry (`P3-01`) so the new row appears at once. Review of the worktree's changes and the pull request are `P3-07`; this unit only creates the tree and records where it came from.

## 3. Design decisions and the reasons for them

### 3.1 Where the worktree goes and what it is called

- Path `<main root>/.worktrees/talaria-<slug>`; branch `talaria/<slug>`; on a clash both get the same `-2` to `-99` suffix. The main root is the main worktree of the repository that holds the launch folder (never a linked worktree, so trees do not nest).
- Same folder as Hermes's own `-w` and Desktop (F18, F19): `hermes worktree list`, `prune` and `restore` then see Talaria's trees too, and the operator has one place to look.
- The `talaria-` and `talaria/` prefixes keep Talaria's trees apart from Hermes's (`hermes-*` trees are reclaimed on the 24-hour tier; `talaria-*` on the 72-hour tier, F20) and keep Hermes's orphan-branch pruner (`hermes/hermes-*` only) away from Talaria's branches.
- The slug rule is Desktop's (F19), applied to `--name` when given, else to the prompt text. An explicit `--name` that cleans to nothing is a usage error (the fallback `work` applies only to a name derived from the prompt).
- Rejected: Claude Code's `.claude/worktrees/` (meaningless to Hermes's tooling); a folder outside the repository (git worktrees work anywhere, but Hermes's sweep and audit would not see them, and the operator would have two conventions).

### 3.2 Living with Hermes's worktree sweep

Hermes may archive and remove an idle Talaria tree (F20): after 72 hours with no file activity, no process inside and no live Hermes lock. The archive keeps every change under `refs/hermes/archive/<tree>`, and `hermes worktree restore talaria-<slug>` brings it back. That is acceptable and consistent with Hermes's own trees, so this unit does not lock its trees. A lock with Talaria's own reason would count as dead and protect nothing (F20); copying Hermes's lock format (`hermes pid=<pid> db=<state.db>`) would protect the tree for as long as a resumable session works in it, but it impersonates an internal Hermes format. That choice is operator question 2.

Talaria never writes into a Hermes home: it does not add the repository to Hermes's worktree registry (`worktree_repos.json`). The cron sweep therefore visits a repository only once a Hermes path has registered it; a `hermes -w` start in that repository sweeps it anyway.

### 3.3 The turn is ordinary, never finite

A finite turn resolves approvals at once (deny by default) and never asks a clarification (F13). A background agent must be able to ask: its approval then waits in Hermes, `P3-01` puts it in the needs-you queue, and the operator answers it from the fleet view. So `prompt.submit` carries exactly `session_id`, `text`, `submission_id` (plus `profile` on the host link). `finite` and `unattended` are never sent; a property test asserts it.

### 3.4 The folder is sent as `cwd`, without `cwd_explicit`

Talaria sends `cwd` (the worktree, or the launch folder) and no `cwd_explicit`, like `P1-12` and Hermes's own chat client (F22). With a local terminal backend the agent works in that folder (F5). With a remote or container backend Hermes keeps the backend's own folder, and isolation cannot apply; Talaria cannot see the backend at v0.22.4 without reading the profile's whole configuration, so this is a documented limitation, not a check. After the create, Talaria compares the snapshot's `info.cwd` with the folder it sent (both canonicalised). A mismatch, or a missing `info.cwd` on a worktree launch, aborts before the prompt is sent: an agent editing the operator's own checkout is the one failure this unit exists to prevent.

### 3.5 Never send `title` or `hidden` on create

`title` makes the create resume an existing session with that title or id (F3): a launch named after an old task would quietly append to the old session. `hidden` would keep the session out of the fleet (F4). The worktree name is never used as a session title. Hermes titles the session itself (U7).

### 3.6 An abandoned empty session is closed

When a session was created but nothing was admitted (the folder check failed, the submit was refused or never written (`NotSent`), the launch was cancelled before the submit, or Hermes took the text as a voice stop phrase), Talaria detaches with `end_reason: "launch_abandoned"` (16 characters, matches F14's pattern), so the empty session leaves the live feed instead of sitting in the fleet as an idle row with no messages. In every other case the detach has no end reason (P1-12's rule that closing Talaria never ends a session). If the submit outcome is unknown, Talaria never ends the session. The exception is operator question 4.

One case cannot be cleaned up: a create whose reply is lost twice (or unreadable) may still have made a session, but Talaria never learned its id, so it cannot send the detach with an end reason. Closing the connection detaches it without one (F15), and such a session stays in the live list as an idle row with no messages (F26). This is accepted: it holds no prompt and runs nothing. The not-started text says so (section 8.4), and the journal records it.

### 3.7 Which connection launches

- **Command line (`talaria --bg`):** `P1-12`'s `ConnectionService::open` for the `--profile` profile (profile scope; it may start the gateway, and honours `--no-ensure` and `--record`).
- **Fleet view (`n`, `w`):** a short-lived launch link opened per launch: `P1-01` discovery with `EnsurePolicy::Never` in the Hermes home this Talaria process uses (`P1-01`'s `default_home()`, the same home `P1-12` passes to `ConnectionService::open`), a host-scoped interactive ticket, the `P1-01` handshake (which declares `client.capabilities {server_requests: true}` and fetches `runtime.describe`, F30), and a `P1-02` client. The fallback copies `P3-01`'s rule (its specification section 6.1, "If the mint fails with `TicketError::BindingRejected` or `TicketError::Refused(_)`, it mints `Scope::profile()` for the same profile"): on exactly those two errors this unit mints `Scope::profile()` for the foreground profile and the link's scope becomes `LinkScope::ProfileOnly`. This unit copies the rule rather than calling `P3-01`'s private dial code, and `P3-01` has merged before this unit starts. It is closed when the launch ends. Like `P3-02`'s peek link, it is an exception to [decision 0007](../../../../platform-specs/04-architecture/adrs/0007-attach-to-the-hermes-session-authority.md) points 2 and 3 (a further connection; server requests left alone, section 6.3), settled by `P3-02`'s operator question 1 on the phase 3 capability. The foreground link is not used: it is profile-scoped and its subscriptions feed the foreground transcript. `P3-01`'s fleet link is not used: it must never create sessions (`P3-01` REQ-20). `P2-07`'s side connection is not used: it refuses every server request at once, and a refusal reads as "skip" to an agent asking for a sudo password (F17).
- Both paths call the same pure launch machine and the same parameter builders through one small enum (`LaunchConn`). Neither path sends its own `runtime.describe`: both read the summary the handshake fetched (F30).

### 3.8 Launching from the fleet view does not block the screen

The launch runs on a task. The dialog shows progress and can be dismissed with Esc; the launch goes on and reports through a notice. At most three launches of this Talaria process run at once; a fourth is refused with a message. The limit is per process, not per machine.

### 3.9 Fresh base, with a cached fallback

The base is always `origin/<default branch>`, fetched just before the tree is created (roadmap: "branched from freshly fetched origin"). If the fetch fails but an earlier `origin/<default branch>` exists, Talaria branches from it and prints a warning naming the fetch error and the short commit, as Hermes does (F18). With no cached ref, the launch is refused. Whether to refuse on any failed fetch instead is operator question 3. Unlike Hermes's `-w`, Talaria does not try the current branch's upstream first: a background task should start from the shared trunk, not from whatever branch the operator happens to be on.

### 3.10 Where the record of a tree lives

`P3-07` needs to know, for a session, its tree, branch and base. This unit writes them into the repository's own git configuration under the tree's branch (`branch.<branch>.talaria-*`, seven keys including the tree's path, section 7.7), not into a Talaria state file: the record travels with the repository, survives a Talaria restart, and disappears with `git branch -D`. No other disk state is added.

### 3.11 Shared `.worktreeinclude` folders, and the limits of isolation

A folder listed in `.worktreeinclude` (typically a large ignored dependency folder) is symlinked, as Hermes does (F33), so the agent's edits inside it reach the main checkout. The isolation promise is therefore "edits to the repository's files", not "every byte". Copying folders instead would cost disk and time on every launch; the operator decides through question 1 (the issue's Notes), and the help text and `docs/configuration.md` state the sharing. The other unguarded case is a remote or container terminal backend (decision 3.4, E15). The pull request names both.

## 5. Request and reply frames

All frames are JSON-RPC 2.0 over the WebSocket. Placeholders in angle brackets. `"profile"` appears only on a host link launching in a profile other than the link's own (`LaunchConn::routed_profile`). Only the canonical schemas apply (F27): the reply of `session.create` is a `CanonicalSnapshot`, the reply of `prompt.submit` a `CanonicalSubmitResult`. The generated types of `P0-03` for the legacy `methods` entries (`SessionCreateResult`, `PromptSubmitResult`) are never used here, and the create parameters are built by hand in `wire::create_params`, so a legacy schema that allows `title`, `hidden` or `cwd_explicit` can never leak them in.

| Call | Client timeout | Retry |
|---|---|---|
| `runtime.describe` | none sent by this unit (F30) | - |
| `session.create` | 30 s (`CREATE_TIMEOUT`) | once, by the service, on the same connection, only when the first attempt ended `Unknown` (lost reply or error 5001, F23) and the connection is still open; never after `NotSent`, a closed connection, a refusal or `Malformed` |
| `prompt.submit` | 30 s (`SUBMIT_TIMEOUT`) | never (a lost reply or error 5001 is `Unknown`) |
| `session.detach` | 2 s (`DETACH_TIMEOUT`, as `P1-12`) | never (closing detaches anyway, F15) |

No call in this unit answers an approval, so the architecture's rule that approval responses may take 300 s does not apply to these timeouts.

Error replies map to `CallFailure` as follows (F23): 4001 and -32601 (and any other code except 5001) give `Refused { code, reason: data.reason or message, fields }`; 5001 gives `Unknown`, because the handler's writes may or may not have been committed. On the create, 5001 therefore takes the one retry (Hermes expects clients to retry it); on the submit it ends the launch `unknown` (exit 1, tree kept, no end reason).

### 5.1 Describe

No frame. `P1-01`'s handshake already sent `runtime.describe {}` on every connection (F30); `LaunchConn::describe()` returns that summary on both paths (`OpenConnection.describe` on the command line, `Handshake.describe` on the launch link). The answer is the same for every served profile (F9), so a host link's summary also holds for a routed profile.

The launch needs `"tui"` in `session_create.sources` and `"cwd"` in `session_create.parameters`; `model`, `provider` and `reasoning` are checked only when they will be sent (as `P1-12`'s `plan` does). Each missing item has its own text (section 8.4).

### 5.2 Create

```json
{"jsonrpc":"2.0","id":2,"method":"session.create","params":{"request_id":"<32 hex>","source":"tui","cwd":"<canonical folder or tree>","profile":"fixture"}}
```

`model`, `provider`, `reasoning` appear only when given or filled by `P2-06`'s saved default. Never `title`, `hidden`, `cwd_explicit`, `yolo`, `toolsets`, `api_key`. Reply (abridged): `{"session_id":"<sid>","stored_session_id":"<sid>","subscription_id":"<sub>","running":false,"info":{"cwd":"<path>","model":"<model>","profile_name":"fixture",...},...}`.

The retry (table above) lives in the service, not in the machine: the service sends the create, and on a first `Unknown` with the connection still open it sends the same params once more (F8 makes this safe). The machine sees only the final result. A lost or unreadable final result gives `NotStarted` with the text of section 8.4 (an empty session may remain; decision 3.6). The fleet launch link has no reconnect: if the connection drops, there is no retry.

`read_created` errors (`session_id` or `subscription_id` missing, or not an object) become `Failed { step: Create, failure: Malformed(..) }`.

### 5.3 Submit

```json
{"jsonrpc":"2.0","id":3,"method":"prompt.submit","params":{"session_id":"<sid>","text":"<prompt>","submission_id":"<P1-12 format>","profile":"fixture"}}
```

Exactly these keys (three, plus `profile` when routed). Reply: `{"admission_id":"<aid>","ref":{"profile_id":"<pid>","session_id":"<sid>"},"sequence":1,"status":"queued","outcome":null,"authority_epoch":<n>,"execution_generation":null}` or `{"voice_stopped":true}`. Read it as JSON (`call_raw`), not as a typed receipt, because of the second shape.

- Any `AdmissionStatus`, whatever its `status` (`queued`, `started`, `unknown`, `terminal`), means admitted (F28): `Launched`, with `status` copied into `admission_status`.
- `{voice_stopped: true}`: nothing admitted, `NotStarted`.
- A refusal (4001, -32601): nothing admitted, `NotStarted`.
- `NotSent`: `LaunchConn::call` returns it only when it knows the frame was never written (the connection was already closed). Nothing can have been admitted, so it is handled as a refusal: `Detach{launch_abandoned}` (which will itself fail and be ignored; closing the connection detaches without an end reason, F15), rollback, `NotStarted`.
- No reply within 30 s, a dropped connection after the frame was written, error 5001, or a reply that `read_submit` cannot read (`Malformed`): `Unknown` (exit 1). The prompt may have been admitted, so the session is never ended and the tree is kept.

### 5.4 Detach

```json
{"jsonrpc":"2.0","id":4,"method":"session.detach","params":{"session_id":"<sid>","subscription_id":"<sub>","profile":"fixture"}}
```

With `"end_reason":"launch_abandoned"` only in the cases of decision 3.6. A failed or timed-out detach is ignored: closing the connection detaches anyway (F15).

### 5.5 Refusal

`{"jsonrpc":"2.0","id":2,"error":{"code":4001,"message":"invalid_params","data":{"reason":"invalid_params","field":"cwd","detail":"must be an absolute path to an existing directory"}}}`. A key-set refusal carries `fields` (a list) instead of `field` (`gateway/session_controls.py:277-280`); `CallFailure::Refused.fields` holds either form, and the text shows them comma-separated.

### 5.6 Which id is which

The create reply has `session_id` (the live id) and `stored_session_id`. For local sessions they are equal (`P1-12` specification H14), but the unit keeps them apart:

| Use | Id |
|---|---|
| `prompt.submit`, `session.detach`, `FleetHandle` (`RowKey.session_id`, which `P3-01` and `P2-07` fill from `session.list`'s `session_id`), the git-config record `talaria-session`, JSON `session_id` | `session_id` |
| The printed `Launched session <id>` line, the `Open it: talaria --resume <id>` hint, JSON `stored_session_id` | `stored_session_id`, falling back to `session_id` when absent |

## 6. Behaviour step by step

### 6.1 Order of work

1. Validate the request (usage errors, section 8.2). Nothing is opened yet.
2. Open the connection (command line: `ConnectionService::open`; fleet view: `LaunchLink::open`). Failure: `NotStarted`, nothing to undo.
3. Check the describe summary from the handshake: `tui` offered, `cwd` offered, and every option that will be sent offered. Failure: `NotStarted`. No git command has run yet.
4. With a worktree: `prepare_worktree` (section 7). Failure: `NotStarted`; `prepare_worktree` cleans up its own partial work.
5. Build the `NewSessionSpec` with `cwd` = the tree (or the launch folder), apply `P2-06`'s saved default when that unit is merged (flags win, section 8.1), send the create (with its one retry, section 5.2).
6. Check the folder: the service calls `compare_cwd(sent, info.cwd)` and feeds `CwdChecked(..)`. Rules (they fail closed): `info.cwd` absent, null or the empty string is `Missing`; either path failing `std::fs::canonicalize` (for example a path from another machine, or a folder deleted meanwhile) is `Differs`; equal canonical paths are `Matches`; anything else is `Differs`. `Differs` aborts; `Missing` aborts a worktree launch and lets a plain launch go on (decision 3.4).
7. With a worktree: `record_session` (adds `talaria-session`). A failure here is a warning only.
8. Send the submit. From the step that emits `Submit`, `submit_sent()` is true and cancellation is ignored.
9. On `Admitted`: tell the fleet the session is running (`FleetRunning`), detach without end reason, tell the fleet it is released (`FleetReleased`, then `refresh_now`), close the connection, finish `Launched`.
10. On a refusal, `VoiceStopped` or `NotSent`: detach with `launch_abandoned`, roll back the tree, finish `NotStarted`.
11. On `Unknown` (including 5001) or `Malformed` (the submit was sent, then its reply was lost or unreadable): detach without end reason, keep the tree, finish `Unknown`.

### 6.2 The state machine

The service runs one effect at a time, in the order the machine emits them, and feeds the result back as the next input. Effects with no result (`FleetRunning`, `FleetReleased`, `Finish`) feed nothing.

| State | Input | Next state | Effects |
|---|---|---|---|
| Start | (start) | Describing | `Describe` (answered at once from the handshake summary) |
| Describing | `Described` ok, no worktree | Creating | `Create` |
| Describing | `Described` ok, worktree | Preparing | `PrepareWorktree` |
| Describing | `Described` missing `tui`, `cwd` or a sent option | Done | `Finish(NotStarted)` |
| Preparing | `WorktreeReady(r)` | Creating | `Create` (cwd = `r.path`) |
| Preparing | `WorktreeFailed(e)` | Done | `Finish(NotStarted{e, tree_removed: false})` |
| Creating | `Created(c)` | Checking | `CheckCwd` |
| Creating | `Failed{Create, _}` (any failure) | RollingBack or Done | `Rollback` if a tree exists, then `Finish(NotStarted)` |
| Checking | `CwdChecked(Matches)`, or `Missing` on a plain launch | Recording (worktree) or Submitting (plain) | `RecordSession` (worktree), or `Submit` (plain) |
| Checking | `CwdChecked(Differs)`, or `Missing` on a worktree launch | Abandoning | `Detach{launch_abandoned}` |
| Recording | `SessionRecorded{warning}` | Submitting | `Submit` (the warning is kept for the outcome) |
| Submitting | `Submitted(Admitted)` | Releasing | `FleetRunning`, `Detach{None}` |
| Submitting | `Submitted(VoiceStopped)`, `Failed{Submit, Refused}` or `Failed{Submit, NotSent}` | Abandoning | `Detach{launch_abandoned}` |
| Submitting | `Failed{Submit, Unknown or Malformed}` | Releasing | `Detach{None}`; outcome `Unknown`, tree kept |
| Releasing | `Detached` or `Failed{Detach, _}` | Done | `FleetReleased` (only after `Admitted`), `Finish(Launched or Unknown)` |
| Abandoning | `Detached` or `Failed{Detach, _}` | RollingBack or Done | `Rollback` if a tree exists, else `Finish(NotStarted or Interrupted)` |
| RollingBack | `RolledBack{kept}` | Done | `Finish(NotStarted or Interrupted{tree_removed: kept.is_none(), tree_kept})` |
| Done | anything | Done | nothing |

`LaunchConn::call` returns `NotSent` only when it knows the frame was never written; a frame that may have been written is `Unknown`. So a `NotSent` submit is treated as a refusal (nothing admitted, `Abandoning`), and an `Unknown` one is never abandoned.

**Cancellation (exit 130).** SIGINT, SIGTERM or SIGHUP (command line), or Talaria quitting (fleet view, through `LaunchService::shutdown`), gives the machine `Cancel`. Further signals change nothing (the first one already set the token). The rule is keyed on `submit_sent()`, never on the state's name:

- `submit_sent()` is true: `Cancel` is ignored; the launch finishes normally and its own outcome and exit code stand.
- `submit_sent()` is false: the machine sets `cancelled`. In `Describing`, it finishes `Interrupted` at once. In any other state it waits for the result of the effect in flight (the service never abandons an in-flight protocol call; git calls stop early, below), then takes the clean-up path instead of the next step: a created session gets `Detach{launch_abandoned}`, a tree gets `Rollback`, and the machine finishes `Interrupted`. A `Created(c)` that arrives after `Cancel` is therefore detached with `launch_abandoned`, never submitted; a `WorktreeReady(r)` that arrives after `Cancel` is rolled back.
- `submit_sent()` becomes true in the same `step` call that emits `Submit`. The service writes that frame before it looks at the cancellation token again, so no signal can fall between "the machine decided to submit" and "the frame was written".
- During `PrepareWorktree` the service also passes the token to `prepare_worktree`, which kills the running git child (`kill_on_drop`), removes its own partial work (section 7.5 step 5) and returns `WorktreeFailed` with the interrupted text; the machine then finishes `Interrupted`. A protocol call in flight is not cut short; its own timeout (30 s at most) bounds the wait.
- **Quitting with fleet launches in flight.** `app.rs` calls `LaunchService::shutdown(Duration::from_secs(5))` before restoring the terminal (the same 5 s bound as `P1-12`'s quit). Each launch gets `Cancel`. A launch that has not finished by then is dropped: its git child is killed on drop, and its connection closes, which detaches without an end reason (F15). After the terminal is restored, Talaria prints one line per id `shutdown` returned (section 8.4, "quit line"). Such a launch may leave a tree (already recorded in git config by `prepare_worktree`) or an empty idle session; both are visible to `talaria fleet list` and `git worktree list`.

Invariants: the machine never emits `Submit` twice. After `submit_sent()`, a detach with an end reason or a `Rollback` is emitted only when that submit's result was a refusal, `VoiceStopped` or `NotSent` (nothing admitted); never after `Admitted`, `Unknown` or `Malformed`, and never because of `Cancel`.

### 6.3 Server requests and events during a launch

The launching connection is a subscribed viewer from the create to the detach, and its handshake declared `server_requests: true` (F30), so server requests can reach it. Events it receives are drained and dropped. Server requests are left alone with `P1-02`'s `Responder::ignore()`; never refused, never answered (F17). Each one is counted and logged once at debug level.

### 6.4 The fleet registry

On the fleet-view path, with `[fleet]` enabled: after `Submitted(Admitted)`, `FleetHandle::observe_subscribed(RowKey { profile, session_id }, view)` with `SubscribedView { turn: SubscribedTurn::Running { started_at: None }, needs: vec![], activity: None, cost_usd: None, model, title: None }` (all six fields: `SubscribedView` has no `Default`); after the detach, `observe_unsubscribed(key)` and `refresh_now()`. `session_id` is the live id (section 5.6). This makes the row `Working` at once, so a turn that ends before the first poll still produces a `Done` (P3-01's attention rules). On the command line there is no fleet (the `talaria fleet list` process of `P3-01` sees the session on its next roster).

## 7. The git procedure

### 7.1 How git is run

- `GitRunner::run` and `run_read_only` spawn the program (`git` from `PATH`, or the test wrapper given to `with_program`) with standard input closed, standard output and error captured, `kill_on_drop`, a timeout, and the environment of `git_env`: the process environment plus `GIT_TERMINAL_PROMPT=0` and `GCM_INTERACTIVE=Never`, plus `GIT_OPTIONAL_LOCKS=0` for `run_read_only` only (F21). The user's global configuration stays active, so credential helpers still work.
- BatchMode is a command-line option, not an environment variable: for `fetch` and `ls-remote` (the only network calls here), the runner puts `git_prefix_args(configured)` before the subcommand. `configured` is true when `GIT_SSH_COMMAND` or `GIT_SSH` is set, or when `git -C <main root> config --get core.sshCommand` (run once per main root, cached) prints a non-empty value. Unconfigured, the call becomes `git -c "core.sshCommand=ssh -o BatchMode=yes" fetch ...`.
- Read-only calls (`rev-parse`, `worktree list`, `symbolic-ref`, `for-each-ref`, `check-ignore`, `config --get`, `config --get-regexp`, `ls-remote`, `rev-list`, `remote get-url`) use `run_read_only`; everything else uses `run`.
- Every git call names `-C <folder>` or runs with `cwd`; no call relies on Talaria's own working directory.
- Timeouts: 10 s for local reads and local writes such as `config`; 30 s for `fetch` and `ls-remote`; 120 s for `worktree add` (Hermes measured 113 s for a large checkout under load, F18); 30 s for `worktree remove`. On timeout the child process is killed and the call returns `GitError::TimedOut`.
- Git's error text shown to the operator is the first non-empty line of standard error, passed through `P1-06`'s `sanitize`, cut to 200 characters.

### 7.2 Names

`slugify(text)`: lower-case; every run of characters outside `a-z` and `0-9` becomes one `-`; strip leading and trailing `-`; keep the first 40 characters; strip trailing `-` again (a cut can land on a `-`); empty becomes `work`. Examples: `"Fix the flaky test in net.rs"` gives `fix-the-flaky-test-in-net-rs`; `"   "` gives `work`; `"Ünïcode only"` gives `n-code-only`; a 200-character prompt gives its first 40 cleaned characters; `"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa bbb"` (39 `a`, a space, `bbb`) gives 39 `a` (the 40th character was `-`). `explicit_slug` applies the same rule but returns `NameError::Empty` instead of `work`; `explicit_slug("--")`, `explicit_slug("!!")` and `explicit_slug("é")` are all `Empty` (only ASCII letters and digits count).

`pick_names`: candidates `talaria-<slug>` and `talaria/<slug>`, then `talaria-<slug>-2` and `talaria/<slug>-2`, up to `-99`; the first pair where the folder does not exist under `.worktrees/` and the branch is not taken. `None` after `-99`. Every produced branch passes `git check-ref-format --branch` (the characters are `a-z`, `0-9`, `-` and one `/`; no `..`, no `.lock`, no leading `-`).

### 7.3 Finding the repository

1. `git -C <folder> rev-parse --is-inside-work-tree` (read-only). Exit status other than 0: refuse "not inside a git repository". (It exits 128 outside any repository, G1.)
2. `git -C <folder> worktree list --porcelain`: the first block is the main worktree. If it holds a `bare` line, refuse "belongs to a bare repository" (G2). This runs before the output of step 1 is judged, because inside a bare repository step 1 prints `false` with exit 0 (G1).
3. Step 1 printed `false` and the repository is not bare (for example, the folder is inside `.git`): refuse "not inside a git repository".
4. The main worktree's `worktree <path>` line is the main root.
5. `git -C <main root> remote get-url origin` must succeed; else "no remote named origin".

### 7.4 The base

1. `git -C <main root> symbolic-ref --quiet --short refs/remotes/origin/HEAD` prints `origin/<b>` (G3). Remove the leading `origin/` to get `<b>`; output without that prefix counts as unset.
2. When unset: `git -C <main root> ls-remote --symref origin HEAD` (30 s); the line `ref: refs/heads/<b>\tHEAD` gives `<b>`. Nothing found: refuse ("could not find the default branch of origin").
3. `git -C <main root> fetch --no-tags --quiet origin +refs/heads/<b>:refs/remotes/origin/<b>` (30 s; the refspec of F18).
4. Fetch succeeded: `base_fetched = true`. Fetch failed and `git rev-parse --verify --quiet origin/<b>^{commit}` succeeds: `base_fetched = false`, warning (section 8.4). Fetch failed and no cached ref: refuse.
5. `base_commit` = `git rev-parse origin/<b>^{commit}`.

### 7.5 Creating the tree

1. Names: list `.worktrees/` folder names; list local branches with `git for-each-ref --format=%(refname:short) refs/heads/talaria/` and remote-tracking branches with `git for-each-ref --format=%(refname:short) refs/remotes/origin/talaria/` (with `origin/` removed), so a name `origin` already has is also taken and `P3-07`'s later push cannot collide. No network call. Then `pick_names`.
2. Ignore rule: `git -C <main root> check-ignore -q -- .worktrees/<dir_name>` (it works on a path that does not exist yet, G7). Exit 0: ignored, nothing to do. Exit 1: not ignored, so append the line `/.worktrees/` to `<git common dir>/info/exclude` (from `git rev-parse --git-common-dir`, made absolute against the main root; create `info/` when missing; add a newline first when the file does not end with one). Any other exit: refuse with git's error (G5); nothing has been written yet. Never edit `.gitignore` or any tracked file.
3. `mkdir -p <main root>/.worktrees`.
4. `git -C <main root> worktree add --no-track -b <branch> <main root>/.worktrees/<dir_name> <base_commit>`. Branching from the commit, not the ref name, pins exactly the commit that was reported. `--no-track` keeps the branch from tracking the trunk, so a plain `git push` never targets `main` (F19).
5. On failure: if the error says the branch or folder already exists (another launch won the race), list the names again, pick again once and retry once. Otherwise, or when the retry fails too, clean up: `git worktree remove --force <path>` (ignore errors), delete the folder if it still exists (`std::fs::remove_dir_all`, which never follows links, G6), `git worktree prune`, `git branch -D <branch>` if it exists. Refuse with git's first error line. On cancellation the same clean-up runs and the result is the interrupted text. The clean-up keeps the `/.worktrees/` line in `info/exclude` and an empty `.worktrees/` folder on purpose: both are untracked, local and idempotent, the next launch would write them again, and the line also keeps Hermes's own trees out of `git status`.

What a refusal leaves behind: every refusal in sections 7.3 and 7.4 and in steps 1 and 2 here writes nothing in the repository, except that a successful fetch (7.4 step 3) has updated `refs/remotes/origin/<b>`, which is what any `git fetch` does.
6. `.worktreeinclude` (section 7.6).
7. Record (section 7.7) and return the `WorktreeRecord`.

### 7.6 `.worktreeinclude`

Read `<main root>/.worktreeinclude` as UTF-8 (a leading byte-order mark is ignored); skip blank lines and lines starting with `#`. For each entry:

- Skip with one warning: an absolute entry; an entry containing a `..` component; an entry whose source (`<main root>/<entry>`) is itself a symbolic link (checked with `symlink_metadata`, so a tracked link pointing outside the repository is never copied or linked); an entry whose source, after `canonicalize`, is not under the canonical main root; an entry whose destination parent, after it is created and canonicalised, is not under the canonical tree.
- A regular file is copied (permissions kept, parent folders created).
- A directory is symlinked to its canonical source when the destination does not exist (no copy of large dependency folders). Edits inside it therefore reach the main checkout (decision 3.11); `--help` and `docs/configuration.md` say so in one sentence.
- Anything else is skipped. A failure on one entry is a warning, never a failed launch.

This matches Hermes (F18) and Claude Code's `.worktreeinclude`, with the extra symbolic-link rule.

### 7.7 The record

Written with `git -C <main root> config --local`, seven keys:

| Key | Value |
|---|---|
| `branch.<branch>.talaria-path` | the tree folder relative to the main root, `.worktrees/talaria-<slug>[-n]` |
| `branch.<branch>.talaria-base` | `origin/<b>` |
| `branch.<branch>.talaria-base-commit` | the 40-character commit |
| `branch.<branch>.talaria-base-fetched` | `true` or `false` |
| `branch.<branch>.talaria-profile` | the profile name |
| `branch.<branch>.talaria-created` | Unix seconds |
| `branch.<branch>.talaria-session` | the live `session_id` (section 5.6), added after the create |

`read_record` and `records_in` read them back (`git config --local --get-regexp '^branch\..*\.talaria-'`); `WorktreeRecord.path` is `main_root.join(talaria-path)`. A branch with no `talaria-path` key is not a record. A branch whose tree folder no longer exists is still returned, with the path as recorded (the consumer decides, `P3-07`).

### 7.8 Rollback

Only for a tree this launch created, and only when nothing was admitted. Guard: the path must be `<main root>/.worktrees/talaria-*` and the branch `talaria/*`, and the tree must have no commit beyond `base_commit` (`git rev-list --count <base_commit>..<branch>` is `0`); otherwise the rollback returns `Ok(Some(reason))` and the tree is kept (reason `it has commits beyond its base` or `it is not a tree this launch made`). Steps:

1. `git worktree remove --force <path>`.
2. Delete the folder if still present with `std::fs::remove_dir_all`, which removes symbolic links made by `.worktreeinclude` without following them (G6). Never a shell `rm`.
3. `git worktree prune`.
4. `git branch -D <branch>`, which also deletes the `branch.<branch>` record section (G4). There is no separate `--remove-section` step.

Never removes anything else. If a step fails, the rollback returns `Err(<git error>)` and the outcome reports the tree as kept with that reason.

## 8. Command line, messages, exit codes, output

### 8.1 Grammar

```text
talaria --bg [PROMPT] [--worktree | -w] [--name NAME] [--output-format text|json]
        [--model NAME] [--provider NAME] [--effort LEVEL] [--profile NAME] [--no-ensure] [--record PATH]
```

- `PROMPT` and standard input are assembled exactly as `P2-14`'s `assemble_prompt` does (same cap, same `NotUtf8` and `Empty` cases), with this unit's own messages.
- `--worktree` and `--name` are flags of `--bg` only. `--name` needs `--worktree`. `--name` takes a value; write `--name=--` or `--name '!!'` to pass a value that starts with `-` (clap reads `--name -- x` as a missing value and prints its own usage error, exit 2).
- `--model`, `--provider`, `--effort`, `--profile`, `--no-ensure` and `--record PATH` are `P1-12`'s flags with `P1-12`'s rules: `--effort` takes exactly `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`, `ultra` (`P1-12`'s `parse_effort`) and is sent as the create parameter `reasoning`; `--model` and `--provider` are passed through unchanged (Hermes does not check that a model exists, F31); a blank value is a usage error; `--record PATH` refuses an existing file.
- Saved defaults (`P2-06`, only if merged): flags win. `--model` or `--provider` given: the saved `model` and `provider` are not used; `--effort` given: the saved `effort` is not used (`P2-06` specification section 4.6, rule 1).
- `P2-14`'s parser rules, changed minimally: clap declares `PROMPT`, `--output-format` and `--timeout` as plain optional strings and `args.rs` validates them by hand in `validate_print_options`. This unit makes two changes there. (1) The checks of section 8.2 for `--bg`, `--worktree` and `--name` run first, before `P2-14`'s `-p` checks, so `talaria --worktree "x"` prints `talaria --worktree needs --bg.`, not `P2-14`'s text. (2) With `--bg`, a positional prompt and `--output-format` are accepted instead of giving `<option> only works with -p.`; `--timeout` stays `-p`-only.
- If `-w`, `--name` or `--bg` is already taken in the merged `Cli`, stop (stop condition).

### 8.3 Exit codes

| Code | `status` in JSON | Meaning |
|---|---|---|
| 0 | `launched` | Hermes admitted the prompt; the session runs in the gateway. |
| 1 | `unknown` | The submit was sent and its reply was lost, unreadable or error 5001; the prompt may be running. The tree is kept. |
| 2 | (no JSON) | Usage error. |
| 4 | `not_started` | Nothing was admitted: no gateway, profile not served, `tui`, `cwd` or a sent option not offered, git or worktree failure, create refused, lost or unreadable, folder not confirmed, submit refused or never written, voice stop phrase. | 130 | `interrupted` | SIGINT, SIGTERM or SIGHUP arrived while `submit_sent()` was false (section 6.2); any tree was removed (or kept, as above) and any created session closed with `launch_abandoned`. A signal after that is ignored, and the launch's own code stands. |

### 8.4 Text output

Success (standard output):

```text
Launched session <stored id> in profile fixture.
Folder: <cwd>
Worktree: branch talaria/<slug> from origin/main at <12-character commit>
Follow it: talaria fleet list --profile fixture
Open it: talaria --resume <stored id> --profile fixture
```

The `Worktree:` line appears only for worktree launches. ` --profile <name>` is left out of both hint lines when the profile is `default`. The stored id falls back to `session_id` when `stored_session_id` is absent (section 5.6). Paths and ids pass `P1-06`'s `sanitize`.

Warnings (standard error, before the success text): `talaria: warning: could not fetch origin/<b> (<git error>); branched from the copy fetched earlier at <12-character commit>.` and `talaria: warning: .worktreeinclude entry "<entry>" was skipped (<reason>).` and `talaria: warning: could not record the session id in git config (<git error>).`

| voice stop | `Hermes took the prompt as a voice stop phrase and started nothing.` | `Rephrase the prompt.` |
| unknown (submit reply lost, unreadable or 5001) | `the prompt may have started, but the reply from Hermes was lost.` | `Check with talaria fleet list[ --profile <p>] before launching it again; the session is <id>.` |
| interrupted | `stopped before the prompt was sent; nothing was started.` | `Run the command again when ready.` |

Kept tree (any not-started or interrupted case where the rollback guard kept the tree): the next step's own text is followed by ` The worktree <path> was kept: <reason>.`, and the clause `and the worktree removed` is left out.

Connection failures (no gateway, profile not served) keep `P1-12`'s `LaunchFailure` texts unchanged and map to exit 4.

Quit line (fleet view only; standard error, after the terminal is restored, one per launch `LaunchService::shutdown` returned): `talaria: a background launch was still starting when Talaria quit; check talaria fleet list and .worktrees/.`

### 8.5 JSON output (`talaria.bg.v1`, documented in `docs/formats/bg-result-v1.md`)

One line on standard output, for every exit except 2:

```json
{"format":"talaria.bg.v1","status":"launched","session_id":"<live id>","stored_session_id":"<stored id>","profile":"fixture","admission_id":"<aid>","admission_status":"queued","model":"<model or null>","cwd":"<path>","worktree":{"path":"<path>","branch":"talaria/<slug>","base_ref":"origin/main","base_commit":"<40 hex>","base_fetched":true},"warnings":[],"error":null}
```

For other statuses, `session_id` and `stored_session_id` are set when known (else `null`), `admission_id` and `admission_status` are `null`, `worktree` is the kept tree (`unknown`, or a tree the rollback guard kept) or `null`, and `error` is `{"what":"...","next_step":"..."}`. Keys appear in exactly this order. Warnings are also printed on standard error in JSON mode.

## 9. The launch dialog

### 9.1 Layout

The box is `min(screen width − 4, 120)` columns wide and is placed by `LaunchDialog::area`, centred: `x = (W − w) / 2` (column 2 at 80 columns, column 20 at 160), on row 2. Its height is 4 (top border, the line above the hints, the hint line, bottom border) plus the Prompt field's visible lines (1 to 6) plus 3 (Profile, Folder, Model) plus 1 in worktree mode. Each field row is: one space, the label padded to 9 columns, `› ` on the focused field or two spaces otherwise, then the value. The Profile row ends with `← → to change` one column before the right border. The title is `New background session` (plain) or `New background session in a worktree` (worktree). This is the exact 80-by-24 frame of test 41 in worktree mode with the Prompt field focused (76 columns, every line checked):

```text
╭─ New background session in a worktree ───────────────────────────────────╮
│ Prompt   › fix the flaky test in tests/net.rs                            │
│ Profile    fixture                                         ← → to change │
│ Folder     ~/proj                                                        │
│ Model      profile default                                               │
│ Worktree   fix-the-flaky-test-in-tests-net-rs                            │
│                                                                          │
│ enter launch · tab next · shift+tab back · esc close                     │
╰──────────────────────────────────────────────────────────────────────────╯
```

At 160 by 48 the same rules give a 120-column box at column 20. The test author draws each expected frame by hand from these rules (the 80-column one above is exact) and a reviewer checks it once; snapshots are never generated from the code under test.

- The `Worktree` row appears only in worktree mode (`w`). Its value is the editable worktree name (the slug, without the `talaria-` or `talaria/` prefix); while untouched it follows the prompt's slug live.
- The Prompt field behaves as `P1-08`'s composer (multi-line; its newline key inserts a line; paste keeps text). At most 6 lines are shown; the field scrolls.
- Profile: Left and Right cycle through the served profiles in the order the fleet snapshot lists them. With a profile-only link it shows the foreground profile and the note `only this profile: the gateway refused a host-scoped ticket`.
- Folder: a single-line text field; `~` expands to the home folder on launch; default is the foreground session's folder (`P1-12`'s session info), else Talaria's launch folder. In worktree mode it names the repository.
- Model: a single-line text field; empty shows `DialogDefaults.model_placeholder` in a dim style and sends no `model` of its own: `profile default`, or `saved default: <model>` when `P2-06` is merged and a saved default model applies (it is then sent, section 8.1).
- All user and Hermes text is drawn literally through `P1-06`'s `sanitize` (control and bidirectional characters become visible stand-ins).

### 9.2 Keys

While the dialog is open it receives every key and paste first (section 4.1); `n` and `w` typed into a field are text.

| Key | Effect |
|---|---|
| Enter | Validate, then launch (section 9.3). In the Prompt field, Enter launches; the composer's newline key inserts a line. |
| Tab, Shift+Tab | Next or previous field (Prompt, Profile, Folder, Model, Worktree). |
| Left, Right on Profile | Previous or next profile. |
| Esc | Close the dialog. The prompt text is kept in memory as the draft for the next `n` or `w` in this Talaria process. While launching, Esc closes the dialog and the launch continues. The fleet view stays open. |

### 9.3 States

| State | What is shown |
|---|---|
| Editing | The fields and the key hint line. |
| Invalid | One red line in place of the blank line above the key hints: `Write a prompt first.`, `The folder does not exist: <path>.`, `The folder must be an absolute path or start with ~.`, `The worktree name needs at least one ASCII letter or digit.` Focus moves to the field. Nothing is sent. |
| Busy | `Three launches from this Talaria are still starting; wait for one to finish.` Nothing is sent. The limit counts launches of this Talaria process only. |
| Launching | The key hint line becomes `<spinner> <stage text> <n>s` with elapsed whole seconds. Stage texts: `Connecting` gives `Connecting to Hermes…`, `Fetching` gives `Fetching origin…`, `CreatingWorktree` gives `Creating worktree…`, `CreatingSession` gives `Starting session…`, `Submitting` gives `Sending prompt…`. Fields are read-only. |
| Failed | The dialog stays open with every field kept and the error in red in place of the blank line: `Could not launch: <what>`, and `<next step>` on the hint line until the next key. |
| Done | The dialog closes; a notice is added (section 9.4). The fleet view stays open. |

### 9.4 Notices

On success: `Launched in <profile>: "<prompt summary>"` plus ` (worktree talaria/<slug>)` for worktree launches. The prompt summary is the prompt after `sanitize`, with every run of line breaks and tabs replaced by one space, cut to its first 60 Unicode scalar values (Rust `char`s), with `…` added when cut. On failure after the dialog was dismissed: `Background launch failed: <what>`. Unknown: `Background launch may have started (<id>); check the fleet before launching again.` Warnings are added as separate notices. Notices use `P2-03`'s `Event::Notice` with an info, warning or error kind.

## 11. Edge cases

| # | Case | Behaviour |
|---|---|---|
| E1 | Prompt is only whitespace | Usage error (command line) or `Write a prompt first.` (dialog). |
| E2 | Launch folder is a linked worktree of the repository | The tree goes under the main root's `.worktrees/`, not inside the linked worktree. |
| E3 | Launch folder is a subfolder of the repository | The session's `cwd` is the new tree's root, not the matching subfolder. |
| E4 | Local `main` is behind `origin/main` | The tree starts at `origin/main` (test 18, UAT-2). |
| E5 | The operator has uncommitted changes in the main checkout | Not carried into the tree (by design; the help text says so). |

| E7 | `.worktrees/` already ignored by `.gitignore` | `info/exclude` is not touched. |
| E8 | `.worktreeinclude` lists `../secrets`, an absolute path, or a tracked symbolic link | Skipped with a warning. |
| E9 | Origin requires credentials that need a prompt | git fails fast (no prompt); cached ref used with a warning, or refused. |
| E10 | `--bg` from a folder Hermes's host cannot see (a different machine's path) | `session.create` refuses field `cwd`; `NotStarted`. |
| E11 | Create reply lost | One identical retry on the same open connection (F8); a second loss, or a dropped connection, is `NotStarted` with the "did not confirm that the session was created" text (decision 3.6). |
| E12 | Submit reply lost or unreadable | `Unknown`, exit 1, tree kept, no end reason. |
| E13 | Profile not served by the gateway | `P1-12`'s message (command line); the dialog never offers it. |

| E27 | Talaria quits while fleet launches are starting | `LaunchService::shutdown` cancels them and waits at most 5 s; any still running print the quit line (section 6.2). |
| E28 | The agent edits a file inside a folder listed in `.worktreeinclude` | The edit reaches the main checkout through the link (decision 3.11); documented, not guarded. |
| E29 | `talaria --bg` with no gateway running | The command line may start it through `P1-12`'s ensure rule unless `--no-ensure`; a fleet launch never starts one (`EnsurePolicy::Never`). |
