# SEAT-ACC: Live proof: a lead sends a prompt to a Talaria seat, waits for it and reads its state

Status: `proposed`. The GitHub issue for this unit is the contract; this document is its reference specification. If they disagree, the issue wins and the disagreement is reported on the issue.

How to use this document. Read the issue for REQ-1 through REQ-7, UAT-1 through UAT-4, and the acceptance checks. This page maps the code those rows stand next to, with `path:line`. It does not restate a requirement or a test. The issue states the sender wrapper, the `alt+enter` chord, the byte-log capture, the event `S7` watches, the operator comments, and the five header lines.

## What is already in the tree

The main command accepts the launch flags the issue names. `crates/talaria-cli/src/args.rs:45` is `--model`, `:47` is `--provider`, and `:51` is `--profile` with default `default`. The guide's first session (`docs/guide.md:38`) shows `talaria`, `talaria -c`, and `talaria --resume <id>` only. The flags are on this parser.

Startup probing is `PROBE_QUERY` at `crates/talaria-tui/src/terminal.rs:80`. Those bytes are cursor position, keyboard flags, synchronized output, OSC 11, OSC 10, and device attributes. They do not include `7501`. `parse_probe_reply` is at `terminal.rs:167`. The issue's probe bytes are settled decision 1. A terminal that understands the probe answers `ESC ]7501;? : states=<comma list> : kinds=<comma list>`, ended by BEL (the bell byte) or by ST (`ESC \`). A status record is `ESC ]7501;state=<word>:app=talaria`, with `:kind=<kind>` added only for `blocked`, ended by BEL; the clear record is `ESC ]7501;state=clear BEL`. [#534](https://github.com/infiquetra/talaria/issues/534) (`SEAT-2`) adds that probe, and adds the example `seat_probe`. Its issue (REQ-8 of [#534](https://github.com/infiquetra/talaria/issues/534) (`SEAT-2`)) says what the example writes: when the terminal answered, one standard error line per record written, two seconds apart, `seat-probe` plus the state word in those bytes and, for blocked, the kind word when one was written, then `seat-probe clear`; when `probe.status` is `None`, no records, nothing on standard error, exit 0. Which state lines appear depends on the states and kinds the terminal's answer lists. Neither name is in this tree. Both are on `main` before the issue starts.

The old reporter is `HerdrReporter::report` at `crates/talaria-app/src/comforts/herdr.rs:90`. It sends `idle`, `working`, or `blocked` (`herdr.rs:92`). `TuiScreen::report_pane` is at `crates/talaria-cli/src/run.rs:4742`. [#535](https://github.com/infiquetra/talaria/issues/535) (`SEAT-3`) adds `AppEffect::ReportSeat(SeatState)` and `TuiScreen::report_seat`. Those names are not in this tree. They are on `main` before the issue starts. This proof does not edit `herdr.rs`.

`[herdr] report_state` defaults to true (`docs/configuration.md:869`, sample at `:354`). The sentence at `docs/configuration.md:414` still says the setting reports blocked, working, or idle. [#535](https://github.com/infiquetra/talaria/issues/535) (`SEAT-3`) updates that sentence. This issue does not.

`hc send` is how the proof submits a prompt. REQ-2 makes up to 20 status reads (`hc get` filtered to two lines), half a second apart, after that call, and starts `hc wait` at the first `working` read. The preconditions build the candidate at `/tmp/talaria-<commit>/talaria` and start Talaria in `/tmp/talaria-<commit>/run`. Pasted command output passes through `scrub`, defined in the candidate checkout so that its first rule replaces the checkout's own path with `<checkout>`; a cargo line that shows the checkout path then passes the record's path check. An operator comment is not scrubbed, so it never holds raw cargo output. The seat shell is a program herdr core runs, so it holds `HC_TERMINAL_ID` and `HC_SCOPE`; Talaria inherits them and keeps them, since it reports its state through that terminal. Once the seat reports a state, a plain `hc send` from another agent arrives with the wrapper the issue expects in the transcript. A slash command sent that way is prose. For the same reason REQ-2 sends shell commands into the seat with `HC_TERMINAL_ID` and `HC_SCOPE` removed from that one call, so the shell never receives the wrapper. UAT-4 types its `/quit` through tmux or a plain terminal, not through `hc`. A typed burst is a different path. `crates/talaria-tui/src/composer/paste_burst.rs:6` says an Enter less than 120 ms after the last burst event is a line break, not a submit. The window constant is `ENTER_SUPPRESS_WINDOW` at `paste_burst.rs:18`. A plain `hc send` is a bracketed paste. `handle_paste` (`composer/mod.rs:251`) resets the burst (`paste_burst.rs:157`), so the Enter that follows submits. UAT-4 waits at least 300 ms before Enter so that Enter submits, because that row types characters.

## Alerts and the pin

Desktop notification kinds default to needs-you, done, and failed (`crates/talaria-app/src/config.rs:290`). The bell default is needs-you and failed (`config.rs:289`). `TuiScreen::alert` (`run.rs:4733`) asks for a BEL and, when desktop is on, Operating System Command 9. The issue's `S7` is the operator watching one turn that ends normally while the Talaria terminal is not the focused terminal in the Herdr window. The operator records the Herdr sound and the desktop alert in the result cell. The two version lines [#541](https://github.com/infiquetra/talaria/issues/541) (`REL-081`) copies are the `Herdr version:` and `hc version:` header lines of `seat.md`. It copies everything after the label's colon and the one space, to the end of the line, unchanged, number included. If either line is missing it stops and reports, and never runs the programs itself. No other line of `seat.md`, including the evidence under `## S7`, begins with either label. There is no pass rule.

`crates/hermes-contract/PINNED` line 1 is `tag=v0.22.4`. The record's Hermes line is whatever the gateway reports on the run. Re-verify `status.state` and `status.kind` on the `hc` used for that run. The status record and the clear record written above both contain the characters `]7501;state=`. The bytes hold no spaces: `ESC` is one byte, followed directly by `]7501;`. Settled decision 4 writes it only after a status record was written, so a terminal that never answered the probe never receives it. UAT-4 passes when the log has no `]7501;state=`. The probe in settled decision 1 is `]7501;?`, so that text can appear in a log that still passes.

## The doctor and the gateway

The plain output of `talaria doctor` has no `running:` line. `talaria doctor` exits 1 only when a row fails (`exit_code` at `crates/talaria-core/src/doctor.rs:958`); a warning still exits 0. A gateway older than `MIN_HERMES` (0.22.3, `doctor.rs:8`) fails its row, so it stops the run. The Hermes version row keeps `running: {v} at {sha}` and `built for: {tag} ({pin})` as details (`doctor.rs:444-445`). `render_text` (`doctor.rs:900`) prints a detail only when it starts with `also:` (`doctor.rs:921`), so the plain output has no `running:` line. `render_json` (`doctor.rs:935`) keeps every detail, which is why the issue reads the version from `--json`. When the gateway reports no version, `{v}` is `unknown` (`doctor.rs:387`).

## What `hc get --json` prints

Measured on hc 0.1.20 and published with the reference page `docs/handoff/2026-11-11-v0-9/hc-facts.md`. Piped output is one compact JSON object. `status` is a top-level key: `null` for a shell at its prompt (`hc-recordings/get_shell.json`), `{"app":"talaria","state":"idle"}` after an idle record (`get_idle.json`), and `{"app":"talaria","kind":"permission","state":"blocked"}` after a blocked record (`get_blocked.json`). `reported` is a top-level boolean: `false` in `get_shell.json`, `true` in `get_idle.json` and `get_blocked.json`. The reference page's table does not name `reported`; the recordings show it. The whole reply also holds folders (`cwd` and `foreground.cwd`, both `/tmp/scratch` in `get_idle.json`), which can be under a home folder. So the issue never pastes a whole reply. Its status read, `hc get <address> --json | grep -oE '"reported":(true|false)|"status":(null|\{[^}]*\})'`, prints exactly two lines: `"reported":true` and `"status":{"app":"talaria","state":"idle"}` for `get_idle.json`, `"reported":false` and `"status":null` for `get_shell.json`, `"reported":true` and `"status":{"app":"talaria","kind":"permission","state":"blocked"}` for `get_blocked.json`. The Verification block's `grep -F '"reported":true'` matches the first line of any status read made after the first status record.

## What `hc wait` prints

Measured on hc 0.1.20 (`hc-facts.md`, section "Waiting"). `hc wait <address>` always exits 0 and prints one JSON line. When the state leaves `working` it prints `"ended":true`, `"reason":"status"` and `"status"` holding the new state: `done` (`wait_done.json`), `blocked` (`wait_blocked.json`), `idle` (`wait_idle.json`) or `error` (`wait_error.json`). It prints the `done` reply at once when the state is already `done` (`wait_already_done.json`); a state that is already `blocked` was not measured, which is why UAT-2 skips `hc wait` when a status read shows `blocked` first. It gives up after 180 seconds by default with `"ended":false` and `"reason":"timeout"` (`wait_timeout.json`, measured with `--timeout 3`). A message waiting for the caller ends it at once with `"reason":"message"` (`wait_message.json`), but only when the caller's environment holds `HC_TERMINAL_ID`; that is why the issue runs it as `env -u HC_TERMINAL_ID -u HC_SCOPE hc wait <address>`.
