# REL-081: Release Talaria v0.8.1

Status: `proposed`. The GitHub issue for this unit is the contract; this document is its reference specification. If they disagree, the issue wins and the disagreement is reported on the issue.

How to use this document: start from the issue. This file is the map of what the repository does today, with line numbers, and the checks the existing release-metadata test already applies to any final version. It does not restate a requirement or a test. Those are REQ-1 through REQ-6 and the two named tests.

## What the version is today

The workspace version is one line, `version = "0.8.0"`, in `[workspace.package]` at `Cargo.toml:20`. `crates/talaria-cli/src/args.rs:32-34` sets clap's `version` with no explicit string, so the package version is the workspace version. `args.rs:128` formats a version request as `talaria {version}` plus a newline and exit 0.

`CHANGELOG.md:11` is `## [Unreleased]`. `CHANGELOG.md:13` is `## [0.8.0] — 2026-11-05`. `CHANGELOG.md:649` points Unreleased at `compare/v0.8.0...HEAD`. There is no `docs/release-notes/v0.8.1.md`. The 0.8.0 notes are `docs/release-notes/v0.8.0.md`, and their level-two headings are the eight names REQ-3 keeps.

`Cargo.lock` repeats `version = "0.8.0"` for path packages, which have no `source` line (for example `hermes-client` at `Cargo.lock:1229-1230` and `talaria-app` at `Cargo.lock:3322-3323`). The same version text also appears on registry packages that do have a `source` line (for example `bit-set` at `Cargo.lock:253-255`). REQ-1 changes only the blocks with no `source` line.

## What the metadata test already enforces

`crates/talaria-cli/tests/release_metadata.rs::workspace_version_has_one_source` (`release_metadata.rs:7`) asserts the workspace version equals `0.8.0` at `release_metadata.rs:37-41`, and that every member inherits `version.workspace = true` once. Its steps today, in order, which test 1 of the issue leaves as they are:

- It calls `root()` (`release_metadata.rs:573`), which canonicalizes `CARGO_MANIFEST_DIR` joined with `../..`, then `read(&root, "Cargo.toml")` (`release_metadata.rs:580`).
- After the line whose trim is `[workspace.package]`, and before the next line whose trim starts with `[`, it counts non-comment lines whose trim starts with `version = "`, and asserts the count is 1. A second line uses `blame` for `a second workspace version line`; a count of zero uses `blame` on line 1 for `workspace package has no version line` (`release_metadata.rs:8-36`).
- It calls `workspace_version(&root)` (`release_metadata.rs:615`), which reads `Cargo.toml` the same way and returns the quoted text of that version line, and asserts it equals the expected version (`release_metadata.rs:37-42`).
- It calls `member_manifests(&root)` (`release_metadata.rs:596`), which lists each `Cargo.toml` one directory under `crates/` or `tools/` and sorts them. For each it asserts a `[package]` table, no non-comment line in it whose trim starts with `version = "`, and `version.workspace = true` once.

`final_version_requires_changelog_section` (`release_metadata.rs:260`) requires, for a final version: an empty Unreleased section (`release_metadata.rs:275-284`), a first dated heading that starts with `## [{version}] ` (`release_metadata.rs:289-297`), one each of `### Added`, `### Changed` and `### Removed` with a bullet (`release_metadata.rs:298-331`), the notes URL for that version (`release_metadata.rs:333-346`), and the tag reference line (`release_metadata.rs:347-353`).

`changelog_shape` (`release_metadata.rs:137`) requires Unreleased first, dated headings of the form version, a dash, and `YYYY-MM-DD`, versions strictly descending, dates not increasing down the file, and the Unreleased compare link ending in `compare/v{newest}...HEAD` (`release_metadata.rs:215-224`). The 0.8.0 date is 2026-11-05, so a 0.8.1 date before that fails this test.

`final_version_requires_release_notes` (`release_metadata.rs:357`) requires the notes file, the title `# Talaria v{version}` (`release_metadata.rs:377-381`), these eight headings and no others (`release_metadata.rs:384-402`):

- `## Read this part first`
- `## What is new`
- `## What changed from 0.6.5`
- `## Install`
- `## Works with Hermes`
- `## Staying on 0.6.5`
- `## Known limits`
- `## What was checked`

It also requires the pin tag text (`release_metadata.rs:404-409`), the phrases `cargo build --release`, `crates.io`, `npm` and `Python Package Index` (`release_metadata.rs:410-421`), the migration URL for that version (`release_metadata.rs:422-429`), and at most 400 lines (`release_metadata.rs:461-465`). The issue-number lists at `release_metadata.rs:430-460` apply only when the version is `0.7.1` or `0.8.0`.

`release_notes_flags_exist_in_help` (`release_metadata.rs:485`) runs `talaria --help` and requires every flag on a `bash` or `sh` line that starts with `talaria` or `target/release/talaria` to be a whole token in that help (`release_metadata.rs:1097-1130`). `release_links_point_at_real_files` (`release_metadata.rs:469`) resolves `blob/v{version}/` links against files in the working tree. `release_text_is_public_safe` (`release_metadata.rs:544`) rejects home paths, attribution fragments, a planning-code shape, and the unattended flag set true, in the changelog section and the notes (`release_metadata.rs:1147-1199`). `no_planned_v080_markers_remain_in_configuration_doc` (`release_metadata.rs:88`) rejects the text `Planned for v0.8.0` in `docs/configuration.md`. A search of the tree for `Planned for v0.8` hits only that test.

`scan_public` treats `REL-` plus two digits as a planning code (`release_metadata.rs:1243-1251`). The notes and the changelog must not contain that code.

## The release runner

`tools/release/rc.sh:5` exits 2 on `rc_error`. A dirty tree hits that at `rc.sh:262` with the text `the working tree is not clean`. Class words are `RC_RESULT`, `RC_RESULT_CI`, `RC_RESULT_LIVE` and `RC_RESULT_OPERATOR` (`rc.sh:268-271`). A partial selection uses `RC_PARTIAL` (`rc.sh:265`). Exit 0 is printed only when every selected required gate passed (`rc.sh:354-356`). A required skip is counted and the run exits 1 (`rc.sh:299-308` and `rc.sh:358`).

`tools/release/gates.tsv` has a header and 26 gates. `contract-latest-drift` at `gates.tsv:12` is the required value `no`. The other 25 are `yes`. `live-pause` at `gates.tsv:27` requires exit 0 and greps for `LIVE_SUBAGENT_RESULT: PASSED`. `tools/release/README.md` says only the full `RC_RESULT` is release evidence, and that an informational result belongs with the release notes. The 0.8.0 notes say a prepared notes file does not itself establish a completed gate (`docs/release-notes/v0.8.0.md:120-124`). `tools/release/README.md:24` says what `allowed-diff` accepts: it exits 0 only when the candidate is an ancestor of the merge commit and the two differ in nothing but documentation and version text (in the lockfile, only version edits in local package blocks without a `source` line). The issue's REQ-3 says how lines for `Known limits` are proposed. REQ-4 names the builder's `--class ci` run, the operator's full run, the command that reads the Hermes version and where the informational result is written. REQ-5 names `allowed-diff` before the tag.

The release-binary gates build and run `${CARGO_TARGET_DIR:-target}/release/talaria` (for example `gates.tsv:19`), so after a full run that binary is the candidate build; REQ-4 reads the Hermes version with it. The `running:` text is built at `crates/talaria-core/src/doctor.rs:444` from the version and commit the gateway reports, so it names the gateway, not Talaria.

`tools/release/README.md` also says a full run needs the operator's authorization for the pause gate, and that the runner does not start or reconfigure Hermes except for that authorized gate. Live smoke is started from a Herdr pane. The smoke gate sets `TALARIA_LIVE_REQUIRE=1` (`gates.tsv:19`).

## Versions the notes must copy

The acceptance index for this release is `docs/acceptance/v0.8.1/seat.md`, owned by `SEAT-ACC`. The guide page is `docs/herdr-seat.md`, owned by `SEAT-5`. Neither path is in the tree at the commit this specification was written against. The older acceptance header, `docs/acceptance/v0.7.0/phase-1.md`, records `Herdr: herdr 0.9.4` and does not record an `hc` line. The smoke fixture `tools/smoke/tests/fixtures/herdr/version.txt` is the single line `herdr 0.9.4`. Neither of those is the live run. REQ-3 copies tokens from `docs/acceptance/v0.8.1/seat.md` only. That file holds one `Herdr version:` line and one `hc version:` line. The token is the whole text after the label's colon and the one space that follows it, through the end of the line, unchanged. For Herdr that text is the whole line `herdr-app --version` printed. For `hc` it is the whole line `hc --version` printed. It is not cut down to the number. If either line is missing, the issue says to stop and report, and not to run either program to fill the gap.

`crates/talaria-app/src/comforts/herdr.rs:96-98` builds the arguments `pane` and `report-agent`. That is the old reporter the changelog's Changed bullet names. The issue does not change the file, and `Known limits` stays the four v0.8.0 bullets unless the operator edits it.

This issue does not edit `docs/engineering-journal/DECISIONS.md`. A `docs/engineering-journal/LEARNINGS.md` entry is only for a required gate whose failure message does not name the cause.

REQ-2 checks the changelog date with `git show -s --format=%cs HEAD` after the second commit. The heading uses the same dash as `CHANGELOG.md:13`, which is `## [0.8.0] — 2026-11-05`.

The wire format was exercised with `hc` 0.1.20 on 2026-11-11, outside Talaria. That observation is not the release live run. Use it only when the acceptance evidence contains the same token.
